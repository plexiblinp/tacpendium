### 実装ガイドライン

- **専用ヘルパ経由**: 各機能から直接 `localStorage` 等を呼ばず、`web/src/lib/browser-storage.ts` 経由で使用する
- **try-catch 必須**: 容量制限・プライベートブラウジング等で書込が失敗してもアプリが落ちない設計とする
- **キーバージョニング**: 全キーに `-v1` 等の suffix を付与し、将来の構造変更時は新バージョンキーを採用して旧データは無視する
- **JSON シリアライズ**: 構造化データは `JSON.stringify` / `JSON.parse` で扱う。parse 失敗時は未保存扱い

## 1.5 `queryKey` の正本

**TanStack Query の `queryKey` は `web/src/lib/query-keys.ts` の `queryKeys` ファクトリが正本である**（M24-08 / `CO-009` / `CHANGE-148`）。**画面・フックの側で配列リテラルを書かないこと。**

**なぜ**: キーを書く側と `invalidateQueries` を書く側は別ファイルに分かれるため、**片方だけ直すと静かにキャッシュが効かなくなる**。TanStack の既定は前方一致であり、当たらなくなっても例外は出ず、画面が「更新されない」だけになる。着手前の実測では本番 58 件の `invalidateQueries` のうち **39 件が前方一致に依存**し、当たりを守る観測は **2/58 ≒ 3.4%** しか無かった。

**検査**:

- `web/src/lib/query-keys.convention.test.ts` — 正本の外に配列リテラルを書かせない
- `web/src/lib/query-keys.invalidation.test.ts` — **実物の `QueryClient` で「どの invalidate がどの query にちょうど当たるか」を表で固定する。** `queryKeys` へキーを足したらこの表にも載せること（載せ忘れは同ファイルの「網羅」テストが赤で知らせる）

**★平坦化していない箇所が 3 件ある**（`tags` の `partialDeepEqual` 依存 ／ `setupCandidates` の同一ルート共有 ／ `combo.recipe` の前方一致依存＝契約 F-2 の FE 側の実体）。**理由は `query-keys.ts` の冒頭に逐語で書いてある。「統一漏れ」と読んで平坦化しないこと**——平坦化すると matching の意味が変わり、静かに壊れる。

## 2. コンボ型の 3 分岐（一覧用 / 詳細用 / 編集用）

フロントエンドは `ComboSummary`（一覧用、`?:` でオプショナル表現）、`ComboDetail`（詳細表示用、`ComboSummary` を継承して `steps?` / `validations?` / `setups?` を追加）、`Combo`（編集用、`| null` を許容してエディタ状態の未入力を表現）の **3 つの interface** を別建てで定義している。

**バックエンド `ComboResponse` は一覧・詳細で同一型のため、新規フィールド追加時は該当する全 interface への追加が必要。** `Combo`（編集用）への追加を忘れると、コンボ編集画面で型エラーまたは表示崩れが発生する。

型定義ファイル（`web/src/features/combo/types.ts` 等）の冒頭には次のコメントを置くこと:

```ts
// 注: ComboSummary と ComboDetail / Combo は別 interface だが、バックエンド ComboResponse は同一型。
// フィールド追加時は該当するすべてに追加すること。
```

---

## 3. フロントの型検査が見ている範囲

`web/tsconfig.json` の `include` は `["src", "vite.config.ts"]` である。**⇒ 型検査が見るのは `web/src/` 配下だけであり、`web/e2e/` の spec と `playwright.config.ts` はどの経路でも型検査されない**（`SUPP-001` §4.5 の「積み残し」がこれ）。**★E2E spec の型エラーはビルドでは出ず、Playwright が実行するまで分からない。**

**★型検査の守備範囲は `pnpm build` と `pnpm exec tsc --noEmit -p tsconfig.json` で同一である。** 前者は `tsc -b && vite build`、`lint` は `tsc --noEmit` であり、いずれも同じ `include` を読む。**`src/` 配下のテストファイルの型エラーは、どちらでも赤くなる**（M24-09d で実測。`tsconfig.tsbuildinfo` の有無と実行順を変えた 4 通りで確認した）。

**★型検査の抜けを疑ったら、対象ファイルが `include` に入っているかを先に確かめること**——`cd web && pnpm exec tsc -p tsconfig.json --listFilesOnly` が、実際に読んでいるファイルを全数で出す。
