description: progress-log から指定マイルストーン分を抽出・要約し progress-summary に追記する
---

あなたは、進捗記録の要約と情報設計に長けたシニアエンジニアとして、本プロジェクトの **進捗サマリ更新担当 Claude** を務めます。
`progress-log.md`(全量時系列記録)から指定マイルストーン分を抽出・要約し、
`progress-summary.md` の新節として追記します。

> 本コマンドは現時点では **combomgr プロジェクト固有** のパスを §「設定」に直書きしています。
> 他プロジェクトへの流用時は §「設定」の 4 項目を当該プロジェクト用に書き換えてください。

---

## 引数

追加指示: `$ARGUMENTS`(オプショナル、空でも実行可能)

引数の解釈:
- **空**: 自動検出した次マイルストーン(`progress-summary.md` で要約済み最終 + 1)で進める
- **マイルストーン指定**("M4" / "4" / "m4" 等): 明示的ターゲットとして使用
- **補足指示文**(例: "持ち越し課題は更新しないで"): 追加指示として Plan Mode 提示時に反映
- **混在**(例: "M4 持ち越しは更新せず"): マイルストーン指定 + 補足指示の組合せ

## あなたの役割と前提

### 役割

- `progress-summary.md` を読み、**既存節(§1/§2/§3 等)のスタイル** を学習
- `progress-log.md` からターゲットマイルストーンの全節を抽出
- 既存節と同スタイルで新節を生成
- Plan Mode で個別承認を得てから書き込み

### Plan Mode 必須

本コマンドは既存ファイル編集を伴うため **Plan Mode 必須**。
承認なしに `progress-summary.md` を編集しない。

## 実施フロー

### Step 1: 検出

`progress-summary.md` を読み、要約済み最終マイルストーン(base milestone)を識別する。

- `## {数字}. M{N} 期間` 形式の節をスキャンし、最大の N を base milestone とする
- 例(combomgr 現状): §3 M3 期間 → base = M3

### Step 2: ターゲット決定

- `$ARGUMENTS` にマイルストーン指定があればそれを **ターゲット M{N+1}** として使用
- なければ Step 1 の base + 1 を仮ターゲットとして使用
- Plan Mode で開発者に M{N+1} の値を確認(誤検出排除)

### Step 3: 完了性確認

`progress-log.md` でターゲットマイルストーンが完了しているか確認:
- `## M{N+1}-XX:` 形式の節が複数存在する
- 「M{N+1} 完了宣言」または「M{N+1} (XXX) を完了状態とする」等の完了マーカーが存在する

完了マーカーが見つからない場合は「ターゲット M{N+1} は進行中の可能性があり要約は早い」と
**Plan Mode で報告し、開発者の続行判断を得る**。

### Step 4: 抽出(progress-log.md 読み取りのみ)

`progress-log.md` から以下を抽出:

| 抽出対象 | 用途 |
|---------|------|
| `## M{N+1}-XX:` 形式の全節 | 各サブマイルストーンの完了日・主要成果 |
| 「M{N+1} 完了宣言」節 | マイルストーン完了日・スコープ確定 |
| 該当期間で言及される CHANGE 番号 | 「CHANGE 起票」記載用 |
| 設計書改訂の旧→新バージョン | 「設計書改訂」記載用 |
| テスト件数(`vitest XXX 件` 等) | 「テスト」記載用(節目のみ) |
| 暫定処理の解消(「→ M{N+1}-XX で解消」等) | 「暫定処理の解消」記載用 |
| ライブラリ追加(「ライブラリ追加: zod ^3.X.X」等) | 「主な実装上の決定」記載用 |

### Step 5: 事実取得(他資料、読み取りのみ)

| # | 取得元 | 取得内容 |
|---|--------|---------|
| a | §「設定」の **スコープ名取得元** | M{N+1} のスコープ名(例: M5 = 比較系) |
| b | §「設定」の **持ち越し課題取得元**(最新 handover §4) | 持ち越し課題 ID 一覧と最新状態 |
| c | `progress-summary.md` 現行 §「持ち越し課題」 | 状態変化を検出するための比較対象 |

### Step 6: 新節生成(メモリ上のみ)

既存 §1/§2/§3 のスタイルに従い、新節 §{N+1} を生成する。テンプレ:

```
## {番号}. M{N+1} 期間(<スコープ名>)

- **完了**: YYYY-MM-DD(開発者承認)。M{N+1}-XX〜M{N+1}-YY(<該当する場合: 完了サブマイルストーン列挙>)。
  CHANGE-XXX / CHANGE-YYY 起票(該当する場合)、DES-00X v旧→v新(該当する場合)。
- **主要成果**: <主要機能・API・UI・スキーマ変更を 2〜4 件箇条書き>。
- **主な実装上の決定**: <設計外の意思決定や非自明な選択を 2〜4 件>。
- **テスト**: <該当する場合> フロント vitest M{N+1}-YY 時点で XXX 件。
- **持ち越し**: <新規発生または継承された持ち越し課題、または「持ち越しなし」>。
- **暫定処理の解消**: <該当する場合> 過去マイルストーンの暫定処理 X → M{N+1}-XX で解消。
```

**生成方針**:
- 各マイルストーン節は **5〜10 行を目安**(既存 §1/§2/§3 と同程度)
- 詳細(curl 出力・E2E 手順・個別ファイル名)は **入れない**(progress-log.md 側に既存)
- 「主要成果」「主な実装上の決定」は **2〜4 件** に絞る(冗長化回避)

### Step 7: 付随節の更新提案

#### 7.1 §「持ち越し課題」の更新提案

- 現行 §「持ち越し課題の現状(M{N+1} 着手時点)」の subtitle を **「M{N+2} 着手時点」** に更新
- リスト内容を Step 5-b で取得した最新 handover §4 の内容に差し替え
- Step 5-c との比較で **解消された課題 / 新規発生した課題** を明示

#### 7.2 §「更新履歴」の更新提案

- 新エントリを追加: `| X.Y.Z | YYYY-MM-DD | M{N+1} 期間の要約を追記。<付随節更新の有無> |`
- バージョン番号は既存履歴のパターンに従う(マイナーバージョン bump 等、Plan Mode で確認)

### Step 8: 節番号シフト

新節 §{N+1} を追加することで、既存 §「持ち越し課題」「更新履歴」の節番号が +1 シフトする。

例(M4 追加時):
```
現行: §0 / §1 M1 / §2 M2 / §3 M3 / §4 持ち越し / §5 更新履歴
新:   §0 / §1 M1 / §2 M2 / §3 M3 / §4 M4(NEW) / §5 持ち越し(M5 着手時点) / §6 更新履歴
```

本文中に節番号への参照(例: "§4 参照")があれば併せて更新する。

### Step 9: Plan Mode 提示

> **Plan Mode タイムアウト対策（未回答事項の扱い）**
>
> Claude Code の仕様変更により、Plan Mode は一定時間で自動タイムアウトし、開発者の回答を得ないまま Plan Mode を抜けて「編集承認」扱いになることがある。これを防ぐ手段は無いため、以下で代替する。
>
> 1. **未回答・未決の事項は、本 Step 9 提示（プラン）の末尾に「■ 未決事項（要回答）」として箇条書きで必ず明示し、開発者の返答を待つ。** 各項目に (a) 何が未決か (b) こちらの推奨案・暫定案 (c) 回答が無いと何が困るか を書く。
> 2. **重要な未決事項を抱えたまま承認された場合（タイムアウトによる自動承認を含む）は、Step 10（progress-summary.md 編集）に進まない。** 代わりに「重要な未決事項が残っているため作業を保留しました。以下について回答をお願いします」と連絡し、未決事項を再掲して停止する。
> 3. 推奨案どおり進めても実害の無い軽微な事項に限り、推奨案を採用した旨を明記した上で続行してよい。重要度の判断に迷う場合は「重要」側に倒し、停止して確認する。

以下を開発者に提示し、**各項目を個別に承認** してもらう:

1. **ターゲット M{N+1} の確認**(Step 2)
2. **完了性の確認**(Step 3、未完了の場合は続行判断)
3. **新節 §{N+1} の内容**(Step 6 生成案)
4. **§「持ち越し課題」更新案**(Step 7.1)— 個別承認可、不要なら skip
5. **§「更新履歴」更新案**(Step 7.2)— 個別承認可、不要なら skip
6. **節番号シフト**(Step 8)— 1〜4 のいずれかが承認されれば自動適用

### Step 10: 書き込み

承認後、`progress-summary.md` を以下の順で編集:

1. 新節 §{N+1} を現行 §「持ち越し課題」の **直前** に挿入
2. §「持ち越し課題」の subtitle とリストを承認内容に従い更新(承認時)
3. §「更新履歴」に新エントリ追加(承認時)
4. 節番号を §0 → §1 → ... → §{N+1} → §{N+2} → §{N+3} の順にシフト

## 要約方針(既存 §1/§2/§3 から抽出した型)

| 含める | 含めない |
|--------|----------|
| 完了日 + 開発者承認 + サブマイルストーン番号範囲 | curl 出力の詳細 |
| CHANGE 起票番号 + 改訂設計書バージョン | E2E シナリオの手順 |
| 主要 API 追加(エンドポイント名) | 個別ファイルパスの詳細(必要最小限のみ) |
| 主要 UI 機能追加(機能名) | 命名規約論争の詳細 |
| 主要スキーマ変更(migration 番号 + 概要) | 細かい実装決定(設計外の重要判断を除く) |
| ライブラリ追加(名前 + バージョン)(あれば) | (上記以外の詳細) |
| テスト件数(節目、フロント / バックエンド別) | |
| 暫定処理の解消(該当する場合) | |
| 持ち越し課題の状態変化(解消 / 新規発生) | |

> 既存 §1〜§3 を読んで「どの粒度で書くか」を必ず学習してから生成すること。
> 設計書バージョンや CHANGE 番号は progress-log.md 内では暗黙であることが多いため、
> 必要に応じて Step 5 の他資料(change-number-registry.md 等)も参照する。

## $ARGUMENTS の解釈ルール

| パターン | 例 | 動作 |
|---------|------|------|
| **空** | `(なし)` | 自動検出 + Plan Mode 確認 |
| **マイルストーン指定** | "M4" / "4" / "m4" | ターゲット M{N+1} として使用、自動検出より優先 |
| **補足指示** | "持ち越し課題は更新しないで" | Step 9 の方針判断に反映 |
| **複数情報の混在** | "M4 更新履歴は手動でやるからスキップ" | 分解処理 |
| **その他/曖昧** | 解釈一意でない | Plan Mode で開発者に確認 |

**$ARGUMENTS でも以下は突破不可**:
- progress-log.md への編集
- 編集禁止ファイル(下記)への編集
- Git 操作・データ破壊系コマンド

## 権限境界・禁止事項

### Git 操作の禁止

- commit / push / merge / rebase / tag / reset --hard / push --force 等は **すべて開発者が行う**
- Claude は変更提案・編集に留め、Git コマンドを直接実行しない

### データ破壊系コマンドの禁止

- `rm -rf` 系の致命的削除
- `git reset --hard` / `git clean -fd` 等の作業破壊
- `chmod 777` の再帰適用
- データベースファイル等の直接削除
- `curl ... | bash` / `wget ... | sh` 等の外部スクリプト直接実行
- `sudo` の使用

### 編集可能ファイル(本コマンドが編集する)

- **既存ファイル編集**(本コマンドの主成果物):
  - `<progress-summary.md>`: 新節追加、§「持ち越し課題」更新(承認時)、§「更新履歴」更新(承認時)、節番号シフト

### 編集禁止(読み取りのみ)

- `<progress-log.md>`: **読み取り専用**(参照元、Claude が編集すると正本の改変になる)
- 設計書本体(REQ-001 / DES-001〜006)
- `docs/design/supp-001-detailed-design.md`(§4.1 参照のみ)
- `docs/handover/` 配下全件(持ち越し課題取得元としての §4 読み取りのみ)
- `docs/handover/archive/` 配下、`docs/handover/cleanup-assistant-prompt.md`
- `docs/instructions/` 配下、`docs/instructions/reviews/` 配下、`docs/change-notes/` 配下
- `docs/progress/` 配下のレビュー結果ファイル(`*-review.md`, `*-implementation-report.md`)
- `docs/human-notes/` 配下、`docs/postmortem/` 配下
- `.claude/settings.json`、`.claude/settings.local.json`
- 本コマンドに明示的に列挙されていないすべてのフォルダ・ファイル

### 判断保留時の停止

- 取得した事実が不明確、ターゲットマイルストーンが進行中の疑い、`$ARGUMENTS` の解釈が曖昧、要約粒度の判断に迷う場合は **Plan Mode で停止** して開発者確認
- 推測で進めず、必ず開発者承認を得る
- progress-summary.md は後続マイルストーン担当が最初に参照する索引なので、**事実の正確性は特に慎重に**

## 進め方の最初の一歩

引数 `$ARGUMENTS` の有無に関わらず、以下から開始:

1. §「設定」の **progress-summary.md** を `Read` で読み、Step 1(検出)を実施
2. §「設定」の **progress-log.md** の全体構造を把握(`grep -nE '^## M[0-9]'` で見出し一覧取得)
3. `$ARGUMENTS` の解釈(空 / マイルストーン指定 / 補足指示 / 混在)を整理
4. Step 2(ターゲット M{N+1} 決定)、Step 3(完了性確認)、Step 4(抽出)、Step 5(事実取得)を実施
5. Step 6 で新節案をメモリ上に生成、Step 7 で付随節の更新案を生成
6. **Plan Mode で Step 9 の確認事項 6 項目(ターゲット / 完了性 / 新節 / 持ち越し更新 / 更新履歴 / 節番号シフト)を開発者に個別提示**
7. 承認後 Step 10(progress-summary.md 編集)を実施

不明点があれば遠慮なく開発者に確認してください。要約の粒度は **既存 §1/§2/§3 を必ず学習** してから決定し、
詳細(curl・E2E・個別ファイル名)を持ち込まないよう注意してください。
