あなたは高度なソフトウェアアーキテクト兼シニアエンジニアとして、**実装 → レビュー → 取り込み** を一気通貫で実施します。
従来は `implement_plan` / `review_plan` / `incorporate_plan` の 3 コマンド（別チャット）で回していた工程を、
本コマンド 1 本で完結させます。**従来の 3 コマンドは手動ゲート版として併存しており、本コマンドはそれを置き換えるものではありません。**

> **本コマンドの設計思想（重要）**
>
> チャット分離が担保していた品質ゲートのうち、**レビュアーの独立性**は「fresh subagent（メイン会話文脈を継承しない新規エージェント）」で代替します。
> **取り込み判断は自動化**しますが、人間トリアージ承認を外す代償として、(1) レビュー報告書の永続化、(2) 採否理由の事後監査可能化、(3) 「高」指摘を不採用とする場合のみのエスカレーション、で品質を補償します。

**最初に以下のバリデーションを行い、問題があれば作業を中断して確認を求めてください。**

### ステップ3-2: 実施済みチェック（安全網）

接頭語指定は打鍵が短い分、**別サブと取り違える危険が上がる**。確定した指示書について、
既に実施済みの成果物が無いかを `docs/progress/` の **ファイル名** で確認する。

確定ファイル名からタスク識別子（ステップ4 と同じ導出＝先頭2セグメント）を取り、次を実行する。
**`docs/progress/` は `phase1/` `phase2/` `phase3/` のアーカイブを含めて再帰探索する**（ステップ3-1 の直下限定とは非対称）。

```bash
find docs/progress -type f -name '*.md' -printf '%P\n' | grep -iE "(^|[-/])<タスク識別子>(-|\.)"
```

> **★境界付きで照合すること**（識別子の直後が `-` か `.`、直前が行頭か `-` か `/`）。
> 単純な部分一致だと `M19-04` が `m19-04b-review.md` / `m19-04c-*` / `m19-04d-*` まで拾い、
> **枝番のサブの成果物を本体の実施済み証跡と誤認する**。直前の `-` を許すのは
> `20260802-M19-04-manual-input-list-developer-decision.md` のような日付接頭辞付きを拾うため。

**1件以上ヒットした場合**: 既に実施済みである可能性が高い。以下を提示して確認を求め、
**承認が得られるまでステップ4 以降（Phase A 実装）に進まない**
```
⚠ この指示書は既に実施済みの可能性があります: docs/instructions/{確定ファイル名}
  docs/progress/ に以下の成果物があります:
    {ヒットしたファイルのパス一覧}
  それでもこの指示書で続行しますか？（再実施・追補が目的であれば「はい」）
```

**0件の場合**: 何も表示せずステップ4 へ進む。

> **本検査は証跡の有無を見るだけの安全網であり、実施済みか否かの判定機ではない。**
> 例えば `M14-03` は指示書が存在するが、実作業は枝番 `M14-03a`〜`M14-03e` に置き換えられており、
> 本体 ID での証跡は 0 件になる。**ヒットしなかったことを「未着手の保証」と読まないこと。**

## Phase A: 実装

1. 指示書本体（指示書パス）を読む
   （`CLAUDE.md` は Claude Code が起動時に自動ロードするため、明示的に読み直す必要はない）
2. 指示書が参照している設計書（docs/design/ 配下）を必要に応じて読む
3. 計画を提示する。以下を含めること
   - 作業対象ファイル一覧と作業順序
   - 不明点・推測で進める箇所（あれば明示）
4. **計画への承認を待ってから実装に入ること**（本コマンドで唯一の入口ゲート。CLAUDE.md §9 で Plan Mode 必須の指示書があるため必ず残す）
5. 承認後、実装する。作業の節目（機能単位の実装完了・テスト追加・リファクタリング完了等）でチェックポイントコミットを切る

> **Plan Mode タイムアウト対策（未回答事項の扱い）**
>
> Claude Code の仕様変更により、Plan Mode は一定時間で自動タイムアウトし、開発者の回答を得ないまま Plan Mode を抜けて「編集承認」扱いになることがある。これを防ぐ手段は無いため、以下で代替する。
>
> 1. **未回答・未決の事項は、プラン（提示）の末尾に「■ 未決事項（要回答）」として箇条書きで必ず明示し、開発者の返答を待つ。** 各項目に (a) 何が未決か (b) こちらの推奨案・暫定案 (c) 回答が無いと何が困るか を書く。
> 2. **重要な未決事項を抱えたまま編集が承認された場合（タイムアウトによる自動承認を含む）は、実装・編集・成果物生成を行わない。** 代わりに「重要な未決事項が残っているため作業を保留しました。以下について回答をお願いします」と連絡し、未決事項を再掲して停止する。Phase B 以降にも進まない。
> 3. 推奨案どおり進めても実害の無い軽微な事項に限り、推奨案を採用した旨を明記した上で続行してよい。重要度の判断に迷う場合は「重要」側に倒し、停止して確認する。

## Phase B: レビュー（fresh subagent で実施）

実装が一段落したら、`Agent` ツールで**レビュー専任のサブエージェントを起動**してレビューさせる。

> **絶対遵守: `subagent_type: fork` を使わないこと。**
> レビュアーの独立性（「自分の答案を自分で採点する」バイアスの回避）を担保するため、
> **メイン会話文脈を継承しない fresh subagent**（`subagent_type` を省略、または `general-purpose` 等の非 fork 型）で起動する。
> fork はメインの実装文脈を引き継ぐため独立性が崩れる。**必ず fresh で起動すること。**

サブエージェントへ渡すプロンプトには、以下の `review_plan` 相当の指示を埋め込む（導出済みのパスを実値で渡すこと）:

```
あなたはこのプロジェクトの「品質レビュー担当」です。
厳格なシニアエンジニアとして、コードを変更せず、指摘のみを行ってください。

「撤回済み・失効した記述がコード上に残っている」は「高」に置くこと。

- 通常のテストでは検出できない。動作は正しいままなので、テストも lint も型検査も緑になる。

見落としではなく優先度較正のずれであるため、基準として明示する。
```

## Phase C: 取り込み（判断は自動）

レビュー報告書を読み、`incorporate_plan` 相当のトリアージを**自動で実行**する。

1. 報告書の各指摘を **取り込むべきもの / 取り込む必要がないもの** に整理する。
2. 取り込むべき指摘の修正を適用し、節目でチェックポイントコミットを切る。
3. **人間トリアージ承認を外す代償としての品質補償（必ず実施）**:
   - トリアージ結果（各指摘の **採否と理由**）をチャットに提示する。
   - 同じトリアージ結果（採否と理由）を**レビュー報告書末尾に「## 取り込み結果（自動トリアージ）」節として追記**し、事後監査可能にする。

## 全数テストの合否は、パイプを挟まずに判定する（必須）

<!-- FULL-TEST-RUN-EXIT-CODE -->

**★★★`go test ./...` / `pnpm test` / `make e2e` の合否を、パイプ越しに判定してはならない。**

```bash
go test ./... > /tmp/gotest.txt 2>&1; echo "EXIT=$?"
grep -cE "^--- FAIL" /tmp/gotest.txt
```

**★★実際に落ちた例**（`M37-05`・2026-09-13）**＝製造は `go test ./... 2>&1 | grep -v "^ok\|no test files" | head -20` で確認し、「緑（exit 0）」と完了報告へ書いた。⇒ 実際は赤であった。**

**★★★破れ方が 2 つ重なっている。**

| # | 破れ方 |
|---|---|
| **1** | **`head -20` が `FAIL` 行を切り落とした** |
| **2** | **読んだ終了コードは*パイプ末尾のコマンド*のものであった。⇒ `go test` の終了コードではない** |

**★同じ型を同じサブでもう 1 度踏んでいる**——**`make e2e` の出力を `| tail -45` で取ったため、既存 spec の個別行が残らず、「影響を受けなかった」の根拠が*全体の結果*しか無い状態になった。**

**⇒ 出力はファイルへ全量を落とすこと。★「失敗 0 件」だけでは、どの spec が走ったのかを後から示せない。**

**★★完了報告に「緑」と書くときは、上の 2 行の実行結果**〔`EXIT=0` と `FAIL` の件数〕**を貼ること。⇒ 貼れないなら、まだ確かめていない。**

### ★★★一般形＝**全数を数えるための出力を `head` / `tail` で切らない**（2026-09-14 追加＝`D-881`・`M37-07` §7-1）

**★上の節はテスト出力を対象に書かれていたが、真の一般形はこれである。⇒ 対象が `grep` へ移っただけで同じ穴に落ちた。**

**★★実際に落ちた例**（`M37-07`・2026-09-14）**＝重複判定キーの*足し先を数える*ための `grep` を `| head -20` へ通した。⇒ 20 行で切られ、`internal/service/validation/duplicate.go` 以降が視界に入っていなかった。**

| 用途 | やること |
|---|---|
| **足し先を数える** | **出力をファイルへ全量落とし、`wc -l` で件数を出す。⇒ 目で 20 行読んで済ませない** |

## Git ルール（全 Phase 共通）

本プロジェクトで Claude Code が直接行える Git 操作は **コミット系のみ**（`git status` / `git diff` / `git log` / `git add` / `git commit`）です（CLAUDE.md §7）。
各 Phase の節目でチェックポイントコミットを切ってよいですが、push / merge / rebase / reset / checkout / restore / clean / rm 等の履歴改変・破壊的操作およびリモート反映は行わず、開発者（私）に委ねてください。
