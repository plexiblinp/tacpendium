description: 新しい Playwright E2E シナリオ spec を追加する
argument-hint: "[フィーチャー名またはフロー概要（例: タグ作成・編集・削除）]"
allowed-tools: Read, Write, Edit, Bash
---

> ⚠️ **このコマンドは初版です。次に利用する担当が改善しながら使うことを前提に設計されています。**
> 生成された spec は必ず `make e2e` で実行・検証し、必要に応じて手修正してください。

あなたは Playwright E2E テストに精通したシニアエンジニアとして、既存のテストパターンに倣い新しいシナリオ spec を追加します。

---

## 引数バリデーション

引数: `$ARGUMENTS`

空の場合は停止し、以下を伝える:

```
フィーチャーまたはフローの概要を引数に指定してください。
例: /add_e2e_spec タグ作成・編集・削除
例: /add_e2e_spec コンボ一覧のタグフィルター操作
```

---

## Stage 0: 規約・テンプレートの読み込み

1. `docs/design/testid-convention.md` を読む
   - セレクタ優先順位（getByRole > getByLabel > getByPlaceholder > getByTestId）
   - 命名規則（`{feature}-{element}` kebab-case）
   - 付与済み data-testid 一覧
2. `web/e2e/combo-crud.spec.ts` を読む（テンプレートパターン確認）
3. `ls web/e2e/` でファイル名の重複を確認

---

## Stage 1: 対象フィーチャーの調査

引数からフィーチャーとページ URL を推定し:

1. `ls web/src/features/` でフィーチャーディレクトリを確認
2. `ls web/src/pages/` で対象ページコンポーネントを特定
3. 対象コンポーネントを Read で調査:
   - `web/src/pages/{TargetPage}.tsx`
   - `web/src/features/{feature}/components/` 配下の主要ファイル
4. 以下を把握する:
   - 対象 URL（`/tags`、`/combos` 等）
   - 操作フロー（ボタン名・入力フィールド・ダイアログ等）
   - セレクタ候補（`getByRole`/`getByLabel`/`getByPlaceholder` で取得できる要素）
   - data-testid が必要な要素（上記で取得できない要素のみ、最小限にする）

---

## Stage 2: spec 設計を提示（承認待ち）

以下を開発者に提示し、承認を得る:

- **spec ファイル名**: `web/e2e/{feature}-{operation}.spec.ts`
- **テスト手順（ステップ番号付き箇条書き）**:
  - 前提: ウィザード完了済み DB。必要なデータは spec 内で作成・削除する
  - 各操作と期待結果を具体的に記述
- **必要な data-testid**（新規付与が必要な場合のみ）:
  - 対象コンポーネントと付与箇所を記載
  - 不要な場合は「追加不要」と明記
- **不確定要素**: セレクタが確定できない箇所や要確認事項

> **ここで一時停止し、開発者の確認を待ってから Stage 3 へ進む。**

---

## Stage 3: 実装

承認を得たら以下の順で実装する:

### 3-1. data-testid の付与（必要な場合のみ）

Stage 2 で合意した対象コンポーネントを Edit:
- `data-testid="{feature}-{element}"` を追加（kebab-case）
- getByRole 等で取れる要素には付与しない

### 3-2. spec ファイルの作成

`web/e2e/{filename}.spec.ts` を Write で作成。以下のパターンを踏襲する:
- `combo-crud.spec.ts` と同じ構造（import、test.describe、自前データ作成・削除）
- ユニーク識別子に `Date.now()` を使用（再実行・並行実行でデータ衝突しない）
- 仮登録モード（draft）が使えるフィーチャーは活用する
- spec ファイル冒頭に環境前提コメントを記載:
  ```typescript
  // 前提: `make e2e` / `make e2e-only` が起動する使い捨てスタックで実行される
  //       (既定はバックエンド :47390 / Vite :5273。worktree ごとに決定的にオフセットされる)。
  //       DB は毎回作り直す seed 済みの使い捨て DB であり、dev DB・dev サーバには影響しない。
  //       ⇒ dev 側の状態(既存データ件数・開発者が最後に選んだ既定キャラ等)を仮定しないこと。
  ```
  **★ポート番号を spec 本文へハードコードしないこと**(上のコメントは前提の説明であり、
  値は `web/playwright.config.ts` が持つ)。**★「ブラウザ未導入のため未実行」と書かないこと**
  ——Chromium はプリインストール済みで、`make e2e` で実行される。
- コメントは「フェーズ区切り」のみ。実装説明コメント禁止

### 3-3. testid-convention.md の更新

`docs/design/testid-convention.md` の「付与済み一覧」を Edit で更新:
- 新規付与した data-testid をアルファベット順に追加
- 付与不要だった場合はスキップ

## 制約・スタイルガイド

- **セレクタ優先順位を守る**: getByRole > getByLabel > getByPlaceholder > getByTestId
- **`fullyParallel: false` を前提**: spec 内で DB データが衝突しないよう一意識別子を使う
- **★グローバル資源を触る spec は、資源ごとに 1 ファイルへ寄せる**（2026-08-14 新設・board **D-362**）。
  **`fullyParallel: false` が直列化するのは「ファイル内」だけであり、ファイル単位では並列に走る。**
  E2E スタックは**バックエンド 1 本・DB 1 個の共有資源**であるため、**総数に上限のあるもの**
  （プリセット総数 8 件 等）**を触る spec を別ファイルへ分けると、上限を検査している側が落ちる。**
  - **実例**（M20-05）——プリセットを作る spec を別ファイルへ置いたところ、
    `m20-04-preset-management.spec.ts` の「上限 8 件」テストが 5 件目を作れずに落ちた。
    当該 spec 単独では 4/4 緑であり、**組み合わせでしか出ない。**
  - **★「作る側」だけでなく「消す側」も資源を触る。** 全削除を `beforeEach` で撃つ spec は、
    上限テストがカスタムを保持している最中に走ると**そちらを数え損ねさせる。**
  - ⇒ **「1 サブ 1 ファイル」の型より、資源の排他を優先する。**
  - **★★適用単位は「画面」ではなく「書き換える共有資源」である**（2026-08-18 明文化・board **D-431**）。
    **サーバ状態を 1 バイトも書き換えない spec**（`page.route` でそのブラウザコンテキストの
    応答だけを差し替える等）**は、同じ画面を触っていても資源を取り合わない。** ⇒ **別ファイルでよい。**
    - **★「同じ画面を触る既存 spec があるならそちらへ足す」と読まないこと。**
      **書き換える spec と書き換えない spec を同居させると、片方の `page.route` が
      もう片方に効く事故の面が増える**（M22-06 で実際にこの理由から分けた）。
  - **★★本ルールが効く射程には限界がある**（2026-08-20 明文化・board **D-466** ／ 教訓 **E-142**）。
    **効くのは「同じ資源を奪い合う」型までであり、「全 spec に影響する状態」には効かない。**
    **⇒ サーバ側のグローバル設定**（認証の ON/OFF、`config.toml` の書き換え、ユーザーの追加）**を
    変える spec は、1 ファイルへ寄せても他ファイルを巻き添えにする。**
    **`fullyParallel: false` が守るのはファイル内の順序だけで、他ファイルは並列に走っているためである。**
    - **⇒ この型は「寄せる」で解けない。** **サーバ状態を一切変えず、ブラウザコンテキスト単位で
      再現する形へ倒すこと**（`page.route` / Cookie の注入 等）。**復元も不要になる**という利点がある。
    - **実例**（M22-01）——認証の ON/OFF を E2E で確かめる必要があったが、**サーバ設定を触らずに
      コンテキスト単位で再現した。** これにより全 spec への影響がゼロになった。
    - **判定の問い**——**「この spec が落ちたら、他のファイルのテストも道連れになるか」。**
      **ならない spec は資源を取り合っていない。**
    別サブのファイルへ足す場合は、**`test.describe` でサブを分け、同一ファイルへ置く理由をコメントで書く。**
- **★E2E でも破壊確認を回す**（2026-08-14 新設・board **D-375**）。**「不具合を復元したら赤くなるか」を必ず確かめる。**
  **★単体だけで確かめると「イベントがそもそも飛んでいない」形の空振りを見逃す。**
  - **実例**（M21-05）——**`page.keyboard.down()` を 1 回呼んで待っても、Playwright は自動でリピートを送らない**ため
    keydown は 1 回しか飛ばない。**⇒ 初版の spec は、スクロール不具合を復元しても緑のままだった。**
    **`down()` を繰り返し呼ぶと 2 回目以降に `repeat: true` が立つ**ため、それで初めて赤くなった。
  - **★測る起点も確かめる**——**同サブでは「起点が最上部では ↑ の検証が空振りする」**（先頭では上へ動けない）。
    **⇒ 途中までスクロールさせてから測る形へ改めた。**
- **★「抑止される／効かない」ことを見る spec には、対照実験を添える**（2026-08-14 新設・board **D-375**）。
  **「対象が抑止されること」だけを見ると、全部を抑止していても緑になる。**
  **⇒ 同じ操作・同じ画面で「対象外なら従来どおり動く」ことまで主張する。**
- **★結果表示を主張する spec・コンポーネントテストは、実アプリと同じ状態遷移で描画する**
  （2026-08-25 新設・教訓 **E-217** ／ 出所 設計伝達レポート **M23-06 §7-1**。**M23-07 §7-4 で再発＝2 サブ連続**）。
  **コールバックを no-op モックに差し替えると親の再描画が起きず、この型の欠陥は構造的に検出できない。**
  - **実例**（M23-06）——新規実装した「一括復元の警告の内訳」は、**実アプリでは一度も表示されていなかった。**
    一括操作の末尾で `onComplete()` を呼ぶと**親が選択状態を空にし**、子は「選択が空なら描画しない」で
    `null` を返すためである。**同じ理由で、既存の「N 件失敗」の警告も 2 サブ前からずっと不可視だった。**
  - ⇒ **親と同じ状態遷移を持つラッパーで描画すること。** `onComplete` 等のコールバックには、
    **親が実際にやること**（選択のクリア・再取得）**まで再現させる。**
  - **★検出できたのはレビューの静的読解だけだった**——テスト・lint・型検査はすべて緑で、
    **人が呼び出し連鎖を追う以外に見つける経路が無かった。**
- **★「〜が残っていない」を主張する走査型テストは、走査の前に「対象が実際に描画されたこと」を 1 行アサートする**
  （2026-08-25 新設・教訓 **E-217** ／ 出所 設計伝達レポート **M23-07 §7-4**）。
  **描画されていなければ、走査は常に真を返す。** 上項とは別の失敗形であり、走査型テスト全般に効く。
- **ウィザード完了済み前提**: DB リセット・初期化ロジックを spec 内に書かない
- **data-testid は最小限**: 既存の getByRole 等で到達できる要素には付与しない
- **コメントは最小限**: 環境前提・フェーズ区切りのみ。実装内容コメント禁止
