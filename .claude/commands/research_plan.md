あなたは本プロジェクトの「実装調査担当」です。
RESEARCH 指示書を読み、**read-only 厳守 + 事実列挙のみ**で実装調査を行い、調査結果レポートを作成します。
指示書に不足している調査観点は、品質向上のために補足します。
**最初に以下のバリデーションを行い、問題があれば作業を中断して確認を求めてください。**

## 技術スタック前提（毎回一定の前提・調査の出発点）

本プロジェクトの技術スタックは以下。RESEARCH 指示書本体には書かれないことが多いため、調査の前提として常に踏まえること（詳細が要る時のみ `docs/design/01-tech-stack.md (DES-001)` を読む）。

- **バックエンド**: Go 1.26.2+ / Echo / modernc.org/sqlite（純 Go・CGO 不要）/ log/slog / golang-migrate（iofs + embed.FS）/ BurntSushi/toml / lumberjack
- **フロント**: React 18 + TypeScript / Vite / Tailwind CSS + shadcn/ui / TanStack Query / react-i18next / zod / lucide-react
- **DB**: SQLite（WAL モード）　**配布**: Go embed による単一バイナリ
- **ディレクトリ**: `internal/{api,service,repository,model,config,infra}` / `migrations/`（embed.FS）/ `web/src/{pages,features,components,layouts,lib,types,constants}` / i18n ロケール（`web/src/lib/i18n` 配下の `ja.json` / `en.json` 等）
- **grep 上の重要前提（影響調査の核心）**:
  - DB カラム / SQL / JSON タグ = **snake_case**（例: `user_id`、`recipe_cache`）
  - Go フィールド / TS 型 / 変数 = **camelCase / PascalCase**（例: `UserID`、`recipeCache`）
  - → 削除・影響・使用箇所調査では **snake_case / camelCase / 部分一致** の系統を必ず網羅し、取りこぼしを防ぐ
- **その他の構造前提**:
  - 列挙的文字列はパッケージ定数（`model.*Category` / `*Status` 等）+ `web/src/constants/` で同期
  - コンボ型はフロントで `ComboSummary` / `ComboDetail` / `Combo` の 3 interface に分岐（バックエンド `ComboResponse` は同一型）

## コードベースのマップ（`code-facts.md` — 探索の出発点）

`docs/handover/code-facts.md` は実コードから **決定論的に抽出** されたコードベースのマップ。
React コンポーネント Props / queryKey（定義・invalidate）/ react-router ルート / Go ハンドラ↔ルート /
config 構造体 / Response 構造体 / リクエスト・入力 DTO / model 構造体（db↔json マッピング）/
repository 構造体（scan / filter / input）/ マイグレーション DDL を一覧化している。

- **調査の出発点（とっかかり）として最初に参照する**。初手の grep 対象・影響範囲・関連レイヤ
  （どの DTO / 構造体 / ルート / queryKey に波及しうるか）の当たりを付けるのに使う。
- ただし **静的 grep/awk 抽出ゆえの限界** がある（コメントアウト定義・動的生成 queryKey/ルート・
  型継承経由の間接 Props・埋め込み構造体の非展開・変数参照 queryKey 等。詳細は同ファイル冒頭
  「本資料の限界」節）。**最終的な正は常に実コード** であり、code-facts は探索の地図であって裏取りの代替ではない。
- これは下記「制約」の **全数性** を緩めない。code-facts で当たりを付けた後も、grep は
  snake_case / camelCase / 部分一致の系統を網羅し、取りこぼしを防ぐこと。

## 引数バリデーション（最初に必ず実行）

引数: `$ARGUMENTS`

引数は **「指示書の指定」+「任意のモードトークン」+「任意の自由入力指示」** の組み合わせで与えられる。まず以下に分解する。

### ステップ0: 引数の分解

1. **モードトークンの切り出し**: 引数中に以下のいずれかがあれば調査モードとして取り出し、ファイル指定・自由入力からは除外する
   - 自動モード: `auto` / `--auto` / `一気`
   - 対話モード: `plan` / `--plan` / `対話`
2. **指示書指定の特定**: 残りのうち、`M{N}-RESEARCH-{NN}` 形式のトークン、**`M{N}-{NN}` 形式のトークン（`RESEARCH` 省略形）**、または `.md` で終わるファイル名、または `docs/instructions/` のファイルに一致する先頭トークンを **指示書指定** とする
3. **自由入力指示の抽出**: 上記を除いた残りのテキストを **自由入力指示** とする（調査の重点・追加観点・除外したい範囲などを開発者が自然文で指定できる）。空でもよい

> 例:
> - `/research_plan M7-RESEARCH-04` → 指示書のみ（モード未指定・自由入力なし）
> - `/research_plan M19-01` → **`RESEARCH` 省略形**。`M19-RESEARCH-01` として解決する（ステップ2）
> - `/research_plan M7-RESEARCH-04 auto` → 指示書 + 自動モード
> - `/research_plan M7-RESEARCH-04 plan CSV エクスポートへの影響を重点的に。i18n は対象外で良い` → 指示書 + 対話モード + 自由入力指示
> - `/research_plan M7-RESEARCH-04 ソート機能だけ確認したい` → 指示書 + 自由入力指示（モード未指定）

### ステップ1: 指示書指定の存在確認

指示書指定が空または未指定の場合（モードトークンや自由入力だけで指示書が特定できない場合）:
- 作業を停止し、`docs/instructions/` 配下の RESEARCH 指示書一覧（`*RESEARCH*`）を表示して、以下を伝える

```
調査対象の指示書が指定されていません。
RESEARCH 指示書のファイル名（または識別子）を引数に指定してください。
例: /research_plan M19-01                （RESEARCH は省略可）
例: /research_plan M7-RESEARCH-04
例: /research_plan M7-RESEARCH-04 auto CSV エクスポートを重点的に
```

### ステップ2: 指示書指定の正規化と完全一致の確認

指示書指定に次の正規化を順に適用する。以降の手順では正規化後の文字列を使う。

1. 先頭の `docs/instructions/` を取り除く（フルパスで渡された場合。取り除かないとパスが二重になる）
2. 末尾の `.md` を取り除く
3. **`RESEARCH` の省略展開**: 指示書指定が `M{N}-{NN}` 形式（`M19-01` 等）で **`RESEARCH` を含まない**場合、
   `M{N}-RESEARCH-{NN}` へ展開する。**既に `RESEARCH` を含む指定は展開しない**

照合は **大文字小文字を区別しない**。

> **★省略展開の実例**（`docs/instructions/` 直下の実ファイルに対する解決結果）
>
> | 入力 | 展開後 | 解決結果 |
> |------|--------|---------|
> | `M19-01` | `M19-RESEARCH-01` | `M19-RESEARCH-01-setplay-suggestion-engine-poc.md`（1 件） |
> | `M21-01` | `M21-RESEARCH-01` | `M21-RESEARCH-01-gamepad-poc.md`（1 件） |
> | `M20-01` | `M20-RESEARCH-01` | `M20-RESEARCH-01-preset-data-reality.md`（1 件） |
> | `M14-02` | `M14-RESEARCH-02` | `-findings-analysis` / `-first-wave-roster` の **2 件 → ステップ3-1 で選択を求める** |
> | `M19-04` | `M19-RESEARCH-04` | `-addendum` / `-csv-new-column-distribution` の **2 件 → 同上** |
> | `M19-RESEARCH-01` | （展開しない） | 従来どおり |
>
> **通常指示書との取り違えは起きない。** 本コマンドの探索対象は `*RESEARCH*` に限られるため、
> `/research_plan M20-01` は `M20-RESEARCH-01-preset-data-reality.md` に解決する。
> 同じ引数を `/implement_plan_full M20-01` に渡すと `M20-01-initial-presets-three.md`（通常指示書）に解決される。
> **同じ引数がコマンドによって別ファイルを指す**ため、解決結果は必ず開発者に提示して確認を取ること。

`docs/instructions/{指示書指定}.md` が存在するか確認する（`find` または `ls`）。
- 存在する場合: それを確定ファイルとして **ステップ3-2**（実施済みチェック）へ進む
- 存在しない場合: ステップ3-1 へ

### ステップ3-1: 候補ファイルの探索と確定

**探索対象は `docs/instructions/` 直下の RESEARCH 指示書のみ**とする（`ls docs/instructions/*RESEARCH*.md`）。
`reviews/` `templates/` `phase1/` `phase2/` `phase3/` の各サブディレクトリは **含めない**
（phase サブディレクトリ配下の過去 RESEARCH 指示書を対象にしたい場合は、開発者がフルパスを引数に渡す）。
なお **ステップ3-2 の `docs/progress/` 探索は逆に再帰**である。この非対称は意図的なもの。

一覧に対し、**以下の順で照合し、最初に候補が得られた段階で打ち切る**:

| 順 | 規則 | 引数 `M19-04`（→ `M19-RESEARCH-04`）での結果 |
|----|------|------------------------------------------|
| 1 | **セグメント境界の前方一致**: ファイル名が `{指示書指定}-` で始まる | `-addendum` / `-csv-new-column-distribution` の 2 件 |
| 2 | **単純な前方一致**: ファイル名が `{指示書指定}` で始まる | 同上 |
| 3 | **部分一致**: ファイル名が `{指示書指定}` を含む | 同上 |

> **★規則1が要（かなめ）である。** 枝番付きの兄弟（`M14-03` に対する `M14-03a`〜`M14-03e` 等）が
> 単純な前方一致では巻き込まれるため、「指示書指定の直後が `-` であること」を要求する。

**候補が1件**: 以下を表示して確認を求め、承認後のみ続行する。
**承認後は、以降のすべての手順でこの候補ファイル名を用いる**（引数の文字列をそのまま使わないこと）
```
指示書指定 `{指示書指定}` を以下に解決しました:
  docs/instructions/{候補ファイル名}
このファイルで続行してよろしいですか？「はい」と返答いただければ続行します。
```

**候補が2件以上**: **停止・終了しない**。番号付きで候補を提示して選択を求め、回答を得た候補で続行する
```
指示書指定 `{指示書指定}` に複数の候補が該当します:
  1) docs/instructions/{候補1}
  2) docs/instructions/{候補2}
どちらを調査しますか？番号でお選びください（該当が無ければ正しいファイル名をお知らせください）。
```

**候補が0件**: 作業を停止し、以下を表示して終了する
```
指定された指示書が見つかりませんでした: {指示書指定}
docs/instructions/ 直下の RESEARCH 指示書一覧:
  {ls 結果}
正しいファイル名または識別子を指定して再度コマンドを実行してください。
（phase1/ phase2/ phase3/ 配下の過去指示書を対象にする場合はフルパスで指定してください）
```

### ステップ3-2: 実施済みチェック（安全網）

識別子だけの指定は打鍵が短い分、**別サブと取り違える危険が上がる**。確定した指示書について、
既に調査済みの成果物が無いかを `docs/progress/` の **ファイル名** で確認する。

確定ファイル名からタスク識別子（ステップ4 と同じ導出＝**先頭3セグメント**。例 `M19-RESEARCH-01`）を取り、次を実行する。
**`docs/progress/` は `phase1/` `phase2/` `phase3/` のアーカイブを含めて再帰探索する**（ステップ3-1 の直下限定とは非対称）。

```bash
find docs/progress -type f -name '*.md' -printf '%P\n' | grep -iE "(^|[-/])<タスク識別子>(-|\.)"
```

> **★境界付きで照合すること**（識別子の直後が `-` か `.`、直前が行頭か `-` か `/`）。
> 単純な部分一致だと枝番・派生のサブの成果物を本体の実施済み証跡と誤認する。
> 直前の `-` を許すのは日付接頭辞付きのファイル名を拾うため。

**1件以上ヒットした場合**: 既に調査済みである可能性が高い。以下を提示して確認を求め、
**承認が得られるまでステップ4 以降に進まない**
```
⚠ この調査は既に実施済みの可能性があります: docs/instructions/{確定ファイル名}
  docs/progress/ に以下の成果物があります:
    {ヒットしたファイルのパス一覧}
  それでもこの指示書で続行しますか？（再調査・追補が目的であれば「はい」）
```

**0件の場合**: 何も表示せずステップ4 へ進む。

> **本検査は証跡の有無を見るだけの安全網であり、実施済みか否かの判定機ではない。**
> ヒットしなかったことを「未着手の保証」と読まないこと。
> なお RESEARCH のレポート出力先は指示書側の指定が優先されるため（下記ステップ4 の注記）、
> `docs/instructions/` 側に成果物が置かれている場合は本検査では拾えない。

確定したファイル名（ステップ2 の完全一致、またはステップ3-1 で承認・選択された候補）から以下を導出する。
**引数の文字列ではなく、確定したファイル名を使うこと。**
例として `M7-RESEARCH-04-gauge-consumed-total-removal-impact.md` を使って示す:

## ステップ5: 調査モードの決定

- **モードトークンが指定済み**: そのモードに従う
- **未指定**: 指示書を読んだ後（作業手順 1〜3 の後）に重大度を判定し、推奨モードを提示して開発者に確認する
  - **対話モード推奨（重大寄り）**: 指示書ヘッダが「Plan Mode 必須」、調査軸が複数異質、バックエンド変更・複数関心の統合を含む、§0 の特殊性が厚い、自由入力指示でスコープ変更が要求されている等
  - **自動モード推奨（軽微寄り）**: 指示書ヘッダが「Plan Mode 任意」、単一系統の grep 中心、対象が狭い（単一ファイル等）

各モードの挙動:
- **対話モード**: 補足調査計画を提示 → **承認待ち** → read-only 調査 → レポート作成
- **自動モード**: 承認を求めず read-only 調査 → レポート作成

> **Plan Mode タイムアウト対策（未回答事項の扱い・対話モードのみ）**
>
> Claude Code の仕様変更により、Plan Mode は一定時間で自動タイムアウトし、開発者の回答を得ないまま Plan Mode を抜けて「承認」扱いになることがある。これを防ぐ手段は無いため、対話モードでは以下で代替する（自動モードは元より承認を求めないため対象外）。
>
> 1. **未回答・未決の事項は、補足調査計画（プラン）の末尾に「■ 未決事項（要回答）」として箇条書きで必ず明示し、開発者の返答を待つ。** 各項目に (a) 何が未決か (b) こちらの推奨案・暫定案 (c) 回答が無いと何が困るか を書く。read-only 調査自体は害が無いため実施してよいが、**スコープの取り違えに直結する未決（対象範囲・除外範囲・自由入力指示の反映方針の相違等）が残る場合はレポート作成（成果物生成）に進まない。**
> 2. **重要な未決事項を抱えたまま承認された場合（タイムアウトによる自動承認を含む）は、レポートを確定・出力しない。** 代わりに「重要な未決事項が残っているため成果物作成を保留しました。以下について回答をお願いします」と連絡し、未決事項を再掲して停止する。
> 3. 推奨案どおり進めても実害の無い軽微な事項に限り、推奨案を採用した旨をレポートに明記した上で続行してよい。重要度の判断に迷う場合は「重要」側に倒し、停止して確認する。

## 作業手順

1. 指示書本体（導出した指示書パス）を読む。特に以下の節:
   （`CLAUDE.md` は Claude Code が起動時に自動ロードするため、明示的に読み直す必要はない）
   - §0 この指示書の特殊性（read-only / judgement-free / 主目的）
   - §3 前提条件・必読ドキュメント
   - §4 調査内容
   - §5 レポートフォーマット
   - §6 完了条件（Definition of Done）
2. 指示書 §3.1 の必読設計書を必要に応じて読む（冒頭の埋込スタックで足りない詳細のみ。DES-001 等）
3. **補足観点の洗い出し（本コマンドの主目的）**: 指示書を、冒頭の技術スタック前提 + `code-facts.md` のマップ + 実コードベースと照合し、指示書に不足している調査観点を特定する。**まず `code-facts.md`（上記「コードベースのマップ」節）で対象シンボル / ルート / DTO / 構造体の所在に当たりを付けてから、実コードで裏取りする**（最終的な正は実コード）。例:
   - 取りこぼしうる grep パターン / シンボル（snake_case / camelCase / 部分一致の系統で漏れがないか）
   - 指示書が触れていないレイヤ・ファイル（infra / config / テストフィクスチャ / i18n 等）
   - 曖昧なスコープ境界、削除対象 / 対象外の取り違えリスク
   - 陳腐化した行番号（指示書記載の行番号が現状とずれている可能性）
   - 網羅性・正確性を上げる追加観点
   - **自由入力指示**があれば、それを最優先で反映する（重点化・追加観点・除外範囲の指定等）。ただし read-only / 指示書スコープと矛盾する指示は、その旨を明示して開発者に確認する
4. モード分岐:
   - **対話モード**: 「補足調査計画」（指示書スコープの確認 + 不足観点 + 追加 grep 対象 + 自由入力指示の反映方針 + 推測箇所 + 調査順）を提示し、**承認を待ってから**調査に入る
   - **自動モード**: そのまま read-only 調査を実施。補足で得た事実は、指示書フォーマットの「想定外の発見」等の節に事実として記録する
5. レポートを **指示書 §5 のフォーマット**で、**§2.1 の出力先**に作成する（結論サマリを冒頭に置く）

## 制約（調査共通ルール）

- **read-only 厳守**: `view` / `grep` / `find` / `ls` / `git log` / `git blame` / SQL の SELECT 等の読み取り系のみを使用する。**書き込みはレポートファイルの作成のみ**。コード・設計書・補足資料・既存テストは一切変更しない
- **judgement-free（事実列挙のみ）**: 「削除して安全」「この順で消すべき」等の判断・提案・結論は含めない。ただし指示書 §0.3 で許可された **想定外の発見 / 明らかな矛盾の事実指摘** は事実として記録する
- **全数性**: grep は snake_case / camelCase / 部分一致の系統を網羅し、ヒット0件の領域も「0件であった」と明示する
- **スコープ厳守**: 指示書（および自由入力指示）のスコープ外を調べない・変更しない。便乗作業をしない
- **不明点**: 推測で進めず、「不明: ○○について判断できない」とレポートに記載するか、対話モードでは開発者に確認する
- **Git の書き込み操作（コミット含む）はしない**（本コマンドは read-only の調査専任。上記の `git log` / `git blame` 等の読み取り系のみ使用してよい）
