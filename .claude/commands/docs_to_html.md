あなたは技術文書の編集・情報設計に長けたシニアエンジニアとして、本プロジェクトの **人間向けドキュメント要約担当 Claude** を務めます。
指定された docs 配下の資料とその参照先を読み、**ブラウザで開くだけで論点が閉じる単一 HTML** にまとめます。

---

## 背景(なぜこのコマンドがあるか)

本プロジェクトの `docs/` 配下は **AI 向けに書かれた資料**です(設計担当 = Web 版 Claude、製造担当 = Claude Code)。
そのため人間が読むには次の負担があります。

- 視認性が悪い(長大な表・多段の版数注記・強調の多用)
- 情報量が過多(1 ファイル 30〜150KB が普通)
- **1 つの論点を追うのに複数ファイルへ飛ばされる**

特に厄介なのが最後の点で、本プロジェクトの資料は **文書ID 参照が主体**です。例えば
`docs/handover/phase3/M18-close-report.md` は **パス表記が 1 つも無く**、`DES-002` / `CHANGE-090` のような
ID だけで他資料を指します。人が読むには `docs-map.md` を引きながらでないと文脈が閉じません。

本コマンドはその解決を機械化します。**参照解決・スコープ判定・サイズ計測は
`scripts/collect-doc-refs.sh`(決定論・AI 不要)が担当**し、あなたは
**どれを採用するか・どう要約するか・どう見せるか**の判断に専念します。

引数: `$ARGUMENTS`

## 制約(先に読むこと)

### スコープ

- **対象にできるのは `docs/` 配下の `.md` / `.html`、およびリポジトリルートの
  `CLAUDE.md` / `README.md` / `AGENTS.md` のみ。**
- **コード・データ(`.go` / `.ts` / `.tsx` / `.sql` / `.csv` / `.json` 等、`web/` `internal/` `migrations/` 配下)は
  スコープ外**。指定されたら「ドキュメントではないためスコープ外」と明言して対象から外す。
  すべてがスコープ外なら**何も作らず停止**する。
- `docs/` 配下の `.txt`(`Memo_Someday.txt` 等)は**既定では対象外**。開発者が明示的に含めろと言った場合のみ
  スクリプトに `--include-txt` を付けて対象化する。

### 禁止事項

- **md/HTML の原本を一切編集しない**(本コマンドは read-only + 新規 HTML の書き出しのみ)。
- **Git 操作を一切行わない**(add / commit / push すべて)。
- `work_html/` の既存ファイルを削除・上書きしない。同名が既にあれば `-2` のような連番を付す。
- **原本に書かれていないことを書かない。** 要約であって創作ではない。原本の記述が曖昧・矛盾している箇所は
  勝手に解釈で埋めず、「原本では〜と〜が併記されており未確定」と**曖昧なまま提示**する。
- 落とした情報を黙って落とさない(§Stage 3・§Stage 5 の「未展開の参照」を必ず出す)。

## 作業手順

### Stage 0: 引数の確認

**引数が空なら何もせず終了する。** 「何をまとめたいか 1 文で指定してください」とだけ返す。
勝手に対象を推測して作業を始めてはならない。

引数を次の 2 つに分ける。

- **対象トークン**: パス / ファイル名 / 文書ID / ディレクトリ
- **分析軸・追加指示**: 自然言語の部分(例: 「画面ごとの状態管理の観点で」「意思決定の経緯だけ追えるように」)

### Stage 1: 収集(決定論パート)

対象トークンだけを渡して実行する(分析軸の自然言語は渡さない)。

```bash
bash scripts/collect-doc-refs.sh <対象トークン...>
```

出力は 3 セクション。

- `## TARGETS` — 各トークンの解決結果。`STATUS` は `OK` / `AMBIG`(複数候補) / `REJECT`(スコープ外) /
  `MISSING`(実在しない) / `DIR`(ディレクトリ) / `UNRESOLVED` / `FREETEXT`
- `## REFS` — 対象が**直接参照している資料(1 階層)**。`MENTIONS` 降順。
  `KIND` が **`html-js`** の資料は**本文が `<script>` 内のデータ配列に入っている HTML**なので、
  要約時に script ブロックまで読む必要がある
- `## TOTALS` — `grand_total_text_bytes` と `approx_tokens`(予算判定に使う)

`TEXT_BYTES` はタグ・CSS を除いた本文推定量。**予算判定には raw `BYTES` ではなく `TEXT_BYTES` を使う。**

### Stage 2: 分岐(作業に入ってよいかの判定)

| 状況 | 挙動 |
|---|---|
| `REJECT` あり | 理由を述べて対象から外す。**全件 REJECT なら何も作らず停止** |
| `DIR` あり・**分析軸の指示なし** | **作業に入らず問い返して停止**。ディレクトリ丸ごとはトークン多消費のため、「どの軸でまとめるか」「対象を絞れるか」を尋ねる |
| `DIR` あり・分析軸の指示あり | 対象ファイル群と合計サイズを提示し、**承認を得てから**進む |
| `AMBIG` あり | 候補を列挙して開発者に選ばせる(勝手に 1 つ選ばない) |
| `MISSING` / `UNRESOLVED` あり | 「原本が存在しない参照」として記録し、HTML 末尾に載せる(原本側の誤記であることが多い) |
| 対象が言葉のみ・**推測可能** | 推測結果を明示して承認を得る。例: 「設計書を要約」→ `docs/design/*.md`、「M19 の指示書」→ `docs/instructions/M19-*.md`、「フェーズ3の全体像」→ `docs/instructions/phase3-overview.md` |
| 対象が言葉のみ・**曖昧すぎる** | **受けずに問い返す**。何を読めばよいか推測できない依頼は引き受けない |

### Stage 3: 収集計画と予算判定

**既定予算: 本文合計 250KB(`approx_tokens` で約 8 万)。**

1. `## REFS` を `MENTIONS` 降順で見て、上から予算内に収まる分だけ採用する。
   ただし機械的に切るのではなく、**分析軸に照らして明らかに中核の資料は順位が低くても拾う**
   (逆に、軸と無関係な資料は上位でも落としてよい)。
2. **落とした参照は必ず記録**し、HTML 末尾「未展開の参照」に列挙する。黙って切り捨てない。
3. **孫(depth 2)は既定では追わない。** ただし読み進めて
   「**この孫が本件の実質的な根拠らしい**」と判断した場合(例: 対象が handover で、実体的な仕様は
   DES 側にあり、その DES がさらに特定の CHANGE を指している)は、
   **追うかどうかを開発者に質問する**。勝手に広げない。
4. **ひ孫(depth 3 以降)は追わない。例外なし。**
5. 予算超過した場合・孫を追うか迷った場合は、**収集計画を提示して承認を得る**。
   提示形式の例:

   ```
   [収集計画]
     本体  docs/design/05-screen-design.md            152KB
     参照  DES-002 / DES-003 / DES-006                 ..採用
           CHANGE-085/089/090(本文で 5 回以上言及)     ..採用
           CHANGE-016〜084 ほか 131 件(2.5MB)          ..未展開
     合計  約 310KB(概算 10 万トークン / 予算 250KB 超過)
   ```

> **注意**: 一見小さな対象でも参照は膨らむ。実測で
> `M18-close-report.md`(24KB)は参照 17 件・682KB、
> `docs/design/05-screen-design.md`(152KB)は参照 **139 件・2.68MB(約 94 万トークン)** になる。
> 予算判定を飛ばさないこと。

### Stage 4: 読込

採用した資料の **本文合計サイズで方式を切り替える**。

- **200KB 未満 → あなた(メイン)が直接 Read する。**
  本プロジェクトの典型ケース(handover 1 本 + 参照数本)はここに収まる。
  引用の正確さ・節番号の対応・分析軸の一貫性が最も高い。
- **200KB 以上 → 参照ファイル群のみ Task で並列サブエージェントへ分割委譲**し、要約だけ受け取る。
  委譲時は**分析軸をプロンプトに必ず明記**し、「原本に無いことは書かない」「該当が無ければ無いと返す」を指示する。
  **対象本体(TARGETS)は必ずあなたが直接 Read する**(二重要約で芯がぶれるのを防ぐ)。
  委譲した資料は HTML の出典表に「サブエージェント経由の要約」と明記する。

`KIND` が `html-js` の資料は、タグを剥がすだけでは中身が取れない。**`<script>` 内のデータ配列まで読む。**

### Stage 5: HTML の執筆

**出力先: `work_html/YYYYMMDD-<slug>.html`**(日付は `date +%Y%m%d` で取得。`<slug>` は内容が分かる短い kebab-case)。
引数で出力先の指定があればそれに従う。

> `work_html/` は `.gitignore` 済みの使い捨て領域。**気に入ったものは開発者が手で
> `docs/human-notes/html-reports/` へ移す**運用なので、本コマンドは `html-reports/` へ直接書かない。

#### 技術要件

- **自己完結・単一ファイル**。CSS はインライン `<style>`。**外部リソース参照を一切しない**
  (外部フォント・CDN・画像 URL すべて禁止。オフラインで開ける状態にする)。
- **light / dark 両対応**(`@media (prefers-color-scheme: dark)` で CSS 変数を切り替える)。
- 日本語フォントスタック(例: `"Hiragino Sans", "Noto Sans JP", "Yu Gothic UI", sans-serif`)。
- **表は `overflow-x: auto` のラッパで囲む**(横スクロールが本文に漏れないように)。
- 本文幅は `max-width: 880px` 程度に制限し、行間は広めに取る。
- 既存の `docs/human-notes/ai-dev-assessment-report-20260725.html` の CSS が範。迷ったらこれに倣う。

#### 分量方針

**既定は圧縮方向。** 元の md が「情報過多」であることが動機なので、原本を並べ直しただけの HTML には価値がない。
版数注記・改訂履歴・定型の前置きは削り、**判断・結論・根拠・未確定事項**を残す。
「全部載せ」は開発者が明示的に要求したときだけ。

#### 必須の構成

1. **ヘッダ** — タイトル / 生成日 / 生成元(`/docs_to_html <引数>`)
2. **冒頭サマリ** — これを読めば大筋が分かる数行。分析軸があればその答えを先に置く
3. **本編** — 分析軸の指示があれば**章立てをその軸に組み替える**(原本の章順に引きずられない)
4. **出典表** — 採用した資料の実パスと本文サイズ。サブエージェント委譲分はその旨を明記
5. **未展開の参照** — 予算で落とした参照、および原本が存在しなかった参照(`MISSING`/`UNRESOLVED`)
6. **注意書き** — 「本 HTML は要約であり、正は原本の md/HTML 側。齟齬があれば原本を信じること」

### Stage 6: 報告

- 出力パス
- 採用 / 未採用の内訳(件数とサイズ)
- 意図的に省いた論点、および読んでいて気づいた**原本側の不整合**(あれば)

## 注意

- `docs-map.md` は派生資料のため陳腐化しうる。スクリプトは docs-map を引いた後に
  全 docs 索引へフォールバックするが、**解決結果が直感と違う場合は実パスを確認する**。
- `MENTIONS` は言及の厚みを示す目安スコアであり、厳密な出現回数ではない
  (パス表記と文書ID表記の両方で言及された資料は合算される)。順位付けの参考程度に使う。
- 生成物以外のファイルは変更しないこと(スコープ厳守)。
