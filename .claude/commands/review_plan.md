## 引数バリデーション（最初に必ず実行）

引数: `$ARGUMENTS`

### ステップ1: 引数の存在確認

引数が空または未指定の場合:
- 作業を停止し、`docs/instructions/` 直下のファイル一覧を表示して、以下を伝える

```

```

### ステップ2: 引数の正規化と完全一致の確認

引数から次を取り除いて **指示書指定** を得る。以降の手順ではこの正規化後の文字列を使う。

- 先頭の `docs/instructions/`（フルパスで渡された場合。取り除かないとパスが二重になる）
- 末尾の `.md`

照合は **大文字小文字を区別しない**（`m7-02-e2e-scenarios.md` のような小文字始まりの実ファイルがあるため）。

`docs/instructions/{指示書指定}.md` が存在するか確認する（`find` または `ls` で確認）。

- 存在しない場合: ステップ3-1 へ

### ステップ3-1: 候補ファイルの探索と確定

> `reviews/M20-01-review-checklist.md` の 2 件に当たり、接頭語指定が常に曖昧化する。
> phase サブディレクトリ配下（M13〜M18 の過去指示書）を対象にしたい場合は、開発者がフルパスを引数に渡す。

| 順 | 規則 | 引数 `M14-03` での結果 |
|----|------|----------------------|

### ステップ3-2: レビュー済みチェック（安全網）

接頭語指定は打鍵が短い分、**別サブと取り違える危険が上がる**。確定した指示書について、
**同じサブのレビュー報告書が既に存在しないか**を `docs/progress/` の **ファイル名** で確認する。

> **本コマンドでは製造成果物（completion-report 等）が存在するのは正常状態**である（レビューは実装後に走るため）。
> したがって判定に使うのは **`{小文字タスク識別子}-review*.md` の有無だけ**とする。
> 再レビューは停止規律の「再レビュー往復上限 2 回」（本ファイル末尾）に関わるため、気づけること自体に価値がある。

確定ファイル名からタスク識別子（ステップ4 と同じ導出＝先頭2セグメント）を取り、次を実行する。
**`docs/progress/` は `phase1/` `phase2/` `phase3/` のアーカイブを含めて再帰探索する**（ステップ3-1 の直下限定とは非対称）。

```bash
find docs/progress -type f -name '*.md' -printf '%P\n' | grep -iE "(^|[-/])<タスク識別子>-review"
```

> **★境界付きで照合すること**（識別子の直前が行頭か `-` か `/`、直後が `-review`）。
> 単純な部分一致だと `M19-04` が `m19-04b-review.md` / `m19-04c-*` / `m19-04d-*` まで拾い、
> **枝番のサブのレビューを本体のものと誤認する**。

**1件以上ヒットした場合**: 以下を提示して確認を求め、**承認が得られるまでステップ4 以降に進まない**
```
⚠ このサブは既にレビュー済みの可能性があります: docs/instructions/{確定ファイル名}
  docs/progress/ に以下のレビュー報告書があります:
    {ヒットしたファイルのパス一覧}
  それでもレビューを実施しますか？（再レビューであれば「はい」。再レビューの往復上限は 2 回）
```

**0件の場合**: 何も表示せずステップ4 へ進む。

> **本検査は証跡の有無を見るだけの安全網であり、レビュー済みか否かの判定機ではない。**
> ヒットしなかったことを「未レビューの保証」と読まないこと。

## 優先度の較正

**「撤回済み・失効した記述がコード上に残っている」は「高」に置くこと。**

コメント・godoc・DTO の値域注記・i18n 文面などで、**実装が変わったのに記述が旧のまま残っている**状態を指す。体裁の問題に見えるため「低」へ落としやすいが、本プロジェクトでは「高」として扱う。理由は 2 つ。

- **通常のテストでは検出できない。** 動作は正しいままなので、テストも lint も型検査も緑になる。人が読む以外に見つける経路が無い。
- **後任は本文をコピーし、注記を読まない。** 旧の記述が次のサブの前提として複製される（`M19-DESIGN-08` §3.1 の D-250 と同型）。

> **実測**: 2026-08-11 の A/B 評価（`docs/progress/20260811-context-load-ab-expansion.md` §1.3）で、この型の指摘（M19-05 の撤回済みコメント 3 か所）を検出した 5 本が **全員「低」に置いた**。正解は「高」である。**見落としではなく優先度較正のずれ**だったため、基準として明示する。

## 完了時: 書いた報告の「閉じない強調」を自分で検査する（必須）

<!-- COMPLETION-REPORT-MD-EMPHASIS -->

この手番で書いた**レビュー報告書** `docs/progress/<タスクID>-review.md` を、`check-md-emphasis.sh` の**ファイル引数モード**へ渡す（2026-09-07・`D-761` 案 A）。**★実測の先例はここである**——`M28-02c` のレビュー報告書がコードを引用した 1 行で、床が 495 から 496 になった。

```bash
bash scripts/check-md-emphasis.sh docs/progress/<この手番で書いたファイル>.md
```

- **非ゼロで終わったら、自分で直してから完了とする。** 直しかたは「閉じ `**` の直前の約物を強調の外へ出す」（`**A（B）**は` → `**A**（B）は`）。
- **★`docs/progress/` は常時走査の対象ではない**（2026-09-07 に外した）。**⇒ ここで見なければ、誰も見ない。**
- **★外した理由は「見なくてよくなった」ではない。** 常時走査は「増やした本人が直す」を前提とするが、**完了報告は歴史記録として書き換えない**（`D-274` (3)）。**2 つの規則が食い違い、誰も直さないまま床だけが上がっていた。⇒ 変わったのは検査の時点だけである。**
- **★読めない行が残ると、次の担当が事実を取り違える**（`M20-07` と `M21-06` が独立に申し送った）。**この 1 行はその実害を防ぐためにある。**
- **★継続更新ファイル（`docs/progress/progress-log.md` 等）は渡さない。** 同ファイルは**歴史記録としての既存の検出行**を持ち、それらは直さない（`D-274` (3)）。**渡すのはこの手番で作った／書き足した報告書だけである。**
- **★検出が出たら、行番号で「自分が書いた行か」を判定し、自分の行だけを直す。** 既存行の是正は別の手番である。
- **★フェンス（3 連バッククォート）内のコード引用は構造上かならず偽陽性で当たる**（`followup` の `md-emphasis-check-fenced-block-false-positive`）。**逐語引用が理由で直せない行は、直さずに完了報告へその旨を 1 行残す。**

## 停止規律（往復上限と未解消項目の扱い）

<!-- STOP-DISCIPLINE -->

- **再レビューの往復上限は 2 回**（初回 ＋ 再レビュー 1 回）。上限に達したら未解消項目を列挙して開発者裁定へ回し、**無限ループにしない**（開発者裁定・2026-08-10。`CLAUDE.md` §9「停止規律」）。
- 上限（往復上限 2 回 / タイムボックス / 開発者の終了指示）に達したときは、報告書の `## 未解消のまま停止した項目` へ **ID（スラッグ）／未解消の理由／再開に必要な条件** を付けて列挙し、**直ちに停止する**。
- **本コマンドは read-only のため、`docs/handover/followup-backlog.md` は 1 文字も編集しない**（ファイル作成はレビュー報告書のみ）。**★★★【2026-09-12 変更＝`D-838`】§J へ書けるのは設計卓だけになった。⇒ 取り込み側**（`/incorporate_plan` ／ `/implement_plan_full` Phase C）**も直接は書かず、設計伝達レポート §4 へ「§J 行の原稿」として出す。★設計卓が受理の手番で転記する。** **⇒ 本コマンドは報告書の `## 未解消のまま停止した項目` 節に必須 5 フィールドを揃えて書くところまでを担う。**
- **記録して停止することは失敗ではなく正規の完了形式である。** 記録せずに完成度の追求を続けることが規律違反にあたる。「これが最後」の指示を受けたターンでは、新たな指摘の掘り起こしを開始せず、残項目の記録に切り替える。
- 検査: `bash scripts/check-stop-discipline.sh`

## 重要なルール

- コードは一切変更しないこと（Read ツールでの読取のみ）
- ファイル作成は上記レビュー結果ファイルのみ
- Git の書き込み操作（コミット含む）はしないこと。本コマンドは read-only のレビュー専任のため、変更点の確認には `git status` / `git diff` / `git log` 等の読み取り系のみ使用してよい
- 不明点があれば「不明: ○○について判断できない」と報告書に記載し、推測で進めない
