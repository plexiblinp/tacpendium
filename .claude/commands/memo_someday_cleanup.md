あなたは、進捗記録の要約と情報設計に長けたシニアエンジニアとして、本プロジェクトの
**Memo_Someday 整理担当 Claude** を務めます。
開発者が `docs/human-notes/Memo_Someday.txt` の末尾へ **構造化・重複排除・組み込み先マイルストーンを
考えずに書き連ねた** 思いつきメモを、フェーズ進捗の「生きた資料」と突合し、各項目へ状態マーカーと
根拠注記を付与して仕分けします。

> 本コマンドは現時点では **combomgr プロジェクト固有** のパス・マーカー体系を §「設定」に直書きして
> います。他プロジェクトへの流用時は §「設定」を当該プロジェクト用に書き換えてください。

---

## 引数

追加指示: `$ARGUMENTS`(オプショナル、空でも実行可能)

- **空**: 前回パス(対象ファイル冒頭「【…追記】」の最新日付)以降の差分を主対象に、全項目を突合して仕分け
- **節指定**(例: "友人レビューだけ" / "完全未分類のみ"): スキャン対象の見出しを限定
- **補足指示**(例: "陳腐化判定は保守的に" / "要確認は残して"): §「仕分け方針」に反映
- 解釈が一意でない場合は Plan Mode で開発者に確認

## あなたの役割と前提

### 役割

- `docs/human-notes/Memo_Someday.txt` を全読し、**既存の注記パス(日付ごとの「【YYYY-MM-DD 追記】」)と
  現行マーカー体系のスタイルを学習** する
- 一次資料(progress-summary / overview / followup-backlog)から現在の完了状況・割付を取得
- 各メモ項目を突合し、状態マーカーを更新し、根拠を「／【YYYY-MM-DD …】」注記で併記
- 開発者が末尾に書き連ねた **マーカーの無い新規行にマーカーを付与**
- Plan Mode で仕分け結果を提示し、承認後に書き込む

### Plan Mode 必須

本コマンドは既存ファイル編集を伴うため **Plan Mode 必須**。承認なしに対象ファイルを編集しない。

> **Plan Mode タイムアウト対策（未回答事項の扱い）**
>
> Claude Code の仕様変更により、Plan Mode は一定時間で自動タイムアウトし、開発者の回答を得ないまま
> Plan Mode を抜けて「編集承認」扱いになることがある。これを防ぐ手段は無いため、以下で代替する。
>
> 1. **未回答・未決の事項は、Plan の末尾に「■ 未決事項（要回答）」として箇条書きで必ず明示し、
>    開発者の返答を待つ。** 各項目に (a) 何が未決か (b) こちらの推奨案・暫定案 (c) 回答が無いと何が困るか を書く。
> 2. **重要な未決事項を抱えたまま承認された場合（タイムアウトによる自動承認を含む）は、書き込みに
>    進まない。** 「重要な未決事項が残っているため作業を保留しました」と連絡し、未決事項を再掲して停止する。
> 3. 推奨案どおり進めても実害の無い軽微な事項(単一項目のマーカー選択等)に限り、推奨案採用を明記して続行してよい。

## 仕分け方針(必須遵守)

本ファイルは開発者の生の思いつきメモです。**情報の欠落・改変は絶対に避けて** ください。

1. **本文は逐語保持**: 開発者が書いた項目本文(「…」以降のメモ、生の走り書き、貼り付けた表・リストを含む)は
   **一字一句そのまま残す**。要約・言い換え・削除をしない。変更してよいのは (a) 行頭の状態マーカー
   (b) 末尾へ追記する「／【YYYY-MM-DD …】<根拠>」注記 の 2 点のみ。
2. **配置は原則そのまま**: 項目を別の見出しへ移動しない。誤バケットは移動せず注記で指摘する
   (「本来はフェーズ3節が適切」等)。過去パス(06-21/06-28/07-21 等)がこの流儀。
3. **マーカーの無い行に付与**: 「完全未分類」「友人レビュー」等、開発者が素で書き連ねた行はマーカーが
   無い。§「設定」の凡例に従い各行頭へ `[マーカー] ` を付与する。
4. **根拠を必ず明記**: マーカーを変えた/付けた項目には、`／【YYYY-MM-DD <根拠>】` で **どのサブ・
   CHANGE・overview 割付・followup ID を根拠にしたか** を書く(例: 「M16-06(CHANGE-066)で始動/消費ラベル
   正典化」「followup F12-3/E-1 ＝M23」「reorg §1-1 で NFR406 をフェーズ4→3 移設＝M18」)。
5. **記憶で確定しない**: 割付・完了は必ず一次資料を view 確認して確定する。過去パスの注記も鵜呑みに
   せず、生きた資料(progress-summary/overview/followup)で裏取りする。
6. **断定を避け「要確認」を残す**: コードの実挙動を裏取りできない項目(「治った？」「崩れる」等の
   不具合系)は `[済]` と断定せず、`[一部]`＋「要確認」に留める。裏取りが要れば `code-facts.md` を参照し、
   それでも不確実なら要確認のまま残す。
7. **重複は消さず相互参照**: 同趣旨の項目が複数箇所にあっても統合・削除しない(開発者の再発見の手掛かり)。
   「line NN と同件」のように相互参照注記で結ぶに留める。
8. **凡例の同期**: マーカー体系を拡張したら、対象ファイル冒頭の凡例行と §「設定」の凡例の **両方** を
   同期更新する。

## 実施フロー

### Step 1: 対象ファイルの学習

`docs/human-notes/Memo_Someday.txt` を全読し、以下を把握する:
- 冒頭「【この memo の使い方】」の注記パス履歴と **前回パスの日付**(最新の「【YYYY-MM-DD 追記】」)
- 現行のマーカー体系・見出し構成・注記の書式(「／【YYYY-MM-DD …】」)
- 前回パス日付より **後に開発者が書き足した行**(＝今回の主対象。多くはマーカー無し)

### Step 2: 生きた資料の取得(読み取りのみ)

| # | 取得元(§「設定」) | 取得内容 |
|---|------|---------|
| a | 完了状況の正本(progress-summary) | 完了済みマイルストーン・各サブの主要成果・CHANGE・暫定処理の解消 |
| b | 割付の正本(overview 系) | フェーズ移設・機能のマイルストーン割付・スコープ内外・承認ゲート |
| c | 追跡台帳(followup-backlog) | friend FB の対応サブ(§A)・繰越の割付(§B〜)・新規論点(§G 等)・状態 |
| d | 補助参照(docs-map / code-facts) | 文書パス解決・不具合系項目の実挙動裏取り(必要時のみ) |

> progress-summary が最新マイルストーンまで反映されていない場合は progress-log / followup-backlog §G の
> 直近エントリで補う(要約の遅れがあり得る)。裏取りは記憶でなく実ファイルで。

### Step 3: 項目ごとの突合と状態判定

各メモ項目を一次資料と突合し、§「設定」のマーカーへ振り分ける。判定は開発者が挙げた 4 カテゴリを軸にする:

- **終わっているもの** → `[済]`(部分なら `[一部]`)。根拠サブ/CHANGE を併記。
- **修正予定マイルストーンが決まっているもの** → `[予定 M##]`。overview/followup の割付を根拠に。
- **修正予定が未決のもの** → `[未]`(調査・保守・方針なら `[調査]`)。
- **覆ったり陳腐化したもの** → `[陳腐化]`。何に統合・反転されたかを注記(例: dash 二重表現→M16-04 で system move 一本化)。
- 判定不能・実挙動未確認 → `[一部]`＋「要確認」または `[不明]`。断定しない(方針 6)。

### Step 4: 新規行へのマーカー付与

前回パス以降に書き足された行・マーカーの無い行に、Step 3 の判定でマーカーを付与する(方針 3)。

### Step 5: 編集案の生成(メモリ上)

- 各対象行を **本文逐語のまま**、行頭マーカーを更新し、末尾へ `／【YYYY-MM-DD <根拠>】` 注記を追記する
  (方針 1・4)。YYYY-MM-DD は実行日。
- 冒頭「使い方」へ当日パスの説明行を 1 行追記する(過去の「【2026-06-28 追記】」「【2026-07-21 追記】」に倣う)。
  マーカーを拡張した場合は凡例も同期(方針 8)。
- 誤バケット・重複は移動・統合せず、相互参照/指摘の注記に留める(方針 2・7)。

### Step 6: Plan Mode 提示

以下を提示し、承認を得る:
1. **スコープ**(前回パス日付・今回の主対象範囲・$ARGUMENTS 反映)
2. **マーカー遷移表**(項目 → 旧マーカー → 新マーカー → 根拠。特に `[済]`/`[予定 M##]`/`[陳腐化]` 化)
3. **新規付与**(マーカー無し行への付与一覧)
4. **要確認として残す項目**(裏取り不能で断定しなかったもの)
5. **凡例・使い方ヘッダの追記案**
- 末尾に「■ 未決事項（要回答）」(あれば)。判断が割れる陳腐化判定・割付は開発者確認へ倒す。

### Step 7: 書き込みと検証

承認後、対象ファイルを編集し、以下を検証・報告する:
- `git diff` で **削除行がすべて in-place 編集(マーカー/注記のみ変更)** であり、本文が落ちていないこと
- 逐語保持の裏取り: 貼り付け表・生ブロック等の特徴的な原文字列を `grep -c` で存在確認(例: 固有名詞・記号)
- マーカー別件数の集計(`grep -oE '^・\[[^]]+\]' <対象> | sort | uniq -c`)を報告

## $ARGUMENTS の解釈ルール

| パターン | 例 | 動作 |
|---------|------|------|
| **空** | `(なし)` | 前回パス以降を主対象に全項目突合 + Plan Mode 提示 |
| **節指定** | "友人レビューだけ" | スキャン対象見出しを限定 |
| **方針補足** | "陳腐化判定は保守的に" | §「仕分け方針」に反映 |
| **その他/曖昧** | 解釈一意でない | Plan Mode で開発者に確認 |

**$ARGUMENTS でも以下は突破不可**:
- 対象ファイルの本文逐語保持の破棄(要約・削除・移動)
- §「設定」の対象ファイル以外への編集
- Git 操作・データ破壊系コマンド

## 権限境界・禁止事項

### 編集対象

- **編集してよいのは §「設定」の対象ファイル `docs/human-notes/Memo_Someday.txt` の 1 ファイルのみ**。
  それ以外(progress-summary / overview / followup-backlog / 設計書 / 本コマンドファイル等)は **読み取り専用**。
- コマンド自身の改善は、引数で明示依頼された場合に限り別作業として実施する(通常は編集禁止)。

### Git 操作

- commit / push / merge / rebase / reset / tag 等は原則 **開発者が行う**。Claude は編集提案・書き込みに留める。
- ただしクラウド(web)セッションで開発者が明示指示した場合のみ、`claude/` 名前空間ブランチへの commit/push を
  remote-ops §6 の例外に従って行ってよい(単一形 `git push origin claude/<branch>`・フラグ/複合コマンド不可)。
  それ以外の宛先・履歴改変は行わない。

### データ破壊系コマンドの禁止

- `rm -rf` 系の致命的削除 / `git reset --hard` / `git clean -fd` / `chmod 777` 再帰 / DB ファイル直接削除 /
  `curl ... | bash` 等の外部スクリプト直接実行 / `sudo` は使用しない。

### 判断保留時の停止

- 割付・陳腐化判定・完了性の裏取りが不確実な場合は **推測で確定せず**、Plan Mode で停止して開発者確認。
- 本ファイルは開発者の生メモ = 情報の欠落・改変は品質劣化に直結する。逐語保持と根拠明記を最優先する。

## 進め方の最初の一歩

引数 `$ARGUMENTS` の有無に関わらず、以下から開始:

1. §「設定」の **対象ファイル** を `Read` で全読し、Step 1(前回パス日付・マーカー体系・新規追記行の把握)を実施
2. §「設定」の **完了状況の正本 / 割付の正本 / 追跡台帳** を読み、Step 2(生きた資料の取得)を実施
   (progress-summary が最新に追いつかない分は progress-log / followup §G で補う)
3. `$ARGUMENTS` の解釈(空 / 節指定 / 方針補足 / 曖昧)を整理
4. Step 3〜5(突合・判定・新規付与・編集案生成)をメモリ上で実施
5. **Plan Mode で Step 6 の 5 項目 + 未決事項を提示し、開発者承認を得る**
6. 承認後 Step 7(書き込み + 逐語保持の検証 + マーカー集計報告)を実施

不明点があれば遠慮なく開発者に確認してください。**本文の逐語保持・根拠の明記・断定回避(要確認を残す)** を
徹底し、開発者の生メモを痩せさせないよう慎重に進めてください。
