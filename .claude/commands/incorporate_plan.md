あなたは高度なソフトウェアアーキテクト兼シニアエンジニアとして、格納されたレビュー結果を取り込み、修正前に計画を提示します。
**最初に以下のバリデーションを行い、問題があれば作業を中断して確認を求めてください。**

## 引数バリデーション（最初に必ず実行）

引数: `$ARGUMENTS`

### ステップ1: 引数の存在確認

あなたが製造担当として作業済み、かつ、引数が空または未指定の場合:
- `docs/progress/` 配下の `*-review.md` ファイル一覧から、あなたが製造を実施したマイルストーンのファイルを見つけて、以下を伝える

```
引数が指定されていません。
以下のファイルを対象に作業を実施してもよろしいですか？
例（あなたがm1-03の実装を担当済みの場合）: docs/progress/m1-03-review.md
```

引数が空または未指定の場合:
- 作業を停止し、`docs/progress/` 配下の `*-review.md` ファイル一覧を表示して、以下を伝える

```
引数が指定されていません。
指示書のファイル名を引数に指定してください。
例: /incorporate_plan M1-03-combo-crud-api.md
```

### ステップ2: レビュー結果ファイルのパス導出

引数からレビュー結果ファイルのパスを導出する。
例として `M1-03-combo-crud-api.md` を使って示します:
- タスク識別子（先頭2セグメント、`-`区切り）: `M1-03`
- 小文字に変換: `m1-03`
- レビュー結果パス: `docs/progress/m1-03-review.md`

引数が `M{X}-{YZ}` 形式（例: `M1-03`）の場合も同様に導出する。

### ステップ3: レビュー結果ファイルの存在確認

導出したパスのファイルが存在するか確認する（`find` または `ls` で確認）。
- 存在する場合: 「作業手順」へ進む
- 存在しない場合: ステップ4へ

### ステップ4: 候補ファイルの探索

`docs/progress/` 配下の `*-review.md` 一覧を取得し、候補を探す:
- 導出した小文字タスク識別子（例: `m1-03`）に **セグメント境界付きで** 一致するファイルを探す。
  すなわち識別子の直前が行頭か `-` か `/`、直後が `-` であること

> **★境界付きで照合すること。** 単純な部分一致だと `m19-04` が `m19-04b-review.md` /
> `m19-04c-*` / `m19-04d-*` まで拾い、**枝番のサブのレビューを本体のものと誤認する**。
> 本プロジェクトには `M14-03` と `M14-03a`〜`M14-03e`、`M19-04` と `M19-04b`〜`M19-04d` のように、
> 枝番付きの兄弟が同じ数字で始まる組が実在する。

**候補が1件のみ**: 以下を表示して確認を求め、承認後のみ続行する
```
レビュー結果ファイルが見つかりませんでした: docs/progress/{導出パス}
以下のファイルを使用しますか？
  docs/progress/{候補ファイル名}
「はい」と返答いただければ続行します。
```

**候補が0件**: 作業を停止し、以下を表示して終了する
```
レビュー結果ファイルが見つかりませんでした: docs/progress/{導出パス}
・引数のファイル名が正しいか確認してください: $ARGUMENTS
・または、レビューがまだ完了していない可能性があります
docs/progress/ 内のレビュー結果一覧:
  {ls 結果}
```

**候補が2件以上**: **停止・終了しない**。番号付きで候補を提示して選択を求め、回答を得た候補で続行する
```
レビュー結果ファイルの候補が複数あります:
  1) docs/progress/{候補1}
  2) docs/progress/{候補2}
番号でお選びください（該当が無ければ正しいファイル名をお知らせください）。
```

## 作業手順（バリデーション通過後に実行）

確定したレビュー結果ファイルを確認し、指摘内容を評価して
**取り込むべきもの・取り込む必要がないもの** に整理して、修正計画を立ててください。

計画への承認を待ってから修正実装に入ること。

> **Plan Mode タイムアウト対策（未回答事項の扱い）**
>
> Claude Code の仕様変更により、Plan Mode は一定時間で自動タイムアウトし、開発者の回答を得ないまま Plan Mode を抜けて「編集承認」扱いになることがある。これを防ぐ手段は無いため、以下で代替する。
>
> 1. **未回答・未決の事項は、プラン（提示）の末尾に「■ 未決事項（要回答）」として箇条書きで必ず明示し、開発者の返答を待つ。** 各項目に (a) 何が未決か (b) こちらの推奨案・暫定案 (c) 回答が無いと何が困るか を書く。
> 2. **重要な未決事項を抱えたまま編集が承認された場合（タイムアウトによる自動承認を含む）は、実装・編集・成果物生成を行わない。** 代わりに「重要な未決事項が残っているため作業を保留しました。以下について回答をお願いします」と連絡し、未決事項を再掲して停止する。
> 3. 推奨案どおり進めても実害の無い軽微な事項に限り、推奨案を採用した旨を明記した上で続行してよい。重要度の判断に迷う場合は「重要」側に倒し、停止して確認する。

## 修正実装時: 新規ファイルを作る前の同名確認（必須）

<!-- NEW-FILE-OVERWRITE-GUARD -->

**「新規ファイルを作る」ときも、作る前に同名の存在を確かめる**（教訓 `E-225` ／ 出所 設計伝達レポート **M23-08 §7-1**）。
**★取り込み工程でも新規ファイルは生まれる**——**レビュー指摘に応えてテストを足す**のが典型で、
`m23-06` は実際に取り込みで破壊確認テストを新設している。**製造 CLI 3 本すべてで守ること。**

- **(a) 作る前に確かめる。** Write の前に `ls` / `find` / Glob で同名の有無を見る。
  **「新規のつもり」は確認の代わりにならない。**
  **★在ったら上書きしない。** 足すなら Edit、別物なら別名にする——M23-08 の是正も、
  新規テストを `setup_carry_trashed_link_test.go` へ**分けた**。
- **(b) `git diff --stat <着手基点>` を読み、「新規のつもりのファイルが `+` だけか」を 1 度確かめる。**
  **deletions のある新規ファイルは、それ自体が矛盾している。**
  **★取り込みでは着手基点が実装完了時点になる**——実装時の統計をそのまま見ても、
  取り込みで消した行は映らない。

> **★根拠（M23-08 で実際に起きたこと）。** `setup_carry_trashed_test.go` を新規のつもりで書き、
> **M23-02 が入れた回帰テスト 3 本を一度消した。**
> **上書きは `go test` を緑のまま通す**——消えたテストは走らないだけであり、
> **テストも lint も型検査も何も言わない。**
> 気づけた唯一の経路は、**変更統計の deletions を読んだこと**であった。

- **各指摘の採否と理由**——**★詳細はレビュー報告書側が正本であり、完了報告には件数と「不採用にしたものの一覧」だけを置く**（同じ本文を 2 か所に持たない＝教訓 `E-76`）

**★プレースホルダが残っていないかを最後に確認する。** 「`incorporate_plan` で埋める」という文字列が完了報告に残っていたら、埋め忘れである。

> **★根拠（`M23-04`・ボード `D-510`）。** レビュー前に書かれた断定が訂正されないまま残ると、**`progress-log` は横断インデックスであるため、次のサブと設計卓が前提としてそのままコピーする**（`CLAUDE.md` §8）。**★機械検査では見つからない**——動作は正しいままなのでテストも lint も型検査も緑になる。

## 全数テストの合否は、パイプを挟まずに判定する（必須）

<!-- FULL-TEST-RUN-EXIT-CODE -->

**★★★`go test ./...` / `pnpm test` / `make e2e` の合否を、パイプ越しに判定してはならない。**

```bash
go test ./... > /tmp/gotest.txt 2>&1; echo "EXIT=$?"
grep -cE "^--- FAIL" /tmp/gotest.txt
```

**★★実際に落ちた例**（`M37-05`・2026-09-13）**＝製造は `go test ./... 2>&1 | grep -v "^ok\|no test files" | head -20` で確認し、「緑（exit 0）」と完了報告へ書いた。⇒ 実際は赤であった。**

**★★★破れ方が 2 つ重なっている。**

| # | 破れ方 |
|---|---|
| **1** | **`head -20` が `FAIL` 行を切り落とした** |
| **2** | **読んだ終了コードは*パイプ末尾のコマンド*のものであった。⇒ `go test` の終了コードではない** |

**★同じ型を同じサブでもう 1 度踏んでいる**——**`make e2e` の出力を `| tail -45` で取ったため、既存 spec の個別行が残らず、「影響を受けなかった」の根拠が*全体の結果*しか無い状態になった。**

**⇒ 出力はファイルへ全量を落とすこと。★「失敗 0 件」だけでは、どの spec が走ったのかを後から示せない。**

**★★完了報告に「緑」と書くときは、上の 2 行の実行結果**〔`EXIT=0` と `FAIL` の件数〕**を貼ること。⇒ 貼れないなら、まだ確かめていない。**

### ★★★一般形＝**全数を数えるための出力を `head` / `tail` で切らない**（2026-09-14 追加＝`D-881`・`M37-07` §7-1）

**★上の節はテスト出力を対象に書かれていたが、真の一般形はこれである。⇒ 対象が `grep` へ移っただけで同じ穴に落ちた。**

**★★実際に落ちた例**（`M37-07`・2026-09-14）**＝重複判定キーの*足し先を数える*ための `grep` を `| head -20` へ通した。⇒ 20 行で切られ、`internal/service/validation/duplicate.go` 以降が視界に入っていなかった。**

**★★★しかも `--include=*.go` しか掛けておらず、フロント**〔`*.tsx`〕**を一度も走査していない。⇒ 失効記述 11 箇所を取りこぼし、レビューが検出した。**

| 用途 | やること |
|---|---|
| **足し先を数える** | **出力をファイルへ全量落とし、`wc -l` で件数を出す。⇒ 目で 20 行読んで済ませない** |
| **走査の範囲** | **`--include` を絞るなら、絞った理由を書く。⇒ 「Go だけ見た」と書けないなら絞らない。★本リポジトリは同じ概念が Go とフロントの両方に居る** |
| **完了報告** | **件数と、数えたコマンドそのものを貼る** |

### ★★「テストが緑」を数え切った証拠として扱わない（同上）

**★★★環境変数で走行が切り替わるテストは、その環境でしか観測できない。**

**★実例＝`existing_duplicates_audit_test.go` はキーを独立に再実装しているが、`TACPENDIUM_AUDIT_DB` 未設定なら skip される。⇒ 追随を落としても `go test ./...` は緑のままであった。**

**★★計画段階では「追随が要る」と一覧に挙げていたのに、実装で落とした。⇒ 一覧に挙げたものは、緑ではなく*一覧*で消し込むこと。**

### ★★★完了報告を入力に取る検査は、**報告を書き終えた後にもう一度回す**（2026-09-17 追加＝`D-890`・`M36-01` §7-1）

**★★★実際に起きたこと**（`M36-01`）**＝`check-progress-log-index.sh` を回して EXIT=0 / 112 件を得て、その値を完了報告の表へ書いた。⇒ その後に完了報告そのものを作成したことで、同検査は「対応する `progress-log` の追記が無い」を検出して*赤へ変わった*。★製造は気づかず、赤い検査を緑と書いた表を残した。**

**★★検査を回した時点と報告を書いた時点がずれると、「緑」が偽になる。⇒ 完了報告は*検査の入力*でもあるからである。**

| 報告を書いた後にもう一度回すもの | なぜ |
|---|---|
| **`check-progress-log-index.sh`** | **完了報告の存在が入力である。⇒ 書いた瞬間に「索引行が無い」が成立する** |
| **`check-completion-report-md-emphasis.sh`** | 完了報告そのものを見る |
| **`check-doc-inventory.sh`** | 新しい文書が増えたことを見る |

**★★★あわせて「完了条件を*未来形*で満たしたことにしない」。⇒ 根拠欄に「Phase D で実施」と書いて完了条件を「満たす」とするのは `D-510` と同型である。**

**★人が読む以外に見つける経路が無い。⇒ `go test` も lint も型検査も文書を見ない。★本件を検出したのは、レビュアーが報告を読むだけで済ませず自分で検査を回したからである。**

## 完了時: 書いた報告の「閉じない強調」を自分で検査する（必須）

<!-- COMPLETION-REPORT-MD-EMPHASIS -->

この手番で `docs/progress/` へ**新規に作った報告書 ＋ 書き足した報告書**を、`check-md-emphasis.sh` の**ファイル引数モード**へ渡す（2026-09-07・`D-761` 案 A）。**★取り込みは既存ファイルを編集する手番である。⇒ 新規だけを見ると漏れる**——完了報告の追記・レビュー報告書の追記も渡すこと。

```bash
bash scripts/check-md-emphasis.sh docs/progress/<この手番で書いたファイル>.md
```

- **非ゼロで終わったら、自分で直してから完了とする。** 直しかたは「閉じ `**` の直前の約物を強調の外へ出す」（`**A（B）**は` → `**A**（B）は`）。
- **★`docs/progress/` は常時走査の対象ではない**（2026-09-07 に外した）。**⇒ ここで見なければ、誰も見ない。**
- **★外した理由は「見なくてよくなった」ではない。** 常時走査は「増やした本人が直す」を前提とするが、**完了報告は歴史記録として書き換えない**（`D-274` (3)）。**2 つの規則が食い違い、誰も直さないまま床だけが上がっていた。⇒ 変わったのは検査の時点だけである。**
- **★読めない行が残ると、次の担当が事実を取り違える**（`M20-07` と `M21-06` が独立に申し送った）。**この 1 行はその実害を防ぐためにある。**
- **★継続更新ファイル（`docs/progress/progress-log.md` 等）は渡さない。** 同ファイルは**歴史記録としての既存の検出行**を持ち、それらは直さない（`D-274` (3)）。**渡すのはこの手番で作った／書き足した報告書だけである。**
- **★検出が出たら、行番号で「自分が書いた行か」を判定し、自分の行だけを直す。** 既存行の是正は別の手番である。
- **★フェンス（3 連バッククォート）内のコード引用は構造上かならず偽陽性で当たる**（`followup` の `md-emphasis-check-fenced-block-false-positive`）。**逐語引用が理由で直せない行は、直さずに完了報告へその旨を 1 行残す。**

## 取り込み完了時: progress-log への追補（必須）

<!-- PROGRESS-LOG-INDEX -->

レビュー指摘の取り込みが完了したら、`docs/progress/progress-log.md` の **当該サブの既存節へ追補**する（`CLAUDE.md` §8。2026-08-11 開発者裁定④により製造 CLI 側へ組み込み）。

- **検査**: `bash scripts/check-progress-log-index.sh`（完了報告に対応する追記の欠落を検出する。**追補した直後に回して緑を確認する**）
- **検査機構そのものの健全性**: `bash scripts/check-artifact-integrity.sh`

  黙って緑を返す。本検査は各 `check-*.sh` の対照が**実際に走った証拠**と、派生資料の生成物健全性を見る）
