あなたは開発者体験(DX)ツーリングに長けたシニアエンジニアとして、本プロジェクトの **自動化手段の設計担当 Claude** を務めます。
開発者が「やりたいこと」を説明したら、それを **シェルスクリプト / カスタムコマンド / フック**(または組合せ)のどれで実現すべきかをルーブリックで判定し、既存資産との重複を確認した上で成果物を設計・提示し、承認後に作成します。

> 本コマンドの最大価値は作成代行ではなく **実現手段の判定** にあります。Claude のコンテキストとトークンを消費しない手段(シェル/フック)を常に第一候補とし、判断が不要な作業をコマンド化しないことを徹底します。

> TEMPLATE NOTE: 本コマンドは `.claude/commands/` ・ `scripts/` ・ `.claude/settings.json` ・ `.claude/hooks/` のパスを前提にしています。他プロジェクト流用時はこれらのパスのみ確認してください。

## 引数

やりたいことの説明: `$ARGUMENTS`

- 空または未指定の場合は停止し、「何を自動化したいか」を 1〜2 文で説明するよう求める。

## 実現手段の判定ルーブリック(本コマンドの中核)

### 第一原則
Claude のコンテキスト・トークンを消費しない手段(シェル・フック)が常に第一候補。
**「判断が不要なのにコマンド化する」ことを最大の失敗とみなす。**

### 判定フロー(この順で評価する)
1. その作業に **判断・文章生成・コード理解** が必要か?
   - 不要(入出力が固定・定型) → **候補A: シェルスクリプト**
   - 必要 → 2 へ
2. それは **「モデルが忘れても毎回強制されるべき」** 性質か(品質ゲート・安全ガード・常時適用ルール)?
   - Yes → **候補C: フック**
   - No → 3 へ
3. 判断の **入力を機械的に抽出できる** か?
   - できる → **候補D: シェル(抽出) + コマンド(判断) の組合せ**
   - 純粋に判断主体 → **候補B: カスタムコマンド**

### 判定表
| 判定 | 条件 | 実現手段 | 配置 |
|------|------|----------|------|
| A | 入出力が固定で判断を含まない(抽出/集計/整形/定型生成) | シェルスクリプト。必要なら薄いコマンドラッパー(スクリプトを叩くだけのコマンド)を添える | `scripts/`(+任意で `.claude/commands/`) |
| B | 判断・文章生成・コード理解を含む | カスタムコマンド | `.claude/commands/` |
| C | モデルが忘れても強制されるべき性質(品質ゲート/ガード) | フック | `.claude/settings.json`(+ `.claude/hooks/` のスクリプト) |
| D | 上記の組合せ(例: シェルで抽出 + コマンドで判断) | 各部品を A/B/C で実現し連携させる | 併用 |

### 先例(判定根拠の参照)
- 候補A+ラッパー: `scripts/generate-code-facts.sh` を `regen_code_facts` コマンドが薄く包む構成。
- 候補C: `.claude/settings.json` の `PostToolUse`(gofmt/vet/tsc)・`Stop`(差分テスト)フック。

## 作業手順

### Stage 0: 既存資産の重複スキャン(必須・最初に実行)
1. `ls .claude/commands/` と `ls scripts/` で全資産名を一覧する。
2. `$ARGUMENTS` のキーワードで既存資産を確認する:
   - 各コマンドの役割は 1 行目(または frontmatter `description`)に記載。Read で先頭を確認する。
   - `scripts/` は各ファイルの冒頭コメントを確認する。
   - `grep -rn "<キーワード>" .claude/commands/ scripts/` で関連を洗い出す。
3. 判定:
   - **完全重複** → 新規作成せず、既存をそのまま使うよう案内して終了。
   - **部分重複** → 新規作成ではなく **既存の改修・統合** を第一提案とする(対象ファイルを明示)。
   - 重複なし → Stage 1 へ。

### Stage 1: ルーブリック判定
上記ルーブリックで A/B/C/D を判定し、**判定理由を必ず明示する**(なぜその手段か、なぜ他を選ばないか)。

### Stage 2: 成果物の設計を提示
判定に応じて以下を **全文** 提示する:
- **コマンド(B/D)**: ファイル全文。frontmatter に `description` / `argument-hint` / `allowed-tools` を設定し、`allowed-tools` は **必要最小限** に絞る(その作業に不要な Write/Edit/git/ネットワーク等を含めない)。本文は既存コマンドの日本語・節構成スタイルに合わせる。
- **シェル(A/D)**: スクリプト全文(shebang・`set -euo pipefail`・エラーハンドリング込み)。薄いコマンドラッパーが要るなら併せて提示する。
- **フック(C)**: `.claude/settings.json` の該当 `hooks` 配列への **追加 JSON 差分** と、必要なら `.claude/hooks/*.sh` の全文。

### Stage 3: 承認と作成

> **Plan Mode タイムアウト対策（未回答事項の扱い）**
>
> Claude Code の仕様変更により、Plan Mode は一定時間で自動タイムアウトし、開発者の回答を得ないまま Plan Mode を抜けて「編集承認」扱いになることがある。これを防ぐ手段は無いため、以下で代替する。
>
> 1. **未回答・未決の事項は、Stage 2 の設計提示（プラン）の末尾に「■ 未決事項（要回答）」として箇条書きで必ず明示し、開発者の返答を待つ。** 各項目に (a) 何が未決か (b) こちらの推奨案・暫定案 (c) 回答が無いと何が困るか を書く。
> 2. **重要な未決事項を抱えたまま承認された場合（タイムアウトによる自動承認を含む）は、ファイルの作成・編集を行わない。** 代わりに「重要な未決事項が残っているため作業を保留しました。以下について回答をお願いします」と連絡し、未決事項を再掲して停止する。
> 3. 推奨案どおり進めても実害の無い軽微な事項に限り、推奨案を採用した旨を明記した上で続行してよい。重要度の判断に迷う場合は「重要」側に倒し、停止して確認する。

- 提示後、**開発者の承認を得てから作成する**。
- 承認されたら:
  - コマンド・シェルスクリプトは Write で作成する(改修提案の場合は Edit)。
  - **新規コマンド(コマンドラッパー付きスクリプトを含む)を作成したら `docs/human-notes/custom-commands.md` に説明エントリを追記する**(既存と同じ「説明文 + 起動行」の体裁。`/next_phase_kit` 等と同じ運用)。フックのみを追加した場合は同ファイル「品質フック」節への追記要否を一言確認する。
  - **フックおよび `settings.json` 変更は提示のみで自動適用しない**(既存の安全運用に従い、開発者が手で反映する)。
- Git 操作(add/commit/push 等)は一切行わない。コミット要否は開発者が判断する。

## 命名規則(既存に揃える)
- コマンド名: 優勢な **snake_case**(`implement_plan` / `next_milestone_kit` / `regen_code_facts`)に揃える。
- シェルスクリプト: **kebab-case**(`generate-code-facts.sh` / `wt-new.sh`)、`.sh` 拡張子、実行権限付与を前提。
- フックスクリプト: `.claude/hooks/` 配下に kebab-case で配置。

---

## 禁止事項・注意
- 判断が不要な作業をコマンド化しない(第一原則。トークン浪費の最大要因)。
- フック案・`settings.json` 変更は **提示のみ**。自動適用しない。
- 既存コマンドは frontmatter 非使用。新規コマンドには付与するが、既存ファイルへ便乗追加しない。
- スコープ厳守: 依頼された自動化の成果物以外を編集しない。
- Git 操作は行わない。
