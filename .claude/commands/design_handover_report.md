あなたは本プロジェクトの製造担当 Claude Code として、実装完了後に **親チャット(設計卓)** へ手交する「設計伝達レポート(**例外レポート**)」を生成します。指示書どおりに実装した内容は書かず、**①製造が独自に確定した実装仕様 ②契約・設計に反する独自判断 ③製造の判断 ④設計担当が未把握の残課題** に絞った差分レポートを作ることが目的です。

> 従来この種のレポートは開発者の都度依頼で手書きされてきた(例: `tmp/20260718-M17-05a-design-handover.md`)。本コマンドはその既運用の正式化であり、形式・粒度は実物に合わせる。

> **★宛先は「親チャット(設計卓)」である。** 親が必要とするのは**記録ではなく例外**であり、親は下記を読まない。したがって本レポートは「例外だけ」を返す設計になっている。用語として「中央」は使わない(並列期の中央は**反映係**を指し、親とは別層だった。**反映担当は 2026-08-11 に廃止**され責務は設計担当へ統合されたが、「中央」は依然として使わない——過去文書の「中央」が別層を指すため、混同を避ける)。
>
> **親が読まないもの(ファイル名単位・2026-08-11 開発者裁定①)**: `docs/progress/progress-log.md` ／ 個別の完了報告・レビュー報告(`docs/progress/<id>-completion-report.md` 等)。
> **例外**: `docs/progress/progress-summary.md` は**親が読む**。ただし**起動キットの投入資材として起動時に読む**ものであり、**進行中の随時参照はしない**(進行中の現在地の正本は `docs/process/parallel-board.md`)。
> 旧記載は「親は完了報告・progress ログを読まない」だったが、「progress ログ」が `progress-log.md` と `progress-summary.md` の双方を指しうるため、**起動キットが `progress-summary.md` を必須投入に含んでいる実態と衝突していた**。裁定の全文は `docs/progress/20260811-progress-doc-responsibility-rulings.md`。

## 源泉(読む順)

1. `docs/progress/<id>-completion-report.md` — **必須**。存在しなければ停止して開発者に報告する(源泉なしで作文しない)。特に §1(実査結果)・§3(推測で進めた箇所)・§5(DES 反映要点)・§6(申し送り)
2. `docs/progress/<id>-review.md`(`-report.md` 等の関連報告があればそれも) — 低指摘の繰越・制約事項
3. `docs/change-notes/` のうち当該サブに関連する CHANGE 通知書(あれば。特に §4 確定した設計判断・§7 開発者への確認事項)
4. `docs/instructions/<id>-*.md`(指示書) — **指示書明文と実装の乖離** の特定(乖離があれば最重要トピック候補)
5. 文体・粒度の手本として、`docs/handover/design-reports/` の直近レポート(無ければ旧運用の `tmp/` にある `*-design-handover.md`)を 1 つ読む
6. 実装直後のセッション内で実行された場合は、セッション中に得た知識(開発者とのやり取りで確定した判断等)も反映する。後日単独で実行された場合はファイル源泉のみで作成し、その旨をヘッダ表に注記する

## レポート構成(実物の家風に合わせる)

- **ヘッダ表**: 対象(**親チャット(設計卓)**)/発信(製造担当 Claude Code+日付)/指示書(パス+版)/実装コミット(ブランチ・コミット数。push 未実施なら注記)/関連(完了報告・レビューのパス)
  - **★★★レビューの集計を 1 行で必ず書く**(2026-09-12 追加)。**⇒ 「高 x / 中 y / 低 z ＝ 全 N 件・採用 n / 不採用 m・『高』の不採用 k 件・再レビュー往復 r 回(上限 2)」の形。**
    - **★これは親の受理判定の基礎資料である。** 個別の指摘だけが本文に散っていると、親は「全部で何件あり、何件落としたのか」を数え直せない。
    - **★2 巡以上回したときは巡ごとに書き、「前巡既出の再掲 n 件」も添える**(先例＝`M30-04` の 2 巡目)。
    - **★不採用が 1 件でもあるなら、その理由を §4 のレビュー低指摘の繰越へ書く。** 「高」の不採用は**必ず開発者確認を経ていること**を明記する。
- **導入文**: 「①独自確定仕様 ②契約違反の独自判断 ③製造判断 ④残課題に絞る。指示書どおりの部分は割愛」+ 最重要項目の指名(例: 「最重要は §1-1 と §2-1」)
- **§1 製造が独自に確定した実装仕様(DES 反映が要るもの)**: 各項目に根拠(ファイルパス:行・テスト名)と、「⇒ DES-XXX §Y に〜を明文化してほしい」の形の反映依頼を付ける
- **§2 契約・設計に反する独自判断(★独立カテゴリ・最優先)**: 下記「§2 の扱い」を参照
- **§3 製造の判断**: 3-1 開発者へ確認して確定した点(表形式)/3-2 推測で進めた点(指示書の推測許容節があればそれを参照)
- **§4 設計担当が未把握の残課題・申し送り**: レビュー低指摘の繰越を含む
- **§5 参考(触れていない=不変の証跡)**: 非波及の担保(`git diff` 空確認・不変テスト名等)。**上限＝1 項目 1 行・本節 15 行以内**(2026-08-11 開発者裁定③)。書けるのは `git diff` 空確認・不変テスト名・パス:行のみで、**コマンド出力・ログ本文の貼付は禁止**する。上限の根拠＝テンプレ準拠の実物 2 本(`20260803-m19-04d-design-exceptions.md` ／ `20260807-m19-phase2-design-exceptions.md`)がいずれも 15〜17 行で足りていた実測
- **§6 CHANGE 起票のたたき台(設計担当向けチェックリスト)**: 末尾に「番号は起票時に registry で採番」と明記。**マイグレを新規作成した場合は、その連番と「着手時に実査して払い出した」旨をここに書く**(予約帯を作らない運用のため)
- **§7 教訓(retrospective 行き)**: 下記「§7 の扱い」を参照

### ★★§1 の扱い: API 経路を新設・変更したら、逐語を本文へ埋める(2026-08-24 追加・M23 クローズ)

**`DES-002` §4.2 の経路表に載る API を新設・変更した場合、次を §1 の本文へ書くこと。** **「完了報告 §X が正本である」と参照だけを書かない。**

1. **応答の実 DTO**(実行結果を貼る。転記ではなく `json.MarshalIndent` の出力等)
2. **エラー契約の全行**(状況 → ステータス+コード)
3. **母集団の述語**(その経路が何を返し、何を返さないか)
4. **★持たせなかった分岐**(例: 「404 は無い。存在しない親は 200+空配列」)。**返らない分岐を実装に残さなかったことは、読む側が誤読しないために要る情報である**

**★理由**——**設計卓は完了報告を読まない**(2026-08-11 開発者裁定①)**し、製造ブランチ上の完了報告は設計卓の作業ツリーに無い。** **⇒ 参照だけを書くと、設計卓が反映できず、開発者へ追加請求が発生する。**

**★★M23 で 3 度発生した**(`D-489` / `D-496` / `D-533`)。**`D-496` が「設計伝達レポートだけでは `DES-002` §4.2 の as-built を反映できない」と構造の問題として指摘していたが、機構化されていなかったため再発した。**

**★分量の心配は要らない。** §5(不変の証跡)には 15 行の上限があるが、**§1 には上限が無い**——**そこが本レポートの本体だからである。**

### §2 の扱い(契約・設計に反する独自判断)

**これが最も危険なカテゴリである。** 実装が設計判断を下した状態を放置すると、DES と実装が乖離する(継ぎ目のドリフト)。

- §1(単に指示書に書かれていなかったので確定させた仕様)とは**分けて書く**。§2 は「**指示書・設計書・契約に書かれている内容と異なる判断を実装が下した**」ものに限る。
- 各項目に「**何に反したか**(文書名・節番号)」「**なぜそう判断したか**」「**実装がどうなっているか**(パス:行)」を書く。
- **親の仕事は、受理して DES/契約を更新するか、却下して差し戻すかの二択である。** 未処理で流れることだけを避けるため、**自分で「たぶん問題ない」と判断して §3 へ混ぜない**。
- 実例: M18-03b の「materialize は基底コンボの採用を解除する」は指示書 §4.4 の処理順に無い挙動だったが、**実装が正しく指示書が不足**していた。この種は §2 に挙げて親に裁定させる。

### §7 の扱い(教訓)

- **親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、**反映担当の廃止(2026-08-11)に伴い実施者は設計担当**(旧記載「反映係(Claude Code)」は失効)。**節の冒頭にその旨を 1 行書く。**
- 宛先が分離されているため、外出先(スマホ)では **§1〜§3 だけコピペすれば足りる**。
- 一般化できる形で書く(「このサブで X を忘れた」ではなく「X は Y のとき忘れやすいので Z で機構化する」)。

### 該当が無い節の扱い(★埋めるために書かない)

- **該当が無い節は「なし」の一行で終える。** 分量を出すために推測や既知事実の再掲で埋めてはならない(差分主義に反する)。
- **全節が「なし」なら、その旨だけのレポートを出す。** 「例外が無かった」は有効な報告である。
- 節そのものを削除しない(受取側が「書き忘れ」と「該当なし」を区別できなくなるため)。

## 品質規則

- **差分主義**: 指示書・設計書に既に書いてあることは繰り返さない。親チャットが読んで新情報になるものだけを書く。**該当が無い節は「なし」の一行で終える(埋めるために書かない)**
- 事実には根拠(ファイルパス:行、テスト名、コミット)を付ける。裏取りできない記憶は「要確認」と明示する
- **設計判断はしない**: 設計変更が必要と考える箇所は「〜へ補正が必要」「設計判断事項として申し送り」の形で、判断を**親チャット**・開発者へ委ねる。**やむを得ず実装が判断を下していた場合は §2 に挙げる**(黙って §3 へ混ぜない)
- **節番号・節名は本テンプレート固定**(2026-08-11 開発者裁定③)。§1〜§7 の番号と名前を独自に振り直さない。**やむを得ずずらす場合**(他文書が既に別番号を参照している等)は、**冒頭に「テンプレ ↔ 本書」の対応表を必須**とする。前例＝`docs/handover/design-reports/20260809-m19-05-design-exceptions.md` の冒頭注記(テンプレ §1〜§7 と本書 §1〜§10 の対応を明記した形)。**この形なら許容する。対応表の無いずれは不可。**
- **`followup-backlog` の項目は番号でなくスラッグで参照する**(playbook §4.20)。番号は動きうる。
- **★`followup-backlog.md` の本表は製造が編集しない**(2026-08-14 改訂・board **D-382**。**D-362 を狭めた**)。
  **理由は git である** — 同ファイルは設計卓と製造が書く**唯一の共有ファイル**であり、
  **両方が既存行を編集すると、main へのマージが競合し、開発者が端末でしか解消できなくなる。**
  **他のファイルは書き手が分かれているため競合しない。**
  - **⇒ 製造は本レポート §4 へ「設計卓が迷わず追加できる形」で書く。**
    **スラッグ ／ 何が起きるか ／ 再現条件または根拠(ファイルパス:行・テスト名) ／ 割付の候補と理由 ／
      新規登録か既存行の更新か(更新なら対象スラッグと更新後の状態)** を揃えること。
    **★「登録をお願いします」だけでは足りない** — 設計卓は実装ソースを読めないため、
    **書かれていないことを自分で確かめられず、開発者への質問リレーになって往復が増える。**
  - **★★★【2026-09-12 変更＝`D-838`】例外は無い。⇒ §J(停止時記録)も設計卓が書く。**
    **★製造は §4 へ「§J 行の原稿」として残す**(必須 5 フィールド＝`ID(スラッグ)` ／ `発生元` ／ `未解消の理由` ／ `再開に必要な条件` ／ `記録日・状態`)。
    **★★原稿を残せば停止規律を満たす**(`CLAUDE.md` §9)。**⇒ 設計卓が受理の手番で §J へ転記する。**
    **★既存 §J 行の状態更新も設計卓の手番である** — **「本文を書き換えず状態欄だけ足す」も既存行の編集に当たる。**
    停止規律は「記録して直ちに停止する」ものであり、レポートを待たせられないためである。
- 日本語で書く。ラベル・用語は源泉の表記に合わせる

## 完了時

- 生成したレポートを `git add` + `git commit` する(コミットメッセージ例: `docs(M19-04): 設計伝達レポートを作成`)。
  **`claude/` 名前空間ブランチ上に居る場合は、そのまま単一形 `git push origin claude/<branch>` で push してよい**
  (remote-ops §6 の例外。フラグ・複合コマンド不可。**それ以外の宛先・履歴改変は行わない**)。
  **★2026-08-30 に「push はしない — リモート反映は開発者」を削除した**(開発者判断)。**形骸化していたため**——
  クラウド実行(Claude Code on the web)では開発者が端末に居らず push できない一方、
  **レポートは push して初めて設計卓から読め、コンテナ回収で作業も消える。**
  ⇒ 実運用は常に push しており、規則だけが実態と乖離していた。
- 生成したフルパスとコミットハッシュを開発者へ報告する。
  **push 済みなら「設計卓が HEAD で読める」旨を、未 push なら push が要る旨を添える。**
  **★「Web 版側で Sync now を」と書かないこと**——親の面は 2026-08-11 に Claude Code へ移っており、Sync now は要らない(上記「出力先」の注記)
- **§2(契約違反の独自判断)に項目がある場合は、報告の冒頭でその件数を明示する。** 親が受理/却下の裁定を要する項目であり、埋もれさせない
