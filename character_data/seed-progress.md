# seed 投入進捗管理

手入力 seed データ(`character_data/*.csv`)の投入前チェック・配布取込の進捗を管理する。
`precheck_seed_data` コマンドが Phase 0 で対象決定に読み、Phase 3 で `precheck` 列を更新する。

- **precheck** = `precheck_seed_data` コマンドでのチェック・command 補完が完了したか(コマンドが更新)
- **seed_imported** = 配布 seed への取込(投入)が完了したか(**seed 投入工程/開発者が手動更新**。コマンドは読むだけ)

> **未処理キャラの自動対象化**: 引数省略で `precheck_seed_data` を実行すると、`character_data/*.csv` のうち `precheck` が「済」でないもの(この表に未登録の CSV を含む)を自動対象にする。既に `precheck=済` のキャラは、引数でキャラ名を明示しない限り再修正しない。
>
> **既配布の保護**: `seed_imported=済` のキャラを修正対象に含める場合、コマンドは警告して停止する(既配布 CSV の変更は後続 UPDATE マイグレ扱いになるため)。

## seed 波ごとに再適用する規則（★M20-02 で新設・2026-08-13）

**新キャラの CSV を投入する seed 波では、`moves` / `move_commands` の seed を作るだけでは足りない。**
**表記プリセット（`numeric` / `srk`）のエイリアスを生成する規則を再適用し、新しい連番のマイグレを起こすこと。**

> **★これを落とすと、新キャラだけエイリアスが空のまま取り残される。**
> `DES-004` §5.3 のフォールバックで `official_ja_move`（日本語の技名）が出るため**画面は壊れず、テストも緑のまま**であり、**人が見る以外に見つける経路が無い**。
> M19 で機械 backfill が第三波 seed より前にあったため 625 行が既定値のまま取り残された前例がある（**D-181**）。

### 手順

```bash
# 1) moves / is_derived / move_commands（従来どおり）
go run ./cmd/seedgen -chars <新キャラ> -out <連番>_seed_moves_<波> -note "..."
go run ./cmd/seedgen -mode derived-backfill -chars <新キャラ> -out <連番>_backfill_moves_is_derived_<波> -note "..."
go run ./cmd/seedgen -mode move-commands    -chars <新キャラ> -out <連番>_seed_move_commands_<波>   -note "..."

# 2) ★表記プリセットのエイリアス（M20-02 で追加。2 プリセット分を必ず両方走らせる）
#    ★-movement-chars には「その波で増えたキャラ」を渡す（省略すると -chars と同じ）。
go run ./cmd/seedgen -mode aliases -preset numeric -chars <新キャラ> -movement-chars <新キャラ> \
  -out <連番>_seed_aliases_numeric_<波> -note "..." -alias-report tmp/aliases-numeric.md
go run ./cmd/seedgen -mode aliases -preset srk     -chars <新キャラ> -movement-chars <新キャラ> \
  -out <連番>_seed_aliases_srk_<波>     -note "..." -alias-report tmp/aliases-srk.md
```

- **規則の実体**は `internal/seedgen/generate_m2002.go`。マイグレはその出力であり**手編集しない**（golden テストが drift を検出する）。
- **★移動系 9 code も波ごとに再適用が要る。** `000072` / `000073` は**適用時点の 19 キャラを明示列挙して**投入しており、新キャラには当たらない。**当初は `characters` を CROSS JOIN する形にしていたが、その場合 down 側を同じ形で絞れず、次の波の down が前の波の投入分まで消すため是正した**（M20-02 レビュー H-2）。⇒ **層 A / 層 B / rush 版と移動系のすべてが波ごとの再適用対象である。**
- **再適用は冪等である**——`NOT EXISTS` ガードで既存行を skip する（upsert ではない＝既存の表記を書き換えない）。
- **`-alias-report` を必ず出して確認すること。** 投入しない行（衝突・元技を解決できない rush・`command` を持たない派生）が全件列挙される。**衝突が出た行は投入されない**ので、放置すると当該技だけ日本語技名のままになる。
- **★`-movement-chars` は「その波で増えたキャラ」を渡すこと**（省略すると `-chars` と同じになる）。移動系の up と down はこの集合で絞られる。**前の波のキャラを混ぜてはならない**——down が前の波の投入分まで消す（生成器テスト `TestAliases_MovementDownIsScopedToItsOwnChars` が守っている）。
- **★`-alias-report` に出ない衝突が 1 種類ある。** 生成器は CSV しか見ないため、**`numeric` / `srk` の表記が同じキャラの別 move の `official_ja_move` 表記と一致する**ケースは検出できない（現状 0 件）。この型はマイグレ適用後に `migrate_m2002_test.go` の「同一キャラ内で 2 技が同表記」検査が拾う。**⇒ レポートが緑でも `go test ./internal/infra/migration/` まで回して確認すること。**

##### ★★#11 CSV と DB の同期 — 3 列は CSV が「運搬役」である（2026-09-04 裁定）

**アップデート対応は「CSV を外部ツールで取込 → 修正 → 差分のみマイグレで取込」という運びである。**
⇒ **CSV 側だけが陳腐化していると、DB にしか無い値が差分に現れず静かに落ちる。**

| 列 | 値の正本 | CSV の役割 |
|---|---|---|
| `startup_basis` | CSV（第四波以降）／ 手書きマイグレ（既 seed 分） | 運搬役。**DB と一致させる** |
| `fastest_unreachable` | 同上 | 同上 |
| `chain_cancel_total` | **`character_data/chain-cancel-measurements.md`**（測定と多重検算の記録） | 運搬役。**DB と一致させる** |

**★`chain_cancel_total` を CSV に書くのは `D-94` / `D-99` を覆した裁定である**（2026-09-04）。`000052` のヘッダは「CSV に書くと値が 2 か所に存在してどちらが正か分からなくなる」として転記しないと書いているが、**パイプラインで値が落ちる方が重い**という判断。**2 か所問題は機械検査で解く**（下記）。**適用済みマイグレのヘッダは改変しない**（`D-535`）ので、**ヘッダと現行運用は食い違ったまま残る**。

1. **DB を唯一の出所にする。** クリーン DB へ全マイグレを適用して `moves` から dump する。**★SQL のパースで再導出しない**——`000064` は `pa.code IN (...)`、`000067` は `pa.code = '...'` の単数形で、同じ正規表現では拾えない（第四段で実際に 90 行を 74 行と見誤った）

⇒ **`internal/infra/migration/csv_db_sync_test.go` の `TestCSVAndDBAgreeOnFrameCostColumns` が唯一のガードである。**

##### ★★#10 `move_code` の入力ミスを直すとき — 三点更新（2026-09-04・第 2 例）

**★「適用済みマイグレは改変しない」との関係は `D-336` が決着させている**——逐語＝「**両者は上下ではなく適用対象が違う。判別の述語＝そのマイグレは生成物か手書きか。**」

| 対象 | 扱い |
|---|---|
| **seedgen の出力**（`-mode moves` / `derived-backfill` / `move-commands` / `aliases`） | **再生成する。** CSV が正本である |
| **手書きマイグレ** | **1 バイトも触らない**（`D-535`）。旧 code を持っていたら、**新規連番の追随マイグレ**で当てる |

**★手順**:

1. **`seedgen -check` で先に測る**（書かずに差分だけ出る）。**どの生成マイグレが動くかを、直す前に知っておく**
2. CSV を直し、動いた生成マイグレだけ再生成して **diff が意図した行だけであること**を目視する
3. 既存 DB 用の改名マイグレを書く。**★`NOT EXISTS` ガードが要る**（m19-04c §12.1＝改名は「新規 DB では 0 行」で済むとは限らず、改名先が既に在る DB では UNIQUE 違反でマイグレ全体が落ちる）
4. **★golden に載らない列を確かめる**（m19-04c §12.2）。`startup_basis` / `is_projectile` / `chain_cancel_total` / `fastest_unreachable` は seedgen が出力しないため、**再生成しても新規 DB では未設定のまま残る**。手書きマイグレが旧 code で当てていたら、**改名「後」の新 code で当て直す追随が要る**
5. **★手書きマイグレの追随対象は「grep ヒット × seedgen が生成していない」の 2 条件**で絞る（m19-04c §12.3）。grep だけだと golden まで拾って過剰になる
6. **★`moves` に `name_ja` 列は無い**（`000001` §moves）。技名の実体は `preset_aliases.alias_text`（`official_ja_move`）である
7. **down は非対称になる**（m19-04c §12.5）。「新しく作った vN」と「HEAD から down した vN」は一致しない。ヘッダに明記する
