01役割（4層）V2

親チャット（設計卓）Web／複数MS同時

設計権限を持つ唯一の層。契約ファイルの発行・指示書作成・逸脱の裁定。製造の完了を待たずに作れる指示書は先行して作る。

V2.1 成果物はダウンロード可能なファイルで出す。応答本文には要旨と「開発者が次にやること」だけを書く。成果物の全文を本文に載せると、媒体が「開発者の手」に戻る（＝転記作業の再発）。既存の巨大文書（DES 本体・registry）の改訂はパッチで出し反映係に当てさせる。例外はボードで、親が全文を保持しているため更新済み全文をそのまま出す。
V2.4 2026-08-11: 親の面が Claude Code になったため、DES 本体・registry・ボードはいずれも親が直接 Edit する。パッチ発行も全文出力も要らない。「応答本文には要旨と次の一手だけ」という上の規律は不変——むしろ成果物が repo に着地する分、本文へ載せる理由がなくなる。

V2.3 記録を先に書いてよいが、断定してはいけない。三点セットを同時に着地させるため change-report は反映の前に発行するが、ステータスを「反映済み」と断定して出すのは誤り（repo を見ないまま「反映済」と宣言する R-03 と同じ形）。先行発行する記録文書はステータスを「ドラフト」とし、事実で埋めるべき箇所を明示し、適用者がそこだけを確定させてから配置する。判断を含む記述は適用者に書き換えさせない。

V2.3 後発のパッチが前発を上書きする箇所を明示する。同一セッションで前後のパッチが同一項目に反対の指示を出した事例がある。適用者は正しく処置したが根拠は適用順という状況証拠だけだった。後発に「本項は〈先発パッチ〉§X の指示を上書きする」と 1 行書く。発行の時系列＝適用の時系列とは限らない。

V2.3 運用を変えた直後は、発行済みの成果物に旧習が残る。「版番号を書かない」運用の発効直後のパッチで、ヘッダは新運用・ボディは旧習の版番号がハードコードという同居が起きた。運用を変えたら、その時点で発行済み・未適用の成果物を洗う——告知だけでは足りない。

設計判断に長い検討が要るサブは個別設計チャットへ外注し、自らは肥大を避ける。状態はボードファイル（§06）に出し、いつでも作り直せるようにする。

リレーは最初と最後だけを心がける（疑問があれば質問は可）。目的達成で役目を終える。連続支援が有利な場合のみ次の設計判断へ継続。

実装。完了報告は repo へ。例外だけを設計伝達レポート（§07）で親へ返す。

文書パッチ適用・registry 更新・retrospective 反映。常駐しない。親は設計書を直接編集せずパッチを発行して反映係に直させる。
【V2.4】この層は無い。文書パッチ適用・registry 更新・retrospective 反映は親が自分で行う（親の面が Claude Code になったため、パッチを介さず Edit できる）。継承した規律 2 件＝(1) 正典内部の自己矛盾を検出する（D-252。範囲を限定して当てるときは同じ正典内の他の出現箇所を先に確認する）(2) 実行できても目的を達成しないなら実行せずに報告する（D-204 (2)）。

02連番 — 資源の性質で二分（第1版から不変）

CHANGE 番号・DES バージョン事前ブロック割当

マイルストーン着手時にレンジを割当（例: M20 = CHANGE 0XX〜0XX）。割当表は repo 内の小さな正本1つ。枯れたら追加ブロック。欠番は無害（順序依存なし）。親が発行する。

マイグレ番号マージ時採番

開発中はレーン別作業 DB ＋ プレースホルダ名（例 m20_xxx_XXXX）。マージ直前に本線の最新番号＋1 へ一括リネーム。マージの直列性が採番の直列性を兼ねる。

WHY — 配布先でだけ壊れるgolang-migrate は単一の現在バージョンで管理するため、DB が version 29 の状態に後から 24 が来ても適用されない。作り直せる作業 DB は常に 0 から順適用なので開発環境では再現しない。友人リリース済み＝配布先の既存 DB だけが壊れる。

03通信 — リレー文の廃止（第1版から不変）

チャット間の伝達は全てファイルにして commit。開発者の仕事は「内容の転記」から「commit/push ＋ ポインタ1行」へ。

FORMAT「docs/relay/m20-to-parent-01.md を読んで」——これだけ。本文は貼らない。

外出先（スマホ）では1ファイルのテキストコピペで代替する。個別設計チャットのレポートが1本に収まる設計なのはこのため。

名前空間の分離（V2 で修正）docs/handover/ を「チャット間リレー」と「設計伝達レポート」の両方に使わない。同じ語が二つを指すと必ず取り違える。
リレー ＝ docs/relay/／設計伝達レポート ＝ docs/design-reports/ に分ける。

04契約ファイル — ズレ検出の正本

マイルストーン開始時に1枚。認識ズレの是正は会話でなく、この契約との diff で行う。

#項目内容
1スコープ作るもの／作らないもの
2DES 所有権改訂してよい文書と §。他レーン所有分は read-only
3予約レンジCHANGE・DES バージョンのブロック。マイグレは「プレースホルダ・マージ時採番」と明記
4触る領域スキーマ／コードの衝突面の宣言
5凍結インターフェース他レーンが依存する API/型/契約。変えたくなったら実装でなく契約改訂を先に
6通信規約成果物・報告・教訓の置き場パスと命名
V2 での強化契約の発行者が親チャット1人になる。第1版では各レーンが自分の契約を持ち、契約自体がドリフトしうる隙があった。全マイルストーンの契約を単一著者が書くことで、DES 所有権の排他性が構造的に保証される。
V2.2判断が覆ったら、その判断に依存していた不変条件の「守り方」を再評価する。不変条件を「どちらに決めても守る」形で書くのは正しいが、決定が下りたら、その不変条件が構造で守られるのか実装で守られるのかを再判定する。文言が同じだからといって放置してはならない＝契約の改訂事項である。

05ボードファイル — 親の寿命対策V2

親もいずれ肥大する。状態がチャットの中にあると引き継ぎがまた大変になる＝今回避けたかった問題の再来。

  • 1ファイルに小さく持つ：マイルストーン状況／外注中の個別設計／保留事項／予約レンジの消費状況
  • 裁定のたびに1行追記（例:「M20-03 の逸脱＝受理・DES-004 §6 更新済み」「指示書に X の制約を書き忘れがち」）
  • → 親はいつでも使い捨てにできる（新しい親はボードから起動）。親が想定外に落ちても学びが失われない
  • 副次：「指示書の誤り」件数の推移が、指示書作成の改善を測る安価な計測点になる
  • V2.1 更新手段＝親が全文を保持し、更新済み全文をファイルで出す。「1行追記」は粒度の規定であって手段の規定ではない。初回運用では手段が手作業（開発者がチャット本文からコピーして貼る）だったため摩擦が積み上がった。ここで頻度を落とすと正本が陳腐化して方式の中核が失われるため、頻度でなく1回あたりのコストを下げる
  • V2.1 ボードを編集してよいのは親だけ。書き手が複数いると、親が観測できない間に repo 側が進み、親の出力がそれを黙って消す
    V2.4 2026-08-11: 手段が変わった。反映係が廃止され親の面が Claude Code になったため、更新は「全文出力して開発者が貼る」ではなく親が直接 Edit する。V2.1 が下げようとした「1 回あたりのコスト」はこれで消える（ボードは 517 KB / 768 行あり、全文出力の摩擦が実際に積み上がっていた）。「編集してよいのは親だけ」という排他は不変
  • V2.1 溜めてよい区分／溜めてはいけない区分を分ける。§3 裁定ログ・§6 指示書の誤り・§7 教訓・§8 予行演習は溜めてよい。§1 マイルストーン状況と §2 予約レンジの消費は溜めない（製造がマイグレ連番を実査して親へ再請求する運用に直結するため、registry の更新と同期する）
  • V2.1 溜める上限＝「反映係を起こす回」「未反映5件」「セッション終了・親のコンテキスト逼迫」のいずれか早い方。未反映がある間は親が応答末尾に1行で持ち回る
RULE親は実装レポートを読まない。ボードだけを見る。読み始めた瞬間、熟考を外出しした意味が消える。

07設計伝達レポート（製造 → 親）V2で改訂

既存のカスタムコマンドを運用中。完了報告とは別に「例外だけ」を返す設計は正しい。親が必要とするのは記録ではなく例外。

改訂点

#改訂理由
1§6 教訓を追加し「親は読まなくてよい」と明記宛先分離が節構造だけで完成する。外出先では §1〜§3 だけコピペすれば足りる
2「契約に反する独自判断」を独立カテゴリに最も危険。実装が設計判断を下した状態の放置＝DES と実装の乖離（継ぎ目のドリフト）。親の仕事は受理して DES/契約を更新するか、却下して差し戻すかの二択。未処理で流れることだけを避ける
3§5 の「registry で採番」を「契約ファイルの予約レンジから採る」へ旧モデルの記述。§02 と不整合
4マイグレのプレースホルダ運用を明記する節を追加製造がマイグレを作った場合、「プレースホルダ名・マージ時に採番」を報告させる
5該当なしの扱いを定義「該当が無い節は『なし』の一行で終える。埋めるために書かない。全節が『なし』ならその旨だけのレポートを出す」＝差分主義を機械的に守らせる
6ファイル名を-design-exceptions.md 等へ「例外だけ」と名前に書くと、生成側も受取側も契約を思い出せる
維持する良い点差分主義（指示書・設計書に書いてあることは繰り返さない）／事実には根拠（パス:行・テスト名）／設計判断はしない（判断は親・開発者へ委ねる）。この三点が外注レーンの契約になっている。
V2.2改訂7点目：レビュー通過後に仕様が動いたら、レポートを追従させたうえで後乗せ分の差分レビューを行う。レビューはコードを見るため「実装は正しいのにレポートだけが古い」状態は通過する。レポートは DES 反映の一次源なので、そのまま反映すると実装は正しいのに設計書だけが間違う。

08progress ログの扱いV2

  • progress は全部書いたログ。基本的に渡さない。親・個別設計チャットへの唯一の入力は設計伝達レポートとする
  • 例外は認める契約（必要時に参照する経路は塞がない）。構造的に隠蔽はしない
  • 要求する側の起動プロンプトにも書く——「progress ログは要求しない」。コマンド側だけ直しても要求は止まらない（双方向の問題）
V2.2「読まない」規律に例外を作るときは、対象と期限を同時に書く。期限のない例外は既定になる。例外には対象・期限・観察点を同時に定義する。

09教訓 — 記録と統制を分けるV2

  • 収集：製造・個別設計の両方が同じ様式の「教訓」節で出す。V2.4 バッチで retrospective へ入れるのは反映係→親（2026-08-11 廃止）
  • V2.1 親は retrospective-log を読まない（巨大で、親のコンテキストへ載せると本方式の意味が消える）。ただしマージ素材（*-lessons-*.md）は、昇格判断のために親が読む。親の担当は「どの教訓を playbook・コマンド仕様・指示書テンプレへ昇格させるか」の判断のみ。V2.4 log への機械的マージと digest の再蒸留も親が行う（反映係は 2026-08-11 廃止。/retrospective-digest-update を親が実行する）。「読まない」規律は不変——書き込む先の線であって、読む線ではない。「記録」と「統制」を混ぜないという本節の趣旨は、読む／読まないの線ではなく、書き込む先の線である
  • retrospective-log は追記専用構造化 or フェーズ分割を推奨（編集のたび全文がコンテキストに載る構造自体が継ぎ目）
重要「プロジェクト知識にあるから全員が見られる」は成立しない。見られるが読まれるとは限らず、検索は取りこぼす。
→ 再発防止が要る教訓は、retrospective に書くだけで終わらせず、playbook・コマンド仕様・指示書テンプレへ昇格させる。
retrospective ＝ 履歴／統制 ＝ 起動プロンプトとコマンド仕様。役割を混ぜない。

10プロジェクト知識の使い分け（第1版から不変）

project knowledge は検索ベース取得（全ファイルが常時コンテキストに載るのではない）。同期資料が各チャットを常時圧迫する心配は不要。ただし検索は取りこぼす（実例：類似名の既存機能に意味検索が吸われ、目的ファイル本文が引けなかった）。

資料渡し方
DES・overview 等のバルク参照project knowledge で可
連番割当表・契約ファイル・ボード検索に頼らない。明示パスで渡す or Claude Code に直接読ませる
RULEロックや counter を検索取得に委ねない。起動プロンプトに要点を載せておけば、同期が多少古くても成立する設計にする（スマホで同期できない場合の保険を兼ねる）。

11スマホ運用V2.1

親チャット自身がスマホから使われる場合の規定。外出先のスマホからはプロジェクト知識の同期を実行できない（同期操作の入口が無い）。したがってセッション中に repo が進んでも、親はそれを観測できない。

重要「現行版の正本は repo に置く」は正しいが、「親がいつでも repo を読める」ことを含意しない。正本が正しい場所にあっても、正本を必要とする層がそれを見られない状況が実在する。
  • 正本の書き手を1人にする。ボードは親が全文を保持し、親だけが書き換える（§05）
  • 親はセッション中に発行した成果物の一覧を保持し、どれが repo に着地したかを開発者に確認する。「成果物は生成しただけでは完了せず、repo へ着地したことの確認までが完了条件」の観測できない環境版
RULEセッション中に確定した事項（採番の消費・裁定・版遷移）は、親が明示的に保持する。「あとで repo を見れば分かる」に頼らない。

12レーン割り（M20〜M23）

M20 ∥ M21好適

M20＝BE 寄り（preset_aliases・recipe_cache）／M21＝FE 入力系。触る層が縦に割れる。条件：recipe_cache の読み書き契約を M20 所有で凍結（M20 は並行性バグ修正そのものを含む）／M21 は Gamepad 検証が重いのでPoC 先行。

M22単独直列を推奨

ログイン・版管理・同時編集安全性は横断関心事（全 API に薄く触る）。並列の相手として構造的に不向き。依存も「FB 蓄積後」で急がない。

M23分割

小修正多数・衝突高低混在。高衝突の小修正だけ1レーンに束ねて直列、低衝突は並列。契約の「触る領域」で振り分ける。

改善版プロセスの初戦は M20∥M21 の2レーン。3レーン同時をもう一度やる必要はなく、バッチ周期を粗くする実験も2レーンの方がクリーンに検証できる。

13起動前チェック（要約）

詳細版は parallel-ops-decisions §5。

  • 連番：ブロック値が具体的。マイグレはプレースホルダ＋マージ時採番。「中央に採番を問い合わせる」文言が残っていない
  • 通信：ファイル＋ポインタ方式。docs/relay/ と docs/design-reports/ が混ざっていない
  • 契約ファイル：6項目すべて記入済み。DES 所有権が他レーンと排他
  • 個別設計チャット：設計変更権限なし・凍結事項・読むべき文書名の明示・レポート様式（DES 差分案と教訓節を含む）
  • 教訓：scratch パス指定・retrospective-log 直接編集の禁止
  • progress：要求しない旨が要求側にも書かれている
  • ホット正本を検索で引かせる前提になっていない
  • V2.1 成果物の渡し方：親の成果物がダウンロード可能なファイルで出る前提になっているか。応答本文への直書き（＝開発者の転記作業）が残っていないか
  • V2.1 ボードの更新手段：「1行追記」の手段が書かれているか。書き手が親だけに限定されているか。溜めてよい区分（§3・§6・§7・§8）と溜めない区分（§1・§2）が分かれているか
  • V2.1 親のスマホ運用：セッション中に同期できない前提で、親が保持すべき情報（発行済み成果物の一覧・着地確認・採番の消費）が定義されているか
