## 0. 分類の定義

| 致命度 | 定義 | 発火ゼロだったら |
|---|---|---|
| **高（不可逆）** | 実行するとデータ・履歴・システムが**戻せない**。または機密が**外部へ出て取り消せない** | **維持**。被弾ゼロは抑止成功の証でありうる（ヘルメット判定） |
| **中（外部影響・回復に手間）** | 外部へ出る／共有物を変える。**取り消せるが手間と調整が要る** | **維持寄り**。削除するなら影響範囲を別途確認する |
| **低（局所・可逆）** | 影響が閉じており、通常の手段で戻せる | 削除検討の余地がある（ただし単独では根拠にならない） |

## 2. 分かったこと

### 2.1 ★削除候補は 1 件も無い

**低（局所・可逆）が 0 件**だった。**deny リストは「不可逆な操作」と「外部影響のある操作」だけで構成されており、
発火実績を根拠に削除できるものが存在しない。**

**⇒ 仮に C3 のアブレーション（1 つ外して評価セットを回す）を実施しても、対象になるルールが無い。**
これは `audit-c3-ablation-not-run` で「非交渉条件と裁定 15 に挟まれて答えられる問いが残っていない」と書いた判断の**裏付けになる**。

### 2.2 パターンの重複は「安全側の冗長」であって無駄ではない

同じ意図のルールが複数行にわたるものがある。

| 重複 | 件数 | 理由 |
|---|---|---|
| `curl`/`wget` × `bash`/`sh` × パイプ前後の空白 | 8 | **`curl * \| bash` と `curl *\|bash` は別パターン**として書かないと素通りする |
| `rm -rf` の対象 8 通り | 8 | `/` `~` `.` `$HOME` とそれぞれの `/*` |
| `.env` の Read/Edit/Write × `./` 有無 × `.*` 有無 | 12 | ツール別・相対パス表記別に書く必要がある |
| `git reset` / `git rm` / `sudo` の `:*` 有無 | 6 | **引数なしの実行を別に書かないと通る** |

**⇒ 「同じような行が並んでいる」ことを理由に整理してはならない。** マッチャの仕様上、
**表記ゆれごとに 1 行が要る**。減らすと穴が開く。

### 2.3 `CLAUDE.md` §10 の 4 目的との対応

`CLAUDE.md` §10「本ルールの目的」が挙げる 4 つと、実際の deny の対応は次のとおり。**すべて充足している。**

| 目的 | 対応する deny |
|---|---|
| アプリ外のファイル・システムへの破壊的変更の防止 | 1–8（`rm -rf`）／31–32（`sudo`）／36–41（デバイス・FS） |
| 機密情報の漏洩防止 | 50–75（`.env` ／ `secrets/` ／ `~/.ssh` ／ `~/.aws` ／ `~/.gnupg`） |
| データの不可逆な破壊の防止 | 76–79（`*.db` ／ `*.db-*`） |
| トレーサビリティの確保 | 12–30（履歴改変・リモート反映）／9–11（別経路の遮断） |

## 3. 使い方（★将来この表を引く人へ）

**ルールの削除・緩和が提案されたときに本表を引く。**

1. 対象ルールの**致命度**を本表で確認する
2. **高・中なら、発火実績を根拠にした削除提案を却下する**（非交渉条件・ヘルメット判定）
3. 緩和するなら、**発火実績ではなく「その操作を許す運用上の必要」**を根拠にする
   - 前例: **コミット系の緩和**（2026-06-11。チェックポイントコミット運用のため）／
     **`claude/` 名前空間ブランチへの push 許可**（2026-07-20。クラウド実行の作業領域として必要だったため）
   - **どちらも「発火実績」ではなく「必要性」を根拠にしている。**
