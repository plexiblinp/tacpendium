## 1. 結論

**追加計測は `M21-overview` のブロッカーではない。overview は今書ける。**

理由は 3 つに分かれる。

| 未測定の範囲 | 追加計測は要るか | いつ | 根拠 |
|---|---|---|---|
| **Firefox** | **要らない** | — | Chrome と構造的に違うことは公表挙動で既に確定しており、測って初めて分かる話ではない。かつ**帰結（index 固定を前提にしない層が要る）は Chrome 単独の実測から既に出ている** |
| **Bluetooth** | **要る** | **overview の前ではない。判定窓を決めるサブの段 2** | **接続方式が FR107 の観測量そのものを変える。** USB 限定の分布から引いた閾値は BT で silent に落ちうる |
| **アケコン／キーボード** | **計測の問題ではない** | — | **スコープの問題である。** アケコンは Firefox と同じ層が吸収する。キーボードはそもそも Gamepad API ではない |

**そして編成を実際に止めているのは計測ではない。** **`REQ-001` FR102 の本文が現行設計と食い違ったまま残っており、その解消先が M21 であること**である（§4）。これは開発者裁定を要する（§6 Q1）。

> **★2026-08-13。開発者回答により上表の 2 行目が変わった。** **開発者は Bluetooth 接続のコントローラを所有していない**（Q4）。**⇒ 「要る」は「要求しても実行できない」へ変わり、`§3.5` が差し替えた。** **結論そのものは強くなっている**——**Gamepad API に接続方式のフィールドが無い以上、測れていても実行時に分岐はできなかったためである。** **同じく Q2 で アケコン非所有が確定し、`§4.1.1` を追加した。** **`§1` の結論**（**追加計測は overview のブロッカーではない**）**は変わらない。**

## 2. Firefox — 計測不要

### 2.1 事実

Gamepad API の実装差は公表されている。Chrome はトリガーをアナログボタン、D-pad をデジタルボタンとして仕様どおりに出すが、**Firefox は `mapping` が `standard` にならない場合があり、トリガーと D-pad が `axes` 側に出る**。さらに **Firefox は Chrome / Edge に無い `axes` 要素を 1 つ多く持つため、Chrome の index を前提にしたコードは全軸が 1 つずれる**。同一機種が **Chrome では 17 ボタン 4 軸、Firefox では 11 ボタン 8 軸**と検出され、**Chrome の start ボタンが Firefox では左スティック押し込みになる**実例も報告されている。

### 2.2 なぜ計測が要らないか

**測る前から答えが決まっているためである。**

1. **「Firefox は違う」は既知**であり、実測は「我々の 2 機種で具体的にどうずれるか」を返すだけである。それは**実装サブの中で 1 回確認すれば足りる作業**であって、編成を決める材料ではない。
2. **帰結が既に出ている。** **D-324 は Chrome 単独でも機種差を検出している**——パッドの button 7 は 12 段階のアナログ値を返し、レバーレスは同じ button 7 で `0` / `1` の 2 値しか返さない。**⇒ 「`mapping` と index の固定を前提にしない機種プロファイル層」は、Firefox の有無にかかわらず必要である。** Firefox はこの結論を補強するだけで、変更しない。

### 2.3 ただしスコープ判断は残る

**アプリは起動時に OS 既定のブラウザを自動で開く**（`DES-001` §6・案C）。**⇒ 利用者のブラウザを我々は選べない。** Edge は Chromium 系なので Chrome と同じ実装だが、**Firefox は別実装である。**

**⇒ 「Firefox を M21 の対応範囲に入れるか」は裁定が要る**（§6 Q2）。設計卓の推奨は、**「対応範囲に入れるが、DoD は Chromium 系に置く」**——プロファイル層があれば Firefox でも動く見込みだが、**動くことを DoD にすると開発者の実機作業が 1 系統増える**ためである。

## 3. Bluetooth — 要る。ただし overview の前ではない

### 3.1 事実

**Bluetooth HID の既定ポーリングは 125 Hz、すなわち 8 ms 刻みである。** 実測ベースの比較では **USB 有線が 1〜4 ms 程度の付加で、押下ごとのばらつきがほぼ無い**のに対し、**Bluetooth は機種により 5〜15 ms を加算する**。さらに **2.4 GHz 帯の混雑により、パケット落ち → 再送に由来するスパイクが出る**。

### 3.2 なぜ効くか

**FR107 の観測量と同じオーダーだからである。**

D-324 の実測（USB・Chrome・rAF 間隔 中央値 4.20 ms）:

| 指標 | レバーレス | パッド |
|---|---|---|
| 同時押しズレ 中央値 | 8.30 ms | 8.30 ms |
| p95 | 20.90 ms | 33.30 ms |
| 最大 | 20.90 ms | 45.80 ms |

**BT にすると 2 つのことが起きる。**

1. **サンプリングの下限が粗くなる**——現在の下限は rAF の 4.20 ms だが、BT では HID の 8 ms が支配的になる。**分布は「広がる」のではなく「量子化される」。**
2. **スパイクが増える**——再送由来の外れ値が出る。**⇒ p95 と最大が USB の値のままである保証は無い。**

**閾値に効くのは 2 のほうである。** **`m21-contract` §1.3 が名指しした失敗型は「机上で選んだ閾値が、動いているように見えて一部の入力を黙って落とす」であり、テールの過小評価はそれそのものである。**

### 3.3 なぜ overview の前ではないか

**計測結果が変えるのは「サブの中の値」であって「サブの分割」ではない。** 判定窓の閾値は M21 本実装の 1 サブが持つ数値であり、その数値が 30 ms でも 45 ms でも編成は変わらない。

**⇒ 置き場所は「判定窓を決めるサブの段 2」とする。** これは**人手作業をサブの継ぎ目に置く**という既存の運用（教訓 E-55）に一致し、**段 2 を先に消化するために overview を待たせる形を避けられる。**

### 3.4 最小の計測仕様

**新しいハーネスを作らない。** PoC の段 1 で作った使い捨てハーネスと、段 2 の手順をそのまま再演する。

| 項目 | 内容 |
|---|---|
| **機種** | **既存の 2 機種のみ**（レバーレス・パッド）。買い足さない |
| **変える変数** | **接続方式だけ**（USB → Bluetooth） |
| **測る軸** | **B（ポーリング周期）と C（同時押しのズレ幅）の 2 軸のみ。** A（取得可否）は済み、D（チャタリング）は §5.2 |
| **成果物** | **分布のみ。閾値は書かせない**（**D-294** を踏襲） |
| **想定所要** | **PoC 段 2 が 2 機種 15 分だったため、軸を 2 本に絞れば同等かそれ以下** |
| **DoD** | **USB の分布と並べて出す**（同じ表に 2 列）。**単独で出すと USB との差が読めない** |

> **★2026-08-13。本節は実行できなくなった。** **開発者は Bluetooth 接続のコントローラを所有していない**（Q4 の回答）。**⇒ §3.5 が本節を差し替える。** **本文は書き換えない**（D-57 ／ D-259 の運用）。

### 3.5 Bluetooth が計測できない場合の扱い

**結論——BT の計測は要求しない。要求しても実行できないためである。** **⇒ 代わりに、測れないことを設計の前提として扱う。**

**★決定的な事実が 1 つある。** **Gamepad API には接続方式を示すフィールドが無い。** `id` にベンダ名や製品名が出ることはあるが、**USB と Bluetooth を判別する標準の手段は存在しない。**

**⇒ これは「測れなかった」の意味を変える。** **仮に BT を測れていたとしても、実行時に接続方式で分岐することはできなかった。** **したがって採りうる形は最初から 2 つしかない。**

| 形 | 内容 | 評価 |
|---|---|---|
| **(α) 単一の窓を、両方を包むだけ広く取る** | 接続方式を問わない 1 つの閾値 | **採りうる。** ただし「どこまで広げれば足りるか」の根拠が USB 側にしか無い |
| **(β) 実行時の自己校正** | **利用者の環境で実際に観測された更新間隔から窓を導く。** `Gamepad.timestamp` の更新間隔と rAF 間隔から実効サンプル周期を推定する | **有望だが未検証。** **`timestamp` の意味づけはブラウザ差がありうる。実装サブの実査項目に置く** |

**★(α) が現実的に足りる理由**——**本アプリは記録ツールであって対戦ではない。** **`FR106` は「正確にゆっくり入力できるよう」と明記している。** **⇒ 窓を広く取ったときの副作用は「別々に入れたつもりの 2 入力が 1 ステップにまとまる」ことだが、ゆっくり入力する用途ではこの誤りは起こりにくく、しかも画面に出るので利用者が気づける。** **逆に窓が狭すぎる副作用は「同時押しが 2 ステップに割れる」で、こちらも画面に出る。** **⇒ どちらの誤りも silent ではない。** **`m21-contract` §1.3 が警戒した「黙って落とす」形は、読取表示**（`FR106`）**があるかぎり成立しにくい。**

**★ただし「だから何でもよい」ではない。** **実装サブへ渡す条件を 4 点に固定する。**

| # | 条件 |
|---|---|
| **1** | **窓は USB の実測から導き、`D-324` の最大値を下回らせない**——**押し始め 45.80 ms ／ 離し始め 83.30 ms。** **どちらを使うかは実装サブが決める**（`D-324` で未決） |
| **2** | **BT は未計測であると明記する。** **「BT でも動く」と書かない**（E-84） |
| **3** | **窓を定数で埋め込まず、1 か所から差し替えられる形にする。** **利用者からの報告で調整しうるため** |
| **4** | **(β) の自己校正が成立するかを実装サブの着手前に実査する。** **成立するなら (β)、しないなら (α)。** **測る前に判定法を決めない**（`D-294` ／ `E-123`）という条項は、ここでも生きている |

## 4. アケコン／キーボード — 計測ではなくスコープの問題

### 4.1 アケコン

**「レバーレスと同じに見えるはずだ」とは断定できない。** アーケードコントローラのレバーが `buttons` に出るか `axes`（hat）に出るかは、**その機体の HID 実装とブラウザの組み合わせで変わる**というのが公表されている一般則であり、**両方を扱ってリマップを許すのが定石**とされている。**設計卓は現物を持たないため、ここを断定しない**（E-117）。

**⇒ しかしこれは §2.2 で既に必要と結論した機種プロファイル層が吸収する。** **アケコン単独のための追加計測は要らない。** 実機が無ければ、**「プロファイル未検証」として明示して出す**——**「対応した」と書かないこと**が要件である（E-84。**「0 件」と「検査していない」を同じ顔で出さない**の同型）。

### 4.1.1 アケコン非所有が確定したときの帰結（2026-08-13・Q2 の回答）

**開発者はアーケードコントローラを所有していない。** **⇒ M21 の期間中、アケコンの実機確認は 1 回も行えない。**

**★ここで設計が 1 つ決まる。** **所有していない機体に「対応した」と言える唯一の形は、機体ごとの決め打ちをやめることである。** **⇒ キャリブレーション／リマップの導線が load-bearing になる**——**「この機体の LP はどのボタンか」を利用者に 1 度押させて覚える形にすれば、我々がその機体を持っていなくても成立する。**

**これは Q1 の (C) を選んだ時点で、実質的に不可避である。** **かつ同じ導線が 3 つの未知を同時に吸収する**——**アケコン**（非所有）／**Firefox**（未計測・index がずれる）／**将来の未知の機体**。

**⇒ 出しかたの条件**——**アケコンは「レバーレス・パッドと同じ経路で動く見込みだが、実機未検証」と明示して出す。** **「アケコン対応」と書かない**（E-84）。

### 4.2 キーボード

**そもそも Gamepad API ではない。** KeyboardEvent はイベント駆動でポーリングが無く、**チャタリングは OS 側で除去済み**である。**⇒ PoC の分布は 1 つも流用できず、同時に FR108 の論点がキーボードには存在しない。**

**⇒ 計測は要らないが、独立したサブになる。** ポーリング型と共通化できるのは「論理ボタンへの写像から先」だけで、その手前は別実装である。

## 5. 編成に直接効く材料の整理

### 5.1 D-324 から編成へ引く 4 点

| # | 事実 | 編成への帰結 |
|---|---|---|
| 1 | **user gesture が全経路で必須。** 入力 UI を開いた直後は `getGamepads()` が空を返す | **接続状態の表示と「最初の 1 回」を促す導線が要る。** 入力サブの一部ではなく、**入力 UI の初期状態そのものの設計である** |
| 2 | **判定窓はミリ秒が一次。** 計測環境は約 238 Hz で、60 Hz 環境では同じ実時間が約 1/4 フレームになる | **フレーム数で閾値を持たない。** DoD にも「ms で書く」を明記する |
| 3 | **アナログ値の機種差**（パッドのトリガー 12 段階／レバーレス 0/1） | **§2.2 のプロファイル層。** ここが独立サブになるかが編成の分岐点 |
| 4 | **押し始めと離し始めで分布が違い、離し始めが一貫して大きい**（中央値 12.50 ms・最大 50.00 ms／83.30 ms） | **どちらを判定に使うかが未決**。判定窓サブが持つ |

### 5.2 チャタリング（FR108）の扱い

**本計測条件では観測されなかった**——立ち上がり総数 50 が指示回数 50 と画面カウンタ 50 に 2 機種とも完全一致し、1〜32 ms の帯に 3 指標とも 0 件だった。

**⇒ 教訓 E-41 型の「対策が不要」という第三の結論の候補である。** ただし **2 機種・USB・Chrome のみ**であり、**一般化しない。**

**設計卓の指定**——**採るなら「2 機種で観測されなかった」を根拠として明記し、一般化しないと書く。** **「チャタリング対策を実装した」と書かないこと。** **§3.4 の BT 計測に軸 D を足すかは開発者判断とする**（§6 Q3）。**BT は再送でパケットが重複しうるため、チャタリングと似た波形が別の原因で出る可能性がある。**

## 6. 編成を止めている本当の論点 — `REQ-001` FR102

### 6.1 検出した食い違い

| 文書 | 記述 | 実装 |
|---|---|---|
| **`REQ-001` FR102**（**必須・フェーズ1**） | **「仮想コントローラはレバーレス、アーケードコントローラ、PS5パッド、キーボードの4種類に対応する」** | **未実装** |
| **`REQ-001` §16 対応表** | 「仮想コントローラ4種対応 → FR102」を **✅ 反映** と記載 | 同上 |
| **`DES-005` §6.1** | **現行の仮想コントローラはカテゴリタブ式の direct-selection であり、4 レイアウトではない。** §6.2〜§6.5 の 4 レイアウトは、**「物理入力（M21）の将来仕様として温存する」** | — |
| **`CHANGE-057`** | 同温存を明示し、**確認事項として開発者に諮って承認を得ている** | — |
| **`REQ-001` の改訂** | **`change-report-057` は「REQ-001 変更なし・本サブは要件を変えない」と記録** | — |

**⇒ 4 レイアウトは「あったらいい将来仕様」ではない。** **必須・フェーズ1 の要件の本体が、重要・フェーズ3 の M21 に預けられたまま、`REQ-001` 側が追随していない状態である。**

**同型が FR103 にもある**——**FR103（必須・フェーズ1）は「物理コントローラ（ゲームパッド・キーボード）を通じて」入力すると書くが、`REQ-001` の技術前提は「物理コントローラ・キーボードはフェーズ3」と書いており、実体は M21 にある。**

### 6.2 これが編成に効く理由

**M21 が 4 レイアウトのうち何種を負うかで、サブの本数と DoD の重さが変わる。** そしてその判断は**計測では出ない**——**測っても「アケコンをやるべきか」は決まらない。**

**設計卓はここで独断しない**（`CLAUDE.md` §8＝設計書間の矛盾は止めて確認／§10＝マイルストーン構造の独断拡張の禁止）。

## 7. スコープの選択肢

| | **(A) 実測地に絞る** | **(B) 4 レイアウト全部** | **(C) 中間 — 設計卓の推奨** |
|---|---|---|---|
| **M21 の対応** | レバーレス ＋ パッド。Chromium 系。USB ＋ BT | 4 レイアウト全部 ＋ Firefox | **ゲームパッド系 3 種を 1 つのプロファイル層で ＋ キーボードは独立サブ** |
| **追加計測** | **BT のみ**（判定窓サブの段 2） | **BT ＋ アケコン ＋ キーボード**。段 2 が 3 回 | **BT のみ ＋ アケコン実機があれば 1 点のプロファイル確認** |
| **overview** | 今書ける | **書く前にアケコン実機の有無を確定する必要がある** | 今書ける |
| **`REQ-001`** | **FR102 の改訂が要る**（対応範囲を 2 種へ縮小する CHANGE） | **FR102 を「物理側で 4 種」へ移す CHANGE** | **FR102 を「物理側で 4 種」へ移す CHANGE** |
| **利点** | 最短。測った範囲だけで作るという D-324 の警告に最も忠実 | 要件を完全に満たす | **プロファイル層を作れば 3 種目の限界費用が小さい。** キーボードは実装量が小さく別 API なので分離が自然 |
| **欠点** | **必須要件の未達が残り、行き先も M21 から外れる。** followup へ落とすと事実上の凍結 | **M21 が肥大し、開発者の実機作業が 3 回に増える。** アケコン実機の所有が前提 | **アケコンが「プロファイル未検証」で出る可能性がある** |

**推奨は (C)。** 理由は 2 つ。

1. **プロファイル層は (A) でも必要である**——D-324 が Chrome 単独で機種差を検出しているため。**⇒ 層を作る費用は (A) と (C) で変わらず、変わるのは「プロファイルを何枚書くか」だけである。**
2. **キーボードを分離すると (B) の膨張要因が消える**——**(B) が重いのは 4 種を 1 つの入力系として扱おうとするからで、Gamepad 系 3 種とキーボード 1 種に割れば、後者は前者の DoD を汚さない。**

**★いずれを採っても `REQ-001` の改訂が要る。** **CHANGE は M21 ブロックの 106 から払い出す**（M20 ブロック 098〜105 とは別）。**ただし着手前ゲートは「通知書 ＋ registry 登録」までであり、`REQ-001` 本体の改訂は as-built 確定後である。**

## 8.1 Q3 の判断材料 — Firefox 対応の負担見積り（2026-08-13 追加）

**開発者の要望**——**「製造、開発者手動確認などの負担はどれぐらい増えますか」。**

### 8.1.1 前提が 1 つ変わっている

**Q1 で (C) が選ばれ、Q2 でアケコン非所有が確定したため、キャリブレーション／リマップの導線は Firefox の有無にかかわらず必要になった**（§4.1.1）。**⇒ Firefox 対応の増分は、この導線が無い前提で見積もってはならない。** **導線が入ると「どのボタンが何番か」を我々が知らなくてよくなり、Firefox 差の大半はそこで吸収される。**

### 8.1.2 製造の増分

| 項目 | 増分 | 理由 |
|---|---|---|
| **キャリブレーション導線** | **ゼロ** | **Firefox とは無関係に必要**（§4.1.1） |
| **`mapping` の扱い** | **小** | **`mapping === "standard"` を必須条件にせず、通常経路として扱うだけ。** 最初からそう書けば追加作業ではない |
| **方向入力の読み取り** | **小** | **`buttons` と `axes` の両方から読む。** **これも Firefox 固有ではない**——**アケコンで同じ分岐が要る**（§4.1） |
| **`axes` の本数差** | **小** | **本数を固定で仮定しない、というだけ** |
| **テスト** | **小・実機不要** | **正規化関数へ Firefox 形の入力を食わせるユニット相当で足りる。** **製造だけで完結する** |

**⇒ 製造の増分は「新しいサブが 1 本増える」規模ではない。** **既に必要なサブの中の条件が数行増える程度である。** **★ただし条件が 1 つ付く**——**後付けは高い。** **Chrome 前提で書いてから Firefox へ広げると、index を仮定した箇所を探し回ることになる。最初から書けば安い。**

### 8.1.3 開発者の実機確認の増分（**こちらが本命**）

**製造はターミナル環境であり実機確認を要求できない**（playbook §1.3）。**⇒ ブラウザを 1 系統増やすと、増えるのは全部こちらである。**

**1 回の確認の中身**——**ブラウザで開く ／ コントローラを 1 度押して認識させる**（user gesture が必須＝`D-324`）**／ キャリブレーションを通す ／ 全ボタンが取れることを見る ／ 同時押しが 1 ステップにまとまることを見る。** **⇒ 目安は 1 組（ブラウザ × 機種）あたり 5〜10 分。**

| 案 | 確認の発生 | 総額の目安 |
|---|---|---|
| **(i) Firefox を DoD に入れる** | **入力に触るサブごとに Firefox × 2 機種 ＝ +2 組** | **1 ラウンドあたり +10〜20 分。** **サブが n 本なら +10n〜20n 分**（**n は overview 未確定のため見積れない**） |
| **(ii) 作りはする・DoD は Chromium 系**（**推奨**） | **M21 の完了時に 1 回だけ ＝ +2 組** | **総額で +10〜20 分** |
| **(iii) 非対応にして警告を出す** | **なし** | **0 分。ただし §8.1.4 の代償がある** |

### 8.1.4 (iii) を採らない理由

**アプリは起動時に OS 既定のブラウザを自動で開く**（`DES-001` §6・案C）。**⇒ 既定が Firefox の利用者は、警告だけを見せられてコントローラ入力を一切使えない。** **`FR105` は「重要」であり、`FR103`（必須）も物理入力を入力手段として数えている。** **⇒ 実機確認 0 分と引き換えに失うものが大きい。**

### 8.1.5 推奨と、その意味

**推奨は (ii)。** **「Firefox でも動くように作るが、動くことを完了条件にはしない」。**

**★これは Firefox を切り捨てる案ではない。** **(ii) と (i) の作りは同じである。** **違うのは、Firefox が壊れていたときに M21 を止めるかどうかだけである。** **⇒ (ii) では、Firefox の不具合は followup へ回り、M21 の完了を妨げない。**

**★(ii) を採るときの明示条件**——**「Firefox 未検証」と書く。** **「対応」と書かない**（E-84）。**完了時の 1 回の確認で問題が出たら、そこで初めて開発者判断を仰ぐ。**
