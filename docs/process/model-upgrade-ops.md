## 0. この文書が要る理由

使うモデルは、プロジェクトの途中で入れ替わる。**実際に入れ替わっている**——
`docs/handover/phase1/m7-design-session-handover_2.md` にはフェーズ1 期の配分として旧世代のモデル名が記録されており、
現在の配分は `docs/human-notes/model-allocation.md` が別の世代を指している。

**モデルが変わるたびにプロンプト体系を書き直すのは誤りである。**
書き直すと、**モデルとは無関係に効いていた規則まで巻き込んで壊す**。
逆に何もしないと、**寿命の短い設定（effort・thinking 等）が古いまま残る**。

**⇒ 触るものと触らないものを、あらかじめ分けておく。** それが本書である。

> **本書は「モデル選定」の文書ではない。** どのマイルストーンにどのモデルを充てるかは
> **`docs/human-notes/model-allocation.md` が正本**（開発者向けリファレンス・マイルストーンごとに追記）。
> **本書は「モデルが変わった後に何をするか」だけを扱う。**

## 1. 基本手順

**新モデル導入 → 現行のまま回帰を当てる → 落ちた箇所だけ直す → 触った箇所を記録する**

**先回りして書き直さない。** 落ちてから直す。

| # | 手順 | 具体 |
|---|---|---|
| 1 | **現行のまま回帰を当てる** | §3。**プロンプトを 1 文字も変えずに**先に当てる |
| 2 | **落ちた箇所だけ直す** | §2 の「触ってよいもの」に該当するかを確認してから直す。**§2 の「触らないもの」が原因に見えるときは、まず §4 を読む** |
| 3 | **触った箇所を記録する** | `docs/human-notes/model-allocation.md` へ新モデルの行を**追記**する（既存行は書き換えない＝§2.3） |

## 2. 触るもの・触らないもの

### 2.1 触らないもの（モデル非依存。モデル更新を理由に変更しない）

- **指示書の `Goal` / `Scope` / `Non-goals` / `Decisions` / `Acceptance Criteria`**
  （実装指示書テンプレの §1 背景と目的・§2 成果物・§2.2 変更しないもの・§2.3 例外条項・§7 完了条件）
- **`docs/handover/design-instruction-playbook.md` §7.1 のモデル配分判断軸**
  ——**関心の絡み合いで判断する**という軸そのものはモデルが変わっても成立する
- **役割名**（高精度実装 ／ 高速実装 ／ 高精度レビュー ／ 高速レビュー）。
  **2026-08-11 に恒久ルール側の実モデル名をこの役割名へ置換済み**（§J `instruction-templates-model-names`）。
  **役割名を実モデル名へ戻さない**——戻すと次のモデル更新でまた全置換が必要になる
- **`docs/instructions/templates/` のメタ表の構造**
- **`CLAUDE.md` ／ `.claude/settings.json` の権限・禁止事項**

### 2.2 触ってよいもの（寿命が短い。変わる前提で扱う）

- **`docs/human-notes/model-allocation.md` の実モデル名**（＝実モデル名の正本）
- **effort ／ thinking 設定 ／ verbosity**
- **サブエージェントの特性に依存した記述**（並列数・分割粒度の目安など）
- **モデル固有の workaround**——**入れるときは「なぜ要るか」と「いつ消せるか」を併記する。**
  併記が無い workaround は、次の更新で消してよいか判断できなくなる

### 2.3 記録は書き換えない（D-274 (2)）

**過去の配分は「当時どう判断したか」の記録であり、事実として正しい。** 新モデルに合わせて書き換えない。

- **`playbook` §7.2「これまでの配分実績」・§7.4** — 実モデル名が残っているのは**意図的**。同節に明記済み
- **`docs/human-notes/model-allocation.md` の完了済みマイルストーンの行** — 同書のメンテナンス方針が
  「完了済みマイルストーンの行は履歴として残す」と定めている
- **`docs/progress/` の完了報告・レビュー報告、`docs/handover/` の各期引き継ぎ**

**新モデルは追記する。** 上書きしない。

## 3. 回帰の当て方

**★新しい回帰スイートを作らない。** 既にあるもので当てる。
（実害が観測されていない段階で評価基盤を新設するのは、テンプレ提案 B-3・B-5 を見送ったのと同じ理由で割に合わない）

### 3.1 機械で当たる部分（そのまま流用できる）

```bash
bash scripts/check-artifact-integrity.sh   # ★1 本目。他の検査が壊れていないかを先に見る
bash scripts/check-stop-discipline.sh
bash scripts/check-progress-log-index.sh
bash scripts/check-doc-refs.sh
bash scripts/check-browser-storage-keys.sh
bash scripts/check-enum-sync.sh
bash scripts/check-instruction-format.sh
bash scripts/check-derived-docs.sh
```

**ただし、これらが見ているのは「成果物が規約を満たすか」であって「モデルが劣化したか」ではない。**
**緑でもモデルの劣化は検出できない。** 検出できるのは §3.2 だけである。

### 3.2 人が当てる部分（常設セットは無い。方法論を再利用する）

**常設の回帰タスクセットは保存されていない**（2026-08-11 時点）。
**保存されているのは方法論である**——

- `docs/progress/20260811-context-load-ab-pilot.md`（M19-04b・6 trial）
- `docs/progress/20260811-context-load-ab-expansion.md`（M19-05・6 trial）

**⇒ 新モデル導入後の最初の実サブで、上記と同じ形の A/B を 1 ラウンド当てる。**
専用の評価タスクを作らず、**そのとき実際にやる作業を使う**（パイロットも拡大もその形で行った）。

**見る指標**（`prompt-quality-improvement-plan` §1.3 ／ 整形版ガイド §6.2）:

| 使う | 使わない |
|---|---|
| タスク完遂率 ／ Acceptance Criteria 達成率 ／ 要件漏れ ／ 不必要な変更 ／ スコープ逸脱 ／ 誤った仕様の補完 ／ 人による修正回数 | **使用トークン ／ 実行時間 ／ 削減行数**（**裁定 15**: 削減量を効果指標にしない） |

> **★Restraint（実在しない欠陥を「高」と指摘しないか）は未測定のまま確定している**
> （§J `context-load-restraint-unmeasured`・開発者裁定で対応不要）。
> **モデルが変わったときは、ここが最初に崩れやすい。** 誤検出が目立ったら §J の当該項目を再開条件として扱う。

## 4. 「モデルのせい」に見えて違うもの

新モデルで問題が出たとき、**プロンプトを直す前にこれを疑う。**

| 症状 | まず疑うもの |
|---|---|
| 指示どおり動かない | **指示書側の欠落**。§2.1 の項目（Goal / Scope / AC）が実際に書かれているか |
| 緑なのに壊れている | **検査そのものの故障**。`check-artifact-integrity.sh` を 1 本目に回す（`environment-reliability` §4.1「資料の記述は証拠ではない」） |
| 「変更していない」はずの箇所が変わる | **`Non-goals` の書き落とし**（playbook §4.14「改変しない」の粒度） |
| 規則に従うと検査が赤 | **機構側の誤り**の可能性。2026-08-11 に実例（§16.4.1 の `\|` エスケープと検査の食い違い） |

**モデル固有 workaround を足すのは、上記を全部潰した後にする。**
