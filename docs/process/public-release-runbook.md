## 1. ★★★全体像（**リポジトリは 2 つある**）

| リポジトリ | 可視性 | 役割 |
|---|---|---|
| **`combomgr`** | **非公開** | **開発。⇒ 設計書・進捗・指示書・作業ブランチのすべてが在る** |
| **`tacpendium`** | **準備中は private、内容確認後に public** | **配布。⇒ 公開スナップショットとリリースだけが在る** |

**★★★生成は一方向である**（`D-637`）**。⇒ 公開側へ内容が渡るのは、開発者が同期を実行したときだけである。**

**★★★リリースのワークフローは*公開リポジトリでのみ*走る**（`if: github.event.repository.private == false`）**。⇒ 理由は 2 つ。**

| # | 理由 |
|---|---|
| **1** | **attestation は private / internal リポジトリでは取れない**（GitHub Enterprise Cloud を除く） |
| **2** | **開発リポへのタグは公開スナップショット生成の正規の契機である。⇒ ガードが無いと、生成のたびリリース区分が赤くなる** |

**★★これが「誤って公開するつもりのなかったバージョンが公開される」ことを構造で塞いでいる**（`CHANGE-233` §3）**。⇒ 非公開の開発リポでは、タグを打っても job がそもそも起動しない。**

### 2.A.2 ★★★来歴の問い合わせを受けたとき

**★★★公開リポジトリはリリースごとの snapshot であり、非公開リポの履歴をそのまま公開しない。⇒ 公開リポだけを見た第三者には、先に公開されていた類似コードを後から取り込んだように見える場合がある。**

**★★この見かけ上の時系列と、実際の開発時系列を混同しないこと。**

| # | 保持する証跡（**★非公開リポ側**） |
|---|---|
| **1** | **対象ファイルの初出 commit SHA と author date** |
| **2** | **当該 commit の変更統計および milestone 名** |
| **3** | **同時に追加された設計・指示・レビュー・進捗記録** |
| **4** | **初回 SCANOSS の chronology CSV と、固定した検査対象 SHA** |

**★★★これらを公開リポジトリへ常時掲載したり、非公開履歴全体を開示したりはしない。⇒ 具体的な問い合わせを受けた場合に、必要なファイル・期間・一致箇所に*限定して*提示できる状態を維持する。★提示方法と範囲は、問い合わせ内容と非公開情報への影響を確認して個別に決める。**

**★★★「日付が先なら自動的に独自実装と証明できる」という意味ではない。⇒ 日付、機能と同時に入った履歴、プロジェクト固有契約、実コード差分を組み合わせて説明するための監査証跡保全方針である。**

**★★★本方針と `ALLOW docs/**` が食い違っている**（2026-09-20 に設計卓が検出＝`D-919`）**。⇒ evidence をどこまで公開するかは `M40-01` 段 5 で候補と根拠を出し、開発者が決める。**
