> **なぜ計測するか**: ディスク使用率 100% 張り付きが一度発生したが、**再現すると固まるため障害時の計測はできない**。
> §3 が求めているのは障害の再現ではなく **平常時の値と増加速度**である。§3.1 が
> 「**15% という警告値には普遍的根拠がない。残り GB・増加速度・復旧に必要な作業領域を合わせて決める**」
> と旧案を訂正しており、**閾値を決めるために計測が先に要る**という順序になっている。

## 2. 第 1 回で判明したこと

### 2.1 ★コンテナ内の `df` は監視指標にならない

コンテナ内は「残り 905 G（使用 6%）」と表示されるが、**これは VHD の内側から見た値**で、
**1007 G は VHD の仮想最大サイズ（既定 1 TB）**である。**VHD は使った分だけ膨らみ、自動では縮まない。**

**⇒ Windows ドライブが逼迫していてもコンテナ内は余裕に見える。**
100% 張り付き時にコンテナ内から異常が見えなかったとすれば、これが理由である。**監視すべきはホスト側の残り GB。**

### 2.2 ★実サイズの 37% は 2 週間以上使われていない build cache

**build cache 23.22 GB が最大区分**で、`LAST USED` は**全件が 2 週間以上前**、大半が 3 か月前である。
**VHDX 実サイズ 58.29 GB の約 40% が、直近 2 週間 1 度も使われていない。**

### 2.3 ★キャッシュの半分が named volume 化されていない

`npm-cache` 1.4 G ／ `playwright` 641 M ／ `go-build-cache` 530 M（計 **約 2.6 GB**）は
**container writable layer に乗っている**。writable layer が 9.35 GB あるのはこれが主因と考えられる。

**writable layer はコンテナを作り直すたびに再取得になる**——§3.1 が「ボリューム化の利点は、
コンテナ writable layer への書込み、**再ビルドごとの再取得**、複数コンテナ間の重複を減らせること」と
述べているのはこの構造。**増加を止める効果ではなく、再取得を減らす効果である。**

### 2.4 孤児 volume が 3 件（計 約 493 MB）

`sf6-gomodcache-0dmoq7…`（458.4 MB）／`codex-cli-config-0dmoq7…`（28.25 MB）／
`claude-code-config-1l9ukr…`（6.375 MB）が **LINKS=0**（どのコンテナからも参照されていない）。
worktree 用コンテナの残骸と見られる。

### 2.5 旧「15%」の出どころは D: の可能性が高い

D: が **14.8%** で、旧案の警告値 15% とほぼ一致する。**Docker は C: にあるため D: の逼迫は Docker とは無関係**で、
§3.1 の「15% には普遍的根拠がない」という訂正は正しい。**割合ではなく残り GB で見るべき。**

## 3. 警告閾値の案（★根拠つき・第 2 回計測で確定する）

§3.1 は「**残り GB・増加速度・復旧に必要な作業領域**を合わせて決める」としている。このうち
**復旧に必要な作業領域は今すぐ決められる**——§3.3 が「既存 VHD の compact は、**バックアップと停止条件を含む
Microsoft 公式手順**で行う」と定めており、**バックアップに VHD と同等の空きが要る**。

> **提案する閾値: Docker のあるドライブ（C:）の残りが「VHDX サイズ × 2」を切ったら警告。**
>
> **根拠**: バックアップ 1 本（VHD と同サイズ）＋ compact の作業余裕 1 本。
> **これを切ると、復旧手順そのものが実行できなくなる。**
>
> 現在値: VHDX 58.29 GB → 閾値 **約 117 GB**。C: の残りは 776.7 GB なので**現状は十分に余裕がある**。

**割合（15% 等）ではなく残り GB で置く**理由は §3.1 のとおり。**閾値は VHD の成長に追随して自動的に上がる**
（VHD が 100 GB になれば閾値は 200 GB）ので、固定値の陳腐化が起きない。

**★増加速度は第 2 回計測でも確定しなかった**（2026-08-22。§1.4.2）。**単純計算では約 0.73 GB/日 だが確定値として扱わない。** 以下は第 1 回時点の記述： **増加速度は第 2 回計測で確定する。** 暫定の目安として、build cache のタイムスタンプ分布
（3 か月で 23.22 GB）から **約 0.25 GB/日** と推定できるが、**1 点計測からの推定であり確定値ではない**。

## 4. 第 2 回計測の手順（数日あけて同じものを実行する）

### 4.1 コンテナ内

```bash
bash scripts/measure-disk-usage.sh          # 人が読む形式
bash scripts/measure-disk-usage.sh --tsv    # 追記用（日付つき）
```

### 4.2 ホスト（Windows PowerShell）

```powershell
"### 計測日時: " + (Get-Date -Format 'yyyy-MM-dd HH:mm')

"`n--- 1) ドライブ残量 ---"
Get-PSDrive -PSProvider FileSystem | Where-Object { $_.Used -ne $null -and ($_.Used + $_.Free) -gt 0 } |
  Select-Object Name,
    @{n='Used_GB'; e={[math]::Round($_.Used/1GB,1)}},
    @{n='Free_GB'; e={[math]::Round($_.Free/1GB,1)}},
    @{n='Free_pct';e={[math]::Round($_.Free/($_.Used+$_.Free)*100,1)}} |
  Format-Table -AutoSize

"`n--- 2) WSL / Docker の VHDX 実サイズ ---"
@("$env:LOCALAPPDATA\Docker\wsl", "$env:LOCALAPPDATA\Packages") | ForEach-Object {
  if (Test-Path $_) {
    Get-ChildItem -Path $_ -Recurse -Filter *.vhdx -ErrorAction SilentlyContinue |
      Select-Object @{n='Size_GB'; e={[math]::Round($_.Length/1GB,2)}}, FullName
  }
} | Format-Table -AutoSize

"`n--- 3) docker system df（要約のみ・2 回目以降はこれで足りる）---"
docker system df
```

> **2 回目以降は `docker system df -v` の `-v` を外してよい。** 内訳の分類（§3.4 の受入条件）は
> 第 1 回で済んでおり、以降は区分ごとの合計と RECLAIMABLE が分かれば増加速度を出せる。

## 5. 回収の候補（★実行しない。§3.3 に従い提示のみ）

§3.3 は「**prune 前に対象一覧と回収見込容量を表示する**」「**全体 prune を無確認で自動実行しない。
利用中データ、再取得費用、復旧方法を確認する**」と定めている。以下は**候補の提示であり、実行は開発者の判断**。

| 候補 | 回収見込 | 再取得費用 | 備考 |
|---|---|---|---|
| **2 週間以上未使用の build cache** | **最大 23.22 GB** | 次回ビルドが遅くなる（再ダウンロード＋再ビルド） | `docker builder prune --filter until=336h`。**まず `--dry-run` 相当で対象を確認すること** |
| **孤児 volume 3 件** | 約 493 MB | worktree 用コンテナを作り直すと再取得 | `sf6-gomodcache-0dmoq7…` ／ `codex-cli-config-0dmoq7…` ／ `claude-code-config-1l9ukr…`。**LINKS=0 を実行時に再確認してから** |
| 未使用イメージ（CONTAINERS=0 が 5 件） | 共有分が大きいため**固有分のみ**（数 GB 程度） | devContainer の再ビルドが走る | 共有レイヤがあるため見かけのサイズほど回収できない |

**★VHD は prune しても自動では縮まない。** ファイルサイズを実際に減らすには、
§3.3 のとおり **バックアップと停止条件を含む Microsoft 公式手順で compact** する必要がある。
**`.wslconfig` の `sparseVhd=true` は新規作成 VHD 向けの実験的設定であり、既存 VHD の縮小操作とは別物**（§3.1）。
