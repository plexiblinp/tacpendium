## 1. 不変条件(いつでも守るもの)

1. **正史(main)への反映は人間のみ**: main は GitHub branch protection で保護(§6)。`claude/` 名前空間はクラウドセッションの作業領域であり正史ではない。正史化は常に人間のマージ。
2. **実装系 PR は、帰宅後の手動E2E 通過までマージしない**(品質ゲート。docs 系・調査系 PR はモバイルマージ可)。
3. **Plan 相当の対話**: クラウドセッションでも「計画提示→開発者応答」の往復を維持する。**重要な未決を抱えたまま進めない**(判断に迷う未決は「保留」を指示。devContainer 側の Plan Mode 自動タイムアウト対策と同じ規律)。
4. 指示書駆動・人間レビュー(PR 差分レビュー+帰宅後 PC レビュー)は従来どおり。

## 2. 出発前チェックリスト(PC・5分)

- [ ] 進行中の devContainer セッションをキリの良い所で終了(遠隔で見守れないため中途タスクを残さない)
- [ ] `git status` クリーン確認 → 開発者 push(Web 版直読とクラウドセッションの出発点の鮮度確保)
- [ ] **個別設計チャットを使う予定があれば** Web 版プロジェクトの GitHub ナレッジで **Sync now** を実行(直読の鮮度=push+Sync 時点)。※ 親(設計卓)は HEAD を直接読むため Sync 不要
- [ ] 未マージの `claude/` ブランチ・未処理 PR を棚卸し(外出中に触るものを決める)
- [ ] PC は通常どおり電源 OFF/スリープでよい(ローカル常駐は不要)

## 3. 外出中(スマホのみ)

- **設計(親・2026-08-11 変更)**: **Claude Code on the web でセッションを開始し、最初の 1 手で `bash scripts/design-desk-arm.sh` を実行する**(武装＝実装ソースを作業ツリーから物理排除)。以後は `docs/` を直接 Read/Edit して設計・指示書作成・ボード更新・DES 反映を行う。**成果物は repo に着地するのでコピー還流が要らない。** 武装しないまま成果物を作らせないこと(`--status` で確認)。
- **設計(個別設計チャット)**: 長い合議が要る設計判断だけ Web 版チャット(Projects)へ外注する。**設計変更権限は持たせず、最終レポート 1 本を出させる**(`parallel-ops` §06)。GitHub 直読しながら作業させ、直読版の鮮度=最終 push+Sync 時点であることを常に認識させる。
- **製造(軽量)**: Claude Code on the web(claude.ai/code)でセッションを開始し、調査・docs 整備・(V-1 通過後は)独立性の高い実装を指示。リポジトリの CLAUDE.md・`.claude/settings.json`(hooks 含む)・`.claude/commands/` はクラウドにもそのまま適用される。**製造セッションは武装しない**(マーカーが無ければガードは即 exit 0 で、実装ソースはそのまま見える)。
- **還流**: 個別設計チャットのレポートをコピー→親のクラウドセッションへ投入→親が配置+commit+push(`claude/` ブランチ)→PR 化。**親自身の成果物は直接 repo へ書くので還流不要**(2026-08-11 の移行で消えた往復)。
- **レビュー**: GitHub モバイルアプリで PR 差分を確認。docs 系はモバイルマージ可。**実装系はマージせず帰宅後へ**(§1-2)。

## 4. 帰宅後(PC)

- `claude/` ブランチ・PR を PC でレビュー(`git log` / `git diff`。人間レビューの最終担保)
- 実装系 PR: ローカルで checkout(開発者操作)→ **手動E2E** → 合格後にマージ
- マージ後に Web 版ナレッジを Sync(次の設計作業の鮮度確保)
- tmp/ の整理・翌日の仕込み

## 5. Claude Code on the web の注意(クラウド VM 固有)

- **フレッシュ VM**: セッションはリポジトリの新規クローンから始まる。ローカルにしか無いもの(未 push のコミット・dev DB・`tmp/` の中身)は存在しない。
- **`tmp/` は揮発**: `.gitignore` 対象のファイルはセッション終了で消える。成果物は必ずコミット対象パスに置く(課題レポートは `docs/handover/design-reports/` = `/design_handover_report` が対応済み)。
- **環境セットアップ**: Go 1.26.x / pnpm 9.13 / 依存取得はクラウド環境設定(環境 UI の Setup script)で構成する(リポジトリ非侵襲)。`go test ./...` / `pnpm test` が通ること(V-1)が実装系タスク解禁の条件。手動E2E は VM では実施不可(§1-2 のゲートで担保)。
- **タスクの出し方**: 指示書パス+スコープを明記(指示書はコミット済みなので VM から読める)。曖昧な大改変指示をしない。
- **統制逸脱時(差戻しトリガー T5)**: 指示書無視の大改変 PR・E2E 前マージ規律違反が出たら、その PR を**閉じるだけ**でよい(`claude/` 隔離が差戻しを内蔵)。2 回連続したらクラウドでの実装系タスクを停止し、調査・docs 系のみ継続(再開は開発者判断)。

**⇒ 運用**: **クラウド実行時の E2E は「小バッチでの切り分け ＋ 開発者機での完走」を前提とする。**

**切り分け手順(この順で行う)**

1. **失敗の分布を見る。** **広範囲に散っていて、変更した面と無関係な spec まで落ちているなら環境要因を疑う。** 変更した面に集中しているならサブ起因を疑う。
2. **小バッチで再実行する。** **同じテストが通るなら環境要因である。**
3. **変更が壊しうる面を狙って実行する。** そこが通れば、サブ起因でないことの積極的な証拠になる。
4. **完了報告には「フルスイートの失敗件数」「小バッチでの再実行件数と結果」「開発者機での完走可否」の 3 つを書く。** **「E2E が落ちた」だけでは、次の担当が 1 から切り分けをやり直す。**

> **★「フルで落ちるが小バッチでは通る」を、サブの失敗として扱わない／サブの失敗を環境要因として流さない**——**両方向に注意する。** 既知の flaky はボード P-14 / P-22 にも別途ある。


### 5.2 ★クラウド環境の設定は 3 種あり、いずれもリポジトリからは変えられない（2026-08-19 新設・`IMPROVE-01` の実測＝**D-452**）

| 経路 | 置き場 | 何に効くか | キャッシュ |
|---|---|---|---|
| **SessionStart hook** | **リポジトリの `.claude/settings.json`** | **ローカルもクラウドも。** resume 含む毎セッション実行 | **★載るかは未確定**（followup `session-start-hook-cache-behavior-unknown`） |
| **Setup script** | **claude.ai/code の環境ダイアログ**（**リポジトリ外**） | **クラウドのみ。** Claude Code 起動前・初回のみ | **完了後にスナップショットされる**と明記あり |

**★到達手段**——**claude.ai/code の環境セレクタ（雲アイコン → 歯車）。** **設定ページや直リンクは無い。** **★スマートフォンからは操作できない**（2026-08-19 開発者実測）。

#### ★5.2.1 Go 製ツールを `go install` で入れるときは `GOTOOLCHAIN` を固定する

**★クラウド実行環境の素の `go` は、プロジェクトが使う版より古い。**

**`go install pkg@version` は、そのツール自身の `go.mod` からツールチェーンを決める。** **⇒ 素の `go` が本体コードより古い環境では、本体コードを型検査できないバイナリができる。**

**症状**——解析時に `package requires newer Go version` の形で落ちる。**★版を上げても直らない**（新しい版ほど新しい Go を要求するが、それでも本体には届かないことがある）。

**対処**——`GOTOOLCHAIN="$(go env GOVERSION)"` を付けて入れる。**⇒ プロジェクトが選ぶ版と同じものでビルドされる。**

> **★devContainer では素の `go` が本体と同じ系列のため、本指定は無害である**（同じ版が選ばれるだけ）。**⇒ 両環境で同じ書き方をしてよい。**
>
> **★エラー文は最初から環境側だと言っている**（`application built with go1.xx`）。**「版を上げる」を試す前に、失敗しているのが「そのツールの中身」なのか「ビルド／実行の環境」なのかを分けること。**

#### ★5.2.2 SessionStart hook の出力は stderr に限る

**stdout は Claude の文脈へ注入される。** **⇒ 毎セッション数行が積まれると、本当に見るべき出力が埋もれる。**

**★副作用**——**Claude 側から hook の発火を言葉で確認する経路が無い。** **⇒ 発火の確認は、hook が触るファイルの mtime とコンテナ起動時刻の突合で行う。**

## 6. push・ブランチ統制(多層防御)

| 層 | 内容 | 状態 |
|----|------|------|

### 6.1 ブランチ戦略(2026-08-11 新設・設計卓の Code 化に伴う)

**Claude Code on the web はセッション開始時に作った 1 ブランチ上で作業し、途中で切り替えられない。** この制約を前提に、**設計卓と製造はどちらも main から分岐し、どちらも main へマージする**。

```
main ──┬─→ claude/desk-YYYYMMDD-N   (設計卓・docs のみ)      ──→ main
       │
       └─→ claude/m{N}-{NN}          (製造・code + progress)  ──→ main
```

| ブランチ | 誰が | 触る範囲 | マージ条件 |
|---|---|---|---|
| `claude/desk-YYYYMMDD-N` | 親(設計卓) | **`docs/` のみ**(武装により実装ソースを持たない) | **docs 系なので即マージ可**(§1-2) |
| `claude/m{N}-{NN}` | 製造担当 | code ＋ `docs/progress/` | **手動 E2E 通過後**(§1-2) |

**★設計卓ブランチから製造を分岐させない。** 一見自然に見えるが、次の 3 つが起きる。

1. **マージが 2 段になり、開発者の作業が倍になる**——マージは deny で人間限定である(CLAUDE.md §10)。「製造 → 設計卓 → main」にすると、サブごとに 2 回マージすることになる。
2. **★共有直列リソースの正本がブランチ上に載る**——`parallel-board.md` ／ `change-number-registry.md` ／ `followup-backlog.md` は playbook §21.3「**現行版の正本は repo に置く**」の対象である。分岐上で採番やボード更新をすると **main の版と分岐版のどちらが正か曖昧になる**。これは E-33／G-5(中央が repo を見られないまま「反映済」と宣言した事故)の再演であり、**別リポジトリ化を却下したのと同じ理由**である。
3. **長命ブランチの鮮度問題**——設計卓は `fetch` / `pull` が deny のため、**稼働中に main の進行を取り込めない**。分岐点が古いまま作業が積み上がる。

**分岐させなくてよい理由**: 設計卓は sparse-checkout により `internal/` `web/src/` を持たないので、**触れるファイルが物理的に分かれており衝突しない**。そして**製造が必要とするのは「マージ済みの指示書」であって、設計卓の作業中ブランチではない**。指示書は docs 系なので書けた時点で即マージでき、待ち時間は生じない。

> **注意**: `followup-backlog.md` は**親と製造の両方が書く**(製造・レビューの停止時記録が §J に入るため)。並列時はここだけコンフリクトしうる。**現行でも同じ構造**なので新規リスクではないが、マージ時に留意する。

## 6.2 設計卓の交換時期(2026-08-11 新設)

**判定の芯が「疲弊の兆候」から「同期点 ＋ 実測」へ変わった。**

Web 版では自己申告・感覚・スクロール量で判断するしかなかった。Code では `parallel-ops` §05 の本来の設計が成立する——

> 状態は repo のボードファイルへ出す ＝ **いつでも使い捨て可**

Web 版でこれが成立していなかったのは、ボード更新が「親が全文出力 → 開発者が貼る」という手作業で、§05 V2.1 が「**未反映 5 件まで溜めてよい**」と上限を設けざるを得なかったからである。**反映係の廃止と Code 化で「未反映」という概念自体が消え、ボードは常に最新に保てる。⇒ 交換のコストがほぼゼロになった。**

**交換トリガ(優先順)**

| # | トリガ | 理由 |
|---|---|---|
| **1** | **サブマイルストーンの完了時**(既定) | 製造が main へマージされると設計卓ブランチは古くなる。`fetch` が deny のため、**新しい情報を取り込む唯一の方法が「畳んで新ブランチで起動し直す」こと**。ここが自然な同期点 |
| 2 | **`/context` の実測が閾値超え** | スクロール量より正確。**閾値は M20 の 1 サブを回して実測してから決める**(サブ 1 本あたりの消費が未計測) |
| 3 | 裁定・契約の発行直後 | 大きな判断のあとは探索の残骸が積もる。`parallel-ops` §00「熟考は高価、結論は安価」からすると、**結論を出した直後が最も安く畳める** |
| 4 | 逼迫の自己申告 | 残すが、1〜3 で先回りできれば到達しないはず |

### ★交換のよい節目(仕事の状態として畳んでよいか) — 2026-08-15 昇格

**上のトリガは「いつ交換するか」を、下のチェックリストは「作業ツリーが片付いているか」を見る。** **本項が見るのは 3 つ目の軸——「仕事の状態として畳んでよいか」である。** **次の 4 条件が揃ったときが交換の好機である。**

| # | 条件 | なぜ |
|---|---|---|
| 1 | **in-flight な裁定がゼロ** | 製造からの差戻しに回答中でない。**回答の途中で畳むと、次の親は「何を問われていたか」を会話文脈から復元できない** |
| 2 | **開発者判断待ちがゼロ、または待ちの内容がボードに書き切れている** | ボード §4 保留事項が受け皿である。**「口頭で聞いてある」は引き継がれない** |
| 3 | **完了したサブの CHANGE 三点セットが着地している** | **as-built と DES が乖離していない**。乖離したまま畳むと、次の親は設計書を信じて誤った前提で書く |
| 4 | **次の手番が「ボードと指示書だけで始められる」** | **前任の会話文脈を要しない**。これが `parallel-ops` §05「新しい親はボードから起動する」の実質的な判定条件である |

### ★交換の合図(劣化は自覚できない) — 2026-08-15 昇格

**上の 4 条件は「畳んでよいか」を見るが、本項は「畳むべきか」を見る。**

- **同じことを二度調べた。**
- **直近の裁定の根拠を、ボードを引かずに記憶から書いている。**
- **起動プロンプトの制約が薄れてきた**(武装ルール・運用規則を破りかける)。
- **自分の裁定同士の食い違いを、ボードを引かずには気づけなくなった。**

> **★長い文脈で最初に劣化するのは出力の質ではなく「自分の過去の判断との整合」である。** 局所的には正常に見えるため、**品質で判断すると手遅れになる**。**節目で機械的に交換するのが正しい運用である。**
>
> **★本項は §6.2 冒頭の「判定の芯を疲弊の兆候から同期点 ＋ 実測へ変えた」と矛盾しない。** **同期点で機械的に交換するのが既定であり、本項は既定が働かなかったときの補助である。** **冒頭が疲弊の自己申告を判定の芯から外したのは「自己申告が不正確だから」であって、「劣化の兆候が無いから」ではない。** **⇒ 上の 4 つは自己申告ではなく、いずれも観測可能な出来事である**(二度調べたか ／ ボードを引いたか ／ 制約を破りかけたか ／ 食い違いに気づけたか)。
>
> **★出所** — `docs/handover/phase3/m20-desk-startup-prompt.md` §補足(開発者向けメモ)。**2026-08-15 の分配漏れ検査で「他のどの資料にも存在しない」と確定したため本節へ昇格した**(ボード **D-389**。検査は `docs/progress/20260815-improvement-lane-batch1-report.md` §5.4)。

> **★★「ボードは状態であって憲章ではない」**（2026-08-20 昇格。出所＝`docs/handover/phase3/m20-desk-startup-prompt.md` §補足「なぜこの形にしたか」）。
> **⇒ 起動プロンプトを書かせる作業を廃止したとき、状態はボードが引き継いだが、規律（＝守るべき規則の集合）は宙に浮きかけた。**
> **★現在の解は「ボードの頭ブロックが【落としてはいけない規律】を持つこと」である**（`parallel-board.md` の冒頭）。**⇒ 新しい親はここから憲章を受け取る。**
> **★この節を薄くしないこと**——**薄くすると、状態だけを引き継いで規律を引き継がない親が生まれる。** **規律はボードの状態が変わっても変わらない部分であり、状態の更新と同じ手番で消してはならない。**

**交換前チェックリスト**

- [ ] `git status` がクリーン(未コミットを抱えたまま畳むとブランチが宙に浮く)
- [ ] push 済み(`git push origin claude/desk-…`)
- [ ] **ボードが最新**(`parallel-board.md` §1 マイルストーン状況・§2 予約レンジ・§3 裁定ログ)
- [ ] PR を出した(開発者のマージ待ち)
- [ ] **★上の「交換のよい節目」4 条件を満たしている**(仕事の状態として畳んでよいか)

> **★引き継ぎプロンプトを書かせる作業は不要になった。** 次の親は**ボードから起動する**(`parallel-ops` §05 の設計どおり)。
> Web 版期に必要だった「親の寿命対策としての引き継ぎ資料作成」は、ボードが常時最新である限り重複作業である。
