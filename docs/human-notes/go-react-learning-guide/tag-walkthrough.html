タグ管理 完全ウォークスルー
— 1 機能でバックエンド 4 層とフロントエンドを通しで読む

題材は /tags/manage(タグ管理画面)。タグの一覧表示・新規作成・編集・削除ができる、このアプリで最も小さく素直な CRUD 機能です。DB の 1 行がブラウザの 1 行になるまで/フォームの入力が DB の 1 行になるまでを、実コードで全区間追跡します。

前提 Go プライマーとReact/TS プライマーの内容(エラー処理・インターフェース・useState・TanStack Query)は説明済みとして進めます。詰まったらそちらへ。

1. 機能の全体像

1.1 API は 5 本

internal/api/tag/routes.go(全 13 行)
func RegisterRoutes(g *echo.Group, h *Handler) {
    g.GET("/tags", h.List)          // 一覧(?category= &include_usage= &character_id=)
    g.GET("/tags/:id", h.Get)       // 単体取得
    g.POST("/tags", h.Create)       // 作成
    g.PATCH("/tags/:id", h.Update)  // 部分更新
    g.DELETE("/tags/:id", h.Delete) // 削除(?force=true で使用中でも削除)
}

g は main.go:480 で作られた /api グループなので、実際の URL は /api/tags です。この 13 行が「この機能の API 仕様の一覧表」を兼ねます — Echo ではルート登録がコードなので、仕様書とコードが乖離しません。

1.2 テーブルは 2 つ

テーブル役割カラム

combo_tagsコンボ⇔タグの多対多関連combo_id, tag_id(tags 削除時は ON DELETE CASCADE で道連れ)

2. バックエンド編 — 下(DB)から上(HTTP)へ

読む順序はあえて下の層からにします。データの形(model)→ 永続化(repository)→ 業務規則(service)→ HTTP 変換(handler)の順に積み上げると、各層の「役割の違い」が見えやすいからです。

2.1 model — データの形と定数

internal/model/tag.go:50-71(抜粋)

2.2 repository — SQL の置き場所

リポジトリ層の責務は「SQL の実行と、行 ⇔ struct の詰め替え」だけです。業務判断はしません。

一覧: 条件分岐を SQL 側に押し込むイディオム

internal/repository/tag/repository.go:49-72(listSimple)
q := `
    SELECT id, user_id, name, category, color
    FROM tags
    WHERE user_id = ?
      AND (? = '' OR category = ?)          -- category 未指定('')なら全件、指定ありなら絞り込み
    ORDER BY CASE WHEN category IS NULL THEN 1 ELSE 0 END, category, name
`
rows, err := r.db.QueryContext(ctx, q, userID, category, category)  // 同じ値を 2 回バインド
if err != nil {
    return nil, fmt.Errorf("tag list: %w", err)
}
defer rows.Close()

var tags []model.Tag
for rows.Next() {                             // カーソルを 1 行ずつ進める
    var t model.Tag
    if err := rows.Scan(&t.ID, &t.UserID, &t.Name, &t.Category, &t.Color); err != nil {
        return nil, fmt.Errorf("tag list scan: %w", err)
    }
    tags = append(tags, t)
}
return tags, rows.Err()
  • (? = '' OR category = ?) は「Go 側で SQL 文字列を組み立て分岐する代わりに、条件そのものを SQL に書く」イディオム。SQL は常に 1 パターンでプリペアが効き、コードも短い
  • rows.Scan(&t.ID, ...) — ORM がないので、SELECT した列の順番と Scan に渡すポインタの順番を手で一致させる。ここがずれるとバグるので、列とフィールドは常に同順で書く規律がある
  • 最後の rows.Err() — ループが「正常終了」か「途中でエラー中断」かはこれで判別する。忘れやすいので定型で必ず付ける

使用件数付き一覧: LEFT JOIN の ON 句に置いた条件

タグ管理画面は各タグの「使用コンボ数」バッジを出すため、include_usage=true で JOIN 集計版が走ります。ここに実務的な SQL の学びどころがあります:

internal/repository/tag/repository.go:74-94(listWithUsage、コメント要約付き)
// characterID のフィルタは LEFT JOIN の ON 句に置く(WHERE に置くと、当該キャラの
// コンボを持たないタグが結果から消えてしまうため)。
// 論理削除(ゴミ箱内)のコンボは数えない。
q := `
    SELECT
      t.id, t.user_id, t.name, t.category, t.color,
      COUNT(c.id) AS usage_count
    FROM tags t
    LEFT JOIN combo_tags ct ON ct.tag_id = t.id
    LEFT JOIN combos c ON c.id = ct.combo_id
      AND c.deleted_at IS NULL                 -- ゴミ箱のコンボは数えない
      AND (? IS NULL OR c.character_id = ?)    -- キャラ絞り込みも ON 句で
    WHERE t.user_id = ?
      AND (? = '' OR t.category = ?)
    GROUP BY t.id
    ORDER BY CASE WHEN t.category IS NULL THEN 1 ELSE 0 END, t.category, t.name
`
なぜ WHERE ではなく ON に書くのか LEFT JOIN の後の WHERE で c.character_id = ? と絞ると、「そのキャラのコンボが 1 件もないタグ」は行ごと消えてしまい、「usage_count = 0 のタグを一覧に出す」要件が壊れます。ON 句に書けば「JOIN の相手が絞られるだけ」でタグ側の行は残り、COUNT が 0 になります。コード内コメント(repository.go:75-80)がこの理由と「削除ガード側の CountUsage はゴミ箱を含む(意図的な非対称)」まで説明しており、コメントは Why を書くという良い見本にもなっています。

作成・更新・削除: RowsAffected と再取得

internal/repository/tag/repository.go:142-154(Create)/ 206-219(Delete)
func (r *repository) Create(ctx context.Context, userID int64, input model.CreateTagInput) (*model.Tag, error) {
    q := `INSERT INTO tags (user_id, name, category, color) VALUES (?, ?, ?, ?)`
    res, err := r.db.ExecContext(ctx, q, userID, input.Name, input.Category, input.Color)
    if err != nil {
        return nil, fmt.Errorf("tag create: %w", err)
    }
    id, err := res.LastInsertId()          // AUTOINCREMENT の採番結果
    ...
    return r.Get(ctx, userID, id)          // INSERT 後に SELECT し直して完全な行を返す
}

func (r *repository) Delete(ctx context.Context, userID, tagID int64) error {
    res, err := r.db.ExecContext(ctx, `DELETE FROM tags WHERE id = ? AND user_id = ?`, tagID, userID)
    ...
    n, err := res.RowsAffected()
    ...
    if n == 0 {
        return ErrNotFound                 // 影響 0 行 = そもそも存在しなかった
    }
    return nil
}

RowsAffected() == 0 を「存在しない」と解釈して ErrNotFound に変換するのは、「SELECT で存在確認 → DELETE」の 2 クエリを 1 クエリで済ませる定石です。Update(repository.go:157-192)も同じパターン + プライマー §8.1 で見た動的 SET 句組み立てです。

CASCADE は「書けば効く」とは限らない — SQLite の PRAGMA は接続単位 combo_tags の道連れ削除(§1.2 の ON DELETE CASCADE)は、実は長らく発火するかどうかが運任せでした。SQLite の PRAGMA foreign_keys は接続ごとの設定ですが、初期化時の 1 回しか発行していなかったため、database/sql のコネクションプールが複数接続を張ると FK=ON なのはそのうち 1 本だけ — DELETE がどの接続に乗るか次第で CASCADE が効いたり効かなかったりし、実 DB に combo_tags の孤児行が残っていました。M23-10 で全接続に PRAGMA が届くよう修正され、現在は Delete のコメント(repository.go:194-205)がこの経緯を Why として記録し、テスト TestForeignKeys_CascadeActuallyFires が挙動を固定しています。「スキーマに書いた制約」と「実行時に有効な制約」は別物という、SQLite + プール構成ならではの学びどころです。

2.3 service — 業務規則の置き場所

サービス層はリポジトリを組み合わせて業務ルールを実現します。一番密度が高いのが削除です:

internal/service/tag/service.go:104-126(DeleteTag = VAL-T03 の実装)
func (s *service) DeleteTag(ctx context.Context, userID, tagID int64, force bool) error {
    if _, err := s.repo.Get(ctx, userID, tagID); err != nil {   // ① 存在確認
        if errors.Is(err, tagrepo.ErrNotFound) {
            return ErrNotFound            // repo のエラーを service のエラーに詰め替え
        }
        return err
    }
    if !force {                                                 // ② force でなければ使用中チェック
        count, err := s.repo.CountUsage(ctx, tagID)
        if err != nil {
            return err
        }
        if count > 0 {
            return &TagInUseError{UsageCount: count}            // 件数付きエラー(VAL-T03)
        }
    }
    err := s.repo.Delete(ctx, userID, tagID)                     // ③ 削除実行
    if errors.Is(err, tagrepo.ErrNotFound) {
        return ErrNotFound
    }
    return err
}
レイヤごとにエラーを持ち替える理由 リポジトリの tagrepo.ErrNotFound をそのまま上に流さず、サービスの ErrNotFound(errors.go:6)へ詰め替えています。ハンドラが「サービス層のエラーだけ知っていればよい」状態を保つためで、層の依存方向(api → service → repository)を崩さない小さな規律です。

作成(CreateTag、service.go:65-79)はプライマー §5.1 で全文を読みました: 空名検証 → 全件取得して重複チェック → INSERT、という素直な流れです。タグは 1 ユーザー数十件程度の想定なので「全件取って Go 側で重複チェック」で十分、という規模感の判断も読み取れます。

2.4 handler — HTTP と Go 世界の境界

ハンドラの仕事は 3 つだけです: (1) HTTP から入力を取り出して型にする、(2) サービスを呼ぶ、(3) 結果・エラーを HTTP(ステータス + JSON)に変換する。Create を見ると全部入りです:

internal/api/tag/handler.go:84-103(Create)
func (h *Handler) Create(c echo.Context) error {
    var input model.CreateTagInput
    if err := c.Bind(&input); err != nil {                       // (1) JSON → struct
        return c.JSON(http.StatusBadRequest, model.NewAPIError("invalid_request", ...))
    }

    tag, err := h.service.CreateTag(c.Request().Context(), mw.UserIDFrom(c), input)  // (2)
    if err != nil {
        switch {                                                  // (3) エラー → ステータス
        case errors.Is(err, tagsvc.ErrTagNameEmpty):
            return c.JSON(http.StatusBadRequest, model.NewAPIError("tag_name_empty", "タグ名は必須です"))
        case errors.Is(err, tagsvc.ErrTagNameDuplicate):
            return c.JSON(http.StatusConflict, model.NewAPIError("tag_name_duplicate", "同名のタグが既に存在します"))
        default:
            slog.ErrorContext(c.Request().Context(), "create tag", slog.String("err", err.Error()))
            return c.JSON(http.StatusInternalServerError, model.NewAPIError("internal_error", ...))
        }
    }
    return c.JSON(http.StatusCreated, tag)                       // (3) struct → JSON、201
}

補足ポイント:

  • mw.UserIDFrom(c)(middleware/user.go:60-65)— 以前は固定の defaultUserID = 1 でしたが、M22-02 の複数利用者対応で廃止。X-User-Id ヘッダをミドルウェア UserContext が解決して echo.Context に載せ、ハンドラは取り出すだけ。★これは認証ではなく「誰として操作するか」の札(DES-002 §8。入場の可否は別の簡易パスワード認証が判定)で、ヘッダが無ければ既定利用者へ倒します。「定数 1 を書かないこと」とコード側にも明記されています
  • 想定内エラー(空名・重複)はログに出さず、想定外(default)だけ slog.ErrorContext でログする。ログノイズを増やさない設計
  • クエリパラメータの取り出しは List(handler.go:37-47)が見本: c.QueryParam("character_id") は文字列なので strconv.ParseInt + 正数チェックを手書きし、不正なら 400
  • エラー応答は常に model.NewAPIError(code, message) の統一形式 {"error": {"code": ..., "message": ...}}。フロントはこの code で分岐する(後述)

3.2 API クライアント — fetch の薄いラッパ

web/src/features/tag/api/tagApi.ts:27-47, 70-75(抜粋)
async function request<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(path, {
    credentials: "same-origin",
    ...init,
    headers: { "Content-Type": "application/json", ...(init?.headers ?? {}) },
  });
  if (!res.ok) {                                    // 4xx/5xx ならエラーボディを読んで throw
    let body: TagErrorResponse | null = null;
    try { body = (await res.json()) as TagErrorResponse; } catch { /* パース失敗は null */ }
    throw new TagApiError(res.status, body, `HTTP ${res.status}`);
  }
  if (res.status === 204) return undefined as T;    // DELETE の No Content 対応
  return res.json() as Promise<T>;
}

export const tagApi = {
  ...
  create(input: CreateTagInput): Promise<Tag> {
    return request<Tag>("/api/tags", { method: "POST", body: JSON.stringify(input) });
  },
  ...
};

TagApiError(tagApi.ts:8-25)は Go 側の統一エラー形式を受け止めるクラスで、err.code でバックエンドのエラーコード("tag_name_duplicate" 等)、err.usageCount で details 内の件数が取れます。バックエンドの handler.go とフロントの tagApi.ts は「エラー形式」という契約で結ばれているわけです。

3.3 フォームの提出 — zod 検証から 409 ハンドリングまで

保存ボタンを押したときの処理は useTagFormDialog に集約されています:

web/src/features/tag/hooks/useTagFormDialog.ts:53-74(handleSubmit)
const handleSubmit = form.handleSubmit(async (values) => {   // zod 検証を通過した値だけが来る
  try {

    }

zod スキーマが「ファクトリ」になった理由(M24-07 の i18n 対応) 検証メッセージも i18n キー化されたため、スキーマは createTagFormSchema(t)(useTagFormDialog.ts:16-22)という関数になりました。モジュール読込時にスキーマを 1 回だけ作ると、エラーメッセージ文字列がその時点の言語で「焼き込まれ」、言語を切り替えても旧言語のまま残ります。フック側で useMemo(() => createTagFormSchema(t), [t])(同 37 行)とし、言語が変わるたびに作り直すのが解です。Flask/Babel で gettext をインポート時に評価してしまい lazy_gettext に直す、あの問題と同型です。

ここで二重のバリデーションが完成します: 空名・色形式は zod がクライアントで即時に弾き(サーバーへ行かない)、名前重複はサーバーだけが判定できるので 409 を受けてフィールドエラーに変換します。category || undefined の正規化は「空文字を送ると Go 側で *string が空文字を指してしまい、NULL と区別がつかなくなる」のを防ぐ、境界面の小さな配慮です。

  • mutateAsync は Promise を返す版。フォーム側の try/catch(§3.3)でエラーを拾うために async 版を使う。削除は結果をフォームに返す必要がないので mutate(投げっぱなし + onSuccess コールバック)
  • 削除フローはバックエンドの VAL-T03 とフロント UI の合作: 一覧は include_usage=true で取得しているので各タグの usageCount を既に知っており、確認ダイアログ(TagDeleteConfirmDialog)で件数を見せた上で ?force=true を付けて DELETE する
  • toast.success は画面上部に出る通知(sonner ライブラリ)。Flask の flash() のクライアント版

3.5 タグ選択欄のキーボード操作 — 部品統合ではなく「挙動の共有」(M27-02a)

コンボ編集画面のタグ欄 TagSelector(features/tag/components/)は、キャラ選択などが使う共通部品 SearchableSelect とは別実装です(タグの新規登録行・×付きチップ列など固有の要素を持つため)。長らく「キャラ選択では ↓ キーで候補へ入れるのに、タグ欄では入れない」という同一画面内の非対称があり、M27-02a で解消されました。このとき採られた設計判断が学びどころです:

web/src/hooks/useListboxKeyNav.ts:22-59(抜粋)
export function useListboxKeyNav<T extends HTMLElement = HTMLUListElement>() {
  const listRef = useRef<T>(null);

  function optionButtons(): HTMLElement[] {
    return Array.from(
      listRef.current?.querySelectorAll<HTMLElement>('[role="option"]') ?? [],
    );
  }

  function moveFocus(delta: number, from?: HTMLElement) {
    const buttons = optionButtons();
    if (buttons.length === 0) return;
    const current = from ? buttons.indexOf(from) : -1;
    // 検索欄からの ↓ は先頭へ、↑ は末尾へ。それ以外は循環移動
    const next =
      current === -1
        ? delta > 0 ? 0 : buttons.length - 1
        : (current + delta + buttons.length) % buttons.length;
    buttons[next]?.focus();
  }
  ...
  return { listRef, handleListKeyDown };
}
  • 部品を統合せず、挙動だけを共有した — TagSelector を SearchableSelect へ丸ごと寄せる案は、タグ固有の機能(新規登録行など)を 15 コントロールが載る共通部品へ持ち込むことになるため退けられ、約 30 行のキーボード処理だけが useListboxKeyNav フックとして切り出されました。「コンポーネントの共通化は重いが、フックの共通化は軽い」という React の再利用単位の使い分けです
  • ハイライト位置の state を持たない — 現在位置を useState で管理せず、実 DOM のフォーカスそのものを位置とする(roving focus)。検索で候補が絞り込まれても「state と DOM の位置合わせ」の同期コードが不要になります
  • role="option" が契約 — フックは listRef 内の [role="option"] だけを対象にするので、「候補として ↓↑ で辿れるか」は利用側が role を付けるかで決まります。ARIA 属性がアクセシビリティとロジック両方の契約を兼ねる設計です
  • Enter はフックで扱わない — 候補は <button type="button"> なので、フォーカスさえ載ればブラウザ既定の動作で onClick が発火します。「選んだら閉じる(単一選択)/開いたまま(複数選択)」の差は利用側の onClick に残り、フックは方向キーだけに徹します
unmount とフォーカスの落とし穴 TagSelector.tsx:72-85 の handleCreate にはもう 1 つ実戦的な教訓があります。「〜を新規登録」ボタンにフォーカスが載ったまま作成すると、作成完了で検索語がクリアされてこのボタン自体が unmount されます。React はフォーカスを親要素へ戻してくれないため、フォーカスは document.body へ落ち、以後 ↓ も Enter も候補へ届かなくなります。対策は作成後に searchRef.current?.focus() で検索欄へ明示的に戻すこと。「フォーカスの載った要素を消すときは、次のフォーカス先を自分で決める」という定石です。

4. 通しシーケンス — 「保存」クリックから一覧更新まで

ここまでの部品を 1 本につなぎます。ユーザーが新規作成ダイアログで「作成」を押した瞬間から:

  1. FETagFormDialog の <form onSubmit={handleSubmit}> が発火。RHF が zod スキーマで検証(createTagFormSchema、useTagFormDialog.ts:16-22)。空名ならここで止まり <FormMessage /> にエラー表示 — サーバーへは行かない
  2. FE検証通過 → onSubmit({name, category, color})(親の handleFormSubmit)→ createMutation.mutateAsync → tagApi.create(input)
  3. FEfetch("/api/tags", {method:"POST", body: JSON.stringify(input)}) — HTTP リクエスト発射。開発時は Vite が localhost のバックエンドへプロキシ
  4. BEEcho がルート表から POST /api/tags → Handler.Create を特定。前段でミドルウェア(RequestID 採番・アクセスログ・CORS・簡易パスワード認証・X-User-Id → 利用者 ID 解決)が通過
  5. BEc.Bind(&input) が JSON を model.CreateTagInput へ逆シリアライズ(struct タグ json:"name" がマッピング表)
  6. BEservice.CreateTag: validateName(VAL-T02)→ 既存タグ全件取得 → 名前重複チェック(VAL-T01)
  7. DBrepository.Create が INSERT INTO tags (user_id, name, category, color) VALUES (?,?,?,?) を実行、LastInsertId() で新 ID 取得、Get で完全な行を SELECT し直す
  8. BEハンドラが c.JSON(http.StatusCreated, tag) — struct が json タグに従いシリアライズされ、{"id":5,"userId":1,"name":"対空",...} が 201 で返る
  9. FErequest<Tag> が res.ok を確認して JSON をパース → mutation 成功。onSuccess で invalidateQueries({queryKey: queryKeys.tags.all()})(= ["tags"])— タグ系キャッシュ全部に前方一致で「古い」マーク
  10. FEフォーム側の await が解けて onClose() → setFormOpen(false) → ダイアログが閉じる。toast.success("タグを作成しました")
  11. FETanStack Query が無効化された queryKeys.tags.list(true)(= ["tags", {include_usage:true}])を自動再取得 → GET /api/tags?include_usage=true が走り(手順 4〜8 の GET 版)、新しい一覧が返る
  12. FEtagsQuery.data が新配列に変わる → TagManagementPage が再レンダリング → TagListTable に新タグの行が現れる

エラー経路(名前重複)の場合は手順 6 で ErrTagNameDuplicate が返り、手順 8 が「409 + {"error":{"code":"tag_name_duplicate",...}}」になり、手順 9 の代わりに TagApiError が throw され、§3.3 の catch が form.setError("name", ...) — ダイアログは開いたまま名前欄の下に赤字が出ます。invalidate は走らないので一覧は変わりません。
