タグ管理のテスト解説
— Go の実 DB テストと Vitest + Testing Library

テストコードは「この機能はこう振る舞うべき」という仕様の実行可能な記述です。ウォークスルーで読んだタグ機能について、Go 側(サービステスト・ハンドラ/スコープテスト)とフロント側(フック / コンポーネントテスト)を読み解きます。

2. Go テストの基本ルール

  • ファイル名: *_test.go はビルド対象から外れ、go test のときだけコンパイルされる
  • 関数名: func TestXxx(t *testing.T) という署名の関数が自動発見・実行される。JUnit の @Test、pytest の test_ プレフィクスに相当。テストランナー設定は不要(言語標準)
  • アサーションライブラリがない: assertEquals は存在せず、普通の if 文 + t.Errorf / t.Fatalf で書く(標準流儀)

t.Fatalf と t.Errorf の使い分け

呼び出し挙動使いどころ
t.Fatalf(...)失敗を記録してそのテストを即中断前提が崩れて以降の検証が無意味なとき(作成に失敗した、など)
t.Errorf(...)失敗を記録して続行独立した検証項目。1 回の実行で複数の失敗をまとめて報告できる

func setup(t *testing.T, who string) (*sql.DB, string) {
    t.Helper()

    dbPath := filepath.Join(t.TempDir(), "test.db")   // テスト専用一時ディレクトリ(自動削除)
    if err := provision(dbPath); err != nil {          // テンプレート複製 or マイグレーション実行(後述)
        t.Fatalf("%s: %v", who, err)
    }

    conn, err := db.Open(dbPath)                       // 本番と同じ PRAGMA(WAL 等)で接続
    if err != nil {
        t.Fatalf("%s: open: %v", who, err)
    }
    t.Cleanup(func() {                                 // テスト終了時の後始末を予約
        _ = conn.Close()
    })
    return conn, dbPath
}
  • t.TempDir() — テストごとに固有の一時ディレクトリを作り、終了時に自動削除。DB ファイルごと消える
  • t.Cleanup() — JUnit の @AfterEach、pytest の fixture teardown に相当。ヘルパの中から登録できるのが便利
  • マイグレーション + seed(リュウの技マスタ等)込みなので、テストは「初回起動直後の本物のアプリ」と同じ土俵で走る

3.1 テンプレート方式 — 「速さ」を「正しさの根拠」にしない設計

初版のガイドを書いた時点では Setup がテストごとに migration.Run を呼んでいましたが、マイグレーション本数の増加でコストが積み上がったため、M24-09d(CHANGE-145)でテンプレート方式に変わりました。テストバイナリ(= パッケージ)ごとに 1 回だけマイグレーションを流して「テンプレート DB」を作り(sync.Once)、そのファイルの中身をバイト列でメモリに保持して、各テストは os.WriteFile で複製するだけです(dbtest.go:174-191 の provision)。

「壊れると何も検証しないまま緑になる」形の最適化 テンプレート方式は「壊れると落ちる」ではなく「壊れると何も検証しないまま緑になる」形をとりえます。複製に失敗して空の DB でテストが走っても、「その行は存在しない」を確かめるテストは緑のままで、しかも速い。だから速度を正しさの根拠にできません。このリポジトリは対策として internal/testutil/dbtest/template_test.go を置き、(1) テンプレート由来の DB と「テンプレートを通さず」マイグレーションを流した DB を、スキーマ全数(列・インデックス・外部キー)+ 全テーブルの行数で突き合わせ、(2) seed が 1 行も無い「両方空だから一致」も明示的に排除しています(比較相手を同じ経路で作ると、壊れたとき両方が同じように壊れて検出できない、という理由までコメントに書かれています)。
internal/testutil/dbtest/template_test.go:237-248
func TestTemplate_BuiltOnlyOnce(t *testing.T) {
    // 本パッケージは DisableTemplate() を呼んでいないため、テンプレート方式で動く。
    _ = dbtest.Setup(t)
    _ = dbtest.Setup(t)
    _ = dbtest.Setup(t)

    if got := dbtest.MigrationRunCount(); got != 1 {   // 速度ではなく「回数」を主張する
        t.Errorf("dbtest.MigrationRunCount() = %d, want 1"+
            "\n  1 でないなら、テンプレートがテストごとに作り直されている"+
            "\n  (テストの実行順によらず、テンプレート方式なら常に 1 である)", got)
    }
}

学びどころは 2 つ。①観測可能性をヘルパ側に仕込む — MigrationRunCount() というカウンタを公開しているのは、「速くなったから効いている」で済ませないためです(除外し忘れても、複製に失敗しても、速くはなる)。②例外はコードで施錠する — マイグレーションの適用過程そのものを検証するパッケージだけはテンプレートを使えないので DisableTemplate() がありますが、runtime.Caller で呼び出し元パッケージを特定し、許可一覧(現在は internal/infra/migration の 1 つ)以外から呼ぶと panic します。「テストが全部緑のまま遅くなるだけ」という誰も気づけない劣化を、機構で防いでいます。

モック派 vs 実 DB 派 Spring で Mockito + H2 を使い分けた感覚で言うと、このリポジトリは「サービステスト = 実 DB(SQLite が軽量だから可能)」「ハンドラテスト = サービスをモック」という切り方です。実 DB 方式の利点は SQL の間違い(JOIN 条件・CASCADE)まで検出できること。SQLite はファイル 1 個 + 純 Go ドライバなので、Testcontainers のような重い仕掛けなしでこれができます。テスト間はプロセス内並列でも DB が別ファイルなので完全独立です。

4.2 関連テーブルを手で仕込むテスト

「使用中タグは削除できない(VAL-T03)」のテストは、combo_tags に関連を作る必要があります。タグサービスにはコンボを作る API がないので、テストが直接 SQL で前提データを仕込みます。初版では inline の INSERT 文でしたが、現在は汎用の INSERT ヘルパ dbtest.Insert に寄せられています:

internal/service/tag/service_test.go:210-232(TestDeleteTag_InUse_ForcefalseReturnsError)

dbtest.Insert は「既定値を 1 つも埋めない」 dbtest.Insert(internal/testutil/dbtest/insert.go)は列名→値の map から INSERT 文を組み立てるだけの小さなヘルパですが、コメントに設計判断が明記されています — ヘルパ側で気を利かせて既定値を埋めると、「その既定値に依存した主張がたまたま通る」テストが生まれるため、指定した列だけを INSERT し、省いた列はスキーマの DEFAULT に委ねる。テストヘルパは便利にしすぎない方が安全、という好例です。ついでに列名を昇順ソートしてから組み立てるので、同じ入力からは常に同じ SQL が出ます(失敗メッセージの再現性)。

続く TestDeleteTag_InUse_ForceTrueDeletes(:234-253)は force=true で削除した後、SELECT COUNT(*) FROM combo_tags で ON DELETE CASCADE が効いて関連も消えたことまで確認します。これはモックでは原理的にテストできない(CASCADE は DB の挙動)ので、実 DB 方式の価値が一番出る箇所です。

スキーマはただの値変換関数なので、描画もモックも不要でそのまま呼べます。ロジックを純粋関数(スキーマ)に切り出しておくとテストが一番安くなる、という設計の見返りがここに出ています。Go 側 TestCreateTag_VAL_T02_EmptyName と同じ仕様(空白のみ禁止)を両側でテストしていることにも注目 — 二重検証(UX 用と防衛線)にはテストも両側必要です。

5.2 フックのテスト: renderHook + act

フックはコンポーネントの中でしか呼べないルールがあるので、Testing Library の renderHook が「フックだけを載せた見えないコンポーネント」を作ってくれます。

web/src/features/tag/hooks/useTagFormDialog.test.ts:80-97
it("送信時に color が空文字列なら undefined に正規化される", async () => {
  const onSubmit = vi.fn().mockResolvedValue(undefined);   // vi.fn = モック関数(Mockito の mock)
  const onClose = vi.fn();

  const { result } = renderHook(() =>
    useTagFormDialog(true, null, onSubmit, onClose),
  );

  await act(async () => {                                  // act = React の状態更新を確定させる枠
    result.current.form.setValue("name", "新タグ");
    result.current.form.setValue("color", "");
    await result.current.handleSubmit();
  });

  expect(onSubmit).toHaveBeenCalledWith(                   // モックの呼び出し内容を検証
    expect.objectContaining({ color: undefined }),          // ウォークスルー §3.3 の正規化の検証
  );
});

読み方のポイント:

  • vi.fn() — 呼び出しを記録するダミー関数。mockResolvedValue / mockRejectedValue で成功/失敗をシナリオ化できる。API を実際に呼ぶ代わりに「onSubmit が 409 で失敗したら」を mockRejectedValue(new TagApiError(409, ...)) で再現するテスト(:136-166)が好例
  • act(...) — 「この中で起きた state 更新を全部反映してから次へ進む」という React テストの約束事
  • result.current — フックの現在の戻り値。再レンダリングされると差し替わる

Testing Library の思想: 実装ではなくユーザーの見え方で選択する 要素の特定に CSS セレクタや内部 state ではなく getByRole("button", {name:"作成"})(役割とラベル)や getByLabelText(/タグ名/)(フォームラベル)を使います。「ユーザー/スクリーンリーダーに見えているもの」でテストを書くと、内部リファクタリングでテストが壊れず、ついでにアクセシビリティの検証にもなる、という設計です。どうしても意味的に特定できないもの(色スウォッチ)だけ data-testid を使います(リポジトリには testid 命名規約 docs/design/testid-convention.md まであります)。

ファイル冒頭(TagFormDialog.test.tsx:8-17)の ResizeObserverStub は、jsdom に無いブラウザ API を UI ライブラリ(Radix)が要求するために置いた最小スタブです。「jsdom は本物のブラウザではない」ことの典型的なパッチとして覚えておくと、他所で同種のコードを見ても驚きません。

5.4 キーボード操作のテスト: user.keyboard と activeElement

M27-02a で「タグ欄だけマウスが必須」という到達性の穴が直され、そのとき TagSelector.test.tsx に describe("キーボード操作") ブロック(:189-300)が加わりました。§5.3 の「ユーザーの見え方でテストする」思想を、キーボード利用者の視点まで押し広げた実例です:

web/src/features/tag/components/TagSelector.test.tsx:198-204, 218-227(抜粋)

it("★Enter で選べる。★複数選択なので候補は開いたままにする(M27-02a §2.2.4-3 の決定)", async () => {

  • user.keyboard("{ArrowDown}{Enter}") — click / type と同じ userEvent 系列でキー操作をシナリオ化する。fireEvent.keyDown より実際のブラウザ挙動(keydown → keyup の連鎖)に近い
  • document.activeElement — 「いまフォーカスがどこにあるか」を直接主張する。同ブロックの白眉は「新規作成した直後もキーボードで続けられる」テスト(:259-279)で、フォーカスの載っていた要素が unmount されるとフォーカスが body へ落ち、以後 ↓ も Enter も効かなくなるという、目視でもモックでも捕まえにくい退行を固定しています
  • getAllByRole("option") / getByRole("listbox") — role でクエリすること自体が「支援技術に候補が公開されている」ことの検証を兼ねる(着手前は role が 1 つも無かった、とコメントに実測が残っています)
  • ファイル冒頭(:10-14)の vi.mock("@/features/tag/hooks/useTagsForSelector", ...) は モジュール単位のモック(vi.fn は関数 1 個、vi.mock は import 先を丸ごと差し替え)。TanStack Query でデータを取るフックを固定データに差し替えて、コンポーネントの操作だけをテストしています
