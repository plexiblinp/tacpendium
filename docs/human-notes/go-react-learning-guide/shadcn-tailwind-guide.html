shadcn/ui + Tailwind スタイリングガイド
— 「スタイルが苦手」から、仕組みで読める人へ

このアプリの画面は Tailwind CSS(スタイルの書き方)と shadcn/ui(部品の作り方)でできています。このページは CSS が苦手な読者を想定し、最低限の CSS の地図 → Tailwind の読み方 → shadcn の仕組み → 実際に色や形を変える方法の順で積み上げます。読み終わると、className="flex items-center gap-2 rounded-md bg-primary" のような呪文が「読める」ようになり、どこを触れば何が変わるかが分かるようになります。

1. CSS 最小限の地図 — 2 つの概念で 9 割読める

CSS の仕様は膨大ですが、このアプリのレイアウトを読むのに必要なのは実質 2 つ、ボックスモデルと flexbox だけです。

1.1 ボックスモデル — すべての要素は「箱」

画面上のあらゆる要素(ボタンも、div も、文字も)は 4 層の箱です:

margin(外側の余白)
border(枠線)
padding(内側の余白)
content(中身)

覚え方: padding は「箱の中のクッション」、margin は「箱と箱の距離」。ボタンを大きくしたければ padding、ボタン同士を離したければ margin(または後述の gap)です。Tailwind ではこれが p-4(padding)、m-4(margin)、border(枠線)になります。

1.2 flexbox — 「横に並べて、間隔と寄せを指定する」

親要素に display: flex を指定すると、子要素が横一列に並び、親が並べ方を制御できるようになります。下の図は実際に flex で描いています:

この 2 つを知っていれば、このアプリで一番よく出るパターンが読めます。タグ管理画面の見出し行(web/src/features/tag/components/TagManagementPage.tsx:82)がまさにそれです:

<div className="flex items-center justify-between mb-4">
  <h1 className="text-lg font-bold text-slate-800">{t("tag.management.title")}</h1>
  <button ...>{t("tag.management.create")}</button>   // 文言は i18n 経由(見た目のクラスとは独立)

// flex           = 横並びにする
// items-center   = 縦方向は中央揃え(h1 とボタンの高さが違っても中心が揃う)
// justify-between = 両端に振り分け(左端に h1、右端にボタン)
// mb-4           = margin-bottom: 1rem(下の要素との距離)

2. Tailwind CSS — 「CSS を書かない」ためのユーティリティファースト

従来の CSS は「クラス名を発明 → 別ファイルにスタイルを書く」でした。Tailwind は逆で、あらかじめ用意された 1 クラス = 1 宣言の部品(ユーティリティ)をタグに直接並べます。text-sm は font-size: 0.875rem、p-4 は padding: 1rem、それだけです。

Bootstrap 世代との違い(Flask/Spring でよく使った人向け) Bootstrap の btn btn-primary は「完成品のボタン」を呼ぶクラスで、見た目の詳細はライブラリの中に隠れています。Tailwind の bg-blue-600 px-4 py-2 rounded は「原材料」で、完成品は自分で組みます。そして次章の shadcn/ui が「Tailwind という原材料で組んだ完成品を、ソースコードごと手元に置く」という第三の道です。カスタマイズで !important 地獄になりがちだった Bootstrap の弱点を、「そもそも完成品を配らない」ことで解決しています。
「インライン style と何が違うの?」 よくある疑問です。style="padding:16px" と className="p-4" の決定的な差は 3 つ: (1) hover: や sm: のような状態・条件付きスタイルはインラインでは書けない、(2) 値が 4px 刻み・色パレット等のデザインシステムに制約されるので画面ごとのバラつきが出にくい、(3) ビルド時に使用クラスだけの CSS が生成される(tailwind.config.js:6 の content が走査対象の指定)。

3. shadcn/ui とは — 「ライブラリ」ではなく「コードの配布」

ここが一番誤解しやすいポイントです。shadcn/ui は npm ライブラリではありません。package.json に「shadcn」という依存は存在せず、CLI で選んだコンポーネントのソースコードが自分のリポジトリにコピーされる仕組みです。このアプリでは web/src/components/ui/ に 21 ファイル(button / dialog / form / input / table / alert-dialog / checkbox / select / tabs / tooltip …)が「自分のコード」として置かれています。「自分のコード」なので、後述(§7)のとおりプロジェクト固有の拡張を直接書き足すこともできます。

web/components.json(shadcn CLI の設定。全 17 行)
{
  "style": "default",
  "tailwind": {
    "config": "tailwind.config.js",
    "css": "src/index.css",
    "baseColor": "slate",          // 生成時の基準ニュートラル色
    "cssVariables": true           // 色を CSS 変数(§4)で管理する方式
  },
  "aliases": { "components": "@/components", "utils": "@/lib/utils" }
}

そして各コンポーネントは 3 つの技術の合成です:

層担当実体
Radix UI挙動とアクセシビリティ(開閉状態、フォーカス管理、Esc で閉じる、aria 属性、キーボード操作)。見た目は一切持たない「headless」コンポーネント@radix-ui/react-* 13 パッケージ(package.json:17-29)
Tailwind見た目(§2 のユーティリティで着色)各ファイル内の className
cvaバリアント管理(「同じボタンの色違い・サイズ違い」を型安全に)class-variance-authority(§6)
既に出会っていた Radix Playwright ガイド §4.1 で「Radix Checkbox は <button role="checkbox"> でレンダリングされ、アクセシブル名が付かないから testid が要る」という話をしました。あれがまさにこの層です。タグのテスト §5.3 の ResizeObserver スタブ(jsdom に無いブラウザ API を Radix が要求する)も同根です。挙動の複雑さは Radix に外注し、見た目だけ自分で持つ — これが shadcn 方式の本質です。

4. デザイントークン — 色が 1 か所で決まる仕組み

shadcn のコンポーネントには bg-blue-600 のような直接色がほぼ出てきません。代わりに bg-primary、text-muted-foreground のような意味の名前(セマンティックトークン)が使われます。この正体は 2 ファイルの連携です:

web/src/index.css:6-27(値の定義)→ web/tailwind.config.js:15-18(クラスへの接続)
/* ① index.css — :root に「HSL の生数値」で色を定義 */
:root {
  --background: 0 0% 100%;          /* 白 */
  --primary: 222.2 47.4% 11.2%;     /* 濃紺(このアプリの主色) */
  --primary-foreground: 210 40% 98%; /* primary の上に載せる文字色 */
  --destructive: 0 84.2% 60.2%;     /* 破壊操作の赤 */
  --radius: 0.5rem;                 /* 角丸の基準値 */
  ...
}

// ② tailwind.config.js — CSS 変数を hsl() で包んでクラス名に割当
colors: {
  primary: {
    DEFAULT: "hsl(var(--primary))",             // → bg-primary / text-primary が使える
    foreground: "hsl(var(--primary-foreground))", // → text-primary-foreground
  },
  ...
},
borderRadius: {
  lg: "var(--radius)",
  md: "calc(var(--radius) - 2px)",   // rounded-md は「基準 − 2px」で自動連動
  sm: "calc(var(--radius) - 4px)",
},

ポイントが 2 つあります:

  • なぜ HSL の数値だけで持つのか(--primary: 222.2 47.4% 11.2% であって hsl(222.2, 47.4%, 11.2%) ではない): 組み立てを config 側に残すことで、bg-primary/90(不透明度 90%)のような透明度修飾が hsl(var(--primary) / 0.9) として合成できるからです。button.tsx:12 の hover:bg-primary/90(ホバーで少し薄く)はこの仕組みの上に成り立っています
  • xxx と xxx-foreground は必ずペア: 「背景が primary のとき、その上の文字は primary-foreground」という約束。ペアで使う限りコントラスト(可読性)が壊れません。実物はこうです → bg-primary + text-primary-foreground
トークン意味(いつ使う色か)ライトテーマでの実際の色
background / foregroundページの地と文字白 / ほぼ黒
primary主要アクション(既定のボタン)濃紺
secondary控えめなアクション(キャンセル等)薄グレー

muted / muted-foreground脇役の背景 / 補足テキスト薄グレー / グレー文字

ダークモードは「基盤あり・未活性」 index.css:29-49 には .dark { --background: 222.2 84% 4.9%; ... } というダークテーマの変数一式が、tailwind.config.js:5 には darkMode: ["class"] があります。つまり html 要素に .dark クラスを付けるだけで全トークンが暗色に切り替わる仕組みは最初から入っています。しかし現状、(1) .dark を付与する切替 UI・ThemeProvider が存在しない、(2) dark: ユーティリティの使用は 0 件、(3) sonner.tsx:15 は theme="light" をハードコード — のため実質ライト固定です。将来ダークモード対応する場合、この教材の §4 がそのまま設計図になります(ただし各画面の生 Tailwind の直接色 bg-slate-50 等はトークンでないため個別対応が必要になる点が本当の工数です)。

5. cn() — たった 6 行の重要関数

web/src/lib/utils.ts(全 6 行)
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}

2 つのライブラリの合成です:

  • clsx: 条件付きのクラス連結。clsx("base", isError && "text-red-600", className) のように、falsy を捨てて空白区切りに結合する
  • tailwind-merge: 競合するユーティリティを後勝ちで解決する。ただの文字列連結だと "px-4 px-2" は CSS の定義順(ビルド成果物内の順序)で勝敗が決まり、意図どおりに上書きできません。twMerge は「px-4 と px-2 は同じ padding-x の指定」と理解して古い方を消し、"px-2" だけを残します

これが効いている実例が §9 で見る DeleteComboConfirm です: AlertDialogAction は内部で cn(buttonVariants(), className)(alert-dialog.tsx:113)としているので、利用側が渡した className="bg-red-600 hover:bg-red-700" が既定の bg-primary hover:bg-primary/90 を確実に上書きします。cn がなければ「上書きしたはずなのに効かない」という CSS あるあるに悩まされるところです。

6. button.tsx を全部読む — shadcn の縮図(全 56 行)

web/src/components/ui/button.tsx:7-34(cva によるバリアント定義)
const buttonVariants = cva(
  // ① 基底クラス: 全ボタン共通(配置・角丸・フォーカスリング・disabled 時の見た目)
  "inline-flex items-center justify-center gap-2 whitespace-nowrap rounded-md text-sm font-medium
   transition-colors focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-ring
   disabled:pointer-events-none disabled:opacity-50 ...",
  {
    // ② バリアント: 「意味」ごとの見た目の違い
    variants: {
      variant: {
        default:     "bg-primary text-primary-foreground hover:bg-primary/90",
        destructive: "bg-destructive text-destructive-foreground hover:bg-destructive/90",
        outline:     "border border-input bg-background hover:bg-accent hover:text-accent-foreground",
        secondary:   "bg-secondary text-secondary-foreground hover:bg-secondary/80",
        ghost:       "hover:bg-accent hover:text-accent-foreground",
        link:        "text-primary underline-offset-4 hover:underline",
      },
      size: {
        default: "h-10 px-4 py-2",
        sm:      "h-9 rounded-md px-3",
        lg:      "h-11 rounded-md px-8",
        icon:    "h-10 w-10",          // アイコンだけの正方形ボタン
      },
    },
    // ③ 未指定時の既定
    defaultVariants: { variant: "default", size: "default" },
  }
)

cva(class-variance-authority)は「基底 + バリアント名 → クラス列」を生成する小さな関数です。buttonVariants({ variant: "outline", size: "sm" }) と呼ぶと ①+outline+sm のクラスが結合されて返ります。if 文で className を組み立てる代わりに、見た目のパターンを宣言的な表として管理するための道具です。

web/src/components/ui/button.tsx:36-53(コンポーネント本体)
export interface ButtonProps
  extends React.ButtonHTMLAttributes<HTMLButtonElement>,   // onClick 等、素の button の全属性を継承
    VariantProps<typeof buttonVariants> {                    // variant / size の型を cva 定義から自動導出
  asChild?: boolean
}

const Button = React.forwardRef<HTMLButtonElement, ButtonProps>(
  ({ className, variant, size, asChild = false, ...props }, ref) => {
    const Comp = asChild ? Slot : "button"
    return (
      <Comp
        className={cn(buttonVariants({ variant, size, className }))}
        ref={ref}
        {...props}
      />
    )
  }
)

3 つの仕掛けを順に:

  • VariantProps<typeof buttonVariants> — cva の定義から variant?: "default" | "destructive" | ... という型を自動生成。variant="destructiv"(typo)はコンパイルエラーになる。見た目の選択肢が型検査されるのが cva の真価
  • forwardRef — 親が実 DOM(<button> 要素そのもの)への参照を必要とする場合に中継する定型。react-hook-form がフォーカス制御に使うため、shadcn のフォーム系部品はほぼ全てこれでラップされている。「おまじない」として読み飛ばして OK、ただし消すと壊れる
  • asChild + Slot — <Button asChild><Link to="/combos">一覧へ</Link></Button> のように書くと、button 要素を作らず子要素(Link)にボタンのクラスを合流させる。「ボタンの見た目をしたリンク」を <a> のまま作れる(role が正しく保たれる)Radix 流の多態パターン

7. dialog.tsx を読む — Radix ラップの型

ダイアログは「見た目より挙動が難しい」部品の代表です(背面スクロール禁止、Esc で閉じる、フォーカスをダイアログ内に閉じ込める、閉じたら元の位置に戻す…)。dialog.tsx を読むと、難しい部分は全部 Radix がやり、shadcn は着せ替えだけという分業が見えます。

web/src/components/ui/dialog.tsx:8-14, 31-59(要点)
const Dialog = DialogPrimitive.Root          // 挙動そのものは Radix を別名 export するだけ
const DialogTrigger = DialogPrimitive.Trigger
const DialogPortal = DialogPrimitive.Portal

const DialogContent = React.forwardRef<...>(({ className, children, ...props }, ref) => (

      {children}
      <DialogPrimitive.Close className="absolute right-4 top-4 ...">
        <X className="h-4 w-4" />            // lucide-react のアイコン

))
  • data-[state=open]:animate-in — Radix は開閉状態を data-state="open"/"closed" という DOM 属性で表明します。Tailwind の属性セレクタ修飾 data-[state=open]: がそれに反応してアニメーション(tailwindcss-animate プラグイン)を適用。JS でアニメを書かず、状態属性 × CSS で完結させる現代的パターン
  • sr-only — 視覚的には隠すがスクリーンリーダーには読ませるクラス。TagFormDialog:48-50 の DialogDescription className="sr-only" も同じ用途(見た目に説明文は不要だが、支援技術には文脈を渡す)
  • Portal — ダイアログを React ツリー上の位置ではなく body 直下に描画。親の overflow: hidden や z-index に切り取られる事故を構造的に防ぐ
  • 独自拡張が直接書き足されている — §3 の「ソースコードごと手元に置く」の実利がここに現れています。生成後に (1) max-h-[85vh] overflow-y-auto(85vh は Tailwind の任意値記法 [...]。スケール外の値を角括弧で直接指定する)、(2) ModalPresenceMarker(モーダルが開いている間、物理コントローラ入力が背後の画面状態を変えないようにする申告。dialog.tsx:45-52 のコメント参照)が追加されました。npm ライブラリなら fork かラッパが要るところを、自分のコードなので 1 か所直せば DialogContent を通る全モーダルへ自動で効く — alert-dialog.tsx:47 にも同じ Marker が入っています

8. form.tsx — フォーム配線の「裏側」(軽めに)

React/TS プライマー §9 で見た FormField → FormItem → FormLabel → FormControl → FormMessage の入れ子。あの定型が何をしているかというと、id と aria 属性の自動配線です(form.tsx:40-124):

  1. FormItem(:73-85)が React.useId() で一意 id を作り、Context で配下に配る
  2. FormLabel(:87-102)がその id を htmlFor に設定 → getByLabelText(/タグ名/) が効くのはこのおかげ(テスト容易性はここで生まれていた)
  3. FormControl(:104-124)が Slot で子の Input に id / aria-describedby / aria-invalid を注入
  4. FormMessage(:143-165)が react-hook-form の fieldState.error?.message を拾って text-destructive(赤)で表示。エラーが無ければ null を返して何も描画しない
  5. FormLabel はエラー時に自分も赤くなる(:96 error && "text-destructive")

つまり利用側(TagFormDialog)が 1 行も id や aria を書いていないのに、ラベル関連付け・エラー読み上げ・赤字表示が揃うのは、この 176 行が Context + useId で裏配線しているからです。Playwright ガイドの testid-convention にあった「Field が htmlFor 未関連でレンダリングされ getByLabel できない」既知ギャップは、この配線に乗っていない自作 Field があるという話 — 仕組みを知ると、あのギャップの意味も正確に読めます。

9.3 共有表示部品: RecipeText — 「面ごとの違い」は呼び手がクラスで渡す

2026-07-22 以降に育った、このアプリ独自の好例です。コンボのレシピ表示はコンボ一覧・マイコンボ・詳細・比較・比較の追加モーダルの 5 画面が、たった 1 つの部品を通ります(web/src/features/combo/components/RecipeText.tsx)。以前は画面ごとに truncate と title を書いていましたが、「面の数だけ見せ方ができて次の不満を生む」ため 1 部品へ集約されました。

web/src/features/combo/components/RecipeText.tsx:104-115(省略表示の分岐)
if (!fullView) {
  return (
    <span
      className={cn("block truncate", compactClassName, className)}
      title={recipe ?? undefined}       // 省略時だけ全文をホバーへ(全文表示時は二重になるので付けない)
      data-testid="recipe-text"
      data-recipe-view="compact"        // E2E がこの属性で表示モードを判定する
    >
      {recipe}
    </span>
  );
}

設計の要点は compactClassName という prop です。「省略表示のときに適用する面ごとの表示制御クラス」を呼び手が渡します — 一覧・比較は max-w-xs(幅で切る)、比較の追加モーダルは sm:max-w-[380px]、コンボ詳細だけは whitespace-pre-wrap break-words(幅で切らず折り返す)。当初の JSDoc は「幅制御クラス」と書いていましたが、実際には折返し制御も渡っていたため、2026-09 の是正(D-628)で「幅」ではなく「表示制御」へと意味の方を広げました(prop 名は最初から幅に限定されない中立な名前だったので改名なし)。§5 の cn がここでも効いています: 基底の truncate と呼び手の折返しクラスが競合せず合成されるのは twMerge のおかげです。「共通部品 + 面ごとの差分は className で注入」は shadcn 自体(§6-7)と同じ構図で、自作部品にも同じ流儀を適用したと読めます。

9.4 固定幅フィルタ — 任意値記法 w-[7.5rem]

コンボ一覧のヒット種別フィルタは「値の長さで横幅が動く」ことが不評で、2026-09 に固定幅 + 閉じたときは短縮表記へ変わりました(M27-03、ComboListFilters.tsx:346-363):

web/src/features/combo/components/ComboListFilters.tsx:350-362(抜粋)+ components/SearchableSelect.tsx:182-183
<SearchableSelect
  mode="single"
  options={hitTypeOptions}              // 各選択肢が label(フル)と shortLabel(短縮)を持つ(:138-145)
  ...
  // ★固定幅。値の長さで横幅が動かなくなることが本件の要求そのものである。
  triggerClassName="w-[7.5rem] justify-between"
/>

// SearchableSelect 側: 閉じたトリガは短縮表記(あれば)、開いた一覧の中は常にフル
<span className={current.shortLabel ? "truncate" : undefined}>
  {current.shortLabel ?? current.label}
</span>

ここで登場する w-[7.5rem] が Tailwind の任意値記法(arbitrary value)です。§2 の表のクラスは 4px 刻みのスケールから選びますが、角括弧 [...] でスケール外の値をピンポイント指定できます(§7 の max-h-[85vh]、上の sm:max-w-[380px] も同じ)。乱用するとデザインシステムの利点(§2 の note)が消えるので、「この幅であること自体が要求」という場面に限るのが作法です。もう 1 つの学び: なぜ native の <select> でないのか。HTML の仕様上、閉じた表示は選択中 option のテキストそのものなので「閉じたら短縮・開いたらフル」は 1 つの select では表現できません。新部品は作らず、既存の SearchableSelect に shortLabel を 1 個足すだけで済ませています。
