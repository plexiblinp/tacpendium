Go 言語プライマー
— Tacpendium のコードで学ぶ言語仕様

このページは Go の文法書ではありません。このリポジトリを読むのに必要な言語仕様だけを、すべて実コードを例にして説明します。順番は「タグ管理ウォークスルーを読むときに登場する順」に近づけてあります。

1. パッケージと可視性 — 大文字/小文字がアクセス修飾子

Go のソースファイルは必ず package 名前 で始まります。同じディレクトリのファイルは同じパッケージに属し、互いに自由にアクセスできます。Java の public/private に相当する仕組みは、識別子の頭文字の大小です。

internal/service/tag/service.go:2-11(抜粋)
package tag                       // このディレクトリは「tag」パッケージ

import (
    "context"                     // 標準ライブラリ
    "errors"
    "strings"

    "github.com/plexiblinp/tacpendium/internal/model"
    tagrepo "github.com/plexiblinp/tacpendium/internal/repository/tag"  // ← 別名 import
)
  • Service、New、CreateTag … 大文字始まり = 公開(パッケージ外から使える。Java の public)
  • service、validateName … 小文字始まり = 非公開(パッケージ内限定。Java の package-private に近い)
  • 公開識別子には godoc コメント(// Service は〜)を付けるのが規約(CLAUDE.md §4)

注目してほしいのが別名 import です。このリポジトリには「tag」という名前のパッケージが 3 つあります(model ではなく api / service / repository の 3 階層)。サービス層がリポジトリ層を使うとき、両方とも tag だと衝突するので tagrepo という別名を付けています。main.go の import 一覧(cmd/tacpendium/main.go:29-83)が大量の別名だらけなのも同じ理由です。

Flask / Spring 経験者向け internal/ というディレクトリ名は Go の言語仕様で特別扱いされます: internal/ 配下のパッケージはこのモジュール(リポジトリ)の外から import できません。ライブラリとして公開するつもりのないアプリ内部コードを守る仕組みで、Java でいう module-info の exports を「書かない」ことに相当します。

2. struct と struct タグ — DTO・Entity・ORM マッピングを 1 か所で

Go にはクラスがなく、データの器は struct(構造体)です。フィールド定義の右にあるバッククォート文字列が struct タグで、シリアライズ時のメタデータになります。Jackson の @JsonProperty と JPA の @Column を 1 行に同居させたものと考えてください。

internal/model/tag.go:50-57
type Tag struct {
    ID         int64   `db:"id"          json:"id"`
    UserID     int64   `db:"user_id"     json:"userId"`     // DB は snake_case、JSON は camelCase
    Name       string  `db:"name"        json:"name"`
    Category   *string `db:"category"    json:"category,omitempty"`
    Color      *string `db:"color"       json:"color,omitempty"`
    UsageCount *int    `db:"-"           json:"usageCount,omitempty"` // db:"-" = DB マッピング対象外
}

読み取りポイント:

  • 型がフィールド名の後ろに来る(ID int64)。Go は「名前 型」の語順
  • json:"userId" — encoding/json がシリアライズ時に使うキー名。このリポジトリは「JSON は camelCase、DB カラムは snake_case」を規約化している(CLAUDE.md §4)
  • omitempty — 値がゼロ値(nil、0、"" など)ならそのキーを JSON から省略する
  • json:"-" — JSON に一切出さない。model.Combo の RecipeCache(combo.go:238)や DeletedAt(combo.go:242)が「内部専用でクライアントに見せないカラム」としてこれを使っている

タグ文字列自体はただのメタデータで、それを読むのは encoding/json や自作のスキャン処理です。マジックはないので、「このキーはどこから来た?」と思ったら struct タグを見れば必ず答えがあります。

3. ポインタと nil — 「値がない」の表現

上の Category *string の * はポインタです。Go でポインタを使う動機は C のようなメモリ操作ではなく、多くの場合「nil = 値がない」を表現するためです。

型とりうる値意味
string"" を含む任意の文字列「値がない」を表せない(ゼロ値 "" と区別できない)
*stringnil または文字列への参照nil = 未設定(DB の NULL)、非 nil = 値あり

タグの Category/Color は DB で NULL 許容カラムなので *string になっています。database/sql の Scan は *string のフィールドに NULL を読み込むと nil を入れてくれます(repository.go:66 の rows.Scan(&t.ID, ..., &t.Category, &t.Color))。

もうひとつの用途が部分更新(PATCH)の「送られてこなかった」表現です:

internal/model/tag.go:66-71
// UpdateTagInput はタグ部分更新 API の入力(M3-01 §4.2.2)。
type UpdateTagInput struct {
    Name     *string `json:"name,omitempty"`     // nil = このフィールドは変更しない
    Category *string `json:"category,omitempty"`
    Color    *string `json:"color,omitempty"`
}

リポジトリの Update(repository.go:157-192)は「nil でないフィールドだけ SET 句に足す」実装で、これが PATCH の部分更新を実現しています。

注意: このやり方の限界と、その先 *string 方式は「キー不在」と「JSON の null」を区別できません(どちらも nil になる)。タグでは問題になりませんが、コンボの PATCH では「null を送って NULL クリアしたい」要求があり、3 状態(キー不在 / null / 値あり)を区別するジェネリック型 Optional[T] が導入されています(internal/repository/combo/optional.go)。詳細はコンボウォークスルー §6で。
Flask / Spring 経験者向け Java の Integer と int の関係に似ています(参照型なら null を持てる)。Python は全部参照なので意識しませんが、Go は「値型がデフォルト、nil が必要なときだけポインタ」と明示的に選びます。&x でポインタを取り、*p で中身を取り出します(service_test.go の ptrStr ヘルパ、combo の ptr[T any] ヘルパはリテラルからポインタを作るための道具)。

4. エラー処理 — 例外はない。エラーは戻り値

Go 最大の発想転換ポイントです。Go に例外(try/catch)はありません。失敗しうる関数は最後の戻り値として error を返し、呼び出し側は毎回それを検査します。

4.1 基本形: if err != nil

internal/repository/tag/repository.go:57-71(一覧クエリ・listSimple)
rows, err := r.db.QueryContext(ctx, q, userID, category, category)
if err != nil {
    return nil, fmt.Errorf("tag list: %w", err)   // %w = 原因エラーを包んで伝播
}
defer rows.Close()

var tags []model.Tag
for rows.Next() {
    var t model.Tag
    if err := rows.Scan(&t.ID, &t.UserID, &t.Name, &t.Category, &t.Color); err != nil {
        return nil, fmt.Errorf("tag list scan: %w", err)
    }
    tags = append(tags, t)
}
return tags, rows.Err()

fmt.Errorf("tag list: %w", err) の %w は「wrap」。元のエラーに文脈("tag list で起きた")を積み増して返します。呼び出し階層を遡るたびに文脈が足され、最終的にログに出るメッセージは "create combo: insert steps: ..." のようにスタックトレースの代わりになる因果の鎖になります。CLAUDE.md §4 の「エラーは必ず wrap する」はこのためです。

4.2 センチネルエラーと errors.Is — 「どの失敗か」を種別で判定

特定の失敗を呼び出し側が判別したいとき、パッケージ変数としてエラー値を定義します。これをセンチネルエラーと呼びます。

internal/service/tag/errors.go:5-16(抜粋・godoc コメント省略)
var ErrNotFound        = errors.New("tag: not found")
var ErrTagNameDuplicate = errors.New("tag: name duplicate") // VAL-T01
var ErrTagNameEmpty     = errors.New("tag: name empty")     // VAL-T02
var ErrTagInUse         = errors.New("tag: in use")         // VAL-T03

ハンドラ層はこれを errors.Is で判別して HTTP ステータスコードに翻訳します。== ではなく errors.Is を使うのは、%w で包まれていても鎖を遡って照合してくれるからです。

internal/api/tag/handler.go:90-101(Create のエラー分岐)
tag, err := h.service.CreateTag(c.Request().Context(), mw.UserIDFrom(c), input)  // ← §6.1 参照(M22 で利用者が固定 ID でなくなった)
if err != nil {
    switch {
    case errors.Is(err, tagsvc.ErrTagNameEmpty):
        return c.JSON(http.StatusBadRequest, model.NewAPIError("tag_name_empty", "タグ名は必須です"))
    case errors.Is(err, tagsvc.ErrTagNameDuplicate):
        return c.JSON(http.StatusConflict, model.NewAPIError("tag_name_duplicate", "同名のタグが既に存在します"))
    default:
        slog.ErrorContext(...)
        return c.JSON(http.StatusInternalServerError, ...)
    }
}
Spring の @ExceptionHandler との対応 Spring では TagNameDuplicateException を throw して @ExceptionHandler が 409 に変換します。Go では「例外クラス」の代わりに「エラー値」、「例外ハンドラ」の代わりに「ハンドラ関数内の switch」です。制御フローが 1 か所に見えるのが利点、各ハンドラに分岐を書く手間が代償です。

4.3 カスタムエラー型と errors.As — エラーにデータを持たせる

「使用中タグの削除エラー」は件数という付加情報が必要なので、struct として定義されています。

internal/service/tag/errors.go:19-26
type TagInUseError struct {
    UsageCount int                      // エラーに載せたいデータ
}

func (e *TagInUseError) Error() string { return ErrTagInUse.Error() }  // これで error 扱いになる
func (e *TagInUseError) Is(target error) bool {                       // errors.Is(err, ErrTagInUse) を成立させる
    return target == ErrTagInUse
}

Error() string メソッドを持つ型は何でも error として使えます(次節のインターフェースの話)。ハンドラ側は種別判定に errors.Is、データ取り出しに errors.As(型としての取り出し)を使い分けています:

internal/api/tag/handler.go:157-166(Delete の 409 応答)
case errors.Is(err, tagsvc.ErrTagInUse):        // ① 種別: 使用中エラーか?
    var inUse *tagsvc.TagInUseError
    errors.As(err, &inUse)                      // ② 具体型を取り出す
    return c.JSON(http.StatusConflict, model.NewAPIErrorWithDetails("tag_in_use",
        "このタグは使用中です。確認の上削除してください",
        map[string]any{
            "usage_count":        inUse.UsageCount,  // ③ データを応答に載せる
            "force_delete_query": "?force=true",
        },
    ))

5. インターフェースと DI — 「実装している」宣言が要らない

Go のインターフェースは暗黙実装です。implements キーワードは存在せず、「必要なメソッドを全部持っていれば、その型はそのインターフェースを満たす」と自動的に見なされます(構造的型付け)。

internal/repository/tag/repository.go:17-35
// Repository はタグ CRUD の SQL 操作インターフェース。
type Repository interface {
    List(ctx context.Context, userID int64, category string, includeUsage bool, characterID *int64) ([]model.Tag, error)
    Get(ctx context.Context, userID, tagID int64) (*model.Tag, error)
    Create(ctx context.Context, userID int64, input model.CreateTagInput) (*model.Tag, error)
    CreateTx(ctx context.Context, tx *sql.Tx, userID int64, input model.CreateTagInput) error  // M22-02: 利用者作成 Tx に相乗りする版
    Update(ctx context.Context, userID, tagID int64, input model.UpdateTagInput) (*model.Tag, error)
    Delete(ctx context.Context, userID, tagID int64) error
    CountUsage(ctx context.Context, tagID int64) (int, error)
}

type repository struct {              // 非公開の実装 struct("implements Repository" とは書かない)
    db *sql.DB
}

func New(db *sql.DB) Repository {     // コンストラクタはインターフェース型で返す
    return &repository{db: db}
}

サービス層は具体実装ではなくインターフェースに依存します:

internal/service/tag/service.go:34-41
type service struct {
    repo tagrepo.Repository            // インターフェース型のフィールド = 差し替え可能な依存
}

func New(repo tagrepo.Repository) Service {
    return &service{repo: repo}
}

そして組み立ては main.go が行います: tagRepo := tagrepo.New(sqlDB) → tagService := tagsvc.New(tagRepo)(cmd/tacpendium/main.go:345-346)。これが Go 流の DI(依存性注入)で、フレームワークもアノテーションもなく、コンストラクタ関数の入れ子呼び出しだけで完結します。

なぜインターフェースを切るのか 最大の理由はテストでの差し替えです。コンボのハンドラテスト(internal/api/combo/handler_test.go:79-99)は combosvc.Service インターフェースを満たす mockService を自作してハンドラに注入しています。暗黙実装のおかげで、本物のサービスに一切手を入れずにモックを作れます。func (m *mockService) Create(...) のレシーバ (m *mockService) が「この関数は mockService のメソッド」という宣言で、Java のクラス内メソッド定義に相当します。

5.1 メソッドとレシーバ

Go では「クラスの中にメソッドを書く」代わりに、関数名の前にレシーバを書きます。

internal/service/tag/service.go:65-79(CreateTag)
func (s *service) CreateTag(ctx context.Context, userID int64, input model.CreateTagInput) (*model.Tag, error) {
    if err := validateName(input.Name); err != nil {   // VAL-T02: 空名検証
        return nil, err
    }
    existing, err := s.repo.List(ctx, userID, "", false, nil)
    if err != nil {
        return nil, err
    }
    for _, t := range existing {                       // VAL-T01: 同名重複検証
        if t.Name == input.Name {
            return nil, ErrTagNameDuplicate
        }
    }
    return s.repo.Create(ctx, userID, input)           // 通ったら INSERT へ
}

(s *service) は「service 型のポインタに対するメソッド、内部では s と呼ぶ」という意味で、Python の self、Java の this に相当します(ただし名前は自由)。for _, t := range existing はコレクション走査の構文で、range は (インデックス, 要素) の 2 値を返し、使わない方は _(ブランク識別子)で捨てます。

6. context.Context — リクエストの「生存信号」を運ぶ

ほぼすべてのサービス・リポジトリメソッドの第一引数が ctx context.Context です。これは Go のサーバー開発の全域的な規約で、主な役割はキャンセル伝播です。クライアントが接続を切ったら、その先の DB クエリも中断できるように、「このリクエストはまだ生きているか」という信号を関数から関数へ手渡しします。

  • 入口: ハンドラが c.Request().Context() で HTTP リクエストの context を取り出す(handler.go:49 など)
  • 中継: サービス→リポジトリへそのまま渡す
  • 出口: db.QueryContext(ctx, ...) / ExecContext(ctx, ...) が ctx を見て中断に応じる
  • 付随機能: slog.ErrorContext(ctx, ...) のようにログへリクエスト ID 等の文脈を紐付けるのにも使われる
Flask / Spring 経験者向け Flask の request コンテキストや Spring の ThreadLocal ベースの RequestContextHolder は「見えない場所」に文脈を隠しますが、Go は明示的に引数で運ぶ選択をしました。冗長ですが、「この関数はリクエスト文脈に依存する」ことがシグネチャから常に読み取れます。テストでは context.Background()(空の context)を渡します(service_test.go 全域)。

6.1 リクエストスコープの値と型アサーション — mw.UserIDFrom(c)

M22 の多人数化で、ハンドラは固定の defaultUserID 定数をやめ、ミドルウェアが X-User-Id ヘッダから解決した利用者 ID を mw.UserIDFrom(c) で受け取るようになりました(§4.2 のコード参照)。ここに Go の型アサーションという言語機能が登場します:

internal/api/middleware/user.go:60-65
func UserIDFrom(c echo.Context) int64 {
    if v, ok := c.Get(userIDContextKey).(int64); ok {  // .(int64) = 型アサーション
        return v
    }
    return 0
}

c.Get(...) の戻り値は any(何でも入る型)なので、そのままでは int64 として使えません。x.(int64) が「中身は int64 のはずだ」という宣言(型アサーション)で、v, ok := の 2 値形式なら型が違っても panic せず ok=false になります(マップの 2 値取得 §8.3 と同じ作法)。値を c.Set で載せるのはミドルウェア UserContext(user.go:35-42)の仕事で、Spring の HandlerInterceptor + RequestContextHolder に相当する分業です。

7. defer — 後始末の予約

defer 文 は「この関数を抜けるとき(return 直前)に実行しろ」という予約です。§4.1 の defer rows.Close() は「どの return 経路を通っても必ず rows を閉じる」を 1 行で保証します。try-finally の代替です。

もっと実戦的な例がコンボ作成のトランザクション処理です:

internal/service/combo/service.go:351-359, 432-434(Create の Tx 管理)
tx, err := s.db.BeginTx(ctx, nil)
if err != nil {
    return nil, validation.ValidationResult{}, busyOr(err, "begin tx")
}
defer func() {
    if err != nil {          // 関数を抜ける瞬間に err が残っていたら…
        _ = tx.Rollback()    // …ロールバック
    }
}()
// … バリデーション(VAL-C02)/ InsertCombo / InsertSteps / ReplaceTagAssociations などを実行 …

if err = tx.Commit(); err != nil {
    return nil, result, fmt.Errorf("commit: %w", err)
}

途中のどの INSERT が失敗して return しても、defer が拾ってロールバックします。Spring の @Transactional(例外なら自動ロールバック)を手続きで書いた形です。defer func(){...}() は無名関数を即座に defer 登録するイディオムで、err という変数を閉じ込めて(クロージャ)、実行時点の最終値を見ます。

2026-07 以降の変更: バリデーションが Tx の内側へ(M24-11) 旧実装は「重複チェック → BeginTx → INSERT」の順で、チェックと INSERT の間に隙があり、同時に来た 2 要求が両方「重複なし」を見て両方 INSERT できました(TOCTOU 競合)。現在は DSN の _txlock=immediate により BeginTx が開始時点で write lock を取り、バリデーションも同じ Tx の内側で実行します(service.go:345-368 のコメントが経緯ごと説明しています)。もうひとつ、busyOr(err, "begin tx") は §4.2 の応用で、SQLite の BUSY エラー(dbinfra.IsBusy)だけをセンチネル ErrDatabaseBusy に包み直し、ハンドラが 503(Service Unavailable)に翻訳できるようにするヘルパです(service.go:46-51)。

8. スライス・マップ・ゼロ値

8.1 スライス = 可変長配列

internal/repository/tag/repository.go:158-179(動的 SQL 組み立て・抜粋)
setClauses := make([]string, 0, 3)    // 長さ 0、容量 3 の string スライス
args := make([]any, 0, 5)             // any = 何でも入る型(Java の Object)

if input.Name != nil {
    setClauses = append(setClauses, "name = ?")   // 末尾追加。append は新スライスを返す
    args = append(args, *input.Name)              // *input.Name = ポインタの中身
}
// … Category / Color も同様 …
q := fmt.Sprintf("UPDATE tags SET %s WHERE id = ? AND user_id = ?",
    strings.Join(setClauses, ", "))

PATCH で送られたフィールドだけ SET 句に足していく典型パターンです。値は必ずプレースホルダ ? で渡し、SQL 文字列には列名しか埋め込まない(SQL インジェクション対策)点も見どころです。

8.2 ゼロ値 — 未初期化でも「使える」

Go の変数は宣言しただけで型ごとのゼロ値(数値 0、string ""、ポインタ/スライス/マップ nil、bool false)に初期化されます。var tags []model.Tag(repository.go:63)は nil スライスですが、nil スライスに append しても安全に動くのが Go の特徴です。

実務ではまる罠: nil スライスの JSON は null nil スライスを JSON にすると null、空スライスは [] になります。フロントで tags.map(...) すると null は落ちるので、サービス層がわざわざ変換しています:
internal/service/tag/service.go:49-51
if tags == nil {
    tags = []model.Tag{}   // 0 件でも JSON で [] になるよう保証
}
コンボ側の toComboResponse(dto.go:576-585)にも同じ配慮(Tags と AffectedMoves は常に非 nil)があります。「API の配列フィールドは null にしない」はこのリポジトリの一貫した設計判断です。

8.3 マップ

internal/model/tag.go:16-20
var MyComboStatusTagNames = map[string]string{   // キー string → 値 string の辞書
    MyComboStatusInUse:      "使用中",
    MyComboStatusPracticing: "練習中",
    MyComboStatusReduced:    "頻度低下",
}

取り出しは v, ok := m[key] の 2 値形式が定番です(存在チェックと取得を同時に行う)。combo リポジトリの label, ok := labelMap[*combo.StarterMoveID](repository.go:619)などで頻出します。

9. ジェネリクス — Optional[T] を読む

Go 1.18 で導入されたジェネリクス(型パラメータ)は、このリポジトリでは控えめに、しかし要所で使われています。テストヘルパの func ptr[T any](v T) *T { return &v }(combo service_test.go:127)が最小例。[T any] が「任意の型 T について」という宣言です。

実戦例が PATCH の 3 状態問題を解く Optional[T]:

internal/repository/combo/optional.go:15-34
type Optional[T any] struct {
    Present bool // JSON にキーが存在した
    Value   *T   // nil ⇒ JSON null(NULL クリア)/ 非 nil ⇒ その値で更新
}

// UnmarshalJSON は JSON のキーが存在したときのみ呼ばれる。
func (o *Optional[T]) UnmarshalJSON(data []byte) error {
    o.Present = true                  // 呼ばれた = キーがあった
    if string(data) == "null" {
        o.Value = nil
        return nil
    }
    var v T
    if err := json.Unmarshal(data, &v); err != nil {
        return err
    }
    o.Value = &v
    return nil
}

ここには 2 つの仕組みが重なっています: (1) ジェネリクスで int にも string にも float64 にも使える 1 個の型を定義、(2) UnmarshalJSON メソッドを持つ型は encoding/json が自動でそれを呼ぶ(= インターフェースの暗黙実装。json.Unmarshaler を満たしている)。「キーが来なければメソッド自体が呼ばれない」性質を逆手に取って presence を検出する、Go らしい設計です。使われ方は UpdateMetadataRequest(combo/dto.go:133-168)を参照。

2026-08 以降の追加: typed-nil の罠と Arg() ヘルパ Optional には SQL バインド用の Arg() と、テストを読みやすくするコンストラクタ Some[T] / Null[T] が追加されました。Arg() のコメントが指摘しているのが Go 名物の typed-nil の罠です:
internal/repository/combo/optional.go:39-44
func (o Optional[T]) Arg() any {
    if o.Value == nil {
        return nil          // untyped nil を返す = database/sql は SQL NULL と解釈
    }
    return *o.Value
}
*T 型の nil ポインタをそのまま any(インターフェース)に入れると、「型情報は *T、値は nil」という非 nil のインターフェース値になり、database/sql は NULL として扱ってくれません。if o.Value == nil { return nil } と明示的に「型なし nil」へ落とすのはそのためです。「インターフェース == nil の判定は型と値の両方が nil のときだけ真」という言語仕様は、Go の FAQ にも載る頻出ハマりどころです。

10. goroutine — 今は「軽量スレッド」とだけ知っておけば OK

Go の看板機能である並行処理(goroutine / channel)は、このアプリではほぼ出てきません。Web サーバーとしての並行性は Echo(net/http)が「1 リクエスト = 1 goroutine」で勝手に面倒を見てくれるからです。唯一の明示的な使用例:

cmd/tacpendium/main.go:641-648(ブラウザ自動起動・抜粋)
go func() {                                    // go キーワード = この関数を別 goroutine で実行
    if err := browser.OpenURL(accessURL); err != nil {
        slog.Warn("failed to auto-launch browser; open the URL manually", ...)
    }
}()

「ブラウザ起動を待たずにサーバー起動を続けたい」ので投げっぱなしにしています。逆に言うと、ハンドラやサービスのコードは同期的に上から下へ読めば良い(async/await の色分け問題がない)のが Go の書き味です。
