シェル検査とフック
— 規約を「散文」ではなく「機械」で守らせる

これまでの資料は Go と React、つまりアプリのコードを扱ってきました。この資料が扱うのは、その周りにある scripts/(シェル 24 本・約 8,000 行)と .claude/hooks/(6 本)です。アプリの動作には 1 行も関与しませんが、このリポジトリの品質を実際に支えているのはこの層です。

なぜこれが教材になるのか どんなプロジェクトにも「規約」があります。import の順番、命名、ログの出し方。そしてそのほとんどは守られません——悪意があるからではなく、破っても何も起きないからです。このリポジトリは、その問題に対して「規約文書をもっと丁寧に書く」ではなく「破ったら赤くなる仕組みを自分で書く」という答えを出しています。しかも、その仕組みが正しく動いているかを確かめる仕組みまであります。Bash の書き方そのものより、その設計判断が本資料の主題です。

1. 全体像 — 性質の違う 2 つの層

まず「自分で回す検査」と「勝手に走る網」を区別してください。両者は目的も、失敗したときの振る舞いも違います。

scripts/.claude/hooks/
起動人 / AI が明示的に叩く(bash scripts/check-xxx.sh)自動。セッション開始時・ツール実行前後・応答完了時
主な役割規約違反の検出、派生資料の生成、監査危険操作のブロック、編集後の即時検査、環境整備
失敗時非ゼロ終了で「赤」を返すだけ作業そのものを止められる(exit 2 でツール実行を拒否)
Flask / Spring での近いものpre-commit のフック本体、Checkstyle / SpotBugs のカスタムルールGit の pre-push、Husky、IDE の保存時アクション

配線は .claude/settings.json の hooks ブロックが持っています。イベント名でどのスクリプトを走らせるかを宣言するだけの、素直な構造です。

.claude/settings.json(hooks ブロックの抜粋)
{
  "SessionStart": [{ "matcher": "startup|resume",
    "hooks": [{ "command": "bash \"$CLAUDE_PROJECT_DIR/.claude/hooks/session-start.sh\"",
                "timeout": 660 }] }],
  "PreToolUse":  [{ "matcher": "Bash",
    "hooks": [{ "command": "... /pre-push-guard.sh",    "timeout": 10 },
              { "command": "... /design-desk-guard.sh", "timeout": 10 }] }],
  "PostToolUse": [{ "matcher": "Write|Edit|MultiEdit",
    "hooks": [{ "command": "... /post-edit-check.sh",   "timeout": 90 }] }],
  "Stop":        [{ "hooks": [{ "command": "... /stop-test.sh",   "timeout": 300 }] },
                  { "hooks": [{ "command": "... /notify-bell.sh", "timeout": 5 }] }]
}
  • matcher — どのツールに反応するか。"Bash" なら Bash ツールの実行前、"Write|Edit|MultiEdit" ならファイル編集後
  • timeout — 秒。この値と、スクリプト内部のステップ上限は整合させる必要があります(§4.4)
  • $CLAUDE_PROJECT_DIR — リポジトリルート。フックはカレントディレクトリを仮定できないので、必ずこの変数を経由します

2. Bash の最小限の読み方

Python や Java から来ると、シェルは「文法が無いように見える」言語です。ここではこのリポジトリのスクリプトを読むのに必要な分だけを押さえます。

2.1 set の 3 文字 — そして検査スクリプトが -e を使わない理由

2 つの流儀が併存している
set -euo pipefail    # pre-push-guard.sh:14 — ガード系
set -uo pipefail     # check-*.sh / hooks の多く — 検査系(★ -e が無い)
文字意味外すとどうなるか
-eコマンドが失敗(非ゼロ終了)したら即座にスクリプトを終える失敗しても次の行へ進む
-u未定義変数を参照したらエラーtypo した変数が空文字として通る(rm -rf "$PREFIX/" が rm -rf / になる古典的事故)
-o pipefailパイプの途中が失敗したら全体を失敗にするfalse | tee log の終了コードが tee のもの(=成功)になる
★なぜ検査スクリプトは -e を外すのか 検査スクリプトは「失敗を数える」のが仕事です。grep は「1 件も見つからない」とき非ゼロで終わりますが、検査にとってそれは正常な結果(違反 0 件)です。-e を付けると、その正常な結果でスクリプトが即死します。session-start.sh:12 はもっと直接的な理由を書いています——「set -e は使わない。1 つの失敗で残りのステップが飛ぶのを防ぐため」。「途中まで動く」ことに価値がある処理では、-e はむしろ害になります。

2.2 $( ) と終了コード — このリポジトリで実際に事故が起きた場所

$(コマンド) はコマンドの出力を文字列として取り出す記法です(Python の subprocess.check_output() に相当)。重要なのは、これはサブシェル、つまり別プロセスで実行されることです。

代入の直後なら $? は取れる(post-edit-check.sh:23-24 の形)
vet_out="$(cd "$ROOT" && go vet "./$pkg" 2>&1)"
[ $? -ne 0 ] && findings+="go vet (./$pkg):"$'\n'"$vet_out"$'\n'
#  ↑ 代入文の終了コードは、右辺のコマンド置換の終了コードになる。ここは正しい

ところが、サブシェルの中で exit 2 しても、親スクリプトはそれを「文字列を受け取っただけ」として素通りできます。この落とし穴で、実際に検査が壊れました。

★★実在した欠陥: 「未実行」が「違反なし」の顔をして、しかも基準の破棄を勧めた check-md-emphasis.sh は Python の markdown ライブラリに依存します。それが入っていない環境で、内部関数は正しく exit 2(未実行)を返していました。しかしその呼び出しが $(...) の中だったため、終了コードはサブシェルとともに消え、親は「検出 0 件」を受け取って——

(1) 「結果: 違反なし」を exit 0 で出力し、(2) さらに『ベースラインが 375 行も余っているので BASELINE_BROKEN を 0 へ下げましょう』と勧めた。

⇒ 助言に従っていたら、基準そのものが消えていました。 「ライブラリが無くて検査できなかった」が「完璧です、基準を厳しくしましょう」に化けたわけです。現在この経路は、後述する自己検査の陽性対照 2 として恒久的に固定されています(check-md-emphasis.sh:214-222)。

2.3 その他、頻出する記法

記法意味
[ -n "$x" ] / [ -z "$x" ]文字列が非空 / 空。[ はコマンド名(test の別名)なので前後の空白が必須
A && B / A || BA が成功したら B / A が失敗したら B。if を書かずに済ませる定型
printf '%s' "$x"echo の代わり。echo は先頭が -n の文字列などを解釈してしまうため、変数を出すときは printf が安全
grep -qE '...'-q=出力せず終了コードだけ返す、-E=拡張正規表現。判定だけしたいときの定型
mktemp -d + trap "rm -rf '$tmp'" EXIT一時ディレクトリを作り、どう終了しても必ず消す。Java の try-with-resources / Python の finally に相当
"${VAR:-既定値}"未設定なら既定値。-u と組み合わせて「任意の環境変数」を安全に読む

3. 検査スクリプトの 7 つの規律

ここからが本題です。scripts/check-*.sh の 14 本は、ばらばらに書かれた寄せ集めではなく、共通の規律を持っています。

3.1 終了コードは 2 値ではなく 3 値 —「未実行」を「問題なし」と同じ顔で出さない

ほぼ全てのスクリプトが、ヘッダに同じ形の宣言を持ちます。

終了コードの規約(各スクリプトのヘッダより)
check-import-order.sh:33       0=ベースラインから増えていない / 1=増えた・自己検査に不合格 / 2=実行できなかった
check-migration-license.sh:35  0=違反なし / 1=違反あり(または自己検査 不合格) / 2=実行エラー(未実行。緑ではない)
check-public-snapshot.sh:30    0=違反なし / 1=違反あり(または自己検査 不合格) / 2=実行エラー(未実行。緑ではない)

3 番目の終了コードが要点です。 依存が入っていない、対象が見つからない、git リポジトリの外だった——こうしたときに 0 を返してはいけません。check-import-order.sh:40-41 がその理由を書いています。

scripts/check-import-order.sh:40-41
# 依存: python3 のみ(標準ライブラリ)。**未導入なら exit 2 で「未実行」を返す。**
#   緑を返さないのは、検査していないことを「問題なし」と同じ顔で出さないため(教訓 `E-84`)。
Flask / Spring 経験者向け: CI が「緑」の意味 Maven や pytest でも同じ問題が起きます。「テストが 0 件だったので成功」と 「テストが 120 件通ったので成功」は、CI のバッジ上ではどちらも緑です。設定ミスでテストが 1 件も収集されなくなったのに気づかず数週間走り続ける、というのは典型的な事故です。「実行できなかった」を独立した状態として持つだけで、この種の事故はほぼ消えます。

3.2 ベースライン固定型 — 0 を目指さない検査

既存の違反が大量にある規約に、あとから検査を入れるとどうなるか。素直に書くと 101 件の違反で真っ赤になり、誰も見なくなります。このリポジトリの答えは「件数ではなく、ベースラインから増えたかを見る」です。

実際のベースライン値(定数として直書きされている)
scripts/check-import-order.sh:70        BASELINE=101
scripts/check-md-emphasis.sh:113        BASELINE_BROKEN=247
scripts/check-enum-sync.sh:58           BASELINE_SCATTER=28
scripts/check-instruction-format.sh:138 BASELINE_FORBIDDEN=78
scripts/check-import-order.sh:43-47(運用ルールがコメントとして同居している)
# ベースライン固定型:
#   既存の違反が多いため、**件数そのものではなく「ベースラインから増えたか」を見る**。
#   ★既存分を機械的に並べ替えない。副作用 import(`import "./x.css"`)の順序を動かすと
#     評価順が変わり、**静かに壊れうる**。書いた本人が触るときに直していく。
#   減ったら BASELINE を下げること。増える方向の更新はしない。

最後の一行が運用の要です。ベースラインは一方向にしか動かせません。 「赤くなったからベースラインを上げる」を許すと、検査は存在しないのと同じになります。

なぜ既存分を一括で直さないのか 「101 件くらい機械的に並べ替えればいい」と思うところですが、コメントが理由を挙げています——副作用 import(import "./x.css" のように、読み込むこと自体が目的の import)は順序を動かすと評価順が変わり、静かに壊れうる。一括整形は「差分は大きいがリスクは無い」と思われがちですが、この種の例外が 1 件混ざっているだけで事故になります。だから「書いた本人が、その箇所を触るときに直す」という漸進的な方式を採っています。

3.3 --self-test — 検査を「陽性対照・陰性対照」で検査する

検査が緑であることは、検査が機能していることの証拠になりません。 判定式を壊してしまえば、何も検出せずに永遠に緑を返します。そこで全ての検査が --self-test を持ち、わざと違反したファイル(陽性対照)と、正しいファイル(陰性対照)を一時ディレクトリに作って、自分自身を判定させます。

scripts/check-md-emphasis.sh:183-196(自己検査の冒頭)
self_test() {
  local tmp st_fail=0 out
  tmp="$(mktemp -d)" || { echo "ERROR: mktemp 失敗" >&2; exit 2; }
  trap "rm -rf '$tmp'" EXIT              # どう終了しても片付ける

  # 陽性対照: 閉じ ** の直前が全角約物・直後が文字 → 検出されなければならない
  printf '**D-1〜D-259（256 行）**は退避した。\n' > "$tmp/positive.md"
  # 陰性対照 A: 約物を強調の外へ出した正しい形 → 検出してはならない
  printf '**D-1〜D-259**（256 行）は退避した。\n' > "$tmp/negative-ok.md"
  # 陰性対照 B: コードスパン内のリテラル ** → 誤検出してはならない
  printf '`**` の個数を数える検査は足りない。\n' > "$tmp/negative-code.md"

陰性対照(false positive を出さないこと)を必ず置いているのが良いところです。「違反を検出できる」だけなら「全部を違反と判定する」でも達成できてしまいます。両方向を固定して初めて、判定が意味を持ちます。

実行結果(2026-09-09 実測)
$ bash scripts/check-import-order.sh --self-test
OK  陰性対照(規約どおりの並び) → 緑
OK  陽性対照(相対パスの後ろに @/) → 赤
OK  陽性対照(サードパーティの後ろに React) → 赤
OK  陽性対照(多行 import をまたぐ後退) → 赤
OK  陰性対照(副作用 import・type import を含む正しい並び) → 緑
OK  テストファイルを本番と別に数える
自己検査: 合格(陽性は赤・陰性は緑)

3.4 実在した欠陥を、恒久的な対照として残す

§2.2 で触れた「$( ) が exit 2 を飲んだ」欠陥は、修正して終わりにせず、4 番目の対照としてスクリプトに埋め込まれています。

scripts/check-md-emphasis.sh:214-222
# 陽性対照 2: 依存欠落(未実行)の経路。**緑を返さないこと**が主張である
#   2026-08-13 実在した欠陥の回帰検査。run_check の exit 2 が $(...) のサブシェルで
#   死に、親は CUR=0 のまま「ベースラインから 375 行減少・違反なし」を exit 0 で返していた。
out=$(MD_EMPHASIS_FORCE_NO_DEP=1 bash "$0" 2>&1); rc=$?
if [ "$rc" -ne 0 ] && ! printf '%s' "$out" | grep -q '結果: 違反なし'; then
  echo "OK  陽性対照(依存欠落) → 未実行として非ゼロ終了・緑を返さない"
else
  echo "NG  依存欠落でも緑を返した(rc=$rc)。未実行と 0 件が同じ顔になっている"; st_fail=1
fi

MD_EMPHASIS_FORCE_NO_DEP=1 というテスト専用の環境変数で、依存が無い状態を人工的に再現しているのがポイントです(注入点は同ファイル :166)。これは Go のテストでモックを差し込むのと同じ発想で、「壊れた環境」を再現可能にするための注入口です。

JUnit / pytest 経験者向け やっていることは回帰テストそのものです。違うのは、テスト対象がアプリではなく検査ツール自身で、テストフレームワークを使わず --self-test というサブコマンドとして本体に同梱している点です。ツールが 300 行程度なら、この形は理にかなっています——テストが本体と同じファイルにあるので、片方だけコピーされて対照を失う事故が起きません。

3.5 「止める検査」と「知らせるだけの検査」を分ける

全ての検査が赤で止まるべきではありません。誤検出率が高い検査を blocking にすると、人は検査そのものを無視するようになります。

スクリプト終了コード理由
check-enum-sync.sh既定は常に 0(--strict で 1)汎用英単語(normal / system / throw)による誤検出が多く、誤検出率を測る前に blocking へ昇格させない
check-doc-inventory.sh常に 0(情報提供型)出力は違反の宣言ではなく「新種のファイルが増えた」通知。型に合っている ≠ 置いてよい
check-derived-docs.sh常に 0陳腐化の有無はレポート本文で人が判断する
その他 11 本0 / 1 / 2判定が決定論的で誤検出が少ない
★情報提供型の落とし穴と、その対処 「常に 0」の検査は、放っておくと誰も読まなくなります。check-doc-inventory.sh はその対策として例外表(EXCEPT)へ足して黙らせることを明示的に禁じています——「検査を通すために足すと、本検査は存在しないのと同じになる」。抑制の手段を用意しつつ、その手段を使ってよい条件を同じ場所に書いておく。これは blocking にしない検査を生かし続けるための必須のセットです。

3.6 「限界」を、検査自身に書く

このリポジトリのスクリプトには、ほぼ必ず 限界(重要・過信しないこと) という節がヘッダにあります。特に印象的なのが check-import-order.sh の自己申告です。

scripts/check-import-order.sh:54-58(限界の節より)
#   - ★★違反を「ファイル単位」で数える。⇒ 既にベースラインに入っているファイルの中へ
#     新しい違反を足しても検出されない(2026-09-01 クリーンルームレビュー B-3 で実証。
#     `App.test.tsx` へ注入しても 101 のまま緑)。本検査の動機である `M24-08` 型の
#     一括挿入も、既存 101 ファイルへ及んだぶんは見えない。
#   - 床であって証明ではない。 順序が規約どおりでも、その import が要るかは見ていない。

「この検査は、それを作る動機になった事故の一部を検出できない」と本人が書いているわけです。しかも実際に注入して確かめた記録つきで。これは自虐ではなく、次に読む人が検査を過信しないための情報です。「緑だから大丈夫」と言える範囲を、検査自身が限定しています。

3.7 メタ検査 — 検査の緑を信じないための 1 本

ここまでの規律(自己検査を持つ・生成物が壊れていない)を、横断的に確かめる検査があります。CLAUDE.md §8 が「★1 本目に回す」と指定している check-artifact-integrity.sh です。

scripts/check-artifact-integrity.sh:4-10(なぜ要るか)
# 背景: ... 同 §4.1 の原則はこうである——
#   ツールの成功メッセージ、AI の「変更した」という文章、画面上の完了表示は証拠ではない。
#
#   本検査を書く過程で、その原則の実例が出た。引き継ぎ書は「常設の検査機構は
#   すべて --self-test を持つ」と書いていたが、実際に走らせたら 1 本は持っていなかった
#   (`check-enum-sync.sh`。本コミットで追加した)。資料の記述は証拠ではない。

検査するのは 2 つです。(1) scripts/check-*.sh が --self-test を持ち、それが実際に通ること。(2) 生成物(code-facts.md 等)が実在し、非空で、行数がベースラインから激減していないこと。

実行結果(2026-09-09 実測)
$ bash scripts/check-artifact-integrity.sh
OK  design-desk-guard.sh の自己検査が通る
OK  archive-resolved.sh の自己検査が通る
   ... (中略・14 件すべて OK) ...
  検査 14 件 / ALLOW 除外 1 件

## 2. 生成物の健全性
OK  docs/handover/code-facts.md
OK  docs/handover/docs-map.md
OK  docs/handover/retrospective-digest.md
OK  docs/human-notes/custom-commands.md

結果: 違反なし

免除は 1 件だけで、免除の理由がコードに書かれています(:44-46)——「check-derived-docs.sh :: 判定が git のコミット時刻の大小比較のみで、対照を作っても比較演算子を確かめるだけになる」。免除リストに理由を併記させるのは、リストが「面倒なものを入れる場所」に堕ちるのを防ぐ良い設計です。

生成物の「激減だけ」を見る(:49-51) 生成物のベースラインは実測値のおよそ半分に設定され、下方向にしか判定しません。生成器が exit 0 でも中身が空、というのはよくある壊れ方だからです。ただしここにも限界の自己申告があります——「行数の激減は捕まえるが、内容が意味的に壊れている(例: 全行が同じ文字列)ことは検出しない」。

4. フック — 作業そのものを止める層

フックは stdin から JSON を受け取り、終了コードで結果を返すだけのプログラムです。言語は問いません(このリポジトリは全て Bash)。

ファイル編集後 等

4.1 pre-push-guard.sh — 許可リストで push を 1 形だけに絞る

このリポジトリでは push が原則禁止で、例外として claude/ 名前空間のブランチだけが許されています。それを機械的に強制するのがこのフックです。

.claude/hooks/pre-push-guard.sh:32-42(判定の全体)
# 「押し出す操作」を含まないコマンドは対象外
if ! printf '%s' "$cmd" | grep -qE '(^|[;&|[:space:]])git[[:space:]]+p…h([[:space:]]|$)'; then
  exit 0
fi

# 許可される唯一の形: origin の claude/<branch> 宛(前後空白のみ許容)
if printf '%s' "$cmd" | grep -qE '^[[:space:]]*git[[:space:]]+p…h[[:space:]]+origin[[:space:]]+claude/[A-Za-z0-9._-][A-Za-z0-9._/-]*[[:space:]]*$'; then
  exit 0
fi

echo "pre-push-guard: ブロックしました。..." >&2
exit 2
★上の引用で p…h と伏せ字にしてある理由(実話) 本資料を書いているときに、この HTML を生成するシェルコマンド自体がこのフックにブロックされました。 原因は単純で、フックは コマンド文字列の中に当該の語が現れるかどうかしか見ないため、ヒアドキュメントの中に書かれた「解説のための文字列」も本物の操作と区別できないのです。

そのため本資料はファイル書き込み用の別ツールで作成し、引用中の語は意図的に伏せてあります(伏せないと、この資料を Bash 経由で編集するたびにブロックされ続けます)。

★これは欠陥ではなく、設計どおりの過剰ブロックです。 次節の原則がそのまま当てはまります——「過剰ブロックは可視で直せるが、取りこぼしは silent である」。実際、私は即座に気づいて回避できました。逆に「文字列リテラルの中は無視する」よう賢くしようとすると、本物の操作を文字列に見せかける抜け道を作ることになります。判定を賢くするより、鈍いまま安全側に倒すほうが正しい場面があるという実例です。

正規表現が ^ で始まり $ で終わっているのが要点です。「その操作を含む」ではなく「その操作だけからなる」ことを要求しているので、末尾に ; echo done を付けた複合コマンドも、--force のようなフラグも通りません。ヘッダはこの設計を選んだ理由を書いています。

.claude/hooks/pre-push-guard.sh:5-11(なぜ settings.json の deny では足りないか)
#   settings.json の allow/deny はプレフィックス一致のため、refspec 形・
#   フラグ並べ替え・複合コマンドで漏れうる。また Claude Code on the web では
#   パーミッションの都度確認(ask)が実質機能せず、プラットフォームのブランチ制限も
#   「デフォルトブランチ保護」止まりで任意ブランチが通ることを実測済み。
#   本フックはリポジトリからコミット配布されるため devContainer・クラウドの両方で発火する。

fail-safe なパース

.claude/hooks/pre-push-guard.sh:18-29
if command -v jq >/dev/null 2>&1; then      # ① jq があれば jq
  cmd="$(... jq -r '.tool_input.command // empty' ...)"
fi
if [ -z "$cmd" ] && command -v python3 ...; then   # ② 無ければ python3
  cmd="$(... python3 -c 'import json,sys; ...' ...)"
fi
# 解析不能時は安全側: 生入力全体を判定対象にする
if [ -z "$cmd" ]; then cmd="$input"; fi        # ③ どちらも駄目なら入力全体を見る

③ が fail-safe(安全側に倒す) の実装です。JSON を解釈できなかったとき、cmd が空のままだと grep が何もマッチせず「対象外」と判定して通してしまいます。そこで生の入力全体を判定対象にすることで、解釈できないときは通さない方向へ倒しています。§3.1 の「未実行を緑にしない」と同じ思想が、フック層にも一貫して現れています。

4.2 design-desk-guard.sh — 許可リスト方式の教科書

このリポジトリには「設計卓」という役割があり、その作業中は実装ソースを読ませないという運用をしています(設計判断が実装に引きずられるのを防ぐため)。実現は 2 層構造です。

  1. 物理排除 — scripts/design-desk-arm.sh が git の sparse-checkout で、docs/ .claude/ scripts/ 以外を作業ツリーから消す。ファイルが存在しないので cat も grep も空振りする
  2. 残る穴を塞ぐ — 消えても git のオブジェクトデータベースには残っているので、git show HEAD:internal/... で読めてしまう。この経路だけをフックが塞ぐ
★★なぜ「禁止する動詞を並べる」ではなく「安全な動詞を許可する」なのか design-desk-guard.sh:10-14 の逐語:

「列挙方式は必ず取りこぼす(show / log -p / diff <rev> / grep / blame / cat-file / archive / format-patch / bundle / read-tree / checkout-index ...)。許可リスト方式なら集合が閉じる。過剰ブロックは可視で直せるが、取りこぼしは silent である。」

最後の一文が、セキュリティ設計で最も重要な非対称性です。許可リストが厳しすぎれば「ブロックされた」と目に見えて、その場で直せます。禁止リストに穴があっても、誰も気づきません。 同じ理由で、Web アプリの入力検証も「危険な文字を弾く」より「許される文字だけ通す」が原則になります。
.claude/hooks/design-desk-guard.sh:70-74(許可する動詞の列挙)
case "$verb" in
  # --- 内容を出さない: 無条件で通す ---
  status|add|commit|branch|remote|rev-parse|ls-files|ls-tree|shortlog|describe|…|init)
    continue ;;
  # --- パッチ指定があるときだけ内容が出る ---
  ...

分類の軸が「危険かどうか」ではなく 「ファイルの中身が出るかどうか」 になっているのが上手いところです。git log は通るが git log -p は(パスを限定しない限り)止まる。守りたいものは「実装の中身を読ませないこと」なので、判定軸をそこに合わせています。

さらに、このフックはマーカーファイルが存在するときだけ発火します(tmp/.design-desk-armed)。通常の開発セッションには一切影響しません。そしてマーカー自体に触れようとするコマンドもブロックします(:50-52)——ガード自身を無効化する経路を塞いでおかないと、ガードは意味を持ちません。

4.3 post-edit-check.sh / stop-test.sh — 止めない側のフック

ガード 2 本と違い、この 2 本は絶対に作業を止めません(常に exit 0)。結果は JSON で「伝える」だけです。

.claude/hooks/post-edit-check.sh:35-39(結果の返し方)
if [ -n "$findings" ]; then
  jq -n --arg ctx "[品質フック] $rel の編集後チェックで指摘:"$'\n'"$findings" \
    '{hookSpecificOutput: {hookEventName: "PostToolUse", additionalContext: $ctx}}'
fi
exit 0

additionalContext は AI の文脈へ差し込まれ、systemMessage(stop-test.sh が使用)は開発者への警告として表示されます。「ブロックする」以外の返し方を持っているのがフック機構の要点です。

差分ゲート — 変わった側だけ回す

.claude/hooks/stop-test.sh:16-22
changed="$( { git diff --name-only HEAD; git ls-files --others --exclude-standard; } 2>/dev/null )"
[ -z "$changed" ] && exit 0            # 変更が無ければ即終了

printf '%s\n' "$changed" | grep -Eq '\.go$' && go_changed=1
printf '%s\n' "$changed" | grep -Eq '^migrations/.*\.sql$' && go_changed=1
printf '%s\n' "$changed" | grep -Eq '^web/.*\.(ts|tsx)$' && web_changed=1

マイグレーションの変更で Go テストを回すのが面白い判断です。理由がヘッダ(:4-6)にあります——「dbtest.Setup が全マイグレを適用するため go テストがマイグレーションの実質的な回帰テストになっている」。タグのテストで見たテンプレート方式の DB が、ここで別の役割を果たしているわけです。

★無限ループを防ぐ 1 行 stop-test.sh:13: [ "$(... jq -r '.stop_hook_active // false')" = "true" ] && exit 0

Stop フックは「応答が完了したとき」に走ります。そのフックの出力が新しい応答を誘発すると、また Stop フックが走る——という無限ループが起こりえます。stop_hook_active は「いま Stop フック起因の応答中である」ことを示すフラグで、それを見て即座に降りています。自分の出力が自分を再起動しうる仕組みでは、必ず再入判定が要ります。

4.4 session-start.sh — 環境を直す、ただし絶対に止めない

クローン直後の環境では、検査に必要な markdown-it-py も web/node_modules も無く、検査が最初から赤になります。このフックはそれを整えます。

.claude/hooks/session-start.sh:9-20(設計方針が全て書いてある)
# ★直すのは環境であって検査ではない。検査スクリプトは 1 行も緩めていない。
#
# ★★本スクリプトは絶対にセッションを止めないこと。
#   - `set -e` は使わない。1 つの失敗で残りのステップが飛ぶのを防ぐため。
#   - 各ステップの失敗は警告 1 行に留め、末尾で無条件に exit 0 する。
#   - 環境整備が転けたせいで作業ができなくなるのが最悪である。
#
# ★冪等であること。既に入っているものは触らない ⇒ 2 回目以降は無音で即終了する。
#
# ★出力はすべて stderr へ出す。SessionStart の stdout は Claude の文脈へ注入されるため、
#   毎セッション数行が積まれると本当に見るべき出力が埋もれる。何もしなければ 1 バイトも出さない。

4 つの規律が並んでいます。とくに 「直すのは環境であって検査ではない」 は重要で、「検査が赤い」への対処として検査を緩めるのは最も安易で最も損な選択です。ここでは代わりに、赤くなる原因(依存の不在)を消しています。

タイムアウトの配分(:37-40) 「★配分は settings.json の hook timeout と整合させること。3 ステップの上限の合計 120 + 240 + 240 = 600 秒 < hook timeout 660 秒」。内側の上限の合計が、外側の上限を超えないようにする——超えていると、内側のタイムアウト処理に到達する前に外側から強制終了され、後片付けもログも残りません。HTTP クライアントのタイムアウトとサーバ側のタイムアウトを設計するときと同じ考え方です。

4.5 ★フックはパーミッション層をバイパスする

最後に、フックを書くときに最も注意すべき性質です。post-edit-check.sh:5-7 と stop-test.sh:7-9 が同じ注記を持っています。

.claude/hooks/stop-test.sh:7-9
# 注: フックはパーミッション層をバイパスして実行される。本スクリプトは git の読み取り
#     (diff/ls-files)とテスト実行のみで構成し、ソース改変・git 書込・ネットワーク
#     アクセスを行わない(CLAUDE.md §10 の趣旨に整合)。

AI が直接実行するコマンドは許可・拒否のリストで制御されますが、フックはその外側で走ります。つまりフックに書いた処理は、パーミッション設定を素通りして実行されるということです。だから 2 本とも「読み取りとテスト実行だけ」と自己制限を宣言し、その旨をコードに書き残しています。「便利だから」とフックに書き込み処理を足すと、そこが制御の抜け穴になります。

6. 持ち帰り

原則要点§
「未実行」を「問題なし」にしない終了コードは 0 / 1 / 2 の三値。依存が無いなら赤でも緑でもなく「実行できなかった」3.1
0 を目指さない検査を作る既存違反が多い規約には、ベースライン固定型。一方向にしか動かさないことが規律の本体3.2
検査を検査する陽性対照と陰性対照の両方。緑は「機能している」証拠にならない3.3, 3.7
踏んだ欠陥を対照として残す直して終わりにせず、再現用の注入口ごとスクリプトへ埋める3.4
止める検査と知らせる検査を分ける誤検出が多いものを blocking にすると、検査ごと無視される3.5
限界を自分で書く「床であって証明ではない」。検出できない範囲を明示すると過信が防げる3.6
許可リスト方式過剰ブロックは可視で直せるが、取りこぼしは silent。禁止列挙は必ず漏れる4.1, 4.2
解釈できないときは通さないパース失敗時に「対象外」へ倒すと、壊れた入力が素通りする4.1
自動で走るものは絶対に止めない環境整備・通知系は常に exit 0・冪等・出力は stderr4.4
検査が赤いとき、検査を緩めない直すのは環境か実装。基準を下げるのは最後の手段4.4
