Playwright E2E シナリオガイド
— 基盤の仕組みと「シナリオの書き方」を体系的に学ぶ

コンボのテスト + E2E では combo-crud.spec.ts を 1 本だけ逐行で読みました。このページはその続編で、E2E 基盤がどう動いているか(実行の仕組み)と、65 本の実 spec から抽出したシナリオ設計パターン、そして自分で新しい spec を書く手順までを体系的に扱います。

このリポジトリの E2E の全体像 spec は web/e2e/*.spec.ts に 65 本(本ガイド初版の 2026-07-22 時点では 20 本でした)。共通の「下ごしらえ」は web/e2e/support/ 配下の共有ヘルパ 12 ファイルに集約されています(§5.6)。実行は全数が make e2e、絞り込みが make e2e-only P=<パターン>(§2.2。playwright を直接叩かないのが規約)。設定は web/playwright.config.ts(184 行)にすべて集約されています。導入経緯は指示書 docs/instructions/phase2/M8-02-e2e-playwright-foundation.md(段階導入方針: 全シナリオの spec 化や全要素への testid 付与は「やらない」と明記)にあります。

2. 実行の仕組み — make e2e で何が起きるか

  1. make e2e(Makefile:147-149)が Chromium を確保(プリインストール版があれば PW_EXECUTABLE_PATH で指し、なければ pnpm exec playwright install chromium。Makefile:123-145 の共通変数)→ pnpm e2e を実行。pnpm e2e = playwright test(web/package.json:13)
  2. Playwright が web/playwright.config.ts を読み、webServer 2 本を自動起動する(下記)
  3. webServer①: バックエンド。rm -rf web/e2e/.tmp → mkdir → cp config.toml.example(E2E 専用の設定ファイルを使い捨て DB と同じ寿命で作る)→ go run -tags=debug ./cmd/tacpendium。環境変数 TACPENDIUM_DB_PATH / TACPENDIUM_CONFIG_PATH / TACPENDIUM_PORT で DB を web/e2e/.tmp/tacpendium-e2e.db に、設定を専用 toml に、ポートを E2E 専用(基準 47390)に向ける。起動時にマイグレーション + seed が自動適用されるので毎回クリーンな seed 済み DB になる(debug タグの意味は §5.8)
  4. webServer②: pnpm build でフロントを本番ビルドし、Vite preview(ビルド済み dist の配信)を E2E 専用ポート(基準 5273、--strictPort)で起動、VITE_API_PORT で API プロキシ先を E2E バックエンドへ向ける(dev サーバから preview へ移行した理由は下記 note)
  5. 両ポートの応答を確認後、web/e2e/ の全 spec を Chromium(headless)で直列実行(fullyParallel: false + workers: 1。後者が要る理由は下記 note)。失敗した spec は 1 回だけ再試行(retries: 1)し、再試行時は実行トレースを記録(trace: "on-first-retry")
  6. 終了後、Playwright が webServer 2 本を落とす。dev 環境(通常ポート・dev DB・dev の config.toml)には一切影響しない
web/playwright.config.ts:66-183(設定の本体・抜粋。長大な理由コメントは省略)

2026-07-22 の初版以降に入った 3 つの大きな基盤変更
  • workers: 1 への固定(M24-09c): fullyParallel: false が直列化するのは「1 ファイルの中」だけで、spec ファイル同士は worker 数だけ並列に走る——ところが E2E スタックはバックエンド 1 本・DB 1 個の共有資源。プリセット総数(上限 8 件)の奪い合いなど「組み合わせでしか出ない」落ち方が実測され、worker を 1 に固定した。代償は実行時間約 1.5 倍。aa-interference-probe-{a,b}.spec.ts の 2 本はこの設定を守るための「検出器」で、ファイル名を aa- で始めて必ず先頭 2 本に置き、workers>=2 なら必ず赤・workers=1 なら必ず緑になるよう設計されている(誰かが workers: 1 を消すと赤くなって検出される)
  • debug ビルドでの起動(M28-02c): go run -tags=debug で、本番バイナリには存在しない /api/debug/* の書き込み口が生える。詳細は §5.8
  • E2E 専用 config + preview 配信(M24-09c 追補 / CHANGE-135): 以前は dev と同じ config.toml を読んでいたため、開発者が設定画面で既定キャラを変えた瞬間に「リュウが出ること」前提の spec が 35 件まとめて落ちた。専用 toml([defaults] なし)で縁を切り、キャラが要る spec は自分で明示する(§5.6 の character.ts)。またフロントは dev サーバでなく pnpm build + vite preview で配る——dev サーバは ESM を 1 モジュールずつ配るため、テストごとに新規コンテキスト(=キャッシュ空)の Playwright では毎回数百リクエストの固定費を払う。実測で 402 秒 → 223〜253 秒。pnpm build を Makefile でなく config 側に置くのは「どの経路から起動しても古い dist を検査しない」ため

2.1 ポートが「導出」される理由(worktree 並行対応)

config.ts:35-53 は E2E ポートを固定値ではなく config.toml の dev ポートからのオフセットで計算します。このリポジトリは git worktree で複数の作業ツリーを並行運用しており(各 worktree に固有の dev ポートが割当てられる)、E2E ポートも worktree ごとにずらすことで 複数 worktree での make e2e 同時実行が衝突しないようにしています。ルートの標準構成ではオフセット 0 で 47390 / 5273 のままです。読めなければ基準値へフォールバックするので、CI や単独環境では意識不要です。

config コメントに刻まれた実際の事故(config.ts:19-22) 「使い捨て DB の破棄をモジュールスコープで行ってはならない」— config.ts は Playwright のワーカープロセスでも再ロードされるため、トップレベルに rm -rf 相当を書くとテスト実行中に稼働中バックエンドの DB が消え、全 API が "no such table" の 500 になります。だから破棄は webServer の起動コマンド内(1 回だけ実行される場所)にあります。「設定ファイルが何回・どのプロセスで評価されるか」を意識する必要がある、という教訓が本番のコメントとして残されています。

2.2 絞り込み実行は make e2e-only — playwright を直接叩かない

絞り込み実行の正しい入口(Makefile:171-179)
make e2e-only P=combo-crud                          # ファイル名パターンで絞る
make e2e-only P="m24-13 -g 保存"                    # さらにテスト名(-g)でも絞る
make e2e-only P="--repeat-each=3 aa-interference-probe-a"  # flaky 調査で反復

cd web && pnpm exec playwright test combo-crud のように playwright を直接叩いてはいけません。Makefile が設定する PW_EXECUTABLE_PATH(プリインストール Chromium の場所)が渡らず、UI を使う spec が Executable doesn't exist ... で全滅します。全数実行(make e2e)では起きず、絞り込みのときだけ落ちる罠で、実際に M24-13 の作業者が踏んで 1 回分の実行を捨てました(D-599)。この対策として e2e-only ターゲットが新設され、e2e と同じ環境変数・同じ Chromium 解決を 1 か所(Makefile:123-145)で共有しています。P= を省略すると「絞ったつもりの全数実行」を防ぐため usage を出して止まります。ここにある設計思想——「注意書きを文書に足す」のではなく「正しい入口をターゲットとして提供し機械で守る」——はこのリポジトリ全体に一貫する型です。

3. Playwright の基本文法

3.1 test / describe / fixture

spec の基本骨格(combo-crud.spec.ts:1-15 の形)
import { test, expect } from "@playwright/test";

test.describe("コンボ CRUD スモーク", () => {          // グループ(Vitest の describe と同じ)
  test("コンボ登録 → 詳細確認 → 編集 → 削除", async ({ page }) => {
    // page がブラウザタブ。テストごとに新しいタブ+新しい文脈が渡される
  });
});

async ({ page }) の分割代入が Playwright の fixture 注入です。テスト関数の引数に欲しいものを書くと、フレームワークが用意して渡してくれます(pytest の fixture と同じ発想)。page(ブラウザタブ)のほか、ブラウザなしで HTTP を叩く request fixture もあります(§5.4)。

3.2 Locator と自動待機 — Playwright 最大の発明

page.getByRole("button", { name: "保存" }) が返すのは「今見つけた DOM 要素」ではありません。「保存ボタンの探し方」を記述した Locator オブジェクトで、実際の探索は .click() や expect(...).toBeVisible() の瞬間に行われ、しかも条件が満たされるまで自動で待ちます(既定タイムアウト付き)。

書いたコード実際の意味
await locator.click()要素が「存在し・可視で・安定し・クリック可能」になるまで待ってからクリック
await expect(locator).toBeVisible()可視になるまで待つ(なった瞬間に成功)
await expect(page).toHaveURL(/\/combos\/\d+$/)URL がパターンに一致するまで待つ(SPA の画面遷移待ちはこれで書く)

だからこのリポジトリの spec は原則 sleep / waitForTimeout を使いません(例外は m21-05 / m21-07 のリアルタイム入力系のみ——「一定時間の窓の中で入力が確定する」という時間そのものが仕様のため、待ち時間が検証対象になっています)。「保存 → API 往復 → invalidate → 再取得 → 再描画」という非同期の連鎖を、「最終的にこう見えるはず」という宣言(expect)だけで待つのが Playwright 流です。React の宣言的 UI(状態→画面)とちょうど対になる、宣言的なテスト(期待→待機)と覚えてください。

4. セレクタ戦略 — 「どう要素を掴むか」は規約で決まっている

このリポジトリには専用の設計書 docs/design/testid-convention.md があり、優先順位が明文化されています(:42-49):

  1. getByRole + アクセシブル名 — 例: getByRole("button", { name: "保存" })。HTML の意味論(role)とユーザーに見える名前で選ぶ。最優先
  2. getByLabel — フォームの <label> 関連付けで選ぶ
  3. getByPlaceholder / getByText — 例: メモ欄はラベルがないので getByPlaceholder("このコンボに関するメモ(任意)")
  4. getByTestId — 上記で一意に取れない場合の最後の手段。命名は {feature}-{element} の kebab-case(例 combo-editor-draft-checkbox)で、付与したら必ず convention の「付与済み一覧」(:58-82)に登録する

「testid を最後の手段にする」理由は 2 つ: (1) role/名前で書かれたテストはユーザーに見える振る舞いの仕様になり、内部実装のリファクタで壊れない。(2) アクセシビリティの検証を兼ねる(role と名前が取れない UI はスクリーンリーダーにも読めない)。

4.1 testid が必要になる典型例 — Radix Checkbox

convention(:30-32)が挙げる代表例: shadcn/ui の土台の Radix Checkbox は <button role="checkbox"> としてレンダリングされ、label で囲んでもアクセシブル名が自動設定されません。だから仮登録チェックボックスは combo-editor-draft-checkbox という testid を持ちます。「UI ライブラリの実装都合でセレクタ戦略が変わる」ことの具体例です。逆に「保存」ボタンや「編集」リンクは素の要素なので testid 不要(:34-40)。

4.2 「文言で判定しない」の強化 — 可変文言は testid + 構造で掴む(M29-01)

優先順位の原則(role + 見える名前が最優先)は変わっていませんが、2026-09 の M29-01(CHANGE-161)で「可変の値を含む案内・バッジは文言で判定しない」方針が明文化され、そのための testid が追加されました:

  • export-truncation-confirm(M29-02): 書出が上限で切り捨てるときの確認 UI。件数は可変であり、文面での照合は語を直すたびに壊れる——だから「確認が出ていること」は testid で掴み、件数の中身を見たいときだけその要素の中を見る
  • combo-recipe-steps-empty / setup-recipe-steps-empty: 空ステップの案内。「まだステップがありません」等の文言一致でなく構造で掴む
  • import-issue: CSV 取込の課題バッジ

使い分けの軸はこうです——ボタン名・リンク名のように「その文言自体がユーザーに見える仕様」であるものは従来どおり文言(role + name)で。一方、件数・エラー詳細のように「文言の細部は仕様でなく、その要素が出ている/出ていないことが仕様」であるものは testid で。なお、m27-02b の必須欄エラーのように「理由が画面に届いていること」自体を主張したい場合は、あえて toContainText("ダメージ") と文言側で見ます(「止まる」だけでは利用者は直せない、という検証意図があるため)。

convention にはもう 1 つ新ルールが刻まれました(:84-88): 同じ testid を面ごとに分けるかは「同時に画面へ出うるか」で決める。上記の空ステップ案内が 2 名に分かれているのは、SetupInputRow が SetupRecipeEditor を描くためコンボエディタでは両方が同時に存在し、共通名 1 本だと Playwright の strict モード(Locator が複数要素に当たるとエラー)で落ちるからです。「別の画面だから衝突しない」は、部品の入れ子で崩れる——共通名を付ける前に包含関係を 1 度たどる、という教訓です。

5. シナリオ設計パターン集 — 65 本の spec から抽出

5.1 スモーク型: 1 機能の一生を 1 本で通す

combo-crud.spec.ts(前章 §4.2 で逐行解説)の「登録 → 詳細 → 編集 → 削除」がテンプレートです。/add_e2e_spec スキルも「まず combo-crud を読め」と指示しています。要素は 3 つ:

  • ユニーク値: const memo = `e2e-smoke-${Date.now()}` — 再実行・並行 worktree でもデータが衝突しない。作った行を後で getByText(memo) で同定する鍵にもなる
  • 仮登録(draft)の活用: 仮登録モードで、テストの関心(CRUD 動線)に無関係なメタデータ入力を省く。★ただし M24-13(CHANGE-139)で「仮登録でもレシピ 1 ステップ以上必須」に変わったため(VAL-C09)、いまは共有ヘルパ addMinimalRecipeStep(page) で非技ステップを 1 本置いてから保存する(§5.7)
  • 自己後始末: 最後に自分が作ったデータを自分で消す。spec 冒頭コメント「既存コンボ件数に依存しない」(combo-crud:10)が設計宣言

5.2 非回帰(regression pin)型: 直したバグを釘付けにする

combo-crud の 2 本目(:77-125)「メモのみ編集しても custom_states が温存される」は、過去に実際に起きた「1 項目だけ編集すると触っていないメタデータが消える」バグ(E-1)の再発防止テストです。E2E の最重要用途のひとつで、テスト名とコメントに「何の回帰を防ぐか」(E-1 / M11-02)を必ず書くのがこのリポジトリの流儀です。半年後に「このテスト消していい?」と迷わないための投資です。

5.3 ハイブリッド型: fixture は API、操作は UI、検証は API

E-1 の完全版 m12-06-presence-detection.spec.ts は、方式そのものを冒頭コメントで宣言しています:

web/e2e/m12-06-presence-detection.spec.ts:11-15, 72-79(抜粋)
// 方式(実装方式非依存・指示書 §10-2):
//   - fixture 作成 = API(全 nullable 項目を確実に設定。FE への新規 test-id 付与=スコープ逸脱を回避)。
//   - 1 項目編集 = UI(editor が GET から全項目をロードし buildPatchPayload が全キーを再送するかを実検証)。
//   - アサート = API GET(= 指示書 §4.1「再取得」。DOM 非依存)。

async function createFixtureCombo(page: Page, memo: string): Promise<number> {
  const characterId = await ryuCharacterId(page);
  const res = await page.request.post("/api/combos", {
    data: fixturePayload(characterId, memo),      // damage/ゲージ/起き攻め…全項目入り
  });
  expect(res.ok(), `fixture 作成失敗: ${res.status()} ${await res.text()}`).toBeTruthy();
  return (await res.json()).id as number;
}

UI で全項目を入力すると、テストが長く・遅く・UI 変更に弱くなります。そこでテストの関心でない部分(前提データ作成・結果確認)は API で直行し、関心の中心(「UI から 1 項目編集する」という操作)だけ UI を通す。E2E の実行時間と壊れやすさを制御する最重要テクニックです。

5.4 純 API 型: ブラウザを開かない E2E

web/e2e/m17-02-command-index-api.spec.ts:30-45(抜粋)
const ryuRes = await page.request.get(`/api/characters/${idOf("ryu")}/command-index`);

5.5 ダウンロード検証: イベントを待つ 2 つの方法

5.6 共有ヘルパ support/ — 「3 spec 以上で必要になったら共有化」が実際に起きた

本ガイド初版(2026-07)の時点では共有ヘルパファイルが無く、「各 spec が自己完結する。同じヘルパが 3 spec 以上で必要になったら共有化を検討」という温度感でした。その後、仕様変更・環境変更が「ほぼ全 spec の下ごしらえ」に波及する事態が続き、共通の下ごしらえは web/e2e/support/(12 ファイル)へ集約されました(判断基準は D-553「同じ数行を複数 spec へ複製しない」)。予告どおりの進化が起きた形で、いつ共有化へ倒すかの生きた実例です。代表的なもの:

5.7 下ごしらえヘルパ: バリデーション強化を「spec の関心」から切り離す

2026-08〜09 に入力仕様が 2 段階で厳しくなりました: M24-13(CHANGE-139)で仮登録でもレシピ 1 ステップ以上が必須に(VAL-C09)、M27-02b(P4M-009 / VAL-C15)で本登録は必須 4 欄(ダメージ・有利フレーム・消費ゲージ 2 欄)が必須に。どちらも「UI から保存する」spec 全部に波及する変更です。これを各 spec に数行ずつ書き足すのではなく、意図が名前になったヘルパへ寄せました:

web/e2e/support/editor-input.ts:50-57, 196-203(抜粋)
// 本登録で保存する spec 用。必須は 4 欄だが、埋めるのは 2 欄だけでよい

// 仮登録で保存する spec 用。非技ステップ(パリィドライブラッシュ)を 1 本置く —
// 技を選ばないため move の解決が要らず、始動技も決まらないので VAL-C03 の警告も出ない。

効果は diff の読みやすさに出ます。仕様変更時に各 spec へ入った変更は「await addMinimalRecipeStep(page); の 1 行 + 理由コメント」だけで、その spec が何を検証しているか(関心)は 1 文字も変わっていないことがレビューで一目で分かる。逐語のステップ操作を 65 spec へ複製していたら、この保証は得られませんでした。「テストの関心でない入力は、意図を名前にしたヘルパへ」——§5.3 の「fixture は API で」と同じ思想の UI 版です。

5.8 debug ビルドの書き込み口: 本番では作れない状態を E2E から作る

M28-02c(ゲーム更新への追従・FR702)の E2E は新しい問題に直面しました。「影響コンボあり」の判定は moves.last_changed_game_version が非 NULL であることを要求しますが、このマーカーを立てる経路は本番では DML マイグレーションしか無く、HTTP からは作れません。しかも初回は必ず 0 件(既存コンボの基準は最新)なので、「画面を開いたら何も出なかった。正しい」は検証したことの証拠にならない——何も出ない画面は、機能が壊れていても同じ見た目だからです。

採られた解決が Go のビルドタグです。バックエンドを go run -tags=debug で起動し(§2 の config)、debug ビルドにだけ存在する /api/debug/* の 5 ルート(internal/api/debug/)から人工的に「古い基準」を作ってから画面を確かめます:

web/e2e/support/game-update.ts:21-34(抜粋)
// 技にマーカーを立てる(配信者の DML マイグレを模す)。
export async function setMoveGameVersion(
  request: APIRequestContext,
  moveId: number,
  version: string | null,
): Promise<void> {
  const res = await request.post(`/api/debug/moves/${moveId}/game-version`, {
    data: { lastChangedGameVersion: version ?? "" },
  });
  expect(
    res.ok(),
    `マーカーの設定に失敗: ${res.status()} ${await res.text()}` +
      "(★E2E バックエンドが -tags=debug で起動しているか確かめること)",
  ).toBeTruthy();
}

学びどころは 3 つ。(1) テスト専用の口はビルドタグで隔離する——本番バイナリには「1 バイトも出ない」ため、テスト都合が製品を汚さない(代償として「E2E が検査するのは debug ビルド」になるが、差分は debug 5 ルートの登録だけ)。(2) 「0 件で何も出ない」は成功の証拠にならない——観測したい状態を人工的に作ってから確かめる。(3) 延期の記録のような共有状態は明示的に復元する(clearGameUpdatePostpone)——起動時の rm -rf .tmp が救ってくれるのは run をまたぐ残渣だけで、同一 run 内の後続 spec は救えない。

5.9 サーバ状態を 1 バイトも書き換えない spec: page.route でスタブする

M29-02(書出の切り捨て確認ダイアログ)の E2E は、また別の型の問題でした。このダイアログは「一覧が上限(100 件)で切れている」ときにだけ出ます。素直にやるとコンボを 101 件投入することになりますが、それは共有 DB を 100 件で埋め、一覧を見る他ファイルの spec を道連れにします。これは「同じ資源を奪い合う」型(→ 同一ファイルへ寄せれば解ける)ではなく「全 spec に影響する状態」型であり、寄せても解けません(D-466)。

解決は page.route(): GET /api/combos の応答だけをそのブラウザコンテキスト内で差し替え、「loaded 100 件 / total 250 件」の一覧を偽装します(total > items が「上限で切り捨てた」の観測。対照として 100 / 100 = 切り捨て無しのケースも同じスタブで作る)。サーバにもDB にも一切触れないため、他 spec への影響はゼロで、復元も不要です。M22-01 が認証の ON/OFF を確かめたときに採ったのと同じ形です。使い分けの判定の問いは「この spec が落ちたら、他のファイルのテストも道連れになるか」——ならない spec は資源を取り合っていない、です。fixture を本物の API で作る §5.3 とは逆方向のテクニックですが、動機は同じ「E2E の壊れやすさと実行コストの制御」で、本物を使うのは検証対象の経路だけ、それ以外は最短の手段でという一貫した方針に収まります。

6. 新しい spec を書く手順 — /add_e2e_spec スキル

spec 追加は手順化されており、Claude Code のスラッシュコマンド /add_e2e_spec タグ作成・編集・削除 のように使います(.claude/commands/add_e2e_spec.md)。手で書く場合も同じ手順をなぞるのが安全です:

  1. Stage 0 — 規約とテンプレートの読込: testid-convention.md(セレクタ優先順位・付与済み testid 一覧)と combo-crud.spec.ts(構造テンプレート)を読み、ls web/e2e/ で命名重複を確認
  2. Stage 1 — 対象フィーチャーの調査: 対象ページ・コンポーネントを読み、URL / 操作フロー / セレクタ候補を洗い出す。getByRole 等で取れない操作要素だけが testid 追加候補
  3. Stage 2 — 設計提示と承認待ち: ファイル名 web/e2e/{feature}-{operation}.spec.ts、手順(ステップ番号付き)、必要 testid、不確定要素を提示し、実装前に開発者の承認を得る(スキルはここで一時停止する設計)
  4. Stage 3 — 実装: (3-1) 必要最小限の testid 付与 → (3-2) spec 作成(Date.now ユニーク化・draft 活用・自己後始末・コメントはフェーズ区切りのみ)→ (3-3) testid-convention.md の付与済み一覧を更新 → make e2e で実行検証
spec を書くときの制約(スキル :103-160 の要約。運用で得た教訓が大幅に増えた)
  • セレクタ優先順位(role → label → placeholder/text → testid)を厳守
  • ユニーク識別子でデータ衝突を避ける——fullyParallel: false が直列化するのはファイル内だけで、設定次第でファイル同士は並列に走る前提で書く(現在は workers: 1 だが、それに甘えない)
  • 総数に上限のあるグローバル資源(プリセット 8 件等)を触る spec は、資源ごとに 1 ファイルへ寄せる(D-362。別ファイルに分けたら上限テストが「組み合わせでだけ」落ちた実例あり)。ただし適用単位は「画面」でなく「書き換える共有資源」であり、サーバ状態を書き換えない page.route 型の spec は別ファイルでよい。認証 ON/OFF のような「全 spec に影響する状態」は寄せても解けない——page.route へ倒す(D-466、§5.9)
  • 破壊確認を回す: 不具合を復元したら本当に赤くなるかを確かめる(D-375)。実例: page.keyboard.down() は自動でキーリピートを送らないため、初版 spec は不具合を復元しても緑のままだった
  • 「抑止される/効かない」ことを見る spec には対照実験(対象外なら従来どおり動く)を添える——全部を抑止していても緑になるのを防ぐ
  • 「〜が残っていない」を主張する走査型テストは、走査の前に「対象が実際に描画されたこと」を 1 行アサートする(E-217。描画されていなければ走査は常に真を返す)
  • ウィザード完了済み DB を前提とし、DB リセット・初期化ロジックを spec 内に書かない(それは基盤=config の仕事)
  • コメントは「環境前提」と「フェーズ区切り(── 登録 ── 等)」のみ。実装説明コメントは書かない

ちなみにタグ管理まわりは、タグフィルタ・タグ管理画面の検索(m24-02)と API での fixture 作成(support/tags.ts)まで整いましたが、UI からの「タグ作成 → 一覧確認 → 編集 → 使用中削除の 409 → force 削除」を通す CRUD spec は依然として存在しません。この手順の練習題材として最適な状況は変わっていません(§8 の課題 4)。

7. 落とし穴と運用知見

落とし穴このリポジトリの対策 / 教訓
flaky(たまに落ちる)最大要因は「環境の共有」と「時間待ち」。対策 = 使い捨て DB・専用ポート(環境の独立)+ 自動待機の expect(時間でなく条件で待つ)+ Date.now ユニーク化(データの独立)
失敗の原因調査が難しいretries: 1 + trace: "on-first-retry": 初回失敗の再試行時に全操作・DOM スナップショット・ネットワークが録画される。pnpm exec playwright show-trace <trace.zip> で時系列を再生できる
UI 文言変更でテストが壊れるアクセシブル名ベースのセレクタは文言に結合する。これは「ユーザーに見える仕様が変わったらテストも変わるべき」という意図的な選択。無関係な壊れ方を避けたい要素だけ testid に逃がす。件数など可変の値を含む文言はそもそも文言で判定しない(§4.2、M29-01)
テストが遅くなるUI 操作は関心の中心だけに絞り、fixture・検証は API 直行(§5.3)。E2E の本数自体を絞る(下層テストで保証済みのことを繰り返さない)。フロントは dev サーバでなくビルド + preview で配る(§2 の note。実測で約 4 割短縮)
設定ファイルの多重評価config はワーカーでも再ロードされる → 副作用(DB 破棄)をトップレベルに書かない(§2 の warn)
絞り込み実行で UI spec が全滅pnpm exec playwright test の直叩きは PW_EXECUTABLE_PATH が渡らない。必ず make e2e-only P= を使う(§2.2)。全数実行では起きないため気づきにくい
「直列のつもり」のファイル間並列干渉fullyParallel: false はファイル内しか直列化しない → workers: 1 に固定 + 検出器 spec(aa-interference-probe 2 本)が設定を守る(§2 の note)。後片付けを足しても直らない——並行実行中は「まだ消していない時間」が必ず在る(E-232)
環境の既定値(既定キャラ等)への暗黙依存E2E 専用 config で dev 設定と縁を切り、キャラが要る spec は support/character.ts で自分から明示する(§5.6)。「初期表示は ryu」の仮定は、設定を変えた環境でだけ落ちた
uncheck() が「正しくガードされた」チェックボックスで落ちるcheck()/uncheck() は「押した結果 state が変わること」を前提の API。変わらないのが正解(確認ダイアログを挟むガード等)の検証では素の click() で押し、変わらないことを自前の expect で確かめる(m27-02b:237-241 のコメントに実例)
ドキュメントの陳腐化testid-convention の旧ポート記述(§4 の warn)。実装(config.ts)を正とし、気づいたら設計書側の追随を開発フローに乗せる
