Flask(Jinja2)や Spring Boot(Thymeleaf)のサーバーレンダリングに慣れていると、React の何が根本的に違うのかが最初の壁になります。このページはまず発想の違いを押さえてから、このリポジトリのタグ機能・コンボ機能の実コードで文法と仕組みを説明します。

1. 発想の転換: 「画面を組み立てる」から「状態を宣言する」へ

Jinja2 / Thymeleaf(サーバーレンダリング)React(このアプリ)
HTML を作る場所サーバー。リクエストごとにテンプレートへ値を流し込むブラウザ。サーバーは JSON しか返さない
画面の更新ページ全体を再リクエスト(またはフォーム POST → リダイレクト)状態(state)が変わると、変わった部分だけ React が再描画
プログラマが書くもの「この操作のときに DOM をこう書き換える」(jQuery 的)または全再描画「状態が X のとき画面はこうあるべき」という宣言。書き換え手順は書かない
データの持ち主常にサーバー(セッション・DB)UI 状態はブラウザ内(useState)、サーバー由来データはキャッシュ(TanStack Query)

実例で見ます。タグ一覧画面の描画部分は「ロード中なら…、エラーなら…、データがあれば…」という状態→見た目の対応表そのものです:

web/src/features/tag/components/TagManagementPage.tsx:94-129(抜粋)
{tagsQuery.isLoading && (
  <p className="text-sm text-slate-500">{t("tag.management.loading")}</p>
)}
{tagsQuery.isError && (
  <p className="text-sm text-red-600">{t("tag.management.loadError")}</p>

{tagsQuery.data && (
  <>
    // …検索欄と件数表示(M24-02 で追加)…
    <TagListTable

      onEdit={handleEditClick}

「ロードが終わったらスピナーを消してテーブルを挿入する」という手順はどこにも書いてありません。tagsQuery の中身が変わるたびに React がこの関数を再実行し、宣言と現実の DOM の差分だけを適用します。再実行されても壊れない純粋な「状態→画面」関数を書く、というのが React の中心思想です。

2. 関数コンポーネントと JSX

React のコンポーネントは「props(引数)を受け取り JSX を返す関数」です。JSX は JavaScript の中に HTML 風の構文を書ける拡張で、ビルド時(Vite)に関数呼び出しへ変換されます。

web/src/pages/TagManagementPageRoute.tsx(全 13 行)
import Header from "@/components/Header";
import { TagManagementPage } from "@/features/tag/components/TagManagementPage";

export default function TagManagementPageRoute() {   // コンポーネント = PascalCase の関数
  return (
    <main className="min-h-screen bg-slate-50 text-slate-900">
      <Header />                                     // 大文字始まり = コンポーネントの呼び出し
      <div className="max-w-7xl mx-auto px-4 py-6">
        <TagManagementPage />
      </div>
    </main>
  );
}

JSX の読み方の要点:

  • className は HTML の class(JS の予約語を避けるため)。値の min-h-screen bg-slate-50 … は Tailwind CSS のユーティリティクラスで、CSS ファイルを書かずにスタイルをクラス名で指定する流儀(読み方はshadcn/Tailwind ガイドで詳説)
  • {...} の中は生の JavaScript 式。{tagsQuery.data && (...)} は「左が truthy なら右を描画」という条件描画イディオム
  • @/ は web/src/ を指すパスエイリアス(Vite 設定)。相対パス地獄の回避策
  • タグの大文字/小文字に意味がある: <main> は素の HTML 要素、<Header /> は自作コンポーネント

4. useState — 再レンダリングの引き金

web/src/features/tag/components/TagManagementPage.tsx:25-37
const [formOpen, setFormOpen] = useState(false);          // [現在値, 更新関数] のペア
const [editingTag, setEditingTag] = useState<Tag | null>(null);
const [deletingTag, setDeletingTag] = useState<Tag | null>(null);

const handleCreateClick = () => {
  setEditingTag(null);     // 「編集対象なし」= 新規作成モード
  setFormOpen(true);       // ← これが再レンダリングを起こし、ダイアログが現れる
};

const handleEditClick = (tag: Tag) => {
  setEditingTag(tag);      // この tag がダイアログの初期値になる
  setFormOpen(true);
};

重要な性質: formOpen = true のような直接代入は禁止です。必ず setFormOpen() を通します。React は「set 関数が呼ばれた」ことを検知してコンポーネント関数を再実行(再レンダリング)するので、変数を直接書き換えても画面には何も起きません。

Flask / Spring 経験者向け サーバーレンダリングでは「新規作成画面」と「編集画面」は別 URL・別リクエストになりがちですが、ここでは editingTag が null か否かという状態の違いだけで同じダイアログが 2 つのモードを演じます。URL 遷移ではなく状態遷移で画面が変わるのが SPA です。

5. useEffect — 「描画の後にやる副作用」の登録

コンポーネント関数は純粋な「状態→JSX」変換であるべきで、描画以外の仕事(タイマー、購読、そして「props の変化に応じた状態の同期」)は useEffect に隔離します。タグフォームの「ダイアログが開いた瞬間に、対象タグの値でフォームをリセットする」処理:

web/src/features/tag/hooks/useTagFormDialog.ts:43-51
useEffect(() => {
  if (open) {
    form.reset({
      name: tag?.name ?? "",                       // ?. = null 安全アクセス、?? = null 合体
      category: tag?.category ?? "",
      color: tag ? (tag.color ?? "") : DEFAULT_TAG_COLOR,  // 新規は既定色、編集は元の色
    });
  }
}, [open, tag, form]);                             // 依存配列: これらが変わった描画後にだけ実行

第 2 引数の依存配列が useEffect の肝です。「配列内の値が前回描画から変わっていたら、描画完了後にこの関数を実行する」という契約で、ここでは「open が false→true に変わった(ダイアログが開いた)」タイミングを捉えています。tag?.name ?? "" は「tag が null でなければ name、それも無ければ ""」という TypeScript の null 安全イディオムで、頻出します。

6. カスタムフック — ロジックを部品化する仕組み

use で始まる関数を自作すると、useState/useEffect を含むロジックの塊を再利用可能な部品にできます。このリポジトリの規約では「見た目(components/)」と「ロジック(hooks/)」を分離するのにカスタムフックを使っています。

web/src/features/tag/hooks/useTagManagement.ts(全 33 行)
export function useTagManagement() {
  const queryClient = useQueryClient();

  const tagsQuery = useQuery({
    queryKey: queryKeys.tags.list(true),             // = ["tags", { include_usage: true }](後述 §7)
    queryFn: () => tagApi.list({ includeUsage: true }),
  });

  const createMutation = useMutation({
    mutationFn: (input: CreateTagInput) => tagApi.create(input),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: queryKeys.tags.all() }),
  });
  // updateMutation / deleteMutation も同型 …

  return { tagsQuery, createMutation, updateMutation, deleteMutation };
}

コンポーネント側は const { tagsQuery, createMutation, ... } = useTagManagement(); と 1 行書くだけで「タグ一覧の取得 + 3 種の更新操作」一式を手に入れます(TagManagementPage.tsx:17-18)。テストでもフック単体を renderHook で検証できます(タグのテスト参照)。

2026-09 追記: 「サーバーアクセス以外」の共通フック化の実例 — useListboxKeyNav カスタムフックは useQuery を包むためだけのものではありません。M27-02a では、検索付きセレクトとタグ入力欄の 2 か所に同じ「候補リスト(role="listbox")を ↑↓ キーで巡回する」操作が必要になり、コピーではなく共通フック web/src/hooks/useListboxKeyNav.ts(全 59 行)へ実体を 1 本化しました。設計が教材的です: useState を一切持たず、「今どの候補にいるか」を state に持つ代わりに実 DOM のフォーカス位置をそのまま現在地として使います([role="option"] の要素列から document.activeElement を探し、次の要素へ focus() する)。state を持たないので、検索で候補が絞り込まれても位置合わせの同期処理が要りません。「状態を持たないで済むなら持たない」の好例です。

7. TanStack Query — 「サーバー状態」という第 3 の概念

ここがサーバーレンダリング経験者にとって一番新しい概念です。React の useState は「UI の状態」を持ちますが、タグ一覧のようなサーバー由来のデータは性質が違います: 自分だけが真実を持っているわけではなく、古くなるし、取得は失敗するし、複数画面で共有されます。TanStack Query はこれを「キー付きキャッシュ」として管理するライブラリです。

7.1 useQuery — 読み取り

  • queryKey: queryKeys.tags.list(true)(実体は ["tags", { include_usage: true }])— キャッシュの住所。キーが同じなら画面が違っても同じキャッシュを共有します
  • queryFn — 実際の取得処理(fetch)。TanStack Query が「いつ呼ぶか」を管理する
  • 戻り値の isLoading / isError / data が §1 で見た宣言的描画の材料になる

コンボ一覧ではキーにフィルタ条件オブジェクトを丸ごと入れています:

web/src/features/combo/api.ts:94-103
export function useCombos(filter: ComboListFilter) {
  return useQuery({
    queryKey: queryKeys.combos.list(filter),  // = ["combos", filter]。フィルタが変わる = 別のキー = 自動で再取得
    queryFn: () => {
      const qs = buildQuery(filter);
      const path = qs ? `/api/combos?${qs}` : "/api/combos";
      return fetchJSON<ComboListResponse>(path);
    },
  });
}

ユーザーがフィルタを変更すると filter オブジェクトが変わり、queryKey が変わり、TanStack Query が新しいキーのデータを自動で取りに行きます。「フィルタ変更時に再取得する」コードはどこにも書いてありません。キー設計 = 再取得戦略です。

7.2 useMutation + invalidateQueries — 書き込みと再同期

作成・更新・削除は useMutation で行い、成功時に invalidateQueries で関連キャッシュへ「古くなった」と印を付けます。印の付いたクエリは自動で再取得され、画面が最新化されます。

web/src/features/tag/hooks/useTagManagement.ts:15-18
const createMutation = useMutation({
  mutationFn: (input: CreateTagInput) => tagApi.create(input),   // POST /api/tags
  onSuccess: () => queryClient.invalidateQueries({ queryKey: queryKeys.tags.all() }),
  // queryKeys.tags.all() = ["tags"]。前方一致: ["tags", {include_usage:true}] などタグ系キャッシュ全部が無効化される
});
この 2 つ + キー設計で「画面が勝手に最新になる」 保存 → invalidate → 自動再取得 → 再レンダリング。このループがこのアプリ全域の更新パターンです。コンボの PUT ではさらに進んだキャッシュ操作(removeQueries で旧詳細を消し、setQueryData で新レスポンスを直接キャッシュに書く。combo/api.ts:231-247)も出てきます。

7.3 queryKey の集約 — 直書きをやめた理由(2026-09 追記)

上のコードで queryKey が配列リテラルではなく queryKeys.tags.list(true) のような関数呼び出しになっているのは、M24-08 で全キーを web/src/lib/query-keys.ts の queryKeys ファクトリへ集約したためです(2026-07 時点の本ガイド初版では直書きでした)。

なぜ集約するのか — 前方一致は「静かに」壊れる キーを書く側(useQuery)と無効化する側(invalidateQueries)は別ファイルに分かれます。配列リテラルの直書きだと、片方のキー構造だけ変えたときに前方一致が外れますが、例外は出ず「画面が更新されない」だけになります。着手前の実測では本番 58 件の invalidateQueries のうち 39 件が前方一致に依存していました。集約後は、正本の外で配列リテラルを書くと専用テスト(query-keys.convention.test.ts)が赤になり、「どの invalidate がどの query にちょうど当たるか」も実物の QueryClient を使うテスト(query-keys.invalidation.test.ts)で表として固定されています。「規約を散文で書く」より「規約をテストで機械化する」——このリポジトリの一貫した流儀です(web/CLAUDE.md §1.5)。
Flask / Spring 経験者向け サーバーレンダリングの「POST → リダイレクト → GET(PRG パターン)」に相当するのが「mutation → invalidate → refetch」です。ページ遷移なしで同じ整合性が得られる、と対応付けると腑に落ちやすいはずです。

8. TypeScript — JSON の形をコンパイル時に固定する

TypeScript は JavaScript に型を足した言語で、ビルド時に型検査してから型情報を消した JS を出力します。このリポジトリでは Go 側の JSON タグと TypeScript の interface を手動で対応させる運用です(コード生成はしていない)。

web/src/types/tag.ts:1-8 と internal/model/tag.go:50-57 の対応
export interface Tag {          // Go 側: type Tag struct {
  id: number;                   //   ID     int64  `json:"id"`
  userId: number;               //   UserID int64  `json:"userId"`   ← camelCase で一致
  name: string;
  category?: string;            //   Category *string `json:"category,omitempty"`
  color?: string;               //   ← Go の「*T + omitempty」 = TS の「?(省略可)」
  usageCount?: number;
}

言語仕様の対応関係:

GoTypeScript意味
*string + omitemptycategory?: stringキーが無いかもしれない(undefined)
*int(null を送る)damage?: number | nullunion 型。コンボ編集用 Combo(combo/types.ts:224-272)は「未入力」を null で表すためこちら
int64 / float64numberTS/JS に整数型はなく number のみ
[]model.TagTag[]配列
ジェネリクス Optional[T]fetchJSON<T>(path)型パラメータ。呼び出し側が「このレスポンスは T 型」と教える
TS の型は「ランタイムでは消える」 fetchJSON<Tag[]>("/api/tags") と書いても、実行時にレスポンスが本当に Tag[] かは検査されません(return res.json() as T はただの表明)。バックエンドと型がずれると実行時に静かに壊れます。だからこそ CLAUDE.md は「JSON タグ camelCase 統一」「列挙定数の両側同期」を規約で強制し、types.ts 冒頭コメント(combo/types.ts:1-7)で「フィールド追加時は全 interface に追加」と注意喚起しています。実行時にも検査したい入力(ユーザーのフォーム)には次節の zod を使います。

9. zod + react-hook-form — フォームの検証

zod は「実行時に値の形を検査できるスキーマ」ライブラリ、react-hook-form(RHF)はフォーム状態管理ライブラリです。タグフォームでの組み合わせ:

web/src/features/tag/hooks/useTagFormDialog.ts:16-24, 36-41
export function createTagFormSchema(t: Translate) {  // Translate = (key: string) => string
  return z.object({
    name: z.string().trim().min(1, t("tag.form.nameRequired")),  // VAL-T02 のフロント側
    category: z.string().optional(),
    color: z.string().regex(/^(#[0-9A-Fa-f]{6}|)$/, t("tag.form.colorFormat")),
  });
}

type TagFormValues = z.infer<ReturnType<typeof createTagFormSchema>>;  // スキーマから TS 型を逆算(二重定義しない)

// …フック本体…
const { t } = useTranslation();
const schema = useMemo(() => createTagFormSchema(t), [t]);  // t が変わらない限り同じスキーマを再利用
const form = useForm<TagFormValues>({
  resolver: zodResolver(schema),                     // RHF の検証エンジンとして zod を接続
  defaultValues: { name: "", category: "", color: "" },
});

z.infer が便利な点です: スキーマ(実行時検証)から型(コンパイル時検証)を導出するので、両者が絶対にずれません。Bean Validation のアノテーション + DTO クラスを 1 つの定義で済ませているイメージです。なお同じ検証(空名・重複)はサーバー側にも必ずあります(service.go の VAL-T01/T02)。フロントの検証は UX のため、サーバーの検証が防衛線という役割分担はサーバーレンダリング時代と同じです。

2026-09 追記: スキーマが定数からファクトリ関数になった理由 本ガイド初版(2026-07)ではスキーマは export const tagFormSchema = z.object({...}) というモジュールトップレベルの定数で、エラーメッセージは日本語リテラルでした。M24-07 で検証メッセージを i18n 化した際、ファクトリ関数 createTagFormSchema(t) に変わっています。定数のままだと文言が「モジュール読込時の言語」で焼き付き、言語切替後も旧言語のメッセージが残るためです。呼び手のフックが毎回 t を渡して組み立て、useMemo で再生成を抑えます。型導出も z.infer<ReturnType<typeof createTagFormSchema>> と 1 段挟む形になりました——「関数の戻り値の型」を取る ReturnType は TypeScript のユーティリティ型の代表格です。副次効果として、テストからは t に恒等関数を渡せばモック無しでスキーマを検証できます。

10. アプリの土台 — エントリポイントとルーティング

SPA の起動は「index.html の空 div に React をマウントする」ことから始まります。

web/src/main.tsx:17-48(抜粋)
const queryClient = new QueryClient({           // TanStack Query のキャッシュ本体(アプリで 1 個)
  defaultOptions: {
    queries: {
      // 401 は再試行しない——認証が要るという応答は繰り返しても変わらず、既定の 3 回再試行は空転(実測で約 7 秒)
      retry: (failureCount, error) => !isUnauthorizedError(error) && failureCount < 3,
    },
  },
});

ReactDOM.createRoot(rootElement).render(
  <React.StrictMode>
    <QueryClientProvider client={queryClient}>  // 配下の全コンポーネントに queryClient を供給
      <BrowserRouter>                            // URL とコンポーネントの対応付けを有効化
        <AuthGate>                               // 入場(認証)を通ってから内側を描画
          <CurrentUserProvider>                  // 現在の利用者を配下へ供給(利用者一覧 API は保護対象)
            <App />
          </CurrentUserProvider>
        </AuthGate>
      </BrowserRouter>
    </QueryClientProvider>
  </React.StrictMode>,
);

この入れ子は React の Context(コンテキスト)という仕組みで、「Provider の内側ならどこでも useQueryClient() / useNavigate() が使える」ようにするものです。Spring の ApplicationContext に少し似た「アプリ全域サービスの供給層」と捉えてください。入れ子の順序に意味がある点も教材的です: AuthGate を App の外側に置くのは、App が先頭で保護対象の API を呼ぶため(認証前に内側を描画すると読めない問い合わせが飛ぶ)、CurrentUserProvider がさらに内側なのは利用者一覧そのものが保護対象だからです(main.tsx:36-39 のコメント参照)。

  <Route path="*" element={<Navigate to="/" replace />} />  // 未知 URL はホームへ
</Routes>

Flask の @app.route("/combos/<int:id>") のクライアント版です。ただしこの「遷移」はサーバーに HTML を取りに行きません。URL が変わるとマッチするコンポーネントが差し替わるだけで、データは各ページのフックが JSON API から取得します。だからこそバックエンドの SPA 配信(internal/api/static/handler.go:53-83。embed ビルド時に cmd/tacpendium/main.go:542-547 で登録)は「未知パスは全部 index.html を返す」フォールバックが必要になります — /tags/manage を直接開いてもサーバーにそんなファイルはなく、index.html + React Router が解決するからです。

11. i18n — 文字列は t() を通す

画面のあちこちにある const { t } = useTranslation(); と {t("common.loading")} は react-i18next による国際化です。初期化は web/src/lib/i18n.ts、文言は翻訳リソース(web/src/locales/ja.json / en.json)にキーで登録され、コンポーネントはキーで参照します。t("comboList.registeredCount", { count: ... }) のように変数埋め込みもできます。テストではこれをモックして「キーがそのまま返る」ようにする例が出てきます(コンボのテスト参照)。

2026-09 追記: 用語統一もテストで守る M29-01 で画面の用語が統一され、未参照キーが削除されました。興味深いのはその守り方で、web/src/locales/ には翻訳 JSON と並んで retired-words.test.ts(廃止した語の再混入を検出)や forbidden-words.test.ts、no-japanese-in-en.test.ts(英語リソースへの日本語混入を検出)といったテストが同居しています。§7.3 の queryKeys と同じく、「表記ルールを散文で書く」のではなく「破ったらテストが赤くなる」形で機械化する流儀です。

12. まとめ — 読むためのチェックリスト

見かけたらこう読む
export function Xxx() { return <...> }コンポーネント。「状態→画面」の純関数。状態が変わるたび再実行される
const [x, setX] = useState(...)UI 状態。setX が再レンダリングの引き金。直接代入は無効
useEffect(() => {...}, [deps])deps が変わった描画後に実行される副作用
useXxx()(自作)カスタムフック。hooks/ にあるロジック部品。中を見れば useQuery 等の組み合わせ
useQuery({ queryKey, queryFn })サーバーデータの購読。キーがキャッシュの住所、キー変更 = 自動再取得。キーは lib/query-keys.ts の queryKeys ファクトリで作る(直書き禁止・§7.3)
useMutation + invalidateQueries書き込み + 関連キャッシュの無効化(= 画面の自動最新化)

z.object({...}) / z.infer実行時スキーマとそこから導出した型。フォーム検証は zodResolver で RHF に接続
{cond && <X />} / {cond ? a : b}条件描画。if 文の代わりに式で書く
