ゲーム更新影響判定 ウォークスルー
— 「保存せず導出する」機能を 1 本通しで読む

この資料は、2026 年 8〜9 月(M28-02a / M28-02c)に実装されたゲーム更新影響判定(FR702)を、DB スキーマ → SQL → Go → React → E2E まで通しで解説するものです。タグ管理・コンボ CRUD の両ウォークスルーを読み終えた人向けの「応用編」で、CRUD では出てこなかった実戦的な設計判断が凝縮されています:

  • 導出(derived)か保存(materialized)か — 「影響コンボ」という概念をテーブルに持たない決断
  • ソート可能なバージョン文字列の設計 — 固定幅ゼロ埋めだけで比較関数が 1 行になる
  • 「静かに壊れる」制約を DB の CHECK で塞ぐ — プロジェクト方針の意図的例外
  • SQL 述語の一本化を「ソースを grep するテスト」で強制する
  • 失敗を 0 件として扱わない UI、複数利用者(LAN)を意識した抑止の分水嶺
この機能が解く問題 SF6 は年に数回バランス調整が入り、技のダメージやフレームが変わります。すると登録済みコンボの一部は「もう繋がらないかもしれない」状態になりますが、どのコンボが該当するか手で調べるのは大変です。この機能は「あなたのコンボのうち、使っている技がアップデートで変わったものはこれです」と一覧で見せ、利用者が 1 件ずつ確認して「問題なし」を付けていける仕組みです。重要な思想として、アプリは「影響可能性あり」までしか言いません(FR307)。実際に繋がるかどうかの断定はせず、検証は利用者に委ねます。

1. 機能の全体像 — 4 つの画面部品と 2 つの API

部品場所役割
告知バナーweb/src/features/game-update/GameUpdateBanner.tsx(ホーム + コンボ一覧の 2 か所にマウント)「影響の可能性があるコンボが N 件」を知らせ、専用画面への導線と「次の更新まで延期」を出す
一覧のボタンweb/src/features/game-update/AffectedCombosButton.tsxコンボ一覧に常設される専用画面への入口。延期しても消えない(§6.2)
専用画面web/src/pages/GameUpdateCombosPage.tsx(/game-update/combos)影響コンボをキャラ別に一覧し、「どの技が変わったか」を出し、行ごとに「問題なし」/「削除」できる
詳細画面の基準行web/src/features/combo/components/ComboDetailMetadata.tsxコンボ詳細に「前提バージョン」と、影響時は変わった技の列挙 + 「問題なし」ボタンを出す
告知 APIGET /api/notices/game-update / POST …/postpone(internal/api/notice/game_update.go)現在版・影響件数・延期状態を 1 本で返す / バナーを次の版まで延期する
確認 APIPOST /api/combos/:id/acknowledge-version(internal/api/combo/handler.go:538)そのコンボの基準版を現在版へ進める(=「見た」の記録)

データの流れを 1 周すると次のようになります。

  1. 開発者がゲーム更新を反映するマイグレーションを配布し、変わった技の moves.last_changed_game_version と games.current_data_version を書く
  2. アプリ起動 → フロントが GET /api/notices/game-update を叩き、影響件数(全キャラ合計)と現在版を得る
  3. 件数が 1 以上ならバナーと一覧ボタンが出る → 利用者が専用画面 /game-update/combos へ
  4. 専用画面は GET /api/combos?affected_by_game_update=true で影響コンボを取り、「変わった技」列付きで表示
  5. 利用者がコンボを確認 → 「問題なし」ボタン → POST /api/combos/:id/acknowledge-version
  6. サーバがそのコンボの baseline_version を現在版へ進める → 判定が false になり、一覧から消えて件数が減る

2. データモデル — 列は 3 本だけ、「影響コンボ」テーブルは無い

2.1 保存せず、導出する

この機能の最重要の設計判断は、マイグレーションファイルの冒頭コメントに書いてあります。

migrations/000104_add_game_update_tracking.up.sql(冒頭コメント抜粋)
-- 足す列は 3 本。
--   1. moves.last_changed_game_version   … その move が最後に変わったゲームバージョン(マーカー)
--   2. combos.baseline_version           … そのコンボが前提としているゲームバージョン(基準)
--   3. games.current_data_version        … 現在のデータバージョン(基準へ書く値の出どころ)
--
-- ★★影響コンボは保存しない。導出する(checklist §5.1 確定事項 3)。
--   ⇒ 本マイグレは中間表を作らない。判定は combo_steps 経由の EXISTS で毎回導出する。

「影響コンボ」はマーカーと基準の比較結果にすぎないので、比較式さえあればいつでも計算できます。もし affected_combos のような中間テーブルに保存すると、コンボの編集・技の変更・確認操作のたびに同期処理が要り、同期漏れ = 「本当は影響があるのに出ない」という最悪の壊れ方をします。導出なら定義上ズレようがありません。

Flask / Spring 経験者向け: 「非正規化するか」の判断と同じ RDB 設計で「集計列を持つか、毎回 COUNT するか」を悩むのと同型です。原則は導出できるものは導出する(Single Source of Truth)で、パフォーマンスが立証されてから初めて materialize を検討します。このアプリは個人用 SQLite でコンボ数は高々数百件なので、EXISTS サブクエリの毎回評価で十分という判断です。

2.2 3 本目の列が要る理由 — MAX() で代用してはいけない

「現在版」は MAX(moves.last_changed_game_version) で求まりそうに見えますが、マイグレーションのコメントが明確に否定しています: 技を 1 本も変えないアップデート(技以外の入力ミス訂正、機能追加で列が増えただけ、など)では MAX が動かず、「版が上がった」ことを表現できません。だから games テーブル(1 行だけ、コード 'sf6')に current_data_version を持ち、これが基準へ書く値の唯一の出どころになります。

2.3 バージョン文字列 `YYYY.MM.DD.NN` — 固定幅ゼロ埋めが全てを支える

バージョンは 2026.08.03.01 のような TEXT です。この形式の要は「全フィールドが固定幅のゼロ埋め」であること。それだけで辞書順 = 時系列順になり、順序用の数値列も専用の比較ロジックも不要になります。アプリ側の正本パッケージがこの割り切りを 1 行で表現しています:

internal/gameversion/gameversion.go:40-46
// Newer は a が b より新しいかを返す。
//
// ★★書式が正しい限り、比較は単なる文字列比較でよい(固定幅ゼロ埋めのため)。
// 専用の比較関数を置くのは、呼び出し側が「なぜ文字列比較でよいのか」を
// 毎回考えずに済むようにするためである。SQL 側も同じ理由で単純な `>` を使う。
func Newer(a, b string) bool { return a > b }

中身は a > b だけなのに関数として存在するのは、「なぜ文字列比較でよいのか」という知識の置き場を作るためです。SQL 側でも同じ理由で素の > 比較が使えます(§3)。

「静かに壊れる」から、入口を全部塞ぐ — 初の DB CHECK 制約

この設計の弱点は、2026.8.3.1 のようなゼロ埋め漏れが 1 個入るだけで順序が壊れ、しかもエラーにならないことです。テストも lint も型検査も緑のまま、判定だけが静かに狂います。そこで「入口を全部塞ぐ」方針が採られました:

migrations/000104_add_game_update_tracking.up.sql(CHECK 制約の抜粋)
ALTER TABLE moves ADD COLUMN last_changed_game_version TEXT
    CHECK (
        last_changed_game_version IS NULL OR (
            last_changed_game_version GLOB '[0-9][0-9][0-9][0-9].[0-9][0-9].[0-9][0-9].[0-9][0-9]'
            AND CAST(substr(last_changed_game_version, 6, 2) AS INTEGER) BETWEEN 1 AND 12
            AND CAST(substr(last_changed_game_version, 9, 2) AS INTEGER) BETWEEN 1 AND 31
        )
    );
プロジェクト方針の「意図的な例外」がコメントで宣言されている このリポジトリは元来「CHECK は DB 側に付けず、アプリ層で制約する」方針でした(DES-003 §3.4)。この 3 列はスキーマ初の CHECK 制約で、マイグレーションのコメントが「意図的な例外であり、指示書が DB 側の CHECK を名指しで要求している」と例外であることを明言しています。理由は上記の「静かに壊れる」性質です — アプリ層のバリデーション(internal/gameversion)だけでは生 SQL の UPDATE を塞げません。方針からの逸脱は逸脱である旨と理由をその場に書き残す、という規約運用の見本です。なお SQLite の GLOB は正規表現を持たないため、書式は GLOB、月日の範囲は substr + CAST という合わせ技になっています。入口は他にアプリ側の gameversion.Validate(gameversion.go:34-39)と seedgen の値域検証があり、3 か所すべてが同じ形式を守る多重防御です。

2.4 NULL の意味論 — 2 列で「安全側」の向きが逆

面白いのは、同じ NULL でも 2 列で意味と扱いが非対称なことです:

列NULL の意味判定での扱い
moves.last_changed_game_version(マーカー)「まだ一度も変わっていない」という既知の状態(初回公開より前の変更は存在しないものと扱う)影響なし側に落ちる
combos.baseline_version(基準)「いつ登録されたか不明」(通常は起きない。CSV 直編集などの防御)影響可能性あり側に倒す(安全側)

「安全側に倒す」の向きを列ごとに考え分けているのがポイントです。マーカー側の NULL を「不明だから影響あり」と扱うと、初期データの全技が NULL なので全コンボが影響ありになってしまいます。既存コンボの基準は、マイグレーション内の UPDATE で「列を足した時点の最新版」に埋められ(ゴミ箱の行も対象 — 復元された瞬間に NULL = 影響あり側へ落ちないように)、初回リリース時の影響件数は 0 件から始まります。

3. 判定式は 1 本 — 「式の書き写し」をテストで禁止する

3.1 正本の述語と 3 つの消費者

「このコンボは影響可能性があるか」の判定 SQL は、リポジトリ層にただ 1 つの定数として存在します:

internal/repository/combo/repository.go:409-423
// 「1 本の move が、そのコンボの基準より後に変わったか」— これが唯一の正本
const affectedMoveCondSQL = `m.last_changed_game_version IS NOT NULL
          AND (combos.baseline_version IS NULL
               OR m.last_changed_game_version > combos.baseline_version)`

// 真偽判定(WHERE 用): コンボの steps に 1 本でも該当 move があるか
const affectedByGameUpdateCondSQL = `EXISTS (
        SELECT 1 FROM combo_steps cs
        JOIN moves m ON m.id = cs.move_id
        WHERE cs.combo_id = combos.id
          AND ` + affectedMoveCondSQL + `
    )`

// SELECT の派生列用: 同じ式に別名を付けただけ
const affectedByGameUpdateExprSQL = affectedByGameUpdateCondSQL + ` AS affected_by_game_update`

この式の消費者は 3 つあります — (1) 一覧・詳細の SELECT 派生列(全コンボ応答に affectedByGameUpdate として載る)、(2) 絞り込みと件数の WHERE 句、(3) 「どの技が変わったか」の列挙クエリ(repository.go:1167-)。3 つとも文字列連結で affectedMoveCondSQL を埋め込んでいて、式の中身はどこにも書き写されていません。

internal/repository/combo/repository.go:1167-1177(変わった技の列挙)
var listAffectedMovesSQLTemplate = `
SELECT DISTINCT cs.combo_id, m.id, m.code, pa.alias_text, m.last_changed_game_version
FROM combo_steps cs
JOIN moves m ON m.id = cs.move_id
JOIN combos ON combos.id = cs.combo_id           -- 述語が combos.baseline_version を読むため join
LEFT JOIN preset_aliases pa ON ...               -- 表示名の解決(引けなければ code へフォールバック)
WHERE cs.combo_id IN (%s)
  AND ` + affectedMoveCondSQL + `               -- ここも同じ 1 本
ORDER BY cs.combo_id, m.id`
「真偽の正本は 1 本」— len(AffectedMoves) で判定しない モデル側のコメント(internal/model/combo.go:275-284)は「AffectedByGameUpdate(真偽)から列挙を導くのであって、逆ではない。len(AffectedMoves) > 0 で影響の有無を判定しないこと(真偽が 2 か所で表せてしまう)」と釘を刺しています。フロント側(ComboDetailMetadata.tsx:141)にも同じ注意コメントがあります。同じ情報を 2 通りで表せる状態を作ると、いつか片方だけ変わって食い違う — この「正本は 1 本」の徹底が本機能の背骨です。

3.2 ソースコードを grep するテスト

「式を書き写さない」という規約は、ふつうはコメントで祈るしかありません。このリポジトリはそれをテストで機械化しました:

internal/repository/combo/m28_02c_predicate_source_test.go(要旨)
// リポジトリ配下の全 .go ソースを走査し、
// 「last_changed_game_version と baseline_version の両方に言及する文字列リテラル」を数える。
// ⇒ ヒットは affectedMoveCondSQL の 1 か所だけでなければならない。
if hits[0].value != affectedMoveCondSQL {
    t.Fatalf("★唯一の判定式が affectedMoveCondSQL ではない: %s:%d", hits[0].file, hits[0].line)
}
// さらに EXISTS / SELECT 派生列 / affectedMoves 列挙が正本を使っていることも検査
if !strings.Contains(affectedByGameUpdateCondSQL, affectedMoveCondSQL) { t.Error(...) }

Go の標準ライブラリ(go/parser 系または単純なファイル走査)でテストコードが自分のパッケージのソースを読み、判定式らしき文字列リテラルが 2 か所以上に現れたら赤にする、という発想です。将来の開発者(あるいは AI)が知らずに式を書き写すと、その場でテストが「足すなら affectedMoveCondSQL を参照して組むこと」と教えてくれます。React/TS プライマーの queryKeys 規約テストと同じ「規約を散文で書くより、規約をテストで機械化する」流儀です。

3.3 件数と一覧が同じ WHERE を通る配線

バナーの「N 件」は告知 API が返しますが、その COUNT は専用画面の一覧とは別のクエリです。別のクエリが別の述語を持ってしまうと「バナーは 3 件と言うのに画面には 2 行」という不整合が起きえます。main.go の DI 配線がこれを構造的に防いでいます:

cmd/tacpendium/main.go:515-532(抜粋)
// ★件数は comborepo.Count を通す —— List と同じ WHERE 組み立てを共有するため、
//   「件数」と「専用画面に出る行」が別々の述語で決まる状態を作れない。
noticehandler.RegisterGameUpdateRoutes(apiGroup, noticehandler.NewGameUpdateHandler(
    filepath.Dir(dbPath),
    func(c echo.Context) (int, error) {
        affected := true
        return repo.Count(c.Request().Context(), comborepo.ListFilter{
            AffectedByGameUpdate: &affected,     // List と同じフィルタ構造体 → 同じ WHERE ビルダ
        })
    },
    func(c echo.Context) (string, error) {
        return gameRepo.CurrentDataVersion(c.Request().Context(), gamerepo.CodeSF6)
    },
))

Count と List が同じ ListFilter 構造体から WHERE を組み立てるので、フィルタ条件を将来変えても両者は一緒に変わります。なお告知応答の設計コメント(game_update.go:23-25)は「GET /api/combos?...&limit=1 の count で代用できない」理由(ページ内件数しか返らない・limit が丸められる)まで書き残しています。

4. 基準(baseline)のライフサイクル — 「書き忘れられない」構造にする

4.1 登録時: サービス層ではなく INSERT 文で入れる

新規コンボの baseline_version には「登録時点の現在版」が入ります。これをどの層で書くか、が設計判断です:

internal/repository/combo/repository.go:455-470(insertComboSQL のコメント)
// ★★baseline_version(FR702 の基準)は COALESCE で入れる —— 呼び出し側が nil を渡せば
// 「その時点の games.current_data_version」が構造的に入る(M28-02a)。
//
// ★★サービス層で埋める形にしなかった理由は先例である。
//   Materialize が ValidateComboForCreate を通さないため、必須 4 欄が空のままの
//   本登録コンボが在りえた(followup: materialize-bypasses-required-fields)。
//   ⇒「登録経路が N 本ある」ものを呼び出し側の責務にすると、経路が 1 本増えたときに
//     静かに抜ける。基準が抜けると そのコンボは永久に「影響可能性あり」側へ出続ける。

コンボの登録経路は通常の Create のほかに「セットプレイからの実体化(Materialize)」「CSV インポート」など複数あります。「各経路が忘れず埋める」ことを期待する設計は、経路が増えた瞬間に静かに壊れた実績(先例 followup)があるので、INSERT 文自体の COALESCE((SELECT current_data_version FROM games ...)) で「どの経路から来ても構造的に入る」形にしました。過去の失敗を followup 台帳に記録し、次の設計判断の根拠として引用する — このプロジェクトの運用がコードコメントに現れている好例です。

4.2 確認時: 楽観的排他の version は上げず、updated_at だけ上げる

「問題なし」ボタンの実体 AcknowledgeGameVersion は、基準を現在版へ進める 1 本の UPDATE です:

internal/repository/combo/repository.go:1405-1421(抜粋)
const advanceBaselineVersionSQL = `
UPDATE combos
SET baseline_version = (SELECT current_data_version FROM games WHERE code = ?),
    updated_at = datetime('now')
WHERE id = ? AND deleted_at IS NULL`

短い SQL ですが、コメントに 3 つの判断が詰まっています:

  • 版数はサブクエリで games から読む — API はリクエスト本文を取りません(handler 側も同様)。クライアントが任意の版を送れる形にすると「任意の版へ確認したことにできる」穴になるため、サーバ側の現在値だけが書かれます
  • version(楽観的排他の列)は上げない — 基準の前進は「コンボ内容の変更」ではなく「利用者が見たことの記録」なので、他端末で編集中の人の保存を競合エラーにしない
  • updated_at は進める — 「いつ確認したか」の痕跡はここにしか残らないし、更新日時順の一覧で最近触ったものが上に来るのは自然、という理由まで書いてある
Spring 経験者向け: @Version を触らない更新 JPA の @Version 付きエンティティを普通に保存すると必ず version が上がりますが、ここでは「この UPDATE は楽観ロックの版を意図的に上げない」という細かい制御をしています。ORM 越しでは書きにくい判断で、生 SQL だからこそ「どの列を動かし、どの列を動かさないか」を 1 行ずつ選べる、という このリポジトリの ORM 不使用方針の利点が出た場面です。

サービス層(internal/service/combo/service.go:1103-1124)はこの UPDATE をトランザクションで包み、コミット後に FindByID で読み直して返します。判定(affected_by_game_update)は導出値なので、「進めた結果 false になった」ことを応答でクライアントに返せるようにするためです。ハンドラ(internal/api/combo/handler.go:538-574)はさらに Get を通し直して、タグを利用者スコープで載せた通常形の応答にします。

5. API 層 — サービス層の無い薄い経路と、その代償の扱い

告知 API(internal/api/notice/game_update.go)にはサービス層がありません。件数と現在版は、main.go で注入された 2 つのクロージャ(§3.3)がリポジトリを直接呼びます。読むだけの薄い経路にレイヤーをフルセットで用意しない、という割り切りです。ただし薄くした代償への手当てがきちんとあります:

    }
    ...

通常の経路ではサービス層が SQLite の busy エラーをセンチネル(ErrDatabaseBusy)へ翻訳してくれますが、この経路には翻訳者がいません。「包み忘れると 503 の契約が黙って到達不能になる — 実装は 500 を返し続けるのに、センチネルを直接注入するテストは緑のまま通る」とコメントが警告し、生エラー(dbinfra.IsBusy)とセンチネルの両方を見る 2 本立てにしています。「テストが緑でも、テストの入力が本番の入力と違えば意味がない」というテスト解説の教訓の実例です。

応答設計にも 2 つ学びどころがあります:

  • 「無ければ 204」にしない — 返しているのは有無ではなく「件数 + 現在版 + 延期状態」の 3 情報なので、常に 200 で本文を返します。REST の作法(204 No Content)から外れるときは、外れる理由をコメントで宣言(game_update.go:18-21)
  • POST /postpone であって /ack ではない — 「永久に既読」と「次の版まで延期」は意味が違うから、と URL の語選びの理由まで書いてあります。延期の印はデータディレクトリ直下のファイル(移行告知と同じ仕組み)に保存され、記録された版 == 現在版のときだけ有効。版が上がれば自動で抑止が外れます

6. フロントエンド — 1 本のクエリを全部品が共有し、失敗を握りつぶさない

6.1 useGameUpdateNotice — 出どころを 1 つに保つ

web/src/features/game-update/api.ts:18-26
export function useGameUpdateNotice() {
  return useQuery({
    queryKey: queryKeys.notices.gameUpdate(),      // = ["notices", "game-update"]
    queryFn: () => fetchJSON<GameUpdateNotice>(NOTICE_PATH),
    retry: false,     // 失敗を失敗として早く出す(告知は再試行で粘るものではない)
  });
}

バナー(2 か所)・一覧ボタン・専用画面の見出し件数が、すべてこの 1 本のフックを呼びます。queryKey が同じなので実際の HTTP リクエストは 1 回で、キャッシュを 4 部品が共有します(TanStack Query の「キーが同じなら画面が違っても同じキャッシュ」の実戦形)。「問題なし」や延期のミューテーションは invalidateQueries でこのキーを無効化し、全部品の件数が一斉に更新されます。

「取得失敗」を「0 件」として扱わない バナーもボタンも、isError のときはエラー表示 + 再試行リンクを出します(GameUpdateBanner.tsx:33-50)。素朴に書くと data?.affectedCount ?? 0 のように失敗を 0 件へ潰しがちですが、それは「影響があるのに何も出ない」= この機能の存在意義が黙って消える壊れ方です。コメントは過去の同型バグ(セットプレイ件数が取得失敗を隠していた followup)を「先例の轍」として名指ししています。optional chaining + デフォルト値は「失敗の握りつぶし」になりうる — TypeScript で最も書きやすい形が最も危ない、という好例です。

6.2 延期の分水嶺 — バナーは消すが、入口は消さない

「次の更新まで延期」を押すと消えるのはバナーだけで、コンボ一覧のボタンは残ります。境界の理由が LAN 運用にあります:

web/src/features/game-update/AffectedCombosButton.tsx:11-12(コメント抜粋)
// ★★延期しても消えない —— 抑止するのはバナーだけである。LAN で 1 人が延期したら
//   他の利用者が入口を失う形にしない。⇒ ここが分水嶺である(CHANGE-162 §2.3)。

このアプリは LAN モードで複数人が同じサーバを使えます(利用者切替は X-User-Id)。延期の印はサーバ側のファイルに保存されるので全員に効きます — だからこそ「1 人の延期で全員の入口が消える」ことのないよう、消してよいもの(通知)と消してはいけないもの(導線)を切り分けています。なお延期を localStorage に持てば利用者ごとに独立しますが、あえてサーバ側にしたのは web/CLAUDE.md §1 のブラウザストレージ台帳へキーを増やさない(移行告知と同じ仕組みに乗せる)判断で、これもコメントに明記されています。

6.3 専用画面 — 既存の表を「表そのものとして」再利用する

GameUpdateCombosPage.tsx は、コンボ一覧の ComboTable をそのまま使い、専用画面のときだけ「変わった技」等の列を渡します。冒頭コメント(1-29 行)が設計の輪郭を宣言しています: 新しい一覧の仕組みを作らない / 全行が該当するのでバッジは置かない(冗長) / キャラは「見出し + 表」を縦に並べる / 取得失敗は失敗として出す。さらに:

  • 件数の正本は告知 API — 一覧クエリは limit=1000 で打ち切られうるので、「表示件数 < affectedCount」のときは打ち切りを明示します。「部分データを全部として見せない」という §6.1 と同族の原則です
  • 削除は一覧と同じ作法 — 確認ダイアログもミューテーションも既存のものを使い、「この画面だけ別の削除の作法」を持ち込みません

6.4 詳細画面 — 「不明」を「-」にしない

ComboDetailMetadata.tsx(129 行〜)は前提バージョンの行を常時出し、baselineVersion が無いときは「-」ではなく「不明」+ 影響可能性の印を出します。「-」は「該当なし(問題ない)」に見えてしまい、NULL = 安全側へ倒す §2.4 のセマンティクスと矛盾するからです。バックエンドの NULL の意味論が、フロントの表示語の選択にまで一貫して繋がっています。

7. テスト — debug ビルドタグの「書き込み口」で E2E の状態を作る

この機能の E2E には固有の難題があります: 「技がアップデートで変わった」状態は、通常の UI 操作では作れません(マイグレーション配布で起きる状態だから)。そこで debug ビルド専用の書き込み API が用意されました:

internal/api/debug/game_version.go:58-67(抜粋)/ routes.go:18
// FR702 の判定は moves.last_changed_game_version が非 NULL であることを要求するが、
// 通常運用でこれを書くのはマイグレーションだけ。E2E が状態を作るための debug 口。
`UPDATE moves SET last_changed_game_version = ? WHERE id = ?`
...
g.DELETE("/debug/notices/game-update", h.ClearGameUpdateNotice)   // 延期ファイルの掃除

internal/api/debug/ はコンボのテストで見たとおりビルドタグ debug のときだけ実体を持ち、本番ビルドでは no-op です。E2E スタックは debug ビルドで起動するので、spec は API で「技 X が版 Y で変わった」状態を仕込んでから UI を検証できます。

web/e2e/m28-02c-game-update.spec.ts(シナリオ構成)
test.describe("M28-02c ゲーム更新の影響コンボ", () => {
  test("バナー → 専用画面 →「問題なし」→ 件数が減る", ...)          // 主動線の往復
  test("★★破壊確認 (b): 延期してもバナーだけが消え、一覧のボタンは消えない", ...)
  test("専用画面の行アクション: コピーは出さず、削除で件数が減り、復元で戻る", ...)
});

2 本目の「破壊確認」は §6.2 の分水嶺そのものを固定するテストです。仕様の中で最も壊れたら困る境界(延期の抑止範囲)を名指しで 1 本の spec にしておく、というシナリオ設計は Playwright ガイドの「仕様の急所を spec にする」パターンの実例です。バックエンド側では、§3.2 の述語一本化テストに加え、サービス・リポジトリの通常テスト(m28_02a_game_update_test.go 等)が判定・確認・境界(ゴミ箱 404 など)を押さえています。

8. この機能から持ち帰る設計判断(まとめ)

判断要点どこで見たか
導出 vs 保存比較で求まる概念はテーブルに持たない。同期漏れという壊れ方を構造的に消す§2.1
ソート可能な文字列設計固定幅ゼロ埋めなら TEXT の辞書順 = 時系列順。比較関数は 1 行、SQL は素の >§2.3
静かに壊れるものは入口で塞ぐ壊れてもエラーにならない制約は、アプリ層 + DB CHECK + 生成側検証の多重防御。方針の例外は例外と明記§2.3
NULL の意味を列ごとに決める「安全側」の向きは列の意味論で決まる。全列一律の規則にしない§2.4
正本は 1 本 + 機械化SQL 述語・真偽値・クエリキー — 二重表現を作らず、規約はテストで強制する§3
忘れうる責務は構造へ埋めるN 経路が各自で書く形にせず、INSERT 文の COALESCE で「必ず入る」形に§4.1
