コンボ CRUD ウォークスルー
— 中核機能で「実戦の設計」を読む

コンボ(combos + combo_steps + 関連テーブル)はこのアプリの中核ドメインで、Go 側だけで約 1 万行あります。全部は追わず、「新規作成 → 一覧表示 → 詳細表示 → 部分更新」の主要フローに絞り、タグ管理には無かった応用要素を重点的に読みます。

応用要素タグ管理ではコンボでは
トランザクション不要(1 テーブル 1 文)親子 4 テーブルを 1 Tx で書く(§3)
集約(親子構造)なしCombo が Steps/Tags/OkiOptions を抱える(§2)
同時編集の防御なし楽観的排他(version カラム)(§6)
部分更新の表現*string(nil=不変更)Optional[T] の 3 状態(§6)
削除物理削除論理削除(ゴミ箱)+ 復元 + 完全削除(§7)
一覧の性能気にしない規模動的 WHERE・ソート whitelist・N+1 回避(§4)
DTOmodel を直接返す専用の dto.go(597 行)で変換(§3.1)
競合状態(race)なし検証と INSERT を 1 つの Tx に閉じ込める(§3.2)

API は 13 本(internal/api/combo/routes.go:22-37)。今回追うのは POST /combos、GET /combos、GET /combos/:id、PATCH /combos/:id の 4 本です。重複検知(check-duplicate)・ゴミ箱系(restore/permanent と読み取り専用詳細 GET /:id/deleted)・レシピ解決(recipe)・確定反撃版の生成(materialize)・ゲーム更新の「確認した」(acknowledge-version、別資料)・CSV 入出力(comboio)は「あることと役割」だけ知っていれば十分です。

読みどころは Steps の nil / 非 nil の使い分け規約です(combo.go:175-179 のコメントに明文化)。一覧 API は 100 件のコンボの Steps を全部返すと重いので Steps を「未ロード(nil)」のまま返し、詳細 API だけがロードします。omitempty により nil なら JSON からキーごと消えるので、フロントの ComboDetail.steps?(optional)と正確に対応します。「ロードしたか」を型で表すこの規約が、後述の N+1 対策の土台です。

ファイル冒頭には列挙的文字列定数がまとまっています: HitType* は 8 値(combo.go:25-35。M27-01 で DI 系 3 種 + stun を追加)、OpponentSize* は 4 値(combo.go:52-57。medium → standard 改名 + large 新設)、Position* は 7 値(combo.go:72-82。M28-02a で mid_self / mid_opponent を挿入)。いずれもフロント側 web/src/constants/ の定数と同期する規約です(CLAUDE.md §4)。定数ブロックのコメントに「新しい値は必ず末尾へ足す」「値の列挙をコメントに書き写さない(1 か所を正典にする)」という運用上の教訓が書かれているのも一読の価値があります。

「未検証」と「無かった」を区別する — 起き攻めの 3 状態(M27-02b) OkiOptions は「行の存在 = そのオプションが成立する」という sparse 表現ですが、これだけだと「行が 0 件」が「まだ調べていない」なのか「調べたが成立するものが無かった」なのか区別できません。この区別を担うのがコンボ単位のフラグ OkiVerified です(combo.go:226-232): false=未検証、true+0 件=調べたが無かった、true+行あり=その行が成立。一度はセル単位の 3 状態(available 列)で作ったものの「入力量が増えるだけ」と実機確認で判明し、コンボ単位へ作り直したという経緯もコメントに残っています — NULL や空配列に 2 つの意味を背負わせない設計の好例です。
符号の意味を後から入れ替える(M27-03) DriveDamage(-6〜6)は当初と符号の意味が逆になり、現在は負が削り・正が回復です。既存データはマイグレーション 000103 が UPDATE combos SET drive_damage = -drive_damage 相当で一括反転しました。面白いのは down マイグレーション: 符号反転は自己逆元(もう一度当てれば元に戻る)なので up と down が同一 SQL です(migrations/000103_flip_drive_damage_sign.down.sql)。「意味の変更はコードだけでなくデータも移行する」「可逆性を数学的性質で担保する」例として覚えておくと役立ちます。

3. 作成フロー(POST /api/combos)

3.1 handler と DTO — model を直接受け取らない

タグは model.CreateTagInput を handler が直接 Bind しましたが、コンボは dto.go に API 専用の CreateRequest(dto.go:28-65)があり、toServiceCreateInput(dto.go:411-480)でサービス層の入力型へ詰め替えます。レスポンスも toComboResponse(dto.go:524-590)で ComboResponse へ変換します。

なぜ層ごとに型を分けるのか API の形(JSON の互換性を守りたい)と内部モデル(自由にリファクタしたい)は変化の理由が違うからです。タグのような小さな機能では省略し、コンボのような大きな機能では分ける — 「常に全部やる」ではなくコストに応じて選ぶ、という判断の実例です。変換関数はただの写経に見えますが、toComboResponse が「Tags と AffectedMoves は常に非 nil の配列にする」(dto.go:576-585)「validations は Issues があるときだけ載せる」のような境界の正規化を担っています。逆に affectedByGameUpdate には意図的に omitempty を付けていません — false は「影響なし」という情報であり、キーごと消えると「判定していない」と区別が付かなくなるからです(dto.go:264-272 のコメント)。

3.2 service.Create — トランザクションの実戦形

ここがこのページの山場です。コンボ 1 件の保存は combos / combo_steps / combo_oki_options / combo_tags(+同時登録セットプレイ)への書き込みで、全部成功か全部無かったことにするかを Tx で保証します。

internal/service/combo/service.go:337-449(骨格を抜粋)
func (s *service) Create(ctx context.Context, input CreateInput) (*model.Combo, validation.ValidationResult, error) {
    normalizePositionAndMass(&input)                     // ① 始動位置のマス数と区分を整合(M28-02a、後述)
    combo, steps := buildComboFromInput(input)

    hash := CalcRecipeHash(steps)                        // ② レシピ指紋(重複検知 VAL-C02 用)

    tx, err := s.db.BeginTx(ctx, nil)                    // ③ ★検証より先に Tx を開く(M24-11、下記)
    if err != nil { return nil, validation.ValidationResult{}, busyOr(err, "begin tx") }
    defer func() { if err != nil { _ = tx.Rollback() } }()  // どこで失敗しても巻き戻す

    // ④ 検証は同じ Tx の内側で実行する
    result := validation.ValidateComboForCreate(ctx, combo, steps, input.IsDraft, hash, s.txScopedDeps(tx))
    if result.HasError() {
        _ = tx.Rollback()
        return nil, result, nil                          // 検証 NG は「エラーではなく結果」→ handler が 400
    }

    combo.Version = 1
    combo.StepCount = len(steps)

    newID, err := s.repo.InsertCombo(ctx, tx, combo)     // ⑤ 親を INSERT(採番)
    ...
    if err = s.repo.InsertSteps(ctx, tx, newID, steps); err != nil { ... }   // ⑥ 子ステップ
    if len(input.OkiOptions) > 0 {
        if err = s.repo.ReplaceOkiOptions(ctx, tx, newID, input.OkiOptions); err != nil { ... }
    }
    if err = s.notationSvc.RecomputeComboCache(ctx, tx, newID); err != nil { ... } // ⑦ 表示文字列を事前計算
    if len(input.TagIDs) > 0 {
        if err = s.repo.ReplaceTagAssociations(ctx, tx, newID, input.UserID, input.TagIDs); err != nil { ... } // ⑧ タグ関連
    }
    // ⑨(M4-04)同時登録セットプレイ。子の検証 NG なら手動 Rollback して 400 相当を返す

    if err = tx.Commit(); err != nil { return nil, result, fmt.Errorf("commit: %w", err) }

    saved, getErr := s.repo.FindByID(ctx, newID)         // ⑩ 完成形を再取得して返す
    ...
    filterTagsByUser(saved, input.UserID)                // タグは見ている利用者の分だけへ絞る(M22-02)
    return saved, result, nil
}

特に重要な設計判断が ④ です。「バリデーション NG」はエラー(error)ではなく戻り値(ValidationResult)として返します。Go のエラーは「想定外の失敗」用で、検証 NG は「想定内の正常な結果」だから、というエラー設計の使い分けです。handler 側(handler.go:67-69)は result.HasError() を見て 400 + 詳細(どのフィールドがどの VAL コードで NG か)を返し、フロントはそれをフォームの各欄に表示します。

check-then-act の競合 — なぜ Tx を検証より先に開くのか(M24-11) 初期の実装は「検証 → BeginTx → INSERT」の順でした。すると VAL-C02(重複検知)の判定と INSERT の間に隙が空き、同じコンボを 2 リクエストが同時に登録すると、両方が「重複なし」を見て両方 INSERT できてしまいます(いわゆる check-then-act / TOCTOU 競合。決定論的に再現する観測が残っています)。対策は「判定と登録を 1 つの操作にする」: DSN の _txlock=immediate により BeginTx が開始時点で write lock を取るため、2 本目の要求はここで 1 本目の commit を待ち、その後の判定は commit 済みの行を見ます(service.go:345-359 のコメント)。さらに txScopedDeps(service.go:318-335)が重複判定の読み取りだけを tx 経由へ差し替え、「この tx が今書いた行」も判定に見えるようにしています。判定ロジック自体は 1 文字も変えず、「いつ・どのハンドルで判定するか」だけを変えたのが読みどころです。Spring で言えば分離レベルやロックで守る問題を、SQLite では「書き込み Tx の直列化」で解いています。

⑦ の RecomputeComboCache は「技 ID の列 → 人間可読なレシピ文字列(例: 屈中P > 波動拳)」への変換結果を全表記プリセット分 JSON で recipe_cache カラムに書き溜める処理です。一覧表示のたびに変換計算しない、書き込み時に前計算する(read-heavy 最適化)というキャッシュ戦略で、モデルの json:"-"・extractDefaultRecipe(service.go:556-565。実体は model.ExtractDefaultRecipe に集約済み)とセットで機能します。

① の normalizePositionAndMass(service.go:1711-1748)は M28-02a で入った「同じ事実の 2 表現を整合させる」ヘルパです。始動位置は保存の正本がマス数(0〜160)へ変わりましたが、区分(position)も重複判定キーとして列に残っているため、「マス数があればマス数が勝ち、区分を導出し直す / 区分だけなら代表値をマス数へ入れる」という規則でずれた状態を DB に入れないようにしています。重複判定より前に呼ぶ順序が要件になっている点も含め、二重表現を持つときの実務の型として読めます。

4. 一覧フロー(GET /api/combos)— 動的検索と N+1 対策

4.1 クエリパラメータ → ListFilter

handler.List(handler.go:219-396)は character_id / is_draft / tag_ids / starter_move_id / position / hit_type / opponent_stance / affected_by_game_update / setup_result 系 3 種 / only_deleted / sort / order / limit / offset を 1 つずつ検証しながら ListFilter struct に詰めます。タグのときと同じ地道な作業ですが量が多いだけです。starter_move_id は M27-03 で追加された始動技フィルタで、リポジトリ側は元々 StarterMoveIDs(IN 句)を持っていたため「足りていなかったのはクエリパラメータの受け口だけ。SQL は 1 バイトも変えていない」というコメントが残っています(handler.go:248-274)。

レスポンスは { items, count, total } の 3 点セットです(M29-02)。一覧は既定 100 件・上限 1000 件でクランプされるため、count(応答に載った件数)だけでは「ちょうど 100 件だった」と「100 件で切り捨てた」を区別できません。total は LIMIT を掛けずに同じ WHERE で数え直した総数で、total > count が「切り捨てた」の観測になります(handler.go:381-395)。ページネーション API を作るときの定石です。

4.2 repository.List — SQL 組み立てと injection 対策

internal/repository/combo/repository.go:718-743(ソートの whitelist)
// SQL injection 対策のため、ここに登録されたフィールドのみ ORDER BY に使用する。
var sortFieldWhitelist = map[string]string{
    "default":         "starter_move_id ASC, position ASC, hit_type ASC, ...",
    "updated_at":      "updated_at",
    "damage":          "damage",
    "step_count":      "step_count",
    "starter_move_id": "starter_move_id",
}

func resolveSortClause(field, order string) string {
    sqlExpr, ok := sortFieldWhitelist[field]
    if !ok {
        return sortFieldWhitelist["default"] + ", id ASC"
    }
    ...
    // id 副次キーで全順序を確定させる。同値行の順序が SQL 上未規定のままだと
    // LIMIT/OFFSET のページ境界で重複・欠落が起こりうる(B9)。
    return sqlExpr + " " + dir + ", id " + dir
}

2 つの実務知識が詰まっています: (1) ORDER BY はプレースホルダにできないので、ユーザー入力をそのまま連結せず許可リストから引く。(2) ソートキーが同値の行の順序は SQL では不定なので、id をタイブレーカに足して全順序を確定させないとページネーションで行が重複・欠落する。WHERE 句の組み立て(buildListWhere、repository.go:889-967)はタグの Update で見た「スライスに条件を append して JOIN」パターンの拡大版です。tag_ids は IN (SELECT combo_id FROM combo_tags WHERE tag_id IN (...)) というサブクエリになる点も見ておいてください。M29-02 の Count(repository.go:972-980)がこの buildListWhere を List と共用しているのもポイントで、「一覧と総数で WHERE を 2 回書かない」ことが total の正しさの担保になっています。

4.3 N+1 の回避 — 「まとめて取ってマップで配る」

一覧 100 件に対し「各コンボのタグを 1 件ずつ SELECT」すると 1+100 クエリになります(N+1 問題)。このリポジトリの対策は一貫して「ID 列で一括取得 → map[comboID][]子 に束ねて配る」です:

  • タグ: findTagsByComboIDs(ctx, comboIDs) map[int64][]model.Tag(repository.go:2115)
  • 起き攻め: FindOkiOptionsForCombos(repository.go:2205)
  • ステップ: FindStepsForCombos(repository.go:1528。一覧では未使用 = Steps は nil のまま、が基本)
  • 変わった技(M28-02c): attachAffectedMoves(repository.go:1224)が listAffectedMovesByComboIDs で一括取得して注入。パターンが後年の機能追加でもそのまま踏襲されている例
  • セットプレイ: handler 層でも同じパターン(handler.go:342 のコメント「セットプレイ情報をバッチ取得(N+1 回避)」)
Flask / Spring 経験者向け JPA の @BatchSize / fetch join、SQLAlchemy の selectinload がフレームワーク側でやってくれることを、ORM を使わないこのリポジトリでは手で書いています。仕組みが全部見えるので、「N+1 とは何で、どう潰すのか」を学ぶ教材としてはむしろ好都合です。

5. 詳細フロー(GET /api/combos/:id)

repo.FindByID(repository.go:570-576)が集約を組み立てる現場です: 親 1 行を SELECT した後、attachComboChildren(repository.go:586-633)がステップ(moves と LEFT JOIN して技コードも取得)→ タグ → 起き攻めオプション → 始動技コード・表示名 → 変わった技、を順に取得して 1 個の model.Combo に注入します。子ロードが 1 関数に切り出されているのは、通常詳細とゴミ箱の読み取り専用詳細(FindByIDAllowDeletedWithChildren)が同じ「詳細として揃えるもの」を共有するためで、「母集団の違いはコンボ行を引く SQL の側だけに置く」という分離が効いています。詳細画面はさらにセットプレイ一覧を handler 層で埋め込みます(handler.go:131-156、「案 B1」)。

なお SELECT 句そのものは comboSelectSQL(repository.go:435-453)という 1 定数に集約されています。M28-02a で baseline_version を足すまで同じ列並びが 6 か所に写しで存在し、「1 か所写し忘れると Scan 順がずれ、エラーにならずに違う列を読む」状態だったため統合された — 列追加を機にコピペを畳んだ良いリファクタリング例です。

6. 部分更新(PATCH)— Optional[T] と楽観的排他

6.1 3 状態の部分更新

コンボのメタデータ編集は「memo を変えたい」「damage をクリアしたい」「他は触りたくない」を 1 リクエストで表現する必要があります。JSON では「キーを送らない / null を送る / 値を送る」の 3 通りがあり、これを受けるのが Go プライマー §9 で読んだ Optional[T] です:

internal/api/combo/dto.go:141-168(UpdateMetadataRequest 抜粋)
type UpdateMetadataRequest struct {
    Version int `json:"version"`                          // 楽観的排他のため必須(§6.2)
    IsDraft *bool `json:"isDraft,omitempty"`               // 非 nullable なので従来のポインタ方式
    Damage  comborepo.Optional[int]     `json:"damage"`   // キー不在=不変更 / null=クリア / 値=更新
    // ★bool なのに Optional(M27-02b)——「省略」と「false」を区別するため。
    //   値型だと、本欄を持たない古いリクエストが「未検証へ戻す」意味になってしまう
    OkiVerified comborepo.Optional[bool]   `json:"okiVerified"`
    Memo        comborepo.Optional[string] `json:"memo"`
    ...
    TagIDs  *[]int64 `json:"tagIds,omitempty"`             // nil=不変更 / 非nil(空含む)=全置換
}

SQL 側(repository.UpdateMetadata、repository.go:1253-1342)は Present なフィールドだけ SET 句に足し、Optional.Arg()(optional.go:39-44)が「Value==nil なら SQL NULL」を返します。タグで見た *string 方式の上位互換が、要求が複雑になったコンボでだけ導入されている — 同じ問題に対する道具の使い分けとして対で覚えると理解が定着します。

部分更新の検証は「更新後の姿」に対して行う(VAL-C15・M27-02b) M27-02b でダメージ・有利フレーム・消費ゲージ 2 欄が本登録の必須入力(VAL-C15、ERROR)になりました。ここで問題になるのが PATCH です — 部分更新のリクエストには「今回触っていない欄」が入ってこないので、入力だけを検証すると未入力に見えて誤って咎めます。実装は applyMetadataInput(service.go:575-629)で「DB の現在値 + 今回の変更」をマージした姿を作り、それを ValidateRequiredForPublished に渡します(service.go:693-717)。編集画面の保存は識別キーが変わらない限り PATCH 経路なので、「PUT だけに掛けると主経路が素通りする」という理由で PATCH 側にも掛けてある点まで含めて、部分更新 × 必須制約の教科書的な解き方です。

6.2 楽観的排他 — version カラムと 409

2 つのタブで同じコンボを開いて両方から保存すると、後勝ちで片方の編集が消えます。これを防ぐのが version カラムです:

  1. GET したとき version: 3 がレスポンスに含まれ、フロントは編集中それを保持する
  2. PATCH のボディに version: 3 を入れて送る
  3. リポジトリは UPDATE ... WHERE id = ? AND version = 3 のように、読んだときの version のままの行だけ更新し、version をインクリメントする
  4. 影響行数 0 = 誰かが先に更新した → ErrConflict → handler が 409 Conflict「このコンボは他の処理で更新されました。再取得してください」(handler.go:418-419)
Spring 経験者向け JPA の @Version + OptimisticLockException と同じ仕組みの手実装です。行ロック(悲観的排他)を取らないので、SQLite のような単純な DB でも安全に同時編集を捌けます。

7. 論理削除(ゴミ箱)

DELETE は行を消さず deleted_at に時刻を入れるだけ(SoftDelete、repository.go:1358-1386)。通常の SELECT はすべて WHERE deleted_at IS NULL が付き(FindByID の SQL、repository.go:567-568)、ゴミ箱画面は逆に only_deleted=true で削除済みだけを出します。復元(restore)は deleted_at を NULL に戻し、完全削除(permanent)だけが本当に DELETE します。タグ集計が「ゴミ箱のコンボを数えない」ために JOIN 条件へ c.deleted_at IS NULL を足していた(タグ §2.2)のは、この仕組みの波及でした — 論理削除は導入した瞬間、全クエリに「生死の考慮」を要求するという良い教訓です。

細部も進化しています。SoftDelete の UPDATE には AND deleted_at IS NULL が付き、既に削除済みの行を 2 度消しても deleted_at を上書きせず冪等に成功します(M23-08。上書きすると利用者から見て「消した日が後ろへずれる」)。またゴミ箱の絞り込みは deleted_at IS NOT NULL AND superseded_by_combo_id IS NULL の 2 条件です(buildListWhere、repository.go:952-957) — PUT(キー変更編集、§8.3)は「旧行を論理削除して新行を積む」方式なので、編集のたびに旧行がゴミ箱に並んでしまうのを、旧行へ後継 id を書いておき既定から外すことで防いでいます(M23-01)。

ComboEditorPage(pages/ComboEditorPage.tsx:12-23)は URL から自分のモードを判定します: /combos/new → new、/combos/:id/edit → edit(既存データを useCombo(id) でロードして初期値に)、/combos/new?copyFrom=5 → copy(5 番のデータを初期値にした新規)。「編集画面と新規画面はデータの初期値が違うだけ」という共通化で、サーバーレンダリングなら 3 テンプレートになりがちなものが 1 コンポーネント + モード分岐で済んでいます。

8.3 ミューテーションのキャッシュ操作 — invalidate の一歩先

web/src/features/combo/api.ts:231-247(useUpdateComboWithKeyChange)
export function useUpdateComboWithKeyChange(id: number) {
  const qc = useQueryClient();
  return useMutation<Combo, ApiError, PutComboRequest>({
    mutationFn: (req) => requestJSON<Combo>(`/api/combos/${id}`, { method: "PUT", ... }),
    onSuccess: (data) => {
      qc.invalidateQueries({ queryKey: queryKeys.combos.all() });      // 一覧系は再取得へ
      qc.removeQueries({ queryKey: queryKeys.combo.detail(id) });      // 旧 ID の詳細キャッシュは破棄
      if (data.id && data.id !== id) {
        qc.setQueryData(queryKeys.combo.detail(data.id), data);        // 新 ID の詳細はレスポンスで直接充填
      }
    },
  });
}

PUT(キー変更編集)はサーバー側で「旧コンボを消して新コンボを作る」ため ID が変わりえます(旧行は論理削除され、後継 id が書き込まれる — §7)。そのため旧キャッシュの破棄と、再取得せずレスポンスをそのままキャッシュに書き込む setQueryData(1 往復の節約)を組み合わせています。invalidate / remove / setQueryData の 3 段活用は TanStack Query の実戦テクニックの見本です。

queryKey は「正本」ファクトリから引く(M24-08) 以前は ["combos"] のような配列リテラルを各所に書いていましたが、現在は web/src/lib/query-keys.ts の queryKeys ファクトリが正本です。キーを書く側と invalidate する側は別ファイルに分かれるため、リテラルだと片方だけ直したときに例外も出ずキャッシュ更新が静かに効かなくなります(TanStack の前方一致は「当たらない」だけで失敗しない)。専用テストが「正本の外の配列リテラル」を機械検出し、「どの invalidate がどの query に当たるか」を表で固定しています(web/CLAUDE.md §1.5)。文字列キーが分散する仕組み全般(イベント名、キャッシュキー、i18n キー)に応用できる考え方です。

8.4 型の三兄弟 — ComboSummary / ComboDetail / Combo

web/src/features/combo/types.ts:1-7, 83, 150, 224(構造のみ)
// 注: ComboSummary と ComboDetail / Combo は別 interface だが、バックエンド ComboResponse は同一型。
//     フィールド追加時は該当するすべてに追加すること。
export interface ComboSummary { ... damage?: number; ... }          // 一覧用。「無い」= undefined
export interface ComboDetail extends ComboSummary { steps?: ...; }  // 詳細用。steps 等が増える
export interface Combo { ... damage?: number | null; ... }         // 編集用。「未入力」= null を許す

バックエンドは 1 つの ComboResponse しか返さないのに、フロントは用途別に 3 つの interface を持ちます。理由は「未指定」の意味が画面ごとに違うから: 一覧・詳細は「サーバーがキーを省略した(undefined)」、編集フォームは「ユーザーがまだ入力していない(null)」を区別したいのです。便利な反面、新フィールド追加時に 3 か所へ追記が必要という保守コストがあり、web/CLAUDE.md §2 とファイル冒頭コメントで注意喚起されています。型設計のトレードオフの生きた実例です。

3 分岐の中で M28-02c の affectedByGameUpdate: boolean だけは 3 つとも optional にせず必須で定義されています(types.ts:106、224 側も同様)。バックエンドが omitempty を付けず false でも必ずキーを出す(§3.1)ことと対になっていて、「型を optional にすると『キーが無い = 判定していない』と false の区別が 1 段下で潰れる。画面側で ?? false を書かないこと」とコメントに明記されています — API 契約の「必ず出す」をフロント型の「必須」で受け止める、両側同期の見本です。
