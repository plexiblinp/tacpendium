コンボのテスト + E2E
— モック・サブテスト・Playwright まで

コンボドメインにはタグのテストで見た型に加えて、タグには無かった 3 種類のテストがあります: モックを使うハンドラテスト、サブテストによるテーブル駆動、そして本物のブラウザで動かす E2E(Playwright)です。この 3 つを重点的に読みます。

1. サービステスト — フィクスチャとサブテスト

1.1 テスト側の DI 配線とフィクスチャ

コンボのサービスは依存が多い(repo・バリデーション依存束・notation・setup)ので、テストヘルパが main.go と同じ配線を組みます(service_test.go:25-39 の newSvc)。もう 1 つの定番がフィクスチャ関数です:

internal/service/combo/service_test.go:99-125
func validRyuInput(t *testing.T, db *sql.DB) combosvc.CreateInput {
    t.Helper()
    move1 := lookupMoveID(t, db, 1, "standing_light_punch")  // seed 済みの技マスタから ID を引く
    move2 := lookupMoveID(t, db, 1, "hadoken_light")
    return combosvc.CreateInput{
        UserID:         1,                    // M22-02 のマルチユーザー化で追加
        CharacterID:    1,                    // リュウ
        IsDraft:        false,
        StarterMoveID:  &move1,
        Position:       ptr("mid_screen"),    // ptr[T any] ヘルパでリテラル→ポインタ
        OpponentStance: ptr("standing"),
        HitType:        ptr("normal"),
        OpponentSize:   ptr("standard"),
        // M27-02b(VAL-C15): 本登録の必須 4 欄。欠けると Create が検証エラーで nil を返し、
        // 以降が nil 参照で落ちる。仮登録(IsDraft: true)の fixture には要らない。
        Damage:             ptr(1000),
        KnockdownAdvantage: ptr(30),
        DriveGaugeConsumed: ptr(1.0),
        SAGaugeConsumed:    ptr(0),
        Steps: []model.ComboStep{
            {StepOrder: 1, MoveID: &move1},
            {StepOrder: 2, MoveID: &move2},
        },
    }
}

「バリデーションを通る正しい入力」を 1 か所に定義し、各テストは input := validRyuInput(t, db) から 1 点だけ変えて使います。技 ID をハードコードせず code から引いているのは、seed データの ID 変動にテストが壊されないための防御です。このパターンの利得は M27-02b で実証されました — 本登録に必須 4 欄(ダメージ・起き攻め有利フレーム・消費ゲージ 2 種)が加わったとき、fixture へ 4 行足すだけで既存テスト群がまとめて追随できています。

1.2 サブテスト(t.Run)によるテーブル駆動 + round-trip 検証

internal/service/combo/service_test.go:156-195(短縮)
func TestService_Create_DriveDamage_FloatRoundTrip(t *testing.T) {
    cases := []struct {          // ① テストケースの「表」を struct スライスで定義
        name string
        val  float64
    }{
        {"negative_decimal", -2.5},
        {"positive_decimal", 3.5},
        {"integer_value", 2},
        {"max", 6},
        {"min", -6},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {   // ② 1 ケース = 1 サブテスト(個別に成否が出る)
            db, svc := newSvc(t)
            input := validRyuInput(t, db)
            dd := tc.val
            input.DriveDamage = &dd

            got, result, err := svc.Create(context.Background(), input)
            ...
            fetched, err := svc.Get(context.Background(), got.ID, 1)   // ③ 保存後に読み直す(第 3 引数は M22-02 で増えた userID)
            ...
            if fetched.DriveDamage == nil || *fetched.DriveDamage != tc.val {
                t.Errorf("round-trip DriveDamage=%v, want %g", fetched.DriveDamage, tc.val)
            }
        })
    }
}

これが Go のテーブル駆動テストの完全形です(タグでは簡易ループ版でした)。t.Run を使うと失敗時に TestService_Create_DriveDamage_FloatRoundTrip/negative_decimal のようにどのケースが落ちたか個別に報告され、-run 'RoundTrip/max' で 1 ケースだけ再実行もできます。JUnit の @ParameterizedTest 相当を言語機能だけで実現する、Go コミュニティの最重要イディオムです。

③ の round-trip(書いて→読み直して→一致確認)も重要な検証思想です。Create の戻り値だけ見ると「メモリ上は正しいが DB 保存で壊れる」バグ(型変換・NULL 化け)を見逃します。実 DB テストだからこそできる検証です。

2. ハンドラテスト — モックと httptest

サービステストが「業務ロジック + SQL」を実 DB で検証済みなので、ハンドラテストの関心は「HTTP の入出力変換だけ」です。そこでサービスをモックに差し替えます。

2.1 インターフェースを満たすモックを自作する

internal/api/combo/handler_test.go:79-111(抜粋)
type mockService struct {
    createFn func(ctx context.Context, input combosvc.CreateInput) (*model.Combo, validation.ValidationResult, error)
    getFn    func(ctx context.Context, id int64) (*model.Combo, error)
    ...                                       // メソッドごとに差し替え可能な関数フィールド(現在 14 個)

func (m *mockService) Create(ctx context.Context, input combosvc.CreateInput) (*model.Combo, validation.ValidationResult, error) {
    return m.createFn(ctx, input)             // フィールドの関数へ委譲するだけ
}
func (m *mockService) Get(ctx context.Context, id, userID int64) (*model.Combo, error) {
    return m.getFn(ctx, id)                   // インターフェース変更(M22-02 で userID 追加)をモック側で吸収
}

// GetDeleted は M23-07 の読み取り専用取得。未設定なら getFn へ落とさず
// 明示的に失敗させる(Get と取り違えたテストが黙って通るのを防ぐ)。
func (m *mockService) GetDeleted(ctx context.Context, id, userID int64) (*model.Combo, error) {
    if m.getDeletedFn == nil {
        return nil, errors.New("getDeletedFn not set")
    }
    return m.getDeletedFn(ctx, id)
}
...

Go には Mockito のようなモック生成の標準はなく、「インターフェースを満たす struct を手書きし、挙動は関数フィールドで注入する」のが定番です(プライマー §5 の暗黙実装が効いています)。テストごとに createFn だけ書き換えれば、成功・検証 NG・エラーの各シナリオを自由に演出できます。

読みどころが 1 つ増えています: 後からインターフェースに生えたメソッドの既定挙動の使い分けです。AcknowledgeGameVersion や PermanentDelete のような追加メソッドは「フィールド未設定なら無害な既定値を返す」nil ガード付きで実装され、既存テストを 1 行も書き換えずに済ませています。一方 GetDeleted は上の引用のとおり未設定なら明示的にエラー — 「Get と取り違えたテストが黙って緑になる」ことを防ぐためで、既定値を用意するか失敗させるかを「取り違えの危険があるか」で選び分けています。

読みどころ:

  • vi.mock(モジュールパス, factory) — そのモジュールを import する全箇所が偽物を掴む。フックの戻り値をテストごとに mockUseCombo.mockReturnValue({data: ..., isLoading: false}) と切り替えることで、ローディング中・エラー・データありの三態を API 通信なしで再現できる
  • MemoryRouter — 本物のブラウザ URL の代わりにメモリ上の履歴を使うルータ。useParams() が id=1 を返すよう「/combos/1 にいる」状況を作る。initialEntries にはパス文字列だけでなく { pathname, state } のオブジェクトも渡せ、「保存直後に遷移してきた」(location.state.fromSave)のような来歴つきの状況も偽装できる
  • 本物のアプリが main.tsx で被せていた Provider(QueryClientProvider / Router / NavigationGuardProvider)を、テストでも自前で被せる必要がある — テストの render は「ミニチュアの main.tsx」と考えると構造が腑に落ちる
「〜しない」だけの検証は弱い(M27-03 レビューの教訓) 「戻る」テスト群(同ファイル :150-211)には検証の書き方の教訓が 2 つ記録されています。1 つ目: 「一覧へ飛ばない」だけを主張すると、戻る処理を丸ごと消して e.preventDefault() だけ残した壊れた実装でも緑になる。そこで vi.mock のファクトリに async (orig) で元モジュールを取り込みつつ 1 関数だけ差し替え、その mockLeaveBack が実際に呼ばれたことまで主張しています(expect(mockLeaveBack).toHaveBeenCalledTimes(1))。2 つ目: 挙動の反転はテストで固定する — M24-05 で候補 0 件でもセクションを出す仕様に反転した際、「出さない」を固定していた旧テストを書き換えるだけでなく、撤去した「既存から紐付け」ボタンが存在しないことのテスト(queryByText(...).toBeNull())も追加されました。復活しても誰も気づけない、を防ぐためです。

4. E2E テスト — Playwright で「本物」を動かす

ここまでのテストは全部「部品」の検証でした。E2E は本物のブラウザ(Chromium)が本物のバックエンド + 本物の DB に対して、ユーザーと同じ操作をします。実行は make e2e(Makefile:147-149)、1 本だけ回すなら make e2e-only P=combo-crud(M24-09d で新設。pnpm exec playwright test を直接叩くと PW_EXECUTABLE_PATH が渡らず、UI を使う spec が「Executable doesn't exist」で全滅する — Makefile の e2e-only 注記参照)。本章は代表 spec を 1 本読む入門編です — E2E 基盤の仕組み・セレクタ規約・シナリオ設計パターン・新規 spec の書き方は、続編のPlaywright E2E シナリオガイドで体系的に扱います。

4.1 独立スタック — dev 環境を汚さない仕掛け

web/playwright.config.ts の冒頭コメント(:5-23)に設計がすべて書いてあります:

  • 使い捨て DB: バックエンドを環境変数 TACPENDIUM_DB_PATH で web/e2e/.tmp/ 配下の専用 DB に向ける。起動時にマイグレーション + seed が自動適用されるので、毎回クリーンな状態から始まる(開発用 DB にゴミが溜まらない)
  • 専用ポート: バックエンド 47390 / Vite 5273(基準値)を使い、通常の開発サーバーとポートを取り合わない。さらに複数 worktree での同時実行にも耐えるよう、dev ポートからのオフセットで決定的に導出する(config.ts:25-53)
  • 専用の設定ファイルまで使い捨てる(M24-09c 追補): E2E バックエンドは dev の config.toml ではなく、起動のたびに config.toml.example から複製する web/e2e/.tmp/tacpendium-e2e.toml を読む(config.ts:55-64)。これが無かった時期、開発者が設定画面で既定キャラを変えた瞬間に「リュウが出ること」前提の spec が 35 件まとめて落ちた
  • workers: 1 に固定(M24-09c): fullyParallel: false が直列化するのは 1 ファイル内だけで、spec ファイル同士は worker 数だけ並列に走る。しかしバックエンド 1 本・DB 1 個は共有資源で、プリセット総数上限(8 件)や重複判定キーの奪い合いが実測されている。外すと必ず赤くなる決定論的な監視 spec(aa-interference-probe-{a,b}.spec.ts)まで置いてある(config.ts:69-99)
  • go run -tags=debug で起動(M28-02c): debug ビルド限定の書き込み口(§4.4)を E2E から叩くため(config.ts:128-145)
  • フロントは dev サーバではなく pnpm build + vite preview で配信(M24-09c 追補)。dev サーバは ESM を 1 モジュールずつ配るため、テストごとに新規コンテキストを作る Playwright では毎回数百リクエストの固定費を払い直す — 実測で 402 秒 → 223〜253 秒に短縮(config.ts:160-174)
  • Playwright の webServer 機能がテスト前にこの 2 プロセスを起動し、終了後に落とす
「テストが環境を壊さない」はインフラで保証する タグ/コンボの Go テストは t.TempDir の使い捨て DB、E2E は専用ポート + 使い捨て DB。どのレベルのテストも「実行前に作り、実行後に消える」環境で走るのがこのリポジトリの一貫方針です。テストが flaky(たまに落ちる)になる最大要因は環境の共有なので、ここに投資する価値があります。config のコメントには「モジュールスコープで DB を破棄してはならない(ワーカープロセスが再ロードして稼働中 DB を消す)」という実際に踏んだ罠まで記録されています。

4.2 combo-crud.spec.ts を読む

web/e2e/combo-crud.spec.ts:15-71(登録→詳細→編集→削除、短縮)
test("コンボ登録 → 詳細確認 → 編集 → 削除", async ({ page }) => {
  const memo = `e2e-smoke-${Date.now()}`;          // ユニーク値で「自分が作った行」を同定
  const memoEdited = `${memo}-edited`;

  // ── 登録 ──
  await page.goto("/combos/new");
  await page.getByTestId("combo-editor-draft-checkbox").click();   // 仮登録モード ON
  await addMinimalRecipeStep(page);   // M24-13: 仮登録でもレシピ 1 ステップ必須(VAL-C09)→ §4.3
  await page.getByPlaceholder("このコンボに関するメモ(任意)").fill(memo);

  // M24-01: 保存後は詳細でなく一覧へ戻る。POST 応答から id を取り、詳細を開き直す(support/new-combo.ts)
  await saveNewComboAndOpenDetail(page, () =>
    page.getByRole("button", { name: "保存" }).click(),
  );

  // ── 詳細確認 ──
  // M24-03: メモの 1 行目はレシピの上にも出る(✎ 付き)。exact 一致で「メモ欄そのもの」を指す
  await expect(page.getByText(memo, { exact: true })).toBeVisible();

  // ── 編集 ──
  await page.getByRole("link", { name: "編集", exact: true }).click();  // 「技編集」ナビとの部分一致衝突を回避
  await expect(page).toHaveURL(/\/combos\/\d+\/edit$/);
  const memoArea = page.getByPlaceholder("このコンボに関するメモ(任意)");
  await memoArea.clear();
  await memoArea.fill(memoEdited);
  await page.getByRole("button", { name: "保存" }).click();
  await expect(page).toHaveURL(/\/combos\/\d+$/);
  await expect(page.getByText(memoEdited, { exact: true })).toBeVisible();

  // ── 削除(ダイアログ確認まで)──
  await page.getByRole("button", { name: "削除" }).click();
  const dialog = page.getByRole("alertdialog");
  await expect(dialog).toBeVisible();
  await dialog.getByRole("button", { name: "削除" }).click();
  await expect(page).toHaveURL(/\/combos(\?character_id=\d+)?$/);   // 削除後は一覧へ戻る
});

読みどころ:

  • セレクタ戦略はコンポーネントテストと同じ: getByRole / getByPlaceholder を優先し、testid は最後の手段。Testing Library と Playwright で同じ思想が通っているので、学習が二度おいしい
  • await と自動待機: Playwright の expect(...).toBeVisible() は「今見えているか」ではなく「見えるまで待つ(タイムアウト付き)」。画面遷移や再取得の完了を sleep で待つコードが無いのはこのため
  • テストの自己完結: Date.now() 入りのメモで自分のデータを同定し、最後に自分で削除して後始末まで含めて 1 本のシナリオ。既存データ件数に依存しない(spec 冒頭コメント :7-12)
  • 画面仕様の変更は support/ ヘルパが吸収: 保存後の遷移先が詳細 → 一覧へ変わったとき(M24-01)、「一覧の一番新しい行を掴む」のではなく saveNewComboAndOpenDetail(support/new-combo.ts)が POST /api/combos の応答そのものから id を取る形にした。並行実行や他 spec の残したデータに影響されない同定方法である
  • 2 本目の spec(:77-125)は「メモだけ編集しても custom_states が誤クリアされない」という過去の不具合の非回帰テスト。E2E の重要な使い道は「ユニットの隙間で起きた統合バグを、再発しない形で釘付けにする」ことだと分かる

4.3 仕様変更を吸収する「下ごしらえヘルパ」(2026-07 以降の新パターン)

このガイドの初版以降、既存 spec の保存が軒並み通らなくなる類の仕様変更が 2 回ありました: M24-13「仮登録でもレシピ 1 ステップ必須(VAL-C09)」と M27-02b「本登録は 4 欄が必須(VAL-C15)」です。対応は、各 spec が見ているものを 1 文字も変えず、下ごしらえだけを web/e2e/support/editor-input.ts の共通ヘルパへ寄せる形で行われました:

web/e2e/support/editor-input.ts:50-57(fillRequiredComboFields)
// M27-02b: 本登録に必須の欄を埋める。必須は 4 欄だが、ここで埋めるのは 2 欄だけでよい
// ——消費ゲージ 2 欄は新規登録の既定値 "0" が入っているため。
// 仮登録で保存する spec には要らない(VAL-C15 は仮登録をスキップする)。
export async function fillRequiredComboFields(page: Page): Promise<void> {
  const damage = page.getByTestId("combo-editor-damage");
  if (!(await damage.isVisible())) {
    await switchEditorTab(page, "basic");   // 欄が隠れていれば先にタブを切り替える
  }
  await page.getByTestId("combo-editor-damage").fill("1500");
  await page.getByTestId("combo-editor-knockdown-advantage").fill("30");
}

§4.2 で見た addMinimalRecipeStep も同族です。面白いのは足すステップの選び方 — 技ではなく「パリィドライブラッシュ」(非技ステップ)を選ぶことで、技 ID の解決が不要になり、始動技も決まらないので VAL-C03(始動技と 1 ステップ目の食い違い)の警告も出ません。§1.1 の validRyuInput(fixture 1 か所に集約 → 必須化は 4 行の追加で全テストが追随)とまったく同じ思想の E2E 版で、仕様変更のコストは「下ごしらえの共通化率」で決まることを両側から示しています。なお必須化そのものの回帰は m27-02b-required-and-oki-states.spec.ts が固定しており、「必須 4 欄が空だと保存が止まり理由が画面に届く」「仮登録では止まらない(止まると仮登録の存在意義が消える)」「起き攻め 3 状態(必須・任意・未検証)が DB を往復して戻る」の 3 点を主張しています — 3 点目は DTO の *bool・リポジトリの列・zod の 3 つを跨ぐため、経路全体を通す E2E でしか確かめられません。

4.4 debug ビルド限定の「書き込み口」で、本番では作れない状態を作る(M28-02c)

ゲーム更新の影響コンボ機能(FR702)の E2E には固有の難題がありました: 判定の起点となるマーカー(moves.last_changed_game_version)を立てる経路が、本番では配信者の DML マイグレしか無い。しかも初回は必ず影響 0 件なので、「画面を開いても何も出ない」ことは正しさの証拠にならない。そこで採られたのが、debug ビルドにしか存在しない書き込み API を E2E から叩く方法です:

web/e2e/support/game-update.ts:21-34(抜粋)
// 技にマーカーを立てる(配信者の DML マイグレを模す)。
// 叩く先は debug ビルドにしか存在しない経路(internal/api/debug/game_version.go。
// 本番バイナリには 1 バイトも出ない)。
export async function setMoveGameVersion(
  request: APIRequestContext, moveId: number, version: string | null,
): Promise<void> {
  const res = await request.post(`/api/debug/moves/${moveId}/game-version`, {
    data: { lastChangedGameVersion: version ?? "" },
  });
  expect(res.ok(), `マーカーの設定に失敗: ...` +
    "(★E2E バックエンドが -tags=debug で起動しているか確かめること)").toBeTruthy();
}

このために E2E バックエンドは go run -tags=debug で起動します(§4.1)。JUnit で言えばテスト用フィクスチャのバックドアを、Go ではビルドタグで本番バイナリから物理的に切り離すのが特徴です。代償は「E2E が本番ビルドではなく debug ビルドを検査する」ことですが、差分は debug ルート 5 本の登録だけで本番コードの経路は同一 — と config のコメントに費用対効果まで記録されています。この口を使った往復シナリオ(バナー →「問題なし」→ 件数が減る)は m28-02c-game-update.spec.ts にあり、機能自体の解説は別資料「ゲーム更新影響判定ウォークスルー」(game-update-walkthrough.html)が扱います。

4.5 共有 DB を前提にした「状態非依存」の書き方

E2E スタックはバックエンド 1 本・DB 1 個を全 65 spec が共有します(§4.1 の workers: 1 で直列化しても、先に走った spec の残したデータは後続から見える)。初版以降に定着した規律が 3 つあります:

  • 既定キャラを仮定しない: 素の goto("/combos/new") は環境の既定キャラで開く。「初期表示はリュウ」を仮定した spec は、既定キャラを変えた環境でだけ落ちる(2026-08-26 に実際に 35 テストが落ちた)。⇒ キャラが要る spec は gotoNewComboFor(page, "ryu")(support/character.ts)で URL クエリから明示的に選ぶ
  • 重複判定キーを spec 固有にずらす: コンボの重複判定キーは(キャラ / 始動技 / 始動位置 / 相手の状態 / ヒット種別 / 相手の大きさ)の 6 項目。他 spec と同じ組を作ると VAL-C02 で作成自体が落ちる — しかも単独実行では緑・全数実行だけ赤という最悪の落ち方をする。m28-02c は「他 spec は技一覧の先頭を使う」ことを実測した上で末尾から始動技を取る(tailNormalMoves)ことでキーを分離している
  • 全体へ及ぶ状態は「過去の値」で作る: マーカーは技に立つので同じ技を使う全コンボへ及ぶ。現在版より新しいマーカーを立てると他 spec が作ったコンボまで一斉に影響ありになるため、m28-02c は基準もマーカーも現在版より古い値(OLD_BASELINE / MARKER)で組み、自分の 1 件だけが検出される形にしている(spec :26-37)
「後片付けを足す」では直らない 並行実行下の干渉は、後片付けを徹底しても防げません — 並行中は「まだ消していない時間」が必ず在るからです(playwright.config.ts の workers 注記)。だからこの節の規律はすべて「消す」ではなく「最初から被らない」方向を向いています: ユニーク値(Date.now())、キーの分離、既定への非依存。共有 DB のテストを書くときの一般則として持ち帰れる形です。

5. まとめ — テストピラミッドの全体像

層何を信じるためのテストか速度/本数偽物にするもの
サービス(実 DB)業務ロジックと SQL が正しい速い・多いなし(DB も本物の使い捨て)
ハンドラ(httptest)HTTP ⇔ Go の変換とステータスコードが正しい速い・中サービス(モック)
フロントのフック/スキーマフォーム検証・正規化・キャッシュ操作が正しい速い・多いAPI 呼び出し(vi.fn)
フロントのページ状態→表示の分岐が正しい中子コンポーネント・フック(vi.mock)
E2E(Playwright)全部つないだとき本当に使えるか遅い・少数精鋭なし(全部本物、環境だけ使い捨て)

各層が「下の層で保証済みのことは繰り返さない」よう関心を絞っているのがポイントです。E2E は現在 65 spec ファイル・252 テストまで育ちましたが、大半は各マイルストーンが 1〜2 ファイルずつ残した非回帰シナリオで、下の層で網羅済みのロジックを E2E でやり直してはいません。しかも workers: 1 の直列実行(§4.1)のため 1 テストの追加コストは高く、「何を E2E に残すか」の判断は今も少数精鋭の思想のままです — その判断基準と新規 spec の書き方は続編の Playwright E2E シナリオガイドが扱います。
