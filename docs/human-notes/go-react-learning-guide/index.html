Tacpendium で学ぶ Go / React
— 自分のリポジトリを教材にした学習ガイド

この資料集は、Tacpendium(SF6 コンボ管理アプリ)の実際のコードを教材にして、Go と React の言語仕様・フレームワークの考え方・アプリが動く流れを解説するものです。Flask / Spring Boot でのアプリ開発経験がある読者を想定し、随所に「Flask / Spring ではこうだった」という対比コラムを挟んでいます。

この資料の読み方 コード引用にはすべて実ファイルのパスと行番号を付けています(例: internal/service/tag/service.go:65)。読みながらエディタで該当ファイルを開き、「引用部分の前後で何が起きているか」を実物で確認するのが最も効果的です。コードは 2026-07-22(フェーズ3)に初版を書き、2026-09-08 時点の main 相当スナップショットへ更新済みです。その後の変更で行番号がずれることがあります。

1. 収録ドキュメントと推奨読了順

  1. 目次・全体アーキテクチャ(このページ) アプリ全体の構造と「1 リクエストの一生」。最初にここで地図を持つ
  2. Go 言語プライマー struct タグ・エラー処理・インターフェース・context など、このリポジトリを読むのに必要な Go の言語仕様を実コードで解説
  3. React + TypeScript プライマー 関数コンポーネント・hooks・TanStack Query・zod。サーバレンダリング(Jinja/Thymeleaf)との発想の違い
  4. タグ管理 完全ウォークスルー 最小で素直な機能を 1 本、バックエンド 4 層とフロントエンドを通しで追跡。本編
  5. タグ管理のテスト解説 Go の実 DB テストと Vitest + React Testing Library。JUnit/pytest との対比
  6. コンボ CRUD ウォークスルー アプリの中核機能。トランザクション・楽観的排他・N+1 対策・presence-detection など実戦的な設計を学ぶ
  7. コンボのテスト + E2E(Playwright) モックを使うハンドラテスト、コンポーネントテスト、独立スタックで動く E2E
  8. Playwright E2E シナリオガイド E2E 基盤の仕組み(使い捨て DB・専用ポート)、セレクタ規約、65 spec に育った実例から抽出したシナリオ設計パターン、新規 spec の書き方
  9. shadcn/ui + Tailwind スタイリングガイド CSS 最小限の地図(ボックスモデル・flex)から、Tailwind の読み方、shadcn の三層構造(Radix × Tailwind × cva)、デザイントークン、実際に色や形を変える方法まで
  10. ゲーム更新影響判定 ウォークスルー 応用編(2026-09 新設)。M28 で追加された FR702 を DB → SQL → Go → React → E2E まで通しで読む。「保存せず導出する」設計、ソート可能なバージョン文字列、DB CHECK 制約、述語一本化をテストで強制する技法など
  11. シェル検査とフック — 規約を機械化する 応用編(2026-09 新設)。アプリの外側にある scripts/(シェル 24 本)と .claude/hooks/(6 本)を読む。ベースライン固定型の検査、陽性・陰性対照による自己検査、終了コードの三値、許可リスト方式のガード、フックの設計規律
なぜ「タグ管理」と「コンボ CRUD」の 2 本立てか タグ管理はバックエンド 4 層 + フロントエンドが最小構成で揃っていて、全体の流れを 1 機能で追い切るのに最適です(Go 側 約 700 行、テスト除く)。一方コンボ CRUD はアプリの中核で、トランザクションや楽観的排他などの実戦的な要素が詰まっていますが、Go 側だけで約 1 万行(CSV 入出力含む、テスト除く)あります。まずタグで「型」を掴み、コンボで「実戦」を読む、という順序を推奨します。

2.2 配布形態: 単一バイナリ + embed

このアプリの配布形態は「exe を 1 個ダブルクリックすると使える」ことを目標にしています。Go の embed 機能でフロントエンドのビルド成果物(Vite が生成する HTML/JS/CSS)をバイナリ内に焼き込み、Echo が API と静的ファイルの両方を配信します。

cmd/tacpendium/main.go:542-559(抜粋)
if tacpendium.WebEmbedded {
    webFS, fsErr := tacpendium.WebFS()
    if fsErr != nil {
        return fmt.Errorf("web fs: %w", fsErr)
    }
    staticapi.Register(e, webFS)   // SPA 静的配信(未知パス→index.html フォールバック)
    ...
    printStartupNotice(os.Stdout, cfg.Server.Mode, actualPort, lanIPs)
                                     // アクセス URL をコンソールへ常時表示(ログ level 非依存)
    launchBrowser(actualPort)        // exe 起動だけでブラウザが開く
}

一方、開発時は 2 プロセス構成です。Go のバックエンド(go run ./cmd/tacpendium)と Vite の開発サーバー(pnpm run dev)を別々に起動し、Vite が /api/* へのリクエストをバックエンドにプロキシ転送します(web/src/lib/api-client.ts:1-4 のコメント参照)。フロントのコードを保存すると即座にブラウザへ反映される(HMR)のは Vite 側の機能です。

Flask / Spring 経験者向け Spring Boot の「fat JAR に静的リソースを同梱して java -jar で起動」とほぼ同じ発想です。違いは、Go は JVM 不要のネイティブバイナリを吐くので、配布物が本当に「exe 1 個」になる点。また Flask の render_template() のようなサーバー側テンプレートは存在せず、サーバーは常に JSON を返すだけで、HTML の組み立ては全部ブラウザ内の React が行います。

2.3 起動シーケンス

cmd/tacpendium/main.go の run()(254 行目〜)が起動のすべてです。上から読むと以下の順で進みます。

  1. config.Load(configPath) — TOML 設定ファイル読込(無ければデフォルト値)。Spring の application.yml に相当。パスは resolveConfigPath() が決め、環境変数 TACPENDIUM_CONFIG_PATH で E2E 用に差し替えられる
  2. prepareDataDir() — 既定データディレクトリの自動移行(M28-01 の Tacpendium 改名にともなう「コピー → 検証 → config 書換 → 旧の退避」。main.go:265)。ログ出力先が旧ディレクトリ配下でありうるため、ロガー初期化より前に行う、という順序制約がコメントに明記されている
  3. applog.Init() — ロギング初期化(標準ライブラリ log/slog + ローテーション)
  4. migration.Run() — マイグレーション自動適用(main.go:279)。Flyway の起動時適用と同じ
  5. dbinfra.Open() — SQLite 接続オープン。WAL モード等の PRAGMA を適用
  6. DI 配線(main.go:295-386)— repository → service → handler の順に依存を手書きで注入。Spring の DI コンテナがやることを、Go では New() 関数の呼び出しで明示的に行う
  7. ポート競合フォールバック(L-04、main.go:390-410)— netutil.ListenAvailable() で先にリスナを確保し、既定ポートが使用中なら次の空きポートへ。確保した実ポートで CORS 許可 Origin を構築する
  8. echo.New() + ミドルウェア登録(RequestID / Logger / CORS / Auth / UserContext の 5 本。main.go:460-475)。Auth(簡易パスワード、M22-01)は「CORS の後ろ」、UserContext(利用者解決、M22-02)は「Auth の後ろ」と、順序自体が設計としてコメントに書かれている
  9. RegisterRoutes() をドメインごとに呼びルート登録(main.go:477-536)
  10. e.Listener = listener + e.Start(bindAddr) — 確保済みリスナで HTTP サーバー起動。以後リクエストを待ち受ける
cmd/tacpendium/main.go:344-347, 487(タグ機能の DI 配線とルート登録)
// M3-01: タグ CRUD API の DI 配線
tagRepo := tagrepo.New(sqlDB)                   // repository を作る(利用者作成時の既定タグ生成で userService とも共用)
tagService := tagsvc.New(tagRepo)               // repository を service に注入
tagHandler := taghandler.NewHandler(tagService) // service を handler に注入
...
taghandler.RegisterRoutes(apiGroup, tagHandler) // /api/tags 系ルートを Echo に登録
Spring との最大の違い: DI が「見える」 Spring では @Autowired / コンストラクタインジェクションで、どのクラスがどこで組み立てられるかはコンテナ任せです。Go にはコンテナがなく、main.go に依存グラフ全体が手書きで並びます。最初は冗長に見えますが、「このハンドラは何に依存しているのか」を追うときに main.go を見れば全部書いてある、というのが Go 流の明示性です。

レスポンスは逆順に戻り、最後に TanStack Query がキャッシュを更新して React が画面を再描画します。具体例で言うと:

  1. ユーザーがタグ管理画面で「+ 新規作成」→ フォーム入力 → 保存をクリック
  2. React のフォームフック(useTagFormDialog)が zod でクライアント側バリデーション
  3. ミューテーションフック(useTagManagement の createMutation)が tagApi.create() を呼ぶ
  4. fetch("/api/tags", { method: "POST", body: JSON.stringify(...) }) が飛ぶ
  5. Echo が POST /api/tags にマッチするハンドラ Handler.Create を呼ぶ
  6. ハンドラが JSON を Go の構造体に Bind(逆シリアライズ)し、サービス CreateTag を呼ぶ
  7. サービスが VAL-T01(名前重複)/ VAL-T02(空名)を検証し、リポジトリ Create を呼ぶ
  8. リポジトリが INSERT INTO tags ... を実行
  9. 作成されたタグが構造体→JSON に変換されて 201 Created で返る
  10. ミューテーション成功時に invalidateQueries({ queryKey: queryKeys.tags.all() }) が走り、一覧クエリが「古い」と印付けされる(クエリキーは M24-08 で web/src/lib/query-keys.ts に集約された。文字列リテラル ["tags"] の散在をやめ、キー階層を 1 か所で定義する)
  11. TanStack Query が自動で GET /api/tags を再取得し、新しいデータで React が一覧を再描画

この 11 ステップの実コードを 1 行ずつ追うのが タグ管理ウォークスルー です。
