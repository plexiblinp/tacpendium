設計卓 Code 移行 — 開発者向け運用説明書

Tacpendium ／ 2026-08-11 ／ 開発者裁定にもとづく運用変更 ／ 正本 docs/progress/20260811-design-desk-surface-study.md
設計卓（親チャット）が Web 版チャットから Claude Code へ移りました。あわせて Web 版の役割が変わり、実装ソースの見え方を守るための新しい手順が 1 つ増えます。この文書は「あなたが何をするか」だけを書きます。理由と根拠は正本にあります。

003 行でいうと

  1. 設計卓は Claude Code で動かします。指示書もボードも DES も、設計卓が自分で書いて commit します。あなたがコピペで運ぶ作業が消えます。
  2. Web 版チャットは「個別設計チャット」になります。親をやめ、長い相談だけを引き受けてレポート 1 本を返す係です。設計を変える権限は持ちません。
  3. 設計卓のセッションでは、最初に 1 コマンド打たせます。bash scripts/design-desk-arm.sh — これで実装ソースが作業ツリーから消え、設計卓から見えなくなります。

01何が変わったか

項目これまでこれから
設計卓（親）の場所claude.ai の通常チャットClaude Code（PC でもクラウドでも可）
ドキュメントの更新設計卓がパッチを出す → あなたが貼る／別セッションが当てる設計卓が自分で Edit して commit
ボード（517 KB）の更新設計卓が全文を出力 → あなたがコピーして貼る1 行を直接 Edit
資料の渡し方プロジェクトナレッジ常設 ＋ GitHub 直読 ＋ Sync now不要（HEAD をそのまま読む）
Web 版チャット親（設計卓）個別設計チャット（使い捨て・権限なし・レポート 1 本）
実装ソースの見え方物理的に見えない（Web だから）物理的に見えない（sparse-checkout で消すから）
POINT 「Code に移ったからソースが見える」わけではありません。見えるようになったのは docs/ .claude/ scripts/ だけです。internal/ web/src/ などの実装ソースは、これまでどおり設計卓から見えません。担保の手段が「Web だから」から「消したから」に変わっただけです。

02あなたがやること

増えるのは実質 1 つ（武装の確認）、減るのは 3 つ（コピペ運搬・Sync now・パッチの貼り付け）です。

設計卓セッションを始めるとき

  • Claude Code を開く（PC なら devContainer、外出先なら claude.ai/code）
  • ブランチ名を claude/desk-YYYYMMDD-N にする（1セッション1ブランチ。詳細は §03.5）
  • 起動キットの §2 プロンプトを貼る（先頭に武装コマンドが入っています）
  • 設計卓が bash scripts/design-desk-arm.sh を実行して報告するのを確認する
  • 報告に「作業ツリーに残した領域: docs .claude scripts」と出ていればOK
確認のしかた 自分で確かめたいときは bash scripts/design-desk-arm.sh --status を打ってください。武装の有無と、いま作業ツリーに何があるかが出ます。トップレベルが docs/ .claude/ scripts/ だけになっていれば武装できています。

設計卓セッションを終えたあと（PC の場合）

同じ作業ツリーで実装作業をするなら、武装を解除してください。解除は設計卓（AI）からはできない設計になっています。あなたの端末で次を打ちます。

git sparse-checkout disable
rm tmp/.design-desk-armed
忘れたらどうなるか 次に開いた製造セッションで internal/ が見つからず作業が止まります。壊れるわけではありません（sparse-checkout はファイルを消しているだけで、git の中身は無傷です）。上の 2 行を打てば元に戻ります。
なお マーカーだけ残って実装ソースが復活している状態はガードが検知して止めます（前提が崩れているため）。

クラウド（claude.ai/code）の場合

セッションごとに新しい環境が用意されるので、解除は不要です。次のセッションは武装なしで始まります。

03M20 + M21 の並列運用

並列で設計したいというご要望を反映した構成です。

┌──────────────────────────────────────────────────┐ │ 親（設計卓） Claude Code・メインツリー・1つだけ │ │ 契約2枚（M20/M21）／採番／ボード／DES反映／指示書 │ └──────────────────────────────────────────────────┘ │ サブエージェントへ外注（使い捨て・コンテキスト分離） ↓ [個別設計] [個別設計] … → レポート1本ずつ返す │ 指示書 ↓ ┌──────────────┐ ┌──────────────┐ │ 製造 M20レーン │ │ 製造 M21レーン │ ← git worktree 2本 └──────────────┘ └──────────────┘
絶対に守ること 親は 1 つだけです。M20 用と M21 用に設計卓を 2 つ立てないでください。契約を出す人が 1 人であることが、DES の所有権が衝突しない唯一の理由になっています（parallel-ops §04）。
M18/M19 の並列で壊れた 4 件のうち 3 件は、設計卓が Web にあったことが直接の原因でした。とくに「設計卓が repo を見られないまま『反映済』と宣言し、独立監査が 2 度走った」件は、並列だと 2 倍露出します。今回の移行はここに効きます。

長い相談をしたくなったら

Web 版チャットを個別設計チャットとして起動してください。親が起動プロンプトを作ります。設計を変える権限は与えず、最後にレポート 1 本を出させて、それを親に渡します。外出先でスマホから設計を進めたいときも、この形になります。

03.5ブランチの切り方と、設計卓の交換

Claude Code on the web は、セッション開始時に作った1ブランチ上で作業します。切り替えられません。それを前提にした形です。

設計卓と製造は、どちらも main から切ります

main ──┬─→ claude/desk-YYYYMMDD-N （設計卓・docs のみ） ──→ main │ └─→ claude/m20-01 （製造・code + progress） ──→ main
ブランチ誰が触る範囲マージ条件
claude/desk-YYYYMMDD-N設計卓docs のみ（武装で実装ソースを持たないため）すぐマージ可（docs 系）
claude/m20-01製造code ＋ progress手動E2E 通過後
設計卓ブランチから製造を分岐させないでください 自然に見えますが、3つ問題が起きます。
① あなたのマージ作業が倍になります — マージは人間限定なので、「製造 → 設計卓 → main」だとサブごとに2回になります。
② ボード・registry・backlog の正本がブランチ上に載ります — 「main の版と分岐版のどちらが正か」が曖昧になります。別リポジトリを却下したのと同じ理由です。
③ 設計卓は fetch できません（deny）。長く生きるほど分岐点が古くなります。

分岐させなくて大丈夫な理由：設計卓は武装で internal/ web/src/ を持っていないので、触るファイルが物理的に分かれていて衝突しません。そして製造が要るのは「マージ済みの指示書」であって、設計卓の作業中ブランチではありません。指示書は docs なので、書けた時点ですぐマージできます（remote-ops §1-2 が既にそう定めています）。

1つだけ注意 followup-backlog.md は設計卓と製造の両方が書きます（製造・レビューの停止時記録が §J に入るため）。並列だとここだけコンフリクトしえます。今までも同じなので新しいリスクではありませんが、マージのとき目に留めてください。

設計卓をいつ作り直すか

これまでは自己申告・感覚・スクロール量で判断されていましたが、Code では判定の芯が変わります。parallel-ops §05 は本来こう設計されていました。

本来の設計 状態は repo のボードファイルへ出す ＝ いつでも使い捨て可

Web 版でこれが成り立っていなかったのは、ボード更新が「全文出力 → あなたが貼る」という手作業で、「未反映5件まで溜めてよい」という上限を設けざるを得なかったからです。反映係の廃止と Code 化で「未反映」という状態自体が消えます。ボードは常に最新なので、交換コストがほぼゼロになりました。

#作り直すタイミング理由
1サブマイルストーンの完了時（既定）製造が main へマージされると設計卓ブランチは古くなります。fetch できないので、新しい情報を取り込む唯一の方法が「作り直し」です
2/context が閾値超え使用量が数値で出ます。スクロール量より正確です。閾値は M20 の1サブを回して実測してから決めましょう
3裁定・契約を出した直後大きな判断のあとは探索の残骸が積もっています。結論を出した直後が一番安く畳めます
4本人の申告残しますが、1〜3で先回りできれば到達しないはずです

作り直す前のチェック

  • git status がクリーン（未コミットを抱えたまま畳むとブランチが宙に浮きます）
  • push 済み
  • ボードが最新（マイルストーン状況・予約レンジ・裁定ログ）
  • PR を出した（あなたのマージ待ち）
減る作業 引き継ぎプロンプトを書かせる必要がなくなります。次の設計卓はボードから起動できます（これが parallel-ops §05 の本来の設計です）。ボードが常に最新である限り、引き継ぎ資料を別に作るのは重複作業になります。

04なぜ「別リポジトリ」にしなかったか

ご提案いただいた案について、採らなかった理由を残しておきます。

ご指摘は正しく、実測で裏が取れました。.claude/settings.json は cat sed head grep rg find をパス制限なしで許可しているため、Read ツールだけを塞いでも sed -n '1,200p' internal/… が確認プロンプトすら出さずに通ります。フックだけでは足りないというご判断はそのとおりでした。

ただし別リポジトリには、この方式が消そうとしている問題を呼び戻すという代償があります。

代償中身
正本が2つになるplaybook §21.3「現行版の正本は repo に置く」は、設計卓が repo を見られないまま『反映済』と宣言した事故の是正でした。disk が2つあると「どちらが正か」「本当に着地したか」が再び曖昧になります
検査が両側にまたがるgenerate-code-facts.sh はコードを読んで docs/handover/code-facts.md を書きます。設計卓の事実源そのものがリポジトリをまたぐことになります
製造の手間は減らない指示書30本を製造が読み、progress 66本を製造が書きます。分離しても製造が2リポジトリ持つだけです
軽くもならないdocs は 20 MB、実装は約 5 MB。docs のほうが大きいです

sparse-checkout なら、物理的に消えるという性質はそのままに、disk は1つのままです。コミットは同じ場所に着地し、あなたのマージ手順も変わりません。

05担保のしくみ（読まなくても運用できます）

仕組みを知っておきたいとき用。3 枚重ねになっています。

① 物理排除scripts/design-desk-arm.sh

実装ソースを作業ツリーから消します。ファイルが無いので cat も sed も grep もまとめて空振りします。「どのツールを塞ぐか」を考えなくてよくなるのがこの層の価値です。

② git 系の遮断.claude/hooks/design-desk-guard.sh

ファイルを消しても git show HEAD:internal/… なら中身を取れてしまいます。この残り経路だけをフックで塞ぎます。「危ない操作を並べて禁止する」のではなく「安全な操作だけを許す」書き方にしてあるので、数え漏れが起きません。docs/ 相手なら git log -p -- docs/ のように範囲を付ければ通ります。

③ 接触の記録成果物の「読んだ資料」節

実装パスに触れた記録を成果物に出させます。これは新しい規則ではなく、parallel-ops §06 のレポート様式にもとからある項目です。

自分で武装するなら自分で外せるのでは？ そのとおりですが、性質が違います。武装しないリスクは、ls すれば一目で分かります（トップレベルが3つだけ）。武装後に外すリスクは②が塞ぎます — 外す経路が git sparse-checkout／git worktree／マーカー削除の3つしかないからです。Read の広域遮断が破られたのは経路が無数にあったからで、消してしまえば有限になります。
設置済み・自己検査つき 3枚とも動いています。①と②はどちらも --self-test を持ち、常設検査 check-artifact-integrity.sh の対象に登録してあります（壊れていると「守れていないのに守れているように見える」ため）。自分で確かめるなら: 
bash scripts/design-desk-arm.sh --self-test          # 武装の前提6項目
bash .claude/hooks/design-desk-guard.sh --self-test  # 通す12件・塞ぐ17件
bash scripts/check-artifact-integrity.sh             # まとめて
なお②の設置には、あなたの明示的な許可が必要でした。フックはツールの実行を止める仕組みなので、AI が勝手に .claude/hooks/ へ書けないよう保護されています。今後フックを増やすときも同じ確認が入ります。
