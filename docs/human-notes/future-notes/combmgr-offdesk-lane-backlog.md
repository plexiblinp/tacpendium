# Tacpendium 外出レーン・バックログ

> **これは何か**：仕事中・移動中など「机に座れない」時間に Claude へ投げられる種のキュー。各項目に *deliverable*（返ってくる物）と *なぜ E2E 不要か* を付す。通勤のたびに即投入できる状態を保つためのもの。
> **最適化対象**：トークン消費でも稼働率でもなく、**机でしかできない仕事（判断・E2E・レビュー）を前倒しで減らすこと**。週間枠の余りで机時間を削るのが目的。
> 作成日：2026-06-26（随時更新）

---

## 0. 使い方 — 振り分けルール（1行）

> **E2E 不要 ∧ 本体へ当日マージしない** → 外出枠。それ以外 → 机の5時間枠。

- **指標は「机時間が減ったか」**。稼働率を埋めること自体は目的でない（handover：週間枠は天井であって埋める対象ではない／希少資源は人間のレビュー時間）。
- **逆効果に注意**：孤立コードの量産は、安い資源（週間枠）で高い資源（あなたのレビュー・マージ待ち）を増やす。だから外出枠は**コードより思考・調査の成果物を優先**。
- **優先順位**：机時間を最も削る §2（人間ゲートの事前咀嚼）＞ §1・§4（調査）＞ §3（需要発掘）＞ §5（コード。レビュー債務を生むので最後）。
- 投入の型：いずれも「まず仕様/狙いを説明 → §1 プランをClaudeに提案させ、合意まで着手させない」。read-only 調査は推奨 Sonnet、判断咀嚼・設計は Opus。

## 1. 将来機能の調査・需要検証（read-only・deliverable＝ドキュメント）

**E2E 不要の理由（共通）**：成果物が文書でコードでない＝E2E の概念が無い。本体リポジトリに一切触れない。レビューは「読んで筋が通るか」だけで債務にならない。

- **②-5 キャラ対策ツリー／チャートの設計探索** — データに触れず、情報構造と入口設計だけ整理。→ 設計オプションメモ。〔future-features 既載・要件未確定なので今は作る前の整理が最も効く〕
- **②-6 技相性・差し返しの位置づけ整理** — 差し合い（メモ用途）と差し返し（確反・連携の親戚）の線引き、既存の器に乗るか。→ 概念整理メモ。〔概念重複回避の判断材料〕
- **②-7 観察ベース行動分析の方式スパイク** — 人が観察を貯め AI が頻出を"仮説"で集約する枠の、誤検出耐性・ローカル限定・対象指定の設計。→ 方式比較メモ。〔AI＝文章処理の線を外さない設計が肝〕
- **AI 機能の拡張方向** — 現在メモ（一人SNS）のみ。"文章処理（要約・分類・再構成）"を共通レイヤに切り出す形の素描。→ アーキ素描。〔ai-feature-draft / persona-analysis-frameworks 参照。判断・生成・断定には広げない〕
- **FTS5（全文検索）の設計スパイク** — *データに触れず方式比較だけ*（FTS5 vs LIKE、トークナイザ、対象テーブル、移行影響の机上評価）。→ 設計メモ。〔実装・スキーマ着手はしない＝専用チャット送り。ここは下調べに限定〕
- **ナビ（ヘッダ）再設計の探索** — 機能増で横並び破綻。目的グループへの畳み方、入口を増やさない方針の案出し。→ IA 案メモ。〔横断的設計課題・実装は別途〕
- **GitHub コンボリポジトリ構想の下調べ** — QMK 型集約・アカウント不要の受け口案の実現方式と運用コストの机上評価（やるか自体も保留のまま）。→ 構想評価メモ。〔pending-decisions 🔵 由来。2026-07-02 改善レーンが追記（pending-decisions「取りこぼし」の⑤解消）〕

## 2. 人間ゲート決定の事前咀嚼（**机時間を最も削る枠**・deliverable＝オプションメモ）

**E2E 不要の理由（共通）**：あなたが机で下す決定の「選択肢・移行コスト・影響範囲」を先に文書化するだけ。コードを書かない＝マージも E2E も無い。机では**読んで決めるだけ**に圧縮される。

- **M14（配布是正・スキーマ整理）の意思決定パッケージ化** — 温存/削除の境界、段階削除の順序、REQ-001 FR704 降格の改訂文案、`dbtest.Setup` 波及。→ 決定用メモ（あなたは机で○×を付けるだけ）。〔研究は実施済み。研究結果を"決定可能な形"に変換するのが本枠。最重要〕
- **M16（SA 消費・起き攻め・小数）の schema-diff 案** — 既存 `combmgr-friend-feedback-datamodel-issues.md` の論点①〜③を、具体的な列追加/型変更の差分案＋移行手順まで一段詰める。→ schema-diff オプションメモ。〔承認ゲートの素材。SA 消費の意味〔記録のみ/検証連動〕は選択肢として両提示〕
- **M19（認証・版管理・同時編集）の設計オプション** — 簡易ログイン方式、楽観排他/version 列、CORS/CSRF ポスチャの選択肢と trade-off。→ 設計オプションメモ。〔データの根・認証は人間判断。先に選択肢を並べておく。※本項の「M19」は組み替え前の旧番号（新番号では M22＝協調基盤）〕
- **M17 recipe_cache の eager/lazy 判断材料** — 無効化トリガの全表示箇所インベントリ（M12-2 教訓）と eager/lazy の比較。→ 判断メモ。〔read-only 調査ベース。配線実装は机/本体側。※本項の「M17」は組み替え前の旧番号（新番号では M20）〕
- **取り込みヘルパーの二段変換プロンプト設計** — ①表記正規化（曖昧・アプリ外プロンプト）→②コード確定（move マスタ厳密照合・アプリ側）の役割分担を外さない実プロンプトの設計。→ 設計メモ。〔新番号 M17（流通基盤④）前提。pending-decisions 🔵 由来。2026-07-02 改善レーンが追記（「取りこぼし」の①解消）〕
- **セットプレイ自動提案の精度ゲート設計** — 本実装前デモの品質確認の観点・合否基準・評価データの設計。→ ゲート設計メモ。〔新番号 M19 前提。pending-decisions ⏳ 由来。2026-07-02 改善レーンが追記（「取りこぼし」の②解消）〕

## 3. 届きにくい層の需要発掘（deliverable＝設計・ヒアリング素材）

**E2E 不要の理由**：要望駆動を機能させる"前提づくり"。文書のみ。

- **上級者ヒアリング設計** — 何を・どう聞くか、観察フレーム（persona-analysis-frameworks 適用）、上位プレイヤーを定期ループに入れる運用。→ ヒアリング設計メモ。
- **サイレントチャーン対策** — 母数が小さく黙って離脱する層（特殊キャラ・上級者）の不満を能動的に拾う仕組みの案。→ 施策メモ。
- **カジュアル層 FB の受け皿設計** — 到着待ちのカジュアル FB を layer-1〜3 トリアージに載せる雛形。→ トリアージ・テンプレ。

## 4. OSS 健全化・法務追従の調査（read-only・deliverable＝レポート）

**E2E 不要の理由**：監査・調査で本体ロジックを変えない。出力はレポート。

- **依存ライセンス棚卸し**（H 群） — 依存の license/維持状況/脆弱性の洗い出し。→ 棚卸しレポート。〔MIT/BSD 統一方針との整合確認〕
- **法務ポスチャの追従確認** — framedata-legal / battlelog-source の前提（robots・EULA・配布禁止 HTML）に変化がないか再点検。→ 追従メモ。〔事実 in／表現 out の線の再確認〕
- **配布物のデータ来歴の机上整理** — 配布禁止 HTML・検証用 CSV を配布物から除外する切り分け（M14 と地続き、ただし*整理案*に限定）。→ 来歴整理メモ。

## 5. コードだが非クリティカル（レビュー軽め枠・**§1〜4 を切らした時だけ**）

**E2E 不要の理由（共通）**：隔離リポジトリの純モジュール。単体テストで自己検証し、本体 UI に組み込まない＝画面通し E2E は不要。本体マージは後日あなたが机で（その時に E2E）。**ただしマージ債務は生む**ので、§1〜4 より後。

- **需要検証プロトタイプ**（`combmgr-prompt-memo-foundation-draft.md`・投入可） — 一人SNS知識管理の検証用。"レビュー"＝需要を検証できたか、で済む。〔本体マージ前提でない＝債務が軽い〕
- **独立汎用ツール**（`punish-finder`＝確反／`damage-lethal-calc`＝ダメージ・削りきり・投入可） — SF6 非依存の純計算モジュール。phase4／独立ツール用途。〔damage 系はあなたのドメイン値指定が要る＝完全無人ではない。FR307 で本体は自動計算しない方針なのでツール止まり〕
- **エクスポートの欠落分**（PNG／クリップボード TSV） — 研究で未充足と確定した分だけ `visual-export`／`csv-export` の該当アダプタ。〔充足済みなら無し＝研究結果が正〕
- **物理コントローラの判定コア**（FR107/108） — チャタリング/同時押しを整える純関数（入力イベント DTO → 整形列）。〔切り出すのは判定ロジックのみ。入力→ステップのマッピング・Gamepad イベント源・配線は本体側＝外出枠に出さない。FB④（M15+M18 通し。※「M18」は旧番号＝新番号では M21）・FB⑦（要ドメイン確認）に縛られる〕
- **本プロジェクト外の自律実行** — それ自体に価値がある物のみ。〔枠を埋めるための make-work は入れない〕

## 6. このレーンに入れない（**机専用**・出すと品質か机時間を悪化させる）

- **E2E が要る本体作業**全般（外出先で検証できない＝自律で進めすぎると不安、の核）。
- **当日中に本体へマージしたいもの**（マージ＝机仕事）。
- **破壊的マイグレの"実行"**（M14-01/02/03）。咀嚼〔§2〕までは外出枠、実行は机。
- **認証・認可の配線**（M19 実装。※「M19」は旧番号＝新番号では M22）、**スキーマ変更の commit**（M16 実装）。データの根は人間ゲート。
- **make-work**（稼働率を埋めるためだけの孤立コード・外部タスク）。handover の戒めに反する。

## 付記 — 育て方

このバックログは**消化したら補充する**前提。特に §1〜2 は、調査が決定を生み、決定が次の実装を生むので、回すほど机時間が減る複利枠。§5 のコードは在庫であって主食ではない。種が §1〜4 で切れそうになったら、future-features と open-issues から次の調査テーマを補充する。
