## 0. 結論

- **初期実装は「手動リレー方式」。API（BYOK）は後から任意機能として追加。**
- **ただし全機能に API とリレーの両方の口を用意する**（開発者確定 2026-07-27）。リレーは「体験は劣るが対象ユーザーが多い」経路であって、劣後の経路ではない。
- **最強の論拠は実績**：一次メモに書かれていないが、**本アプリは既にリレー方式を実運用している**（既存コンボの変換・取り込みヘルパー）。新方式ではなく**既存方式の適用範囲拡大**であり、プロンプト設計の勘所も溜まっている。
- **市場の読み（確定の理由）**：API 課金者より **ChatGPT Plus / Claude Pro 等のサブスク課金者のほうが多い**。

---

## 1. リレー先行を支える論拠（一次メモの補強）

一次メモの利点リスト（サブスク活用・キー不要・従量課金なし・対話で微調整・実装が軽い・特定事業者に依存しない）はいずれも妥当。加えて：

### 1.1 プライバシー上むしろ優れている（副次でなく主要な正当化）

- メモ機能は**「愚痴でもいいから書け」**という設計。その内容が API 経由で黙って外部送信されるのと、**ユーザーが自分で貼り付ける**のとでは意味が違う。
- 一次メモの「ユーザー自身が送信内容を確認できる」は、**副次的利点ではなく主要な正当化**。

### 1.2 API の本当のコストはレビュー時間

- 一次メモは API の欠点を課金・キー管理として挙げるが、**本プロジェクトにとっての本当のコストは恒久的な保守面**：複数プロバイダ・モデル廃止・価格改定・ストリーミング・キャンセル・再試行・料金推定。
- **希少資源はレビュー時間**という中心価値に照らすと、これは**永久に払い続ける税**。

---

## 2. 用途によって必要な機械化のレベルが違う（一次メモの過剰装備を削る）

| 用途 | 出力の性質 | 必要な装備 |
|---|---|---|
| **取り込みヘルパー（既存）** | **アプリのデータになる** | JSON スキーマ・境界マーカー・**構文検証**が要る |
| **記事・チェックリスト・統括・整理** | **人が読む散文** | パースも検証も**ほぼ不要** |

- 一次メモの「出力形式の安定化」一式（JSON 要求・スキーマ明示・前置き禁止・コードフェンス禁止・構文検証）は**構造化ケースから借りた重装備**。**散文用途にはほぼ不要**で、ここを分けると初期実装はさらに軽くなる。
- 境界マーカーは**用途タグの担体として残す**（§4）。

---

## 3. API が本当に必要になる条件＝対話型 AI 返信

一次メモが見落としている分岐点。AI 構想は**頻度の異なる2種類**を含む：

| 種別 | 例 | 判定 |
|---|---|---|
| **低頻度・バッチ** | 記事化・チェックリスト・VOD 統括・比較の整理 | **リレーで十分**（数回のコピペは許容範囲） |
| **高頻度・対話** | メモ機能の**七色 AI 返信**・ペルソナ返信 | 1投稿ごとのコピペ往復は **SNS 的体験を壊す** |

> **API は「後から追加」ではなく「対話型 AI 返信を実装する時まで作らない」。** 需要駆動の具体化。
> ただし**メモ機能にもリレーの口は含める**（開発者確定）。API 前提の機能にしない。

---

## 4. 単一受け口（確定方針・拡張性の核）

**リレーの貼り戻しは、機能ごとに置かず「AI 出力を取り込む」単一動線にする。**

### 4.1 拡張性を守る唯一の鍵

**受け口が「何の出力か」を知らないこと。**

- 貼り戻されたテキストに**用途タグが埋め込まれており、受け口はタグを見て担当ハンドラへ渡すだけ**。
- タグは**プロンプト生成時に埋め込む**ので**ユーザーは意識しない**。境界マーカーに用途を含めるだけで済む。
- **効果**：新機能（VOD 統括・比較の整理）が増えても**受け口のコードは変わらない**。ハンドラを1つ足すだけ。
- 逆に受け口が用途ごとの分岐を持つと、機能追加のたび中央が肥大する。
- → **単一ファイル HTML エクスポートで採った「容れ物＋寄稿者」と同じ形**（`combmgr-html-export-design-memo.md` §2）。

### 4.2 着手前の必須確認

- **取り込みヘルパーの既存実装が、この形になっているか実コードで確認する。**
- 既にリレーが動いているので、単一受け口を作る＝**既存動線をそこへ合流させる**話になる。**見ずに新設するとリレーの受け口が2つできる＝継ぎ目のドリフト。**

### 4.3 決めておくのはここだけ

拡張性の観点で先に決めるべきは §4.1 の構造のみ。**検証の粒度・UI の置き場・エラー表示は実装時でよい**（開発者確定：確定は実装時に委ねる）。

---

## 5. 両方の口を用意するための構造（後から API を足せる条件）

- **AI 呼び出しを1つの内部インターフェースに集約し、リレーと API をその実装として並べる。**
  - リレー ＝「プロンプトを出す／結果を受け取る」
  - API ＝「送る／返る」
  - **上位の機能（記事化・統括・返信生成）はどちらを使っているか知らない。**
- **プロンプト生成器は両方で共有する。** リレー用と API 用を別に書かない（二重表現）。
- ここを分けずにリレー前提で UI を作ると、**API 追加時に全機能を書き直す**ことになる。

## 6. 会話が発展した場合の取り込み（メモ機能・重要）

### 6.1 開発者の懸念（正しい。設計で表明する）

> 基本的には API と同じ**一回きりのチャットの結果を推奨**したい。**長いセッションほどユーザーが AI を誘導してしまい、事実よりも望む結論へ着地する可能性が高い**ため。ただしこれに従うユーザーは少ないと見られる。

- これは**アプリの中核原則そのもの**（AI に断定させない・出力は仮説/要約止まり）。
- 誘導された結論は、AI が生成した意見でありながら**ユーザー自身の意見の反響**でもある。**最も紛れやすい形の断定。**

### 6.2 対策＝禁止でなく「識別」

**紛れ込みを防ぐのではなく、紛れ込んだものが後から見て分かるようにする。**

1. **取り込み時に出自を記録する**：**一回きりの生成か／会話の抜粋か**。**表示でも区別する。**
2. **発展度ティアでの扱い（メモ機能に既に器がある）**：発展度5ティアで「AI 返信のみ」は下位、「人間返信・要約素材」が上位。**会話の抜粋はユーザーが誘導した AI 出力であって人間の思考ではない**ので、**AI 生成側のティアに置く**。
   - **人間発言と同格にすると発展度の指標が壊れる。**
3. **貼り戻しの形式は「まとめ」を要求する**：会話ログ全文でなく、**AI に最後に要約させたもの**を貼る。**長さ対策であり、同時に誘導の圧縮**でもある。

## 6.5 外部の実発言を材料として引く（アイデア・保留）

> **アイデア記録のみ。需要が見えてから判断。** 発端は「**Grok を連携させれば X からよりリアリティのある返信を引けるのでは**」という開発者の着想（2026-07-27）。検討の結果、**モデル推奨ではなく用途として立てる**形なら原則を曲げずに実現できると整理した。

### 6.5.1 発想の核（開発者）

**「全く同じ悩みを抱えた人がいて、有益なフィードバックで解決したパターンが X 上にはある。その場合はそれをそのまま持ってきて、ユーザーが検証する。」**

- **それっぽい批判意見を生成させるより、実在の解決事例のほうが価値がある。**
- 理由：**それは意見でなく事例**だから。「あなたはこうすべき」ではなく「こういう人がこう解決した」。
- **生成された批判はどこまでいっても文章の尤もらしさだが、実在の解決事例は反証可能**（試して駄目なら駄目と分かる）。
- ユーザーが検証する前提は、**アプリの原則（AI 出力は仮説止まり・検証はユーザー）とそのまま一致する**。

### 6.5.2 成立する形／崩れる形

| | 内容 | 判定 |
|---|---|---|
| **(a) 実在の発言を持ってくる** | 外部の実発言を**検索・要約し、出典を明記**する | **可**。`combmgr-pending-decisions.md` の「本人の"声"が欲しい場合の唯一の安全域＝材料 in／要約 out」と同じ形 |
| **(b) X らしい返信を生成する** | 実在しない格ゲープレイヤーが実在の攻略について意見を言う | **不可**。AI が攻略を断定する経路そのもの。**七色 AI 返信の枠内に置くとリアルに見えるぶん危険度が上がる** |

**(a) だけを取るなら筋が通り、(b) が混ざると崩れる。** BYOK・リレー方式である以上、実際に何が返るかはユーザーの環境次第で開発者は制御できない。→ **プロンプトと UI で (a) に寄せる設計が要る。**

### 6.5.3 特定モデルを推奨しない（確定）

- **「Grok 推奨」と書いた瞬間、廃止・仕様変更・X のポリシー変更にアプリが縛られる。** §7 のモデル抽象化方針（画面に具体的モデル名を出さず fast/balanced/quality の論理モデルを持つ）と矛盾する。
- → **モデルを推奨するのでなく、「外部の実発言を材料として引く」という用途を1つ立てる。** どのモデルでもよく、**Grok を使う人は結果的に X から引ける**。

### 6.5.4 用途として立てる場合の要件

- **出典（URL 等）を必須**にする。無い場合は取り込まない。
- **要約 out・生成 in なし**（意見の追加をさせない）。
- **未検証であることを保つ**（検証はユーザー。アプリは断定しない）。
- **エクスポート時も出典を保つ**（§ 法務。他人の投稿の取り込み・表示は「素材となる情報があれば元の権利者が主張しうる」に該当。CONTRIBUTING の規律と同じ）。
- **発展度ティアでの位置づけ＝実装時の論点**：X から引いた実発言は**他人の人間の発言**なので、生成された AI 返信より上に置く根拠がある（メモ機能は人間返信が最上位）。**ただし出典と未検証性を保つ限りにおいて。** 会話抜粋（§6）と同じく、**指標を壊さない置き場を決めてから実装する。**

### 6.5.5 残る懸念

- **「有益なフィードバックだけを抜き出す」は選別であり、選別は判断。** 何が有益かを AI が決める＝品質判定をさせることになり、**「AI は文章処理エンジン・知識源ではない」に対して越境**しうる。**集計は可・選別は微妙**（VOD の AI 統括で引いたのと同じ線）。
- → 実装するなら、**選別させるのでなく「関連する実発言を集めて出典付きで並べる」に留める**のが安全側。**判断はユーザーが下す**（比較機能の「フォームの構造が分析装置」と同じ思想）。

## 7. API（BYOK）側の要件（実装時の申し送り・一次メモから採用）

> 作るのは §3 の条件が来てから。以下は一次メモの内容で妥当と判断したもの。

- **BYOK**（ユーザー自身の API キー。運営者は利用料を負担しない）。
- **キー管理**：React へ渡さない／Go バックエンドのみ／OS 資格情報ストア／ログ出力しない／エラー表示でもマスク／設定から削除可／接続テスト／バックアップ対象外／Git 混入しない設計。
- **課金の透明性**：送信前に使用モデル・入力推定トークン・最大出力・検索の有無・推定料金・月間利用量を表示。**価格はコードに固定せず設定として管理**。
- **状態管理**：送信待ち／送信中／生成中／検証中／完了／失敗／キャンセル済み。**リクエスト ID で重複送信を防止**。
- **モデル抽象化**：画面に具体的モデル名を出さず **fast / balanced / quality** の論理モデルを持ち、実モデル ID はプロバイダ設定へ分離。

---

## 8. 採用しないもの（一次メモの判断を支持）

- **非公式なブラウザ操作・Cookie 取得・画面スクレイピングによる自動連携**：壊れやすい／アカウント情報を危険にする／規約上の問題／UI 変更で停止／保守が重い。
- **諦める点**（設計で解こうとしない）：ユーザーによるプロンプト改変の完全防止／消費者向け AI 画面からの結果自動取得／モデル間の出力差の完全排除／AI サービス側のシステム指示の制御。

---

## 9. リレーの操作負担軽減（一次メモから採用・実装時）

- ワンタップコピー／クリップボードから貼り付け／モデル別テンプレート／最後に使った AI サービスを記憶／スマホ向けコピー導線／**入出力の境界マーカー**（＝§4.1 の用途タグの担体）。
- **長文対策**：推定トークン数の表示／文字数警告／複数記事への分割／重複除去／優先度の低い情報を除外／**「要約後に記事化」の二段階処理**（§6.2-3 とも整合）。

## 10. プロンプト設計のレーン

- **リレープロンプトの設計は既に backlog にある**（`combmgr-pending-decisions.md` 🔵「取り込みヘルパーの実プロンプト設計。アプリ外・無料サービスで動く整形。**コマンド解決とエンジン共通化前提**」）。
- **記事生成・統括・返信生成のプロンプトも同じ設計レーンに乗せる。別物として立てない。**
