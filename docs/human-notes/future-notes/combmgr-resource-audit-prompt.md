# 自律調査プロンプト — リソース枯渇リスク監査（レポートのみ・修正なし）

> **これは調査依頼であり、修正依頼ではない。** 出力はレポート1本。コード変更・リファクタ・「ついでの修正」は一切行わない。
> **投入先**：本体リポジトリを読める Claude Code（読み取り専用の姿勢で運用）。
> **背景**：開発者の PC で実装作業中にディスク使用率 100% 張り付き→再起動する事象が発生。**原因はおそらく別プロセス（Claude Code / Codex / ビルドキャッシュ等）**だが、**本アプリがストリートファイター6 と同時起動される前提上、PC のフリーズは絶対に許容できない**ため、原因究明とは独立に**要件充足の確認**として実施する。

---

## プロンプト本文（ここから下を投入）

CLAUDE.md と docs/ の関連文書（要件・設計・アーキテクチャ）を読んだうえで、**このリポジトリのコードベース全体に対してリソース枯渇リスクの監査**を行ってください。

**これは調査のみの作業です。コードは一切変更しないでください。** 修正案は書いてよいが、適用はしない。作業ブランチも作らない。出力は下記のレポート1本のみです。

### 背景と、この監査が満たそうとしている要件

- 本アプリは**ゲーム（ストリートファイター6）と同時起動される**ことが前提のツール。**PC のフリーズ・スワップ・ディスク飽和は絶対に許容できない。**
- 本アプリの根本価値は「軽量・即応答（100ms 以内）」。ただし**それはアプリ単体の応答速度の話**であり、本監査が見たいのは**長時間稼働時の資源の振る舞い**と**ゲームと資源を奪い合う挙動**。
- 既存のコーディング方針には「アプリ外のユーザーデータを消さない」等は明記されているが、**メモリリーク／ディスク膨張／IO 競合が明示的に含まれているか不明**。本監査の副産物として、**方針へ追記すべき規律**も提案してほしい。

### 観点（この順に見る）

#### A. 無制限に増えるもの（ディスク膨張）— 最優先

「上限も失効もなく単調増加するもの」を全て洗い出す。

- **ログ**：出力先・ローテーションの有無・上限・デバッグレベルで何が出るか。**ローテーションのないログは長期稼働で最も一般的なディスク食い。**
- **キャッシュ**（recipe_cache 等）：上限・失効・破棄経路の有無。
- **生成物**：サムネイル・エクスポート成果物・一時ファイル。**作りっぱなしで消えないものはないか。**
- **SQLite**：WAL の肥大（checkpoint されているか）、VACUUM の方針、論理削除の残骸、`journal_mode` と `wal_autocheckpoint` の設定。
- **一時ディレクトリ**：`os.TempDir()` 等への書き込みで、消し忘れる経路がないか。
- 各項目について「**何が上限を決めているか**」を明示する。決めているものが無ければ、それが指摘事項。

#### B. 解放されないもの（メモリリーク・ハンドルリーク）

- **`sql.Rows` の `Close()` 漏れ**、`defer` の欠落。
- **`defer` をループ内で積む**パターン（関数終了まで解放されない）。
- **goroutine の停止経路**：起動した goroutine が必ず終わるか。context のキャンセルが伝わるか。**停止経路のない goroutine** はないか。
- **`time.Ticker` / `time.Timer` の Stop 漏れ**。
- **ファイル・HTTP レスポンスボディのクローズ漏れ。**
- **無制限に伸びるメモリ上の構造**：スライス・マップへの追記で上限がないもの、キャッシュ的な map。
- **大きなデータの一括読み込み**：ファイル全体・クエリ結果全件をメモリに載せる箇所。ファイルサイズや件数の上限は誰が保証しているか。

#### C. ゲームと同時に走る時の資源競合（本監査の核心）

**アプリ単体では問題にならないが、ゲームが CPU/GPU/ディスクを占有している最中に走ると害になるもの。**

- **バックグラウンドの定期処理**：ポーリング・定期再計算・自動保存の**間隔と重さ**。
- **起動時の全走査**：起動時に全件読み込み・全ファイル走査・整合性チェックをしていないか。
- **ファイル監視**：監視対象の範囲と頻度。
- **フロントエンドの常時処理**：ブラウザ側のタイマー・アニメーション・再レンダリングループ。**ブラウザは常時開かれている前提。**
- **DB 接続とロック**：`SetMaxOpenConns` 未設定の影響、長時間トランザクション、WAL 書き込み競合。
  - ※既知の指摘あり：接続プール上限未設定＋`setup.FindDuplicateInCombo` が rows 反復中に入れ子クエリを発行する構造。**これが本観点でどう効くかも評価する。**

#### D. エラー握りつぶし（ディスクフル時に静かに壊れる経路）

- **書き込みエラーを無視している箇所**（`errcheck` 相当の観点）。
- 特に**ディスクフル・書き込み失敗時に、握りつぶした結果データが失われる／不整合になる経路**。
  - ※既知の指摘あり：`RecomputePresetCache` が既存 cache の Unmarshal 失敗を握りつぶす（`DeletePresetCache` は判定しており非対称）。**同種の箇所が他にないか**を横断で探す。

#### E. 静的解析の導入余地

- `go vet` / golangci-lint（**errcheck・rowserrcheck・bodyclose・contextcheck** 等）が CI に入っているか。入っていなければ、**入れるべきリンタと、それが本監査の指摘のどれを恒久的にカバーするか**を示す。
- フロント側（eslint）についても同様に、リーク系ルール（`react-hooks/exhaustive-deps` 等）の有無。

### 調査の方法

- **実際にコードを読んで根拠を示すこと。** 推測で書かない。
- 各指摘には **ファイルパス:行** を付ける。
- 「見たが問題なかった」領域も**明示的に列挙する**（何を確認済みかが分かるように）。**カバレッジの申告が無いレポートは価値が半減する。**
- 可能なら**定量的な見積り**を添える（例：「1日8時間の常用でログは約 X MB 増える見込み」）。根拠が無ければ「見積り不能」と書く。

### 出力

`docs/audits/YYYYMMDD-resource-exhaustion-audit.md`（ディレクトリが無ければ作成）に、以下の構成で1本。

1. **要約**：重大度別の件数と、**もっとも危険な3件**。
2. **重大**：放置するとフリーズ・データ損失・復帰不能に至りうるもの。各項目に 根拠（パス:行）／影響の説明／**再現条件**／修正の方向性。
3. **中**：長期稼働で問題になるもの。
4. **軽微・様式**：規律として直したいもの。
5. **確認済みで問題なかった領域**（カバレッジ申告）。
6. **コーディング方針へ追記すべき規律の提案**：現在の方針に不足している項目を、**既存の「アプリ外データを消さない」と同じ粒度の文言**で提案する。
7. **静的解析の導入提案**：入れるべきリンタと、それが何を恒久的に防ぐか。

**重大度の基準**：ユーザーの PC を不安定にする（フリーズ・スワップ・ディスク飽和）／データを失う ＝ 重大。単調増加するが年単位で問題にならない ＝ 中。

### やらないこと

- **コードの修正・リファクタ・フォーマット**（レポートのみ）。
- **依存の追加・削除。**
- **設計判断**：直し方が設計に関わる場合は「設計判断事項」として申し送る。
- **憶測での断定**：確認できないものは「要確認」と明記する。

まず調査計画（どの領域をどの順で見るか）を簡潔に示してから、着手してください。
