## 0. 一行で言うと

ユーザーが書いた攻略メモを、**AIで「整形・分類・再構成・詳細度変換」する**機能。
AIは「知識源」ではなく **「文章処理エンジン」** として使う。

---

## 1. なぜ作るか（背景）

- 格闘ゲームの攻略知識は**文書化されていない暗黙知**が多く、AIの学習データには乏しい
- プレイヤーの知見はバラバラのメモに散在し、体系化されないまま忘れられる
- 「分かっているつもり」で整理されていない知識が多い
- → **散在する暗黙知を、構造化された使える知識に変換する**ことを支援したい

### この設計の核心的判断
- AIに攻略を**生成させない**（ハルシネーション・誤情報のリスクを排除）
- 情報源は**常にユーザー自身のメモ**
- AIの役割は「ユーザーが書いた内容を、使いやすい形に変形する」ことに**限定**する

## 1.5. 知識管理の中核コンセプト候補：一人SNS方式

> **位置づけ**: 知見を「書き・貯め・繋ぐ」入れ物のUIコンセプト。**現時点の有力候補**だが確定ではない。
> より良いコンセプトが出れば差し替え/併存しうる。この節は拡張前提で書く。

### 一行で言うと
知識管理を**「一人で運用するSNS」**のメタファーで実現する。タイムラインに呟き、返信で育て、引用で繋ぐ。

### 仕組み
- **とにかく書く**: 未検証の情報でも、愚痴でもいい。思いついた断片をそのまま投稿する（書く心理的ハードルを最小化）
- **返信で育てる**: 反応・解決策・検証結果を、その投稿への返信として足していく
- **引用で繋ぐ**: 引用リツイート相当で別の投稿を参照 → 階層構造から**実質ネットワーク構造（知識グラフ）**へ
- **AIが建設的批判**: 一人運用は視点が偏るため、AIが「もう一人の視点」として問いかけ・反例提示する返信をつける
- **メディア添付**: 投稿に動画・画像を添付可能
- **最終的にAIがまとめる**: 蓄積した投稿スレッドを、AIが記事やチェックリストに変換（§2の機能3・4と連動）

### なぜ優れているか（解決する課題）
| 課題 | 一人SNS方式での解決 |
|------|--------------------|
| 書く心理的ハードル（暗黙知の言語化） | 「呟くだけ」でいい。Zettelkastenのアトミックノートを自然な形で実現 |
| 知識の成熟過程が残らない | スレッド（投稿→返信）として時系列で残る。Evergreen的 |
| 状態分類が手間 | スレッドの状態が成熟度を自然に表現（返信なし=仮説、解決返信=解決済み） |
| リンクが難しい概念 | 「引用」という馴染みある操作でネットワーク構造を実現（非エンジニア向け） |
| 一人運用の偏り | AIが建設的批判で「もう一人の視点」を補う |
| フロー→ストック変換 | AIまとめ機能（§2機能3・4）が変換点になる |

### 設計上の注意点（懸念と対策）
- **SNSは「流れる」、知識管理は「貯める」**: 重要な知見が埋もれないよう、検索（FTS5）・タグ/キャラ/技での絞り込み・ピン留め・「関連する過去の投稿」のAI浮上が必要
- **AI批判の頻度とトーン**: 毎回批判されると書く気が削がれる。**ユーザーが求めたときだけ**（「AIの意見を聞く」操作）or 頻度を抑える。トーンは否定でなく問いかけ・視点提供。AI返信も一意見として扱い絶対視しない
- **「とにかく書く」と「整理する」の使い分け**: 書くフェーズではAIは黙り、整理・検証フェーズでAIが登場する設計が望ましい
- **愚痴とノイズ**: 投稿に軽い種別（気づき/愚痴/質問/検証結果等）を**任意で**付けられると、まとめAIがノイズを除外しやすい。必須にすると手軽さが失われるので任意
- **データモデルの複雑さ**: スレッド（自己参照）+ 引用（ネットワークリンク）+ メディア + AI返信 + コンボ/技紐付け。SQLiteで素直に表現可能（親投稿IDを持つ再帰構造）だが、メモより複雑

### 運用範囲：一人運用を主軸とする
- **一人運用が主軸**（自分 + AI）。設計はこれを前提に進める
- チーム運用（LAN内で仲間内 + AI）は**将来の拡張**。Tacpendiumの既存LAN/ゲスト機能と噛み合うが、最初から作り込まない
- 同じUIのまま人数だけ変わる構造が理想

### 視点・立場の仕組み（投稿者風表示）
投稿に「視点・立場」を持たせる。実態は視点分類だが、**UIはSNSの投稿者（アイコン/名前）風に見せる**。
- **目的**: 格ゲー知識は「使う側」と「対策する側」で意味が変わる（例: リュウの昇竜は、リュウ使いには使う技、対リュウでは警戒する技）。視点で知見を整理する
- **必須にする**（試行）。ただし入力負担をゼロにする3点セットで成立させる:
  - 起票時に「現在の視点」が**自動で入る**（デフォルト = メインキャラの「○○使い」）
  - **プルダウンで即切替**（認証なし。ログインユーザー的な概念だが、あくまで立場なので軽量に切り替え）
  - **投稿後の差替も可能**（間違えても直せる → 必須のプレッシャーを消す）
- **入力方法**:
  - ①キャラ選択から半自動生成（「リュウ」→「リュウ使い」「対リュウ」。表記統一）
  - ②完全自由入力でペルソナを定義（例: 立場・信頼度のニュアンスを名前で表現）
- **再利用**: 一度作った視点は登録され、次回からプルダウンで選べる（自由入力の乱立・表記揺れを防ぐ）
- **保存先**: SQLite（localStorageは使わない。Tacpendiumのデータ管理と一貫させる）。前回選択も記憶
- **ペルソナ → AI要約の重み付け**（構想）: 各発言が誰の視点かを、AI要約時の**重み付けの手がかり**にする見込み（例: 「検証済み」視点は重め、「思いつき」視点は軽め）。重みは参考程度（AI判断はブレうるので絶対視しない）。**ペルソナ設計の詳細は今後決める**

> **追加検討事項（参照）**: ペルソナ／視点・体験を扱う既存の分析フレームワーク（ジョブストーリー、上達ジャーニー、シックスハット、メンタルモデル・ダイアグラム 等）を別紙リサーチノート **`combmgr-persona-analysis-frameworks.html`** に整理した。ペルソナ設計・重み付け・まとめAIの入力骨子を詰める際の検討材料とする（いずれも将来検討であり確定ではない）。

### ターゲット習熟度・難易度の考え方
**アプリ全体を一律の難易度にしない。機能ごとにターゲットの習熟度が違う。**
| 機能 | 想定ユーザー | 許容難易度 |
|------|------------|-----------|
| コンボ管理・仮想コントローラ（入口） | 全ユーザー | 低くすべき |
| セットプレイ・比較 | 使い込む人 | 中 |
| 一人SNS知識管理 + AI | 気に入って深く使う人 | **やや高くてよい** |
- 本機能（知識管理+AI）は、**コンボ・セットプレイ管理を気に入った人が、さらに興味を持って使うもの**と位置づける
- APIキー取得・入力という参入障壁が自然に存在し、それを越える人は使いこなす意欲がある → 多少複雑でも価値が伝われば使われる
- **入口（コンボ管理）さえ簡単なら、奥（AI知識管理）は深くてよい**
- 残る難易度は、**UIで自明にできる部分はUIで**（累進的開示）、**本質的に説明が要る部分（APIキー手順・ペルソナの発想）はドキュメント・動画**で補う。操作手順は文書（更新が楽）、思想・使い方の魅力は動画、と分担
- **機能は1つに統一**（シンプル版/高機能版の2モード分けはしない＝複雑さ2倍の罠を回避）。「1つの機能が、デフォルトはシンプル、使い込むと深くなる」累進的開示で実現。シンプルにも使える仕組みは実装着手時に具体化
- **留意（仮説）**: 「気に入った人が深く使う」は仮説。先行リリースでコア機能への反応・「もっとこう管理したい」という声を観察し、需要を確認してから本実装に入る

### 既存機能との統合
このコンセプトは、これまで個別に設計してきた機能を統合するメタファーになる。
- メモ機能 → SNS投稿そのもの
- 状態分類 → スレッドの状態が自然に表現
- メモのリンク → 引用 = ネットワーク構造
- 視点・立場 → 投稿者風表示で、使う側/対策側の知見を区別
- AI変形（整形/分類/再構成/詳細度変換, §2） → まとめ機能として活きる
- AI壁打ち → 建設的批判の返信
- コンボ/技との紐付け → 投稿を関連付け
- メディア添付 → 投稿に動画・画像
- エクスポート（§5.6） → まとめた知見をHTMLでスマホ閲覧
- LANチーム共有 → チーム運用でSNS化

### 拡張性メモ（このコンセプトは確定ではない）
- 一人SNS方式は現時点の有力候補。**別のUIコンセプト（例: アウトライン型、カンバン型、グラフ型等）が浮かべば差し替え/併存を検討**
- §2以降のAI機能は、入れ物のコンセプトが変わっても流用可能なように、なるべく独立に設計する
- 「知見を貯める入れ物（§1.5）」と「貯めた知見を加工するAI（§2以降）」を疎結合に保つ

## 2. 提供する4つの機能（AIによる加工）

| # | 機能 | 内容 | 難易度 |
|---|------|------|--------|
| 1 | **整形** | 乱雑なメモを読みやすい文章に整える | 低 |
| 2 | **状態分類** | メモを「解決済み / 未解決 / 仮説段階」等に分類して一覧化 | 低〜中 |
| 3 | **再構成（記事生成）** | 複数メモを結びつけて、ニーズに沿った新しい記事を作る | 中 |
| 4 | **詳細度変換** ★ | 同じ知識を、詳細度レベル指定で出し分ける（長文記事 〜 余計な情報を削いだチェックリスト） | 中 |
| 5 | **建設的批判（壁打ち）** | 一人SNS方式（§1.5）で、投稿に対しAIが問いかけ・反例提示の返信をする。一人運用の偏りを補う | 中 |

★ = **最大の差別化要素**。同じデータを「学習中は詳細記事」「対戦直前はチェックリスト」と用途別に出せる。
他ツールにない価値。

機能5（建設的批判）は他の4つ（変形系）と性質が異なり、**AIを「対話相手」として使う**。「知識源にしない」原則は守りつつ、断定でなく問いかけ・視点提供に限定することでハルシネーションリスクを抑える。

## 3. 設計原則（最重要・必ず守る）

1. **AIの役割は「変形」に限定する**
   - ✅ 整形・分類・要約・再構成
   - ❌ 知識の追加・攻略の生成
   - システムプロンプトで「与えられたメモの情報のみを使い、外部知識で補完しない」と強く制約

2. **AI下書き → 人間確定のワークフロー**
   - AIの出力は必ず「下書き」として提示
   - ユーザーが編集・確定したものが正式データになる
   - AIの誤りがそのまま蓄積されるのを防ぐ

3. **生成物と元メモの紐付けを保持する**
   - 生成された記事・チェックリストが、どのメモから作られたか辿れる
   - 「この情報の根拠は？」を確認できる
   - パッチで情報が古くなったら、元メモを更新して再生成できる
   - ハルシネーションの検証手段になる

4. **AIなしでもメモ機能は動く（AIは完全にオプション）**
   - APIキー未設定でも、メモの作成・編集・閲覧は可能
   - Tacpendiumの「軽量・即応答・前提ソフト不要」DNAを守る
   - AI機能は「あると便利」な拡張に留める

5. **プライバシーの明示**
   - ユーザーのメモが外部AIに送信されることを明示し、同意を得る
   - ローカルLLM選択でメモを一切外部に出さない選択肢を提供

6. **システムプロンプトは出力言語ごとにネイティブで用意する**
   - **プロンプトの言語 = 出力言語の最も強いシグナル**。明示的な「日本語で答えて」指示より効く
   - 英語プロンプト + 出力言語指示だと、英語が混入しやすい（実体験ベース）
   - 日本語出力なら日本語のシステムプロンプト、英語出力なら英語のシステムプロンプト
   - 合わせる基準は「UI言語」ではなく**「ユーザーが選んだ出力言語」**
   - 各言語版で「その言語のみで出力、他言語の文字（英語・中国語の漢字等）を混ぜない」と明記
   - 完全制御は不可能。中国漢字の稀な混入等は実用上問題ないレベルまで減らすのが現実的ゴール
   - 二重管理を避けるため、**i18nリソースと同じ仕組みで管理**する（修正漏れで日英の挙動がズレるのを防ぐ）

## 4. AIプロバイダ方針

### 対応プロバイダ
| プロバイダ | 位置づけ | 備考 |
|-----------|---------|------|
| Google Gemini | **推奨デフォルト** | 無料枠あり・キー取得が最も簡単・コスパ良 |
| OpenAI | 主要対応 | 知名度最大、既にキーを持つ人が多い |
| Anthropic Claude | 主要対応 | 文章処理品質が高い |
| **カスタム（OpenAI互換）** | 上級者・ローカルLLM向け | エンドポイントURL可変。Ollama/LM Studio等に自力接続 |

- **Copilot系（GitHub/Microsoft）は非対応**（汎用LLM APIではない、BYOKに乗らない）
- **Azure OpenAIはMVP不要**（個人ユーザーに縁が薄い）

### BYOK（Bring Your Own Key）が大前提
- APIコストはユーザー負担 → 開発者はコスト最適化責任が薄い
- ユーザーが既に持っているキーを使える構造にする
- だから単一プロバイダ固定にしない

### モデル階層
- メモ変形は**高度な推論を要さない文章変形タスク**
- **ミッドティア〜budget で十分**（Flash / mini / Haiku クラス）
- **フラッグシップ（Opus/GPT-5.x/Gemini Pro）は不要** — コストが上がるだけで品質は頭打ち
- **モデル名はハードコードしない** → 設定/定数で管理。新世代が出たら設定変更で追従

## 5. 対応するAPI呼び出しの種類

### 必須
- **基本テキスト生成（chat completion）** — 全機能の中核
- **システムプロンプト と ユーザー入力の分離** — 変形ルールはシステム側、メモはユーザー側。インジェクション対策にも

### 推奨
- **ストリーミング応答** — 長い記事生成時の体感待ち時間を減らす
- **構造化出力（JSONモード）** — 状態分類の結果を構造化データで受け取り後処理を楽に

### 不要（この用途では）
- 関数呼び出し / ツール使用
- 画像入力（将来、動画/画像メモのAI解析をやるなら別途）
- 埋め込み（embeddings）（高度な検索を実装するなら将来検討）
- バッチAPI

### プロバイダ差異の吸収
- 主要3社のエンドポイント・認証・レスポンス形式の違いを内部の抽象化層で吸収
- 上位コードは「プロンプトを渡す → テキストが返る」のシンプルなインターフェースで扱う
- OpenAI互換APIを軸に組むと、カスタムエンドポイント（ローカルLLM等）も同じ仕組みで扱える

## 5.5. データ基盤（SQLiteのまま）

**結論: 既存のSQLiteで十分。Elasticsearch等の重量級ミドルウェアは導入しない。**

- ES等はJavaランタイム・別プロセス・GB級メモリが必要 → TacpendiumのDNA（単一バイナリ・前提ソフト不要・低リソース）と真っ向から矛盾
- 想定規模（コンボ1000・セットプレイ3000 + 個人メモ）にESは完全に過剰
- メモも既存のSQLiteに格納するのが自然（テキストファイル別管理は検索・紐付けが面倒になる）

### SQLiteで実現できること
- メモのCRUD・タグ/状態での絞り込み（インデックス付きWHERE）
- コンボ/セットプレイとの紐付け（外部キー・中間テーブル）
- **全文検索 → FTS5（SQLite標準の全文検索拡張）** で対応
- 長文メモ・生成記事 → TEXT型で問題なし（数KB〜数十KBは余裕）
- 動画・画像 → **ファイル本体はファイルシステム、SQLiteにはパスだけ**持つ

### 将来「賢い検索」が欲しくなったら（ESではなく）
- キーワード検索 → FTS5（今すぐ使える）
- 意味的な類似検索 → SQLiteのベクトル拡張（sqlite-vec等）or 軽量埋め込み + ローカル計算
- AIによる関連メモ抽出 → AI機能側で処理（メモを渡して判断させる）
- いずれも単一バイナリ・低リソースの範囲内で実現可能

## 5.55. 外部連携の方針（特定ソフトと密結合しない）

**結論: 特定ソフト（Obsidian等）と連携せず、汎用形式のインポート/エクスポートで「誰とでもゆるく連携」する。**

### Obsidian等と密結合しない理由
- Tacpendiumのターゲットは非エンジニアのSF6プレイヤーが大半 → Obsidian等の高リテラシー層とほぼ重ならない
- 前提ソフトの追加はNFR303/304（前提ソフト不要）に違反。二重のセットアップは非エンジニアに不可能
- 体験の分断（コンボはTacpendium、メモは別ツール）が起き、シームレスさが失われる
- 外部ソフトの仕様変更・有料化・廃止に振り回される

### 自前実装は「車輪の再発明」ではない
- Tacpendiumのメモは汎用メモではなく、**SF6攻略に特化し、コンボ/セットプレイ/技と紐付くメモ**
- 「コンボデータとメモが同じアプリ内でシームレスに紐付く」体験が独自価値 → 外部連携では得られない
- ただし**低レベルな汎用機能はライブラリで済ませる**（Markdownパース/レンダリング、エディタ基礎機能、全文検索=FTS5）。SF6特化部分とAI変形フローのみ自前

### ローカルフォルダ読み込みについて
- Claude Codeは「AIエージェントが直接ファイルを読む」構造。Tacpendiumは「アプリがデータ管理主体でAIに必要分を送る」構造で思想が違う
- メモはSQLiteに持つのが基本（MVPの正解）
- フォルダ内Markdownの一括インポートは、高リテラシー層が既存メモ資産を持ち込む補助機能としてならあり
- フォルダ常時監視・双方向同期はターゲットに合わず複雑すぎ → やらない

## 5.6. インポート / エクスポート

特定ソフトに依存せず、**汎用形式での入出力**を持つ。これにより非エンジニアはアプリ内で完結し、高リテラシー層は自力で外部ツール（Obsidian等）に持ち出せる。

### インポート（欲しい）
- 汎用形式（Markdown / テキスト / CSV）での取り込み
- フォルダ内のMarkdown一括取り込みも検討（既存メモ資産の持ち込み）
- インポート時のマッピング（どのコンボ/セットプレイに紐付けるか）をどうするかは要検討

### エクスポート（欲しい）
- 汎用形式（Markdown / テキスト / CSV）での書き出し
- **HTML出力に対応させる** ★
  - 構想: **チェックリスト形式のHTMLを出力 → 外出中にスマホで見る**
  - 対戦前・移動中に「このキャラ対策の要点」をスマホでサッと確認する用途
  - 単一HTMLファイルとして書き出せれば、スマホに送って閲覧できる（アプリ起動不要）
  - 詳細度変換（§2の機能4）の「チェックリスト形式」出力と連動させると強力
  - スマホ閲覧前提なので、HTMLはレスポンシブ・オフラインで見られる自己完結型が理想（外部CSS/JS依存なし）

### インポート/エクスポートの位置づけ
- これが「特定ソフトと密結合しない代わりの、ゆるい連携」の実体
- 「特定ソフトと連携する」のではなく「誰とでも連携できる汎用形式を持つ」のが方針

## 5.65. 構造化出力の確実性確保（モデル/サービス変更への耐性）

**課題: AIモデルがアップデートで変わったり、サービスを変えても、プログラムで扱える形式で必ず値を返させたい。**

LLMは確率的なので「お願い」だけでは不十分。**機械が検証できる契約（スキーマ）を強制し、外れたら検知して直す多層防御**を、プロバイダ非依存で自前で持つ。

### 多層防御（重ねる）
| 層 | 役割 | プロバイダ非依存 |
|----|------|:---:|
| 1. プロバイダの構造化出力機能 | 使えれば使う（最も確実だが依存する。**ボーナス扱い**） | ✗ |
| 2. プロンプトでの形式指定 | スキーマを具体例付きで明示、前置き/コードブロック囲み禁止 | ⚪️ |
| 3. パース前処理 | コードブロック囲み剥がし、JSON部分だけ抽出、前置き除去 | ⚪️ |
| 4. **スキーマ検証** | 必須フィールド・型・許容値を機械的に確認（最重要の層） | ⚪️ |
| 5. リトライ・修復 | 失敗時、エラー内容を添えて再依頼。回数上限あり（2〜3回） | ⚪️ |
| 6. フォールバック | それでもダメなら生テキストを見せ、**クラッシュさせない** | ⚪️ |

### モデル/サービス変更に強くする工夫
- **スキーマを単一の真実の源（SSOT）にする** → モデルが変わっても検証基準は不変
- プロバイダ機能（層1）を使った場合でも、**返り値を自前の層4で再検証する**（プロバイダの保証を信用しない）
- 検証は必ずプロバイダ非依存の層で行う
- テスト用の「壊れた出力」サンプル（前置き付き・フィールド欠落・型違い）を持ち、モデル変更時の回帰テストに

### 機能ごとに構造化レベルを変える
| 機能 | 構造化の必要性 | 防御の重点 |
|------|---------------|-----------|
| 整形 | 低（テキストが返ればよい） | 層3で十分 |
| 状態分類 | **高**（後で絞り込みに使う機械処理データ） | 層4を厳密に・許容値チェック必須 |
| 再構成（記事生成） | 中（本文 + 参照元メモリスト） | 層4で構造確認、本文は緩め |
| 詳細度変換 | 中（指定形式の文書） | 詳細度ごとに期待構造を定義 |

### 実装の優先順位
- **必須**: 層2・3・4・6（プロンプト指定・前処理・検証・フォールバック）
- **推奨**: 層5（リトライ）
- **任意**: 層1（プロバイダ機能、使えれば）

## 5.7. MCPについて（今回は使わない・将来の別機能）

**結論: メモ変形機能にはMCPではなくLLM APIを使う。MCPは用途が違う。**

- MCPとLLM APIは競合する選択肢ではなく、**別レイヤーの話**
- メモ変形 = 「アプリが主体でAIに文章を変形させる」 = **LLM APIの領域**
- MCP = 「AIクライアントが外部ツール・データ源を使う」仕組み。主体はAIクライアント側
- メモ変形にMCPを使うのはオーバーエンジニアリングで、BYOK・非エンジニア対応とも噛み合わない

### MCPが活きる将来シナリオ（別機能・拡張④候補）
- 「Claude Desktop等の外部AIクライアントから、Tacpendiumのデータを読み書きさせたい」場合
- このとき **TacpendiumがMCPサーバーを提供する**側になる（メモ変形とは別物）
- 対象は上級者（AIクライアント側の設定が必要）。非エンジニアのメインターゲット向けではない
- → ロードマップに「MCPサーバー提供（外部AI連携）= 拡張④候補」として残すだけ

## 6. 固定する / カスタム可能にする の切り分け

**原則: 「何を・どのAIで」はユーザー、「どう処理するか」は開発者固定**

### 開発者が固定（品質と安全性の核心）
- システムプロンプト（変形ロジック） ← **最重要**。機能の品質そのもの
  - **出力言語ごとにネイティブで用意**（日本語版・英語版）。i18nリソースとして管理
  - ユーザーが選んだ出力言語に応じて、使うプロンプトの言語を切り替える

- 出力フォーマットの規定（詳細度ごとの構造、分類スキーマ）= スキーマのSSOT
- プロンプトインジェクション対策（メモを渡す際のサニタイズ・区切り）
- 構造化出力の多層検証（5.6参照）
- エラーハンドリング（APIエラー時の挙動・リトライ・タイムアウト）
- デフォルトモデル（推奨値の提示）

### ユーザーがカスタム可能（コスト・選択・好み）
- APIプロバイダの選択
- APIキーの入力（ローカル暗号化保存）
- 使用モデルの選択（コスト/品質のトレードオフをユーザーが選ぶ）
- 詳細度レベルの指定（機能そのもの）
- 出力の言語（日本語/英語等）
- 出力のトーン・長さの軽い好み（任意）

### 上級者向けの逃げ道（MVP不要・要望が出たら）
- デフォルトのシステムプロンプトは固定のまま
- 末尾に「追加の指示（カスタムインストラクション）」を足せる程度の自由度

## 7. BYOK運用上の注意（実装時に忘れないこと）

- **キーの検証**: 入力されたキーが有効か、軽いテスト呼び出しで確認
- **コスト透明性**: 「この操作で概算◯トークン使います」を表示できると安心
- **エラーの翻訳**: APIエラー（レート制限・残高不足・無効キー）を非エンジニアに分かる日本語に
- **APIキー保存**: ローカルに暗号化保存（平文NG）
- **カスタムエンドポイント**: ローカルLLMはキー不要な場合が多い → APIキーは任意項目に
