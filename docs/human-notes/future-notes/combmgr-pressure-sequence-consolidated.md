## 1. ドメイン定義 — 固め連携とは【確定（理解の擦り合わせ済み）】

**固め（かため）＝ガードさせて相手を動けない状態に縛り続ける攻め。** コンボ（ヒット中に繋ぐ連続技）とは目的が逆で、**ガードされている前提**で組み立てる点が最大の違い。

- ガード硬直＋有利フレームを使い、自分の次の行動が間に合う技を重ねていく。相手は割り込みづらく、ガードを続けざるを得ない。
- **目的はダメージではなく、状況維持と択の押し付け**（打撃／投げ、上段／下段、詐欺飛び・シミー 等）。
- 連携の途中に**隙間**があると割り込まれる（リバーサル無敵技、SF6 なら無敵 SA・昇龍系、ドライブリバーサル、ジャストパリィ 等）。**どこが連続ガードで、どこに隙間があるか**がフレーム的に意味を持つ。
- 詐欺重ね（持続重ね）やディレイで、相手の暴れ・無敵技をスカして狩る駆け引きが乗る。
- SF6 文脈：ドライブラッシュで距離と有利を作って固めを継続、ガード時の有利で次の中段／下段／投げへ。
- **コンボとも、起き攻めセットプレイ（ダウン後の重ね）とも別概念。**

**記録したいのは「固め全体」**（複数技のシーケンス＋隙間・択・弱点の情報を 1 つの記録単位とする）。【確定】

## 2. 記録の単位とツリー表示【確定】

- 固め全体を**1記録単位**とする。
- **ある通常技から派生する複数の連携**を、その始動技を親として**ツリー表示**する（要件5）。
- データ上は「始動通常技（共通の親キー）＋各連携（枝）」で表現し、表示側が木に描く。

---

## 3. 要件（開発者提示・原文に忠実）【確定】

1. **modifier が必要**（コンボと同様）。
   - 必殺技キャンセルを少し遅らせることで連携が強くなることがある。
   - 連携の始めの技を**先端当て**すると強くなる、など。
2. **空振る可能性がある技も連携に含める。**
   - 例：弱P 弱P 弱P 中P。最後の中Pは、相手が何もしていなければ空振り、相手が打ち返しの技を出していたらカウンターで当たる。こういう技も連携の一部として記録する。
3. **ドライブゲージをどれくらい削るか記録したい。**
   - SF6 は相手がガードしている場合、体力の代わりにドライブゲージを削るため。
   - **相手はパリィしなかった前提**で記録する。
4. **連携の弱点を記録したい。**
   - 連ガか、隙間があるか、反撃や打ち返しを受けるか、など。
5. **ある通常技から派生する連携という形で記録・表示したい（ツリー）。**
   - 例（**実態とは不一致の単なる表記例**）：
     - 中P 中P 中波動拳 → 二回目の中Pは弱攻撃で割り込まれる。相手が動かなければ反撃なくドライブゲージを削って仕切り直し。
     - 中P 弱P 弱波掌撃 → 弱攻撃で割り込まれないが、弱波掌撃が近距離で不利フレームを背負う。
   - これをツリーっぽく表示したい。

## 5. 論理データモデル（骨子）【確定（論理）／物理は §7】

### 5.1 pressure_sequence（連携＝記録単位／ツリーの枝）

| 論理フィールド | 意味 | 備考 |

| character_code | どのキャラの連携か | コンボと同様の参照 |

| weakness_4f | 4F 割り込み可否 | bool フラグ |
| weakness_punish | 確定反撃可否 | bool フラグ |
| weakness_note | 弱点の自由入力 | フラグで表せない補足 |
| memo | 自由メモ | |
| tags | タグ | コンボのタグ機構を流用できるか要検討 |

### 5.2 pressure_sequence_step（ステップ）

| 論理フィールド | 意味 | 備考 |
|---|---|---|
| sequence_id | 所属する連携 | FK |
| step_order | 順序 | 昇順 |
| move_code | 技 | moves.code 参照。非技ステップは type で識別（コンボ流用） |
| modifiers | 入力上の工夫 | **コンボと同型**＝flags/notes/type。例：必殺技キャンセルのディレイ、始動の先端当て |

## 6. 決定の根拠（rationale）

- **別テーブルにする理由**：目的が「ヒット連続」でなく「ガード拘束＋択」で、削りゲージ・弱点・空振りステップなど**固め固有の属性が多い**。コンボに無理に乗せない。
- **step／modifiers はコンボ流用**：将来マージと一貫性のため、構造を同型に保つ。
- **move 参照は code ベース**：CSV 列契約（FR401↔FR405）と同方針。整数 ID 直参照にしない。
- **drive_gauge_drain は最新仕様（-6.0〜6.0 小数）を優先**：渡している設計書の「正数」表記より新しい。
- **データの根なので承認ゲート**：スキーマ追加＋マイグレーションは設計の根。AI に勝手に物理設計・マイグレーションさせず、提案→開発者承認→実装、の順を取る。

## 7. 物理設計で詰める論点【未確定→設計担当】

- 各フィールドの**型・制約**（特に `drive_gauge_drain` の小数型・範囲 -6.0〜6.0・符号）。
- `starter_move_code` / `move_code` の **moves 参照方式**（code 参照方針）。
- **modifiers の格納形式**（コンボ recipe の `modifiers`＝flags/notes/type と同一 JSON 構造を共有するか）。
- **非技ステップ**（コンボの `move_code:""`＋`modifiers.type` 方式）を踏襲するか。
- **weakness フラグ群**を個別カラム／ビットフラグ／サブテーブルのどれにするか。
- **tags** をコンボのタグ機構と共有するか専用にするか。
- **index**（`(character_code, starter_move_code)` でのツリー取得を想定）。
- **DES-006 系の検証**（必須・範囲・ステップ0件の扱い・VAL 採番）。
- マイグレーション方針（既存データへの影響・ロールバック）。

## 8. マージ方針（コンボとの将来統合）【確定（方針）】

別テーブルだが、最初から揃えておき、将来の統合に備える。

| 区分 | 項目 |
|---|---|
| **コンボと共有（揃える）** | step 構造 / modifiers(flags,notes,type) / move の code 参照 / tag / 命名・規約 |
| **連携固有** | starter_move_code（ツリー親）/ drive_gauge_drain(-6.0〜6.0) / weakness_* フラグ5種＋note / whiff_or_counter |

- 共有部分は綴り・JSON 形をコンボと**同型に保つ**。
- マージ手順を書く際は、この「共有／固有」区分が出発点。共有部分はそのまま寄せ、固有部分は専用列で残すか、コンボ側に概念拡張するかを判断する。
