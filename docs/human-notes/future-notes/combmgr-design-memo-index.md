## 3. 繰り返し適用した判断基準（新機能を見る時のレンズ）

- **器を分けるか**：データの形と入力の性質が違えば分ける（比較・VOD）。同じなら既存の器に乗せる（軸＝フィルタ、グループ＝多対多）。
- **導出 vs 保存**：派生値は保存せず導出。例外はソースが不変でハッシュが鮮度キーになる場合のみ（VOD の体力検出キャッシュ）。
- **AI は集計まで・診断はしない**：頻度を数えて束ねるのは可、評価・断定は不可。
- **需要駆動**：先回りして抽象化しない。二例目が出てから一般化する。
- **希少資源はレビュー時間**：恒久的な保守面（複数プロバイダ対応等）は永久に払う税。
- **機械化で潰す**：継ぎ目は「注意する」でなく SSOT・パリティ・ゲートで潰す。

## 3.5 機能連携の骨格 — 4つの共有の器

> **「統合的な攻略アプリ」の連携は、新しい統合レイヤーを作ることではない。** 本セッションで既に3回同じことをしている（VOD の出口＝メモ／比較の出口＝メモ／HTML エクスポートの容れ物＋寄稿者／AI の単一受け口）。**すべて同じ形＝中央に器があり、機能はそこへ寄稿する。**

| 器 | 役割 | 正本 |
|---|---|---|
| **メモ** | 思考の集積所（あらゆる気づきの出口） | `combmgr-memo-spine-design.md` |
| **エクスポート** | 出力の容れ物（寄稿契約4項目） | `combmgr-html-export-design-memo.md` §2 |
| **AI 受け口** | 生成の入口（受け口は用途を知らない） | `combmgr-ai-integration-design-memo.md` §4 |
| **タグ／フィルタ** | 横断の索引（既存の階層フィルタ・プリセット・マイリスト） | DES-005 |

**運用ルール**

- **新機能を作るたびに「この4つのどれに接続するか」を問う。** これが連携設計のすべて。
- **接続先が無い機能が出てきた時が、5つ目の器を立てるべき瞬間。** それまで立てない。
- **先回りして統合レイヤーを作らない**（需要駆動に反し、レビュー時間を最も食う抽象化）。
- **「切り出して別アプリにしてほしい」と言われる条件は、機能が多いことではなく、その機能が他と何も共有していないこと。** VOD が「メモへ起票できる」なら切り出す理由は消える。
  - 逆に**メモ機能を汎用モジュールとして切り出す予定なのは、本当にゲーム非依存だから**＝正しい切り出し（`combmgr-license-strategy-outline.md` §3）。
- **設定画面での機能非表示**は、起動時の圧を下げる対処として正しいが**連携の代替にはならない**。むしろ**「非表示にしても困らない機能＝他と繋がっていない機能」という診断ツール**として使える。

## 3.6 ユーザーによるカスタマイズ（Claude Code）の位置づけ

**構想**：公開後、エンジニアでない一般ユーザーも Claude Code（on the web 想定）で要望を打ち込めば自分好みにカスタムできる。非公開の私的改変にコピーレフトは及ばない（AGPL の理解として正しい）。

**評価と留保**

- **敷居は「打ち込むだけ」ではない。** Claude Code on the web ならローカル環境構築は不要になるが、**難所はその後**——改変版を**ビルドして手元で動かす**必要がある。第一の受益者は一般ユーザーではなく、**開発者自身と少数の技術寄りユーザー**と見積もるのが正確。
- **サポート負担の経路になる。**「カスタムしたら動かなくなった」は必ず来る。→ **SUPPORT.md に「改変版は対象外」を明記**する（`combmgr-license-strategy-outline.md` §9.4 に反映すること）。
- **発信者北極星には直結しない。** 発信者が欲しいのは「アップデートごとに CSV を出し続けられること」であってコード改変ではない。→ **売り文句にせず、副次的な性質として置く。**
- **本当に価値がある使い方＝需要駆動のための観測装置。** **同じ改変を複数人が繰り返しているなら、それは本体に入れるべき機能**。「OSS の新しい形」より、この位置づけのほうが原則と噛み合う。
