Performance Strategy

Tacpendium 性能改善の方針

「コンマ秒でも速くしたい」に応えるための考え方。結論は明快で、推測で最適化せず、まず計測する。そして基盤（言語・DB）を変えるのでなく、ボトルネックを特定して直す。

DRAFT / 現状でも十分速い前提。これは「さらに詰めたくなった時」のための指針。優先度は機能完成より低い。

大原則 計測 ボトルネックの所在 DB・SQLite 最適化の順序 速さと見た目 やらないこと
01

大原則：推測するな、計測せよ

性能改善の最重要原則。これを外すと、すべての労力が空振りする。

GOLDEN RULE人間（とAI）の「ここが遅いはず」という直感は高い確率で外れる。実際のボトルネックは予想外の場所にあることが多い。計測せずに最適化すると、体感が変わらない箇所を必死に直して時間を溶かす。コンマ秒を追うなら、どこで何ミリ秒使っているかをデータで把握することが絶対の出発点。
早すぎる最適化は諸悪の根源機能が固まる前に性能を作り込むのは早すぎる。機能が変われば最適化が無駄になる。まず機能を完成させ、性能改善は計測に基づいてフェーズ3以降にまとめてやる。
02

計測の手段

バックエンドとフロントエンドで手段が分かれる。基本思想は両方とも「測りたい箇所にログを仕込む」。

対象手段備考
バックエンド処理Goのpprof / 処理時間のログ「どの関数で何ミリ秒」を可視化。コンマ秒を追う最強の武器
DBクエリEXPLAIN QUERY PLAN / 実行時間計測フルスキャンしているクエリを特定できる
フロント（特定処理）console.time / timeEnd最も手軽。バックエンドのログ計測と同じ感覚で処理を囲んで測る
フロント（レンダリング）React <Profiler> APIコンポーネントのレンダリング時間をコードで仕込んで計測
フロント（総合診断）Lighthouse自動で改善点を指摘。CI連携でリリース前チェックにも
フロント（再描画の原因）React DevTools「なぜ描画したか」記録設定（歯車→記録オプション）で有効化すると使いやすい
開発者ツールが使いにくい場合GUIが合わないなら、コードに計測を仕込む方式（console.time / <Profiler>）が、バックエンドのログ計測と同じ思考で扱えて直感的。「バックエンドはログを仕込めばいい」と同じことをフロントでもやる。
過剰なツールは不要Datadog/Sentry/LogRocket等の有償RUMツールは本番クラウドサービス・チーム向け。ローカルアプリの開発中計測には過剰で、軽量・前提ソフト不要のDNAにも合わない。当面不要。
03

ボトルネックの所在を見極める

「遅さ」の原因は言語ではないことが多い。Webアプリの体感速度の大半はフロントで発生する。

遅さの原因どこの問題か対処
フロントのレンダリング・再描画React/ブラウザ体感速度の大半はここ。再レンダリング削減・仮想化
非効率なDBクエリSQLite（使い方）インデックス・クエリ見直し
データの取得方法設計一度に大量取得していないか、N+1問題はないか
バックエンド計算Goここが重いケースは稀。並行処理・キャッシュ
起動・ページ読み込み構成遅延読み込み等
重要な事実Webアプリの「もっさり感」の大半はフロントエンド（React/ブラウザ）側で発生する。バックエンドの言語を変えても、ここは変わらない。だから「遅い→言語を変える」は筋が違い、「遅い→原因を測る→その箇所を直す」が正道。
04

DB：SQLiteは変えない、インデックスで直す

クエリが遅い場合の話。結論は「SQLiteの限界でもDB選択でもなく、インデックスとクエリ・設計の問題」。

問い答え理由
SQLiteに速度の限界は？遠い限界は超大量データ・高頻度同時書き込みで初めて問題に。Tacpendiumの規模はSQLiteの得意領域のど真ん中
他のDBの方が速い？否ローカル単一ユーザーではSQLite（同プロセス・ネットワーク往復ゼロ）が最速の部類。サーバー型はオーバーヘッドで逆に遅くなりうる＆DNA違反
インデックスで爆速に？可能性大クエリが遅い原因の大半はインデックス不足。10〜100倍変わることも。これが本命の改善手段
インデックスが効く箇所タグ/キャラ/状態での絞り込み、コンボと技の関連を辿る、全文検索（FTS5）、ソート、一人SNS方式のスレッド辿り（親投稿ID参照）。Tacpendiumは「絞る・辿る」操作が多く、これらの列のインデックス有無で速度が激変する。
インデックスの注意貼りすぎは書き込みを遅くする（読み書きのバランス）／クエリの書き方次第で使われないことがある／EXPLAIN QUERY PLANで実際に使われているか確認。「貼れば自動で爆速」ではなく「計測→遅いクエリ特定→効くインデックス→確認」の手順が必要。
05

最適化の正しい順序

「どの手段で速くするか」の前に「どこが遅いか測る」。その上で、軽い改善から順に。

0計測 pprof / EXPLAIN / console.time / Profiler で、どこで何ミリ秒かを特定。推測しない。
1機能完成を優先 性能はまだ追わない。早すぎる最適化を避ける。
2フェーズ3以降に性能改善をまとめて 専用マイルストーンとして。計測でボトルネックが見つかったら着手。
3見た目を犠牲にしない最適化を尽くす 再レンダリング削減・仮想化・遅延読み込み・クエリ最適化。多くはこれで十分。
4静的解析で候補出し（補助） 性能アンチパターンを拾う。ただし本当に遅いかは計測で確認。
5ボトルネックの領域を学んで直す 計測が示した領域をピンポイントで学習（AI+自分）。漠然と勉強しない。
6最後の手段：見た目とのトレードオフ ここまでで足りなければ、アニメ削減等を検討。
性能改善担当Claude毎マイルストーンで常時設けるのは時期尚早・労力過剰。フェーズ3以降に専用マイルストーンとして設けるのが妥当。ただし「計測でボトルネックが特定できたら」が条件。
06

速さと見た目：必ずしもトレードオフではない

「エクスプローラ並みの速さは見た目との引き換えか？」への答え。多くは見た目を犠牲にせず速くできる。

速くする手段見た目への影響
再レンダリング削減（React最適化）影響なし 内部効率だけ改善
仮想化（見える分だけ描画）影響なし 見た目そのままで大量データを高速表示
遅延読み込み影響なし 見た目同じ、初期表示が速い
DBクエリ最適化無関係
アニメーション・トランジション削減トレードオフ 滑らかさは減る
大量画像・複雑なレイアウト・影の削減トレードオフ
順序が答え①まず見た目を犠牲にしない最適化を尽くす（多くはこれで十分速くなる）→ ②それでも足りなければ見た目とのトレードオフを検討。見た目を削るのは最後の手段。
構造的な壁Webアプリである以上、ネイティブアプリ（エクスプローラ等）の瞬間性には原理的に届きにくい部分がある。ただし「十分速い・引っかからない」と体感されるレベルは、見た目そのままで到達可能。完全同等を目標にするのは高すぎるかも。
07

やらないこと・戒め

✗Rust版を別途作る。 労力対効果が最悪。体感速度の大半はフロント（Rust化で変わらない）。CRUD中心ではGo/Rustの速度差は体感困難。2バージョン保守・学習コスト・一貫性喪失で、得るものより失うものが大きい。「やらないことを決める」対象。
✗DBをサーバー型に変える。 ローカル用途では逆に遅くなりうる。前提ソフト不要のDNA違反。
✗計測せずに最適化する。 直感は外れる。空振りで時間を溶かす。
✗機能完成前に性能を作り込む。 早すぎる最適化。機能が変われば無駄になる。
?体感できないコンマ秒を追う。 人間が速さを体感する閾値は約100ms。それ以下の改善はユーザーに分からず自己満足になりうる。「遅くて困る操作」は直す価値があるが、「十分速いものをさらに」は優先度を厳しく問う。
