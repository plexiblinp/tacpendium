Update Strategy · Draft

Tacpendium アップデート戦略

アプリ本体とSF6データの更新に、個人OSSとして持続可能なペースで追従するための方針。「全部に追従する」ではなく「リスクだけ即応、他はまとめて・必要時に」が基本姿勢。

DRAFT / 拡張前提 — リリース運用の主要論点（区分・チェンジログ・後方互換・ロールバック・テスト・検知）を反映。バージョニング規約の細部は保留中。随時更新する。

更新トリガー 影響レベル リリース区分 バージョニング チェンジログ 後方互換 ロールバック テスト範囲 SF6検知・ペース 依存追従 環境変化 配布戦略 データ維持 バージョン方針 データ配布の法務 原則
01

更新が必要になるトリガー

起因を Tacpendium側 と SF6側 に分けて整理。SF6側は「影響レベル」（§02）で対応の重さが変わる。

Tacpendium 起因（アプリ自身）

  • 機能追加
  • バグ修正
  • 脆弱性修正
  • 依存ライブラリ更新追従（→ §03）
  • AIプロバイダの仕様変更追従（モデル廃止・API変更）
  • OS・ブラウザ・ランタイム環境変化への対応（→ §04）
  • パフォーマンス改善・リファクタリング
  • ドキュメント・翻訳の更新

SF6 起因（外部ゲーム）

  • キャラ性能調整（数値: ダメージ・フレーム変更）
  • 技の追加・削除
  • 技の挙動・仕様変更
  • キャラ追加（固有システムを伴う場合あり）
  • 共通システムの数値調整
  • 新システムの追加（新ゲージ・新メカニクス）
  • システムの廃止・仕様変更
  • 公式データの表記・フォーマット変更
  • メジャー/シーズン更新（複数変更の束）
  • 用語・名称の変更
02

影響レベル（対応の重さ）

SF6変更を「アプリの何に影響するか」で分類。いかに多くをL1に収めるかが追従の手間を最小化する設計目標。

レベル内容対応
L1 データのみ数値調整、キャラ追加、システム数値変更データ更新だけ。アプリ更新不要が理想
L2 データ構造新技種別、新データ項目の発生スキーマ拡張 + アプリ更新
L3 ロジック/UI新システム、新メカニクス、表示変更コード変更 + アプリ更新
L4 データ取得方法公式フォーマット・表記変更取り込み方法の見直し
設計目標データと機能を分離し、多くのSF6変更を「データ更新（L1）」で吸収する。L1はアプリ再配布不要で追従できる状態を目指す。
03

リリースの3区分

性質の異なる3種類のリリースに分ける。それぞれ判断軸とペースが違う。

区分内容ペース
① 脆弱性対応公開範囲から見て危険性の高い脆弱性への対応即時〜数日（最優先）
② SF6追従SF6のコンボ・フレーム等に影響する変更への追従SF6パッチに応じて
③ 機能追加新たに作りたい機能・取り入れたいユーザー要望の実現時気分次第・ベストエフォート
②の判断軸「バグfixか調整か」ではなく「コンボ・データに影響するか否か」で判断する。UI修正・サーバー安定化などコンボに無関係な変更は無視。
バグコンボの例外経験上、異常なバグコンボは明らかに異常なものばかりで1ヶ月もかからず公式に修正される。よって、バグfixで影響を受けるようなコンボへの追従は不要と判断（短命なため）。
04

バージョニング規約

アプリのバージョンと、対応するSF6の調整表記を併記する。

表記イメージアプリ本体バージョン + 対応SF6調整表記を併記（例: v1.3.0 (SF6: 対応表記)）。ユーザーが「今どのSF6バージョンに対応しているか」を一目で分かるようにする。
保留中の確認事項SF6の調整表記が「年月日」か「シーズン/バージョン番号」か、採用前に公式の現行仕様を確認する（うろ覚えのため）。アプリ本体のバージョン番号の付け方はSemVer（メジャー.マイナー.パッチ）推奨だが、決定は保留（急がない）。
SemVer対応の目安（採用する場合）: 脆弱性対応=パッチ / SF6データ更新=パッチ〜マイナー / 機能追加=マイナー / 破壊的変更=メジャー
05

チェンジログの運用（開発者向け / 一般向け）

読み手で2種類に分ける。それぞれ作り方と負荷が違う。

種別内容作り方・負荷
開発者向けgitログと実際の差分の中間ぐらいの情報AIに書かせる。レビューだけなので低負荷
一般向け細かい点は抽象化。どんな要件に対応したか・どんな新機能か・新機能の使い方に重点重いが重要。AIだけでなく自分も注力
負荷の見立て開発者向けはAI生成+レビューで軽い。一般向けは重いが、ユーザー体験に直結する重要部分なので手をかける価値がある。
06

後方互換性の方針

どのバージョン間でデータの動作を保証するか。

方向方針
旧バージョン → 新バージョン動作を担保する（マイグレーションで対応）
新バージョン → 旧バージョン担保しない。ユーザーには「動く可能性があるかも」レベルの通知
破壊的変更がある場合その時だけ「補償しない」と明示通知
技削除への備え技の削除事例はこれまでSF6にないため積極対応は不要。ただし最低限の防衛策（参照先がなくなっても壊れない程度）はつける。起きていないことに過剰投資せず、保険だけ持つ。
07

ロールバック（最優先で担保）

更新して問題が起きたとき、前の状態に戻せること。データ完全消失は絶対に防ぐ。

定義ロールバック = アプリとデータをセットで更新前の状態に戻す。アプリだけ戻すのではなく、マイグレーション前のバックアップDBもセットで復元する。これにより「新→旧のデータ互換（§06で非担保）」と矛盾せず、ロールバックを実現できる。
絶対原則多少ユーザーに復旧手順を任せる場合があっても、データの完全消失は絶対に防ぐ。§13の「マイグレーション前の自動バックアップ」がこれを支える決定的な仕組み。
08

リリース前のテスト範囲

個人OSSの現実解は「変更箇所 + データ周り・コア機能は毎回」のハイブリッド。仕事の「変更箇所だけ」とは少し違う。

対象方針
変更した箇所必ずテスト（仕事と同じ）
データに関わる箇所（マイグレーション・保存・読込）変更有無に関わらず毎回確認。データ消失は致命的なため聖域扱い
コア機能（起動・コンボCRUD・主要画面）リリース前に毎回スモークテスト（最低限動く確認）
それ以外変更時のみ
継続の鍵は自動化「毎回の最低限確認」を手動でやると続かない。静的解析ツール（Semgrep/gosec/govulncheck等）と自動テストをCIで回して自動化するのが、ベストエフォート運用で続けるコツ。
09

SF6アップデートの検知・対応ペース

SF6の更新をどう知り、どのペースで対応するか。

検知SF6の更新検知は自分の役目。SF6プレイヤーなので更新タイミングは自然に分かる。検知は容易。
対応ペース＝ベストエフォート金銭が発生していないため対応ペースはベストエフォート。自分が何らかの理由で更新不能にならない限りは追従する。OSSなので、更新が途絶えても誰かが引き継いでくれればよい（MITライセンスと一貫。抱え込まない健全な手放し方）。
10

依存ライブラリ更新の追従ペース

大原則: 全部を最新に追わない。目標は「動き続ける + 脆弱性を放置しない」であって「最新であること」ではない。

更新の種類ペース理由
セキュリティ修正即時〜数日放置はリスク。最優先
パッチ（バグ修正・後方互換）月1まとめて低リスク。溜めて一括
マイナー（機能追加・後方互換）数ヶ月 or 必要時急がない
メジャー（破壊的変更）年1 or 必要に迫られたとき最も手間。慎重にまとめて
頻度やること
自動（常時）Dependabotが脆弱性検知 → アラート/PR自動生成
週1（5分）セキュリティアラートだけ確認・マージ
月1（30分〜1h）溜まったパッチ/マイナーをまとめて確認・マージ、テスト確認
年1〜2（半日〜1日）メジャーバージョンアップ対応
Go と npmGo本体は約半年ごと更新だが、後方互換性が高く年1回程度の追従で十分（直近2バージョンがサポート対象）。実はnpm側の方が依存が多く手間。govulncheckは「実際に使う脆弱なコード」だけ検知し誤検知が少ない。Dependabotのグループ化・週次設定でPRの洪水を防ぐ。
11

OS・ブラウザ・ランタイム環境変化

定期メンテではなくトリガー駆動。普段は放置でよい。能動的に先回りしない。

トリガー例緊急度
ユーザーの「動かない」報告新Windowsで起動しない等高
新OSメジャー版リリースWindows/macOSの新版中（出たら確認）
ブラウザのメジャー変更挙動が変わる大型更新中
使用APIの廃止予告Gamepad API等の仕様変更・非推奨中（予告期間中に）
Goランタイムのサポート終了使用バージョンがサポート外に低〜中
Tacpendium特有の注意Gamepad API（仮想コントローラの核）と配布バイナリの実行制限（Gatekeeper/SmartScreen厳格化）は環境変化の影響を受けやすい。OS/ブラウザのメジャー更新時に軽く確認する価値あり。LANアクセスがOSのファイアウォール強化でブロックされる可能性も。
手間削減の鍵READMEに「動作確認済み環境」を明記し、サポート範囲を限定する。全環境テストの義務から解放され、ユーザーの期待値も調整できる。
12

配布戦略（アプリ本体更新）

完全自動アップデートは攻撃対象を増やし、安全に作るコストが個人OSSに見合わない。更新通知 + 公式ページ誘導を基本とする。

方式内容採否
A. 完全手動ユーザーが自分で確認・DL先行リリースはこれで十分
B. 更新通知のみ新版を通知し公式ページへ誘導。実コードは自動取得しない公開後の基本
C. 通知+DL補助通知からDLページを開く等。適用は手動必要なら
D. 完全自動自動DL・適用・再起動基本やらない
「不正サイト誘導」への対策更新方式の最大リスクは誘導先のすり替え。対策: 誘導先URLをアプリにハードコード（サーバーから動的に受け取らない）／バージョン取得元を固定（GitHub Releases API）／HTTPS／DL後のSHA256検証を案内／「公式はここ」と明示。
実装方針更新はポータブル版のファイル差し替え（新exeに置き換えるだけ）が単一バイナリのTacpendiumに最適。バージョン確認はGitHub Releases API（追加インフラ不要・無料）。確認は任意で無効化可能に（オフライン動作を尊重）。更新するのはオーナーのみ（ゲストは不要）。
13

ユーザーデータの維持

アプリをどう更新しても、ユーザーが登録したデータ（コンボ・メモ等）を失わないことが最優先。

大原則データをアプリ本体とは別の固定の場所（例: %APPDATA%\Tacpendium）に保管する。これだけで、本体を丸ごと差し替えてもデータは無傷。exeと同じ場所にDBを置かない。
仕組み内容
DBマイグレーション起動時にスキーマバージョンを確認し、必要な変換を順に適用。ユーザーは意識せず新機能が使える
マイグレーション前の自動バックアップスキーマ変更前にDBをコピー。失敗時はロールバック。直近数世代を保持
手動バックアップエクスポート機能を流用。「更新前にエクスポート推奨」と案内
3点セット「データを別の場所に置く + マイグレーション + 事前バックアップ」が揃えば、アプリをどう更新してもデータは守られる。インポート/エクスポート機能がデータ更新とバックアップを兼ねる。
14

バージョン管理方針（このアプリは「今」を管理する）

バージョン管理の複雑さ（組み合わせ爆発・横断検索）を避けるため、アプリが管理するのは現行バージョンのみと割り切る。

対象更新の責任
キャラクターデータ（マスター）アプリが配布・更新する（公開版はインゲーム手入力 seed 由来）
ユーザー登録データ（コンボ・メモ等）ユーザーがメンテ。キャラデータ変更時の見直しもユーザー
過去バージョンの参照ユーザーがバックアップ + 参照SQLiteファイルの差し替えで対応（やや不親切を許容）
製品思想「知的好奇心で過去バージョンのコンボを見るのは面白いが、このアプリで管理するのは"今"」。過去はユーザーの自助（バックアップ＆ファイル差し替え）に委ね、アプリのデータモデルをシンプルに保つ。
検討中 / 後で考える: ユーザーによるデータメンテをやりやすくする施策（キャラデータ更新時に影響を受けるユーザーデータをハイライト、バックアップ/復元のワンクリック化、軽量スナップショット等）。今の設計判断がこれらを阻害しないことだけ意識する。
15

キャラデータ配布の法務スタンス

キャラクターデータの配布は、CAPCOM著作物に関わるグレーゾーンである、と認識した上での判断。公開版と友人版でデータの出所を分ける方針に更新（決定記録: framedata-legal-decision を参照）。

判断キャラクターデータはアプリが配布する。グレーゾーンであることは認識しているが、個人非営利・小規模である以上、大きな問題にはならないと判断（削除要請ベースのリスク認識に基づく）。ただし公開版のデータ出所は「インゲーム観測の手入力 seed」とし、公式Webデータの直接利用・配布はしない。
データの出所（公開版 / 友人版）友人版（プライベート）: 公式データ＋インポーターを使う。インポーターはプライベートに残し、配布・公開しない（出力は手入力版の数値クロスチェック用）。公開版: 開発者がインゲームで観測して入力した seed を同梱。中核原則は「事実は入れ、表現は持ち込まない」——数値（フレーム等）は入れるが、公式の文章・画像・アイコン・公式名称文字列・ページ配列は持ち込まない。技識別子は表記ベース（5HP 等）を志向。
撤退ライン（あらかじめ決めておく）CAPCOMから通達があればただちにデータ配信を停止し、ユーザーが自分でデータを入力する形式に切り替える。この切り替えを可能にするため、§02の「データと機能の分離」設計が保険として効く（データ配布を止めても、アプリ本体は無傷で動く構造）。
関連: 公開版データ出所の最終決定は別レポート（framedata-legal-decision）に集約。本スタンス（黙認領域での公開・MIT+注意事項・即時公開停止対応・データ配布停止→ユーザー入力方式への即時切替）と一貫させる。「他が放置されている」事実は盾にしない（実際の保護は撤退ライン）。
16

全体を貫く原則

01リスクだけ即応、他はまとめて・必要時に。 セキュリティは即時。それ以外は実害が出てから/定期的に。完璧な追従を目指すと個人開発は潰れる。
02データと機能を分離する。 多くのSF6変更をL1（データ更新）で吸収。データ配布停止時にユーザー入力へ切り替える保険にもなる。
03ユーザーデータは何があっても守る。 別の場所に保管 + マイグレーション + 事前バックアップの3点セット。更新の利便性より優先。
04情報は自動取得してよいが、実行コードは人間を経由。 バージョン番号の取得は自動でよい。DL・適用は手動。完全自動更新の脆弱性を避ける。
05「今」に集中し、過去はユーザーに委ねる。 バージョン管理の複雑さを避け、アプリをシンプルに保つ。スコープを守る。
06撤退ラインを先に決めておく。 データ配布はグレーと認識。通達あれば即停止しユーザー入力方式へ。慌てないよう設計で備える。
07ベストエフォート。抱え込まない。 金銭が発生していない以上、対応ペースはベストエフォート。OSSなので更新が途絶えても誰かが引き継げばよい。燃え尽きないことが最大の持続可能性。
