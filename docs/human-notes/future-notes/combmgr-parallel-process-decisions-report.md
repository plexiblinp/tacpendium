## 1. 診断（なぜ今のプロセスが重いか）

現行の負担は2つの構造要因に分解される：

1. **開発者がメッセージバスになっている。** チャット間通信（リレー文）が全部開発者の手を通る。リレー文の生成・貼付でコンテキストも消費（特に中央）。スマホ（Claude Code on the web）では貼付コストがさらに高い。
2. **中央チャットが「人力ロックサーバー」になっている。** マイグレ連番・CHANGE 番号の払出し＝直列資源の**同期的**調停。各担当は中央の応答待ちでブロックし、中央は割り込み対応でコンテキストを浪費し、チャット作り直し頻度が上がる。

適用すべき原則は Fable の学びそのもの：**継ぎ目は「注意する」でなく機械化・SSOT で潰す**。これをプロセス自体に適用する。

## 2. 決定事項（6部品）

### 部品1: 連番 — 資源の性質で二分する

- **CHANGE 番号・DES 文書バージョン＝マイルストーン着手時に事前ブロック割当。**
  - 例：M20＝CHANGE 0XX〜0XX、M21＝次ブロック。割当表は repo 内の小さな正本ファイル1つ。枯れたら追加ブロック。
  - 欠番が出るが無害（既に 008/009/014 を運用で許容済み。順序依存がない資源のため）。
  - 中央への同期問い合わせが構造的にゼロになる。
- **マイグレ番号＝事前割当は不採用。「マージ時採番」とする。**
  - 理由：golang-migrate は単一の現在バージョン番号で管理し、DB が version 29 にいる状態へ後から 24 が来ても遡って適用されない。マージ順は予測できないため、ブロック割当だと**本線で番号順とマージ順がズレる**。
  - **危険点は開発中でなく配布先。** 友人リリース済み＝配布先の既存 DB は連番順に up を適用する。作り直せる作業 DB は常に 0 から順適用するため**開発環境では再現しない**——「配布ユーザーの DB でだけ壊れる」類の事故。
  - 運用：開発中＝**レーン別作業 DB**（既存のシェル運用）＋**プレースホルダ番号**（例 `m20_xxx_XXXX`）で自由に。マージ時＝本線の最新番号＋1 へ**一括リネームして採番**。マージは開発者の手で直列化されているので、マージの直列性が採番の直列性を兼ねる。リネームは up/down ファイル名の rename だけで機械化可能。

### 部品2: 通信 — 媒体を「開発者」から「repo」へ

- チャット間のリレー文を全部ファイルにして commit。開発者の仕事は「内容の転記」から「**commit/push ＋ ポインタ1行**（『docs/handover/m20-to-central-XX.md を読んで』）」に縮む。
- スマホで特に効く：Claude Code on the web は repo を直接読める＝貼付不要。プロジェクト内チャットは project knowledge で読める。
- リレー文生成によるコンテキスト消費が消える。

### 部品3: 中央 — 同期調停者から非同期バッチ反映者へ（Claude Code 化）

- 部品1で連番調停が消えると、中央の残る実務は **DES 反映・registry 更新・横断整合**＝repo 内ファイル編集。これは Claude Code の本領。
- **チャット窓口としての中央は廃止**。Claude Code として**必要時起動**（常駐しない）。開発者確認1への回答＝可、むしろ推奨。
- 反映は**チェックポイント制のバッチ**：各担当は change-report ドラフトをファイルで置いて進み続け、中央はサブ完了時などの定期タイミングでまとめて DES へ反映。
- 判断が要る場面（横断整合の相談等）だけ相談チャットへ持ち込む。
- **認識ズレの是正を会話でなく契約との diff にする**：マイルストーンごとの契約ファイル（§3）と機械的に突き合わせる。

### 部品4: retrospective — 書き捨て→バッチ反映（開発者提案を採用）

- 各担当は教訓を一時ファイル（例 `docs/handover/m20-lessons-scratch.md`）へ書き捨て。中央がチャット切替時/完了時にまとめて retrospective-log へ反映。
- 追加推奨：retrospective-log は巨大で編集のたび全文がコンテキストに載る＝この構造自体が継ぎ目。**追記専用の構造**（末尾 append で完結・全文読み込み不要）にするか、**フェーズ単位で分割**する。

### 部品5: 衝突管理 — 契約ファイル＋レーン割り

- 契約ファイル（§3）に **DES セクション所有権**を明記（「M20 は DES-003 §X/§Y を所有」）。DES の衝突は実態として「マージ地獄でなく連番問題」（開発者回答）なので、部品1＋所有権でほぼ消える。
- スキーマ・コードは一部衝突の可能性あり（同一 DB を使う箇所あり）→ 契約に「触る領域」を書き、重なる場合のみ調整。
- **M20〜M22＝低衝突予想 → 中央バッチ周期を粗くする試験台**（サブ完了時 → マイルストーン完了時まで落とせるか検証）。
- **M23＝あちこち小修正で衝突高低混在 → 高衝突の小修正だけ1レーンに束ねて直列、低衝突は並列。**

### 部品6: プロジェクト知識の使い分け

- project knowledge は**検索ベース取得**。全ファイルが常時コンテキストに載るのではなく、クエリに関連する断片だけ返る。→ GitHub 同期資料が各チャットを常時圧迫する心配は不要。
- ただし**検索は取りこぼす**（実例：本日、`combmgr-player-comparison-design.md` の本文が3回クエリを変えても引けなかった。INDEX の言及断片は返ったが本文断片は返らず。既存の「コンボ比較機能」DES-005 §5.8 に意味検索が吸われたのが最有力。index 不在か検索負けかは判別不能）。
- 使い分け：**DES・overview 等のバルク参照＝project knowledge で可／連番割当表・契約ファイル等のホットな正本＝検索に頼らず明示的に渡すか Claude Code に直接読ませる。** ロックや counter を検索取得に委ねない。

## 3. 契約ファイル（マイルストーン開始時に1枚）

各並列マイルストーンの起動時に作る正本。項目：

1. **スコープ**（このマイルストーンで作る/作らないもの）
2. **DES セクション所有権**（改訂してよい文書と §。他レーン所有分は read-only）
3. **予約レンジ**（CHANGE ブロック・DES バージョンブロック。マイグレは「プレースホルダ・マージ時採番」と明記）
4. **触るスキーマ/コード領域**（衝突面の宣言）
5. **凍結インターフェース**（他レーンが依存する API/型/契約で、このマイルストーン中に変えないもの)
6. **通信規約**（成果物・報告・教訓の置き場パスと命名）

ズレ検出＝この契約との diff。会話での是正に頼らない。

## 4. 開発者Q&Aの記録

1. **中央は Web 版から Claude Code に写して必要時起動でいい？** → 可・推奨。チャット窓口の役割自体を廃止するのが部品2/3。
2. **予約による大量欠番はプログラム的に問題ない？** → CHANGE/文書番号は無害。マイグレは順序問題があるため事前予約自体を不採用にし、マージ時採番へ（§部品1）。既存欠番（008/009/014）は初期の混乱・取消由来であり意図的でない旨も記録。
3. **retrospective-log 反映も中央担当。一時ファイル→まとめ反映でよい？** → 正しい。＋追記専用構造化/分割を推奨（§部品4）。
4. **「検索は取りこぼす」の意味は？** → §部品6 に正確な説明を記載。「コンテキストに常時入っている」モデルではない。

## 4.5 第2版での追加決定（親チャット方式・2026-07-27）

> **手順書は `combmgr-parallel-process-playbook-v2.html` が正本**（第1版 HTML は破棄してよい）。本節は第2版で追加・改訂された決定の記録。**§1〜§4 の6部品はすべて生存**（矛盾なし・追加と具体化のみ）。

### 部品7: 親チャット方式（設計側のチャット構成）

**第1版が未規定だった空白を埋めるもの。** マイルストーン単位の長期チャットを複数同時運用すると、起動時に渡すファイルが多く、肥大時の引き継ぎも重い——という開発者の観測に対する構造的解答。

- **芯＝熟考と結論の分離。** 設計判断で消費されるコンテキストの大半は探索・往復・却下案であり、確定事項ではない。それを使い捨てのチャットに閉じ込め、**親は蒸留された結論だけを読む**。「隔離リポジトリで自律実装させ、人はマージだけする」を設計フェーズに適用した形。
- **4層**：親チャット（設計卓・**設計権限を持つ唯一の層**）／個別設計チャット（使い捨て・**設計変更権限なし**・レポート1本）／製造担当 Claude Code／反映係 Claude Code（必要時起動）。
- **命名**：第1版の「中央」は**反映係**を指す。第2版の「親」は別の層。**両方を中央と呼ばない**（混乱の主因になる）。
- **親は設計書を直接編集せず、パッチを発行して反映係に直させる**（親の再起動回数を減らす）。
- **構造的な改善点**：契約ファイルの**発行者が単一著者**になる。第1版では各レーンが自分の契約を持ち契約自体がドリフトしうる隙があったが、親が全マイルストーンの契約を書くことで **DES 所有権の排他性が構造的に保証される**。
- **残るリスク（正直に）**：親が単一障害点になる／マイルストーンごとの文脈は浅くなる。→ ボードファイルで緩和。

### 部品8: ボードファイル（親の寿命対策）

- 親もいずれ肥大する。状態がチャット内にあると引き継ぎがまた重くなる＝**今回避けたかった問題の再来**。
- **小さな1ファイル**に：マイルストーン状況／外注中の個別設計／保留事項／予約レンジの消費状況。
- **裁定のたびに1行追記**（「M20-03 の逸脱＝受理・DES-004 §6 更新済み」等）。→ **親をいつでも使い捨てにできる**。落ちても学びが失われない。
- 副次：**「指示書の誤り」件数の推移＝指示書作成の改善を測る安価な計測点**。
- **親は実装レポートを読まない。ボードだけを見る**（読み始めた瞬間、熟考を外出しした意味が消える）。

### 部品9: 個別設計チャットの契約

- 起動は**親が作ったプロンプトのコピペのみ**（開発者の負担はこれだけ）。
- プロンプト必須項目：凍結事項／スコープ／**設計変更権限を持たないことの明示**／**読むべき文書名の明示**（検索取りこぼし対策）。
- **最終レポート様式（固定）**：目的／**読んだ資料**（鮮度パリティ）／検討した選択肢／**確定事項**／開発者判断が要る未決／**DES 差分案**／指示書に入れるべき制約／**教訓（親は読まなくてよいと明記）**。
- **DES 差分案まで書かせるのが親の負担をゼロに近づける鍵**。そこまで入っていれば親の仕事はレビューとパッチ発行だけになる。
- リレーは**最初と最後だけ**。目的達成で役目を終える（連続支援が有利な場合のみ継続）。

### 部品10: 設計伝達レポート（既存カスタムコマンド）の改訂

> 既存コマンドは**想定より良くできている**。§1〜§5 が既に宛先で割れており、差分主義・根拠必須・「設計判断はしない」の三点が外注レーンの契約として機能している。以下は埋まっていない穴のみ。

| # | 改訂 | 理由 |
|---|------|------|
| 1 | **§6 教訓を追加**し「親は読まなくてよい」と明記 | 宛先分離が節構造だけで完成。外出先では §1〜§3 だけコピペで足りる |
| 2 | **「契約に反する独自判断」を独立カテゴリに** | 最も危険。放置＝DES と実装の乖離。親の仕事は**受理して DES/契約を更新するか、却下して差し戻すか**の二択。**未処理で流れることだけを避ける** |
| 3 | §5「registry で採番」→**「契約ファイルの予約レンジから採る」** | 旧モデルの記述。部品1 と不整合 |
| 4 | **マイグレのプレースホルダ運用**を明記させる節を追加 | 「プレースホルダ名・マージ時に採番」を報告させる |
| 5 | **該当なしの扱いを定義** | 「該当が無い節は『なし』の一行で終える。埋めるために書かない」＝差分主義の機械化（LLM が節を埋めるため作文する実リスクへの対策） |
| 6 | ファイル名を **`-design-exceptions.md`** 等へ | 「例外だけ」と名前に書けば、生成側も受取側も契約を思い出せる |

### 部品11: 名前空間の分離（V2 で修正）

- **`docs/handover/` を「チャット間リレー」と「設計伝達レポート」の両方に使わない。** 同じ語が二つを指すと必ず取り違える。
- **リレー ＝ `docs/relay/` ／ 設計伝達レポート ＝ `docs/design-reports/`。**

### 部品12: progress ログの扱い

- **progress は全部書いたログ。基本的に渡さない。** 親・個別設計チャットへの唯一の入力は設計伝達レポート。
- **例外は認める契約**（開発者確定）。構造的な隠蔽（同期対象から外す）はしない。
- **要求する側の起動プロンプトにも「progress ログは要求しない」と書く。** コマンド側だけ直しても要求は止まらない（双方向の問題）。

### 部品13: 教訓 — 記録と統制を分ける

- 収集：製造・個別設計の**両方が同じ様式の「教訓」節**で出す → 反映係がバッチで retrospective へ。**親は読まない。**
- **「プロジェクト知識にあるから全員が見られる」は成立しない。** 見られるが読まれるとは限らず、検索は取りこぼす。
- → **再発防止が要る教訓は、retrospective に書くだけで終わらせず、playbook・コマンド仕様・指示書テンプレへ昇格させる**（改善レーンが提案 #1/#3/#5 を機構化したのと同じ動き）。
- **retrospective ＝ 履歴／統制 ＝ 起動プロンプトとコマンド仕様。** 役割を混ぜない。

### スマホ運用について

- **同期に正しさを依存させない**（部品6 の再確認）。個別設計チャットは親の起動プロンプトを受け取る設計なので、**要点がプロンプトに載っていれば project knowledge が多少古くても成立する**。
- 実務：Safari から claude.ai を開いて同期を試す価値はある（web とアプリの機能差は変動するので自分で確認）／**外出前の同期を習慣化**／repo 由来の情報は **Claude Code on the web が直接読める**ので同期不要の経路が既にある。

## 5. 起動プロンプト／playbook レビュー時のチェックリスト（相談役用）

M20 以降の担当起動前に、プロンプト/playbook へ以下が**検証可能な形で**書かれているかを確認する：

- [ ] **連番**：CHANGE/DES のブロック割当値が具体的に書かれているか。マイグレは「プレースホルダ命名規則＋マージ時採番＋リネーム手順」が書かれているか。**「中央に採番を問い合わせる」記述が残っていないか**（残っていたら旧プロセスの混入）。
- [ ] **作業 DB**：レーン別作業 DB の使用と、その限界（本線・配布 DB では番号順適用＝マージ時採番が必須の理由）が書かれているか。
- [ ] **通信**：リレー文でなく「ファイル＋ポインタ」であること。置き場パス・命名規約が契約ファイルと一致しているか。
- [ ] **契約ファイル**：§3 の6項目が全て埋まっているか。DES 所有権が他レーンと排他か（同一 § を2レーンが所有していないか）。
- [ ] **凍結インターフェース**：他レーンが依存するものが列挙され、「変えたくなったら実装でなく契約改訂を先に」という手順があるか。
- [ ] **教訓**：scratch ファイルのパスが指定され、「retrospective-log を直接編集しない」と書かれているか。
- [ ] **中央**：中央への同期依頼を前提にした文言が無いか。バッチ反映のタイミング（サブ完了時 or MS 完了時）が契約と一致しているか。
- [ ] **プロジェクト知識**：ホットな正本（割当表・契約）を検索で引かせる前提になっていないか（明示パスで渡しているか）。
- [ ] **既存規律との整合**：spec-driven・隔離リポジトリ・人間マージ・データの根は人間、という既存原則と矛盾する記述が無いか。

**第2版で追加（親チャット方式）**

- [ ] **個別設計チャットの起動プロンプト**：凍結事項・スコープ・**設計変更権限を持たない旨**・**読むべき文書名の明示**が入っているか。
- [ ] **レポート様式**：目的／読んだ資料／検討した選択肢／確定事項／未決／**DES 差分案**／指示書に入れるべき制約／**教訓（親は読まなくてよい旨つき）** が指定されているか。
- [ ] **親の役割の純度**：親が実装レポートや progress を読む前提になっていないか。**ボードだけを見る**設計になっているか。
- [ ] **名前の衝突**：「中央」が親と反映係のどちらを指すか曖昧でないか。`docs/relay/` と `docs/design-reports/` が混ざっていないか。
- [ ] **設計伝達レポート**：改訂6点（教訓節・逸脱の独立カテゴリ・予約レンジ採番・マイグレ プレースホルダ・該当なしの扱い・ファイル名）が反映されているか。
- [ ] **progress**：「要求しない」が**要求する側**（親・反映係）のプロンプトにも書かれているか。
- [ ] **教訓の昇格**：再発防止が要るものを playbook／コマンド仕様／指示書テンプレへ昇格させる運用が書かれているか（retrospective に書いて終わりになっていないか）。

## 6. 未決・要観察
