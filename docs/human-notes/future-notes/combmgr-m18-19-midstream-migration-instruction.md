## 4. 親チャット起動プロンプトの必須項目

`decisions-report.md §5` のチェックリストを満たすこと。特に：

- **担当範囲**：M18/M19 の残タスクを**1つの親**が持つ。
- **親は実装レポートと progress を読まない。ボードだけを見る。**
- **親は設計書を直接編集しない。** パッチを発行して反映係（Claude Code）に適用させる。
- **「中央」という語を使わない。** 第1版の中央＝**反映係**。新設の**親**とは別層。両者を同じ語で呼ぶと必ず取り違える。
- **設計判断に長い検討が要るサブは個別設計チャットへ外注する**（親が肥大しないため）。外注時は親が起動プロンプトを作り、開発者がコピペで渡す。
- **CHANGE 番号は M18/M19 の間は従来どおり registry 採番**（ブロック割当は M20 から）。
- **マイグレは新規作成分からプレースホルダ運用**（§7）。

## 5. 設計伝達レポート コマンドの改訂（今回入れる分）

対象＝既存のカスタムコマンド（正本は `docs/process/remote-ops-proposal.md §4.3`）。**今回入れるのは4点のみ**：

1. **§6 教訓を追加**し、「**親は読まなくてよい**（反映係が retrospective へバッチ反映する）」と節に明記。
2. **「契約・設計に反する独自判断」を独立カテゴリに切り出す。** 親の処理は**受理して DES/契約を更新するか、却下して差し戻すか**の二択。**未処理で流れることを避けるのが目的。**
3. **該当なしの扱いを定義**：「該当が無い節は『なし』の一行で終える。埋めるために書かない。全節が『なし』ならその旨だけのレポートを出す。」
4. **ファイル名を「例外だけ」と分かる形へ**（例 `YYYYMMDD-<id>-design-exceptions.md`）。出力先も `docs/design-reports/` へ（§ 名前空間の分離）。

**持ち越し**（M20 から）：§5「registry で採番」→「契約ファイルの予約レンジから採る」の書き換え。**M18/M19 は registry 採番のままなので今は変えない。**

> 既存コマンドの良い点（差分主義・根拠必須・**設計判断はしない**）は**維持する**。§1〜§5 が既に宛先で割れている構造も壊さない。

## 7. マイグレ番号の扱い（M18/M19 に固有）

**確認済みの前提**（開発者回答 2026-07-27）：M18/M19 のマイグレ番号は**重複しないよう事前に割り当て済み**。開発は**別環境で `go run`**（レーンごとに 0 から順適用される DB）。

→ **番号の衝突は無い。開発環境でも問題は出ない。** ただし以下の1点だけ残る。

### 残る危険＝マージ順と番号順の不一致

- golang-migrate が見るのは**単一の現在バージョン**のみ。仮に M18=24／M19=25 で**重複ゼロでも**、**M19 が先に本線へ入って既存 DB が 25 に達すると、後から来る 24 は永久に適用されない。**
- **レーン別作業 DB は毎回 0 から順適用されるため、この事象は開発中に絶対に再現しない。**
- 壊れるのは**すでに番号を通過した長寿命の DB** ＝ **友人配布分**と**開発者の常用 DB**。

### 実務上の危険条件は1つだけ

**2つのマージの間に、配布（または常用 DB の up）が挟まるかどうか。**

| ケース | 判定 |
|---|---|
| 両方が次の配布より前にマージされ、その間に既存 DB が高い番号へ進まない | **問題なし** |
| M19 だけ入った状態でビルドを配布してしまう | その後の M18 の 24 が**友人の DB に入らない** |

### 対処（どちらか）

1. **番号順にマージする**（低い番号を含むレーンを先にマージ）。**これだけで危険は構造的に消える。** M18/M19 は本方式で足りる。
2. マージ順を自由にしたい場合のみ、**マージ直前に本線の最新番号＋1 へリネーム**する（up/down 両方）。

### 統合担当への指示（この作業で実施すること）

開発者はどちらのレーンが低い番号を持つか把握していない。**統合担当が確認して確定させる。**

1. **番号の実査**：両レーン（M18/M19 の worktree・ブランチ）の `migrations/` を走査し、**各レーンが持つマイグレ番号を列挙**する。本線（main）の現在の最大番号も併せて確認する。
2. **マージ順の確定**：**低い番号を含むレーンを先にマージする順序**を決め、ボードへ明記する（例「マージ順＝M18(024) → M19(025,026)」）。
3. **矛盾があれば報告**：番号が実際には重複している／本線の最大番号を下回るものがある／レーン内で連続していない等を見つけた場合は、**自分で振り直さず ⑤ 突き合わせ報告へ挙げて開発者へ返す**（マイグレ番号は「データの根」に触るため人間判断）。
4. **番号順マージが困難と判明した場合**（例：先に仕上がるのが高番号側で待てない）は、§7 対処2（マージ直前のリネーム）を提案し、リネーム手順を指示書に落とす。
5. **記録**：現況（どのマイグレが何番を持ち、マージ順がどうなるか）を**ボードの「予約レンジの消費」欄**へ。
6. **配布の制約**：**「配布は両レーンのマージ完了後に行う」**をボードの保留事項へ1行。公開が近いため、片方だけ入った状態でビルドを配ると既存 DB に穴が開く。

> **M20 以降の一般則**：事前割当は「**マージ順を番号順に縛る**」条件付きで安全。マージ時採番はその縛りを外せる（先に仕上がったレーンから merge できる）。どちらを採るかは開発者判断。

## 8. 予行演習としての記録（今回限り）

M18/M19 は**新方式の予行演習**であり、失敗しても被害が小さい。M20∥M21 の本番前に playbook を直すため、**うまくいかなかった点をボードへ1行ずつ残す**。特に：

- **親が結局読まされてしまったもの**（＝宛先分離の漏れ）
- **レポート様式で足りなかった節**
- **リレー回数が最初と最後だけに収まらなかったケースとその理由**
