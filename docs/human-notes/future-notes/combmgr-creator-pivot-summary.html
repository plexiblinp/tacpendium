Strategy Summary · Creator-Centric Pivot

発信者中心への戦略転換
現時点まとめ

Tacpendium ／ ステータス: 検討中（一部決定・記録） ／ 種別: 戦略メモ

本アプリの利用者は少数の発信者（生産者）と多数の閲覧者（消費者）に分かれる、という市場構造の発見を受けた戦略整理。普及の鍵は代表的なコンボ発信者の移行、継続価値の北極星は主要発信者がアップデートごとに本アプリ用 CSV を出し続けているか。機能は需要駆動の規律で濃淡をつけ、メディア保持・取り込み変換・GitHub 集約の各論点を記録する。

01結論（一言で）

CONCLUSION コンボ/セットプレイを能動的に探す人は多数派でない。本アプリは「発見者が記録・発信しやすくするツール」と捉え直す。大多数は発信者の CSV をインポートして閲覧する側で、自力探索は新キャラ登場直後など例外。よって生産者を獲れば消費者は付いてくる（逆は成立しない）。次の一手は機能追加でも体系研究でもなく、発信者便益仮説の言語化と少数検証。

本書は決定記録ではなく検討中のスナップショット。確定済みはメディア保持方式（§06）と差し返しの後回し、事実はセットプレイ自動提案の自律作成済み（§05）。

02市場構造の発見 — 生産者と消費者

「ユーザー像」でなく「市場構造」の発見である点が重要。

これは CGM（消費者生成メディア）の普通の形。これまで設計してきた「分析者が自分のために記録する」像は、実は生産者像だった。消費者が欲しいのは記録ツールでなく「信頼できる最新コンボを速く引ける」閲覧体験。

NORTH STAR 継続価値の測り方＝主要発信者がアップデートごとに本アプリの CSV を出し続けているか。少数の生産者の継続を見れば全体が分かる。「蓄積閾値」より市場構造に合った指標。

03訂正 — 「生産者/消費者は真逆」は撤回

当初「必要な品質が真逆」と述べたが、行き過ぎ。共通基盤は大きく、phase3 の入力 UX 修正はそのまま消費者にも効く。正確には「真逆」ではなく——

正確な言い方 共通基盤（速い入力・正確な表記・信頼できる参照）の上に、消費者固有の追加面（閲覧・検索・フィルタ・インポート体験）が乗る。別アプリを作る話ではない。ただしその追加面は現状ほぼ未着手で、普及の本体はそこになる、という意識は要る。

04規律 — 「乗り換えは自動では起きない」

危険な仮定 「より優れていれば乗り換えるはず」は最も危険な仮定。発信者は既に YouTube・X・Discord・Sheets で完結し、視聴者もそこにいる。本アプリは二重投稿（既存発信＋CSV 書き出し）を強いる。必要なのは「優れていること」でなく追加の手間を上回る固有便益。

固有便益の候補（テキスト/動画にできないこと）＝視聴者が検索・フィルタ・自分のと比較できる／パッチ差分を構造化して出せる。これを言語化できないとコンタクトは空振る。ゆえに順序を固定する。

  • 発信者便益仮説を言語化（CSV を出す手間を上回る便益は何か）。
  • 代表的発信者 2〜3 人に当てて検証（使う気になるか）。
  • 反応を見てから既存発信フォーマットの体系研究・広いコンタクト。重い研究を先にしない。

05機能スコープの濃淡（需要駆動の規律）

判断軸：(a) 純ロジックで隔離実装できるか (b) 自分で品質検証できるか (c) スキーマの根を動かさないか。一律に止めず濃淡をつける。

初期候補・最有力

確定反撃

  • 純ロジック・あなた自身がドメイン検証者・公開が少なく自力探索需要が高い、の三拍子。
  • punish-finder（汎用計算モジュール）が既にある。
  • 初期スコープへの引き上げを前向きに検討する価値が最も高い。
自律作成済み（事実）

セットプレイ自動提案 — 目玉機能

  • 過去担当と自律作成済み。「作る」作業は終わっている。前例を聞かない差別化。
  • テコの鋭さ：コンボは探すがセットプレイは面倒で皆サボる（最も退屈な工程の自動化）。アレンジ版コンボを見つけた人が走査だけしたい需要は確実。機能が入口になり「これを動かしたくてコンボを探し始める人」も生む。
残る関門 目玉だけに提案精度が生命線。外れると逆に信頼を毀損する。残作業は「作る」でなく精度ゲート（デモで実用域か）＋初期採用判断。品質検証はあなた（ドメイン）が机で。
設計先行（スキーマに触る）

メディア添付・SNS リンク

「無いと論外」に同意。ただしロジックでなくデータモデル＋ストレージの話で、要望駆動で後付けすると破壊的移行になる＝「継ぎ目を最初に残す」案件。方式は §06 で決定済み。

後回し（合意）

差し返し

  • 需要はあるが優先度を下げ、後続フェーズへ。

06メディア保持方式（決定）

DECIDED — 保持する2フィールド コンボ/セットプレイに、①インターネットリンク1つ（YouTube・X 等）と、②tacpendium.exe のカレントからの相対パスで video/ 配下のファイルを指すパス1つを持たせる。
  • CSV 同梱：可。リンク切れ・ファイル不在は「ただ閲覧できないだけ」で許容するため、往復 CSV にそのまま含めてよい。
  • 初手はリンク先行が安全。URL とパスは軽量・即値で、スキーマの継ぎ目（リンク列）を最初から持たせる。
  • 「自分の動画が回ってほしい」という発信者動機を、リンク保持が同時に満たす。
分離する論点 動画ファイル実体の配布方法（サイズ問題）は別途検討。本決定は「参照（リンク／相対パス）を持つ」までで、実体の同梱・配布・容量設計は切り離す。スキーマは参照を持てば足り、配布は後で詰める。

07取り込みプロンプトと最大の鬼門 — 技コード変換

発信者の既存成果物（動画・Sheets・テキスト）を AI 整形で取り込むヘルパー。移行障壁を直接下げる隠れた獲得テコ。

鬼門 表記揺れより内部 move_code への変換が本丸。「立ち弱P」「2LP」「c.LP」等無限の表記 → 一意のコードの多対一マッピングで、AI はもっともらしく誤る（存在しないコードを自信満々に生成）。ここで誤ると「信頼できる参照」という価値の根が腐る。
AI にやらせる（曖昧でよい所）
  • 自由表記の正規化・候補トークン列への分割
  • 「要約・候補提示」止まり
AI にやらせない（確定が要る所）
  • 技コードの生成・確定（生成させた瞬間に負ける）
  • 断定。事実 in／表現 out の原則を厳格適用

二段変換：①AI が表記を正規化し候補に割る（曖昧）→ ②アプリが move マスタ（キャラ別・エイリアス込み）への厳密照合で確定し、未解決は人に出す（確実・コード側）。副次の鬼門＝キャラ固有表記・ラッシュ版・システム技（ドライブ系）・modifier（ジャスト/ディレイ）の混入。テコ：未解決を人に出す UI は moves-input-tool／CSV import の人レビュー動線にそのまま乗る（新規でなく既存突合動線の拡張）。

08GitHub コンボリポジトリ構想（記録）

QMK 型の集約。アイデアとして記録、需要が見えてから器を作る位置づけ。

構想・時期尚早

方向性は良いが、器は需要の後

  • QMK が機能したのは設定共有に強い既存需要があったから。リポジトリは需要を作らず既存需要を増幅する器。CSV を出す習慣がまだゼロの今は空のままになる。
  • アカウント不要案：プッシュ＝コミット＝アカウントが GitHub の前提。代替は (a) PR でなくフォーム/Gist/ファイル受け → 開発者が束ねてリポジトリ化（投稿者は GitHub 不要・Awesome リスト型）、(b) アプリ内「共有用 CSV 書き出し」を磨き、流通は既存 SNS に委ねリポジトリは集約に徹する。
  • 初手は (b)。分散プッシュの器は需要が見えてから。

09次の一手・オープン論点

NEXT 機能追加でも体系研究でもなく、発信者便益仮説の言語化と 2〜3 人での検証。通ってから研究・器・機能を需要駆動で足す。

外出レーン §1 へ追加で記録する調査・設計テーマ：

  • 取り込みプロンプトの二段変換設計（AI は表記を均すだけ・コードはアプリ照合）。
  • セットプレイ自動提案の精度ゲート設計（作成済みゆえ、検証プロトコルが残作業）。
  • 確定反撃の初期スコープ引き上げ検討（純ロジック・自分が検証者・需要高）。
  • メディア参照のスキーマ継ぎ目設計（リンク列・相対パス列・CSV 往復への載せ方。実体配布は分離）。
  • GitHub 集約構想（Awesome 型・アカウント不要受け口・初手は共有 CSV 書き出し）。
