## 0. 一行

**外出先（大会会場・オフライン対戦会）の対戦前に、必要な情報へ索引から辿り着ける単一ファイル HTML を出力する。** アプリがやるのは**対象データを集めて目次を付けるだけ**。

---

## 1. なぜスマホアプリ版ではないのか（確定）

問いの出発点は「PC 版をメインとしつつ、スマホでデータを持ち運びたい」。**ネイティブアプリ版は採らない。**

| 理由 | 内容 |
|---|---|
| **DNA 衝突** | 「軽量・**インストール不要**」が根本価値。ネイティブアプリはインストール・ストア審査・リリースサイクルを伴う |
| **レビュー時間の恒久的倍増** | 第二のコードベース。**希少資源はレビュー時間**という中心価値に真っ向から反する（並列プロセス改善の努力と方向が逆） |
| **本当のコストは UI でなく同期** | 「持ち運ぶ」＝同期＝競合解決・版管理・同一性。それは **M22（協調基盤）＋分散同期層**。最難関を前倒しすることになる |

**PWA も答えではない**（一度検討し却下）。PWA は「同じアプリをアプリらしく見せる」もので、問題が「**アプリの形が対戦前に合っていない**」（編集 UI・登録フローは会場で邪魔・読み取り特化ではない）なら解決しない。

→ **要るのはプラットフォームでなく出力形式。** 「PDF/PNG には索引が付けられない」という不満そのものへの回答が単一ファイル HTML。

### 単一ファイル HTML が良い理由

- **iPhone / Android 両方でブラウザで開くだけ**。インストール不要・ネット不要・ファイル1つなのでメールでも Drive でも運べる。**DNA を一切壊さない**。
- **既存レーンに乗る**。新機能でなく M13/M17 のエクスポートの延長。器を増やさない。
- **発信者ピボットに直結**。便益リストの「派手出力モード」そのもの。しかも**閲覧者はスマホにいる**＝自分用の持ち運びと配布物が同じ成果物になる。
- **同期が要らない**。会場では読むだけ＝片方向。**M22 を待たずに解ける**。

## 2. 容れ物と寄稿者（構造の核・確定）

**アプリがやるのは「対象データを集めて目次を付けるだけ」。**

拡張が自然に吸収される理由は明確で、**容れ物は各機能の中身を知らない**。知っているのは「セクションの見出しと本文の断片をくれ」という契約だけ。将来機能（確定反撃・メモ・比較・VOD 等）はその契約を満たすだけで載り、**容れ物側の改修はゼロ**。

### 2.1 寄稿契約（最小4つ）

| # | 項目 | 備考 |
|---|------|------|
| 1 | セクション名 | 目次に出る見出し |
| 2 | アンカー ID | 目次からのジャンプ先 |
| 3 | 並び順 | 出力内の位置 |
| 4 | **既存の表記ソースで整形済みの本文** | **重要**（下記） |

### 2.2 容れ物の責務（これだけ）

- 目次生成（全セクションから自動）
- アンカー結線
- 自己完結パッケージング（単一ファイル化）

### 2.3 禁止事項（継ぎ目のドリフト対策）

- **第二のレンダリング層を作らない。** 表記・整形は**既存の単一ソース**（表記正典・共通コード）から生成し、エクスポート用テンプレートに書き写さない。書き写した瞬間に**アプリ表示と出力がずれる未来が確定**する（Fable 指摘の「同じ概念の二重表現」そのもの）。
- **機能ごとに個別エクスポートを生やさない。** 確定反撃用・メモ用・コンボ用と分裂させると出力が3系統になる。**共通の容れ物へ寄稿する**構造を守る。

## 3. 選択の仕組み（確定・新設しない）

会場で見たいものは人によって違う（コンボ／セットプレイ／確定反撃／メモのチェックリスト／要約記事…）。**しかしこれを設定マトリクスにしない。**

- 出力対象 × 詳細度 × 機能種別の組み合わせを設定画面で持たせると、**レビュー時間を食う割に誰の最適にもならない**。友人 FB の教訓（過保護な UI は UX を下げる）と同じ罠。
- **アプリには既に階層フィルタ・プリセット・マイリストがある。「いま画面で絞り込んでいる状態」こそがその人の需要。**
- → **新しい選択 UI を作らず、既存の絞り込みをそのまま持ち出す。**

> **M17 で既に実現済み**：エクスポートダイアログは「選択中コンボ、選択ゼロなら現フィルタ結果の全件」を `range=selected&ids=[...]` で渡し、**画面に見えているものと出力が一致する（WYSIWYG）ことを構造的に保証**している（DES-005 §5.13a・CHANGE-072）。**本方針は M17 の設計思想と完全に一致**しており、新たに作るものはない。

---

## 4. 出力内容（確定）

- **テキストと表のみ。**
- **画像・動画は対象外**（実ファイルは出さない）。base64 埋め込みで数十 MB になりスマホで開けなくなるため。
- **外部 URL リンクのみ出力する**（YouTube 等）。
- **ローカルのファイルパス（画像・動画）は出力しない**（開発者確定 2026-07-27）。

> **M17 に前例あり**：視覚出力（PDF/PNG/クリップボード）では **media は `link` のみ**とし video/image は除外、CSV のみ3列維持（roundtrip 契約）という書き分けが既に確定・実装済み（CHANGE-073・DES-005 §5.13）。**HTML 出力もこの前例に従う＝新しい流儀を作らない。**

---

## 5. 前提確認：M17 の as-built（着手前に必読）

**M17（発信者の流通基盤＝import/export 強化）は完了済み**（CHANGE-071〜075）。エクスポート周りは**最近作り込んだばかり**なので、この構想は*新規追加*ではなく**既存構造への形式追加**になる可能性が高い。設計前に実物を確認すること（記憶で確定しない）。

確認済みの as-built（本メモ作成時に project knowledge で確認）：

| 事項 | 状態 |
|---|---|
| **エクスポートダイアログ**（DES-005 §5.13a・CHANGE-072） | 一覧/マイコンボから開くモーダル。**§5.13 の旧エクスポート画面を廃止する「段階廃止案」の第1段**（第2段＝画面除去は別途承認） |
| **出力形式** | CSV / PDF / PNG / クリップボード。**複数同時選択可**（クリップボードのみ排他）・順次生成／順次DL・**ZIP に束ねない** |
| **対象選択** | `selectedIds`（比較機能と共有）または現フィルタ全件。**WYSIWYG 保証**（§3） |
| **出力項目** | チェックボックス**形式別出し分け**（視覚15／CSV 含む17・案B・CHANGE-073） |
| **生成場所** | **すべてフロント側**（DOM→画像/PDF・in-memory・サーバ FS 書込ゼロ） |
| **i18n 境界** | **エクスポート文書内のラベルは固定 ja**／ダイアログ UI ラベルは i18n（M16-06 で正典化・CHANGE-068 踏襲） |

**含意**：HTML は**第5の出力形式としてダイアログに1つ追加**する形が最も自然。選択・対象範囲・項目チェックボックスの機構は既存を再利用でき、新規に作るのは「HTML 生成器（＝容れ物）」と「目次生成」のみ。**i18n 境界（文書内は固定 ja）も踏襲する**。

## 6. 想定シーン（需要の出所）

- 大会会場・オフライン対戦会などの**外出先での対戦前**。
- PDF/PNG のみだと**索引が付けられない**ため、持ち運んでも必要な瞬間に必要な情報へ辿り着けない恐れがある——これが本メモの直接の起点。
- 補強：メモ機能の AI 記事生成でも「学習中は長文記事／**対戦直前はチェックリスト**」という同じ瞬間が独立に想定されている。**別々の構想が同じ瞬間を指しているのは、需要が本物である傍証**。

---

## 7. 段取り（需要駆動）

1. まず **コンボ＋セットプレイだけ**を容れ物に載せる（＝今エクスポート対応済みの範囲）。
2. 開発者自身が実際に会場へ持って行く。
3. 「確定反撃も要る」と分かってから**寄稿口を増やす**。

「人によって需要が違う」は現時点では推測であり、実データは友人 FB 第一波のみ。**先回りして全機能分の寄稿口を作らない。**
