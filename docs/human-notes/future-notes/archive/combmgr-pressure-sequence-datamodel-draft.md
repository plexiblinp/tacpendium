# 連携技（固め連携 / pressure sequence）— 論理データモデル草案

> **種別**: 論理モデル草案（全般相談役がドメイン要件から起こした骨子）。**物理設計は未確定**。
> **次工程**: 設計担当が des-003 の規約に沿って物理スキーマ（型・制約・index・命名・マイグレーション）へ落とす。本書は「何を・どんな単位で持つか」の合意まで。
> **前提**: des-003 に連携技の器は**無い**（新規）。自律運用は `reference/` 蒸留版のみ・本体ソース非参照。

---

## 1. これは何か

**固め連携**＝ガードさせて相手を拘束し、隙間と択を管理する一連の行動。コンボ（ヒット連続技）とは目的が逆で**ガード前提**。1つの固め全体を**1記録単位**とし、**ある通常技から派生する複数の連携をツリー表示**する。

- コンボとは**別テーブル**（目的・属性が異なる）。
- ただし**ステップ／modifier の構造はコンボに揃える**（流用・将来マージのため。別紙 CSV 契約 `recipe[].modifiers` と同型）。

## 2. エンティティ（論理）

### 2.1 pressure_sequence（連携＝記録単位 / ツリーの枝）

| 論理フィールド | 意味 | 備考 |
|---|---|---|
| character_code | どのキャラの連携か | コンボと同様の参照 |
| starter_move_code | 始動の通常技 | **ツリーの親キー**（同一 starter の連携が枝として集まる） |
| drive_gauge_drain | ガード時のドライブゲージ削り量（合計） | **小数許容・範囲 -6.0〜6.0**／**相手パリィなし前提**／連携合計のみ（step 単位は持たない） |
| weakness_renga | 連ガか | bool フラグ |
| weakness_invincible_reversal | 無敵（=ジャスパ）割り込み可否 | bool フラグ |
| weakness_impact | インパクト割り込み可否 | bool フラグ |
| weakness_4f | 4F 割り込み可否 | bool フラグ |
| weakness_punish | 確定反撃可否 | bool フラグ |
| weakness_note | 弱点の自由入力 | 上記フラグで表せない補足 |
| memo | 自由メモ | |
| tags | タグ | コンボのタグ機構を流用できるか要検討 |

> **drive_gauge_drain の注記**: 渡している設計書ではドライブダメージが正数かもしれないが、**最新仕様では -6.0〜6.0 の小数**。最新を優先。符号・小数の扱い（DB 型・丸め）は物理設計で確定。

### 2.2 pressure_sequence_step（ステップ）

| 論理フィールド | 意味 | 備考 |
|---|---|---|
| sequence_id | 所属する連携 | FK |
| step_order | 順序 | 昇順 |
| move_code | 技 | moves.code 参照。非技ステップは別途 type で識別（コンボ流用） |
| modifiers | 入力上の工夫 | **コンボと同型**＝flags/notes/type。例: 必殺技キャンセルのディレイ、始動の先端当て |
| whiff_or_counter | 空振り得るステップか | bool。「相手が暴れたらカウンター、何もしなければ空振り」を表す（例: 弱P弱P弱P中P の最後の中P）。連携の一部として残す |

## 3. 要件 → モデル対応（トレーサビリティ）

1. **modifier 必要（キャンセルディレイ・先端当て等）** → `step.modifiers`（コンボ流用）。
2. **空振り得る技も連携に含める** → `step.whiff_or_counter`。
3. **ドライブ削り量（パリィなし前提）** → `pressure_sequence.drive_gauge_drain`（-6.0〜6.0 小数・合計のみ）。
4. **弱点記録** → フラグ5種（連ガ／無敵割り込み／インパクト割り込み／4F割り込み／確定反撃）＋ `weakness_note`。
5. **始動通常技から派生・ツリー表示** → `starter_move_code` を親キーに、複数 sequence を枝として描画（表示側で木に）。

## 4. 物理設計で詰める論点（設計担当へ）

- 各フィールドの**型・制約**（特に `drive_gauge_drain` の小数型・範囲チェック、符号）。
- `starter_move_code` / `move_code` の **moves への参照のしかた**（code 参照か内部 ID か。CSV 契約は code 参照方針）。
- **modifiers の格納形式**（コンボと同じ JSON 構造を共有するか）。
- weakness フラグ群を**個別カラムにするか、ビットフラグ/サブテーブルにするか**。
- tags をコンボのタグ機構と**共有するか専用にするか**。
- index（`(character_code, starter_move_code)` でのツリー取得を想定）。
- **非技ステップ**（コンボの `modifiers.type` 方式）を連携でも踏襲するか。
- des-006 系の検証（必須・範囲・ステップ 0 件の扱い等）。

## 5. コンボとのマージを見据えた指針（重要）

別テーブルだが、**将来コンボと統合・相互運用する可能性**があるため、最初から揃えておく。

- **step / modifiers の構造をコンボと同型に保つ**（フィールド名・JSON 形）。別物の綴りにしない。
- **move 参照は code ベース**で統一（CSV 契約と同じ）。整数 ID 直参照にしない。
- **命名・enum・日時・論理削除の規約を des-003 / combomgr-conventions に合わせる**（コンボ側と一貫）。
- マージ時に効くよう、**「コンボと共有する概念（step・modifier・tag・move 参照）」と「連携固有の概念（drive_gauge_drain・weakness_*・whiff_or_counter・starter ツリー）」を明示的に区別**して記録しておく（下表）。

| 区分 | 項目 |
|---|---|
| コンボと共有（揃える） | step 構造 / modifiers(flags,notes,type) / move の code 参照 / tag / 命名・規約 |
| 連携固有 | starter_move_code（ツリー親）/ drive_gauge_drain(-6.0〜6.0) / weakness_* フラグ5種＋note / whiff_or_counter |

> マージ手順を後で書くときは、この「共有／固有」の区分が出発点になる。共有部分はそのまま寄せ、固有部分は連携専用列として残すか、コンボ側に概念拡張するかを判断する。
