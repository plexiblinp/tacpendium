## 0. なぜこの話が出てきたか（経緯）

唐突に映るかもしれないので、考えるに至った流れを先に共有します。

本アプリについて、開発の合間に考えることがありました。本アプリは一発屋ではなく**継続して利用してもらいたい**。そこで「短期間で離脱されないために大切なことは何か」「アプリが本当に継続して使われているかをどう知るか」を考えていました。

その時に気づいたのが、**コンボやセットプレイを積極的に探す人は、そもそも多数派ではない**ということです。多くの利用者は、誰かが見つけたコンボを受け取って使う側です。

ここから結論が出ました。**発信者にとって魅力的な機能と、記録・発信しやすくする仕組みを提供して、発信者を取り込むことが一番重要**だ、と。そういう発信者に、メモやエクセルといった他の手段から**乗り換えてもらいたい**。そして本アプリの価値は、**この少数の発信者が継続して利用し、CSV 等を配布し続けているか**で測れる、と考えています。

この観点で見ると、**現状のフェーズ3までの施策では不十分**でした。そこで、フェーズ3 内にさらに取り込みたい機能が出てきた、というのが本書の趣旨です。

## 1. フェーズ3 に追加で取り込みたい機能

以下を取り込みたいです。**確定反撃とセットプレイの自動提案は、本体設計にまだ取り込んでいないはず**なので、特に丁寧に説明します。

### 1-1. 確定反撃の記録機能（**本体未取り込み・先行設計あり**）

相手の攻撃を**ガード**または**ジャストパリィ（just parry）**した後の有利フレーム中に、自分の技を当ててコンボを始める——これが本アプリでの確定反撃です。通常コンボと違い、**技をガード／ジャストパリィされた相手**と**反撃する自分**の二人が登場するのが特徴です。

これを記録する機能は**隔離環境に先行設計・実装が存在**し、本体設計には未取り込みのはずです。**詳しくは別資料 `combmgr-punish-finder-spec-draft.md` を取り込む形にしたい**。骨格だけ要約すると、

- **確定反撃は「新しいコンボ」ではなく「既存コンボ＋文脈（誰の・何の技をガード／ジャストパリィしたか）の関係」**として持つ。別コンボの自動生成はしない（表示のみ）。
- ストリートファイター6 では**確定反撃は必ずパニッシュカウンター（punish counter）**になるため、ガード始動はダメージ再計算が要る。**ただし自動確定はせず「提案値を入れておきユーザーが確認・編集」**とする（FR307＝自動計算しない原則に合わせる）。ジャストパリィ始動はダメージが大きく狂うので**ユーザー手入力**。
- 探す画面と、実際に使う反撃だけを残す画面（マイコンボ相当）の**2画面・ツリー表示**。

データの根に関わる論点（相手キャラ／相手技という文脈軸の追加、ジャストパリィ後の有利フレームが現在 `moves` に無い＝新データ要求、距離による除外の永続化）は spec draft に整理してあります。物理設計はそちらを土台にお願いします。

### 1-2. セットプレイの自動提案（**本体未取り込み・先行設計あり**）

これも本体設計に未取り込みのはずなので丁寧に説明します。**コンボの有利フレーム（ノックダウン後など）から、成立するセットプレイのレシピを自動で提案する機能**です。コンボは皆そこそこ探すが、**セットプレイは探すのが面倒で後回しにされがち**で、ここに未充足の需要があります。「アレンジ版コンボを見つけた人が、その後のセットプレイ走査だけ自動でやりたい」「この機能を使いたくてコンボを探し始める」——といった入口になり得る、**差別化の目玉**だと考えています。前例も聞きません。

これも**先行設計・実装が存在**するので、それを取り込む形にしたい。統合は確定でお願いします。ただし**提案の精度が生命線**（外れると逆に信頼を損なう）なので、**一度デモで出力品質を確認してから本実装**に進めたい。精度が低ければ提案ロジックを直してから出す、という品質チェックの一段だけ挟む想定です。

### 1-3. インポート／エクスポート機能の強化

M13 で実装してもらいましたが、発信者の流通を支えるには**さらにテコ入れが必要**だと思っています。ここは作り込みを先に固めるより、**マイルストーンを作って協議しながら改善**していきたいです。

### 1-4. 発信者の既存フォーマットをなるべく簡単に取り込む仕組み

発信者がメモ・エクセル・テキストで持っている既存資産を、取り込み CSV に変換するヘルパーです。**最大の鬼門は表記揺れより、内部 `move_code` への変換**です。ここは原則を外したくありません。

**[決定] 二段の役割分担は外さない：**
- **① 表記正規化（曖昧）＝アプリ外プロンプト**。無料サービスで動く整形プロンプトとして作る。AI の役割は「自由表記 → *候補*トークン列への正規化・要約」**まで**。
- **② コード確定（確実）＝アプリ側**。`move_code` の確定は **move マスタ（キャラ別・エイリアス込み）への厳密照合**で行い、未解決は人レビューに出す。**AI に技コードを生成・確定させない**（生成させた瞬間に信頼の根が腐る）。

**[要設計]**：①の出力契約（AI が返す正規化候補の形式）と、②の照合 IF・未解決の人レビュー動線。**②の人レビュー動線は既存の `moves-input-tool`／CSV import 突合動線の拡張**として設計可。副次の鬼門＝キャラ固有表記・ラッシュ版・システム技・modifier の混入。

### 1-5. メディア参照（リンク＋ローカル相対パス）

**ローカル上の画像・動画、および YouTube 等の URL をコンボに添付可能**としたい。

- 搭載単位：**コンボのみ**。セットプレイは持たない（その動画にセットプレイまで録画する運用で吸収）。
- フィールド：**3つで確定**。①**インターネットリンク1つ**（YouTube・X 等）、②**`combomgr.exe` のカレントからの相対パスで `video/` 配下のファイルを指すパス1つ**、③**`combomgr.exe` のカレントからの相対パスで `image/` 配下のファイルを指すパス1つ**。
- 個数：**各1個**（リンク1・`video/` 相対パス1・`image/` 相対パス1）。
- 重複判定：**dup 判定の対象外**（FR301 のレシピ同一性に含めない）。
- CSV：**往復 CSV に同梱可**。リンク切れ・ファイル不在は「閲覧できないだけ」で**許容**。
- 順序依存（重要）：**M13 完了済み＝既存 CSV 列契約が確定している**ため、メディア参照列の追加は**既存 CSV 契約の改訂**になる。export/import 契約への列追加を破壊的にしない形（意味単位・後方互換）で設計してください。

> なお、**動画ファイルの実体の配布方法（容量設計）は別途検討**とし、今回は分離します。本書で確定するのは「**参照（リンク・相対パス）を持つ**」ところまでで、実体の同梱・配布・サイズ設計は後で詰めます。

### 1-6. コマンド入力解決（簡易版・**仮想/物理コントローラ入力の自然化**）

発信者にとって入力の自然さ・速さは魅力に直結しますが、現状のレシピ入力は**プルダウン中心で手間が大きい**（FB④）。そこで方向＋ボタンを技に解決する「コマンド入力解決」を入れたい。**入力方式の改善（FB④）と通しで読んでください。**

ただし**ゲーム内仕様の忠実再現はせず、簡易化**します。死守する契約と範囲だけ示します（詳細はスタンドアロン版 `combmgr-command-resolution-request.md` を正とする）。

- **[決定] 公式表記のみ解決**。簡易入力（623 でなく 636 等の汚い入力）はサポートしない。→ 曖昧なモーション認識ではなく**クリーンな入力状態 → `move_code` の決定論的ルックアップ**になる（入力エンジン再実装ではない）。この線は緩めない。
- **[決定] 段階2まで決定論解決を実装**：①しゃがみ・ジャンプ攻撃（押下時の方向ゾーンで variant を引く）、②単方向＋ボタンの特殊技（`moves.command`〔CHANGE-027〕からキャラ別ルックアップ。「特殊技が定義されていれば優先」の一行ルール）。
- **[決定] 必殺技・空中特殊技はモーション解決しない**。方向トークン列＋時間＋溜めは段階1-2 と別物で、仮想クリックでの 236 実演も不自然。代わりに**「技を直接指定する入力」**とする。
- **[委譲] 必殺技の直接指定の UI 形式は決め打ちしない**（必殺技ボタン＋強度／技ピッカー／直前方向＋必殺技ボタン 等は選択肢）。**割り切るのは「仮想コントローラでモーションを実演させない」一点のみ**で、代替 UI の形は開けておく。
- **[決定] 物理コントローラでの実モーション入力は M18 へ後送り**（物理限定・別マイルストーン）。仮想側は必殺技＝常に直接指定。
- **[決定] どの UI・段階でも出口は必ずキャラ別 `move_code`**（死守）。
- **[要設計] エンジンは取り込みヘルパー（§1-4）と共通化**：「クリーントークン → キャラ別 `move_code`」の引き当ては `236LP → hadoken_light` の表記解決と同一エンジン。`moves.command` から一度索引を作り、(a) コントローラ入力と (b) 取り込み表記解決の両方を賄う。二度作らない。

## 2. すでにフェーズ3 に取り込み済み／重複の可能性があるグループ（**要確認・申し送り**）

ここからは**新規に追加してほしいものではありません**。私の整理の中に含まれていたが、**おそらく現行のフェーズ3（overview の M14〜M18 あたり）で既に検討中のはず**の項目です。重複している可能性が高いので、**現行フェーズ3 と突き合わせて重複を排除**してください。新設でなく、二重作業を避けるための共有です。

- **データモデル拡充系**：SA ゲージの消費記録、ドライブゲージの小数化、起き攻めへの「打撃重ね」追加＋起き攻めの正規化、ジャンプ（前ジャンプ・垂直ジャンプ）の move 化。中身の差分案は `combmgr-friend-feedback-datamodel-issues.md` に options として整理済み（消費量＝手入力で持つ／ジャンプ move 化は FR301 レシピ同一性に波及、の2点だけ注意）。
- **UX 改善（友人フィードバック第一波）**：入力方式（プルダウン→ボタン等）、表記整理、タグ色選択、初回オンボーディング。
- **配布是正・スキーマ整理（M14）の実行**：調査は終了済み。取込画面廃止・取込専用列削除・FR704 降格を含む破壊的整理。これは overview に既にあるはずです。

> これらが現行フェーズ3 とどう重なるか／重ならないかは、設計担当の側が正です。私の整理と矛盾があれば、現行を優先してください。
