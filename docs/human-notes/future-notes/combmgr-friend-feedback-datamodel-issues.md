# 友人フィードバック起点・データモデル設計論点メモ（承認ゲート向け）

> **用途**：友人リリースの UX フィードバックのうち、**UX 磨き（layer 1〜3）ではなくデータモデル/仕様の判断が必要な項目**だけを切り出し、設計担当の承認ゲートに渡すための論点整理。
> **スコープ外**：ラベリング・アフォーダンス・入力動線（プルダウン→ボタン等）の layer 1〜3 修正は本メモに含めない。それらは可逆自律枠で別途進める。
> **フィードバック主の属性**：エンジニア＋SF6 複数キャラ上位1%。開発者本人よりドメインが深く、各指摘は**ドメイン妥当性が高い前提**で扱う。
> **本メモの性格**：相談役の整理と暫定推奨。**スキーマの最終決定はデータの根を握る人間（承認ゲート）が行う**。本メモは決定しない。
> 生成日：2026-06-26

## 0. 一行サマリ

データモデル判断が要る指摘は4つ：**①ゲージ属性（始動/消費/バーンアウト）の設計**、**②ドライブゲージの数値型と内部不整合**、**③起き攻けモデルの欠落と平置き設計**、**④レシピステップの taxonomy（技/非技/移動の線引き）**。最大の論点は①。FR303 廃止の経緯を取り違えると判断を誤る。

---

## 論点①　ゲージ属性の設計：始動 / 消費 / バーンアウト

### 現状（事実）
- `combos.drive_available_at_start`（INTEGER 0〜6）、`combos.sa_available_at_start`（INTEGER 0〜3）の**2列のみ**。意味は「コンボ**開始時点**の残量」。
- 消費量は保持していない。かつて存在した `drive_gauge_consumed_total` / `sa_gauge_consumed_total` は **CHANGE-019 / FR303 廃止**で削除済み。
- バーンアウト判定列も無い。
- FR301 重複判定キーは数値ゲージを**対象外**（始動残量は dup キーに含まれない）。

### 友人の指摘
- SA は「始動」と「消費」の**両方**が欲しい。現状の画面表記ではどちらを表すのか判別できない（#11）。
- ドライブの始動残量も、総消費量と誤読されないよう「始動」と明示すべき（#9, #13、キャラ固有資源〔イングリッドのサンシンボル等〕も同様）。

### 論点の核（FR303 廃止の射程に注意）
FR303 廃止が否定したのは**「消費量を自動算出してキャッシュ列に持ち、異常を機械判定する」仕組み**であり、無意味と結論されたのは*その自動キャッシュ*。**ユーザーが消費量を手入力で記録したいというニーズは、この廃止では否定されていない**。ここを「FR303 で消費量は不要と決まった」と短絡すると、ドメインの深い指摘を誤って却下する。

SF6 のドライブは「残量＜消費量でも技を出せ、出した後にバーンアウトする」仕様（用語定義）。このため用語定義自身が**「実行に必要な最低ゲージ量」と「実行後バーンアウトするか」を分けて管理せよ**と明記している。つまり属性空間は単一列より広い。

| 候補属性 | 意味 | 性格 | 自動算出 |
|---|---|---|---|
| A. 始動残量（現行 `*_available_at_start`） | 開始時に持っている量＝前提条件 | situation/前提 | 不可（手入力） |
| B. 消費量（友人の要望、drive/SA） | このコンボが使う量＝リソースコスト | メタデータ | 不可（コンボ補正同様、原理的に手入力） |
| C. バーンアウト有無（用語定義の (2)） | 始動残量から実行して焼けるか＝終了状態 | メタデータ | 不完全（下記） |
| D. 終了時残量 | 起き攻め・追撃の資源計画用 | メタデータ | 不完全（A−B だが端数・閾値で破綻） |

C・D が自動算出で破綻するのは、(1)「残量＜消費でも発動可」ルール、(2) 端数管理、(3) 始動残量が状況で変動するため。**コンボダメージを自動計算しない（FR307）のと同じ理由で、C・D も自動確定は危うい**。

### 影響範囲
- 列追加は**メタデータ**であり FR301 dup キーに影響しない（同一レシピ＝同一消費なので衝突も起きにくい）。
- 一覧/比較表示・recipe_cache 周辺の表示項目（FR203）に列が増える。
- 入力 UX（cluster B）と連動：消費量の手入力が増えると軽快 DNA を削る。ボタン/ステッパー前提で設計しないと layer-3 の摩擦に化ける。

### 相談役の暫定推奨（決定は承認ゲート）
1. **B（消費量）を drive・SA に手入力カラムとして追加する**方向で再検討。根拠＝高ドメインの実需、ダメージと同じ「手入力で記録」哲学と整合、FR303 が否定した自動キャッシュとは別物。
2. **自動算出キャッシュは復活させない**（FR303 の判断は尊重）。あくまで手入力・参考値（FR305）。
3. **C（バーンアウト）は当面、独立列にしない**のが無難。入力負担増の割に自動確定できず、Bと始動残量から人間が読めば足りる。ただし用語定義が明示する関心事なので、将来「表示上のヒント」として導出表示する余地は残す。
4. **A は列としては正しい。修正は純ラベリング**：「始動時に最低限必要な残量」と明示する一貫表記規約を drive / SA / キャラ固有資源（custom_states）に**横断適用**。→ #9/#13 はこれで解消（layer-1 側で実施、本メモの決定対象外）。

### 開発者確定（2026-06-26）
- **SA ゲージ消費は「記録・表示・比較のみ」。検証（VAL）連動はしない。** phase3-overview の M16 着手前ドメイン確認に対する回答。消費値は B（手入力カラム）として持ち、比較画面で比較軸に使うが、消費量の妥当性を機械判定する検証は**設けない**（FR303 廃止の精神と整合）。
- バーンアウト（C）は引き続き独立列にしない（推奨3 のまま）。

## 論点②　ドライブゲージの数値型と combo↔sequence 内部不整合

### 現状（事実）
- `combos.drive_available_at_start` は **INTEGER（0〜6、整数管理）**。
- 一方、連携技（pressure-sequence）の `drive_gauge_drain` は **-6.0〜6.0 の小数**で設計合意済み。
- 用語定義は「残り 0.1 本」を明示＝ゲージは本来**連続値**。

### 友人の指摘
- ドライブゲージも小数にしてほしい（#8）。

### 論点の核
**combo＝整数 / sequence＝小数という内部不整合が既にある**。友人の指摘は、上位プレイヤーの資源管理が 0.5 本単位以下で効く（キャンセルラッシュ可否が端数で決まる）という実感に基づく。単に「小数化する/しない」ではなく、**combo 側と sequence 側で粒度を揃えるか否か**が本質。

論点①で消費量（B）を入れるなら、消費も小数で持つべきか（OD技1本・キャンセルラッシュ3本など実値は整数寄りだが、複合すると端数が出る）も同時に決める。

### 影響範囲
- 型変更（INTEGER→REAL）はマイグレーション対象。始動残量は dup キー対象外なので**重複判定への波及は無し**（blast radius 小）。
- 入力 UX：自由な小数入力はマニア向け・摩擦大。**0.5 刻み等のステッパー/ゲージ UI** 前提でないと cluster B を悪化させる。

### 相談役の暫定推奨
- **小数（REAL）に寄せて combo↔sequence の粒度を揃える**方向を推奨。ただし入力は数値直打ちでなくゲージ widget（刻み入力）に限定し、軽快 DNA を守る。最終判断は承認ゲート。

## 論点③　起き攻めモデル：打撃重ねの欠落と平置き設計

### 現状（事実）
- `combos` に起き攻け bool が6列：`oki_meaty_neutral_tech_throw` / `_dr`、`oki_meaty_back_tech_throw` / `_dr`、`oki_shimmy_neutral_tech`、`oki_shimmy_back_tech` ＋ `knockdown_advantage`（INTEGER）。
- すべて**手入力前提**（フレームデータから自動推定不可と明記）。
- **カバーしているのは「投げ重ね」と「シミー」のみ**。データモデル設計書自身が、他ゲーム対応時に正規化テーブル `combo_oki_options(combo_id, tech_type, attack_type, uses_dr, available)` への移行を将来検討と注記している。

### 友人の指摘
- 起き攻め状況に**打撃重ね可否**も欲しい（#12）。
- そもそも**起き攻めの書き方の整理が必要**（#12）。

### 論点の核
- **具体的欠落**：起き攻けの三本柱（打撃重ね／投げ重ね／シミー＝詐欺・遅らせ）のうち、**打撃重ねが丸ごと無い**。上位プレイヤーが真っ先に気づく欠落で、ドメイン的に正当。
- **構造的問題**：打撃重ねを「neutral/back tech × DR有無」で足すと bool 列が更に膨らみ、平置き設計が破綻に近づく。**設計書が将来検討としていた正規化（`combo_oki_options`）を、今このタイミングで前倒しすべきか**が判断点。
- 「書き方の整理が必要」＝上位1%の知見で起き攻けオプションの**語彙・分類を一度棚卸し**する価値がある、という示唆。

### 影響範囲
- 列追加 or 正規化は表示（起き攻け情報の UI、FR203）とマイグレーションに波及。
- 正規化に倒すと、6 bool を読んでいた箇所（一覧/比較/recipe_cache 周辺）の改修が要る。
- dup キーには起き攻け情報は含まれない（影響無し）。

### 相談役の暫定推奨
- **打撃重ねを追加して具体欠落を埋める**＋**それを契機に `combo_oki_options` 正規化を前倒し**を推奨。理由＝bool 平置きは追加のたびに列が増え、設計書自身が移行を予見している。NFR407（他ゲーム）への布石にもなる。
- 併せて**友人を巻き込んで起き攻け語彙の棚卸し**を1回行う（彼が言う「整理」）。これは pressure-sequence（連携技）の設計と地続きなので、**そちらと同じ場で詰める**のが効率的。

## 論点④　レシピステップの taxonomy（技 / 非技 / 移動の線引き）

### 現状（事実）
- `combo_steps` は `move_id`（NULL可）＋ `modifiers`（JSON）。
- **技ステップ**＝`move_id` あり。**非技ステップ**＝`move_id` が NULL で `modifiers.type` で識別（例：`parry_drive_rush`、`cancel_drive_rush`、その他テクニック）。
- 一方、ドライブパリィは**システム技として moves に登録**（`category="system"`）。パリィ派生ドライブラッシュは**非技ステップ**（`modifiers.type`）。→ **「moves 行にする」か「modifiers.type の非技ステップにする」かの線引きが既にやや場当たり**。
- 前ジャンプ・垂直ジャンプ（移動としてのジャンプ）は moves にも無く、現状クリーンな置き場が無い。

### 友人の指摘
- 前ジャンプ・垂直ジャンプが move として扱われていない（#7）。
- 「技ステップ／非技ステップ」という表現が分かりにくい（#6、※表現の問題自体は layer-1）。

### 論点の核
- **原則が無い**：レシピ要素を (a) moves 行（システム技含む）、(b) 非技ステップ（modifiers.type）、(c) 隣接 move への modifier、のどれにするかの**判断基準が明文化されていない**。ジャンプ・移動（ダッシュ・歩き含む）がその基準の隙間に落ちている。
- #6 の「技/非技」分かりにくさは、taxonomy が場当たりで、かつ**内部語彙が UI に露出**しているのが原因。**taxonomy を原則化すれば #6 のラベル修正（layer-1）も筋が通る**。

### 影響範囲（重要）
- ジャンプ・移動を「ステップ」として表現に組み込むと、**レシピ本体が変わる**＝**FR301 dup キー（レシピ完全一致）と既存データのレシピ同一性に波及**。マイグレーション設計が要る。
- recipe_cache / エイリアス生成（move ベース）にも影響。移動を move 行にするなら custom alias の対象にもなる。

### 相談役の暫定推奨
- **「moves 行 / 非技ステップ / modifier」の振り分け原則を1枚に明文化**することを最優先。
- 移動（ジャンプ・ダッシュ・歩き）は、ドライブパリィの前例に倣い**システム move として登録**するのが一貫性は高い（エイリアス・表示・始動技参照に素直に乗る）。ただし dup キー／既存レシピ同一性への影響を移行計画とセットで判断。
- 原則確定後、#6 の「技/非技ステップ」というラベルは**ユーザー語彙へ翻訳**（layer-1 側で実施）。

## 付記　「要望駆動で判断」の正しい射程（2026-06-26 追記）

運用方針＝「全キャラ網羅や特殊キャラ使い・上位プレイヤーの需要は掴みきれていないので、要望次第で判断していく」。**この方針は正しい。ただし適用対象を分けること。** 今回のフィードバックが示した教訓そのものなので明文化しておく。

- **機能・UI・動線は要望駆動でよい**。未検証の作り込みを避ける線と整合し、可逆で、要望が来てから動いても遅くない（特殊キャラ専用表示、上級者向け効率機能など）。
- **データモデルの自由度は要望駆動にしてはいけない**。スキーマは後から次元を足すのが高コスト（マイグレーション・FR301 のレシピ同一性・既存ライブデータ）。正しい姿勢は「要望が来てから設計」ではなく「**来うる要望の*形*を吸収できる継ぎ目を最初に残す**」（NFR407/408 の趣旨）。本メモ①〜④は全て、放置すれば後で破壊的移行になっていた*スキーマの穴*＝要望駆動に委ねてはいけない側だった。
- **判断ルール（一つ）**：要望が来たら、まず「**既存モデルの上に乗る機能か／モデル変更を伴うか**」を仕分ける。前者は要望駆動でビルド、後者は承認ゲートで移行コストの非対称性を天秤にかけ、「最初から継ぎ目を持つべきだったか」を問う。**先回りの対象は後者だけ。**
- **過剰一般化の戒め**：だからといって未来の全キャラ向けにスキーマを作り込むのは NFR407 が禁じる過剰抽象化。継ぎ目を残すのは「無いと破壊的移行になる」箇所に限る。判断軸は*移行コストの非対称性*であって、最大柔軟性ではない。
- **サイレントチャーンの補正**：要望駆動は*要望が届くなら*成立する。特殊キャラ使い・上級者は母数が小さく、不満を述べず黙って離脱しやすい（要望ゼロ＝需要ゼロではない）。**上級者を一人、定期的にループに入れておく**——届きにくい層を受け身で待つのでなく能動的に一本釣りする方が、チケットを待つより速い。今回の上位1%フィードバックも、能動的に聞いて初めて得られたもの。
