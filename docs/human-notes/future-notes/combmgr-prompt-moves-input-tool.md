## プロンプト本文（ここから投入）

CLAUDE.md と docs/(01-tech-stack.md / 03-data-model.md / requirements.md / 「FR704 取込規則の正」) を読んで。

これからこのリポジトリで「**moves 手入力支援ツール**」を作る。独立したツールで、フレームデータを手で入力し、**本体（FR704 取込）が受ける CSV を出力するだけ**。本体 DB には触らない。「データは手入力」という本プロジェクトの方針の実行装置でもある。

まず私が仕様を説明する。理解したうえで §1 の計画（内部データモデル・画面構成・モジュール境界・永続化・スタック・**作る範囲の提案**）を簡潔に提案して。合意またはプランでのスコープ提案までは実装に入らないで。格ゲー知識や前提で不足があれば質問して。

### 取込契約（最重要・"正"）

別紙「FR704 取込規則の正」が、CSVスキーマ・code生成・ラッシュ版/固定技・重複定義の**契約**。ツールはこれに厳密に従う。要点：

- **CSV列・型・順序・文字コードは別紙§1（config形YAML）が正**。`total` は CSV に持たない（本体が算出）、`recovery` は持つが非永続、`name_en` は出力しない、に注意。
- **code 生成は別紙§2（DES-004 §2.1）**の決定論ルール。**code と表記（5HP 等）は層が違うので揃えない**（5HP は本体の表示プリセットが後段で当てる）。
- **ラッシュ版はツールが出力しない**（別紙§3.1。本体 FR703 が生成）。出すのは元の通常技・特殊技まで。
- **固定/共通**（別紙§3.2）：共通なのは "code の形" と system/移動/投げの統一 code。**「弱P 等の共通値一覧は存在しない」**（各キャラが固有フレームを持つ）。移動動作は CSV 取込外。
- **重複キーは `(character_code, move_code)`**（別紙§4）。技名では弾かない。FR301 とは別ドメイン。
- **正規化はツール側で一次完了**（別紙補足）：on_hit/on_block 退避・properties の code 化・category 写像・name_ja のフレーバー除去・付記書式 `【ツール付記】{内容}`（複数は `;` 連結）。

**規則はできるだけ設定データ（JSON/YAML）として実装し、別紙の config をそのまま読み込む形**にして。未定項目（改行=LF・BOM なし／列必須セット＝`character_code`・`move_code`・`category`(+実質 `name_ja`) 必須・他は空欄NULL許容／列順=ヘッダ名一致）は**暫定既定で進め、判断が要る箇所は理由つき TODO コメントで明示**（後で直せるように）。細かいロジックは課題として残してよい。

### 機能要件

**出力 / 連携**
- 入力内容から本体取込用 CSV を出力（契約準拠）。
- **CSV 出力後もアプリ上のデータは残る**。
- **FR701 公式フレームデータとの突合チェック**（手入力値の入力チェック）。可能なら本体 FR704 プレビュー相当のドライランで「取込 OK/NG 件数」を表示。

**入力支援（自動化）**
- **英語表示名 → code 自動生成**（別紙§2準拠。衝突時フォールバック含む）。
- **標準技セットのプリフィル**：全キャラが共通して持つ技を、**code とフレーム以外の既定値を入れた行として最初から用意**（フレームは空欄、ユーザーが入力）。対象は2系統。
  - **通常技の標準セット（本命）**：立ち/しゃがみ/ジャンプ × 弱/中/強 × パンチ/キック の標準的な組み合わせ（例：弱P=`standing_light_punch`、しゃがみ強P=`crouching_heavy_punch`、しゃがみ弱K=`crouching_light_kick`、ジャンプ中K=`jumping_medium_kick`）。code は別紙§2 のパターンで機械生成。`is_aerial` は**ジャンプ系のみ true**、それ以外 false。
  - **system/投げ系**：`drive_impact` ＋ `throw_forward`/`throw_back` ＋ `drive_parry`（drive_parry は 発生1・ダメージ0・属性なし）。移動動作・ラッシュ版は対象外。
  - **注意**：通常技の "標準の顔ぶれ" はキャラで過不足があり得る（立ち/しゃがみで欠ける組み合わせ、キャラ固有技など）。**既定セットを出したうえで、各キャラの過不足はユーザーが行追加/削除で調整**できる前提にする（過剰網羅より調整前提）。正確な標準リストは別紙または設計担当に確認（TODO）。
  - ※共通の "値"（フレーム等）は存在しないのでフレームは埋めない。共通なのは code の綴りと既定値のみ。

**編集操作**
- 行の編集／空行追加／行挿入／1行コピー／行削除／行クリア。
- **必須項目が未充足でも途中保存可**。
- **Undo / Redo**。

**入力体験**
- **キーボード中心**（Tab/Enter でセル移動、矢印キー、Excel 的操作）。
- **スプレッドシートからの貼り付け一括入力**（TSV/クリップボード。行・列単位）。※複数人同時編集は作らない（オフラインで各自が用意して貼る運用を想定）。
- **入力途中の自動保存・復元**（更新・クラッシュで消えない）。
- **キャラ単位の作業**（1キャラを選んで集中入力 → そのキャラだけ出力）。

**検証**
- リアルタイムの最低限バリデーション（数値項目に数値以外 → 即警告）。
- **重複チェック**（`(character_code, move_code)`。技名では弾かない）。
- 必須未充足の可視化（保存はできるが、未完のセル/行に印）。

**表示 / UX**
- 通常技・必殺技などの**セクション分け**。
- 列ヘッダを**常時固定表示**（Excel の固定行のように）。
- 行は**縞模様**。
- **ダーク基調・モード切替なし**（私用ツール）。

### 永続化・スタック

- スタックは本体に合わせる。入力途中状態の自動保存はローカル永続化（SQLite 等）。
- ツールは**ローカルで CSV を吐くだけ**。本体 DB へは書かない。

### テスト要件（決定的に検証）

- **CSV ラウンドトリップ**（入力 → CSV 出力 → 再パースで一致）。
- **code 生成規則**のユニットテスト（別紙§2 の例・衝突フォールバックで検証）。
- **重複検知**（`(character_code, move_code)`）のテスト。
- **バリデーション**（型チェック・必須未充足の可視化）のテスト。
- **突合チェック**（FR701 データとの diff）のテスト。

### コーディング方針（流用前提）

- 規則は設定データ化し、別紙 config を読む形にする。
- 未定・暫定・簡略化・非効率な箇所は**理由つき TODO コメント**を残す（後で別の人/AI が直せるように）。
- **本体取込仕様とズレないことを最優先**（二重管理を避ける）。
