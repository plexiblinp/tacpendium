## 0. 一行

**ローカルの対戦動画に、目的を持ってタイムスタンプ付きメモを残し、メモから該当時刻へ飛ぶ。** アプリは動画を持たず、**参照のみ**を保持する。

---

## 1. なぜメモ機能と別軸なのか（確定）

- **入力の性質が違う。** メモ＝ふわふわした思いつきから素通しで起票／**VOD 分析＝はっきりした目的を持って観て記録する**。
- **データの形が違う。** メモ＝自由テキストの思考ループ／VOD＝動画参照に紐づく時刻付きレコード。
- **比較機能を分けたのと同じ基準**（データの形と入力の性質が違えば器を分ける）。一貫している。
- 連携はする（気づきをメモへ起票する導線）。器は分けたまま、**流れは一方向（VOD → メモ）**。比較機能と同じ関係。

## 2. スコープ（確定）

**採用**（一次資料の優先順位 1〜4）：

1. ローカル動画登録
2. 動画再生
3. タイムスタンプ付きメモ
4. メモ → 動画ジャンプ

**不採用・後送り**：

| 項目 | 判断 | 理由 |
|---|---|---|
| 5. コンボ・セットプレイとの関連付け | **不採用**（開発者判断 2026-07-27） | 目的に対して余計 |
| 「状況 → 攻略データ」の自動接続<br>（18:22 → 端投げ → +42F → 候補表示） | **不採用** | 機械が動画から状況を判定する読み。**アプリは状態を持たない**・**AI に断定させない**の両方に触れる |
| 6. サムネイル生成 | 任意（安価なので入れてよい） | ブラウザで seek → canvas。ffmpeg 不要 |
| **三層構造（動画/グループ/軸）** | **採用**（§5.5） | 軸はグループに属する。正体はフィルタで器は増えない |
| **取り込み待ち一覧** | **採用**（§5.5.8） | 参照切れ検出と同じ突合処理の裏側 |
| ユーザー定義のメモフォーマット | **不採用**（§5.5.7） | 構造化は軸で済んでいる。開発者が要望後に撤回 |
| **AI による統括** | **保留・別レイヤー**（§6） | BYOK 任意機能。1〜4＋軸を使ってから要否を判断 |
| 7. 区間切り出し／8. プロキシ動画生成 | **不採用**（§3） | ffmpeg 同梱が DNA と衝突。かつ問題を解かない |
| 体力ゲージ検出によるジャンプ | **別マイルストーン・PoC ゲート付き**（§7） | 1〜4 と同規模以上。需要駆動で後から判断 |

**5 を落とした結果、本機能は 1〜4 で完全に自己完結する。** 既存スキーマへの依存がほぼ無く、衝突面が小さい＝**並列レーンの相手として理想的**。

## 3. ffmpeg を採用しない（確定・根拠）

### 3.1 DNA との衝突

- Tacpendium の根本価値は**軽量・インストール不要**。ffmpeg 同梱は数十〜百 MB 級の外部バイナリを配布物に載せ、ビルド構成によっては GPL 系ライセンスも載る。OSS 配布・友人配布の前提が変わる。

### 3.2 そもそも MVP に要らない

- **再生・シーク** ＝ HTML5 `<video>`（ブラウザがデコード）。Go 側は `http.ServeFile` の Range 対応でローカルファイルを配信するだけ。
- **サムネイル** ＝ ブラウザで指定時刻へ seek → canvas で1フレーム取得。
- → **優先順位 1〜6 は ffmpeg ゼロで全部作れる。**

### 3.3 「ディスクがパンクする」懸念への回答（重要・理屈が逆向き）

- アプリは動画を**コピーしない**（参照のみ）。**アプリが原因でディスクが増えることは無い**。増えるのはユーザーの録画そのものであり、アプリの有無と無関係。
- ffmpeg でプロキシ／切り出しを作ると、元動画＋生成物で**一時的にむしろ増える**。減るのは「元を消す」ところまでやった時だけで、**アプリがユーザーの元動画を消すのは禁じ手**（データの根＝ユーザーが握る／可逆性の原則）。
- → **エンコード機能はパンク問題を解かない。** 諦めてよい。

### 3.4 代わりに入れる安価な対策

- **参照切れ検出（MVP に要る）**：ユーザーがファイルを移動・削除するのは確実に起きる。ハッシュ／パスで死んだ参照を検出し一覧で示す。無いとメモだけが残って腐る。
- **参照サイズの可視化**：登録済み動画の合計サイズ・個別サイズを一覧に出す。「そろそろ整理しよう」の判断材料になる。メタデータは既に取るので実装コストほぼゼロ。

### 3.5 将来の扱い

- ffmpeg は「**あれば使う・無ければ機能を隠す**」**オプショナル外部依存**としてのみ検討する。**同梱はしない。**
- **コンボ機能側への取り込みについての回答**：**器（メディア参照）は共有する・エンコードは共有しない**。M17 のメディア参照（G-j）と同じ器に乗せ、別テーブルを作らない。

## 4. 保存する情報

動画本体はコピーしない。参照メタデータのみ：

- **動画**：動画 ID / 元ファイルパス / ファイル名 / 作成日時 / 再生時間 / ファイルサイズ / ハッシュ（識別・参照切れ検出・鮮度キー）/ サムネイル（任意）
- **基本情報（すべて任意）**：タイトル / 自キャラ / 相手キャラ / **ゲームバージョン** / 日付
- **グループ**：`(id, name)`。分析の単位
- **所属**：`(video_id, group_id)` の多対多（同じ動画が複数グループに属せる・所属ゼロも可）
- **軸**：`(group_id, axis_name)` ＝ **グループに属する**
- **メモ**：`(video_id, group_id, axis, timestamp, text)`

**器の共有**：videos は M17 のメディア参照（G-j）と**同じ器**に乗せる。コンボ側動画と別テーブルにしないこと（同じ概念の二重表現＝継ぎ目のドリフトを自分で作らない）。

## 5. メモ機能との関係（出口）

- VOD で見つけた気づきは、**メモへ起票して初めて永続・発展する**（比較機能 §7 と同じ構造）。
- 「メモへ起票」導線を用意する。器は分けたまま、流れは一方向。

## 5.5 三層構造（動画 / グループ / メモ）— 確定

**追加設計（2026-07-27）。スコープ 1〜4 の上に乗る。**

### 5.5.1 フロー（開発者の記述）

1. ユーザーが動画を撮影し、**所定の場所に配置**する。
2. 動画に**基本情報**を入力する：タイトル・自キャラ・相手キャラ・**ゲームバージョン**・日付など。**すべて任意**（必須にしない）。ただし動画が増えた場合の整理のため**入力は推奨**する。
3. この「実ファイル＋基本情報」の動画を、**特定の分析のために集めたグループへ割り当てる**（例：コンボミス分析／○○対策）。
4. **同じ動画が複数グループに属してよい。グループに割り当てないことも可能。**
5. 動画画面には、**そのグループの分析軸がタブとして表示される。**

> 割り当てを後からできるのは、**とりあえず目的先行で動画を撮っておいて、後から分析を加えるため**。

### 5.5.2 三層

| 層 | 内容 |
|---|---|
| **動画** | 実ファイル参照 ＋ 基本情報（すべて任意）。**分析とは無関係に存在できる** |
| **グループ** | 分析の単位（キュレートされた集合）。**軸を定義するのはここ** |
| **メモ** | `(動画, グループ, 軸, timestamp, text)` |

### 5.5.3 なぜこの構造が良いか

- **「とりあえず撮っておいて後から分析を加える」を構造が支えている。** 撮影時に分析目的が決まっている必要がなく、動画は分析なしで存在できる。実際の使い方に忠実。
- **軸がグループに属することで、軸の意味が安定する。** 「○○対策」グループの中の「起き攻め」軸は意味が一意に決まる。**グローバルな軸マスタを作らずに済む**（§5.5.6 の「マスタ化しない」と整合）。
- **同じ動画が2つのグループにあれば、メモも軸も完全に別**になる。**同じ動画を別の目的で二度観る、という行為がそのままデータ構造になっている。**

### 5.5.4 グループは手動割り当て（確定）

- **自動判別はしない**（開発者確定）。様々な需要があるため自動判別には限界がある。
- → グループは「保存されたクエリ」ではなく **「キュレートされた集合」**。比較機能と同じ性質（人が意図を持って集める）。

### 5.5.5 削除の非対称（比較機能 §3.3 と同じ判断）

- メモは `(動画, グループ)` の交差に属するため、**グループから動画を外すとメモが道連れになる**。**破壊的操作なので警告する。**
- 動画の追加・軸の追加は可逆＝**警告しない**。

### 5.5.6 分析軸（タブ）

- 画面イメージ：**動画プレイヤーが中央。グループの分析軸ごとのタブ**があり、切り替えるとその軸のタイムスタンプ＋コメントが表示される。
- **正体はフィルタであって新機能ではない。** メモは `(動画, グループ, 軸, timestamp, text)`。**保存に効くのは軸1列、UI に効くのがタブ。**
  - **軸ごとに別テーブルを作らない**（器の分裂＝二重表現）。
- **軸の語彙はマスタ化しない。** グループ内で自由入力＋既出のサジェスト程度に留める。固定リストにした瞬間、**アプリが SF6 の語彙を定義し始める**（§2 の「型にはめない・マスタ語彙不要」＝比較機能と共通の思想）。

### 5.5.7 メモの入力形式＝タイムスタンプ ＋ テキストのみ（確定）

- **ユーザー定義のメモフォーマット機能は作らない**（開発者が一度要望し、検討のうえ撤回・2026-07-27）。
- 理由：`(グループ, 軸, timestamp, text)` の時点で**構造化は既に済んでいる**（軸が「まとめ方」、タイムスタンプが「位置」）。フォーマット機能は**済んでいる構造化をもう一度やる**ことになり、「起票の素通し」から最も遠い4層目を作る。
- 撤回の背景にあった懸念（「テキストエリアに全部まとめて書く使いにくさ」）は**構造側で解消済み**：メモは**1件ずつ独立したレコード**で、軸タブが分類し、タイムスタンプが動画と結びつく。長文を1枚に書く形にはならない。
- **将来もし本当に構造化フォームが要るなら、それは比較機能に近い性質**。VOD の中に作らず、比較機能の器を拡張できないか先に見る。

### 5.5.8 取り込み待ち一覧（未登録動画）

- ユーザーが動画を配置した後、**アプリ側の情報が未割り当てのものを一覧に出して入力させる**。
- **「基本情報が未入力の動画は分析対象として扱わない」**（開発者確定）。登録前の動画は **「取り込み待ち」という別の状態**として持ち、登録済みと混ぜない。
- **登録＝「このファイルを分析対象にする」という宣言**であって、入力の完了ではない。**基本情報は任意**のままなので、**必須入力を強いる過保護な UI にしないこと**（友人 FB の教訓）。
- **参照切れ検出（§3.4）と表裏**：参照切れ＝登録済みだがファイルが消えた／取り込み待ち＝ファイルはあるが未登録。**同じ突合処理の両側**なので実装を共有する。

## 6. 将来：AI による統括（保留・アイデア記録）

> **保留。** BYOK 前提の任意機能であり、**AI 統括を前提にした設計にしない**。メモと軸だけで完結する価値があり、統括は上乗せ、という順序を守る。
> **⚠ 連携方式（リレー／API・単一受け口・出自の扱い）の正本は `combmgr-ai-integration-design-memo.md`。** 本節は VOD 固有の内容のみを扱う。本機能の統括は**低頻度・バッチ**なので**リレーで足りる**（同 §3）。

### 6.1 位置づけ（開発者の意図・2026-07-27）

- **動機**：データを収集したものの、**一つの分析結果にまとめるのが苦手な人への支援**。
- **前提**：**1動画だけで分析し切るのは不可能かつ科学的でない。複数の動画をしっかり分析した後に動かす機能**とする。
- **方針**：**データに基づき、推論の余地が少ない形にする。**

### 6.2 なぜ「複数動画の統括」が安全側なのか

**単一動画の要約より、複数動画の統括のほうが構造的に安全で価値も高い。**

- 複数動画に跨って何度も出てくることは、**ユーザーが実際に何度も書いたという事実**。AI は**頻度を数えて束ねるだけ**で済み、推論の余地が小さい。
- 例：「起き攻めの対応が難しい」と**AI が判定する**のは診断／「その軸で 5 本中 4 本にメモがある」と**提示する**のは集計。**後者だけをやる。**
- **支援の形は「結論を出してあげること」ではなく「並べ方を与えること」。** 比較機能で確立した**「フォームの構造が分析装置」と同じ**で、AI は素材を配置し、判断は人が下す。

### 6.3 越えてはいけない線

| 種別 | 可否 | 例 |
|---|---|---|
| **要約・整理・集計** | **可** | 軸ごとの件数・出現した動画数、時系列整理、重複の束ね、同じ語が繰り返される箇所の抽出 |
| **診断・断定・助言** | **不可** | 「あなたの弱点は起き攻めの対応」「この状況ではこう対応すべき」＝**攻略の生成**。**AI に断定させない原則に正面から違反** |

- **危険は「統括」という語が両者を自然に跨ぐこと。** プロンプト次第で後者へ滑る。→ **出力の性質を制約として設計時に書いておく**：
  - **入力されたメモに書かれていないことを言わない**
  - **評価・診断をしない**
  - **出典（どのタイムスタンプ・どの動画由来か）を保つ**（クリックで根拠へ戻れる＝メモ機能の可視化と同じ思想）

### 6.4 実装上の含意

- **AI 要約エンジンはメモ機能と共有する。** メモ機能（一人SNS）の「AI が記事やチェックリストに再構成する」と**同じ機構**。器は分けても、ここで別実装を作ると二重表現になる。
- **BYOK ＝ 鍵を入れない人には機能自体が存在しない。** 前提にしない。
- **別レイヤーである**（BYOK・プロンプト設計・出力制約）。1〜4＋軸は自己完結・低リスクだが、統括はそうではない。
- → **まず 1〜4＋軸を出して使ってから、統括の要否を判断する**（需要駆動。§7 の体力検出と同じ扱い）。

## 7. 将来：体力ゲージ検出による動画ジャンプ（別マイルストーン・PoC ゲート）

> **1〜4 より明確に優先度が下。** 1〜4 は自己完結・低リスク・すぐ効く。本機能はキャリブレーション UI ＋ サンプリング処理 ＋ 精度ゲートで、1〜4 と同規模かそれ以上。**1〜4 を出して自分で数週間使ってから**、「手動マーカーで足りているか、体力ジャンプが欲しいか」を判断する（需要駆動。開発者自身が最初のユーザーとして検証できる）。

### 7.1 技術的判定：可能。しかも AI 不要

- 体力バーは**画面の固定位置にある高コントラストの UI 要素**。フレームを間引いてサンプリングし、バー領域を切り出して色の付いた幅を測るだけ。**古典的な画像処理で、機械学習も推論も不要**。
- 「ここでダメージが入った」は**事実の測定**であって攻略の断定ではない。**AI 断定禁止の原則に触れない**。

### 7.2 キャリブレーション＝プロファイル方式（設計の核）

**再フレーミング（重要）**：ソースの多様性は**ユーザー間**にあり、**1人のユーザーの中にはほぼ無い**。キャプチャソフト（OBS / GeForce ShadowPlay / その他）・解像度・HUD 位置オプションは、どれも個人の環境で固定。同じ人が毎回設定を変えることはない。
→ **キャリブレーションは「動画ごと」でなく「セットアップごとに一度」**で済む。コストは想定よりかなり低い。

- **キャリブレーションプロファイルを器にする**：一時停止フレーム上で体力バーの矩形を2つドラッグ → 名前を付けて保存（例「うちの OBS 1080p」）。以後は解像度一致で自動サジェスト、ワンクリック適用。**ほとんどのユーザーは生涯1〜2プロファイル**。
- **YouTube / Twitch の大会 VOD**：オーバーレイ込みでレイアウトが違うが**同一大会内では一貫**。イベントごとに1プロファイル。
- **極端な HUD 位置**（SF6 のオプションで変更可能・一部ユーザーは極端な配置）：プロファイル方式なら**そのまま吸収できる**。自動検出だと死ぬケースであり、**手動キャリブレーションを選ぶ決定的な理由**。
- **未キャリブレーションの動画**：機能を出さない（グレースフルに消す）。誤検知で嘘のマーカーを出すより無い方がいい。
- → **自動検出は要らなくなる。** 任意の補助として「開始フレームから矩形を推定して初期位置を提案」を足せるが、外しても成立する。**実装しないのが正解に近い。**

### 7.3 実装上の注意

- **SF6 固有のノイズ**：白ゲージ（回復可能ダメージ）とドライブゲージの区別、ラウンド遷移・リプレイ再生・メニュー画面での誤検知。閾値と最小変化量で抑える。
- **実行時間**：ブラウザ完結（seek＋canvas）だと 30 分動画で数分かかりうる。ffmpeg があれば桁違いに速いが、**無くても動く設計**にする（あれば速い・無ければ遅い）。
- **非同期のバックグラウンドジョブにする**。**100ms DNA の critical path から外す**（必須）。
- **結果はキャッシュしてよい**（「導出は保存しない」原則の正当な例外）。理由：**ソース（動画ファイル）が不変**で、ハッシュが鮮度キーになる。ハッシュが変われば破棄。**ドリフトしない**。
- **出すのは「候補マーカー」であって判定ではない。** 「ここでミスした」とは言わせない。
- **セットプレイ自動提案と同じ「PoC → 精度ゲート → 本実装」パターンを踏む**（前例あり）。実動画数本で検出率と誤検知率を見てから作るかを決める。

---

## 8. 戦略上の位置づけ（率直に）

- 本機能は**発信者北極星（更新ごとに CSV を出し続ける）には直結しない**。比較機能・メモ機能と同じ「**自分の上達**」軸。
- 悪いことではないが、需要駆動の観点では**「開発者本人の需要」として位置づける**べきで、乗り換え便益として売り込む筋ではない。
- **順序依存はない**（5 を落として自己完結したため）。メモ機能を待つ必要はない。ただし**メモへの起票導線**を作る時点ではメモが要る。
