## プロジェクト前提（Tacpendium）

- ストリートファイター6 のコンボ管理 Web アプリ。**Go + React + SQLite**。DNA＝軽量・インストール不要・**即応答（100ms 以内）**。
- **開発体制**：ソロ開発者が複数 AI を指揮。spec-driven。隔離環境で自律実装 →（機械レビュー＋テスト）→ 人がマージ。
- **最重要制約**：希少資源は**人間（開発者）のレビュー時間**。トークンや利用枠ではない。だから成果物は「あなたが直した量」でなく「開発者がレビューしやすいか・将来のレビュー時間を減らすか」で価値が決まる。
- **データの根（スキーマ／マイグレ／認証／データ層／外部契約）は人間が握る**。可逆かつ自己検証可能なものだけ手を入れてよい。
- **原則**：AI は「文章処理」（要約・分類・再構成・指摘）に限り、**判断・生成・断定はしない**。バグや不整合は「断定」でなく「疑い・仮説」として出す。
- 現在地：フェーズ3。破壊的スキーマ整理の M14 が終わり M15 へ移行中。

## あなたへの依頼（改善レーン）

対象は改善系4種。**どこを見て何を直すかの計画から、あなたが立てる**（開発者は現状どれも曖昧な指示しか持っていない。あなたに実物を読ませて計画させるのが狙い）。
1. **テスト網羅の監査＋補強**（正しさが重い経路にテストの穴がないか。受け入れテストが回帰を捕まえているか）
2. **ドキュメント整合監査**（アイデアごとに文書を乱造した結果カオス化。統合・重複排除・**矛盾のあぶり出し**・正典構造の提案）
3. **リファクタリング**（初実施。規模は大きめでも可、ただし下記の安全条件に従う）
4. **放置バグ探し**（既知の取りこぼしの他にも潜んでいないか）

## 計画と対象の基準（ここは固定・あなたの計画はこの枠内で）

- **発見は広く、実行は狭く。** 読み取りによる発見（バグ・リファクタ候補・テストの穴・文書矛盾）はリポジトリ全体を広く。実際に**書き換える**のは下記を満たすものだけ。
- **実行の対象基準**（すべて満たすもの）：(1) 現実的に再テスト・検証できる範囲、(2) 重度なもの、(3) 低コストで修正可能なもの。
- **除外基準**：(A) **今後のマイルストーンで書き換える予定の部分**（直しても二重作業。ロードマップを渡すので参照）、(B) **最新の実装調査資料に影響が及ぶもの**。
- **三分類でトリアージせよ**：**対象**（上記を満たす→実行）／**対象外**（除外→触らない、理由を記録）／**要判断**（マイルストーン被り疑い・資料との不整合疑い・大きすぎる等→勝手に決めず開発者に積む）。迷ったら実行せず「要判断」へ。
- **実装調査資料は勝手に更新しない。** 資料と食い違う点に気づいても**修正せず「不整合レポート」として指摘**する。更新すべきと考えるなら「要判断」に提案として積み、開発者の承認を待つ。
- **内部順序：テストの安全網を先に。** リファクタは静かな回帰が最大リスク。**先にテスト網羅監査・補強で安全網を張り、それからリファクタ**に入る。テストで守られていない経路の大規模リファクタはしない（「要判断」へ）。
- **コミットは意味の塊ごとに分ける。** 全部盛りの巨大コミットにしない（開発者が切り分けてレビューできる粒度に）。

## 進め方（段階を踏む）

- **フェーズA（まず）**：判断と計画に必要な情報・成果物を、あなたから**優先順位付きで列挙して要求**せよ（例：後述のマップファイル、フェーズ3 のロードマップ／マイルストーン計画、実装調査資料の一覧、受け入れ基準、既存テストの現状 等）。憶測で埋めず質問する。
- **フェーズB（計画提示・承認待ち）**：材料を読み、**計画（見た範囲・発見・三分類トリアージ・実行順）を提示**して開発者の方向確認を受ける。**承認前に広範な書き換えを始めない。**
- **フェーズC（実行）**：承認された「対象」を、テスト安全網→リファクタ／バグ修正の順で実行。各変更にテストを添え、実行後にテストを走らせる。
- **フェーズD（引き継ぎ）**：下記形式の引き継ぎファイルを残す。

## 引き継ぎ・レポート形式

- **やったこと**：変更点・根拠・添えたテスト・テスト結果。意味の塊ごと。
- **発見（未実行分）**：バグ疑い・リファクタ候補・テストの穴を、症状／該当箇所（ファイル・行）／なぜ問題か／推奨対応／**やってはいけない対応**／重要度で。断定でなく疑いとして。
- **要判断リスト**：マイルストーン被り疑い・資料不整合・大きすぎる変更を、開発者が決められる形で。
- **資料不整合レポート**：実装調査資料と食い違う点（更新提案は要判断へ）。
- 発見・要判断は開発者の受け皿（`combmgr-pending-decisions.md` 等）に合流できる粒度で。

## 制約・やってはいけないこと

- **worktree 封じ込め（後述・資料2）を厳守。** 自分の worktree フォルダ内のみ参照・更新する。
- 実装調査資料を勝手に更新しない（指摘のみ）。
- バグ・不整合を断定しない（疑い・仮説として）。
- main へのマージ時の**意味の絡む競合の解消と最終確定は人が行う**。あなたは競合の列挙・分類・両者の意図の要約・機械的に自明な部分の解消案までを支援する（意味判断はしない）。
- 検証できない変更・除外基準に触れる変更はしない（「要判断」へ）。
