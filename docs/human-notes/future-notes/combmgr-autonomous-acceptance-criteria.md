# 自律先行実装の受け入れ判定基準 — 本体組み込み担当（Claude）向け

> **読み手**: 本体組み込みの設計・指示書作成担当（Claude）。
> **用途**: 「ダメ元・先行実装」で自律生成された成果物を、本体に **そのまま組み込む／手直しして組み込む／作り直す** のどれにするか判定する。
> **位置づけ**: 判定ルブリック。コードレビューの手順書ではなく、**採否の意思決定**のための基準。

---

## 0. 前提と中心原則

- 判定する問いは「コードが良いか」**ではない**。**「この成果物を起点にすると、ゼロから作るより速いか？」**の一点。
- **希少資源は人間（および担当）のレビュー時間**。基準もそこで引く。
- 比較するのは常に **再実装コスト vs 手直しコスト**。手直しが小さければ採用、再実装が小さければ破棄。
- **迷ったら破棄寄り**。未検証コードを抱える保守コストは後でずっと効く。自律は安く速いので、作り直しの実コスト・心理コストは低い。
- 「動かなくてもいい」前提の先行実装である以上、**破棄（C）が多く出るのは正常**。失敗ではない（§4 参照）。

---

## 1. 判定の階層（上ほど致命的・直しにくい／下ほど直しやすい）

上位が壊れていると作り直し相当。下位は後からいくらでも直せる。**採否の重みは上ほど大きい**。

| 層 | 観点 | 壊れていたら | 採否の重み |
|---|---|---|---|
| 1. 契約適合（ゲート） | 公開API・データ形・CSV/列契約・モジュール境界が、こちらの仕様と合うか | 中身が良くても**接続できない＝作り直し相当** | 最大 |
| 2. 境界の安全性 | 「触るな」境界（DBに書かない／認証・データ層に触れない 等）を守れているか | 安全の根幹。後から剥がすのは高い → **原則破棄** | 最大 |
| 3. テストの存在と緑 | 受け入れ基準がテストで表現され、通っているか | 正しさを確認できない | 大 |
| 4. 構造の素直さ | 疎結合で、直す箇所を局所化できるか | スパゲッティ＝手直しコストが跳ねる | 中 |
| 5. コードの細部品質 | 命名・重複・軽い非効率 | **最も直しやすい** | 最小 |

> **重要な原則**: 細部のコード品質を採否の**主因にしない**。契約と境界が合っていれば汚くても救えるし、契約がズレていれば綺麗でも捨てる。直感に反するが、ここを守るとレビューが速くなる。

---

## 2. 3段階の判定（A / B / C）

### A — そのまま組み込める
- 契約適合 ◎／境界 ◎／テスト緑／主要動線が動く。
- 残るのは細部の粗だけ。→ **マージして、粗は後で直す（または放置可）**。

### B — 手直しして組み込める
- 契約はほぼ合う or 軽いズレ／境界は守れている／構造が局所修正可能。
- **B の条件＝「直す箇所が特定でき、範囲を見積もれる」こと。** 見積もれる手直しは採用してよい。

### C — 作り直した方が早い（破棄）
- 次の **いずれか一つでも該当**したら C：
  - 契約が根本からズレている。
  - 境界違反（DB・認証・データ層に手を出した）。
  - 構造が絡まって**直す範囲が見えない**。
  - テストが無く、正しさを確認できない。
- 未検証コードの考古学に時間を溶かすより、**捨てて作り直す**。

> **B と C の境目＝「直しの範囲が見積もれるか」。** 見積もれない不確実性こそが、作り直しより高くつく元凶。広範囲・不明なら迷わず C。

---

## 3. 判定手順（速く・安く）

1. **受け入れ基準を先にプロンプトへ書いておく**（公開API・契約・テスト・「触るな」境界）。判定が「指定どおりか」のチェックに変わり、レビューが速くなる。
2. **トップダウンで見て、上位で落ちたら下を読まない**：契約 → 境界 → テスト → 構造 → 細部 の順。上位で C が出たら**全コード精読はしない**。これがレビュー時間の最大の節約。
3. **テスト緑＋機械レビュー通過を足切りにする**：人が見る前のフィルタ。落ちているものは人が読む前に C 寄りに置く。
4. **A / B / C を割り当てる**。B は直し範囲をメモ（見積もれなければ C へ落とす）。

---

## 4. ダメ元・先行実装ならではの取り分（捨てても学びは回収する）

「動かなくてもいい」前提で走らせている以上、狙いは「動くもの」ではなく**設計の叩き台・アルゴリズムの種・つまずきポイントの発見**である。

- **成果物＝コードだけ、と思わない。** 動かなくても、契約・構造・アルゴリズムの考え方が参考になるなら、**コードは捨てても学びは採用**する（プロンプトや設計に反映）。
- **露見した仕様の穴・難所は「失敗の記憶」へ記録**する。次の自律の精度が上がる。これが先行実装の本当の取り分。
- **C が多いのは想定どおり**。破棄率の高さを失敗と捉えない。

---

## 5. クイック判定チェックリスト

上から順に。No が出た時点で下を読まず判定を打ち切ってよい。

- [ ] **契約**（API／データ形／列契約／モジュール境界）が仕様と一致しているか → No なら ほぼ **C**
- [ ] **「触るな」境界**（DB・認証・データ層）を守っているか → No なら **C**
- [ ] **テストがあり緑**か／機械レビュー通過か → No なら 正しさ未確認、**C 寄り**
- [ ] 直す箇所が**局所で、範囲を見積もれる**か → Yes なら **B**／No なら **C**
- [ ] 上が全部 OK で**主要動線が動く**か → **A**
- 細部の綺麗さでは判定しない（直せばよい）。
- どの段でも、捨てる場合は**学び（仕様の穴・難所）を記録**してから捨てる。

---

## 6. 一言要約

**「契約適合 → 境界 → テスト → 構造 → 細部」の順に見て、上位で落ちたら破棄、直しの範囲が見積もれるなら B、全部通れば即 A。** 細部の綺麗さで悩まない。そして**捨てたものからも学びだけは回収する。**
