## 1. A：アプリ本体 = AGPL-3.0-or-later

### 採用理由（確定した動機・誤りを除去済み）

1. **「有償化は可・タダ乗りは不可」＝ GPL/AGPL の設計思想そのもの。** コピーレフトは販売を禁じない。売ってよいが、ソースを渡し同じ自由を引き継がせる。開発者の意図と完全一致（**主柱**）。
2. **改変版のクラウド展開に対する透明性要求**（補強・薄い壁）。
   - 無改変の公開デプロイでは AGPL の追加価値はほぼゼロ（ソースは元々公開）。
   - **AGPL が実際に効くのは「改変してデプロイ」した場合**で、危険なのもまさにそのケース（勝手な認証改変・トラッキング追加等）。壁が立っている場所を正確に書くこと。
   - **執行力は無い**（誰も巡回しない）＝規範表明。多層防御の一枚として数えるのは妥当。
3. **コピーレフト系ライブラリの採用余地**（補強・重みは控えめ）。
   - MIT のままでも **MPL・LGPL は使える**。詰まるのは GPL/AGPL 本体のみで、Go + React 圏には稀。
   - ただし**具体例は存在する＝ffmpeg**（ビルド構成により LGPL/GPL）。VOD 機能で現時点は「同梱しない」と決めたが、将来同梱したくなった時に MIT だと詰む。

### 書いてはいけない動機（一次メモから削除）

- ✗ 「クラウド公開時の**利用者の安全**のため」——**AGPL は安全性を一切保証しない**。ソース開示を強制するだけ。安全性の答えは README 警告・起動時案内・**M22 の認証**（既知の穴＝LAN 未認証 API・F12-8）。

### 互換性メモ

- AGPLv3 は **GPLv3 / Apache-2.0 / MPL-2.0 / MIT / BSD** を取り込める（一方向）。
- **GPLv2-only は不可**。
- 既存依存はすべて MIT / BSD-3 / Apache 系＝問題なし。MPL の `hashicorp/golang-lru/v2` は非リンク確認済み。

### バイナリ配布の義務

- 対応するソースの提供義務がある。**リリースタグと版を対応づけ**、「本バイナリのソースは tag vX.Y.Z」と NOTICE / README に明記する運用で満たす。

### ネットワーク越しの利用（AGPL §13）の解釈整理

> **★本節は `combmgr-prerelease-checklist.md` `A1` が逐語で要求している節である**（「M22 で LAN 共有が入ったため、AGPL §13 の解釈整理を骨子に 1 節足すこと」）。**2026-09-04 に開発者の説明を受けて追記した**（設計卓ドラフト・`D-701`）。**★法的助言ではない。**

**採用の動機（開発者の逐語に基づく）**

- **本アプリは自宅内 LAN での運用が前提である。** そのため**一部のセキュリティ要件は甘い**〔簡易ログイン ／ 平文 HTTP 前提＝M22 の契約 F-3 ／ CORS・CSRF は LAN 前提の設定〕。
- **しかし OSS である以上、クラウド上で運用しようとする人が現れうる。**
- **⇒ そうした運用者に対し「安全な修正をした上で公開していること」を利用者へ示させる、最低限の防御策として AGPL のコード公開義務を課す。**これが AGPL を選んだ動機である。

**AGPL §13 が実際に課すもの**

| 事象 | 義務 |
|---|---|
| **改変して、ネットワーク越しに他人へ使わせる** | **その利用者へ、改変後の対応するソースを提供する義務が生じる**（§13。GPL には無い条項） |
| 無改変のまま運用する | §13 の追加義務は生じない（配布時の §4〜§6 は従来どおり） |
| 自分だけで使う（他人へ使わせない） | 義務なし |

**★正直な限界（過信しない）**

- **AGPL §13 が義務づけるのはソースの提供であって、安全な修正ではない。** ⇒ 効くのは「**隠したままクラウドで運用させない**」という一点であり、**運用者が安全に直したことを保証するものではない**。保証するのは「**利用者が改変内容を検証できる状態**」までである。
- **執行は権利者が自分で行う必要がある。** 違反を自動で検出する仕組みは無い。
- **⇒ したがって §13 は防御の主役ではなく、下記の明示と組み合わせて初めて意味を持つ。**

**あわせて必要な明示（§9 の配置ファイルへ回す）**

- **`README` / `SECURITY.md` に「本アプリは LAN 内での利用を前提とし、インターネットへ直接公開しないこと」を明記する。**
- **クラウドで運用する場合に自分で塞ぐべき箇所**〔認証・通信路の暗号化・公開範囲〕**を列挙する。**
- **★「安全である」と書かない**（M22 契約 F-3 と同じ規律）。

## 2. B：ゲームデータ = CC BY-SA 4.0（NC を採らない）

### なぜ NC を捨てるか（重要な方針転換）

- **NC は北極星と正面衝突する。** 発信者の多くは収益化している（広告・メンバーシップ・有料コーチング）。NC は非フリーなので、獲りたい層をそのまま締め出す。
- **継承（Share-Alike）で目的は達成される。** 買った人が同条件で再配布できるため、**データを売るビジネスは事実上成立しない**＝「有償販売による搾取」は防げる。
- **収益化発信者は安全**（動画・メンバーシップ・コーチングで使い放題）。
- **「Moves はコミュニティのもの」という開発者の意図と意味が一致する。**
- → **NC は目的に対して過剰で、副作用が戦略を殺す。**

### 権利の強さは過信しない（正直な前提）

- **フレームデータは事実であり著作権は弱い。** 日本には EU 型のデータベース権がなく、著作権法12条の2 は選択・配列の創作性を要求する。網羅的な数値表はここが薄い。**手入力の労力（額の汗）は権利を生まない。**
- 保護されうるのは**選択・配列・taxonomy・`move_code` 命名体系**等。薄いが存在する。
- → ライセンスは**規範表明**として機能させ、法的強度に依存した設計にしない。

### 権利元（カプコン）への配慮＝ライセンスでなく別立て

- 本体は**商標と表示**の問題。ロゴ・アセット不使用、**非公式・非提携の明示**、公式 HTML 非配布（M14 で対応済み）。→ NOTICE の仕事。
- 「ゲーム会社が例外の最上位」は**ライセンス条項に書かない**。既存原則の**「可逆＋即時撤退」を公開ポリシーとして明文化**する方が強い（§6）。

## 3. C：汎用モジュール = MIT（切り出しの生命線）

### 問題の正体

**障害はライセンスではなく他人の著作権。** AGPL は開発者自身を縛らない（単独著作者は何度でも再ライセンスできる）。しかし**外部 PR を1本マージした瞬間、その部分は AGPL でしか使えなくなり、MIT/MPL で切り出せなくなる。**

### 対策（両方やる）

1. **汎用部分は最初から別リポジトリ・MIT で育てる**（開発者確定：メモ機能は別リポジトリで育成後に組み込む）。MIT なら外部貢献も MIT で入り、サブライセンス可能＝**切り出しが永久に自由**。AGPL 本体からの利用も問題なし。
2. **DCO を導入**（§4）。

### 相互参照・コピーのルール（方向で扱いが違う）

| 方向 | 可否 |
|---|---|
| **notes（MIT）→ 本体（AGPL）** | **常に自由。** 制約なし |
| **本体（AGPL）→ notes（MIT）** | **開発者が100%自分で書いた部分のみ可能。** 外部 PR が入った箇所は**永久に持ち出せない** |

**実務ルール：共有される可能性のあるロジックは、本体でなく notes 側に先に書く。** 後から引き戻す動線に依存しない。やむを得ず本体側で育った場合、**外部 PR がその領域に入る前が唯一の引き戻し窓**。

## 4. 貢献の受け入れ = DCO（CLA は採らない）

- **DCO（Developer Certificate of Origin）** ＝ コントリビュータが「このコードは自分が書いた、または提出する権利を持っている」と表明する軽量な仕組み。実体は `git commit -s` が付ける `Signed-off-by:` 一行。Linux カーネル等が採用。
- **著作権譲渡でも再ライセンス権付与でもない**（それが欲しければ CLA になり、ぐっと重くなる＝個人プロジェクトには過剰）。
- **AI 生成コードの混入にも効く**（「提出する権利がある」の表明）。開発者自身が AI 併用で開発している以上、外部にも同じ規律を求めるのは筋が通る。
- **inbound = outbound** を CONTRIBUTING に明記（本体への貢献は AGPL、notes への貢献は MIT）。

## 6. 撤退ポリシー（ライセンスの外）

- 既存原則**「法務：事実 in／表現 out。可逆＋即時撤退」**を、**公開ポリシーとして明文化**する。
- 内容：権利者から異議があれば**即座に該当データを取り下げる**。公式 HTML・公式アセットは配布しない。非公式・非提携である。
- 置き場：NOTICE ＋ README。

## 7. 配布物の構造

- **同梱ゲームデータ DB は go:embed でバイナリに埋め込まず、別ファイルとして同梱する。**
  - 理由(1)：ライセンスの層が違うものをバイナリに混ぜない（疑義そのものを発生させない）。
  - 理由(2)：CC BY-SA へ切り替えたことで法的緊張はほぼ消えたが、**分けるコストがゼロなので分ける**。
  - **ユーザーの手間は増えない**：単一バイナリ DNA は「インストーラ不要・前提ソフト不要」の意味であり、ファイルが物理的に1個という意味ではない。既に README・LICENSE・config.toml を同梱する zip 配布で、`seed.db` が1つ増えるだけ（解凍して起動、のまま）。
  - **フロントエンドの go:embed は現状どおり**（同じ AGPL の層なので問題なし）。

## 8. devContainer の扱い（保留・公開しない）

**結論：現時点では公開しない**（開発者確定 2026-07-27）。publication manifest（§10.4）から除外する。

### 8.1 調査結果（2026-07-27 時点・要再確認）

| 事項 | 内容 |

| **`anthropics/claude-code` のライセンス** | **未記載ではなく「全権利留保」**。LICENSE.md があり、Claude Code は Anthropic PBC の専有ソフトウェア。`.devcontainer/`（Dockerfile・devcontainer.json・init-firewall.sh）も同リポジトリ内＝同条件 |

### 8.2 なぜ公開しないか（リスクの低さで判断しない）

「個人開発でこの程度が問題視されるとは思えない」という感覚自体は妥当。しかし判断基準はそこではない：

- **公開の便益がほぼゼロ。** devContainer は §10.1 の3つの狙い（致命的欠陥の検出・透明性・証跡）の**どれにも寄与しない**。監査者が見たいのは「アプリが何を読み書きし、どこへ通信するか」であって開発環境ではない。**リスクが低くても、得るものが無いなら取る理由がない。**
- **方針との整合。** AGPL・CC BY-SA で権利関係を明示する姿勢と、由来不明のファイルを抱えたままの公開は噛み合わない。
- **REUSE 準拠を入れると機械的に検出される**（§9.5）。
- 開発参加の許可は**しばらく先**＝それまで devContainer が要るのは開発者だけ。**保留のコストがゼロ**。

### 8.3 将来公開したくなった場合＝「書き下ろし」に切り替える

**線引きは書き方でなく由来の切り方。**

- **元ファイルを開いて編集していく方式は、どれだけ書き換えても派生物。** 「事実の列挙だから同じになる」は、この場合**同じになった原因が参照ではなく必然だと示せない**ため、むしろ不利に働く。
- **「何が必要か」を自分の要件から書き下ろした結果として似る**なら独立創作。Go の版・Node・SQLite・**許可ドメインのリスト**（既に本プロジェクト独自）といった要件は開発者固有であり、実際にはかなり違うはず。

実務：

1. **元ファイルを閉じる。**「この開発環境に必要なもの」の箇条書きから新規に書く。
2. **`init-firewall.sh` 相当のスクリプトが最もリスクが高い**（表現の幅が大きい）。許可ドメインは既に独自なので、自分の要件から書き直す。
3. **現在の「Anthropic 公式 devcontainer 構成をベースにカスタマイズ」というコメントは、書き下ろしに切り替えるまで削除しない**（正直な記述であるため）。書き下ろし後は「参考にした」程度に改める。

```
data/                    … CC BY-SA 4.0（ディレクトリ単位で SPDX 明示）
```

### 9.1 NOTICE の骨子

- 本ソフトウェアは**非公式であり、いかなるゲーム会社とも提携・承認関係にない**。
- ゲームタイトル名・キャラクター名は各権利者の商標。**ロゴ・ゲームアセットは一切含まない**。
- 同梱するフレームデータは**開発者およびコミュニティによる手入力・観測に基づく事実情報**であり、公式配布物の複製ではない。
- **権利者からの申し出があれば、該当データを速やかに取り下げる**（撤退ポリシー・§6）。
- 本バイナリに対応するソースコードの入手先（リポジトリ URL + タグ）。
- 第三者ライブラリのライセンス一覧。

### 9.2 DATA-LICENSE.md の骨子

- **層の説明**：コードは AGPL、データは CC BY-SA 4.0、**あなたが作ったデータはあなたのもの**（最重要・冒頭に置く）。
- **CC BY-SA 4.0 を選んだ理由**：コミュニティのものとして育て、**タダ乗り販売を継承条項で防ぐ**。
- **FAQ（発信者向け・戦略上もっとも重要）**
  - Q. 収益化している動画・配信で使ってよいか → **よい。制限しない。**
  - Q. メンバーシップ限定・有料コーチングで使ってよいか → **よい。**
  - Q. データを改変して再配布してよいか → **よい。ただし同じ CC BY-SA 4.0 で。**
  - Q. データそのものを商品として販売してよいか → 継承条項により**事実上成立しない**（買った人が同条件で再配布できる）。
  - Q. 自分が作ったコンボの権利は？ → **あなたのもの。アプリは一切主張しない。**
- **帰属の分類表**（§5 を転記）。
- **注意**：フレームデータは事実であり、権利は薄い。本ライセンスは**コミュニティの規範表明**として置いている（過度な権利主張はしない）。

### 9.3 CONTRIBUTING.md の骨子

- **DCO**：`git commit -s` を必須にする（説明つき）。
- **inbound = outbound**：本体への貢献は AGPL-3.0-or-later、notes（汎用モジュール）への貢献は MIT。
- **素材由来の注意**：他人の動画・記事の書き起こしをそのまま投稿しない（元の権利者が主張しうる・§5）。
- **本家への貢献を促す**（**ライセンスでは強制できない**ので、ここは規範・運用で）。
- データ更新の受け入れ口（コミュニティ更新を歓迎する旨・開発者が永久に関与する保証はない）。
- 依存追加時のライセンス確認ルール（SUPP-001 §5.7 と整合）。

### 9.4 SUPPORT.md / SECURITY.md の骨子

- **SUPPORT**：無保証・SLA なし・ベストエフォート。個人プロジェクトである旨。**改変版は対象外**であることを明記（Claude Code 等でユーザーが自分好みにカスタムする使い方を想定。詳細は `combmgr-design-memo-index.md` §3.6）。
- **SECURITY**：報告窓口。**既知の制約として LAN モードの未認証 API を明示**（F12-8・M22 で対応予定）。**インターネットへの直接公開を想定していない**ことを警告として明記。

### 9.5 AI 時代への対応（実効性のある順）

1. **SPDX ヘッダ + REUSE 準拠**（機械可読）。スキャナや AI エージェントが**コードとデータの層を取り違えない**ようにする。これが最も実効的。
2. **DCO**（AI 生成コードの権利表明）。
3. AI_USAGE.md は**法的効力を持たない**姿勢表明。置くのは自由だが、**学習利用を防げるかのような誇張は書かない**。

## 10. 段階的公開モデル

### 10.1 公開の狙い（3つ）

1. **致命的欠陥の外部検出・報告**（メモリリーク・アプリ外データ削除等）。
2. **透明性の確保**。得体の知れない exe をローカルに置いてもらう都合上ほぼ必須。格ゲー界隈にはウイルス感染によるアカウント乗っ取り事例（配信者・プロ・個人）がある。
3. **証跡**。問題発生時に「コードに悪意があったのではなく、サプライチェーン攻撃等の外部要因」を主張できるようにする。

いずれも開発者側でベストを尽くした上で、**拾いきれない部分を外部監視させる**のが目的。

### 10.2 恐れているもの（4つ）と、その正体

| # | 恐れ |
|---|---|
| 1 | 将来機能の方針は決まっているのに、**ロードマップがブレる** |
| 2 | 「公開だが PR 拒否」なのに**参加を要求する厄介な人**が現れる |
| 3 | 期限付き非公開なのに**即公開を要求する厄介な人**が現れる |
| 4 | **AI 開発による低品質 Issue の連発**。対応ミスや無反応を問題視される（個人ブログでこき下ろされる等） |

**4つともライセンスの問題ではなく、注意力とガバナンスの問題。** どのライセンスを選んでも解決しないし、逆にライセンスを変えずに全部緩和できる。

**決定的な非対称性**：**「閉じて始めて後で開く」は滑らかに進み、「開いて始めて後で閉じる」が炎上を生む。** 期待を作ってから撤回するのが火種であり、最初から「受け付けない」と宣言している状態は攻撃しにくい（**無反応が方針どおりの挙動になる**）。→ **最初は最大限閉じるのが安全側。開くのは後からいつでもできる。**

補足2点：

- **規模の校正**：日本語ニッチの SF6 ツールに、数千ユーザー規模のプロジェクトの力学はまず来ない。恐れの一部はより大きなプロジェクトの力学で校正されている。
- **需要駆動との整合**：コミュニティ要望は**声の大きい少数からの未検証の需要信号**。無批判に受けることは**需要駆動原則への違反**であり、**断ることが原則の遵守**にあたる（恐れ1 への本質的な防御）。

### 10.3 公開方式 = リリース毎スナップショット公開（継続ミラーではない）

- 私有リポジトリで従来どおり開発し、**リリース時に選別済みの状態を公開リポジトリへ1コミットとして落とす**（`Release vX.Y.Z` ＋ タグ）。**継続同期はしない。**
- 理由：**3つの狙いは開発途中の全コミットを必要としていない。** 継続同期はパス除外を毎回正しく効かせ続ける必要があり、**一度の漏れが取り返しのつかない公開**になる。スナップショットなら**履歴が構造的にクリーン**で、後から履歴を書き換える作業も要らない。
- 副次効果：**CI が公開リポジトリからビルドして成果物を出す**構成にすれば、来歴署名の指す先とユーザーが読めるソースが一致する（狙い2 の強化）。私有リポジトリからビルドしていると、その一致は主張どまりになる。
- リポジトリ名は**仮名 `combomgr` → 正式名へのリネームと同時**に切る（§10.10）。

### 10.4 除外は「許可リスト」で（publication manifest）

**拒否リスト方式は、新しく作った文書が既定で公開されるので、いつか必ず事故る。** 許可リスト（publication manifest）にすれば、**新種の文書は既定で非公開**になり、公開は毎回の明示的な判断になる。

>
> **`D-637`（2026-09-02・開発者判断）と `M26-overview` §M26-02 が「`docs` はアーカイブ含め全部公開する」「`CLAUDE.md` / `.claude/` / `AGENTS.md` / `.codex/` も公開してよい」と定めた。⇒ こちらが新しい。**

**第1段階（貢献を求めない間）**

| | 対象 |
|---|---|
| **公開** | コード全体 ／ REQ-001 ／ DES 各書 ／ architecture-patterns ／ README・LICENSE 系 ／ SECURITY・CONTRIBUTING |
| **非公開** | retrospective-log ／ instructions（指示書）／ handover ／ 改善レーン報告書 ／ offdesk backlog ／ **future-notes** |

- 公開側の基準：監査者が「**このアプリが何を読み書きし、どこへ通信するか**」を確かめられること（狙い2 の実質）。
- **future-notes を出さない理由は、秘密だからではなく恐れ1 に直結するから。** 未発表構想の公開は、期待と要求の的を自分で作り出す。

**第2段階（貢献を開くとき）**

- **実装手順・過去の進め方は成果物の一部であり、開発参加者にとって重要**。よって**内容チェックの上で公開する**（開発者確定 2026-07-27）。
- **貢献を求めない間は不要なので出さない。** 開示範囲の拡大は §10.2 の非対称性どおり「後から開く」側なので安全。

### 10.5 受け口の設計

- **Issues / Discussions は閉じる。**
- **Private vulnerability reporting のみ開く**（公開リポジトリで使える非公開報告窓口）。SECURITY.md に「致命的な問題はここへ」と導線を書く。**高信号・低ノイズの一方向チャネル**で、公開の場で議論が始まらないため炎上経路にならない。→ **狙い1 と 3 が空振りしないための必須要素**（Issues を全部閉じると、最も欲しい報告まで閉じてしまう）。
- 公開リポジトリでは PR 自体を完全無効化できないため、**CONTRIBUTING に「現在は外部 PR を受け付けない」と明記＋自動クローズ**。SQLite に長年の前例があり、説明もしやすい。
- **AI 生成 Issue 対策**（恐れ4・唯一、実在して増加中の問題）：第1段階は Issues 無効化で足りる。開く段階ではテンプレート必須化＋「**AI 生成で人間の検証を経ていない報告は無応答でクローズする**」と明記。

### 10.6 供給網・来歴（狙い2・3 の実質）

**ソースを公開しても「配布した exe がそのソースから作られた」証明にはならない。** 得体の知れない exe への不安に対し、ソース公開は半分しか答えていない。実効性のある順：

- **CI（GitHub Actions）でビルドし、リリース成果物をそこから出す。手元のマシンからアップロードしない。**
- **artifact attestation（ビルド来歴の署名）＋ チェックサム公開**。「このバイナリはこのリポジトリのこのコミットから、この workflow で作られた」が検証可能になる。
- **SBOM の生成とリリースへの添付。**
- **Dependabot 有効化**／`go.sum`・lockfile 固定（既に有）／**リリースタグの署名**。
- → これらは「ベストを尽くした記録」そのもので、狙い3 を**主張から証明へ格上げ**する。
- **コード署名は費用対効果で判断**（個人だと年額数万円規模、かつ新しい証明書は SmartScreen の警告がすぐには消えない）。この規模では **CI 来歴＋チェックサムの方が費用対効果が高い**。

> GitHub の機能は変化が速い。実際の有効化手順は**現時点の公式ドキュメント**で確認すること。

### 10.7 外部監視の期待先を正確に

- **人間の自発的な監査者はほぼ来ない**（ニッチな日本語 SF6 ツール）。期待先を誤らないこと。
- **確実に働く外部の目は自動化されたスキャナ。** 公開の実利は **CodeQL と Dependabot が回せるようになること**（公開リポジトリなら無償）。メモリリークや破壊的 FS 操作の一部は静的解析が拾う。
- → **人間の善意でなく機械に監視させる。**「継ぎ目は機械化で潰す」の適用先そのもの。

### 10.8 公開前ゲート（機械化する）

`make publish` 一発に以下を組み込む：

- **manifest 外のファイル混入検出**
- **gitleaks 等による秘匿情報の走査**（過去のどこか1コミットで十分に事故になる）
- **前回公開との差分レビュー**

→ 集中力が落ちている日でも事故らない形にする。

### 10.9 （条件付き）非公開期間を置く場合の制約

今回は**初回から公開**の方針のため通常は不要だが、将来「バイナリのみ配布・ソース非公開」の期間を置く場合：

- **AGPL を適用しない。** 独自の配布条件（無保証・改変再配布不可等）で配り、**AGPL はソース公開の瞬間から適用**する（単独著作者なので自由）。
- **コピーレフト依存を1つでも入れたら成立しなくなる**（GPL/LGPL/AGPL ライブラリを組み込むとバイナリ配布にソース提供義務が付く）。→ その期間は **MIT/BSD/Apache 系のみで固める**必要があり、**ffmpeg 等の判断に直結**する。

### 10.10 リネームで潰す依存（公開の前提工程）

仮名 `combomgr` → 正式名への変更は、公開設計の切れ目であると同時に**破壊的変更**を含む。

- **Go module path の変更**＝全 import の書き換え。
- **既定データディレクトリ名の変更**（`%APPDATA%/tacpendium/tacpendium.db` 等）。→ **友人リリースの利用者は、更新した瞬間にデータが消えたように見える。** 旧ディレクトリの維持か、初回起動時の移行を用意するかを決める必要がある。
- `config.toml` のキー名・ログパス・ポート既定値など、**名前を含む定数**。
- → **マイルストーン化が要る規模。公開の前提工程として計画に載せる。**

## 11. タイミング（重要）

- **いまは公開前・ソース非公開・友人バイナリ配布のみ**＝単独著作者として将来版のライセンスを自由に選べる。
- **この自由は「公開 ＋ 外部コントリビュータ受け入れ」の瞬間に永久に失われる。**
- 既に MIT で配った友人向けバイナリは、その版に限り MIT のまま（撤回不要・問題なし）。**将来版を AGPL にすることは妨げられない。**
- → **公開前に三層を確定し、LICENSE / DATA-LICENSE / NOTICE / CONTRIBUTING を揃えてから公開する。**

## 12. 実施順序（案）

1. 三層の方針を開発者確定（本書の承認）。
2. **notes（メモ機能）を別リポジトリ・MIT で開始**（§3。実装より先にライセンスを置く）。
3. DES-001 §5 / SUPP-001 §5.7 の CHANGE 起票（設計担当）。
4. **リネーム（仮名 → 正式名）をマイルストーン化**（§10.10。module path・データディレクトリ移行・定数）。
5. LICENSE / LICENSES/ / DATA-LICENSE.md / NOTICE / CONTRIBUTING.md / SUPPORT.md / SECURITY.md を配置。
6. SPDX ヘッダ + REUSE 準拠を導入（`data/` の層分けを含む）。
7. 配布物の構造を確認（**seed.db を go:embed していないか実コードで確認**・§7）。
8. **publication manifest（許可リスト）を確定**（§10.4 第1段階）。
9. **公開前ゲートを機械化**（`make publish`＝manifest 外検出・gitleaks・差分レビュー。§10.8）。
10. **公開リポジトリを新規作成**（履歴なし・スナップショット方式。Issues/Discussions 無効・Private vulnerability reporting 有効。§10.3/§10.5）。
11. **CI ビルド＋来歴署名＋チェックサム＋SBOM** を配線（§10.6）。CodeQL / Dependabot 有効化（§10.7）。
12. 公開（初回リリース）。
13. （後日）貢献を開く段階で **DCO 導入・PR 受け入れ開始・内容チェック済みの内部文書を追加公開**（§10.4 第2段階）。
