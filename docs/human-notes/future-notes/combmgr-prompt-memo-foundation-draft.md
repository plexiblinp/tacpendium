### この機能は何か（背景・ゴール）

一行で：知識管理を「**一人で運用するSNS**」のメタファーで実現する。タイムラインに呟き、返信で育て、繋ぐ。

ゴール／なぜ作るか：
- **書く心理的ハードルを最小化**する（未検証の断片でも、愚痴でもいいから、思いついたことをそのまま投稿できる）。
- 知識の**成熟過程をスレッド（投稿→返信）として時系列で残す**（返信なし＝仮説、解決の返信＝解決済み、のように状態が自然に表れる）。
- **視点・立場（使う側／対策する側）で知見を整理**する（例：リュウの昇竜は、リュウ使いには「使う技」、対リュウでは「警戒する技」）。
- 最終的に、蓄積した投稿を**AIが記事やチェックリストに再構成**する。同じ知識を詳細度別に出し分けられる（学習中は長文記事、対戦直前はチェックリスト）のが最大の差別化。※**本プロトタイプでは AI の実処理は作らず、UI だけ**置く。

中核要素：
- **投稿とスレッド**：トピックを投稿し、それに返信できる（投稿が親、返信が子の自己参照構造）。
- **ペルソナ（視点・立場）**：投稿者を SNS 風（アイコン／名前）に見せる。実態は視点分類。
  - 現在のペルソナを**プルダウンで即切替**（認証なし・軽量。ログインユーザー的だが、あくまで「立場」）。
  - **投稿後の差し替えも可能**（間違えても直せる）。
  - 作成方法は ①キャラから半自動生成（「リュウ」→「リュウ使い」「対リュウ」）、②自由入力で定義。
  - 一度作ったペルソナは登録され、次回からプルダウンで選べる（表記揺れ防止）。前回選択も記憶する。
- **繋ぐ仕組み（独自ハッシュタグ）**：本機能独自の**ハッシュタグのような仕組み**で投稿を分類・連結できる（本体のタグ機能とは別系統）。データモデルに無い攻略概念（どのエンティティにも紐づかない知見）も、これで束ねられる。Twitter風に本文中へ書ける形が自然（実装形は §1 で提案して）。
- **まとめ（AI記事生成）**：複数の投稿を選んで、記事 or チェックリストに再構成する。※本プロトでは UI のみ。

入力形式（重要）：
- **ユーザーの入力は一貫してプレーンテキスト**。ユーザーは Markdown を意識しない（記法を見せない・書かせない）。これは**投稿本文もペルソナ作成画面も同じ**。
- 内部的には Markdown に埋め込んで保持してよいが、**その存在をユーザーに露出しない**。

位置づけ：一人SNS方式は知識管理 UI の**有力候補だが確定ではない**。このプロトタイプは「この形が手に馴染むか」を検証するためのもの。失敗してよい。

### 作ってほしいもの（最大ゴール／厳守ではない）

API キー連携はまだ不要。次を**最大ゴール**とする。これは上限であって必達ではない。**実装担当が自分の能力・状況をもとにスコープを決めてよい**（または §1 のプランで「どこまで作るか」を提案して、私が選ぶ形でもよい）。

1. **Twitterっぽい形**：あるトピックを投稿 → それに返信できる（スレッド）。タイムライン表示。
2. **ペルソナを選べる**：現在のペルソナをプルダウンで切替。投稿はそのペルソナとして表示される。
3. **ペルソナ作成画面**：①キャラから半自動、②自由入力 でペルソナを作成・登録できる。
4. **まとめ（記事生成）の UI だけ配置**（実処理なし）：
   - 複数の投稿を**チェックボックスで選択**。
   - **テーマをテキストエリアに入力**。
   - 「**記事作成**」ボタン。
   - 押すと**ダイアログ表示** → 記事のレベルを選択（**チェックリスト** / **ちゃんとした記事**）→「**実行**」or「**キャンセル**」。
   - 「実行」を押した後は**今は何もしない**（スタブ。将来ここに API 連携が入る前提）。

1 だけでも、1〜3 でも、全部でもよい。判断するか、プランで段階を提案して。

### 永続化・データベースの持ち方

- スタックは本体に合わせ **SQLite** を使う（localStorage は使わない。Tacpendium のデータ管理と一貫させる）。
- ただし本プロトタイプは隔離リポジトリなので、**プロト中はこの機能専用の独立した SQLite ファイル**で動かす（本体のユーザーデータに一切触れず、自由に作り直せるように）。
- 設計は「**いずれ本体の単一 SQLite DB に新規テーブル群として統合される**」前提にする。理由：将来この投稿をコンボ／セットプレイ／キャラ／確定反撃へ紐づけたく、それらと同じ DB 内にあるほうが外部キー・JOIN が素直（SQLite は DB をまたいだ参照が扱いづらい）。よって**マージ可能な形**で設計する（テーブル名の衝突回避、紐付け用カラムは nullable で用意 等）。
- 01-tech-stack.md / 03-data-model.md の既存規約（命名・型・日時・論理削除の扱い等）に合わせる。

### データモデルの紐付け要件

- 投稿は、将来これらに**紐づけられる拡張余地**を残す（本プロトでは実装しなくてよい）：**コンボ／セットプレイ／キャラクター／（将来実装の）確定反撃**。
- **どれにも紐づかない投稿も正当**（データモデルに無い攻略概念など）。紐付けは任意。
- それとは別に、**本機能独自のハッシュタグ**（上記「繋ぐ仕組み」）を投稿に付けられること。これは本体エンティティへの紐付けが無くても知見を束ねる手段になる。

### デザイン方針

- 既定は「**最小・プレーン**」。隔離リポジトリで本体のデザインシステム（コンポーネント／トークン）を参照できないため、後で本体側デザインへ差し替え可能な薄い作りにし、見た目の磨き込みに時間をかけすぎない。
- ただし**SNS風の見た目であることは必須**。タイムライン・スレッド・ペルソナのアイコン/名前表示・記事作成ダイアログが「SNSっぽい」と分かる程度には**最低限スタイルを当てる**。**完全に無スタイルは不可**（イメージが掴めず検証にならないため）。単なるメモ帳ではなく、想定形のプロトタイプにする。

### コーディング方針（プロトタイプだが流用前提）

- プロトタイプとして「**まず動く**」を優先してよい。完璧さより検証。
- ただし**今後の流用・改良を意識**して書くこと。具体的には、コメントで次を残す：
  - **何を作っていないか**（未実装・スタブの箇所）

  後で別の人（または別の AI）が引き継げるように。
