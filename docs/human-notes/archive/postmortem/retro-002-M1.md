## 0. このレポートの使い方

本レポートは、SF6コンボ管理アプリの実装準備工程 M1(コア基盤)で得られた知見を体系化し、本プロジェクトの M2 以降および将来の新規アプリ開発に活かすための内部文書です。

第1章で工程の総括、第2章で反省点(14項目)、第3章で M2 以降の推奨プロセス、第4章で新規アプリ開発時の推奨プロセス、第5章でチェックリスト、第6章で最優先改善事項を提示します。

本レポートは前作 RETRO-001(要件定義〜基本設計フェーズ反省会)の続編であり、RETRO-001 の項目(R-01〜R-15)で継続課題として残っているものは第2章 §2.5 で扱います。RETRO-001 を併読すると、プロジェクト全体を通した改善方針が見えます。

## 1. 工程の総括

### 1.1 成果

本工程では、M1(コア基盤)の指示書群7本(M1-01〜M1-07)を作成し、Claude Code による実装、機械レビュー、統合 E2E までを完遂した。

設計品質と運用面で、以下が評価できる。

- **段階的並列(2並列×2段階)** による M1 後半の効率化を実現した(理論最短時間には届かなかったが、直列実行よりは短縮)
- **機械レビューチェックリストの分離** により、製造担当の必読範囲を最小化(指示書本体のみ)し、レビュー担当が独立してチェックできる構造を確立した
- 製造担当(Claude Code)の **CLAUDE.md §8 遵守による Plan Mode での停止・確認** が機能し、設計書本体の不整合(DES-003 と DES-004 の `presets.code` カラム不在)を発見できた。これにより CHANGE-006 / CHANGE-007 として正式な設計変更通知書を起票できた
- M1 → M2 への引き継ぎメモ(`m1-to-m2-handover.md`)を整備し、次セッションへの接続体制を整えた

### 1.2 課題

一方で、以下の課題が明確になった。

- **設計書本体との照合不足**: 私(設計担当)が DES-003 を厳密に確認せず、推測で指示書を書いた箇所が複数発覚した(`name_ja`/`name_en` カラムの誤記、存在しないインデックス、タイムスタンプカラムの誤追加 等)
- **指示書記述の曖昧表現**: 「(あれば)または」「実装時に決定」「既に返している実装ならOK」等の表現が複数解釈を許し、実装漏れ(`modifiers.notes` 表示処理)を生んだ
- **指示書間の矛盾**: M1-04 と M1-05 の責任所在が曖昧で、M1-05 製造担当が CLAUDE.md §8 に基づき停止・確認する事態が発生した
- **並列実行のペナルティ過小評価**: worktree セットアップ、マージ衝突、5ターミナル同時運用の認知負荷が想定を超え、開発者に体調不良(片頭痛)を発生させた
- **言語固有知識制約とレビュー困難**: 開発者が Go + React 初見であり、UI 以外の領域でレビュー精度が出せなかった
- **個別 worktree での E2E 構造的限界**: 各 worktree が独立した変更しか持たないため、統合前の動作確認は実質不可能だった

## 2. 反省点と改善案(14項目)

### 2.1 指示書品質系

#### R-01 設計書本体との照合不足(最重要)

**現象**: 私が指示書を作成する際、対応する設計書節を厳密に確認せず、推測で構造体やマイグレーションを書いた箇所が複数発覚した。具体的には:

- `moves` テーブルに存在しない `name_ja` / `name_en` カラムを seed SQL に書いた
- `presets` テーブルに存在しない `name_ja` / `name_en` カラムを記載した
- DES-003 §4 にない `(preset_id, alias_text)` インデックスを記載した
- `games` / `characters` / `presets` / `preset_aliases` に存在しない `created_at` / `updated_at` カラムを INSERT 文に含めた
- `combos` テーブルに存在しない `name` カラムを CreateRequest DTO に含めた

これらは M1-02 製造担当のレビュー、および M1-03 製造担当の質問により発覚し、複数回のホットフィックスとなった。

**原因**: 指示書作成時、開発担当(過去)時代の知識や M0 プロトタイプの記憶を頼りにフィールドを列挙してしまい、設計書本体(DES-003)を view ツールで開いて確認するプロセスを省略した。

**改善案**:

- 指示書の各 DTO・構造体・マイグレーション SQL に、**対応する設計書節を必ず引用元として併記**する(例: 「`combos` テーブルの定義は DES-003 §3.4 に従う」だけでなく、「[DES-003 §3.4 行範囲 X〜Y を参照]」レベルで具体化)
- 指示書作成プロセスに「**設計書本体を view ツールで開いて該当節を読む**」を必須ステップとして組み込む
- レビューチェックリストの先頭に「**設計書本体との照合**」項目を必ず含める(本プロジェクトでは部分的に含めていたが徹底されていなかった)
- 推測で書いた箇所には「**推測。設計書 §X.Y との整合性を要確認**」と明記する(製造担当が照合しやすくなる)

**優先度**: 最高

#### R-02 指示書記述の曖昧表現の使用

**現象**: 指示書中に複数の解釈が可能な曖昧表現を使い、製造担当を迷わせた。具体例:

- 「`recipe_cache` を `ComboResponse` に展開して含める(M1-03 の handler を必要に応じて修正、ただし**既に `recipe_cache` を返す実装になっているなら追加修正不要**)」 → 製造担当が「現状でOK」と解釈し、実装漏れ
- 「`GET /api/combos/:id/recipe?preset_id=X`(**あれば**)または combos detail API のレスポンスに含まれる cache から取得」 → 専用エンドポイントが存在しないのに「あれば」で読んだ製造担当が停止
- 「UI フォーマットは**実装時に決定**」 → 誰が、いつ、どこで決めるのかが曖昧で、結果的に `modifiers.notes` の表示処理が実装漏れ
- 「**任意で導入可能**」(shadcn/ui 等) → 並列実装中の他指示書との衝突を考慮せず判断する余地を残してしまう

**原因**: 設計担当が判断を保留したい場面で、「実装担当に委ねる」つもりで曖昧表現を選んだが、結果的に「誰も決めない」状態を生んだ。

**改善案**:

- 指示書執筆時の **禁則表現リスト** を作る:
  - 「あれば」「必要に応じて」「実装時に決定」「任意で」「適切に」「既に〜していれば不要」
- 判断を後回しにする場合でも、**「誰が・いつ・どこで決めるか」を必ず明記**する:
  - 例: 「UI フォーマットは M2-XX 着手時に開発者が決定」
  - 例: 「shadcn/ui 導入は M1-05 製造担当が Plan Mode で開発者承認を得てから判断」
- 「条件付き OK」を書くときは、条件を満たさない場合の動作も明記する:
  - 悪い例: 「既に X を返す実装ならOK」
  - 良い例: 「現状の実装で X が返っていなければ Y を追加実装すること。返っていれば追加修正不要」

**優先度**: 最高

---

#### R-03 指示書間の矛盾(M1-04 と M1-05 の責任所在曖昧)

**現象**: M1-04 と M1-05 の責任分担が曖昧で、製造担当が停止・確認する事態が発生した。

- M1-04 §4.5.3 で「専用エンドポイントは M1-05 で必要に応じて追加可」と書いた
- M1-05 §2.3 で「バックエンド側のコードは変更しない」と書いた
- M1-05 §4.2.2 で「専用エンドポイント(あれば)または cache から取得」と書いた

→ M1-05 製造担当が「§2.3 と §4.2.2 が矛盾している」と CLAUDE.md §8 に基づき停止。

同様の構造が M1-06 でも発生(`/api/moves` エンドポイントが M1-04 までで実装されておらず、M1-06 §2.3 が「バックエンド変更しない」と矛盾)。

**原因**:

- フロント指示書を書く時点で、必要な API が既存指示書群で実装されているか逆算チェックしていなかった
- 「変更しないもの」と「例外的に許容するもの」の境界を明示する節を最初から設けていなかった

**改善案**:

- フロント指示書作成時、**API 依存マップ**(必要な API の一覧と、それがどの指示書で実装されるか)を必ず確認する手順を入れる
- 指示書テンプレートに **「§2.3 変更しないもの(原則)」「§2.4 例外: バックエンドへの最小限の追加が許容される箇所」** の節を初期から用意する(本プロジェクトでは事後に追加したが、初期から組み込むべき)
- 「フロント実装時にバックエンド最小追加が必要になるパターン」を運用ルールとして明文化する(本プロジェクト後半で確立した、M1-05 の `/api/combos/:id/recipe` と M1-06 の `/api/moves` の追加パターンを正式運用化)

**優先度**: 高

### 2.2 並列実行運用系

#### R-04 並列実行のペナルティ過小評価(健康影響まで発生)

**現象**: 段階的並列(2並列×2段階)を採用したが、実際の所要時間は理論値を超え、**開発者に体調不良(片頭痛)が発生**した。

並列遅延の主原因(開発者からの指摘):

- worktree セットアップコスト(各 worktree で `pnpm install`、`config.toml` で別 DB パス指定 等)
- マージ衝突対応(`cmd/combomgr/main.go` の import / ルート登録ブロックがほぼ確実に衝突)
- 並列中の質問対応による認知負荷(製造担当4名 + レビュー担当2名から同時に質問が発生)
- **開発者の同時運用ターミナル数が5本(Web 版1 + 開発CLI2 + レビューCLI2)に達し、各指示の振り分けで作業が雑になった**

**原因**: 並列実行の効率化メリットを過大評価し、開発者の認知負荷・健康への影響を軽視した。1人プロジェクトでの並列実行は、企業開発の並列実行と同じスケーラビリティが期待できない。

**改善案**:

- 並列実行の判断基準として「**開発者が安全に管理できる同時稼働ターミナル数**」を一次指標とする:
  - 推奨: Web 版1本 + Claude Code 2本(製造1 + レビュー1)= 計3ターミナルが**実質上限**
  - これは「2並列」という用語ではなく「**1並列で進める(製造1 + レビュー1)**」と表現する方が正確
- 並列実行を採用するのは「**指示書の完成度が高く、製造担当の質問が出にくいタスク群**」に限定する(例: 既存パターンの繰り返し、独立性の高い API 群)
- **初回プロジェクトや新領域の機能実装は直列実行を基本**とする(並列の誘惑を断つ)
- 並列実行採用時は **健康配慮** を運用ルールに含める:
  - 1セッションで複数並列を回す時間を制限(例: 連続2時間まで)
  - 体調不良の兆候が出たら即時中断、直列に切り替える

**優先度**: 最高

#### R-05 worktree 個別 E2E の構造的限界の見落とし

**現象**: 段階的並列で4本の worktree(M1-04 / M1-05 / M1-06 / M1-07)を並走させたが、各 worktree で個別に E2E テストしようとすると、互いの API 呼び出しが繋がらず動作しないことが後から判明した。

例:

- `combomgr-m1-05` の worktree には M1-06 が追加した `/api/moves` が存在しない → 技セレクタが空
- `combomgr-m1-06` の worktree には M1-05 が追加した `/api/combos/:id/recipe` が存在しない → プリセット切替不可

結局マージ後の統合状態でしか E2E が実施できず、並列実行の利点(独立してテストできる)が活かせなかった。

**原因**:

- 並列実行ガイド(`parallel-execution-guide.md`)を作る際、「マージ前 E2E は各 worktree で可能」という前提で書いてしまった
- 実際にはフロント・バックエンドが密結合した機能を並列で開発する以上、統合前テストは構造的に困難であることに気付かなかった

**改善案**:

- 並列実行ガイドに「**マージ前 E2E はできない、統合後にしかコア機能の動作確認はできない**」を明記する
- 並列タスクごとに「**単体ビルドが通る**」「**ユニットテストが通る**」だけを完了基準とし、E2E は統合後に実施する運用に統一する
- 並列実行採用時は、**マージ手順を事前に明文化**しておく(衝突しやすい箇所、衝突解決の方針、マージ後の動作確認手順)

**優先度**: 高

---

#### R-06 5ターミナル同時運用の認知負荷

**現象**: M1 後半で開発者が同時運用したターミナル数が以下に達した:

- Web 版 Claude(設計担当): 1本
- Claude Code(製造担当 M1-05、M1-06 など): 2〜4本
- Claude Code(レビュー担当): 2〜4本

合計5〜9本のターミナルを切り替えながら、各指示を間違えないように振り分けるのは、**ソフトウェア開発というよりオペレーター業務**に近い負荷を生んだ。

**原因**: AI に作業を任せられる範囲を最大化しようとして、人間側の管理負荷を過小評価した。

**改善案**:

- 同時稼働ターミナル数の上限を運用ルール化(R-04 と連動):
  - **常時最大3本**(Web版 + 製造1 + レビュー1)
  - **短時間で最大4本**(段階的並列時、製造2 + レビュー2)
- 各 Claude Code に振る指示の **書き出しテンプレート**を統一(誤送信を防ぐ):
  ```
  【担当】M1-XX 製造担当
  【作業】(具体的な指示)
  ```
- 並列度を下げる代わりに、**1指示書あたりの製造担当・レビュー担当の質を上げる**(指示書の完成度を上げて質問頻度を下げる)

**優先度**: 高

### 2.3 品質保証系(本工程の最重要課題)

#### R-07 開発者の言語固有知識制約とレビュー困難領域

**現象**: 開発者は経験豊富だが、Go と React は初見であり、本プロジェクトで初めて触れる。M1 の実装結果をレビューする際、UI 領域は問題なくチェックできたが、**それ以外の領域(バックエンドコード品質、API 整合性、バリデーション動作、データモデル整合性)はそもそも何が書いてあるか理解する段階で困難**だった。

期間内に基礎知識を習得する余裕もなく、結果として「動くことは確認したが、設計意図通りに動いているかは不明」な状態が複数発生した。`modifiers.notes` の表示漏れはその象徴。

**原因**:

- AI による実装速度に対し、開発者の言語学習速度が追いつかない構造的問題
- 個人 OSS 開発で AI を活用する際の、本質的な課題

**改善案**:

- 開発者の言語熟練度に応じて、**品質保証の責任を AI 側に持ち込む**:
  - 製造担当の自己テスト強化(R-09 で詳述)
  - AI レビュアーの強化(R-10 で詳述)
  - 段階的 E2E の組み込み(R-11 で詳述)
- 開発者は「最終動作確認」と「ドメイン知識のチェック」に集中し、**コード品質判定は AI に委ねる**運用を許容する
- 本プロジェクト規模では「コード品質の見逃し」は許容範囲と捉え、技術的負債は M2 以降や運用フェーズで気付いた時点で対応する方針を明文化

**優先度**: 最高

#### R-08 UI 以外の品質保証戦略の欠落

**現象**: 本プロジェクトの品質保証は、機械レビュー(Claude による独立レビュー)+ 開発者の手動 E2E で構成されていたが、**UI 以外の領域(バックエンドコード品質、API 整合性等)に対する独立した品質保証**が事実上欠落していた。

機械レビューはチェックリスト項目に従って動くが、「製造担当が書いたコードが本当に設計通りか」を深く読み込んで判定する責務を担っていなかった(チェックリストが浅い項目の羅列に留まっていた)。

**原因**: レビューチェックリストの作成時、設計書本体との照合・API 整合性・バリデーション動作確認といった深い項目を十分に組み込まなかった。

**改善案**:

- レビューチェックリストの **必須項目を強化** する:
  - 設計書本体との照合(各 DTO・構造体が DES-X §X.Y と一致するか)
  - API 整合性(レスポンス DTO の型がフロントの useQuery で扱える形か)
  - バリデーション動作確認(各 VAL-ID がエラー条件で実際にエラーを返すか)
  - エラーハンドリング(404 / 400 / 500 の各シナリオが適切に処理されるか)
- レビュー担当 Claude に対し、「**チェックリストを機械的にチェックするだけでなく、設計意図との整合を読み取る**」役割を明示する
- レビュー結果の品質を、開発者が「(実際にバグを発見できているか)」で評価する習慣を作る(レビューをしただけで満足しない)

**優先度**: 高

#### R-09 DoD と E2E シナリオの具体化不足

**現象**: 各指示書の DoD(Definition of Done)が「動作する」「テストが通る」レベルに留まり、「**こういう振る舞いを示すこと**」レベルまで具体化されていなかった。

例: M1-05 の DoD §7「プリセット切替で `official_ja_move` のエイリアス変換が反映される」は具体的だが、`modifiers.notes` の表示は DoD に含まれていなかったため、実装漏れが見逃された。

**原因**: 指示書作成時、開発者(=最終レビュアー)目線で「何が確認できれば完了と言えるか」を十分に列挙していなかった。

**改善案**:

- 各指示書に **E2E シナリオ節** を新設し、「実装後にこの操作を実行して、こう動くこと」を具体的に書く:
  ```
  ## E2E シナリオ
  1. /combos/new で新規コンボを開く
  2. 技ステップに notes("テスト") を入力
  3. 保存
  4. 詳細画面で notes が表示されている  ← これが見えるまで DoD 不達成
  ```
- DoD は「動作する」だけでなく「**設計意図通りの振る舞いを示すこと**」レベルで定義する
- 各指示書完了時に、**開発者がそのシナリオを実際に手動実行**して合格判定する運用にする(機械レビューだけでは見つからない実装漏れを防ぐ)

**優先度**: 高

---

### 2.4 Claude 運用系

#### R-10 Web 版と Claude Code の使い分け(現状運用は妥当だが整理)

**現象**: 設計担当を Web 版、製造・レビュー担当を Claude Code で運用したが、AI 同士の質問の仲介(製造担当 → 設計担当へ Web 版経由で確認)が認知負荷の一因となった。

ただし、開発者は「今回の開発規模だと適切な苦労の範疇」と判断しており、Web 版主体運用は本プロジェクトには合っていた。

**原因**: なし(現状運用が現実的最適解)

**改善案**:

- 現状の Web 版主体運用を維持。新規プロジェクトでも、**設計担当は Web 版、実装は Claude Code** という分離運用を推奨。
- 設計担当の作業のうち、機械的な反映作業(CHANGE 起票時の波及修正、複数指示書の一括バージョンアップ等)は、必要に応じて Claude Code に切り出す。ただし**主軸は Web 版**を維持。
- 「AI 同士の質問の仲介」は人間が必ず介在する形を維持(開発者が判断・承認する機会を担保)。

**優先度**: 中(現状維持)

---

#### R-11 Claude Code の権限調整不足

**現象**: 製造担当・レビュー担当の Claude Code に対し、参照系コマンド(`view`、`ls`、`grep`、`cat`)まで承認を求める設定になっていた。M1 後半の並列実行時、「ただの参照コマンドを何度も承認」する作業が発生し、結果的に作業が雑になった(承認を流し見してしまう、誤った承認をしてしまう)。

**原因**: プロジェクト初期の `.claude/settings.json` で、安全側に倒した設定をそのまま運用し続けた。M1 後半の負荷増に応じた権限調整を行わなかった。

**改善案**:

- `.claude/settings.json` で **読み取り専用コマンドの自動許可** を設定する:
  - `view`、`ls`、`find`、`grep`、`cat`、`head`、`tail`、`wc` 等
  - これらはファイルシステムを変更しないため、誤実行のリスクが低い
- **make コマンドの自動許可** も検討(`make build`、`make test` 等は副作用が小さい)
- ただし **書き込み系・git 系・実行系** は明示確認のまま維持:
  - 書き込み: `create_file`、`str_replace`、`bash_tool` の `>` リダイレクト
  - git: 全コマンド禁止(本プロジェクトの方針)
  - 実行: `go run`、`pnpm dev` 等(プロセスを起動するもの)
- 認知負荷を下げることで、**重要な書き込み・実行系の承認に集中力を回せる**ようにする

**優先度**: 高(M2 着手前に実施推奨)

---

#### R-12 Claude Code カスタムコマンド未活用

**現象**: 製造担当・レビュー担当を Claude Code で起動する際、毎回手動で「指示書を読む」「レビューチェックリストを読む」「Plan Mode で計画提示する」を伝える必要があった。これは反復作業であり、Skills(Claude Code のカスタムコマンド機能)で簡素化できた。

**原因**: 本プロジェクト開始時、Claude Code のカスタムコマンド機能を活用する発想がなかった。

**改善案**:

- 以下のカスタムコマンドを `.claude/commands/` 配下に配置する:
  ```
  /manufacture <指示書ID>
  → 例: /manufacture M1-04
     自動で M1-04-presets-and-recipe-cache.md を読み、
     関連設計書(SUPP-001、DES-003 等)も参照し、
     Plan Mode で計画提示を開始する

  /review <指示書ID>
  → 例: /review M1-04
     M1-04 指示書 + reviews/M1-04-review-checklist.md を読み、
     生成物を view ツールで確認してレビュー開始する

  /handover <マイルストーン>
  → 例: /handover M2
     M{N}-overview.md と関連指示書を読み込み、
     M{N+1} への引き継ぎメモを作成する
  ```
- カスタムコマンドの作成は M2 着手前に実施し、M2 以降の運用を効率化する
- カスタムコマンド自体の品質を Skill として整備する選択肢もある(余裕があれば)

**優先度**: 高

---

### 2.5 RETRO-001 からの継続課題

#### R-13 判断トレース(Decision Log)の弱さ

**現象**: RETRO-001 の R-06 で挙げられた「判断記録の不在」は、本工程でも継続課題として残った。

本工程では指示書の更新履歴に変更経緯を記録する運用が確立したが、**「なぜこの判断になったか」の議論経緯**は完全には残せていない。製造担当との Q&A の結果が指示書に反映される過程で、議論内容が要約・省略されている。

**改善案**:

- RETRO-001 の R-06 で提案された **ADR(Architecture Decision Record)形式** での判断記録を、本プロジェクトの M2 以降で導入する:
  ```
  docs/adr/
  ├── 0001-aggregate-combo-step-model.md
  ├── 0002-recipe-cache-as-column-json.md
  ├── 0003-counter-type-renamed-to-hit-type.md
  └── ...
  ```
- 各 ADR で「判断日時、選択肢、採用案、理由、代替案却下理由」を記録
- 軽量で済む場合は、**指示書の §10「注意事項」付近に判断経緯を残す**運用でも代替可

**優先度**: 中

---

#### R-14 やりとりフォーマットの完全統一余地

**現象**: RETRO-001 の R-04 で挙げられた「やりとりフォーマット」は、本工程で部分的に改善した(製造担当への回答コピペ用テンプレートが定着)。しかし、**完全な統一**には至っていない。

例: 製造担当からの質問への返信は、毎回類似のフォーマット(承認理由 → 採用しない案 → 実装方針 → お詫び 等)で書いたが、テンプレート化されておらず毎回ゼロから記述した。

**改善案**:

- 製造担当への回答テンプレートを正式化:
  ```
  ## 結論: 案X を承認

  ## 承認理由
  (製造担当の判断との一致、設計書との整合性、他案を採用しない理由)

  ## 実装方針
  (具体的な実装範囲、ファイル列挙、レスポンスフォーマット等)

  ## お詫び(指示書ミス起因の場合)
  (指示書の不備を認め、修正方針を伝える)

  ## 指示書更新
  (バージョン、変更内容)
  ```
- カスタムコマンド `/answer-question` で、上記テンプレートを自動展開する選択肢も検討

**優先度**: 中

## 3. M2 以降の推奨プロセス(本プロジェクト継続用)

本プロジェクトの M2(編集系の本格化)以降を効率的に進めるため、以下を M2 着手前に整備する。

### 3.1 並列実行ポリシーの見直し

R-04 / R-05 / R-06 を踏まえ、M2 以降の並列実行ポリシーを以下に変更する。

**基本方針**: **直列実行を基本とする**。並列実行は限定条件下のみ。

**並列実行を採用してよい条件**(全てを満たすこと):

- 並列タスクの独立性が高い(API・画面が完全に分離されている)
- 各タスクの指示書完成度が高い(製造担当の質問が出にくい)
- 開発者の体調が良好で、長時間の集中が可能
- 同時稼働ターミナル数が4本以下(Web版1 + 製造2 + レビュー1)に収まる

**並列実行を採用しない条件**(いずれかを満たす場合):

- 新領域の機能実装で指示書の完成度が読めない
- 製造担当の Plan Mode で多数の質問が出る可能性が高い
- 開発者が疲れている、または週後半で集中力が落ちている

### 3.2 開発者の言語学習を補完する品質保証

R-07 / R-08 / R-09 を踏まえ、以下を M2 以降に組み込む。

#### 3.2.1 製造担当の自己テスト強化

各指示書の DoD に以下を必ず含める:

- **API 動作確認**: `curl` コマンドで主要 API を叩き、レスポンスを報告書に貼付
- **エラーケースの動作確認**: 400 / 404 / 500 の各シナリオを `curl` で再現
- **データ整合性確認**: 登録した内容を `GET` で取り直し、入力と一致するか確認

製造担当の実装完了報告に「自己テスト結果」セクションを必須化。

#### 3.2.2 AI レビュアーの強化

レビューチェックリストを以下の項目で強化:

- 設計書本体との照合(各 DTO・構造体が DES-X §X.Y と一致)
- API 整合性(リクエスト/レスポンスの型が DTO・フロント側 hook と整合)
- バリデーション動作確認(各 VAL-ID がエラー条件で発火することを確認)
- エラーハンドリング網羅(各エラーシナリオが適切に処理される)
- 設計意図との整合(チェックリストの機械的チェックを超えた、文脈理解)

#### 3.2.3 段階的 E2E の組み込み

各指示書完了時点で、開発者が以下を実施:

- バックエンド指示書: `curl` でコア API を叩き、期待レスポンスが返るか確認
- フロント指示書: ブラウザで該当画面を開き、E2E シナリオを通す

「全部完了してから E2E」ではなく「各指示書完了ごとに動作確認」する運用に変更。

### 3.3 Claude Code のカスタムコマンド導入

R-12 を踏まえ、M2 着手前に以下を整備:

- `.claude/commands/manufacture.md`: 製造担当起動コマンド
- `.claude/commands/review.md`: レビュー担当起動コマンド
- `.claude/commands/handover.md`: 引き継ぎメモ作成コマンド

各コマンドの引数は指示書 ID(例: `M2-01`)。コマンド内部で関連ファイルを自動 view する。

### 3.4 Claude Code の権限調整

R-11 を踏まえ、`.claude/settings.json` を以下に変更:

```json
{
  "permissions": {
    "allow": [
      "Bash(view:*)",
      "Bash(ls:*)",
      "Bash(find:*)",
      "Bash(grep:*)",
      "Bash(cat:*)",

}
```

書き込み系・実行系・git 系は明示確認のまま維持。

## 7. 本工程を振り返って

本工程は、SF6コンボ管理アプリの M1(コア基盤)を、設計担当(Web 版 Claude)・製造担当(Claude Code)・レビュー担当(Claude Code)の三者構成で完遂した。AI を実装担当として活用し、人間が品質保証と判断を担う「AI-Driven Development」の実践として、貴重な学びが得られた。

特に重要な学びは以下の3点:

第一に、**設計書本体との照合プロセスを軽視できない**ことが分かった。私(設計担当)が推測で指示書を書いた箇所が複数発覚し、製造担当のレビューで救われた。次プロジェクトでは、指示書作成時に設計書本体を view ツールで開いて確認するプロセスを必須化する。

第二に、**並列実行は健康と相談しながら**行うべき領域だと明確になった。1人プロジェクトで5ターミナルを同時運用すると、認知負荷が体調不良を引き起こす。並列実行の効率化メリットは、開発者の健康と引き換えにするほどの価値はない。

第三に、**開発者の言語固有知識制約は、AI 活用の本質的課題**だと判明した。AI による実装速度に対し、開発者の言語学習速度が追いつかない構造で、UI 以外の領域でレビュー精度が出せなかった。次プロジェクトでは、品質保証の責任を AI 側に持ち込む運用(製造自己テスト、AI レビュアー強化、段階的 E2E)を最初から組み込む。

これらの学びを M2 以降の本プロジェクトと、将来の新規アプリ開発に活かす。

RETRO-001 の最後に書かれた「対話型設計の強みを活かして高品質な成果物を生み出せた」は、実装準備工程でも変わらず妥当である。製造担当(Claude Code)が CLAUDE.md §8 を遵守して律儀に質問してきたこと、設計担当(私)と開発者の対話で判断を細かく確認したこと、これらの **対話の積み重ねが設計と実装の品質を支えた**。

次回も、対話を恐れず、判断を細かく確認する姿勢で進めたい。
