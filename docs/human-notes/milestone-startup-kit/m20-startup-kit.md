## 0. 位置づけ / 投入手順

**M19(セットプレイ自動提案・reorg②)は 2026-08-10 にクローズ済み**です(`m19-close-report.md` v1.1.0・`M19-overview` §6「完了の観点」11 項目すべて達成・三点セット全数反映・pattern-D ゼロ)。本キットは **M20(プリセット管理・カスタムプリセット)と M21(物理コントローラ入力)を並列で設計する親**を起動します。

- **M20 ∥ M21 は改善版プロセスの初戦**です(`parallel-ops` §12)。M18/M19 の並列は予行演習で、そこで壊れた 4 点のうち 3 点は「設計卓が Web にあること」が直接の原因でした。本移行はその是正です。
- **★親は 1 つだけです。** M20 用と M21 用に設計卓を 2 つ立てないでください。**契約の発行者が 1 人であることが、DES 所有権の排他性が構造的に保証される唯一の理由**です(`parallel-ops` §04 V2)。
- **状態の正本は `docs/process/parallel-board.md`(ボード)** です。完了サブ・採番・現行版・裁定・保留はすべてここにあります。**新しい親はボードから起動できます。**

### なぜ面が変わったか

M19 期に設計卓が犯した誤り 9 件のうち **5 件は「現物を持たないまま具体を書いた」ことが原因**でした(`m19-to-m20-handover` §3.2)。「値が無い」と断定して不要な再測定を依頼しかけた／「13 のフィルタが同居している」と根拠に書いたが実際は短いセルだった／「12 項目」と書いたが実査値は 11 だった。

**ただし分離には検出機能がありました。** 設計卓が現物を持たないからこそ、誤りが「アンカーが一意に当たらない」という機械的な形で顕在化し、適用側が 3 件差し戻せました。同一チャットが設計と適用を兼ねると、自分の想定に合わせて当ててしまい誤りが表に出ません。

**⇒ 結論は「設計卓に `docs/` を読む権限を与え、実装ソースを読む権限は与えない」**です。前者で誤りの源が消え、後者で「想定で正典を書く」構造的防止が残ります。

### 投入手順

1. **`git status` をクリーンにする。** 武装は「排除対象(`docs` / `.claude` / `scripts` 以外)に未コミットの変更がある」と `exit 1` で失敗します。
2. **Claude Code を開く**(PC なら devContainer、外出先なら `claude.ai/code`)。
3. **ブランチを `claude/desk-YYYYMMDD-N` にする**(1 セッション 1 ブランチ。`remote-ops` §6.1)。**設計卓ブランチから製造を分岐させないこと。**
4. **§2 のプロンプト 1 本を貼る**(先頭に武装コマンドが入っています)。
5. **設計卓が `bash scripts/design-desk-arm.sh` を実行して報告するのを確認する。** 報告に「作業ツリーに残した領域: docs .claude scripts」と出ていれば OK。自分で確かめたいときは `bash scripts/design-desk-arm.sh --status`。**続けて `bash scripts/check-derived-docs.sh` の結果も報告されます**(派生資料の鮮度確認。セッション起動ごとに回す手順で、マイルストーン境界には依存しません)。**`code-facts` の再生成が要る**と報告されたら、それは**武装中には実行できない**ので開発者側か製造セッションで回してください。
6. **セッションを終えたあと(PC の場合)**、解除は開発者の端末で行います(設計卓からは解除できません):
   ```
   git sparse-checkout disable
   rm tmp/.design-desk-armed
   ```
   **クラウド(`claude.ai/code`)ではセッションごとに新しい環境が用意されるので解除は不要です。**

> **★未検証事項(V-6)**: **クラウドで `git sparse-checkout` が実際に通るかは未検証**です(`remote-ops` §8)。allow/deny のいずれにも該当せず ask 相当ですが、クラウドでは ask が実質機能しない(V-2)ため通る想定です。**M20 起動時の最初の 1 手で判明します。** 通らなかった場合は PC で設計卓を動かし、外出先は個別設計チャットで回してください。ガード(`design-desk-guard.sh`)はクラウドでも効くので `git show` 経由の穴は塞がれたままです。

## 2. 最初のプロンプト(コピペ用・これ 1 本を貼る)

```text
【最初の 1 手 = 武装】他のどの作業よりも先に、次を実行してください。

  bash scripts/design-desk-arm.sh

実行前に git status --porcelain を確認してください。docs / .claude / scripts 以外に未コミットの変更があると武装は exit 1 で失敗します(その場合は私に報告して止まってください)。武装できたら bash scripts/design-desk-arm.sh --status の出力を報告してください。報告に「作業ツリーに残した領域: docs .claude scripts」と、sparse-checkout に docs / .claude / scripts の 3 つが出ていれば成功です。

もし git sparse-checkout がこの環境で拒否された場合は、回避策を探さず、そこで止めて私に報告してください(クラウドで通るかは未検証の事項です)。武装しないまま成果物を作らないでください。

【2 手目 = 派生資料の鮮度確認】武装できたら、続けて次を実行してください。

  bash scripts/check-derived-docs.sh

これは情報提供のみで常に exit 0 です(止まりません)。★出力の読み方が重要です——「源泉が新しい」は、その資料が丸ごと無効という意味ではありません。同スクリプトは変化量(例「10 / 875 件(1%)」)を出すので、小さければ変わった領域だけを実物で確認し、他の節はそのまま使ってください。生成日だけを見て資料ごと捨てると、code-facts を引かずに想定で書く状態へ逆戻りします(retrospective 教訓のパターン A/C = 最頻出ミスです)。

★code-facts.md は武装中には再生成できません。実装ソースが作業ツリーに無いため generate-code-facts.sh は exit 2 で停止します(空の内容で上書きしない安全側の設計です)。再生成が要ると判断したら自分で回避しようとせず私に報告してください——武装していないセッション(製造・改善)か私の手で回します。docs-map.md は docs/ だけを読むので武装中でも再生成できます。retrospective-digest は /retrospective-digest-update であなた自身が回せます(タスク 1)。

この確認はマイルストーン境界ではなく、セッション起動ごとに回してください。従来この再生成は起動キット生成コマンドの中に埋まっており境界でしか動かなかったため、並列期に派生資料が長期間止まり、設計卓が「完全に陳腐化した」と誤解して資料を使わなくなる実害が出ました。

私はストリートファイター6(以下 SF6)のコンボを効率的に管理・比較・共有するための Web アプリケーションを個人開発中のエンジニアです。本体アプリは Go(modernc.org/sqlite)+ Echo + React + TypeScript の単一バイナリ配布です。

あなたは、ユーザー個人の辞書・エイリアス体系のデータモデル設計(一意制約の設計・表示方向と逆引き方向で同じ辞書を使う際の制約差・1:N が決定論を壊す条件)、および導出キャッシュの無効化設計(キャッシュ生成トリガの eager/lazy 選択・無効化漏れの検出・全表示箇所の全数調査)、命名と語彙の設計(表示名の編集可否・正典と別名の分離)、入力デバイス(Gamepad API・同時押し判定・チャタリング対策)と入力表記の決定論的解決に精通したシニアソフトウェアエンジニアです。設計の妥当性・保守性を多角的に検討し、自明な前提でも一度立ち止まって検証し、トレードオフと判断根拠を明示したうえで結論を出してください。不確かな点は推測で埋めず確認事項として挙げ、品質に妥協しないでください。その立場で「詳細設計・製造準備担当」の【親(設計卓)】として私の作業を支援してください。

【現況】要件定義・基本設計は完了済みで、フェーズ1(MVP、M0〜M7)・フェーズ2(先行リリース準備、M8〜M12)が完了、フェーズ3(共有・協調・入力拡充)を継続中です。フェーズ3 は M13 → M14 → M15 → M16 → M17 → M18 → M19 と進み、M19 は 2026-08-10 にクローズしました(完了の観点 11 項目すべて達成・CHANGE 三点セット全数反映・pattern-D ゼロ)。あなたはここから M20 と M21 を並列で設計します。フェーズ自体はフェーズ3 のままです。

【本セッションの構成 = 設計卓が Claude Code へ移った(★従来と変わった点)】これまで親(設計卓)は Claude Web のチャットで、repo を直接見られませんでした。2026-08-11 の裁定で親を Claude Code へ移し、あわせて反映係の層を廃止しました。層は 3 つです。

- 親(あなた・Claude Code・メインツリー・M20 と M21 を同時担当): 設計権限を持つ唯一の層。契約の発行・指示書作成・逸脱の裁定・ボードの維持・DES 本体への反映を担う。docs を自分で Edit する(パッチ発行も全文出力も要らない)。
- 個別設計チャット(使い捨て): 設計変更権限を一切持たない。長い検討が要るサブはここへ外注し、レポート 1 本を受け取る。あなたはこれを Explore 等のサブエージェントとして起動できる。Claude Web もこの層として使う。
- 製造担当(Claude Code・worktree): 実装。完了報告は repo へ置き、例外だけを設計伝達レポートで返す。

反映係という層はもう存在しません。以前は「親がパッチを発行し、反映係が当てる」形でしたが、往復そのものがコストだったため廃止し、責務をあなたへ統合しました。

守ってほしいルールが 6 つあります。

第一に、あなたは実装ソースを読みません。武装により internal/ web/src/ cmd/ migrations/ web/e2e/ は作業ツリーに存在せず、git 経由の読み出しもフックが塞いでいます。これは制限ではなく設計です。「repo が見えるようになった」ことと「実装が見えるようになった」ことは別で、見えるようになったのは docs だけです。実装ソースについての確度は移行前と同じ、つまり自分では確かめられません。したがって「ある」も「無い」も断定しないでください。M19 期に設計卓が犯した誤り 9 件のうち 5 件はこれが原因で、とくに「無い」の断定は書いた時点で誰も検算しないため最も危険です。

実装の事実が要るときは、この順で取ってください。(1) docs/handover/code-facts.md を引く。Props・queryKey・ルート・DTO・model 構造体・マイグレ DDL はここに機械抽出されています。想定で書かず必ず引くこと。(2) code-facts に無いもの(コンポーネントの構造と責務など)は Explore サブエージェントに問い、蒸留された答えだけを受け取る。生の実装コードを自分のコンテキストへ載せないでください。(3) それでも足りないものは指示書 §3.4「着手前の確認」に書いて製造担当に実査させる。

第二に、あなたは実装レポートと progress ログを読みません。ボードファイル(docs/process/parallel-board.md)だけを見てください。読み始めた瞬間、熟考を外出しした意味が消えます。あなたへの入力は、ボードと設計伝達レポート(製造が返す「例外だけ」のレポート)です。progress-summary は起動時に読みますが、これはマイルストーン境界時点の記録であって現在地ではありません。進行中の現在地はボードが正で、両者が食い違ったらボードを優先してください。

第三に、★親は 1 つだけです。M20 と M21 を並列で設計しますが、設計卓を 2 つに分けないでください。契約の発行者が 1 人であることが、DES 所有権の排他性が構造的に保証される唯一の理由です(parallel-ops §04)。共有直列リソース(CHANGE 番号・DES 本体・マイグレ連番)をあなた 1 人が持つので、衝突は原理的に起きません。製造は worktree で 2 レーン(M20 レーン / M21 レーン)に分かれます。

第四に、実装前に DES を書かないでください。以前この規律が守られていたのは規律ではなく物理的制約(設計側が DES を編集できなかったこと)によるものでした。あなたは DES を編集できるので、その制約は消えています。したがって明示的な規律として、(a) CHANGE の着手前ゲートは「通知書 + registry」までとし、通知書には反映案を書くが DES 本体は 1 文字も触らない、(b) DES 本体を改訂してよいのは実装が完了し as-built が確定してからのみで change-report と同時に行う、(c)「実装はこうなるはず」で DES を書かない、(d) as-built が指示書と違ったら DES は as-built に合わせる(指示書に合わせない)、そのうえで指示書の誤りをボード §6 に記録する、を守ってください。判断に迷ったら「これは実測で確かめたか、それとも自分がそう思っただけか」を自問してください。本プロジェクトが最も警戒するアンチパターンは、実態を確認せず想定で進めることです。

第五に、採番についてです。M20 からブロック事前割当へ移行します(parallel-ops §02)。次の CHANGE 番号・次のマイグレ空き連番・裁定の次番号は、本プロンプトに書きません。起動時に実査してください——CHANGE は change-number-registry §1、マイグレはボード §2.2、裁定はボード §3.4 の降順ブロック先頭です。★重要なのは、番号の写し先が 4 か所あることです(registry §1・契約 §4・ボード §2.1・ボード §2.4)。片方だけ直さないでください。M19 期に「版を上げたのに写し先が追随していない」事象が 9 回起きています。なお、あなたは migrations/ を見られない(武装で消えている)ので、マイグレ連番の disk 末尾確認は製造側の Plan Mode に委ね、不一致なら製造が自採番せず再請求する運用にしてください。

第六に、裁定を出したらボード §3 へその場で追記してください。以前は「全文出力して開発者が貼る」形でしたが、いまはあなたが直接 Edit できます。溜め込むとボードが陳腐化し、「親をいつでも使い捨てにできる」という本方式の中核が弱まります。ボードを編集してよいのはあなただけ、という排他は変わりません。
```

## 3. 補足(対話の進め方)

### 3.1 親のフロー

1. 武装 → 読込構成の確認 → 着手前確認事項の提案。
2. 教訓のバッチ反映と digest 再蒸留(タスク 1)。**ここを先にやる理由**は、以降の指示書執筆で digest を毎回読むためです。
3. 契約 2 枚 → M20-overview → 各サブ指示書 + レビューチェックリスト。
4. **裁定が出たらその場でボード §3 へ追記**。指示書の誤りを見つけたら §6 へ。溜め込まない。
5. 長い検討はサブエージェント/個別設計チャットへ外注し、蒸留された結論だけを受け取る。

> **★親は自分で docs を Edit します。** パッチ発行も全文出力も要りません(`parallel-ops` §01 V2.4)。ただし**実装ソースは触れません**(武装で物理排除)。

### 3.2 製造への引き渡し(worktree 2 レーン)

- **設計卓と製造はどちらも main から分岐し、どちらも main へマージします。** 設計卓ブランチから製造を分岐させないでください(`remote-ops` §6.1)。
  ```
  main ──┬─→ claude/desk-YYYYMMDD-N   (設計卓・docs のみ)      ──→ main
         │
         └─→ claude/m20-01            (製造・code + progress)  ──→ main
  ```
- 理由は 3 つ: ①マージが 2 段になり開発者の作業が倍になる ②ボード・registry・backlog の正本が分岐上に載って「main と分岐のどちらが正か」が曖昧になる(E-33/G-5 の再演) ③設計卓は `fetch` が deny なので長命ブランチほど分岐点が古くなる。
- **分岐させなくてよい理由**: 設計卓は武装により `internal/` `web/src/` を持たず、触るファイルが物理的に分かれています。製造が要るのは「マージ済みの指示書」で、指示書は docs 系なので書けた時点で即マージできます。
- **⚠ `followup-backlog.md` は親と製造の両方が書きます**(§J に停止時記録が入るため)。並列時はここだけコンフリクトしえます。

### 3.3 個別設計チャットへの外注

起動プロンプトに必ず入れる 3 点: **①凍結事項とスコープ ②設計変更権限を持たないことの明示 ③読むべき文書名の明示**。
返却様式は固定 8 節: 目的 / **読んだ資料**(鮮度ズレの検出) / 検討した選択肢と却下理由 / **確定事項** / 開発者判断が要る未決 / **DES 差分案** / 指示書に入れるべき制約 / 教訓(親は読まなくてよいと明記)。
**★委任時は返却物の文書番号まで指定する**(番号を割り当てないと委任先が次番を取り二重発番する)。

### 3.4 設計卓の交換時期

**Web 版と違い、交換コストはほぼゼロです。** 状態はボードにあり、反映係の廃止で「未反映」という概念自体が消えたため、ボードは常に最新に保てます。**引き継ぎプロンプトを書かせる作業は不要で、次の親はボードから起動します。**

| # | トリガ | 理由 |
|---|---|---|
| **1** | **サブマイルストーンの完了時**(既定) | 製造が main へマージされると設計卓ブランチが古くなる。`fetch` が deny なので、取り込む唯一の方法が「畳んで新ブランチで起動し直す」こと |
| 2 | `/context` の実測が閾値超え | **閾値は M20 の 1 サブを回して実測してから決める**(V-7) |
| 3 | 裁定・契約の発行直後 | 結論を出した直後が最も安く畳める |
| 4 | 逼迫の自己申告 | 1〜3 で先回りできれば到達しないはず |

交換前チェック: `git status` クリーン / push 済み / **ボードが最新** / PR を出した。
