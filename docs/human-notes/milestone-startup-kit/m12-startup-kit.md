## 3. 補足(対話の進め方)

- 流れ: 最初のプロンプト + A〜E のファイルを投入 → 設計担当の読み込み・確認事項提示 →
  **(1) M12 着手前確認(残フェーズ2 全件処遇の索引化・seed 整理範囲の実査・統合 E2E の E-1 回帰穴)** →
  **(2) M12-01 UX・正しさ修正の overview / 製造指示書** → M12-02 seed 整理 → M12-03 統合 E2E + 先行リリース判定、という流れ。
- **M12 は自由改訂中心**(phase2-overview §M12)。設計書本体改訂が必要なら CHANGE 通知書必須(次回 044)。
- **全件処遇が本マイルストーンの肝**: Memo トリアージ抜粋(#20)を索引に、残フェーズ2 を漏れなく処遇する。
  「多いので最終的な線引きは策定時」(元メモ注記)= M12-01 計画でその線引きを確定し文書化する。
- **想定で書かない、必ず引く**: 修正対象 UI・E2E 起点の導線は「あるはず」で書かず実コードで存在確認してから
  指示書に書く(M10-4 教訓)。**DB 実査 ≠ 仕様正典**、正典は DES 本体(最新 CHANGE 反映後)で確認(M10-1 教訓)。
  seed 整理(M12-02)では migration 000012 / 000015 の実体と共存状態を実査する。
- **CHANGE 二層運用**: 設計書本体(REQ-001 / DES-001〜006)改訂は CHANGE 通知書必須(次回 044)。
  補足資料(SUPP-001 / handover / playbook / registry / progress / architecture-patterns / phase2-overview /
  model-allocation / retrospective-digest / docs-map / followup-backlog)は自由改訂。
- **指示書執筆前に retrospective-digest を必読**。M11 教訓(PATCH トライステート / 局所センチネル vs 一般解 /
  前向き注意の再現)は retrospective-log §6.6.4(v1.0.39)に記録済みで digest も再蒸留済み(M11-1〜M11-5)。
  とくに **半更新 PATCH に nullable 項目を足すなら不在/null/値のトライステートを設計時に決め切る**(M11-2、M12 の
  UX 修正で nullable メタデータの編集・クリアを触る場合に直結)。継続パターンは「実コード・実態・正典の未確認 /
  前提の取り残し」(digest §1 A)。
- **【実験運用①:質問の文末集約】**§2 の指示どおり、各成果物の文末に「開発者への確認事項」を集約する運用を試行する。
  有効性(質問の見落とし減・往復効率)を本セッションで評価し、有効なら playbook へ恒久化を提案、不要なら撤去してよい。
- **【実験運用②:添付ファイルの受領確認】**§2 プロンプト末尾のブロックは複数ファイル添付時の一部未着・認識遅延への
  対処(M10 / M11 で有用と評価され継続)。効果を本セッションでも評価し、冗長・不要なら撤去・簡略化してよい。
- 「任意」ファイル(testid-convention、retrospective-log、followup-backlog、過去指示書テンプレ〔M11-01 / M11-02〕、
  過去 CHANGE 通知書、progress-log、Memo_Someday 本体、アーカイブ handover)は要望が出たとき、または次チャットで渡す。
- 各サブユニットの粒度・統合は phase2-overview を正本に、playbook のモデル運用基準で関心数を抑えて協議確定する。
  **マイルストーン構造の拡張・新規 overview の増設は独断せず開発者と合意する**(M9-5 / playbook §4.12 教訓)。
