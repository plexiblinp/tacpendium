## 0. 位置づけ / 投入手順

**並列 3 チャット(中央 + M18 指示書担当 + M19 指示書担当)から、統合 1 チャット(親)への移行**です。

- **実装は M18・M19 とも止まっていません。** M18 は全サブ(01/02/03a/03b/03c)実装完了・受理、M19 は RESEARCH 3 本 + 01/02/03 完了・受理。
- **止まっているのは設計側の反映だけ**です。CHANGE-090(M18-03c)と CHANGE-087(M19-03)が**通知書のみで、DES 本体反映と change-report が未着手**。
- **再開点** = ① CHANGE-090 の三点セット確定 → M18 クローズ ② CHANGE-087 の三点セット確定 ③ M19-04 の指示書化。
- **状態の正本は `docs/process/parallel-board.md`(ボード)** です。完了サブ・採番・現行版・裁定・保留はすべてここにあります。

### なぜ移行するか

並列 3 チャットで実際に壊れたもの(ボード §8.1):

- **開発者がメッセージバス化した** — チャット間通信が全部人手リレーで、中央のコンテキストを消費した
- **中央が人力ロックサーバー化した** — 採番の同期調停で担当がブロックし、中央は 2 回セッション交代した
- **搬送段が断絶した(G-5)** — 中央が repo を見られないまま「反映済」と宣言し、独立監査が 2 度走った
- **番号払い出しとゲートを混同した(G-8)** — 番号だけ渡した結果、通知書なしで製造が完了した

処方箋は**親チャット方式**(`docs/process/parallel-ops.html`)。芯は **熟考と結論の分離** — 探索の往復は使い捨てチャットに閉じ込め、親は蒸留された結論だけを読む。状態は repo のボードに置き、**親をいつでも使い捨てにできる**ようにする。

### 投入手順

1. **`git status` をクリアにして push** し、Web 版プロジェクトの GitHub ナレッジで **Sync now** を実行する(直読の鮮度 = push + Sync 時点)。
2. **§2「最初のプロンプト」1 本を Web チャットに貼る**。
3. **§1 Ⅱ の 11 件だけ**を直読で確認させる(恒久資料は §1 Ⅰ のとおり**ナレッジ常設なので渡さない**)。読めないパスがあれば Sync 漏れ・push 漏れ・ナレッジのファイル選択漏れを疑う(添付は直読が使えないときのフォールバック)。
4. **投入前にナレッジ側を 1 点確認**: 派生資料 3 件(code-facts・docs-map・retrospective-digest)を再生成 → push → **Sync now** したか。※ §1 Ⅰ の常設資料は登録済み(**SUPP-001 を含め 2026-07-30 に確認**)。

> **★投入前の前提は解消済み**: `docs/handover/M19-DESIGN-07-frame-cost-model.md` v1.0.4(M19-04 の設計正本)は **2026-07-30 に配置済み**です。実体は `M19-DESIGN-06-frame-cost-model.md` として追跡されており、**二重発番の解消(06 → 07)が文書内部の番号にだけ適用されファイル名に適用されていなかった**ための参照切れでした。リネーム済みなので**そのまま直読できます**。

## 1. 資料の渡し方(ナレッジ常設 + セッション固有の直読)

> **★2026-07-30 切替**: 恒久資料は **Web 版 Projects の GitHub ナレッジに常設**し、**毎回渡すのをやめた**。キットが列挙するのは「**ナレッジに任せてよいもの**」と「**任せてはいけないもの**」の線引きであって、投入ファイル一覧ではない。
>
> **線引きの根拠(`parallel-ops` §10)**: プロジェクトナレッジは**検索ベース取得**で、**全ファイルが常時コンテキストに載るわけではない**。そして**検索は取りこぼす**(実例＝類似名の既存機能に意味検索が吸われ、目的ファイルの本文を 3 回クエリを変えても引けなかった)。したがって:
>
> | 資料の性格 | 渡し方 |
> |---|---|
> | DES・overview 等の**バルク参照** | **ナレッジで可** |
> | **ロック・counter・状態**(ボード・契約・registry) | **検索に頼らない。明示パスで読ませる** |
>
> **RULE: ロックや counter を検索取得に委ねない。** 起動プロンプトに要点(次 CHANGE 091 / 次マイグレ 000043 / 現行版)を載せてあるので、**ナレッジの同期が多少古くても成立する**設計になっている。
>
> **鮮度**: ナレッジも直読も「**最終 push + Sync now 時点**」。**Sync を忘れると両方が古くなる**。

【本セッションの構成 = 親チャット方式(★従来と変わった点)】これまで M18/M19 は「中央(採番と DES 反映)+ M18 指示書担当 + M19 指示書担当」の 3 チャット並列で進めていましたが、うまく機能しませんでした。実際に壊れたのは次の 4 点です。(1) チャット間通信が全部私(開発者)の手を通る人手リレーになり、私がメッセージバスと化した。(2) 中央が採番の同期調停者すなわち人力ロックサーバーになり、各担当が中央の応答待ちでブロックし、中央はコンテキストを浪費して 2 回セッション交代した。(3) 中央はリポジトリを直接見られないまま「反映済」と宣言でき、実際の disk は古いままだったため、担当が「系統的な搬送停止」と報告して独立監査が 2 度走った。(4) 番号だけ払い出したことが担当側では「着手前ゲートを通った」と等価に受け取られ、通知書が欠けたまま製造が完了した。

そこで本セッションから親チャット方式へ移行します。芯は「熟考と結論の分離」です。設計判断で消費されるコンテキストの大半は探索・往復・却下された案であり、確定事項ではありません。それを使い捨てのチャットに閉じ込め、親は蒸留された結論だけを読みます。層は 4 つです。

- 親チャット(あなた・Claude Web・複数マイルストーン同時): 設計権限を持つ唯一の層。契約の発行・指示書作成・逸脱の裁定・ボードファイルの維持を担う。
- 個別設計チャット(Claude Web・使い捨て): 設計変更権限を一切持たない。検討の往復を閉じ込め、最後にレポート 1 本を出す。長い検討が要るサブはここへ外注する。
- 製造担当(Claude Code): 実装。完了報告は repo へ置き、例外だけを設計伝達レポートで親へ返す。
- 反映係(Claude Code・必要時起動): 文書パッチの適用・registry 更新・retrospective 反映。常駐しない。

この構成には守ってほしいルールが 5 つあります。

第一に、「中央」という語を使わないでください。並列期の「中央」は 2 つの別の職務(設計を決める権限と、repo へ書く権限)を兼ねており、統合後は前者が「親チャット」・後者が「反映係」に分離されます。1 つの語が 2 つの層を指すと必ず取り違えるため、以後この語は使いません。

第二に、あなたは実装レポートと progress ログを読みません。ボードファイル(docs/process/parallel-board.md)だけを見てください。読み始めた瞬間、熟考を外出しした意味が消えます。progress ログは私に要求しないでください。あなたへの入力は、ボードと設計伝達レポート(製造が返す「例外だけ」のレポート)です。

第三に、あなたは設計書を直接編集しません。改訂は「どの文書のどの節を、どう変えるか」のパッチとして発行し、反映係(Claude Code)に適用させてください。これはあなたの再起動回数を減らすためです。ボード(docs/process/parallel-board.md)への追記だけは例外で、反映係を起こしません——裁定が出たら §3 へ追記する 1 行を、指示書の誤りを見つけたら §6 へ追記する 1 行を、そのまま応答内に出力してください。私がそれを commit します。都度でもセッション終了時にまとめてでも構いません。反映係を毎回起こすと摩擦で追記されなくなり、かといって溜め込むとボードが陳腐化して「親をいつでも捨てられる」という本方式の中核が弱まるためです。

第四に、これが本移行の最大のリスクなのですが、実装前に DES を書かないでください。これまで「DES 本体の反映は実装完了後」という規律(M17-D10)が守られていたのは、規律ではなく物理的制約でした。指示書担当は DES を編集できず、中央は実装を見ていない、という分業が「想定で正典を書く」ことを構造的に防いでいました。統合するとこの制約が消え、設計しながら DES に手を伸ばせてしまいます。したがって明示的な規律として、(a) CHANGE の着手前ゲートは「通知書 + registry」までとし、通知書には反映案を書くが DES 本体は 1 文字も触らない、(b) DES 本体を改訂してよいのは実装が完了し as-built が確定してからのみで change-report と同時に行う、(c)「実装はこうなるはず」で DES を書かない、(d) as-built が指示書と違ったら DES は as-built に合わせる(指示書に合わせない)、そのうえで指示書の誤りをボード §6 に記録する、を守ってください。実際に、M18-03b の「materialize は基底コンボの採用を解除する」は指示書に無かった挙動で、実装側が正しかった事例です。判断に迷ったら「これは実測で確かめたか、それとも自分がそう思っただけか」を自問してください。本プロジェクトが最も警戒するアンチパターンは、実態を確認せず想定で進めることです。

第五に、採番についてです。CHANGE 番号は M18/M19 の間は従来どおり change-number-registry で採番してください(ブロック事前割当は M20 から)。次は 091 です。マイグレ連番は予約帯を作らず、着手時に実査して 1 個ずつ払い出してください。次は 000043 です。ただしあなたはリポジトリを直接見られないので、マイグレの disk 末尾確認は製造側の Plan Mode(ls migrations/)に委ね、不一致なら製造が自採番せず再請求する運用にしてください。指示書番号(M19-NN 等)はマイルストーンローカルで、採番の一元管理対象外です。

## 3. 補足(対話の進め方)

### 3.1 親のフロー

1. §2 プロンプト投入 → 親の読み込み・受領確認 → 着手前の確認事項提示。
2. **CHANGE-090 → CHANGE-087 の順に 1 本ずつ直列で三点セット確定**(同じ DES-003 / DES-005 を両方が触るため。順序は親が提案し開発者が承認)。親は**パッチを発行**し、開発者が Claude Code(反映係)に適用させる。
3. followup 棚卸し → **教訓の昇格判断**(親)。**retrospective への機械的マージと digest 再蒸留は反映係**(下記 §3.2)。
4. M19-04 の承認前提(契約 §2 の F-1〜F-4)を再確認 → 番号払い出し(CHANGE-091 / マイグレ 000043〜) → 指示書化 → 製造。
5. **裁定が出るたびにボード §3 へ 1 行追記**。指示書の誤りが見つかったらボード §6 へ 1 行追記。
   - **追記の経路(★明示)**: **親は追記する 1 行を応答内に出力し、開発者がそのまま commit する。反映係は起こさない。** 都度でもセッション終了時にまとめてでも可。
   - 理由: 反映係を毎回起こすと摩擦が増えて追記されなくなり、かといって溜め込むとボードが陳腐化して「**親をいつでも捨てられる**」という本方式の中核性質が弱まる。1 行の出力なら親のコンテキストをほぼ消費せず、開発者の手も 1 コミットで済む。

### 3.2 反映係(Claude Code)の起動

親が出したパッチを repo へ適用するときに起動する。**常駐しない。** 適用後は必ず `git status` / `git diff` で**disk への着地を確認**してから registry を「反映済」にする(G-5 / E-33 の再発防止 — 「反映した」は disk 着地まで完了ではない)。

**★retrospective のマージと digest 再蒸留は反映係の作業**(`parallel-ops` §09「親は読まない。反映係がバッチで retrospective へ」)。親のタスク 5 は昇格の判断のみで、実際の書き込みはここで行う。

- **順序を厳守**: **マージ → 再蒸留**。マージ後に `/retrospective-digest-update` を回す。
- **対象**: **G-8**(番号の払い出しと着手前ゲートの完了は別イベント)・**G-9**(中央帰属資料への「起票済み」は担当側の文書に書いても成立しない)・**台帳 §1.10 の未採番 5 件**(撤回した定義は否定形確認へ登録する / 「当然そうなる」と感じた挙動こそ指示書の処理順に書く / 共有コンポーネントへの追加はレイアウトの容量も突合対象 / 実測が出るまで規則を確定させない運用が「決める必要がなかった」という結論を生んだ / 分割軸の例外は破る側が自己申告して補償の回帰ゲートを張る)・`docs/handover/M19-lessons-retrospective-merge.md` の **M19-E01〜E14**。
- **★G-1〜G-7 は 2026-07-26 に E-29〜E-35 として既にマージ済み。二重マージしないこと。**
- **採番**: `retrospective-log.md` は §6.6.14 まで記録済みで最大 ID は **E-35**。新規は **E-36 以降**。M19-E01〜E14 の ID は暫定なので、衝突は取り込み側で調整する。
- 区分の正本はボード §7。手順書は `tmp/retrospective-merge-patch.md` v1.0.0。

### 3.3 個別設計チャットへの外注

長い検討が要るサブが出たら外注する。起動プロンプトには **① 凍結事項とスコープ ② 設計変更権限を持たないことの明示 ③ 読むべき文書名の明示** を必ず入れる。レポート様式は固定(目的 / 読んだ資料 / 検討した選択肢と却下理由 / 確定事項 / 開発者判断が要る未決 / **DES 差分案** / 指示書に入れるべき制約 / 教訓)。**DES 差分案まで書かせるのが親の負担をゼロに近づける鍵。**

### 3.4 予行演習としての観察

M18/M19 は新方式の予行演習で、本番は M20∥M21 の 2 レーンである。**うまくいかなかった点をボード §8.3 へ 1 行ずつ残す** — 親が結局読まされてしまったもの / レポート様式で足りなかった節 / リレーが最初と最後だけに収まらなかったケース / ボードだけで親が再起動できたか。
