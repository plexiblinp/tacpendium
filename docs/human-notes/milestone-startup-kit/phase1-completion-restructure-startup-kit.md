## 3. 補足(進め方の標準フロー)

整理工程の標準的な進め方(`docs/handover/cleanup-assistant-prompt.md` の Stage 思想を踏襲しつつ、本工程の
対象作業・Web 実施に合わせたもの)。

1. **スコープ確認**: handover 第2層カタログ + cleanup-report §5 routing 表で、本工程の対象(スケジュール再設定 +
   番号再設定)と完了済み/別オーナー項目(G-1 開発者責任 / G-2 開発者管理 / G-3 `/update_progress_summary` 委譲)を
   切り分けて開発者に確認。
2. **編集境界の確認**: CLAUDE.md(§8 設計書本体は設計担当が CHANGE で改訂 / §10 禁止事項)を踏まえ、改訂対象が
   「設計書本体(CHANGE 対象)」か「補足資料(自由改訂)」かを早めに切り分ける。
3. **Part A(決定)**: フェーズ新番号スキーム案 + スケジュール再設定案を作成。開発者要望ノート(全面公開)と
   handover の `[意図送り]` / `[流れN]` タグ・持ち越し課題を突き合わせて優先順位を立て、開発者と確定。
4. **参照洗い出し**: 確定スキームに対し、フェーズ参照(`フェーズ2`/`フェーズ3`/`phase2`/`phase3` 等)の箇所を
   投入資料から網羅的に洗い出す。**設計書本体(REQ/DES)= CHANGE 通知書 + 該当箇所改訂** と
   **補足資料 = 自由改訂** に仕分け。
5. **Part B(改訂)**: 設計書本体は CHANGE 通知書(020〜)起票 + 該当箇所改訂、補足資料(handover /
   retrospective-log / architecture-patterns / SUPP-001 / playbook / progress 系)は自由改訂で、渡された資料を改訂する。
   開発者がその改訂結果を受け取ってコミットする。
6. **検証**: 改訂の網羅性(漏れ・新旧の齟齬がないか)を自己点検し、改訂したファイルと変更点を一覧で開発者へ提示。
   設計書本体に及ぶ変更は CHANGE 通知書とセットで提示する。
