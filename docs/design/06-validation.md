## 1. 方針

### 1.1 基本原則

- **バリデーションは非ブロッキング**：警告であり、入力・登録を阻害しない（FR305）
- **例外はブロッキング**：重複コンボの登録、致命的なデータ不整合、**★★本登録コンボの必須項目の未入力**（**2026-09-05・`CHANGE-153`・`M27-02b`**。`VAL-C15`。**★★★2 欄＝ダメージ ／ 有利フレーム**〔**`CHANGE-216`・`M38-01`・2026-09-18 で 4 欄 → 2 欄。★以下は失効した記述：** 4 欄＝ダメージ ／ 有利フレーム ／ ドライブゲージ消費 ／ SAゲージ消費〕）**のみ登録を阻害する。★`FR305` 本文にも 3 つ目の例外として明記した。★仮登録には掛からない**（下の「仮登録は緩和」のとおり）
- **仮登録は緩和**：`is_draft = true` のコンボには多くのバリデーションを適用しない
- **責任分担の明確化**：SQLite CHECK制約は使わず、バックエンド（サービス層）が主たるバリデーション責任者。フロントエンドは入力UIの固定選択式・範囲制限で第一防衛線を担う
- **コンボの成立可否は判定しない**：技のつながり（連続ヒットするか）はアプリの判定対象外（FR306）
- **ダメージ自動計算によるレシピのダメージ量のバリデーションは行わない**：補正の端数処理が非公開、空振り技・多段技の扱いなどで正確な計算が原理的に困難（FR307）

### 1.2 バリデーション結果の種類

| 種類 | 挙動 | 用途 |
|------|------|------|
| WARNING | 保存処理続行、UI上に警告表示 | 参考情報の提示、軽微な不整合 |
| ERROR | 保存処理中止、UI上にエラー表示 | データ破壊や重大な矛盾を含むケース |

WARNINGはFR305の「参考値」に相当する。ERRORは重複コンボなど例外的な場合のみ。上記2種類のいずれにも該当しない場合（問題なし）は、特別な表示は行わない。

### 2.3 重複判定のロジック

VAL-C02 の「同一コンボ」判定は以下の条件すべてを満たす場合とする。重複の場合は **ERROR** として登録を中止する。

- `character_id` が同じ
- `starter_move_id` が同じ
- レシピ（`combo_steps` のシーケンス）が同じ（move_id列とmodifiers列の順序込み完全一致）
- 状況の主要項目（`position`, `opponent_stance`, `hit_type`, `opponent_size`）が同じ
- **★★`starter_meaty` が同じ**（**`CHANGE-208`・`M37-07`・2026-09-14**）
  - **★★★本列は `NOT NULL` であり、他の 5 列のような「NULL 同士は一致」の扱いを持たない。⇒ 判定 SQL の述語は常に `starter_meaty = ?` である。**
  - **★`VAL-C14` / `VAL-S07` / `VAL-R03` / `VAL-R04` の判定内容は変わっていない。⇒ 本列はキーの器**〔`duplicateKeyPredicates`〕**を共有しているため 4 件へ自動的に及ぶ。**

**【2026-07-26 追記・実装詳細の明文化】**（M18-RESEARCH-02 実測。矛盾の是正ではなく、設計書側が未言及だった挙動の正典化）

- **【2026-07-27・CHANGE-089】FR301 の適用面に materialize が加わった。** 確定反撃版の生成前に「**同一レシピ ＋ `hit_type` = `punish_counter`**」の既存コンボを探索し、**あれば生成せず既存の id を返す**（エラーにしない）。**materialize はレシピを編集できない**ため（CHANGE-089 §3.1 のスコープ境界）、**生成物のレシピは常に基底と同一＝`recipe_hash` の一致が構造的に保証される**。
- **【判定の穴・明文化】dup 判定 SQL は `is_draft = 0` と `deleted_at IS NULL` を固定条件に含む。** したがって**既存の確定反撃版が仮登録（下書き）またはゴミ箱にある場合は検出されず、二重生成される**。**これは materialize 固有の欠陥ではなく、既存の全登録経路と一貫した挙動**である（仮登録・削除済みを重複判定の対象にしない、という既存方針の帰結）。
- **NULL 同士は「一致」として扱う**。実装は判定 SQL の WHERE に `col IS NULL` を一貫して足す解釈で、`position` などが未設定のコンボ同士も**同じ状況として重複判定される**。
- **「順序込み完全一致」は `Modifiers.Flags` 配列の内部順序を含まない**。`Flags` は比較前に `sort.Strings` で正規化されるため、**同じフラグ集合であれば並び順が違っても同一**と判定される。順序が意味を持つのは **`combo_steps` のシーケンス**であって、1 ステップ内のフラグ集合ではない。

仮登録と本登録の間では重複判定は行わない（仮登録は試案のため、本登録と被っても問題ない）。

**編集による再登録時の扱い**：本登録済みコンボの編集保存は「旧コンボを論理削除し新コンボを登録する」方式（FR004参照）のため、同一内容の新コンボが一時的に重複しないようトランザクション内で論理削除→新規登録の順に実行する。論理削除済みレコードは重複判定の対象外とする（`deleted_at IS NULL` のレコードのみを対象）。

エラー時には「重複している既存コンボへのリンク」をUIに表示し、ユーザーが既存コンボを編集する選択肢を提示する。

**★★`deleted_at IS NULL` を外してはならない**（**CHANGE-125**・**M23-05**・2026-08-23 明記）。

**上の「編集による再登録時の扱い」が、この述語が在る理由そのものである。** **`PUT`（識別キーを変える編集）は同一トランザクション内で「旧行を論理削除 → 新行を登録」の順に実行する。** **⇒ 述語を外すと、`PUT` が自分の消した旧行に衝突し、あらゆる編集が重複エラーで落ちる。**

**★「削除済み行が重複判定の外に居る」ことは穴ではなく、`PUT` を成立させるための条件である。** **⇒ 気づいた担当が「穴だから塞ごう」と `VAL-C02` を触らないこと。**

### 2.4 キャラ固有状態（custom_states）入力に対する検証 — 行わない（CHANGE-040／M11）

- **コンボ重複時の選択肢＝2 択**：**「スキップ（skip・既定）」／「セットプレイのみ取込（setups_only）」**。**旧「新規追加（add）」は廃止**（dup キー〔VAL-C02〕が同一のまま挿入するため**必ず再衝突＝選択肢として成立しない**）。ワイヤ値は `"skip" | "setups_only"`（**廃止した `"add"` を含む未知値は既定 `skip` へ倒す**＝後方互換・安全側）。
- **「セットプレイのみ取込（setups_only）」の意味**：重複した**コンボは skip** し、その配下 setups の `parent_combo_local_id` を**既存コンボ（重複相手の実 id）へ解決して取り込む**（同一コンボへセットプレイだけ足す実ユースケース）。
- **setups の重複判定＝レシピ一致で skip（名前非依存）**〔**既存 VAL-S04〔§2.3・L109〕に整合**〕：VAL-S04 は「同一キャラの同じ親コンボに**同一レシピ**のセットプレイが既に紐付いていないか」を **ERROR** とする（**名前を見ない**）。したがって取込は、**レシピが一致する既存 setups があれば graceful skip**（＝ユーザーには「失敗」でなく「スキップ」と表示）する。**「同名＋同レシピ＝skip／別名＋同レシピ＝取込む／別名＋別レシピ＝取込む」という名前依存の 3 分岐は採らない**（**VAL-S04 が名前非依存のため「別名＋同レシピ＝取込む」は原理的に実現不能＝`CreateSetup` が VAL-S04 で失敗する**。旧 M17-05a 指示書 §5.1 の 3 ケースは VAL-S04 未確認の拡大解釈だった＝本改訂で補正）。
- **判定の実装境界**：setup ドメインの正規判定（VAL-S04）を尊重し、**combos の `recipe_hash` は流用しない**（意味の混線回避）。**graceful skip は「検証結果が VAL-S04 のみで構成される場合だけ」skip に翻訳**し、**他エラー併発時は failed 優先**（＝本当の不整合は隠さない）。
- **VAL エラーの表示＝FE 表示層で日本語化（register 分離・BE 不変）**：BE の `[VAL-CODE] column: message` 単一文字列を FE が parse し日本語へ写像（`comboImport.val.*`／`comboImport.col.*`・ja/en parity）。**未写像は英語原文フォールバック・VAL コード原文は折りたたみで保持**（サポート/レビュー用）。**重複警告（VAL-C02）は構造化フィールド `duplicateComboId` から「既存コンボ(ID N)と重複」と表示**し、**純内部コード VAL-C02 のみ折りたたむ**（**既存コンボの ID は表示に残す**＝どのコンボと衝突したか＝実用情報・`/combos/N` で実物確認可）。**BE の検証メッセージ本体は不変**（CHANGE-066 の register 分離）。
- **file レベル検証エラーは現状 日本語化しない**（BE が CSV 全体拒否時に `[VAL-CODE]` prefix なしの `Issue.Message` のみを返す＝register 分離のため code 非露出→FE 写像不能→英語原文のまま。**行レベル badge は完全に日本語化**）。**将来 file レベルも日本語化するなら、BE が FileError に code を含めて返す小改修〔DES-002 §4.2〕が要る**＝設計判断事項として保留。
- **「上書き（M13-i）」は本サブでも未実装＝繰越**。ただし選択肢を**配列/型 union の構造で予約**し、**UI には出さない**（要素追加だけで 3 択化できる形＝3 度目の改修回避。**未対応機能を利用者に予告しない**）。

**CSVファイル形式（コンボとセットプレイの分離）**：コンボとセットプレイは別々のCSVファイルとしてインポート/エクスポートする。理由は、形式が単純で利用者が理解しやすいこと、ファイル単位での部分インポートが自然にできること、エクスポート時にも対称的に出力できること。

紐付け方式：
- コンボCSVには各行にローカル一時ID（例：`local_id` 列）を持たせる
- セットプレイCSVには `parent_combo_local_id` 列を持たせ、コンボCSVのlocal_idを参照する
- インポート時は両ファイルを同時にアップロードし、コンボを先にインポートして本IDを発行、その後セットプレイをインポートして紐付けを確立する
- セットプレイのみのインポート（既存コンボへの紐付け）も可能とする。この場合は `parent_combo_local_id` の代わりに既存コンボの実IDを指定する

## 11. エラー・警告の表示方針

### 11.1 WARNING

- 入力フォーム下部に警告リストとして表示
- 各警告はアイコン付きで視認性を確保
- 警告があっても保存ボタンは押せる
- 保存時にサーバーから返された警告は、保存完了トーストと一緒に画面に表示

### 11.1.1 ★★「警告の表示」と「操作の分岐」は別である（CHANGE-141／M23-09）

**§11.1 は「警告をどう表示するか」の規定であって、「WARNING はモーダルにしてはならない」という規定ではない。**

| 種別 | 形 |
|---|---|
| **警告の表示** | **利用者は読むだけで、そのまま進める。** ⇒ §11.1 のとおり、フォーム下部の警告リストか、保存完了トーストと一緒に出す |
| **★操作の分岐** | **選ばないと次へ進めない。** ⇒ **モーダルが正しい** |

**★先例＝`VAL-N02`**（§7）。**severity は WARNING だが、利用者に選ばせるためモーダルで出している。**

**★★書かずに済ませないこと。** **書かないと、次の担当が「WARNING なのにモーダルだ」を欠陥として起票する。** **実際、`M23-05` の指示書は §11.1 を根拠に「モーダルにしない」と指示していた**——**そのときは正しかった**〔当該の警告は読むだけのものだった〕**が、根拠として §11.1 を引いた形が残ると、次に「選ばせる」warning が出たときに同じ引き方をされる。**

**★判定の順序**——**severity を見る前に「利用者は選ばないと進めないか」を見る。** **進めるなら §11.1、進めないならモーダル。**

### 11.2 ERROR

- 保存実行時にモーダルダイアログで表示
- 原因と対処方法を併記
- 重複エラー（VAL-C02）の場合は、重複している既存コンボへのリンクを表示

**★版不一致（409 ＋ `version_conflict`）の扱い**（**CHANGE-115・M22-04・2026-08-16**）——**上記 3 点だけでは足りない。** **版不一致は他の ERROR と性質が違う。**

| # | 版不一致が他の ERROR と違う点 |
|---|---|
| 1 | **★利用者の手元に「まだ保存されていない作業」がある。** 値の範囲・必須未入力なら直せばその場で保存できるが、**版不一致は直しようがない**——**相手が変えたのであって、自分の入力が間違っているわけではない** |
| 2 | **★「失敗」ではなく「防いだ」である**（`FR501`）。**⇒ 他の ERROR と同じ見せ方をすると、利用者は自分が何か間違えたと思う** |

**⇒ 版不一致では次を守る。**

1. **★入力を保持したまま表示する。自動で読み込み直さない。**
2. **★進む道を示す**——**相手の現在の内容を見る ／ 読み込み直す**（画面ごとの詳細は `DES-005` §5.7・§5.9）。
3. **★読み込み直すと自分の編集が消えることを、押す前に伝える。**
4. **★「防いだこと」が伝わる文言にする。** **「エラー」「失敗」と書かない。**

**★409 は 2 種類ある。見分けはエラーコードで行い、ステータスでは行わない。**

| 由来 | コード |
|---|---|
| **版不一致** | **`version_conflict`**（資源によらず 1 つ。`DES-002` §4.2） |
| **一意制約違反** | **それ以外。実測で 10 種**——`duplicate_setup` ／ `alias_conflict` ／ `preset_name_duplicate` ／ `preset_limit_exceeded` ／ `preset_in_use_by_config` ／ `tag_name_duplicate` ／ `tag_in_use` ／ `user_name_duplicate` ／ `combo_not_in_trash` ／ `rush_variant_exists` |

**★ステータスだけで判定すると、プリセット別名やセットプレイの重複が「ほかの人が変更しました」と表示される。** **⇒ 2026-08-16 まで `duplicate_setup` で実際にそうなっていた。**

**★重複エラー（`VAL-C02`）は 409 ではない。** **`POST /api/combos` の重複は 400 `validation_failed` であり、`details.validations` に載る。** **⇒ 「重複＝409」と読んでステータスで分岐しないこと。**

**★上記の「重複している既存コンボへのリンク」は、`POST /api/combos` の経路では未実装である**（2026-08-16 実測。`DuplicateWarning` は文言と「閉じる」だけを持つ）。**⇒ 実装するまでは、重複で弾かれた利用者の脱出路は「キー項目を変えて再度登録する」「一覧へ戻る」の 2 つである。**

**★ERROR をモーダルで出すのは原則であって、例外を許す。** **利用者が同じ画面で直せる ERROR は、モーダルで作業を遮るより該当欄の近く（インライン）に出す方がよい**（例＝セットプレイの同一レシピ重複）。**★版不一致がモーダルなのは「直しようがない」からであり、同じ線引きである。**

### 11.3 文面の多言語対応

エラー・警告メッセージは翻訳キー経由で管理し、日本語・英語の両方を提供する（NFR307、react-i18next）。

**★★複数の警告を連結するときは、区切りと終端も翻訳キーで持つこと**（**CHANGE-127**・**M23-06**・2026-08-23）。

- **★個々の文面に句点を持たせない。** **持たせると 2 件同時に発火したとき「A。 / B。」になり、連結が読めなくなる。**
- **★区切り（`" / "` 等）と終端（`"。"` / `"."`）を翻訳キーにする。** **★直書きの「。」を使わない**——**英語側が壊れる。**

**★★2026-08-23 時点で作法は割れている**——**復元経路の警告は翻訳キー経由だが、登録経路の警告は区切りが直書きで終端句点も付かない。** **同じ「警告の連結」が 2 か所で違う形になっている**（`E-76`）。**followup `save-warning-concat-style-drift`。**

## 12. 実装時に決定する項目

- 各WARNING/ERRORの具体的なメッセージ文言（日本語・英語）
- ~~起き攻めBOOLEAN整合性（VAL-C11）の具体ルール（対となるカラムの組み合わせ）~~ → **確定済み（CHANGE-063／M16-03）**：`combo_oki_options` の全 attack_type へ一様適用（uniform）＝同 attack_type・同 tech_type で `uses_dr=true` の行があるのに `uses_dr=false` の行が無い場合に WARNING（VAL-C11 本文参照）。

これらはユーザーの使用感や実データを見ながら調整が必要な値のため、実装時に開発者とClaude Codeが協同で決定する（DES-003 6.1節の協同方針参照）。

## 13. ゴミ箱からの復元時のバリデーション（CHANGE-124／M23-04）

### 13.1 位置づけ——**★本節は §1.1「例外はブロッキング」に対する明示的な例外である**

**復元経路では、種類が ERROR の検証結果であっても復元を中止しない。** **警告として応答に載せ、復元そのものは成功させる。**

| 検証の種類 | 通常の登録・更新経路 | **復元経路（本節）** |
|---|---|---|
| WARNING | 保存処理続行・警告表示 | **同じ。復元続行・警告を返す** |
| **ERROR** | **保存処理中止** | **★復元は続行する。警告として返す** |

**★根拠**——**落とすと利用者は取り返す手段を失い、ゴミ箱が安全網でなくなる**（**D-463**）。**ゴミ箱は「間違って消したものを戻す場所」であり、戻すこと自体を検証で妨げると存在意義が消える。**

**★この例外を本節に明記しているのは、後から不具合として「直されない」ためである。** **書かないと、次に本書を読んだ担当が「ERROR なのに止めていない」を欠陥と読む。**

**★ただし「復元そのものが成立しない」場合は従来どおり `404` である**（削除済みでない行への復元＝`DES-002` §4.2）。**これは検証ではなく前提条件であり、本節の対象ではない。**

### 13.2 復元経路で走らせる既存の検証（**新設ではない。適用先の追加である**）

| ID | 検証内容 | 種類 | 定義元 |
|----|----------|------|--------|
| VAL-C08 | レシピ中の各ステップの `move_id` が該当キャラに存在する技か | WARNING | §2.1 |
| VAL-S03 | セットプレイのレシピ中の `move_id` が該当キャラに存在する技か | WARNING | §3 |

**★この 2 件を走らせる理由は「削除中に技が消えた」を見るためではない**（技は消えない＝§13.4-2）。**「登録時から不整合だった行が、検証の緩かった経路（CSV 取込・API 直叩き）で入っていた」場合に気づくためである。** **走らせる費用はほぼ 0 であり、判定の母集団も変わらない。**

### 13.3 新設する検証

| ID | 検証内容 | 種類 | 適用経路 |
|----|----------|------|----------|
| **VAL-R01** | **復元するコンボが紐付けているセットプレイに、論理削除されたものが 1 件でも含まれる** | WARNING | `POST /api/combos/{id}/restore` |
| **VAL-R02** | **復元するセットプレイに親コンボが 1 件以上あり、かつそのすべてが論理削除されている** | WARNING | `POST /api/setups/{id}/restore` |
| **VAL-R03** | **復元するコンボと重複判定キーが一致する生きたコンボが在る**（CHANGE-125／M23-05） | WARNING | `POST /api/combos/{id}/restore` |
| **VAL-R04** | **復元するセットプレイと同じ親コンボに、同一レシピの生きたセットプレイが在る**（CHANGE-125／M23-05） | WARNING | `POST /api/setups/{id}/restore` |

**★★発火条件の非対称は意図的である。揃えてはならない。**

| ID | 発火条件 | 理由 |
|---|---|---|
| **VAL-R01** | **1 件でも含まれる** | **コンボ詳細のセットプレイ欄が、期待より少なく見えるため。** 1 件でも欠ければ利用者には「戻りきっていない」 |
| **VAL-R02** | **すべて削除済み** | **セットプレイは親コンボ経由でしか画面に出ない**（`VAL-S05`＝親に紐付かない単独作成は禁止）。**生きた親が 1 つでも残っていれば、そこから見える。** 0 個のときだけ「戻したのにどこにも出ない」になる |

**★★`VAL-R02` は、親が 1 件も無い場合には発火しない**（`M23-04` の as-built）。**親 0 件は「すべて削除済み」ではなく「紐付けが既に失われている」状態であり、別の事象である**（`M23-02` 適用前に論理削除されたセットプレイ）。**⇒ 空集合のときに真になる述語を書くと、該当する行が復元のたびに警告を浴びる。** **本書が発火条件を「親が 1 件以上あり、かつ」と書いているのはこのためである**——**「すべて削除済み」だけだと、空集合の扱いが読む人によって割れる。**

**★★`VAL-R03` / `VAL-R04` の母集団**（**CHANGE-125**・**M23-05**）。

- **生きた行だけを見る。復元しようとしている行自身は数えない**（**★復元は `deleted_at` を NULL にしてから検証するため、素直に書くと自分が自分の重複相手になる**）。
- **★★`VAL-R03` は `PUT` の旧行（`superseded_by_combo_id IS NOT NULL`）を除かない。** **`VAL-C14`（§2.1）が除くのと非対称であり、これは意図である。** **⇒ `VAL-R03` の母集団は生存行であり、そこに居る旧行は「隠されている旧行を API 直叩きで復元した」結果として画面に見えている生きたコンボである。** **除くと、見えている重複を黙って見逃す**（偽陰性）。
- **判定キーの定義は `VAL-C02` / `VAL-S04` と同じものを使う。別の定義を作らない**（**★2 つの「同じ」が並ぶと、片方だけ直されて静かにずれる**）。
- **`is_draft = 0` を保つ。仮登録を復元するときは実行しない**（§2.3 の末尾）。

**★`VAL-R04` の検出できない範囲は `VAL-S07` と同じである**（§3 の末尾の注記）。

### 13.4 ★★作らないと決めた検証（**4 件。「検討していない」ではない**）

**削除中に世界が変わる例は 4 つ挙がったが、そのいずれにも検証を設けない。理由がそれぞれ違う。**

| # | 変化 | 結論 | 理由 |
|---|---|---|---|
| **1** | **プリセット・エイリアスの変更で `recipe_cache` が現在の表記規則と食い違う** | **作らない** | **★既に解決している。** 復元は同一トランザクション内で `recipe_cache` を再計算する（`DES-002` §4.2 の副作用）。**⇒ 復元した時点で現在の表記規則に揃っており、食い違いは発生しない** |
| **2** | **技の改名・削除／キャラクターの変更** | **作らない** | **★起こりえない。** `moves` / `characters` はアプリの操作で消える経路を持たない（`M23-04` の実査＝削除経路 0 件）。公式データ取り込みはフェーズ2 の別ツールである（§9）。**⇒ 起こりえないことに検証を書かない** |
| **3** | **`superseded_by_combo_id` を持つ旧行の復元** | **作らない** | **★到達せず、不変条件も壊れない。** (a) 旧行はゴミ箱の一覧に出ず、一括復元でも選べない（`CHANGE-121`／`M23-01`） ／ (b) `PUT` は重複判定キーを変える操作であるため旧行と新行のキーは通常異なり、両方が生きていても重複にならない。**⇒ `DES-002` §4.2 が `M23-04` へ持ち越していた判断は、これをもって「検証を作らない」で決着した** |
| **4** | **タグの削除で紐付けが消えている** | **★作れない** | **`combo_tags` は `ON DELETE CASCADE` であり、タグを削除した時点で行が消えている。** **⇒ 復元の時点では「そこに何が紐付いていたか」の情報がどこにも残っておらず、検出のしようが無い。** 検出するには消える前の記録＝監査ログが要り、それは `FR013` により実装しないと決めている |

**★本表を残す目的は、次に同じ問いが来たときに調査をやり直させないことである。** **「検証が無い」と「検証を作らないと決めた」は、読む人にとってまったく違う情報である。**

### 13.5 応答と見せ方

- **警告は `200 OK` の応答本文の `warnings` フィールドに載せる**（§1.2 の WARNING の扱い ／ `DES-002` §4.2 の一般規定）。**★逐語の形と `details` の構造は `DES-002` §4.2 が正本である。**
- **★★登録 2 経路も同じ器に載る**（**CHANGE-125**・**M23-05**）——`POST /api/combos` の `201` 応答 ／ `POST /api/combos/{comboId}/setups` の `200` 応答。
- **★★登録応答では `validations` と `warnings` の両方に警告が載りうる**（**CHANGE-125** で新しく生まれた状態）。**`POST /api/combos` は `VAL-C03` / `VAL-C08` / `VAL-C10` / `VAL-C11`〔いずれも WARNING〕を従来どおり `validations` に載せたまま、`VAL-C14` を `warnings` に載せる。** **⇒ 同じ種別の警告が 2 経路に分かれている。** **★実害は無い**〔画面はそれぞれ別の表示経路を持つ〕**が、「登録応答の警告はどちらを見ればよいか」で迷わないよう明記する。** **復元応答に `validations` は載らない**（`DES-002` §4.2）。
- **警告が 0 件のときは `warnings` キー自体を出さない。** **★空配列を返さない**——返すと画面側が「警告があった」と誤って分岐する。
- **画面では、復元完了のトーストと一緒に表示する**（§11.1 の WARNING の見せ方）。**★モーダルにしない**（§11.2 は ERROR の見せ方であり、本節の警告は ERROR ではない）。
- **一括復元で複数件に警告が付いた場合は、件数を畳んで 1 枚にまとめる**（**★1 件ずつトーストを積み上げない**）。
- **文面は翻訳キー経由で管理する**（§11.3）。**★サーバは診断用の文言を併せて返すが、画面はそれを表示せず `code` から翻訳キーで組み立てる**（§6 の先例＝「VAL エラーは FE 表示層で日本語化」）。**サーバ側に文言を残しているのは、API を単体で叩いたときに何の警告か分かるようにするためである。**
