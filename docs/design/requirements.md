## 1. プロジェクト概要

### 1.1 目的

ストリートファイター6（以下SF6）のコンボを効率的に管理・比較・共有するためのWebアプリケーションを開発する。利用者が自分に最適なコンボ（マイコンボ）を整理し、スキル向上に合わせて段階的にコンボを発展させていくことを支援する。

### 1.2 背景

SF6ではコンボの組み合わせが膨大であるにもかかわらず、専用の管理ツールが存在しない。プレイヤーはメモ、ノート、Excelなどで個別に管理しており、以下の問題が発生している。

- **管理方法の分散**：人によって管理方法が異なり、他者との共有・統合が困難
- **表記の不統一**：ルートの記法が統一されておらず、共有時に誤解が生じる。同一人物のメモ内でさえ重複コンボが発生する
- **検証手段の欠如**：レシピとダメージの不一致を検出できない。特にトレーニングモードのカウンター設定ミス等により実際と異なるダメージを記録してしまい、コンボ比較が破壊される
- **入力の非効率**：手入力に依存しており、キーボードに不慣れなプレイヤーは誤入力や時間浪費が多い
- **比較の困難**：既存ツールでは必要な情報だけを抽出して横並び比較することが難しい

### 1.3 対象ユーザー

- SF6プレイヤー（初心者〜上級者）
- ITリテラシーが低い方、年配の方を含む
- 個人利用を基本とし、ローカルネットワーク内での少人数共有も想定

### 1.3.1 想定ユーザー規模とペルソナ

本アプリはSF6コミュニティへの配布を想定する。規模感は数百人〜数千人を仮置きとするが、コンボ管理専用アプリは既存に存在しないブルーオーシャン領域であり、実際の需要は未知数である。この前提に基づき、以下の設計方針を採用する。

- 認証は簡易維持、本格的なマルチテナント機能は不要
- i18nは日本語・英語のみ（NFR307に準拠）
- 配布はGitHub ReleasesのZIP配布で十分、インストーラ等は初期リリースでは不要
- パフォーマンスチューニングは個人〜少人数利用規模を前提とし、数万件レベルのコンボ同時管理は想定外

### 1.4 プロジェクトの特性

- 個人開発プロジェクト（OSSとしてGitHubに公開）
- Claude Codeを活用して開発
- 段階的に機能を拡充するフェーズ開発方式

### 2.2 アプリ固有用語

| 用語 | 定義 |
|------|------|
| マイコンボ | 利用者が自身のスキルレベルや運用方針に合わせて選定した、利用者にとっての現在の最適コンボ群。タグなどで管理する |
| 状況 | コンボが成立する前提条件の集合。画面位置、距離、カウンター種別、ゲージ残量、始動技、相手キャラ体格、相手の姿勢（立ち・しゃがみ）、体力残量、キャラ固有状態などを含む |

| エイリアス表示 | データベース上は統一表記で保存しつつ、画面表示ではユーザーの好みの表記で見せる仕組み |

### 2.3 概念定義

#### 2.3.1 「最大コンボ ≠ 最適コンボ」の概念

最大ダメージのコンボは、リソースの大量消費、高い入力難易度による失敗リスク、コンボ後のポジション不利（起き攻め不可）などのデメリットを伴うことがある。最適コンボはダメージだけでなく、ゲージ温存、起き攻めの獲得、安定性などを総合的に評価して選択される。一つの状況に対して、プレイヤーの目的（削り切る／ゲージを貯める／起き攻めをしたい）によって複数の最適解が存在し得る。

#### 2.3.2 「マイコンボ」の概念

初心者やキャラクター習熟度が低い段階では、複数コンボの使い分けが困難である。そのため利用者は以下のような作業を行う。

- 数を絞った簡単なコンボを選択する
- 途中まで似たルートでコンボを統一する

この結果できあがったものが「マイコンボ」であり、タグ等を用いて以下を管理する。

- 利用者にとっての現在の最適コンボ（実戦で使用中）
- 将来的に取り入れたい絶対的な意味での最適コンボ（練習中・目標）
- 最適コンボの一つだが利用率が減っているもの（非推奨・頻度低下）

| NFR203 | 複数名利用時に同時実行による問題（データ競合・消失）が起きないこと。実現方式として楽観的排他制御を採用（combosテーブルにversionカラムを保持し更新時にバージョン比較）、衝突時はユーザーにエラー表示し再読込を促す。SQLiteのWALモードを併用してDB レベルの同時書き込み問題を軽減する。LAN共有時の同時利用人数は数人程度を想定し悲観ロックは採用しない。 **【★★2026-08-28・CHANGE-136・M24-11】★楽観的排他制御は UPDATE を守る手であって INSERT を守らない**（比較すべき既存行が無いため）。 **⇒ 「検査してから書く」形**（重複判定・上限判定など）**は、検査と書き込みを同じ書き込みトランザクションの内側に置き、そのトランザクションを直列化することで守る**（`DES-002` §6.4）。 **★楽観的排他制御は撤回しない**——UPDATE を守る手として不変である（対象＝`combos` / `setups` の 2 表・粒度＝集約）。 **★「悲観ロックは採用しない」とも抵触しない**——**SQLite は WAL でも writer を元来 1 本に直列化しており、トランザクションの開き方を変えるのは新たな悲観ロックの導入ではなく、そのロックを取る時刻を早めることである。** |

## 6. データモデル方針

要件定義レベルでの方針を記載する。詳細は基本設計で決定する。

### 6.1 階層構造

本アプリのデータは以下の階層を意識して設計する。将来的な他ゲーム対応のために、ゲームをトップレベルの概念として保持する。

- ゲーム → キャラクター → 技データ → コンボ

### 6.2 コンボの構造

コンボは以下の情報を保持する。

- 所属キャラクター
- 状況（前提条件の集合）：画面位置、距離、カウンター種別、ゲージ残量、始動技、相手キャラ体格、相手の姿勢（立ち・しゃがみ）、体力残量、キャラ固有状態など
- レシピ：「ステップの列」として設計し、各ステップに技と修飾情報（ジャスト、ディレイ、微歩き等）を持つ
- ダメージ（手動入力値。将来的な自動計算の可能性を残しつつ、現時点では手動入力のみ）
- 相手へのドライブゲージ削り量
- コンボ後の状況（起き攻めの可否、画面端到達の有無、運び量など）
- タグ（マイコンボ管理用）
- メモ（自由入力欄）

### 6.3 技データの内部表現

- データベース上は表記ゆれのない統一された内部表現で保存する
- 表示時はエイリアスで利用者の好みの表記に変換する
- 数値化が困難な情報（画面端からの距離、運び距離など）は段階的ラベル（大／中／小 等）で扱う
- 技データはダメージ値および各種補正値（始動補正・コンボ補正・即時補正・乗算補正）を保持する。現時点ではコンボ自動計算には使用しないが、技一覧表示や将来のダメージ推定機能に備える

### 6.4 キャラ固有状態

AKIの毒状態などのキャラクター固有の特殊状態は「状況」の一部として扱う。

キャラ固有状態として扱うのは、**その状態によってコンボの成立・分岐が変わるもの**に限る。値が変わってもダメージしか変わらない状態は、キャラ固有状態として定義しない。

- **★マノンのメダルレベルは扱わない。** 付与数で変わるのはダメージだけであり、コンボの成立・分岐を変えないためである（2026-08-25 開発者判断・`CHANGE-131`）。**本節は第30版まで「マノンのメダルレベル、AKIの毒状態など」と名指ししていた。マノンの分は撤回する。**
- 実データ上の定義の正本は `characters.custom_states`（seed＝`migrations/`）であり、表現の形は `DES-003` §3.2 が定める。

### 6.5 セットプレイ連携

セットプレイを「始動状況」の一つとして位置づけ、そこからつながるコンボを紐づける。セットプレイ自体の登録機能は拡張フェーズで対応するが、データモデル上は関連を考慮する。

### 8.3 ドキュメント運用ルール

本プロジェクトでは要件定義書と設計書が相互に参照し合うため、更新時の整合性管理が重要となる。以下のルールを遵守する。

- 要件定義書（REQ-001）に変更を加えた場合、各設計書の「前提文書」セクションを最新バージョンに更新する
- 設計書相互で参照関係がある場合（例：画面設計書がデータモデル設計書を参照）、参照先が更新されたら参照元の「前提文書」も更新する
- 各ドキュメントのバージョンとステータス欄を更新し、変更履歴として残す
- 設計書に「この記述は要件定義書のFR〇〇に対応」といった参照を入れる場合、参照先のFR番号が変更されていないことを確認する

### 8.2 基本設計で決定すべき事項

- 技術スタック（フロントエンド、バックエンド、データベース）の選定
- 配布方式：シングルバイナリ配布（DES-001で確定済み）
- OSSライセンスの選定
- 仮想コントローラUIの詳細設計
- 内部表現（統一表記）の具体的な仕様
- エイリアス管理の仕組みの詳細
- 修飾情報（ジャスト、ディレイ等）のマスタ定義
- キャラ固有状態のデータスキーマ
- ダメージ計算ロジックの詳細（補正テーブルの構造含む）
- 状況を構成する要素のマスタ定義
- CSV形式の仕様
- ローカルネットワーク共有時のアーキテクチャ
- 同時実行制御の方式

## 10. 基本設計への橋渡し

本要件定義書の内容を受けて、基本設計では以下の順序で設計を進めることを推奨する。

1. **技術スタック選定**：要件（ローカル実行、前提ソフト不要、軽量、OSS）を満たす技術構成の決定
2. **データモデル設計**：6章の方針に基づく具体的なスキーマ設計（ゲーム→キャラ→技→コンボの階層、状況の定義、修飾情報の定義）
3. **内部表現仕様**：技の統一表記ルールとエイリアスの仕組みの確定
4. **画面設計**：主要画面（コンボ一覧、コンボ登録、比較表示、仮想コントローラ）のワイヤーフレーム
5. **バリデーション設計**：ダメージ計算ロジック、補正テーブル構造の設計
6. **アーキテクチャ設計**：フロントエンド/バックエンド構成、API設計、同時実行制御方式
