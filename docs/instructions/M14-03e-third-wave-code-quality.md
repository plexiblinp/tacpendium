## 1. 背景と目的

### 1.1 背景

**本サブは M14-03d（manon）の続き**であり、**手順はほぼ同一**（同じ seedgen・同じ変換規則・同じ検証）。違いは **対象キャラと、当たる品質問題の種類**である。

M14-RESEARCH-02〔T4/T5/F-13〕が報告した **combomgr-importer（FR701）側の `move_code` 品質問題**のうち、manon（アクセント）以外の 2 類型がこの 4 キャラに集中している:

| 類型 | 対象 | 実態（RESEARCH-02） |
|------|------|--------------------|
| **括弧の過長 code** | **m_bison / rashid / jamie**（＋manon） | 技名の括弧内が code に取り込まれ **40〜57 字**〔T4〕 |
| **公式英語名そのものの誤り** | **luke**（＋juri＝第一波で投入済み） | **公式サイトの英語名が誤っている**ため **code 衝突・base 不一致**〔T5/F-13〕 |

**marisa / jp は上記 2 類型のいずれにも該当しない。** したがって本波は「**類型あり 4 体 ＋ 類型なし 2 体**」の構成になり、**同じ観点で実測することで「品質問題は類型のあるキャラ固有か、全キャラ共通か」を切り分けられる**。量産波（M14-03f 以降）の前提を確定するうえで、**対照群があるほうが判定が強くなる**。

**重要な区別**（`M14-RESEARCH-02-findings-analysis.md` §1.3・開発者確認 2026-07-16）: これらは **importer CSV（公式変換）**の話であり、**配布 seed の源は手入力 CSV**（`move_code` は **input-tool の自前採番＋人手付与**）。**importer の壊れ code がそのまま seed に入るわけではない**。**実際に何が入っているかは各 CSV を見るまで分からない**。

## 4. 詳細仕様

### 4.1 6 キャラの seed

- **M14-03b の変換インフラ（seedgen）で** `character_data/{m_bison,rashid,jamie,luke,marisa,jp}.csv` → seed SQL を生成（**新規実装・コピー実装・手作業生成をしない**）。
- FK 依存順（**characters → moves → preset_aliases**）。**alias（`official_ja_move`）は対で投入**。**`characters` 行・移動 system move 9 種が未投入なら、先行する前提マイグレで投入する**（§3.3-10／§3.3-11）。
- **`recovery` は単一整数**・材料が欠ければ `total` は NULL。**`is_derived`・`target_combo` は passthrough**。**移動 9 種は drop**（seedgen 経路では入れない＝前提マイグレ側で投入する）。

> **【既知の誤り・直さないこと】生成マイグレのヘッダコメントは「移動 system move 9 種は drop 済（投入元は 000025）」と出力するが、本波の実際の投入元は本サブで作成する前提マイグレである。** 文字列は `internal/seedgen/generate.go` の `CustomHeader` にハードコードされており、**直すと変換規則の改変になり golden 4 stem が byte 単位で全部変わる**（M14-03c §4.3.1 の 3 条件違反）。**直さないこと**（followup `seedgen-header-provenance`）。**ヘッダの投入元表記を信じないこと。**

### 4.2 `move_code` の扱い（**是正しない・報告する**）

- **正準形検証のみ**（`^[a-z0-9_]+$`・DES-004 §2.1）。**再採番・自動リネーム・自動修正を一切しない**（CSV が正）。
- **過長 code は「正準形としては合法」**（`^[a-z0-9_]+$` は長さを制約しない）＝**機械的には落ちない**。**実測して報告**し、**判断は開発者に委ねる**（§4.3）。**製造が短縮しない**。
- **正準形に反する code があれば生成を止めて報告**（推測で直さない）。

### 4.3 【本サブの核】実測と判定

**完了報告に次の 3 点を必ず含める**:

1. **実測表**（§3.3-3 の (a)〜(e)）を**キャラ別**に出す（**6 キャラ**）: 件数＋実例（`move_code` と `name_ja` の対）＋**最長 code の字数**。**判定は「類型あり 4 体」と「類型なし 2 体（marisa / jp）」を切り分けて書くこと**——**類型に該当しない 2 体でも同じ問題が出たなら、量産波では全キャラで本観点を見る。出なければ、類型のあるキャラに限って見る。**
2. **判定**: 次を**根拠付きで明示**する。
   - **過長 code は実害があるか**（**DB・API・CSV・UI のどこかで問題になるか**を実コードで確認して答える。例: `move_code` に長さ制約が無いか〔code-facts §10 の DDL〕・CSV 往復に影響しないか・画面18 やレシピ表示でレイアウトが壊れないか）。⇒ **実害がなければ「許容」と明示**して以降の波で気にしない。**実害があれば「要対応」**として**どこで壊れるか**を具体的に報告する。
   - **公式英語名の誤り（luke）が seed に実害を出すか**（dup fail・base 不一致による alias 欠落等）。**juri（第一波・投入済み）で実害が出ていない**ことと**同じ結論になるか**。
3. **量産波（M14-03f 以降）への申し送り**: **残キャラで同じ問題が出る見込みと、その扱い**（「以降は品質問題なしで量産できる」or「この観点だけは毎回見る」）。**本波完了後の seed 済みは 17 / 30、残り 13 キャラ**（**c_viper / dhalsim を含み、この 2 体は UNIQUE 衝突で起動不能になる経路があるため必ず最終波**）。**配布 blocker は本波では解除されない。**

> **なぜ製造が判定するのか**: **実データと実コードを読まないと分からない**（spec からは演繹できない）。設計担当が spec から規則を提案して実データに否定された前例がある（2026-07-16・`lily/great_spin`）。**データに効く判断は、実データを見た側が根拠を出す**のが安い。

### 4.4 検証

> **`chain_cancel_total` の投入（§4.5）は本節の検証の対象外**である。件数の固定は §5 のテスト要件で行う。

- **dup スキャン**（M14-03b §4.6）を 6 キャラの新 moves に適用。**検出時は生成 fail＋一覧報告**。
- **clean マイグレ由来 DB から構築**（dev DB 残渣不可）。**dev DB は事前退避**。
- `make e2e` が新 seed 下で通過（**非回帰**）。**他キャラ非波及**（件数で確認）。

### 4.5 【条件付き】`chain_cancel_total` の投入

**実施条件**: **§3.3-13 の実査で `moves.chain_cancel_total` 列が存在する場合のみ実施する。** 存在しなければ**本節を飛ばし、対象行を完了報告の申し送りに記載する**（M19-04 の DDL 着地後に別途 backfill する）。

> **★列が無い状態で UPDATE を書いてはならない。** `no such column` でマイグレが失敗する。**「M19-04 が先に入っているはず」で書かないこと。**

## 9. 注意事項・判断に迷ったら

### 9.1 推測で進めてはいけない

- **マイグレ連番**（実査で確定）。

### 9.2 推測で進めてよい（明示のこと）

- マイグレの分割数（6 キャラを 1 本にまとめる／キャラ別に分ける。**消費した連番を完了報告に明記**）。

### 9.3 不明時

- **変換規則に触れたくなったら止める**（golden に差分が出たら止める）。
