| **3 spec に固定して flaky** | **恒久対策を入れる。** 案＝**待機のポーリング化**（推奨）／ タイムアウト延長（**★安易に採らない**。§4.1-1） |
| **落ちる spec が毎回違う** | **★★本項は「3 spec の問題」ではない。** **スイート全体の実行タイミングに起因する**（`m23-close-report` §7-1 の見立て）。**⇒ 3 spec を直しても解決しない。実測を報告し、恒久対策は入れずに終える** |
| **3 回とも 0 flaky** | **★実装しない。** **「現在は再現しない」ことを実測つきで報告し、`CO-025` を「既に解消（または再現不能）」として報告する** |

#### 4.1-1 ★タイムアウト延長を安易に採らないこと

**タイムアウトを伸ばすと、flaky は減るが「遅くなったこと」が見えなくなる。** **⇒ 本当に遅いのか、待ち方が悪いのかが以後わからなくなる。**

**★採るなら理由を書くこと**——「何を待っているのか」「その待ちが原理的に何 ms かかりうるのか」。**書けないなら、待機のポーリング化を採る。**

#### 4.1-2 ★flaky を「フレーク」で閉じないこと

**切り分けの最小手は「隔離実行」と「直列実行」の 2 手である**（教訓 `E-216`）。**`M23-05` の flaky 2 件は `--workers=1` で緑・既定の並列で 3 failed と、再現条件が判っている競合だった。**

**⇒ §3.3-2 の 3 回の実行に加えて、`--workers=1` を 1 回回すこと。** **結果が変わるなら、それは timing ではなく競合である。**

### 4.2 `CO-007`: `migrations/000012` の down が orphan を残すか——**★判定だけを行う**

**★★既存マイグレーションの本文を 1 バイトも編集しないこと**（§2.2）。

**成果物は判定である。** 完了報告に次の 3 点を書くこと。

1. **`000012` の up が何を作り、down が何を消すか**（DDL / DML の逐語）。
2. **down で消し残る行が構造上ありうるか。ありうるなら、どの表のどの条件の行か。**
3. **★言えないことは「言えない」と書くこと**——**実データを見ないと判定できない部分は、そう書く。** **★「実測で落ちなかった」を「落ちる経路が無い」と書かないこと**（教訓 `E-237`）。

**★rollback 方針まで決めない。** **判定が出てから設計卓が決める**（ドラフト §3 の gate＝「migration cleanup は orphan 判定と rollback 方針を先に確定する」の前半だけが本サブの範囲）。

**★あわせて `architecture-patterns` §11 を読むこと**——**FK=ON だけで回るテストは CASCADE → 明示削除の変更を 1 行も守らない**（教訓 `E-226`）。**down の判定でも同じ非対称が効く。**

### 4.3 `CO-006`: テストの inline INSERT のパターン化

**§3.3-3 で数えた全数を、共通の作り方へ寄せる。**

- **★既存ヘルパが在るなら新設しない**（§3.3-3）。**★「新規ファイルを作る」ときも作る前に同名の存在を確かめること**——**上書きはテストを緑のまま通し、消えたテストは走らないだけで lint も型検査も何も言わない**（教訓 `E-225`。`M23-08` が回帰テスト 3 本を一度消した実例）。
- **★寄せた結果、テストの主張が弱くならないこと。** **ヘルパが既定値を埋めると、その既定値に依存した主張が「たまたま通る」形になりうる**（教訓 `E-218` の変種）。**⇒ 寄せた後に、寄せる前と同じかそれ以上の主張を持つことを示すこと。**
- **★低優先である。** **§4.4 / §4.5 と時間が競合したら、本項を後回しにしてよい。** **その場合は「やらなかった」と理由を報告すること**（黙って落とさない）。

### 4.4 `CO-012`: config 系 BE の「TOML 全再エンコード ＋ アトミック書込」の重複

**§3.3-4 で重複の実体を確かめてから着手すること。**

- **★「重複しているから寄せる」と決めつけないこと。** **`M23-03` は `#6` を分割するのが正しかった**——**求めている集合が違えば、入口も別に要る**（教訓 `E-205` / `E-255`）。**⇒ 2 つが同じことをしているのか、似て見えるだけなのかを先に判定する。**
- **寄せる場合、層をまたがないこと。** `internal/api/config/` と `internal/service/config/` は別の層である。**★またぐ必要があると判明したら、止めて報告すること。**
- **★★後続で「コメント保全」を扱う可能性を考慮すること**（§11 確認事項 2）。**現在の方式は「TOML を全再エンコードする」であり、その性質上コメントが落ちる。** **⇒ コメントを保全するには、書き換えの方式そのものを差分書き換えへ変える必要がありうる。** **★本サブで統合した 1 本が「全再エンコードする実装」として固定されると、後でコメント保全をやるときに作り直しになる。** **⇒ 統合するとき「書き換えの方式」を差し替え可能な形にしておけるなら、そうすること。** **★無理に一般化しないこと**——**できない形なら、できないと報告すればよい**（後任がそれを読んで判断する）。
- **★アトミック書込の性質を落とさないこと。** **書込中に落ちても設定ファイルが壊れない、という性質が本項の守りたい不変条件である。** **⇒ 寄せた後に、その性質が保たれていることをテストで示すこと**（§5.1-3）。

### 4.5 `calc-recipe-hash-three-implementations`: `CalcRecipeHash` の 3 実装

- **★`CO-021` の spec 名は `m14-03b-custom-states-realdata.spec.ts` で、`CO-025` のクラスタにも `combo-custom-states` がある。** **似ているが同じファイルとは限らない**（§3.3-2 で確かめること）。**同じなら、そもそも `CO-021` と `CO-025` は 1 件である。**

**★暫定案**: **本サブでは「観測されたかどうかだけを実測して報告する」に留める。実装（恒久対策）は割り付けない。**

- **理由 1＝追加費用がほぼゼロである。** **本サブは §3.3-2 で `make e2e` を 4 回回す。** **落ちた spec 名を全部記録すれば、`CO-021` / `CO-022` の分もそのまま取れる。**
- **理由 2＝割付を設計卓が独断で広げることは禁止されている**（playbook §4.11 / §4.12）。**「同じ面だから」は広げてよい理由にならない。**
- **理由 3＝実測が出てから決めるほうが安い。** **「3 件とも落ちない」なら 3 件まとめて閉じられる。「全部落ちる」なら 1 本のサブで扱うべきだと分かる。** **⇒ いま割付を決めると、その判断材料が無いまま決めることになる。**

**★開発者に決めていただきたいのは 2 つ。** **(a) 実測だけを本サブに含めてよいか**〔暫定案〕。**(b) 「fe-e2e 安定化サブ」という存在しない割付先を、`M24-CLOSE` までにどう畳むか**〔`M24-overview` §2.3 の「割付先が消えている」表へ 2 件を足すのが素直〕。

**2. `e2e-suite-rewrites-config-toml-comments` を `CO-012` と一緒に見るか**

**★まず実体を並べる**（`followup-backlog` §K）。

| 項目 | 内容 |
|---|---|
| **症状** | **E2E スイートが `config.toml` のコメントを落とし `[defaults]` を追加する。** |
| **実害** | **値は保たれるため小さい。** **ただし `config.toml.example` から生成した直後にコメントが消えるので、利用者が設定の意味を読めなくなる。** |
| **関連** | **`config-toml-write-back-env-asymmetry` の残りにあたる**——**同項は「env 上書き中の項目を書き戻さない」ところまでを直したが、コメントの保全までは扱っていない。** |
| **面** | **`internal/api/config/`**——**`CO-012` とまったく同じ。** |
| **割付** | **未割付。** |

**★★なぜ一緒にしないのか（本質）**——**性質が違う。**

| | `CO-012` | コメント保全 |
|---|---|---|
| **やること** | **重複の解消** | **挙動の変更** |
| **利用者から見た変化** | **無し** | **有り**（コメントが残るようになる） |
| **失敗したときの見え方** | テストが赤くなる | **★設定ファイルが壊れうる** |

**⇒ 一緒にすると「挙動を変えないリファクタ」という本サブの性格が崩れる。** **★性格が崩れると、レビューの基準も崩れる**——**「挙動が変わっていないこと」を見るのか「変わった挙動が正しいこと」を見るのかが、1 つのサブの中で混ざる。**

**★★ただし順序の問題がある。これが本件で一番重要な点である。**

**現在の方式は「TOML を全再エンコードする」であり、その性質上コメントが落ちる。** **⇒ コメントを保全するには、書き換えの方式そのものを差分書き換えへ変える必要がありうる。**

**★`CO-012` が「全再エンコード」の重複を解消すると、その統合された 1 本が「コメントを落とす実装」として固定される。** **後でコメント保全をやるとき、統合した 1 本を作り直すことになる。**

**⇒ 本サブでは §4.4 に「書き換えの方式を差し替え可能な形にしておけるなら、そうすること。無理なら、できないと報告すること」を置いた。** **★無理に一般化させない**——**使われるかどうか分からない抽象を先に作るのは、それ自体が負債である。**

**★暫定案**: **本サブでは扱わない**（§1.3）。**ただし `CO-012` の実査（§3.3-4）でこの面を読むことになるため、「コメントが落ちる機序」が分かったら報告だけさせる。** **⇒ 次に扱う担当が実測をやり直さずに済む。**

**★開発者に決めていただきたいのは 2 つ。** **(a) 扱わない判断でよいか**〔暫定案〕。**(b) 扱うなら、どのサブへ割り付けるか**〔**★本サブへ足すのは推奨しない**——上の性格の話。**新サブを起こすならサブの新設は開発者の承認事項である**〕。
