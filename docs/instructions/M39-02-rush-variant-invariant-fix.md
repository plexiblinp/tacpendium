## 0. この指示書の特殊性

### 0.1 ★★★これは「実行時に不変条件を破る経路」である

**★`M39-01` が置いたガードは `TestRun_HEAD_*` 族であり、*新規 DB の最終状態*を見る。⇒ 利用者が操作して作った行は見ない。**

**★★★だからこの穴は、`M39-01` のガードが緑のまま素通りする。⇒ 「ガードが在るから大丈夫」は本サブには効かない。**

**★★是正が効いたことは、*API を叩いて*示すこと**（段 1 / 段 3）**。⇒ 新規 DB のテストだけでは示せない。**

### 0.2 ★★何が起きるか（**`M39-01` が段 1 で実測した**）

**★`startup` が `NULL` の元技からラッシュ版を生成すると、`startup NULL` ＋ `startup_basis='through'` の行ができる。⇒ 新たな `D-187` 違反である。**

| # | 根拠（**★`M39-01` の実測。⇒ 着手時に実査すること**） |
|---|---|
| **★★1** | **`internal/repository/move/rush.go` の `insertRushVariantSQL` が `startup_basis` を `'through'` のリテラルで INSERT しつつ、`startup` を元技からコピーする** |
| **★★2** | **`internal/service/move/service.go` の `rushEligible` は `category ∈ {normal, unique} ∧ !is_aerial` しか見ず、`startup NOT NULL` を要求しない** |

**★★★HEAD に該当元技が *3 件実在する*＝`rashid/run`**〔id 1364〕**／ `alex/prowler_stance`**〔2145〕**／ `dee_jay/speedy_maracas`**〔2555〕**。⇒ 仮説ではない。★id は実測値であり、着手時に `move_code` で引き直すこと。**

**★実害は fail-closed である**〔`candidateStartup` が `nil` を返し候補から落ちる〕**。⇒ 出力は壊れない。★それでも直すのは §0.4 の理由による。**

### 0.3 ★★`M19-04` §4.5 とは衝突しない（**★覆しではない**）

**★`'through'` をリテラルで書くのは `M19-04` §4.5 の明示的な設計判断である。⇒ 本サブはそれを覆さない。**

**★★★同判断は「ラッシュ版は通し値である」を述べたものであり、*通し値の元が無い*場合を扱っていない。⇒ 未処理のケースを埋めるだけである。**

**★★元技が `startup` を持つ場合の挙動は 1 ビットも変えないこと。⇒ `'through'` のままである。**

## 4. 危険（**★起きやすい順**）

### 4.1 ★★★最大＝**「直った」を新規 DB のテストだけで示すこと**

**★この穴は*実行時*である。⇒ `M39-01` のガードは是正の前後どちらでも緑である。**

**★★★段 1-3 で「ガードが緑のまま素通りする」ことを先に示しておくこと。⇒ それが無いと、レビューは何をもって直ったと判定してよいか分からない。**

### 4.2 ★★2 番目＝**`'through'` を一般に外してしまうこと**

**★★元技が `startup` を持つ場合は `'through'` が*正しい*。⇒ 一律に `'unknown'` へ倒すと、通し値の情報が消える。**

**★★★対照テスト**（§2.3-3）**が唯一の歯止めである。**

### 4.3 ★★3 番目＝**破壊確認を置かないこと**

**★★規約 (24)-2。⇒ 是正を外して赤くならないテストは、何も見ていない。**

### 4.4 ★★4 番目＝**件数のハードガードを「ついでに」置くこと**

**★★★実行時に増えうる違反を起動時に止めると、アプリが起動しなくなる。⇒ 規約 (24)-4 はこの実例から書かれている。**

### 4.5 ★**3 件の id を引き写すこと**

**★`1364` / `2145` / `2555` は 2026-09-19 の実測値である。⇒ `move_code` で引き直すこと**（§0.6 の版ゲート 4）**。**
