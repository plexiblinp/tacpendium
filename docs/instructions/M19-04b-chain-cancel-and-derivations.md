## 4. 実装

### 4.1 【A】`chain_cancel_total` 16 行の転記

**値の一次源は `character_data/chain-cancel-measurements.md` の「確定値」表である。CSV から読まない**（当該列は空欄）。

**対象は第三波 6 キャラ**（m_bison / rashid / jamie / luke / marisa / jp）**の 16 行**。

> **★ロースターは 4 種で固定ではない。キャラごとに違う。** 実測資料の**確定ロースター**節を必ず見ること。例——**ジェイミーは `Stand LP` が圏外で `Stand LK` が対象**（逆転）／**ルーク・マリーザは立ち弱攻撃が両方とも圏外**。**「4 技 × 6 キャラ = 24 行」と数えてはならない。16 行はロースターの実体である。**

**書き方**:

- **手書き UPDATE マイグレ。** 1 行 1 UPDATE で、**キャラクターコードと `move_code` を明示**する（条件式で束ねない——写像の誤りが見えなくなる）。
- **各 UPDATE に provenance コメント**（実測資料のどの行から取ったか）。
- **`WHERE chain_cancel_total IS NULL` を条件に加える**（二重投入の防止）。
- **down は当該 16 行を NULL へ戻す**（他の行に触れない）。

> **★「total − 4」等の規則で埋めてはならない。** 実測資料 §1 が、**同一の単発値が最大 3 通りに割れる**ことを多重検算つきで示している。**資料に無い行は投入しない。**

### 4.2 【B】`move_derivations` 9 行の投入

**確定した親子関係（開発者回答 2026-08-02・ボード D-153）**:

| | 親（通常版） | su / act / rec / total |
|---|---|---|
| P1 | `standing_light_punch` | 7 / 3 / 9 / **18** |
| P2 | `crouching_light_punch` | 6 / 2 / 8 / **15** |
| P3 | `crouching_light_kick` | 4 / 3 / 12 / **18** |

| | 子（連打版） | su / act / rec / total |
|---|---|---|
| C1 | `standing_light_punch_rapid` | 4 / 3 / 9 / **15** |
| C2 | `crouching_light_punch_rapid` | 3 / 2 / 8 / **12** |
| C3 | `crouching_light_kick_rapid` | 3 / 3 / 12 / **17** |

**仕様上、どの親からも 3 つの連打版すべてへ派生できる**（例：立弱P → 立弱P連打版／屈弱P連打版／屈弱K連打版）。**したがって 3 × 3 = 9 行の全組み合わせを投入する。1 対 1 の 3 行ではない。**

> **★上のフレーム値は照合用である。** **DESIGN-07 §1-3 の実測値表と 6 技すべてで一致することを、実装前に DB の実値で確認すること**（`moves.startup` / `total`）。**一致しなければ停止条件 5 として報告する**——`move_code` の取り違えを検出する唯一の手段である。

**書き方**:

- **`moves.id` をハードコードしない。** `character_code` と `move_code` から引く。
- **`INSERT ... SELECT ... FROM moves WHERE ...` 型を使う場合、親行が無くても 0 行投入でマイグレは成功する。** **§5 の件数固定テストが必須。**
- **down は当該 9 行を明示削除する**（`DELETE FROM move_derivations WHERE ...`。**表を空にしない**——将来ほかの行が入ったときに巻き添えにする）。

### 4.3 【C】第三波 6 キャラの人手判断一覧を生成する（**読み取りのみ**）

**M19-04 §4.7 と同じクエリ・同じ列で、第三波 6 キャラ分だけを出す。**

| 系統 | 抽出条件 |
|---|---|
| `startup_basis` | `is_derived = 1` **かつ** `category <> 'rush_variant'` **かつ** `startup_basis = 'unknown'` |
| `fastest_unreachable` の **B 型** | `is_aerial = 1` **かつ** `code` に `jumping_` を**含まない** |

**対象キャラ**: `m_bison` / `rashid` / `jamie` / `luke` / `marisa` / `jp` の **6 体のみ**。**既に記入済みの 11 キャラは出さない**（二重記入を避ける）。

**★各行に、判断に必要な列を必ず添える**——`character_code` / `move_code` / `name_ja` / `category` / `is_derived` / `is_aerial` / `command` / `startup` / `total` / **親技（`original_move_code`）** / `condition_ja`。**技名と入力コマンドが並んでいないと判断できない。件数だけの報告にしない。**

**キャラクター順・`move_code` 順で安定ソートする**（差分が取れる形）。

**★書式は `docs/progress/20260802-M19-04-manual-input-list-developer-decision.md` に揃えること**（開発者が同じ手順で記入できるようにするため）。**記入欄の許容値は次のとおり**:

| 系統 | 記入できる値 |
|---|---|
| `startup_basis` | `standalone` / `through` / **`unknown`** / `保留` |
| `fastest_unreachable` | `true` / `false` / `保留` |

> **★`unknown` と `保留` を書き分ける欄であることを、一覧の冒頭に明記すること。** `保留`＝**まだ判断していない**（後日の消化対象）／`unknown`＝**判断した結果、単独値とも通し値とも言えないと確定した**（消化対象から外してよい）。**実装上はどちらも UPDATE 対象外だが、後日の再判断の対象になるのは `保留` だけである**（ボード D-138）。
>
> **★`chain_cancel_total` の系統は本一覧に含めないこと。** 第三波 6 キャラ分は §4.1 で投入され、**残る候補は「確定ロースター外＝圏外」として決着済み**である（ボード D-137／D-143）。**`IS NULL` で機械抽出すると圏外の行まで「未実測」として並ぶ。** `NULL` には「圏外だから NULL」と「未実測だから NULL」の 2 種類があり、**機械条件では区別できない。区別できるのは実測資料の確定ロースターだけである。**

## 5. テスト（★本サブの主要な失敗モードはサイレント no-op である）

| # | 固定すること |
|---|---|
| 1 | **`chain_cancel_total` の投入件数がちょうど 16 行**であること。**キャラ別・`move_code` 別の値も固定する** |
| 2 | **投入前に NULL だった 16 行だけが変わり、それ以外の `chain_cancel_total` が 1 行も変わっていない**こと（**000052 で入った 37 行を含む**） |
| **3** | **★`move_derivations` のうち `child_move_id` が zangief の連打版 3 行のいずれかである行が、ちょうど 9 行**であること |
| **4** | **★`move_derivations` のテーブル総数は「9 行以上」の下限のみを固定する** |
| 5 | **9 行の親子の組み合わせが 3 親 × 3 子の全組み合わせと一致する**こと（`move_code` のペアで固定） |
| 6 | **down で 16 行が NULL へ戻り、9 行が削除される**こと。**re-up で復帰する**こと |
| 7 | **他キャラ・他行が 1 行も増減していない**こと |
| 8 | **確定反撃サーチの canary 判定値が不変**であること（契約 F-1） |
| 9 | **golden 7 stem が green・`go run ./cmd/seedgen -check` が OK** であること |

> **★項目 3 と 4 の書き分けが本サブの要点である。**
> **総数を 9 で固定してはならない。** `move_derivations` の行数は**固定ではない**——親参照は `startup_basis` の人手付与と**同一パスで付与される**設計であり、**人手付与が進むほど増える**（実際に guile の 5 行に「派生元が複数」の記入がある）。**総数を 9 に固定すると、次に親参照が入った瞬間に落ちる。** そのとき「期待値を緩める」誘惑が発生する——**M14-03c / 03d で製造が正しく回避した罠に、こちらから突っ込むことになる。**
> **一方、zangief スコープの 9 行は固定しなければならない。** **親の基数を 3 と取り違えて 3 行しか入れなくても、それはエラーにならない。**

> **★「静かに壊れる」ものを足したら、それを消したときに落ちるテストを 1 本書く。** M19-04 で `insertRushVariantSQL` の `'through'` リテラルが**消してもどのテストも落ちない**状態だったことがレビューで検出されている。**テストを足して終わりにせず、実際に壊して FAIL することを確認してから復元すること。**
