## 1. 背景と目的

### 1.1 `DES-002` §4.4 は 2 本の対策を定めたが、片方しか成立していない

**§4.4 の逐語**——

> **第一対策**：SameSite=Strict Cookie による Cookie 送信制限
> **補助対策**：POST/PUT/DELETE/PATCH リクエストに独自ヘッダ（`X-Requested-With`）を要求し、CORS preflight と組み合わせて簡易的な検証を行う

| # | 対策 | 状態 |
|---|---|---|
| 1 | **SameSite=Strict Cookie** | **★`M22-01` で成立した**——**`combomgr_session; Path=/; HttpOnly; SameSite=Strict` を発行している**（`DES-002` §8.1）。**★従来は「Cookie を発行するコードが 0 件」で前提そのものが無かった** |
| 2 | **`X-Requested-With` の要求** | **★サーバ側で検証する実装が 0 件。** フロントは **`PUT /api/config` の 1 経路にだけ付与**しており、**他の非 GET ルートには付けていない** |

**⇒ 本サブは 2 をどうするかを決め、`DES-002` §4.4 を as-built へ揃える。**

### 1.2 ★守るべきものは 2 つある

#### 最重要ゲート 1 — **LAN の他端末を塞がないこと**

**★本アプリの目的は「ほかの機器から開く」ことである**（`FR406` / `FR501`）。**CORS や独自ヘッダの要求を締めすぎると、スマートフォンから使えなくなる。**

**★しかもこの壊れ方は `localhost` で操作している限り 1 度も現れない。** **⇒ 自分のブラウザでは全部通る。**

**⇒ 開発者の手動確認が完了条件である**（§7.1・**D-398**）。**「スマートフォンから開いて 1 つ保存できる」ことを実機で確かめる。**

#### 最重要ゲート 2 — **`curl` 相当の復旧経路を塞がないこと**

**★`DES-002` §8.2 は「`curl` 相当の経路が唯一の復旧経路である」と定めている**（2026-08-16・`CHANGE-119`）。**パスワードを非 ASCII で決めてしまった利用者は、そこからしか戻れない。**

**⇒ 非 GET の全経路へ独自ヘッダを要求すると、この経路が消える。** **★`DES-002` §8.2 の歯止め b を無効化することになる。**

**★この 2 つは方向が同じである**——**どちらも「締めることの代償」を数える話である。**

### 1.3 ★平文 HTTP が前提である（**書き換えないこと**）

**`DES-002` の LAN 構成は平文 HTTP である**（契約 F-3）。**⇒ Cookie に `Secure` 属性を付けてはならない**——**付けると HTTP では送られなくなり、ログインが成立しなくなる。**

**★「安全である」と書かないこと。** **書けるのは「この条件下でこう振る舞う」までである。**

**★脅威モデルは `DES-002` §4.4 が定めている**——**「LAN 内は信頼する」。** **WPA2/WPA3 で守られた LAN の内側を前提とし、同一 LAN 内の悪意あるデバイスからの攻撃はネットワーク側の防御責任とする。** **⇒ 本サブはこの割り切りを変えない。**

### 1.4 目的

完了時に、次の状態が達成されている。

1. **CORS の許可 Origin が確定し、その根拠が書かれている。**
2. **CSRF 対策の方式が確定し、`DES-002` §4.4 の 2 本が as-built と一致している。**
3. **★LAN の他端末から、いままでどおり使える**（実機で確認済み）。
4. **★`curl` 相当の経路から、いままでどおり操作できる**（`DES-002` §8.2 の歯止め b）。
5. **★締めた／締めなかったことの理由が、設計卓が設計書へ書ける形で報告されている。**

1. **日本語の散文を否定文字クラスで走査するときは `LC_ALL=C.UTF-8` を付ける。**
2. **行を跨ぐ文脈（`-A1 -B1`）またはファイル単位（`grep -rl`）でも回す。**
3. **★陽性対照を 1 つ混ぜる**（**`DES-002` §4.4 の「`X-Requested-With`」は必ず当たる**）。**「0 件だった」は「無い」ではなく「走査が壊れている」かもしれない**（`E-84`）。
4. **★当たったファイルは全文を目で見る。**
5. **走査コマンドそのものを完了報告へ残す。**

| # | 確認項目 |

## 9. 注意事項・判断に迷ったら

### 9.1 推測で進めてはいけない事項

1. **★CSRF 対策の方式**（§4.2）。**`CHANGE-116` §4 が定める。選び直さないこと。**

3. **★脅威モデル**（`DES-002` §4.4 の「LAN 内は信頼する」）。**変えないこと。**

### 9.2 推測で進めてよい事項（その旨を明示）

1. **判定を置く層**（ミドルウェアか、ルート単位か）。**★既存 3 本の順序を変えないこと。**
2. **エラーコードと HTTP 状態の綴り**（**★拒否する場合**）。**`internal/model` のパッケージ定数として置くこと**（`SUPP-001` §5.2）。**★テストの期待値はリテラルで固定すること**（同 §5.5 (13)）。
3. **許可 Origin の組み立て方**（§4.1-3）。**★迷ったら「塞がない側」を採る**——**締めすぎの壊れ方は `localhost` で気づけないためである。**
