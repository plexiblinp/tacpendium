## 1. 背景と目的

### 1.1 サーバ側は完成している。本サブは画面と「誰として使うか」を足す

**`M22-01`（2026-08-15 完了・`CHANGE-112` 反映済み）が、入場ゲートのサーバ側を作った。** **★契約は `DES-002` v1.50.0 §8.1 と §4.2 が正本である。** **本サブが受け取る 4 点を先に挙げる。**

| # | サーバ側の契約 | 本サブへの影響 |
|---|---|---|
| 1 | **未認証は `401` ＋ `{"error":{"code":"unauthorized",...}}`。リダイレクトしない** | **★遷移は画面が決める。** いま既存画面は**生の応答本文を表示している**（followup `auth-401-shows-raw-error-body`） |
| 2 | **セッションは Cookie**（`HttpOnly` / `SameSite=Strict` / `Path=/` / **`Secure` なし**） | **★フロントは Cookie を触らない。`fetch` は既に `credentials: "same-origin"` を持つ。** **⇒ 本サブでトークンを持ち回さない** |
| 3 | **★保護が無効な間はログインできない**（正しいパスワードでも 401） | **★画面は `GET /api/auth/status` の `passwordRequired` を見て出し分ける**（§4.1）。**`GET /api/config` の `security.passwordEnabled` を見てはならない**（§4.1-3） |
| 4 | **パスワード変更が通ると既存セッションが全破棄される** | **★変更した端末自身も切れる。** **⇒ 変更後にログインへ戻る導線が要る**（§4.4-4） |

### 1.2 ★「ユーザー選択」と「パスワード」は別物である（**混ぜないこと**）

**`DES-002` §8 は 2 つの別々の仕組みを書いている。** **★本サブは両方を作るが、1 つの画面にしない。**

| 仕組み | 何のためのものか | 画面 |
|---|---|---|
| **簡易パスワード** | **LAN へ公開したときの入場ゲート。全員で 1 本を共有する。** **入場の可否だけを決め、誰が入ったかは分からない** | **ログイン画面**（**★新設**） |
| **ユーザー選択** | **タグ・プリセットのスコープと「誰の編集か」の札**（`FR013` ／ `FR501`＝**誤上書きの防止**）。**★認証ではない。名前を選ぶだけである** | **ユーザー選択画面**（`DES-005` §5.3。**★既存の記述は利用者ごとのパスワードを前提にしており、`CHANGE-113` で改訂する**） |

**★`DES-005` §5.3 の現行記述は as-built と食い違う**——**「ユーザークリックで認証（パスワード設定ユーザーはパスワード入力→認証）」。** **利用者ごとのパスワードは採らないと確定している**（`CHANGE-112`）。**⇒ `CHANGE-113` で改訂する。製造は設計書を編集しない。**

### 1.3 目的

完了時に、次の状態が達成されている。

1. **`password_enabled = true` のとき、ログイン画面が出て、通ると使える。**
2. **`password_enabled = false` のとき、いままでどおり何も出ない**（`FR502`）。
3. **利用者が 2 人以上のとき、起動時にユーザー選択が出る**（`DES-002` §8）。**1 人ならスキップする**（`FR502`）。
4. **★`userID` の供給元が、定数からセッションへ差し替わっている**（**⇒ `FR501` が初めて効く**）。
5. **初回起動ウィザードの Step 6 でパスワードを設定できる。**
6. **パスワードを変更できる**（設定画面から。現在のパスワードを要求する）。
7. **LAN 共有モードを ON にするときの警告と同意ダイアログが、パスワードの設定状況を見て出し分けている。**
8. **★上記のいずれも、文言が一般の利用者に読める言葉で書かれている**（§4.6）。

### 1.4 ★`FR013` 後半は、タグとプリセットで形が違う（**設計卓の誤りを訂正した**）

**`REQ-001` `FR013`**——「**本方針の射程はコンボ・セットプレイに限る**。タグ・プリセットはユーザー個人の好みを反映するデータとして、**作成者のみ編集・削除可能**（他ユーザーは参照のみ可能）という従来方針を維持する」。

**★本節の v1.0.0 は「`userID` の供給元を差し替えた瞬間、何も足さずに効き始める」と書いていた。** **★これは誤りであり、製造担当の実査で判明した**（2026-08-15＝**D-402**）。**プリセットでは成立し、タグでは成立しない。**

| 対象 | 実査で判明した as-built | `FR013` の逐語との関係 |
|---|---|---|
| **プリセット** | **`List` は絞らない。`authorizeMutation`（`VAL-P07`）で書き込みを弾く** | **★「見えるが編集不可」＝逐語どおり** |
| **タグ** | **リポジトリの `List` / `Get` が `WHERE user_id = ?` で絞る** | **★「見えない」＝「参照のみ可能」にならない** |

**★誤りの型**——**`M22-RESEARCH-01` C-6 の「タグは全 SQL が利用者で絞る」を「所有者制御が効いている」と読んだ。** **要件の文（参照は可能）と実装の性質（読みも絞る）を突き合わせずに、片方だけ見て結論を書いた。**

#### 1.4.1 ★開発者裁定（**2026-08-15＝D-402**）——**タグは個人スコープのままとする**

| # | 確定した内容 |
|---|---|
| 1 | **★タグの読みの絞り込みは維持する。** **⇒ 他の利用者のタグは見えない。** **`WHERE user_id = ?` を外さないこと** |
| 2 | **★`FR013` 後半の「（他ユーザーは参照のみ可能）」の射程は、プリセットに限ると `REQ-001` 側で明確化する**（`CHANGE-113` §2-i。**★反映は設計卓が行う。製造は設計書を編集しない**） |
| 3 | **★理由は 3 つ**——**(a) `mycombo_status` は各人の進捗そのものであり、一律に共有すると破綻する**〔カテゴリで例外を作ると仕組みが二重になる〕 ／ **(b) 他人の分類タグが自分のフィルタ一覧に並ぶ利点が薄い** ／ **(c) コンボは全員共有・タグはその上に各人が貼る個人の付箋、という構図になり `FR013` 前半と衝突しない** |
| 4 | **★プリセットの形は変えない。** **`internal/service/preset/` の所有者チェックの実装には触れない**（§2.2-1） |

#### 1.4.2 ★既定タグを利用者作成時に生成する（**段 2 の追加作業**）

**★実査で実害が判明した**——**`mycombo_status` の 3 タグは `user_id = 1` にのみ seed されており、絞り込みが効くと 2 人目はマイコンボのステータスを 1 件も引けず機能不全になる。**

**★これは可視範囲の問題ではない。** **`migrations/000007` のヘッダが逐語で宣言している**（`CHANGE-112` §3 に引用済み）——

> 本来は **M6 初回起動ウィザードで生成**（`SUPP-001` §2.5）。M3 期間は未実装のため seed で凌ぐ。／ **M6 着手時にウィザード経由生成へ切り替える。**

**⇒ 既定 3 タグは「利用者ごとに生成する」のが元の設計であり、seed は暫定だった。** **欠けているのは可視範囲ではなく「利用者を作ったときに既定タグを生成する処理」である。**

**★本サブは `users` の CRUD を作る担当であるため、ここが引き取る**（§4.5-6）。**⇒ 段 2 の作業が 1 つ増える。§9.3-1 の停止条件はそのまま効く。**

#### 1.4.3 ★利用者に見える帰結

| # | 帰結 | 求めること |
|---|---|---|
| 1 | **★プリセットは「見えるが編集できない」** | **★「他の人のものだから触れない」が伝わる形にする**（§4.5-3）。**★無反応にしない**——**押せるのに何も起きない、あるいは失敗だけが出るのが最も分かりにくい** |
| 2 | **★タグは「そもそも見えない」** | **★「編集できない」という見せ方は要らない**（見えないため）。**★代わりに、既定タグが自分の分として生成されていること**（§4.5-6） |
| 3 | **コンボ・セットプレイは全員が等しく編集できる**（`FR013` 前半・契約 F-1） | **★これは穴ではない。「タグだけ触れないのはおかしい」と読んで揃えないこと**（§1.6-2） |
