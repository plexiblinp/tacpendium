## 1. 背景と目的

### 1.1 背景——**ゴミ箱の配線が片方しか無い**

**`M23-01`〜`M23-06` は、ゴミ箱の「中」を作ってきた**——復元・完全削除・警告・列。**★だが入口と出口の配線が 3 か所で切れている。**

| # | 切れている配線 | 帰結 |
|---|---|---|
| **1** | **★★UI からセットプレイを論理削除する導線が 1 つも無い** | **`M23-02` が足したゴミ箱のセットプレイ欄は、画面操作だけでは永久に空のままである。** 行を入れるには API を直接叩くか E2E が要る |
| **2** | **行をクリックすると 404 になる** | **`DES-005` §5.15 の「行クリック → 詳細表示（読み取り専用のコンボ詳細）」が機能しない。** **完全削除は不可逆なのに、中身を確認する手段が一覧の列だけである** |
| **3** | **完全削除を拒まれたときに、紐付けを解除する導線が画面に無い** | **API では行えるが、ゴミ箱からは辿れない。** **⇒ 拒否されたら詰む** |

**★1 は本サブでいちばん重い。** **★同サブ以前からの未配線であり、`M23-02` が作った欠落ではない**（当該フックは `M20/M21` 期から在る）。

### 1.2 ★`M23-03` が本サブのために道具を残している

**`M23-03` は参照側の除外の穴 6 か所のうち、`#1`（`FindByIDAllowDeleted`）だけを意図的に塞がなかった。** **その理由は 2 つ書かれている。**

1. **完全削除の前チェック**
2. **★★ゴミ箱の行から読み取り専用詳細を出す道具**

**⇒ 2 は本サブのために残されたものである。** **★新しく道具を作る前に、これを使えるかを確かめること**（§3.3-2）。

### 1.3 ★★`M23-06` の裁定は、面が変われば答えも変わる

**`M23-06` は「コンボのルート列を消す」と裁定した。** **その軸は「その情報が無いと利用者が困るか」であり、答えは「一覧では困らない」だった**——**コンボは `memo` と始動状況で識別できるからである。**

**★本サブは同じ軸を「詳細」の面へ当てる。答えは変わる。**

| 面 | 目的 | レシピは要るか |
|---|---|---|
| **一覧** | **識別**（どれを復元するか選ぶ） | **★要らない**（`M23-06` の裁定。他の列で足りる） |
| **詳細** | **確認**（本当にこれでよいか中身を見る） | **★要る。完全削除は不可逆である** |

**★★同じ軸を別の面に当てると別の答えになる。これは矛盾ではない。** **⇒ 本サブは読み取り専用詳細でレシピを出す**（§4.2-4）。

### 1.4 目的

1. **セットプレイをゴミ箱へ入れる導線を作る**（§4.1）。
2. **ゴミ箱の行から読み取り専用詳細を開けるようにする**（§4.2）。
3. **完全削除を拒まれたときに、紐付けを解除できるようにする**（§4.3）。
4. **一括操作バーの文言を i18n 化し、置き場を決める**（§4.4）。
5. **★`M23-06` が `M23-07` へ書き換えた Go コメント 7 か所を、本サブの完了で正しく消す**（§4.5）。

## 4. 詳細仕様

### 4.1 ★★セットプレイをゴミ箱へ入れる導線（**本サブでいちばん重い**）

**API・API クライアント・フックはいずれも実在する。呼ぶ画面が 1 つも無い。**

**⇒ 画面から呼べるようにする。**

#### 4.1-1 どこに置くか

**★セットプレイは親コンボ経由でしか画面に出ない**（`VAL-S05`＝親に紐付かない単独作成は禁止）。**⇒ 導線もそこに置く。**

**★置き場の候補を §3.3-5 の実査で確かめ、選んだ理由を報告に書くこと。** **★設計卓は具体の置き場を指定しない**——**画面の現物を見ないと決められない。**

**★守ること**——**コンボの削除と混ざらないこと。** **「セットプレイを消したつもりがコンボが消えた」は起きてはならない。**

#### 4.1-2 ★確認を挟むこと

**論理削除は取り消せる**（ゴミ箱から戻せる）**が、それでも確認を挟む。**

**★理由**——**セットプレイは複数のコンボから共有されうる**（`M23-02` の開発者要求）。**⇒ 消す前に「他のコンボからも見えなくなる」ことを伝える。**

**★何件のコンボから参照されているかを示すこと。** **材料は在る**（`parentComboIds`＝`DES-002` §4.2）。

#### 4.1-3 ★消した後にゴミ箱へ行けること

**★トーストから直接ゴミ箱へ行ける導線を置くこと。** **⇒ 「消した → 間違えた → 戻す」が 1 画面で完結する。**

### 4.2 行クリックの読み取り専用詳細

#### 4.2-1 何を直すか

**ゴミ箱の行をクリックすると `/combos/:id` へ遷移し、`GET /api/combos/:id` が `deleted_at IS NULL` で締め出して 404 を返す。**

**★遷移リンクは 2 つある**（行全体の `onClick` と列内の `<Link>`）。**★全数を §3.3-8 で数えること。**

#### 4.2-2 ★★経路は新設する。既存経路にフラグを足さない

**`GET /api/combos/{id}` は削除済みを返さないままにする。**

**★理由**——**`M23-06` の教訓がそのまま当たる。** **同サブは `ResolveSetupRecipe`（生存行用の入口）が削除済み行に使えないことを発見し、別の入口を新設した。** **⇒ 求めている集合が違えば、入口も別に要る。**

**★既存経路にフラグを足すと、通常の詳細表示で削除済みが返る事故の余地が残る。** **⇒ 別の経路にする。**

**★`FindByIDAllowDeleted` を使うこと**（§1.2。**`M23-03` が本サブのために残した道具である**）。**★新しく取得処理を作らない。**

#### 4.2-3 画面も別のルートにする

**★読み取り専用であることが URL から分かる形にすること。**

**★出さないもの**——**編集 ／ 削除 ／ セットプレイの追加・編集 ／ タグの編集。** **★出すもの**——**復元 ／ 完全削除 ／ 一覧へ戻る。**

**★「編集できない」ことが利用者に分かること。** **押せないボタンを並べるのではなく、出さない。**

#### 4.2-4 ★レシピを出す

**削除済みコンボの `recipe_cache` は NULL だが、`combo_steps` は残っている**（§3.3-4）。**⇒ そこから組み立てて出す。**

**★`M23-06` がセットプレイ側で作った形を踏襲すること**（§3.3-3）——**計算本体を呼ぶ読み取り専用の経路。**

**★2 点を守ること。**

1. **★`recipe_cache` へ書き戻さない**（`DES-002` §4.2 の不変。**`M23-06` がテストで固定している**）。
2. **★解決に失敗しても詳細そのものを落とさない**（`DES-002` §4.2 の縮退の規則）。**レシピ欄だけを空にし、ログに残す。**

**★これは `M23-06` がルート列を消した裁定と矛盾しない**（§1.3）——**一覧は識別、詳細は確認であり、目的が違う。**

#### 4.2-5 ★セットプレイの詳細は作らない

**セットプレイは親コンボ経由でしか画面に出ない**（`VAL-S05`）。**⇒ 単独の詳細という概念が無い。**

**★ゴミ箱のセットプレイ行はクリックで遷移しないこと。** **★遷移しないことが分かる見た目にすること**（カーソル・ホバー）。

### 4.3 完全削除を拒まれたときの逃げ道

**生きたコンボから参照されているセットプレイの完全削除は拒否される**（`409 setup_in_use`。`CHANGE-122` / `M23-02`）。**★そのとき紐付けを解除する導線が画面に無い。**

**⇒ 拒否の表示から、紐付けを解除できるようにする。**

**★3 点を守ること。**

1. **★どのコンボが参照しているのかを見せる。** **材料は `details.combos` の `{id, memo}` に在る**（`DES-002` §4.2）。**★新しくデータを取りに行かない。**
2. **★解除は「そのコンボからの紐付けを外す」であって「そのコンボを消す」ではない。** **★文言でその区別が伝わること。**
3. **★解除した後、完全削除を自動で再実行しないこと。** **利用者にもう一度押させる。** **理由＝解除の結果を見てから決められるようにするためである。**

**★既存の紐付け解除の API を使うこと**（§3.3-7）。**新しい API を作らない。**

### 4.4 一括操作バーの i18n と置き場

**ゴミ箱画面に日本語直書きが残っている**（一括操作バーのボタン文言・件数表示 ／ `TrashPage` の見出し・状態表示）。**`M23-06` が列見出しを i18n 化したため、同じ画面の中で作法が割れている。**

**⇒ ゴミ箱画面の直書きを全数 i18n 化する**（§3.3-9 で数える）。**★射程はゴミ箱画面だけである。**

**★`DES-006` §11.3 の規則に従うこと**——**複数の警告を連結するときは区切りと終端も翻訳キーで持つ**（**`M23-06` が復元側で確立した形**）。

#### 4.4-2 置き場

**バーはコンボ表の上に固定されている。** **⇒ セットプレイだけを選んだ利用者は画面上部まで戻る必要がある。**

**★判断材料が 1 つ増えている**——**`M23-06` により、結果が残る間はバーが表示され続けるようになった**（`CHANGE-127`）。

**★暫定案＝画面下部への固定**（両方の表から届く）。**★他の形を採ってもよい。理由を報告に書くこと。**

**★守ること**——**選択が残っている間だけ操作ボタンを出す**（`M23-06` が確定した規律）。**結果の表示は選択が空になっても残る。**
