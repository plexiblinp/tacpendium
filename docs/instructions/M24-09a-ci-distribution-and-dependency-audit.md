- **★「緑になった」を「検査が働いている」と取り違えないこと。** **2 と 3 がそれを分ける唯一の根拠である**（`E-84`）。

## 11. 開発者への確認事項

1. **リポジトリの可視性と GitHub Actions の可用性・課金**
   何を: **public か private か。private の場合、Actions の無料枠で nightly の 3 OS クロスビルドまで回してよいか。**
   なぜ: **ベースライン計測 §5 の未決 1 が「開発者確認」として残している。** **★private の場合は実行時間に上限がある。**
   暫定案: **`M24-09a` の Plan Mode で製造に確認させ、実行できない場合はワークフローを書かずに停止させる**（§2.3）。

2. **必須 check として扱う範囲**
   何を: **PR の高速検査だけを必須にし、nightly は必須にしないでよいか。**
   なぜ: **nightly が赤いとき、壊れているのはクロスビルドであって当該 PR ではない場合がある。** **★必須にすると、無関係な PR が止まる。**
   暫定案: **PR の高速検査のみ必須。** **nightly の赤は通知として扱い、`followup-backlog` へ 1 行足す運用にする。**

3. **`5 分程度` の目標の扱い**
   何を: **ベースライン §6 が「10 分以内は満たす見込み・5 分は未達の見込み」としている。5 分を目標として残すか。**
   なぜ: **達成できない数字を受入条件に置くと、以後の判断が「未達のまま」で固定される。**
   暫定案: **10 分以内だけを受入条件とし、5 分は目標から外す。** **★短縮の余地は `internal/infra/migration` の 91.3 秒の内訳が分かってから議論する**（同 §5 の未決 4）。
