## 0. この指示書の特殊性

### 0.1 製造担当として起動 + 調査だけ実施して閉じる運用

本指示書は **調査担当運用パターン**(architecture-patterns §6)に基づく事実列挙のみの調査依頼。製造担当として Claude Code セッションを起動し、本指示書 §4 の事実列挙を実施 → §5 レポートに記録 → セッションを閉じる。実装(R-1 / C-12 の修正)は本調査の対象外(M12-03 で別指示書)。

### 0.2 read-only 厳守

本指示書では **コードの変更を一切行わない**。`view` / `grep` / `git log` / `git blame` / `find` / `ls` / SQL の SELECT などの読み取り系のみを使用。ファイル編集系(`str_replace` / `create_file` / 書き込み系 `bash`)は **使用禁止**。例外は §5 レポートファイル作成のみ。DB は **SELECT のみ**(INSERT / UPDATE / DELETE / マイグレーション実行は禁止)。

### 0.3 判断・提案を含めない(judgement-free)

調査結果は **事実列挙のみ**。「ここを直すべき」「中段化はこの行が原因なので修正する」等の判断・提案・修正方針・設計結論は **含めない**。観察された事実 + 既存コード状態 + 設計書本体規定との比較 = 設計担当が M12-03 修正設計に活用するための情報供給のみが目的。**修正方針・設計判断は設計担当 + 開発者が行う**。

ただし以下 2 種類は判断ではないため記録する:
- **想定外の発見**(起き攻め / 始動技が想定外の箇所で参照・描画・上書きされていた等)。
- **明らかな矛盾の事実指摘**(設計書本体規定とコードの不整合、ラベルとデータの乖離、コメントとロジックの矛盾等): 事実として列挙し、解釈・解消方針は含めない。

### 0.4 本調査の主目的

| 軸 | 主目的 |
|----|--------|
| **§4.1 起き攻め表示の現状と「中段化」の真因(R-1)** | 起き攻め 6 BOOLEAN(`oki_meaty_*` × 4 / `oki_shimmy_*` × 2)+ `knockdown_advantage` が、コンボ詳細(DES-005 §5.6)・コンボ比較(DES-005 §5.8)・編集(DES-005 §5.7)で **どう描画されるか**を事実列挙。「いつのまにか中段攻めになる」症状に関わる **ラベル・段(high/mid/low)表現の出所**と、**詳細と比較の表示方式の差異**を確定する。真因レイヤ(フロント描画 / BE 返却データ / i18n ラベル)の切り分け材料を供給 |

### 0.5 背景(M12 で確定済みの前提 = 調査のフレーミング)

> 以下は設計担当 + 開発者で確定済みの前提。調査担当は **この前提を変更しない**。事実が前提と食い違う場合は §0.3 のとおり「矛盾の事実」として記録する(解釈は設計担当が行う)。

- **R-1**(残フェーズ2 必須): コンボ詳細の起き攻め情報がおかしい(いつのまにか中段攻めになる)/ 比較画面と表示方式を統一したい。先行リリースの妨げとなる正しさの不具合。
- **C-12**: コンボ編集画面の始動技プルダウンを消し、自動推定のみにしたい(二重入力が面倒)。**ただし開発者の実績は通常技・ジャンプ攻撃の始動のみ**で、必殺技・投げ・ターゲットコンボ等の始動での自動推定挙動は未確認 = 本調査で網羅性を裏取りする。
- 起き攻め 6 BOOLEAN の意味(DES-003 §3.x、L368-374): `oki_meaty_neutral_tech_throw`(その場受け身に投げ重ね)/ `_dr`(同 DR 版)/ `oki_meaty_back_tech_throw`(後ろ受け身に投げ重ね)/ `_dr`(同 DR 版)/ `oki_shimmy_neutral_tech`(その場受け身シミー)/ `oki_shimmy_back_tech`(後ろ受け身シミー)。`knockdown_advantage` は INTEGER(有利フレーム)。
- 起き攻めは **フレームデータから自動推定不可・手動入力前提**(DES-003 L447)。`properties` の段表現は `high`(上段)/ `mid`(中段)/ `low`(下段)等のコード値で **move 側の属性**(DES-003 L298)であり、起き攻め 6 BOOLEAN とは別系統 ——**この両者が表示上どう交差するか**が R-1 調査の焦点。

### 0.6 結果の扱い

調査結果レポート(`docs/progress/M12-RESEARCH-01-report.md`、配置は docs-map の RESEARCH レポート規約に従う)は設計担当が読んで、以下を判断する材料に使う:
- R-1 修正方針(真因が描画ロジックか / 返却データか / i18n ラベルか、詳細と比較のどちらの表示方式へ統一するか)と CHANGE 要否(DES-005 §5.6 / §5.8 改訂の有無)。
- C-12 の安全性判断(始動技プルダウン除去で `starter_move_id` 導出が全 move 種別で破綻しないか)と修正方針。

## 1. 背景と目的

### 1.1 背景

- M11 完了(custom_states 開始時状態の機能化、E2E 通過)によりフェーズ2 機能スパインが揃い、M12 で先行リリースの UX・正しさを仕上げる。残フェーズ2 必須の R-1(起き攻め表示の不具合)と候補 C-12(始動技二重入力)は、修正対象の描画・導出ロジックを実コードで確認しないと修正指示が書けない(retrospective-digest §1 パターンA「症状のレイヤ ≠ 真因のレイヤ。フロント↔バックエンドを決めつけず両層を疑う」/「修正対象・E2E 起点の導線は『あるはず』で書かず実コードで存在確認」M10-4)。
- R-1 は「中段攻めになる」という **ラベル / 段表現の症状**で、起き攻め 6 BOOLEAN(meaty / shimmy)と move の `properties`(high / mid / low)が表示上どこで交差するかを実コードで切り分ける必要がある(想定で真因レイヤを決めない)。
- C-12 は手動選択と自動推定の **二重入力**で、自動推定の網羅範囲(対応 move 種別)を裏取りしないと「プルダウン除去が安全か」を判断できない(`starter_move_id` は重複判定キー = DES-005 §5.6)。

### 1.2 目的

本指示書完了時に以下を達成する:

- 起き攻め 6 BOOLEAN + `knockdown_advantage` の **詳細 / 比較 / 編集における描画方式の完全なマップ**(項目・ラベル・レイアウト・i18n キー)。
- 「中段」等の **段表現が起き攻め表示に現れる経路の有無**と、現れる場合の出所(move `properties` 由来か / 起き攻めラベル由来か)の事実列挙。
- **詳細(§5.6)と比較(§5.8)の表示方式差異**の事実列挙(表示する BOOLEAN の数・順序・ラベル・有利フレームの扱い)。
- `autoStarterMoveId` の **導出ロジックと対応 move 種別の範囲**、手動プルダウンとの優先順位・上書き・保存経路の事実列挙。
- 自動推定が **空 / 手動選択と異なる値になりうるケース**(必殺技・投げ・ターゲットコンボ・ラッシュ等の始動)の事実列挙。
- 設計担当が M12-03 修正設計・CHANGE 判断に必要な情報の供給。

### 1.3 このマイルストーンで作らないもの

- **R-1 / C-12 の修正実装**(本調査は事実列挙のみ。修正は M12-03)。
- **判断・提案・修正方針・設計結論**(§0.3 judgement-free)。
- **設計書本体(DES-003/004/005/006)の改訂**(改訂は設計担当が CHANGE で実施)。
- 起き攻め / 始動技と無関係な領域の深掘り(§4.3 対象外)。

## 4. 調査内容

本節は §0.2 read-only 厳守 + §0.3 judgement-free 原則に従って実施する。コマンド例は **参考**(より効率的な手段が存在する場合は調査担当の裁量で変更してよい)。**全数性が核心**: grep は snake_case / camelCase 両系統で実行し、ヒット 0 件の領域も「0 件であった」と明示的に記録する。

追跡するシンボルのバリエーション:
- snake_case(DB / SQL / JSON タグ): `oki_meaty_*` / `oki_shimmy_*` / `knockdown_advantage` / `starter_move_id` / `properties`
- camelCase(Go フィールド / フロント型 / API): `okiMeaty*` / `okiShimmy*` / `knockdownAdvantage` / `starterMoveId` / `autoStarterMoveId` / `properties`
- 段表現: `high` / `mid` / `low` / `中段` / `上段` / `下段`(i18n キー・ラベルを含む)

### 4.2 始動技自動推定の網羅性(Q2)

#### 4.2.1 `autoStarterMoveId` の導出ロジック

- [ ] `autoStarterMoveId`(code-facts §1 `ComboEditorBasicFields` の Props)の **供給元**(親コンポーネント・hook・useMemo 等)を実コードで特定し、導出ロジックを事実記録: レシピの何番目のステップから / どのフィールド(`move_id` 等)を根拠に始動技を推定するか。
- [ ] 推定が **対象とする move 種別の範囲**を事実記録: 通常技 / ジャンプ攻撃 / 必殺技 / SA / 投げ / ターゲットコンボ / ラッシュ版 / ドライブ系等のうち、どれを始動として推定できるか(move の `category` / `is_aerial` 等の分岐が存在する場合は列挙)。

#### 4.2.2 手動プルダウン(DES-005 §5.7 表示項目4)との関係

- [ ] 手動の始動技選択 UI(DES-005 §5.7 L335「始動技選択(moves からの選択)」)の実装(コンポーネント・選択肢の絞り込み条件)を事実記録。
- [ ] 自動推定 `autoStarterMoveId` と手動選択値の **優先順位・上書き関係**を事実記録: 初期値として自動推定が入るか / 手動選択が常に優先か / 自動推定と手動が併存して `starter_move_id` の最終保存値を決めるのはどちらか。
- [ ] `starter_move_id` の **保存経路**(CREATE / PUT / PATCH リクエストでどのフィールドとして送られ、BE でどう保存されるか)を事実記録。重複判定キー(DES-005 §5.6 編集(a)、`starter_move_id` を含む)に効く値がどこで確定するかを明示。

#### 4.2.3 自動推定と手動選択が食い違いうるケースの裏取り

- [ ] 自動推定値と手動選択値が **異なりうる具体ケース**を、ロジックの分岐から事実列挙(例: 必殺技始動・投げ始動・ターゲットコンボ始動・ラッシュ版始動でレシピ先頭から推定した値が手動選択肢と一致しない可能性の有無)。**再現操作は行わず**(read-only)、ロジック上の分岐の事実として記録。
- [ ] 開発者実績(通常技 / ジャンプ攻撃のみ)以外の始動 move 種別が、自動推定で `starter_move_id` として確定可能かを、§4.2.1 のロジック範囲から事実判定(0 件 / 不可なら明示)。

### 4.3 調査対象外シンボルとの混同回避(重要)

以下は R-1 / C-12 と **別物**。grep で同時ヒットしうるため、レポートで明確に区別する:

- [ ] `combos.situation` / `characters.custom_states`(キャラ固有状態、M11 完了)= **別物**(起き攻めでも始動技でもない)。
- [ ] `combos.position` / `opponent_stance` / `hit_type` / `opponent_size`(独立カラム化済みの状況)= **別物**。
- [ ] moves 取込 / 編集グリッド(`MoveEditGrid` 等)・`move.properties` の編集系 = **別物**(ただし `properties` の段コードが起き攻め表示に交差する §4.1.5 の調査は対象)。
- [ ] セットプレイ系(`Setup*`)= **別物**。

レポートでは §4.1.1 の grep ヒットのうち上記に該当するものを「調査対象外(別シンボル)」として分離記録する。

## 7. 注意事項

### 7.1 read-only 厳守の徹底

本指示書では **コードの変更を一切行わない**。読み取り系のみを使用し、DB は SELECT のみ。書き込みは §5 レポートファイル作成のみ例外。R-1 の「中段化」を**再現するための編集・保存操作も行わない**(ロジックの事実から経路を記録する)。

### 7.2 judgement-free の徹底

調査結果は **事実列挙のみ**。修正方針・設計結論・推奨は含めない。

事実列挙の典型例:
- ✅「コンボ詳細は 6 BOOLEAN を 6 行で描画、比較は『その場 / 後ろ受け身 × DR 無 / 有』の 4 セルに集約(shimmy 2 列を別表示)。有利フレームは詳細が独立行、比較が末尾列」(表示方式差異の事実)
- ✅「起き攻め表示パスで `中段` / `mid` のヒットは 0 件。段表現は move 一覧の `properties` 描画(別コンポーネント)にのみ存在」(段表現経路の事実)
- ✅「`autoStarterMoveId` は recipe[0].moveId を `movesById` で引いた move の id。category による分岐はなし」(導出ロジックの事実)
- ❌「よって中段化はこの共通関数の取り違えが原因なので分離すべき」(判断 = 禁止)
- ❌「始動技プルダウンは安全に除去できる」(判断 = 禁止)

### 7.3 全数性の徹底(本調査の核心)

本調査の価値は **M12-03 修正設計の前提となる現状を 1 件も取りこぼさないこと**。grep は両系統で実行し、ヒット 0 件の領域も「0 件であった」と明示する。判断に迷う箇所は「判断せず事実だけ記録」する(設計判断は設計担当)。

### 7.4 設計担当への質問チャネル

調査内容で迷った場合、製造担当(調査担当)は **Plan Mode CLI 直接質問**(playbook §8.4.1)で開発者を介して設計担当に確認する。直接の Q&A セッションは設けない(playbook §1 役割分離)。

### 7.5 関連教訓

本指示書は調査担当運用パターン(architecture-patterns §6)に基づく。retrospective-digest §1 パターンA「症状のレイヤ ≠ 真因のレイヤ。フロント↔バックエンドを決めつけず両層を疑う」を R-1 真因切り分けの中核に据える。「想定外の発見が価値」(§0.7)/「設計担当のコンテキスト温存と判断品質向上の両立」(調査担当 = 事実列挙、設計担当 = 判断)を継承する。
