## 1. 背景と目的

### 1.1 背景

M12-06 はフェーズ2(先行リリース準備)の最終サブ。完了 = **フェーズ2 完了 = 先行リリース実施点**。M12-01〜05 で UX・正しさ・seed・B-7 が片付いた後、(1) フェーズ2 全体の統合 E2E を通し確認し、(2) 先行リリース配布判定を行う。

最大の回帰リスクは **E-1**:CHANGE-043 で全 nullable メタデータが presence-detection 単一トライステート(キー不在=不変更 / null=NULL クリア / 値=更新)へ統一された後、「**通常編集で触っていない項目が消える**」退行が起きうる。既存 `combo-crud.spec`(仮登録・メモ中心)はこの観点の自動検証が穴(handover §3.2 / §3-c)。

### 1.2 目的

1. **E-1 自動 spec 化(最優先)**: 多項目メタデータのコンボを 1 項目だけ編集 → 他項目が保持される(+ クリア時は当該項目のみ NULL)ことを Playwright で検証する。
2. **フェーズ2 統合 E2E の棚卸し + 穴埋め**: 主要フローのスモーク/回帰が既存 spec で覆われているかを確認し、不足を最小限で補う。
3. **先行リリース配布判定**(§7、開発者実施): M12-overview §6 の観点を具体化したチェックリストで判定する。

### 1.3 このサブで作らないもの
- 新機能・新画面(本サブは検証のみ。実装の修正が要る退行を発見したら独自対応せず設計担当へ報告)。
- **CI 構築**(本フェーズ非構築 = phase2-overview M8-02。ローカル実行のまま)。
- 視覚 / レスポンシブ / LAN / 実機の自動化(手動 E2E 継続)。
- 英語ロケールの E2E(フェーズ3)。

## 4. 詳細仕様

### 4.1 E-1 回帰 spec(最優先・実装方式非依存で記述)

- **準備**: 多項目メタデータを持つコンボを 1 件作成(§3.4.2 で確定した nullable 項目のうち、memo + damage + drive_damage + ゲージ + knockdown_advantage + 起き攻め複数を値ありで設定)。
- **保持検証(本体)**: 編集画面で **1 項目だけ**変更(例: memo のみ書き換え)→ 保存 → **リロード後 or 再取得で他の全項目が元のまま保持**されていることをアサート。presence-detection(キー不在=不変更)が効いていることの回帰ネット。
- **クリア検証(対)**: 編集画面で 1 項目を**クリア**(present + null)→ 保存 → 当該項目のみ NULL・**他項目は保持**をアサート。
- **記述方針**: 特定の DOM 実装に依存せず test-id ベースで記述(M5-2)。製造担当の実装裁量を想定し、アサーションの意図(保持/クリアの区別)を明確化。

### 4.2 統合 E2E の棚卸し・穴埋め

- §3.4.1 の対応表で、フェーズ2 主要フロー(5体の登録・閲覧 / 取込済みデータの表示 / custom_states 付与・表示 / コンボ CRUD / 比較 / セットプレイ / 仮登録→本登録昇格)のスモーク/回帰が既存 spec で覆われているかを判定。
- **不足分のみ最小限で穴埋め**する。既存 spec で足りるフローに重複 spec を増やさない(過剰作成回避)。
- 穴埋めの要否・対象は完了報告で根拠とともに示す。

## 開発者への確認事項

1. **E-1 が検証する nullable 項目セット**
   何を確認したいか: E-1 spec の「触らず保持」対象を、DES-002 §4.2 の presence-detection 全項目(memo/damage/drive_damage/ゲージ/knockdown_advantage/situation/起き攻め6)で網羅するか、代表サブセット(例 memo + damage + drive_damage + 起き攻め1)で足りるか。
   なぜ確認が必要か: 全項目網羅は堅牢だが spec が重くなる。回帰ネットの目的(presence-detection が効くことの担保)は代表サブセットでも満たせる。
   暫定案: **代表サブセット(複数型をまたぐ memo〔文字列〕+ damage〔数値〕+ drive_damage〔小数〕+ 起き攻め〔BOOLEAN〕+ situation〔custom_states 系〕)** で 1 spec、加えてクリア検証 1 spec。全項目網羅をご希望なら拡張します。

2. **先行リリース配布判定の実施タイミング**
   何を確認したいか: §7 チェックリストを、製造担当の E2E + レビュー通過後すぐ開発者が実施し、その結果をもって M12 完了処理(フェーズ2 完了)へ進む段取りでよいか。
   なぜ確認が必要か: 配布判定は開発者ゲートのため、設計担当・製造担当の工程と分離して進む。
   暫定案: E2E 緑 + レビュー OK → 開発者が §7 実施 → 全 OK で先行リリース実施 → 設計担当が M12 完了処理(教訓メモ転記・フェーズ2 完了処理)。
