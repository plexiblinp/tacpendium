## 0. この指示書の特殊性(最初に読む)

本指示書は通常の製造指示書ではなく、**調査担当運用パターン**(architecture-patterns §6)に基づく read-only の事実調査である。実装・設計変更は一切行わない。

### 0.1 製造担当として起動 → 調査だけ実施して閉じる

- あなた(調査担当 Claude Code)は製造担当として起動するが、本指示書 §4 の調査を実施して §5 のレポートを出力したらセッションを閉じる。実装には進まない。
- 本プロジェクトで調査担当運用は 6 例以上の実績がある(M5-RESEARCH-01 / M6-RESEARCH-01 / M7-RESEARCH-01〜04 等、architecture-patterns §6.2)。本指示書はその系譜に連なる。

### 0.2 read-only 厳守

- ファイルの作成・編集・削除を行わない。例外は §5 の調査レポート 1 ファイル(`docs/instructions/M8-RESEARCH-01-report.md`)の新規作成のみ。
- `git` 操作・マイグレーション実行・`pnpm install` 等の環境変更を行わない。
- 調査手段は `view` / `grep` / `ls` / `cat` 等の閲覧系コマンドに限る。

### 0.3 判断・提案を含めない

- 本調査は **事実の列挙のみ** を行う。「Playwright を導入すべき」「この工数なら前倒しが妥当」等の採否判断・提案・推奨は書かない。採否は設計担当 + 開発者が本レポートを材料に行う。
- 「工数の見積り」も、あなたが工数を算定するのではなく、**設計担当が工数を算定できる素材**(シナリオ件数・ステップ数・自動化不可手順の件数・data-testid 未付与の件数等)を事実として列挙する。「N 時間かかる」「容易/困難」のような評価語は書かない。
- 想定外の発見・明らかな矛盾は §5 の「特記事項」に **判断を加えず事実として** 記録する(architecture-patterns §6.1)。

### 0.4 本調査の主目的

E2E テスト自動化(Playwright)をフェーズ2 で前倒し導入するかの採否判断に向けて、現行の手動 E2E の規模・自動化適合性・導入前提環境を実数化する。設計書本体の現状では Playwright はフェーズ3以降の予定(DES-002 §12 / SUPP-001 §4.5)であり、本調査結果次第で設計担当が CHANGE-024(DES-002 §12 改訂)の起票要否を判断する。

### 0.5 結果の扱い

- レポートは `docs/instructions/M8-RESEARCH-01-report.md` に出力する(§5 のテンプレート)。
- 設計担当が本レポートを受け取り、phase2-e2e-playwright-handover §2 の開発者疑問 (4) Claude 委任可否 / (5) コスト の実数化に用いる。(1) 理由 / (2) 自動・手動分担 / (3) 手動頻度 / (6) コスパ は設計担当の整理範囲のため、本調査の対象外。

## 1. 背景

- 現在頻繁に実施している開発者 E2E は **手動の実機 E2E**(シナリオを開発者がブラウザで実行)。Playwright 等の自動 E2E は未導入(SUPP-001 §4.5「フェーズ1ではPlaywright等を導入しない」、DES-002 §12「Playwright(フェーズ3以降)」)。
- 開発者は手動 E2E がボトルネックで早期改善を希望。フェーズ2(M8〜M12)は各大MS に統合 E2E があり、自動回帰の償却が効く可能性がある一方、初期構築コストと自動化しきれない手順(LAN 実機・視覚判断)が論点(phase2-e2e-playwright-handover §2)。
- 本調査はこの論点を実数化する。

## 4. 調査内容(事実列挙のみ)

以下の 4 軸を調査する。各軸とも **事実(件数・一覧・有無)** のみを §5 レポートへ記録する。コマンド例は参考であり、より効率的・正確な手段が存在する場合は調査担当の裁量で変更してよい(grep のパターン取りこぼし等に注意)。

### 4.1 軸 A: 現行手動 E2E シナリオの棚卸し

**手動 E2E シナリオは 2 形態で `docs/instructions/phase1` 配下に存在する**:

1. 個別ファイル形式(指示書の肥大化回避のため分離): 例 `m7-03-e2e-scenarios.md` のような `*e2e-scenarios*.md`。
2. 指示書内インライン記載: 例 `M7-04-1-change019-cleanup-and-bug5.md` のように、指示書本文の §5.2「E2E シナリオ」節等に直接記載。

両形態を網羅して、以下を列挙する:

- シナリオを含むファイルの一覧(個別ファイル / インライン記載の指示書、それぞれ)。
- 各ファイルに含まれるシナリオの本数(「シナリオA / B / C…」「U-1 / U-2…」等の単位)と、合計本数。
- 各シナリオが対象とする画面・機能(コンボ登録 / 編集 / 削除 / 一覧フィルタ / 比較 / タグ / セットプレイ紐付け / 設定 / ウィザード / ホーム 等)。

```bash
# 個別ファイル形式の洗い出し
ls docs/instructions/phase1/ | grep -i 'e2e'
# インライン記載を含む指示書の洗い出し(見出し語で当たりを付ける)
grep -rln 'E2E シナリオ\|E2Eシナリオ\|シナリオ[A-Z]\|シナリオ [A-Z]\|U-[0-9]' docs/instructions/phase1/
# 各ファイルのシナリオ単位の出現
grep -nE 'シナリオ *[A-Z0-9]|^### *U-[0-9]|^#### *シナリオ' docs/instructions/phase1/<file>
```

### 4.2 軸 B: data-testid 付与状況

Playwright のセレクタ安定性に直結する `data-testid`(または同等の安定属性)の現状を列挙する:

- `web/src` 配下の `data-testid` 付与箇所の総数と、付与されているファイル一覧(feature 単位で集計)。
- 軸 A で列挙したシナリオが操作する主要 UI 要素(ボタン・入力・行・モーダル等)について、安定セレクタ(`data-testid` / 一意な `role`+`name` / 一意な `id`)が既に存在するか、存在しないかを要素単位で列挙(「主要」の線引きはせず、シナリオ本文が言及する操作対象を機械的に拾う)。
- `data-testid` 以外に既存で使えそうな安定属性(`aria-label`、`role`、固定 `id`)の使用状況の概数。

```bash
grep -rn 'data-testid' web/src/ | wc -l
grep -rln 'data-testid' web/src/
grep -rcn 'aria-label\|role=' web/src/ | grep -v ':0$' | head -40
```

### 4.3 軸 C: シナリオ → Playwright spec 変換の素材

軸 A の各シナリオについて、spec 変換の手数を設計担当が算定できる素材を列挙する(算定・評価はしない):

- 各シナリオのステップ数(手順の箇条書き行数 or 番号付き手順の数)。
- 各シナリオに含まれる **自動化が困難または不可能な手順** の件数と内容。具体的には次の語を含む手順を該当候補として列挙する: `LAN` / `実機` / `スマホ` / `QR` / `スクリーンショット` / `目視` / `見た目` / `レイアウト` / `崩れ` / `レスポンシブ` / `別端末`。
- 各シナリオで前提となる DB 状態・seed 依存(「リュウのコンボが N 件ある状態」等、データ前提を述べている手順)。

```bash
# シナリオ本文中の自動化困難候補の語を含む手順
grep -nE 'LAN|実機|スマホ|QR|スクリーンショット|目視|見た目|レイアウト|崩れ|レスポンシブ|別端末' docs/instructions/phase1/<file>
```

### 4.4 軸 D: Playwright 導入の前提環境

導入初期コストに関わる現状を列挙する:

- `web/package.json` の `devDependencies` / `scripts` の現状(Playwright・@playwright/test の有無、E2E 関連 script の有無)。
- リポジトリに CI 設定が存在するか(`.github/workflows/` 等のディレクトリ・ファイルの有無と、存在する場合その内容の概要)。
- フロントエンドのローカル起動手段(`pnpm dev` 等の既存 script)と、ポート・起動方法の記述箇所。
- 既存のテスト実行手段(Vitest の script、Go test の実行方法)の記述箇所。

```bash
cat web/package.json
ls -la .github/workflows/ 2>/dev/null || echo "no .github/workflows"
grep -nE '"(dev|test|e2e|playwright)"' web/package.json
```

- §0.3 のとおり、評価語(容易/困難/妥当/べき)・推奨・採否提案を書かない。検出した語が判断語か事実かに迷ったら、件数・一覧・有無に還元できる形で書く。
