## 0. この指示書の特殊性

### 0.1 ★★本サブは「黒窓を消す」サブではない

**★★黒窓を消すのは `M34-02` である。⇒ 本サブは、消しても開発が止まらない足場を先に作る。**

**★★1 本にまとめない理由＝OS 分離を誤ると Linux の devContainer でビルドが通らなくなり、開発そのものが止まる**（`M34-overview` §7）**。⇒ そこを固定してから常駐の中身へ進む。**

### 0.2 ★★開発者の判断は決着している

| # | 事項 | 決着 |
|---|---|---|
| **★★1** | **受領した方式を採るか** | **★★採る**（2026-09-09・`D-790`） |
| **★★2** | **`127.0.0.1` 固定にするか** | **★★固定しない。⇒ 待ち受けは現行のまま。★ブラウザで開く URL だけを `127.0.0.1` にする** |
| **★★3** | **流用元をどう持ち込むか** | **★★移植する**（参照しない）**。⇒ ライセンス上の扱いは `M34-overview` §3.2 が正本** |

### 0.3 ★★移植元は本リポジトリの外にあり、本セッションからは見えない

**★★流用元＝`autopilot-combomgr/projects/moves-input-tool`。⇒ 開発者の非公開リポジトリである。**

**★★したがって本サブは、移植元のファイルを開発者から受け取ってから進む形になる。⇒ 受け取り方が決まっていないなら、そこで止めて報告すること**（`CLAUDE.md` §9 の「進めて報告する」の例外＝**進めようが無い**）**。**

**★受領した実装方式の要約は `docs/progress/M34-RESEARCH-01-report.md` に在る。⇒ 中身の設計はそこから読めるが、コードそのものは無い。**

## 2. やること

### 2.1 ★★段 1——実査 4 件（**★1 行も書き換えずに、先に数える**）

| # | 実査 | 出し方 |
|---|---|---|
| **★★1** | **CLI サブコマンドが在るか** | **`cmd/` の全数を読み、引数を解釈している箇所を挙げる。⇒ 在るなら「引数なしの起動を常駐モードとして扱う」案が既存の挙動と衝突しないかを書く** |
| **★★2** | **`golang.org/x/sys/windows` を使うか `syscall` だけで足りるか** | **★★前者は依存追加に当たる**（`CLAUDE.md` §6）**。⇒ 使うなら、実装へ進む前に提案して止まること。★`go.mod` の現状を実測して書く** |
| **★★3** | **`DES-001` の配布方針が他 OS を含むか** | **★含むなら、Windows 専用コードをビルドタグでどう切るかが本サブの中心になる。⇒ 含まないなら分離は軽い** |
| **★★4** | **★★移植元にライセンスファイルが在るか ／ 第三者由来の断片が無いか** | **`M34-overview` §3.2.2 の 2 件。⇒ 探した場所を挙げること。★「無い」と書くには、`LICENSE` だけでなく `README` の記述・ファイル冒頭の `SPDX` ヘッダ・`go.mod` の隣の表記まで見る必要がある** |

**★★あわせて実測すること 1 件＝ログと DB の実際の置き場**（§2.4）**。**

### 2.2 ★★段 2——OS 分離を先に固定する

| # | やること |
|---|---|
| **★★1** | **Windows 専用コードを `internal/desktop/`**（仮）**へ置き、ビルドタグで切る。⇒ 命名は実装時に確定してよいが、`internal/` の既存の層**（`api` / `service` / `repository` / `model` / `infra`）**のどれでもない新しい面であることを報告に書くこと** |
| **★★2** | **★★`go build ./...` が Linux で通ることを固定する。⇒ 「通った」ではなく、通ることを機械で確かめる形にすること** |
| **★★3** | **`go vet ./...` と `go test ./...` も Linux で通ること。⇒ ビルドタグの掛け違いは `vet` で出ることがある** |
| **★4** | **Windows 側は本サブではビルドしなくてよい。⇒ 実機確認は `M34-02` の後に開発者が行う**（§5） |

**★★分離を先にやる理由＝ここを誤ると、以後のすべての手番が「ビルドが通らない」から始まる。⇒ `M34-02` へ持ち越さない。**

### 2.4 ★★段 4——★★ログと DB の置き場を実測し、常駐で動かないことを確かめる

**★★これは黒窓対策の前提である。⇒ `-H=windowsgui` で標準出力が消えると、ログファイルだけが手掛かりになる**（`M34-overview` §4.1）**。**

**★★`config.toml.example` の既定は次のとおりである**（**設計卓が実測・2026-09-09**）**。**

> **★★★【2026-09-09 errata＝`D-795` / 計測点 `M-149`】下表の DB とログの名前は誤りである。⇒ 実測は `%APPDATA%/tacpendium/tacpendium.db`**（`internal/infra/db/db.go:191`）**と `logs/tacpendium.log`**（`internal/config/config.go:57`）**である。**
>
> **★原因＝`M28-01` の改名**（`combomgr` → `Tacpendium`）**の反映漏れ。★「DB とログは別の場所である」という結論そのものは変わらない。**
>
> **★★本文は書き換えない**（`D-274` (3)＝**完了済みサブの指示書は注記で追随する**）**。⇒ 正本は `M34-overview` §5.1.7 である。**

| 対象 | 既定 | 性質 |

| **★★ログ** | **`logs/combomgr.log`** | **★★相対パスである** |
| **設定ファイル** | **`config.toml`** | **★★相対パスである** |

| # | 実査すること |

| **★★2** | **★★カレント基準なら、起動経路が変わるとログの出先が動く。⇒ 常駐化すると起動経路が増える**（**ダブルクリック ／ ショートカット ／ 将来のスタートアップ登録**）**。★「ログフォルダを開く」が毎回別の場所を指しうる** |
| **★★3** | **★動くなら、基準を実行ファイルの位置へ寄せることを提案すること。⇒ 本サブで直すか `M34-02` で直すかは、影響範囲を見てから決めてよい**（`CLAUDE.md` §9-2＝**自己判断でよい実装詳細。★検討した案と理由を報告へ**） |

**★★これを段 4 に置く理由＝`M34-02` の「ログフォルダを開く」は、ログの場所が一意でないと作れないからである。**
