### 0.1 ★★本サブが在る理由 — 設計卓の見立てが誤っていた

## 2. やること

### 2.1 ★★段 1-a：`ComboResponse.affectedMoves`

| # | 内容 |
|---|---|
| **★★1** | **判定式**（`DES-003` §3.4 の `EXISTS`）**と同じ 1 か所から導出すること。★★式を書き写さない**——**書き写すと表示と絞り込みが静かにずれる。⇒ `CHANGE-159` §2 が「判定式は 1 か所しかなく、SELECT の派生列と一覧の WHERE が同じ式を共有する」と明言している。** |
| **★★2** | **一覧の N 件ぶんはバッチ取得で作ること**（先例＝`ListSetupsByComboIDs`）**。★N+1 にしない。** |
| **★3** | **`nameJa` は NULL 可。⇒ 引けないときは `code` へ落ちる**（先例＝`starterMoveNameJa`）**。** |
| **★★4** | **空のときは `[]` を明示すること**（キーごと消さない）**。★理由＝`affectedByGameUpdate` に `omitempty` を付けなかったのと同じである。** |
| **★★5** | **`affectedMoves.length > 0` で影響の有無を判定する経路を作らないこと。⇒ 真偽の正本は `affectedByGameUpdate` の 1 本である。** |
| **★6** | **`GET /api/moves` の応答 DTO にもマーカーを載せるかを判断し、報告に書くこと**（**★載せなくても本サブは成立する。⇒ 載せるなら理由を書く**）。 |

### 2.2 ★★段 1-b：告知の経路 2 本 ＋ `COUNT`

| # | 内容 |
|---|---|
| **★★1** | **`GET /api/notices/game-update`＝`{currentDataVersion, affectedCount, postponedForVersion?}` を常に 200 で返す。★204 にしないこと**（`CHANGE-162` §2.1）**。** |
| **★★2** | **判定式を共有した `COUNT` を新設すること。★式を書き写さない。** **★現行リポジトリは `LIMIT` 付きの `SELECT` しか持たない。⇒ 一覧 API の `count` では総数が取れない**（`Count: len(items)` かつ `limit` が丸められる）**。** |
| **★★3** | **`POST /api/notices/game-update/postpone`＝要求本文を取らない。サーバが `games.current_data_version` を読んで書く。** |
| **★★4** | **保存先＝`filepath.Dir(dbPath)` 直下の `.game-update-notice.json`。⇒ マイグレもブラウザストレージ台帳も消費しない。** |
| **★★5** | **★★延期が抑止するのはバナーだけである。一覧のボタンは抑止しないこと。⇒ ここが分水嶺である**（`CHANGE-162` §2.3。**ボタンまで消すと LAN では許容できない**）**。** |
| **★6** | **エラー契約の全行を報告に書くこと**（`CHANGE-159` §1.1 と同じ粒度）。 |
