## 1. 背景と目的

### 1.1 背景——**`DES-005` §5.15 は列構成を定義していない**

**`M23-01` が実測して記録した**（`DES-005` §5.15 の末尾）。

> **★本節は列構成を定義していない**（2026-08-20 記録）。**上の「表示項目」は 2 行だけであり、実装が持っている「ルート」「タグ」といった列は本節に根拠が無い。**

**⇒ 本サブは「実装に合わせて書く」のではなく、「どの列を持つべきかを決めて、実装と設計書の両方を揃える」サブである。**

### 1.2 ★★中心の発見——**2 つの症状は同じ根から出ている**

**入力のうち 3 件が、1 つの原因に収束する。**

| 症状 | 原因 |
|---|---|
| **ゴミ箱の「ルート」列が常に `(レシピ表示なし)` の固定値** | **論理削除の時点でサービス層が `combos.recipe_cache` を NULL にしている。** **⇒ 削除済み行に出せるレシピは構造的に存在しない** |
| **ゴミ箱の名無しセットプレイが「(名称未設定)」でしか識別できない** | **論理削除の時点で `recipe_cache` を物理削除しているため、レシピ文字列へのフォールバックが到達しない** |
| **セットプレイのレシピ文字列を解決する処理に本番の呼び出し元が 0 件** | **★上の 2 つを解く手段が、使われないまま存在している** |

**★★3 件目は「撤去するか」という形で `M23-08` へ振られていたが、設計卓が本サブへ差し戻した**（**D-513**）——**撤去の可否は「レシピ文字列を画面に出すか」に従属し、それは本サブの判断だからである。**

### 1.3 ★★そして、同じ根に対して逆の答えを出す

**★本サブでいちばん重要な判断である。**

| 対象 | 答え | なぜ |
|---|---|---|
| **コンボのルート列** | **★消す** | **コンボは `memo` と始動状況（キャラ・始動技・position 等）を持っており、それだけで行を識別できる。** **⇒ レシピ列は「あると親切」であって「無いと困る」ではない** |
| **セットプレイの識別** | **★出す**（レシピ文字列で） | **セットプレイは名前が空だと「(名称未設定)」しか無く、識別手段がゼロになる。** **★完全削除は不可逆であり、取り違えは取り返しがつかない** |

**★★「根が同じなら答えも同じ」ではない。** **これは `architecture-patterns` §11 の「機能ごとに『出すか出さないか』を決める」とまったく同じ形であり、`M23-03` が 6 か所を 1 件ずつ違う扱いにしたのと同じ判断の型である。**

**★判断の軸は「その情報が無いと利用者が困るか」であって「技術的に出せるか」ではない。** **どちらも技術的には出せる**（§3.3-1 / §3.3-2 で確かめる）。

### 1.4 ★もう 1 つの軸——**「出せない列」と「出していない列」は別である**

| 列 | 状態 | 答え |
|---|---|---|
| **ルート** | **★出せない**（`recipe_cache` が NULL であり、列を残す限り常に定数） | **消す**（§4.1） |
| **タグ** | **★出せる。出していないだけ**（一覧 API はタグをバッチ取得し、応答へ常に非 nil で載せている。描画していない） | **出す**（§4.2） |

**★この 2 つを同じ「列が空である」として扱わないこと。** **前者は「存在しない概念の列を残さない」**（**D-458** で残日数に適用したのと同じ論理）、**後者は単に配線が抜けている。**

### 1.5 目的

1. **ルート列を撤去する**（§4.1）。
2. **タグ列を描画する**（§4.2）。
3. **セットプレイをレシピ文字列で識別できるようにする**（§4.3）。**★`resolve-setup-recipe` の本番呼び出し元をここで作る。**
4. **ゴミ箱の一括選択をコンボとセットプレイの両方に対応させる**（§4.4）。
5. **`DES-005` §5.15 に列構成を定義する**（§4.5）。**★「未定義である」という記述を埋める。**
6. **警告表示の仕上げ 3 件**（§4.6）。
7. **不活性なテストを作り替える**（§4.7）。

## 4. 詳細仕様

### 4.1 ルート列を撤去する

**★列そのものを消す。** 「常に定数を出す」を「空文字を出す」へ変えるのではない。

**★理由**——**論理削除の時点で `combos.recipe_cache` が NULL になっており、削除済み行に出せるレシピは構造的に存在しない。** **⇒ 列を残す限り常に定数になる。**

**★同じ論理を残日数に適用した先例がある**（**D-458** / `M23-01`）——**「存在しない概念の列を残さない」。** **★開発者も同じ理由で「常に表示なしなら一覧から消したい」と述べている**（2026-08-20 実機確認時）。

**★コンボは `memo` と始動状況を持っており、レシピ列が無くても行を識別できる。** **⇒ これが §4.3 と答えが分かれる理由である**（§1.3）。

**★i18n のキーも消すこと**（見出しと `(レシピ表示なし)` の文言）。**★使われないキーを残さない。**

### 4.2 タグ列を描画する

**★消さない。出す。**

**ルート列と性質が逆である**——**一覧 API はタグをバッチ取得し、利用者で絞り込み、応答へ常に非 nil で載せている。描画していないだけである。**

**⇒ 新しくデータを取りに行かないこと**（§3.3-3 で確かめる）。**★取りに行く実装になったら、それは想定が違っている。報告すること。**

**★見せ方**——**一覧画面の既存のタグ表示に揃える。** **ゴミ箱専用の新しい見せ方を作らない**（**D-417**）。**★タグが 0 件のときの表示も既存に揃える。**

### 4.3 ★★セットプレイをレシピ文字列で識別できるようにする（**本サブの中心**）

#### 4.3-1 何が問題か

**ゴミ箱の名無しセットプレイは「(名称未設定)」でしか識別できない。** **論理削除の時点で `recipe_cache` を物理削除しているため、レシピ文字列へのフォールバックが到達しない。**

**★完全削除は不可逆である。** **⇒ 取り違えると取り返しがつかない。** **★これがルート列と答えが分かれる理由である**——**セットプレイは名前が空だと識別手段がゼロになる。**

#### 4.3-2 どう解くか——**`setup_steps` から組み立てる**

**`setup_steps` は論理削除で消えていない。** **⇒ そこからレシピ文字列を組み立てられる。**

**★★`resolve-setup-recipe` に相当する処理が既に存在し、本番の呼び出し元が 0 件である。** **⇒ 本サブがその呼び出し元になる。**

**★これは `D-513` の差し戻しの決着でもある**——**「撤去するか」ではなく「使う」で閉じる。** **⇒ 完了報告に「撤去しなかった。使う側で決着した」と明記すること**（§4.9-2）。

#### 4.3-3 ★どこで組み立てるか——**サーバ側**

**削除済みセットプレイ一覧の応答にレシピ文字列を載せる。**

**★理由 2 つ。**

1. **`resolve-setup-recipe` がサーバ側の処理である。** クライアントへ `setup_steps` を丸ごと送って組み立て直すのは、既にある処理を使わない形になる。
2. **★表記はプリセット・エイリアスに依存する**（`DES-004`）。**サーバ側の解決経路がその責務を持っている。** **クライアント側で組み立てると、その規則を 2 か所に持つことになる**（`E-76`＝同じ情報を 2 か所に持つと必ずドリフトする）。

**★N+1 に注意すること。** **一覧の件数ぶん解決する形になる。** **1 件ずつ問い合わせる実装になるなら、一括で取る形に変えること。** **★件数と方式を報告に書くこと。**

**★応答にフィールドが増えるため `DES-002` §4.2 の改訂対象である**（設計卓が `CHANGE-127` で反映する）。

#### 4.3-4 ★採らない案——**論理削除で `recipe_cache` を消すのをやめる**

**★これなら根本から解けるが、採らない。**

| # | 理由 |
|---|---|
| 1 | **削除の副作用を変える判断であり、`DES-002` §4.2 の契約に触る。** **★`M23-03` が as-built で固定したばかりである**（**D-504**） |
| 2 | **コンボ側の `recipe_cache` の NULL 化は `PUT` の旧行の扱いと絡んでいる**（`DES-002` §4.2 の `PUT` の副作用）。**片方だけ変えると非対称が増える** |
| 3 | **★本サブは画面のサブである。** サーバ側の削除の副作用を変えるのは射程が違う（`M23-08` でも扱っていない） |

**⇒ 読み取り側で解く。** **★この判断と理由を完了報告に書くこと**（§4.9-3）。

### 4.4 一括選択をコンボとセットプレイの両方に対応させる

**現在の選択状態はコンボ id の配列であり、セットプレイを混ぜると id が衝突する。** **⇒ `D-491` が意図的に持たなかった。**

**★解き方は 2 つある。どちらを採ってもよい。理由を報告に書くこと。**

| 案 | 形 |
|---|---|
| **(a)** | **選択状態を型付きにする**（`{ kind: "combo" \| "setup", id: number }` 等） |
| **(b)** | **コンボ用とセットプレイ用の 2 本の配列を持つ** |

**★守ること 3 点。**

1. **★一括操作（復元・完全削除）が、選んだ種別に応じて正しい API を叩くこと。** **★コンボの id でセットプレイの API を叩く形が絶対に起きないこと**（§5.1-4）。
2. **★「全選択」の対象範囲を決めること**——**表示中のタブ／テーブルの中だけか、両方か。** **暫定案＝表示中のテーブルの中だけ**（`M23-02` がセットプレイを独立テーブルに置いた＝`DES-005` §5.15）。

## 11. 開発者への確認事項

**★2 件。どちらも暫定案で進み、投入は止めない。**
