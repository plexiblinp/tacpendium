## 1. 背景と目的

### 1.1 何が起きているか

**`M24-09c` の E2E 並列実行で、`VAL-C02`（同一キャラ・同一レシピ・同一状況のコンボの重複登録）の検証をすり抜けて、同一識別キーの本登録コンボが 2 件同時に存在した。**

**★製造は決定論的な再現手順を持っている**（設計伝達レポート §4-1）。**⇒ 本サブはそこから始まる。**

### 1.1.1 ★★機序——**check-then-act**

| 段 | 起きること |
|---|---|
| 1 | **検証（重複の SELECT）が `BeginTx` の前に走る** |
| 2 | **2 つのリクエストが両方「重複なし」を見る** |
| 3 | **両方が INSERT する** |
| 4 | **6 項識別キー ＋ `recipe_hash` への UNIQUE 制約も無いため、DB 側でも止まらない** |

### 1.1.2 ★★これは `NFR203` の既知の未達である

> **`REQ-001` `NFR203` の逐語**——**「複数名利用時に同時実行による問題（データ競合・消失）が起きないこと。実現方式として楽観的排他制御を採用（`combos` テーブルに version カラムを保持し更新時にバージョン比較）」**

**★★楽観排他は UPDATE を守る手であって、INSERT を守らない**——**比較すべき既存行が無い。**

**⇒ `VAL-C02` の check-then-act は、`NFR203` が挙げた実現方式が構造的にカバーできない領域である。** **★「対策済み」の顔をした穴が空いている。**

**★あわせて `FR406`（LAN 共有・複数端末から編集）はフェーズ3＝現行フェーズの要件である。**

**★★`M22` が LAN・多人数モードを実装した時点で、2 クライアントから到達しうる状態になっている**（`M24-09c` の実査）。**⇒ 「将来の要件」ではなく「今の到達可能性」である。**

### 1.1.3 ★★害の形——**静かに壊れる**

**同一識別キーの本登録が 2 件生存すると:**

| # | 何が起きるか |
|---|---|
| **1** | **`PUT`（識別キーを変える編集）は「旧行を論理削除 → 新行を登録」なので、どちらが supersede されるかが不定になりうる** |
| **2** | **`materialize` は「同一レシピ ＋ `hit_type = punish_counter` の既存を見つけたら生成せず既存 id を返す」ので、返る id が不定になる**（`DES-006` §2.3・`CHANGE-089`） |
| **3** | **利用者から見ると「消しても消しても同じコンボが残る」形になる** |

**★どれもエラーにならない。⇒ 気づく契機が無い。**

### 1.1.4 ★★起票時に設計卓が確かめていないこと

**設計卓は実装ソースを読めない。** 以下は**設計書からの引用**であり、実装の現物は確かめていない。

| 対象 | 設計書が示すこと | **分からないこと** |
|---|---|---|
| **識別キー** | **`DES-005`:1336 の逐語＝`(character_id, starter_move_id, position, opponent_stance, hit_type, opponent_size)` ＋ `recipe_hash`** | **★実装の `DuplicateKey` がこのとおりか** |
| **DSN の `_pragma`** | **`DES-002` §4.2 の逐語＝`file:` ＋ パーセントエンコードしたパス ＋ `_pragma` 4 種**（`busy_timeout` / `foreign_keys` / `journal_mode` / `synchronous`）。**`M23-10` / `CHANGE-142` で根治済み** | **★`busy_timeout` の実値**（`SUPP-001` §7.1.1 は「5 秒」と書いているが、それは `M20-05` 時点の記述である） |
| **トランザクションの開き方** | **記述が無い** | **★★`database/sql` の `BeginTx` をそのまま使っているか。`BEGIN IMMEDIATE` を発行する手が在るか** |
| **`VAL-C02` の検証位置** | **記述が無い** | **★どの層に在るか**（サービス層 / リポジトリ層） |

**⇒ 上記を断定形として扱わないこと。§3.3 で 1 件ずつ実査し、食い違ったら報告すること**（計測点 `M-77` の再発防止）。

### 1.2 目的

**`VAL-C02` の判定と登録を、割り込まれない 1 つの操作にする。**

**★★判定ロジックそのものは 1 文字も変えない。** **変えるのは「いつ判定するか」だけである。**

### 1.3 ★★このサブで作らないもの（スコープ外）

| # | 作らないもの | 理由 |
|---|---|---|
| **1** | **★★UNIQUE 制約の追加** | **開発者が案 (b) を選択した**（`D-568`）。**★理由 3 つが `P-43` に記録されている**——**(a) `recipe_hash` は `combos` の列ではなく、レシピの実体は子表 `combo_steps` である**〔子表を跨ぐ UNIQUE は書けない〕**／(b) `DES-006` §2.3 の「NULL 同士は一致」を素の UNIQUE では再現できない**〔SQL の UNIQUE は NULL を互いに異なるものとして扱う〕**／(c) `DES-006` §2.1 自身が「条件で書くと 2 本目が書き起こされて静かにずれる」と戒めている** |
| **2** | **`VAL-C02` の判定ロジック**（6 項 ＋ `recipe_hash`） | **★1 文字も変えない。** 変えるのは判定の時刻だけである |
| **3** | **`deleted_at IS NULL` ／ `is_draft = 0` の述語** | **★★1 文字も変えない**（`CHANGE-125` / `D-516`）。**`deleted_at IS NULL` は穴ではなく `PUT` を成立させるための条件である**——**外すとあらゆる編集が重複エラーで落ちる** |
| **4** | **楽観排他（`version` カラム）** | **★別の機構である。** 本サブは INSERT 経路を守る |
| **5** | **★保存ボタンの二度押し防止**（フロント） | **★★サーバ側が守られていれば、二度押しは 400 の重複エラーになるだけでデータは壊れない。** **⇒ §3.3-11 で確かめ、無効化していなければ報告する。直すのは `M24-04`（エディタ）の面** |
| **6** | **`VAL-P05` / `VAL-S04` ほかの個別の手当て** | **★★一律の手でそのまま守られるものは守られる。個別に手当てが要るものは §4.4 で報告するところまで** |
| **7** | **既存データに入り込んだ重複の掃除** | **★★別の話である**（§4.5）。**⇒ 検出だけ行い、消さない** |
| **8** | **接続プールの上限設定**（`SetMaxOpenConns`） | **★`DES-002` §4.2 が「無制限」を as-built として記録している。** 変えると `M23-10` の根治の前提が動く |

## 4. 詳細仕様

### 4.1 ★★採る手——**書き込みトランザクションを `BEGIN IMMEDIATE` で開始する**

#### 4.1.1 なぜ「境界を前へ動かす」だけでは足りないのか

**★★検証 SELECT をトランザクションの内側へ入れるだけでは、この欠陥は閉じない。**

**SQLite の既定の `BEGIN`（DEFERRED）は、最初の読みで read lock を、最初の書きで write lock を取る。**

**⇒ 2 つのトランザクションが両方 SELECT して「重複なし」を見たあと、順に INSERT できる。check-then-act はそのまま残る。**

**★★要るのは `BEGIN IMMEDIATE`**（**開始時点で write lock を取る**）。**⇒ 2 本目は 1 本目の commit を待ち、その後の SELECT は commit 済みの行を見る。**

#### 4.1.2 決めたこと

| 論点 | 決めたこと |
|---|---|
| **★★適用範囲** | **書き込みトランザクション全部。★経路ごとに選ばない** |
| **★なぜ全部か** | **★★経路ごとに選ぶと、次に足す経路が忘れる。** **`DES-006` §2.1 の「同じ条件にする」ではなく「同じ 1 本を呼ぶ」と同じ理由である** |
| **★★読み取り専用トランザクション** | **含めない。★不要に write lock を取らせない** |
| **並行度への影響** | **★実質変わらない。SQLite は WAL でも writer を元来 1 本に直列化している。** **⇒ `BEGIN IMMEDIATE` は新たな悲観ロックを導入するのではなく、ロックを取る時刻を早めるだけである** |
| **`NFR203` の「悲観ロックは採用しない」との関係** | **★抵触しない**（上記）。**★ただし `NFR203` の実現方式の記述は本 CHANGE で足りない部分を補う**（`CHANGE-136` §2.1） |
| **★発行方法** | **★★§3.3-5 の実査で決める。設計卓は指定しない**——**(i) DSN の `_txlock=immediate` は全トランザクションに効くため §4.1.2 の「読み取り専用は含めない」と衝突する。⇒ 採るなら理由を報告すること ／ (ii) 書き込み用のヘルパ 1 本で `BEGIN IMMEDIATE` を発行する形が筋である** |
| **★★`M23-10` の型と混同しない** | **`CHANGE-142` の「接続単位の PRAGMA は DSN で入れる」は接続単位の設定の話である。** **`_txlock` はトランザクション単位の話であり、同じ型ではない** |

#### 4.1.3 ★共通ヘルパが無い場合

**§3.3-3 で「各所で `BeginTx` を直接呼んでいる」と分かったら:**

1. **まず共通ヘルパ 1 本へ寄せる。**
2. **★寄せる作業と `BEGIN IMMEDIATE` の導入を、別のコミットに分けること**（**★どちらが原因で壊れたかを切り分けられる形にする**）。
3. **★寄せられない箇所が在れば、その理由を報告すること。**

### 4.2 ★`VAL-C02` の検証をトランザクションの内側へ入れる

| 論点 | 決めたこと |
|---|---|
| **やること** | **検証の SELECT を、登録と同じトランザクションの内側で行う** |
| **★★渡すもの** | **`*sql.Tx` を渡し、検証もその tx で読むこと** |
| **★★`*sql.DB` 直読みを残さない** | **`SUPP-001` §7.1.1 の一般規約（`D-360`）＝「署名が `*sql.Tx` を取るなら、その tx を読みにも使うこと。使わないなら取らないこと」。** **⇒ tx を取りながら `*sql.DB` で読む形を作らない** |
| **判定条件** | **★1 文字も変えない**（§1.3-2 / -3） |
| **★`PUT` 経路** | **★★同じ扱いにすること。** **`PUT` は「旧行を論理削除 → 新行を登録」を同一トランザクション内で行う**（`DES-006` §2.3）。**⇒ 既にトランザクションが在るので、開き方だけが変わる** |
| **★`materialize` 経路** | **★同じ扱い**（`DES-006` §2.3・`CHANGE-089`。**同一レシピ ＋ `punish_counter` の探索も check-then-act である**） |

### 4.3 ★★最大のリスク——**潜在的な自己デッドロックが顕在化する**

> **`SUPP-001` §7.1.1-3 の逐語**——**「接続プールが無制限・`busy_timeout` 5 秒 ⇒ 開いている書き込み tx の内側から非 tx の UPDATE を撃つと別コネクションになり `SQLITE_BUSY`」**（**`M20-05` が陽性対照で確認**）

**★★`BEGIN IMMEDIATE` にすると、この形が確実に踏まれるようになる。**

**理由＝DEFERRED では write lock を遅く取るため、そういう経路が「まだロックを握っていない」あいだにすり抜けられた可能性がある。IMMEDIATE では開始時から握るので、内側からの非 tx クエリは自分自身のロックと衝突する。**

| 論点 | 決めたこと |
|---|---|
| **★★これは悪いことではない** | **顕在化するのは、既に壊れている経路である**（`D-360` の規約に反している）。**⇒ 見えるようになるのは前進である** |
| **★ただし「直したのに壊れた」に見える** | **⇒ §3.3-7 で先に全数を洗い出すこと**（**母数付き**） |
| **★見つかったものの扱い** | **★★`*sql.Tx` を渡す形へ直せるものは直す。** **★直すと射程が広がるものは、直さずに報告すること**（**`RecomputePresetCache` は「コミット後に呼ぶ」が現在の規約であり、それは守られていれば踏まない**） |

#### 4.3.1 ★`SQLITE_BUSY` になったときの応答

| 論点 | 決めたこと |

| **★設計卓の指定** | **★★重複エラー（`VAL-C02` の 400 `validation_failed`）と混ぜないこと。** **★版不一致の 409 とも混ぜないこと**（`DES-006` §11.2＝**409 は 2 種類あり見分けはエラーコードで行う**）。**⇒ 第 3 の区別を作る** |

| **★★UI を作り込まない** | **1 人利用では `busy_timeout` を使い切ることは実質起きない。** **⇒ 汎用のエラー表示に載るところまででよい** |
