## 1. 背景と目的

### 1.1 背景

**M20-04 がプリセットの作成・コピー・エイリアス編集・削除の経路を作った。** **しかし `recipe_cache` の再計算は、その経路のどこからも呼ばれていない。**

**★実測で分かっていること 3 点**（`architecture-patterns` §9.2 ／ ボード **D-354**）——

1. **再計算のメソッドは既に実装済みで、本番の呼出元が 0 件である**（`RecomputePresetCache` ／ `DeletePresetCache`。いずれもテスト以外から呼ばれていない）。
2. **⇒ 本サブは「層を作る」サブではなく、既にある 2 メソッドを呼び出し元へ挿すサブである**（**この見積りは 2 度是正されている**＝**M-53** ／ **D-354**）。
3. **現在の as-built**——**作成直後は壊れない**（キャッシュミス時に遅延計算して書き戻す）／**エイリアス編集の直後は古い値が残り、stale な表記が出る**／**削除の直後は当該 `preset_id` のキーが JSON 内に孤児として残る**（実害なし・JSON が肥大する）。

**★あわせて、既定プリセットの設定が `recipe_cache` の読み出しへ効いていない**（**D-313**）。**`config` の `[defaults] preset_id` を変えても、取り出すキーは別の定数から来る。** **同じ概念を 2 か所で独立に持っている状態である。**

### 1.2 目的

1. **プリセットの書き込み経路から再計算を呼ぶ**（`SUPP-001` §7.2 の preset 側 3 行）。**eager で確定済みである**（**D-303**）。
2. **`recipe_cache` の読み出しキーを既定プリセット設定に追随させる**（**D-313**）。**切替先にキャッシュが無い状態を同じ手番で塞ぐ。**
3. **`config.preset_id` の実在確認を完成させる**（followup `preset-config-preset-id-existence`。**M20-04 は削除側の拒否だけを実装した**）。
4. **再計算の途中失敗が部分更新として残らない形にする**（**D-303** の実測 (2)）。
5. **`P-34` の 27 行を列挙して報告する**（**値は決めない・投入しない**。§4.5）。

## 4. 詳細仕様

### 4.1 ★再計算のロジックを書き直さない（本サブの中核の制約）

**本サブが足すのは「いつ呼ぶか」であって「どう計算するか」ではない。**

| # | 規約 |
|---|------|
| 1 | **★既存の `RecomputePresetCache` / `DeletePresetCache` を呼ぶ。** **同等の処理を呼び出し元へ書かない** |
| 2 | **★再計算の中身**（どのエンティティを対象にするか・何を JSON へ書くか）**を変えない。** **変える必要が出たら、それは `SUPP-001` §7.1 の改訂にあたるため止めて報告する** |
| 3 | **★`SUPP-001` §7.1 の記述と as-built が食い違っていても、as-built を正とする。** **同節は「delete → insert」と書くが、実測は「インライン JSON の当該キーを行単位で UPDATE する」である**（**D-303**）。**⇒ 記述のほうを是正する。是正は設計卓の手番であり、製造は食い違いを完了報告に書く** |
| 4 | **★呼び出しの有無を利用者の操作で分岐させない。** **プリセットが書き換わったら必ず呼ぶ**（eager＝**D-292** / **D-303**） |

> **★なぜここを縛るか**——**「呼び出し元で同じことをする」形は動いてしまう。** **壊れるのは、再計算の規則が後から変わったときであり、片方だけ追随して他方が古い規則で書き続ける。** **エラーにならない**（`E-76`＝**同じ情報を 2 か所に持つと必ずドリフトする**）。

### 4.2 既定プリセットへの追随（**D-313**）

**`recipe_cache` の読み出しキーを、既定プリセットの設定から取る。**

> **★【2026-08-14・D-360】本節と §4.3 は不可分である。片方だけ入れない。**
>
> **製造の実査**——**現在は実在しないプリセット ID を指しても起動が黙って通り、表示にも影響しない**（読み出しキーが固定値のため）。**しかし本節で追随させると、同じ状態でレシピ行が黙って消える**（**キー不在は空文字を返しエラーにならない**）。
>
> **⇒ 本節の追随は、§4.3 の実在検査**（**起動時に組み込みの既定へ倒す**＝**D-358**）**が効いている状態でのみ成立する。** **順序として先に入れるか同時に入れるかは実装判断だが、「追随だけ入って実在検査が無い」中間状態をコミットに残さないこと。**
>
> **★これは新しい silent failure を作る変更である。** **`D-356` で開発者が許容したのは「古い表記が一時的に見えること」であって「行が消えること」ではない。**

**★固定値は 3 か所である**（**製造の実測**。**`D-313` の記録「2 か所」は 1 少なかった**——**model 層 1 ／ コンボ側サービス 1 ／ セットプレイ側サービス 1 で、いずれも同内容の抽出を private に複製している**）。

### 4.4 再計算の境界（**D-303** の実測 (2)）

**実測＝全体を囲むトランザクションが無く、途中でエラーが返ると先行行の UPDATE が残る**（**53 行の部分更新が起きうる**）。

> **★【2026-08-14・D-360】製造の実査で、委任の前提が違っていた。裁定を出す。**
>
> **実測**——**`RecomputePresetCache` は 4 兄弟のうち唯一 `*sql.Tx` を取らず、さらに内部でエイリアスを引く経路が DB ハンドル直読みで、渡されたトランザクションを見ない。** **⇒ 書き込みトランザクションの内側で呼ぶと、コミット前のエイリアスが見えず「古い表記」を書き込む。** **エラーにならず、テストも緑のまま通る。** **加えて SQLite の接続プールが無制限・`busy_timeout` 5 秒のため、開いている書き込みトランザクションの内側から非 tx の UPDATE を撃つと別コネクションになり競合する。**
>
> **★裁定＝案 A を採る。** **書き込みをコミットしたあとに、再計算だけを 1 つの境界で走らせる。**

| # | 仕様 |
|---|------|
| 1 | **★途中失敗が部分更新として残らない形にする。** **全部書き換わるか、1 行も書き換わらないかのどちらかにする。** **★対象は「再計算バッチ」である**——**書き込み本体と再計算をまたぐ全か無かは求めていない** |
| 2 | **★失敗を黙って捨てない。** **呼び出し元が失敗を受け取り、利用者から見える形で分かること**（`E-84`＝**「起きなかった」と「失敗した」を同じ顔で出さない**） |
| **★3** | **【D-360 で確定】書き込みをコミットしたあとに再計算する。** **書き込みトランザクションの内側で呼ばない**（上の実測）。**⇒ 「保存は成功したが再計算に失敗した」状態が原理的に生じる。これを許容する**——**★`D-356` で開発者が許容した状態と同じ形であり、項目 2 により利用者へ伝わる。** **★キャッシュの stale はデータの不整合ではない**〔真実は `preset_aliases` にあり、再実行で回復できる〕 |
| **★4** | **【D-360 で確定】署名が `*sql.Tx` を取るなら、その tx を読みにも使うこと。** **読みが見ないなら tx を取らないこと。** **★「tx を取るのに読みは見ない」形は採らない**——**呼び出し側は「この tx の内側で呼んでよい」と読み、将来の担当が項目 3 の逆をやる。** **どちらの形にするかは実装判断である** |
| **★5** | **【D-360 で確定】呼び出し順（コミット後）を固定する検査を置くこと。** **★順序が正しさの根拠になる以上、順序が壊れたことを検出できないと silent に古い表記を書く**（§5 (l)）。**`D-354` で `M20-04` が採った形と同じ**——**件数の観測ではなく、実装の形を固定する** |

## 9. 注意事項・判断に迷ったら

### 9.1 推測で進めてはいけない事項

1. **再計算のロジックそのものを変える判断**（§4.1-2）——**`SUPP-001` §7.1 の改訂にあたる**
2. **eager から lazy への変更**（§9.4 の停止条件 1）
3. **config サービスの公開インターフェースを組み替える判断**（§9.4 の停止条件 2）
4. **`migrations/` の払い出しが要ると判断した場合**（**自採番しない**＝**D-293**）
5. **契約 F-2 の「形」に触れる判断**（§2.2-4）
6. **`P-34` の値を決めること**（§4.5-4。**列挙までが本サブである**）

### 9.2 推測で進めてよい事項（その旨を明示すること）

1. **実在確認をどの層に置くか**（§4.3-4）——**要件は「実在しない値が入ったまま起動できないこと」だけである**
2. ~~**書き込み本体と再計算の成否を 1 つの結果へ畳み込むかどうか**~~ **【2026-08-14・D-360 で裁定済み】**——**コミット後に再計算する**（§4.4-3）。**「保存は成功したが再計算に失敗した」状態を許容する。** **★残る実装判断は「署名が tx を取るか取らないか」だけである**（§4.4-4）
3. **再計算の失敗を利用者へどう見せるか**（§4.4-2。**形は問わない。伝わることだけが要件である**）
4. ~~**読み出しキーをどこへ寄せるか**~~ **【2026-08-14・D-360 で裁定済み】**——**注入で寄せる**（§4.2-1）。**可変なプロセス状態を作らない。** **★残る実装判断は「注入の配線の書きかた」だけである**
5. **`P-34` の列挙結果の並び順・表の形**（§4.5-2）

**★覆ったら理由を書く。** **とくに §9.2 の 5 項目は設計卓の見込みを書いてあるだけであり、実装を見た判断のほうが強い。**

### 9.3 不明事項発見時の対応

**原則は「進めて報告する」**（`CLAUDE.md` §9）。**ただし §9.1 の 6 項目と、設計書間の矛盾を見つけた場合は止めて上げる**（同 §8）。
