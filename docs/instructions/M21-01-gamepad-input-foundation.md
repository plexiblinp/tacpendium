## 1. 背景と目的

### 1.1 背景

**M21 は物理コントローラでレシピを入力できるようにするマイルストーンである。** 本サブはその**土台**を作る。

**PoC で分かったこと**（**D-324** ／ `M21-RESEARCH-01`）——

| # | 実測 | 本サブへの帰結 |
|---|------|---------------|
| 1 | **経路 (a)(b) で Gamepad が取れた**（2 機種・`Gamepad.id`・`mapping`・ボタン数が両経路で一致） | **M21 は成立する。取得そのものは問題にならない** |
| 2 | **★全経路で user gesture が必須。** 入力 UI を開いた直後は `navigator.getGamepads()` が空を返す | **★本サブの UI の初期状態そのものの設計である。** 後から足す装飾ではない（§4.4） |
| 3 | **アナログ値に機種差がある。** パッドの button 7 は押し込みを **12 段階**で返すが、レバーレスは同じ button 7 で **`0` / `1` の 2 値**のみ | **★機種プロファイル層が要る根拠。** **Chrome 単独・2 機種でも既に差が出ている**（§4.2） |
| 4 | **測っていない範囲がある**——**Chrome 151 のみ ／ USB のみ ／ 2 機種のみ** | **未検証を「未検証」と書く**（§7.4・`E-84`） |

**設計上の制約 2 つ**（**D-328**）——

- **開発者はアーケードコントローラを所有していない。** **⇒ M21 の期間中、アケコンの実機確認は 1 回も行えない。**
- **開発者は Bluetooth 接続の機体も所有していない。** **⇒ 接続方式による差は測れない。**

**⇒ 所有していない機体に「対応した」と言える唯一の形は、機体ごとの決め打ちをやめることである。** **キャリブレーション／リマップの導線が本サブの中核になる。**

### 1.2 目的

1. **Gamepad の取得と論理ボタンへの正規化を行う層を作る**（§4.1・§4.2）
2. **利用者が自分の機体のボタン対応を 1 度登録すれば、以後それが使われる**（§4.3）
3. **コントローラが認識されているかが画面で分かり、認識させる導線がある**（§4.4）
4. **機種差・ブラウザ差を、この層より上へ漏らさない**（§4.2）

### 1.3 このサブで作らないもの（スコープ外）

| 対象 | 誰が持つか |
|---|---|
| **同時押しの判定窓・チャタリングの決着** | **M21-02**（`CHANGE-107`）。**★本サブは「複数ボタンが押された」という生の事実を上へ渡すところまで。まとめない** |
| **レシピへのステップ追加・読取表示** | **M21-03** |
| **余ったボタンへの機能割当**（確定／削除／保存／並び替え／修飾トグル） | **M21-04**（`DES-005` §6.5） |
| **キーボード入力** | **M21-05**（**KeyboardEvent 経路。Gamepad API ではない**） |
| **コマンド実モーション入力**（236P 等） | **M21-06** |
| **プリセット・`recipe_cache`・エイリアス辞書** | **M20**（契約 F-1。**触らない**） |
| **`internal/moveindex` ／ `move_commands`** | **M17 の所管**（契約 F-3。**読むだけ**） |

## 4. 詳細仕様

### 4.1 取得ループ

| # | 仕様 |
|---|------|
| 1 | **`requestAnimationFrame` でポーリングする。** **Gamepad API はイベント駆動ではない**（`gamepadconnected` / `gamepaddisconnected` を除く） |
| 2 | **入力面を表示していない間はループを回さない。** **マウント／アンマウントで開始・停止する** |
| 3 | **`gamepadconnected` / `gamepaddisconnected` を購読する。** **★ただしこれだけに頼らない**——**§4.4 のとおり user gesture 前は取得できない** |
| 4 | **rAF 間隔を観測できるようにしておく**（**PoC の計測環境は中央値 4.20 ms ＝ 約 238 Hz**）。**★M21-02 が (β) 実行時の自己校正を採る場合、この観測値を使う。** **本サブは値を持つだけで、判定には使わない** |
| 5 | **★複数の Gamepad が接続されている場合の扱いを決めて報告すること。** **設計卓の見込みは「最初に入力があった 1 台を使い、切り替え導線は本サブでは作らない」。** **覆ってよい。覆ったら理由を書く** |

### 4.2 機種プロファイル層（★本サブの中核）

**目的**——**機種差とブラウザ差を、この層より上へ漏らさない。**

| # | 仕様 |
|---|------|
| 1 | **入力は `Gamepad` のスナップショット、出力は論理ボタンの集合**（`DES-005` §6.2。**過不足は §3.3-1 で確定する**） |
| 2 | **★純粋関数として実装する。** **`navigator` にも `window` にも触らない。** **⇒ テストで Firefox 形の入力を食わせられる**（§5.1・**D-329** の条件 4） |
| 3 | **★`mapping === "standard"` を必須条件にしない。** **通常経路として扱う** |
| 4 | **★方向入力を `buttons` と `axes` の両方から読む。** **どちらに出るかは機体と HID 実装で変わる** |
| 5 | **★`axes` の本数を固定で仮定しない。** **Firefox は Chrome / Edge に無い要素を 1 つ持つ場合があり、index が全軸ずれる** |
| 6 | **★アナログ値を持つボタンは `pressed`（デジタル）と `value`（アナログ）の両方を保持する。** **パッドのトリガーは 12 段階、レバーレスは 0/1**（**D-324**）。**★どちらを判定に使うかは本サブでは決めない**——**M21-02 の範囲。本サブは両方を上へ渡す** |
| 7 | **プロファイルは「機体 ＋ ブラウザ」で解決する。** **`Gamepad.id` は同じ機体でもブラウザで異なる**ため、`id` だけを鍵にしない |
| 8 | **★プロファイルが無い機体でも動くこと。** **未知の機体はキャリブレーションへ誘導する**（§4.3）。**「対応機種一覧」で弾かない** |

> **★§4.2-3〜5 は Firefox 固有の作業ではない。** **アケコンでも同じ分岐が要る**（レバーが `buttons` と `axes` のどちらに出るかは機体次第）。**⇒ 「最初からそう書く」こと。** **Chrome 前提で書いてから広げると、index を仮定した箇所を探し回ることになる**（**D-329**）。

### 4.3 キャリブレーション／リマップ

**★これが本サブの load-bearing な部分である。** **開発者はアケコンを所有せず、Firefox も未計測である。** **⇒ 我々が持っていない機体で動くための唯一の手段がこれである**（**D-328**）。

| # | 仕様 |
|---|------|
| 1 | **「この論理ボタンに対応する物理ボタンを 1 度押してください」を順に案内し、押されたものを記録する** |
| 2 | **★中断できること。** **全部を埋めないと使えない形にしない**（**14 論理ボタンを毎回押させるのは重い**） |
| 3 | **★やり直せること。** **1 つだけ取り直せる導線を持つ** |
| 4 | **★既定プロファイルからの差分として持つか、全体を持つかを決めて報告すること。** **設計卓の見込みは「全体を持つ」**（**差分にすると既定が変わったときに壊れる**）。**覆ってよい** |
| 5 | **方向入力のキャリブレーションは、`buttons` と `axes` のどちらで来ても記録できること**（§4.2-4） |
| 6 | **保存は §4.5** |
| 7 | **★同じ物理ボタンを 2 つの論理ボタンへ割り当てようとしたときの挙動を決めて報告すること。** **設計卓の見込みは「警告して上書きを確認させる」。覆ってよい** |

### 4.4 接続状態表示と user gesture 導線

**★PoC の実測**——**全経路で user gesture が必須であり、入力 UI を開いた直後は `navigator.getGamepads()` が空を返す**（**D-324**）。

| # | 仕様 |
|---|------|
| 1 | **「認識しています」「認識していません」が画面で分かること** |
| 2 | **★未認識のとき「コントローラのボタンをどれか 1 度押してください」を出すこと。** **これが無いと、利用者は接続しているのに壊れていると判断する** |
| 3 | **認識できたら表示が変わること。** **機体名**（`Gamepad.id`）**を出すかは判断して報告すること**（**設計卓の見込みは「出す」**——**複数機体があるときに自明になるため**） |
| 4 | **★「認識していません」と「まだ 1 度も押されていません」を同じ文言にしないこと。** **前者は障害、後者は正常な初期状態である**（**`E-84` の同型**） |
| 5 | **切断されたときに表示が戻ること**（`gamepaddisconnected`） |

### 4.5 保存（ブラウザストレージ）

| # | 仕様 |
|---|------|
| 1 | **`DES-005` §6.4.1 のとおり localStorage を使う。** **DB へ永続化しない** |
| 2 | **★専用ヘルパ `web/src/lib/browser-storage.ts` 経由で読み書きする**（`web/CLAUDE.md` §1）。**直接 `localStorage` を叩かない** |
| 3 | **try-catch 必須 ／ キーバージョニング ／ JSON シリアライズ**（同 §1 のガイドライン） |
| 4 | **★台帳に未記載のキーを使わない。** **§3.3-8 で実査し、未記載なら `CHANGE-106` の addendum で台帳へ追記してから使う。** **実装を先行させた場合も必ず addendum で通知して台帳へ反映する** |
| 5 | **★保持してよいのは UI 状態のみ。** **キャリブレーション結果は「その利用者の環境設定」であって DB 永続化対象のユーザー入力データではない**（コンボ本体・タグ・プリセットエイリアス・セットプレイとは性質が違う）。**⇒ 許容範囲と判断する。** **判断の根拠を addendum に書くこと** |
| 6 | **検査＝`bash scripts/check-browser-storage-keys.sh` が緑であること**（§7.3） |

| # | 撤回・変更した定義 | 走査キーワード | 走査対象 |
|---|---|---|---|
| 1 | **レイアウトごとの決め打ちボタン割当** | **`WASD` ／ `JIKLUO` ／ 機種名のハードコード** | 本番コード ／ テスト資産 |
