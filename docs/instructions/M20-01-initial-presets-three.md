## 1. 背景と目的

### 1.1 背景

**組み込みプリセットは `DES-004` §3.1 が 5 種を正典としている**（`official_ja_move` ／ `official_ja_command` ／ `numeric_ja` ／ `numeric_en` ／ `srk`）。**5 行とも `migrations/000005_seed_presets` で投入済みである。**

**2026-08-12 に開発者判断で 3 種へ再整理した。**

| 裁定 | 内容 |
|---|---|
| **D-288** | **`official_ja_command`（公式のコマンド表記）は需要を感じないため出さない。** |
| **D-299** | **`numeric_ja` と `numeric_en` は `numeric` 1 枚へ統合し、`numeric_en` は出さない。** **設計卓が全記録を実査した結果、両者の実体としての差分は 1 つも記録されていなかった**（`DES-004` §3.4 のサンプル表は 7 行すべて同一 ／ §4.2 の連結子はどちらも `>` ／ エイリアスは両方とも空）。 |

**★エイリアスは空で出荷されている**（`SUPP-001` §3.4＝**実データ投入済みは `official_ja_move` のみ**）。**したがって廃止による表示の変化は無い**——選択していても `DES-004` §5.3 のフォールバックで `official_ja_move` が出ていた。

**★実ユーザーは不在である**（`retrospective-log` §1 パターン G の発動条件・playbook §4.17 の緩和）。**消すなら今が最も安い。**

1. **`presets` テーブルが 3 行になっている**——`official_ja_move`（id=1）／ `numeric`（id=3）／ `srk`（id=5）。

## 4. 詳細仕様

### 4.1 マイグレ up

**2 つの操作を 1 本のマイグレで行う。**

```sql
-- (1) 提供しないプリセット 2 行の削除
DELETE FROM presets WHERE code = 'official_ja_command';
DELETE FROM presets WHERE code = 'numeric_en';

-- (2) numeric_ja のリネーム
UPDATE presets
   SET code = 'numeric',
       name = 'ナンバリング記法'
 WHERE code = 'numeric_ja';
```

**★規則 4 点。**

- **(a) `id` ではなく `code` を条件にする。** **`code` が canonical な識別子であり**（`DES-004` §3.1 が code で正典を定義している）、**`id` は投入順の産物である。**
- **(b) 1 行 1 文で書く。** **`IN (...)` で 2 行をまとめない**——**`SUPP-001` §5.5 (4)「一次源が DB / CSV に無い転記マイグレは 1 行 1 UPDATE でキーを明示する」と同じ理由**で、**どの行に当てたかを diff で読めるようにする。**
- **(c) `name` の新値は `ナンバリング記法` である**（**D-300**）。**旧値 `ナンバリング記法(日本語版)` の括弧は半角である**（C-1 の実測）。**down で戻すときはこの逐語を使う**（§4.2）。
- **(d) `is_builtin` / `base_preset_code` / `user_id` は触らない。**

**★`SUPP-001` §7.3 の「`is_builtin = true` のレコードは削除不可」との関係。** **同節はサービス層での拒否（403 応答）を定めたものであり、マイグレの DELETE を禁じるものではない。** **本サブはサービス層を経由しないため矛盾しない。** **⇒ サービス層の保護を緩めてはならない。**

### 4.2 マイグレ down（忠実復元）

**`000005_seed_presets` 投入直後の 5 行へ戻す。**

```sql
-- (1) リネームの反転
UPDATE presets
   SET code = 'numeric_ja',
       name = 'ナンバリング記法(日本語版)'
 WHERE code = 'numeric';

-- (2) 削除した 2 行の復元（★id を明示する）
INSERT INTO presets (id, user_id, code, name, base_preset_code, is_builtin)
VALUES (2, NULL, 'official_ja_command', '公式表記(日本語・コマンド表示)改善版', NULL, 1);
INSERT INTO presets (id, user_id, code, name, base_preset_code, is_builtin)
VALUES (4, NULL, 'numeric_en', 'ナンバリング記法(英語版)', NULL, 1);
```

**★規則 4 点。**

- **(a) `id` を明示する。** **省略すると復元後の `id` が変わり、`preset_aliases.preset_id` ／ `recipe_cache` の JSON キー ／ `config` の `defaults.preset_id` との対応が壊れる**（§4.3）。
- **(b) `name` は `migrations/000005_seed_presets.up.sql` の逐語をコピーする。** **上のコードブロックの値は C-1 の実測（DB から読んだ値）であり、`000005` の SQL リテラルと一字一句同じであることを実査で確認すること。** **記憶で書かない**（教訓 `E-80`＝**一次源から機械的にコピーする**）。**括弧が半角か全角か・中黒の有無が典型的な差である。**
