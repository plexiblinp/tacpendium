## 1. 目的・位置づけ

**M24 は「フェーズ3 で溜めた未完を、全件に行き先を与えて畳む」マイルストーンである。**

### 1.1 ★「未完を片づける」は全行を実装する意味ではない

**★全行に検証済みの `disposition` を与える意味である**（起票時の開発者指示・2026-08-20）。**`M24-RESEARCH-01` がその ledger を作った。**

| 系統 | 母集団 | 内訳 |
|---|---:|---|
| **系統 1**（`Memo_Someday.txt` 未完行 ＋ `[調査]`） | **160** | `実装` 60 ／ `返却` 52 ／ `要判断` 36 ／ `調査` 8 ／ `却下` 4。**未付与 0** |
| **系統 2**（`followup-backlog` ＋ `phase3-overview` §M24 の繰越） | **26** | `CO-001`〜`CO-026` |

**⇒ M24 が実装するのは 60 件（うち重複を束ねると 126 個の独立要求のうちの一部）であり、残り 100 件は「返却先・却下理由・判断の論点」を持って閉じる。**

### 1.2 ★性格

- **★横断関心事ではないが、面が広い。** **`実装` 60 件が触るのは `code-facts` §3 の 22 ルートのうち 17 ルート**（`/combos` 18 件・`/combos/new` 10 件・`/combos/:id` 9 件が最多）。**⇒ サブ分割の軸は「機能」ではなく「触る面」である。**
- **★スキーマ変更は 0 件である**（`M24-RESEARCH-01` §5.4 の実測）。**M23 と連番を取り合う場面は現時点の分類では発生しない。** **★★2026-08-26 是正（`D-560`）——「マイグレーションを消費しない見込み」は失効した。** **`M24-02` が `000079` を 1 本消費する**〔**キャラ表示名の是正**。**★DML であって DDL ではなく、スキーマ変更 0 という上の記述は今も有効である**〕。 **★★機序＝ledger は「スキーマ変更 0」を実測したが、「DML の消費 0」は実測していない。** **⇒ スキーマを変えないことと、マイグレーションを消費しないことは別である。**

- **★`parallel-ops` §12 が旧 M23 に与えた評価が、そのまま当たる**——「**小修正多数・衝突高低混在。高衝突の小修正だけ 1 レーンに束ねて直列、低衝突は並列。契約の『触る領域』で振り分ける**」。**実測はこの評価と整合した**（§5）。

## 1.5 ★★画面変更のモック HTML（**M24 全体の運用方針**・`D-543`）

**画面の見た目を変えるサブでは、製造に「変更後の姿」を単一 HTML で出させる。**

**★★理由は M24 に固有である**（2026-08-25 開発者要請。**★以下は開発者の逐語引用である。本書が「あれば」という曖昧語で指示しているのではない**——**運用の規則は直下の表 6 点で確定させてある**。逐語＝**「実画面は今見れないため、製造担当にはモック html を出して欲しい。直っている可能性がある。M24 は画面修正が多く、外出先で指示を出すことも多いので、要請があればこの方針でいきたい。」**）。

| 論点 | 決めたこと |
|---|---|
| **いつ出すか** | **★★Plan Mode の提示に含める。実装後ではない。** **実装後に出すと、開発者が形を却下したときに作り直しになる** |
| **何を出すか** | **変更前と変更後を並べる**（同一ファイル内で上下に並べてよい）。**★変更前が無いと「もう直っているのか」を開発者が判定できない**——**`M24` の入力は思いつきメモであり、症状が既に解消している可能性が常にある**（`D-539`） |
| **形式** | **単一 HTML。外部 CSS / JS / 画像に依存しない**（開発者が外出先で開く。ネットワークが無い場合がある） |
| **置き場** | **`docs/progress/M{N}-{NN}-mock/` 配下。完了報告からリンクする** |
| **粒度** | **判断に要る最小限。★作り込まないこと**——**作り込みそのものが実装の約束に見える** |
| **対象の決め方** | **各サブの指示書が名指しする。** **★「画面を触るサブは全部」ではない**——**実装で見た目が変わらない箇所は出さない** |

**★★これは実装の証拠ではない。** **「実画面を見られない開発者が、形の妥当性だけを判断するための材料」である。** **⇒ モックが承認されても、実装が正しいことの根拠にはならない。** 実装の証拠は各サブの §5 のテストと破壊確認である。

> **★機構化は開発者の手番である。** **`.claude/commands/implement_plan.md`（および `_full` / `_wt`）へ工程として落とすかは、`.claude/commands/` が開発者のルールファイルであるため設計卓も製造も触れない**（`D-510` の注記）。**⇒ 当面は各サブの指示書が個別に要求する形で運用する。** **★同じ要求を 8 本の指示書へ写すことになるため、写し漏れが起きうる**（`E-114` の型）。**M24-CLOSE の観点で「モックを出したサブ／出さなかったサブとその理由」を数えること。**
