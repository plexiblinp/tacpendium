## §1. 背景と目的

### 1.1 背景 — **★新しい保存機構を作るサブではない**

**M19-01 は `SetupSelectorModal` に保存 UI を置こうとして失敗した。** 原因は「あの画面が悪い」ではなく、**親コンボがまだ存在しない状態で即時保存しようとしたこと**である（`DES-005` §5.6「保存 UI を置ける面の原則 v3」）。

**M19-03 でセットプレイ単独作成の口には既に対応が入っている。** 一方、**コンボと同梱で作る口には入っていない。**

| DTO | フィールド |
|---|---|
| **`CreateSetupRequest`**（セットプレイ単独作成） | characterId / name / description / steps / **`verifiedConditions []SetupResultConditionRequest`** |
| **`BundledSetupRequest`**（コンボと同梱） | characterId / name / description / steps ／ **`verifiedConditions` が無い** |

**⇒ 本サブは、片側に既にある形をもう片側へ揃えるだけである**（ボード **D-246**）。

**★裏づけ 3 点**（実査 2026-08-07／08-08）:

1. **`internal/repository/setup/setup_results.go:89`**——「**呼び出し側は `combo_setups` を作った後・同一トランザクション内で呼ぶこと**」。**前提が既にコードに書かれている。**
2. **`SetupRegistrationSection`**（`web/src/features/combo/components/`）が **`CreateSetupInput[]` をステージング**し、**`knockdownAdvantage` を既に受け取っている。**
3. **`DES-005` §5.6 の v3 原則は着地済み**（`05-screen-design.md:315-324`）。**「v1 のままだと後続が『M19-01 の再発』と誤判定して弾く」というリスクは消えている。**

### 1.2 目的

**コンボの新規登録・コピー時に、同梱で作るセットプレイの「確認できた条件」を入力し、コンボと同一トランザクションで `combo_setup_results` へ記録できるようにする。**

### 1.3 このサブで作らないもの（スコープ外）

| # | 内容 | 理由 |
|---|---|---|
| 1 | **編集モードでの入力** | **既存経路がある**（`DES-005` §5.6 項目10 の 2×2 グリッド ＋ `UpsertSetupResult` API）。**親が確定しているため v3 原則を既に満たしている** |
| 2 | **`SetupSelectorModal`（既存セットプレイの紐付け）への入力** | **親が確定していれば既存経路。していなければ v3 原則に反する。§2.5 で実査して判定する** |
| 3 | **`result='ng'` や note の入力** | **`SetupResultConditionRequest` は `techType` / `inCorner` のみ**（`ok` 固定・note なし）。**`CreateSetupRequest` と同じ非対称であり、意図的である**（§2.2） |
| 4 | **`combo_setup_results` のスキーマ変更** | 記録の形は M19-03 で確定済み |
| 5 | **`moves` に触る変更** | 契約 F-1〜F-6 |
| 6 | **`internal/service/punishfinder/` ／ `setplay/`** | 契約 §3.2。**M19-05 が触っている。衝突させない** |

## §2. 詳細仕様

### 2.1 バックエンド — **`BundledSetupRequest` を `CreateSetupRequest` に揃える**

**`internal/api/combo/dto.go` の `BundledSetupRequest` へ、`CreateSetupRequest` と同名・同型のフィールドを追加する。**

```
verifiedConditions,omitempty  []SetupResultConditionRequest
```

**★型を新設しないこと。** `internal/api/setup/dto.go` の **`SetupResultConditionRequest`（techType `string` / inCorner `bool`）を再利用する。**

**★パッケージ境界をどう跨ぐかは製造の判断とする**（再エクスポート／共有パッケージへの移動／`combo` 側での同名型の定義）。**ただし「同名で中身が違う型を 2 つ作る」ことだけは避けること。** 採った形と理由を設計伝達レポートに書く。

**サービス層**——**コンボ作成のトランザクション内で、`combo_setups` を作った直後に `combo_setup_results` を書く。**

**★`internal/repository/setup/setup_results.go` の既存関数を使うこと。** **新しい書き込み経路を作らない**（`setup_results.go:89` が「呼び出し側は `combo_setups` を作った後・同一トランザクション内で呼ぶこと」と既に述べている）。

### 2.2 ★`ok` 固定・note なしの非対称は維持する

`SetupResultConditionRequest` は **`techType` と `inCorner` しか持たない。** **投入されるのは `result='ok'` の行だけ**であり、**`ng` も note も入らない。**

**★これは `CreateSetupRequest` の既存仕様であり、意図的である。** 由来は `DES-005` §5.6 項目12——**採用ダイアログは「確認できた条件」をチェックする形**であって、3 値を指定する形ではない。

**★「対称にするついでに `ng` と note も足す」ことをしないこと。** 足すなら**両方の口に足す**必要があり、それは**別の設計判断**である。**本サブは非対称を揃えるだけである。**

**★未検証セルのメモは永続化されない**（`DES-005` §5.6 項目10）。**下書きは保持し保存を無効化して明示メッセージ**が現行の最善手であり、**本サブでも同じ扱いにする。**

### 2.3 フロントエンド

**入力 UI を `SetupRegistrationSection` ／ `SetupInputRow`（`web/src/features/combo/components/`）の系統に載せる。**

| 観点 | 指示 |
|---|---|
| **操作モデル** | **`DES-005` §5.6 項目10 と同じ 2×2 グリッド（受け身種別 × 画面端）を再利用する。** **新しい操作モデルを作らない**（項目12 が同じ方針を採っている） |
| **実装の再利用** | **`web/src/features/setup/components/SetupResultGrid` ／ `SetupResultEditor` の既存実装を再利用できないかを先に検討すること。** できない理由があれば設計伝達レポートに書く |
| **セルの定義** | **`web/src/constants/setup-result.ts` の `SETUP_RESULT_CELLS` を使う。** **セルの組を自前で組み立てないこと** |
| **語彙** | **`OKI_TECH_TYPE_LABELS`（項目6 由来）と 画面端＝「相手が画面端」／「画面中央」。** **第 3 の語彙を作らない** |
| **状態** | **`CreateSetupInput` に載せてステージングする。** **即時保存しない**（v3 原則） |
| **既定** | **全セル未チェック**（＝未検証で開始） |

### 2.4 ★`ComboEditor` の 3 モードの扱い

`ComboEditor` の `mode` は **`"new"` / `"edit"` / `"copy"`**（`code-facts.md` §1）。

| モード | 扱い |
|---|---|
| **`new`** | **入力 UI を出す。** 本サブの主対象 |
| **`copy`** | **入力 UI を出す。ただし成立条件を引き継がない**——**全セル未検証で開始する** |
| **`edit`** | **★本サブでは触らない。** 既存経路（項目10 の 2×2 グリッド ＋ `UpsertSetupResult` API）がある |

**★`copy` の扱いは開発者確定済みである**（2026-07-28・`DES-005` §5.6）——「**コンボのコピー時は成立条件を引き継がない。全セル未検証で開始。引き継ぐと未検証のものが検証済みに見える誤認のほうが害が大きい**」。

**★これは「値が同じでも意味が違うものを混ぜない」の一例である。** 引き継いだ `ok` は「このコンボで確認した」ではなく「元のコンボで確認した」であり、**同じ `ok` でも根拠が違う。**

### 2.5 ★実査で判定する 2 件

| # | 対象 | 判定すること |
|---|---|---|
| 1 | **`SetupSelectorModal`（既存セットプレイの紐付け）** | **紐付け時に親コンボが確定しているか。** 確定していれば既存経路で足りる（本サブでは触らない）。**確定していなければ v3 原則に反するため、報告して止まる**（M19-01 の再発） |
| 2 | **`CreateSetupRequest` を使う既存の面** | **本サブの変更が影響しないこと**（`BundledSetupRequest` への追加であり、`CreateSetupRequest` は変えない） |

**★1 で「触らない」と判定した場合、理由を完了報告に明記すること。** **触らなかったことと、気づかなかったことは違う。**

## §8. 注意事項

### 8.1 推測で進めてはいけない事項

- **トランザクション境界。** 実査してから書くこと。**同一 Tx でないと VAL-S05 を満たせない。**
- **`copy` モードの現行の引き継ぎ範囲。** 実査してから、成立条件だけを外すこと。
- **`SetupSelectorModal` が親を持つか。** **持たないなら v3 原則に反する。推測で「持つ」としないこと。**

### 8.2 推測で進めてよい事項（**その旨を明示させる**）

- **パッケージ境界を跨ぐ手段**（§2.1）。**同名で中身が違う型を 2 つ作らないことだけが制約である。**
- **フィールド名・関数名・ファイル配置。** 既存の命名に合わせること。

**★推測した箇所は、設計伝達レポートに全数列挙すること**（CLAUDE.md §9-2）。

### 8.3 ★「対称にする」を超えないこと

**本サブは `BundledSetupRequest` に 1 フィールド足すだけである。**

- **`CreateSetupRequest` を変えない。**
- **`ng` や note を足さない**（§2.2）。
- **`UpsertSetupResult` の既存経路を変えない。**
- **新しい書き込み経路を作らない**（既存の `setup_results.go` を使う）。

**★「ついでに揃える」誘惑が最も強いサブである。** 揃える必要があると判明したら、**実装に入らず報告して止まる。**
