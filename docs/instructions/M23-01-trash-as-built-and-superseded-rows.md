## 1. 背景と目的

### 1.1 背景

**ゴミ箱と復元は既に動いている。本サブは「機能を作る」のではなく「実態と仕様の食い違いを畳む」。**

`M23-RESEARCH-01`（2026-08-20・報告 `docs/progress/M23-RESEARCH-01-report.md`）が 3 つの食い違いを実測で確定させた。

| # | 実測された食い違い | 帰結 |
|---|---|---|
| 1 | **`PUT /api/combos/:id`（キー項目を変える編集）は旧行を論理削除して新 id で採番し直す**（**D-413**）。**その旧行はゴミ箱の一覧に出ている**——絞り込みは `deleted_at IS NOT NULL` ＋ `character_id = ?` の 2 述語しかなく、画面の 8 列にも区別を示すものが無い | **利用者から見て「自分で消した行」と「編集で積まれた行」が同じ見た目である。** **⇒ ゴミ箱が編集履歴の墓場になり、本来の用途（消したものを戻す）が埋もれる** |
| 2 | **旧行を判別できる情報が 1 つも無い。** 候補 4 つを全部潰した——**`materialized_from_combo_id` は `PUT` の経路で書かれない**〔`buildComboFromInput` の struct literal に同フィールドが無く、書き込みは `Materialize` の 1 か所のみ〕**／時刻の近接は推定の材料にしかならない**〔`datetime('now')` の精度は秒〕**／`recipe_cache` は `PUT` が旧行の分を削除している**〔しかも「キー変更」の操作であり一致を前提にできない〕**／それ以外の列も無い**〔`version` は新行が `1` で採番し直され、`updated_at` は手動削除と区別しない〕 | **⇒ 印を作らない限り「既定で隠す」は実装できない**（**D-460**）。**★スキーマ変更が要る側に倒れた。開発者が 2026-08-20 に承認済み**（**D-479**） |
| 3 | **「自動完全削除までの残日数」は表示だけが在り、機構が無い。** `TrashListRow.tsx` に `TRASH_RETENTION_DAYS = 90` とクライアント側の残日数計算があり、列 7 に「あと N 日」／「期限切れ」を出す。画面本文にも 90 日で完全削除される旨の告知が出ている〔逐語は報告 §A-2 が持つ〕。**サーバ側に削除する機構は無い** | **⇒ 画面が利用者に嘘をついている。** **保持は無期限で確定しており**（**D-458**）、**設計書だけを直すと嘘が画面に残る** |

### 1.2 目的

1. **`PUT` が積む旧行を判別できるようにし、ゴミ箱の既定から外す**（**D-460** ／ 形は **D-479**）。
2. **90 日の残日数という存在しない概念を、画面と設計書の両方から消す**（**D-458**）。
3. **ゴミ箱まわりの API 契約の as-built を設計卓へ報告する**（`DES-002` §4.2 の経路表に**ゴミ箱系の経路が 1 本も載っていない**ことを設計卓が実査済み。§4.5）。

## 4. 詳細仕様

### 4.1 マイグレーション `000078`——`combos.superseded_by_combo_id`

| # | 事項 | 内容 |
|---|---|---|
| 1 | **列** | **`superseded_by_combo_id INTEGER NULL REFERENCES combos(id) ON DELETE SET NULL`**。**`materialized_from_combo_id` と同型の self-FK である**（`DES-003` §3.4） |
| 2 | **既定値** | **既定値を持たない（NULL）。** **★`ADD COLUMN` で足す**——テーブル再構築を行わない（既存の DDL の写し落としを避ける。`DES-003` §3.9 の先例と同じ理由） |
| 3 | **★`ON DELETE SET NULL` を当てにしないこと** | **`P-04` により FK の連鎖動作は保証されない。** **⇒ 宣言は意図の記録として置くが、「後継が完全削除された旧行」がゴミ箱へ再び現れうる前提で挙動を決める。** **★暫定の扱い＝現れてよい**（後継が完全削除された時点で、その旧行は「編集で積まれた行」ではなく通常の削除済み行として扱う）。**★§3.3-7 の実測が暫定と食い違った場合は、実装を変えずに完了報告へ書くこと** |
| 4 | **★`setups` には足さない** | **報告 §C / §D の実測では `setups` にキー変更編集の経路が無い**（`PATCH` のみ）。**⇒ 積まれる旧行がそもそも生じない。** **★「無い」と断ぜず §3.3-6 で 1 回だけ確認すること** |
| 5 | **★既存行は埋めない** | **マイグレ適用時点で既に積まれている旧行は `NULL` のままである。** **⇒ 遡って埋めることはできない**（旧行と新行の対応は `PUT` を処理している瞬間にしか分からない＝§1.1-2）。**★これは仕様である。利用者に見える形は「本サブ以降に積まれた分から隠れる」であり、この非対称を `DES-005` §5.15 へ書く**（設計卓が `CHANGE-121` で反映する） |
| 6 | **down** | **列を落とす。** **★SQLite の `DROP COLUMN` の可否と、既存マイグレの流儀に合わせること**（`§3.3-1` の実査で既存 down の書き方を確認する） |

### 4.2 `PUT /api/combos/:id`——旧行へ後継 id を書く

1. **書き込み位置は「旧行を論理削除している箇所」である。** **同一トランザクション内で、新行の id が確定したあとに旧行へ書く。**
2. **書く値は新行の id。** **★`deleted_at` と同時に書いてよい**（1 文でも 2 文でもよい。**トランザクションの外へ出さないこと**が要件である）。
3. **★`version` を動かさない。** 旧行は論理削除済みであり、版を動かす経路が無い（`M23-overview` §4.2）。
4. **★`updated_at` の扱いは既存の論理削除に合わせる**（本サブで新しい規則を作らない）。
5. **★失敗時**——**新行の作成が失敗したときは旧行への書き込みも巻き戻る。** トランザクションの外へ出さない要件はここから来る。
6. **★`PATCH /api/combos/:id`（メタデータ編集）では書かない。** 同経路は行を積まない。

### 4.3 ゴミ箱の絞り込み——既定で旧行を出さない

1. **`OnlyDeleted` の分岐へ `AND superseded_by_combo_id IS NULL` を足す**（報告 §G-3 の実測どおりリポジトリ層が最小である）。
2. **★「既定で」と書いてあるが、本サブでは切り替えの導線を作らない。** **⇒ 旧行を見る手段は本サブの完了時点で存在しない**（§1.3-1。**これは意図である**）。
3. **★一括復元・一括完全削除の対象も、絞り込み後の集合に揃うこと。** **画面に出ていない行が一括操作で戻る・消えることがあってはならない。** **★一括操作が一覧とは別のクエリを通っている場合は、そちらにも述語を足す**（§3.3-3 の実査で両方を確認する）。
4. **★件数表示（在る場合の総件数）も絞り込み後の値に揃うこと。**

### 4.4 残日数表示の撤回——**画面から消す**

1. **`TRASH_RETENTION_DAYS`（= 90）とクライアント側の残日数計算を撤去する。**
2. **列 7（「あと N 日」／「期限切れ」）を撤去する。** **★文言だけを変えて列を残さないこと**——**無期限が確定した以上、残日数という概念そのものが存在しない。何の日数か説明できない列になる。**
3. **画面本文の「90 日後に完全削除される」旨の告知を撤去する。**
