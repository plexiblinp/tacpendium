## 1. 目的・位置づけ（発信者中心への舵切り）

フェーズ3 は REQ-001 §7「共有・協調・入力拡充」を起点とするが、先行リリースを経て**発信者中心の戦略へ舵を切る**（reorg §0）。継続利用の鍵は「コンボ／セットプレイを能動的に探し、CSV 等で配布し続ける少数の発信者」を取り込むことにあり、その発信者にとって魅力的な機能と、記録・発信を容易にする仕組みを優先する。

本フェーズの達成目標：

- **配布健全化（OSS 化の前提・継続）**: 配布禁止の公式フレームデータ HTML に依存しない配布形態へ是正（手入力データの DB 同梱・取込画面廃止・取込前提スキーマ整理・FR704 降格）。M13 export = データ安全網の上で破壊的整理を行う。
- **発信者の差別化機能**: 確定反撃（punish counter）記録、セットプレイ自動提案（前例なき目玉）を新規導入。
- **発信者の流通基盤**: import/export 強化、既存フォーマット取込ヘルパー、メディア参照（リンク＋ローカル相対パス）。
- **データモデルの継ぎ目**: SA ゲージ消費・起き攻め正規化・ドライブ小数・レシピステップ taxonomy。放置すれば後で破壊的移行になるスキーマの穴を、上位プレイヤー需要に基づき先回りで埋める（datamodel-issues 付記）。
- **使いやすさの底上げ**: friend FB（17 件）が示す入力・表記・説明・オンボーディングの品質向上。
- **共有・協調・入力拡充**: 物理コントローラ入力（FR105〜108）、プリセット管理、簡易ログイン（FR501/502）、データバージョン管理（FR601）、LAN 多人数同時編集の安全性（FR406/407）。

到達点は「発信者がメモ／エクセルから本アプリへ乗り換え、確定反撃・セットプレイ提案・流通基盤を使って記録・配布を継続でき、OSS として配布可能な健全性を備え、一般利用者も説明なしに使える品質に達した状態」。

## 2. スコープ

- 公式データ配布是正・スキーマ整理・DB 同梱（§M14。配布禁止 HTML 非依存化）。
- 確定反撃（punish counter）記録（**NFR406 をフェーズ4 から本フェーズへ移設**＝reorg §1-1。REQ-001 CHANGE 起票。§2.1 参照）。
- セットプレイ自動提案（reorg §1-2。先行設計統合＋品質確認 PoC）。
- import/export 強化（reorg §1-3。M13 の後継・反復改善）、既存フォーマット取込ヘルパー（reorg §1-4・二段役割分担）、メディア参照（reorg §1-5・コンボのみ・後方互換 CSV 改訂）。
- **コマンド入力解決（簡易版）**（command-resolution-request＝唯一の未ハンドオフ追加依頼）: 公式表記のみ・段階2まで決定論解決（段階1＝しゃがみ/ジャンプ攻撃・段階2＝単方向＋ボタンの特殊技）。必殺技・空中特殊技はモーション解決せず「技の直接指定」。物理コントローラでの実モーション入力は M21 後送り。**出口は必ずキャラ別 `move_code`**。配置は §2.3・M15/M17/M21 へ分配。

- friend FB の使いやすさ品質向上（§5）。
- 物理コントローラ入力（FR105〜108）、プリセット管理 UI・カスタムプリセット作成。
- マルチユーザー・LAN 共有の拡充（FR406/407）、簡易ログイン（FR501/502）、データバージョン管理（FR601）、編集中の画面遷移時データ保持。

- 確定反撃の物理設計は spec draft 進展（**2026-06-26 改訂＝別コンボ materialize 転換・パニッシュカウンター補正則確定**）を反映。**補正則は「始動技ダメージにのみ 1.2 倍（＝合計に始動技ダメージ×0.2 を加算）・例外は生成後編集で吸収」で確定**（旧「技依存か一律か」の未決は解消。**「一律 1.2 倍」＝コンボ合計への適用ではない**点に注意）。残る未決は **seed 充足の最終確認（距離依存技は手動確認）** のみ。⇒ **REQ レベルのフェーズ移設 CHANGE（着手前正典化）と物理設計 CHANGE（spec 確定後）を分離**（digest M13-3 の二段）。詳細は §M18・§2.4 ゲート表。

### 2.2 データモデル拡充の境界（datamodel-issues）

- **SA ゲージ消費**: 始動値とは別の消費フィールドを**手入力**で追加（FR303 が否定した自動キャッシュとは別物）。バーンアウト独立列は当面見送り。一般 custom_states 消費は非モデル化据え置き（arch §9.1。SA のみ例外）。
- **ドライブ小数**: combo 側 `drive_available_at_start`（INTEGER）を REAL へ寄せ、sequence 側（小数）と粒度統一。入力はゲージ widget 刻み前提。
- **起き攻め**: 打撃重ね追加＋ `combo_oki_options` 正規化前倒しの是非（bool 平置きの限界・設計書自身が将来移行を予見）。語彙棚卸しを伴う。
- **ステップ taxonomy**: 「moves 行／非技ステップ／modifier」の振り分け原則を明文化。移動（ジャンプ・ダッシュ）をシステム move 登録に寄せる（FR301 dup・既存レシピ同一性への波及を移行計画とセットで判断）。

### 2.3 コマンド入力解決の配置境界（command-resolution-request）

死守契約 3 点＝**公式表記のみ解決／モーション解析はしない（決定論ルックアップに徹する）／出口は必ずキャラ別 `move_code`**。この 3 点を守る限り UI 形式は委譲。段階別に既存マイルストーンへ分配し、新マイルストーンは増設しない（playbook §4.12。分配は既存枠内・本 v1.1.0 で承認済み 2026-07-02）。

- **段階1（しゃがみ／ジャンプ攻撃）→ M15**: `move_code` 構造（`crouching_*`/`jumping_*`）から引き当て。**追加データ不要・M16 非依存・非スキーマ**。プルダウン摩擦の主因でありここだけで体感が大きく変わる。
- **段階2（単方向＋ボタンの特殊技）→ M17**: 決定論ルックアップ。**取込ヘルパー（④）の表記解決とエンジン共通化**（`236LP`→`hadoken_light` と同一索引）。索引元 command は §2.4 G-k。
- **必殺技・空中特殊技＝技の直接指定**: モーション解決しない。**UI 骨格（必殺技ボタン＋強度／ピッカー等・形式委譲）は M15 で先行**（仮想で 236 を実演させない一点のみ割り切り・motion 解決を待たない）。
- **物理コントローラでの実モーション入力 → M21**（FR105〜108。仮想側は常に直接指定）。
- **command データ源（★M14 実態）**: replan/request の「既存 `moves.command` を索引化・新規列不要」は、**M14-01（CHANGE-054）が raw_data 退避キー（`command` 含む 5 キー）を除去したため現状不成立**。段階2 の索引元 command は**取込ヘルパー経由で入力し再確立する見込み**（開発者確定 2026-07-02）。列としての持ち方等の物理は M17 着手時に取込ヘルパーと一体で確定（§2.4 G-k）。段階1 は command 非依存で先行可。
