## 2. やること

### 2.1 束 A — 保存が通らないときに理由へ届かせる

**★★3 件は同じ経路である。⇒ 1 つの動線として設計すること。バラバラに直すと、直した先で別の行き止まりが残る**（`M27-overview` §3 M27-02）。

#### 2.1.1 ★★`editor-validation-errors-unreachable-from-ui` — 設計卓の判断は「(a) そのまま残す」である

**追跡行の実測**——**画面から到達できる検証エラーが 1 件も無くなった**。メモは `maxLength` が zod の上限と同値／ステップメモも同値／数値欄はクランプ／`VAL-C02` は `field` が空で振り分け対象外（モーダルで出る）／レシピ 0 件が残る唯一の経路だったが `M24-13` が塞いだ。

**⇒ `M24-04`（`SM-148`）／`M24-12` の「エラーの在り処をタブ見出しで示す」機構が、実装としては生きているが利用者が見る機会がほぼ無い。**

**★★追跡行は選択肢を 3 つ挙げ、「設計判断であり製造は判断しない」としていた。⇒ 設計卓が決めた。**

| 案 | 中身 | 採否 |
|---|---|---|
| **(a)** | **そのまま残す**（API 直叩き・将来の BE 検証への備え） | **★★採用** |
| (b) | UI 側の上限を緩めて到達可能にする | **不採用** |
| (c) | 機能を畳む | **不採用** |

**★★(a) を採る理由 3 つ。**

| # | 理由 |
|---|---|
| **★★1** | **フェーズ4 は初回全体公開の準備である。⇒ API が自分以外の手に届く。UI の外から不正な値が来る経路は、いま増える方向にある**（`DES-002` §8 の LAN 共有）。**BE 検証の受け皿を、公開の直前に畳むのは向きが逆である** |
| **★★2** | **(b) は一次の防御を弱めて二次の防御を試す形である。⇒ 順序が逆。★「到達不能なのは、手前が正しく効いているからである」——これは不具合ではなく、正しく積んだ結果である** |
| **3** | **(c) の撤去は安くない**——**タブ見出しのバッジ機構は束 A の 2 件目（`editor-tab-badge-misroutes-setups-errors`）と同じ機構であり、そちらは直す価値がある。⇒ 片方だけ畳めない** |

**★★製造がやること**——**(a) の採用を前提に、次を確かめて報告する。判断そのものはやり直さない。**

| # | やること |
|---|---|
| **★★1** | **「到達不能」がいまも成り立つか**（§0.3）。**★`M24-13` 以後に到達経路が復活していないか** |
| **★★2** | **★BE 検証が実際に発火したとき、その応答が画面へ届くか**——**これが (a) の前提である。⇒ 発火経路を 1 つ作って確かめること**〔API を直接叩く等〕。**★届かないなら、(a) は「備え」になっていない。その事実を報告に書く** |
| **3** | **`VAL-C02` が `field` 空でモーダルへ落ちる件が、いまも同じか** |
