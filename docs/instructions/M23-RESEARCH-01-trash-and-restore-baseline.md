## 0. この指示書の特殊性

### 0.1 製造担当として起動し、調査だけ実施して閉じる

**製造担当セッションを起動し、§4 の事実列挙 → §5 のレポート作成 → クローズ。** **実装は本調査の対象外である**（後続の `M23-01`〜`M23-06` で別指示書として出す）。

### 0.2 read-only 厳守

**許可**: ファイル内容の閲覧（`cat` / `sed -n` / エディタの閲覧機能）／ 検索（`grep` / `rg`）／ 一覧（`find` / `ls` / `wc`）／ Git の参照系（`log` / `diff` / `blame`）／ **dev DB に対する SQL の `SELECT`**。

**禁止**: 編集系・書き込み系のすべて（本番コード・テスト・マイグレ・seed・`docs/design/` 配下・`docs/handover/` 配下）。

> **★書き込みの例外は 2 つだけである。両方とも許可であり、片方を落とすと DoD と禁止表が正面衝突する。**
>
> 1. **§5 の調査レポート** — `docs/progress/M23-RESEARCH-01-report.md`
> 2. **`docs/progress/progress-log.md` への索引行の追記** — `CLAUDE.md` §8 の常設要求
>
> **★`docs/handover/followup-backlog.md` を編集してはならない。** **同ファイルを編集できるのは設計卓だけである**（**D-382**）。**候補は §5 の末尾へ書く。**

### 0.3 判断・提案を含めない（judgement-free）

**事実列挙のみ。** 「ここを直すべき」「この案がよい」といった設計結論は含めない。**複数案の併記はしてよいが、決定はしない。**

- **例外は 2 つ**——**(1) 想定外の発見** ／ **(2) 明らかな矛盾**（設計書どうし、または設計書と実装の食い違い）。**この 2 つは §5 の「想定外の発見」節へ書く。**

### 0.4 ★本調査が存在する理由——**「作る」前提で書くと必ず外す**

**M23 の骨格は既に存在する。** **`code-facts.md`（2026-08-19 生成）の範囲で、次がいずれも実在する。**

## 1. 背景と目的

### 1.1 背景

**M23 は `FR601`（データのバージョン管理・誤った更新や削除の取り消し）を扱う。** **`REQ-001` `FR013` が「誤った訂正等はゴミ箱からの復元（`FR601`）で対応し、監査ログは実装しない」と本文で名指ししており、`FR601` は「所有者を持たない」というコンセプトを成立させている当の機構である。**

**★設計卓は 4 つの設計論点を M22 の実測から確定させたが、いずれも「実装がどうなっているか」を知らないと決着しない。**

| 論点 | 未確定の部分 | 本調査の軸 |
|---|---|---|
| **論理削除・復元は `version` を据え置く**（`M22-overview` §4.2.2 の (iii)） | **削除済みの行を他の利用者が編集できるか**（できるなら復元が古い内容で上書きしうる） | **D** |
| **`PUT /api/combos/:id` は旧行を論理削除して新行を作る**（**D-413**） | **旧行を既存の情報で判別できるか**（できなければ列追加＝スキーマ変更） | **G** |
| **論理削除では CASCADE が効かない**（`architecture-patterns` §11） | **復元時に子がどう扱われているか。参照側が `deleted_at` を除外しているか** | **D / E / F** |
| **削除後に同じコンボが再登録されていた場合の復元挙動**（**D-458**） | **`FR301` の重複判定が削除済み行を見ているか** | **H** |

### 1.2 目的

**§4 の各軸を実コード・実 SQL・実テストの閲覧と検索で確認し、§5 の様式で報告する。** **本調査の成果が `M23-01`〜`M23-06` のスコープ確定入力になる。**

### 1.3 この調査でやらないこと

- **実装・マイグレ・seed・コードの変更を一切しない。**
- **最終決定をしない**（材料提示のみ）。
- **`DES` / `REQ` 本体を変更しない。** **★とくに `DES-005` §5.15 の記述を直さない**（撤回は `M23-01` の CHANGE の手番である）。
- **★M24 のスコープに踏み込まない**（UX 整理・i18n・繰越・リファクタ）。

## 4. 調査項目

> **★各軸で共通の作法**——**(1) 実コード・実 SQL を開いて読み、検索で全数を取る。** **(2) 列名・関数名・件数は実値で書く。** **(3) 走査コマンドを報告へ残す**（`E-84` ／ `E-182`＝**「0 件」は「無い」ではなく「走査が壊れている」かもしれない**）。**(4) 「無い」と書くときは、どの範囲で無いのかを同じ文に書く**（`E-106`）。

### A. ゴミ箱画面（`TrashPage`）の現状

- **A-1**: **`TrashPage` が実際に表示している項目を全数列挙する**（列・ボタン・空状態）。
- **A-2**: **★「自動完全削除までの残日数」に相当する表示・計算が実在するか。** **`DES-005` §5.15 は表示項目として挙げている。** **★在否のどちらでも、根拠（実コードの該当箇所 ／ 走査コマンドと 0 件）を示す。**
- **A-3**: **「一括復元」「一括完全削除」が実在するか。** 実在するなら**何を単位に一括するか**（画面上の全件か、選択したものか）。
- **A-4**: **コンボとセットプレイを 1 画面に混ぜているか、分けているか。**
- **A-5**: **行クリックで開く詳細が読み取り専用か。**
- **A-6**: **`TrashPage` に関するテストの全数**（ファイル・ケース数）。**★何を主張しているかを 1 行ずつ書く**（`M22-06` §7-1 の教訓＝**名指しされたファイルではなく、対象シンボルの参照元の全数から始める**）。

### B. ゴミ箱一覧の取得経路

- **B-1**: **`TrashPage` がどの API を叩いているか**（専用ルートか、`GET /api/combos` の絞り込みか）。
- **B-2**: **絞り込みの場合、クエリパラメータの名前と値、およびサーバ側の SQL 述語を実値で書く。**
- **B-3**: **`queryKey` を実値で書く**（`code-facts` §2-2 と突き合わせる）。**★M24 の「queryKey 統一」と交差する面であり、`M24-RESEARCH-01` 軸 F の入力にもなる。**
- **B-4**: **セットプレイ側の削除済み一覧を取る経路が在るか。**

### C. セットプレイ側の復元・完全削除

- **C-1**: **`setups` の復元・完全削除に相当する API・サービス・リポジトリのメソッドが在るか。** **★`code-facts` §4 に列挙されていないが、それは「ルートが無い」であって「機能が無い」とは限らない**（サービス層だけ在る可能性）。**⇒ ルート・ハンドラ・サービス・リポジトリの 4 層すべてで探す。**
- **C-2**: **`setups.deleted_at` に書き込む経路の全数**（どこで論理削除され、どこで NULL に戻されるか）。
- **C-3**: **★「無い」と確定した場合、`DELETE /api/setups/:id` で消したセットプレイが、現状どこからも戻せない状態かを述べる。** **★これは欠陥の断定ではなく、事実の記述として書く。**

### D. 復元時の子の扱い ＋ `version` 据え置きのすり抜け

- **D-1**: **`combo.Handler.Restore` から実 SQL までを辿り、`UPDATE` の対象と `SET` 句・`WHERE` 句を逐語で書く。**
- **D-2**: **★子（`combo_steps` / `combo_tags` / `combo_setups` / `combo_oki_options`）に対して、復元時に何かしているか。** **していないなら「していない」と書く**（`code-facts` §10 の前提どおりなら、子は物理的に残っており何もしない見込みである）。
- **D-3**: **★削除済みの行を `PATCH /api/combos/:id` で編集できるか。** **⇒ `UPDATE` の `WHERE` 句に `deleted_at IS NULL` が在るかを逐語で確認する。** **★これが本軸の最重要項目である**——**在れば復元のすり抜けは構造的に起きず、無ければ起こりうる。**
- **D-4**: **同じことを `PUT /api/combos/:id` と `PATCH /api/setups/:id` についても確認する。**
- **D-5**: **復元が `version` に触れているかを逐語で確認する**（前提事実 10 の (iii) を裏取りする）。
- **D-6**: **復元・論理削除・完全削除がトランザクションを張っているか。張っているなら境界を書く。**

### E. 参照側の `deleted_at` 除外（**全数**）

- **E-1**: **`combos` を参照する SQL の全数を取り、`deleted_at IS NULL` を持つものと持たないものに分けて列挙する。** **★件数を実値で書く。**
- **E-2**: **同じことを `setups` についても行う。**
- **E-3**: **★「持たないもの」について、それが意図的か否かを判断しない。** **どこで使われる SQL かだけを書く**（一覧 / 詳細 / 集計 / 提案エンジン / export / 確定反撃 等）。
- **E-4**: **★既知の先例を確認する**——`DES-005` の「`hiddenCurations` は論理削除済みコンボを除外する。`ON DELETE CASCADE` は物理削除にしか効かないため、`deleted_at` が入ったコンボの curation は明示的に除外する」という記述が実装と一致するか。
- **E-5**: **子の側から親を辿る経路で、削除済みの親が見えてしまう箇所が在るか**（例＝セットプレイ詳細から紐付くコンボを出すとき）。

### F. 完全削除と CASCADE（`P-04` の影響）

- **F-1**: **`combo.Handler.PermanentDelete` から実 SQL までを辿り、`DELETE` の対象を逐語で書く。**
- **F-2**: **★子を明示的に削除しているか、CASCADE に任せているか。** **任せているなら、`P-04`（`PRAGMA foreign_keys` が接続プール全体に効かない）の影響を受ける。**
- **F-3**: **`PRAGMA foreign_keys` をどこで、どのように設定しているか**（DSN パラメータか、実行時のクエリか）。**`SetMaxOpenConns` の設定の在否も書く。**
- **F-4**: **完全削除に関するテストの全数**と、**そのテストが「子も消えたこと」を主張しているか。** **★主張していないなら、CASCADE が効かなくても緑のままである。**

### G. `PUT` が積む「旧行」の判別（**★スキーマ変更の要否がここで決まる**）

- **G-1**: **`combo.Handler.UpdateWithKeyChange`（`PUT /api/combos/:id`）から実 SQL までを辿り、旧行の論理削除と新行の作成を逐語で書く。**
- **G-2**: **★旧行と新行を結びつける情報が既に在るか。** **候補を全部確認する**——**(a) `materialized_from_combo_id`**〔materialize 用の由来列。**`PUT` でも使われているか**〕／**(b) `deleted_at` と新行の `created_at` が同一トランザクション内で近接すること**／**(c) `recipe_cache` の一致**／**(d) それ以外の列。**
- **G-3**: **★現在、`PUT` で積まれた旧行がゴミ箱の一覧に出ているか。** **B 軸の絞り込み条件に照らして述べる。**
- **G-4**: **dev DB に対して `SELECT` を回し、`deleted_at IS NOT NULL` の行の件数と、そのうち `PUT` 由来と推定できる行の件数を出す。** **★推定の根拠（どの列をどう見たか）を必ず書く。** **★推定であることを明示する。**
- **G-5**: **★`materialized_from_combo_id` が `PUT` の経路で書かれるかを逐語で確認する。** **★書かれないなら (a) は使えない。**

### H. `FR301` の重複判定と削除済み行

- **H-1**: **重複判定（`POST /api/combos/check-duplicate` ／ 作成時の判定）の実 SQL を逐語で書く。**
- **H-2**: **★判定の `WHERE` 句に `deleted_at IS NULL` が在るか。** **在れば削除済み行は判定の外に居る。**
- **H-3**: **`recipe_hash` に相当するものが列なのか計算なのかを書く**（`CalcRecipeHash` は静的抽出の対象外であり `code-facts` に出ない）。
- **H-4**: **復元の経路が重複判定を通るかを確認する。** **通らないなら「通らない」と書く。**
- **H-5**: **dev DB に対して `SELECT` を回し、「削除済み行と生きている行で同じ判定キーを持つ組」が実在するかを件数で出す。** **★0 件でも「0 件だった」と書き、走査コマンドを残す。**
