## 1. 背景と目的

### 1.1 背景

**コンボ側には復元も完全削除も在る。セットプレイ側には片方も無い。** `M23-RESEARCH-01`（2026-08-20・報告 `docs/progress/M23-RESEARCH-01-report.md`）が 4 層すべてを走査して確定させた。

| # | 実測 | 逐語の出どころ |
|---|---|---|
| 1 | **復元・完全削除はルート／ハンドラ／サービス／リポジトリの 4 層すべてで 0 件である。** ルートは 11 本の全数が報告に載っており、`/setups/:id/restore` も `/setups/:id/permanent` も無い。リポジトリの 36 メソッドにも `Restore` / `HardDelete` に相当するものが無い | 報告 §C-1 |
| 2 | **`setups.deleted_at` を NULL に戻す SQL が本番コードに 1 件も無い。** 書き込むのは `SoftDelete` の 1 か所だけである | 報告 §C-2 |
| 3 | **`DELETE /api/setups/:id` は 1 トランザクションで 3 つを同時に行う**——`setups.deleted_at` の設定 ／ **`combo_setups` の当該行の物理削除** ／ **`setups.recipe_cache` の物理削除** | 報告 §C-2 / §C-3 |
| 4 | **⇒ 仮に `deleted_at` を NULL に戻す経路だけを足しても、紐付けと `recipe_cache` は戻らない。** 利用者から見ると「戻ってきたが、どのコンボにも紐付いていない」 | 報告 §C-3 |
| 5 | **`architecture-patterns` §11 の「論理削除された親の子は物理的に残る」という一般化は、セットプレイには当てはまらない。** コンボについては成り立つ | 報告 §C-3「契約・正典との差」 |
| 6 | **`DES-005` §5.15 は「論理削除されたコンボ・セットプレイ一覧」「復元ボタン」を既に書いている。** つまり設計書が先行しており、セットプレイ側だけ実装が追いついていない | 報告 §C-3 |

### 1.2 ★`combo_setups` の物理削除は事故ではない——フェーズ1 の意図的な判断である

**本サブでいちばん重要な前提である。**

実装の当該行にはコメントが付いている（報告 §C-2 の逐語）。

```go
// 案 P1: combo_setups を明示的に削除（論理削除時は CASCADE 不発火）
```

**この「案 P1」は `M4-01`（フェーズ1）で開発者と Plan Mode で確認して採られたものである**（`docs/instructions/phase1/M4-01-setup-backend-foundation.md` §4.2.6）。当時の根拠は同書に逐語で残っている——**「setup が論理削除中の場合、紐付け表示の意味がないため」**、および **「M4-02 のフロント側でも論理削除中の setup は表示しない方針」**。

**⇒ 当時の前提は「論理削除されたセットプレイは二度と戻らない」だった。** 復元の経路が無かったのだから、紐付けを保つ意味も無かった。**本 MS はその前提を変える。** 復元を足す以上、紐付けは保たれていなければならない。

**★したがって本サブは既存の判断を覆す。** 覆すこと自体は設計卓が決めた（**D-483**）。**製造担当が判断する余地は無い。** ただし **「覆したことに気づかずに書き換えた」という形にはしない**——完了報告に、案 P1 の撤回であることと、撤回してもフロントの表示が壊れない根拠（§4.5）を書くこと。

### 1.3 ★開発者からの要求（2026-08-20）

**逐語**——**「同一のセットプレイが複数のコンボに紐づいている事があるので、セットプレイ削除の仕組みを作った時に、まだ生きているコンボの紐付けも解けた上で消える事はないようにしたい」**（**D-484**）。

**⇒ 本サブは 2 か所でこれに応える。**

| 段 | 現状 | 本サブの後 |
|---|---|---|
| **論理削除**（ゴミ箱へ入れる） | **紐付けが物理削除される。** 生きているコンボ A・B が共有していた場合、A も B も紐付けを失う。**戻す手段は無い** | **紐付けを保つ**（§4.1）。A・B からは見えなくなるだけで、復元すると A・B の両方へ一斉に戻る |
| **完全削除** | **経路が無い** | **生きているコンボから参照されている間は拒否する**（§4.4）。**巻き添えで紐付けが解ける状態を作らない** |

### 1.4 目的

1. **`POST /api/setups/:id/restore` と `DELETE /api/setups/:id/permanent` を足す**（§4.2 / §4.3）。
2. **論理削除で `combo_setups` を消すのをやめる**（案 P1 の撤回。§4.1）。
3. **生きたコンボから参照されているセットプレイの完全削除を拒否する**（**D-484**。§4.4）。
4. **セットプレイのゴミ箱まわりの API 契約の as-built を設計卓へ報告する**（§4.6）。

## 11. 開発者への確認事項

> **3 点セット（何を確認したいか／なぜ／暫定案）で書く。** **★1 と 2 は本サブの投入を止めない**——暫定案で実装し、食い違ったら設計卓が判断する。**3 は投入前に決着している。**

1. **【確定・記録】完全削除は拒否する。専用の表示は作らない**（**D-485**・2026-08-20）
   **開発者回答＝「セットプレイの完全削除は拒否で良い。なお生きたコンボに紐づくのでセットプレイは消さなかったという表示は別にユーザーに出す必要はない」。**
   **⇒ 拒否は残す（§4.4-3）。参照元コンボを列挙する専用の表示は作らない（§4.4-3b）。** **★1 点だけ設計卓の判断が入っている**——**§4.4-3c＝「何も起きない」形にはしない。** 押しても無反応だと、削除できたのか壊れたのか利用者に判別できない。**既存のエラー表示に載る短い文言 1 つで足りる。** **この読みが違う場合は実装前に戻すこと。**

2. **【確定・記録】ゴミ箱に居るコンボからの参照は拒否の理由に含めない**（**D-486**・2026-08-20）
   **開発者回答＝「実装が複雑になりそうなので含めなくて良いと思っている」。** **設計卓も同じ結論である。**
   **★ただし複雑になる先は実装ではなく利用者の逃げ道である**——**判定の SQL はむしろ述語が 1 つ減って単純になる。** 複雑になるのは、**ゴミ箱のコンボが拒否の理由になったとき、利用者はそのコンボを編集できない（ゴミ箱に居るため）ので、いったん復元 → 紐付け解除 → 再び削除、という手順を踏むしかなくなる**点である。**⇒ 含めないほうが実装も利用者体験も単純になる。**
   **★失われるものは小さい**——**セットプレイが完全に削除されている以上、紐付けが無いのは正しい状態である。** 失われるのは事前警告の機会だけであり、**保持は無期限なので完全削除を急ぐ必要も無い**（**D-458**）。

3. **【確定・記録】`M23-02` のスコープ＝案 1**（**D-483**・2026-08-20）
   **`DeleteSetup` で `combo_setups` を消すのをやめ、参照側の `deleted_at IS NULL` 除外に委ねる。`recipe_cache` は復元時に作り直す。** **★スキーマ変更を伴わない。** `M23-overview` 確認事項 6 は本裁定で決着した。

4. **【確定・記録】完全削除は明示削除で書く**（**D-484**・2026-08-20）
   **`P-04` により CASCADE の発火が保証されないため。** コンボ側が既に同型である。**★`M23-overview` 確認事項 5（既存 5 表を明示削除へ移すか）とは別件である**——本サブは**これから書く新しい経路**の書き方を決めているだけであり、**既存の経路を書き換えない。** **確認事項 5 が「移さない」に決まっても本判断は変わらない。**
