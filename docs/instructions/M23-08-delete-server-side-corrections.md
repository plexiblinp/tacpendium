## 1. 背景と目的

### 1.1 背景——**削除の周りに 5 つの是正が溜まった**

**`M23-01`〜`M23-05` は、そのつど「これは別のサブで」と送ってきた項目がある。** **本サブはその受け皿であり、共通点は「画面を触らない」ことである。**

| # | 項目 | 出所 |
|---|---|---|
| **(1)** | **完全削除が CASCADE に依存している 5 表を明示削除へ移す** | `M23-overview` §4.10 ／ **確認事項 5** |
| **(2)** | **`combos.materialized_from_combo_id` の self-FK が `ON DELETE` 句を持たない** | 同 §4.10 の末尾 |
| **(3)** | **コンボ側の完全削除の前チェックがトランザクションの外にある** | followup `setup-permanent-delete-precheck-tx` |
| **(4)** | **論理削除が、既に削除済みの行の削除日時を上書きする** | followup `combo-soft-delete-overwrites-deleted-at` |
| **(5)** | **引き継ぎオプションが削除済みセットプレイを見ないため、紐付けを黙って落とす** | followup `setup-carry-drops-trashed-links` |

### 1.2 ★★(1) の本体は 5 つの DELETE 文ではない

**★本サブでいちばん誤解されやすい点である。先に読むこと。**

**`HardDelete` が明示削除するのは `combo_setup_results` → `combo_setups` → `combos` の 3 表であり、`combos(id)` を `ON DELETE CASCADE` で参照する子 6 表のうち明示削除されているのは `combo_setups` の 1 表だけである**（`M23-RESEARCH-01` 軸 F）。

**⇒ CASCADE 依存は 5 表**——`combo_steps` / `combo_tags` / `combo_oki_options` / `combo_punishes` / `combo_punish_curations`。

**★`P-04` の影響下にあることは逐語で確定している**——**`PRAGMA foreign_keys = ON` は `*sql.DB.Exec` で 1 回だけ流されており DSN パラメータではない**（`_pragma=` の走査 0 件）。**`SetMaxOpenConns` / `SetMaxIdleConns` は本番コードに 0 件** ⇒ プールは無制限に増えうる。**⇒ PRAGMA を受け取っていない接続では CASCADE が発火しない。**

**★★そして CASCADE 依存の 5 表が消えたことを主張するテストは 0 件である。発火しなくても全テストは緑のままである。**

**★★ここからが本サブの核心である。**

**明示削除は、それ自体が新しい弱点を作る形である。**

| | CASCADE 依存 | 明示削除 |
|---|---|---|
| **新しい子表が増えたとき** | **何もしなくても消える**（FK が効いていれば） | **★誰かが `HardDelete` に 1 行足すのを忘れる** |
| **FK が効いていないとき** | **黙って orphan が溜まる** | **確実に消える** |

**⇒ 明示削除へ移すことは「忘れられる形」を選ぶことである。** **だから移すなら、忘れたことが分かる仕組みを同時に入れなければならない。**

**★★本サブの成果物のうち最も価値があるのは、5 つの DELETE 文ではなく §4.1-3 のテストである**——**スキーマから `combos` の子表を列挙し、完全削除の後にそのすべてが空であることを主張するテスト。** **新しい子表が増えて明示削除を書き忘れると、このテストが落ちる。**

### 1.3 (2)——**self-FK は明示削除では解けない**

**`combos.materialized_from_combo_id` の self-FK は `ON DELETE` 句を持たない**（既定の `NO ACTION`）。

**⇒ materialize 生成物を持つ基底コンボを完全削除すると、FK=ON の接続では FK 違反で失敗し、FK=OFF の接続では dangling 参照が残る。** **どちらになるかは接続次第であり、これが `P-04` の影響そのものである**（**★実挙動は未実査**＝§3.3-2）。

**★これは (1) と別の問題である。** 子表を明示削除しても、`combos` 自身を指すこの参照は解けない。

### 1.4 目的

1. **CASCADE 依存の 5 表を明示削除へ移す**（§4.1）。
2. **★子表の一覧が将来ずれることを検出し続けるテストを書く**（§4.1-3）。**本サブでいちばん重要な成果物である。**
3. **self-FK を明示的に NULL 化する**（§4.2）。**★マイグレーションを使わない。**
4. **コンボ側の完全削除の前チェックを Tx 内へ移す**（§4.3）。
5. **論理削除が削除日時を上書きするのをやめる。ただし成功は返し続ける**（§4.4）。
6. **引き継ぎオプションの母集団に削除済みセットプレイを含める**（§4.5）。

## 4. 詳細仕様

### 4.1 CASCADE 依存 5 表を明示削除へ移す

#### 4.1-1 何をするか

**`HardDelete` に、`combos` の行を消す前に子表を明示削除する処理を足す。** **★対象は §3.3-7 で実測した一覧であり、指示書に書いた 5 表ではない**（**★指示書の記述は 2026-08-20 の実測である**）。

**★順序**——**子から親へ。** 既存の `combo_setup_results` → `combo_setups` → `combos` と同じ並びに揃える。

#### 4.1-2 ★既存の 2 表の書き方に揃えること

**新しい書き方を作らない。** `combo_setup_results` / `combo_setups` の明示削除がどう書かれているかを読み、同じ形で足す。

#### 4.1-3 ★★子表の一覧が将来ずれることを検出するテスト（**本サブの中心**）

**実 DB テストとして、次を書くこと。**

1. **スキーマから `combos` を `ON DELETE CASCADE` で参照する子表を機械的に列挙する**（`sqlite_master` ＋ `PRAGMA foreign_key_list(<table>)`）。
2. **各子表に行を持つコンボを 1 件作る。**
3. **完全削除する。**
4. **★列挙したすべての子表で行数が 0 であることを主張する。**

**★このテストの価値は「今日 5 表が消えること」ではない。** **新しい子表が増えて `HardDelete` に明示削除を書き忘れたときに落ちることである。**

**★★ハードコードした表名の一覧でテストを書かないこと。** **それでは「忘れたことが分かる」という目的を果たさない**——**表を足す人は、テストの一覧も一緒に忘れる。**

**★列挙が空になったとき（走査が壊れたとき）にテストが緑で通らないようにすること。** **★件数が 0 件の一覧に対する「すべて空である」は常に真である**（`M23-04` / `M23-05` と同じ形の罠）。**⇒ 列挙が 1 件以上あることを先に主張する。**

### 4.2 self-FK を明示的に NULL 化する

**`combos` の行を消す前に、`UPDATE combos SET materialized_from_combo_id = NULL WHERE materialized_from_combo_id = ?` を同一トランザクション内で実行する。**

**★2 点を守ること。**

1. **★マイグレーションで FK 句を変えない**（§2.2）。**SQLite は制約の `ALTER` を持たず、表の作り直しになる。** **コストが本サブの目的に見合わない。**
2. **★NULL 化であって削除ではない。** materialize 生成物は独立したコンボであり、基底が消えても利用者のデータとして残る。**★消すと利用者のデータが黙って失われる。**

**★同型の先例がある**——`superseded_by_combo_id` は `ON DELETE SET NULL` である（`DES-003` §3.4）。**⇒ 挙動を揃えることになる。**

### 4.3 完全削除の前チェックを Tx 内へ

**`PermanentDelete` は現在、`FindByIDAllowDeleted` で存在と削除済みを確かめてから `BeginTx` している**（`M23-RESEARCH-01` D-6）。

**★実害**——**判定してから Tx を張るまでの間に、他の利用者がその行を復元しうる。** **⇒ 復元されたコンボが完全削除される。** **★これはデータの消失であり、TOCTOU の中でも重いほうである。**

**⇒ 前チェックを Tx の内側へ移す。** **★`M23-02` がセットプレイ側で採った形と同じである**（同サブの契約違反 2 件のうち 1 件・開発者承認済み）。

**★応答は変えないこと**（§2.2）。**存在しない／ゴミ箱に無い場合の `404` はそのまま。**

### 4.4 論理削除が削除日時を上書きするのをやめる

#### 4.4-1 何が起きているか

**コンボの論理削除は、既に削除済みの行に対しても成功し、`deleted_at` を上書きする**（`SoftDelete` の SQL に `deleted_at IS NULL` の述語が無い＝軸 E-1）。

**⇒ 利用者から見ると「消した日が後ろへずれる」。**

#### 4.4-2 ★★どう直すか——**成功は保つ。日時だけ保つ**

**★「2 度目は `404` を返す」へ変えてはならない。**

**`M23-03` が `DES-002` §4.2 へ契約として固定したばかりである**——**「論理削除は楽観排他を行わず冪等に成功する」。** **排他を入れると「消したいのに消せない」経路が生まれる。**

**⇒ 直し方は「`UPDATE` の条件に `deleted_at IS NULL` を足し、0 行でも成功を返す」である。**

| | 変える前 | 変えた後 |
|---|---|---|
| **2 度目の論理削除の応答** | **成功** | **成功**（変えない） |
| **`deleted_at` の値** | **上書きされる** | **★最初の値のまま** |

**★既存テスト「2 度目も成功する」は緑のまま通る。** **⇒ 期待を書き換える必要は無い**（followup の記述は「変えるならその期待も変わる」としていたが、**この直し方なら変わらない**）。

#### 4.4-3 ★セットプレイ側は触らない

**セットプレイ側は 2 度目が「見つからない」を返す。** **⇒ 非対称は残る。**
