## 0. この指示書の特殊性

### 0.1 ★★向きは決着している＝削るのではなく、末尾へ回す

**★★★開発者の判断**（2026-09-09）**は 3 点である＝(1) 一番上に出るのが違和感である ／ (2) 削る修正量が大きいなら、末尾へ出すだけでよい ／ (3) 並びが単純な DB 挿入順でないなら再検討する。**

> **★★逐語は `docs/process/parallel-board.md` の `D-801` に在る。⇒ 本書へ写さない。★禁則表現**（`scripts/check-instruction-format.sh`）**に当たる語を含むため、指示書側へ戻さないこと。**

**★★再検討の条件は満たされていない＝並びは単純な DB 挿入順である**（`M30-02` の実測。`deriveSpecialFamilies` は `moves` 配列の初出順を保持し、その配列は `moves.id` 昇順＝seed CSV の行順）**。⇒ 再検討は不要。**

**★★★したがって本サブは「削る」を実装しない。⇒ 末尾へ回すだけである。**

**★末尾を選ぶ理由は安さではない。⇒ どちらも同じ判定**（`is_derived`）**が要り、費用の本体はその値がフロントへ届いていないことだからである。★安さで選べないなら、望ましいほうを選ぶ。**

**★★★末尾のほうが安全でもある＝削ると入力手段が消える面が出うるが、末尾なら消えない。⇒ `M30-02` が「素は押せるが OD が押せない」を 7 組作ったのと同じ形の事故を避けられる。**

### 0.2 ★★★費用の本体は `is_derived` をフロントへ届けることである

**★実測**（`M30-02` ／ `followup` の `special-family-derived-variants-crowd-the-row`）:

| # | 実測 |
|---|---|
| **★★1** | **`is_derived` はフロントへ届いていない。⇒ `MoveResponse` にも `Move` にも無い** |
| **★★2** | **`code` だけの代理判定は使えない。⇒ 取りこぼし 90 / 116・誤爆 7** |
| **★★3** | **「非攻撃技を末尾へ」も `damage` が要るが、`damage` もリスト DTO に無い** |
| **★★★4** | **「魔身（酔い+1）以外の魔身」は `is_derived = true` と完全に一致する**（実測） |

**⇒ したがって本サブがやるのは「`is_derived` を届け、並べ替えのキーに使う」ことである。★4 が、開発者の言う母集団と `is_derived` が一致することの根拠である。**

**★★DTO 拡張の型は `followup` G-12 に在る＝`model.Move` ＋ `MoveListItem` ＋ SELECT 列 ＋ divergence guard の同期追加。⇒ `internal/repository/move/divergence_test.go` が両構造体の同期を強制する。★片側だけ足すと赤くなる。**

### 0.3 ★★捨てた案を 2 つ書いておく。⇒ 再検討しないこと

| 案 | なぜ捨てたか |
|---|---|
| **CSV の行順を並べ替える** | **★★成立しない。⇒ 既存 DB では `moves.id` が既に振られており、CSV を並べ替えても既存 DB の並びは変わらない。★id を振り直すのは破壊的である**（`combo_steps.move_id` 等が参照している） |
| **`code` から派生変種を判定する** | **★★取りこぼし 90 / 116・誤爆 7**（実測）**。⇒ 使えない** |

### 0.4 ★★`M30-05` とは直列にすること（**★`M30-03` は着地済み**）

**★★★【2026-09-10 更新＝`D-813`】`M30-03` は完了・受理された。⇒ 本サブの前提は満たされた。★かわりに `M30-05`**（ファミリー行の表示名に残る強度語）**が同じ面に立った。⇒ 本サブ → `M30-05` の順で直列にすること。**

**★★どちらも必殺技ファミリー行を触る。⇒ 本サブは並び、`M30-05` は表示名。★同じ関数の周辺である。**

### 0.5 ★★★設計上の衝突は「半分ほどける」。⇒ 残る半分を設計卓が裁定済みである

**`M30-01` §2.9 は「`is_derived` を入力面の可否に使わない」を 2 つの理由で決めている。**

| 理由 | 本サブでどうなるか |
|---|---|
| **(a)** `M19-DESIGN-08` §0 の述語は filler 候補から**除く**側であり、裏返すと `target_combo` 117 行が入力できなくなる | **★★起きない。⇒ 本サブは並び順にしか使わず、可否の判定に使わないからである** |
| **(b)** `is_derived` は既に 3 義を兼ねており、第 4 の用途は同書 §7 の列追加審査規約が禁じる形 | **★★★設計卓が裁定した**（2026-09-10・`D-807`）**＝本サブは審査規約に当たらない。⇒ 理由は下記** |

**★★★裁定の理由 2 つ＝(1) 本サブは列に第 4 の意味を足さない。⇒ 既に在る列を、既に在る意味のまま**（「入力トークン単独では技を解決できない」）**フロントへ届けるだけである ／ (2) 審査規約が禁じているのは「列に用途を積み増すこと」であり、「既存の値を表示側で読むこと」ではない。**

**⇒ 製造はこの点を再検討しなくてよい。★ただし実装の途中で「並び順のためだけの新しい列や意味が要る」と分かったら、止めて設計卓へ返すこと**（`CLAUDE.md` §8）**。**

## 4. 危険な箇所

### 4.1 ★★★`divergence_test.go` が構造体の同期を強制する

**⇒ `model.Move` と `MoveListItem` の片側だけに足すと赤くなる。★SELECT 列も同時に要る。**

### 4.2 ★★★陽性対照が無いと「並べ替えた」を証明できない

**⇒ 末尾に居ることだけを測ると、元から末尾だったキャラで緑になる。★入れる前の位置を測ってから入れること。**

**⇒ 実態は「入力トークン単独では技を解決できない」であり、酔いレベル変種など非派生技にも `true`**（`followup` の `M19-flag-semantics-drift`）**。★これは本サブでは都合がよい**（開発者の言う母集団と一致する）**が、「派生技だけが末尾へ行く」と説明しないこと。**

### 4.4 ★★`M30-03` と同じ関数の周辺を触る

**⇒ 直列にすること**（§0.4）**。★同時に走らせるとマージで衝突する。**
