### M26-01 — 依存ライセンスの棚卸しと三層の承認（`A2` → `A1`）

**★順序が固定されている。** `checklist` `A2` の逐語——**「AGPL 化するなら AGPL と非互換な依存が無いかを承認前に確認（承認後に発覚すると詰む）」。⇒ `A2` が `A1` より先か同時。**

| # | やること |
|---|---|
| 1 | **直接依存の棚卸し**——`go.mod` の direct ＋ `web/package.json` の dependencies / devDependencies。**license ／ 最終更新 ／ 既知脆弱性の 3 列**。**★母数を出すこと**（「N 件」だけ書かない） |
| 2 | **★AGPL-3.0-or-later との互換性判定**——**不許可なのは「AGPL の配布物に取り込めないライセンス」である。★MIT / BSD / ISC / Apache-2.0 / MPL-2.0 / LGPL / GPL-3.0 はいずれも AGPL-3.0-or-later 側へ取り込める。詰まるのは Apache-2.0 を GPL-2.0-only と混ぜる形などの限られた組み合わせである。⇒ 実物で 1 件ずつ判定する** |
| 3 | **third-party notices の同梱**——生成物の置き場と、配布バイナリからの参照方法 |
| 4 | **`DES-001` §5 の改訂**（**現行は MIT＝`CHANGE-053` で正典化済み**）と、**`SUPP-001` §5.7 の射程の明確化** |
| 5 | **`LICENSE` / `LICENSES/` / SPDX ヘッダの配置方針**（層 A / B / C で別ファイル） |

**★★`SUPP-001` §5.7 との関係を取り違えないこと。** 同節の禁止リスト〔GPL / LGPL / AGPL / CC BY-SA〕は **「取り込む依存のライセンス」＝ inbound の規定**である。**本体を AGPL-3.0-or-later にするのは outbound であり、同節に違反しない。⇒ 必要なのは「撤回」ではなく「inbound と outbound を分けて書く」明確化である。**

**★むしろ outbound を AGPL にすると inbound の許容範囲は広がる**（LGPL / MPL / GPL-3.0 が取り込めるようになる）。**⇒ §5.7 を緩めるかどうかは別の判断であり、本サブでは「広がった」事実だけを書き、ポリシーは据え置く**（`CLAUDE.md` §6 の「新規依存追加は必ず開発者に提案」は不変）。

**★★本サブは法務の判断を含む。⇒ 三層の採否そのものは開発者の承認事項**（§開発者への確認事項 1）。
