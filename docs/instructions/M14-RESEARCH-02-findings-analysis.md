## 0. 要旨（何が変わったか）

RESEARCH-02 は「第一波キャラ選定材料」を超えて、**M14-03b の前提を複数覆す事実**を出した。影響度で分類すると:

- **【指示書を直す必要がある・重】4 件**: (1) 移動 system move 9 種が手入力 CSV に既に入っており「全キャラ静的 seed」方針と二重になる〔H-2〕、(2) recovery 非整数 764 行は importer 側の問題で手入力側は解消済み＝変換系の total 検算方針が変わる〔T15/C-3-5〕、(3) move_code は英語名採番で ryu 既存 seed と体系が違う＋壊れ 3 系統〔F-1/T3/T5/F-13〕、(4) 「意図的除外データ」の存在＝除外リストが M14-03b の前提〔H-5〕。
- **【M17 段階2 に直結・重】1 件**: command→move_code が 442 グループで 1:N〔T12/F-15〕。索引は 1:N 前提でないと成立しない。
- **【第一波選定の材料・中】**: 一回転は lily/zangief のみ・literal `_2` は guile のみ・show_delta 4 キャラは custom_states 未定義〔F-8〕。
- **【AI 補完スコープの新論点・重】**: 開発者総括「公式 CSV も手入力 CSV も一部 AI 補完が必要。補完のスコープ検討が必要」。これは指示書化されていない新テーマ。

以下、影響先ごとに確定・要確認を分ける。

## 1. M14-03b 指示書（v2.2.0）に効く新事実

### 1.1 【要改訂】移動 system move の投入元二重化〔H-2〕

- **事実**: テリー手入力 CSV に `system` 10 件（`drive_parry` ＋ 移動 9 種）が含まれる。M14-03b §1.2/§4.2〔(a)〕は「移動 system move は CSV 非依存＝全キャラ静的 seed」としており、**手入力 CSV にも入っていると投入元が二重**になる。
- **開発者トリアージ**: 「移動 9 種の混入は誤りであり削除を検討する」（H-2・§C-3-2）。
- **設計判断（暫定）**: M14-03b の (a)〔全キャラ静的 seed＋alias〕を**正のまま維持**し、**変換系は手入力 CSV の `category=system` の移動 9 種を無視（drop）**する（`drive_parry` は取込＝別扱い）。手入力ツール側の是正（9 種を出さない）を待たずに本体変換系で吸収する（ツール修正と非同期で進める）。
  - 指示書 §4.1 に「category=system の移動 9 種は変換系で除外（(a) の静的 seed が唯一の投入元）。`drive_parry` は通過」を追記。
- **要確認 A**: この drop 方針でよいか（ツール側修正を待つのでなく本体で吸収）。

### 1.2 【要改訂】recovery/total 検算方針〔T15・C-3-5〕

- **事実**: recovery 非整数 764 行は **importer（公式変換）側**の問題。**手入力 CSV は recovery 全行整数で total 式も 59 行すべて一致**（T15 は手入力工程で解消済み）。ただし再出力版は `着地後N`/`全体 N` 系を数値化でなく**空欄化**しており充填が後退（作業途中）。
- **含意**: M14-03b の入力は手入力 CSV（seed 源）であり importer CSV ではない。よって**変換系が受け取る recovery は整数化済みが前提**＝指示書 §4.1 の「total 検算」は「値がある行のみ検算・空欄は total NULL」で足り、764 行問題は M14-03b に**直接は来ない**（importer 側の課題）。
- **【確定 B（開発者回答 2026-07-09）】**: recovery の**非整数情報は捨ててよい**。本アプリがセットプレイに必要とする recovery は**単一の数値（空振り時フレーム・インゲームで観測できたもの）だけ**。注釈・複数 recovery 併記は保持しない。**手入力 CSV が NULL の行は入力ミスの可能性が高い（すぐ入れられる）ので待機**（来てから投入）。
  - **設計**: 変換系は recovery を単一整数として受け（非整数が来る想定はない＝手入力側で単一値化済み）、NULL 行は total NULL（DES-003 §3.3 欠落規則）。**NULL の多い作業途中キャラは投入を待つ**（段階投入の「来た分」の粒度＝キャラ単位でなく「充填が揃ったキャラ」）。指示書 §4.4 を「recovery 単一値・NULL 許容だが NULL 過多キャラは充填待ち」へ更新。

### 1.3 【要確認・重】move_code の体系相違と壊れ〔F-1/T3/T5/F-13/T4〕

- **事実**: (i) importer CSV の move_code は英語名採番で ryu 既存 seed（000004）と共通 15/67 件のみ〔F-1〕。(ii) manon はアクセント欠落で 21 行の code が壊れる（`À Terre`→`terre` 等）〔T3/F-14〕。(iii) juri/luke は**公式英語名そのものが誤り**で code 衝突・base 不一致〔T5/F-13〕。(iv) manon/m_bison/rashid/jamie は括弧内が code に入り 40〜57 字〔T4〕。
- **重要な区別**: これらは **importer CSV（公式変換）**の話。**M14-03b の seed 源は手入力 CSV**であり、手入力 CSV は move_code を人手付与（例 `quick_burn`→`quick_burn_light` に改名・§H-6）。よって **importer の壊れ code は M14-03b に直接は入らない**が、次の 2 点が M14-03b に残る:
  - (a) 手入力 CSV の move_code をそのまま seed する（指示書 v2.2.0 §4.1 で「ツール採番値の正準形検証・再採番しない」と確定済み）＝**検証で正準形〔DES-004 §2.1〕に反する code をどう扱うか**。manon 系がテリー以外の第一波に入ると顕在化。
  - (b) ryu 既存 seed（000004）は「仮」（F-1 開発者回答）＝手入力 CSV が来たら **ryu も手入力 CSV 由来へ差し替え**が要る可能性。現行 seed の code 体系（`crouch_light_punch`）と手入力 CSV の体系（`crouching_light_punch`）が違うため、**ryu の再 seed が必要か**が新論点。
- **【確定 C（開発者回答 2026-07-09）】**: ryu の現行 seed（000004・仮）を**手入力 CSV 由来へ差し替える**。**既存 ryu コンボは消えてよい**＝moves 差し替え＋ryu の combos を**クリア**（削除）する。これにより move_id 参照の整合を気にせず（参照元コンボを消すため）clean に差し替えられる。
  - **設計**: (1) ryu の既存 moves（000004 由来 56 行）と ryu の combos/combo_steps/combo_setups/combo_oki_options/combo_tags を削除、(2) 手入力 CSV 由来の ryu moves を新規 seed、(3) 移動 system move＋alias は (a) の全キャラ静的 seed で供給。**この破壊的差し替えは M14-03c として分離**（下記 §4 末尾）。clean マイグレ DB 前提なので「消える既存コンボ」は dev DB のみ（配布 DB には ryu の実コンボ seed は無い）。

### 1.4 【要確認】意図的除外データ〔H-5〕

- **事実**: `sa2_triple_geyser_dud`（不発技）が手入力 CSV から意図的に除外。開発者「他にも意図的に抜くべきデータはありそう」。
- **含意**: M14-03b は「手入力 CSV にある行を投入」するので、除外は手入力工程で完結する（変換系は CSV を信頼）。ただし**除外の網羅性チェック**（公式にあって手入力に無い行の一覧＝importer CSV との差分レポート）を M14-03b の Plan Mode で出せると、意図的除外か漏れかの判別材料になる。
- **設計判断（暫定）**: 指示書 §5 の品質チェックに「importer CSV（公式）と手入力 CSV の move 差分一覧を完了報告に添付（意図的除外の可視化）」を追加。変換系は手入力 CSV を正とし差分を止めない（報告のみ）。

### 1.5 【軽微・確定済み確認】is_aerial・rush_variant・target_combo

- `is_aerial` は「ラッシュ版生成判定用・空中フラグでない」〔F-4〕＝手入力 CSV 値を採る（指示書 v2.2.0 §11-2 で確定済み）。**追加対応不要**。
- `rush_variant` を手入力側へ寄せるのは合意済み〔H-3〕＝指示書 v2.2.0 §11-1 で確定済み。**追加対応不要**。
- `target_combo` は手入力側で 7 件（公式 unique から再分類）〔C-3-2〕＝人手付与の passthrough〔(d)〕で正。**確定どおり**。
- `notes`/`notes_tool` 空は仕様〔H-4〕＝変換系は空を許容（raw_data 空→NULL）。**確定どおり**。

## 2. M17（command 解決 段階2）に効く新事実

### 2.1 【重・M17-02 の前提更新】command→move_code は 1:N〔T12/F-15〕

- **事実**: 同一 command に複数 move が対応するのが**全 30 キャラ・442 グループ**（最多 mai 31・blanka 23・juri 22）。例: ryu `d dl l d dl l plus p` に 6 move。
- **含意**: handover §3-(f)・M17-overview §4.4 で「condition 違いの索引衝突」を論点化していたが、実態は**必殺技レベルで広範に 1:N**。ただし **M17 段階2 のスコープは「単方向＋ボタンの特殊技」**（溜め・一回転・空中・必殺技は直接指定）なので、442 グループの大半（必殺技コマンド `d dl l plus p` 等）は**段階2 の決定論解決の対象外**。段階2 が扱う `[単方向] plus [ボタン]` の 3 トークン command に限れば 1:N は激減する見込み（要実測）。
- **【確定 D（開発者回答 2026-07-09）】: 1:N のときは move.id が最小の行を優先する**（「若い id を優先」＝派生技でない本体技が若い id になるよう、必要なら AI 補正で CSV 行順を並び替える）。
  - **設計**: 共通索引モジュール（M14-03b §4.8）は **`Lookup(charKey, token) move_code`（単一返却・同一 token に複数該当時は move.id 最小を返す）**。副次的に候補一覧を返す `LookupAll`（デバッグ・人レビュー用）も持たせる。id 最小＝seed 投入順で最初の行なので、**CSV の行順が優先順位を決める**（本体技を派生技より前に置く）。
  - **CSV 行順の要件（新規・重要）**: 「r+HP が特殊技と派生技の両方を示すとき、若い id の特殊技を優先」を成立させるには、**手入力/変換系の段階で本体技が派生技より前（若い id）に来る保証**が要る。これは §6【F・AI 補完スコープ】の一項目（command 索引のための行順正規化）として整理する。
  - 段階2 消費者は「単方向＋ボタン」に絞った索引参照で id 最小を採る（1:N でも決定論的に 1 つに決まる＝死守契約の「決定論解決」を満たす）。
  - **M14-03b §4.8 への追記**: 索引器は id 最小優先の単一返却＋LookupAll。索引構築時に同一 (charKey, token) の複数 move を id 昇順で保持。

### 2.2 【M17-02 論点】command 空欄・未知トークン・条件残留〔T8/T9/T10/T11〕

- 空欄 command 11 行〔T8〕・`raw{-}` 3 行〔T9〕・日本語条件残留 1 行〔T10・guile〕・`alt_sep`（1 move 2 command）5 行〔T11〕。
- **含意**: これらは索引源に載らない/特殊な行。段階2 スコープ（単方向＋ボタン）ではほぼ無関係（必殺技・システム寄り）だが、**索引構築時に「載せられない行」をエラーにせず skip＋記録**する方針が要る。
- **設計判断（暫定）**: M14-03b §4.8 の索引器に「command 空欄・未知トークン・条件残留の行は索引に載せず記録（fail しない）」を追記。M17-02 でこの記録を人レビュー材料にできる。

### 2.3 【設計余地・後続】溜めの扱い〔F-7/F-5〕

- 開発者「コマンド解決時に溜めを無視して通常の矢印として扱える可能性・`charge` を省く選択肢」〔F-7〕、「`circle` は方向不問の例外・`r` 起点正規化可」〔F-5〕。
- **含意**: token→索引キー正規化（M17-02・SUPP-001 §9.9→numpad 相当）の設計自由度。段階2 スコープ外（溜め・一回転は直接指定）なので **M17-02 の正規化層設計時の考慮事項**として記録。M14-03b には影響しない。

## 3. 第一波選定への所見（決定は開発者）
