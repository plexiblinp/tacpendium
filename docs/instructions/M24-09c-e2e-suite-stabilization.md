## 1. 背景と目的

### 1.1 背景

**同じ症状（E2E が時々落ちる）の未着手記録が 8 件、別々のスラッグで散らばっている。**

| # | スラッグ | 記録された症状 |
|---|---|---|
| 1 | `CO-021` | `m14-03b-custom-states-realdata.spec.ts:23`（キャラ一覧 API の初回 `res.ok()` が false）。2026-07-16 に 2 回観測 |
| 2 | `CO-022` | `m17-01` spec の初回 attempt（保存→詳細遷移の timeout）。M17-01 で 1 回観測 |
| 3 | `CO-025` | E2E timing flake クラスタ（`moves-edit` / `combo-custom-states` / `m12-06-draft-promotion`） |
| 4 | `e2e-flaky-isolation` | M14-03d 由来。**e2e 基盤の問題として §C-1 から移された** |
| 5 | `e2e-sqlite-write-contention`(a) | 並列 worker からの書き込みで `internal_error` |
| 6 | `e2e-flaky-combo-post-500` | `m19-03-setup-results.spec.ts:379` の前準備 `POST /api/combos` が 500 |
| 7 | `e2e-flaky-m18-03c-drainage` | `m18-03c-drainage.spec.ts` の 1 件 |
| 8 | `e2e-flaky-one-per-run-persists` | **`make e2e` で「毎回 1 件・毎回別のテスト」が M23 期から続いている** |

**★★8 件は「別々の不具合」ではなく「1 つの構造から出た 8 通りの現れ方」である可能性が高い。** これが本サブを立てた理由である（**D-554**）。

**★★見立ての根拠は、独立した 2 サブの実測である。**

| サブ | 落ちた spec | 隔離実行 | 直列実行（`--workers=1`） |
|---|---|---|---|
| **`M24-09b`** | `m23-09-pre-save-duplicate-dialog.spec.ts` の 2 本 | — | **緑** |
| **`M24-01`** | `m14-03e-third-wave-seed.spec.ts` | **1 passed** | **178 passed・flaky 0** |

**⇒ `E-216` の基準——結果が変わるなら timing ではなく競合。** **どちらも「並列だと落ち、直列だと通る」形であり、2 サブが独立に同じ答えへ到達した。**

**★★2026-08-26 追加——3 つ目の観測が開発者から出た**（**D-557**。逐語＝**「現状、ローカル環境で回す時も、flackyどころか、多重度の高さのせいか失敗する事があり、個別にやり直す時間が起きて無駄」**）。

| 観測者 | 環境 | 症状 | 見立て |
|---|---|---|---|
| **`M24-09b`** | クラウド実行環境 | **flaky**（`--workers=1` で緑） | 競合 |
| **`M24-01`** | クラウド実行環境 | **flaky**（隔離・直列とも緑） | 競合 |
| **★開発者** | **ローカル** | **★★`flaky` ではなく `fail`。個別にやり直している** | **多重度の高さ** |

**★★3 者とも独立に「並列度が原因」へ到達している。**

**★★しかし症状の重さが違う**——**製造 2 サブは `flaky`（retry で通った）、開発者は `fail`（通らなかった）と言っている。** **⇒ 同じ現象を違う語で数えていた可能性がある。§4.1.1 で 3 語の定義を固定した。**

**★環境差の候補**——**worker 数が CPU コア数依存なら、コアの多い環境ほど並列度が上がり、干渉も増える**（§3.3-11 で実査する）。

**★`M24-09b` が構造まで特定している**（同レポート §4-4）——**E2E は 1 スイートにつき使い捨て DB を 1 個だけ作り、全 worker で共有する**〔`web/playwright.config.ts` の `webServer` は 1 組・`COMBOMGR_DB_PATH` は 1 個〕。**⇒ spec ファイル間でデータが干渉しうる。**

### 1.1.1 ★★起票時に設計卓が確かめていないこと（**すべて §3.3 の実査項目である**）

**設計卓は実装ソースを読めない。** 上の §1.1 は**製造の 2 レポートからの引用**であり、設計卓が現物で裏を取ったものではない。

- **`web/playwright.config.ts` の現在の内容**（`webServer` の構成・`workers` の既定値・`retries` の設定）
- **使い捨て DB の作り方**（`Makefile` の e2e ターゲット ／ `COMBOMGR_DB_PATH` の渡し方 ／ 1 スイート 1 個であることの現物確認）
- **8 件の記録が現在も再現するか**（**★`M24-09b` の実測では `CO-021` / `CO-022` / `CO-025` の 5 spec は 4 回とも 0 flake だった**）
- **spec の総本数と総テスト数**

**⇒ 上記を断定形として扱わないこと。** **§3.3 で 1 件ずつ実査し、食い違ったら報告すること**（計測点 `M-77` の再発防止）。

### 1.2 目的

**E2E スイートを「信用できる」状態にする。**

**★★「信用できる」の定義を先に固定する**——**緑が出たときに「本当に通った」と読めること。** 現在は**緑が出ても「たまたま今回は干渉しなかっただけかもしれない」が常に付きまとう。**

**⇒ これは以後すべてのサブの完了判定に効く。** `M23` クローズは「毎回 1 件・毎回別のテストで flaky」を残ゲートとして記録し（`D-536`）、`M24-09b` と `M24-01` でも 1 度ずつ出た。**flake が残る限り、どのサブも「落ちたのは自分のせいか」の切り分けに毎回コストを払う。**

| # | 作らないもの | 理由 |

| **2** | **新しい E2E シナリオの追加** | **★例外が 1 つある**——**§5.3 の破壊確認のために「干渉を決定論的に起こす spec」を 1 本書く**（§4.3）。**それ以外のシナリオ追加はしない** |

### 4.1.1 ★★`flaky` と `fail` を分けて数える（2026-08-26 追加・**D-557**）

**★★開発者のローカル環境では「flaky どころか失敗する」ことが起きている**（2026-08-26 開発者申告。逐語＝**「現状、ローカル環境で回す時も、flackyどころか、多重度の高さのせいか失敗する事があり、個別にやり直す時間が起きて無駄」**）。

**★これは `M24-09b` / `M24-01` の報告よりも重い症状である。** どちらも「flaky」としか書いておらず、**retry で吸収された分と、retry でも通らなかった分が区別されていない。**

**⇒ 同じ現象を、開発者と製造が違う語で数えていた可能性がある。**

**必ず 3 つに分けて数えること。**

| 語 | 定義 |
|---|---|
| **`passed`** | 1 回目で通った |
| **`flaky`** | **1 回目で落ち、retry で通った**（`retries` が 1 以上のときだけ存在する） |
| **`fail`** | **retry でも通らなかった。★開発者が見ているのはこれである** |

**★`retries` が 0 なら `flaky` という区分は存在せず、すべて `passed` か `fail` になる**（§3.3-6 で確認する）。**その場合は「1 回目で落ちた数」を別途数えること。**

**★★これは実測の設計の穴だった。** 設計卓は §4.1 の実測 1 を「pass / fail / flaky」と書いたが、**3 語の定義を固定していなかった。** **⇒ 定義を先に固定してから数える**（`E-220` / `E-236` の型＝**「N 件だけである」の N は、母集合と定義を宣言してから数える**）。

### 4.2 ★★第 2 段——**最小の手を選ぶ**

| 系統 | 内容 | 見込みの費用 |

| **(A) worker ごとに実行環境を分ける** | DB（と必要ならサーバ）を worker 単位にする | **根治。ただし起動の仕組みを大きく変える。ポートも worker 数だけ要る** |

| **(B') worker 数を環境非依存の固定値にする** | **1 とは限らない小さい固定値**（2 など）。**★2026-08-26 追加＝D-557** | **★(A) と (B) の中間。** **★★現在の worker 数が CPU コア数依存なら、環境ごとに並列度が違い、flake の出方も違う**〔開発者のローカルと製造のクラウド実行環境でコア数が違う〕。**⇒ 固定するだけで再現性が上がりうる。§3.3-11 で決まり方を実査する** |

| **1** | **spec ファイルの書き換えが 0 本で済む手を優先する。** **★これが「積み上げない」の意味である**（§1.3-1）。0 本で済まないなら、書き換え本数が最小の手を選び、**なぜ 0 本の手が採れないかを報告する** |

### 4.2.1 ★★基準 2 の差し替え——**測るのは「1 回の実行時間」ではなく「緑になるまでの総時間」である**（2026-08-26・**D-557**）

**★★開発者が実行時間の伸びを許容した**（逐語＝**「時間が伸びるのは許容します。現状、ローカル環境で回す時も、flackyどころか、多重度の高さのせいか失敗する事があり、個別にやり直す時間が起きて無駄なため、それなら一発で上手くいく方がマシです。」**）。

**★★これは旧・基準 2 の前提そのものを覆した。**

| | 旧・基準 2 が比べていたもの | 実際に払われているもの |
|---|---|---|
| **量** | **成功した 1 回の実行時間**（並列 vs 直列） | **★緑になるまでの総時間**＝**1 回の実行時間 ＋ 落ちた分を個別にやり直す時間** |

**⇒ 並列化で稼いだ時間より、落ちた分をやり直す時間のほうが大きい。** **★★直列化すれば後者が消えるので、総時間はむしろ短くなりうる。**

**★★一般形＝「速いか」を比べるときは、成功した 1 回の時間ではなく、目的（緑）に到達するまでの時間を比べる。** **設計卓は前者だけを見て門を置いていた。**

**⇒ 新しい基準 2**:

> **実行時間の伸びは制約ではない。ただし測って報告する。**
>
> **報告する量は 2 つ**——**(a) 1 回あたりの実行時間** ／ **(b) ★「一発で緑になった回数 / 実行回数」**（実測 1 と実測 2 のそれぞれについて）。
>
> **★(b) が本質である。** **(a) が 3 倍になっても (b) が `3/3` なら、`1/3` の現状より総時間は短い。**
>
> **★10 倍を超えるような手を採る場合は、そこで止めて報告すること**（**★これは門ではなく、桁違いの手を無言で採らせないための保険である**）。

**★以下は旧・基準 2 の読み方である。系統ごとの伸び方の説明は今も有効なので残す**（2026-08-25 追記＝開発者の問い「なぜ時間が伸びるのか」への回答。**D-556**）:

**★実行時間が伸びるのは系統 (B) を採ったときだけである。**

| 系統 | 並列度 | 実行時間 |
|---|---|---|
| **(A)** worker ごとに実行環境を分ける | **維持** | **伸びない**（起動コストが worker 数だけ増える分の微増のみ） |
| **(B)** 直列化する | **N → 1** | **★ここだけが伸びる** |
| **(C)** データの名前空間を分ける | **維持** | **伸びない** |

**⇒ 基準 2 は実質「(B) を採ってよいかの門」である。(A) と (C) には掛からない。**

**★伸び幅は「N 倍」ではない。** E2E の実行時間は **サーバ起動 ＋ テスト実行** の 2 成分であり、**直列化しても起動は 1 回のままである。** 伸びるのはテスト実行部分だけなので、実際は `起動時間 + テスト実行時間 × N` に近い。

**★★「2 倍」が意味を持つかは、現在の worker 数次第である。**

- **現在 `workers=2` なら、直列化しても約 2 倍であり、基準 2 は何も止めない。**
- **現在 `workers=8` なら、直列化は明らかに 2 倍を超え、基準 2 は (B) を実質禁止する。**

**★★設計卓は現在の worker 数を知らないまま「2 倍」と置いた。** **⇒ §3.3-10 で worker 数と時間の内訳を実測すること。** **★★2026-08-26 追記——「2 倍」の門そのものが撤回されたので、この実測は「門として働くか」の判定ではなく、`(B')`（worker 数を環境非依存の固定値にする）を選ぶための材料になった**（§4.2.1 ／ §3.3-11）。

**★★「調べて報告するだけ」が正しい結末でありうる。** **レビューは「実装していない」ことを欠陥と判定しない**（チェックリスト §0.3）。

**★選定理由を完了報告に書くこと。** 採らなかった 2 系統について「なぜ採らなかったか」も書く（`CLAUDE.md` §9 共通原則3）。
