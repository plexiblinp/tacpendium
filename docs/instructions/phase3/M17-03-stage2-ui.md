## 1. 背景と目的

### 1.1 背景

**M17-02（G-k）で BE 側は完成している**: `move_commands` 索引（DES-003 §3.14）・**畳んだ解決表を配る API**（DES-002 §4.2＝`GET /api/characters/{id}/command-index`）・正規化と解決規則（DES-004 §2.4）。**本サブはその消費者（FE）を作る**。

**動機**（`combmgr-command-resolution-request` §0）: 現状のレシピ入力は**プルダウン・直接指定が中心で手間が大きい**（友人フィードバック④）。**仮想コントローラの入力を自然にする**ことが発信者の魅力に直結する。

**本サブの核心は「API を繋ぐこと」ではない**。現行 UI（M15-03・DES-005 §6.4）は:

- **通常技タブ＝方向ゾーン 3 つ（立ち `5` / しゃがみ `2` / ジャンプ `8`）× 6 ボタン**（段階1＝`standing_`/`crouching_`/`jumping_` の構造引き）
- **特殊技タブ＝ワンプッシュ直接指定**（技を直接選ぶ）

であり、**「前＋中P」を入力する面それ自体が存在しない**（前/後の方向ゾーンが無い）。**段階2 のスコープは「単方向＋ボタン」**（DES-004 §2.4.4）なので、**方向入力面の拡張が本サブの本体**である。

### 1.2 目的

- **仮想コントローラに単方向（前/後・斜めを含む）の入力面を用意**し、**段階2 の解決表を消費**して `move_code` を確定できるようにする。
- **段階1／段階2 の境界を一様フォールバックで実装**（DES-004 §2.4.5＝**解決表を先に引き、ミスなら段階1 の構造引きへ**）。
- **FE は規則を持たない**（DES-002 §4.2＝正規化・特殊技優先・タイブレークは BE が畳み済み。**FE は引くだけ**）。

### 1.3 このサブで作らないもの（スコープ外）

- **BE の解決規則・索引**（M17-02 の成果物＝**改変しない**。**例外は §4.5 のニュートラル正規化のみ**＝要判断）。
- **モーション解析・簡易入力**（死守 3 契約＝DES-004 §2.4.1。**236 等を仮想コントローラで実演させない**）。
- **必殺技・SA・投げ・空中特殊技・溜め・一回転の段階2 解決**（**直接指定のまま**＝各タブの既存 UI を温存）。
- **物理コントローラでの実モーション入力**（**M21**・FR105〜108）。
- **取込ヘルパー**（M17-04）。**スキーマ変更**。
- **`is_derived` の UI 利用**（技ピッカーでの派生技グルーピング等）＝**model.Move に `IsDerived` が無い**（`GET /api/moves` に出ない）ため、やるなら **model.Move ＋ MoveListItem ＋ SELECT 列 ＋ divergence guard の同期追加**が要る＝**本サブのスコープ外**。

### 1.4 前提

- **M17-02 完了**（マイグレ 000032〜000035）。**API の正は DES-002 §4.2**、**解決規則の正は DES-004 §2.4**。
- **解決表のレスポンス**: `{"characterId": N, "entries": {"2MP": "crouching_medium_punch", …}}`。**未 seed／不存在 ID とも 200 ＋ 空 entries**（**404 を返さない＝「壊れない」仕様**）。不正 ID は 400。
- **FE のキー構築契約**（DES-002 §4.2・DES-004 §2.4.3）: **方向テンキー数字 ＋ ボタン名**（例 `2MP`／`6HP`）。**ニュートラルは数字なし**（例 `MP`）。
- **索引カバレッジ**（2026-07-16 実測）＝搭載 **530**／非搭載 **306**（`is_derived` 304・`command` 空 2）。**未 seed キャラ（c_viper/dhalsim）は解決表が空**＝段階1 だけが動く。

## 4. 詳細仕様

### 4.1 入力面の拡張（**推奨案＝9 方向テンキー配列**・最終形は §3.3-1 で判断）

- **通常技タブの方向ゾーンを 3 → 9（テンキー配列）へ拡張**する。
  - `5`（ニュートラル）・`2`（しゃがみ）・`8`（ジャンプ）＝**現行の 3 ゾーン**（段階1）。
  - `4`/`6`（後/前）・`1`/`3`（下後/下前）・`7`/`9`（上後/上前）＝**新規**。
- **なぜこの形か**:
  - **段階2 のスコープが「単一方向トークン（斜めを含む）＋ボタン」**（DES-004 §2.4.4）であり、**9 方向がそのまま `token_key` の方向部になる**（`6HP`／`2MP`／`3MK` …）。**FE のキー構築が「方向数字をそのまま使う」だけで済む**（規則を持たない＝DES-002 §4.2）。
  - **ドメイン事実**（開発者・2026-07-16）: **「下前＋中P」も「下後ろ＋中P」も、特殊技が設定されていれば特殊技／無ければ しゃがみ中P**。**しゃがみ技はガードしながら出す場面が多く「下後ろ＋ボタン」の入力が多い**＝**斜め下は実用上重要**であり、**3 ゾーンでは表現できない**。
  - **段階1 との接続が「ゾーン縮約」1 段で済む**（§4.3）。
- **1P 側（右向き）を基準**とする（`6`＝前）。左右反転の扱いは**現行の流儀に従う**（実査）。
- **スマホ幅での成立**を確認（DES-005 §5.7＝「仮想コントローラは画面幅フルで大きめに表示」）。

### 4.2 解決表の取得と消費

- **キャラ選択時に `GET /api/characters/{id}/command-index` を 1 回**取得（**入力ごとに呼ばない**＝往復を作らない）。**queryKey は code-facts §1.1 の規約に従う**。
- **FE は `entries[key]` を引くだけ**。**正規化・特殊技優先・タイブレークを FE に実装しない**（**BE が畳み済み**＝DES-002 §4.2。**二重実装は「二度作らない」違反**）。
- **未 seed キャラは空 entries**＝**段階1 だけが動く**（壊れない）。**取得失敗時も同様**（**段階2 が使えないだけ**＝入力自体は続行できる）。

### 4.3 段階1／段階2 の一様フォールバック（DES-004 §2.4.5）

**方向ゾーンで経路を分けない**。すべての「方向＋ボタン」入力について:

1. **`token_key` を組む**（方向テンキー数字＋ボタン名。**ニュートラルは数字なし**）。
2. **解決表を引く** → **ヒット＝その `move_code` で確定**（＝**特殊技優先の結果**。BE が畳み済み）。
3. **ミス → 段階1 の構造引きへフォールバック**: **9 方向を 3 ゾーンへ縮約**（上系 `7`/`8`/`9` → `jumping_` ／ 下系 `1`/`2`/`3` → `crouching_` ／ 中段 `4`/`5`/`6` → `standing_`）し、`<zone>_<強度>_<ボタン>` を引く（**既存実装＝改変しない**）。
4. **段階1 でも引けない**（技が存在しない）＝**入力を成立させない**（既存の流儀に従う）。

> **この一様規則が「特殊技優先」の実体**である（request §1-2 の「特殊技が定義されていれば特殊技を優先」＝**解決表にあれば特殊技／無ければ通常技**の二段引き）。**方向ゾーンごとの分岐を書いてはならない**。

### 4.4 スコープ外の技の入力（**既存 UI を温存**）

- **必殺技・SA・投げ・空中特殊技・溜め・一回転**は**解決表に載っていない**（DES-004 §2.4.4 の形状フィルタ・category ガード・`is_aerial` 除外で落ちる）。**各タブの既存 UI（ワンプッシュ直接指定・2 段選択）で入力する**＝**温存**。
- **全技プルダウン（網羅フォールバック）**＝最終手段として不変。
- **段階2 は代替でなく追加**（「解決できない＝正常な結果」＝DES-006 §2.6）。

### 4.5 【要判断】ニュートラルの非対称（M17-02 残課題）

- **BE の正規化はニュートラルを `5` にする**（DES-004 §2.4.3）が、**FE のキー構築契約は「ニュートラルは数字なし」**（DES-002 §4.2）。**`5X` 形の単独キーは現 seed 0 件**のため現状は無害だが、**入ると FE から永久に引けない**（サイレント）。
- **§3.3-6 で実測**する。**0 件なら現状維持**（本サブで触らない）。
- **1 件以上あれば設計担当へ報告し、止まる**（**推測で BE を触らない**＝§2.3）。〔**設計担当の暫定案**〕**BE 側の解決表を畳むときにニュートラルの `5` を落として配る**（索引 `move_commands` はそのまま・**API レスポンスのキーを FE 契約へ揃える**）。理由＝**規則を Go に一元化する原則に忠実**（FE に「両方引く」規則を足さない）・**索引とマイグレを改変しない**。**ただしこれは DES-002 §4.2／DES-004 §2.4.3 の改訂＝CHANGE が要る**ため、**設計担当が判断する**。

## 11. 開発者への確認事項

1. **【本サブの核】入力面の形**: 〔何を〕単方向（前/後）と斜めをどう入力させるか。〔なぜ〕**現行 UI に前/後の方向ゾーンが無く、段階2 の入力面それ自体が存在しない**（DES-005 §6.4）。**DES-005 §6.6 が「実装フェーズで使い勝手を見ながら決定する」と明記している領域**であり、机上で決め切るべきでない。〔**設計担当の推奨案**〕**通常技タブの方向ゾーンを 3（`5`/`2`/`8`）→ 9（テンキー配列）へ拡張**（§4.1）。理由＝**9 方向がそのまま `token_key` の方向部になり FE が規則を持たずに済む**・**斜め下（ガードしながらの入力）が実用上重要**・**段階1 とはゾーン縮約 1 段で繋がる**。**Plan Mode で実物に近い提案が出た時点で最終判断をお願いします**。
2. **【要判断・実測後】ニュートラルの非対称**: 〔何を〕`5X` 形のキーが実在した場合の対処。〔なぜ〕**BE の正規化は `5`／FE 契約は数字なし**＝**入ると永久に引けない**（サイレント）。〔暫定案〕**現 seed 0 件なら現状維持**。**1 件以上あれば BE の解決表配信でニュートラルの `5` を落とす**（索引は不変・**規則は Go に一元化**）＝**DES-002 §4.2／DES-004 §2.4.3 の改訂＝CHANGE が要る**ため、実測後に設計担当が判断します。
