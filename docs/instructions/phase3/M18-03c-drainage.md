## 4. 詳細仕様

### 4.1 項目 1：案C（`neutral_jumping_heavy_kick` を候補に含める）

| | 現行（as-built） | 案C |
|---|---|---|
| 述語 | `sm.IsAerial && strings.HasPrefix(sm.Code, jumpHeavyPrefix)` | `sm.IsAerial && sm.Category == "normal" && strings.Contains(sm.Code, "jumping_heavy_")` |
| 定数名 | `jumpHeavyPrefix` | **改名する**（中間一致へ変わるため `prefix` の語が実態と食い違う＝**L-7**） |

- **フレーム判定・レーン境界・`JumpSlack`（実値 4）・`MovementTotals` は不変。** `jump_neutral` を取得していないが、`jump_neutral`／`jump_forward`／`jump_back` の `total` は **12 キャラ全数一致**（RESEARCH-02 C-3・不一致 0 件）のため `JumpForward` のみで判定できる。
- **増分は 2 件**：`juri.neutral_jumping_heavy_kick`（startup 10／damage 800）・`ken.neutral_jumping_heavy_kick`（startup 6／damage 900）。
- **unique 系空中特殊技 7 行（7 code）は `category='normal'` 条件で自動除外**される（全件 `category='unique'`）。
- **相手技の除外規則には触れない**（移動 system move 9 種 ＋ `is_aerial=1` の完全除外は不変）。

### 4.2 項目 2：materialize 後のノーマル版を「畳む」

**1. 判定条件（裁定 1・2）**

```
変換済み(X) ⇔ EXISTS( Y : Y.materialized_from_combo_id = X.id AND Y.deleted_at IS NULL )
```

- **相手技を問わない。** FR301 の dup キーに**相手技は入っていない**（DES-006 §2.3）ため、**1 つの基底から作れる PC 版は 1 つだけ**である。相手技 B 用に作り直そうとしても FR301 で弾かれ、正しい使い方は「既存の PC 版を相手技 B にも紐づける」。したがって**基底は PC 版を生んだ時点で変換元としての役目を終えている**。
- **`is_draft` は問わない**（裁定 2）。仮登録の PC 版でも「変換済み」とみなす。
  - **既知の非対称（許容・DES に注記）**：FR301 の dup 判定は `is_draft = 0` 固定なので、**「畳まれているのに重複防止では検出されない」**状態が生じる。**これは承知のうえで許容した**（欠陥ではない）。
- **PC 版を削除すると自動的に畳み解除される**（EXISTS 判定の帰結）。**正しい挙動**であり、基底から作り直せる必要がある。

**2. 見せ方（裁定 1＝「畳む」・消さない）**

- **既定では孫のコンボ一覧に出さない。**
- **始動技ノード配下のコンボ一覧の末尾に「変換済み (N 件)」の折りたたみ**を置く。開くと該当コンボが **「PC 版を作成済み」バッジ付き**で見える。
- **03a の第3セクションと同じイディオム**（件数を出して折りたたみ、開けば中身が見え、理由が分かる）。**新しい見せ方を作らない。**
- **N が 0 のときはセクションごと出さない**（03a の「隠したもの」空表示と同じ流儀）。

> **なぜ消さずに畳むか**：探す画面は M18-02 以来「除外は消さず理由バッジ付きで出す」を一貫して守っている。ここで無言で消すと **M18 で初めての例外**になり、ユーザーから見て「さっきまであったコンボが消えた」となる。**silent に消さないのが M18 の設計思想の核**である。

**3. 実装の分界（BE／FE）**

- **判定（EXISTS）は BE** で行い、孫 `ComboNode` に**フラグを 1 つ追加**する（出力専用・後方互換の追加フィールド）。
- **畳む／開くの表示は FE。**
- **走査規則を FE に二重実装しない**（DES-002 §4.2）。「判定は BE・表示は FE」は M18-02 で確立した分界であり、これに従う。
- **レーンごとに配列を分けない**（レスポンスが複雑化する）。フラグ 1 つで足りる。

**4. 既知の穴（許容・裁定 3）**

ノーマル版 X から PC 版 Y を作った後、**同一レシピの counter 版 Z は FR301 で弾かれて変換できず、孫に残り続ける**（X は畳まれるのに Z は残る）。**対処しない**——候補集合の判定に `recipe_hash` を持ち込むのは重すぎるため。発生条件（同一レシピで normal 版と counter 版を別々に登録）は限定的。**DES に注記する。**

### 4.3 項目 3：手動確認レーンの登録導線を `combo_punishes` まで繋ぐ

**1. 現状**：「手動で確定反撃を登録」ボタンは `/combos/new` へ遷移するが、**`punishContext` は保存後のトースト文言にしか使われておらず `combo_punishes` を作らない**。結果、03a が実装した「登録済みの確定反撃」表示が**現状 UI から発火しない**。

**2. 実装**

- **`location.state` に `opponentMoveId` を追加**する。**`ComboEditor` の Props 契約（`mode`／`initial`／`initialCharacterId`）は変更しない**（M18-02・03b と同じ流儀）。
- **コンボ保存の成功後に `POST /api/combo-punishes` を呼ぶ**（既存 endpoint。新設しない）。
- 成功後は探す画面の元の位置へ復帰し、**当該相手技の「登録済みの確定反撃」に現れる**。

**3. 失敗時の扱い（設計判断）**

コンボ保存と紐づけは**別リソースであり原子性を求めない**。保存が成功して紐づけが失敗した場合：

- **コンボは保存済みである旨を明示**し、紐づけに失敗したことを**ユーザーに伝える**（silent に失敗させない）。
- **コンボを削除して巻き戻さない**（ユーザーの入力を失わせない方が害が小さい）。

**4. ボタン文言を実挙動に合わせる**

03a・03b では「**登録と名乗るボタンが登録しない**」状態を許容してきた（開発者が 2026-07-26 に据え置きを再判断）。**本サブで解消する。** 文言は製造判断でよいが、**登録という語が実挙動と一致すること**を条件とする。

**5. 完了後、DES-005 §5.20 の既知の限界 2 を「解消済み」と書けるようになる**（03a・03b では表示側のみのため書けなかった）。完了報告の DES 反映要点に明記すること。

### 4.4 項目 4：curation の登録導線

**1. 置き場所＝第3セクション（区分を判定できない反撃）のコンボ行のみ**

**2. 実装**

### 4.5 項目 5：手動入力の `hit_type` プリフィル

- **ジャストパリィタブからの登録**＝`just_parry_punish_counter`／**ガードタブからの登録**＝`punish_counter` をプリフィルする。

### 4.6 項目 6：materialize のダメージ加算の訂正

**1. Super Arts／Critical Arts は加算しない**

| 始動技の `category` | 挙動 |
|---|---|
| `super_art`／`critical_art` | **加算しない** ＋ **加算スキップ理由コードを 1 つ追加**（既存 3 コード〔`base_damage_null`／`starter_move_not_set`／`starter_move_damage_null`〕の命名流儀に合わせる。コード名は製造判断） |
| それ以外 | 従来どおり加算 |

- **表示**：「Super Arts／Critical Arts にはパニッシュカウンター補正が乗らないため、加算していません」の趣旨。**内部値と表示ラベルは分離して記述する**（L-7）。
- **§3.3-2 の実測が 0 件なら本項は実装しない**（例外自体が不要）。**実装しなかったことを完了報告に明記**する。
- **実測が 0 件でも、DES-003 §3.3 errata の記述（Super Arts／Critical Arts は等倍・多段技の `damage` は合計値）は保全する**（通知書 §6-1）。**インゲーム検証でしか再発見できない事実**であり、実装の要否とは独立に価値がある。

**2. 生成時メッセージ（無条件表示）**

- 「始動技が多段の場合、加算量は概算です。実測値で調整してください」の趣旨を、**materialize の生成成功時に表示**する。
- **無条件に表示する。** `moves` に**ヒット数を表す列が存在せず**（`active` は持続フレームでありヒット数ではない）、**多段かどうかを機械判別できない**ため。**「多段のときだけ出す」と工夫しないこと**——判別できないので必ず誤る。
- **生成物への永続的な注記（`memo` 自動追記等）は行わない**（開発者裁定）。条件付きに書くには多段の検出が要り、無条件に書くと**加算が厳密に正しいケース（単発の通常技始動＝大多数）まで汚染**するため。

**3. 触ってよい範囲**

**ダメージ計算の分岐のみ。** `model.Combo`・`combos` の INSERT 列・`DuplicateKey`／`CalcRecipeHash`／`RecomputeComboCache`・コピー範囲・FR301・トランザクション境界には**手を出さない**（§2.2・§2.3）。
