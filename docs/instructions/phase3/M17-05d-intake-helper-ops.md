## 1. 背景と目的

### 1.1 背景（§G-14 の要点）

M17-04 の実データ検証で、**取込ヘルパーの二段パイプライン**（① アプリ外 AI プロンプト → 候補トークン列／② 本アプリ厳密照合 → `move_code` 確定）のうち、**② は仕様どおり動く（実測 54/67≒81%）が、① が SF6 実コンボ（ドライブラッシュ・OD・SA1〜3・DI・パニッシュカウンター・回数・選択・条件・注記）をトークン語彙 24 種に原理的に落としきれない**ことが判明した（followup §G-14）。

**テコ入れの方向は「語彙拡張」ではない**（語彙は索引正規化と一体で安易に増やせない＝DES-004 §2.4.3）。**§G-14 を段で分割**し、**§G-14a＝① プロンプト側＝本サブ**（M17 内）／**§G-14b＝② エイリアス照合側（`preset_aliases` の充実）＝M20**、とした（M17-overview v1.3.0 §3）。

**本サブの狙い＝「AI に頑張らせる」のでなく「ユーザーの前処理と複数 AI で ① の負荷を下げる」**（語彙 24 種を一切触らずに解決率を上げる）。

### 1.2 目的（実装する 3 件）

- **(a) 複数の AI サービスを試す旨の明示**。
- **(b) 入力整形の最低限のお願い 3 件**（回数展開・切れ目明示・分岐記法の行単位化）。
- **(c) ユーザー独自ルールの自由入力欄**（プロンプトへ結合・**保存する**）。

### 1.3 スコープ外（触らない）

- **② 厳密照合（`internal/moveindex`・`csvcore`・`inputresolve`・intake の照合ロジック）**＝**差分ゼロ**（M17-04 の成果＝本サブは ① 側だけ）。
- **トークン語彙 24 種・索引正規化**（§G-14b・M20）。
- **`preset_aliases` の充実**（§G-14b・M20）。
- **BE（`intake.Handler.Resolve`／`BuildCSV`）・DTO・スキーマ・CSV 契約**。
- **M17-05a が触る `ComboImportPage`（§5.14）**＝**別サブ・別サーフェス**（05d は §5.19 のみ）。

## 2. 変更しないもの（非回帰）

- **② 厳密照合の挙動と実測解決率**（本サブ前後で `resolve` の出力が変わらないこと＝**プロンプトの文面変更は ① の出力〔ユーザーが AI から得るトークン列〕の質を上げるだけで、② の照合には触れない**）。
- **「本体から LLM を呼ばない」**（DES-005 §5.19・CHANGE-071）＝**(a) は「ユーザーが自分で複数 AI に投げる」ことの明示**であって、アプリが複数 AI を呼ぶのではない。
- **i18n 境界**＝§5.19 は**固定 ja**（M16-06 境界・キーを足さない）。

## 3. 実装の要点

### 3.1 必読

- **DES-005 §5.19**（取込ヘルパー・**固定 ja**）・**CHANGE-071 通知書**（二段の役割分担・「プロンプトをコピー」・人レビュー表）・**M17-04 伝達資料 `20260717-M17-04-design-handover.md`**（① の限界の実例）・**followup §G-14／§G-14a**。
- **code-facts**（`/import/combo/helper` → `IntakeHelperPage`・`web/src/features/intake/`・**`prompt.ts`**・`useIntakeResolve`／`useIntakeBuildCsv`・**config 構造体＝§5〔自由入力欄の保存先判断の材料〕**・**localStorage 前例＝`onboarding-seen-v1`**）。

### 3.2 (a) 複数の AI サービスを試す旨の明示

- **「プロンプトをコピー」の近傍に、複数の AI サービスで試すことを促す注記**を置く。**要旨**: 「1 つの AI で上手くいかない場合、別の AI サービスでも試してください。出力の安定度は AI やコンボの書き方によって変わります」。
- **特定モデルを単一指名しない**（当初案の「GPT 等の高性能モデルを推奨」は撤回＝**Gemini でも動くことが判明**・2026-07-18 開発者観察）。**「複数を試す」に寄せる**（投入フォーマットは実運用で無数＝100% は保証できないため）。
- **文言は仮でよい**（確定は開発者・§6-1）。

### 3.3 (b) 入力整形のお願い 3 件

- **プロンプト本文（`prompt.ts`）＋画面注記**に、ユーザーへの前処理のお願いを**3 件**入れる:
  1. **回数表記の展開**: 「`2弱P×2〜3` のような回数つき表記は、`2弱P > 2弱P > 2弱P` のように展開してください」。
  2. **コンボの切れ目を明示**: 「コンボの切れ目が分かるように、1 コンボ 1 行にする・行頭に番号を付けるなどしてください」。
  3. **分岐記法の行単位化**: 「途中から分岐するコンボ（1 本の始動から複数の締めに枝分かれする書き方）は、分岐ごとに独立した行へ戻してください」。**具体例を添える**（下記）。
- **(3) の具体例**（プロンプト or 注記に含める）:
  ```
  【分岐している例（そのままだと取り込みにくい）】
  - [ストック1〜2] 2強P(PC)>強ライズ>OD空フレア(Lv2〜3)>…
      - 中ライズ 3925〜4180dmg
      - SA1 4345〜4565dmg
      - SA3 5605〜5716dmg
      - ODライズ>SA3 5745〜6015dmg

  【行単位に戻した例（取り込みやすい）】
  - [ストック1〜2] 2強P(PC)>強ライズ>OD空フレア(Lv2〜3)>中ライズ 3925〜4180dmg
  - [ストック1〜2] 2強P(PC)>強ライズ>OD空フレア(Lv2〜3)>SA1 4345〜4565dmg
  - [ストック1〜2] 2強P(PC)>強ライズ>OD空フレア(Lv2〜3)>SA3 5605〜5716dmg
  - [ストック1〜2] 2強P(PC)>強ライズ>OD空フレア(Lv2〜3)>ODライズ>SA3 5745〜6015dmg
  ```
- **これらは「AI へのお願い」としてプロンプトに書く**（AI に前処理させる）**＋「ユーザーへのお願い」として画面にも出す**（ユーザーが手で直せる）。どちらの経路でも効く。

### 3.4 (c) ユーザー独自ルールの自由入力欄

- **取込ヘルパー画面に自由入力欄（textarea）**を設け、**「プロンプトをコピー」時に、その内容をプロンプト本文へ結合**する（ユーザー固有の別名・書き方のクセを AI へ伝えられる）。
- **開発者のプロンプトをそのまま使わなくてよい**旨を注記（一部整形＋ユーザールール追加を許容）。
- **保存する**（開発者承認 2026-07-18＝毎回書き直す形は実運用で使われなくなる）。
- **【保存先＝Plan Mode で確定・設計推奨は localStorage】**:
  - **config（TOML）に足さない**ことを推奨。config は固定構造（server/database/logging/security/defaults）で**可変長テキスト欄が無く、足すと TOML スキーマ変更＝承認ゲート**になる（重い・1 テキストのために config を広げるのは過剰）。
  - **localStorage を推奨**（前例＝`onboarding-seen-v1`・CLAUDE.md §10.X 許容表・**スキーマ変更ゼロ**・取込ヘルパーは他画面と共有しない単一画面のローカル設定）。**キー案 `intake-helper-user-rules-v1`**。
  - **Plan Mode で実コードの保存機構（config／localStorage／他）を実査**し、**localStorage で足りるか・config を触る必要が本当にあるか**を提示すること（**config を触るなら承認ゲート＝設計担当へ報告**。推測で config を広げない）。

### 3.5 Plan Mode 着手前確認（**必須**）

1. **`prompt.ts` の現行構造**（本文＋moves 一覧＋エイリアスをどう結合しているか）を実査し、**(b) のお願い 3 件と (c) の自由ルールをどこに差し込むか**を提示。
2. **(c) の保存先**（§3.4）＝**localStorage で足りるか・config 拡張が要るか**を実査で確定。**config を触るなら承認ゲート**（設計担当へ報告）。
3. **`IntakeHelperPage` の現行 UI**（「プロンプトをコピー」ボタン・人レビュー表）と、**(a) 注記・(b) 注記・(c) textarea の配置**（画面が縦に伸びすぎないか・スマホ幅で成立するか）。
4. **② 照合への非波及**（`prompt.ts` 以外の intake を触らないこと＝`git diff` で `internal/moveindex`・`csvcore`・`inputresolve`・intake の照合部が差分ゼロ）。
5. **i18n 境界**（§5.19 は固定 ja＝キーを足さない）。

## 4. テスト

- **プロンプト結合**: (c) の自由ルールが「プロンプトをコピー」の出力へ結合される（空なら結合しない）。(b) のお願い 3 件がプロンプト/注記に含まれる。
- **保存の往復**: (c) を入力 → リロード → 復元される（保存先の実装に応じた単体/E2E）。
- **② 非波及**: `resolve`／`BuildCSV` の既存テストが**不変で通る**（intake 照合部に差分ゼロ）。
- **i18n**: 追加 UI 文言があれば固定 ja（キーを足していない）。`make e2e` 非回帰。品質 grep（禁則・簡体字・「起き攻け」・「DR」略記）。

## 6. 開発者への確認事項

1. **(a)(b) の文言・(c) の注記文言**＝**仮で実装し、出力確認後に確定でよいか**。〔暫定案〕仮句で実装（M16-07・M17-05c-fix と同じ運用）。
2. **(c) の保存先＝localStorage（`intake-helper-user-rules-v1`）で確定でよいか**。〔暫定案〕localStorage（config 拡張＝承認ゲートを避ける）。**LAN 越しに別端末から使う場合、localStorage は端末ローカルなので共有されない**が、自由ルールは個人の入力癖なので端末ローカルで妥当と判断。**サーバ保存（config/DB）を望む場合のみ承認ゲート**。
3. **(b) の「お願い」を プロンプト側とユーザー画面側の両方に出す**方針でよいか。〔暫定案〕両方（AI にもユーザーにも効く）。冗長と感じるなら画面側は折りたたみに。
