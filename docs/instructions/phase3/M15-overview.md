## 1. 目的・位置づけ

M15 はフェーズ3 の**使いやすさ底上げクラスタ**。完了 = friend FB 第一波（2026-06-28・17 件）が示した「機能は満たすが使いやすさが低い」への対処が反映され、発信者・一般利用者双方の入力摩擦・説明不足が軽減した状態。加えて **コマンド入力解決 段階1（しゃがみ／ジャンプ攻撃）と必殺技＝直接指定の UI 骨格**を先行導入する（command-resolution-request）。

M15 の性格（M14 と対照的）：**破壊的マイグレ・新規テーブルを持たない自由改訂中心**。DES-004（表記正典）・DES-005（画面）の**軽微 CHANGE が一部**見込まれる程度。**M14 と並走可**（早期に体感品質を上げる価値が高く、発信者の入力摩擦低減にも効く）。

達成目標：

- **入力摩擦の低減**: プルダウン中心の入力をボタン等へ改善（FB④）。コマンド入力解決 段階1（方向ゾーン＋ボタン → `move_code` variant 引き当て）で通常技入力を軽く。必殺技は直接指定の UI 骨格を用意（モーション解決はしない）。
- **説明不足の解消**: 「選択モード」「modifier」等の説明を info-mark ヘルプ機構で束ねて提示（FB③⑤⑩）。
- **タグ色の選択性**: 灰色固定・カラーコードのみを、色名／スウォッチ選択 UI へ（FB⑭⑮）。
- **初回体験の可読性**: 初回起動時に何をすべきかを示すオンボーディング（FB⑯）と、入力項目を隠せる上級者モード（FB⑰）。
- **表示整理・バグ是正**: 登録画面の縦スクロール軽減・表示項目整理（FB①）、比較画面の始動技「#196」生 ID 表示バグの是正（FB②）。
- **E2E 拡充の前提整備**: メタデータ入力の安定 test-id（F12-4）。

**M16 依存の分離（重要）**: 始動 vs 消費の曖昧さ（FB⑨⑪⑬）と「技/非技ステップ」表記（FB⑥）は、**モデル判断（M16）が確定してからでないと正しいラベルを書けない**（datamodel-issues 付記の順序依存）。M15 は **M16 非依存項目を先行**し、これら表記追従は M16 完了後に回す（§2.1・§5・確認事項5）。

## 4. 主要設計判断・調査結果の反映

### 4.1 M16 非依存の切り分け原則（M15 スコープの核）

- M15 は **M16 非依存の 10 項目（①②③④⑤⑩⑭⑮⑯⑰）＋コマンド解決 段階1・必殺技 UI 骨格**を先行する。**再編確定を待たず着手できる**（phase3-overview §M15）。
- **表記ラベル（⑥⑨⑪⑬）は M16 のモデル判断確定後**にしか正しく書けない（始動 vs 消費の区別＝M16 ①／技/非技 taxonomy＝M16 ④）。M15-07 として分離し M16 完了後に実施（順序を逆にすると誤ラベルになる＝datamodel-issues 付記）。

### 4.2 比較画面 生 ID バグ（FB②）の着手前実査（M15-05・裏取りゲート）

- 「始動技#196」の生 ID 表示は、**症状のレイヤ ≠ 真因のレイヤ**の典型（digest §1-A・M12-1/M10-4）。フロント表示の名称解決漏れか、バックエンドの応答が id のみか、**着手前に実画面・実コードで真因を特定**してから指示書に修正対象を書く（「あるはず」で書かない）。
- **F12-2 連動**（M12-01 C-20 比較画面取りこぼし疑い）。比較画面の始動技表示経路（一覧/比較/詳細で共有の move 名称解決）を grep 全数特定してからスコープを切る（M12-3 UI 現状の全数調査）。

### 4.3 info-mark の横断機構化（M15-02）

- FB③⑤⑩ を個別対処せず**横断ヘルプ機構**（項目に info-mark を付し説明を出す）として設計し、③（選択モード）・⑤（modifier）をその最初の適用先とする。
- **表示箇所の全数調査**（一覧/詳細/比較/編集で説明を出す箇所）を着手前に行う（digest M12-2＝表示トークン・全表示箇所調査）。DES-005 の表示方式に触れるため CHANGE 要否を着手時 view で確定。

### 4.4 コマンド解決 段階1 の非スキーマ設計（M15-03）

- **段階1（しゃがみ／ジャンプ攻撃）は `move_code` 構造（`crouching_*`/`jumping_*`）から決定論で引き当て**、追加データ・スキーマ変更を伴わない（§2.3 phase3-overview）。方向ゾーン（上／下／ニュートラル）＋ボタンで variant を引く。
- **必殺技・空中特殊技は「技の直接指定」の UI 骨格のみ**（必殺技ボタン＋強度／ピッカー等・形式は委譲）。**モーション解決はしない**（仮想で 236 を実演させない一点のみ割り切り）。段階2 の決定論エンジン（M17・取込ヘルパー共通）を待たずに先行。
- **死守契約 3 点**（公式表記のみ／モーション解析しない／出口は必ず `move_code`）を指示書で明記。ISSUE-002（modifier 専用ボタン化）と整合。

### 4.5 タグ色の現状確認と実装レイヤ（M15-04）

- 現状（新規登録で灰色固定・カラーコードのみ）の**実態を着手前に code-facts／実コードで確認**する（決め打ちしない＝digest M12-1）。タグの色保持（既存 `tags` の color 保持形態）が既にカラーコード列なら **UI 追加（色名/スウォッチ選択）のみで非スキーマ**、保持形態の変更が要るなら §2.4 のデータ変更判定へ回す。
- 色名／スウォッチ選択 UI は既存 shadcn/ui パターン踏襲（自作再発明しない＝playbook §4.6）。

### 4.6 上級者モードの永続化スコープ（旧 M15-06 ⑰）

> **【v1.2.0 更新】⑰上級者モードは M15-05 の登録画面セクション折り畳み（既定全展開・任意で畳む）で目的（入力項目を隠す）を達成したため、別建ての上級者モードは新設しない（M15-06 から除外）。以下の永続化スコープ検討は不要になった（記録として残す）。M15-06 は⑯オンボーディングのみ＝初回既読フラグ `onboarding-seen-v1`（localStorage・UI 状態・CHANGE-059）。**

- FB⑰（入力項目を隠す上級者モード）は、**表示制御に閉じれば M15 スコープ**。ただし**モード選択を設定として永続化**する場合は、Settings 構造・永続化層（CLAUDE.md §10.X・SUPP-001 §5.8 予約等）を着手前に確認してスコープを確定（設定永続化は横断要件で取りこぼしやすい＝digest §1-E）。
