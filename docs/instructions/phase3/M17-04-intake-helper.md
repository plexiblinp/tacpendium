## 1. 背景と目的

### 1.0 【最重要】本サブが移行するのは「ユーザーのコンボ」であって moves ではない

**混同しやすいので最初に固定する**（開発者指摘 2026-07-17）。

| 項目 | 本サブ（M17-04） | ※混同しがちな別物 |
|------|-----------------|-------------------|
| **移行するもの** | **ユーザー（発信者）が自分の形式で管理している「コンボ」**（メモ・エクセル・テキスト） | **moves マスタ**（技データ）＝**M14-03 系列の seed で入る**（本サブの対象外） |
| **出力** | **コンボ CSV**（`combos.csv` ／ `setups.csv`。**DES-002 §7.6 の契約**）→ **既存の import 動線**（DES-005 §5.14） | 手入力 CSV（20 列）＝**seed 源**（`moves-input-tool` の出力） |
| **moves との関係** | **照合先として参照するだけ**（キャラ別・エイリアス込み）。**moves を作らない・変えない** | — |
| **ツール** | **本サブ＝本体アプリの機能** | `moves-input-tool`（別 module）／`combomgr-importer`（FR701・別リポジトリ） |

- **`move_code` を確定するのは「コンボのレシピの各ステップ」**（例: 発信者のメモ「弱P > 弱昇竜」→ ステップ 2 件がそれぞれ `standing_light_punch` / `shoryuken_light` に確定する）。**技マスタを作っているのではない**。
- **phase3-overview §M17 ④ の逐語に `moves-input-tool` が出てくる**（「未解決は人レビュー動線へ（既存 `moves-input-tool`／CSV import 突合動線の拡張）」）が、これは**人レビュー動線の"形"の前例**として挙げられているだけで、**本サブが moves-input-tool を触るという意味ではない**（同ツールは別 module・`.gitignore` 配下）。**本サブが拡張するのは本体の CSV import 突合動線**（DES-005 §5.14）。
- **したがって本サブは `moves` テーブルに一切書き込まない**（read only）。

### 1.1 背景

**M17＝発信者の流通基盤**。その ④ が本サブ。動機は phase3-overview §1 の「**発信者にメモ／エクセルから本アプリへ乗り換えてもらう**」であり、**乗り換えの摩擦を下げる**のが目的。

**本サブの「発信者」とは**（開発者定義 2026-07-17）: **一般の利用者のうち、特にコンボを見つけて世界へ発信することに関心がある層**（**大半の利用者は自分で見つけるより人のコンボをインポートしたい**側）。**この層は Excel やメモに"独自の方式"で記録を蓄積してきている**。**それを手作業でなく、なるべく簡単にインポートできるようにするのが本サブの目標**。

**なぜ AI（① アプリ外プロンプト）が要るのか**（開発者 2026-07-17）: **人によって記録の仕方が違う**ため、**シェルスクリプトや固定パーサでは対応できない**。**「人それぞれの自由表記」を吸収する部分だけを AI に任せ、コードの確定は決定論に戻す**——これが二段の役割分担（§1.2）の理由である。

**スコープの正本は phase3-overview §M17 ④**（**逐語**）:

> 発信者のメモ/エクセル/テキストを取込 CSV へ変換するヘルパー。**二段の役割分担を外さない**＝① 表記正規化（曖昧）は**アプリ外プロンプト**（自由表記→候補トークン列）、② コード確定（確実）は**アプリ側**で **move マスタ（キャラ別・エイリアス込み）への厳密照合**。**AI に技コードを生成・確定させない**。未解決は人レビュー動線へ（既存 `moves-input-tool`／CSV import 突合動線の拡張）。

**本サブが作るのは ② だけ**（① はアプリ外＝本体の実装対象でない・§1.3）。

**エンジンは既にある**: M17-02 が `internal/moveindex`（M14-03b 由来）を本体ランタイムへ確立済み。**本サブは「二度作らない」の実践＝同じ索引の消費者を増やすだけ**（`combmgr-command-resolution-request` §2＝「引き当て表は取込ヘルパーの表記解決（`236LP` → `hadoken_light`）と同じエンジン。共通化を前提に設計するのが経済的」）。

### 1.2 死守事項（**これを外したら本サブの意味が無い**）

1. **AI に技コードを生成・確定させない**。**AI（アプリ外プロンプト）の役割は「曖昧な自由表記 → 候補トークン列」まで**。**`move_code` の確定は必ずアプリ側の厳密照合**で行う。**AI が `hadoken_light` のような code を吐いて、それをそのまま信じる実装は禁止**（存在しない code・別キャラの code・綴り違いが静かに混入する）。
2. **照合は決定論**（曖昧一致・あいまい検索・編集距離・「たぶんこれ」を実装しない）。**引けなければ未解決**。
3. **未解決は人レビューへ**（**フォールバックしない**＝M17-overview §4.3。**段階2〔M17-03〕は「通常技へ落とす」フォールバックを持つが、取込側は持たない**＝挙動が分岐する。**共通 IF は「未解決を未解決のまま返す」に固定**＝M14-03b §4.8）。
4. **エンジンを二度作らない**（`internal/moveindex` の**消費者拡張**。**新規実装・コピー実装は違反**）。

### 1.3 このサブで作らないもの（スコープ外）

- **① アプリ外プロンプト（自由表記 → 候補トークン列）**＝**アプリ外**。**本体 repo に実装しない**（`pre-seed-data-check-prompt` と同型の運用資産。**ひな形の作成主体は §11-3 で確認**）。

- **`moves.command` 列の復活**（index-only＝判断3）。

- **import の動線・重複挙動**（M17-05a）。**CSV 契約の変更**（DES-002 §7.6 の列構成は不変）。

### 4.1 二段の役割分担（**外さない**）

| 段 | 誰が | 何を | 性質 |
|----|------|------|------|
| **①** | **アプリ外プロンプト（AI）** | 発信者の**自由表記**（メモ/エクセル/テキスト）→ **候補トークン列** | **曖昧**（AI が得意） |
| **②** | **アプリ側（本サブ）** | 候補トークン列 → **move マスタ（キャラ別・エイリアス込み）への厳密照合** → `move_code` 確定 | **確実**（決定論・**AI に触らせない**） |

- **AI に `move_code` を生成・確定させない**（§1.2-1）。**AI の出力を `move_code` として信じる実装は禁止**。
- **本サブが実装するのは ② のみ**。

### 4.2 照合（BE）

- **`internal/moveindex` の消費者拡張**（**新規実装・コピー実装をしない**＝「二度作らない」）。
- **`Lookup(charKey, token) → (move_code, ok)`** を使う（**非派生技のみ・id 最小タイブレークで単一返却**）。**`Lookup` はクエリを常に正規化する**ため、**呼び出し側で正規化を再実装しない**。
- **フォールバックを持たない**（**M17-overview §4.3**＝**段階2 は「通常技へ落とす」を持つが取込側は持たない**）。**引けなければ未解決のまま返す**。
- **エイリアス経由の照合**（`preset_aliases`）を含めるかは §3.3-4 で提示（**DES-004 §5＝表記→内部表現の変換に alias が使われる**＝「波動拳」のような**日本語表記**を引けるようにする価値がある）。
- **曖昧一致・編集距離・「たぶんこれ」を実装しない**（§1.2-2）。

### 4.3 人レビュー動線（FE）

- **未解決行を提示**する（**何が引けなかったか**が分かること）。**エラーで止めない**（**未解決は正常な結果**＝DES-006 §2.6 と同じ思想）。
- **解決手段**を用意する（**`LookupAll` の候補提示**／技ピッカー／直接 code 入力＝**形は §3.3-3 で提示**）。
- **既存の CSV import 突合動線（DES-005 §5.14）の拡張**として作る（**新画面を作るかは提示**）。
- **未投入キャラ・キャラ不明**＝**全行未解決として人レビューへ**（**壊れない**）。

### 4.4 出力＝**コンボ CSV**（**確定**・開発者回答 2026-07-17）

- **コンボ CSV（`combos.csv` ／ `setups.csv`）を生成し、既存の import 動線へ乗せる**（phase3-overview §M17 ④ の逐語）。**moves の CSV ではない**（§1.0）。
- **CSV 契約は不変**（DES-002 §7.6）＝**既存の import がそのまま食える形**。
- **既存資産（VAL-I01〜I10・重複判定・プレビュー・M17-05a の import 再設計）を再利用**できる＝**検証を迂回しない**。**直接登録しない**。

### 4.5 プロンプト（①）の運用と受け渡し（**確定**・開発者回答 2026-07-17）

**① アプリ外プロンプトは本体の実装対象でない**（§1.3）が、**② が使えるかどうかは ① の出力形式に依存する**ため、運用を固定しておく。

| 項目 | 確定 |
|------|------|
| **ひな形の作成** | **設計担当が作る**（`combo-intake-normalize-prompt.md`） |
| **実データでの調整** | **製造担当（Claude Code）が行う**（**本サブの成果物＝§2.1**） |
| **最終確認** | **開発者** |
| **トークン語彙** | **TOOL-002 §9.9 の 24 種に揃える**（方向 `u`/`d`/`l`/`r`/`ul`/`ur`/`dl`/`dr`・`n`・`charge_d`/`charge_l`/`charge_r`・`circle`・`plus`・`or`・`chain`・`p`/`p_l`/`p_m`/`p_h`・`k`/`k_l`/`k_m`/`k_h`・`hold`・`alt_sep`・`opt_open`/`opt_close`。**空白区切り**）。理由＝**索引キーの正規化（DES-004 §2.4.3）がそのまま効く**＝**変換層を増やさない** |
| **取り込み単位** | **1 キャラずつ**（基本運用） |
| **プロンプトへ渡す moves** | **必要なキャラ分だけ**（**全キャラ分を渡さない**＝コンテキストが膨らむ・誤キャラの技を引く事故を防ぐ） |

- **§3.3-1 の設計含意**: **「そのキャラの moves 一覧」をプロンプトへ渡す運用**であるため、**その一覧をどう用意するか**（アプリから出せると楽か／既存の `GET /api/moves?character_id=N` で足りるか／人手で用意するか）を **Plan Mode で提示**すること。**新機能を足すかは開発者判断**（**推測で足さない**）。
- **キャラの指定**は入力の受け口（§3.3-1）で**明示的に受ける**（**AI に推測させない**＝別キャラの技を引く事故を防ぐ）。

### 4.6 「プロンプトをコピー」ボタン（**本サブのスコープ**・開発者承認 2026-07-17）

**① の利用者は一般の発信者**（§1.1）。**GitHub の `docs/` を探してプロンプトをコピペさせるのは非現実的**であり、**① の摩擦が ② の利便を食い潰す**（本機能は「入力が大変」を解決するためのものなので本末転倒になる）。したがって **アプリがプロンプトを提供する**。

- **取込ヘルパー画面に「プロンプトをコピー」ボタン**を置く。押すと**次を結合してクリップボードへ**入れる:
  1. **プロンプト本文**（設計担当のひな形＝`combo-intake-normalize-prompt.md` を製造が実データで調整したもの）
  2. **選択中キャラの moves 一覧**（**そのキャラの分だけ**＝§4.5。`move_code` は含めず**技名・別名・カテゴリ**で足りるか Plan Mode で判断＝**AI に code を書かせないため、code を渡す必要が無い**可能性が高い）
  3. **カスタムプリセットのエイリアス**（**あれば**。将来 M20 で価値が増す＝§10。**無ければ省略**）
- **これで §3.3-1 の「moves 一覧をどう用意するか」が同時に解決する**（ユーザーは AI に貼るだけ）。
- **キャラの取り違えが構造的に起きない**（**選択中キャラの分しか入らない**）＝§4.5 の「1 キャラずつ」がそのまま UI になる。
- **プロンプト本文の正は、実装後はコード**（＝UI ラベルと同じ性格）。**`docs/human-notes/combo-intake-normalize-prompt.md` は本サブへの入力（ひな形）**であり、**実装後はコードが正**になる（docs 側は起源の記録として残す／archive するかは開発者判断）。
- **本体から LLM を呼ばない**（§1.2-1）＝**コピーするだけ**。ユーザーが自分の使う AI に貼る。

### 10.1 M20（プリセット）への申し送り — **カスタムプリセット＝ユーザー個人の表記辞書**

**開発者の着想（2026-07-17）**: 「プリセットはデフォルト 4 点の他、**キャラクターごとにカスタムプリセット**を用意できるようにしたい。**ユーザーがカスタムプリセットを用意していれば、さらに精度が高くプロンプトが作れそう**」。

**設計担当の評価＝有効。しかも効き方が 2 つあり、②の方が価値が大きい**:

| | 効果 |
|---|------|
| **①（プロンプト）** | AI に「**この人は しゃがみ中P を"屈中P"と書く**」という**辞書**を渡せる＝**正規化の精度が上がる** |
| **②（厳密照合）** | **カスタムプリセットは `preset_aliases` に行を持つ**（DES-003 §3.9）＝**本サブが確定した「エイリアス照合を含める」（§11-4）がそのままユーザー個人の表記を引く**＝**AI を通さずに決定論で引ける行が増える** |

**②が本命である理由**: 本サブの死守事項は「**AI にコードを確定させない**」（§1.2-1）。**カスタムプリセットが育つほど AI の出番が減り、決定論の領域が広がる**＝**アーキテクチャの方向と完全に一致する**（AI を賢くするのでなく、**AI に頼らなくて済む範囲を広げる**）。

**鶏と卵の解＝人レビューの解決を書き戻す**: カスタムプリセットを手で作るのは、まさに発信者が避けたい手作業。しかし**本サブには人レビュー動線がある**（§4.3）。**そこで解決した対応（「屈中P = しゃがみ中パンチ」）をカスタムプリセットのエイリアスへ書き戻せば、2 回目以降は ② が決定論で引ける**。**学習するのは AI ではなく決定論的な辞書**であり、**人が 1 回教えたことが以後ずっと機械的に効く**。発信者は蓄積を持っているため、**最初の 1 回で辞書がほぼ完成する**。

**M20 の設計に入る前に潰すべき論点（重要）**: **カスタムプリセットは「表示」の仕組み**（DES-004 §5＝**内部表現 → プリセット**）だが、**取込は逆方向**（**表記 → 内部表現**）＝**同じ辞書を逆引きする**ことになる。**逆引きの一意性が要件になる**（同じ別名を複数の move に付けられると逆引きが 1:N になり決定論が壊れる）。**`preset_aliases` に `UNIQUE(preset_id, alias_text)` があるか**（現行のキーは `(preset_id, move_id)`）を確認し、無ければ **M20 で「取込に使うなら `alias_text` も一意」**という制約が要る。

**本サブでは書き戻しを実装しない**（M20 の領分）。ただし **§4.6 の「プロンプトをコピー」はカスタムプリセットのエイリアスを"あれば"同梱する**形にしておく（**M20 が来たら自動で効く**）。
