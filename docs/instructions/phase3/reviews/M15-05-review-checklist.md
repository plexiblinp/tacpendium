## 1. 設計・パターンとの照合（最重要）

### 1.1 ②比較 生 ID バグ＝真因層での修正（指示書 §4.2・§3.3・最重要）
- [ ] **名称解決経路を一覧/比較/詳細で grep 全数特定**し、比較だけ生 ID になる**差**を突き止めたか（§3.3-1）。
- [ ] **真因層で修正**されているか（比較の描画層だけ塞いでいない・症状≠真因＝digest §1）。真因（実査で特定した層）が完了報告に明記されているか。
- [ ] 比較の始動技が**技名表示**になり「始動技#<id>」の生 ID が解消されたか。**一覧/詳細と同じ名称**が出るか（共有経路の整合）。
- [ ] **正しく出ている一覧/詳細側を壊していない**か（比較を正しい側へ寄せた）。
- [ ] 真因が上流（DTO/クエリ）でも、**API 契約・スキーマを変えていない**か（既存 `starterMoveCode` 等の活用に留める・§11-2）。

### 1.2 ①表示整理・縦スクロール軽減（指示書 §4.1・§3.3-4）
- [ ] **現行の左右余白/狭幅の理由を実査**したか（レスポンシブ意図 vs 特段の理由なし）。**理由がなければ横幅を活用した再配置**で縦を圧縮したか。レスポンシブ意図がある場合は**PC で広げ狭幅で縦積みに戻る**形になっているか（意図を壊していない）。
- [ ] **折りたたみ/段組みを唯一解と決め打っていない**か（横幅活用を含めて検討したか）。
- [ ] **情報過密で入力しにくくなっていない**か（横に広げた結果の操作性を担保）。過密になり得る場合は製造がサンプル HTML 等で操作性を判断したか。
- [ ] **登録画面の項目が削除されていない**（全項目温存・整理のみ・機能不変）。
- [ ] 既存の始動技自動推定・セットプレイ節・タグ・メモ等の挙動が不変か。モバイル/狭幅の到達性・操作性が改善/非悪化か（arch §10）。

### 1.3 test-id・DES 直接編集禁止（指示書 §4.3・§7.4）
- [ ] 既存 test-id 規約を grep 実値確定してから採用（digest §4）。範囲が本サブの触れる箇所に限定。
- [ ] DES-005 CHANGE 要否判定が完了報告にあり、**製造が DES を直接編集していない**か（要なら設計担当起票）。

## 9. 重大な問題の判定基準（完了承認を妨げる）
- **②を症状層で塞いでいる**（比較の描画だけ直し、真因＝名称解決経路の差を特定せず・digest §1）。真因が完了報告に無い。
- **一覧/詳細の正しい始動技表示を壊した**（比較に合わせて逆に劣化させた）。
- **②で API 契約・スキーマを変更した**（既存 `starterMoveCode` 等の活用に留めるべき・非スキーマ前提に反する）。
- **①で登録画面の項目を削除した**（整理のみが正・機能温存）。または**余白/狭幅の理由を実査せず横に広げてレスポンシブ意図を壊した**／**横に広げた結果、情報過密で入力しにくくなった**。
- Plan Mode 実査（§3.3 #1〜#5）のいずれか未確認のまま実装（推測実装）。既存ヘルパーを実査せず自作再発明（playbook §4.6）／test-id を grep 確定せず衝突（digest §4）。
- 既存 E2E が非回帰でない。製造が DES 本体を直接編集している。

## 10. 軽微な問題の判定基準（持ち越し許容）
- ①のグルーピング/折りたたみ/段組みの見た目微調整。②の技名表示の細部（生 ID が解消され一覧/詳細と整合していれば可）。
