## 1. 背景と目的

### 1.1 背景

M17（発信者の流通基盤）の command 解決 段階2。仮想コントローラの入力を自然にするため、**単方向＋ボタンで出る特殊技を決定論的に `move_code` へ解決**する（command-resolution-request §1-2）。段階1（しゃがみ/ジャンプ攻撃）は M15 実装済み、必殺技・溜め・一回転・空中特殊技は「直接指定」（M15-03 骨格）。段階2 がその中間を埋める。

索引源は command（判断3＝index-only。`moves.command` 列は復活せず、M14-03b が seed/CSV から索引器 IF を確立済み）。本サブはその IF を消費者拡張し、**索引の物理的な持ち方（専用索引テーブル）を確立**し、**段階2 の解決サービス（BE）**を実装する。

### 1.2 死守 3 契約（command-resolution-request §1.1・全サブ遵守）

1. **公式表記のみ解決**（汚い入力はサポートしない＝入力エンジン再実装をしない）。
2. **モーション解析はしない**（クリーンな入力状態→move_code の決定論ルックアップに徹する）。
3. **出口は必ずキャラ別 `move_code`**（後段の比較・エクスポート・取込と整合）。

### 1.3 目的

- **G-k 索引源の物理確立**: M14-03b の moveindex IF を土台に、command トークン→キャラ別 `move_code` の**専用索引テーブル**（例 `move_commands`）を seed マイグレで構築する。**非派生技（`is_derived=false`）のみ索引化**（別紙 command-index-resolution-design v2.1.0）。
- **段階2 解決エンジン（BE）**: 「単方向＋ボタン」のクリーン入力状態→`move_code` を決定論解決するサービス。**特殊技優先**・未定義フォールバック（通常技へ）・1:N は非派生＋id 最小タイブレーク・曖昧は未解決（直接指定へ）。
- **numpad 正規化層**: TOOL-002 §9.9 トークン語彙（レポート §1.7）→索引キーの正規化を確定し、M14-03b が「後付け位置」に残した箇所へ差し込む。
- **取込ヘルパーとの共通化**（「二度作らない」）: 索引エンジンは M14-03b remap と共通モジュール。段階2 解決も取込の表記解決も同一索引を引く。

### 1.4 このサブで作らないもの（スコープ外）

- **段階2 UI（仮想コントローラ消費者）**＝M17-03。
- **溜め（`charge_*`）・一回転（`circle`）・空中特殊技・必殺技のモーション解決**＝直接指定（非対応）。
- **物理コントローラ実モーション入力**＝M21（後送り）。
- **取込ヘルパー本体（メモ/エクセル→CSV）**＝M17-04。本サブは索引の BE 確立まで。
- **`moves.command` 列の復活**＝判断3 で否定（index-only）。
- **アップデート追従の運用手順の明文化**＝FR702・フェーズ4（本サブは派生技フラグの仕組み導入まで）。

## 4. 詳細仕様

### 4.1 G-k 索引テーブル（`move_commands`）

- 専用テーブルで command トークン→move の索引を持つ（index-only＝`moves.command` 列は復活しない）。
- 列（案・Plan Mode 確定）: `move_id`（FK moves.id）・`character_id`（検索用・冗長だが引きやすさ優先）・`token_key`（正規化済み索引キー・TEXT）。
- **非派生技のみ載せる**（`is_derived=false`）。派生技は索引に不在＝解決対象外（§1.3・§1.5-1）。
- seed: M14-03b の索引器 IF が構築するデータをマイグレで投入（M14-03b と同一エンジン＝「二度作らない」）。seed 済みキャラ分の command から構築。
- **索引は広く持つ**（§1.5-6）: **必殺技・空中技も載せる**（M17-04 取込ヘルパーが使う）。**段階2 のスコープ絞り込みは §4.3 の解決表側で行う**＝索引段階では落とさない。
- 索引非搭載（M14-03b の skip 規則を踏襲）: `is_derived=true`・command 空欄・`raw{-}`・`cond{…}` 途中挿入。**正規化層を差し込む際、この文字列マーカ方式の簡易判定の妥当性を再評価する**（正規化後にトークン単位で判定する方が堅牢な可能性）。

### 4.2 numpad 正規化層

- レポート §1.7 の 24 トークン（空白区切り）を索引キーへ正規化。段階2 が引くのは方向（`u/d/l/r/ul/ur/dl/dr/n`）＋`plus`＋ボタン（`p/k`・強度 `_l/_m/_h`）の組。
- 正規化の確定仕様（token→numpad 索引キー・SUPP-001 §9.9 が M17 で確定と handover §4 が予告した箇所＝実体は TOOL-002 §9.9 語彙）。
- M14-03b が「CSV 正準表記そのまま」で置いた索引キーに正規化層を差し込む（M14-03b の手戻りなし＝後付け位置に用意済み）。

### 4.3 段階2 解決サービス（BE）＝**畳んだ解決表を配る**（案C・§1.5-2）

- **成果物＝キャラ 1 体分の解決表**: `token_key → move_code` が**既に 1 対 1 に畳まれた**マップ。API（§4.3.1）で FE へ配る。**FE は引くだけ＝規則を持たない**。
- **表を畳む手順**（すべて BE・Go）:
  1. 索引（`move_commands`）から当該キャラの非派生技を取得。
  2. **スコープで絞る**: **`moves.is_aerial = false`**（**空中特殊技を除外**＝§1.5-4）かつ **token_key が「単一方向トークン＋`plus`＋ボタン」または「ボタンのみ」**の形（**`charge_*`/`circle`/`or`/`chain`/`hold`・複数方向トークンを含むものは対象外**＝必殺技・溜め・一回転は自動的に落ちる）。
  3. **特殊技優先**: 同一 `token_key` に特殊技（`unique`/`special`）と通常技（`normal`）が該当する場合は**特殊技を採る**（request §1-2。「前＋ボタン＝特殊技か歩き＋通常技か」の曖昧をこれで畳む）。
  4. **id 最小タイブレーク**: なお複数残る場合は `moves.id` 最小を採る。
  5. **曖昧は載せない**: 意味的に決めきれない組は**表から落とす**（＝FE は「表に無い」→ 段階1 or 直接指定へ）。死守契約「曖昧なら決定論解決しない」を**データ構造で強制**。
- **フォールバックは表に持たせない**: 「解決表に無ければ段階1 の構造引き」は**消費者（FE・M17-03）の分岐**（§1.5-3 の一様規則）。索引モジュールは候補返却のみ（M14-03b IF 規約・M17-overview §4.3）。
- 出口は必ず `move_code`（死守契約 3）。

### 4.3.1 解決表配信 API

- `GET /api/characters/{code}/command-index`（**エンドポイント名・レスポンス形は Plan Mode で確定**）。**キャラ 1 体分**（キャラ選択時に 1 回取得＝入力ごとの往復を作らない）。
- レスポンス＝`{ token_key: move_code }` 相当（畳み済み）。**未 seed キャラは空**（＝段階1 だけが動く＝壊れない）。
- **性能**: NFR001（DB 操作 100ms 以内）に収まるか Plan Mode で確認（索引の INDEX 設計）。

### 4.6 `is_derived` の backfill（投入済み 10 キャラ）

- **値の在処は手入力 CSV のみ**（M14-03b は seedgen 時フィルタに使い DB に保存していない）。
- **seedgen で backfill マイグレを生成**（**手書きしない**＝M14-03c で確立した定石）。`UPDATE moves SET is_derived = 1 WHERE character_id = (…) AND code IN (…)`。**CSV に載る code のみ UPDATE**＝**ユーザー生成行（画面18 追加・rush 版）は DEFAULT false のまま**で正しい。
- **既存マイグレ（000024〜000031）は非改変**。**生成マイグレ 1 本につき golden テスト 1 本**（M14-03c の運用）。
- ※**削除と非対称**: 削除は「残すものの列挙＋NOT IN」が要る（ユーザー生成行の消し漏れが起動不能を招く＝M14-03c）が、**UPDATE は列挙で正しい**（触らない行が既定値のまま正しく振る舞う）。
- **第二波以降**は seedgen が最初から `is_derived` を INSERT に含める＝**変換規則の改訂＋golden 更新**（第二波 seed 指示書で扱う。伝達メモの `original_move_code` 実在検証の追加と同時が経済的）。

### 4.7 `rush_variant` の `is_derived=true`（§1.5-5）

- **本体の `POST /moves/:id/rush-variant`（画面18・FR703）が生成する move も `is_derived=true` を立てる**（一貫性。索引は seed 由来のみのため段階2 への実害は無いが、UI 再利用時に効く）。
- seed 側（入力ツール生成分）は CSV の値をそのまま信頼（本体は導出しない＝CHANGE-065 と同型）。

### 4.4 取込ヘルパーとの共通化

- 索引モジュール（`move_commands` を引く）は、段階2 解決サービスと M17-04 取込ヘルパー（`236LP`→`hadoken_light` 相当）の**両方が同一 IF で消費**する。本サブで IF を本体ランタイム消費可能にし、M17-04 が乗る土台を作る。
- ただし取込ヘルパー本体（メモ/エクセル→CSV）は M17-04。本サブは索引の BE と段階2 消費者まで。

## 11. 開発者への確認事項

1. **索引テーブル vs moves 列**: 〔何を〕`is_derived` を moves 本体の bool 列にするか索引テーブルのフィルタにするか。〔なぜ〕派生技の概念が UI（技ピッカーの区別）でも使えるなら moves 本体列が資産価値高。索引専用なら索引テーブル内で完結。〔暫定案〕moves 本体の bool 列（`is_aerial` 型・UI 再利用可）＝索引は join で非派生を絞る。
2. **段階2 解決の BE/FE 分担**: 〔何を〕決定論解決を BE API にするか FE 内完結にするか。〔なぜ〕索引を BE に持つなら API が自然だが、決定論なら FE でも可。〔暫定案〕BE に索引・解決 API を置く（索引の SSOT を BE に）。M17-03 は API 消費。
3. **段階2 と段階1 の境界**: 〔何を〕しゃがみ/ジャンプ（段階1・move_code 構造引き）と単方向特殊技（段階2・command 索引）の解決経路を分けたまま統合 UI で見せるか。〔暫定案〕BE は 2 経路を別サービスで持ち、FE（M17-03）が統合。
