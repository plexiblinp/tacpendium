## 1. ツリー構造の確定（開発者指示 2026-07-22・**v0.1.0 から変更**）

```
[親] 相手技 M（ガード/ジャストパリィ後の有利フレームを表示）
  └ [子] 刺さる始動技 S（frame 条件: S.startup ≤ 有利フレーム）
        └ [孫] S から繋がるコンボ C（既存コンボ・materialize 生成物を含む）
```

**ワークフロー（開発者の意図）**：
1. **フレームベース**で「反撃できそうな始動技」を機械的に列挙する（＝子まで）。
2. ユーザーが**実践で距離等の他要素を検証**し、始動技を**採用／不採用（届かない）**に振り分ける。
3. 採用した始動技の下に**孫＝コンボ**を展開し、使えるものをマイリスト（M18-03）へ送る。

**設計上の含意**：
- 子（始動技）は **`moves` 由来**であり、コンボの有無に依存しない（コンボ未登録の始動技も候補として出る＝先に反撃手段を見つけ、後からコンボを作る流れが成立する）。
- 孫（コンボ）は `combos.starter_move_id = S` で引く。
- **フレーム判定は子まで、人間の判断は子で、コンボ選択は孫**、という 3 段の役割分担が画面の骨格になる。

## 2. 【要承認】現行スキーマで表現できない状態がある（新スキーマの承認ゲート候補）

3 階層化により、**子（始動技）レベルの永続状態**が必要になりましたが、M18-01 で作った 3 表はいずれも粒度が合いません。

| 保存したい状態 | 必要な粒度 | 現行スキーマ | 可否 |
|---|---|---|---|
| 孫コンボを採用（keep） | (combo, 相手技) | `combo_punishes` | **可** |
| 孫コンボを隠す（curation） | (combo, 相手技) | `combo_punish_curations` | **可** |
| 相手技そのものが反撃不能 | (自キャラ, 相手技) | `combo_punish_prunings` | **可** |
| **始動技 S は距離的に届かない（不採用）** | **(自キャラ, 相手技, 始動技)** | — | **不可** |
| **始動技 S を採用（検証済み・コンボ選択はこれから）** | **(自キャラ, 相手技, 始動技)** | — | **不可** |

**なぜ問題か**：ワークフローの中核である「実践で検証した結果」が、まさに検証を行う粒度（始動技）で保存できません。現行の `combo_punish_prunings` は相手技ごと一括の除外なので、「この相手技に対し 5MK は届かないが 2LP は届く」を表現できず、ユーザーは**毎回同じ検証をやり直す**ことになります。これは M18-01 で是正した G-d の curation 粒度問題（マッチアップ単位では個別コンボの隠しを表現できない）と**同じ型の不足**です。

**対応案**：

- **案 A（推奨）＝新表 1 本**：仮称 `combo_punish_starters`（`self_character_id`・`opponent_move_id`・`starter_move_id`・`verdict`〔adopted／unreachable〕・`note`・UNIQUE 3 列）。採用と不採用を 1 表の verdict で持ち、keep/hide の対称構造（`combo_punishes` ↔ `combo_punish_curations`）とも整合。ツリーの子レベルがそのまま 1 表に対応し、finder のクエリも素直。
- **案 B**：`combo_punish_prunings` に `starter_move_id`（nullable＝NULL は相手技ごと一括）を追加し、採用側は別途持つ。既存表の意味が二重化し、UNIQUE と NULL 比較の扱いが複雑になるため非推奨。
- **案 C**：子レベルを永続化しない（毎回フレーム計算のみ・検証結果は残さない）。実装は最小だが、ワークフロー 2 の成果が消えるため意図に反します。

> **手続き**：委任 v1.2.0 §6 は「M18-02/03 で新テーブル/新列が必要と判明したら、**着手前に中央経由で開発者の個別承認**を得る（勝手に足さない）」と定めています。本件はこれに該当するため、**承認ゲート・CHANGE 番号・マイグレ連番はすべて中央へ請求**します（私は採番しません）。承認まで M18-02 の実装指示書は起こしません。

## 3. 走査対象の除外規則（**damage=0 を追加**）

| # | 条件 | 扱い | 根拠 |
|---|------|------|------|
| a | **相手技の `damage = 0`** | **走査対象外・画面に出さない** | 開発者指示 2026-07-22＝ダメージのないキャラ固有 move はガード後の反撃対象にならない |
| b | `is_projectile = 1` | 自動走査から除外し**手動確認レーン**に表示 | 距離依存（CHANGE-081） |
| c | `on_block IS NULL`（ガードタブ） | 同上 | 有利フレーム算出不能 |
| d | `recovery IS NULL`（ジャストパリィタブ） | 同上 | 同上 |
| e | `recovery = 0` かつ `is_projectile = 0`（ジャストパリィタブ） | 同上（**開発者承認済 2026-07-22**） | 有効値 0 だと結果が静かに空になり「刺さらない」と「データがない」が区別できない |
| f | `combo_punish_prunings` 登録済 | 候補から除外（解除で復帰） | 物理的に届かない |

**a と e の関係（重要）**：a を先に適用すると、e の対象 11 件のうち移動・構え系（`sprint`／`quick_dash`／`emergency_stop`／`genius_at_play`／`denjin_charge`／`condor_wind_light` 等）の多くは **damage=0 で先に落ちる**見込みです。結果として e の手動確認レーンに残るのは実質的にダメージを持つ技（`mai.hoshi_kujaku` 等）に絞られ、レーンのノイズが減ります。**実際の重なりは実装時に dev DB で再計測**します（E-16/E-18・L-4＝addendum は M18-01 是正前のスナップショット）。

**自技（子＝始動技）側にも同じ考え方を適用**：`damage=0` の自技（ダッシュ・構え等）は確定反撃の始動になり得ないため、子の候補から除外します。

# 追補（v0.3.0・2026-07-22 開発者フィードバック 2 件）

## 7. 採用確定反撃画面（M18-03）のツリーは 2 階層（開発者指示）

探す画面（M18-02）は 3 階層（相手技→始動技→コンボ）だが、**採用確定反撃画面（M18-03）は始動技を省いた 2 階層**とする。

```
探す（M18-02）      : 相手技 → 始動技 → コンボ     （3 階層・検証の作業台）
採用済み（M18-03）  : 相手技 → コンボ              （2 階層・結果の一覧）
```

- 理由（開発者意図）：採用済み画面は「相手の技に対して実際に使うコンボ」を引く場所で、始動技は既に検証・確定済みのため中間ノードとして出す必要がない。
- **データ的には自然**：採用コンボは `combo_punishes`（combo, 相手技）で保持済み。始動技は `combo.starter_move_id` から**表示に含めることは可能**だが、階層のノードにはしない（コンボ行の一属性として見せる程度）。
- **§2 の新表 `combo_punish_starters` は探す画面専用**（検証の作業状態）。採用済み画面は `combo_punishes` だけで引ける。→ M18-03 は新スキーマ不要の見込みを補強。

## 8. 前ダッシュを確定反撃候補に含める（開発者指示）＋**ダッシュのフレーム欠損（要中央・実コード確認）**

### 8.1 要件
相手技をガード/ジャストパリィ後、**前ダッシュ（`dash_forward`）してもなお 4F 以上の猶予が残る**なら、「ダッシュで近づいて打撃で反撃」する候補として出す。

判定式（案）：
```
残り猶予 = 有利フレーム − dash_forward の全体フレーム
残り猶予 ≥ 4  かつ  ダッシュ後の始動技 S について S.startup ≤ 残り猶予
→ 候補（ツリーの子に「↳ 前ダッシュ経由」ノードとして S を出す）
```
- 「4F 以上」は開発者指定の下限（最速技の始動が概ね 4F 以上のため実用上の足切り）。実装ではこの閾値を定数で持つ（マジックナンバーにせず命名）。

### 8.2 【問題】ダッシュの全体フレームが「キャラごとに保持されていない」疑い＝開発者の懸念は実データで裏付け

実査で判明した事実：

| 事実 | 出所 | 含意 |
|------|------|------|
| `dash_forward` は `category=system` の独立 move として全キャラに実在 | DES-004 §2.1・RESEARCH A-1（`000025_seed_movement_system_moves_all`） | move としては引ける |
| ただし `000025` は**全キャラ一括投入の「移動 system move」**で、フレーム値はキャラ別に採取された形跡がない（c_viper/dhalsim は移動 9 件のみで攻撃 0 件） | RESEARCH A-1 | **全キャラ同一値 or 空の可能性が高い** |
| `moves` の frame 列は `startup`/`active`/`total`/`recovery`/`on_block`/`on_hit`（すべて `*int`＝**NULL 可**） | code-facts（Move struct） | ダッシュ全体フレーム専用の列はない。転用するなら `total`（＝発生+持続-1+硬直）だが、ダッシュに発生/持続/硬直の概念を当てるのは無理があり、実際に値が入っている保証がない |
| `total` は「算出不能なら NULL」 | DES-003 §3.5 | **ダッシュの total は NULL の可能性が高い**（発生・硬直が空欄の 11 件が実在との記述もあり） |

**結論**：SF6 のダッシュ全体フレームは**キャラごとに異なる実ゲーム値**（例：おおむね 15〜21F 前後でキャラ差がある）だが、現行スキーマの `dash_forward` にその値が**キャラ別で正しく入っている確証がない**。開発者の「対応されていない気がする」は妥当な懸念です。

**これは実 DB を見ないと確定できません**（中央も未把握・実コード/seed 確認が要る、というのは正しい）。私の手元の資料（code-facts・RESEARCH・DES）では「列は存在するが値の中身は不明」までしか言えません。

### 8.2-R 調査結果（2026-07-23・M18-02-RESEARCH-01-report）＝**ケース B 確定**

- **対象 4 code × 12 キャラ＝48 行すべてでフレーム列が NULL**（便宜値ですらなく値が不在）。移動 system move 9 種すべて同傾向。code 間・キャラ間の非対称なし。
- 投入元は `000025`（全キャラ・`character_id, code, category` の 3 列のみ）＋ `000004`（ryu）。**フレーム値を入れるマイグレは 1 本も存在しない**。
- CSV に対象 4 code の行は **0 件**（seedgen が移動 9 種を drop する設計のため、CSV は投入経路にならない）。
- `raw_data` にも全体フレーム相当の記述なし（48 行すべて NULL）。
- 空中技は `is_aerial=1` が **70 件**（母数 944）で、**全 70 件が `startup` を保持**。ジャンプ move 自体は `is_aerial=0`。

**確定した設計判断（詳細は `M18-02-approval-request.md`）**：
1. **新列を作らない＝`total` を使う**。根拠＝`character_data/rashid.csv` の `buffed_dash_forward` が `startup=1/active=20/recovery=0/total=20` を持ち、DES-003 §3.5 の算出式（`1+20-1+0=20`）と整合。**ダッシュ系を既存フレーム列で表現する前例が実データに存在**する（教訓 L-1＝先例の実機序を引いてから「同型」と言う、の適用）。移動 system move は `total` を「全体フレーム」として直接保持する旨を DES-003 に注記（DES 反映要点）。
2. **投入は backfill マイグレ・seedgen は非改変**。seedgen の drop 解除は **M18-01 の seedgen 問題と完全に同型**（`000026`/`000030` の golden byte-identical 比較が必ず壊れ、解消には既存マイグレ改変が要る）ため採用不可（教訓 L-2 の適用）。`is_derived`／`is_projectile` と同じ backfill 経路にする。
3. **値は開発者から提供を受ける**（12 キャラ分）。DB/CSV/マイグレのどこにも一次源がないため。画面 18（moves 編集グリッド）で後から修正可能。
4. **ジャンプ移動 move（`jump_forward` 等）は判定に使わない**（全 NULL のままでよい）。ただし**ジャンプ攻撃経由の候補は M18-02 に含める**（開発者指示 2026-07-23・下記 §8.4）。当初の見送り判断は`離陸〜攻撃発生`・`全体`・`着地硬直` の 3 値が要り `total` 1 値では表現できない（列追加が必要）／ジャンプ move と空中技 move の連結設計も別途要る／跳び込みの当否はジャンプ軌道と距離に強く依存し、距離は本ツールが原理的にモデル化しない要素（pruning/curation で人間が判断する設計）。判定思想を「全体ベース・偽陽性許容」に変えれば既存データで実装可能と判明したため撤回した。

### 8.4 ジャンプ攻撃経由の候補（開発者指示 2026-07-23）

```
候補 ⟺ 有利フレーム ≥ （ジャンプ攻撃 move の total − JUMP_SLACK）   [JUMP_SLACK = 4・定数]
       かつ is_aerial = 1  かつ 強攻撃（code 規約で絞る）  かつ damage > 0
```
- **判定基準が地上/ダッシュ（startup ベース）と異なる**ため、**別レーン／別バッジ**で提示する（silent に混ぜない）。
- **追加データ不要**：使うのは空中技自身の `total` のみ。ジャンプ移動 move の欠損は影響しない。
- **既存モデルと整合**：DES-004 §2.3(c)／SUPP-001 §3.3.2 ＝「ジャンプ→攻撃」は空中技＋`{forward_jump}` フラグで表現し純移動 move はステップに含めない。よって**ツリーの子＝空中技 move**、孫は `starter_move_id = 当該空中技` で引ける。**新表 `combo_punish_starters` がそのまま使える**。
- **要実査（Plan Mode）**：空中通常技の実 code 接頭辞（DES-004 §2.1 正典表は `jumping_`・同節本文は `jump_` で**表記ゆれ**。`jump_` は移動 move と衝突するため誤ると巻き込み/取りこぼし）／強度表記／`total` 充足率。抽出は `is_aerial=1` を主条件にし、code 規約は補助にする（二重の担保）。

### 8.3 対応（2 段階）※調査完了により (1) は実施済み

**(1) 事実確認（read-only・先行）**：dev DB で `dash_forward` 各キャラの `startup`/`active`/`total`/`recovery` を実測し、(i) キャラ別に異なる値が入っているか、(ii) 全キャラ同一 or NULL か、を確定する。→ **`M18-02-RESEARCH`（仮）として read-only 調査を先行**させることを提案（M18-RESEARCH-01 と同じ枠組み・Sonnet 可）。

**(2) 判定の分岐（調査結果次第）**：
- **ケース A：ダッシュ全体フレームがキャラ別に正しく入っている** → 8.1 の判定式をそのまま実装。使う列（`total` か新列か）は調査で確定。
- **ケース B：入っていない or 全キャラ同一の便宜値** → **前ダッシュ経由の判定に必要なデータが無い**ため、(b-1) ダッシュ全体フレームを保持する**新列 `moves.dash_full_frames`（仮）or 専用の扱い**を追加する承認ゲート、または (b-2) 当面は前ダッシュ経由を「データ待ち」として**手動確認レーンに出すに留める**、のいずれか。**新列追加は §2 と同じ承認ゲート**（委任 §6・中央へ請求）。

> 私の推奨：まず (1) の read-only 調査を回す。ケース B だった場合、ダッシュ全体フレームは「1 キャラ 1 値」なので `moves` 行に持たせるのが素直か、キャラ属性として別に持つのが素直かは調査後に設計判断。**憶測で新列を決め打ちしない**（推測で埋めない原則）。

# 追補（v0.4.0・2026-07-22 追加要件＝新規登録への遷移）

## 10. 孫コンボ末尾に「新規登録へ」リンク（開発者指示）

**要件**：確定反撃サーチのツリーで、孫（コンボ）の**末尾に新規登録への遷移リンク**を置く。フレーム上は候補技が刺さると分かったが (a) その始動技のコンボが未登録、(b) その場で新しいコンボを思いついた、というケースに対応する。

```
[親] 相手技 M（有利 +9F）
  └ [子] 始動技 S（5MP・startup 5F）      ← 採用/届かない を記録（§2 新表）
        ├ [孫] コンボ C1 … 
        ├ [孫] コンボ C2 …
        └ ＋ このコンボを新規登録する      ← 本要件（孫リストの末尾・常時表示）
```

**表示条件**：孫が 0 件のときも表示する（未登録ケースがまさに主目的のため）。子が「届かない」と記録済みの場合は、その子の配下ごと畳まれるため自然に出ない。

### 10.1 遷移仕様（実査済みの既存パターンに乗る）

| 項目 | 実査した既存事実 | 本要件での使い方 |
|---|---|---|
| route | **`/combos/new` → `ComboEditorPage`**（code-facts） | そのまま遷移先に使う（新 route を作らない） |
| コンポーネント | `ComboEditor`（`mode: "new" \| "edit" \| "copy"`・`initialCharacterId?: number`） | `mode="new"` ＋ 自キャラを渡す |
| キャラ文脈追従 | **CHANGE-039 で確立**＝「キャラ文脈のある遷移（一覧で選択中キャラからの新規登録）は当該文脈キャラを既定選択」（DES-005 §4.3） | **確定反撃サーチも同じ文脈追従の対象に加える**（自キャラを既定選択）。新しい流儀を作らない |
| 空状態 CTA の先例 | §5.4 の空状態に新規登録 CTA リンク（文脈キャラ付き href・CHANGE-059） | 「孫 0 件でもリンクを出す」の先例として踏襲 |

### 10.2 プリフィルの範囲（**要確認・§11-10**）

自キャラは CHANGE-039 の文脈追従で確定として、**始動技 S までプリフィルするか**が論点。

- **案 P1（推奨・最小）＝キャラのみ文脈追従**。始動技は `ComboEditor` の既存仕様どおり**レシピ 1 ステップ目から自動推定**（DES-003＝`starter_move_id` は常にレシピ 1 ステップ目と一致／DES-005 §5.7＝始動技は自動推定・読み取り専用。CHANGE-046 #4）。ユーザーは登録画面でレシピの 1 手目に S を入れる。
  - 利点：**既存契約に一切触れない**。`starter_move_id` を外から与える口を新設すると「レシピと始動技が食い違う」状態を作りかねず、VAL-C03 の前提（1 ステップ目と一致）と衝突するリスクがある。
- **案 P2 ＝レシピ 1 ステップ目に S を積んだ状態で開く**（router state で `initialSteps` 相当を渡す）。始動技は結果として自動推定で S になるため契約とは矛盾しない。
  - 利点：候補技からの導線として自然（1 手目を入れ直す手間がない）。
  - コスト：`ComboEditor` に初期ステップを受ける口が必要（現行 Props は `initial?: ComboDetail`／`initialCharacterId?` のみ）。**M18-02 で FE の新 Props を足す**ことになる（スキーマ変更ではないので承認ゲートには当たらないが、既存コンポーネントの契約変更）。

> 推奨は **P1 で確定 → 使ってみて不足なら P2 を後追い**。理由は、P2 が `ComboEditor`（コンボ登録の中心コンポーネント）の契約に手を入れるため、確定反撃サーチという新機能の都合で既存の中核を変えるのは順序として重いからです。ただし「その場で思いついたコンボを登録する」という要件の主眼が**手数の削減**なら P2 の価値は高いので、開発者判断を仰ぎます。

### 10.3 戻り動線（**要確認・§11-11**）
登録後に確定反撃サーチへ戻るか（戻れば、登録したコンボが孫に現れ、そのまま採用へ進める）。
- **暫定案**：**戻す**（router state に戻り先を持たせる）。E-20「上から下へ 1 本の動線」に沿い、探す→登録→採用が 1 本で繋がる。ただし実装コストは上がるため、まずは**通常の新規登録（登録後は一覧へ）で足りるか**を確認したい。

## 11. 開発者への確認事項（v0.4.0 追加分）

10. **【確定・2026-07-22】プリフィル範囲＝案 P1**：キャラのみ文脈追従（CHANGE-039 の既存流儀に乗る）。始動技は `ComboEditor` の既存仕様どおり**レシピ 1 手目から自動推定**＝`starter_move_id` の契約（VAL-C03・常にレシピ 1 ステップ目と一致）に一切触れない。`ComboEditor` の Props 契約変更なし。→ クローズ。

11. **【確定・2026-07-22】登録後は確定反撃サーチへ戻す**：router state に戻り先（自キャラ・相手キャラ・タブ・展開中の相手技/始動技）を持たせ、登録完了後に**元の位置へ復帰**する。登録したコンボが孫に現れ、そのまま採用へ進める＝**E-20「上から下へ 1 本の動線」**（探す→登録→採用）が成立。
    - **実装メモ（指示書に落とす）**：(a) 戻り先 state が無い場合（直接 `/combos/new` を開いた等）は**従来どおり一覧へ**＝フォールバックを必ず持つ。(b) 復帰時に走査結果を再取得し、新規コンボが孫に反映されること（キャッシュ invalidate）。(c) キャンセル時も同じ戻り先へ。→ クローズ。
