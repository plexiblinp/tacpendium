## 2. 指示書担当の検証（中央判断不要・記録）

**§1-1 の追加除外規則は妥当**と判断しました。移動 system move を相手技として見ると `damage=0`（規則 a）または `damage IS NULL`（規則 b＝手動確認レーンに露出）に該当し、レビュー低-3「移動 move が手動確認レーンにノイズとして出る」の原因でした。§1-1 はこれを**規則 a の手前で刈る**もので、「そもそもガード後の反撃対象になり得ない技は手動確認する意味もない」ため、設計思想（除外は消さず手動確認レーンに出す）の**正当な例外**です。実画面確認に基づく開発者判断とも整合します。

**1 点だけ注記を残したい**：`is_aerial=1` の相手技を**完全除外**する含意として、「ジャストパリィ後に相手の空中技を確定反撃する」場面は扱えなくなります。空中技の着地硬直等は本 DB に未整備で、対空は別系統の判断のため**現状は除外が妥当**ですが、将来この用途が要れば要再訪です（DES に注記して残すことを推奨・§1 の #3 に含める）。

**E-21 の good practice が機能した（記録）**：指示書 §3.3-2 で「空中技の実 code 接頭辞は DES-004 の記述ではなく実データで確定せよ」と指示していた点が的中しました。完了報告 §3 によると、`is_aerial=1` の 70 件のうち **9 件は `jumping_` 接頭辞を持たない**（`elbow_drop`/`flying_body_press` 等の unique 系＋`neutral_jumping_heavy_kick`）。接頭辞のみ／`is_aerial` のみでは取りこぼし・巻き込みが起きるため、製造は **`is_aerial=1`（主）AND `HasPrefix("jumping_heavy_")`（補助）の二重担保**を採用しました。文書（errata 済）と実データの一致を実装時に検証させたことが、silent なフィルタ事故を防ぎました。

## 3. 設計判断が要る残課題（開発者・中央へ）

**3-1【要起票・優先度高】pruning の解除・再表示 UI が未スコープ**：解除 API（`DELETE /api/combo-punish-prunings`）は実装済みですが、**FE の解除 UI と「隠した相手技」一覧がどのマイルストーンにも設計されていません**。現状、隠した相手技は画面から消え、**戻す導線が無い**（誤操作で隠すと DB を触らない限り復元不能）。**片道操作に逆操作の UI が無いのは実用上のリスク**なので、優先して起票を推奨します。**私の暫定案**：「隠した相手技」一覧＋解除を M18-03（採用確定反撃画面＝使う）に相乗りさせる（curation の解除 UI と設計が近く、pruning/curation を同じ「隠したもの管理」として1箇所に集約できる）。

**3-2【設計課題】自動判定できない相手技に紐づく既登録確定反撃の表示導線が無い**：「自動判定できない相手技」には始動技→コンボのツリーが出ないため、その相手技に既登録の確定反撃（`combo_punishes`）があっても本画面で見返せません。**暫定案**：当該相手技の配下に「登録済みの確定反撃」を（フレーム判定を経ずに）直接出す。M18-03 の表示設計とあわせて詰めます。

**3-3【将来対応】レーン別採否（§1-2）**：`combo_punish_starters` に `lane` 列を追加し UNIQUE を `(self, opp, starter, lane)` へ拡張するスキーマ変更が要ります。**今回は見送り確定**。**暫定案**：verdict の分布（`unreachable` 件数）を運用で見て、「その場では不採用だが前方ステップなら採用」の需要が実データで確認できてから起票（早すぎる一般化を避ける）。需要が出れば承認ゲート＋CHANGE。

**3-4【環境制約・繰越】E2E**：pin 不一致（browser 1194／expected 1223）で正規 `make e2e` 未実施。`executablePath` 一時上書きで 2 spec green を実測（設定は revert 済）。spec は決定論・自己完結。**M18-01 と同じ扱い**＝開発者環境（pin 一致）での `make e2e` 再実行を残ゲートとする（M18-01 は開発者が実行し green 確認済の前例あり）。

**3-5【要確認・設計思想の一貫性】`startup IS NULL` の自技が地上/ダッシュ経由レーンから静かに脱落**：`service.go` の `Startup != nil` ガードにより、始動技側で startup が NULL の自技はレーンから**静かに消えます**。レビューは「`startup ≤ 有利` を NULL は満たせない以上妥当」として据え置きですが、**これは相手技側で徹底した「silent に消さない（データ不足は手動確認レーンに出す）」思想と非対称**です。**なぜ確認したいか**：自技に「フレーム未整備だが本当は使える始動技」があると、それが黙って消えます。**暫定案**：現状据え置き（自技の startup 欠損は相手技ほど頻度が高くない見込み）。ただし件数を実測し、多ければ自技側にも「データ不足」表示を検討。Plan Mode で `is_aerial=0 かつ damage>0 かつ startup IS NULL` の自技件数を数えていれば、その値で判断します（完了報告に無ければ M18-03 着手時に実測）。

---

**3-6【要確認・エッジケース】`neutral_jumping_heavy_kick` がジャンプ経由レーンから除外される**：ジャンプ経由の抽出条件は `is_aerial=1 AND HasPrefix(code, "jumping_heavy_")` の AND です。完了報告 §3 が挙げる非接頭辞 9 件のうち、`neutral_jumping_heavy_kick`（category=normal・強キック・is_aerial=1）は**接頭辞 `neutral_jumping_` が `jumping_heavy_` に一致せず、ジャンプ経由レーンから落ちます**。**なぜ確認したいか**：これは正当な強空中通常技で、silent に消える（相手技側で徹底した「消さない」思想との非対称）。**指示書担当の見立て**：ジャンプ経由レーンの判定は `jump_forward.total`（前方跳び）基準なので、**前進しない「垂直ジャンプ専用の強K」を前方跳びレーンに出さないのは妥当**と考えます（除外は正しい可能性が高い）。ただし SF6 の実挙動として「この move が前方跳びからも出せるか」は私が断定すべきでないため、**開発者に可否を確認**したいです。**暫定案**：現状の除外を維持（他 8 件の unique 系空中技も同様に除外で妥当）。もし前方跳びからも当てられる強空中通常技があるなら、抽出条件を「`jumping_heavy_` または `*_jumping_heavy_`」等へ緩める（実データで該当 code を洗い出してから）。
