## 1. 背景と目的

### 1.1 背景

M18-02 で「探す」画面、M18-03a で「使う」画面ができ、**採用済みの確定反撃を記録・閲覧できる**ようになった。しかし M18 の中核である **materialize（パニッシュカウンター版を別コンボとして生成する）が未実装**であり、動線は「探す → 採用 → 使う」で止まっている。

確定反撃は相手の硬直中に当てるため**本来パニッシュカウンター判定**になる。ところが現状は、ノーマルヒットで記録したコンボをそのまま「確定反撃に採用」できてしまい、**03a が新設した「区分を判定できない反撃」セクションに溜まる**。このバケツは**ゴミ箱ではなく materialize の入力キュー**であり、それを処理する機能が本サブである。

あわせて **03a で発見された最も重い残課題**を本サブで解消する。識別キー変更を伴う編集（PUT）は旧コンボを `deleted_at` で論理削除して新コンボを INSERT するが、**`combo_punishes`／`combo_punish_curations` を新コンボへ引き継ぐコードが存在しない**（`setups` は `SetupCarryOptions` で引き継がれるが punish は対象外）。したがって **ユーザーがコンボを編集しただけで、その採用がマイリスト・隠したもの管理・探す画面の既登録表示のすべてから同時に消える**。ゴミ箱経由より頻度の高い経路での silent-drop であり、M18 の思想の中核に反する。**開発者裁定（確認事項 11・2026-07-26）で本サブに含めることが確定した。**

### 1.2 目的（本サブ完了時の状態）

- **materialize が生成規則どおり動作する**（ダメージ・`hit_type`・出自・コピー範囲・FR301 重複防止）。
- **「区分を判定できない反撃」セクションと探す画面の孫ツリーから変換できる**（endpoint だけ作って到達できない状態を作らない）。
- **生成物の出自が記録され**（`combos.materialized_from_combo_id`）、マイリストに**生成元バッジ**が出る。
- **コンボを編集しても確定反撃の採用が消えない**（`combo_punishes`／`combo_punish_curations` が新コンボへ引き継がれる）。
- **生成物が出力正典どおり export される**（DES-005 §5.13＝A4 固定・縮小フィット下限 70%・メディアは link のみ・セットプレイは名称のみ）。**開発者の実出力目視で確認する（E-17）**。
- 既存のコンボ機能・探す画面・マイリストが**回帰していない**。

## 4. 詳細仕様

### 4.1 materialize の対象判定

| 生成元の `hit_type` | 扱い |
|---|---|
| `normal` | **対象**。始動技ダメージ × 0.2 を加算し `punish_counter` で生成 |
| `counter` | **対象**。**ダメージ不変**で `punish_counter` へ（カウンターもパニッシュカウンターも補正は 1.2 倍で同値＝既に加算済み。**二重計上しない**） |
| `punish_counter` | **対象外**。**UI にボタンを出さない**。代わりに既存の「確定反撃に採用」だけを出す |
| `just_parry_punish_counter` | **対象外**。ジャストパリィ始動は**手入力が正典** |
| **NULL** | **対象**。`normal` と同じ扱い（区分未設定＝ノーマルヒットとみなす）。**取りこぼさないこと** |

**BE でも対象外を弾く。** FE がボタンを出さないだけでは API 直叩きで二重計上が起こる。endpoint 側で生成元の `hit_type` を検査し、`punish_counter` 系なら **400 ＋ 理由コード**を返す（M19-01 の `knockdown_advantage_required` と同じ流儀＝UI が理由を表示できる専用コード）。

### 4.2 【スコープ境界・厳守】materialize が扱わないもの

開発者裁定（確認事項 10・2026-07-26）：

> パニッシュカウンターでコンボ自体が全然違うものになることはあるが、**それは別コンボとして登録すればいい**し、その導線も充分用意されている（**孫ツリーにいるから**）。

| ケース | 扱い |
|---|---|
| PC 始動でも**同じレシピが通る** | **materialize の対象**。レシピを複製し、ダメージと `hit_type` だけを変える |
| PC 始動だと**レシピ自体が変わる** | **materialize の対象外**。探す画面の孫ツリーにある**既存の「新規登録」導線から別コンボとして手入力**する |

**したがって materialize に「レシピを編集してから生成する」機能を作らない。** 生成物は基底のレシピをそのまま複製したものに限る。編集は生成後に通常のコンボ編集で行う（独立フォーク）。**親切心で編集機能を足さないこと。**

### 4.3 生成内容（ダメージ・コピー範囲）

**ダメージ式**：

```
generated.damage = base.damage + round( starterMove.damage × 0.2 )
```

**丸めは §3.3-2 の実測で決める**（0 件なら整数演算・1 件以上なら実装を止めて開発者実測を待つ）。

**縁の扱い（裁定2＝許して注記）**：**生成を止めない**。M18 の「silent に消さない」思想の適用であり、加算できなかった事実を**画面で伝える**（黙って 0 加算にしない）。

| 条件 | 挙動 | UI 表示 |
|---|---|---|
| `base.damage` が NULL | 生成する。`damage` は **NULL のまま** | 「基底コンボにダメージが未入力のため、加算していません」 |
| `base.starter_move_id` が NULL | 生成する。`damage` は **基底の値のまま** | 「始動技が未設定のため、加算していません」 |
| 始動技の `moves.damage` が NULL | 同上 | 同上 |

**コピー範囲（裁定9・10）**：

| 項目 | 扱い |
|---|---|
| レシピ（`combo_steps`） | **コピー**（必須。§4.5 の `recipe_hash` 一致にも要る） |
| 状況系（`position`／`opponent_stance`／`opponent_size`／`situation`） | **コピー** |
| ゲージ系（始動残量 4 列・消費 2 列）／`drive_damage` | **コピー** |
| **`knockdown_advantage`** | **コピー**。**注記は不要**（裁定10＝同じコンボならパニッシュカウンターの有無で KA は変わらない） |
| 起き攻め（`combo_oki_options`） | **コピー** |
| `memo`／メディア 3 列（`link`／`video_path`／`image_path`） | **コピー** |
| タグ（`combo_tags`） | **コピー** |
| **セットプレイ紐づけ（`combo_setups`）** | **コピーしない**（別コンボへの紐づけは意味が変わる） |
| `is_draft` | **コピー**（裁定3＝基底の状態を引き継ぐ） |
| `hit_type` | **`punish_counter` を設定**（`model.HitTypePunishCounter` を参照。**リテラルを増やさない**） |
| `materialized_from_combo_id` | **基底の id を設定** |
| `version`／`created_at`／`updated_at`／`deleted_at` | **コピーしない**（新規行の初期値） |

> **`combo_steps`／`combo_oki_options`／`combo_tags` は別テーブルであり、`combos` の INSERT だけでは複製されない。** §3.3-3 で引いた PUT 経路の機序を使い、**トランザクション内で子テーブルまで複製する**こと。

### 4.4 API とトランザクション境界

**`POST /api/combos/{id}/materialize`**（`{id}` ＝ 基底コンボ）。

| 項目 | 内容 |
|---|---|
| リクエスト | `opponentMoveId`（**必須**。裁定7 により `combo_punishes` を同時に作る）／`note`（任意・`combo_punishes.note` へ） |
| 処理順 | 基底読み込み → **対象判定（§4.1）** → **FR301 チェック（§4.5）** → ダメージ計算（§4.3）→ `combos` INSERT → **子テーブル複製** → `combo_punishes` INSERT → **【v1.0.2】基底コンボの採用を解除**（下記） |
| トランザクション | **上記すべてを 1 トランザクション**（裁定7） |
| レスポンス（生成時） | **200**。`{ comboId, alreadyExisted:false, damageAdded, damageSkipReason? }` |
| レスポンス（既存あり時） | **生成せず**、**200** で既存コンボの id を返す（`alreadyExisted:true`）。**エラーにしない**（§4.5-3） |
| レスポンス（対象外 `hit_type`） | **400 ＋ 理由コード `hit_type_not_materializable`**（§4.1） |
| 加算スキップ理由コード | `base_damage_null`／`starter_move_not_set`／`starter_move_damage_null`（§4.3 の縁 3 パターンに 1:1）。**FE は内部値と表示ラベルを分離して文言化**（L-7） |

**【v1.0.2・重要】基底コンボの採用を解除する（開発者裁定 2026-07-27）**

> **v1.0.1 の穴**：§5.3-A（E2E）と §1.2 は「変換後に基底が第3セクションから消える」「このバケツは materialize の**入力キュー**であり、それを処理する機能が本サブ」と書いていたが、**本節の処理順にその操作が無かった**。「当然そうなる」と感じたものこそ処理順に書き下す必要があった（設計者自身に対する L-1）。

- **`combo_punishes(基底コンボ, 相手技)` と同キーの curation を削除する。** これにより基底が第3セクションから外れる。
- **基底コンボ自体は削除しない**（独立フォークとして残る）。消えるのは「その相手技への採用」だけ。
- **FR301 で既存一致だった場合も解除する**（生成はしないが、基底はキューから出る）。
- **対象が無ければ no-op（冪等）。** 探す画面の孫ツリーからの**未採用の基底の変換では何も消さない**。
- **`combo_punishes` と `combo_punish_curations` をペアで削除**し孤児を作らない（03a §4.1 の規則と一貫）。

**`CreateRequest` に `materializedFromComboId` を足さないこと。** 理由は 3 つ。(1) **出自はシステムが付ける値**であり、通常のコンボ登録経路から任意の出自を後付けできると**ドリフト検出という列の目的が壊れる**。(2) **規則を BE に一元化する**（DES-002 §4.2 の流儀）。(3) **クライアントに steps を往復させない**——既存 PUT は「クライアントがフルレシピを再送」方式だが、materialize でそれを採るとレシピが往復中に改変されうる。サーバ内で基底の `Steps` をそのまま複製すれば **`recipe_hash` が基底と一致することが構造的に保証**される。

**解除は独立**：`combo_punishes` を解除しても生成物のコンボは残る（ユーザーが自分で削除する）。この非対称を UI 文言で伝える。

### 4.5 FR301 重複防止

**1. 判定式**（RESEARCH-02 A-2／A-3 の実機序をそのまま使う。**DES-006 §2.3 errata が明文化済み**）

| 段 | 内容 |
|---|---|
| 1 段目（SQL） | `character_id`＝基底と同じ／`starter_move_id`・`position`・`opponent_stance`・`opponent_size`＝基底と同じ（**nil は `col IS NULL`＝nil 同士は一致**）／**`hit_type` ＝ `punish_counter`**（ここだけ基底と異なる） |
| 2 段目 | 候補の `recipe_hash` と、**基底 steps から計算した `recipe_hash`** の文字列完全一致 |

- **基底自身は衝突しない**（`hit_type` が 6 項に含まれるため）。
- **HTTP を往復しない**。サービス層で `FindActivePublishedDuplicates` ＋ `recipe_hash` 比較を**直接再利用**する。
- `recipe_hash` は **DB 列ではなくサービス層の SHA-256 計算値**。`Modifiers.Flags` は `sort.Strings` で正規化されるため、**steps をそのまま複製すれば hash は必ず一致する**。

**2. 判定の穴を明示してテストに入れる**

dup 判定の WHERE には **`is_draft = 0` と `deleted_at IS NULL` が固定**で入っている。したがって次の 2 ケースは**検出されず、二重生成が起こる**。

1. 既存の PC 版が**仮登録**（`is_draft = 1`）である。
2. 既存の PC 版が**ゴミ箱にある**（`deleted_at` が非 NULL）。

**これは既存の全登録経路と一貫した挙動であり、materialize だけの欠陥ではない。** ただし「重複防止がある」と説明された機能で二重生成が起きると驚きになる。**テストケースに 2 ケースとも入れ、期待値を「生成される（既存仕様どおり）」と明示する**（M17-E19 の対策＝テスト軸を実機序に合わせる）。なお裁定3 により**基底が仮登録なら生成物も仮登録**になるため、仮登録の基底から生成した PC 版は最初から網の外にある。

**3. 見つかったときの返し方**

**生成しない**。既存コンボの **id を返す**。FE は「この確定反撃は既に登録されています」と表示し **`/combos/{id}` へのリンク**を出す。`CheckDuplicateResponse` は id を含むため必要な情報は揃っている（**ダメージ・名称は含まれない**ので、リンク先で見せる。追加の GET を挟まない）。

### 4.6 【裁定11】編集経路での採用の引き継ぎ

**識別キー変更を伴う編集（PUT）で、`combo_punishes`／`combo_punish_curations` を新コンボへ引き継ぐ。**

- **現状**：旧コンボを `deleted_at` で論理削除して新コンボを INSERT するが、punish 系の引き継ぎコードが存在しない（`combo_punish` 参照 0 件）。結果、**編集しただけで採用が全画面から同時に消える**。
- **先例**：`setups` は `SetupCarryOptions` で引き継がれている。**§3.3-3 でこの実機序を引き、同じ形で punish を足す**（**L-1**＝「同型」を名乗る前に引く）。
- **引き継ぐもの**：`combo_punishes`（`combo_id` を新コンボへ）／`combo_punish_curations`（同上）。**`opponent_move_id`・`note` は不変**。
- **同一トランザクション**で行う。途中失敗で片方だけ移る状態を作らない。
- **識別キーが変わらない編集**（同一 id のまま UPDATE）では**何も起きない**ことも確認する。

> **これは 03a で凍結していた `internal/service/combo/` を開ける変更である。** DoD の回帰ゲート（§7.3）を必ず通すこと。

### 4.7 export 整合（E-17）

RESEARCH-02 D-8 のとおり、**既存経路のままで出力される見込み**（CSV は `hit_type` を verbatim、PDF／PNG は `HIT_TYPE_LABELS` 経由で `just_parry_punish_counter` のラベルも定義済み）。**新規の出力実装は不要**。

- **`materialized_from_combo_id` を CSV export に含めない**（裁定6）。CSV は意味単位（code ベース・DB 管理列除外）であり、combo の id をそのまま出すと往復で意味を失う。**import 後は出自が失われ独立コンボになる**（spec §2「生成後は独立フォーク」と整合）。
- **DoD に開発者の実出力目視を入れる**（§7.5）。

### 4.8 FE（変換導線・生成元バッジ）

**1. 変換ボタンの設置箇所（2 箇所）**

| 箇所 | 文脈 |
|---|---|
| **「区分を判定できない反撃」セクション**（03a が「変換機能は M18-03b で対応予定です」と告知している箇所） | 相手技が確定しているので `opponentMoveId` をそのまま渡せる。**告知文は変換ボタンの実装に合わせて書き換える** |
| **探す画面の孫ツリー（コンボ行）** | 既存の「確定反撃に採用」の隣。相手技は第1階層から確定 |

- **`hit_type` が `punish_counter` 系のコンボにはボタンを出さない**（§4.1）。
  - **【v1.0.2】そのために探す画面の孫 `ComboNode` に `hitType` を出力専用フィールドとして追加する**（`internal/service/punishfinder/service.go`）。**走査述語・フレーム/レーン判定・除外規則は一切変更しない**（案C は 03c・同一ファイルのため最小変更に留める）。FE 側は PC 系の判定を定数に集約する。

- **既存あり時**は「既に登録されています」＋リンクを出す（§4.5-3）。エラー扱いにしない。
