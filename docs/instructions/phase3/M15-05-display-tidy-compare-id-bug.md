## 1. 背景と目的

### 1.1 背景

- **FB①**（followup-backlog §A）: **登録画面の縦スクロールが過多**。現行画面は**左右に余白があり全幅を使わない縦長レイアウト**。この余白/狭幅が**スマホ対応・画面縮小に備えた意図**か、**特段の理由がない**のかは不明。**特段の理由がなければ横に広げて再配置**して縦を圧縮したい（UX/レイアウト）。ただし横に広げると**情報が過密になり入力しにくくなる懸念**があるため、Plan Mode で慎重に設計する。**折りたたみ/段組みは選択肢の一つで唯一解ではない**。**製造担当からのより良いレイアウト提案を歓迎**する。
- **FB②**（followup-backlog §A・M12-01 C-20・F12-2 連動）: **比較画面で「始動技#196」のように生 ID（`starter_move_id` の数値）が表示される**バグ。技名に解決されていない。
- **②は「着手前に実画面/実コード確認」が必須**（followup §A・handover §3.3・playbook §4.10）。**症状（比較画面で#196）のレイヤと真因のレイヤは異なり得る**（digest M12-1/M10-4）。名称解決経路（一覧/比較/詳細で共有される想定）を **grep 全数特定してから真因層を確定**する。
- **入力の実体**（code-facts §1）: 比較は `CompareTable`（Props `combos: (ComboDetail|undefined)[]`/`ids`/…）・`CompareTargetList`・`ComparePage`（`/compare`）・hook `useCompareCombos`（query `["combo", id]`）。始動技は **`ComboResponse.starterMoveId *int64` と `starterMoveCode string` の両方が DTO にある**（code-facts §DTO）。model `Combo` は `StarterMoveCode *string`（db:-・json:-）＝サーバ側で導出。**②の真因（なぜ比較だけ生 ID か）は §3.3 で実査**。
- 登録/編集は `RecipeBuilder`/`ComboEditorBasicFields` 等（DES-005 §5.7）。**非スキーマ**（①②とも表示層のみ・スキーマ/API/データ不変）。

### 1.2 目的

完了時に達成される状態:

- **①**: 登録画面の**縦スクロールが軽減**される。**現行の左右余白の理由を実査したうえで、理由がなければ横幅を活用した再配置**で縦を圧縮する（折りたたみ/段組みも選択肢だが唯一解ではない）。**項目の削除はしない**（機能温存）・**情報過密で入力しにくくならない**ことを担保。
- **②**: 比較画面で始動技が**技名で表示**される（生 ID「#196」表示の解消）。**真因層で修正**され、名称解決が一覧/詳細と**共有経路**に整合する（比較だけ別経路の取りこぼしを是正）。
- ①②とも既存機能・データ・API 不変（非破壊・非スキーマ）。

### 1.3 このマイルストーンで作らないもの（スコープ外）

- スキーマ・API・データの変更（①②は表示層のみ）。
- 登録画面の**項目そのものの削除・仕様変更**（①は整理＝配置/グルーピングのみ・機能は温存）。
- recipe_cache 全数調査/再生成（F12-2 の cache 側＝M20〔旧M17〕。本サブは表記/表示のみ）。
- タグ表示崩れ・タグフィルタのドロップダウン化（F12-2 G-3＝M23〔旧M20〕）。
- M16 依存の表記・他 M15 サブ（タグ色=M15-04／入力方式=M15-03／オンボーディング=M15-06）。

### 3.3 着手前の確認（Plan Mode 必須・②が最重要）

**②（比較画面 生 ID）＝真因実査（推測で直さない・digest §1）**:
1. **名称解決経路の grep 全数特定**: 始動技名がどこでどう解決/表示されるかを**一覧（ComboList）／比較（CompareTable/CompareTargetList）／詳細（ComboDetail）**で全数 grep。一覧/詳細は正しく技名を出し、比較だけ「始動技#<id>」の生 ID を出す**差**を特定する。
2. **真因層の確定**: 生 ID 表示の真因が (a) 比較が `starterMoveId` を直描画し `starterMoveCode`/名称を使っていない、(b) 比較クエリ（`useCompareCombos`＝`["combo", id]`）の `ComboDetail` に名称が来ていない、(c) 名称解決ヘルパーが一覧/詳細のみで共有されず比較が別経路、のどれか（またはそれ以外）を**実コードで確定**。**症状のレイヤ≠真因のレイヤ**を疑い、直近の見た目だけ塞がない。
3. **修正方針の確定**: 真因層で、一覧/詳細と**共有の名称解決経路**へ比較を寄せる（`starterMoveCode` 利用 or 共有ヘルパー）。真因が上流（DTO/クエリ）なら修正層をそこに置く。

**①（縦スクロール軽減）**:
4. **①の余白/狭幅の理由と横幅活用の可否を実査**（DES-005 §5.7 の表示項目 1〜14・現行 CSS/コンテナ幅制約）: 現行の左右余白・狭幅コンテナが **(a) スマホ対応/画面縮小のためのレスポンシブ意図か、(b) 特段の理由がないか** を実コード/実画面で確定する。
   - **(a) の場合**: レスポンシブ意図を壊さず、**PC/広幅では横に広げ・狭幅では縦積みに戻る**形を設計。
   - **(b) の場合**: **横幅を活用した再配置**で縦を圧縮する。
   - いずれも**情報過密で入力しにくくならない**ことを最優先に設計。**折りたたみ/段組みは選択肢の一つ**として検討するが唯一解ではない。**必要なら製造担当がサンプル HTML/レイアウト案を作成**して開発者と判断する（**設計担当はサンプルを出さない**＝製造の裁量と提案に委ねる）。**より良いレイアウト提案を歓迎**。
5. **DES-005 CHANGE 要否**: ①の表示項目整理が DES-005 §5.7 の配置仕様を変えるか／②の名称解決是正が §5.6/§5.8 の表示仕様に触れるかを着手時 view で判定。要すれば設計担当が起票（採番は起票時に registry 確認・製造は DES 直接編集しない）。②が既存仕様どおりの**バグ修正**なら CHANGE 対象外の可能性。

## 4. 詳細仕様

### 4.1 ①表示整理・縦スクロール軽減（DES-005 §5.7）

- 登録/編集画面の**縦スクロールを軽減**する。**§3.3-4 で余白/狭幅の理由を実査**し、**理由がなければ横幅を活用した再配置**で縦を圧縮する（レスポンシブ意図があれば PC で広げ狭幅で縦積みに戻す）。**折りたたみ/段組みは選択肢の一つ**（唯一解ではない）。**項目の削除・機能変更はしない**（配置/まとめ方のみ）。
- **情報過密で入力しにくくならないことを最優先**に設計。**必要なら製造担当がサンプル HTML/レイアウト案を作成**して開発者と判断（設計担当はサンプルを出さない）。**製造担当のより良い提案を歓迎**。
- モバイル/狭幅での到達性・操作性を担保（arch §10）。既存の始動技自動推定・セットプレイ節・タグ・メモ等の機能・挙動は不変。

### 4.2 ②比較画面 生 ID バグ（真因層で修正）

- 比較画面の始動技を**技名表示**にする（「始動技#196」の生 ID を解消）。**§3.3-1〜3 で特定した真因層**で修正し、一覧/詳細と**共有の名称解決経路**に整合させる（`starterMoveCode` 利用 or 共有ヘルパー・真因次第）。
- **正しく出ている一覧/詳細側を壊さない**（比較を正しい側へ寄せる）。真因が DTO/クエリ上流なら、その層で技名が届くようにする（ただし**API 契約・スキーマは変えない**＝既存 `starterMoveCode` 等の活用に留める）。

### 4.3 test-id

- 既存規約を grep 実値確定 → 本サブが触れる比較の始動技表示・①の整理箇所に必要な test-id を付与（範囲限定・digest §4）。
