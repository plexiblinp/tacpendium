## 1. materialize の対象判定

| 生成元の `hit_type` | 扱い | 根拠 |
|---|---|---|
| `normal` | **対象**。始動技ダメージ × 0.2 を加算し `punish_counter` で生成 | spec §5 |
| `counter` | **対象**。**ダメージ不変**で `punish_counter` へ | spec §5（カウンターもパニッシュカウンターも補正は 1.2 倍で同値＝既に加算済み。二重計上しない） |
| `punish_counter` | **対象外**。**UI にボタンを出さない**（裁定8） | 既に PC 版。代わりに「確定反撃に採用」だけを出す |
| `just_parry_punish_counter` | **対象外**。ジャストパリィ始動は**手入力が正典** | 物理設計プラン §2.5 |

**BE でも対象外を弾く**。FE がボタンを出さないだけでは API 直叩きで二重計上が起こる。endpoint 側で生成元の `hit_type` を検査し、`punish_counter` 系なら 400 を返す（理由コードを添える。M19-01 の `knockdown_advantage_required` と同じ流儀＝UI が理由を表示できる専用コード）。

### 1.2 【v0.2.0・重要】materialize のスコープ境界（裁定 10 から導出）

裁定 10 の回答に、**materialize が扱う範囲を確定させる一文**が含まれていました。

> パニッシュカウンターでコンボ自体が全然違うものになることはあるが、**それは別コンボとして登録すればいい**し、その導線も充分用意されている（**孫ツリーにいるから**）。

これにより、次の境界が引かれます。

| ケース | 扱い |
|---|---|
| **PC 始動でも同じレシピが通る** | **materialize の対象**。レシピを複製し、ダメージと `hit_type` だけを変える |
| **PC 始動だとレシピ自体が変わる**（追撃が伸びる・ルートが変わる等） | **materialize の対象外**。**探す画面の孫ツリーにある既存の「新規登録」導線から、別コンボとして手入力する** |

**設計上の含意が 3 つあります。**

1. **materialize に「レシピを編集してから生成する」機能を作らない。** 生成物は基底のレシピをそのまま複製したものに限る。編集は生成後に通常のコンボ編集で行う（§2.4 の「独立フォーク」と一貫）。
2. **§5 の FR301 が素直に成り立つ根拠になる。** レシピが常に基底と同一であるため、`recipe_hash` は必ず一致し、判定が 6 項 SQL ＋ hash 一致の 2 段で閉じます（§3.1-3 でサーバ内複製を選んだ理由がここでも効く）。
3. **「PC 版はレシピが違う」ケースに materialize が中途半端に対応しない**ことを、指示書の「やらないこと」に明記する。製造が親切心で編集機能を足すのを防ぎます。

## 2. ダメージ計算（**本アプリ初のダメージ自動計算経路**）

RESEARCH-02 B-4 の実測により、`combos.damage` は**常に手入力値をそのまま保存**しており、`moves.damage` から自動計算・コピーする既存コードは**存在しない**。materialize が最初の経路になる。

### 2.1 式

```
generated.damage = base.damage + round( starterMove.damage × 0.2 )
```

### 2.2 縁の扱い（裁定2＝**許して注記**）

| 条件 | 挙動 | UI 表示 |
|---|---|---|
| `base.damage` が NULL | 生成する。`damage` は **NULL のまま** | 「基底コンボにダメージが未入力のため、加算していません」 |
| `base.starter_move_id` が NULL | 生成する。`damage` は **基底の値のまま** | 「始動技が未設定のため、加算していません」 |
| 始動技の `moves.damage` が NULL | 同上 | 同上 |

**生成を止めない**。M18 の「silent に消さない」思想の適用であり、加算できなかった事実を**画面で伝える**（黙って 0 加算にしない）。

### 2.3 丸め規則（裁定1＝**机上で決めない**）

**着手前 Plan Mode の実査項目**に次を入れる。

```sql
SELECT COUNT(*) FROM moves WHERE damage IS NOT NULL AND damage % 5 <> 0;
```

- **0 件なら**：`× 0.2` は常に整数になるため、丸めは論点として消える。**実装は整数演算**（`damage / 5`）で書き、丸め関数を持ち込まない。
- **1 件以上なら**：**該当技を実値で列挙して報告し、実装を止める**。開発者がインゲームで当該技のパニッシュカウンター時ダメージを実測し、その結果で丸め規則を決める（裁定1）。**推測で四捨五入・切り捨てを選ばない。**

> この運用は、M18 が一貫して採ってきた「フレーム・ダメージの規則を机上で作らない」原則そのもの。DES への丸め規則の記載も、**実測が出るまで確定させない**（中央へ連絡済）。

### 2.4 生成後は編集可・独立フォーク

基底を直しても生成物は追従しない（spec §2）。**バグではなく仕様**であり、UI 文言でもそう伝える。ドリフト検出は `materialized_from_combo_id` によって将来可能になるが、**本サブでは検出機能を作らない**（列に出自を記録するところまで）。

### 2.5 【v0.2.0・確定】基底からのコピー範囲（裁定 9・10）

**裁定 9＝`combo_setups` 以外をコピーする。** 裁定 10＝`knockdown_advantage` もコピーしてよい。

| 項目 | 扱い | 根拠 |
|---|---|---|
| レシピ（`combo_steps`） | **コピー** | 必須。§5 の `recipe_hash` 一致にも要る |
| 状況系（`position`／`opponent_stance`／`opponent_size`／`situation`＝キャラ固有状態） | **コピー** | 同じ状況の反撃版なので変わらない |
| ゲージ系（始動残量 4 列・消費 2 列） | **コピー** | 同じレシピなら変わらない |
| `drive_damage` | **コピー** | 同上 |
| **`knockdown_advantage`** | **コピー** | **裁定 10**＝「同じコンボならパニッシュカウンターの有無で `knockdown_advantage` が変わることはない」。**注記も不要**（v0.1.0 の暫定案では注記を出す想定だったが、変わらないと確定したので不要） |
| 起き攻め（`combo_oki_options`） | **コピー** | 同じ〆なら同じ |
| `memo`／メディア 3 列（`link`／`video_path`／`image_path`） | **コピー** | 記録者が残した参照情報は出発点として有用 |
| タグ（`combo_tags`） | **コピー** | マイコンボのステータス管理を引き継げる |
| **セットプレイ紐づけ（`combo_setups`）** | **コピーしない** | 別コンボへの紐づけは意味が変わる。生成後に記録者が判断する |
| `is_draft` | **コピー**（基底の状態を引き継ぐ） | 裁定 3 |
| `materialized_from_combo_id` | **基底の id を設定**（コピーではない） | 出自。§4 |
| `version`／`created_at`／`updated_at`／`deleted_at` | **コピーしない**（新規行の初期値） | DB 管理列 |

> **`knockdown_advantage` がコピー可と確定したことは、M19 への波及リスクが消えたことを意味します。** M19 のセットプレイ自動提案は KA を直接使うため、誤値が混ざると提案精度に効く懸念がありましたが、**PC の有無で KA は変わらない**ため生成物の KA は基底と同じく正しい値になります。中央への共有事項として §10-7 に記載。

**実装上の注意**：`combo_steps`／`combo_oki_options`／`combo_tags` は**別テーブル**であり、`combos` の INSERT だけでは複製されません。**§3.1 のトランザクション内で子テーブルまで複製する**こと。RESEARCH-02 B-5 のとおり複製ヘルパーは存在しないため、**PUT 経路が新コンボを作るときに子テーブルをどう作り直しているかを着手前 Plan Mode で実査し、同じ機序を使う**（L-1＝「既存と同型」を名乗る前に実機序を引く）。

## 3. API 経路とトランザクション境界

### 3.1 専用 endpoint

**`POST /api/combos/{id}/materialize`**（パス名は指示書で確定）。`{id}` ＝ 基底コンボ。

| 項目 | 内容 |
|---|---|
| リクエスト | `opponentMoveId`（必須。裁定7 により `combo_punishes` を同時に作るため）／`note`（任意・`combo_punishes.note` へ） |
| 処理 | 基底読み込み → 対象判定（§1）→ steps 複製 → ダメージ計算（§2）→ **FR301 チェック（§5）** → `combos` INSERT → `combo_punishes` INSERT |
| トランザクション | **上記すべてを 1 トランザクション**（裁定7） |
| レスポンス（生成時） | 生成コンボの id と、加算の有無・理由（§2.2 の注記を FE が出せる情報） |
| レスポンス（既存あり時） | **生成せず**、既存コンボの id を返す（§5.3） |

**`CreateRequest` に `materializedFromComboId` を足す案を採らない理由**（3 点）：

1. **出自はシステムが付ける値**である。`CreateRequest` に足すと通常のコンボ登録経路から任意の出自を後付けでき、ドリフト検出という列の目的が壊れる。
2. **規則を BE に一元化する**（DES-002 §4.2 の流儀。M18-02 の走査で確立）。ダメージ加算と `hit_type` 決定を FE に持たせない。
3. **クライアントに steps を往復させない**。既存 PUT は「クライアントがフルレシピを再送」方式（RESEARCH-02 B-5）だが、materialize でそれを採るとレシピが往復中に改変されうる。サーバ内で基底の `Steps` をそのまま複製すれば **`recipe_hash` が基底と一致することが構造的に保証**され、FR301 の判定（§5）が素直になる。

> **DES-002 v1.36.0 第37版が「materialize endpoint は M18-03 で追加〔本版では未追加＝候補のまま〕」と記していることと整合する。**

### 3.2 `combo_punishes` の同時作成（裁定7）

- 生成と紐づけは**同一トランザクション**。materialize は必ず「この相手技への反撃」という文脈から起動されるため、相手技が確定していない materialize は起こり得ない。
- **解除は独立**。`combo_punishes` を解除しても生成物のコンボは残る（ユーザーが自分で削除する）。
- **03a が入れた連動削除との関係**：03a で `DELETE /api/combo-punishes` は同一キーの curation も削除する。生成物のコンボ自体は消さない。この非対称（紐づけを消してもコンボは残る）を UI 文言で伝える。

## 5. FR301 重複防止

### 5.1 判定式（RESEARCH-02 A-2／A-3 の実機序をそのまま使う）

| 段 | 内容 |
|---|---|
| 1 段目（SQL） | `character_id`＝基底と同じ／`starter_move_id`・`position`・`opponent_stance`・`opponent_size`＝基底と同じ（**nil は `col IS NULL`＝nil 同士は一致**）／**`hit_type` ＝ `punish_counter`**（ここだけ基底と異なる） |
| 2 段目 | 候補の `recipe_hash` と、**基底 steps から計算した `recipe_hash`** の文字列完全一致 |

- **基底自身は衝突しない**。`hit_type` が 6 項に含まれるため、基底（`normal` / `counter`）と生成物（`punish_counter`）は設計上すでに別コンボである（spec §2 の転換理由そのもの）。
- **HTTP を往復しない**。`POST /api/combos/check-duplicate` は同じ判定を通るが（A-5）、materialize はサーバ内の操作なので、サービス層で `FindActivePublishedDuplicates` ＋ `recipe_hash` 比較を**直接再利用**する。
- **`recipe_hash` は DB 列ではなくサービス層の SHA-256 計算値**（A-3）。`Modifiers.Flags` は `sort.Strings` で正規化されるため、**steps をそのまま複製すれば hash は必ず一致する**（§3.1-3 の設計がここで効く）。

### 5.2 判定の穴を**明示して**テストに入れる

dup 判定の WHERE には **`is_draft = 0` と `deleted_at IS NULL` が固定**で入っている（A-2／B-6）。したがって次の 2 ケースは**検出されず、二重生成が起こる**。

1. 既存の PC 版が**仮登録**（`is_draft = 1`）である。
2. 既存の PC 版が**ゴミ箱にある**（`deleted_at` が非 NULL）。

これは既存の全登録経路と一貫した挙動であり、**materialize だけの欠陥ではない**。ただし「重複防止がある」と説明された機能で二重生成が起きると驚きになる。**指示書のテストケースに 2 ケースとも入れ、期待値を「生成される（既存仕様どおり）」と明示する。** M17-E19（既存 VAL の判定キーを確認せず矛盾する振る舞いを書いた）の対策として、**テスト軸を実機序に合わせる**。

なお裁定3 により**基底が仮登録なら生成物も仮登録**になるため、仮登録の基底から生成した PC 版は最初から FR301 の網の外にある。この connection も指示書に書く。

### 5.3 見つかったときの返し方

- **生成しない**。既存コンボの **id を返す**。
- FE は「この確定反撃は既に登録されています」と表示し、**`/combos/{id}` へのリンク**を出す。

### 7.1 手動入力（overview j）

| 経路 | `hit_type` の扱い |

### 7.3 出自は CSV に出さない（裁定6）

`materialized_from_combo_id` を CSV export に含めない。CSV は**意味単位**（code ベース・DB 管理列除外・DES-002 §7.6）であり、combo の id をそのまま出すと往復で意味を失う。含めるなら `local_id` 参照方式が要り、契約が複雑になる。

- **import 後は出自が失われ独立コンボになる**。spec §2 の「生成後は独立フォーク」と整合する。
- **ドリフト検出は自環境内でのみ機能する**、と割り切る。この割り切りを **DES 反映要点に明記**して、後から「なぜ出自が消えるのか」を問われたときの根拠を残す。

### 9.6 【要設計判断】編集経路での採用の引き継ぎ

**03a で発見された最も重い残課題**です。識別キー変更を伴う編集（PUT）は旧コンボを `deleted_at` で論理削除して新コンボを INSERT しますが、**`combo_punishes`／`combo_punish_curations` を新コンボへ引き継ぐコードが存在しません**（`setups` は `SetupCarryOptions` で引き継がれるが punish は対象外）。したがって **ユーザーがコンボを編集しただけで、その採用がマイリスト・隠したもの管理・探す画面の既登録表示のすべてから同時に消えます**。ゴミ箱経由より頻度の高い経路での silent-drop です。`followup-backlog.md` §I-(b) `combo-punish-carryover-on-edit` に起票済み。

**03b で決めるのが自然な理由**：materialize は `combos` の INSERT 経路と `combo_punishes` を**同一トランザクションで扱う唯一の実装**になるため、採用の引き継ぎ規則を設計する場所として最も近い。

**処遇候補**：(1) 引き継ぎ実装（PUT で新コンボへ `combo_punishes` を移す）／(2) 編集時の注記・警告（「この編集で確定反撃の採用が外れます」）／(3) 許容の明文化（DES に書いて閉じる）。

**私の暫定案＝(1)**。`setups` に `SetupCarryOptions` という先例がある以上、punish だけ引き継がないのは一貫性を欠きます。ただし **03b のスコープが膨らむ**ため、**確認事項 11** として開発者に諮ります。
