## 1. 背景と目的

### 1.1 背景
M18-02（確定反撃サーチ）に、開発者要件として「**前ダッシュ経由の確定反撃候補**」が追加された。相手技をガード/ジャストパリィ後、前ダッシュで接近してもなお猶予が残るなら、打撃で反撃できる候補として提示する。判定には次が要る。

```
残り猶予 = 有利フレーム − dash_forward の全体フレーム
残り猶予 ≥ 4  かつ  S.startup ≤ 残り猶予  →  候補
```

**`dash_forward` の全体フレームはキャラごとに異なる**（SF6 の実ゲーム仕様）。しかし本プロジェクトでその値がキャラ別に保持されているか、開発者・中央とも未把握であり、設計担当の手元資料（code-facts・DES・RESEARCH-01）でも**「列は存在するが値の中身は不明」**までしか確定できなかった。

**ジャンプ（`jump_neutral`／`jump_forward`／`jump_back`）も同じ調査対象に含める**（開発者指示 2026-07-22）。ジャンプも**キャラごとに全体フレーム（離陸〜着地〜着地硬直）が異なる**実ゲーム仕様であり、`dash_forward` と**まったく同じ投入経路**（`000025` の全キャラ一括 seed）で入っているため、値の保持実態も同型である可能性が高い。前ダッシュ経由の候補判定と同様に、将来ジャンプ経由（めくり・跳び込み等）を扱う場合の前提データになる。

**既知の事実（実査済・調査の出発点）**：
- `dash_forward`／`dash_back` は `category="system"` の独立 move（DES-004 §2.1・§2.2 taxonomy 原則 (a)）。
- 投入元は **`migrations/000025_seed_movement_system_moves_all.up.sql`**＝**全キャラ一括**の移動 system move 9 件（`forward`/`back`/`micro_forward`/`micro_back`/`dash_forward`/`dash_back`/`jump_neutral`/`jump_forward`/`jump_back`）。攻撃技を持たない `c_viper`/`dhalsim` もこの 9 件だけは持つ（M18-RESEARCH-01 §A-1）。
- `moves` のフレーム列は `startup`/`active`/`total`/`on_hit`/`on_block`/`recovery`（すべて `*int`＝**NULL 可**。code-facts `Move` struct）。**ダッシュ全体フレーム専用の列は存在しない**。
- `total` の定義は **`total = 発生 + 持続 − 1 + 硬直`**、**算出不能なら NULL**（DES-003 §3.5・CHANGE-025/028）。

### 1.2 目的
**`dash_forward` および `jump_neutral`／`jump_forward`／`jump_back` に、キャラ別のフレーム値が実際に入っているか**を事実として確定する（**対象 4 code**）。結果により M18-02 の設計が次のように分岐するため、**推測で埋めずに実測**する。

- **ケース A**：キャラ別に妥当な値が入っている → 判定式をそのまま実装（使用列も確定）。
- **ケース B**：全キャラ同一の便宜値、または NULL → **新列追加の承認ゲート**（中央経由で開発者承認）か、前ダッシュ経由を「データ待ち」として手動確認レーンに留めるかを設計判断。

### 1.3 このタスクでやらないこと（スコープ外）
- **データの修正・投入・マイグレ作成**（read-only。値が無くても入れない）。
- **どの列に持たせるべきかの設計判断**（新列の要否・命名は指示書担当／中央／開発者の判断）。
- **ジャンプを確定反撃の判定にどう使うかの設計判断**（下記注記のとおり式が異なる。本調査は値の実態のみ）。
- 調査対象外の移動（`dash_back`・`micro_forward`・`micro_back`・`forward`・`back`）の実装方針決定。※**値の実測は §3-3 で併せて採る**（比較材料として有用なため。判断はしない）。

> **注記（設計担当より・調査では判断しない）**：ジャンプは前ダッシュと**判定式が異なる**見込み。ダッシュは「移動して地上技で反撃」＝`有利フレーム − ダッシュ全体` で残り猶予が出るが、ジャンプは滞空中に**空中技（`is_aerial=true`）で攻撃**し、さらに着地硬直が絡むため、`離陸〜攻撃可能になるまで` と `全体` を区別する必要がある。式の設計は本調査の結果を見て指示書担当が行う。**調査は「どの列に何が入っているか」の事実収集に徹すること**。
- `combos`・`combo_steps` 側の調査（本調査は `moves` の値の実態のみ）。

## 3. 調査項目

### 3-1【最重要】移動 system move 4 code のキャラ別フレーム値（全キャラ実列挙）
`moves` から **`code IN ('dash_forward','jump_neutral','jump_forward','jump_back')`**（**4 code**）の全行を、**キャラを解決して全件列挙**する。

> **対象 code（確定）**：`dash_forward`／`jump_neutral`／`jump_forward`／`jump_back` の **4 code**。`dash_back` は §3-3 の比較材料側で採る。

- 取得列：`characters.code`（キャラ）・`moves.code`・`category`・`startup`・`active`・`total`・`recovery`・`on_block`・`on_hit`・`damage`・`is_aerial`・`is_derived`・`is_projectile`・`raw_data`。
- **母数を明示**：`characters` の総行数と、**各 code ごとに**それを持つキャラ数（すべて一致するか。欠けているキャラがあれば列挙）。
- **判定の核心**：
  - (a) `total` に値が入っているか、**NULL か**。
  - (b) 値が入っている場合、**キャラごとに異なるか**（全キャラ同一値なら便宜値の疑いが濃い）。
  - (c) `startup`/`active`/`recovery` の入り方（`total` が算出式で導出できる形になっているか）。
  - (d) **ジャンプ 3 code どうしの差**（`jump_neutral`/`forward`/`back` で値が異なるか、同一か）。
- **異なる値の種類数を code ごとに**数えて明記（例：「`jump_forward` は 12 キャラ中 `total` 非 NULL が N 件、うち相異なる値は M 種」）。
- **結論は code ごとに出す**（ダッシュだけ値があってジャンプは NULL、等の非対称があり得るため一括りにしない）。

### 3-2 値の出所（マイグレ・CSV の追跡・**4 code 分**）
- `migrations/` 全体を grep し、**対象 4 code を INSERT または UPDATE している箇所を全件**特定する（ファイル名・行番号・投入している列と値）。
- `000025_seed_movement_system_moves_all.up.sql` が **どの列に何を入れているか**（フレーム列に値を入れているか、NULL/未指定か）。
- `character_data/*.csv` に対象 4 code の行が**存在するか**（code ごとに）。存在する場合、フレーム列（発生/持続/硬直/全体に相当する列）に値があるか。**CSV の列名は実ヘッダを確認して記載**（推測しない）。
- **seedgen 経路との関係**：対象 4 code は seedgen（CSV → SQL）で生成される行か、`000025` の手書き SQL で投入される行か。**どちらが値の一次源か**を code ごとに明示。

### 3-3 比較材料（判断はしない・事実のみ）
- `dash_back`・`micro_forward`・`micro_back`・`forward`・`back`、**その他の移動 system move のフレーム列の入り方**（対象 4 code と同傾向か）。
- `drive_parry`（`category=system` の非攻撃 move）の入り方（**先例＝「持続は注釈付き範囲のため active は空とし raw_data へ退避」**という扱いが DES-003 §3.3 にある。対象 4 code の `raw_data` にも同様の退避があるかを確認）。

### 3-4 実ゲーム値との突合可能性（**事実確認のみ・値の正誤判定はしない**）
- `raw_data`（`notes`/`notes_tool` 等）に、**ダッシュ／ジャンプの全体フレーム・着地硬直等に相当する記述**が**文字列として残っていないか**を確認する（あれば原文を引用・code ごとに）。
- **注意**：外部サイト等から「正しいダッシュ／ジャンプのフレーム」を調べて補完することは**本調査のスコープ外**（データ投入も禁止）。あくまで DB/CSV/マイグレ内に何があるかのみ。

### 3-5 空中技（`is_aerial=true`）の存在状況（**事実のみ**）
ジャンプ経由の反撃は「ジャンプ → **空中技**で攻撃」となるため、空中技側のデータ有無も前提になる。

- `moves` で **`is_aerial = 1` の行数**（全体・キャラ別）。母数（`moves` 総行数）を併記。
- そのうち `startup` が非 NULL の件数（＝フレーム判定に使える空中技がどれだけあるか）。
- **判断はしない**（ジャンプ経由の式をどう組むかは指示書担当が決める）。
