## 1. 背景と目的

### 1.1 背景

**クリーンなクローン直後の環境で、検査とテストが人手の前準備なしには回らない。** **`M22` 期だけで 4 サブ連続、`markdown-it-py` 単体では `M22-01` から数えて 6 回目の再発である。**

| # | 欠けているもの | 症状 |
|---|---|---|
| 1 | **`markdown-it-py`** | `scripts/check-md-emphasis.sh --self-test` が「未実行」を返し、**`check-artifact-integrity.sh`**〔**★1 本目に回す検査**〕**が違反 1 件を報告しつづける** |
| 2 | **`web/node_modules`**（`pnpm install` 未実行） | `make e2e` が `@playwright/test` を見つけられずに落ちる。**`pnpm test` も回らない** |
| 3 | **`govulncheck`** | `/app_build_check` が SKIP する。**★「脆弱性が無い」ではなく「検査していない」** |

### 1.2 ★これは実装の欠陥を直す作業ではない

**★`check-md-emphasis.sh` は依存が無いとき緑を返さず非ゼロ終了する設計であり、正しく振る舞っている**（`D-327` の修正どおり）。**`check-artifact-integrity.sh` がそれを拾って赤にするのも正しい。**

**⇒ 直すのは環境の側である。**

### 1.3 ★★歯止め（**これを破ると本作業は害になる**）

| # | 歯止め |
|---|---|
| **1** | **★スクリプトを「依存が無くても通る」形に緩めないこと。** **それをすると、検査が存在しないのと同じになる** |
| **2** | **★`--self-test` の陽性対照を弱めないこと。** **「依存欠落 → 未実行として非ゼロ終了・緑を返さない」という振る舞いは、検査が空回りしていないことの保証である** |
| **3** | **★ベースライン固定型の検査**（`check-md-emphasis.sh` ／ `check-instruction-format.sh` ／ `check-doc-inventory.sh`）**のベースライン値を動かさないこと。** **本作業は検査対象を 1 行も変えない** |
| **4** | **★`docs/design/` 配下に差分を出さないこと**（設計書を変える作業ではない） |

### 1.4 目的

**完了時に、次が成立している。**

1. **★クリーンなクローン直後に、人手の前準備なしで `bash scripts/check-artifact-integrity.sh` が「違反なし」を返す。**
2. **★同じく、人手の前準備なしで `make e2e` が完走する。**
3. **`/app_build_check` が `govulncheck` を **未インストール**を理由に SKIP しない**（**★2026-08-19 に射程を限定＝D-454**）。**⇒ 「バイナリが在り、起動して解析を開始する」までが本作業の完了条件である。** **★DB ホストへ到達できるかは egress ポリシーの側であり、リポジトリからは解けない。** **⇒ 本作業の完了条件から外した**（followup `cloud-env-cannot-reach-vuln-go-dev`。**開発者の環境設定の手番**）。
4. **★上記が devContainer とクラウド実行環境の両方で成立している**（§1.5）。
5. **followup 3 行がまとめて畳める状態になっている**（§7.4）。

### 1.5 ★★「クラウド実行環境だけの話」ではない

> **★2026-08-18 の開発者の問い「これは web 版 Claude での話ですね？」への回答である**（**D-444**）。

**★半分は正しいが、半分は違う。**

| 道具 | devContainer | クラウド実行環境 |
|---|---|---|
| **`markdown-it-py`** | **★`.devcontainer/Dockerfile` へ導入済み** | **★効いていない**（クラウドは Dockerfile を使わない経路で立つ） |
| **`web/node_modules`** | **★クリーンなクローン直後は無い** | **★同じく無い** |
| **`govulncheck`** | **要実査**（§3.3-2） | **★未導入** |

**⇒ `markdown-it-py` だけが「クラウド固有」であり、残り 2 つは両方で踏む。** **★devContainer 側だけを直しても本件は閉じない。逆にクラウド側だけを直しても閉じない。**

### 1.6 このサブで作らないもの（スコープ外）

| # | 項目 | 理由 |
|---|------|------|
| 1 | **検査スクリプトの振る舞いの変更** | **§1.3-1 / §1.3-2 の歯止め** |
| 2 | **依存ライブラリの追加・更新**（`go.mod` / `package.json`） | **★新規依存追加は開発者への提案が要る**（`CLAUDE.md` §6）。**本作業が入れるのは「開発ツール」であって本体の依存ではない** |
| 3 | **`.devcontainer/` のベースイメージの変更** | **★リビルドの影響が読めない。** 必要と判断したら止めて報告する（`/devcontainer_rebuild_check` の手番） |
| 4 | **CI の新設** | 本プロジェクトに CI は無い。**作らない** |
| 5 | **`docs/design/` 配下すべて** | §1.3-4 |

## 4. 詳細仕様

### 4.1 ★入れるもの 3 つ

| # | 道具 | 何のため |
|---|---|---|
| 1 | **`markdown-it-py`** | `check-md-emphasis.sh` の前提。**無いと `check-artifact-integrity.sh` が 1 本目で赤** |
| 2 | **`web/node_modules`**（`pnpm install`） | `make e2e` ／ `pnpm test` |
| 3 | **`govulncheck`** | `/app_build_check` の CVE 検査 |

**★`sudo` は使えない**（`CLAUDE.md` §10 で機械的に禁止）。**⇒ ユーザ権限で入る形を採ること。**

**★`curl ... \| bash` も使えない**（同）。**⇒ パッケージマネージャか公式のインストール手順を、パイプなしで使うこと。**

### 4.2 ★冪等であること

**SessionStart hook を使う場合、毎セッション実行される。** **⇒ 次を満たすこと。**

| # | 内容 |
|---|---|
| 1 | **★既に入っているときは何もしない**（再インストールしない）。**⇒ セッション起動が遅くならない** |
| 2 | **★失敗してもセッションを止めない**（**環境整備が転けたせいで作業ができなくなるのが最悪である**）。**失敗は見える形で出すが、非ゼロ終了でセッションを殺さない** |
| 3 | **★出力は静かにすること。** **毎回長いログが出ると、本当に見るべき出力が埋もれる** |

### 4.3 ★スラッグの一般化

**followup 3 行は同型として散らばっている。** **⇒ 本作業の完了時に 1 つのスラッグへまとめる**（例＝`clean-clone-missing-toolchain-deps`）。

**★ただし製造は `followup-backlog` を編集しない**（**D-382**。§J を除く）。**⇒ 完了報告へ「3 行をこのスラッグで畳んでよい」と書いて設計卓へ渡すこと。**

### 4.4 ★直したことの証明

**「入れた」ではなく「クリーンな状態で通る」を示すこと。**

| # | 示し方 |
|---|---|
| 1 | **★`node_modules` を消してから `make e2e` が完走することを示す**（**★`web/node_modules` の削除は破壊的操作ではない。再生成できる**） |
| 2 | **★`check-artifact-integrity.sh` が「違反なし」を返すことを、実出力の転記で示す** |
| 3 | **★`/app_build_check` が `govulncheck` を SKIP しないことを示す**（**★脆弱性が見つかっても本作業では直さない。依存更新の判断は開発者**＝`CLAUDE.md` §6） |
| 4 | **貼り付ける出力はフェンス付きコードブロックで書くこと**（`E-126`。**★Markdown 表のセルへ置かない**） |


### 4.5 ★★hook を入れたら、新しいセッションが起動できることを確認する（**2026-08-19 追加＝D-451**）

> **★本作業で唯一「取り返しがつきにくい」失敗である。** **SessionStart hook が壊れると、次のセッションが起動しない。** **⇒ 直しに行くセッションも起動できない。**

| # | 内容 |
|---|---|
| 1 | **★製造セッションは自分を再起動できない**（`M22-overview` §4.4.1 の (b)＝「機械に手が無い」）。**⇒ 確認は開発者の手番である** |
| 2 | **★製造は「hook を入れた」で完了としないこと。** **完了報告へ「開発者の起動確認待ち」と明記し、そこで止まる** |
| 3 | **★開発者が確認するのは 1 つだけ**——**新しいセッションを 1 本起動し、起動すること。** **あわせて起動時の出力が静かであること**（§4.2-3） |
| 4 | **★復旧手順を完了報告へ書くこと**——**壊れたときに開発者が手で戻せる形**〔どのファイルの何行を消せば元に戻るか〕。**★これを書かずに hook を入れないこと** |
| 5 | **★段階を分けてよい**——**devContainer 側だけ先に入れて確認し、hook は後から入れる形も採れる。** **採ったなら理由を完了報告へ書く** |

**★§4.2-2（失敗してもセッションを止めない）は、hook の中の処理が失敗した場合の話である。** **hook そのものが壊れている場合は §4.2-2 では守れない。** **⇒ 本節が別に要る。**
