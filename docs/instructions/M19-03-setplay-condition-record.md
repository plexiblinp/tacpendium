## 1. 背景と目的

### 1.1 背景

セットプレイ自動提案（M19-01／M19-02）は、**フレーム計算のみで候補を導出しており、間合いを一切モデル化していない**。実際に成立するかは、**相手の受け身種別（その場受け身／後ろ受け身）**と、**コンボ終了時に相手が画面端にいるか**で変わる。

そのためユーザーは実機で検証してから採択するが、**その検証結果を記録する場所がない**。「後ろ受け身では駄目だった」を残せないため、同じ検証を何度も繰り返すことになる。

**開発者要望（2026-07-26）**により、これを記録し**後から絞り込める**ようにする。

**確定している設計判断**（`M19-DESIGN-06` v1.1.0・CHANGE-087 通知書）:

| 論点 | 確定 |
|---|---|
| 帰属先 | **コンボ × セットプレイの組**（`combo_setups` の組）。`setups` は複数コンボに紐づき得、**転用先ではコンボの終わり際の距離が違うため成立条件も変わる** |
| 端の扱い | **独立軸**。`combos.position` は**コンボ開始位置**であり、セットプレイに効くのは**コンボ終了時**の位置。区分は**「端にいるか」の真偽のみ** |
| 記録する状態 | **未検証／成立／不成立**の三値。**攻撃種別（シミー・投げ重ね）の軸は不要**＝記録するのは「**セットプレイの最後の重ねが成立するか否か**」の 1 軸 |
| 三値の表現 | **行の有無 ＋ `result`**。**`result` に NULL を入れて意味を持たせない** |
| 検証日時 | **持たない**（バランス調整パッチへの追従は後続フェーズの範囲） |
| 編集導線 | **コンボ詳細（DES-005 §5.6 項目10）**。**セットプレイ編集画面には置かない**（§4.4.1） |

### 1.2 目的

1. **新テーブル `combo_setup_results` を追加**する（§4.1）。
2. **識別キー変更編集で検証結果が失われないようにする**（§4.2）。
3. **コンボ詳細（項目10）に表示と編集導線**を置く（§4.4）。
4. **提案の採用時に「確認できた条件」を記録**できるようにする（§4.5）。
5. **語彙を既存 SSOT に揃える**（§4.6）。

### 1.3 このマイルストーンで作らないもの（スコープ外）

| 項目 | 理由・行き先 |
|------|------------|
| **セットプレイ一覧・検索・エクスポートでの絞り込み** | 対象画面が広がるため**後続サブ**。本サブのデータモデルは絞り込み可能な形になっている（`M19-DESIGN-06` §7-1） |
| **提案ロジックへの反映**（不成立の条件を提案から外す等） | **提案は距離を判定しない**ため接続しない。記録は**絞り込みと表示にのみ使う** |
| **検証日時の保持・パッチ日との突合** | 後続フェーズの範囲（開発者判断 2026-07-26）。**列を先回りして置かない**。必要になれば NULL 可の ALTER 1 本で足せる |
| **セットプレイ編集画面への設置** | **不可**。あの画面は setup 単位で `comboId` を持たず、保存先の行を特定できない（§4.4.1） |
| **`moves` 系の変更**（`startup_basis`・チェーンキャンセル・`fastest_unreachable`） | **M19-04／M19-05**。本サブは `moves` に一切触れない |
| 攻撃種別（シミー・投げ重ね）・DR の軸 | **不要**（開発者確定）。`combo_oki_options` の 12 変種とは目的が異なる |
| `combo_oki_options` の変更 | 触らない。あちらは**コンボが提供する起き攻めオプションの可否**、本表は**特定セットプレイの検証結果**で粒度が違う |

## 4. 詳細仕様

### 4.1 データモデル

#### 4.1.1 新テーブル（CHANGE-087 §2 のとおり）

```
combo_setup_results（セットプレイ成立条件の検証結果）

| カラム    | 型      | 制約     | 説明 |
|----------|---------|----------|------|
| combo_id  | INTEGER | NOT NULL | コンボID |
| setup_id  | INTEGER | NOT NULL | セットプレイID |
| tech_type | TEXT    | NOT NULL | 相手の受け身（'neutral_tech' / 'back_tech'） |
| in_corner | BOOLEAN | NOT NULL | コンボ終了時に相手が画面端にいるか |
| result    | TEXT    | NOT NULL | 検証結果（'ok' / 'ng'） |
| note      | TEXT    | NULL可   | 不成立の理由・補足 |

主キー：(combo_id, setup_id, tech_type, in_corner)
外部キー：(combo_id, setup_id) → combo_setups(combo_id, setup_id) ON DELETE CASCADE
```

- **1 組あたり最大 4 行**（受け身 2 × 端 2）。
- **検証日時の列は持たない**（§1.3）。**timestamps も持たない**（CHANGE-087 §5＝新表 TEXT 統一の既存方針は列自体が無いため非該当）。
- **インデックス**: PK で足りる見込み。組単位の取得が主用途のため。追加が要ると判断した場合は根拠を完了報告に記載する。
- **マイグレは CREATE TABLE のみ・データ移行なし**。down で DROP。**連番は中央払い出し**（着手時に請求）。

#### 4.1.2 値域と語彙

| 列 | 値 | 注意 |
|---|---|---|
| `tech_type` | `neutral_tech` / `back_tech` | **`combo_oki_options` の既存値域を再利用**。**第 3 の語彙を作らない** |
| `in_corner` | 真偽 | **`combos.position` の値を流用しない**。`position` は**コンボ開始位置**、本列は**コンボ終了時**で意味が違う（§3.3-6） |
| `result` | `ok` / `ng` | **`BOOLEAN` にしない**。将来 `unstable` 等を足す余地を残す（DES-003 の既存流儀＝文字列コード値） |

- **値域の正典は本表の定義**（CHANGE-087 §4-1 裁定）。**DES-006 に VAL を足さない。**
- **保存はコード値**。表示ラベルのみ i18n で解決する（§4.6）。

#### 4.1.3 「未検証」の表現（★誤実装しやすい）

- **行が無い＝未検証。行がある＝`result` が成立／不成立。**
- **`result` に NULL を入れて三値を表さない。**
- **「未検証へ戻す」操作は行の物理削除**とする。`result` に「未検証」を意味する値を持たせない。
- §3.3-3 の実査で **CASCADE が期待どおり働かない**（コンボが論理削除される等）と判明した場合は、**孤児行が「未検証でない状態」として残らないこと**を担保する。方式（取得時に `combo_setups` と JOIN して絞る等）は製造が決めてよいが、**判断と根拠を完了報告に記載する**。

### 4.2 ★識別キー変更編集での参照の引き継ぎ

**設計時に見落としていた要件である。実装漏れは「ユーザーが実機で検証した結果が、コンボを編集しただけで消える」というデータ消失に直結する。**

DES-003 §3.15／§3.17 のとおり、**コンボの識別キーを変更編集すると、関連行の `combo_id` が旧→新へ再ポイントされる既存機構**がある（`combo_punishes`／`combo_punish_curations`＝M18-03b、`setups` の `UpdateSetupReferences` と同型）。**`combo_setups` もこの経路に乗っている。**

- **要件**: **識別キー変更編集の前後で、`combo_setup_results` の内容が失われないこと。** `combo_setups` が再ポイントされるなら、**本表も同一トランザクションで整合が保たれること**。
- **実装方式は §3.3-1 の実査結果で決める。** 想定される選択肢:
  - (a) 既存の再ポイント処理に本表を**明示的に追加**する（`combo_punishes` と同じ流儀＝既存パターンへの追従）。
  - (b) FK に **`ON UPDATE CASCADE`** を付けて自動追従させる。※ 親キーが **UPDATE** される場合にのみ有効。DELETE＋INSERT で新 `combo_id` が発番される実装なら**効かない**。
  - **既存の流儀に合わせること**を優先する（新しい仕組みを発明しない）。`combo_punishes` が (a) なら (a) を採る。
- **`ON DELETE CASCADE` は削除しか守らない。** これで足りると判断しないこと。
- **§5.2 に回帰テストを必須で置く**（識別キー変更編集 → 検証結果が新コンボ側で引ける）。

### 4.3 API

#### 4.3.1 取得

**コンボ詳細で組ごとの結果が要る。** 次のいずれかを、**既存の流儀に合わせて**製造が選んでよい（判断と根拠を完了報告に記載）。

- (a) **コンボ詳細のレスポンスに同梱**する（`GET /api/combos/:comboId` の紐づくセットプレイ一覧に各組の結果を含める）。**追加のみの後方互換**とする。
- (b) **専用エンドポイント**（例: `GET /api/combos/:comboId/setup-results`）。

> **(a) を推奨**する。項目10 は**コンボ詳細を開いた時点で全セットプレイ分を表示**するため、(b) だと **N+1 の往復**になる（M19-02 の `alreadyAdopted` で同型の問題があった）。ただし既存のコンボ詳細 DTO が肥大している場合は (b) でよい。

#### 4.3.2 更新

- **1 セルの更新**（`combo_id` / `setup_id` / `tech_type` / `in_corner` を指定して `result` と `note` を設定・または削除）。
- **upsert** とする（行が無ければ作成、あれば更新）。
- **「未検証へ戻す」は削除**（§4.1.3）。
- **紐付けが存在しない組への書き込みは拒否する**（複合 FK が構造的に防ぐが、**API 層でも明示的に弾く**＝多層防御。M19-02 §4.6-2 の `category=system` と同じ流儀）。
- 値域外の `tech_type`／`result` は **400**。

### 4.4 画面：コンボ詳細（DES-005 §5.6 項目10）

#### 4.4.1 ★編集導線をここに置く理由（他所に置かない）

**成立条件は `combo_id` と `setup_id` の両方が無いと保存先の行を特定できない。** セットプレイ編集画面は **setup 単位**で `comboId` を持たない（`setups` は `combo_setups` 経由で複数コンボに紐づく）。**したがってセットプレイ編集画面には置けない。**

> これは **M19-01 で `SetupSelectorModal` が `comboId` を持たず採択保存（VAL-S05）が成立しなかった件と同型の失敗**である（M19-01 完了報告 教訓①＝「UI 相乗り先は名指しの一意性ではなく**必須動線の充足**で確定する」）。CHANGE-087 §2-h が正典に残すよう指定している。**セットプレイ編集画面に置かないこと。**

> **★【2026-08-09 撤回マーカー・D-274】上記は v1（画面名による禁止）の文言であり、現行仕様ではない。** **現行は v3（`DES-005` §5.6）＝「親が確定しているか／同一 Tx でコミットできるか」で判定する。** **同じコンボエディタ上でも、同一 Tx でコミットできる面は v3 で可である**（実例＝**M19-07** のコンボ新規登録）。**本文は当時の指示の記録として残す。**

**項目10（紐づくセットプレイ一覧）は `comboId` を持ち、各行が `setupId` を持つ。両方が揃う唯一の面である。**

#### 4.4.2 表示

各セットプレイの行に **2×2 のグリッド**を併記する。

```
              その場受け身    後ろ受け身
  中央（非端）     ○             ×
  端               ○             —
```

- **`○` 成立／`×` 不成立／`—` 未検証**。
- **記号ではなくアイコンで描く**（`○`/`×` は日本語圏の慣習で、英語圏では `✓`/`✗` が自然。**i18n サーフェスとして扱う**）。
- **凡例を近くに置く**（初見で読めないため）。
- **全 4 セルが未検証なら本要素を出さない**（tags・メディアと同じ hidden-when-empty の流儀＝DES-005 §5.6 項目9）。
- **4 セルの集計（「4 条件中 2 条件で成立」等）は出さない**。条件ごとの可否が意味を持つのであり、集計値に意味はない。

#### 4.4.3 編集

- **各行から編集**（インライン展開またはモーダル。**`comboId` と `setupId` を両方渡す**）。
- 各セルが **3 状態**（未検証 → 成立 → 不成立 → 未検証）を明示的に区別でき、**未検証へ戻せる**こと。**操作形式は既存流儀に合わせて製造が決めてよい**。
- **`note` はセル単位**。選択中のセルに対して入力欄を開く。**成立（`ok`）のセルにも書ける**（「端では距離がシビア」等）。
- 既存の**行クリックでセットプレイ編集へ遷移**する挙動を壊さないこと（項目10 の既存仕様）。編集導線は**それと区別できる操作**にする。

### 4.5 画面：提案の採用ダイアログ（DES-005 §5.6 項目12）

- 採用ダイアログに **「確認できた条件」の 2×2 チェックグリッド**を置く。
- **既定は全て未チェック。チェックせずに採用できる。**
- **チェック＝成立（`ok`）のみを記録**する（開発者確定 2026-07-27）。**不成立（`ng`）と `note` はここでは扱わない**——採用は「使えたから登録する」動作であり、不成立の記録は後から項目10 側で行う。
- 保存は **セットプレイ作成（`setups` ＋ `setup_steps` ＋ `combo_setups`）と同一トランザクション**で行う。**紐付けが作られる前に結果行を書かない**（複合 FK が成立しない）。
- **M19-02 の delivered 契約（名前の自動生成・編集可）を壊さないこと。**

### 4.6 語彙・i18n

- **受け身種別のラベルは既存 SSOT を再利用**する＝`web/src/constants/oki.ts` の **`OKI_TECH_TYPE_LABELS`**（その場受け身／後ろ受け身。DES-005 §5.6 項目6 で正典化済み）。**第 3 の語彙を作らない。**
- **画面端の語彙は新規 2 語**（端／中央）を i18n に足す。**`combos.position` の表示ラベルと矛盾しない**表現にする（§3.3-6）。
- **保存されるのはコード値**。表示ラベルのみ i18n で解決する。**BE で日本語固定文字列を組まない**（`setups.name` で英語 UI に日本語が保存された既知の課題＝M19-01 §3.5 と同じ轍を踏まない）。
- **ja / en parity 必須。**

## 11. 開発者への確認事項

1. **端の語彙**
   何を: 画面端の表示ラベルを「**端／中央**」でよいか。
   なぜ: `combos.position` には `corner_self`（自分が端）／`corner_opponent`（相手が端）の区別がありますが、本表の `in_corner` は「**コンボ終了時に相手が端にいるか**」の真偽 1 本です。ラベルが `position` と紛らわしいと、利用者が別物と気づけません。
   暫定案: **「相手が端」／「中央」**。`position` との違い（開始位置 vs 終了時の相手位置）が伝わる表現にします。

2. **項目10 の情報密度**
   何を: 紐づくセットプレイが多いコンボで、各行に 2×2 グリッドが並ぶと過密になり得ます。**折りたたむ**か、**そのまま出す**か。
   なぜ: 項目10 は M12-02／C-13 で**アコーディオンを廃止して常時展開**にした経緯があります。ここで折りたたみを復活させると、その判断と逆行します。
   暫定案: **そのまま出す**（全 4 セル未検証なら非表示＝hidden-when-empty で密度は抑えられる）。実際に使ってみて過密なら後続で調整。
