## 0. この指示書の特殊性

### 0.1 製造担当として起動 + 調査だけ実施して閉じる運用

本指示書は **調査担当運用パターン**(architecture-patterns v1.0.8 §6)に基づく事実列挙のみの調査依頼。製造担当として Claude Code セッションを起動し、本指示書 §4 の事実列挙を実施 → §5 レポートに記録 → セッションを閉じる。

### 0.2 read-only 厳守

本指示書では **コードの変更は一切行わない**。`view` / `grep` / `git log` / `git blame` などの読み取り系のみを使用。ファイル編集系コマンド(`str_replace` / `create_file` / `bash_tool` の書き込み系)は **使用禁止**。例外は §5 レポートファイル作成のみ。

### 0.3 判断・提案を含めない

調査結果は **事実列挙のみ**。「こうすべき」「こう実装すべき」「この方針が良い」等の判断・提案は含めない(judgement-free)。観察された事実 + 既存コード状態 + 設計書本体規定との比較 = 設計担当が後続マイルストーンの指示書スコープ判断に活用するための情報供給のみが目的。

ただし以下 2 種類は判断 / 提案ではないため記録する:
- **想定外の発見**(想定していなかった事実が見つかった旨): retrospective-log §6.6 + architecture-patterns §6.5 で蓄積された運用知見
- **明らかな矛盾の事実指摘**(設計書本体規定との明確な不整合、コード内のコメントとロジックの矛盾等): 事実として列挙、解釈・解消方針は含めない

### 0.4 本調査の主目的

| 軸 | 主目的 |
|----|--------|
| **§4.1 指摘 1 軸** | ComboDetailPage(または相当画面)でドライブゲージ消費 / SA ゲージ消費の値が表示されない事象の **原因領域を特定**(バックエンドキャッシュ計算 = `drive_gauge_consumed_total` / `sa_gauge_consumed_total` の保存・返却処理 / API レスポンス / フロント側受け取り処理 / フロント側表示処理のどこに問題があるかを事実列挙)|

## 7. 注意事項

### 7.1 read-only 厳守の徹底

本指示書では **コードの変更は一切行わない**。`view` / `grep` / `git log` / `git blame` / `find` / `ls` / SQL の SELECT 等の読み取り系のみを使用。書き込み系コマンド(`str_replace` / `create_file` の対象は §5 レポートファイルのみ、それ以外への書き込みは禁止)。

### 7.2 judgement-free の徹底

調査結果は **事実列挙のみ**。「こうすべき」「こう実装すべき」「この方針が良い」「修正案として」「この問題の原因は」「次のステップとして」等の判断・提案を含めない。

事実列挙の典型例:
- ✅「ComboDetailMetadata.tsx 56-58 行で `props.driveGaugeConsumedTotal` を表示している」
- ✅「GET /api/combos/{id} のレスポンス DTO に `drive_gauge_consumed_total` フィールドが存在する」
- ✅「DES-005 §5.6 item 2 に『ドライブゲージ消費量』の表示規定は存在しない、『ドライブゲージ開始残量』のみ規定されている」(矛盾の事実指摘 = 許容)
- ❌「バックエンド側で再計算する必要がある」(判断 = 禁止)
- ❌「DES-005 §5.6 を改訂すべき」(提案 = 禁止)

### 7.3 設計担当への質問チャネル

調査内容で迷った場合、製造担当(調査担当)は **Plan Mode CLI 直接質問**(playbook v1.9.0 §8.4.1)で開発者を介して設計担当に確認する。直接の Q&A セッションは設けない(playbook §1 役割分離)。
