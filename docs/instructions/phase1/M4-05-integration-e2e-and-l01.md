## 1. 背景と目的

### 1.1 背景

M4-01(setup CRUD バックエンド)、M4-02(setup 単体 UI + 紐付け操作 UI)、M4-03(FR011 転用支援 + knockdown_advantage 確認モーダル)、M4-04(コンボ + セットプレイ同時登録 API DTO 拡張 + UI + フック拡張)がすべて完了承認済み(2026-05-21 時点)。M4 の主要機能はすべて実装完了している。

本指示書では M4 全体の **統合 E2E 確認** と、**持ち越し課題 L-01 / C-1 の解消** を行い、M4 を完了状態にする。M4-overview v1.1.3 §3.6 で M4-04 から分割された仕上げマイルストーン。

### 1.2 目的

- **M4 統合 E2E シナリオの実施**: M4-01〜M4-04 で実装した機能を横断的に検証
  - 個別シナリオ(機能ごとの検証、5〜6 シナリオ)+ ユースケースシナリオ(複数機能を 1 シナリオで横断、3〜4 シナリオ)の併用構成
  - 計 8〜10 シナリオで M4 機能の網羅検証
- **L-01 オプショナル型解消**(m3-to-m4-handover §4.2):
  - `ComboSummary` / `Combo` の `defaultRecipe?: string` / `starterMoveCode?: string` から `?` を外し `string` 型に修正
  - フロント側型定義 + 関連参照箇所の修正(動作リスクなし、バックエンドが常に値を返すため)
- **C-1 持ち越し確認課題の解消**(retrospective-log v1.0.15 §5.5):
  - M4-03 製造担当の連絡事項「PATCH パス(=b 保存方式)にも同条件(KA 変更なし + setup ≥ 1)が該当するため、両パスで implicitCarry 判定を実装」と DES-005 §5.7 (b) 規定「(b) 保存方式は combo_setups 状態変化なし、トースト通知も表示しない」の整合性確認
  - **静的(コード)+ 動的(実機)の併用検証**(M4-10 反省踏襲): 実装ファイルの view + E2E シナリオでの実機検証の両方

- **M4-04 で扱った同時登録機能の機能修正**(本指示書では動作検証のみ、機能修正が必要な場合は別マイルストーンとして起票)

- **新規 UI コンポーネントの実装**(本指示書のスコープ外)
- **L-02(エラーコード文字列大小混在)解消** — M5 以降または M7、CHANGE 通知書必要(m3-to-m4-handover §4.3)
- **L-03(ハンドラエラーヘルパ命名)解消** — M4 各サブマイルストーンで個別判断、本指示書では既存パターン踏襲(m3-to-m4-handover §4.4)

#### 4.2.2 影響範囲の使用箇所修正

§3.3.2 で洗い出した使用箇所で、必須型化により不要になる undefined チェックを削除:


- **動作リスクなし**(m3-to-m4-handover §4.2 規定通り、バックエンドが常に値を返すため)
- **必須型化により可読性向上**(undefined チェーンの削除)
- **テストへの影響**: `defaultRecipe: undefined` を前提とするテストが存在する場合は修正、存在しない場合は追加修正なし

#### 4.2.3 ビルドエラー対応

- **モックデータが defaultRecipe を持っていない**: テストファイルのモックを修正
- **API レスポンスのデシリアライズで undefined が混入**: もし発生したらバックエンド側の確認が必要だが、M3-05 で実装済みのため発生しないはず

## 9. 注意事項・判断に迷ったら

### 9.1 推測で進めてはいけない事項

以下は推測で進めず、Plan Mode で開発者に確認する:

- §3.3.1 `ComboSummary` / `Combo` の現状型定義が想定と異なる場合(例: 既に必須型化されている、または追加のオプショナルフィールドがある)
- §3.3.2 L-01 影響範囲の使用箇所が想定より大幅に多い場合(10 ファイル超等)
- §3.3.3 implicitCarry 判定の実装が DES-005 §5.7 (b) 規定と **重大に乖離** している場合(C-1 検証で不整合発覚)
- §3.3.5 既存フックの queryKey 形式が architecture-patterns.md v1.0.3 §1.1 で記載した実態(combo 系 flat tuple / setup 系 object)と乖離している場合
- E2E シナリオ実施中に重大な不具合(機能ロジックの誤動作、データ破損等)が発覚した場合

### 9.2 推測で進めてよい事項(その旨を明示)

以下は推測で進めてよいが、実装時に「推測:〜と仮定した」とコード内コメントまたは完了報告に明示する:

- L-01 影響範囲の使用箇所での undefined チェーン削除の判断(`?.` を削除すべきか `?.toUpperCase()` を `toUpperCase()` に変更すべきか等)
- E2E シナリオ実施中の軽微な UI 不具合(タイポ、色調整等、機能ロジック変更を伴わないもの)の修正判断
- C-1 検証で軽微な不整合(コメント不足、命名統一等)を発見した場合の対応判断

### 9.3 不明事項発見時の対応

- 設計書本体(DES-005 §5.7)と M4-03 で実装した implicitCarry 判定の挙動が乖離している場合 → 実装を止めて開発者に報告し、対応方針を協議(CHANGE 通知書起票要否含む)
- L-01 型変更で TypeScript の型エラーが大量発生した場合 → エラー箇所を Plan Mode で開発者に報告、優先度を協議
- M3-05 統合 E2E シナリオが回帰している場合 → 実装を止めて開発者に報告し、原因調査と対応方針を協議

### 9.4 Plan Mode で計画提示時に含めるべき項目

Plan Mode 必須:

- §3.3 着手前確認の結果(全 5 項目)
- 特に §3.3.1 L-01 既存型定義の実態、§3.3.2 L-01 影響範囲(ファイル数 + 使用箇所数)、§3.3.3 implicitCarry 判定の実装位置 + DES-005 §5.7 (b) 規定との対照結果
