## 0. 前提となる重要事項

### 0.1 このマイルストーンの位置づけと背景

M7-05 の F-5(L-04 ポート競合)検証で、**フロントが Go に embed/配信されておらず(embed は migrations のみ)、アプリが「Vite dev server(:5173) + Go API + proxy」の 2 プロセス構成でしか動作しない**ことが判明した。これは DES-002 §5.1(dist を embed、未知パスを index.html フォールバック)/ §11(単一バイナリ配布、exe 起動)/ NFR303・NFR304(利用者は exe を起動するだけ)の**配布アーキテクチャが未実装**であることを意味する。

本 M7-06 で **フロント embed + 単一バイナリを成立**させ、**配布構成(embed 済み単一バイナリ + LAN 内スマホ実機)でスマホ LAN 実機検証**を行う。これをもって **M7-06 完了 = フェーズ 1 完了判定** とする(フェーズ 1 完了判定は M7-05 ではなく M7-06 完了時に実施)。

順序: M7-05(機能完了)→ **M7-06(embed + 単一バイナリ + 配布構成 LAN 検証)→ フェーズ 1 完了判定 → handover 作成(設計担当)**。

### 0.2 CHANGE 起票要否

embed / 単一バイナリ配信 / ブラウザ自動起動は **既に DES-002 §5.1 / §11.1 / §11.2 + NFR303/304 に規定済み**。本タスクはそれらの**実装(設計への準拠)**であり設計書本体の変更を伴わない = **CHANGE 不要**。万一、実装過程で DES-002 規定の変更が必要と判明した場合のみ Plan Mode 停止 → 設計担当へ報告(CHANGE 判断)。

## 4. 詳細仕様

### 4.1 go:embed 静的配信 + SPA フォールバック(DES-002 §5.1)

- `web/dist` を go:embed で同梱(Vite 出力に `_`/`.` 始まりファイルがある場合 `all:` プレフィックス考慮)。
- echo で静的配信 + **未知パス → index.html フォールバック**。`/api/*` は静的より優先 or 明確に除外し、API が index.html を返さない/静的が API を飲まないようルーティング順序を担保。
- React Router のクライアントルート(`/combos/:id` 等)を直 URL・リロード・スマホ共有で開いて 200 + index.html。

### 4.2 同一オリジン化(api-client / proxy 両立)

- 配布構成: `API_BASE=""` で同一オリジン直アクセス(proxy 不在)。
- dev 構成: 引き続き Vite proxy 経由(M7-05 で入れた config.toml 追従ロジックは dev 専用として温存。配布構成では経路外)。
- dev 用 CORS / proxy 専用設定が本番で不要/有害でないか点検。

### 4.3 静的アセットの MIME / キャッシュ(§3.4 項目 3 確定方式)

- `assets/` フィンガープリント付きファイルに長期キャッシュ、`index.html` は no-cache。Content-Type 正常。

### 4.4 起動 UX(NFR303/304、DES-002 §11.1)

- 起動時、L-04 で確定した**実ポート**でローカルサーバー起動 → **ブラウザ自動起動**(`github.com/pkg/browser`)。失敗時は起動ログ + コンソールに URL を案内(利用者が実ポートを知らなくても開ける)。

### 4.5 クロスコンパイル + 配布物(§3.4 項目 5/7 確定範囲、DES-002 §11.2)

- 最低限ホスト OS 向けに単一バイナリを `go build` し起動・配信確認。Windows 公式 + macOS/Linux 非公式のビルド成立は確定範囲で確認。

### 4.6 配布構成検証 + スマホ LAN 実機(DES-002 §14)

- embed 済み単一バイナリで配布構成スモーク(§3.4 項目 6 範囲)。
- **スマホ LAN 実機検証**: 開発者がホスト OS で単一バイナリを実行 → LAN 内スマホ実機から同一サーバーへアクセスして主要機能確認(M7-05 で配布構成では未実施だった分)。製造担当は手順整備 + 開発者結果の取りまとめ。

### 4.7 F-5 手順整合

- `m7-integration-e2e-results.md` の F-5 手順を配布構成(`http://localhost:<actual_port>/` 直アクセス)に整合(M7-05 Q3 保留分)。

## 8. 注意事項・判断に迷ったら

### 8.1 Plan Mode 停止が必須のケース

- DES-002 規定の変更が必要と判明(CHANGE 判断、設計担当報告)
- スキーマ変更が必要と判明
- embed 化で既存 API/ルーティングに想定外の干渉(SPA フォールバックが /api を飲む等)

### 8.2 設計担当の判断意図(製造担当が誤解しやすい点)

- **embed は dev の置き換えではない**。dev は Vite HMR(proxy 経由、M7-05 の config.toml 追従ロジック温存)、配布は embed 単一バイナリ、の**二系統が両立**することがゴール(§3.4 項目 1 で「dev/embed の区別」を 1 行明記する開発者方針と整合)。
- **SPA フォールバックの /api 除外が最重要の落とし穴**。ルーティング順序を誤ると API が index.html を返す/静的が API を飲む事故になる。
- **「exe 起動だけで使える」= ブラウザ自動起動 + 実ポート連携が UX の肝**(NFR303/304)。利用者は L-04 で変わった実ポートを知らないため、自動起動 or 明示案内が必須。

### 8.3 CHANGE 起票判断

- 通常は不要(embed は既に DES-002 規定、実装 = 準拠)。DES-002 規定の変更が必要な場合のみ設計担当が CHANGE 判断(製造担当は起票しない)。
