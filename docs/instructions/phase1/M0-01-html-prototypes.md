## 1. 背景と目的

### 背景

本プロジェクト(SF6コンボ管理アプリ)は設計書一式が完成し、これから実装フェーズに入る。いきなりReactコンポーネントで画面を実装するのではなく、**HTML+CSSのプロトタイプを先行して作成**し、画面の見た目・レイアウト・情報密度をMIの段階で検証する。

### 目的

- 画面設計書(DES-005)で論理的に定義された16画面のうち、主要10画面について視覚的なモックアップを作成する
- 本番Reactコンポーネント実装の前に、開発者がレイアウトの違和感・情報過多・余白バランス等を確認できるようにする
- 開発者レビュー後、このプロトタイプを基準にM1以降のReact実装を進める
- プロトタイプはフェーズ1完了時(M7後)に削除する(git履歴には残る)

### このプロトタイプで目指すレベル

**「中程度」の完成度** — レイアウトと構造を本番相当に固めつつ、細部の色調整や最終的なUIポリッシュは本実装側で行う。具体的には:

- レイアウト・要素配置・情報階層は本番相当
- タイポグラフィと間隔は妥当な初期値を設定
- 色はTailwindの標準パレットから無理なく選ぶ(本番デザインで最終調整する前提)
- 影・遷移・アニメーション等のポリッシュは不要

## 4. 詳細仕様

### 4.1 技術スタック(プロトタイプ専用、本番とは独立)

| 項目 | 内容 |
|------|------|
| HTML | HTML5、各ファイル単体で動作 |
| CSS | **Tailwind CSS CDN版**(`<script src="https://cdn.tailwindcss.com"></script>`) |
| JS | 最小限。クリックで別HTMLに遷移する `<a>` リンクのみ可。本格的な動作(フォーム送信、計算、API等)は実装しない |
| アイコン | Lucide のSVGを必要時にインラインコピーで使用、または Unicode記号(▼、✓、×、📋等)で代替 |
| shadcn/ui | **使用しない**(本番React実装で使用) |
| 静的データ | 各HTMLファイル内に直接記述(JSON分離しない) |

### 4.2 レイアウト方針

#### PC想定画面(9画面)

- 幅 1280px 程度の画面を主要ターゲットとする(`max-w-7xl` 中央寄せ等を活用)
- ヘッダ・サイドバー・メインコンテンツの3ペイン構成を基本とする(DES-005 §4 のグローバルUIに基づく)
- スマホで見ると崩れるが、プロトタイプ段階では許容する

#### スマホ専用画面(1画面: home-mobile.html)

- 幅 375〜414px(iPhone SE〜iPhone Pro Max相当)を想定
- ビューポート設定: `<meta name="viewport" content="width=device-width, initial-scale=1">`
- 大きなタップ領域、縦スクロール前提のレイアウト
- ブラウザを縮小して見た時に、スマホらしく見えれば OK

### 4.3 各画面の仕様

各画面について、以下を遵守すること。

#### 4.3.1 コンボ一覧(`combo-list.html`)— DES-005 §5.4 参照

**表示要素:**

- ヘッダ(アプリ名、現在キャラクター表示、言語切替UI、設定への導線)
- 現在選択中キャラクター情報バー(キャラクターアイコン+名前を目立つ形で表示。プロトタイプではリュウ固定で良い)
- フィルタ・ソート領域:
  - キャラクター選択プルダウン(プロトタイプではリュウのみ表示で良いが、UIとしては選択可能に見えること)
  - タグフィルタ(複数選択可)
  - 状況フィルタ(position、hit_type、opponent_stance 等)
  - 仮登録表示トグル(仮登録のみ/全て/本登録のみ)
  - ソート指定(更新日時、ダメージ、ステップ数、始動技、ドライブゲージ消費、SAゲージ消費)
  - 表示列のカスタマイズUI(各列の表示/非表示切替、Excel風)
- コンボリスト(**ツリー構造**):
  - 各コンボ行の項目(横並び): 展開アイコン(▶/▼、セットプレイ紐付け時のみ)、ダメージ、ステップ数、ルート(レシピ文字列、長い場合は省略表示)、タグ、状況アイコン、仮登録バッジ(該当時)、アクションアイコン(編集/コピー/削除)
  - **セットプレイ展開時の表示形式(重要)**: コンボ行の直下にインデント付きでセットプレイ行を表示。表示例:
    ```
    ▼ コンボA    [ダメージ/ステップ数/ルート]
      └ セットプレイ1  [レシピ]
      └ セットプレイ2  [レシピ]
    ▶ コンボB    [ダメージ/ステップ数/ルート]
    ```
- 新規登録ボタン(右上)
- 選択モードトグル(複数選択→比較画面への導線)

**ルートの省略表示:** DES-005 §5.4 で複数の選択肢が示されているが、プロトタイプではいずれか1つの方式を採用する(末尾省略+ホバー全文、前方優先表示、始動+締め残し中略、等)。判断はClaude Codeに委ねるが、Plan Modeで採用方式を提示すること。

**ダミーデータ:**

- **リュウのコンボを15件**程度ハードコーディング
- うち**3件はセットプレイ展開済み(▼)**で、その下にインデント付きで**セットプレイ2〜3件**が表示されている状態にする(ツリー構造を視覚的に確認できるよう)
- うち2件はセットプレイ紐付けあり(▶折りたたみ状態)
- うち2件は仮登録(仮登録バッジ表示で識別)
- ダメージ、ゲージ消費等は SF6 の実データに近い範囲(ダメージ 800〜3500、ドライブゲージ -2〜+1 等)
- タグは「使用中」「練習中」「頻度低下」から複数組合せ
- セットプレイ行のレシピも実態のある内容(例:「前ジャンプ中K」「投げ間合い前歩き」等)

#### 4.3.2 コンボ詳細(`combo-detail.html`)— DES-005 §5.6 参照

**表示要素:**

- 上部: キャラ、状況(position/opponent_stance/hit_type/opponent_size)、ダメージ、ドライブゲージ消費、SAゲージ消費、タグ、メモ
- レシピ表示エリア: プリセット切替UI + レシピ本体(技名を矢印で繋いだ形式、DES-004 の表記に準拠)
- プリセット切替で表示が変わるイメージを見せるため、サンプルとして `official_ja_move` 選択時の表示を想定
- セットプレイ展開エリア: **3件程度のセットプレイを展開表示**(名前、レシピ、ノックダウン有利フレーム、メモ)
- アクション(編集、コピー、削除、戻る)

**ダミーデータ:**

- 代表的なリュウのコンボ1件分(例: `stand_light_punch > stand_medium_punch > hadoken_medium`)
- セットプレイは 3件(例: 入れ替え前提の垂直ジャンプ、起き上がりへの投げ、遠ざかりからの前ジャンプ中K等)
- セットプレイ名がNULLのケースも1件含める(SUPP-001 §2.4 フォールバック表示の確認、「レシピ先頭30文字 + …」形式)

#### 4.3.3 コンボ登録・編集(`combo-editor.html`)— DES-005 §5.7 参照

**重要:** 本プロトタイプでは**仮想コントローラを取り扱わない**(DES-005 §5.7 で4種類の仮想コントローラが定義されているが、見た目の確定はM1以降で開発者と協議しながら行う)。プロトタイプではレシピ入力の枠と、レシピ確認エリアの表示イメージのみを示すに留める。

**表示要素:**

- 基本情報入力エリア(キャラ、状況コード各種、タグ付け、メモ、ダメージ、ゲージ消費)
- レシピ入力エリア:
  - 「ここに仮想コントローラが配置される(M1で実装)」というプレースホルダ枠を矩形で配置(高さ300px程度、グレー背景に説明テキスト)
  - **仮想コントローラそのものは作らない**
- レシピ確認エリア(構築済みレシピの表示):
  - 順番に並ぶステップを矢印で繋いだ形式で表示
  - 各ステップに削除アイコン、並び替えハンドル
  - 空の挿入位置(「+」アイコン等)の表示イメージ
- 保存/キャンセル/下書き保存ボタン
- 重複チェック警告の**表示イメージ**(ダミー警告として「同一レシピのコンボが既に存在します」の例示を1件入れる)
- セットプレイ同時登録セクション(DES-005 §5.7)

**ダミーデータ:**

- 編集画面として「編集中の既存コンボ」をロードしたようなダミー状態で表示する
- レシピは3〜5ステップ程度を確認エリアに表示(例: `立ち弱P > 立ち中P > 波動拳・中`)

#### 4.3.4 マイコンボ(`my-combo.html`)— DES-005 §5.5 参照

- 基本はコンボ一覧と同じ構造、ただしタグフィルタが主役
- タグ選択UIが画面上部に大きく出ている
- 選択中タグに応じた絞り込み結果が見えるイメージ

**ダミーデータ:** コンボ一覧と同じデータを流用可。タグ「使用中」で絞った状態を表示。

#### 4.3.5 セットプレイ登録・編集(`setup-editor.html`)— DES-005 §5.9 参照

**重要:** §4.3.3 と同様、本プロトタイプでは仮想コントローラを取り扱わない。

**表示要素:**

- セットプレイ名(任意入力、空OK)
- 親コンボ選択(複数紐付け可能、多対多)
- レシピ入力エリア(仮想コントローラのプレースホルダ枠のみ、§4.3.3 と同様)
- レシピ確認エリア(構築済みレシピの表示)
- ノックダウン有利フレーム入力
- メモ
- 保存/キャンセル/下書き保存ボタン

**ダミーデータ:** セットプレイ1件分の編集状態。

#### 4.3.6 コンボ比較(`combo-compare.html`)— DES-005 §5.8 参照

- 3件のコンボを横並びで比較するイメージ
- 各列に: レシピ、ダメージ、ゲージ消費、状況、セットプレイ有無
- 差分を視覚的に強調する(ダメージの大小で色分け等)

**ダミーデータ:** 上記一覧と整合するリュウのコンボ3件を並列表示。

#### 4.3.7 設定(`settings.html`)— DES-005 §5.16 参照

- セクション分割: 言語、デフォルト表示キャラ、LAN共有、パスワード、バックアップ、表示設定等
- 各設定項目の見せ方(トグル、プルダウン、テキスト入力)が分かる状態

**ダミーデータ:** 初期値として妥当な状態を表示。

#### 4.3.8 初回起動ウィザード(`first-run-wizard.html`)— DES-005 §5.1 参照

**プロトタイプの方針:** 全ステップを縦に並べるのではなく、**代表1ステップ「ユーザー名入力ステップ」のみ**を画面として作成する(SUPP-001 §2.5 で新設されたステップであり、視覚化の必要性が高いため)。

**表示要素:**

- ステップインジケータ(「ステップ X/Y」、現在ステップが「ユーザー名入力」であることを明示)
- ユーザー名入力フィールド:
  - ラベル「ユーザー名(任意)」
  - 入力欄(空欄でも次に進める旨をプレースホルダで明示、例: 「空欄の場合は default が設定されます」)
  - 補助テキスト(「後から設定画面で変更できます」等)
- 「戻る」「次へ」ボタン
- 必要に応じて、画面上部にウィザード全体の進行状況(他ステップ名の薄い表示)を含める

**ダミーデータ:** ユーザー名フィールドは空欄状態で表示(初期状態を示す)。

#### 4.3.9 ホーム(スマホ専用)(`home-mobile.html`)— DES-005 §5.2 参照

- **本プロトタイプ唯一のスマホレイアウト**
- 375〜414px 幅を想定
- 大きなボタン(コンボ一覧、マイコンボ、設定等)を縦積みで配置
- 現在キャラ表示、ユーザー名表示等の上部エリア
- PCブラウザで閲覧時も、縮小して見ればスマホらしく見える状態

#### 4.3.10 ゴミ箱(`trash.html`)— DES-005 §5.15 参照

- 論理削除されたコンボ・セットプレイの一覧
- 各行に「復元」「完全削除」ボタン
- 削除日時表示
- 一覧はコンボ一覧と似た形式だが、アクションが異なる

**ダミーデータ:** ゴミ箱内コンボ5件程度、セットプレイ2件程度。

### 4.4 index.html(プロトタイプ一覧)

- 10画面へのリンクを一覧表示
- 各リンクに画面名、DES-005 の参照節番号、簡単な説明を付ける
- 開発者がプロトタイプ全体を俯瞰できる入口とする

### 4.5 共通ルール

- 全画面共通のヘッダ・ナビゲーションはどの画面でも同じ見た目にする(コード重複OK、プロトタイプなので)
- ただし `_shared.css` に共通スタイルを切り出すのも可(Tailwindで間に合うなら不要)
- 日本語UIで作成。i18n対応は不要
- フォントは `system-ui, -apple-system, "Segoe UI", "Noto Sans JP", sans-serif` 等、OS標準日本語フォントを想定
- カラーは Tailwind パレットから:
  - プライマリ: blue-600 前後
  - アクセント: emerald(使用中タグ色)、amber(仮登録)、slate(通常テキスト)
  - 背景: white / slate-50 / slate-100
  - テキスト: slate-900(主要)、slate-600(補助)

## 6. レビュー観点(品質レビュー担当Claude向け)

**本セクションの位置づけ:** 本プロジェクトは **並列レビュー運用**を採る(SUPP-001 §6.6)。すなわち、開発者の目視レビュー(「一目で違和感があるか」を見る短時間チェック)と、品質レビュー担当Claude(別チャット)による独立した品質レビューを**同時並行**で進める。本セクションのチェックリストは主に**品質レビュー担当Claude向け**であり、開発者は通読する必要はない(必要に応じて参照する程度)。

### 設計準拠性

- [ ] DES-005 の各画面で定義された**表示項目**が全て存在するか
- [ ] DES-005 の各画面で定義された**アクション**が UI として存在するか(機能しなくて良いが、ボタン等の存在は必要)
- [ ] DES-005 §5.4 のツリー展開構造が `combo-list.html` に反映されているか(▼展開状態で3件、▶折りたたみ状態で2件等)
- [ ] SUPP-001 §2.5(初回起動ウィザードの**ユーザー名入力ステップ**)が `first-run-wizard.html` の代表1ステップとして実装されているか
- [ ] SUPP-001 §2.4(setup name NULL時のフォールバック表示例)が `combo-detail.html` に含まれているか
- [ ] SUPP-001 §4.1 の M0 規定(`web/prototypes/` 配下、10画面)に従っているか
- [ ] **仮想コントローラはプロトタイプの対象外**であり、`combo-editor.html` および `setup-editor.html` でプレースホルダ枠のみ表示されているか(本物のコントローラUIを作っていないか)

### レイアウト品質

- [ ] 情報階層が視覚的に明瞭か(重要情報が目立つ、補助情報が控えめか)
- [ ] 余白・行間・フォントサイズが読みやすいか
- [ ] 画面幅 1280px 想定で主要9画面が破綻なく表示されるか
- [ ] home-mobile.html が幅 400px で破綻なく表示されるか

## 9. 注意事項・判断に迷ったら

### Plan Mode の使い方

本指示書は **Plan Mode 必須**。着手前に以下を含む計画を提示すること。

1. 作成する10画面の作業順序(依存関係を考慮)
2. 各画面の主要要素の洗い出し(DES-005 からの抽出結果)
3. 共通スタイル・共通コンポーネント(ヘッダ等)の扱い
4. ダミーデータの準備計画
5. 想定所要時間の見積もり

開発者が計画を承認してから実装に入ること。

### 不明点が発生した場合

HANDOVER-001 §4.1 に従い、以下のいずれかで対応する。

- 推論で決めた場合: コード内コメントまたは Claude Code の出力メッセージで「推測:〜と仮定した」と明示する
- 設計書で複数解釈可能な箇所: 開発者に選択肢を提示してから進める
- 「実装時協同で決定」とされている事項: 開発者確認必須

### 本指示書がカバーしない事項

以下は本指示書のスコープ外。もし必要と判断した場合は開発者に確認すること。

- React コンポーネント化(M1以降)
- API 呼出・データ永続化(M1以降)
- テスト自動化(プロトタイプはテスト不要)
- 残り6画面(ユーザー選択、プリセット一覧、プリセット編集、タグ管理、エクスポート、インポート)のプロトタイプ化 — これらは必要性が見えた時点で別指示書で追加検討

### 禁止事項(`.claude/CLAUDE.md` 発行後は常時適用、本プロジェクトでも適用)

- `localStorage` / `sessionStorage` / `IndexedDB` 等のブラウザストレージ使用禁止
- Git 操作(commit、push 等)は開発者のみ、Claude Code は変更提案に留める
- `rm -rf /` 等の危険なシェル操作禁止
