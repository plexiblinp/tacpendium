## 0. レビュー担当の作業手順

1. 本ファイル、対象指示書本体、CLAUDE.md、SUPP-001、DES-003 §3.4-§3.5、DES-006 §1-§2 を読む
2. 製造ターミナルで作成されたファイル群を `view` ツールで読む
3. 下記チェックリストに沿ってレビュー実施
4. レビュー結果を `docs/progress/m1-03-review.md` に出力

**重要ルール:**

- コードは一切変更しない
- ファイル作成は `docs/progress/m1-03-review.md` のみ
- Git 操作はしない
- 不明点があれば報告書に記載し、推測で進めない

---

## 1. 設計準拠性

- [ ] DES-006 §2 の VAL-C01〜VAL-C12 が全て実装されているか
- [ ] SUPP-001 §2.1 仮登録のNULL許容ルール(VAL-C09スキップ等)が実装されているか
- [ ] SUPP-001 §2.2 重複判定がリスト定数で定義され、modifiers含む完全一致になっているか
- [ ] HANDOVER-001 §3.1 編集方式分離(PATCH/PUT)が実装されているか
- [ ] PUT 時に旧コンボ論理削除 + 新作成 + セットプレイ引き継ぎが実装されているか
- [ ] NFR203 楽観的排他制御(version カラム + UPDATE WHERE version=?)が実装されているか
- [ ] SUPP-001 §5.1 APIレスポンスに `move_id` と `move_code` 両方が含まれているか
- [ ] SUPP-001 §2.3 recipe_cache 関連は M1-04 への TODO として明示されているか
- [ ] 起き攻めBOOLEAN が **6カラム**(CHANGE-001、7カラムでない)
- [ ] opponent_stance に `any` が許容値に含まれているか(CHANGE-003)

## 2. コード品質

- [ ] エラーラップが `fmt.Errorf("...: %w", err)` 形式
- [ ] `context.Context` がサービス層・リポジトリ層の全公開メソッドに引数として存在
- [ ] 公開関数に godoc コメント
- [ ] ハンドラ層がビジネスロジックを持たず、サービス層に委譲しているか
- [ ] リポジトリ層が SQL のみを扱い、ビジネスロジックを持っていないか
- [ ] DTO ↔ モデル変換が適切に分離されているか
- [ ] SQL Injection 対策(全クエリでプレースホルダ `?` 使用)

## 3. テスト網羅性

- [ ] サービス層のテストが SUPP-001 §5.5 の「必須」レベルを満たしているか
- [ ] VAL-C01〜VAL-C12 全てに対応するテストケースがあるか
- [ ] 重複判定の正常系・異常系・エッジケース(modifiers キー順違いで同一ハッシュ)がテストされているか
- [ ] テストが他のテストに影響を与えないか(各テストで独立DB)
- [ ] 楽観的排他衝突のテストケースがあるか
- [ ] PUT(キー変更編集)で旧コンボ論理削除+新作成+セットプレイ引き継ぎが確認されているか

## 4. API設計準拠

- [ ] 7エンドポイント(POST/GET/GET-list/PATCH/PUT/DELETE/POST-restore)が実装されているか
- [ ] エラーレスポンス形式が統一されているか(`error`、`message`、`validations` キー)
- [ ] HTTPステータスコードが妥当(201 新規、204 削除、400 バリデーション、404 不在、409 楽観衝突、500 内部)

## 5. 禁止事項

- [ ] `localStorage` 等のフロント禁止項目に触れていないか
- [ ] `console.log` / `fmt.Println` の本番コード残存がないか
- [ ] Git 操作の Bash 実行がないか
