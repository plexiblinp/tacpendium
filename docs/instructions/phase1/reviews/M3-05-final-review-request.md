## 3. 最終総合レビューで重点的に確認いただきたい観点

初回レビューチェックリスト v1.0.0 §0〜§12 のすべてを再確認することを前提に、以下を **重点観点** として特に意識的に評価してください。

### 3.A. 初回レビューで見落とされた観点の網羅性確認(最重要)

#### 3.A.1 必須テストの実装状況の再確認

レビューチェックリスト v1.0.0 §4.3 / §5.1.3 で「必須テスト」と明記されている項目を、**指示書本文と一行ずつ照合**してください。M-01 が初回レビューで見落とされた事実を踏まえ、他に同種の見落としが残っていないか確認することが目的です。

特に以下のテストファイルが、指示書要求項目を網羅しているか:

- `internal/model/api_error_test.go`(指示書 §4.5.6 / §5.1.1)
- `internal/api/tag/handler_test.go` / `internal/api/character/handler_test.go` / `internal/api/combo/handler_test.go`(指示書 §4.5.5 / §5.1.2)
- `internal/service/combo/service_test.go`(M-01 追加後)
- `internal/repository/combo/repository_test.go`(M-01 追加後)
- `web/src/features/combo/components/RecipeBuilder.test.tsx`(指示書 §4.4 → 製造担当判断で未実装、P-01 として持ち越し)
- 空状態メッセージ改善のテスト(指示書 §5.1.4)

各テストファイルで、指示書が要求した「ケース」が **テスト関数として実体化されているか** を確認してください。テストファイルが存在するだけでは不十分で、要求されたケース数・観点が網羅されている必要があります。

#### 3.A.2 指示書 §2.1 / §2.2 のファイル一覧との整合

指示書で「作成する」「修正する」と明記されたファイルがすべて実装されているかを、再度 grep で確認してください。製造担当が 5 ハンドラ統一(2-C)で preset / move を追加した影響で、指示書記載の 3 ハンドラ以外の修正があったはずです。修正範囲が **製造担当の実装報告書と整合** しているかも確認してください。

#### 3.A.3 指示書 §7「完了条件」のチェック項目との一対一対応

レビューチェックリスト §1〜§8 の各項目が、指示書 §7 の DoD と一対一対応しているかを確認してください。M-01 が見落とされた原因の一つは、「§5.1.3 必須テスト」と「§7 DoD」の連動が緩かった可能性があります。

### 3.B. 製造担当の指示書逸脱判断 5 件の妥当性確認

製造担当の判断 2-A〜2-E は設計担当が追認しましたが、レビュー担当として **技術的妥当性** を独自に評価してください。設計担当の判断追認とは別軸の評価が必要です。

#### 3.B.1 2-A: recipe_cache 活用方式

- 指示書 §4.1 が「案 Y(サービス層で生成)」を推奨していたが、製造担当は「recipe_cache 活用」を選んだ
- **評価観点**: (i) 既存の `recipe_cache` のメンテナンス責務(SUPP-001 §7.2)を破壊していないか、(ii) `defaultPresetID = "1"` の暗黙前提がハードコードされている箇所の保守性、(iii) `recipe_cache` の NULL / 空文字 / パース失敗時のフォールバック挙動が安全か
- M-01 のサービス層テスト追加で正常系・異常系が網羅されるはずなので、テスト網羅後に再評価してください

#### 3.B.2 2-B: Validations の Details 格納方法

- `map[string]any{"validations": result}` 形式は CHANGE-010 §2.1 の設計範囲内
- **評価観点**: (i) フロント側で `error.details.validations.issues[*].field` / `message` を正しくパースできているか(M3-05 §4.5.4 後方非互換変更の修正範囲内か)、(ii) 型安全性のトレードオフは将来のリファクタで解消可能な範囲か(handover 記録方針で十分か)

#### 3.B.3 2-C: 5 ハンドラ全統一

- 指示書スコープは 3 ハンドラ(tag / character / combo)、製造担当が preset / move を追加
- **評価観点**: (i) preset / move ハンドラの修正が他の機能に回帰を起こしていないか(M0〜M2 の preset / move 関連機能の動作確認)、(ii) 5 ハンドラすべてで JSON 構造が完全に同一形式で返ることの確認(レビューチェックリスト §2.3 の curl 拡張)

特に **playbook §4.7 全ハンドラ列挙原則** の適用範囲が指示書記載より広かった事実は、設計担当のミスでもあります。製造担当が現場判断で正しく拡張してくれたことを、レビュー担当としても確認・追認してください。

#### 3.B.4 2-D: RecipeBuilder console.warn 未実装

- 指示書 §4.4 が要求した実装・テストが取り込まれていない
- 製造担当の判断: M2-04 の実際の実装が視覚的 UI 警告のみで、`console.warn` は実装されていなかったため、指示書の前提が誤っていた
- **評価観点**: (i) 既存テスト 4 ケース(M2-04 由来)が回帰せず通過しているか、(ii) この未実装を「重大判定」とせず別マイルストーンに送ることが妥当か、(iii) 指示書の前提誤りが他の節にも波及していないか(指示書 §4.4 以外で M2-04 実装内容に依存する記述がないか)

レビュー担当として、これを **M3-05 完了承認の妨げにしない判断** を独自に確認してください。設計担当の追認と同じ結論なら承認、結論が異なる場合は理由を報告してください。

#### 3.B.5 2-E: ComboSummary と Combo の型分岐

- フロント側で `ComboSummary`(一覧用)と `Combo`(詳細用)が別 interface
- 両方に `defaultRecipe` / `starterMoveCode` が追加されている
- **評価観点**: (i) 両 interface への追加が完了しているか(コンボ詳細画面・コンボ編集画面で型エラーが発生していないか)、(ii) フロント型定義ファイル冒頭にコメント明記が推奨されたが、製造担当がコメント追加を完了しているか(任意項目だが、追加されていれば加点)

### 3.C. M-01 テスト追加完了後の動作確認

製造担当の M-01 完了報告を受け取った後、以下を確認してください:

#### 3.C.1 追加テストの実装妥当性

## 6. 補足: レビュー担当の判断尊重

本最終総合レビューは「初回レビューで見落とした観点を網羅する」目的ですが、初回レビューで承認した範囲を全否定する意図ではありません。

製造担当の現場判断(2-A〜2-E)を設計担当が追認した経緯は、レビュー担当の独自評価で **追認不可** と判定する余地があります。その場合、本メッセージの §3.B の各観点で具体的に「なぜ追認不可か」を技術的根拠とともに報告してください。

レビュー担当の判断は設計担当・開発者の判断と独立しています。重大な問題を見つけた場合は遠慮なく報告してください。
