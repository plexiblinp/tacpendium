## 0. レビュー担当への前置き

### 0.1 準備

- [ ] M7-06 指示書 v1.0.0 通読(特に §3.4 dev/embed 両立方式、§8.2 設計担当の判断意図)
- [ ] DES-002 §5.1 / §11.1 / §11.2、NFR303/304 を参照可能にする
- [ ] `git diff` で変更把握、Plan Mode 確定事項(dev/embed 両立方式・起動 UX・キャッシュ戦略)を確認

### 0.2 基本姿勢

- 本タスクは **配布アーキテクチャ(単一バイナリ)の成立**。「dev が引き続き動く」かつ「配布構成で全機能が同一オリジンで動く」の**両系統成立**を確認。
- **embed 特有の落とし穴**(SPA フォールバックが /api を飲む、静的キャッシュ過多で更新反映されない、同一オリジンで api-client が壊れる、実ポートが利用者に伝わらない)を重点的に。
- スキーマ変更が混入していないか。

### 0.3 報告フォーマット

- 冒頭に「単一バイナリ起動・配信の成否」「dev 構成の継続動作」「配布構成スモーク結果」を要約。重大(§8)/ 軽微(§9)を一覧。

---

## 1. SPA フォールバック + ルーティング(最重要の落とし穴)

- [ ] 未知パスが index.html にフォールバックする(DES-002 §5.1)
- [ ] **`/api/*` がフォールバックに飲まれていない**(API パスは静的より優先 or 明確に除外。API が index.html を返さない、静的が API を飲まない)。ルーティング登録順序を確認
- [ ] React Router の直 URL / リロード / スマホ共有リンク(`/combos/:id` 等)で 200 + index.html が返る
- [ ] 存在しない静的アセット(`/assets/xxx`)が index.html を返して 200 化していないか(本来 404 が望ましいケースの扱い)

## 2. 同一オリジン化 + dev proxy 両立

- [ ] 配布構成で `API_BASE=""` 同一オリジン直アクセスが動作
- [ ] **dev 構成(Vite + proxy)が引き続き動作**(M7-05 の config.toml 追従ロジックが温存され、dev で壊れていない)
- [ ] dev 用 CORS / proxy 専用設定が本番(同一オリジン)で不要/有害になっていないか(過剰な CORS 許可が残っていないか)

## 3. 静的アセットの MIME / キャッシュ

- [ ] JS/CSS/フォント等の Content-Type が正しい
- [ ] `assets/`(フィンガープリント付き)に長期キャッシュ、`index.html` は no-cache(SPA 更新が反映される)

## 4. dev / embed 両立方式

- [ ] §3.4 項目 1 で確定した方式(placeholder dist commit / build タグ / その他)で実装され、**`web/dist` 不在/空でも開発フローが破綻しない**(go build が意味のあるエラー or 成功する)
- [ ] dev と embed の区別が 1 行以上明記されている(開発者方針)

## 5. 起動 UX(NFR303/304、DES-002 §11.1)

- [ ] 起動時に L-04 実ポートでローカルサーバーが立ち上がる
- [ ] **ブラウザ自動起動**(`github.com/pkg/browser`)が実ポートで動作。失敗時は起動ログ + コンソールに URL 案内(利用者が実ポートを知らなくても開ける)
- [ ] ポートフォールバック(L-04)発生時も自動起動 URL が実ポートに追従

## 6. クロスコンパイル + 配布物

- [ ] 最低限ホスト OS 向けに単一バイナリが `go build` でき起動・配信する
- [ ] §3.4 項目 5 確定範囲のクロスビルド成立(Windows 公式 + macOS/Linux 非公式のビルドが通る範囲)
- [ ] §3.4 項目 7 で README.txt を作る判断なら、起動方法・注意事項が記載されている

## 7. 既存非破壊・スキーマ非変更

- [ ] `go test ./...` / `npm test`(`pnpm test`)が全パス(embed 追加で既存テストが壊れていない)
- [ ] **スキーマ変更なし**(embed は配信層の話。ALTER TABLE 等が混入していない)
- [ ] 既存 API の挙動・レスポンスが embed 化で変わっていない

## 8. 配布構成検証

- [ ] embed 済み単一バイナリで配布構成スモーク(§3.4 項目 6 範囲、全機能 or 主要パス)
- [ ] **スマホ LAN 実機検証の手順整備 + 開発者結果の取りまとめ**(DES-002 §14「同一サーバーへ」。コード上判定不能部分は開発者実機結果待ち)
- [ ] F-5 手順が配布構成(`http://localhost:<actual_port>/` 直アクセス)に整合

## 9. 重大な問題の判定基準(完了承認を妨げる)

- SPA フォールバックが `/api/*` を飲む / API が index.html を返す
- 配布構成で全機能が動かない(同一オリジンで api-client が壊れる等)
- dev 構成が壊れた(Vite + proxy で動かなくなった)
- ブラウザ自動起動が実ポートに追従しない(利用者が開けない)
- ビルド / `go test` / `npm test` 失敗、スキーマを Plan Mode 停止なしに変更
- スコープ外(新機能/フェーズ2-3先行/インストーラ/実リリース)に着手

## 10. 軽微な問題の判定基準(持ち越し許容)

- クロスビルドの非公式 OS(macOS/Linux)の実機起動未確認(ビルド成立まででよい、§11.1 非公式)
- README.txt の詳細度(§3.4 項目 7 で最小限/送りと確定した範囲)
- CI(§11.3)整備の有無(Plan Mode で本タスク範囲外と確定した場合)

## 11. 質問・確認のフォーマット

判断に迷ったら Plan Mode CLI 経由で設計担当に質問(直接 Q&A なし)。「観点番号 + ファイル/行 + 事実 + 迷っている点」を明記。特に (a) SPA フォールバックと /api の干渉、(b) dev/embed 両立で開発フローが壊れる懸念、(c) DES-002 規定の変更が必要そうな場合 は重大問題候補として明示報告。

- [ ] §5 起動 UX(ブラウザ自動起動 + 実ポート追従)= NFR303/304 を確認
- [ ] §7 既存非破壊・スキーマ非変更・全テストパス
- [ ] §8 配布構成スモーク + スマホ LAN 実機検証(開発者結果取りまとめ)
- [ ] スコープ外への変更なし(§9)、フェーズ 1 完了判定 + handover は設計担当作業として残置
