## 0. レビュー担当への前置き

本チェックリストは M2-01 指示書(`docs/instructions/M2-01-virtual-controller-and-modifiers.md`、v1.2.0)に対するレビュー観点を整理したものである。レビュー担当 Claude Code は以下のフローでレビューを進める。

### 0.1 レビュー前の準備

1. M2-01 指示書(本指示書本体)を一読する
2. 製造担当の実装完了報告(自己テスト結果、E2E 動作確認手順書、§3.4 確認結果)を確認する
3. 関連する設計書を確認する(必読: DES-005 §6.2 / §6.7、SUPP-001 §3.3.0〜§3.3.4、M1-06 §4.3 / §4.4。レビュー観点ごとに§1以降で個別の参照箇所を指示)
4. ローカルでビルドを実行して動作することを `pnpm build` で確認する
5. ローカルでテストを実行して通過することを `pnpm test` で確認する

### 0.2 レビューの基本姿勢

retro-2-M2.md §3.2 / §3.3 に基づく姿勢:

- **機械的チェックを超えて設計意図を読む**: 各項目が「動くか」だけでなく「設計書の精神に沿っているか」を確認する
- **設計書本体との照合を優先する**: 指示書ではなく設計書を真の情報源として、実装が乖離していないかを確認する
- **疑問は遠慮せず提起する**: M1 期間で「指示書記述の曖昧さ」「責任所在の不明確さ」が複数回問題化した(retro R-02 / R-03)。レビューで違和感を覚えた箇所は、設計担当 Claude(M2 期間担当)経由で開発者に確認する流れで提起する

## 1. 設計書本体との照合(retro R-01 対応、最重要観点)

本節は M1 期間で発生した「指示書記述と設計書本体の乖離」(retro R-08 §3.2.2 の M1-02 事例)を再発させないための照合観点。レビュー担当はここを最も丁寧に確認する。

### 1.1 論理ボタン(DES-005 §6.2 / SUPP-001 §3.3.0 との照合)

`web/src/features/combo/components/VirtualController/controllerTypes.ts` を確認:

- [ ] `LogicalButton` 型の取り得る値が **DES-005 §6.2 の14種と完全一致** している(direction_neutral / direction_1〜9 / light_punch〜heavy_kick / drive_impact / drive_parry / throw / parry_drive_rush / step_commit / step_delete)
  - 注: ここでの `throw` は**論理ボタン名**であり、move.code ではない。論理ボタン `throw` は実装上 `forward_throw` の move を解決する(指示書 §4.2.2 / 本チェックリスト §1.4 参照)
- [ ] 設計書にない値が追加されていない(例: `direction_5` のような重複名、`super_art` のような独自ボタン)
- [ ] 設計書の値が削除されていない

### 1.2 modifiers の構造(SUPP-001 §3.3.0 との照合)

`ModifiersEditor.tsx` および `useControllerInput.ts` で扱う modifiers の構造:

- [ ] modifiers は **3フィールド構造**(`Flags []string` / `Type string` / `Notes string`)に従っている
- [ ] flags の取り得る値が **SUPP-001 §3.3.1 の4種**(just / delay / link / low_jump)と完全一致
- [ ] type の取り得る値が **SUPP-001 §3.3.3 の4種**(parry_drive_rush / cancel_drive_rush / dash_forward / dash_back)と完全一致(本指示書 §4.6.2 にも同じ列挙が記載されている)
- [ ] 設計書にない flag や type の値が追加されていない
- [ ] notes 入力欄が **50文字超で UI 警告**を表示する(SUPP-001 §3.3.4 の方針)

### 1.3 moves テーブルの seed 確認(指示書 §3.4 関連)

製造担当の実装完了報告で §3.4.1 の確認コマンド結果が報告されている前提で確認:

- [ ] §3.4.1 の確認コマンド出力が実装完了報告に含まれている
- [ ] 出力に `drive_parry` および `forward_throw` の両方が含まれている(M2-01 では `back_throw` は使用しないが、データとしての存在確認のみ求めるレベルで OK)
- [ ] code の値・name_ja の値が DES-003 §3.4 の moves テーブル定義と整合している(category=`system` 想定、properties は `forward_throw` で `throw`、`drive_parry` で NULL 想定)

万一、確認結果に `drive_parry` または `forward_throw` が含まれていなかった場合(本来は seed 済み確定だが安全策として):

- [ ] 製造担当が独断でマイグレーションを作成しておらず、Plan Mode で停止して開発者に報告している(指示書 §3.4.3)

### 1.4 move.code 検索パターン(指示書 §4.2.2 との照合)

`useControllerInput.ts` の論理ボタン → move 解決ロジック:

- [ ] 9種の技ボタン(LP〜HK の6種 + drive_impact + drive_parry + throw)が指示書 §4.2.2 の表に従って `move.code` で検索されている
- [ ] 検索する code が指示書 §4.2.2 表の値と完全一致(`stand_light_punch` / `stand_medium_punch` / `stand_heavy_punch` / `stand_light_kick` / `stand_medium_kick` / `stand_heavy_kick` / `drive_impact` / `drive_parry` / `forward_throw`)
- [ ] **論理ボタン `throw` の解決先が `forward_throw` であり、`back_throw` ではない**(指示書 §4.2.2 の SF6 仕様反映、M2 では方向状態を保持しないため投げボタンは常に前投げ)
- [ ] move 不在時の挙動が指示書 §4.4.2 と一致(`console.warn` でログ出力、クリック無視)
- [ ] ログメッセージが指示書 §4.4.2 のフォーマット例(`characterId` と `code` を含む)に概ね沿っている

### 1.5 非技ステップの構造(指示書 §4.2.2 / §4.4.1 との照合)

`parry_drive_rush` クリック時のステップ生成:

- [ ] 生成されるステップが `{ moveId: null, modifiers: { type: "parry_drive_rush", flags: [], notes: "" } }` または同等の構造になっている
- [ ] move_id が `null` であり、moves テーブルへの不要な検索が発生していない

## 4. API 整合性とエラーハンドリング(retro R-08 §3.2.2 対応)

### 4.1 API 呼出の整合(M1-06 既存実装との整合)

- [ ] M1-06 §4.4 の `hasKeyChanges()` 関数が変更されていない
- [ ] modifiers 変更が PUT(キー変更編集)を発火させる挙動が温存されている(modifiers は重複判定キーの一部のため)

## 8. 重大な問題の判定基準

以下のいずれかに該当する場合は **重大な問題**として開発者に即座に報告する:

- 設計書本体(DES-005 §6.2 / SUPP-001 §3.3.x)と実装が乖離している(列挙値の不一致、フィールド構造の違い等)
- §3.4 の seed 確認が実施されておらず、コマンド出力が報告されていない
- 9種の技ボタンのうち、コア機能(LP〜HK)で move 解決が動作しない実装ミス
- modifiers の保存パスが壊れており、新規入力した notes / flags / type が DB に保存されない
- M1-06 既存挙動を破壊している(技セレクタが動作しない、編集2方式判定が壊れている等)
- E2E シナリオ A〜D のいずれかが動作しない、または動作確認手順書が未提出

## 9. 軽微な問題の判定基準

以下は **軽微な問題**として開発者に報告するが、修正は M2-02 以降への持ち越しを許容する:

- ボタンのビジュアル(色、サイズ、余白)が SF6 風でない、Tailwind デフォルトのままで素朴
- アクセシビリティ属性(aria-*)が最小限のみ
- ログメッセージのフォーマットが指示書 §4.4.2 例より簡素
- テストのアサーションが粒度粗い

これらは M7 仕上げまでに改善されればよい。
