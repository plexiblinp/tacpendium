## 0. 確定事項(開発者確定 2026-06-03、Plan Mode 不要)

本指示書執筆時点で以下は開発者確定済み。Plan Mode での再協議は不要(§3.4.10 の Plan Mode 必須項目からは除外)。

### 0.1 追加キャラ = AKI / ジェイミー / ガイル(リュウと合わせ計 4 キャラ)

| キャラ | code(想定) | custom_states | 耐久テスト上の役割 |
|--------|-----------|----------------|--------------------|
| リュウ(既存) | `ryu` | なし(NULL) | NULL custom_states のベースライン(既存 seed、変更しない) |
| AKI | `aki` | **あり**(毒 = `subject: opponent` 系) | 相手付与状態の custom_states 耐久 |
| ジェイミー | `jamie` | **あり**(酔いレベル `drunk_level` = `subject: self` / **`type: composite`** / value_definition = object{ level integer 0-4, unlocked_moves string_list }) | 自己永続 composite 状態(DES-003 §3.2 の composite 正準例)+ レベルで使用可能技が変わる moves/recipe 耐久 |
| ガイル | `guile` | なし(NULL) | 溜めキャラ = 溜め技のレシピ表記 + NULL custom_states の追加ベースライン |

- 「自己/相手 subject × flag(boolean)/composite(object) 型 × 溜め系表記 × NULL」を被覆し、スキーマ耐久テスト(C 系統)の被覆を最大化する選定。**特にジェイミーの `drunk_level` は DES-003 §3.2 の composite 正準例そのもの**(マノン不採用のぶん、最も複雑な composite 型をジェイミーが担う。composite を通せば単純な flag/level も自動的にカバー)。
- 3 体ともベースロスター or Year 1(2023 年配信)= Claude の知識が厚く、HTML 抽出結果の妥当性チェック + custom_states JSON の妥当性確認が効く。
- キャラ固有 `custom_states` の具体構造(AKI の毒 = `type: flag` / boolean、ジェイミーの酔いレベル = `type: composite`、§4.2 参照)は、提供 HTML の内容 + DES-003 §3.2 構造に従って製造担当が組み立てる。

### 0.2 シードデータの出所 = 開発者提供 HTML からの抽出

- 開発者が **`work_html/aki.html` / `work_html/jamie.html` / `work_html/guile.html`** にフレームデータ記載の HTML を配置して製造担当へ提供する。
- 製造担当はこれらの HTML から技マスタ・custom_states・代表コンボ等を **抽出** し、seed SQL(§2.1)を生成する。
- **データの正確性は厳密でなくてよい**(最終的にフェーズ 3 の公式データ取り込みツールで総入れ替えされる見込みのため、多少変なデータの混入は許容)。本系統の目的はスキーマ耐久 + 複数キャラ UI の確認であり、production 正確な技データではない。
- **`work_html/` フォルダは本サブマイルストーン(M7-04-2)完了後に開発者が削除する一時フォルダ**。seed SQL に抽出済みであれば HTML 原本は不要になる。製造担当は `work_html/` を成果物リポジトリの恒久ファイルとして扱わない(seed SQL 化が成果物)。
- HTML の具体的な構造(どのフィールドが moves のどのカラム / custom_states / エイリアスに対応するか)は提供時点で未知のため、**製造担当が実 HTML を view し、フィールド対応付けを Plan Mode で開発者に確認する**(§3.4.10 必須項目 1)。

### 0.3 複数キャラ UI の de-hardcode 範囲 = 閲覧のみ動的化(案 2)

- **動的化する(閲覧系 3 箇所)**: コンボ一覧のキャラ絞り込み / コンボ詳細ヘッダのキャラ名 / マイコンボのキャラ別セレクタ。これらを `useCharacters` / CharacterSelector で複数キャラ対応にする。**セットプレイはコンボ配下にアコーディオン展開される**(DES-003 = setups は自キャラに紐づき、相手キャラ次元は存在しない)ため、コンボのキャラ別表示が正しく動けば自動的にキャラ別に表示される = 独立の de-hardcode 対象ではない。
- **本 M7 で作らない**: **ComboEditor のキャラ選択(= 他キャラのコンボを UI から登録する機能)はフェーズ 3(公式取り込みツール導入)の前提作業へ送る**(§1.3)。フェーズ 1 は設計上リュウ単独でオーサリングする期間(SUPP-001 §3.1)であり、取り込みツール前に他キャラ登録 UI を作るのは使い捨てになるため。
- **代表コンボは seed 投入**(§2.1 / §4.3)。E2E の「登録(作成)」確認はリュウ + seed 投入で行う。
- **ただし custom_states キャラの作成パス担保のため、非リュウ(AKI または ジェイミー)のコンボを service/API 経由で作成し recipe_cache + custom_states 整合を確認する API/統合テストを 1 本追加**(§5.1。ComboEditor の UI を作らずに作成パスの耐久を担保する)。

### 0.4 検証用リュウデータの全クリア = M7-05 送り

- 開発中にリュウで作成した検証用コンボ・セットプレイの全クリア(SUPP-001 §3.1 手順 1)は、**フェーズ 1 完了判定 = M7-05 で実施**(SUPP-001 §3.1 が「M7 完了後」の追加作業と明記)。論理/物理削除の方式も M7-05 で確定。
- **本 M7-04-2 では既存リュウデータを温存**し、複数キャラ追加で既存リュウのコンボ・セットプレイが壊れないかの **回帰確認のベースライン** として活用する(レビューチェックリスト §7)。

## 1. 背景と目的

### 1.1 背景

フェーズ 1(M0〜M7)はリュウ 1 キャラのみで開発してきた(SUPP-001 §3.1)。フェーズ 1 完了マイルストーン M7 の総仕上げとして、複数キャラを投入し、(A) プリセット切替動作、(B) 複数キャラ環境での既存機能、(C) スキーマ耐久を確認する。

- **A 系統(残り 4 プリセット切替確認)**: 組み込みプリセット 5 種(`official_ja_move` / `official_ja_command` / `numeric_ja` / `numeric_en` / `srk`)は M1 の seed(000005)でレコード投入済み。フェーズ 1 では `official_ja_move` のみ実エイリアスを持ち、**他 4 種はエイリアス空で出荷**(SUPP-001 §3.4)。よって本系統は「空プリセットを選択した際に DES-004 §5.3 のフォールバック(`official_ja_move` → `moves.code`)が正しく機能するか」の **動作確認が主**(新規プリセットデータ作成ではない)。
- **B 系統(キャラ追加)**: §0.1 確定の AKI / ジェイミー / ガイルを、§0.2 確定の HTML 抽出ワークフローで seed 追加する。AKI / ジェイミーは `custom_states`(characters テーブルの JSON 列、DES-003 §3.2)を持つ。M1-02 で確立したリュウのシード SQL パターン(`moves` / `presets` エイリアス / `characters`)を踏襲。
- **C 系統(スキーマ耐久テスト)**: 複数キャラ + 各キャラの典型コンボ 10〜20 件を投入し、検索・フィルタ・ソートが NFR001(100ms 以内)を満たすか、`custom_states` を持つキャラ(AKI / ジェイミー)がエンドツーエンドで破綻しないかを確認。**スキーマ変更が必要な問題が発覚した場合は Plan Mode 停止 + 設計担当へ報告(CHANGE 通知書起票判断)**。

### 1.2 目的

本指示書完了時に以下を達成する:

- 残り 4 プリセット(空エイリアス)を選択した際のフォールバック表示が正しく機能する
- AKI / ジェイミー / ガイル(§0.1)が seed で投入され、複数キャラ環境で既存機能(一覧キャラ絞り込み / マイコンボ / 比較 / セットプレイのコンボ配下展開)が動作する
- `custom_states`(AKI の毒 / ジェイミーの飲酒レベル)がエンドツーエンドで破綻しないことを確認
- 各キャラ 10〜20 件の典型コンボで検索・フィルタ・ソートが NFR001 を満たす
- **M7-15 由来の持ち越し = M7-03 E2E シナリオ B-2 / B-4(AddComboToCompareModal のキャラ切替動作確認)がキャラ追加により実施可能になり、完全動作確認される**(retrospective-log §6.6 M7-15)

### 1.3 このマイルストーンで作らないもの(スコープ外)

- **公式データ取り込みツールでのキャラ投入**(フェーズ 3、FR701)
- **残り 4 プリセットのエイリアス実データ整備**(フェーズ 2、SUPP-001 §3.4。本系統は空プリセットのフォールバック動作確認のみ)

- **ComboEditor のキャラ選択(他キャラ登録 UI)**(§0.3、**フェーズ 3 = 公式取り込みツール導入の前提作業へ送り**。本 M7 では閲覧系のみ動的化)

## 4. 詳細仕様

### 4.1 A 系統: 残り 4 プリセット切替動作確認

- 組み込みプリセット 5 種は M1 の 000005 で投入済み(レコードのみ、`official_ja_command` / `numeric_ja` / `numeric_en` / `srk` はエイリアス空)。**本系統で新規プリセットデータは作らない**。
- プリセット切替 UI で空プリセット(4 種)を選択した際、DES-004 §5.3 のフォールバック(`official_ja_move` → `moves.code`)が正しく機能し、レシピが破綻なく表示されることを確認(SUPP-001 §3.4「M7 終盤の確認事項」)。
- 追加キャラのレシピでも同フォールバックが機能することを確認(複数キャラ × 空プリセット)。
- recipe_cache が全プリセット分計算される設計(SUPP-001 §7)のため、追加キャラのコンボ登録時に空プリセット分も含めて recipe_cache が破綻しないことを確認。

### 4.2 B 系統: AKI / ジェイミー / ガイルの seed 追加(HTML 抽出)

- `work_html/{aki,jamie,guile}.html` を抽出元として、§3.4.10 必須項目 1 で確定したフィールド対応付けに従い、新規マイグレーションで 3 キャラを追加。
- M1-02 リュウ seed パターン踏襲: `characters`(`custom_states` 含む)→ `moves`(キャラごと)→ `preset_aliases`(`official_ja_move` 分、キャラごと)。
- `custom_states`(DES-003 §3.2 構造 = subject / scope / type / value_definition)を、提供 HTML の内容に基づいて構築:
  - **AKI**: 毒(`subject: opponent` 想定。boolean の付与有無 + level 等、HTML の記載に従う)
  - **ジェイミー**: 酔いレベル(`code: drunk_level` / `subject: self` / `scope: persistent` / **`type: composite`** / `value_definition: { kind: object, fields: [ {code: level, kind: integer, min: 0, max: 4}, {code: unlocked_moves, kind: string_list} ] }`)。DES-003 §3.2 の composite 正準例に一致。`unlocked_moves`(各レベルで解禁される move code の list)は HTML から抽出、読めない部分は代表値で補完可。`name_ja` は HTML 表記(飲酒レベル等)でも可だが code は `drunk_level` で正準例に合わせる
  - **ガイル**: `custom_states` なし(NULL)。溜め技は通常の `moves` として登録(溜め固有のフラグが必要なら HTML + 既存 modifiers 仕様で表現)
- i18n(キャラ名・技名ラベル)を ja/en に追記。
- down マイグレーションで追加 3 キャラ分を削除可能に保つ。
- 追加後、recipe_cache がキャラ横断で整合すること(SUPP-001 §7 = コンボ登録時に全プリセット分計算)。
- **データの正確性は厳密でなくてよい**(§0.2、フェーズ 3 で総入れ替え)。HTML から読み取れない項目があれば、スキーマ耐久 + UI 確認に支障ない範囲で妥当な値を補完してよい(完璧な正確性に時間をかけない)。判断に迷う構造的な点は Plan Mode で確認。
- 追加後、recipe_cache がキャラ横断で整合すること(SUPP-001 §7 = コンボ登録時に全プリセット分計算)。

### 4.3 C 系統: スキーマ耐久テスト

- §3.4.10 必須項目 3 の確定方式で、各キャラ 10〜20 件の典型コンボを投入。
- 検索・フィルタ(キャラ / タグ / 始動技等)・ソートが NFR001(100ms 以内)を満たすことを確認。

## 8. 注意事項・判断に迷ったら

### 8.1 Plan Mode 停止して開発者協議が必須のケース

- **スキーマ耐久テストでスキーマ変更が必要と判明した場合**(`custom_states` が既存スキーマで扱えない等)= 実装を止めて設計担当に報告。設計担当が CHANGE 通知書起票要否を判断(SUPP-001 §3.1 手順 6、製造担当は CHANGE 起票しない)

- キャラ固有技名がプリセット解決で本格的な再設計を要する問題を起こした場合(P-1 フェーズ 2 送りの判断)

### 8.2 設計担当の判断意図(製造担当が誤解しやすい点の補足)

- **A 系統は「フォールバック動作の確認」であり、4 空プリセットのエイリアスを埋める作業ではない**(エイリアス本格整備はフェーズ 2)。空のまま選択してフォールバックが効くことの確認が目的。

- **C 系統で見つかる「スキーマで扱えない」事象こそが本テストの成果**。問題を握り潰さず Plan Mode で報告する(SUPP-001 §3.1 がスキーマ耐久テストを M7 に置いた本来の目的)。

- 本指示書は既存スキーマでの確認が前提で、**通常は設計書本体の変更を伴わない**(CHANGE 不要)。スキーマ耐久テストでスキーマ変更が必要と判明した場合のみ、設計担当が CHANGE 起票を判断する(製造担当は起票しない、playbook §1 / §16)。
