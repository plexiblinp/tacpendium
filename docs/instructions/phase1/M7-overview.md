## 0. 本書の位置づけ

本書は M7(仕上げ + フェーズ 1 完了)の **全体像と方針確定** を目的とする overview 文書。M7 のサブマイルストーン分割・モデル配分・主要設計判断・フェーズ 1 完了判定基準を本書で確定し、開発者承認後に M7-RESEARCH-01 指示書本体の執筆に進む。

playbook §2 / §3 / §15 の運用ルール(1 マイルストーン = 1 チャット + サブマイルストーン分割は関心数で判断 + 完全直列実行)に従う。

### 0.1 M7 が他マイルストーンと質的に異なる 4 点

M7 は M1〜M6 と質的に異なる構造的特徴を 4 点持つ:

1. **「新機能の追加」がほぼゼロで、「既存機能への横断的改修」が中心**: shadcn/ui 統一導入(系統 A)・レスポンシブ仕上げ(系統 C)はいずれも M1〜M6 で実装した全画面を対象とする横断作業。playbook §4.6「UI ライブラリの統一導入は単独マイルストーンとして扱う(部分導入はハイブリッド状態を悪化させる)」の正本実施回となる
2. **持ち越し課題の消化が主目的**: 継承課題 R-1/R-2/R-3/M-1〜M-4/C-2/C-3/C-4/L-02/L-03/L-04 + M6 新規 + スマホ LAN 検証 で計十数件。M1〜M6 のように「未着手機能を作る」のではなく「既に動くものを整える」期間
3. **フェーズ 1 完了マイルストーンであり、次は通常マイルストーンではなくフェーズ移行となる**: M7 完了承認後はフェーズ 2 を飛ばして **フェーズ 3(公式データ取り込みツール FR701)** に進む方針(2026-05-26 開発者意向、知人配布のためキャラ数拡充が必須)。本書 §6 / §13 でフェーズ 1 完了判定基準を明示
4. **handover はマイルストーン間ではなくフェーズ間文書となる**: M7 完了承認時に作成する `m7-to-phase2-handover.md` は **凍結保存的文書**(いつでもフェーズ 2 を再開できる状態の宣言)で、過去の `m{N}-to-m{N+1}-handover` とは性質が異なる。フェーズ 3 へは別途 DES-003(データモデル)+ REQ-001 §6.2-6.5 + DES-004(内部表現)を開発者が新セッション Claude に提示する想定で、本体プロジェクトの handover からの引き継ぎは行わない(2026-05-26 開発者方針)

#### 0.3.3 R-1 持ち越し課題の意味の根本的見直し

M5 期間担当が R-1 を起票した際は「M1〜M4 期間のレスポンシブ対応のばらつき」として理解されていたが、M7-RESEARCH-02 で **「ばらつきではなく、ほぼ未実装」** が実態だったことが事実として判明した。R-1 解消基準を以下に再定義:

- **旧解消基準(M5 期間担当時の想定)**: 全画面の Tailwind ブレークポイント整備、3 段階レスポンシブで正常表示
- **新解消基準(本 v1.0.1 改訂で確定)**: **Header 共通化 + ハンバーガーメニュー化(shadcn/ui Sheet) + 既存横スクロール対応の温存 + R-2 / R-3 解消 = フェーズ 1 完了レベル**。本格スマホ UI(DES-005 §5.6 / §5.8 / §5.9 / §5.10 / §7 規定のカード形式 / アコーディオン / ボトムシート / スワイプ操作)は **フェーズ 3 以降へ送り**

#### 0.3.4 案 Y 採用の根拠(2026-05-27 開発者方針)

M7-RESEARCH-02 結果評価で提示した 3 案(案 X = 完全実装 / 案 Y = 最小限のみ / 案 Z = 中間)のうち、**案 Y を採用**(2026-05-27 開発者方針「PCでの体験を重視する、スマホは後回しでも良い」)。採用根拠:

1. **フェーズ 3 取り込みツール先行意向との整合**(2026-05-26 開発者意向): 知人配布を急ぐ意向と、フェーズ 1 で本格スマホ対応する選択は両立しない
2. **SUPP-001 §4.6「PC 版で機能を固めてから合わせ込む」思想との一貫性**: i18n 英語ロケール整備のフェーズ 3 後送り判断(2026-05-26)と同質の思想、本格スマホ UI も「最終 UI 確定後の一括整備」が手戻り少ない
3. **playbook §17.1 個人開発の規模感**: M7-03 で 9 件のレイアウト規定すべてを実装すると指示書サイズ 1500-2000 行クラスとなり、過剰実装の懸念
4. **DES-005 §5.6 / §5.8 / §5.9 / §5.10 / §7 規定はフェーズ 1 完了基準として必須ではない**: NFR306「PC・タブレット・スマートフォンの3段階対応」は実現する必要があるが、その実現方法(横スクロール vs カード形式)は実装側の選択。本 M7 では「実用可能レベル」を目指す

## 2. 主要設計判断(本 overview で確定)

### 2.1 i18n 英語ロケール整備のフェーズ 3 以降送り(2026-05-26 開発者方針)

  ↓

**完全直列実行**: M7 は **完全直列** で進める。並列実行は採用しない(playbook §15、M2 以降から継続)。

- M2〜M6 期間で直列実行が安定運用として確立した

- 同時稼働ターミナル数 3 本(Web 版 1 + 製造 1 + レビュー 1)を超えない方針を継続

## 10. リスクと対策

### 10.1 shadcn/ui 統一導入の影響範囲過大(技術リスク中〜大)

- **リスク**: shadcn/ui 統一導入は本プロジェクト初の大規模 UI ライブラリ移行、既存自作ラッパーの呼び出し箇所が全画面に及ぶ可能性、Props 契約の変更で型エラー多発のリスク
- **対策**:
  - M7-RESEARCH-01 で事実列挙(自作ラッパーの全件特定 + 呼び出し箇所網羅 + Props 契約整理)を事前に実施
  - M7-01 / M7-02 を 2 サブマイルストーンに分割(Dialog + Popover を先、Form + Toast + その他を後)で段階的に移行

  - M7-01 / M7-02 を Opus 4.6 推奨(関心数 + 判断分岐への対応力強化)
