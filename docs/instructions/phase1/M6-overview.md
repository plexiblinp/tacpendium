本書は M6(初期体験系)の **全体像と方針確定** を目的とする overview 文書。M6 のサブマイルストーン分割・モデル配分・関心数・主要設計判断を本書で確定し、開発者承認後に M6-01 指示書本体の執筆に進む。

### 1.2 目的(M6 完了時に達成される状態)

- 初回起動時に対話的セットアップウィザードが表示され、基本設定(言語 / デフォルトキャラ / プリセット / LAN 共有モード / パスワード)を完了できる
- ウィザード完了時に `config.toml` が自動生成される(SUPP-001 §5.8 既定通り)
- 設定画面(`/settings`)から各種設定の表示・編集が可能(`GET /api/config` / `PUT /api/config` 経由)
- スマホで起動した場合、ホーム画面(`/` または `/home`)が表示され、主要機能ボタン経由で各画面に遷移できる
- コンボ登録・編集画面で入力中の内容がブラウザストレージに自動保存され、再訪時に「編集途中のデータがあります。復元しますか?」ダイアログを表示して復元可能

## 2. 主要設計判断(本 overview で確定)

### 2.1 LAN バインドロジックは M1 既存実装を活用、M6 では追加実装しない

M6-RESEARCH-01 調査結果(2026-05-23)で判明:

- `internal/config/config.go`(136 行)で `config.toml` 読込・Config 構造体・バリデーション・デフォルト値処理が **すべて実装済み**
- `cmd/combomgr/main.go:determineBindAddr()` で `[server].mode` を読んで `127.0.0.1` / `0.0.0.0` を切り替える実装が **既に存在**
- `cmd/combomgr/main.go:buildAllowedOrigins()` で CORS 許可 Origin を動的構築する実装も **既に存在**
- `internal/config/config_test.go`(7 ケース)で関連テスト整備済み

**M6 期間の対応方針**:

- 既存実装を変更しない(既存挙動の温存)
- 設定 API(`GET /api/config` / `PUT /api/config`)は既存の `*config.Config` 構造体を読み書きする形で実装する
- `PUT /api/config` でモード変更があった場合の動作は **サーバー再起動を要求する**(SUPP-001 §4.2 の動作確認方針「`config.toml` を直接編集してアプリ再起動」と整合、設定画面の LAN 切替 UI 自体はフェーズ 2 送りのため M6 では再起動要求が露見しない)
- M6-RESEARCH-01 §4.5 (3) で発覚した `config.toml` サンプルファイル未配置は、M6-02 初回起動ウィザード実装時の自動生成で解決(案 α 採用)

### 2.2 設定 API のスコープ(`GET /api/config` / `PUT /api/config` 限定、認証なし)

- **`GET /api/config`**: 既存の `*config.Config` を読み込んで JSON で返す。`SecurityConfig.PasswordHash`(将来追加予定)等の機微情報は **レスポンスから除外** する設計(JSON タグで `-` 指定、現状 `password_hash` フィールド未存在のため新規追加時の規約として M6-01 指示書で明示)
- **`PUT /api/config`**: リクエストボディで設定値を受け取り、バリデーション(既存 `validate()` 関数活用)→ `config.toml` 書き戻し → メモリ上の `*config.Config` 更新を行う
- **認証は M6 では実装しない**(SUPP-001 §4.2「パスワード保護 UI と認証ロジックはフェーズ 2」、CLAUDE.md §10「セキュリティ関連の自己判断は禁止」)
- **既存挙動の温存**: M1 で実装済みの `cfg.Server.Mode` / `cfg.Server.Port` 等の読込・利用ロジックには変更を加えない

### 2.3 設定画面と初回起動ウィザードの API 共通化

設定画面(DES-005 §5.16)と初回起動ウィザード(DES-005 §5.1)は **同一の `GET /api/config` / `PUT /api/config` を消費** する設計とする。これにより以下のメリット:

- API クライアント(`web/src/lib/configApi.ts` 等)を 1 セット作って 2 画面で共有可能
- 初回ウィザード ⇔ 設定画面の値の整合性を API 層で担保
- M6-01(設定 API 基盤)を M6-02(設定画面 + 初回ウィザード)から独立サブマイルストーン化することで、M4-01 が setup BE 基盤を独立化した先例(M4-overview §3.2)と整合する流れ

### 2.4 下書き自動保存は `web/src/lib/browser-storage.ts` 既存ヘルパ経由

CLAUDE.md §10.X 既定運用:

- キー名: `combo-draft-<comboId|new>-v1`(編集対象 ID 別に分離、新規時は `new`)
- 専用ヘルパ経由(`web/src/lib/browser-storage.ts`、M3-03 で新設)
- try-catch 必須(容量制限・プライベートブラウジング対応)
- JSON シリアライズ(parse 失敗時は未保存扱い)
- キーバージョニング(`-v1`)

**M6-04 着手前の確認事項**:

- M3-03 で新設された `web/src/lib/browser-storage.ts` の **現状 API シグネチャ** は M6-04 指示書 §3.4 着手前確認で製造担当が検証する(設計担当は実コード未確認、handover §6.1 推測回避運用)
- 既存のキー(`combo-list-columns-v1`、M3-03)との命名規則整合確認

### 2.5 スマホ専用ホームの遷移先(コンボ一覧経由か直接遷移か)

DES-005 §5.2 規定の主要機能ボタン(6 件: コンボ一覧 / マイコンボ / 新規コンボ登録 / コンボ比較 / プリセット管理 / 設定):

- **遷移先は既存ルート**(M5-RESEARCH-01 調査結果でルート定義は確認済み、M6-RESEARCH-01 では未確認のため M6-03 §3.4 着手前確認で再確認推奨)
- **「最近更新したコンボ」上位 3 件のリンク**(DES-005 §5.2 item 4)は **`GET /api/combos?limit=3&sort=updatedAt&order=desc`** で取得想定(既存 API で実現可能、新規 API 追加なし)
- **PC/タブレットではスキップ**(DES-005 §5.2 レスポンシブ): ルーティング側で画面幅判定して、PC ではコンボ一覧へリダイレクト

### 2.6 shadcn/ui 未導入のまま実装(M7 まで継続)

- playbook §17.2 / handover §6.4 で M7 まで未導入が確定
- 標準 HTML + Tailwind の自作ラッパーで実装(M2 / M3 / M4 / M5 で確立済みのパターン踏襲)
- Toast 通知は既存 `topMessage` パターン流用(M4-03 由来、M5-01 でも活用)

### 2.7 初回起動ウィザードの判定方法

「初回起動か否か」の判定は **`config.toml` ファイルの存在有無** を基準とする(SUPP-001 §5.8「設定ファイルが存在しない場合はデフォルト値で動作し、初回起動ウィザード完了時に `config.toml` を自動生成」既定通り)。

具体的な実装方法:

- バックエンド: `GET /api/config` のレスポンスに `isInitialized: boolean` フィールドを含める(`config.toml` 存在有無を反映)
- フロント: アプリ起動時に `GET /api/config` を呼び、`isInitialized: false` ならウィザードルート `/wizard` にリダイレクト(または `/wizard` で初期化)
- ウィザード完了時に `PUT /api/config` を呼び、サーバー側で `config.toml` を初回生成 → 以降は `isInitialized: true`

詳細仕様は M6-01 / M6-02 指示書本体で確定。

### 2.8 レスポンシブ方針(M6 スマホホームは新規スマホ専用、既存画面のスマホ対応は M7 持ち越し)

- **M6 スマホホーム(M6-03)**: 新規スマホ専用画面として独立実装、PC では遷移先をコンボ一覧にスキップ(レスポンシブの判定はルーティング層で行う)
- **既存画面(M1〜M5 実装済み)のスマホ向け調整**: M6 スコープ外、M7「レスポンシブ仕上げ」で対応(handover §3.1 R-1 持ち越し)
- **遷移先(コンボ一覧等)でスマホ表示が崩れる可能性**: M6 完了承認時に progress-log.md に既知制限事項として記録、M7 で対応(handover §3.1 推奨案踏襲)

### 4.2 M6-01: 設定 API 基盤(`GET /api/config` / `PUT /api/config`)

## 5. 実行順序と依存関係

```
M6-RESEARCH-01(設定 API + LAN バインド調査)── 完了承認済み(2026-05-23)
  ↓
M6-01(設定 API 基盤: GET/PUT /api/config)
  ↓
M6-02(設定画面 + 初回起動ウィザード)
  ↓
M6-03(スマホ専用ホーム)
  ↓
M6-04(下書き自動保存 + M6 統合 E2E)
M6 完了
```

**完全直列実行**: M6 は **完全直列** で進める。並列実行は採用しない(playbook §15、M2 / M3 / M4 / M5 から継続)。

直列を採用する根拠:

- M2 / M3 / M4 / M5 期間で直列実行が安定運用として確立した
- M6 の M6-01 〜 M6-04 は前のサブマイルストーンの成果物に依存している(設定 API → 設定画面 + ウィザード → スマホホーム → 下書き保存 + 統合 E2E)

## 9. CHANGE 通知書の起票予定

### 9.1 M6 着手前(該当なし)

M6 期間着手前に起票必要な CHANGE 通知書は **なし**。設計書本体(REQ-001 / DES-001〜DES-006)への変更を伴う事象は、M6-RESEARCH-01 調査結果でも発見されなかった。

### 9.2 M6 期間中に発生可能性のある起票

**現時点で M6 期間中の追加 CHANGE 起票は未想定**(handover §6.4「CHANGE 通知書起票判断の厳格化」厳格適用)。M6 スコープ 5 領域は設計書本体に明示済みのため、追加起票は基本不要。

ただし、以下のシナリオで CHANGE 起票が発生する可能性は残る(発生時の運用):

- M6-RESEARCH-01 §4.5 (1) ポート競合フォールバック未実装(DES-002 §3.3 既定義)を M6 内で対応する場合 → 本 overview §1.3 でスコープ外確定済み、起票不要
- M6-02 で QR コード生成ライブラリ(`qrcode.react` 等)追加判断 → CLAUDE.md §6 依存追加ポリシーの範囲、CHANGE 通知書ではなく `progress-log.md` に選定理由記録
- 初回ウィザードの `config.toml` 自動生成方式が設計書本体と矛盾する場合 → 通常は矛盾しない見込み、矛盾発覚時に Plan Mode で開発者協議
- 設定画面のセクション構成・項目が DES-005 §5.16 と乖離する必要が生じた場合 → 設計書本体改訂が必要 → CHANGE 通知書起票判断(playbook §16 厳格適用、軽微なら指示書本文記述で対応)

**起票が必要となった場合の運用(Q3 開発者方針)**: いきなり CHANGE 通知書を起票せず、過去の CHANGE 通知書の例(CHANGE-006 / 010 / 011 / 012 / 013 / 015 等)を開発者に提示依頼してから書式を確認してドラフト作成する。

次回採番は **CHANGE-016** から(change-number-registry v1.4.0 §1)。

### 9.3 SUPP-001 改訂(CHANGE 不要、自由改訂)

現時点で M6 期間中の SUPP-001 改訂は未想定。下書き自動保存(M6-04)・初回起動ウィザード(M6-02)関連は SUPP-001 §5.8(設定ファイルフォーマット)+ CLAUDE.md §10.X(ブラウザストレージ運用)で既定義済みのため、追加追記は基本不要。

## 10. リスクと対策

### 10.1 設定 API の `config.toml` 書き戻し時のアトミック性確保(技術リスク中)

- **リスク**: `PUT /api/config` で `config.toml` 書き戻し中にプロセスがクラッシュした場合、ファイル破損のリスク
- **対策**: 一時ファイル(`config.toml.tmp`)に書き込み → `os.Rename()` でアトミックに置換する実装パターンを M6-01 指示書で明示(Plan Mode で確定)

### 10.2 初回起動判定とリダイレクトの実装位置(設計判断リスク低)

- **リスク**: アプリ起動時に `GET /api/config` の `isInitialized: false` を判定する場所(ルーター層 vs ページ層 vs `web/src/App.tsx`)で実装方針が分散する可能性
- **対策**: M6-02 指示書 Plan Mode で実装位置を確定。M3-04 マイコンボ画面実装で確立した「`web/src/App.tsx` でグローバル状態を初期化、ルーティングはルーター層で行う」パターン踏襲を推奨

### 10.3 既存実装(LAN バインド)の挙動温存(回帰リスク低)

- **リスク**: M6-01 で設定 API 実装時に、既存の `cmd/combomgr/main.go:determineBindAddr()` を変更してしまう可能性
- **対策**: M6-01 §1.3 / §2.3 / §3.4 着手前確認で「既存実装を変更しない」を厳格に明示、M6-04 統合 E2E シナリオ U-1〜U-4 で LAN モードの動作確認を 1 件含める

### 10.4 言語選択(react-i18next)の現状実装状態が不明(調査範囲外リスク中)

- **リスク**: 設定画面の言語選択・初回ウィザードの言語選択(ステップ 2)で `react-i18next` が必要だが、CLAUDE.md §2 に列挙されているのみで実装状態未確認
- **対策**: M6-02 §3.4 着手前確認で製造担当に「`react-i18next` の package.json 存在確認、初期化ファイル(`web/src/lib/i18n.ts` 等)の有無、現状の翻訳キー実装状況」を検証させる(handover §1.4 推測回避運用)。未実装の場合は M6-02 スコープ内で初期化 + 最低限のキー(設定画面 + ウィザード用)を追加する形で対応、ただし全画面の翻訳キー整備は M7「i18n(英語ロケール整備)」のスコープ送り

### 10.5 既存画面のスマホ表示崩れ(handover §3.1 R-1 由来、UX リスク低)

- **リスク**: M6-03 スマホホームから既存画面(M1〜M5 実装済み)に遷移した時にスマホ表示崩れが発生
- **対策**: handover §3.1 推奨案踏襲(本 overview §1.3 / §6.2 既決定)= M6 完了承認時に progress-log.md に既知制限事項として記録、M7「レスポンシブ仕上げ」で対応

### 10.6 M5 期間最頻出パターン(M4 由来「実コード確認の省略」)の再発リスク(中)
