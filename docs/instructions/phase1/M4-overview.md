## 1. 本書の位置づけ

SUPP-001 §4.1 で M0〜M7 のマイルストーン全体が定義されている。本書は M4(セットプレイ系)を **6 つのサブマイルストーン(M4-00 / M4-00b / M4-01〜M4-04)** に細分化した構成と相互関係、および M3 完了時点で確立した運用ルール(playbook v1.5.0 → v1.6.0、retrospective-log v1.0.0 → v1.0.1、architecture-patterns v1.0.0、m3-to-m4-handover v1.1.0)を踏まえた M4 期間中の運用方針を示す。なお M4-00b は M4-00 §3.4.2 着手前確認で発見された隠れ P-01 相当の課題(ModifiersEditor 側の console.warn 未実装、M2-04 設計担当ミスの双子事例)を清算するため、M4-00 完了後に追加起票された経緯を持つ(2026-05-16)。

各指示書を実装する Claude Code は、本書を読むことで「自分の作業範囲」「依存関係」「M4 で扱わないもの」「M3 反省点を踏まえた運用ルール」を把握できる。

M4 は **完全直列実行** で進める(後述 §4)。M2 / M3 期間で確立した直列実行の安定性(playbook §15)を継続する。

### 1.1 M4 のスコープ(SUPP-001 §4.1)

### 3.2 M4-01: セットプレイ ドメイン バックエンド基盤

**目的**: セットプレイ(`setups` / `setup_steps` / `combo_setups` テーブル、DES-003 §3.11〜§3.13)の API 基盤を整備し、M4-02 以降のフロント実装の前提を完成させる。VAL-S05(CHANGE-012)をサービス層で強制する。

**スコープに含むもの**:

- バックエンド 3 層パターン(architecture-patterns.md §2)で `internal/api/setup/` / `internal/service/setup/` / `internal/repository/setup/` を新設
- API エンドポイント(初期案、M4-01 起票時に Plan Mode で詳細確定):
  - `POST /api/combos/{id}/setups` — 親コンボ ID 経由でセットプレイ新規作成(VAL-S05 適用)
  - `POST /api/combos/{id}/setup-links` — 既存セットプレイの紐付け追加
  - `DELETE /api/combos/{id}/setup-links/{setup_id}` — 紐付け解除
  - `GET /api/setups/{id}` — セットプレイ詳細取得
  - `PATCH /api/setups/{id}` — メタデータ・レシピ編集(SUPP-001 §5.9 PATCH 送信ポリシー適用)
  - `DELETE /api/setups/{id}` — 論理削除
  - `GET /api/combos/{id}/setup-candidates` — 転用候補取得(FR011、M4-03 で挙動仕上げ)
- バリデーション層: VAL-S01〜S05 を `internal/service/setup/validate.go` に実装
- notation サービス層拡張(SUPP-001 §7 追記、案 X 採用): `ResolveSetupRecipe / RecomputeSetupCache / DeleteSetupCache` を実装。プリセットエイリアス変更時の `RecomputePresetCache` をセットプレイ側も対象に拡張
- エラーレスポンス: `model.APIErrorResponse` 共通型(CHANGE-010 / CHANGE-011)を最初から使用(architecture-patterns.md §3)
- コンボ作成 API の DTO 前方互換予約: `Setups []CreateSetupInput \`json:"setups,omitempty"\`` を **形だけ予約**(本指示書では実装しない、M4-04 で実装)

**スコープに含まないもの**:

- FR011 転用候補抽出ロジックの実装 — M4-03 で実装(本指示書では API エンドポイントの形のみ確定)
- フロント側 UI 全般 — M4-02 以降で実装
- コンボ作成 API の setups 束受領実装 — M4-04 で実装(本指示書は DTO 形予約のみ)

**前提**: M4-00 完了は不要(並行投入可)。M3 完了が前提。

**例外条項**: コンボ作成 API の DTO に `Setups` フィールドを形だけ予約する(`omitempty` で前方互換、M3 既存呼び出しは影響なし)。新規エンドポイント `POST /api/combos/{id}/setups` 等の追加と notation サービス層拡張は本指示書のスコープに含む。

**推奨モデルの根拠**: 複数ハンドラ・複数サービス関数の新設(関心数 5+)、recipe_cache 整理ロジック拡張、VAL-S05 を含むバリデーション層設計、M4-04 用の前方互換配慮が必要。M3-05 で複数関心統合に Opus 4.6 を採用した先例と整合。

**Plan Mode 必須の根拠**: API エンドポイント設計の選択肢が複数あり(parent_combo_id の渡し方、エンドポイント分離方針)、Plan Mode で開発者協議が安全。

**指示書執筆時の留意点(設計担当 Claude 向け)**:

- VAL-S05 は **リクエスト DTO 直接ではなくサービス層関数の引数レベル** でチェックする(CHANGE-012 §6.2 R-2 対策、M4-04 同時登録時の動的 parent_combo_id 取得との整合)

## 4. 実行順序と依存関係

```
M4-00(P-01 RecipeBuilder console.warn)── 完了承認済み(2026-05-16)
  ↓
M4-00b(隠れ P-01 ModifiersEditor console.warn)── 完了承認済み(2026-05-16)
  └─ M4-01 と並行投入可能
M4-01(setup BE 基盤)
  ↓

  ↓
M4-03(FR011 + knockdown モーダル)
  ↓
M4-04(同時登録: API DTO 拡張 + UI + フック拡張)
  ↓
M4-05(M4 統合 E2E + L-01 解消)
M4 完了
```

M4-00 と M4-00b は M4-01 投入と並行進行可能(M4-00b の起票は M4-00 §3.4.2 で発見された経緯から M4-00 完了後に追加されたが、現時点で両者とも完了承認済み)。

**完全直列実行**: M4 は **完全直列** で進める。並列実行は採用しない(playbook §15、M2 / M3 から継続)。

直列を採用する根拠:

- M2 / M3 期間で直列実行が安定運用として確立した
- M4 の M4-01 〜 M4-04 は前のサブマイルストーンの成果物に依存している(setup API → setup UI → 転用支援 + 確認モーダル → 同時登録)
- 同時稼働ターミナル数 3 本(Web 版 1 + 製造 1 + レビュー 1)を超えない方針を継続

M4-00 / M4-00b のみ独立で M4-01 と並行投入可能だが、製造担当・レビュー担当の同時稼働 1 セット内で処理する形(playbook §15.2 ターミナル 3 本制約内)。M4-00 / M4-00b はいずれも完了承認済み(2026-05-16)。

各サブマイルストーン完了後に開発者が動作確認・承認を行ってから次に進む。

### 6.2 M4 期間で特に意識すべき点(M3 反省を踏まえた重点項目)

M3-04 の **4 回スコープ拡張**(retrospective-log §4.1 #9 / #10 / #11 + §1 パターン B)を最大の教訓と位置づける。M4 期間中、特に以下を意識する:

**重点 1: ユーザーフロー視点での網羅確認**(retrospective-log §1 パターン B)

M3-04 では「画面ごとの UI」を考えて、ユーザーが「どの画面から入り、どの画面で完結するか」のフロー視点を欠いた結果、初回登録経路・既存データ操作経路・削除/解除経路の網羅性が崩れた。

M4 では各指示書執筆前に **以下のフローを脳内シミュレーション** する:

- 新規セットプレイ作成経路: コンボ詳細 / コンボ編集 → セットプレイ追加ボタン → SetupEditorPage(M4-02)
- 既存セットプレイ紐付け経路: コンボ詳細 / コンボ編集 → 「既存セットプレイから選択」モーダル → 紐付け追加(M4-02)
- セットプレイ転用経路: コンボ詳細 → 転用候補セクション → 「このコンボにも紐付ける」ボタン(M4-03)
- セットプレイ編集経路: コンボ詳細のセットプレイ一覧クリック / 紐付き一覧 → SetupEditorPage 編集モード(M4-02)
- セットプレイ削除経路: SetupEditorPage の削除ボタン → 論理削除(M4-02)
- 紐付け解除経路: コンボ詳細 / コンボ編集 → 紐付き一覧の紐付け解除ボタン(M4-02)
- knockdown_advantage 変更時の紐付き継承経路: コンボ編集 → 確認モーダル → 引き継ぎ判断(M4-03)
- 同時登録経路: コンボ登録画面のセットプレイセクション → コンボ作成と同時にセットプレイ作成 + 紐付け(M4-04)

**重点 2: 既存実装の確認漏れ防止**(retrospective-log §1 パターン A)

M3-04 では「設計書本体に書かれている = 実装済み」と思い込んで character API 未実装に気づけなかった。M4 でも以下を製造担当の §3.4 着手前確認に必ず組み込む:

- M2-02 編集 2 方式分離の実装実態(M4-03 で knockdown_advantage 確認モーダルを書く前に調査担当 Claude Code 経由で確認)
- recipe_cache 整理関数のセットプレイ向け既存実装の有無(SUPP-001 §7 追記前の確認)
- コンボ作成 API の現状の DTO 構造(M4-04 で setups 束受領拡張前の確認)

**重点 3: 既存パターンとの整合確認**(retrospective-log §1 パターン C)

M3-04 では `mode` 切替単一コンポーネント設計が、M3-01〜M3-03 で確立した「フックでロジック、コンポーネントで表示」分離パターンと矛盾した。M4 では以下のパターンを必ず踏襲する:

- フロント: フック分離パターン(architecture-patterns.md §1)
- バックエンド: 3 層パターン(architecture-patterns.md §2)
- エラー共通型(architecture-patterns.md §3)
- 列挙定数同期(architecture-patterns.md §4)
- ブラウザストレージ運用(architecture-patterns.md §5)

逸脱する場合は指示書本文に **理由を明記**(architecture-patterns.md §0 ルール)。
