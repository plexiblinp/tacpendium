## 0. 本書の位置づけ

本書は M5(コンボ比較系)の **全体像と方針確定** を目的とする overview 文書。M5 のサブマイルストーン分割・モデル配分・関心数・主要設計判断を本書で確定し、開発者承認後に M5-01 指示書本体の執筆に進む。

playbook §2 / §3 / §15 の運用ルール(1 マイルストーン = 1 チャット + サブマイルストーン分割は関心数で判断)に従う。

## 1. M5 のスコープと目的

### 1.1 スコープ(SUPP-001 §4.1)

| 項目 | 内容 |
|------|------|
| 主スコープ | コンボ比較画面(DES-005 §5.8)の新規実装 |
| 副スコープ | コンボ一覧画面・マイコンボ画面への「比較対象選択モード」追加(比較画面への遷移動線、DES-005 §5.4 item 6) |
| 関連 FR | FR008(コンボ比較表示、必須)、FR203(表示項目の選択は本 M5 で実装しない、表示項目は §5.8 規定の 11 種全件常時表示) |
| 関連設計書 | DES-005 §5.4(コンボ一覧の選択モード)、DES-005 §5.5(マイコンボの選択モード、§5.4 と同様)、DES-005 §5.8(コンボ比較画面) |

### 1.2 目的(M5 完了時に達成される状態)

- コンボ一覧画面・マイコンボ画面で複数コンボを選択して比較画面に遷移できる
- コンボ比較画面で DES-005 §5.8 表示項目 11 種が常時横並び表示される
- 比較対象を画面上で追加・削除できる(別窓モーダルでコンボ追加、行削除ボタンで除外)
- 比較対象の上限が 5 件で、上限超過時に Toast 通知が表示される(上限値は定数化で拡張性確保)
- PC レイアウト(表形式横並び)で動作する(スマホ向けレスポンシブは M7 持ち越し、§2.8 参照)

### 1.3 このマイルストーンで作らないもの

- **エクスポート機能**(FR402〜FR404、PDF / PNG / リッチテキスト): フェーズ 2 送り、本 M5 ではエクスポートボタン UI も実装しない
- **CSV エクスポート / インポート**: SUPP-001 §4.4 でフェーズ 2 送り確定済み
- **`POST /api/combos/compare` API**: CHANGE-015(2026-05-23)で DES-002 §4.2 から削除済み、案 1(既存 `GET /api/combos/{id}` を N 件並列呼出)採用
- **比較対象の自動候補提示**: FR008 で「フェーズ 1 では採用しない」と明記、手動選択方式のみ
- **比較画面での表示項目選択**(FR203 の一部): 11 項目すべて常時表示、ユーザーによる表示項目の選択 UI は本 M5 では実装しない(コンボ一覧画面の表示列カスタマイズ機能とは別)
- **スマホ向けレスポンシブ実装**(DES-005 §5.8 §4.4 規定のスマホ向けレイアウト = 横スクロール表 / 縦並びカード形式の切替): SUPP-001 §4.1 M7「レスポンシブ仕上げ」のスコープに含まれるため、M5 では実装しない。M5 期間中はスマホからのアクセス手段が未整備(M6 でホーム画面(スマホ)・LAN 共有バインドが実装されるまで開発者によるスマホ表示確認ができない)= スマホ向け実装を本マイルストーンで進めても確認できないため、M7 にまとめる方針。本 M5 は **PC レイアウトのみ実装**(DES-005 §5.8 の論理構造に従う、PC では表形式横並び)
- **持ち越し確認課題 C-2 / C-3 / C-4 / L-02 / L-03**(m4-to-m5-handover §3 / §4): M5 スコープ外、m5-to-m6-handover.md で次工程へ引き継ぐ
- **playbook 改訂**: M5 着手時には playbook を改訂しない(m4-to-m5-handover §4.5 推奨踏襲、M5 期間中盤以降に必要時のみ判断)

## 2. 主要設計判断(本 overview で確定)

### 2.1 案 1 採用(`POST /api/combos/compare` を実装しない、既存 API 流用)

CHANGE-015(2026-05-23)で確定済み。

- 比較画面は **既存 `GET /api/combos/{id}` を N 件並列呼出**(TanStack Query の `useQueries` 使用)で実現
- バックエンド新規実装ゼロ
- M5-RESEARCH-01 §4.1 で `ComboResponse` の全フィールドが比較画面表示項目 11 種に対応可能と確認済み
- レシピ表示は `defaultRecipe`(既定プリセット解決済み文字列)を使用(`recipeCache` は API レスポンスから除外されているため、調査結果 §4.1 (c) 特記 1)

### 2.2 比較対象上限 5 件、定数化で拡張性確保

- `web/src/constants/compare.ts`(新規)に `MAX_COMPARE_COMBOS = 5` を定義
- 上限増減時は定数変更のみで全コード反映
- バックエンドには上限ロジックを持たせない(案 1 採用に伴う)
- フロント側で `selectedIds.length >= MAX_COMPARE_COMBOS` 判定 + 上限到達時に「比較」ボタン無効化 + Toast 通知(既存 topMessage パターン流用、M4-03 で確立)

### 2.3 `useQueries` 初導入

- M5-RESEARCH-01 §4.3 で本プロジェクト未使用が確認された
- TanStack Query 標準機能のため技術的問題なし
- `web/src/features/combo/hooks/useCompareCombos.ts`(新規)に集約
- 後続マイルストーンで類似の N 件並列取得が必要になった場合の **参照実装** として位置付け(m5-to-m6-handover で記録予定)

### 2.4 queryKey 整合性

- `useCompareCombos` 内部で各 ID について **既存 `useCombo` の queryKey `["combo", id]` をキャッシュ共有**(architecture-patterns.md v1.0.3 §1.1、combo 系 flat tuple 形式)
- 比較画面 → コンボ詳細画面遷移時に **キャッシュヒットで体感速度向上** が見込まれる(M5 で追加の最適化は不要、自然に発生する効果)

### 2.5 選択モードはコンボ一覧 + マイコンボの両方に実装

- DES-005 §5.4 item 6「選択モードトグル」を **両画面で実装**(マイコンボは §5.5「アクション: コンボ一覧と同様」より自然に派生)
- 共通フック化を **検討するが現時点では強制しない**: 各画面で `useState<number[]>` で持つシンプル実装でも YAGNI 観点で許容、M5-01 指示書本体で「共通フック化が自然か / 個別実装が自然か」を製造担当が判断する余地を残す(Plan Mode 案件)
- ゴミ箱画面の `selectedIds`(M2-03 実装、一括復元・永久削除用)とは **別機能として実装**: 用途も挙動も異なるため YAGNI で分離維持(M4-12 LinkExistingSetupModal / SetupSelectorModal 分離判断と同パターン)

### 2.6 shadcn/ui 未導入のまま実装

- playbook §17.2 / handover §6.5 / M5-RESEARCH-01 §4.7 で M7 まで未導入が確定
- 標準 HTML + Tailwind の自作ラッパーで実装(M2 / M3 / M4 で確立済みのパターン踏襲)
- Toast 通知は既存 `topMessage` パターン流用(M4-03 由来)

### 2.7 ルーティング(方式 X: URL クエリパラメータ採用)

- 新規ルート `/compare?ids=1,2,3` を追加(M5-RESEARCH-01 §4.4 で予約なし確認済み)
- クエリパラメータ方式(方式 X)を採用する根拠(本 v1.0.1 で正式確定):
  - **他画面との統一性**: M3-03 で `useComboListFilters` が URL SearchParams 操作の確立済み実装(M5-RESEARCH-01 §4.2 (a) で確認) = 既存パターン踏襲
  - **リロード時に比較状態が維持される**(URL に状態を持つ)= UX 観点で重要
  - **URL 共有で比較状態を再現可能**: REQ-001 NFR306「LAN 内のスマホ利用が主要ユースケース」と整合(ただし本 M5 ではスマホ向けレイアウト未実装、URL 共有自体は M7 完了後に本格活用)
  - ブラウザ戻る・進むで比較状態履歴を辿れる
  - REST 的に自然(GET 動線の延長)
- 採用しなかった案(方式 Y: React state ベース、URL は `/compare` 固定): リロードで比較状態が消える / URL 共有不可 / 既存パターンと不整合のため不採用
- 「コンボ追加」モーダル経由で ids が増減した場合、URL を `useSearchParams` の `setSearchParams` で更新

### 2.8 レイアウト方針(PC のみ実装、スマホ向けレスポンシブは M7 持ち越し)

- **PC レイアウト**: 表形式(`<table>` または CSS Grid)、横方向に比較対象、縦方向に表示項目 11 行
- **スマホ向けレスポンシブ実装は本 M5 で実施しない**(本 v1.0.1 で確定、解釈 B 採用):
  - SUPP-001 §4.1 で M7「レスポンシブ仕上げ」がスコープに含まれている
  - M5 期間中はスマホからのアクセス手段が未整備(M6 でホーム画面(スマホ)・LAN 共有バインドが実装されるまで)= 開発者がスマホでの動作確認をできない時期に実装しても検証不可
  - DES-005 §5.8 規定の「スマホ: 横スクロール可能な表、または縦並びカード形式(切替可能)」の論理構造は M7 で実装
  - 関連: REQ-001 NFR306「レスポンシブ対応」は最終的に必須要件(M7 完了時点で達成)
- **本 M5 で実装するのは PC レイアウトのみ**: Tailwind のブレークポイント(`md:` 等)による条件付きスタイルは **必要最小限**(例: コンテナの最大幅指定など)に留め、スマホ向けの専用レイアウト切替は実装しない
- **持ち越し**: スマホ向けレイアウト実装は M7「レスポンシブ仕上げ」で全画面通しての対応として行う。本 M5 完了時の handover (m5-to-m6-handover.md) で持ち越し課題として記録

## 3. サブマイルストーン分割

### 3.1 分割方針(案 a 採用、関心数 3 つを 1 サブマイルストーンに収める)

m4-to-m5-handover §6.5「指示書サイズの目安: 関心数 3 つを超えるなら分割検討」+ playbook §7.1「Sonnet 適性: 関心の数 1〜3 機能」に従い、M5 の関心数 3 つを 1 サブマイルストーン(**M5-01**)に集約する。

#### 関心数の内訳(本 overview で確定)

| # | 関心 | 規模感 |
|---|------|------|
| 1 | コンボ比較画面本体(新規画面、表示項目 11 種、PC レイアウト) | 中 |
| 2 | 比較対象選択モード(コンボ一覧 + マイコンボ拡張、共通化判断は製造担当に委ねる) | 中 |
| 3 | 比較画面への遷移動線 + コンボ追加モーダル + 統合 E2E | 中 |

合計関心数 3、playbook §7.1 Sonnet 適性ボーダー内。

### 3.2 採用しない案

| 案 | 内容 | 不採用理由 |
|---|------|----------|
| 案 b(統合 E2E を別サブマイルストーンに分離、M5-01 / M5-02 の 2 分割) | M4-05 パターン踏襲(本体 + 統合 E2E 分離) | M4-04 / M4-05 は同時登録機能 + L-01 解消 + C-1 解消で関心数 4+ だったが、M5 は関心数 3 で 1 サブマイルストーンに収まる。分割すると M5-02 の DoD が「E2E 実機確認のみ」となりサブマイルストーン化のオーバーヘッドが過大 |

## 4. モデル配分案

playbook §7.1 判断ヒューリスティック + handover §1.1 M4 配分実績を踏まえた配分案。

| サブマイルストーン | 実装モデル | レビューモデル | 配分理由 |
|------------------|----------|--------------|--------|
| M5-01 | **Sonnet 4.6** | Sonnet 4.6 | 関心数 3、新規 API 実装なし、フロント中心(useQueries 初導入はあるが TanStack Query 標準機能で技術的難易度は低)、既存パターン(画面新規 + 選択モード追加)の応用が中心。M3-04(マイコンボ画面、Sonnet 4.6 で完結)と同規模感 |

### 4.1 Opus 推奨に該当しない判断根拠(playbook §7.1)

- 既存ロジック再利用の整合確認: 4 関数未満(`useCombo` / `useCharacters` / `useComboListFilters` / `useColumnVisibility` 等を参照する程度、既存ハンドラ層・サービス層に変更なし)
- 編集 2 方式分離のようなモード分岐の設計判断なし
- 整合性違反時のリスク: フロント層のみのため、データ破壊リスクなし
- 設計判断のオプションが 3 案以上の領域は本 overview で確定済み(案 1 採用、案 a 採用)
- 同時に変更するファイル数: 8〜10 ファイル想定(画面新規 + 選択モード追加 + フック + 定数)、Sonnet ボーダー内
- 統合・仕上げの複数関心の絡みなし(M5 単体で完結)

### 4.2 1 の調査結果による再評価条件(m4-to-m5-handover §7.2 余地)

M5-RESEARCH-01 結果を踏まえた現時点の判断は Sonnet 4.6。**製造担当 Plan Mode で以下のいずれかが顕在化した場合、Opus 4.6 への切替を再評価**:

- `useQueries` のエラーハンドリング設計が想定より複雑化した場合(個別クエリ失敗時の表示挙動等)
- 選択モードの共通フック化判断で重複コードが大規模に発生する場合
- PC レイアウトのテーブル設計で 11 行 x 5 列のスクロール挙動・スティッキーヘッダ実装が想定より複雑化した場合

判断は M5-01 製造担当 Plan Mode 段階で開発者と協議。

## 5. リスクと対策

### 5.1 useQueries 初導入(技術リスク低)

- **リスク**: 本プロジェクト未使用、エラーハンドリング・ローディング表示の集約方針が確立されていない
- **対策**: M5-01 指示書 §4.x で `useQueries` 利用方針を明文化(各クエリの個別エラー扱い、全体ローディング判定、空配列時の挙動)。製造担当 Plan Mode で確認

### 5.2 比較画面の縦長化(UX リスク低、handover §3.1 C-2 と類似性質)

- **リスク**: 比較対象 5 件 x 表示項目 11 行 = PC 表形式でも縦に長くなる傾向(スマホ向け実装は本 M5 ではスコープ外、§2.8 参照)
- **対策(M5 期間)**: M5-01 指示書本体でスティッキーヘッダ(項目名列)の採用是非を製造担当 Plan Mode で判断(playbook §17.1 個人 OSS の規模感に応じた YAGNI 判断)。仕様確定は本 overview ではせず、製造担当裁量に委ねる
- **持ち越し可能性**: PC レイアウトで許容範囲なら維持、UX 違和感が顕在化したら M7「レスポンシブ仕上げ」と合わせて再調整(m5-to-m6-handover §3 で C-2 と同系統の持ち越し候補として記録)

### 5.3 選択モードの状態管理範囲(YAGNI 違反リスク低)

- **リスク**: コンボ一覧 + マイコンボの 2 画面に同じ選択モードを実装するため、共通フック化の誘惑が発生(M4-5 mode prop YAGNI 違反と同パターンの構造)
- **対策**: M5-01 指示書 §4.x で「**現時点で共通化が自然なら共通フック化、個別 useState が自然なら分離維持** を製造担当 Plan Mode で判断」と明記(playbook §17.1 個人 OSS の規模感 + M4-12 由来 YAGNI 教訓)

### 5.4 レシピ表示の動的プリセット解決対応(機能不足リスク低)

- **リスク**: 比較画面のレシピ列が `defaultRecipe`(既定プリセット解決済み)のみで、ユーザーが現在選択中プリセットでの解決済みレシピを見たい場合の動的解決が未実装
- **対策**: M5 では `defaultRecipe` で要件充足(コンボ一覧 §5.4 と同パターン、M3-05 で確立)、動的解決は要件として明示されていないため M5 スコープ外。必要性が顕在化したら m5-to-m6-handover で持ち越し候補として記録

### 5.5 M4 期間最頻出パターン「実コード確認の省略」の再発リスク(中)

- **リスク**: M4-1〜M4-18 で 9 件発生した「設計担当が実コードを確認せず指示書を書く」パターンの再発
- **対策**:

### 6.5 設計担当の前提資料確認原則(M5-1 反省由来、本 v1.0.1 で新設)

M5-overview v1.0.0 ドラフト作成時に、設計担当(本セッション)が **SUPP-001 §4.1 M7「レスポンシブ仕上げ」記述および REQ-001 NFR306 を確認せず、レスポンシブ切替方針(旧 §2.8)を M5 スコープとして組み込んだ事象** が、開発者ご指摘で発覚した(2026-05-23)。

- **教訓**: overview / 指示書ドラフト作成時、スコープ判断に関わる節は **SUPP-001 §4.1 マイルストーン分割表 + REQ-001 関連 NFR + 関連 DES の「レスポンシブ」等の節** を **少なくとも一度は grep で実態確認** してから判断を組み込む

- **記録予定**: M5 完了時の retrospective-log v1.0.17 §5.1 に「M5-1: M5-overview ドラフト作成時の前提資料確認漏れ(SUPP-001 §4.1 / REQ-001 NFR306)」として独立記録する。本セッション内では記録のみ、retrospective-log の正式改訂は M5 完了時の正規ルートで実施
