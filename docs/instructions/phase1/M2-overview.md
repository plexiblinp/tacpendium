## 1. 本書の位置づけ

SUPP-001 §4.1 で M0〜M7 のマイルストーン全体が定義されている。本書は M2(編集系の本格化)を **4つのサブマイルストーン(M2-01〜M2-04)** に細分化した構成と相互関係、および M1 振り返り(RETRO-002)を踏まえた M2 期間中の運用ルールを示す。

各指示書を実装する Claude Code は、本書を読むことで「自分の作業範囲」「依存関係」「M2 で扱わないもの」「M1 反省点を踏まえた運用ルール」を把握できる。

M2 は **直列実行** で進める(後述 §4)。M1 期間で得た並列実行の課題(RETRO-002 §2.2)を踏まえた判断であり、M2-01 → M2-02 → M2-03 → M2-04 の順に1本ずつ着実に完了させる。

## 3. 各サブマイルストーンの概要

本節は M2-overview としての全体像を示す。**詳細仕様・成果物・テスト要件は各指示書本体(後続作成)に記述する**。本節の記述と指示書本体に差異がある場合、指示書本体が優先される。

### 3.1 M2-01: 仮想コントローラとmodifiers 編集 UI 格上げ

**目的**: M1-06 で「技セレクタ + 追加ボタン」レベルにとどめていたレシピ入力 UI を、レバーレス配置の仮想コントローラに置き換える。あわせて modifiers 編集 UI を「ステップ追加時のオプション選択」から「ステップ行から開けるポップアップ/ドロワー」に格上げする(DES-005 §6.7)。

**スコープに含むもの**:

- 仮想コントローラ(レバーレス1種のみ、SF6 デフォルトのレバーレス配置に従ったボタン配置レベル)
- 論理ボタン群(DES-005 §6.2)を画面に並べ、クリックでステップ追加ができる動作
- modifiers 編集 UI のポップアップ/ドロワー化(既存ステップの flags / type / notes を編集可能に)
- 現状の RecipeBuilder からの差し替え

**スコープに含まないもの**:

- レバーレス以外のレイアウト(アケコン、PS5パッド、キーボード)— M7 仕上げで実装
- ビジュアル仕上げ・スタイル統一 — M7 で実装
- 同時押し判定の時間窓・チャタリング対策 — フェーズ2(物理コントローラと一緒に)
- modifiers.notes の **画面表示処理** — M2-04 で対応(ここでは編集 UI のみ)

**前提**: M1-06 の `RecipeBuilder.tsx` および `StepRow.tsx` が動作している。

**推奨モデルの根拠**: UI 配置作業中心、ロジック新規性は modifiers 編集 UI 程度。Sonnet 4.6 の生成速度が活きる(RETRO-002 §3.2 の「過剰な Opus を避ける」方針)。

**Plan Mode 任意の根拠**: 既存 RecipeBuilder の拡張で範囲が明確、設計書(DES-005 §6.2 / §6.7)で論理ボタン群が定義済み。

### 3.2 M2-02: 編集系 UX 改善

**目的**: コンボの登録・編集における UX を、設計書記載のレベルまで引き上げる。M1 では最小実装にとどまっていた以下を本格化する。

**スコープに含むもの**:

- **コピー機能(FR012)**: コンボ一覧・コンボ詳細からの「コピー」操作。コピー元コンボの全情報を新規登録フォームに初期値投入し、ユーザーが差分を編集して保存する動線を実装(DES-005 §5.7「コピーモード」、HANDOVER-001 §3.2 参照)
- **重複検知 API の新設とリアルタイム警告**: 既存 API(`POST /api/combos`)とは別に、保存前のチェック専用エンドポイントを新設(例: `POST /api/combos/check-duplicate`)。フロントは入力中に300msデバウンスで叩き、重複時は画面上部に動的警告表示(DES-005 §5.7「リアルタイム重複検知」)
- **仮登録 ⇔ 本登録の昇格 UI**: コンボ詳細画面または編集画面から「本登録に昇格」ボタンで仮登録→本登録へ切替(FR010)。逆方向(本登録→仮登録)の扱いについては Plan Mode で開発者と確認する事項
- **PUT 時(キー変更編集)の確認ダイアログ**: 「この編集はコンボの再登録となります(古いコンボはゴミ箱へ移動)。続行しますか?」の確認モーダル(M1-06 §4.4.3 で文言は提示済みだが、実装は M2 に持ち越し)

**スコープに含まないもの**:

- knockdown_advantage 変更時のセットプレイ引き継ぎ確認モーダル(DES-005 §5.7)— M4 でセットプレイが実装される前提のため、M2 では実装しない。ただし将来の差し込みポイントは TODO コメントで残す
- セットプレイ同時登録(DES-005 §5.7 item 10)— M4 で実装
- タグ新規作成 UI — M3 で実装

**前提**: M2-01 が完了している。

**例外条項(指示書 §2.4 で明記予定)**:

- バックエンドへの追加: 重複検知 API(`POST /api/combos/check-duplicate`)の新設は本指示書のスコープに含む
- 既存 API(POST/PATCH/PUT/DELETE /api/combos)の修正は原則行わない
- 必要が生じた場合、Plan Mode で開発者と確認の上で範囲を確定

**推奨モデルの根拠**: 編集2方式分離の応用 + コピーモード + 重複検知 API 新設(バックエンド変更を伴う)+ 昇格 UI と複数の関心が絡み、設計書の解釈・整合確認の負荷が高い。Opus 4.6 + Plan Mode 必須が妥当(SUPP-001 §6.1 の M2 配分案と整合)。

### 3.3 M2-03: ゴミ箱画面

**目的**: M1 では「論理削除はされるが UI なし」だったゴミ箱機能を、画面として完成させる(DES-005 §5.15、SUPP-001 §4.1 で明示された M2 スコープ)。

**スコープに含むもの**:

- `/trash` ページの新設(DES-005 §5.15 準拠)
- 論理削除済みコンボの一覧表示(削除日時、自動完全削除までの残日数)
- 一行クリックで読み取り専用のコンボ詳細表示
- 復元ボタン(`POST /api/combos/:id/restore`、M1-03 で実装済み)
- 完全削除ボタン(API 新設の可能性あり、後述 §例外条項)
- 一括復元・一括完全削除ボタン

**スコープに含まないもの**:

- ゴミ箱内のセットプレイの扱い(M4 でセットプレイが実装される前提)
- 自動物理削除(90日超過分)の cron 的バックグラウンド処理 — フェーズ2以降
- 復元時の重複競合(復元しようとしたコンボと同じキー値のコンボが既に存在するケース)の詳細 UI — Plan Mode で開発者と方針確認

**前提**: M2-02 が完了している。

**例外条項(指示書 §2.4 で明記予定)**:

- 完全削除 API(`DELETE /api/combos/:id/permanent` 等)は M1-03 で未実装である。本指示書で新設する想定だが、Plan Mode で開発者と最終確認する
- 復元時の `RecomputeComboCache` 呼出整合(SUPP-001 §7.2)を確認(M1-04 の notation サービスを呼ぶ箇所が論理削除時に対応する形になっているか、復元時も対称的に動作するかを実装時に確認)

**推奨モデルの根拠**: M1-05 のコンボ一覧画面を参考に作れる定型作業。`RecomputeComboCache` 呼出の整合だけ注意点。Sonnet 4.6 で十分。

### 3.4 M2-04: 統合・仕上げ(modifiers.notes 表示、M2 全体 E2E)

**目的**: M1 で実装漏れた **modifiers.notes の画面表示処理**(m1-known-limitations.md)を統合実装し、M2 全体の動作確認を完了する。M1 の責任所在曖昧による実装漏れの再発防止として、本サブマイルストーンを独立指示書として切る(RETRO-002 R-03 参照)。

**スコープに含むもの**:

- **バックエンド側**: `internal/service/notation/resolver.go` で notes を出力テキストに組み込む処理を追加(SUPP-001 §3.3.4 の方針に従う)
- **フロントエンド側**: `web/src/features/combo/components/ComboDetailRecipe.tsx` で `step.modifiers.notes` を読み取って画面表示する処理を追加
- 表示形式: **括弧付きインライン表示**で実装(SUPP-001 §3.3.4 の2案のうち、開発者により採択済み)
- M2 全体の手動 E2E 確認(M2-01 → M2-02 → M2-03 が統合された状態で、登録→コピー→編集→ゴミ箱→復元→詳細表示まで一連動作を確認)

**スコープに含まないもの**:

- modifiers.notes の検索・フィルタ対応(SUPP-001 §3.3.4 で「検索対象にしない」と明記)
- notes の文字数 DB 制約追加 — UI 側の警告表示のみ(SUPP-001 §3.3.4)

**前提**: M2-01、M2-02、M2-03 が完了している。

**実装の責任所在を明示する**(RETRO-002 R-03 への対策):

| 修正対象ファイル | 内容 |
|----------------|------|
| `internal/service/notation/resolver.go` | notes を出力テキストに組み込むロジック追加 |
| `web/src/features/combo/components/ComboDetailRecipe.tsx` | notes を画面表示するロジック追加 |

両方の修正が完了して初めて M2-04 完了とする。片方だけでは DoD 未達成。

**推奨モデルの根拠**: 範囲が明確、修正箇所が限定的、E2E 確認が中心。Sonnet 4.6 で十分。

## 4. 実行順序と依存関係

```
M2-01(仮想コントローラ)
  ↓
M2-02(編集系 UX 改善)
  ↓
M2-03(ゴミ箱画面)
  ↓
M2-04(統合・仕上げ、notes 表示)
  ↓
M2 完了
```

**直列実行**: M2 は **完全直列** で進める。並列実行は採用しない。

直列を採用する根拠(RETRO-002 §2.2 / §3.1 を踏まえた開発者判断):

- M1 期間で並列実行のペナルティ(worktree セットアップ、マージ衝突、認知負荷増、健康影響)が想定を超えた
- 1人プロジェクトで安全に管理できる同時稼働ターミナル数が3本(Web版1 + 製造1 + レビュー1)であることが判明
- M2 の各サブマイルストーンは前のサブマイルストーンの成果物に依存しており、独立性が低い

各サブマイルストーン完了後に開発者が動作確認・承認を行ってから次に進む。M1-overview の §3 にあったような並列実行時の競合に関する注意は M2 では不要。

## 6. M1 反省点を踏まえた M2 運用ルール

RETRO-002 で抽出された反省点のうち、M2 期間中に運用として組み込むものを列挙する。本ルールは M2 指示書本体・レビューチェックリスト・製造担当の実装フローに反映される。

### 6.1 設計書本体との照合(RETRO-002 R-01 対応)

**指示書作成時(設計担当)**:

- 各 DTO・構造体・マイグレーション SQL に、対応する設計書節を引用元として併記する(例: 「`combos` テーブルの定義は DES-003 §3.4 に従う」レベルに加え、可能な限り具体的に節を指定)
- 指示書作成時、設計書本体を view ツールで開いて該当節を確認する
- 推測で書いた箇所には「**推測。設計書 §X.Y との整合性を要確認**」と明記する

**製造担当の実装時**:

- 指示書に書かれた設計書節を view ツールで開いて、フィールド名・型・制約を確認してから実装する

**レビュー担当のレビュー時**:

- レビューチェックリストの先頭項目として「**設計書本体との照合**」を必ず含める
- 各 DTO・構造体・マイグレーション SQL が設計書節と一致するかを機械的に確認する

### 6.2 禁則表現の根絶(RETRO-002 R-02 対応)

指示書で以下の表現を使用しない:

- 「あれば」「(あれば)または」
- 「必要に応じて」
- 「実装時に決定」
- 「任意で」
- 「適切に」
- 「既に〜していれば不要」

判断保留する場合は、以下のいずれかの形式で書く:

- 「**Plan Mode で製造担当が開発者に方針提示し、開発者が決定する**」
- 「**M2-XX 着手時に開発者と協議して決定する**」
- 「**実装時に Claude Code と開発者の協同で決定する(SUPP-001 §6.1 協同方針)**」

「条件付き OK」を書くときは、条件を満たさない場合の動作も必ず明記する。

### 6.3 例外条項の明示(RETRO-002 R-03 対応)

各 M2 指示書テンプレートに以下の節を初期から組み込む:

- §2.3 変更しないもの(原則)
- §2.4 例外: バックエンドへの最小限の追加が許容される箇所(該当する場合のみ記述、なければ「該当なし」と明記)

フロント指示書を書く際、必要な API が既存指示書群で実装されているかを逆算チェックし、不足が判明した場合は §2.4 で「本指示書で新設する」または「別指示書で先行実装される」のいずれかを明記する。

M2 では特に M2-02 の重複検知 API、M2-03 の完全削除 API(可能性あり)が該当する。

### 6.4 E2E シナリオの必須化(RETRO-002 R-09 対応)

各 M2 指示書の §5「テスト要件」に **E2E シナリオ** 節を必ず含める。形式は以下:

```
## E2E シナリオ
1. /combos/new で新規コンボを開く
2. 技ステップに notes("テスト") を入力
3. 保存
4. 詳細画面で notes が表示されている  ← これが見えるまで DoD 不達成
```

DoD は「動作する」だけでなく「**設計意図通りの振る舞いを示すこと**」レベルで定義する。

各指示書完了時に、開発者がそのシナリオを実際に手動実行して合格判定する。

### 6.5 製造担当の DoD テンプレート(RETRO-002 R-09 §3.2.1 対応)

各 M2 指示書の §7「完了条件(Definition of Done)」に、以下のテンプレートを組み込む。製造担当は実装完了報告時に、以下のチェック結果を報告書に貼付する。

#### 6.5.1 機能要件(指示書ごとに具体化)

- [ ] §2 のファイル一覧が全て作成されている
- [ ] 主要機能が動作する(指示書ごとに具体的に列挙)
- [ ] §5 の E2E シナリオが全て通過する

#### 6.5.2 自己テスト結果(全指示書共通)

製造担当は実装完了時に、以下を実施し報告する。

**バックエンド指示書の場合**:

- [ ] `make test` が全通過する
- [ ] 主要 API を `curl` で叩き、レスポンスを報告書に貼付する
- [ ] エラーケース(400 / 404 / 409 / 500)を `curl` で再現し、レスポンスを報告書に貼付する
- [ ] データ整合性: 登録した内容を `GET` で取り直し、入力と一致することを確認する

**フロントエンド指示書の場合**:

- [ ] `pnpm test`(Vitest)が全通過する
- [ ] `pnpm build` が成功する
- [ ] TypeScript の型エラーが残っていない
- [ ] 開発サーバー起動時にコンソール警告(React の key 警告等)が新規発生していない
- [ ] 主要ロジック(form のバリデーション、状態遷移など)を Vitest + React Testing Library のユニットテストで検証する
- [ ] 開発者向けの「動作確認手順書」を実装完了報告に含める(開発者がブラウザで E2E シナリオを通す際のステップ・確認ポイント・想定される画面表示)

なお、ブラウザでの実機動作確認・画面遷移確認・スクリーンショット取得は **開発者の責任範囲** であり、製造担当 Claude Code はターミナル環境のため実行不可。製造担当は上記の Vitest 中心のテストで自己責任範囲を果たす。

#### 6.5.3 品質チェック(全指示書共通)

- [ ] CLAUDE.md の禁止事項(localStorage 使用等)に抵触していない
- [ ] `console.log` / `fmt.Println` を本番コードに残していない
- [ ] 設計書本体(該当節)と実装が一致している(差異がある場合は CHANGE 起票を提案)

#### 6.5.4 完了報告

- [ ] 開発者に「M2-XX が完了しました」と報告
- [ ] 上記の自己テスト結果を報告書に含める

### 6.6 レビューチェックリストの強化(RETRO-002 R-08 §3.2.2 対応)

各 M2 指示書のレビューチェックリストに以下の項目を必須で含める:

- **設計書本体との照合**: 各 DTO・構造体・マイグレーション SQL が DES-X §X.Y と一致するか
- **API 整合性**: リクエスト/レスポンスの型が DTO・フロント側 hook と整合するか
- **バリデーション動作確認**: 各 VAL-ID がエラー条件で発火することを確認
- **エラーハンドリング網羅**: 各エラーシナリオ(400/404/409/500)で、設計書(DES-002 §4.3、DES-006)に従ったレスポンスとUI表示が行われるか
- **設計意図との整合**: チェックリストの機械的チェックを超えた、設計書の文脈理解に基づく整合性

レビュー担当 Claude には、上記項目を「機械的にチェックするだけでなく、設計意図との整合を読み取る」ことを明示的に依頼する。

### 6.7 段階的 E2E(RETRO-002 R-09 §3.2.3 対応)

「全部完了してから E2E」ではなく、**各指示書完了ごとに動作確認**する運用に変更する:

- バックエンド指示書: 製造担当が `curl` でコア API を叩き、期待レスポンスが返るかを自己テストとして実施
- フロント指示書: 開発者がブラウザで該当画面を開き、§5 の E2E シナリオを通す
- 各サブマイルストーン完了後に開発者が承認してから次のサブマイルストーンに進む(直列実行と整合)

M2-04 で M2 全体の統合 E2E を実施する。

### 6.8 製造担当 Q&A の運用(RETRO-002 R-14 対応、参考)

製造担当(Claude Code)が Plan Mode で質問してきた場合、設計担当(M2 期間担当)は以下のフローで対応する:

1. 質問内容を評価(設計書・SUPP-001・指示書本体を参照)
2. 開発者に判断を仰ぐ(複数案提示、推奨を明示)
3. 開発者の判断を踏まえて回答案をコピペ用で作成
4. 回答内容に応じて指示書を修正・バージョンアップ(指示書本体に反映が必要な判断の場合)

回答テンプレート(参考、設計担当の状況に応じて使用):

```
## 結論: 案X を承認

## 承認理由
(製造担当の判断との一致、設計書との整合性、他案を採用しない理由)

## 実装方針
(具体的な実装範囲、ファイル列挙、レスポンスフォーマット等)

## お詫び(指示書ミス起因の場合)
(指示書の不備を認め、修正方針を伝える)

## 指示書更新
(バージョン、変更内容)
```

## 8. 完了判定

各サブマイルストーンの完了は以下の条件を全て満たすこと:

- 指示書 §7「完了条件(Definition of Done)」の機能要件・自己テスト結果・品質チェックを全て満たす
- 指示書 §5 の E2E シナリオが全て通過
- レビューチェックリスト(別ファイル)で重大な問題がないと確認される
- 開発者が動作確認の上で承認する

M2 全体の完了は、M2-01〜M2-04 全ての完了をもって判定。M2 完了時点で以下が達成される状態とする:

- レバーレス仮想コントローラでレシピ入力ができる
- modifiers の編集 UI が「ステップ行のポップアップ/ドロワー」で動作する
- modifiers.notes が画面に表示される(M1 既知制限事項の解消)
- コンボのコピー機能が動作する(FR012)
- 編集中のリアルタイム重複警告が動作する(DES-005 §5.7)
- 仮登録 ⇔ 本登録の昇格が UI から実行できる(FR010)
- PUT 編集時の確認ダイアログが表示される
- ゴミ箱画面でコンボの復元・完全削除が可能(DES-005 §5.15)

M2 完了後、`m2-to-m3-handover.md`(または同種の引き継ぎメモ)を作成して M3 着手準備に入る(RETRO-002 §3.6 の節目設定に従う)。
