## 1. 背景と目的

### 1.1 背景

#### 1.1.1 系統 A: CHANGE-019 クリーンアップ

CHANGE-019(2026-06-03 反映済み)で、`combos.drive_gauge_consumed_total` / `sa_gauge_consumed_total`(ドライブ/SA ゲージ消費量キャッシュ)を設計書本体から削除した。本指示書はこの設計変更を実装に反映する = コードベースから当該 2 カラムおよび全関連シンボルを削除する。

削除の根拠と安全性:
- 当初「コンボ登録・編集時に combo_steps から自動集計」する設計だったが集計ロジックが未実装で **全行 NULL**(M7-RESEARCH-03)
- 2026-06-02 開発者方針転換: 消費量は有意義でないため削除
- M7-RESEARCH-04(2026-06-03)で削除影響を全数調査: **47 箇所特定 / 書き込み経路なし(データ損失なし)/ 機能影響なし**(ソートは全行 NULL で実質不能、CSV 未実装、詳細は開始残量表示、比較画面は §5.8 に消費行の規定なし)

#### 1.1.2 系統 B: バグ #5 修正

M7-02 E2E 中に発見された既存バグ #5(M7-02 起因ではない、Q20 (Y) で M7-04 編入):

> 仮登録コンボ(`is_draft = true`)を本登録に昇格する際、レシピが空(VAL-C09 = ERROR)等のバリデーションエラーで HTTP 400 が返るが、フロント側でこれが「HTTP500 のような」「ボタンのような形」の崩れたエラー表示になる。正しくは 400 のバリデーションエラー内容を通常のエラー表示として見せるべき。

= フロントのエラーハンドリングの不統一。本登録昇格ボタン(PromoteToFinalButton 相当)の 400 レスポンス処理を、他のバリデーションエラー表示と統一する。

> 本修正は **バグ #6(M7-05 編入、レシピなしセットプレイ登録時のエラー表示なし、VAL-S02 由来 HTTP 400)と共通のフロントエラーハンドリング統一パターン**(retrospective-log §6.6)。M7-04-1 で確立したパターンを M7-05 のバグ #6 が踏襲する想定のため、**汎用的に再利用しやすい形**で実装すること。

#### 1.1.3 受領済み資料

- **M7-RESEARCH-04 調査結果レポート**(`docs/progress/M7-RESEARCH-04-report.md`)= 削除箇所マップの正本(47 箇所、§1〜§4)
- CHANGE-019 通知書(`docs/change-notes/CHANGE-019-gauge-consumed-total-removal.md`)= 設計変更の根拠
- CHANGE-019 反映後の設計書本体 4 ファイル(REQ-001 v2.13.0 / DES-003 v1.15.0 / DES-005 v2.12.0 / DES-006 v1.10.0)
