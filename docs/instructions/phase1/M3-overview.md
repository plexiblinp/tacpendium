## 1. 本書の位置づけ

SUPP-001 §4.1 で M0〜M7 のマイルストーン全体が定義されている。本書は M3(マイコンボ系)を **5つのサブマイルストーン(M3-01〜M3-05)** に細分化した構成と相互関係、および M2 完了時点で確立した運用ルール(playbook v1.0.0、m2-to-m3-handover で抽出された反省点)を踏まえた M3 期間中の運用方針を示す。

各指示書を実装する Claude Code は、本書を読むことで「自分の作業範囲」「依存関係」「M3 で扱わないもの」「M2 反省点を踏まえた運用ルール」を把握できる。

M3 は **直列実行** で進める(後述 §4)。M1 期間で得た並列実行の課題、M2 期間で確立した直列実行の安定性(playbook §15)を踏まえた継続判断であり、M3-01 → M3-02 → M3-03 → M3-04 → M3-05 の順に1本ずつ着実に完了させる。

## 3. 各サブマイルストーンの概要

本節は M3-overview としての全体像を示す。**詳細仕様・成果物・テスト要件は各指示書本体(後続作成)に記述する**。本節の記述と指示書本体に差異がある場合、指示書本体が優先される。

### 3.1 M3-01: タグ機能(バックエンド + 管理 UI、初期タグ seed 投入)

**目的**: タグ管理機能のバックエンド・フロントを M3 全体の土台として整備する。マイコンボ画面(M3-04)はタグ(`mycombo_status` カテゴリ)で絞り込まれた仮想ビューとして実装されるため、タグ機能の完成が M3 全体の前提条件となる。

**スコープに含むもの**:

- バックエンド: `tags` / `combo_tags` テーブルの API 整備(M1-02 で DDL 整備済み、CRUD 実装は本指示書で行う)
- バックエンド: タグカテゴリ別取得 API(`GET /api/tags?category=mycombo_status` 等のクエリ対応)
- フロントエンド: 設定画面内のタグ管理 UI(新規作成・編集・削除、カテゴリ・色設定を含む。DES-005 §5.12 準拠)
- マイグレーション新設: `000007_seed_initial_tags_user1.up.sql`(SUPP-001 §3.5 の3タグを user_id=1 に投入: 使用中・練習中・頻度低下、いずれも category=`mycombo_status`)
  - down は対称な DELETE(user_id=1 かつ category='mycombo_status' の3件のみ削除、ユーザー追加分は保護)
  - **本 seed は M3 期間限定の暫定措置**: 本来 SUPP-001 §3.6 で「ユーザー別データはウィザード経由生成」と定めた方針があるが、ウィザード実装は M6 のため M3 では seed で凌ぐ。M6 着手時に Plan Mode で開発者と協議し、衝突回避ロジックを組み込んだ上でウィザード経由生成に切り替える方針(本書では暫定措置である事実をマイグレーションファイル冒頭コメントに明記する)

**スコープに含まないもの**:

- 既存コンボへのタグ付与 UI(コンボ編集画面のタグ選択 UI)— M3-02 で実装
- マイコンボ画面(別画面方式)— M3-04 で実装
- タグ別フィルタ機能(コンボ一覧のフィルタ条件にタグを含める)— M3-03 で実装

**前提**: M2 完了。M3 着手の最初のサブマイルストーン。

**推奨モデルの根拠**: タグ CRUD は M1-03 で確立したリポジトリ層・サービス層・ハンドラ層の3層パターンを踏襲する定型作業。フロントの管理 UI は shadcn/ui の Dialog + Form の組合せで M2-02 のパターンを再利用可能。新規性が低く、Sonnet 4.6 の生成速度が活きる。

**Plan Mode 任意の根拠**: スコープが明確、依存関係が単純(既存パターンの応用)、設計書(DES-005 §5.12、DES-003 §3.6 / §3.7)で必要な情報が揃っている。Plan Mode で計画提示すると安全だが必須ではない。

### 3.2 M3-02: コンボへのタグ付け UI

**目的**: 既存コンボ編集画面・新規登録画面でタグを選択・新規作成できる UI を整備し、コンボ一覧のタグ列に実データを反映する。M2-02 で記録された M1-05 の暫定処理(タグ列「(なし)」固定表示)を解消する。

**スコープに含むもの**:

- コンボ登録・編集画面のタグ選択 UI(複数選択可、shadcn/ui の MultiSelect または Combobox 相当)
- タグ選択 UI 内からの新規タグ作成 UI(M3-01 の API を呼び出す)
- コンボ保存時の `combo_tags` 中間テーブルへの登録・更新ロジック
- コンボ一覧のタグ列実データ反映(現状の暫定「(なし)」固定表示を解消)
- コンボ詳細画面のタグ表示

**スコープに含まないもの**:

- タグ別フィルタ機能(コンボ一覧のフィルタ条件にタグを含める)— M3-03 で実装
- マイコンボ画面(タグ `mycombo_status` 系での絞り込み表示)— M3-04 で実装

**前提**: M3-01 が完了している。

**例外条項**: バックエンド側の追加変更は **原則行わない**。コンボ保存系 API(`POST /api/combos`、`PATCH /api/combos/:id`、`PUT /api/combos/:id`)に `tag_ids` 等のフィールド追加が必要になる可能性が高いが、この拡張は本指示書の §2.4 で明示的に許容する。実装中に追加で必要が生じた場合は Plan Mode で開発者に確認する。

**推奨モデルの根拠**: 既存編集 UI(M1-06 / M2-02 で完成)への追加実装。タグ選択コンポーネントはサードパーティパターンの応用で、新規性は低い。Sonnet 4.6 で十分。

### 3.3 M3-03: フィルタ・ソート・表示列カスタマイズ

**目的**: コンボ一覧の機能を DES-005 §5.4 のレベルまで完成させる。M1-05 では更新日時ソートのみ・フィルタなしの最小実装にとどまっていたものを本指示書で本格化する。あわせて表示列カスタマイズの localStorage 永続化を実装し、CLAUDE.md §10.X で示した共通ヘルパ `web/src/lib/browser-storage.ts` を新設する。

**スコープに含むもの**:

- コンボ一覧のフィルタ機能(キャラクター、状況コード値、タグ、本登録/仮登録、その他 DES-005 §5.4 で定義された項目)
- コンボ一覧のソート機能(ダメージ降順・昇順、更新日時降順・昇順、その他 DES-005 §5.4 で定義された項目)
- 表示列カスタマイズ(各列の表示/非表示切替 UI、localStorage 永続化、CLAUDE.md §10.X 準拠)
- **共通ヘルパ `web/src/lib/browser-storage.ts` の新設**(CLAUDE.md §10.X §共通の実装ガイドラインに従う):
  - try-catch でラップした安全な get/set/remove 関数
  - JSON シリアライズ/デシリアライズ
  - キーバージョニング(`-v1` suffix)
  - parse 失敗・容量超過時のフォールバック動作統一
- バックエンド側のフィルタ・ソート対応 API 拡張(`GET /api/combos` のクエリパラメータ追加)

**スコープに含まないもの**:

- 表示列カスタマイズのサーバー永続化(将来検討事項、SUPP-001 v1.6.0 改訂時の議論経緯あり。フェーズ2 以降の認証本格化に合わせて再検討する余地)
- マイコンボ画面機能 — M3-04 で実装(本指示書で完成したフィルタ機構をマイコンボ画面側で再利用する想定)
- 仮想コントローラ選択保持の localStorage 利用 — M7 で実装(本指示書で新設した `browser-storage.ts` ヘルパを再利用する想定)
- 下書き自動保存の localStorage 利用 — M6 で実装(同上)

**前提**: M3-01、M3-02 が完了している(タグフィルタ実装のため)。

**例外条項**: バックエンド側の `GET /api/combos` 拡張は本指示書のスコープに含む(フィルタ・ソートのクエリパラメータ追加、ハンドラ層・サービス層・リポジトリ層の SQL 拡張)。新規 API は追加しない。

**推奨モデルの根拠**: フロント・バックエンド両方への変更を伴い、フィルタ・ソート・表示列カスタマイズという複数の関心が絡む。`browser-storage.ts` ヘルパ新設は M6/M7 でも再利用される共有資産のため、安全性(try-catch 漏れ・キーバージョニング規約逸脱の検出)を考慮した設計が必要。Opus 4.6 + Plan Mode 必須が妥当。

### 3.4 M3-04: useCharacters フック化 + マイコンボ画面追加

**目的**: M2-02 で記録された持ち越し課題1(`CHARACTER_NAMES` 定数マップ → useCharacters フック差し替え)を解消し、マイコンボ画面を独立画面として新設する。マイコンボ画面はタグ `mycombo_status` 系(使用中・練習中・頻度低下)で絞り込まれたコンボのビューとして実装し、M3-03 で完成したフィルタ機構を再利用する。DES-005 §5.5(L238-251)が定める独立画面前提に沿った実装。

**スコープに含むもの**:

- `useCharacters` フックの実装(`GET /api/games/{id}/characters` を呼び出してキャラクター一覧を取得、TanStack Query でキャッシュ。**API パス注意**: `/api/characters` ではなく `/api/games/{id}/characters`、DES-002 §4.2 L133)
- 既存の `CHARACTER_NAMES` 定数マップ参照箇所を `useCharacters` フックに差し替え(主に DuplicateRealtimeWarning.tsx、その他 M1-05 / M1-06 / M2-02 で導入された箇所)
- **マイコンボ画面の新規追加(別画面方式、DES-005 §5.5 準拠)**:
  - 新規ルート(`/mycombo` 等、DES-005 §3 画面遷移図と整合させる)
  - 画面構造: キャラクター情報バー(上部、目立つ表示)+ マイコンボステータス切替タブ(3つ:使用中・練習中・頻度低下)+ コンボ一覧テーブル(コンボ一覧画面と同等)
  - **キャラクター情報バー**: キャラクターアイコン + 名前を目立つ形で表示(DES-005 §5.5 表示項目)。**上振れ要素**として、選択中キャラの「使用中コンボ件数 / 練習中コンボ件数 / 頻度低下コンボ件数」のダッシュボード的情報を組み込む(M3-01 の `usage_count` API を活用)
  - **マイコンボステータス切替タブ**: 上部に3タブ(使用中/練習中/頻度低下)、選択中タブのタグでフィルタリング。**上振れ要素**として、各タブに件数バッジ表示「使用中 (5) / 練習中 (3) / 頻度低下 (1)」
  - **キャラクター切替プルダウン**: M3 ではリュウのみ運用だが、複数キャラ展開(M7)に拡張しやすい基盤として実装(useCharacters フックの結果を選択肢として表示、現状はリュウ1件のみ)
  - ソート機能: コンボ一覧と同様(useComboListFilters の再利用、または同等の自前実装)
  - 表示列カスタマイズ機構: M3-03 の `useColumnVisibility` を再利用、または別キー(`mycombo-columns-v1` 等)で分離管理(指示書執筆時に判断、本 overview では未確定)

**スコープに含まないもの**:

- 複数キャラクターの seed データ追加 — M3 ではリュウのみ継続(M2 と同じ運用)。useCharacters フックの API 経由取得自体は実装するが、結果は1キャラのみ
- マイコンボ画面のスマホボトムシート対応 — M7 仕上げで対応(本マイルストーンは基本のレスポンシブのみ)
- マイコンボ画面内でのコンボ編集・新規登録の特殊フロー — 既存のコンボ編集画面(M1-06 / M2-02)への遷移で完結

**前提**: M3-01、M3-02、M3-03 が完了している(タグデータ・タグ付与 UI・フィルタ機構が必須)。

**例外条項**: バックエンド側の追加変更は **原則行わない**。`GET /api/games/{id}/characters` は M1-02 で実装済み、コンボ一覧 API のタグフィルタは M3-03 で実装済み、タグの usage_count は M3-01 で実装済み。マイコンボ画面は既存 API の組合せで実装可能と想定する。実装中に追加で必要が生じた場合は Plan Mode で開発者に確認する。

**推奨モデルの根拠**: useCharacters フックの実装は定型(TanStack Query パターン、M1-05 で確立)、マイコンボ画面は M3-03 で完成したフィルタ機構の再利用 + 新規ルート追加。新規性は中程度だが、新規 API・新規バックエンドロジックがないため Sonnet 4.6 で十分。上振れ要素(件数ダッシュボード、カウントバッジ)も既存 API の組合せで実現可能。

**指示書執筆時の留意点(設計担当 Claude 向け)**: DES-005 §5.5(マイコンボ画面)の表示項目「現在選択中キャラクター情報バー」「マイコンボステータス切替タブ」「キャラクター切替プルダウン」を漏れなく反映する。M3-overview v1.0.0 ではタブ切替方式と私が記録したが、v1.0.2 で当初想定の別画面方式に回帰している経緯を理解した上で、設計書本体との整合を最優先する。CHANGE 通知書は不要(設計書本体と一致するため)。playbook §5 行レベル照合原則に従い、DES-005 §5.5 を必ず view で確認してから指示書本文を書く。

### 3.5 M3-05: コンボ一覧仕上げ(レシピ表示改善 + 始動技表示改善 + M3 統合・仕上げ)

**目的**: M2-04 完了時に判明した持ち越し課題7(コンボ一覧のルート列ハイフン問題)を案 A 方式で解消し、あわせて M1-05 で残された暫定処理2件(始動技 ID 表示、useControllerInput テスト未追加)も同サブマイルストーンで解消する。M3 全体の統合動作確認も行う。複数の関心が絡む仕上げサブマイルストーンとして Opus 4.6 + Plan Mode 必須。

**スコープに含むもの**:

- **持ち越し課題7の解消(案 A 確定)**: コンボ一覧 API `GET /api/combos` のレスポンス DTO に `default_recipe` フィールドを追加する:
  - 値: 既定プリセット(初期は `official_ja_move` 固定)で解決されたレシピ文字列
  - 解決ロジック: 既存の `notation.Service.ResolveComboRecipe(comboID, presetID)`(SUPP-001 §7.1)を一覧処理ループ内で呼ぶ
  - フォールバック動作(エイリアスなし → official_ja_move → moves.code)はサービス層に委譲済みのため、本指示書での新規実装は不要
  - フロント側: `ComboTableRow.tsx` の `recipePreview = "-"` 固定を解除し、`combo.default_recipe` を表示
  - 「ユーザー既定プリセット」設定機能は M3 では実装しない(`official_ja_move` 固定でハードコード)。将来「ユーザーごとのお気に入りプリセット」が要件化された時点で別 CHANGE 通知書で拡張する
- **暫定処理3の解消(始動技 ID 表示)**: コンボ一覧 API のレスポンス DTO に `starter_move_code` フィールドを追加する:
  - 値: `starter_move_id` から解決された moves.code(例: `crouching_light_kick`)、フロント側で localized name へ変換可能な機械可読キー
  - フロント側: `始動技#42` のような ID 表示を解消し、`starter_move_code` を `useMovesByCharacter` フックで解決した name_ja 表示に切り替え
  - 関連 progress-log §M1-03 暫定処理3
- **持ち越し課題4の解消(useControllerInput テスト追加)**: `useControllerInput.ts` の moves not found 時の console.warn のエッジケーステストを Vitest で追加(レビューで「品質向上」扱い、M2-01 起源)
- **M3 全体の手動 E2E 確認**: M3-01〜M3-04 が統合された状態で、タグ作成→コンボ登録→タグ付与→マイコンボ画面表示→フィルタ・ソート・表示列カスタマイズ→コンボ一覧でレシピ・始動技が正しく表示されることまで一連動作を確認

**スコープに含まないもの**:

- ユーザー既定プリセット設定機能(将来要件、M3 では `official_ja_move` 固定)

## 6. M2 反省点を踏まえた M3 運用ルール

playbook §3〜§16 に統合済みのため、本節では **M3 期間中に特に意識すべき要点のみ** を抜粋する。詳細は playbook を参照。

### 6.1 設計書本体との行レベル照合(playbook §5、retro R-01 継続的注意)

M2-04 で発生した「コンボ一覧ハイフン問題」は、`model.Combo` の `json:"-"` タグ確認漏れが原因だった。M3 ではタグ・マイコンボ・フィルタ・表示列カスタマイズと多くの DTO・テーブル・SQL を扱うため、設計書本体との行レベル照合を徹底する。

**指示書作成時(設計担当)**:
- 各 DTO・構造体・マイグレーション SQL に対応する設計書節(DES-X §X.Y、可能なら行番号レベル)を併記
- 推測で書いた箇所には「**推測。設計書 §X.Y との整合性を要確認**」と明記
- セルフチェック: `grep -nc 'DES-001\|...' {file}` で参照回数を確認

**製造担当の実装時**:
- 指示書に書かれた設計書節を view ツールで開いてフィールド名・型・制約を確認してから実装
- 「副次効果として〜される」「自動的に〜になる」という前提が成立するかを view で確認

**レビュー担当のレビュー時**:
- レビューチェックリスト先頭項目に「**設計書本体との照合**」を必ず含める

### 6.2 禁則表現の根絶(playbook §4、retro R-02 継続)

指示書・チェックリストで以下の表現を使用しない:

- 「あれば」「(あれば)または」
- 「必要に応じて」
- 「実装時に決定」
- 「任意で」
- 「適切に」
- 「既に〜していれば不要」
- 「動作するはず」「動作すると思われる」

判断保留する場合は以下のいずれかの形式で書く:

- 「**Plan Mode で製造担当が開発者に方針提示し、開発者が決定する**」
- 「**M3-XX 着手時に開発者と協議して決定する**」
- 「**実装時に Claude Code と開発者の協同で決定する(SUPP-001 §6.1 協同方針)**」

セルフチェック必須: `grep -n 'あれば\|必要に応じて\|実装時に決定\|任意で\|適切に\|既に〜していれば不要\|動作するはず' {file}`

### 6.3 例外条項の明示(playbook §6、retro R-03 継続)

各 M3 指示書テンプレートに以下の節を初期から組み込む:

- §2.3 変更しないもの(原則)
- §2.4 例外: バックエンドへの最小限の追加が許容される箇所(該当する場合のみ記述、なければ「該当なし」と明記)

フロント指示書を書く際、必要な API が既存指示書群で実装されているかを **逆算チェック** し、不足が判明した場合は §2.4 で「本指示書で新設する」または「別指示書で先行実装される」のいずれかを明記する。

M3 では特に M3-02(コンボ保存系 API への `tag_ids` フィールド追加)、M3-03(`GET /api/combos` のフィルタ・ソートクエリ拡張)、M3-05(`GET /api/combos` レスポンス DTO への `default_recipe` / `starter_move_code` フィールド追加)が該当する。

### 6.4 E2E シナリオの必須化(playbook §11、retro R-09 継続)

各 M3 指示書の §5「テスト要件」に **E2E シナリオ** 節を必ず含める。形式は以下:

```
## E2E シナリオ
1. /tags/manage で新規タグ「使用中」を作成
2. /combos/new で新規コンボを開く
3. タグ選択 UI で「使用中」を選択
```

### 6.5 製造担当の DoD テンプレート(playbook §12、retro R-09)

各 M3 指示書の §7「完了条件(Definition of Done)」に、以下のテンプレートを組み込む。製造担当は実装完了報告時に以下のチェック結果を報告書に貼付する。

#### 6.5.1 機能要件(指示書ごとに具体化)

#### 6.5.4 完了報告

- 開発者に「M3-XX が完了しました」と報告
