## 1. 概要と目的

### 1.1 概要

DES-005 §5.8 で規定されたコンボ比較画面を新規実装する。同時にコンボ一覧画面(§5.4)・マイコンボ画面(§5.5)に「選択モード」を追加し、比較画面への遷移動線を整備する。

### 1.2 目的

- DES-005 §5.8 で規定された表示項目(本指示書 §4.1.4 で 12 行構成に再整理:始動状況・ルート・ダメージ・ドライブ消費・SA 消費・状況・有利フレーム・起き攻め 2 行・セットプレイ・タグ・備考)を、ユーザーが選択した複数コンボ(最大 5 件)で横並び表示できる
- コンボ一覧画面・マイコンボ画面で複数コンボを選択 → 「比較」ボタン押下 → 比較画面に遷移する動線が動作する
- 比較画面上で「コンボ追加」モーダル経由で比較対象を後追い追加できる
- 比較対象の上限 5 件を超える操作で Toast 通知が表示される(上限値は定数化で拡張性確保)
- URL クエリパラメータ(`/compare?ids=1,2,3`)で比較状態を保持し、リロード・URL 共有でも再現可能

### 1.3 このマイルストーンで作らないもの

M5-overview v1.0.1 §1.3 に準拠。再掲:

- **エクスポート機能**(FR402〜FR404): フェーズ 2 送り、本指示書ではエクスポートボタン UI も実装しない(DES-005 §5.4 item 7 エクスポートボタンも含めて触らない)
- **CSV エクスポート / インポート**: SUPP-001 §4.4 でフェーズ 2 送り
- **`POST /api/combos/compare` API**: CHANGE-015(2026-05-23)で DES-002 §4.2 から削除済み、案 1(既存 `GET /api/combos/{id}` を N 件並列呼出)採用
- **比較対象の自動候補提示**: FR008「フェーズ 1 では採用しない」
- **比較画面での表示項目選択**(FR203 の一部): 11 項目すべて常時表示
- **スマホ向けレスポンシブ実装**: SUPP-001 §4.1 M7「レスポンシブ仕上げ」のスコープ、本 M5 は PC レイアウトのみ実装
- **持ち越し確認課題 C-2 / C-3 / C-4 / L-02 / L-03**: m4-to-m5-handover §3 / §4
- **ゴミ箱画面の選択モード変更**: M2-03 で実装済みの `TrashPage` の `selectedIds`(一括復元・永久削除用)とは別機能、本指示書では触らない
- **下書き保存仕様**(DES-005 §5.7 L343): M6 以降のスコープ
- **新規バックエンドハンドラ・サービス・リポジトリ**: 案 1 採用により不要

#### 3.4.2 useQueries 初導入の実装方針確認

- TanStack Query `useQueries` の公式ドキュメント参照(エラーハンドリング、ローディング状態の集約、個別クエリの enabled 制御)
- 各 ID で `useCombo` と同じ queryKey `["combo", id]`(number 正規化済み)を使うことでキャッシュ共有する方針を確認(architecture-patterns.md v1.0.3 §1.1)
- 並列クエリのエラーハンドリング方針(本 v1.0.2 で確定、§4.1.3 参照): **全クエリ結果に関わらず CompareTable を常時描画**、失敗列は「取得失敗」表示、loading 中の列はスケルトン or スピナー表示で「-」フラッシュを防止。全体エラー画面で CompareTable をスキップする分岐は採用しない(統合案 Q 採用)

#### 3.4.3 選択モードの状態管理範囲判断(共通フック化要否)

- コンボ一覧 + マイコンボの選択モードを **共通フック化するか / 各画面個別に useState で持つか** を Plan Mode で判断
- 判断基準:
  - 各画面の選択モードの挙動が **完全に同一** な場合は共通フック化を採用
  - 挙動が異なる箇所(例: マイコンボはタブ切替で selectedIds をクリアする等)が存在する場合は個別実装で分離
- 設計担当(私)の現状認識: マイコンボ画面はステータスタブ切替を持つため、タブ切替時の selectedIds クリア挙動が分かれる可能性あり = **個別実装が自然な可能性が高い** が、最終判断は製造担当に委ねる(M4-12 LinkExistingSetupModal / SetupSelectorModal 分離判断と同パターン、YAGNI 重視)

#### 3.4.4 URL クエリパラメータの parse / serialize 方針確認

- `useSearchParams` の取得値は `string` = `?ids=1,2,3` をどう parse するか:
  - **推奨方式**: カンマ区切り文字列を `split(",").map(Number).filter(n => !Number.isNaN(n) && n > 0)` で number 配列に変換
  - 既存パターン: `useComboListFilters` の URL SearchParams 操作を参照
- 不正値(NaN、負数、上限超過件数)が含まれる URL の挙動を Plan Mode で提案(推奨: 不正値を silently 除外、上限超過は先頭 5 件まで採用)

- アクセス制御: なし(公開ルート、他画面と同様)

#### 4.1.2 URL クエリパラメータ

- 形式: `/compare?ids=1,2,3`(カンマ区切り number 配列)
- ids が **空 or 不在の場合**: 「比較対象が選択されていません」のプレースホルダ表示 + 「コンボを追加」ボタン(モーダル起動)を中央に表示
- ids に **1 件のみ含まれる場合**: 比較表を 1 列で表示(比較機能の最小ケース、エラーにはしない)
- ids に **6 件以上含まれる場合**: 先頭 5 件まで採用 + Toast 通知「比較対象は最大 5 件までです。上限を超える分は除外しました」
- ids に **不正値(NaN・負数・0)が含まれる場合**: silently 除外、エラー表示なし

#### 4.1.3 データ取得

- `useCompareCombos(ids: number[])` フックで `useQueries` を用いて並列取得
- 各クエリは既存 `useCombo` と同じ queryKey `["combo", id]` を使用(キャッシュ共有)
- 並列クエリのエラーハンドリング(本 v1.0.2 で改訂、統合案 Q 採用、開発者承認 2026-05-23):
  - **全クエリ結果に関わらず CompareTable を常時描画**(全体エラー画面で CompareTable をスキップする分岐は採用しない)
  - **全クエリ成功**: 通常表示(全列にコンボデータ表示)
  - **クエリ単位での失敗**: 失敗列のセルに「取得失敗」表示、上部の比較対象一覧カードに「× 削除」ボタンで個別除去可能
  - **loading 中の列**: スケルトン or スピナー表示(従来は「-」表示でデータ未存在と区別がつかずフラッシュ問題が発生していたため、loading 状態を明示する表示に変更)
  - **全列が削除されて 0 件**: 「比較対象が選択されていません」プレースホルダ表示(§4.1.2 と整合)
- データ未存在(`null`)と loading 中の区別:
  - loading 中(`query.isLoading === true`): スケルトン or スピナー表示
  - 取得失敗(`query.isError === true`): 「取得失敗」表示
  - 成功 + データ取得済み(`query.data !== undefined`): セル内容表示(各セル内のフィールド null 時は §4.1.4 規定の「-」表示)

#### 4.1.4 表示項目(DES-005 §5.8 規定の 11 種、全件常時表示)

比較表の縦方向(行)に以下 12 行を並べる。横方向(列)は比較対象コンボ N 件(最大 5):

| 行 | 項目 | データソース(ComboResponse のフィールド) | 表示形式 |
|----|------|-----------------------------------------|---------|
| 1 | 始動状況(始動技 + カウンター種別 + ポジション) | `starterMoveCode` / `hitType` / `position` のグループ表示 | 各値を改行または区切り文字で結合 |
| 2 | ルート(レシピ文字列) | `defaultRecipe`(既定プリセット解決済み) | 文字列、長い場合は CSS で省略表示 + ホバーで全文(`title` 属性) |
| 3 | ダメージ | `damage` | 数値、null 時は「-」 |
| 4 | ドライブ消費 | `driveGaugeConsumedTotal` | 数値、null 時は「-」 |
| 5 | SA 消費 | `saGaugeConsumedTotal` | 数値、null 時は「-」 |
| 6 | 状況 | `position` / `opponentStance` / `hitType` のグループ表示 | プロトタイプ風のタグ並び(例: `中央` `立ち` `通常`)。各値の日本語ラベルは既存定数(`POSITION_LABELS` 等、M5-RESEARCH-01 §4.6 (b) 参照)から取得 |
| 7 | 有利フレーム | `knockdownAdvantage` | 数値、null 時は「-」。表記は「+26F」「-3F」のように単位 F を末尾付与(プロトタイプ準拠) |
| 8 | 起き攻め(改行)その場受け身 | `okiMeatyNeutralTechThrow` + `okiMeatyNeutralTechThrowDr` + `okiShimmyNeutralTech` | 2 段構造(下記 §4.1.4.1 参照)|
| 9 | 起き攻め(改行)後ろ受け身 | `okiMeatyBackTechThrow` + `okiMeatyBackTechThrowDr` + `okiShimmyBackTech` | 2 段構造(下記 §4.1.4.1 参照)|
| 10 | セットプレイ | `setups` 配列の `name` を箇条書き表示(`name` null 時は `defaultRecipe` 先頭を表示) | 改行区切り、件数 0 時は「-」 |
| 11 | タグ | `tags` 配列の `name` を箇条書き表示 | 改行区切り、件数 0 時は「-」 |
| 12 | 備考(メモ) | `memo` | 文字列、null 時は「-」 |

> 注 1: DES-005 §5.8 の「11 項目」は **大項目数** であり、本指示書ではご開発者承認(2026-05-23)に基づき表示構成を再整理。シミー独立行は廃止し、起き攻め 2 行のセル内に投げ重ね情報 + シミー情報を併記する(下記 §4.1.4.1)。「ドライブ消費」「SA 消費」「状況」の 3 行を新規追加。
>
> 注 2: 始動状況行(行 1)の構成要素「ポジション」と「カウンター種別」は、状況行(行 6)にも含まれる(重複表示)。これは始動状況を始動技中心に簡潔に提示しつつ、状況行で前提条件をタグ形式で一覧化する意図的な構成(解釈 X 採用、ご開発者承認 2026-05-23)。DES-005 §5.8 規定の改訂は伴わない。

##### 4.1.4.1 起き攻め行のセル内表示仕様(2 段構造)

行 8(その場受け身)/ 行 9(後ろ受け身)の各セルは以下の 2 段構造で表示する:

```
DR 無: 〔判定結果〕
DR 有: 〔判定結果〕
```

判定結果は以下 5 パターン(その場受け身行は `_neutral_*` カラム、後ろ受け身行は `_back_*` カラムを参照):

| 段 | 投げ重ね | シミー | 表示 |
|---|---------|--------|------|
| DR 無 | `oki_meaty_*_throw` = true | `oki_shimmy_*_tech` = true | **両方可** |
| DR 無 | `oki_meaty_*_throw` = true | `oki_shimmy_*_tech` = false | **投げ重ねのみ可** |
| DR 無 | `oki_meaty_*_throw` = false | (シミーの値に関わらず) | **両方不可** |
| DR 有 | `oki_meaty_*_throw_dr` = true | (現状データモデル未保持、§3.4.7 参照) | **投げ重ねのみ可** |
| DR 有 | `oki_meaty_*_throw_dr` = false | (同上) | **両方不可** |

カラムが `null`(未登録)の場合は該当段を「-」表示とする(DR 無 / DR 有 個別に null 判定)。

**前提**: 上記判定は「投げ重ね可能ならシミー可能の論理包含」を前提とする = `oki_meaty_*_throw` = false かつ `oki_shimmy_*_tech` = true の組み合わせは **登録画面側のバリデーションで防止済みのため発生しない前提**。比較画面側で不整合データのフォールバック処理は実装しない(発生時の挙動は未定義動作として扱う、案 α 採用)。

**DR 有時のシミー情報**: 現状データモデル `ComboResponse` に `okiShimmyNeutralTechDr` / `okiShimmyBackTechDr` フィールドは存在しないため、DR 有時は投げ重ね情報のみで判定する。シミー DR 有データのカラム追加は M7 持ち越し課題 R-2(§9 参照)。

##### 4.1.4.2 状況行のラベル取得(行 6)

`position` / `opponentStance` / `hitType` は文字列コード値(`corner_self` / `crouching` / `normal` 等、DES-003 §3.4)で保持されており、表示時は日本語ラベルに変換する。変換方式は以下:

- `POSITION_LABELS[position]`(`web/src/constants/combo-list.ts` 既存定数、M5-RESEARCH-01 §4.6 (b) 確認済み)
- 同様に `OPPONENT_STANCE_LABELS` / `HIT_TYPE_LABELS` を流用(既存ファイルに該当定数が存在するかは §3.4.1 既存 UI 確認時に併せて確認、不在なら本指示書スコープ内で追加)
- 値が `null` のフィールドはタグ表示から除外(全 3 フィールド null 時は「-」表示)

#### 4.1.5 レイアウト方針(PC のみ、M5-overview §2.8 確定)

- PC レイアウト:
  - 表形式(`<table>` または CSS Grid)、項目名列(左端)+ 比較対象 N 列
  - 横スクロール対応(`overflow-x-auto`)
  - スティッキーヘッダ(項目名列を `position: sticky; left: 0;` で左端固定)は **製造担当 Plan Mode で採用是非を判断**(縦 12 行 + 5 列で必要性判定)
- Tailwind ブレークポイント `md:` 等での条件付きスタイルは **必要最小限**(コンテナ最大幅指定など)に留め、スマホ向け専用レイアウト切替は実装しない(M5-overview §2.8 解釈 B)

### 4.2 コンボ一覧画面・マイコンボ画面の選択モード

#### 4.2.1 選択モードトグル(DES-005 §5.4 item 6)

- 画面上部のツールバー領域に「選択モード」トグルボタンを追加
- 配置: 既存の「新規登録」ボタン近辺(製造担当 Plan Mode で具体位置を確定)
- 表示: 「選択モード ON」「選択モード OFF」のラベル切替、またはアイコン + テキスト

#### 4.2.2 選択モード ON 時の挙動

- 各コンボ行の左端にチェックボックス列を表示
- チェック状態を `selectedIds: number[]` で管理
- 上限: `selectedIds.length >= MAX_COMPARE_COMBOS`(5 件)に達した時点で、新たなチェック操作を拒否 + Toast 通知「比較対象は最大 5 件までです」
- 選択中件数バッジ表示(例: 「3 / 5 件選択中」)
- 画面上部に「比較」ボタンを表示(`selectedIds.length === 0` 時は無効化、1 件以上で有効)
- 「比較」ボタン押下 → `useNavigate(`/compare?ids=${selectedIds.join(",")}`)` で比較画面へ遷移

#### 4.2.3 選択モード OFF 時の挙動

- チェックボックス列・選択中件数バッジ・「比較」ボタンを非表示
- 既存のコンボ一覧 / マイコンボの挙動と完全に同一(回帰なし)

#### 4.2.4 共通フック化判断(製造担当 Plan Mode 案件)

- コンボ一覧 + マイコンボの選択モード状態管理を **共通フック化するか個別実装するか** は製造担当 Plan Mode で判断(§3.4.3 参照)
- 共通フック化採用時のフック名(案): `useSelectMode(maxItems: number)`、配置: `web/src/features/combo/hooks/useSelectMode.ts`
- 個別実装採用時: 各画面で `useState<number[]>([])` + ヘルパ関数を直接記述

#### 4.2.5 マイコンボ画面固有の挙動

- ステータスタブ切替時(現状実装は M3-04 / M3-05 由来)に `selectedIds` をクリアするか保持するか:
  - **推奨方針**: タブ切替時にクリア(タブが変わると比較対象として見えなくなるコンボが選択中に残ることを避ける)
  - 製造担当 Plan Mode で実装方針を確認

### 4.3 「コンボ追加」モーダル(比較画面側、DES-005 §5.8 アクション)

#### 4.3.1 起動

- 比較画面の上部ボタン「コンボを追加」押下で起動
- `selectedIds.length >= MAX_COMPARE_COMBOS` 時は起動ボタン無効化 + ホバー時のツールチップ「上限に達しています(最大 5 件)」

#### 4.3.2 表示内容

- モーダル内にコンボ一覧を表示(キャラクターフィルタ + 検索程度の最小フィルタ)
- 既に比較対象に含まれているコンボは **選択不可表示**(チェックボックス無効化 + 「選択済み」ラベル)
- 「追加」ボタンで選択中のコンボを比較対象に追加 → URL を更新(`useSearchParams` の `setSearchParams`)

#### 4.3.3 既存コンボ一覧コンポーネントの再利用判断

- 既存 `ComboTable.tsx`(または相当)を **モーダル内で再利用するか / 簡素なリストを新規実装するか** は製造担当 Plan Mode で判断
- 設計担当の見解: フィルタ・ソート機能をフルに使う必要はないため、**簡素なリスト新規実装が自然** な可能性が高い(YAGNI、M4-12 分離判断と同パターン)。最終判断は製造担当に委ねる

### 4.4 比較対象一覧(画面上部、削除ボタン付き)

- 比較画面の上部に、現在比較中のコンボ一覧をカード形式で表示
- 各カードに「× 削除」ボタン → 比較対象から除外(URL を更新)
- 0 件になった場合は「比較対象が選択されていません」プレースホルダに戻る

### 4.5 定数・型定義

#### 4.5.1 `web/src/constants/compare.ts`(新規)

```typescript
/**
 * 比較画面で同時に比較できるコンボの最大数。
 * 上限を増減する場合は本定数のみ変更すること(全コードに反映される)。
 */
export const MAX_COMPARE_COMBOS = 5;
```

命名規則: `web/src/constants/combo-list.ts` / `mycombo.ts` と同じ SCREAMING_SNAKE_CASE(M5-RESEARCH-01 §4.6 (b) 確認済み)

#### 4.5.2 型定義

- 既存型(`ComboResponse` / `Combo` / `SetupSummary` / `Tag` 等)をそのまま利用、新規型は不要
- 比較画面内部の型定義(`CompareCellValue`、`CompareRow` 等)が必要な場合は `ComparePage.tsx` または `CompareTable.tsx` のローカル型として定義

#### シナリオ C: URL 直アクセスと不正値除外(本 v1.0.2 で改訂、全件失敗ケース明示化)
