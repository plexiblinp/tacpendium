## 0. この指示書の特殊性(最初に読むこと)

### 0.1 本指示書は「製造担当として起動し、調査だけ実施して閉じる」運用です

本指示書は通常の製造指示書(`M{N}-{NN}-*.md`)とは異なり、**コード変更・ファイル新規作成・テスト実行を一切行いません**。M6(初期体験系)の指示書を設計担当が確定するための前提情報を、コードベースから事実列挙形式で抽出することだけが目的です。

製造担当 Claude Code セッションを Sonnet 4.6 で起動し、本指示書に従って調査レポートを作成・出力したら、そのセッションは閉じます(製造作業は行いません)。

本指示書は M5-RESEARCH-01(2026-05-22 実施、本プロジェクト初の調査担当運用)に続く 2 例目の調査専用指示書です。M5-RESEARCH-01 が 7 項目を調査対象としたのに対し、本指示書は **2 項目に絞った小規模調査** です(調査対象が「特定 2 機能の実装有無確認」に集中するため)。

### 0.2 read-only 厳守

以下を **絶対に行わない** こと:

- ファイルの新規作成・編集・削除(調査レポート出力以外)
- `git` コマンド(`git status` 等の参照系も含めて、本指示書では使わない)
- `go build` / `go run` / `pnpm build` / `pnpm test` 等のビルド・テスト実行
- マイグレーション実行(`go run ./cmd/combomgr` でアプリを起動しない)
- npm / pnpm の install 系コマンド
- 設定ファイルの変更(`config.toml` の編集を含む)
- `rm`、`mv`、`cp` 等のファイル操作

使ってよいツールは **`view` / `bash`(grep / cat / ls / find / wc 等の参照系のみ)** に限定します。`view` で複数ファイルを横断的に読むことが本作業の中核です。

万一実装変更が走った場合は開発者がロールバックします。判断に迷ったら何もせずに **Plan Mode で開発者に確認** してください。

### 0.3 判断・提案を含めない

調査結果は **事実の列挙のみ** とし、「こうするべき」「こちらが推奨」のような判断・提案を含めないでください。判断は設計担当 Claude が調査結果を受けて行います。

ただし、調査中に発見した **明らかな矛盾・想定外の事象** は §5 完了報告の「特記事項」欄に **事実として** 記載してください(例: 「`internal/config/` パッケージが存在しない」のような事実報告は OK、「これは設計書を改訂すべき」のような提案は NG)。

### 0.4 本調査の主目的(設計担当からの背景共有)

開発者の認識として、以下の 2 つは **未実装** と思われている。本調査は、その認識が正しいかを実コードで確認することが主目的:

- **項目 A**: DES-002 §4.2 主要エンドポイント表に列挙されている `GET /api/config` / `PUT /api/config`(設定取得・設定更新 API)
- **項目 B**: SUPP-001 §4.2 / DES-002 §3.2 で規定されている「`config.toml` の `[server].mode` を読み込んでバインドアドレスを `127.0.0.1` / `0.0.0.0` で切り替える処理」

**想定される結果**(調査前):

- 項目 A: **未実装**(M1〜M5 で実装の必要性が発生していない)
- 項目 B: **未実装**(現状は `127.0.0.1` 固定でバインドされている可能性が高い)

**想定外の発見が価値**: 想定外に「実装されていた」「部分実装だった」「設計書本体と異なる挙動」が判明した場合は、M6-overview のスコープ判断に大きく影響するため **特記事項として詳細に報告** すること。M5-RESEARCH-01 で「想定外の事象は事実として詳細に報告」という運用が確立されている。

### 0.5 結果の扱い(設計担当からの背景共有、調査担当の作業には影響しない)

本調査結果は M6-overview の確定 + M6-01 指示書(LAN バインド + 設定 API 基盤)のスコープ決定に使用される。調査結果次第で M6-01 の規模感が変わる(例: 既に半分実装されていれば M6-01 のスコープが縮小)。調査担当は事実列挙のみ行い、判断は設計担当に委ねる。

## 1. 背景と目的

### 1.1 背景

M6(初期体験系)では、SUPP-001 §4.1「M6 LAN 共有のバインドアドレス切替ロジック(UI はフェーズ 2)」と DES-005 §5.16「設定画面」が主要スコープに含まれる。

設計担当 Claude が M6-overview 作成にあたり、以下の前提情報を確定したい:

- **判断 A**: M6-01(LAN バインド + 設定 API 基盤)サブマイルストーンで、設定 API(`GET /api/config` / `PUT /api/config`)を **新規実装するか、既存実装を拡張するか**
- **判断 B**: M6-01 で、`config.toml` の `[server].mode` 読込 + バインドアドレス切替を **新規実装するか、既存実装を拡張するか**

これらの判断は **既存実装の実態確認** が前提となるため、本指示書で事実情報を収集する。

### 1.2 目的

本指示書完了時に、設計担当 Claude が M6-overview / M6-01 指示書作成のために必要な以下の情報が揃っている状態を達成する:

- (1) `GET /api/config` / `PUT /api/config` の実装有無(ハンドラ、サービス、リポジトリ層)。実装されている場合は、レスポンス DTO 構造と現状の振る舞い
- (2) `internal/config/` パッケージの構造と `config.toml` 読込実装の現状(`[server].mode` を実際に読み込んでいるか、デフォルト値処理、TOML パース実装)
- (3) サーバー起動時のバインドアドレス決定ロジックの現状(`127.0.0.1` 固定か、`config.toml` から動的に決定するか)
- (4) `internal/api/config/` パッケージの存在有無(設定 API 用ハンドラパッケージが存在するか)
- (5) 関連する既存テストコードの存在(`config_test.go`、`infra_test.go` 等)

### 1.3 このタスクで作らないもの

- 実装コード(ハンドラ、サービス、API 等)
- 設計判断の提案(調査結果は事実列挙のみ、判断は設計担当が行う)
- 修正提案・リファクタ提案
- テストコード
- マイグレーション SQL
- 設定ファイルの編集(`config.toml` の編集を含む)

## 4. 調査内容

各調査項目について、§5 完了報告で報告すべき情報を明示する。

### 4.1 `GET /api/config` / `PUT /api/config` の実装有無

**目的**: 設計担当の現状認識(未実装と想定)を実コードで検証する。実装されていた場合は、レスポンス DTO 構造と現状の振る舞いを把握する。

**調査手順**:

1. `grep -rn '"/api/config"\|/api/config' internal/api/` で `/api/config` パスを参照しているハンドラ実装の有無を確認
2. `grep -rn 'GET.*config\|PUT.*config' internal/api/ --include='*.go'` でハンドラ登録(echo ルーター登録、`e.GET("/api/config", ...)` 等)の有無を確認
3. `find internal/api/ -type d -name 'config*'` で `internal/api/config/` パッケージの存在を確認
4. 存在した場合は、`internal/api/config/handler.go`(または該当ハンドラファイル)を `view` で開き、ハンドラ実装の概要を確認
5. ルーター登録ファイル(`cmd/combomgr/main.go`、`internal/api/router.go` 等、リポジトリの実態に応じて特定)を `view` で開き、`/api/config` 系のルート登録があるか確認

**報告すべき情報**:

- (a) `GET /api/config` ハンドラの実装有無(yes / no)
  - yes の場合: 実装ファイルパス + ハンドラ関数名 + レスポンス DTO 型名(`ConfigResponse` 等)
  - no の場合: その旨を明記
- (b) `PUT /api/config` ハンドラの実装有無(yes / no)
  - yes の場合: 実装ファイルパス + ハンドラ関数名 + リクエスト DTO 型名 + レスポンス DTO 型名
  - no の場合: その旨を明記
- (c) ルーター登録(echo の `e.GET("/api/config", ...)` / `e.PUT("/api/config", ...)`)の有無(yes / no、yes の場合は登録ファイルパス + 行番号)
- (d) `internal/api/config/` パッケージの有無(yes / no、yes の場合は配下ファイル一覧)
- (e) 関連サービス層 `internal/service/config/`(想定)の有無(yes / no、yes の場合は配下ファイル一覧)
- (f) (a)〜(e) すべてが no なら「**設定 API は未実装**」と結論を明記

### 4.2 `config.toml` 読込実装と `[server].mode` 利用状況

**目的**: 設計担当の現状認識(未実装、`127.0.0.1` 固定と想定)を実コードで検証する。`config.toml` 読込実装の現状と、`[server].mode` を実際にバインドアドレス決定に使用しているかを把握する。

**調査手順**:

1. `find internal/config/ -type f -name '*.go'`(存在する場合)で設定読込パッケージの全ファイルを列挙
2. `grep -rn 'BurntSushi/toml\|toml\.' internal/ --include='*.go'` で TOML パース呼出の有無を確認(CLAUDE.md §2 で `github.com/BurntSushi/toml` が採用済み)
3. `grep -rn '\[server\]\|server\.mode\|server\.port\|"local"\|"lan"' internal/ --include='*.go'` で `[server]` セクション読込の実態を確認
4. `grep -rn 'config\.toml' internal/ cmd/ --include='*.go'` で `config.toml` ファイルパス参照の有無を確認
5. 存在した場合、関連ファイルを `view` で開き、以下を確認:
   - TOML 構造体定義(`type Config struct { Server struct { Mode string; Port int } ... }` 等)
   - 読込関数の実装(デフォルト値処理、ファイル不在時の挙動)
   - `[server].mode` の値を使う箇所(後続の 4.3 調査と関連)

**報告すべき情報**:

- (a) `internal/config/` パッケージの存在有無(yes / no)
  - yes の場合: 配下ファイル一覧 + 主要関数名(`Load()` / `LoadConfig()` 等)
- (b) TOML パース呼出(`BurntSushi/toml` の `toml.Decode` / `toml.DecodeFile` 等)の有無(yes / no、yes の場合は呼出ファイル + 行番号)
- (c) Go 側の Config 構造体定義の有無(yes / no、yes の場合は構造体定義の **全フィールド一覧**(SUPP-001 §5.8 設定ファイル例との対応を確認))
- (d) `[server].mode` の値を実際に **読み取って利用しているコード** の有無(yes / no、yes の場合はファイルパス + 行番号 + 何に使われているか)
- (e) `config.toml` のリポジトリ内ファイル存在有無(yes / no、yes の場合はファイルパスと内容の概要(機微情報なし前提))
- (f) (a)〜(e) の総合判定: 「**`config.toml` 読込未実装**」「**読込実装はあるが `[server].mode` 利用未実装**」「**`[server].mode` 利用実装あり**」のいずれに該当するか

### 4.3 サーバー起動時のバインドアドレス決定ロジック

**目的**: 現状のサーバー起動コードが、バインドアドレスを **どのように決定しているか** を把握する。`127.0.0.1` 固定か、`0.0.0.0` 固定か、`config.toml` から動的に決定するか、を事実として確認する。

**調査手順**:

1. `grep -rn 'echo\.New\|e\.Start\|http\.ListenAndServe\|http\.Server{' cmd/ internal/ --include='*.go'` でサーバー起動コードを特定
2. `grep -rn '127\.0\.0\.1\|0\.0\.0\.0\|"localhost"' cmd/ internal/ --include='*.go'` で IP リテラル参照を確認(`*_test.go` を除外して確認)
3. `grep -rn ':47318\|:8080\|Port:' cmd/ internal/ --include='*.go'` でポート番号参照を確認
4. 特定したサーバー起動ファイル(`cmd/combomgr/main.go` 等、リポジトリの実態に応じて)を `view` で開き、`e.Start(...)` または `http.ListenAndServe(...)` の引数を確認

**報告すべき情報**:

- (a) サーバー起動コードのファイルパス + 行番号(サーバー起動行)
- (b) 起動関数(`e.Start` / `http.ListenAndServe` 等)に渡されているアドレス文字列の **実態**(文字列リテラルか、変数か、`config.toml` 由来か)
  - 例: `e.Start("127.0.0.1:47318")` / `e.Start(":47318")` / `e.Start(fmt.Sprintf("%s:%d", cfg.Server.BindAddress, cfg.Server.Port))` 等の事実をそのまま記載
- (c) ポート番号の決定方法(固定値か、`config.toml` 由来か)
- (d) ポート競合時のフォールバック実装(DES-002 §3.3「使用中の場合は次の空きポートを探索」)の有無(yes / no、yes の場合は実装箇所)
- (e) 総合判定: 「**`127.0.0.1` 固定**」「**`:47318`(IP 省略 = 0.0.0.0 等価)固定**」「**`config.toml` から動的決定**」「**その他**」のいずれに該当するか
  - 「その他」の場合は実態を詳細に記載

### 4.4 関連する既存テストコードの存在

**目的**: 設定読込・サーバー起動・バインドアドレス関連の既存テストコードの有無を把握する。M6-01 で新規実装する場合の自己テスト範囲を見積もるため。

**調査手順**:

1. `find internal/config/ internal/infra/ -name '*_test.go' 2>/dev/null` で関連テストファイルを列挙
2. `grep -rn 'config_test\|server_test\|bind' internal/ --include='*_test.go'` でテストファイル名・テスト関数名を確認
3. 存在した場合は対象テストファイルを `view` で開き、テスト関数名一覧を記録

**報告すべき情報**:

- (a) `internal/config/` 配下のテストファイル一覧(存在する場合)
- (b) `internal/infra/` 配下のサーバー起動関連テストファイル一覧(存在する場合)
- (c) 各テストファイルのテスト関数名一覧(`func Test*` の列挙、テスト本体までは読み込み不要)
- (d) (a)〜(c) すべてが該当なしなら「**関連テスト未整備**」と明記

### 4.5 関連設計書記述と実装の乖離(任意)

**目的**: 調査中に発見した **設計書本体と実装の明らかな乖離** を事実として記録する。これは §0.3 の「想定外の事象」の派生で、§5 特記事項にも記載する。

**調査手順**:

調査 4.1〜4.4 を実施中に発見した、以下に該当する事実が **存在する場合のみ** 記録(存在しない場合は §5 完了報告の (b) に「乖離なし」と明記):

- 設計書本体(DES-002 §3.2 / §3.3 / §3.4 / §4.2 / §4.4、SUPP-001 §4.2 / §5.8)に記載されているが実装されていない事項
- 設計書本体に記載されていないが実装されている事項
- 設計書本体と実装で **異なる挙動** が確認できる事項

**報告すべき情報**:

- (a) 発見した乖離の事実(箇条書き、設計書節 + 実装箇所 + 乖離内容)
- (b) なければ「乖離なし」と明記
