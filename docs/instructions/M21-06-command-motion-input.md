## 1. 背景と目的

### 1.1 背景

**`DES-005` §6.6 の残り 1 件**——**「必殺技（波動拳のような ↓↘→ 入力）の方向キー連続入力の UI 表現」**——**が本サブの対象である。** **同節は「机上の設計では最適解を導きにくい領域」と定めており、開発者判断で 3 点が確定した**（**D-377**）。

| # | 論点 | 開発者判断 |
|---|---|---|
| 1 | **そもそも実演させるのか** | **★実演させる** |
| 2 | **入力ミスをどう扱うか** | **★入力ミスは解決しない。ただしコマンドの前方一致は許す**（`2 3 6 9 + P` は波動拳として解決する） |
| 3 | **ゆっくりな入力をどう扱うか** | **★インゲームと違い、非常にゆっくりな入力でも解決される仕組みを取る。** **例＝特定のボタンを押したらコマンド技入力モードになる**（削除・保存・修飾と同じ層の操作） |

> **★論点 3 が本サブの骨格である。** **インゲームのコマンド入力は十数フレームの窓で成立するが、本アプリは「入力の記録」であって「対戦」ではない。** **⇒ 時間で切れない状態を持つ。**

### 1.2 目的

| # | 目的 |
|---|------|
| 1 | **コマンド技入力モードを足す**（**4 つ目の操作**。**時間で切れない**） |
| 2 | **モード中の方向をステップにせず、コマンド列として溜める** |
| 3 | **溜まった列 ＋ ボタンを、前方一致 ＋ 最長一致で技へ解決する** |
| 4 | **解決できなかった入力を捨てずに出す** |

| # | 作らないもの | 理由 |

| 2 | **モーション解析**（波形・軌跡の解釈） | **契約 F-3 の死守。** **本サブは「押された方向の列」を索引と突き合わせるだけである** |
| 3 | **曖昧一致・編集距離・入力ミスの補正** | **開発者判断**（`§1.1` の論点 2）。**先頭のゴミは解決しない** |

## 4. 詳細仕様

### 4.0 ★着手前に `GamepadInputProvider` を改名する（**D-375**）

**供給元が 2 つになったのに `GamepadInputProvider` が "Gamepad" を名乗っている**（`M21-05` の申し送り）。

| # | 制約 |
|---|---|
| 1 | **★本サブの実装に入る前に、改名だけを単独のコミットで行う。** **挙動の diff を伴わせない** |
| 2 | **周辺の識別子も同じ手番で改める**（`§3.3-1` で列挙したもの）。**★片方だけ改名すると、名前が 2 通りになる** |
| 3 | **★これは機械的 diff であり、本サブの中身とは無関係である。** **混ぜると、レビューが「どこが本題か」を見失う** |

> **★なぜ今か**——**本サブは同じ層に乗り、3 つ目の供給元を足しうる。** **後になるほど呼出元が増え、乖離が広がる。**

### 4.1 コマンド技入力モード（**4 つ目の操作**・**本サブの骨格**）

| # | 仕様 |
|---|---|
| 1 | **削除・保存・修飾と同じ層に、4 つ目の操作としてモードの開始／終了を足す** |
| 2 | **★操作の種別は 3 値 → 4 値になる。** **`M21-04`（Gamepad）と `M21-05`（キーボード）の両方へ同時に足す**（`§2.3`） |
| 3 | **★モードは時間で切れない。** **`DES-005` §6.4.2 の判定窓に乗せない**——**乗せると「非常にゆっくりでも解決される」という要件そのものが壊れる** |
| 4 | **モード中、方向はステップにならない。** **コマンド列として溜まる** |
| 5 | **確定の契機は攻撃ボタンである。** **列 ＋ ボタンで 1 技を解決する** |
| 6 | **★溜まっている列を画面に出す。** **出さないと、利用者は何が溜まっているか分からない**（`DES-005` §6.5.1 (1) の「状態として出す」と同じ流儀） |
| 7 | **★モードから抜けられる。** **抜け方は実装判断に委ねるが、溜めた列が黙って消えないこと**（`E-84`） |
| 8 | **★モードは切替である。** **モードに入っていない間は今までどおり**（方向 1 つ ＝ ステップ 1 つ）。**既存の入力経路を 1 つも変えない** |
| 9 | **Gamepad とキーボードの両方から入れる**（**合流層に乗る**＝`§2.2-3`） |

> **★`D-370` は「操作の種別は 3 値。増やさない」と書いたが、これは `M21-05` 時点の as-built であって恒久の上限ではない。** **⇒ 4 値目を足すのは正当である。** **★守るべきは「1 か所で定義し、両側が同じものを参照する」ことのほうである。**

### 4.2 解決の規則（**前方一致 ＋ 最長一致**）

| # | 規則 |
|---|---|
| 1 | **コマンドの方向列が、溜まった方向列の「先頭」に一致することを条件とする**（**前方一致**） |
| 2 | **★末尾の余りは無視する。** **`2 3 6 9 + P` は波動拳として解決する**（開発者の例） |
| 3 | **★候補が複数なら、方向列が最も長いものを採る**（**最長一致**）。**★これが無いと `2 3 6 2 3 6 + P` が波動拳になる**——**SA のコマンドは波動拳のコマンドを先頭に含むためである** |
| 4 | **★同じ長さで複数残るなら解決しない。** **`DES-004` §5 の逆引きと同じ流儀である**（**1 つに定まるときだけ確定する**） |
| 5 | **★先頭のゴミは解決しない**（開発者判断＝入力ミスは解決しない）。**`1 2 3 6 + P` は波動拳にしない** |
| 6 | **出口は必ずキャラ別の `move_code` である**（契約 F-3 の死守 3） |
| 7 | **★解決できなかった入力は捨てずに出す**（`DES-005` §6.4.3 の読取表示の 3 つ目）。**「なぜ解決できなかったか」が分かる粒度で出す** |

> **★規則 3 は設計卓が加えた。** **開発者の指示は規則 1・2 までである。** **⇒ 実データで「最長一致にすると意図と違う技になる」組が見つかったら、そこで止めて報告すること**（`§9.4` の停止条件 2）。

### 4.3 ★契約 F-3 と衝突して見えるが衝突しない（**契約が明記を求めている**）

**F-3 の死守 3 点**——**公式表記のみ解決 ／ モーション解析はしない ／ 出口は必ずキャラ別 `move_code`。**

**★「モーション解析はしない」と本サブは衝突して見える。** **衝突しない**——**段階 1・2 の決定論解決は「表記 → `move_code`」の索引引きであり、本サブは「利用者の実入力 → どの技を指したか」という別の問いである。** **どちらも出口が `move_code` であることは共通で、これは破らない。**

| # | 制約 |
|---|---|
| 1 | **★波形・軌跡・タイミングを解釈しない。** **押された方向の列を、索引が持つコマンドの列と突き合わせるだけである** |
| 2 | **`move_commands` ／ `internal/moveindex/` は読むだけ**（`m21-contract` §5）。**書かない・形を変えない** |
| 3 | **出口は `move_code`**（`§4.2-6`） |

### 4.4 既存の 3 経路を 1 つも変えない

| # | 制約 |
|---|---|
| 1 | **判定層**（`§2.2-1`）——**判定窓・アルゴリズムを触らない。** **モード中に「ステップにしない」を、判定層の分岐で実現しない**（**供給する側で止める**） |
| 2 | **調停・配送チャネル**（`§2.2-2`・`§2.2-4`）——**新しいものを作らない** |
| 3 | **合流層**（`§2.2-3`）——**方向は合流後に採り直す。** **モードの状態は合流の後段に置く** |
| 4 | **§6.5.1 の 3 つの守り**（`§2.2-6`）——**編集可能ガードが先に効くこと・登録済みキーの既定動作を抑止することは不変である。** **★方向キーを更に多用するため、抑止が効いていることを本サブでも確かめる**（§5 (i)） |

### 4.6 ★モーション用の読み取り経路を新設する（**2026-08-14 追加＝D-379**）

**製造の実査で、フロントからモーション用のコマンドを読む経路が存在しないことが判明した。** **既存の解決表は単方向 ＋ ボタンだけに絞っており、多方向のコマンドは全て落ちる。**

| # | 制約 |
|---|---|
