## 1. 目的・位置づけ

**M21 は入力拡充の技術的本丸である。** 物理コントローラを実際に握って、コンボレシピを入力できるようにする。

**性格**——

- **スキーマ変更は予定なし**（契約 §4.2）。**発生したら着手前に設計卓の個別承認を取る。** **⇒ 破壊的マイグレを持たないマイルストーンである。**
- **実機依存が本質である。** **製造担当はターミナル環境であり、実機確認を要求できない**（playbook §1.3）。**⇒ 各サブの DoD で開発者手番を明示する。** **これは M21 の全サブに掛かる横断条件であり、本書 §6 に集約した。**
- **M20 と並走できる。** **契約 F-1 により `recipe_cache` ／ `preset` ／エイリアス辞書は M20 の所有であり、M21 は触らない。**
- **既存の仮想コントローラを壊さない。** **M15-03 / M17-03 で実装済みのカテゴリタブ式 direct-selection は現行の正であり、M21 は物理経路を「追加」する。置き換えではない。**

**達成目標**——

1. **物理コントローラからレシピを入力できる**（`FR105`）
2. **入力内容が読み取り表示され、正確にゆっくり入力できる**（`FR106`）
3. **OD 技等の同時押しが、ズレて入力されても 1 ステップにまとまる**（`FR107`）
4. **チャタリングの扱いが決着している**（`FR108`。**「対策する」とは限らない**＝§4.4）
5. **パッドで実際に 236P 等を振って必殺技を入力できる**（`phase3-overview` §2.3・物理限定）
6. **`REQ-001` FR102 の食い違いが解消している**（§4.1）

**次マイルストーンとの依存**——**M22（協調基盤）・M23（UX 整理）とは順序依存が無い。** **M20 とも独立**（契約 F-1）。

## 4. 主要設計判断・調査結果の反映

### 4.1 `REQ-001` FR102 の食い違いを M21-01 で解消する

**`FR102`（必須・フェーズ1）は「仮想コントローラはレバーレス、アーケードコントローラ、PS5パッド、キーボードの4種類に対応する」と書いたまま残っている。** **一方 `DES-005` §6.1 は「現行の仮想はカテゴリタブ式であって 4 レイアウトではない。§6.2〜§6.5 は物理入力 M21 の将来仕様として温存する」と書いている。**

**`CHANGE-057` は温存を確認事項として開発者に諮り承認を得ているが、`change-report-057` は「REQ-001 変更なし」と記録しており、REQ 側が追随していない。**

**⇒ 4 レイアウトは「あったらいい将来仕様」ではなく、必須・フェーズ1 の要件の本体が重要・フェーズ3 の M21 に預けられた状態である**（**D-326**）。

**⇒ `CHANGE-106` で `FR102` を改訂する。** **改訂の向きは「4 レイアウトの対応範囲を物理入力側へ移す」**（**D-328**＝案 (C) の承認）。

> **★着手前ゲートは通知書 ＋ registry 登録までである。** **`REQ-001` 本体の改訂は M21-01 の as-built 確定後に、change-report と同時に行う。** **「実装はこうなるはず」で DES／REQ を書かない。**

### 4.2 4 レイアウトの負いかたは案 (C)（**D-328**）

**ゲームパッド系 3 種**（レバーレス／アケコン／PS5パッド）**を 1 つのプロファイル層で扱い、キーボードは独立サブとする。**

**理由 2 点**——

1. **プロファイル層は「2 種だけ」でも必要である。** **D-324 が Chrome 単独で機種差を検出している**——**パッドの button 7 は 12 段階のアナログ値を返し、レバーレスは同じ button 7 で `0` / `1` の 2 値しか返さない。** **⇒ 層を作る費用は 2 種でも 3 種でも変わらず、変わるのは「プロファイルを何枚書くか」だけである。**
2. **キーボードを分離すると膨張要因が消える。** **KeyboardEvent はイベント駆動でポーリングが無く、チャタリングは OS 側で除去済みである。** **⇒ PoC の分布を 1 つも流用できない代わりに、`FR108` の論点も存在しない。** **前者の DoD を後者が汚さない。**

### 4.3 キャリブレーション／リマップが load-bearing である（**D-328**）

**開発者はアーケードコントローラを所有していない。** **⇒ M21 の期間中、アケコンの実機確認は 1 回も行えない。**

**★所有していない機体に「対応した」と言える唯一の形は、機体ごとの決め打ちをやめることである。** **「この機体の LP はどのボタンか」を利用者に 1 度押させて覚える形にすれば、我々がその機体を持っていなくても成立する。**

**★同じ導線が 3 つの未知を同時に吸収する**——**アケコン**（非所有）／**Firefox**（未計測・index がずれる）／**将来の未知の機体**。

**⇒ `DES-005` §6.3 の「具体的なキー割当は実装時に確定する」を、決め打ちの表ではなくキャリブレーション方式として実装形へ更新する。** **これが M21-01 を先頭に置く理由である。**

**★出しかたの条件**——**アケコンは「レバーレス・パッドと同じ経路で動く見込みだが、実機未検証」と明示して出す。** **「アケコン対応」と書かない**（**E-84**）。

### 4.4 判定窓とチャタリング（**D-324**・**D-328**）

**PoC の実測**（USB・Chrome・rAF 間隔 中央値 4.20 ms・標本 各 90）——

| 指標 | レバーレス | パッド |
|---|---|---|
| 同時押しズレ 中央値 | 8.30 ms | 8.30 ms |
| p95 | 20.90 ms | 33.30 ms |
| 最大 | 20.90 ms | 45.80 ms |
| **離し始め** 中央値 | **12.50 ms** | **12.50 ms** |
| **離し始め** 最大 | **50.00 ms** | **83.30 ms** |

**★`DES-005` §6.4 の「例：16ms」は実測と合わない。** **押し始めの p95 が既に 20.90 / 33.30 ms である。** **⇒ `CHANGE-107` で是正する。**

**★フレーム数で判定窓を置いてはならない。** **計測環境は約 238 Hz であり、60 Hz 環境では同じ実時間が約 1/4 のフレーム数になる。** **ミリ秒が一次で、フレーム数は本環境の換算値である。**

**★押し始めと離し始めのどちらを判定に使うかは M21-02 が決める**（**D-324** で未決）。

**★Bluetooth は測れない**（**D-328**）。**Gamepad API に接続方式のフィールドが無いため、測れていても実行時に分岐はできなかった。** **⇒ 実装サブへ渡す条件 4 点**——

| # | 条件 |

| 3 | **窓を定数で埋め込まず、1 か所から差し替えられる形にする** |

**★チャタリング（`FR108`）は「対策不要」という第三の結論の候補である**（**E-41** 型）。**PoC では立ち上がり総数 50 が指示回数 50 と画面カウンタ 50 に 2 機種とも完全一致し、1〜32 ms の帯に 3 指標とも 0 件だった。**

**⇒ M21-02 の DoD**——**採るなら「2 機種・USB・Chrome で観測されなかった」を根拠として明記し、一般化しないと書く。** **「チャタリング対策を実装した」と書かない。**

### 4.5 user gesture とブラウザストレージ（**D-324**）

**★全経路で user gesture が必須である。** **入力 UI を開いた直後は `navigator.getGamepads()` が空を返し、利用者が最初の 1 回を押すまでコントローラは見えない。**

**⇒ これは M21-01 の入力 UI の初期状態そのものの設計である。** **「認識しています／していません」の表示と、最初の 1 回を促す導線が要る。** **後から足す装飾ではない。**

**★`DES-005` §6.4.1 は選択保持を localStorage と定めている。** **`CLAUDE.md` §10.X により、許容キーの台帳は `web/CLAUDE.md` §1 が正本である。**

> **★設計卓は `web/` を読めない**（武装）。**⇒ 台帳に当該キーが載っているかを本書は断定しない。** **M21-01 の §3.3 着手前実査に置く**——**載っていなければ CHANGE addendum 経由で台帳へ追記してから使う。** **未記載のまま運用しない。** **検査＝`bash scripts/check-browser-storage-keys.sh`。**

### 4.6 FB⑦ の前提は実査ゲートを置く（契約 F-5）

**FB⑦（前ジャンプ・垂直ジャンプの move 化）は M16 ④ の taxonomy／移動 move 化で先行決定済みという前提に載る**（`DES-004` §2.1）。

**★理由**——**前提が偽のまま入力系を作ると、入力できる技と登録できる技がずれる**（契約 F-5 の症状欄）。

### 4.7 死守契約 3 点との関係（契約 F-3）

**`phase3-overview` §2.3 の死守契約は「公式表記のみ解決／モーション解析はしない／出口は必ずキャラ別 `move_code`」である。**

**★M21-06 の物理モーション入力は、素直に読むとこれに反して見える。** **⇒ 反しない。**

> **★これを M21-06 の指示書 §3.4 にも書くこと**（契約 §5 の注記）。 **理由**——**製造は契約の全数列挙と突合するため、書かないと「モーション解析はしない」に反すると判断して正しく止まる**（**E-105** の逆向き＝**発行側が書かないと適用側が不要に止まる**）。

### 4.8 Firefox は案 (ii)（**D-329**）

**Firefox でも動くように作るが、動くことを M21 の完了条件にはしない。** **実機確認は M21 の完了時に 1 回だけ**（Firefox × 2 機種＝2 組・**総額 +10〜20 分**）。
