## 3. ★★危険

### 3.1 ★★【最重要】DTO の改名は両側同時でないと静かに壊れる

**★`tag-error-detail-dto-snake-case` は「片側だけ直すと壊れる」ことそのものが登録理由である。⇒ 直す手番でそれをやると、本末転倒になる。**

| # | 対象 |
|---|---|
| **1** | **バックエンド**＝`internal/api/tag/handler.go:163-164`（`"usage_count"` / `"force_delete_query"`） |
| **2** | **フロント型**＝`web/src/types/tag.ts:23-25`（`TagErrorDetail`） |
| **3** | **消費**＝`web/src/features/tag/api/tagApi.ts:23`（`details?.usage_count`） |

**★★3 か所を 1 コミットで直すこと。⇒ 分けると、その間の状態が壊れている。**

**★同じ手番で `existing_tag_id` も消す**（バックエンドは 1 か所も返しておらず、フロントも型定義の 1 行以外に参照が無い）**。**

### 3.2 ★★スコープテストは「通ること」ではなく「弾かれること」を見る

**★`tag-delete-user-scope-untested` の試験は、他人のタグを消そうとして失敗することを主張する。⇒ 自分のタグを消せることを確かめても意味が無い。**

**★★破壊確認が要る＝実装から `AND user_id = ?` を外すと赤くなることを実測すること。⇒ 外して緑のままなら、その試験は何も見ていない。**

### 3.3 ★仕様の明文化は、実装に触れないぶん忘れられやすい

**★`tag-category-color-cannot-be-cleared` は実装を変えない。⇒ 「何もしない」で終わらせると、後任が「バグだ」と読んで直しに行く。★それが登録理由である。**
