## 0. この指示書の特殊性

### 0.1 ★★これは機能を足すサブではない

**足すものは無い。やることは「版を上げて、壊れていないことを示す」ことだけである。**

**⇒ 本サブの成果物は動くコードではなく、★「何をどこまで上げ、何で確かめたか」の記録である。**

### 0.2 ★★`go test ./...` が緑でも足りない

**開発者の当初の見立ては「バージョンアップして `go test` すればいいだけ」であった**（2026-09-05）。**設計卓は概ね正しいと判断したうえで、3 点を足した**（`D-724`）。

| # | `go test ./...` が見ないもの | なぜ効くか |
|---|---|---|
| **★★1** | **クロスビルド** | `make build-all` が windows / darwin / linux の 3 つを吐く。**`.github/workflows/nightly-crossbuild.yml` が在るのはそのためである** |
| **★★2** | **`modernc.org/sqlite` の挙動** | **純 Go 実装であり、Go の版に敏感な部類である**（生成コードが標準ライブラリの内部挙動に寄っている）。**⇒ `go test` は通るがクロスビルドで落ちる、が起こりうる面である** |
| **★3** | **E2E** | `make e2e` はバックエンドを実際に起動する |

**⇒ 検証は `go test ./...` ＋ `make build-all` ＋ `make e2e` の 3 点である。**（§2.6）

### 0.3 ★★版数の記載は既に食い違っている

**設計卓が読める範囲で実測した**（2026-09-05）。

| 場所 | 記載 |
|---|---|
| `go.mod` | **`go 1.26.4`** |
| `CLAUDE.md` §2 | **「Go 1.26.2 以上」** |
| `README.md` | **「Go 1.22 以上(devContainer は 1.26.2)」** |
| `docs/design/01-tech-stack.md`（**`DES-001`**） | **「Go 1.22+」** |

**★★4 か所すべてが違う値である。⇒ 1 か所だけ上げると食い違いが増える。**

**★設計卓が読めていない場所がある**——**`.devcontainer/`（`Dockerfile` / `devcontainer.json` / `devcontainer-lock.json`）と `.github/workflows/`（`nightly-crossbuild.yml` / `pr-checks.yml`）**。**武装中の作業ツリーに実体が無いためである。⇒ 母数は製造が出す**（§2.1）。

### 0.4 ★★`M28-01` と同じコミットに混ぜない

**`M28-01` は母数 2,852 件の一括リネームである。⇒ 同じコミットに版上げを混ぜると、赤が出たときに「リネームのせいか Go のせいか」が分からない**（`D-724`）。

**★本サブの中でも同じ理由でコミットを割る**（§2.7）。

## 2. やること

### 2.1 ★★母数を出す（**最初の成果物**）

**版数を書いている場所を全数で出すこと。実装へ入る前に一覧を提示する。**

| # | やること |
|---|---|
| **★★1** | **Go の版数を書いている場所を全数で挙げる。** 設計卓が実測した 4 か所（§0.3）に加え、**`.devcontainer/` と `.github/workflows/`、および `AGENTS.md` / `.codex/` / `.agents/` の Codex 派生物**を必ず見ること |
| **★★2** | **食い違いをそのまま報告する。★直す前に一覧を出す**——**「どれが正しいか」は上げ幅が決まってから決まる** |
| **★3** | **フロント側も同じことをする**（Node の版 ／ `packageManager` の pnpm 版）。**★`web/package.json` の `"packageManager": "pnpm@9.13.x"`** |
| **★4** | **`.claude/` に版数が直書きされていないか。★在れば報告するだけ**（**`.claude/` は開発者のルールファイルであり製造は編集しない**） |

### 2.2 ★★Go ツールチェーンの版上げ

| # | 規則 |
|---|---|
| **★★1** | **上げるのはツールチェーンである。`go.mod` の `go` ディレクティブは上げない。** **★両者は別物である**——**ディレクティブを上げると言語仕様・`vet` の既定・標準ライブラリの挙動が変わりうる**（先例＝1.22 の loopvar）**。セキュリティ更新が目的ならツールチェーンだけで足りる** |
| **★★2** | **上げ先は「同じ minor の最新 patch」を既定とする。★minor を跨ぐ必要があると判明したら、跨ぐ理由を添えて止まり、開発者へ報告する** |
| **★★3** | **どのセキュリティ修正が入るのかを報告に書くこと。★「新しいから上げた」で終わらせない**——**本サブの目的は「利用者へ届くバイナリに入る修正を特定すること」である**〔単一バイナリ配布であり、ビルドに使った Go の版がそのまま利用者へ届く〕 |
| **★4** | **`go.mod` の `go` ディレクティブを上げたくなったら §7 の確認事項へ回す。★製造が単独で上げない** |

### 2.3 Go 依存の版上げ

| # | 規則 |
|---|---|
| **★★1** | **`/app_build_check` を回すこと**（`bash scripts/app-build-supplychain-check.sh`）**。★★総合判定（SAFE / CAUTION / WAIT）をそのまま報告に載せる。判定を上書き・要約しない** |
| **★★2** | **上げるのは patch / minor までとする。★メジャー版上げは §7 の確認事項へ回す**——**API が変わり、`CLAUDE.md` §6 の「新規依存追加は提案してから」と同じ重さになる** |
| **★★3** | **新規依存を足さない。★`indirect → direct` 昇格もしない**（`CLAUDE.md` §6。2026-08-14 開発者裁定＝**「モジュールは既に依存グラフに居た」は理由にならない**） |
| **★4** | **上げた 1 本ごとに、何が変わったか（とくにセキュリティ修正か機能追加か）を報告に書く** |
| **★5** | **`go.sum` の差分は当然出る。★`go mod tidy` の結果として出た差分と、意図して上げた差分を分けて報告すること** |

### 2.4 フロント依存の版上げ

| # | 規則 |
|---|---|
| **★★1** | **`pnpm` を使う。`npm` / `yarn` / `npx` は使わない**（`CLAUDE.md` §11） |
| **★★2** | **`web/pnpm-lock.yaml` はコミット対象である。★`package-lock.json` / `yarn.lock` を作らない** |
| **★3** | **上げるのは patch / minor まで。★メジャーは §7 へ**（React 18 → 19 のような跨ぎは本サブの射程外） |
| **★4** | **`pnpm` 自体の版（`packageManager` フィールド）を動かすなら、動かす理由を報告に書くこと** |

### 2.5 devContainer

| # | 規則 |
|---|---|
| **★★1** | **★`M28-01` が既に `tacpendium` へ書き換えている前提で触る。⇒ リネームをやり直さない** |
| **★★2** | **`/devcontainer_rebuild_check` の存在を報告に書くこと。★★リビルドそのものは開発者の手番である**——**製造の環境でリビルドしても、開発者の環境で同じものが再現する保証がない** |
| **★3** | **`.devcontainer/devcontainer-lock.json` の差分は報告に明示すること**（**★lock の更新はサプライチェーンの変更である**） |
| **★4** | **`.devcontainer/init-firewall.sh` の許可リストに手を入れる必要が出たら、止まって報告する。★製造が単独で広げない** |

### 2.6 ★★検証（3 点 ＋ 常設検査）

| # | やること |
|---|---|
| **★★1** | **`go test ./...`** |
| **★★2** | **`make build-all`**（**★3 OS すべて。1 つでも落ちたら緑ではない**） |
| **★★3** | **`make e2e`**（全数。**★絞り込みの `make e2e-only` では代用しない**） |
| **★4** | **`cd web && pnpm test`** |
| **★5** | **常設検査**（**`scripts/check-artifact-integrity.sh` を 1 本目に回す**＝`CLAUDE.md` §8） |
| **★★6** | **★★落ちたテストを skip / disable / quarantine して緑にしないこと。★落ちたら、落ちた事実を報告して止まる** |

### 2.7 ★★コミットの割り方（**本サブの規約**）

**★理由は §0.4 と同じである**——**赤が出たときに原因を切り分けられるようにする。**

| 順 | コミット |
|---|---|
| **1** | **版数の記載の同期のみ**（コードは動かない） |
| **2** | **Go ツールチェーンの版上げ** |
| **3** | **Go 依存の版上げ** |
| **4** | **フロント依存の版上げ** |
| **5** | **devContainer / CI の版数反映** |

**★2〜5 は、それぞれ単独で revert できる形にすること。**
**★1 コミットにまとめない。★逆に、意味の無い粒度まで割らない**（例＝依存 1 本ごとに 1 コミット）。
