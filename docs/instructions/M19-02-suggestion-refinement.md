## 1. 背景と目的

### 1.1 背景

M19-01 で提案機能（エンジン移植・受理帯方式による窓化・提案 API・提案 UI・採択保存）が完了・受理された（PR #10・独立監査で実装欠陥なし）。delivered 契約は DES-002 v1.36.0 §4.2 と DES-005 v2.50.0 §5.6 項目12 に反映済みである。

その後、以下が確定した。本サブはこれらを製品に反映させる。

1. **filler 規則が広すぎた**（M19-01 完了報告 教訓⑧）。M19-01 は `total ≥ 1` の全技を filler 候補としたが、**`category = target_combo`（多段技の 2 段目以降）は単独で空振りできず、かつ `total` の意味が「派生部分のみ」か「連携全体」か判別できない**（M19-RESEARCH-03 R-C）。実害は **リュウ KA=40 の既定 3 種別で 210 件中 19 件（9.0%）**（同 R-D）。
2. **打ち切りが通常運用で発生している**。ryu KA=40 の既定条件で提案 **210 件 > `MaxResults` 200** に達し `truncated = true` となる。さらに**打ち切りはグルーのランキングより前**（エンジンは少手数優先で列挙し 200 件で切る）に起きるため、**N が深い＝実用価値の高い提案が切り落とされ得る**。加えて `alreadyAdopted` を**打ち切り前の全件**（210〜459 往復）で算出しており N+1 クエリになっている（M19-01 完了報告 §3.7-3）。
3. **負 KA が無説明**。DES-006 VAL-C10 は KA を -600〜+600 で保存可とするが、エンジンは `KA < 0` を弾き、グルーがエラーを飲んで 200 ＋ 0 件を返す。KA NULL には専用文言があるのに負 KA は汎用の「提案なし」で、利用者に「未対応」が伝わらない（同 §3.7-4）。
4. **`rush_variant` の通し値の起点が確定した**（開発者確認 2026-07-26）。**ニュートラル起点で、ラッシュを最速キャンセルして技を出したときの「ラッシュ分＋技分」**である。起き攻めはニュートラルから入るため前提が一致し、followup §H(e) はクローズした。**rush を filler から除外しない**判断が裏付けられた。
5. **「あえて重ねない」提案（通称・汚連携）の要望が確定した**（開発者 2026-07-26）。相手の起き上がりに**意図的に重ねず**、相手の行動を誘発して刈り取る用途。現行の受理条件は「重なる」ものしか返さないため、**別モードとして新設**する。

実装の実体は以下（`code-facts.md` commit `d074002` で裏取り済み）。

### 1.2 目的

1. **filler 候補から `category = target_combo` を除外**する（§4.1）。
2. **負 KA に専用の応答と文言**を与える（§4.2）。
3. **打ち切り仕様を是正**し、**ランキング後に切る**構造へ変える。`totalFound` を返し、UI から「さらに表示」で追加取得できるようにする。あわせて `alreadyAdopted` を**返却分に限定**して N+1 を解消する（§4.3）。
4. **汚連携（gap）モードを新設**する。受理帯の**定数を差し替えるだけ**で実現し、探索アルゴリズムには手を入れない（§4.4）。
5. **制約告知の文面を実装へ追従**させる（`M19-LIMITATION-NOTICE` の全箇所。§4.5）。
6. **撤回済み仕様が資産に残っていないこと**を全文走査で確認する（playbook §4.18。§5.6）。

### 2.2 変更しないもの（原則）

- **DB スキーマ**（テーブル・列・インデックス）。**マイグレを追加しない**。

### 4.3 打ち切り仕様の是正と「さらに表示」

#### 4.3.1 現行の問題

エンジンは**少手数優先**で列挙し `MaxResults`（200）で打ち切る。**打ち切りはグルーのランキング（第 1 キー = N 降順）より前**に起きるため、**N が深い＝実用価値の高い提案が、単に手数が多いという理由で切り落とされる**。ryu KA=40 の既定条件で 210 件に達し、実運用で発生している。

#### 4.3.2 新しい構造

**「エンジンは安全上限まで全列挙 → グルーがランキング → 上位 `limit` 件を返す」**へ変える。

1. **エンジンの `MaxResults` は「安全上限」として残す**。値は §3.3-1 の実測に基づいて決める（**指示書では数値を固定しない**＝playbook §4.15）。目安は「実測した総数分布の最大値に十分な余裕を持たせた値」。この上限に達した場合のみ `truncated = true` とする。
2. **グルーは受け取った全解をランキングしてから `limit` で切る**。`limit` の既定値も §3.3-1 の実測で決める（現行の表示件数＝200 を既定とするのが素直だが、実測次第で製造が決めてよい。**決めた値と根拠を完了報告に記載**する）。
3. **`SuggestionsResponse` に `totalFound`（ランキング対象となった総解数）を追加**する。`truncated` は **1 の安全上限に達したときのみ true**（＝「エンジンが数え切れていない」の意味に限定する）。`limit` で切っただけの状態は `truncated` にしない（`totalFound > len(items)` で表現できる）。
4. **`alreadyAdopted` は返却する `items` の分だけ算出**する（打ち切り前の全件で回さない）。これで N+1 クエリが解消する。

#### 4.3.3 API パラメータ

### 4.4 汚連携（gap）モードの新設

#### 4.4.1 定義

> **【v1.2.0 訂正】** 初版〜v1.1.2 は gap を「起き上がり**後**に隙間を作る（第 1 active が `KA+1` の G フレーム後）」と定義していたが、**これは誤り**。開発者確認（2026-07-26 最終）により、**当てる意図のセットプレイは meaty で実現済みであり、gap は「当てない」専用＝技を丸ごと空振りさせるもの**と確定した。以下が正しい定義であり、実装は既にこの定義で動いている（M19-02 as-built）。**旧定義（`S = KA+1+G`／`G = 1−N`／帯 `[1−Gmax, 1−Gmin]`）は撤回**＝§5.6 の否定形確認の対象。

**あえて重ねない**セットプレイ。相手の起き上がりまでに技を**完全に空振り**させ、相手の行動を誘発して刈り取る用途。

- **ギャップ `G`** ＝ target の**最終 active** が、起き上がり（`KA + 1` フレーム目）の**何フレーム前**に出るか。
- 最終 active `= (KA + 1) − G` かつ 最終 active `= S + active − 1`、`N = KA + 2 − S` より **`G = N − active`**（`S = KA + 2 − G − active`）。恒等式 `N = KA + 2 − S` と着弾 `= KA + 1` は不変で、**別の式は持ち込まない**。
- `G ≥ 1` で最終 active ≤ `KA`（起き上がり前）＝**完全空振り**。よって `N > active` となり、**meaty（`N ≤ active`）と完全に排他**である。
- **範囲は `G = 1 〜 13`**（開発者確定 2026-07-26）。

#### 4.4.2 実装：受理帯の一般化（**エンジンの探索構造には手を入れない**）

現行の受理帯は、実質的に **「`N` が帯 `[NLo, NHi]` に入るか」** を判定している。

- meaty: `NLo = NMin`／`NHi = Active`（`n_max` 指定時は `NHi = min(Active, n_max)`）
- **gap**: `NLo = Active + Gmin`／`NHi = Active + Gmax`（`Gmin=1`・`Gmax=13` なら `[Active+1, Active+13]`）
  - **帯が `Active` に依存する＝target ごとに帯が変わる**。target をまたいで共通の定数にしない。

したがって次のとおり**定数を差し替えるだけ**で成立する。

```go
// 一般化後（NMin / Active を直接使わず、帯の下限・上限を渡す）
budgetMax = KA + 2 − NLo − target.Startup
受理:      0 ≤ remaining ≤ NHi − NLo
成立時の N: N = remaining + NLo
```

- **検証**: `remaining = budgetMax − Σfiller.total = KA + 2 − NLo − S`。よって `remaining = N − NLo`。受理条件 `0 ≤ remaining ≤ NHi − NLo` は `NLo ≤ N ≤ NHi` と**代数的に等価**である。`NLo = NMin`・`NHi = Active` を代入すると**現行の受理帯と完全に一致**する（＝meaty モードの挙動は不変）。
- **反復深化・少手数優先・枝刈り・`sanitize`・`computeMaxDepth` は現行構造を維持**する。gap では `NLo` が `Active` より大きく `budgetMax` が**小さく**なる（旧定義の想定と逆）。**枝刈りが帯に入る解を切り落とさないこと**を §5.1 のテストで担保する。
- `NLo > NHi` のときは**エラーではなく空結果**（既存の `NMin > Active` と同じ扱い）。
- `target.Active < 1` は既存どおり `ErrInvalidTargetActive`。

> **gap では `Active` が受理帯そのものを決める**（旧定義の「`Active` を受理条件に使わない」は**撤回**）。完全空振りの判定が「最終 active の位置」を見るものである以上、`Active` は本質的なパラメータである。

#### 4.4.3 API パラメータと DTO

```
GET /api/combos/:comboId/setplay-suggestions
    ?mode=meaty|gap   // 追加。省略時 meaty（既存挙動＝後方互換）
    &g_min=1          // 追加。gap のときのみ。省略時 1
    &g_max=13         // 追加。gap のときのみ。省略時 13
```

- **`mode=meaty` のとき `g_min`／`g_max` は無視**する。**`mode=gap` のとき `n_min`（および `n_max`）は無視**する（いずれもエラーにしない＝絞り込み設定は不正入力ではない）。
- `g_min < 1` は 1 に丸める。`g_max` は上限 13 で丸める（開発者確定の範囲。**13 を超える指定をエラーにしない**）。`g_min > g_max` は空結果。
- **DTO への追加（後方互換・追加のみ）**:

```
SuggestionDTO {
  ...既存（steps / s / n / landing / targetActive / alreadyAdopted）は不変...
  mode: "meaty" | "gap",   // 追加
  g: int                   // 追加。gap のときのみ意味を持つ（= n − active）。meaty のときは 0

```

- **`n` の型と意味は変更しない**。gap モードでは **`n > active`** になる（`G = n − active`）。**これは恒等式どおりの正しい値**であり、FE は `mode` で分岐して表示を切り替える。
- **ランキング**：meaty は現行どおり（`sort=n` = N 降順／`sort=target` = 重ねる技順・**手数ソートは持たない**）。gap は **`sort=n` のとき `G` 昇順**（隙間が小さいほど相手の行動を狩りやすい）とする。**★`G` を直接比較すること**——`G = N − active` は target ごとに `active` が異なるため、**`N` で並べても `G` 順にはならない**。`sort=target` は同じ。

1. **gap モードのソート順**
   何を: gap モードの `sort=n` を **G 昇順**（隙間が小さい順）としてよいか。
   なぜ: meaty は「N が深い＝有利が大きい」で降順が明確だが、汚連携は「隙間が小さいほど相手を刈りやすい」のか「特定の隙間幅（相手の暴れが出る幅）が有用」なのかで最適な並びが変わる。
   暫定案: **G 昇順**。もし「4F 前後（最速暴れが出る幅）が最も有用」等の実戦的な最適点があれば、そちらを第 1 キーにします。

2. **`limit` 既定の考え方**
   何を: 「さらに表示」の 1 回あたりの増分と既定表示件数を、**現行と同じ 200** で始めてよいか。
   なぜ: 開発者の懸念は「不採用にしていって最後まで来たら到達できない」でした。**ランキング後に切る是正（§4.3.2）で「隠れているのは価値の低い分」になる**ため、既定件数自体は変えなくても懸念は解消するはずです。
   暫定案: **既定 200・増分 200**。実測（§3.3-1）で総数が常に 300 件程度に収まるなら、既定を上げて「さらに表示」が出ない運用にしても構いません。
