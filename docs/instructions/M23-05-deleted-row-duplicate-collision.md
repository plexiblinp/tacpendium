## 1. 背景と目的

### 1.1 背景——**衝突は成立する。実データでも起きている**

**`M23-RESEARCH-01` 軸 H が逐語で確定させた 2 つの事実。**

| # | 事実 |
|---|---|
| **H-2** | **重複判定 `FindActiveByDuplicateKey` の `WHERE` は `deleted_at IS NULL` を持つ**（`is_draft = 0` も持つ）。**⇒ 削除済み行は判定の候補集合に入らない。同じものを再登録する操作は通る** |
| **H-4** | **`Restore` は重複判定を通らない。** **⇒ 復元も通る** |

**⇒ 削除 → 再登録 → 復元 の順で、A と B が同時に「生きている重複」として並ぶ。どちらの操作も現在の実装では拒否されない。**

**★★これは机上の話ではない。** 開発者が dev DB を実測した結果（`M23-RESEARCH-01` 追補 H-5・2026-08-20）——

- **レシピ以外の重複判定キーが一致する組: 8 組**
- **`CalcRecipeHash` 相当を含む完全な重複判定キーが一致する組: 3 組**（`deleted_id -> alive_id` で **`6 -> 7`** / **`5 -> 8`** / **`33 -> 34`**）

**⇒ 「起こりうる」ではなく「起きている」。**

### 1.2 ★★`deleted_at IS NULL` は手落ちではない——**外すと `PUT` が壊れる**

**★本サブでいちばん誤りやすい点である。先に読むこと。**

**`DES-006` §2.3 は、その述語が在る理由を既に書いている。**

> **編集による再登録時の扱い**：本登録済みコンボの編集保存は「旧コンボを論理削除し新コンボを登録する」方式（FR004参照）のため、同一内容の新コンボが一時的に重複しないようトランザクション内で論理削除→新規登録の順に実行する。**論理削除済みレコードは重複判定の対象外とする**（`deleted_at IS NULL` のレコードのみを対象）。

**⇒ 述語は意図的である。** **`VAL-C02` から述語を外すと、`PUT`（識別キーを変える編集）が自分の消した旧行に衝突して、あらゆる編集が重複エラーで落ちる。**

**★★だから本サブは `VAL-C02` を変えない。** **別の、落とさない検証を横に足す。**

### 1.3 目的——**落とさずに知らせる。両側で**

**`M23-overview` §4.6 は決着させるべき問いを 3 つ挙げていた。**

| # | 問い | 答え |
|---|---|---|
| 1 | **`FR301` の重複判定は、削除済み行を見ているか** | **見ていない**（H-2・確定済み） |
| 2 | **復元時に重複判定を掛けるか** | **掛ける**（§4.2） |
| 3 | **掛けるとして、落とすか警告するか** | **警告する**（`M23-04` §13.1 の原則を継承） |

**★★あわせて、本サブは登録側にも掛ける。** **これは `M23-overview` §4.6 が挙げていない側であり、起票時に設計卓が足した。**

**★理由——開発者の懸念に直接効くのは登録側である。** 逐語＝**「削除後に別途同じコンボが登録されていた場合の復元挙動は注意したい。無期限ならそういうコンボがたくさん残る可能性がある」**（`D-458`）。

- **復元側の警告は「もう重複している」を告げるだけである。** そのとき利用者にできることは限られる。
- **登録側の警告は「作り直す前に、ゴミ箱に同じものがある」を告げる。** **⇒ 重複そのものが減る。**

**⇒ 本サブは 2×2 で塞ぐ**（登録側／復元側 × コンボ／セットプレイ）。**★この対称は正当である**——**4 面とも同じ機構で開いている**（判定 SQL が `deleted_at IS NULL` を持つ、あるいは判定そのものを通らない）。**`D-494`（揃えることは無償ではない）は「理由のある非対称を守る」であって「対称を禁じる」ではない。**

| 5 | **仮登録（`is_draft = 1`）を判定の母集団へ入れること** | **★対象外。** 「仮登録と本登録の間では重複判定は行わない」は既定の方針である（`DES-006` §2.3） |
| 6 | **自動的な重複解消・マージ** | **作らない。** 利用者のデータを黙って消す形になる |
| 7 | **`PATCH` 経路への適用** | **★対象外。** `PATCH` は重複判定キーを変えられない（`DES-002` §3.4）ため、重複が新しく生まれない |

## 4. 詳細仕様

### 4.1 新設する検証——**4 件（2×2）**

| ID | 検証内容 | 種類 | 適用経路 |
|---|---|---|---|
| **`VAL-C14`** | **登録しようとしたコンボと重複判定キーが一致する論理削除済みのコンボが在る**（ゴミ箱に同じものがある） | **WARNING** | **`POST /api/combos` のみ** |
| **`VAL-S07`** | **登録しようとしたセットプレイと同じ親コンボに、同一レシピの論理削除済みセットプレイが在る** | **WARNING** | `POST /api/setups` |
| **`VAL-R03`** | **復元するコンボと重複判定キーが一致する生きたコンボが在る** | **WARNING** | `POST /api/combos/{id}/restore` |
| **`VAL-R04`** | **復元するセットプレイと同じ親コンボに、同一レシピの生きたセットプレイが在る** | **WARNING** | `POST /api/setups/{id}/restore` |

**★3 点を守ること。**

1. **★どれも登録・復元を止めない。** `M23-04` §13.1 の原則をそのまま継承する（`DES-006` §13.1）。
2. **★判定キーの定義は `VAL-C02` / `VAL-S04` と同じものを使う。** **別の定義を作らない**——**2 つの「同じ」が並ぶと、片方だけ直されて静かにずれる。**
3. **★件数が 0 でも 4 件とも実装する**（§3.3-7）。**実データの件数は優先度を決めるだけであり、作るかどうかを決めない。**

### 4.2 ★★母集団——**`PUT` が積んだ旧行を除く**

**★★2026-08-23 訂正（D-517）——本節は誤っていた。** **旧行を除くのは `VAL-C14` だけである。`VAL-R03` では除かない。**

**★誤りの中身**——**下の理由 2 つは、どちらも「削除済みを見る母集団」にしか当てはまらない。** **`VAL-R03` の母集団は生存行であり、そこに居る旧行は画面に見えている生きたコンボである。** **⇒ 除くと、見えている重複を黙って見逃す**（偽陰性）。

**★`VAL-R03` の母集団に旧行が入りうるのは「隠されている旧行を API 直叩きで復元した」場合だけであり、そのとき利用者から見えているのは「生きた重複が 2 件」である。** **⇒ 警告するのが正しい。**

**★訂正の経緯**——**本節（散文）は「`VAL-C14` と `VAL-R03`」と書き、§4.4（表）は `VAL-R03` に旧行除外の述語を置いていなかった。** **製造は表に従い、その理由を報告した。** **設計卓は実装を受理し、本節を実装へ合わせた**（**D-517**）。

**⇒ 以下は `VAL-C14` にのみ当てはまる。**

**`VAL-C14` の母集団から、`superseded_by_combo_id IS NOT NULL` の行を除くこと。**

**★理由は 2 つあり、どちらか一方では足りない。**

| # | 理由 |
|---|---|
| **1** | **利用者が復元できない行について「ゴミ箱に同じものがあります」と言っても、できることが無い。** **★これは削除済みを見る母集団にしか当てはまらない**（2026-08-23 訂正）。旧行はゴミ箱の一覧に出ない（`CHANGE-121` / `M23-01`）。**⇒ 対処できない警告は、無視される警告になる** |
| **2** | **★`PUT` は「識別キーを変える編集」だが、キーを変えない編集にも使われうる**（ダメージだけ直す 等）。**その場合、旧行は新行と同じ判定キー ＋ 同じレシピを持ったままゴミ箱に入る。** **⇒ 除かないと、次に似たコンボを作るたびに「ゴミ箱に同じものがあります」が出る** |

**★★ただし印による除外だけでは `PUT` 自身を守れない**（§3.3-1）——**印は新行 id を要するため 2 文目に書かれ、検証の時点ではまだ付いていない可能性がある。** **⇒ §4.5-1 の「経路で絞る」と併用すること。**

### 4.3 ★復元側の母集団——**生きた行だけを見る**

**`VAL-R03` / `VAL-R04` は、復元しようとしている行を除いた「生きた行」の中に一致するものが在るかを見る。**

- **★自分自身を数えないこと。** 復元は `deleted_at` を NULL にしてから検証する（`M23-04` §4.2＝検証は Tx 内・復元の後）。**⇒ 素直に書くと自分が自分の重複相手になる。**
- **★これは「壊れても緑のまま通る」形ではない**——**常に 1 件ヒットするため、テストを書いてさえいれば必ず落ちる。** それでも §5 で明示的に守ること。

### 4.4 問い合わせの作り方

**★既存の問い合わせを変えない。新しい問い合わせを足す**（§2.2）。

| 用途 | 形 |
|---|---|
| **`VAL-C14`** | **`deleted_at IS NOT NULL` ＋ `is_draft = 0` ＋ `superseded_by_combo_id IS NULL` ＋ 判定キー 6 項** → 候補ごとに `CalcRecipeHash` で比較 |
| **`VAL-R03`** | **`deleted_at IS NULL` ＋ `is_draft = 0` ＋ 判定キー 6 項 ＋ `id <> ?`** → 同上 |
| **`VAL-S07`** | 同一親コンボ ＋ **`deleted_at IS NOT NULL`** → レシピ比較 |
| **`VAL-R04`** | 同一親コンボ ＋ **`deleted_at IS NULL`** ＋ `id <> ?` → レシピ比較 |

**★`NULL` 同士を一致として扱うこと**（`DES-006` §2.3。既存の `addNullable` と同じ意味論＝`col IS NULL` を生成する）。**★ここを取り違えると、`position` などが未設定のコンボが検出されなくなる。**

**★レシピの比較を SQL だけで済ませないこと。** `recipe_hash` は列ではなくサービス層の計算値である（H-3）。**追補 H-5 の SQL は `group_concat` による近似であり、`CalcRecipeHash` と一致する保証は無いと自ら断っている。** **⇒ 本番実装は既存の 2 段（SQL で絞る → ハッシュで比較）を踏襲する。**

### 4.5 ★経路の絞り込み

1. **★★`VAL-C14` は `POST /api/combos` の経路でだけ走らせる。** **`PUT` では走らせない**（§4.2 の理由 2 ／ §3.3-1）。**★「述語で除くから経路は絞らなくてよい」と考えないこと**——**印の書き込み順序に依存する形になる。**
2. **`PATCH` では走らせない**（§1.4-7）。
3. **materialize では走らせない**（§1.4-4）。
4. **`VAL-R03` / `VAL-R04` は復元経路のみ。**

### 4.6 応答と見せ方

- **`M23-04` が作った器をそのまま使う**（`DES-002` §4.2 の「復元経路の `warnings`」）。**★器を作り直さない。**
- **★`M23-04` §1.6-2 は「既存の登録・更新経路へ `warnings` を遡って足さない」としていたが、それは同サブの射程を守るための線であり、恒久の禁止ではない。** **本サブが登録 2 経路へ広げる。** **⇒ 設計書間の矛盾ではない**（`CLAUDE.md` §8 の停止条件に当たらない）。
- **`details` の中身**——**`VAL-C14` / `VAL-R03` は `combos` キーに `{id, memo}` ／ `VAL-S07` / `VAL-R04` は `setups` キーに `{id, name}`。** **★`M23-04` が定めた形に揃える。新しい形を作らない**（`DES-002` §4.3 の規則 1）。
- **文言は翻訳キー経由**（`DES-006` §11.3）。**★登録側と復元側で文面を分けること**——**利用者にできることが違う**（登録側＝「復元する／このまま作る」、復元側＝「もう 2 件並んでいる」）。
- **★モーダルにしない。** 本サブの警告はどれも ERROR ではない（`DES-006` §11.1 / §11.2）。

### 4.7 マイグレーション——**1 本も消費しない**

**スキーマを変更しない。** **★「これは列が要る」と判断した場合は実装を進めずに報告すること**（`CLAUDE.md` §10）。
