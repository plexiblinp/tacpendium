## 1. 背景と目的

### 1.1 背景

**`FR103` はレシピ入力の手段として「物理コントローラ（ゲームパッド・キーボード）」を挙げているが、`M21-01`〜`M21-04` が実装したのは Gamepad API の経路だけである。** **キーボードは `KeyboardEvent` の経路であり、まだ 1 行も無い。**

**★設計書のキーボード記述は、本サブで逆転する。** **`REQ-001` の技術前提は「キーボードはデフォルト操作設定のみ対応」と書き、`DES-005` §6.3 は「WASD 方向入力 ＋ JIKLUO などのキーボタン。SF6 のデフォルトキー割当に準拠」と書いている。** **⇒ 開発者判断（2026-08-14・**D-370**）で、**デフォルトは用意せず、全キーを利用者が登録する形**へ改める。**

> **★理由**——**キーボードは利用者により操作設定がかなり変わる。** **推測で当てた既定は、多くの利用者にとって「間違った割当が黙って入っている」状態になる**（`DES-005` §6.3.2 がマクロを既定に含めない理由と同じ構造である）。

### 1.2 目的

| # | 目的 |
|---|------|
| 1 | **`KeyboardEvent` の経路を、既存の論理ボタン層へ接続する**（**判定層を分岐させない**） |
| 2 | **キー割当を全件、利用者が登録する形にする**（**既定を持たない**） |
| 3 | **操作 3 種（削除／保存／修飾）をキーへ直接割り当てる**（**前置き方式は採らない**） |
| 4 | **テキスト入力欄との衝突を塞ぐ** ＋ **設定できないキーを設定させない** |

### 1.3 このサブで作らないもの（スコープ外）

| # | 作らないもの | 理由 |
|---|---|---|
| 1 | **前置きボタン方式** | **`M21-04` が採ったのは「余りボタンが尽きる機体がある」ためである**（**D-358**）。**キーボードにその制約は無い** |
| 2 | **キー割当の既定プロファイル** | **`D-370`＝開発者判断。「デフォルトは用意しない」** |
| 3 | **受け手を決める新しい仕組み** | **`DES-005` §6.4.3 項目 4 の調停へ相乗りする**（**別の調停を作ると 2 通りの答えが並ぶ**） |
| 4 | **配送チャネルの新設** | **`M21-04` が作った操作の配送チャネルへ相乗りする**（**同上**） |

## 4. 詳細仕様

### 4.1 ★既定を持たない全キー登録制（**D-370**・本サブの中核）

| # | 仕様 |
|---|---|
| 1 | **キー割当の既定プロファイルを持たない。** **`DES-005` §6.3.1 の 2 段**〔標準配置の既定 ＋ キャリブレーションによる上書き〕**のうち、キーボードは第 1 段を持たない** |
| 2 | **★`REQ-001` の技術前提「キーボードはデフォルト操作設定のみ対応」は逆転する。** **`DES-005` §6.3 の「WASD 方向入力 ＋ JIKLUO などのキーボタン。SF6 のデフォルトキー割当に準拠」も失効する**（**設計書を直すのは設計卓である**＝`§1.3-9` の対象外だが、本サブは編集しない） |
| 3 | **★登録しないと 1 つも入力できない。** **Gamepad は標準配置の既定があったため未登録でも動いたが、キーボードは動かない。** **⇒ この違いを利用者へ出す**——**「キーボードで入力するには先に登録が要る」ことが、入力面に立った時点で分かること** |
| 4 | **★これは失敗ではなく状態として出す**（`DES-005` §6.5 の「割り当てられない機体がある前提」と同じ流儀）。**エラー表示にしない** |
| 5 | **「対応キーボード一覧」を作らない**（`DES-005` §6.3.1 の条件 2 と同じ理由） |

> **★項目 3 が本サブで最も見落とされやすい。** **開発者の手元では登録済みの状態でテストするため、「未登録の初回」を通らない。** **⇒ テストで固定する**（§5 (a)）。

### 4.2 操作 3 種をキーへ直接割り当てる（**前置き方式は採らない**）

| # | 仕様 |
|---|---|
| 1 | **削除 ／ 保存 ／ 修飾の 3 操作を、それぞれ 1 つのキーへ直接割り当てる** |
| 2 | **★前置きボタン方式を採らない。** **`M21-04` がそれを採ったのは「余りボタンが尽きる機体がある」ためであり**（**D-358**）、**キーボードにその制約は無い** |
| 3 | **★操作の種別は `M21-04` と同じ 3 値を共有する。** **別の列挙を作らない**（`§2.2-3`）。**★作ると、操作を 1 つ足すたびに 2 か所を直すことになり、片方だけ古くなる**（`E-76`） |
| 4 | **★操作用のキーは押下集合に含めない**（`DES-005` §6.2）。**含めると、削除キーを押すだけでステップ候補が立ち、「解決できなかった入力」が読取表示に出る**（`M21-04` が実測した壊れ方と同型） |
| 5 | **登録対象の件数は as-built で確定する**（**`DES-005` §6.3.2 は Gamepad の 14 件を書いている。キーボードは前置きを持たない代わりに操作 3 件を直接持つため、件数が違う**）。**完了報告へ内訳つきで報告すること** |

### 4.3 ★設定できないキーを設定させない（**開発者要求**）

**ファンクションキー・Windows キー（Meta）等、OS やブラウザがより高い優先度の動作を持つキーは、登録対象から除外する。**

| # | 仕様 |
|---|---|
| 1 | **除外したキーは登録導線で選べない**（**押しても登録が完了しない**） |
| 2 | **★除外の理由を利用者へ出す。** **無反応にしない**——**利用者は自分の押し方が悪いと思い、何度も押す** |
| 3 | **★「除外」と「未登録」を区別して出す**（`E-84`。**「使えないキー」と「まだ登録していないキー」が同じ顔で出てはならない**） |
| 4 | **除外するキーの具体的な集合は as-built で確定する**（**OS・ブラウザ・キーボード配列で差があり、設計卓は実測していない**）。**完了報告へ列挙し、判断の根拠を書くこと** |

> **★「登録できたのに動かない」が最悪の形である。** **OS 側が先に横取りするキーを登録させると、利用者からは本アプリの不具合に見える。** **しかも本アプリのログには何も残らない**（イベントが届かないため）。

### 4.4 ★テキスト入力欄にフォーカスがあるときは発火させない（**開発者要求**）

| # | 仕様 |
|---|---|
| 1 | **編集可能な要素にフォーカスがある間は、技入力も操作も発火しない** |
| 2 | **★判定は「フォーカスが編集可能な要素にあるか」で行う。** **要素の種類を列挙して分岐しない**（**列挙は必ず取りこぼす**） |
| 3 | **★操作キーも同じ扱いである。** **メモ欄を打っている最中に保存キーの文字を打っても、保存が走らない** |
| 4 | **テストで固定する**（§5 (d)） |

> **★これを落とすと何が起きるか。** **レシピ入力面はコンボ名・メモ欄と同居する。** **⇒ 文字を打つたびにステップが入り、しかも文字は正しく入る。** **動作を見ても原因が分からず、利用者は「勝手にステップが増える」としか言えない。**

### 4.5 判定層を分岐させない

| # | 仕様 |
|---|---|
| 1 | **`KeyboardEvent` を押下状態へ変換し、Gamepad と同じ判定層へ流す** |
| 2 | **`DES-005` §6.4.2 の判定窓・アルゴリズムを変えない**（`§2.2-1`） |
| 3 | **★OS のキーリピートを新しい押下として扱わない**（**押下の継続として扱う**）。**扱うと、キーを押しっぱなしにしただけで同じステップが並ぶ** |
| 4 | **★サンプルの供給頻度が違うこと**（ポーリング ／ イベント）**を、判定層の側で吸収しない。** **供給する側で形を合わせる**——**判定層に「キーボードのときは」という分岐が入った時点で、`M21-02` の as-built が 2 通りになる** |

### 4.6 受け手の調停に相乗りする

| # | 仕様 |
|---|---|
| 1 | **`DES-005` §6.4.3 項目 4 の調停をそのまま使う**（**最後に触った入力面が受け手**）。**新しい調停を作らない** |
| 2 | **`M21-04` の操作の配送チャネルをそのまま使う**（`§2.2-4`） |
| 3 | **★供給元が 2 つになる**（Gamepad ＋ キーボード）。**`DES-005` §6.4.3 項目 4 は「供給元はアプリ全体で 1 個」と書いているが、これは Gamepad についての記述である。** **⇒ 受け手の調停は 1 つを共有したまま、供給元が 2 つになる形を採る**（**設計書の当該記述は設計卓が是正する**） |
| 4 | **★排他にしない。** **Gamepad とキーボードのどちらからでも入る。** **「キーボードモード」を作らない** |

### 4.7 ブラウザストレージ台帳（**followup を本サブで解消する**）
