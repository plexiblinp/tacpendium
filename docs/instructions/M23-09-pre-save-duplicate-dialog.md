## 1. 背景と目的

### 1.1 背景——**`M23-05` の目的は達成されていない**

**`M23-05` は「ゴミ箱に同じものがある」ことを告げる検証を 4 件足した**（`VAL-C14` / `VAL-S07` / `VAL-R03` / `VAL-R04`）。**同サブの指示書 §1.3 はその目的をこう書いた。**

> **登録側の警告は「作り直す前に、ゴミ箱に同じものがある」を告げる。⇒ 重複そのものが減る。**

**しかし実装された手段は「保存が成功した後の応答に載せるトースト」である。**

**★★保存後に告げるものは、定義上「作り直す前」に告げられない。⇒ 重複は減らない。** **利用者にできるのは「いま作ったものを自分で消し、ゴミ箱から戻す」手作業だけである。**

**★これは製造の実装の漏れではない。設計卓の起票の誤りである**（**D-518**）。**目的は正しく、手段がその目的を果たさなかった。**

**★開発者が実機で見つけた。逐語＝**

> 登録時に同一のレシピであれば、いったんダイアログを出して、入力内容を入れるかゴミ箱から復元するか、両方入れるかを選ばせるべきです。

**★上記は開発者の逐語引用である。** **本指示書が同じ言い回しで曖昧に指示しているのではない**（`scripts/check-instruction-format.sh` のベースライン注記を参照）。

### 1.2 目的

**保存する前に、ゴミ箱に同じものがあることを知らせ、選ばせる。**

1. **保存前チェックの経路を、コンボ側とセットプレイ側の両方に用意する**（§4.1）。
2. **保存ボタンを押したときに、重複が在ればダイアログを出す**（§4.2）。
3. **選択肢は 2 つ**——**「ゴミ箱から復元する」「新しく作る」**（§4.3）。**★「両方入れる」は出さない**（§1.4-1）。
4. **復元を選んだときに入力内容が失われることを、押す前に伝える**（§4.4）。
5. **ダイアログで告げたことを、保存後にもう一度告げない**（§4.5）。

### 1.3 ★★本サブでいちばん大事なこと——**「利用者が次に取れる行動」を実装に持つ**

**`M23-05` の失敗は文面ではなく構造だった。** **同サブの文面は当初「復元できます」「代わりに」と書き、開発者の実機確認でこう指摘された。**

> **作り直すか復元するか選べるのような印象を受けますが、実際は新しいセットプレイが作成され詳細画面に遷移します。**

**⇒ 文面が、実装のしないことを約束していた。** **自動テストでは検出できない**——翻訳キー経由で正しく描画され、テストも lint も型検査も緑になる。

**★★本サブでは、出すすべての文言について「この文を読んだ利用者が次に取れる行動」を 1 つ挙げ、それが実装に在ることを確かめること。** **無ければ、文面か実装のどちらかが間違っている。**

## 4. 詳細仕様

### 4.1 保存前チェックの経路

#### 4.1-1 コンボ側——**既存の経路を広げる**

**`POST /api/combos/check-duplicate` は現在、生きた行しか見ていない**（§3.3-3）。**⇒ 削除済みの一致も返すよう応答を広げる。**

- **★生きた側と削除済み側を別のキーで返すこと。** 混ぜない。**画面は「生きた重複」と「ゴミ箱の重複」で違う振る舞いをする**（§4.1-4）。
- **★母集団は `M23-05` の `VAL-C14` と同じにする**——**`deleted_at IS NOT NULL` ＋ `is_draft = 0` ＋ `superseded_by_combo_id IS NULL` ＋ 判定キー 6 項 → レシピのハッシュ比較。** **★`M23-05` が作った処理を呼ぶ。判定を書き直さない**（§3.3-1）。
- **★既存の応答のキーを変えないこと。** 追加だけである。

#### 4.1-2 セットプレイ側——**新設する**

**同等の経路が無い**（§3.3-6）。**⇒ 新設する。**

- **★形はコンボ側に揃える**（生きた側と削除済み側を別のキーで返す）。**★新しい形を作らない**（**D-417**）。
- **★母集団は `M23-05` の `VAL-S07`（削除済み）と `VAL-S04`（生存）と同じにする。**
- **★経路名はコンボ側の実経路に倣うこと**（§3.3-3 で確かめた形）。**★セットプレイの登録は `POST /api/combos/{comboId}/setups` であり、親コンボ id を要する**（`M23-05` as-built）。

#### 4.1-3 ★応答は「人が読める文字列」を持つこと

**ダイアログは「どれを復元するのか」を利用者へ見せる。** **⇒ id だけでは足りない。**

- **コンボ＝`memo`**（**★`M23-04` / `M23-05` が `ComboRef{id, memo}` を使っている。揃えること**）。
- **セットプレイ＝`name`**（同じく `SetupRef{id, name}`）。
- **★§3.3-4 で「持っていない」と分かったら足すこと。** **★足せない理由が見つかったら、実装を進めずに報告すること**——**「どれを復元するのか」が見えないダイアログは、選ばせているように見えて選ばせていない。**

#### 4.1-4 ★生きた重複は本サブでは扱わない

**応答には載せる**（§4.1-1 / §4.1-2。**★安いうえ、経路の形が素直になる**）。**ダイアログは出さない。**

| 種類 | 本サブ後の振る舞い |
|---|---|
| **削除済みの重複** | **★ダイアログを出す**（§4.2） |
| **生きた重複（コンボ）** | **★従来どおり。** リアルタイム警告の表示のみ。保存すると `VAL-C02` で `400` |
| **生きた重複（セットプレイ）** | **★従来どおり。** 保存すると `VAL-S04` で `409 duplicate_setup` |

**★理由**——**生きた重複は既に ERROR で止まっている。** **本サブの目的は「ゴミ箱の重複に気づかせる」ことであり、そこへ手を広げない。**

### 4.2 ダイアログを出す条件

#### 4.2-1 ★保存ボタンを押したときに出す。入力中には出さない

**★リアルタイムに出すと、入力のたびにモーダルが出る。**

**⇒ 保存ボタン押下 → 保存前チェック → 削除済みの一致が在ればダイアログ → 選択 → 実行。**

#### 4.2-2 ★WARNING でモーダルを出すことは、逸脱ではない

**`DES-006` §11.1 は WARNING を「入力フォーム下部に警告リストとして表示」としており、§11.2 の「ERROR はモーダル」と対になっている。** **本サブはその線を越えるように見える。**

**★★越えていない。区別は「警告の表示」か「操作の分岐」かである。**

- **警告の表示**——**利用者は読むだけでよい。** §11.1 の形。
- **操作の分岐**——**利用者が選ばないと次へ進めない。** モーダルで出すのが正しい。

**★先例がある**——**`VAL-N02`**（`DES-006` §7）。**LAN 共有モードをパスワード未設定で有効にするとき、種別は WARNING でありながら「明示的な同意ダイアログで承認を得る」としている。**

**⇒ 本サブのダイアログは同じ型である。** **★`CHANGE-141` で `DES-006` §11 へこの区別を明文化する**（設計卓が行う）。

#### 4.2-3 チェックが失敗したときは、保存を止めない

**保存前チェックがエラーを返した場合、ダイアログを出さずに従来どおり保存へ進むこと。** **★ログには残す。**

**★理由**——**チェックは付加価値であり、それが壊れたことで登録という利用者の主目的を巻き添えにしない。** **★`M23-04` §4.2 が復元の検証で採ったのと同じ規律である。**

### 4.3 ダイアログの中身

#### 4.3-1 ★選択肢は 2 つ ＋ キャンセル

| # | 選択肢 | 何が起きるか |
|---|---|---|
| **1** | **ゴミ箱から復元する** | **復元 API を叩く。★いま入力した内容は保存されない**（§4.4） |
| **2** | **新しく作る** | **従来どおり登録する。★ゴミ箱の行はそのまま残る** |
| — | **キャンセル（戻る）** | **何もしない。編集を続ける** |

**★★「両方入れる」は出さない**（§1.4-1・**D-518**）。

#### 4.3-2 ★どれが該当したのかを見せる

**該当した行を、人が読める文字列付きで示すこと**（§4.1-3）。**★「ゴミ箱に同じものがあります」だけでは、利用者は何を復元するのか判断できない。**

**★該当が複数のときの扱いを決めること。** **暫定案＝一覧で示し、復元する 1 件を選ばせる。** **★選ばせずに「1 件目を復元」としないこと**——**どれが戻るか分からないまま不可逆でない操作をさせるのは、選ばせているように見えて選ばせていない。**

#### 4.3-3 ★復元を選んだ後の遷移

**復元して詳細画面へ行く。** **★編集画面へは行かない**（§1.4-8）。

**★理由**——**復元したものと、いま入力した内容は違いうる**（判定キーとレシピは同じでも、memo やダメージは違う）。**⇒ 利用者に「戻したものを見る」機会を先に与える。編集するかは利用者が選ぶ。**

### 4.4 ★★復元を選ぶと入力内容が失われることを、押す前に伝える

**★これが本サブでいちばん落としやすい点である。**

**利用者は入力を終えて保存ボタンを押している。** **⇒ 手元に未保存の作業がある。** **★その状態で「復元する」を押すと、入力が消える。**

**⇒ 押す前に伝えること。** **★押した後に「消えました」と伝えるのでは遅い。**

**★先例がそのまま当たる**——**`DES-006` §11.2 の版不一致の規律**：

> **★読み込み直すと自分の編集が消えることを、押す前に伝える。**

**★同じ形である。** **⇒ 文面と配置を §11.2 の 4 点に揃えること**（入力を保持したまま表示する ／ 進む道を示す ／ 消えることを押す前に伝える ／ 「失敗」と書かない）。

### 4.5 ★ダイアログで告げたことを、保存後にもう一度告げない

**「新しく作る」を選んだ場合、サーバは従来どおり `VAL-C14` / `VAL-S07` の警告を応答に載せる**（`M23-05`）。**⇒ そのままだと、ダイアログで告げた同じことをトーストでもう一度告げる。**

**⇒ 画面側で抑制すること。**

**★3 点を守ること。**

1. **★サーバの契約を変えないこと**（§2.2）。**「確認済み」を示すフラグをサーバへ送らない**——**サーバが「確認済み」の意味を持つと、API を単体で叩いたときの意味が曖昧になる。**
2. **★抑制するのは「ダイアログを出したうえで『新しく作る』を選んだとき」だけである。** **ダイアログを出さずに保存した場合**（チェックが失敗した §4.2-3 のとき 等）**は、従来どおりトーストを出す。**
3. **★`M23-05` が入れた文面の回帰ガードを消さないこと**（§3.3-8）。**保存後トーストの文面は変えない。**

### 4.6 その他の実装上の注意

1. **★ダイアログの表示中に保存ボタンを二重に押せないこと。**
2. **★キャンセルしたとき、入力内容が失われないこと。**
3. **★§3.3-9 で多重送信の防止が無いと分かった場合は、本サブの範囲で防ぐこと**——**ダイアログを挟むと押下から送信までの間が長くなり、二重送信の窓が広がる。**
4. **文面は翻訳キー経由**（`DES-006` §11.3）。**ja / en の両方。**

### 4.7 マイグレーション——**1 本も消費しない**

**スキーマを変更しない。** **★「これは列が要る」と判断した場合は実装を進めずに報告すること**（`CLAUDE.md` §10）。

### 4.8 ★否定形確認——**本サブは「出さない」を 3 件持つ**

**完了報告に、以下 3 件を理由付きで明記すること。**

| # | 出さなかったもの | §のどれか |
|---|---|---|
| 1 | **「両方入れる」の選択肢** | 1.4-1（**★目的と逆行する**） |
| 2 | **生きた重複に対するダイアログ** | 4.1-4（**★既に ERROR で止まっている**） |
| 3 | **入力中（リアルタイム）のダイアログ** | 4.2-1（**★入力のたびにモーダルが出る**） |

### 4.9 ★★文言の自己検査（**必須**）

**§1.3 のとおり、出すすべての文言について次を行うこと。**

1. **「この文を読んだ利用者が次に取れる行動」を 1 つ挙げる。**
2. **それが実装に在ることを確かめる。**
