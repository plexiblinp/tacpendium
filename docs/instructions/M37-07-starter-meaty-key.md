## 0. この指示書の特殊性

### 0.1 ★★★これは「8 つ目の重複判定キー」を足すサブである

**★開発者裁定**（`D-874`・逐語）**＝「重複判定キーに入れる（カウンターやパニッシュカウンターのようにレシピ等が同一でも、この区分が違えば別コンボ判定になる系と認識した上での回答）」。**

**★★★着手前のキーは 7 要素である**（`SUPP-001` §重複判定キー）**。**

```
character_id ／ recipe〔combo_steps の順序込み move_id 列 ＋ modifiers の完全一致〕
／ starter_move_id ／ position ／ opponent_stance ／ hit_type ／ opponent_size
```

**⇒ ここへ 8 つ目を足す。★`hit_type` と同じ立ち位置である。**

### 0.2 ★★★`hit_type` とは別枠である

**★開発者の逐語＝「始動技用としては別枠として欲しい。ヒット種別とも別枠」。**

**⇒ `hit_type` へ値を足す形にしないこと。★`hit_type` は 8 値のままである**（`CHANGE-198`）**。**

**★★理由＝持続当ては*ヒットの種類*ではなく*当て方*である。⇒ 「持続当てのカウンターヒット」がありうる。★1 つの列に畳むと表せない。**

### 0.3 ★★★`combo_oki_options` の打撃重ねとは**向きが違う**

**★実物＝`combo_oki_options` は 12 変種を持ち、そのうち `oki_strike_meaty_*` が打撃重ねである**（`CHANGE-063` / `M16-03`）**。**

| | 何を表すか |
|---|---|
| **`combo_oki_options` の打撃重ね** | **★このコンボの*後に*、どんな起き攻めができるか**（出る側） |
| **★★本サブが足す列** | **★このコンボの*始動が*持続当てか**（入る側） |

**★★★概念はスキーマに在るのに、向きが片方だけであった。⇒ 開発者の「サブの作り忘れ」という見立ては当たっている。**

**★★混ぜないこと。⇒ `combo_oki_options` を 1 バイトも触らない。**

### 0.4 ★★フェーズ5 の要件の前提になる

**★`followup` の `setup-to-combo-navigation-by-last-move`**（`SM-146`・フェーズ5・`D-646`）**の逐語＝「始動技がセットプレイの最後の技**〔セットプレイの最後の技以外は相手がダウン中の空振りであり、**最後の技が当たるとコンボが始まる**〕**でフィルターした内容を見せたい」。**

**⇒ その「当たる」が持続当てである。★本サブはその前提を用意する。**

**★★★ただし本サブでセットプレイとの連携は作らない**（§3-2）**。⇒ フェーズ5 の射程である。**

### 0.5 ★★★列は `NOT NULL DEFAULT 0` である

**★★重複判定キーに入るため NULL にしない。⇒ SQL では `NULL != NULL` であり、NULL を許すと「不明どうし」が別コンボになる。★意味の無い分岐が生まれる。**

**★既存 133 行はすべて `0`**〔非持続当て〕**になる。⇒ 一様であるから、既存行のあいだに新しい重複も新しい分離も起きない。**

**★★★3 値**〔持続当て / 非持続当て / 不問〕**にしないこと。⇒ 「不問」を許すと、上と同じ問題が起きる。**

## 4. ★★危険（**先に読むこと**）

### 4.1 ★★★最大の危険＝**足す先を数え落とすこと**

**★重複判定キーは 1 か所ではない。⇒ Go の判定 ／ フロントの `extractKeyFields` / `hasKeyChanges` ／ `CheckDuplicateInput` ／ CSV の事前重複判定。**

**★★1 か所でも漏れると、症状が*静か*である。⇒ 「重複でないものが重複と言われる」または「`PUT` へ行くべき編集が `PATCH` へ行く」。★どちらも型検査もテストも通る。**

**★★★段 1-1 で数え、報告へ箇所数を書くこと。⇒ 数えずに直し始めない。**

**★既知の弱点が 1 つ在る＝CSV 取り込みの事前重複判定は正規化前の値を使う**（`followup` の `csv-import-precheck-duplicate-uses-unnormalized-position`）**。⇒ 本サブでその穴を直す必要は無いが、足す先には含まれる。**

### 4.2 ★★2 番目＝**`recipe_hash` と混同すること**

**★重複判定キーは「recipe ＋ 6 つの列」である。⇒ `recipe` の側は `combo_steps` の move 列 ＋ `modifiers` の完全一致であり、ハッシュで持つ。**

**★★`starter_meaty` は*列の側*である。⇒ `recipe_hash` は 1 バイトも変わらない。**

**★★★変えてしまうと、既存全行のハッシュが変わり、重複判定と `recipe_cache` が同時に狂う。**

### 4.3 ★★3 番目＝**`hit_type` へ寄せたくなること**

**★実装上は `hit_type` に値を足すほうが安い**〔列を足さずに済む〕**。⇒ ★★しかし開発者が明示的に否定している。**

**★★★「持続当てのカウンターヒット」が表せなくなる。⇒ 1 つの列に畳んではならない。**

### 4.4 ★★4 番目＝**キーが増える向きを取り違えること**

**★キーを 1 つ増やすと、これまで「重複」とされた組が「別コンボ」になりうる。⇒ *減る*方向には動かない。**

**★★既存行はすべて `0` であるから、実際には何も変わらない。⇒ ★確認すること**（§5-3）**。**

**★★★意図は「これから」である。⇒ 同じレシピの「持続当て始動」と「通常始動」を別々に登録できるようになる。**

### 4.5 ★5 番目＝**CSV の往復を壊すこと**

**★任意列として*列末尾*へ足す。⇒ 旧 CSV**〔列が 1 つ少ない〕**が読めなくなったら射程超過である。**
