### 1.3 ★なぜ検査が要るのか（**方針の根拠。書き換えないこと**）

**★最も重いのは正規化のゆれである。**

**検証子は受け取ったバイト列に対して計算する。** **`が` は NFC（U+304C）と NFD（`か`＋U+3099）の 2 通りがあり、見た目が同一なのにバイト列が違う。** **⇒ 決めた端末と入れる端末で正規化が違うと、正しく打っているのに永久に入れない。**

**★本アプリは「ほかの機器から開く」ことが目的であり、この経路は例外ではなく主経路である。** **しかも症状は「パスワードが違います」だけで、利用者からは原因が絶対に分からない。**

**★次に重いのは全角・半角の取り違え**（`Ａ` と `A`、全角スペース U+3000 と半角スペース）。**マスク表示では見分けられない。**

**★3 つ目は、マスク欄で IME が使えない可能性である**（`<input type="password">` では OS / ブラウザが IME を無効化することがある）。**⇒ 日本語で決めると、ログイン画面で「表示」を押すまで打てない事態が起こりうる。**

| # | 内容 |
|---|---|
| 1 | **★印字可能な ASCII のみを受け付ける**（`U+0020`〜`U+007E`。**半角スペースを含む**）。**⇒ §1.3 の 3 つをまとめて消す** |
| 2 | **前後の空白を除去する** |
| 3 | **長さの下限と上限を設ける** |
| 4 | **本文サイズの上限を設ける**（**★掛ける範囲に注意する**＝§4.2） |
| 5 | **★NFC 正規化（案 a）は採らない。** **理由**——**問題を半分しか解かない**〔正規化のゆれは消えるが、全角・半角の取り違えと IME の問題が残る〕**うえ、`golang.org/x/text` の direct 昇格が要る**（`CLAUDE.md` §6） |

## 4. 詳細仕様

### 4.1 パスワードの検査（**最重要ゲート 1 を含む**）

| # | 内容 |
|---|---|
| 1 | **★採番済みの検証コードは 3 つである**（`CHANGE-119`。**製造は採番しない**）——**`VAL-N05`＝文字種** ／ **`VAL-N06`＝長さ** ／ **`VAL-N07`＝本文サイズ** |
| 2 | **★★検査は「決めるとき」だけに掛ける。照合には掛けない**（**最重要ゲート 1**）。**⇒ `Service.Login` の照合と、変更時の「いまのパスワード」には文字種検査も長さ検査も掛けない。** **★理由**——**掛けると、既に非 ASCII や短いパスワードで決めた利用者が入れなくなり、しかも変更もできなくなる〔変更は現在のパスワードを要求するため〕。** **⇒ 詰みが生まれる。** **★開発者の手元がこれに当たりうる**（§3.3-3） |
| 3 | **`VAL-N05`（文字種）**——**印字可能な ASCII（`U+0020`〜`U+007E`）以外を含むなら 400 で拒否する。** **★半角スペースは含む**（合い言葉の形を残すため） |
| 4 | **`VAL-N06`（長さ）**——**前後の空白を除去したうえで、`4` 文字未満または `128` 文字超なら 400 で拒否する。** **★数は設計卓の判断であり、実装上の理由で変えたいなら報告すること。** **★下限の目的は「打ち間違いで空に近い値が通るのを防ぐ」ことであり、強度ではない。** **★上限は反復コストには効かない**〔PBKDF2 は HMAC の鍵正規化で長い鍵を 1 度ハッシュしてから反復するため〕**——効くのはメモリと帯域である** |
| 5 | **前後の空白の除去**——**★「決めるとき」と「入れるとき」の両方に掛ける。** **★受け入れる代償を明記する**——**前後に空白を含む既存のパスワードは使えなくなる。** **★確率は極めて低く**〔意図して空白で囲んだ場合のみ〕**復旧経路も在る**（`config.toml` の `[security]` の 2 行を消す＝`D-407`）。**⇒ 完了報告へこの代償を書くこと**（§7.5-3） |
| 6 | **拒否は 400 とし、理由を区別できるコードを返す**（`VAL-N05` と `VAL-N06` で別）。**★`invalid_password`〔ログイン失敗〕と混ぜないこと**——**あちらは理由を区別しないのが仕様である** |
