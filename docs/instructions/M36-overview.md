## 0. なぜこのマイルストーンが要るか

### 0.1 ★★★配布物を組む仕組みが存在しない

**★開発者回答**（2026-09-12・逐語）**＝「リリースの zip はいまは作っていないです。GitHub にも自動で作るような仕組みはないはずです。確か exe だけで zip 化はしていないはず。なのでこれからやり方を新設する必要があります」。**

**⇒ `DES-002` §11.2 が定める配布物の構成は、一度も実現されていない。★設計と as-built の乖離である。**

| 分かっていること | 根拠 |
|---|---|
| **CI は組まない** | §11.3 ＋ `CHANGE-129`＝**CI の artifact は配布物ではない。nightly が残すのは素のバイナリ** |
| **`Makefile` にも zip ターゲットは無い見込み** | 開発者回答 |
| **手順書も無い** | 実査（`docs/` 全走査） |

### 0.2 ★★`M26` はこの面を埋めていない

**★`M26`（公開ゲート A）が実装したのは*ソースの公開スナップショット生成*である**（許可リスト方式。`M26-02`）**。⇒ *バイナリのリリースパッケージング*ではない。★別の面である。**

### 0.3 ★★★`B1`（コード署名）の代替案が同じ面に載る

**★開発者判断**（2026-09-12）**＝コード署名は後回し。⇒ 代替案を実施する。**

**★根拠＝`docs/human-notes/future-notes/combmgr-license-strategy-outline.md` §10.6 の逐語**——**「コード署名は費用対効果で判断（個人だと年額数万円規模、かつ新しい証明書は SmartScreen の警告がすぐには消えない）。この規模では CI 来歴＋チェックサムの方が費用対効果が高い」。**

**⇒ 同節が推す 4 件は、いずれも「リリース成果物をどう出すか」の話である。★zip の組み立てと同じ CI / リリース手順に載る。⇒ 別々に起票すると同じ面を 2 回触る。**

## 4. ★★危険

### 4.1 ★★★「組んだ」と「検証できる」は別である

**★zip を作るだけなら数行で済む。⇒ しかし本 MS の値打ちは、`B1` を諦めた代わりに「このバイナリはこのコミットから作られた」を*検証可能にする*ことにある。**

**⇒ 射程 2〜5 は飾りではない。★`B1` の代替として開発者が選んだものである。**

### 4.2 ★★手元からアップロードしないこと（射程 6）

**★`license-strategy-outline` §10.6 の逐語＝「CI（GitHub Actions）でビルドし、リリース成果物をそこから出す。手元のマシンからアップロードしない」。**

**⇒ 手元から出すと、来歴署名の意味が消える。★射程 3 は射程 6 とセットである。**

### 4.3 ★`CHANGE-129` と衝突しないこと

**★同 CHANGE は「CI の artifact は配布物ではない」と定めた。⇒ 本 MS は*リリース時*に成果物を出す経路を作るのであり、nightly の artifact を配布物へ格上げするのではない。**

**★★契機が違う**（nightly＝定時 ／ リリース＝タグ）**。⇒ 混ぜないこと。★混ぜると `CHANGE-129` の改訂が要る。**

### 4.4 ★★GitHub の機能は変化が速い

**★`license-strategy-outline` §10.6 の注記＝「GitHub の機能は変化が速い。実際の有効化手順は*現時点の公式ドキュメント*で確認すること」。**

**⇒ artifact attestation / SBOM の具体的な設定は、記憶で書かないこと。★`/ask_external_ai` で最新を確かめる手がある。**
