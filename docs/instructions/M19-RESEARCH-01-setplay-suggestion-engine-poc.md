## 0. この指示書の特殊性

### 0.1 製造担当として起動 + 調査＋PoC デモだけ実施して閉じる運用
製造担当セッションを起動し、§4 の事実列挙（A〜C・E）と §4 D の PoC デモ実行を行い、§5 レポートを書いてクローズする。**本実装（エンジンの本体統合・提案 UI・保存導線）は本調査の対象外**で、PoC 品質確認後に別指示書（M19-01・M19 ローカル採番）で扱う。ただし本実装は DES 反映を伴うため、その段で **CHANGE 番号・マイグレ連番・DES/REQ 本体反映の 3 リソースを中央へ請求**する。

### 0.2 read-only の範囲（PoC 実行を含むよう明確化）
本サブは「調査」と「PoC デモ」を兼ねる。許可・禁止を厳密に分ける。

**許可**:
- `view`／`grep`／`git log`／`find`／`ls`／SQL `SELECT`（本体リポ・別リポ双方）。
- **別リポ `autopilot-combomgr/projects/setplay-suggestion` のエンジンの実行**（`go build`／`go test`／`go run`＝デモ目的）。
- **一時的な PoC ハーネスの作成**（`/tmp` 配下など**リポ外の使い捨て領域**に限る。エンジンへ入力を渡し出力を集めるだけの薄いドライバ）。
- 本体 SQLite DB からの読み取り（**コピーを `/tmp` に作って読む**。原本を開いたまま書き込む操作はしない）。

**禁止**:
- 本体リポ・別リポの**ソース／マイグレ／seed／テスト／DES/REQ 本体の変更**（1 バイトも変更しない）。
- 本体 DB 原本への**書き込み**（INSERT/UPDATE/DELETE/マイグレ適用）。
- エンジンを本体へ**移植・vendor すること**（本実装の作業＝対象外）。
- 採番（CHANGE・マイグレ連番）。read-only＋PoC ゆえ**採番不要**。必要が生じたら中央へ請求（自採番しない）。

### 0.3 判断・提案を含めない（judgement-free）— PoC の扱い
- 調査（A〜C・E）は**事実列挙のみ**。「ここを直すべき」等の修正方針・設計結論は書かない。
- PoC（D）は**評価的“事実”を出す**：golden-case が出たか（hit/miss）・成立しないレシピを出したか・既存紐付けを再現したか・実行時間、を**数値と実出力で**示す。**「品質が十分か（合格線）」の判定はしない**＝合格線は開発者が数値を見て置く（起動キット §2「先に測る→後で置く」）。
- 例外として記録してよいのは (1) 想定外の発見、(2) 明らかな矛盾の事実指摘（例: エンジンが参照する列が現行スキーマに存在しない）。これらは判断ではなく事実。

## 1. 背景と目的

### 1.1 背景
M19（セットプレイ自動提案）は「既存コンボを選択 → その `knockdown_advantage` からセットプレイのレシピを提示 → ユーザーが間合い等を検証 → 繋がるものだけ採択 → 既存 `setups`＋`combo_setups` に保存」する機能である（起動キット v1.3.0 §1）。その中核ロジックは**別リポ `autopilot-combomgr/projects/setplay-suggestion` に先行実装済みのフレーム導出エンジン**であり、本体アプリ（code-facts の対象）には存在しない。エンジンは**しばらく前に作成**され旧式化リスクがあるため、本実装着手前に read-only で実体を確定し、実データで出力品質をデモする（M17-E11＝「ロジックが動く」と「機能が使える」は別・実データ実経路で確かめる）。

### 1.2 目的
§4 の項目を、**本体リポ・別リポ双方の実コード／実 SQL／実行結果**を view・grep・SELECT・エンジン実行で確認し、§5 の様式で報告する。特に **(a) エンジンの入力に `knockdown_advantage` が入るか（最重要裏取り）**、**(b) 言語＝Go 1.24/stdlib-only の申告の検証（G-4）**、**(c) 旧式化ギャップ**、**(d) golden-case 再現**を事実で確定する。本 report が本実装（M19-01）のスコープ確定入力となる。

### 1.3 この調査でやらないこと（§0.2 の再掲）
実装・移植・vendor・マイグレ・seed/コード変更を一切しない。最終決定（合格線・統合方式の確定）をしない（材料提示のみ）。DES/REQ 本体を変更しない。別リポのソースを変更しない。採番しない。

## 4. 調査項目

各項目は「実コード/実 SQL/実行結果を view・grep・SELECT・実行し、**関数名・列名・件数・生出力は実値で**報告する」「確認不能は**未確認と明記**する」を徹底する。

### A. 別リポエンジンの実体（I/O 契約・言語・アルゴリズム・動作可否）
- **A-1**: リポ `autopilot-combomgr/projects/setplay-suggestion` の実在・トップ構成（`ls`/`find`）・`go.mod`（module 名・Go バージョン・**require 節＝外部依存の有無**）を実値で報告。**開発者申告「Go 1.24/stdlib-only」の真偽を go.mod と全 import の grep で裏取り（G-4）**。
- **A-2**【最重要】: エンジンの**公開エントリ関数のシグネチャ**を全数 grep（`func` 定義・exported なもの）。**入力パラメータに `knockdown_advantage`（有利フレーム）に相当するものが含まれるか**を実コードで確定。入力が「当てたい技＋その startup/active＋moves のみ」なのか、有利フレームも取るのかを、型定義（struct）とともに実値で報告。
- **A-3**: レシピ探索アルゴリズムの概要を関数本体の view で要約（事実のみ）。特に **(i) 相手起き上がりタイミングをどう扱うか**、**(ii) meaty の active 窓（何 active 目が当たるか＝「持続 3F 目」相当）を計算するか**、**(iii) filler（dash/歩き/繋ぎ技）で有利フレームを消費してレシピを組むか**、を実装の有無で報告。
- **A-3b**【オフバイワン・最重要級】: エンジンが meaty 着弾フレームを **`knockdown_advantage`（例 40）そのもの**で扱うか、**`knockdown_advantage+1`（例 41＝起き上がり・無敵明け）**で扱うかを、**該当計算の実コード行を引用して**確定（前提事実 8）。無敵ダウン時間の +1 補正の有無・その定数/式を実値で報告。**「先行実装は 40 で計算していた可能性が高い」という開発者仮説の真偽を事実で判定**（judgement ではなく「実装が N か N+1 か」の事実）。
- **A-4**: 現状動作可否＝`go build`・`go test` が通るか（結果を実値で）。付属サンプル/テストデータでの実行例があれば 1 件実行して生出力を報告。
- **A-5**: エンジンが前提とする**データ形状**＝moves の表現（フィールド名・frame 単位・技コード体系）・当てたい技の指定方法を、型定義とサンプル入力から実値で報告。

- **B-2**: エンジンの**技コード体系**を現行 DES-004 v1.14.0 の表記正典と突合。乖離（旧コード・改名・欠落）を事実列挙。

- **B-4**: 上記から**互換ギャップを事実で列挙**（「エンジンが参照する X が現行スキーマに Y として存在/不在」の形）。moves-input-tool「旧式の可能性」前例（M14-d）に照らし、同種のドリフトがあるかを明示。

### C. グルー層の分界（エンジン既存 vs M19 新規）

- **C-2**: **ランキング**（複数レシピの優先順位付け）がエンジンにあるか。あれば基準を、無ければ「M19 新規」と記録。
- **C-3**: **採択 → 保存**（`setups`＋`combo_setups` へ）連携がエンジン/本体にあるか。無ければ「M19 新規（既存 setups API 再利用の見込み）」と記録。
- **C-4**: DES-005 v2.47.0 §5.6 項目11 / `SetupSelectorModal` の候補面が、提案結果の**表示先**として受けられる形か（既存 DTO・props を view して事実確認。UI は作らない）。

### D. PoC 品質デモ（実データ実行・§0.3 の判定は開発者）
- **D-1**: `/tmp` に本体 DB のコピーを作り、**seed 10 キャラ＋開発者の実コンボ・実セットプレイ**から、エンジン入力（キャラの moves・当てたい技候補・A-2 で判明した有利フレーム入力）を SELECT で組み立てる薄いハーネスを `/tmp` に作成し、エンジンを実行。**本体 DB 原本・リポは不変**。
- **D-2**【主判定軸】: **golden-case（有名セットプレイ）の再現**。開発者提供の有名セットプレイ一覧（§開発者への確認事項 Q2）に対し、エンジンが当該レシピを**出せたか（hit/miss）を技名付きで表**にする。**一覧が未提供の段階では、seed/実データから著名例の候補を抽出して開発者確認に回す**（推測で確定しない）。
  - **golden-case の記述フォーマット（開発者提供の様式・PoC ハーネス投入用）**: 1 件を以下の項目で持つ。
    - キャラクター（例: リュウ）
    - 始動コンボ（例: 立ち中パンチ＞しゃがみ中パンチ＞中上段足刀蹴り）
    - そのコンボの有利フレーム `knockdown_advantage`（例: 40）
    - 期待セットプレイのレシピ（例: 立ち弱キック＞鎖骨割り）
    - **当てる active フレーム**（例: 鎖骨割りの持続 4F 目）
    - **想定 meaty 着弾フレーム**＝有利フレーム+1（例: 41F 目。前提事実 8 の +1 を明示的に持たせ、A-3b のオフバイワン検証に使う）
  - hit 判定は「エンジン出力レシピが期待レシピと一致し、かつ着弾フレームが +1 側（41）で成立している」ことを基準にする（40 側でしか出ないなら miss かつオフバイワンの証跡として D-3 に記録）。
- **D-3**: **誤導出**＝フレーム上成立しないレシピ（active 窓が起き上がりに届かない等）を出していないか、サンプル抽出で事実確認（出したなら件数・具体例）。**特にオフバイワン**＝エンジンが着弾を有利フレーム値そのもの（例 40）で解いている場合、実際の起き上がり（41）では 1F 早く「無敵に空振り」する。golden-case（D-2）と誤導出サンプルの双方で、**着弾が 40 側か 41 側か**を実出力から判定し、系統的な 1F ズレがあれば件数と代表例を記録（前提事実 8・A-3b と突合）。
- **D-4**【副次】: **取りこぼし（recall）**＝既存 `combo_setups` の手動紐付けのうち、同一コンボの有利フレームからエンジンが当該セットプレイのレシピを再現できた割合を実数で。**ただし A-2 でエンジン入力が「当てたい技」起点と判明した場合は、combo_setups 由来の当てたい技を与えた条件での再現率**として測る（前提を report に明記）。
- **D-5**: **性能の事実**＝1 コンボあたりの導出時間・キャラ全 moves 走査時間（NFR001＝100ms の参考値。合否判定はしない）。

### E. 母集団実測
- **E-1**: `SELECT` で `knockdown_advantage` 非 NULL のコンボ数・**キャラ別分布**を実数で。
- **E-2**: `combo_setups` 行数・`setups` 件数・`setup_steps` 件数を実数で。
- **E-3**: golden-case 母集団＝有名セットプレイを**エンジン入力として与えられるだけの moves/frame が seed に揃っているか**を確認。薄い箇所（frame 欠損の主要技等）を列挙し、**「薄い場合は開発者へ実データ追加を依頼」する分岐**を report の要決定事項に載せる。
