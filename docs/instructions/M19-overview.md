## 1. 目的・位置づけ

- **目的**: 既存コンボを選択 → その `knockdown_advantage`（KA）から成立セットプレイのレシピを**自動提案** → ユーザーが間合い等を検証 → 繋がるものだけ採択 → 既存 `setups`＋`setup_steps`＋`combo_setups` に保存。**前例なき差別化の目玉**。
- **性格**: 提案精度が生命線のため PoC 先行。**先行実装＝別リポ `autopilot-combomgr/projects/setplay-suggestion` のフレーム導出エンジン**（Go 1.24・stdlib-only）を `internal/service/setplay/` へ移植済み。**FR011（転用ヘルパー・実装済み）とは別機能**。
- **提案の 2 モード（M19-02 で確定）**:
  - **重ねる（meaty）**: 起き上がりに技を重ねる。成立条件 `1 ≤ N ≤ active`。
  - **汚連携（gap）**: 起き上がりまでに技を**完全に空振り**させ、相手の行動を誘発して刈る。`G = N − active`（`G ≥ 1` ⇔ `N > active`）＝**meaty と完全に排他**。
- **破壊的マイグレ**: M19-01/02 は**なし**。**M19-03 以降で発生**（§3）。
- **依存**: M18 とは相互独立。ただし **UI 面（単一コンボ候補面）が M18-03・followup E-1 と交差**＝親チャット経由で調整（§5）。

## 4. 主要設計判断・調査結果の反映

### 4.1 KA の意味論（確定・DES-003 §3.4 に反映済み）
KA ＝ダウン中の無敵時間。起き上がりは **`KA + 1`** フレーム目。`S = Σ(先行ステップの実消費) + target の startup`／**`N = KA + 2 − S`**／着弾 `= KA + 1`。

### 4.2 受理帯方式と 2 モード（確定・M19-02 で一般化）
受理は「`N` が帯 `[NLo, NHi]` に入るか」。**探索構造（subset-sum・反復深化・少手数優先・枝刈り）は不変**で、帯の定数だけを差し替える。

| モード | 帯 | 意味 |
|---|---|---|
| **meaty（重ねる）** | `[max(1, n_min), min(active, n_max)]` | 持続 N フレーム目が起き上がりに重なる |
| **汚連携（gap）** | `[active + Gmin, active + Gmax]`（既定 1〜13） | 最終 active が起き上がりの `G` フレーム**前**＝**完全空振り**。`G = N − active` |

> **【訂正記録】** M19-02 指示書 v1.1.2 以前は gap を「起き上がり**後**に第 1 active（`G = 1 − N`）」と定義していたが**誤り**。開発者確認（2026-07-26 最終）で「当てる意図は meaty で実現済み＝gap は**当てない専用**」と確定し、指示書 v1.2.0 で訂正した。**旧定義は否定形確認（§5.6-5b）の対象**。

### 4.3 `rush_variant` の通し値（確定・followup §H(e) クローズ）
起点は**ニュートラル起点で、ラッシュを最速キャンセルして技を出したときのラッシュ分＋技分**（開発者回答 2026-07-26）。起き攻めの前提と一致するため、**rush を filler から除外しない**。**target の既定 OFF は維持**（候補を絞る目的・開発者判断）。

### 4.4 filler 候補規則（M19-02 で是正・M19-05 で再変更予定）
現行: **`total ≥ 1` かつ `category != target_combo`**。`is_derived` / `rush_variant` / `setup_only` は**除外しない**（`is_derived` を「単独入力不可」と読み替えない）。判別不能な状態前提技は告知で吸収。
**M19-05 で 4 点変更予定**（M19-DESIGN-07 §5）: 実現不能解の排除（チェーン隣接の費用是正）／取りこぼしの回復（チェーン合成単位）／`target_combo` 除外の**解除**（basis 確定分）／**単独入力不可ゲートの追加**（既存の穴の是正）。

> **【★2026-08-02・ボード D-149】現行実装は、確定済みの設計判断を実装していない。**
>
> 現行 filler 規則（`total ≥ 1` かつ `category != target_combo`）は **`is_derived` を見ていない**ため、**空振りでも出るパターン 3 の 4 行**——ザンギエフ `machine_gun_chops` / `machine_gun_chops_2hits` / `power_stomps` / `power_stomps_2hits`——**も一律に除外されている**。2026-07-09 の確定メモは「**パターン 3 は区別が必要**（空振りでも繋がる＝空振りフレームが意味を持つ）」と明記している。

### 4.7 新列 3 本の投入経路（Phase 2 で確定）

**`startup_basis` / `chain_cancel_total` / `fastest_unreachable` は、CSV を経由せず UPDATE マイグレで直接 DB へ投入する。**

| 対象 | 経路 |

| **DB** | **UPDATE マイグレ**（Phase 2 の主作業） |
| **CSV** | **同じ値を保全として書く**（値の正本としての記録。seedgen の挙動は変えない） |

## 9. ★プロジェクト横断の申し送り・既知の限界

### 9.1 FK 強制が接続プール全体に効いていない（プロジェクト横断の申し送り）

**M19-03 で発見された、M19 の範囲を超える構造的事実**（設計伝達レポート §1-2）。

- SQLite の外部キー制約は**接続単位**の設定だが、`internal/infra/db/db.go` は `*sql.DB.Exec` で `PRAGMA foreign_keys = ON` を流しており、**プール中の 1 接続にしか適用されない**。本番コードに `SetMaxOpenConns` が無くプールは無制限に増えるため、**後から張られた接続は OFF のまま**になる。
- **影響は `ON DELETE CASCADE` に依存する既存テーブルすべて**に及ぶ（`combo_punishes`／`combo_punish_curations`／`combo_punish_prunings`／`combo_steps`／`setup_steps` 等。**M18-01 系を含む**）。
- **M19-03 は自表についてのみ FK 非依存にした**（`ON UPDATE CASCADE` ＋ 明示再ポイント／明示削除の**併用**）。根治は未着手。
- **★M19-04 への影響**: `M19-DESIGN-07` の新テーブル **`move_derivations` が CASCADE に依存する設計なら、M19-03 と同じ手当て（明示削除の併用）が要る**。指示書化の際に必ず確認すること。
- **根治は M19 の中で片付けない**。対応候補（DSN へ `_pragma=foreign_keys(1)`／`SetMaxOpenConns(1)`／各 CASCADE 依存箇所を明示削除へ）は**いずれも全テーブルの FK 強制挙動を変える**ため、独立した調査＋全テーブルの回帰ゲートが要る。**独立サブを推奨**（開発者の followup 起票 OK 済み）。

### 9.2 B 型（`fastest_unreachable`）の対象は機械判別できない

**B 型の抽出条件（`is_aerial = 1` かつ `code` が `jumping_` を含まない）は不完全である**（ボード **D-225**）。**空中から出す必殺技が `is_aerial = 0` で入っており、B 型にも C 型にも入らない。** 根本原因は `is_aerial` の意味の多義（D-222）。

**Phase 2 では、開発者が名指しした 13 系統を一次源とする。** **網羅の保証は無い。** 今後の技の追加時に開発者が注意する運用とし、followup **`fastest-unreachable-c-type-naming-gap`** へ送る。

### 9.3 派生元ごとに `active` / `recovery` が変わる技は表現できない

**m_bison `devil_reverse_od` / `head_press_od` は、シャドウライズ（弱/中/強/OD の 4 行）を経由しないと出せず、かつ派生元ごとに最速派生できる高度が変わるため `active` / `recovery` まで変わる**（開発者確認 2026-08-07）。**`moves` 行に `active` / `recovery` は 1 つずつしかないため、現行スキーマでは表現できない。**

**Phase 2 では `startup_basis = 'unknown'` とする**（ボード **D-226**）——「**この行の値は、消費側が安全に使える形になっていない**」という記録である。**近似値は入れない**（未実測値の捏造を避ける＝D-121 と同型）。**現在格納されている値は OD シャドウライズからの通し値であり、弱/中/強からの値は未実測である**旨を記入欄に残す。

**★「単独では出せない」の判定述語を `startup_basis = 'standalone'` から `startup_basis IN ('standalone', 'unknown')` へ広げる**（いずれも `∧ move_derivations に親参照あり`。ボード **D-227**）。**誤爆しない**——親参照は `startup_basis` の人手付与と同一パスで付与されるため、保留の行には付かない。**`DES-003` §3.3 と `M19-DESIGN-07` §5-4 の改訂＝CHANGE 起票を伴う**（**2026-08-07 に CHANGE-093 として起票済み**）。**消費は M19-05。**

**参考**——**派生元が複数ある技は 3 類型に分かれる**。(A) 派生元が 1 つ → `through` で足りる ／ (B) 派生元が複数で **`startup` だけ変わる**（地上技・ken 迅雷脚系） → ゲーム内で別技扱いなら行を分ける、そうでなければ `chain_cancel_total`（D-206） ／ (C) 派生元が複数で **`active` / `recovery` も変わる**（空中技・本件） → **表現できない**。followup `parent-dependent-frame-variance` へ送る。
