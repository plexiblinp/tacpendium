## 0. この指示書の特殊性

### 0.1 位置づけ
M19-RESEARCH-01 の**狭い追試**と、**新設設計チャットへの事実供給**を兼ねる。**RESEARCH-01 のやり直しではない**。RESEARCH-01 の事実調査（A/B/C/E）は精度が高く、再実施は不要。

### 0.2 read-only の範囲（RESEARCH-01 と同一）
**許可**: `view`／`grep`／`git log`／`find`／SQL `SELECT`／エンジンの実行（`go build`/`test`/`run`）／`/tmp` 配下の使い捨て PoC ハーネス／本体 DB の**コピー**を `/tmp` に作って読む。
**禁止**: 本体リポ・別リポの**ソース／マイグレ／seed／テスト／DES/REQ 本体の変更**／本体 DB 原本への書き込み／エンジンの本体への移植・vendor／採番。

### 0.3 判断を含めない（judgement-free）
事実列挙のみ。「こう直すべき」という設計結論は書かない。**例外**として、(1) 想定外の発見、(2) 明らかな矛盾の事実指摘（例: 前提と実データが食い違う）は記録してよい。

### 0.4 検証姿勢（重要）
**R-A / R-B は「M19 指示書担当の机上計算が正しいか」を検証する項目である。結論に迎合せず、独立に実測し、違っていれば違うと報告すること。** 一致した場合も「一致した」という事実として報告する。

## 1. 背景

M19-RESEARCH-01 の PoC は golden-case を strict 0/5 と報告したが、一次受けの再検算で **hit 判定式の取り違え**が判明した。正しい判定は「開発者が指定した**持続 N フレーム目**が起き上がり（KA+1）に載るか」であり、この基準では GC-1／GC-3／GC-4／GC-5 が成立する（机上計算）。本サブはこれを**実測で追試**する。

あわせて、残る 1 件 GC-2 は**派生技のフレーム二重計上**という別種の問題であることが判明した。これは moves マスタ・表記正典にまたがる横断設計課題として専任チャットへ分離されたため、**その設計に必要な事実を本サブが供給する**。

### 1.1 確定している定義（本サブの前提）
- `KA` ＝ `combos.knockdown_advantage`。**ダウン中の無敵時間**を表し、相手の起き上がりは **KA+1 フレーム目**。
- `S` ＝ `Σ(filler.total) + target.startup` ＝ target の**第1 active の絶対フレーム**。
- `N` ＝ `KA + 2 − S` ＝ **起き上がりに重なる持続フレーム番号**。
- 成立条件（窓方式）: `N_min ≤ N ≤ target.active` ⇔ **`KA + 2 − active ≤ S ≤ KA + 2 − N_min`**。
- `N_min` ＝ ユーザー指定の最小持続番号（既定 1）。**絞り込み設定であって正しさの条件ではない**。

## 3. 調査・追試項目

### R-A. golden-case の実フレーム値の再出力（机上計算の土台検証）
- **R-A-1**: 下表の各 golden-case について、seed DB から **filler の `total`／target の `startup`／target の `active`** を SELECT で実値出力する（move の解決に使った `moves.code` も併記）。

| # | キャラ | KA | filler | target | 開発者申告 N |
|---|--------|----|--------|--------|--------------|
| GC-1 | リュウ | 40 | 立ち弱K | 鎖骨割り | 4 |
| GC-2 | ケン | 43 | 奮迅脚 | 紫電カカト落とし | 3 |
| GC-3 | ジュリ | 27 | 立ち中P | 前投げ | **3**（2→3 に訂正済み） |
| GC-4 | テリー | 27 | しゃがみ弱K | 中K（立ち中K） | 3 |
| GC-5 | ガイル | 34 | ニーバズーカ | 立ち中P | 2 |

- **R-A-2**: 各件について `S = Σtotal + startup`、`N = KA+2−S`、着弾 `= S+N−1` を計算し、**着弾が KA+1 と一致するか**、**N が開発者申告と一致するか**を実値の表で報告する。

### R-B. 窓方式の実測追試
- **R-B-1**: `/tmp` のハーネスに**窓条件**を実装する（**別リポのエンジン本体は変更しない**。ハーネス側でエンジンを呼びつつ窓判定を行う、またはエンジンをコピーせず判定ロジックのみ外側に実装する）。`N_min=1` で 5 件を走らせ、**期待レシピが提案に含まれるか（hit/miss）**と、成立時の `N` を報告。
- **R-B-2**: 同じ実行を `N_min=3` でも行い、**除外されるケースを実値で示す**（GC-5 が N=2 のため除外される見込み。これは仕様どおりの挙動であり不具合ではない）。
- **R-B-3**: 窓化による**候補数の増加**を実測（現行 `S==KA` と窓 `N_min=1` で、同一入力に対する提案件数と実行時間を比較）。
- **注意**: 品質評価（再現率）は必ず **`N_min=1`** の結果で報告すること。`N_min` はユーザーの絞り込み設定であり、golden-case の正当性を否定するものではない。

### R-C. 派生技の現況棚卸し（設計チャットへの主要入力）
- **R-C-1**: `is_derived`（マイグレ 000032）の**実 DDL・カラム構成・意味**を実コードで確認。派生技であるフラグのみか、**親技への参照を保持しているか**を明示。
- **R-C-2**: 現行スキーマに**親子関係を保持する仕組みが存在するか**を全数調査（`moves` の列・関連テーブル・`combo_steps`／`setup_steps` の格納形）。存在しなければ「不在」と明記。
- **R-C-3**: seed 内の**派生技の件数・一覧**（キャラ別）。`is_derived=1` 相当の行を実数で。
- **R-C-4**: ケン「紫電カカト落とし」の **`startup` 実値と、その値が単体の公式値か派生時実測値かを判別できる材料**（seed のコメント・関連 move の値・`is_derived` の状態など）を事実として報告。**判別できない場合は「判別不能」と明記**（推測しない）。
- **R-C-5**: **派生元が複数ある技**が seed 内に存在するか（例: ケン迅雷脚系）。存在するならその一覧と、現在どう格納されているか（公式記法のままか）。

### R-D. 「単体発生でない値を格納している技」の棚卸し
- **R-D-1**: 派生技以外に、**`startup` が単体発生でない可能性のある技種別**を洗い出す（空中技・ラッシュ派生・ドライブ系など）。判別材料（列・命名規則・コメント・値の傾向）を事実で示す。
- **R-D-2**: 空中技について、`startup` の**計測基準点**が判別できる材料があるか（ジャンプ入力からか、技入力からか）。判別不能なら明記。

### R-E. 表記・格納の現況
- **R-E-1**: DES-004（表記正典）で**親＞子の派生技をどう表記する規定があるか**を確認。規定の有無を事実で。
- **R-E-2**: phase3-overview §M16 ④'（`target_combo`＝多段特殊技区分の正典化）の**確定内容**を確認し、派生技の扱いについて**既に決まっていること**を列挙する（設計チャットが再発明しないため）。
- **R-E-3**: `combo_steps`／`setup_steps` が、レシピを **1 ステップ 1 move で持つか**、親＞子を 2 行で持てるかを DDL とモデルで確認。

### R-F. `N_min` の機械判定可能性
- **R-F-1**: moves に「**その技のヒット時有利フレーム**」に相当する列が存在するか（`hit_advantage` 等）。存在すれば列名・NULL 状況・seed の充足率を実数で。
- **R-F-2**: 存在する場合、「**持続何フレーム目以降ならコンボになるか**」を機械的に導出できる材料が揃っているか（後続技の発生と比較できるか）を事実で評価。**足りない場合は何が足りないかを列挙**。

## 開発者への確認事項

1. **GC-2 の差し替え要否**: R-C-5 で「紫電カカト落とし」が複数親と判明した場合、GC-2 は開発者判断で**スコープ外カテゴリ**にあたる。**単一親の派生技による golden-case へ差し替え**をご検討いただきたい（暫定案: 差し替え。差し替え先は開発者提供）。
2. **空中技の計測基準点**: R-D-2 が判別不能だった場合、開発者の実測ルール（ジャンプ入力からか、技入力からか）をご教示いただきたい。
3. **実データでの再走**: seed には `combos`／`setups` が 0 件のため、実 recall は依然未測定。窓方式導入後に**開発者ローカル DB で golden-case を再走**できると、実データでの裏取りになる（暫定案: 可能なら実施。不可なら M19-01 の DoD に残す）。
