## 1. 背景と目的

### 1.1 背景

M14-03b（第一波 9 キャラ）・M14-03c（ryu 再 seed）で**配布 seed のインフラは完成**している。残るのは手入力 CSV の完成に応じた**段階投入**（M14-overview §3・§5-4）。本サブはその第二波。

**manon を単独の波として切り出す理由**（M14-overview §5-4）: M14-RESEARCH-02〔T3/F-14〕が **manon はアクセント欠落で 21 行の `move_code` が壊れる**（`À Terre` → `terre` 等）と報告している。これは **combomgr-importer（FR701）側の `assign_codes`（英語名からの決定論採番）**に由来する既知の品質問題である。

**ただし重要な区別**（`M14-RESEARCH-02-findings-analysis.md` §1.3・開発者確認 2026-07-16）:

- **配布 seed の源は手入力 CSV**（moves-input-tool 出力・20 列）であり、**`move_code` は input-tool の自前採番**。**importer CSV の `move_code` を prefill として引き継ぐ経路は存在しない**（importer の code は `reconcile` の突合キーとして使うだけで手入力行へ書き戻さない）。
- したがって **importer の壊れ code がそのまま seed に入るわけではない**。**実際に何が入っているかは manon の手入力 CSV を見るまで分からない**。
- 開発者は**意図的に `move_code` を変える**ことがある（公式表記が分かりにくい／インゲームで確認できない語のとき）＝**不一致は正常に起きる**。そのため **AI 補正の仕組み**（`pre-seed-data-check-prompt`）が用意されている。

**よって本サブの主目的は「manon を入れること」＋「アクセント問題の解を 1 体で確定させること」の 2 つ**である。20 体を入力してから問題が発覚すると全滅するため、**濃い 1 体を先に通す**（重量サブは調査→実装の順が安い）。

### 1.2 目的

- **manon の moves を seed する**（手入力 CSV 由来・M14-03b/03c と同一の変換規則）。
- **アクセント transliteration の実地検証**: manon の手入力 CSV の `move_code` に**アクセント由来の破損・非正準形が実在するか**を実測し、**「AI 補正で埋まっている／input-tool の codegen 修正が要る」のどちらかを判定して報告する**（§4.3）。
- 検証結果を**第三波（M14-03e）以降の前提**として設計担当へ返す。

## 4. 詳細仕様

### 4.1 manon の seed

- **M14-03b の変換インフラ（seedgen）で** `character_data/manon.csv` → seed SQL を生成（**新規実装・コピー実装・手作業生成をしない**＝「二度作らない」）。
- FK 依存順（moves → preset_aliases）。**alias（`official_ja_move`）は対で投入**（無いと生 code フォールバック）。
- **`recovery` は単一整数**・材料が欠ければ `total` は NULL。**`is_derived`・`target_combo` は passthrough**（本体は取込値を信頼＝CHANGE-065 と同型）。
- **移動 9 種は drop**（M14-03b (a) の静的 seed が唯一の投入元）。

### 4.2 `move_code` の扱い（**是正しない・報告する**）

- **`move_code` はツール採番値の正準形検証のみ**（`^[a-z0-9_]+$`・DES-004 §2.1）。**再採番・自動リネーム・自動修正を一切しない**（CSV が正）。
- **正準形に反する code があった場合**: **生成を止めて報告**する（**推測で直さない**）。**是正はデータ側（開発者が CSV を直す or input-tool を直す）で行う**のが本プロジェクトの原則（本体は取込値を信頼）。
- **意味が壊れているが正準形は満たす code**（例: `terre`＝語頭が落ちている）は**機械的には検出できない**。§4.3 の実測表に「**アクセント由来と推定される破損**」として**候補を列挙**し、**判定は開発者に委ねる**（製造は候補提示まで）。

### 4.3 【本サブの核】アクセント transliteration の実地検証と判定

**完了報告に次の 3 点を必ず含める**:

1. **実測表**（§3.3-3 の (a)〜(e)）: 件数＋実例（`move_code` と `name_ja` の対）。
2. **判定**: 次のいずれかを**根拠付きで明示**する。
   - **【解あり】AI 補正で埋まっている** ＝ (a)〜(d) がすべて 0・(b) の候補も開発者判断で問題なし ⇒ **第三波以降は品質問題なしで進められる**。
   - **【要対応】input-tool の codegen 修正が要る** ＝ (a)〜(d) が非ゼロ ⇒ **どの規則が要るか**（例: アクセント文字の transliteration `À`→`a`・`é`→`e`／括弧内の除去）を**具体的に提案**する。**修正自体は本サブのスコープ外**（input-tool は別 go module・`.gitignore` 配下＝本体から import 不可。**開発者が別途対応**）。
3. **第三波（M14-03e＝m_bison/rashid/jamie/luke）への申し送り**: 括弧の過長 code（40〜57 字）・公式英語名の誤り（luke）が**同じ経路で顕在化するか**の見通し。

> **なぜ製造が判定するのか**: この検証は**実データを読まないと分からない**（spec からは演繹できない）。設計担当は spec から「`condition_ja` 非空を落とす」という規則を提案して**実データに否定された**前例がある（2026-07-16・`lily/great_spin` の実測で判明）。**データに効く判断は、実データを見た側が根拠を出す**のが安い。

### 4.5 【M17-02 由来・要是正】`manon.csv` の rush 行の `is_derived`

- **`manon.csv` の rush 15 行が `is_derived=false` のまま**（M17-02 実装メモ §2-5。M17-02 の対象外指示どおりの状態）。
- **`rush_variant` の正は `is_derived=true`**（**ドライブラッシュ状態でのみ出る**＝判定原理「単独でいきなり出せるか？ 出せない → true」。DES-003 §3.3・CHANGE-069）。**false のまま seed すると索引に載り、通常版と `token_key` 衝突する**。
- **是正の方式は 2 択＝Plan Mode で提示する**:
  1. **CSV 側を是正**（`manon.csv` の rush 行を `is_derived=true` へ）＝**データ側で直す＝本プロジェクトの原則**（本体は取込値を信頼）。**開発者の作業**になるため**報告して待つ**。
  2. **seedgen の変換規則に組み込む**（`category=rush_variant` なら `is_derived=1` を INSERT）＝**変換規則の改訂＝golden 更新を伴う**（`000026` の byte-identical が崩れる＝**§2.3 の例外条項＝止めて報告**）。**第二波以降の全キャラに効く**ため、**恒久的にはこちらが安い**可能性がある。
- **〔設計担当の暫定〕(1) を既定**（データ側で直す）。ただし**残り 20 キャラすべてで同じ是正が要るなら (2) が経済的**＝**manon の実測（rush 行が何行あるか・他キャラでも同様か）を添えて報告**し、**設計担当が判断**する（**伝達メモの `original_move_code` 実在検証の追加と同時にやるのが経済的**）。
- **どちらの場合も、本サブで勝手に変換規則を変えない**（§2.3）。

### 4.4 検証

- **dup スキャン**（M14-03b §4.6）を manon 新 moves にも適用。**検出時は生成 fail＋一覧報告**（自動リネーム・自動 skip なし）。
- **clean マイグレ由来 DB から構築**（dev DB 残渣不可）。**dev DB は事前退避**。
- `make e2e`（seed 非依存 self-contained）が新 seed 下で通過（**非回帰**）。
- **他キャラ非波及**（件数で確認）。
