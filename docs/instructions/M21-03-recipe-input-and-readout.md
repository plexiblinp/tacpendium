## 1. 背景と目的

### 1.1 背景

**M21-01 が論理ボタン層を作り、M21-02 が同時押しの判定を確定させた。** **どちらも画面には最小の可視化しか持っておらず、レシピには 1 ステップも入っていない。** **本サブが両者をレシピ入力へ接続する。**

**★実機で 1 つ、新しい事実が出た**（開発者・2026-08-13）——**素早く入力すると、別々に入れたつもりの 2 入力が 1 ステップにまとまる。** **判定窓を 90 ms と広く取ったことの副作用であり、設計どおりで silent ではない**（画面に出る）。**しかし「出ている」ことと「利用者がそれを予期している」ことは別である**（**D-347**）。

**⇒ 本サブは、動く導線を作ると同時に、利用者へそれを伝える場所を作る。** **告知が落ちると、利用者は「壊れている」と判断する。**

### 1.2 目的

1. **物理コントローラの入力からレシピのステップを作る**（`FR105`）。
2. **入力を読み取って画面に出す**（`FR106`）——**押されたボタンと確定したステップの両方。**
3. **`DES-005` §6.6 の実装フェーズ決定事項から 2 件を回収する**（**2. TC のような 2 つ以上の通常技ボタンを連続入力する際の UI 挙動** ／ **5. 物理コントローラ接続時の入力検出と画面上ボタン点灯の連動**）。
4. **まとまりうることを利用者へ伝える**（**D-347**）。
5. **★コンボのレシピ入力面とセットプレイの入力面の両方で使えるようにする**（**D-350**）。**接続層を 1 つの部品にして 2 面が共有する。**

## 4. 詳細仕様

### 4.1 ★出口は必ず `move_code` である（契約 F-3 の死守契約）

**物理コントローラの入力は、「どのボタンが押されたか」を決めるところまでが本サブの守備範囲である。** **そこから先——どの技を指したか——は、既存の仮想コントローラと同じ決定論ルックアップへ合流させる。**

| # | 規約 |
|---|------|
| 1 | **★モーション解析をしない。** `236P` のような方向の連続入力を技へ解決してはならない（**M21-06**）。**本サブでは、方向は「その時点の 1 つの状態」のままである** |
| 2 | **★解決規則を新設しない。** 段階1 の構造引き（`standing_` / `crouching_` / `jumping_`）も、段階2 の解決表も、ラッシュ版の `rush_<code>` も、**既存の実装を呼ぶ**（§3.3-2） |
| 3 | **★9 方向 → 3 ゾーンの縮約も既存に従う**（`DES-005` §6.4）。**上系 `7`/`8`/`9` → `jumping_` ／ 下系 `1`/`2`/`3` → `crouching_` ／ 中段 `4`/`5`/`6` → `standing_`** |
| 4 | **★解決できない入力は、ステップにしないで読取表示に出す**（§4.3）。**推測で近い技を選ばない** |
| **★5** | **【v1.2.0 で明記＝D-352】物理入力が決めるのは「仮想 UI のどの操作に当たるか」までである。** **操作 → `move_code` は既存の実装が持つ。** **⇒ 「弱P」を押した ／ 「ドライブインパクト」を押した、まで決めたら、そこから先は渡す。** **★この線を越える写像**（**入力から技のファミリーを選ぶ等**）**は本サブでは書かない** |

> **★なぜここまで書くか**——**「物理コントローラで入力できる」は、実装者から見ると「入力から技を決める」に見える。** **しかし本アプリの死守契約は「モーション解析はしない・決定論ルックアップに徹する・出口は必ずキャラ別 `move_code`」である**（`phase3-overview` §2.3 ／ 契約 F-3）。**物理入力は「利用者の実入力 → どのボタンか」の問いであり、「どの技か」は既存の索引引きが答える。** **2 つを 1 つの関数に混ぜると、契約が壊れたことに誰も気づけない。**

| **★2′** | **【v1.2.0 で差し替え＝D-352】同じ強度の P＋K は、既存のシステム技へ写す**——**強P＋強K → `drive_impact` ／ 中P＋中K → `drive_parry` ／ 弱P＋弱K → 投げ。** **★これは新しい解決規則ではない**——**仮想 UI の共通技エリア**（`DES-005` §6.4 の SystemRow）**に同じ操作のボタンが実在し、そこから `move_code` への写像は既存である。** **物理入力は「その操作を押した」ことを決めるだけである**（§4.1-5）。**実機のボタン割当と同じ形でもある** |

### 4.4 画面上ボタンの点灯連動（`DES-005` §6.6-5 の回収）

**物理コントローラで押したボタンが、画面上の仮想コントローラのボタンに点灯として現れること。**

- **点灯は表示だけの効果であり、解決には関与しない**（§4.1-2）。
- **★点灯の状態源は論理ボタン層であって、確定したステップではない。** 押している間ずっと光り、離すと消える。
- **test-id は `recipe-<領域>-<識別子>` に従う**（`DES-005` §6.8）。**新しい流儀を持ち込まない。**

### 4.5 TC の連続入力（`DES-005` §6.6-2 の回収）

**ターゲットコンボのように通常技ボタンを 2 つ以上続けて入力したとき、UI がどう振る舞うかを決める。**

| # | 仕様 |
|---|------|
| 1 | **★判定窓の外に出た入力は別ステップである。** これは M21-02 の as-built がすでに決めている。**本サブで判定を足さない** |
| 2 | **⇒ 本節で決めるのは「連続して入ったステップを、画面上でどう見せるか」だけである**（例＝直近に確定したステップを強調する・連続入力中であることが分かる） |
| 3 | **★TC としてまとめるデータ構造を作らない。** レシピは 1 ステップ 1 行であり、TC も通常技の連続として表現される（`DES-004` §2.1） |

### 4.6 ★まとまりうることの告知（**D-347** の帰結・必須）

**`DES-005` §6.4.2 が「入力面に置く」と定めている。本サブが実装する。**

| # | 伝える内容 |
|---|------|
| 1 | **素早く入力すると、別々のつもりの入力が 1 ステップにまとまることがある** |
| 2 | **ゆっくり正確に入力する** |
| 3 | **★不具合ではなく、入力を取りこぼさないための意図的な設定である** |

- **置き場は物理入力を使う面**（常設の注記でも、初回の説明でも、info-mark の Popover でもよい。**形は問わない**）。
- **★3 点目を落とさないこと。** **1・2 だけだと「使いにくいツール」に読める。** **窓を広く取ったのは、狭いほうが silent に入力を落とすからである**（`DES-005` §6.4.2 の「誤りの非対称性」）。
- **★「窓は 90 ms」のような実装値を利用者向け文言へ書かない**（値は実装の 1 か所が正であり、UI へ写すとドリフトする＝`E-76`）。

### 4.7 M21-02 の最小可視化の撤去

**M21-02 の可視化は「DoD を机上にしないための足場」であり、撤去前提で作られている**（同指示書 §4.6-3）。**本サブの読取表示が本番 UI である。**

- **撤去したことを完了報告に書く。** **★残したなら、残した理由を書く**（開発用として残す判断はありうるが、**本番画面に 2 つ出ているのは事故である**）。

### 4.9 ★2 面で使うための部品化（**D-350**）

**開発者判断により、セットプレイの入力面も対象である。** **★ただし「2 面ぶんの接続を別々に書く」ことは認めない。**

| # | 仕様 |
|---|------|
| 1 | **接続層を headless な部品として作る**——**描画を持たず、「入力 → 確定したステップ候補」だけを供給する形にする。** **フックでもコンテキストでも形は問わない**（§9.2） |
| 2 | **★部品の出口は、面に依存しない中立な形にする**——**`move_code` ＋ 方向 ＋ 修飾**。**面ごとのステップ型への写し替えは、呼び出し元の面が行う** |
| 3 | **★`move_code` の解決は部品の中で 1 回だけ行う**（§4.1 の合流点）。**面ごとに解決を書かない** |
| 4 | **点灯の状態も同じ部品から供給する**（§4.4）。**面ごとに論理ボタン層を購読しない** |
| 5 | **告知**（§4.6）**は、両方の面から見える形にする。** **★同じ文言を 2 か所へ書き写さない**（`E-76`＝**同じ情報を 2 か所に持つと必ずドリフトする**）。**共通コンポーネント化するか、1 か所へ置いて両面から参照する** |
| 6 | **★2 面のどちらでも、同じ入力が同じ `move_code` になること**（§5 (h) で固定する） |

> **★なぜ部品化を条件にするか**——**面ごとに接続を書くと、`move_code` を決める箇所が 2 つになる。** **そのときは動く。** **壊れるのは、段階2 の解決表やラッシュ版の規則が更新されたときであり、片方だけ追随して他方が取り残される。** **そして取り残されたほうは「動いているが古い規則で解決している」状態になり、エラーにならない。** **§4.1 の死守契約が守られているかどうかを、以後だれも 1 か所では確認できなくなる。**

> **★セットプレイ側で差が出ても、それは部品の問題ではなく面の問題である。** 例——**セットプレイのステップが `modifiers` を持たない ／ 選べる技に制限がある。** **その場合は、部品の出口はそのままにして、面の側で受け取れないものを落とす**（**落としたことを読取表示に出す**＝§4.3-3）。

### 4.10 否定形確認（撤回した仕様の残骸の全文走査）

**最終コード状態で走査し、件数と「検査した範囲」の両方を報告する**（`E-84`）。

| 走査キーワード | 何が残っていたら残骸か |
|---|---|
| `236` / `モーション` / `motion` | **入力列からコマンドを解決しようとしている箇所。** **★`move_code` や既存の解決表の中に数字表記が現れるのは正常である**——**残骸は「本サブが新しく書いた解決規則」だけである** |
| M21-02 の最小可視化のコンポーネント名（§3.3-6 で確定） | **撤去し損ねた本番描画。** **開発用に意図的に残したものは残骸ではない**（理由が完了報告にあること） |
| 判定窓の実値（`90` 等） | **本サブが値を写していないこと。** **★M21-02 の定数定義 1 か所だけが正である** |

> **★走査キーワードは「撤回した仕様の残骸を探す網」であって、その文字列の全面禁止ではない**（テンプレート §4.5 の記入指針）。**否定形確認は、サブの完了時点ではなく最後にコードを触った時点で回すこと。**

## 5. テスト要件

**判定は M21-02 が持つ。本サブのテストは「接続」を固定する。**

| 区分 | 固定する内容 |
|---|---|
| **(a) 出口** | **確定したステップの `move_code` が、同じ入力を仮想 UI で行った場合と一致する**（**§4.1 の合流が効いていることの主張**） |
| **(b) 解決不能** | **解決できない入力がステップにならず、読取表示に出る**（**黙って消えない**） |
| **(c) 混在** | **物理と仮想の入力が交互に来ても、ステップの順序が入力順どおりになる** |
| **(d) 点灯** | **押している間だけ点灯し、離すと消える**（**確定したステップではなく論理ボタン層が状態源であることの主張**） |
| **(e) 削除** | **直前のステップを削除しても、点灯状態と判定窓の状態が壊れない** |
| **(f) 告知** | **告知の 3 点が画面に存在する**（**★文言の完全一致ではなく、存在をテストする**。i18n で変わりうるため） |
| **★(h) 2 面の一致** | **レシピ入力面とセットプレイ入力面で、同じ入力が同じ `move_code` になる**（§4.9-6。**解決が 1 か所であることの主張**） |
| **(g) 非回帰** | **M21-01・M21-02 の既存スイートが全緑。** **仮想コントローラの既存テストも全緑** |

**E2E**——**実機コントローラと user gesture を要するため Playwright から模擬できない**（M21-02 で確認済み）。**書けないことを完了報告に明記する**（`E-84`＝**「書かなかった」と「書けなかった」を同じ顔で出さない**）。**★ただし告知の存在**（f）**はコンポーネントテストで固定できる。**
