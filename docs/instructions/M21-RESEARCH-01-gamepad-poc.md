## 0. この指示書の特殊性

### 0.1 本 PoC が答える問いと、答えない問い

| 答える | 答えない |
|---|---|
| **何を測ればよいかが決まるか** | **実装できるか** |
| 同時押しのズレ幅・チャタリングが**どういう分布か** | **判定の閾値をいくつにするか** |
| 経路ごとに Gamepad API が**取れるか** | **入力 UI をどう作るか** |

> **★閾値を決めない。分布を出す。**
> **測る前に判定法を決めてはならない**（ボード **D-267** ／ 教訓 `E-123`）。**M19 では見込み値が繰り返し失効した**（除外は 3 行の見込みに対し実測は桁違い ／ ある案は見積りの 2.7 倍）。
> **同時押し判定とチャタリング対策は、机上で選んだ閾値が「動いているように見えて一部の入力を落とす」型であり、失敗が silent である。**

### 0.2 3 段構成（★製造だけでは完結しない）

**Gamepad API は実機のコントローラと実ブラウザが要る。** **製造担当はターミナル環境であり、ブラウザ実機確認・スクリーンショット取得を要求してはならない**（playbook §1.3）。**devContainer では実機・実ブラウザ確認ができないことは followup §G-2 (c) に記録がある。**

| 段 | 担当 | やること |
|---|---|---|
| **段 1** | **製造** | **計測ハーネス（静的ページ 1 枚）と解析スクリプトを作る。** 生ログを JSON で吐かせる |
| **段 2** | **開発者** | **実機で開き、§4 の操作手順どおりに入力して生ログを保存する** |
| **段 3** | **製造** | **生ログを解析スクリプトに通し、§5 の様式で分布を報告する** |

> **★段 2 を製造に要求しない。** 段 1 の成果物には、**開発者が読んで実行できる手順**（何を開き・何を押し・何回・どう保存するか）を同梱すること。
> **★段 2 が実行できないと分かった時点で、段 3 へ進まず報告して止まる**（教訓 `E-77`＝**指示を実行できても目的を達成できないなら、実行せずに報告する**）。

### 0.2' read-only の範囲（探索モード。PoC 実行を含む）

| 許可 | 禁止 |
|---|---|
| **使い捨ての計測ハーネスを、リポジトリ外の使い捨て領域に作る**（`/tmp` 配下等） | **本体リポのソース／マイグレ／seed／テスト／`DES`・`REQ` 本体を 1 バイトも変更する** |
| **ハーネスをローカルの静的サーバで配信する**（`python3 -m http.server` 等） | **`web/` 配下・`internal/` 配下へファイルを追加する** |
| **本体アプリを起動して経路 (b)(c) を確認する**（§4-A） | **本体アプリの設定・DB を変更する。DB を開いたまま書き込む** |
| **`docs/progress/` へ §2.1 のレポートを作る** | **`docs/` 配下の他ファイルを変更する** |

**★ハーネスは「入力を渡し、出力を集めるだけの薄いドライバ」に留める。** 判定ロジック・フィルタ・閾値をハーネスへ入れない——**入れると、測った分布ではなく「ハーネスが通した分布」を測ることになる。**

### 0.3 判断・提案を含めない（judgement-free）

**事実列挙のみを行う。** 「この閾値がよい」「この方式を採るべき」は書かない。**ただし (1) 想定外の発見 ／ (2) 明らかな矛盾の事実指摘 は判断ではないため記録する。**

**★数字には「何を・どの単位で・どの基準時点で数えたか」を必ず併記する**（`E-16` / `E-93`）。**★「0 件」には「検査した件数」を併記する**（`E-84`）。

## 1. 背景と目的

### 1.1 背景

M21 は物理コントローラ入力（**FR105〜FR108**）とコマンド実モーション入力（物理限定）を扱う。**Gamepad の検証が重いため PoC を先行させる**（`parallel-ops` §12 のレーン割り条件 (b) ／ ボード **D-294**）。

**★前提が 2026-08-12 に是正されている**（board **M-37**）。**採用案は `DES-001` §2.3 の案C（Go + React）であり、フロントは Go サーバが配信して起動時にブラウザを自動で開く**（同 §6）。**WebView ではない。** **旧記述「Gamepad API（WebView 内・DES-001 §2.1 案C）」は、§2.1 の案A〔Tauri・不採用〕のメリット欄を孫引きしたものだった。**

**⇒ 取得可否は「WebView か」では決まらない。経路ごとに違いうる。**

### 1.2 目的

**§4 の 4 軸について、実測値と分布を出す。** **M21 本実装の指示書は、本 PoC の結果が出てから書く。**

### 1.3 この PoC でやらないこと

- **判定閾値の決定**（§0.1）。
- **入力 UI の設計・実装。**
- **`move_code` への解決ロジックの実装**（コマンド入力解決の死守契約 3 点は契約 F-3 の凍結対象）。
- **本体アプリへのコード追加。**

## 4. 調査項目

### A. 経路ごとの取得可否（★最重要。ここで M21 の進め方が決まる）

**次の 3 経路それぞれで、`navigator.getGamepads()` がコントローラを返すかを確認する。**

| 経路 | URL の形 | 備考 |
|---|---|---|
| **(a)** | **使い捨てハーネスを `http://localhost:<port>` で配信** | 段 1 の最小確認 |
| **(b)** | **本体アプリを起動し、自動で開いたブラウザ**（`http://localhost:<port>`） | **実運用の主経路** |
| **(c)** | **LAN 内の別端末から `http://<LAN IP>:<port>`** | **secure context ではない。ここが (a)(b) と違いうる**。**★2026-08-12 縮小（D-309）**——**スマホへのコントローラ接続は M21 対象外になったため、これは「非 localhost で取れるか」の確認であってブロッカーではない。機材が無ければ「未測定」でよい** |

- **A-1**: 経路 (a)(b)(c) それぞれで、**コントローラが列挙されるか**を出す。**ブラウザ名とバージョン、OS、コントローラの製品名を実値で併記する。**
- **A-2**: **列挙に user gesture（ボタンを 1 回押す等）が要るか**を、経路ごとに出す。**要る場合、何をしたら列挙されたかを手順の形で書く。**
- **A-3**: **`gamepadconnected` / `gamepaddisconnected` イベントが発火するか**を経路ごとに出す。
- **A-4**: **経路 (c) で取得できなかった場合**、**ブラウザのコンソールに出たメッセージを逐語で記録する**（secure context 由来か、別の原因かを後で判別するため）。**「取れなかった」だけでは原因が判別できない。**
- ~~**A-5**~~: **【2026-08-12 削除・D-309】スマホへのコントローラ接続は M21 では対応しないと決まったため、本項は測らない**（**対応しないと決めたものを測らせない**＝開発者の手番を減らす）。

### B. ポーリング周期と入力遅延

- **B-1**: `requestAnimationFrame` によるポーリングで、**1 フレームあたりの実測間隔の分布**を出す（**中央値・最小・最大・標本数**）。**ブラウザのリフレッシュレートを併記する。**
- **B-2**: **ボタンを押してから `getGamepads()` の `buttons[i].pressed` が `true` になるまでの遅延**を、**取得可能な範囲で**測る。**測れない場合は「測れない」と、その理由を書く**（比較の基準となる外部時刻が無い等）。
- **B-3**: **`Gamepad.timestamp` が更新されるか**を確認し、**更新される場合は `timestamp` 差分の分布**を出す（B-1 の rAF 間隔と一致するか）。

### C. 同時押しのズレ幅（FR107）

**`REQ-001` §3.1 の FR107 は「OD技等の同時押し入力は、ズレて入力される場合を考慮して適切に読み取る」と定める**（逐語引用。**本指示書が「適切に」と指示しているのではない**）。**その「適切に」を決めるための分布を取る**——**FR の文言が抽象的であることが、本 PoC が要る理由そのものである。**

- **C-1**: **開発者に「2 ボタン同時押し」を 1 セット 30 回、3 セット行ってもらう**（合計 90 回）。**各回について、先に `pressed` になったボタンと、もう一方が `pressed` になるまでのフレーム数・ミリ秒を記録する。**
- **C-2**: C-1 の**ズレ幅の分布**を出す（**中央値・パーセンタイル 50/90/95/99・最大・標本数**）。**セット間で分布が動くかも見る**（慣れの影響）。
- **C-3**: **3 ボタン同時押し**（該当する操作がある場合）についても同じ形で取る。**該当が無ければ「該当なし」と、そう判断した根拠を書く。**
- **C-4**: **押し始めのズレ**と**離し始めのズレ**を分けて出す。**どちらを判定に使うかは本 PoC では決めない。**

### D. チャタリングの実波形（FR108）

- **D-1**: **開発者に「1 ボタンを 1 回だけ押す」を 50 回行ってもらう**（**2026-08-12 是正＝旧記載「100 回」。§4.5.2 (2) と §4.5.4 の削減案表はどちらも 50 回を基準に書かれており、本項だけが取り残されていた**）。**各回について `pressed` の立ち上がり・立ち下がりの回数**を記録する。**1 回の押下で 2 回以上の立ち上がりが観測された回数**を出す。
- **D-2**: D-1 で多重の立ち上がりが観測された場合、**その間隔の分布**を出す（**中央値・最小・最大・標本数**）。
- **D-3**: **`buttons[i].value`（アナログ値）が取得できるか**を確認し、取得できる場合は**押下 1 回あたりの値の推移**を記録する（デジタル `pressed` だけでは見えない揺れが出る場合がある）。
- **D-4**: **★機種は 2 種で確定している**（**D-309**＝**レバーレスコントローラとパッド**）。**両方で測り、機種ごとに分けて報告する。** **★2 機種は入力機構が根本的に違うため、チャタリングの実波形が機種で分かれる蓋然性が高い**——**合算した分布を出さない。分けて出す。** **片方が測れなかった場合は、その旨と理由を書く。**

## 4.5 ★段 2（開発者の実機計測）で実際に行う作業

**本節は開発者が読んで、そのまま実行できる粒度で書く。** 段 1 の成果物（ハーネス）には、**本節と同じ内容を画面上の手順として同梱すること。**

> **★記録は機械が取る。開発者は数えないし、申告しない。**（2026-08-12 追記）
>
> **ハーネスは `requestAnimationFrame` のポーリングでボタンの状態遷移を時刻付きで記録する**（§4 の B-1・C-1・D-1 が求めている値は、いずれもこのログから解析で出す）。**開発者が「30 回押した」「ズレは体感で 2 フレームくらい」と申告する場面は無い。**
>
> **したがってハーネスの必須要件が 2 つある。**
>
> - **(1) 回数カウンタを画面に出す**——**セットごとの現在回数と目標回数を表示し、目標に達したら明示する**（例「同時押し 30 / 30 — 完了」）。**開発者に数を数えさせないため**。数えさせると、数える動作そのものが入力の速さを変える。
> - **(2) 自己申告の入力欄を作らない**——**機種名と接続方式（USB / Bluetooth）だけは開発者が入力する**（機械では取れないため。`Gamepad.id` は取れるが人が読む名前と一致しない）。**それ以外を人に書かせない。**
>
> **★段 3（製造の解析）が読むのは JSON だけである。** **開発者の所感は §5 の報告に「気づいたこと」として書いてよいが、統計値の出所にはしない。**

### 4.5.1 準備（1 回だけ・約 3 分）

1. **製造が渡すハーネス（HTML 1 枚）をブラウザで開く。**
2. **コントローラを接続し、いずれかのボタンを 1 回押す**（多くのブラウザは user gesture が無いとコントローラを列挙しない＝A-2）。
3. **画面上部に接続されたコントローラ名が出ることを確認する。** 出なければ、**そこで止めて報告する**（A-1 が「取れない」で確定する。以降の計測は成立しない）。

### 4.5.2 計測（★機種ごとに繰り返す。機種は 2 種＝レバーレスとパッド）

| # | 何を | 回数 | 目安時間 | 何のため |
|---|---|---:|---:|---|
| **(1)** | **2 ボタン同時押し**（OD 技を出すときの押し方。**普段どおりの速さで**） | **30 回 × 3 セット＝90 回** | **約 4 分** | **C-1／C-2＝ズレ幅の分布**。**セットを分けるのは、慣れで分布が動くかを見るため**（セット間の休憩は任意） |
| **(2)** | **1 ボタンを 1 回だけ押す**（**素早く 1 回。連打しない**） | **50 回** | **約 2 分** | **D-1／D-2＝チャタリングの有無と間隔** |
| **(3)** | **ボタンを押しっぱなしにして 3 秒待つ** | **3 回** | **約 1 分** | **D-3＝アナログ値の推移**（押している間の揺れ） |

**1 機種あたり約 7 分 / 合計 143 回。2 機種で約 15 分・286 回。**

### 4.5.3 保存

- **画面の「ログを保存」ボタンを押し、JSON ファイルをダウンロードする。**
- **機種ごとにファイルを分ける。** ファイル名に機種名を入れる（例 `poc-leverless.json` / `poc-pad.json`）。
- **保存したファイルを製造へ渡す**（段 3 の入力になる）。

### 4.5.4 ★回数を減らしてよい条件と、そのときの制約

**負担が大きい場合は次まで減らしてよい。** ただし**減らした分だけ出せる統計値が減る**ため、**レポートに標本数を明記し、出せない値を出さない**こと（教訓 `E-93`＝**標本が足りない分布から出した値を、出せる値と同じ顔で載せない**）。

| 削減案 | 回数 | 出せる統計値 | 出せなくなる値 |
|---|---:|---|---|
| **提示どおり** | (1) 90 / (2) 50 | **中央値・パーセンタイル 50/90/95・最大** | パーセンタイル 99（標本 90 では境界的） |
| **半減** | (1) 30 × 1 セット / (2) 25 | **中央値・パーセンタイル 50/90・最大** | **パーセンタイル 95 以上。セット間の比較も不可** |
| **最小** | (1) 20 / (2) 20 | **中央値・最大・「起きたか起きないか」** | **分布としては使えない。判定窓の根拠にならない** |

**★(2) チャタリングは「分布」より先に「起きるか」が主眼である。** **50 回で 1 度も多重の立ち上がりが観測されなければ、それは「現行 2 機種では発生しない」という結論になる**（**E-41** の型＝**「決める必要がない」という第三の結論**）。**その場合 FR108 の対策は不要という判断材料になり、回数を増やす価値は低い。**

**★(1) 同時押しは減らさないことを推奨する。** **判定窓を何フレームに置くかの根拠がここにしか無く、パーセンタイル 95 が取れないと「どこまで許容するか」を決められない。**

## 開発者への確認事項

1. **段 2（実機計測）をどの機材で行うか**
   何を: **試せるコントローラの機種数**と、**スマホでコントローラを接続できるか**（経路 (c) の A-5）。
   なぜ: **D-4 のとおり、分布の一般性は機種数で決まる。** また **経路 (c) が成立しないと分かった時点で、M21 の入力 UI の前提（対応する端末）が変わる。**
   暫定案: **手元にある機種すべてで測る。** **1 機種しか無ければ 1 機種で進め、レポートに「1 機種のみ」と明記する**（**一般化しないことを記録に残せば、後から機種を足せる**）。

2. **C-1 / D-1 の試行回数（90 回 / 100 回）は妥当か**
   何を: **開発者の手番の量**として許容できるか。
   なぜ: **パーセンタイル 95 / 99 を出すには標本数が要る**が、**手入力の実測は開発者の時間を直接使う。**
   暫定案: **提示の回数で始め、負担が大きければ C-1 を 30 回 × 1 セット・D-1 を 50 回へ落とす。** **★その場合はレポートに標本数を明記し、パーセンタイル 99 を出さない**（**標本が足りない分布から出した値を、出せる値と同じ顔で載せない**＝`E-93`）。
