## 1. 目的・位置づけ

**M23 は「消したものを、消した覚えのないものと区別して、安全に戻せる」ことを作るマイルストーンである。**

### 1.1 性格

- **★「作る」より「揃える・見せる・守る」である。** **ゴミ箱と復元の骨格は既に存在する**——`code-facts.md`（2026-08-19 生成）の範囲で、**`/trash` → `TrashPage`（§3 ルート）／ `DELETE /api/combos/:id`（論理削除）／ `POST /api/combos/:id/restore`（復元）／ `DELETE /api/combos/:id/permanent`（完全削除）（§4）／ `combos.deleted_at` と `setups.deleted_at`（§10）** がいずれも実在する。**⇒ M23 の仕事は「機能を作る」ではなく「効いているかを確かめ、欠けている側を揃え、利用者に説明できる形にする」である。**
- **★★`M23-RESEARCH-01` の実測（2026-08-20）で、この見立ては裏付けられた**——**ゴミ箱画面は 5 ファイル・8 列・24 テストで既に動いており、復元も完全削除も実装されている。** **★ただし「作らなくてよい」ではない**——**実測は「揃っていない側」を 4 つ確定させた**〔**(1) セットプレイの復元・完全削除が 4 層すべてに無い** ／ **(2) `PUT` が積む旧行を判別する情報が 1 つも無い** ／ **(3) 参照側の `deleted_at` 除外に穴が 6 か所** ／ **(4) 「自動完全削除までの残日数」は表示だけが在り機構が無い**〕。 **★これは `M22-06`（QR）と同じ性格であり、同じ失敗の型を持つ**——**`M22-06` の初版指示書は「実装する」前提で書かれ、実際には本番コードの差分が 0 バイトで完了した**（`E-117` の型・M22 レーンで 3 件目）。**⇒ 本 MS では `M23-RESEARCH-01` を先頭に固定し、実装サブの指示書を RESEARCH の前に書かない。**
- **★横断関心事ではない。** M22（協調基盤）が全 API に薄く触ったのに対し、**M23 が触るのはコンボ・セットプレイの削除／復元経路と、ゴミ箱画面に閉じる。** **⇒ M24 との並列可否を検討する余地がある**（§5.3。**判定は `D-461` により `M24-RESEARCH-01` の ledger を得てから**）。
- **★★スキーマ変更が要る側に倒れた**（2026-08-20・`M23-RESEARCH-01` 軸 G）。**保持を無期限で確定させたこと**（**D-458**）**により期限・件数上限のための列は要らないが、「`PUT` が積む旧行を判別する印」は既存の情報では作れないことが実測で確定した**——**(a) `materialized_from_combo_id` は `PUT` の経路で書かれない**〔`buildComboFromInput` の struct literal に同フィールドが無い。書き込みは `Materialize` の 1 か所のみ〕**／(b) 時刻の近接は推定の材料にしかならない**〔`datetime('now')` の精度は秒〕**／(c) `recipe_cache` は `PUT` が旧行の分を削除している**〔しかも `PUT` は「キー変更」の操作であり一致を前提にできない〕**／(d) それ以外の列も無い**〔`version` は新行が `1` で採番し直され、`updated_at` は手動削除と区別しない〕。 **⇒ `D-460`〔旧行を既定で隠す〕を実装するには、印を作ることが先である。** **★これは開発者の個別承認事項である**（`CLAUDE.md` §10。確認事項 3）。**M22 は全 9 サブでマイグレ消費 0 で終わったため、M23 が `000078` の最初の消費者になりうる。**

### 1.2 達成目標

1. **消したものを戻せる。戻したものが壊れていない**（`FR601`）。
2. **消した覚えのないものがゴミ箱に並ばない**（`PUT` が積む旧行を既定で隠す＝**D-460**）。
3. **戻す単位が、競合を検出する単位と揃っている**（**D-459**。`M22-overview` §4.2.2 の線引きを踏襲）。
4. **戻した結果が不正なデータにならない、またはそのことが利用者に伝わる**（**D-463**）。
5. **無期限に溜まっても、利用者がゴミ箱を扱える**（**D-458**）。

## 4. 主要設計判断・調査結果の反映

### 4.1 ★`FR013` と `FR601` の関係——**これは制約ではなく前提である**

**`REQ-001` `FR013` の本文が `FR601` を名指ししている**（逐語）——「**誤った訂正等はゴミ箱からの復元（FR601）で対応し**、運用上の誤解はアプリ外でのコミュニケーションで解決する」。

- **⇒ `FR601` は「所有者を持たない」というコンセプトを成立させている当の機構である。** **★「誰でも消せるが、誰でも戻せる」という対称性が、所有者を持たないことの安全網になっている。**
- **⇒ ここを緩めると `FR013` の設計全体が崩れる。** **★とくに「復元は削除した本人だけができる」という形にしてはならない**——**それは所有者の概念を裏口から導入することであり、`FR013` の必須要件に反する。**
- **★監査ログも実装しない**（`FR013` 後半）。**⇒ ゴミ箱に「誰が消したか」を出さない。** **出すには `REQ-001` の改訂が先である**（`M22` 契約 F-1 と同じ扱い）。

> **★M22 の契約 F-1 をそのまま引き継ぐ。** **凍結の範囲は「条項番号 ＋ 対象」で書く**（`D-379` ／ `M-65`。**包括表現を使わない**）。

### 4.2 ★論理削除・復元は `version` を据え置く——**復元が楽観排他をすり抜けないか**

> **★★2026-08-20 に決着した**（`M23-RESEARCH-01` 軸 D）。**答えは「すり抜ける経路は無い」である。** **⇒ 本節が想定していた危険は、実装上は既に塞がれていた。**
>
> **★根拠は 3 経路の `WHERE` 句の逐語である**——**`PATCH /api/combos/:id`（`UpdateMetadata`）／ `PUT /api/combos/:id`（旧行の論理削除）／ `PATCH /api/setups/:id` の 3 つとも `AND deleted_at IS NULL` を持つ。** **⇒ 削除済みの行は編集経路から締め出されており、「削除 → 他人が編集 → 復元が古い内容で上書き」という並びは成立しない。**
>
> **★★`version` が据え置かれること自体が問題にならない理由もここにある**——**削除済みの間は `version` が動く経路そのものが無い。**
>
> **★あわせて 3 つの実測が出た。いずれも本節の想定外である。**
>
> 1. **復元は `deleted_at = NULL, updated_at = datetime('now')` の 2 列だけを更新し、`version` に触れない**（前提どおり）。**ただし `WHERE id = ? AND deleted_at IS NOT NULL` を持つため、削除済みでない行への復元は 404 になる。**
> 2. **★論理削除の側は `WHERE` に `deleted_at IS NULL` も `version = ?` も持たない**——**`DELETE /api/combos/:id` は楽観排他を行わず、既に削除済みでも冪等に成功して `deleted_at` を上書きする。** **⇒ 残日数の計算の基点も動く**（§4.5）。
> 3. **★`PermanentDelete` の前チェック（`FindByIDAllowDeleted` と `DeletedAt == nil` の判定）はトランザクションの外にある。** **⇒ 判定してから `BeginTx` するまでの間に他の利用者が復元しうる。** **在否の記述にとどめ、対処は `M23-03` の判断とする。**
>
> **⇒ 本節の以下の記述は「決着前の問い」として残す**（`E-111` の分類 2＝当時どう判断したかの記録）。


**`M22-overview` §4.2.1 の実測**（`M22-RESEARCH-01` 軸 A / B ＋ `D-413` の是正）——**`version` の増え方は 3 通りある。**

| 増え方 | 経路 |
|---|---|
| **(i) `+1`** | `PATCH /api/combos/:id` ／ `PATCH /api/setups/:id` の 2 本のみ |
| **(ii) `1` で採番し直す** | `PUT /api/combos/:id`（旧行を論理削除して新行を作るため `+1` の SQL を持たない） |
| **(iii) 据え置き** | **論理削除・復元**・`recipe_cache` |

**⇒ 論理削除と復元は (iii) に属する。** **★これは「壊れている」という意味ではない**——**削除・復元はコンボの内容を変えないため、版が動かないこと自体は整合している。**

**★決着させるべき問いは 1 つ**——**「削除 → 他の利用者が編集 → 復元」の順で操作が起きたとき、何が起きるか。**

- **(a) 削除済みの行を他の利用者が編集できるか**（`PATCH` が `deleted_at IS NULL` を条件にしているか）。
- **(b) できないなら、復元は「削除時点の内容をそのまま戻す」ことになり、すり抜けは起きない。**
- **(c) できるなら、復元が古い内容で上書きする経路が成立しうる。**

**⇒ (a) を `M23-RESEARCH-01` 軸 D で実査し、結果に応じて `M23-03` で契約を固定する。** **★設計卓は実装を読めないため、ここで結論を先取りしない**（`E-117`）。

### 4.3 ★復元の単位——**楽観排他の集約単位に揃える**（**D-459**・確定）

> **★★2026-08-20 の実測で、`D-459` の前提が裏付けられた**（`M23-RESEARCH-01` 軸 D-2）。**復元は `combos` 1 表と `recipe_cache` の再計算だけを触り、子 7 表**〔`combo_steps` / `combo_tags` / `combo_setups` / `combo_oki_options` / `combo_punishes` / `combo_punish_curations` / `combo_setup_results`〕**に対して何もしていない。** **⇒ 子は物理的に残っており、親の `deleted_at` を戻すだけで繋がったまま復帰する。**
>
> **★★したがって `M23-03` の本体は「子に何かする」ではない。** **実測が示した本当の穴は参照側にある**——**`combos` を読む SQL 15 本のうち述語を持たないものが 3 本 ＋ 部分的が 1 本、`setups` を読む 14 本のうち 1 本、加えて子から親を辿る経路が 2 本。計 6 か所である**（§4.9）。

> **★★セットプレイには `D-459` がそのまま当てはまらない**——**`DeleteSetup` が `combo_setups` と `recipe_cache` を明示的に物理削除している。** **⇒ `setups.deleted_at` を NULL に戻しても紐付けは戻らない。** **`architecture-patterns` §11 の一般化の外にある**（followup `architecture-patterns-s11-setup-exception`）。


| 層 | 復元の対象か | 根拠 |
|---|---|---|
| **コンボ本体・ステップ・起き攻め・タグ** | **★一緒に戻す** | `M22-overview` §4.2.2 の「対象」。**利用者から見た単位が「そのコンボ」である** |

**★親が消えている間に子だけが変わった場合は、子の現在値を採用する**（**D-459**）。

### 4.10 ★★完全削除は CASCADE に依存しており、それを守るテストが 0 件である（2026-08-20 実測）

**★★そして CASCADE 依存の 5 表が消えたことを主張するテストは 0 件である。** **⇒ 発火しなくても全テストは緑のまま。**
