## 0. この指示書の特殊性

### 0.1 ★★★本サブが作るのは*不変条件*である

**★★★決着した形は 1 行で書ける**（`D-864` ／ 2026-09-13 開発者裁定）**。**

```
start_position_mass IS NULL  ⇔  position = 不問
```

**⇒ 区分が決まっているなら、マス数は必ず値を持つ。★マス数が空なら、区分は不問である。**

**★★開発者の逐語＝「NULL は不問として解決してください」。⇒ NULL に 2 つ目の意味を持たせない。**

### 0.2 ★★★この不変条件は、すでに `POST` / `PUT` では成り立っている

**★実測**（`M37-RESEARCH-01` §2.4）**＝`normalizePositionAndMass` は「マス優先で `position` を導出、マス無しなら `position` の代表値を補完」する。**

| 入力 | 既存の挙動 | 不変条件 |
|---|---|---|
| マス数あり | **`position` をマス数から導出する。⇒ 不問にはならない** | **★満たす** |
| マス数なし ＋ `position` が区分 | **代表値で埋める** | **★満たす** |
| マス数なし ＋ `position` が不問 | **代表値が無いので NULL のまま** | **★満たす** |

**★★★穴は `PATCH` だけである。⇒ `PATCH` 経路**（`service.go:634`）**は `normalizePositionAndMass` を呼ばない**（`CHANGE-195` の「持たせなかった分岐 1」）**。**

**⇒ 本サブがやるのは「`PATCH` にも同じ不変条件を守らせる」ことだけである。★新しい規則を発明しない。**

### 0.3 ★★★ただし `PATCH` で `normalizePositionAndMass` をそのまま呼んではならない

**★★★同関数は 2 つの仕事をする。⇒ 本サブが要るのは*片方だけ*である。**

| 半分 | 内容 | `PATCH` で要るか |
|---|---|---|
| **(a) 補完** | **マス数が無いとき、`position` の代表値で埋める** | **★★★これが要る** |
| **(b) 導出** | **マス数が在るとき、`position` をマス数から導出する** | **★★★これは要らない。⇒ 呼んではならない** |

**★★★理由＝`position` は重複判定キーである。⇒ `PATCH` は「識別キーが変わらない編集」の経路であり、その契約は「キーを変えない」ことそのものである**（`CHANGE-195` §2.4）**。**

**★★(b) を呼ぶと、区分をまたぐマス数が `PATCH` で届いたときに `position` が黙って変わる。⇒ 既存行と重複キーが衝突しうるうえ、`PUT`**〔旧行を論理削除して新規行を作る〕**を通らないため、履歴の作られ方も変わる。**

**★★★これが本サブ最大の危険である**（§4.1）**。**

### 0.4 ★★想定しない経路が 2 つある（**開発者の指示**）

**★開発者の逐語**（2026-09-13）**＝「API を直接叩く経路は基本的に想定しなくていいです」／「あとは異常な CSV も想定しなくていいです」。**

**⇒ 本サブは*画面から作られる状態*を正す。★API / CSV から不変条件を破る値が来た場合の網羅的な防御は射程外である。**

**★★★ただし「壊さない」ことは要る。⇒ CSV の空セルが `nil` として通る既存挙動**（`M37-RESEARCH-01` §2.4）**を、本サブで拒否へ変えないこと。★取り込みが落ちるようになったら射程超過である。**

### 0.5 ★★★運び量は対象外である

**★`carry_distance_mass` は区分を持たない**（`D-731` 不変条件 2＝運び量は「通常入力」を持たず、区分へ丸めない）**。⇒ 代表値という概念が存在しない。**

**★★`normalizePositionAndMass` は元から carry を触っていない**（`M37-RESEARCH-01` §2.4 の逐語＝「carry は触らない」）**。**

**⇒ 運び量の NULL は正常な状態である。★埋めない。★不変条件の対象にしない。**

### 0.6 ★★保存してから値が生えてくる見え方にしない

**★★★帰結が 1 つある＝区分が決まっている始動位置では、マス数を空にできなくなる。**

**⇒ 空欄のまま保存すると代表値が戻る。★これを*サーバの応答で初めて見せる*と、利用者には「消したのに生えてきた」と映る。**

**★★画面の側で先に埋めること。⇒ 通常入力で区分を選ぶと代表値が入る既存の作りと同じ形にする**（`D-730` / `CHANGE-196`）**。★サーバ側は後ろの守りに回る。**

## 4. ★★危険（**先に読むこと**）

### 4.1 ★★★最大の危険＝`PATCH` から `position` が動くこと

**★`normalizePositionAndMass` を `PATCH` からそのまま呼ぶと、区分をまたぐマス数が届いたときに `position` が導出し直される。**

**★★★`position` は重複判定キーである。⇒ 動くと (1) 既存行と重複キーが衝突しうる (2) `PUT`**〔旧行を論理削除して新規行を作る〕**を通らないため履歴の作られ方が変わる (3) `PATCH` の契約**〔識別キーが変わらない編集〕**が嘘になる。**

**★★破壊確認を置くこと**（§5-3）**＝区分をまたぐマス数を `PATCH` へ直接投げても `position` が変わらないこと。⇒ 画面からは起きないが、契約として押さえる。**

### 4.2 ★★2 番目＝NULL に 2 つ目の意味を持たせること

**★★★決着は「NULL＝不問」の 1 意味である。⇒ 「未測定」「クリア済み」といった別の意味を後から足さない。**

**★足すと、区分が決まっている行の NULL が「意味のある空」に見えてしまい、本サブが消したはずの状態が戻る。**

### 4.3 ★★3 番目＝運び量を巻き込むこと

**★★`carry_distance_mass` は名前が似ているだけである。⇒ 区分が無く、代表値が無く、`normalizePositionAndMass` も触っていない。**

**★「2 欄あるから両方そろえよう」と考えたら、それは誤りである。**

### 4.4 ★★★4 番目＝既存行を黙って埋め戻すこと

**★段 1 で違反行が見つかっても、本サブで埋めないこと。⇒ 件数と内訳を報告し、止めて請求する。**

**★★理由 2 つ＝(1) 利用者が登録したデータの書き換えである**（`CLAUDE.md` §10 の「データの不可逆な破壊の防止」）**。(2) マイグレを消費するなら自採番しない**（`D-293`）**。**

### 4.5 ★5 番目＝画面とサーバで規則が 2 本になること

**★段 2 と段 3 は同じ規則を 2 か所で実装することになる。⇒ 片方だけ直すと静かにずれる。**

**★★代表値表は 1 つの出所から引くこと**（`web/src/constants/position.ts` ／ `model.PositionBands`）**。⇒ どちらも既存であり、`position-bands-duplicated-go-and-ts` として既知の二重化である。★本サブで 3 本目を作らない。**
