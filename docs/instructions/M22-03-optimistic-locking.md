## 1. 背景と目的

### 1.1 楽観排他は「入っていない」のではなく「固定されていない」

**`M22-RESEARCH-01` 軸 A / B の実測**（`M22-overview` §4.2.1）——

| 事実 | 値 |
|---|---|
| `version` を受け取る更新経路 | **3 件**（`PATCH /api/combos/:id` ／ `PUT /api/combos/:id` ／ `PATCH /api/setups/:id`） |
| そのうち DB の現在値と突き合わせているもの | **★3 件（全件）**。**受け取るだけの経路 0 件・突き合わせるが無視する経路 0 件** |
| `version` 列を持つ表 | **`combos` と `setups` の 2 表のみ** |
| `version` を `+1` する SQL | **2 本のみ**（`combos` の `UpdateMetadata` ／ `setups` の `UpdateSetup`） |
| タグ・起き攻めの変更で `combos.version` が上がるか | **★上がる**（同一トランザクションで走り、`SET` 対象が空でも +1 される） |

**⇒ 仕組みは既に効いている。** **★本サブの仕事は「作る」ではなく、次の 4 つである。**

1. **効いていることを、壊すと赤くなる形で固定する**（§4.1）。
2. **版を上げるべきなのに上げていない経路の在否を、線引きに照らして判定する**（§4.2）。
3. **エラーコードを 1 つに揃える**（§4.3。**★`M22-04` から本サブへ移した**＝§1.5）。
4. **`version: 0` フォールバックを是正する**（§4.4）。

### 1.2 ★スキーマを 1 バイトも変えない（**確定済み**）

**粒度は `D-394` で確定している**（`M22-overview` §4.2.2）。**★案 A（集約）を採り、新しい `version` 列を 1 本も足さない。**

**⇒ マイグレーションを消費しない。** **⇒ 開発者の個別承認事項（新テーブル・新列・制約追加）にも当たらない。** **★要ると判断したら §9.3-1 で止まる。**

### 1.3 ★集約の外の線引き（**逐語で持ち込む。判定はこれに照らす**）

**`M22-overview` §4.2.2 の表を、そのまま本サブの判定基準とする。**

| 層 | 楽観排他の対象か | 理由 |
|---|---|---|
| **コンボ本体・ステップ・起き攻め・タグ** | **★対象**（`combos.version`） | **利用者から見た編集の単位が「そのコンボ」である。** **実装は既にこの粒度で動いている**——タグだけを送る PATCH でも版が上がる |
| **セットプレイ本体・そのステップ** | **★対象**（`setups.version`） | 同上。`UpdateSetup` が同一 tx でステップを差し替える |
| **成立条件（`combo_setup_results`）** | **★対象外** | **「別の人が別の状況を検証して足す」性格の記録である。** **集約に含めると、検証記録を 1 行足すたびに本体編集と衝突する。** **衝突はコンボ単位ではなく `(combo_id, setup_id, tech_type, in_corner)` の組単位で起きる** |
| **セットプレイ紐付け（`combo_setups`）・確定反撃系 4 表** | **★対象外** | 同上。**紐付けの追加／削除は「そのコンボの内容」ではなく関係の記録である** |
| **タグ・プリセット（`tags` / `presets`）** | **★対象外** | **`FR013` により作成者のみ編集可能であり、衝突するのは同一人物の 2 端末に限られる** |
| **`recipe_cache`** | **★対象外**（**現状どおり**） | 実装コメントが「キャッシュは排他対象外」と明記。**★`updated_at` は進むため、`updated_at` と `version` が同期しない書き込みが実装上存在する**（followup `updated-at-version-desync-on-recipe-cache`）。**⇒ 本サブは直さない。仕様として確定させる**（§4.5） |

**★この表の「対象外」を穴として塞がないこと**（§1.6-1）。**塞ぐと、検証記録を 1 行足すたびに本体編集と衝突する。**

### 1.4 ★409 は既に別の意味で使われている（**本サブの最重要の前提**）

**`DES-005` §5.11（`CHANGE-101` / `M20-04` の as-built）**——**「一意制約違反は 409 で衝突表記を載せる」。**

**⇒ 409 というステータスだけでは、版不一致と一意制約違反を区別できない。**

**★ここから 2 つの帰結が出る。**

| # | 帰結 |
|---|---|
| 1 | **★ステータスだけを見るテストは、版の突き合わせが効いていることを証明しない**（§4.1-2）。**別の理由の 409 でも緑になる** |
| 2 | **★エラーコードは `conflict` のような総称であってはならない**（§4.3-2）。**どの衝突かが読めない** |

### 1.5 ★エラーコードの統一を `M22-04` から本サブへ移した（**設計卓の割付変更**＝**D-406**）

**`M22-overview` §4.2.2 の脚注は、当初こう書いていた。**

> **★エラーコードの不一致（`conflict` / `version_conflict`）は `M22-03` ではなく `M22-04` の担当**（followup `conflict-error-code-inconsistency`）。**「どう見せるか」を決めるサブと同じ面だからである。**

**★これを本サブへ移す。理由は 3 つ。**

| # | 理由 |
|---|---|
| 1 | **★本サブの仕事 4 に「`DES-002` へ版不一致の契約を書く根拠を作る」が入っている**（followup `des002-4-2-lacks-conflict-contract`）。**⇒ 実装が資源によって 2 つの異なるコードを返したままでは、契約を 1 つに書けない。** **「コンボは `conflict`、セットプレイは `version_conflict`」と設計書に書くことになり、それは契約ではなく現状の記述である** |
| 2 | **★エラーコードは通信の契約であって、見せ方ではない。** **`M22-04` は「競合したときの利用者体験」を作るサブであり、そこでサーバの応答本文を変えるのは面の逸脱である** |
| 3 | **★本サブで現状のコードをテストで固定すると、`M22-04` の変更が「回帰」に見える。** **既知の不整合をテストで固めるのは、後で直す人の妨げになる** |

**⇒ `M22-04` の担当は「409 をどう見せるか」に純化する。** **`M22-overview` は本裁定に合わせて改訂済みである。**
