## 0. この指示書の特殊性

### 0.1 製造担当として起動 ＋ 調査だけ実施して閉じる運用

製造担当セッションを起動し、**§4 の事実列挙 → §5 レポート → クローズ**まで行う。**実装は本調査の対象外であり、後続サブ（`M22-01`〜`M22-07`）で別指示書として扱う。**

### 0.2 read-only 厳守

**許可**——`view` ／ `grep` ／ `git log` ／ `find` ／ `ls` ／ SQL の `SELECT` ／ `go list` ／ `go mod graph` ／ `go env` などの**参照系コマンドのみ**。

**書き込みの例外は 2 つだけである。**

| # | 許可される書き込み |
|---|---|
| 1 | **§2.1 の調査レポート**（`docs/progress/M22-RESEARCH-01-report.md`） |
| 2 | **`docs/progress/progress-log.md` への索引行の追記**（`CLAUDE.md` §8 の常設要求） |

> **★(2) を落とすと、DoD と禁止表が同じ指示書の中で正面衝突する。** **`CLAUDE.md` §8 は「progress-log への追記」を常設で要求する一方、禁止表が「`docs/` 配下の他ファイルを変更しない」とだけ書いていると、片方を満たすともう片方に違反する。** **これは 2 本連続で実際に起きた**（**M-40**＝`M20-RESEARCH-01` ／ **M-49**＝`M21-RESEARCH-01`）。**⇒ ここで明示的に許可する。**

**禁止**——

- **本体リポのソース／マイグレ／seed／テスト／`docs/design/` 配下の変更**（**1 バイトも変更しない**）。
- **DB への書き込み**（`INSERT` / `UPDATE` / `DELETE` / マイグレの適用）。**★DB を読むときは必ずコピーを作って読む。**
- **`docs/handover/followup-backlog.md` の編集**（**D-382**。**設計卓のみが編集する。候補は §5 の該当節へ書く**）。
- **採番**（CHANGE 番号・マイグレ連番）。**必要が生じたら請求する。自採番しない**（**D-293**）。
- **新規依存の追加**（`go get` / `pnpm add`）。**★軸 G は「いま何が在るか」を読むだけである。**

### 0.3 判断・提案を含めない（judgement-free）

**事実列挙のみ。** 「ここを直すべき」「この方式が良い」といった修正方針・設計結論は**含めない**。

**★とくに軸 G（パスワードハッシュ）では、方式の推奨を書かないこと。** **セキュリティ関連の方式決定は開発者の承認事項である**（`CLAUDE.md` §10 ／ **D-386 (4)**）。**本調査が出すのは「何が在るか」であり、「何を使うべきか」ではない。**

**★同じ理由で「安全である」「安全でない」と書かない。** **書けるのは「この条件下でこう振る舞う」までである。**

**例外は 2 つ**——**(1) 想定外の発見**、**(2) 明らかな矛盾の事実指摘**。**これらは判断ではないため記録する**（§5 の該当節）。

### 0.4 本調査の主目的

| 軸 | 主目的 | 混同回避 |
|---|---|---|
| **A** | **楽観排他がどこまで効いているか** | **「列が在る」と「更新時に突き合わせている」は別である。** 本調査は後者を見る |
| **B** | **`version` を持たない更新経路の全数** | **「持たない」と「持つが使っていない」を分けて数える** |
| **C** | **`users` 表の実データと、単一利用者を前提にしている箇所** | **「表が在る」と「使われている」は別である** |
| **D** | **`[security]` の配線状況** | **設定ファイルの例と、実装の構造体は別物である**（§3.2 の前提事実 3） |
| **E** | **CORS/CSRF の現状** | **「掛かっていない」と「掛かっているが緩い」を分ける** |
| **F** | **設定画面の構成と LAN IP の取得経路** | `FR407`（QR）の前提 |
| **G** | **パスワードハッシュ候補の実在とライセンス** | **★「機械が出した結果」だけを書く。記憶で書かない** |

### 0.5 ★`M21-07` と同時に走らせてよい

**本調査は read-only であり 1 バイトも変更しない。** **かつ 7 軸はいずれも物理入力の面を対象にしていない**（認証 ／ 排他 ／ `[security]` ／ CORS ／ 設定画面 ／ 辞書）。**⇒ `M21-07`（`web/src/features/physical-input/` ほか）と交差しない。**

**★ただし 1 点だけ注意する**——**`M21-07` が同時に走っている場合、`web/src/` の一部は作業中の状態にある。** **軸 F で設定画面を読むときに `git status` で作業ツリーの状態を確認し、レポートへ「どの commit 時点で読んだか」を書くこと**（`E-56`＝**自動生成資料は生成コミットと現 HEAD の差を意識して使う**の同型）。

## 4. 調査項目

**★各軸で「何を・どの単位で・どの基準時点で数えたか」を必ず併記する**（`E-93` / `E-16`）。**★走査は「回したこと」ではなく「当たることを確かめたこと」を証跡にする**（`SUPP-001` §5.5 (11′)）。**日本語の散文を否定文字クラスで走査するときは `LC_ALL=C.UTF-8` を付ける。**

### A. 楽観排他がどこまで効いているか

| # | 実測すること |
|---|---|
| A-1 | **`version` を受け取る更新経路の一覧**（ハンドラ名 ／ HTTP メソッド ／ パス）。**`code-facts` §7-2 の 3 件が全数かを確かめる** |
| A-2 | **各経路が受け取った `version` を実際に何に使っているか。** **(a) DB の現在値と突き合わせている ／ (b) 受け取るだけで使っていない ／ (c) 使うが不一致でもエラーにしない、の 3 通りに仕分ける** |
| A-3 | **突き合わせている経路について、不一致のときに何が返るか**（HTTP ステータス ／ エラーコード ／ 本文の形）。**★`DES-002` §4.2 の記述と一致するかも見る** |
| A-4 | **`version` が増える契機**——**どの操作で `+1` されるか。** **本体だけか、ステップ・タグ・起き攻めの変更でも増えるか** |
| A-5 | **既存のテストが楽観排他を固定しているか**（テスト名と、そのテストが主張していること） |
| A-6 | **★フロント側が `version` をどこから取り、どう送っているか**（`code-facts` §2-2 の queryKey と併せて見る）。**取り違えると「保存できたのに古い値で上書き」になる** |

## 8. 注意事項・判断に迷ったら

### 8.1 推測で進めてはいけない事項

1. **ライセンス**（G-5）。**★記憶で書かない。ファイルの実体から引く。**
2. **「効いている／効いていない」**（軸 A）。**コードを追って確かめる。**
3. **「無い」の断定**（C-7 / D-2 / F-4）。**探した範囲を必ず添える。**

### 8.2 推測で進めてよい事項（その旨を明示）

1. **走査コマンドの組み立て方**（結果とコマンドを両方残せばよい）。

| # | 停止条件 |
|---|---|
| 1 | **調査のために書き込みが要ると判断した**（§0.2 の 2 例外を除く）。**⇒ 止めて報告する** |
