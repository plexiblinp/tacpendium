## 1. 背景と目的

### 1.1 出所——**製造が実測したコスト構造**

`M24-13`（仮登録のレシピ必須化）の所要が約 2 時間だった。**製造が内訳を実測し、設計卓へ改善 5 件の可否を諮った。**

| バケット | 内訳 | 小計 |
|---|---|---:|
| レビュー 2 往復 | 2 回目のみ実測 27 分（71 ツール実行 / 218k トークン）。1 回目も同規模 | 約 45 分 |
| **テスト実行** | `make e2e` 4.4 分 × 5 回 ＝ 22 分 ／ Vitest 2.2 分 × 4 ＝ 9 分 ／ `go test` 全体 約 2 分 × 5 ＝ 10 分 ／ 破壊確認の絞り込み実行 約 8 分 | **約 49 分** |
| 初回の並列探索 | Explore 3 本（並列） | 5 分 |

**⇒ 手戻りを除いても約 100 分。コードを書いていた時間はごく一部で、大半が「回して待つ」と「レビュー」である。**

**★レビューは削らない**（`D-597`。**2 回目のレビューが `M24-13` の失効文字列を捕まえており、対価は機能している**）。**⇒ 短縮の余地は「回して待つ」側にしか無い。それが本サブである。**

### 1.2 ★★本サブの最大の危険——**壊しても「速くなった」で緑に見える**

**テスト DB の作り方を変えるサブである。⇒ 壊し方が「テストが落ちる」ではなく「テストが何も検証しないまま緑になる」形をとりうる。**

**具体例**——**テンプレートのコピーに失敗して空の DB でテストが走っても、「その行は存在しない」を確かめているテストは緑のままになる。しかも速くなる。**

**★★だから本サブでは「速くなったこと」を正しさの根拠にしてはいけない**（製造自身が相談で挙げた注意点。**設計卓はこれを完了条件へ格上げした**＝§7.1）。

### 1.3 ★★設計卓が差し戻した点——**効果見込みが CPU で語られている**

**製造は効果を CPU で語った**〔`go test` の CPU 合計 705 秒・うち約 7 割が DB 構築〕。**しかし `go test ./... -count=1` の wall は約 2 分である。**

| 量 | 値 | 出所 |
|---|---:|---|
| `go test` の CPU 合計 | 705 秒 | 製造の実測 |
| `go test ./... -count=1` の wall | 約 2 分（約 120 秒） | 製造の実測 |
| `internal/service/combo` 単独 | 193 秒（178 テスト） | 製造の実測 |
| `internal/infra/migration` 単独 | 64.6 秒（**★除外対象**） | 製造の実測 |

**★★この 4 つは内部で食い違っている**——**`internal/service/combo` 単独 193 秒が、wall 全体 120 秒より長い。1 パッケージが全体より長いことはない。**

**⇒ パッケージ内で並列に走っているか、2 つの数字が別条件で採られたか、どちらかである。**

**★★さらに、除外対象の `internal/infra/migration`（64.6 秒）は、除外した瞬間に wall の床になりうる。**

**⇒ CPU を 7 割削っても wall が 7 割縮むとは限らない。wall はクリティカルパス（最長パッケージ）で決まる。**

**★★本サブは「wall での削減見込みを出してから射程を確定する」**（§3.3-1 / §4.1.0）。**これは playbook §4.32 / §4.40 の同型である**——**「705 秒の 7 割」は数として正しくても、時間短縮の量ではない。**

## 4. 詳細仕様

### 4.1 ★★テスト DB のテンプレート化（**本丸**）

#### 4.1.0 ★★射程の確定は実査の後である

**★★§3.3-1 / -2 / -3 の答えが出るまで実装に入らないこと。**

| 実査の結果 | 本節の扱い |
|---|---|
| **wall の削減見込みが十分に大きい** | **予定どおり実施する** |
| **★wall の削減見込みが小さい**（例＝除外対象が床になり、数十秒しか縮まない） | **★★実施せず、根拠を付けて報告すること。★「せっかく調べたから作る」をしない** |
| **★数字の食い違いが解けない** | **★★止めて設計卓へ報告する**（§9.1） |

#### 4.1.1 方式

| 論点 | 決めたこと |
|---|---|
| **形** | **テストバイナリ（＝パッケージ）ごとに 1 回だけマイグレーション済み DB を作ってテンプレートとし、各テストはそのファイルをコピーする** |
| **1 回性の担保** | **`sync.Once`**（**★置き場は製造が決めてよい**＝§2.3） |
| **★★WAL** | **★★テンプレートを作った直後に `wal_checkpoint(TRUNCATE)` して閉じ、単一の `.db` ファイルをコピーする**（**★`-wal` / `-shm` を持ち込まない**。製造の注意点 2） |
| **★署名** | **★`Setup(t)` の署名は変えない**（**呼び出し元 200 か所超を触らないため**） |
| **★★除外** | **`internal/infra/migration`**（**マイグレーション自体を検証するテストであり、再生させることが目的である**） **＋ §3.3-6 の実査で見つかったもの** |
| **除外の実現手段** | **★製造が決めてよい**（§2.3）。**★ただし「除外が効いていることを速度以外の指標で観測できる」ことが条件である**（§5.3-2） |

#### 4.1.2 ★★「速くなったこと」を正しさの根拠にしない

**★★導入の前後を同一セッション内の背中合わせで採り**（playbook §4.37）**、次の 3 つが不変であることを示すこと。**

| # | 不変であるべき量 |
|---|---|
| **1** | **`go test ./... -count=1` の ok パッケージ数** |
| **2** | **FAIL 数**（**★0 のまま**） |
| **3** | **★★テスト本数**（**★これが最も重要である。★★コピーに失敗して空 DB で走っても、「無いこと」を確かめているテストは緑のままになりうる**） |

**★別時点の値どうしを引き算しないこと**（§4.37）。**⇒ 導入前の測定は、本サブの作業を始めた同じセッションで採る。**

### 4.2 ★`Makefile` への絞り込み用 E2E ターゲット

**★★出所＝製造が `M24-13` で実際に踏んだ罠である**（followup §AR `playwright-narrow-run-env-trap`）。

> **`make e2e` を経由せず `pnpm exec playwright test` を直接叩くと `PW_EXECUTABLE_PATH` が渡らず、UI を使うテストが全滅する**（`Executable doesn't exist at /opt/pw-browsers/chromium_headless_shell-...`）。**`Makefile` の `e2e` ターゲットが同変数を設定しているため、絞り込み実行のときだけ落ちる。**

| 論点 | 決めたこと |
|---|---|
| **★★形** | **★★注記を文書へ足すのではなく、`Makefile` へ絞り込み用ターゲットを足して罠に落ちない経路を作る**（`D-599`） |
| **理由** | **★本プロジェクトの一貫した姿勢と同じ形である**（`.claude/settings.json` の deny・各 check スクリプト＝**機械で強制できるものを文書へ書かない**） |
| **★名前と引数** | **★製造が決めてよい**（例＝`make e2e-only P=<パターン>`） |
| **★★環境変数** | **★★`make e2e` と 1 か所から共有すること。★2 か所に書くと `E-76`（同じ情報を 2 か所に持つとドリフトする）に触れる** |
| **★`make e2e` 自体** | **★挙動を変えない**（§2.2） |
| **★★対象の変数** | **★§3.3-9 で数えた全数を通すこと。`PW_EXECUTABLE_PATH` だけとは限らない** |

### 4.3 ★★nightly への E2E 追加

**★★出所＝`D-594`。E2E は `pr-checks.yml` にも `nightly-crossbuild.yml` にも載っていない**（製造の実測）。**⇒ main の E2E が緑かを知る経路は、人間が書いた完了報告の文言しかない。報告は主張であって観測ではない。**
