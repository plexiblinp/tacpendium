## 1. 背景と目的

### 1.1 背景

**M21-01 が論理ボタン層を作った。本サブはその上に「時間」を持ち込む最初のサブである。**

**M21-01 は同時押しをまとめていない**——複数ボタンが押されていれば `states` に複数入るだけで、**それが「OD 技として 1 ステップ」なのか「2 つの別入力」なのかを決めていない。** **本サブがそれを決める。**

**PoC の実測**（**D-324** ／ `M21-RESEARCH-01` 軸 C・軸 D。**USB・Chrome 151・rAF 間隔 中央値 4.20 ms ＝ 約 238 Hz・標本 各 90**）——

| 指標 | レバーレス | パッド |
|---|---|---|
| **押し始め** のズレ 中央値 | 8.30 ms | 8.30 ms |
| 同 p95 | 20.90 ms | 33.30 ms |
| 同 最大 | **20.90 ms** | **45.80 ms** |
| **離し始め** のズレ 中央値 | 12.50 ms | 12.50 ms |
| 同 最大 | **50.00 ms** | **83.30 ms** |

**★押し始めと離し始めで分布が違い、離し始めが一貫して大きい**（2 機種・両方向で同じ向き）。**どちらを判定に使うかは未決であり、本サブが決める。**

**★チャタリングは本計測条件では観測されなかった**——**立ち上がり総数 50 ＝ 指示回数 50 ＝ 画面カウンタ 50 が 2 機種とも完全一致**し、**1〜32 ms の帯に 3 指標**（立ち上がり間隔・押下時間・離間時間）**とも 0 件**だった。

### 1.2 目的

1. **OD 技等の同時押しが、ズレて入力されても 1 ステップにまとまる**（`FR107`）
2. **チャタリング（`FR108`）の扱いが、根拠とともに決着している**——**「対策する」とは限らない**（§4.4）
3. **SOCD（相反する方向の同時入力）の規則が確定している**（§4.5）
4. **判定窓が 1 か所から差し替えられる形になっている**（§4.2-3）

## 4. 詳細仕様

### 4.1 何を「1 ステップ」とみなすか

**入力は時刻つきの状態列、出力はステップ候補の列である。**

| # | 仕様 |
|---|------|
| 1 | **判定窓の内側で立ち上がった複数のボタンを、1 ステップにまとめる** |
| 2 | **★方向は「まとめる対象」ではない。** **方向は状態であってイベントではない**（M21-01 の公開インターフェース）。**ステップは「その時点の方向 ＋ まとまったボタン集合」で構成する** |
| 3 | **★窓の起点をどう置くかを決めて報告すること。** **設計卓の見込みは「最初の立ち上がりを起点に固定窓」。** **代案＝最後の立ち上がりから窓を延長する形**（**押し続けている限りまとまり続けるため、意図しない結合が起きうる**）。**覆ってよい。覆ったら理由を書く** |
| 4 | **押し始めと離し始めのどちらを判定に使うかを決めて報告すること**（**D-324** で未決）。**★設計卓の見込みは「押し始め」**——**離し始めは分布が広く**（最大 50.00 / 83.30 ms）、**かつ利用者の意図は押した時点で確定しているため。** **覆ってよい** |

### 4.2 判定窓の決めかた（★本サブの中核）

**★Bluetooth は計測できない**（**D-328**。**開発者が BT 接続の機体を所有していない**）。**かつ Gamepad API に接続方式を示すフィールドが無いため、実行時に接続方式で分岐することもできない。**

**⇒ 採りうる形は 2 つである。§3.3-1 の実査で選ぶこと。**

| 形 | 内容 |
|---|---|
| **(α) 単一の広い窓** | 接続方式を問わない 1 つの閾値 |
| **(β) 実行時の自己校正** | **利用者の環境で実際に観測された更新間隔から窓を導く**（`Gamepad.timestamp` の更新間隔と rAF 間隔から実効サンプル周期を推定する） |

**★実装へ渡す条件 4 点**（**D-328**。**どちらを採っても守ること**）——

| # | 条件 |
|---|---|
| **1** | **窓は USB の実測から導き、`D-324` の最大値を下回らせない**——**押し始め 45.80 ms ／ 離し始め 83.30 ms** |
| **2** | **BT は未計測であると明記する。「BT でも動く」と書かない**（`E-84`） |
| **3** | **窓を定数で埋め込まず、1 か所から差し替えられる形にする**（**利用者からの報告で調整しうるため**） |
| **4** | **測る前に判定法を決めない**（**D-294** ／ `E-123`）。**§3.3-1 の結果で (α) / (β) を選ぶ** |

**★フレーム数で窓を置いてはならない。** **計測環境は約 238 Hz であり、60 Hz 環境では同じ実時間が約 1/4 のフレーム数になる。** **ミリ秒が一次で、フレーム数は本環境の換算値である。**

**★`DES-005` §6.4 の「同時押し判定は時間窓（例：16ms）内の入力を1ステップにまとめる」は実測と合わない。** **押し始めの p95 が既に 20.90 / 33.30 ms である。** **⇒ `CHANGE-107` で是正する**（**製造は設計書を編集しない**。実測値を完了報告に出すこと）。

### 4.3 窓を広く取ることの副作用（★silent ではない、を担保する）

**窓が広すぎる副作用＝「別々に入れたつもりの 2 入力が 1 ステップにまとまる」。** **窓が狭すぎる副作用＝「同時押しが 2 ステップに割れる」。**

**★どちらも画面に出る**（`FR106` の読取表示があるため）。**⇒ `m21-contract` §1.3 が警戒した「黙って落とす」形は、読取表示があるかぎり成立しにくい。**

**⇒ 本サブの担保**——**§4.6 の最小可視化で、判定結果が目視できること。** **本番 UI は M21-03 が作るが、本サブの完了判定を机上にしないため最小の表示を持つ。**

### 4.4 チャタリング（`FR108`）の決着

**★「対策不要」という第三の結論が候補である**（教訓 `E-41`）。

**PoC の実測**——**立ち上がり総数 50 ＝ 指示回数 50 ＝ 画面カウンタ 50 が 2 機種とも完全一致**（**チャタリングが起きていれば立ち上がり総数が押下回数を上回る**）。**1〜32 ms の帯に 3 指標とも 0 件。**

| # | 仕様 |
|---|------|
| 1 | **対策を実装するかしないかを、実測を根拠に決めて報告すること** |
| 2 | **★「対策不要」を採る場合の書き方**——**「2 機種・USB・Chrome で観測されなかった」を根拠として明記し、一般化しないと書く。** **「チャタリング対策を実装した」と書かない** |
| 3 | **★対策を実装する場合**——**閾値は §4.2 の条件 1〜3 に従う。** **かつ「観測されなかったのになぜ入れるか」を書くこと**（**入れること自体は否定しないが、根拠なく入れると次の担当が消せなくなる**） |
| 4 | **★どちらを採っても、`FR108` は「決着した」と言える。** **実装の有無が完了条件ではない** |

> **★(f) が本サブのテストの主眼である。** **窓は「利用者の入力が黙って落ちるかどうか」を決める唯一の数値であり、実測から離れたら気づけない。** **定数を直接読んで固定すること**（**間接的な挙動テストだけでは、定数が変わったときに落ちない**）。

> **★比較区間は自サブに閉じる**（`SUPP-001` §5.5 (1)）。**HEAD スコープの主張を本サブの名前空間に置かない**（同 (2)）。
