## 1. 背景と目的

### 1.1 背景

M19 は「既存コンボを選択 → その `knockdown_advantage`（以下 KA）から成立するセットプレイのレシピを提示 → ユーザーが間合い等を検証 → 繋がるものだけ採択 → 既存機構へ保存」する機能である。

中核ロジックは別リポ `autopilot-combomgr/projects/setplay-suggestion` に**先行実装済み**で、M19-RESEARCH-01 により以下が事実確定している。

- 公開エントリ `Suggest(knockdownAdvantage int, moves []Move, target Target, opt Options) ([]Suggestion, error)`。探索は subset-sum（反復深化・少手数優先・枝刈り・sanitize）。
- **Go 1.24・標準ライブラリのみ**（`go.mod` に `require` 節なし・`go.sum` 不在・全 import が stdlib）＝外部依存ゼロ。テスト 18 関数 PASS。
- 現行の受理条件は `Σ(filler.total) + target.Startup == KA` の**完全一致のみ**で、**持続（active）窓を持たない**。
- 列ドリフトは無し（エンジンが読む `moves.total`／`startup`／`code` はすべて現行スキーマに存在）。

一方 M19-RESEARCH-01 の PoC は golden-case を strict 0/5 と報告したが、**判定式の取り違え**であることが判明した（正しい判定は「開発者が指定した持続 N フレーム目が起き上がりに載るか」）。再検算・RESEARCH-02 実測により、**現行 1/5・窓方式で 4/5**（残り GC-2 は派生技の論点＝M19-02）と確定している。

**確定した意味論**（**DES-003 §3.4 に errata② で明文化済み**＝中央預かり解消・2026-07-24。KA＝無敵時間／起き上がり KA+1／`N = KA+2−S`／`1 ≤ N ≤ active`）:
- KA ＝**ダウン中の無敵時間**。相手の起き上がりは **KA+1 フレーム目**。
- `S = Σ(filler.total) + target.startup` ＝ target の**第 1 active の絶対フレーム**。
- `N = KA + 2 − S` ＝ **起き上がりに重なる持続フレーム番号**。
- 成立条件（窓方式）＝ `N_min ≤ N ≤ target.active`　⇔　`KA + 2 − active ≤ S ≤ KA + 2 − N_min`。

### 1.2 目的

1. エンジンを本体 `internal/service/setplay` へ**移植**する（stdlib-only ゆえ外部依存を増やさない。NFR303/304 維持）。
2. 受理条件を**受理帯方式**へ変更し、窓方式を実装する（§4.1）。
3. 提案エンドポイントを新設する（§4.3）。
4. グルー層（target 列挙・filler 候補・ランキング・DTO 組み立て）を実装する（§4.2・§4.4）。
5. 提案 UI を**単一コンボ候補面に相乗り**させ、N 併記・N_min・ソート切替を提供する（§4.5）。
6. 採択→**既存 `setups`＋`setup_steps`＋`combo_setups` へ保存**する（§4.6。新テーブルを作らない）。
7. golden-case **GC-1／GC-3／GC-4／GC-5 の 4 件**が `N_min=1` で再現することを実測する（§5.3）。
8. **提案の制約を利用者へ告知**する（初回のみ自動表示・以降は明示操作。§4.6.3）。あわせて**保守マーカー**を仕込み、以後の機能改修時に文面の更新漏れが起きない状態にする。

## 4. 詳細仕様

### 4.1 エンジンの移植と窓化（受理帯方式）

#### 4.1.1 移植

`autopilot-combomgr/projects/setplay-suggestion` の `setplay` パッケージを `internal/service/setplay` へ移植する。**stdlib 以外の import を持ち込まない**。移植元は変更しない。

#### 4.1.2 型の変更

```go
type Target struct {
    Name    string
    Startup int
    Active  int   // 追加: 持続フレーム数
}

type Options struct {
    AllowRepeat bool
    MaxFillers  int
    MaxResults  int
    NMin        int  // 追加: 最小持続番号。DefaultOptions() で 1
}

type Suggestion struct {
    Fillers        []Move
    Target         Target
    TotalFrames    int  // 意味変更: 「常に KA」→「S（第1 active の絶対フレーム）」
    HitActiveFrame int  // 追加: N（起き上がりに重なる持続フレーム番号）
}
```

#### 4.1.3 受理条件（**本サブの中核**）

- 予算: `budgetMax = KA + 2 − NMin − target.Startup`
- 受理: **`0 ≤ remaining ≤ target.Active − NMin`**（現行の `remaining == 0` を置換）
- 成立時の N: **`N = remaining + NMin`**

> **根拠と検証**: 上記は窓条件 `KA+2−Active ≤ S ≤ KA+2−NMin` と**代数的に等価**である（設計側で乱択 20,000 ケースの全数照合を実施し不一致 0 件）。また `N = remaining + NMin` は `N = KA+2−S` と恒等であり、**N の算出に減算を別途行う必要はない**（remaining から直接復元する）。

#### 4.1.4 境界条件

| 条件 | 挙動 |
|------|------|
| `target.Active < 1` | 新エラー `ErrInvalidTargetActive` を返す（グルーが事前除外するのが原則。エンジンは防御） |
| `target.Startup < 1` | 現行どおり `ErrInvalidTargetStartup` |
| `NMin > target.Active` | **エラーではなく空結果**（N_min は絞り込み設定であり不正入力ではない） |
| `NMin < 1` | **1 に丸める**（エラーにしない） |
| `budgetMax < 0` | 空結果（エラーにしない） |

#### 4.1.5 既存の探索構造は温存する

反復深化（少手数優先）・枝刈り・`sanitize`（非正 total の除外・dedup・昇順整列）・`computeMaxDepth` は**現行の構造を維持**する。ただし受理条件が帯になったことで、**枝刈りが帯に入る解を切り落とさないこと**を §5.1 のテストで担保する（`computeMaxDepth` の分母・下限枝刈りの条件式が `budgetMax` を基準に計算されているかを確認する）。

#### 4.1.6 破壊的変更の明示

`Suggestion.TotalFrames` の意味変更は移植元テストの前提を壊す。移植したテストのうち当該前提に依存するものは**期待値を修正**し、修正した件数を完了報告に記載する。

### 4.2 target（当てたい技）の列挙規則

target 候補は当該コンボのキャラクターの moves から、以下を**すべて**満たすものとする。

| # | 条件 | 根拠 |
|---|------|------|
| 1 | `startup ≥ 1` かつ `active ≥ 1`（いずれかが NULL の技は除外） | エンジンが両方を要求（§4.1.4）。ドライブパリィ等の非攻撃技は `active` が空のためここで落ちる（DES-003 §3.3 注記） |
| 2 | **`is_derived = false`** | DES-003 §3.3 の判定原理「**コントローラでこの技だけをいきなり出せるか。出せない → true**」より、**`is_derived = false` ⇒ 単独入力可**が成立する。したがって保守側ゲートとして安全（設計回答 Q1） |
| 3 | **`is_aerial = false`** | `is_aerial = true` の C 型ジャンプ攻撃は**着弾フレームが滞空中の攻撃タイミングで可変**であり、スカラーの S では表現できない（M19-DESIGN-01 §3-6・DESIGN-02 §2） |

**明示指定モード**: リクエストで target を明示指定できる経路を必ず設ける（§4.3 の `target_move_id`）。この経路では条件 2・3 を適用しない（条件 1 は適用する）。golden-case の検証と、除外が保守的すぎる場合の逃げ道を兼ねる。

`is_derived` は現状 model 非搭載＝`GET /api/moves` に出ない（DES-003 §3.3 明記）。**BE 内の SELECT で参照すれば足り、API 露出は必須ではない**。UI 表示に使う場合のみ §2.3 の例外条項に従う。

> **本規則の既知の限界（完了報告に明記する）**
> - **`rush_variant` は `is_derived = true`**（DES-003 §3.3 明記）。よって本サブではラッシュ版技が target から外れる。**カバレッジの損失であり誤りではない**。解禁は M19-02。
> - **状態変種**（酔いレベル等）も `is_derived = true` のため外れる。同上。
> - **B 型 air-only 技**（例: ケン空中竜巻旋風脚＝最速で出しても当たらない技）は `is_derived=false`・`is_aerial=false` の**両ゲートを通過**し、**機械判別できない**（M19-DESIGN-01 §3-8）。本サブでは**誤提案として出得る**。提案は表示→ユーザー採択（FR307）であり実害は限定的だが、**件数を完了報告に記載**する。恒久対策（人手除外マーキング）は中央/開発者判断。

### 4.3 提案エンドポイント

```
GET /api/combos/:comboId/setplay-suggestions
    ?n_min=1              // 省略時 1
    &sort=n|steps         // 省略時 n（N 降順）
    &target_move_id=123   // 任意。指定時はその技のみを target とする
```

- 入力の KA は当該コンボの `knockdown_advantage` を用いる。**NULL の場合は 400 系**を返し、UI 側で「有利フレーム未入力のため提案できません」と表示できるエラーコードを含める。
- **副作用なし（非永続）**。保存は既存 API を使う（§4.6）。
- レスポンスは `SuggestionDTO` の配列（§4.4）。
- 既存の FR011 候補 API とは**別エンドポイント**とし、既存の挙動を変更しない。

### 4.4 提案 DTO とランキング

```
SuggestionDTO {
  steps: [ { moveId: int, code: string, role: "filler"|"target", counted: bool } ],  // 表示順
  s: int,             // 第1 active の絶対フレーム
  n: int,             // 起き上がりに重なる持続フレーム番号
  landing: int,       // = KA + 1
  targetActive: int,
  alreadyAdopted: bool  // 既存 setups とのレシピ一致（VAL-S04 と同一基準）照合結果
}
```

- `role` に **`"parent"` を含む値域**を最初から定義しておく（M19-02 の表記展開で使う。本サブでは出力しない）。
- **`alreadyAdopted`**: 当該提案のレシピが、**同一親コンボに既に紐付く `setups` と一致**するか（VAL-S04 と同一基準＝名前非依存）。`true` の行は UI で「採択済み」と表示し、**採択操作を抑止**する（§4.6.2）。
- `counted` は本サブでは常に `true`（親ステップを出さないため）。**フィールド自体は最初から持たせる**（M19-02 で `false` の行が入る）。
- **ランキング（グルー側で実施）**: 第 1 キー **N 降順**（後の持続で当たるほどヒット時有利が大きく実用価値が高い）→ 第 2 キー **手数（filler 数）昇順** → 第 3 キー **Σtotal 昇順** → 第 4 キー **Name 昇順**（決定論）。`sort=steps` 指定時は第 1・第 2 キーを入れ替える。
- **`MaxResults` 到達の計測**: エンジンは少手数優先で列挙し `MaxResults` で打ち切るため、**打ち切りはグルーのソートより前**に起きる。到達した場合はレスポンスに `truncated: true` を含め、§5.3 で到達頻度を計測する。

### 4.5 filler（空振り技）候補

- 基本: 当該キャラの `total ≥ 1` の技（エンジン `sanitize` と整合）。
- **`moves.setup_only` による絞り込みは行わない**（開発者確定 2026-07-24）。
  > **`setup_only` の実セマンティクス（開発者確定）**: 「**ユーザー登録のセットプレイ専用 move**」＝コンボ登録等の技選択から隠すための**行区分**であり、「filler として有用な技」を示すフラグではない。したがって「ON があるキャラはそれのみを filler 候補にする」という当初案は**撤回**された（M19-DESIGN-02 §5 も書き換え）。
  > **本サブの扱い**: `setup_only` の値によらず**全技を filler 候補**とする。`setup_only = true` の技は**セットプレイ専用として登録された move** であるから、**filler 候補に必ず含める**（除外しない）。実用上の絞り込みが要るかは運用後に判断する（M19-DESIGN-02 §10(g)）。
- 空振り時硬直が変動する技（DES-003 §3.3 の注記）は total が実挙動とズレ得るが、**本サブでは除外しない**（既知割り切り＝§9.2）。

### 4.6 提案 UI（相乗り）と採択→保存

#### 4.6.1 UI

- 載せ先は **DES-005 §5.6 項目 11 の単一コンボ候補面（`SetupSelectorModal`）**。既存の FR011 候補表示を**作り直さず**、提案リストを追加する。
- **`selectedIds`（§5.13a）は入口にしない**。提案は単一コンボ文脈である。
- 各行の表示: レシピ（filler > target）／**N の併記**（例「持続 3F 目ヒット」）／S。
- コントロール: **N_min**（既定 1）／**ソート切替**（N 順／手数順）。
- KA が NULL のコンボでは提案セクションを出さず、理由を明示する。
- **レイアウトの最終確定は中央経由**（§9.1）。本サブは既存構造への追加に留め、面の再設計をしない。

#### 4.6.2 採択→保存

**提案は自動確定しない**（FR307）。ユーザーが明示的に採択した場合のみ、**既存 API を再利用**して保存する。

**前提（DES-006 v1.20.0 §2.3 を現物確認）**:

| 検証 | 内容 | 重大度 | 本サブへの影響 |
|------|------|--------|---------------|
| **VAL-S05** | セットプレイ作成に**親コンボID（`parent_combo_id`）が必須**。単独作成は禁止 | ERROR | 採択保存では**必ず親コンボ ID を渡す** |
| **VAL-S04** | 同一キャラの**同じ親コンボに同一レシピ**のセットプレイが既に紐付いていないか（**名前を見ない**） | **ERROR＝ブロック** | 同一 target・同一 N の再採択は**同一レシピになり保存が失敗する**。§4.4 の `alreadyAdopted` で**事前に抑止**する |
| VAL-S06 | セットプレイ名が空でないか | ERROR | 自動生成名で満たす |
| VAL-S02 | レシピが空でないか | ERROR | 提案は必ず 1 手以上 |

> `setups.name` に **UNIQUE 制約はない**ため、名前重複による保存失敗は起きない。**実際の衝突点はレシピ一致（VAL-S04）**である。

**手順**:

1. `setups` を作成する。`name` は**自動生成**し、**保存前にユーザーが編集できる**ようにする（開発者確定 2026-07-24）。**VAL-S06（必須名）を満たすこと**。**名前の重複回避は実装しない**（UNIQUE が無いため不要）。
   - **書式**: `{target 表示名} 持続{N}F目重ね`（例: `鎖骨割り 持続4F目重ね`）。
   - **★生成は FE 側で行い、i18n キーから組み立てる**（ja/en parity・Playbook §4.13）。`name` は DB に保存される**データ**であり BE で日本語固定文字列を組むと英語ユーザーに日本語名が保存されるため、**FE の現在ロケールで生成 → ユーザーが編集 → create API へ渡す**構成とする。
     - ja: `{{move}} 持続{{n}}F目重ね`
     - en: `{{move}} meaty on active frame {{n}}`
   - 生成した名前はあくまで初期値であり、ユーザーが編集した場合はその値を保存する。
2. `setup_steps` に steps を**表示順で 1 ステップ 1 move** で格納（本サブでは filler と target のみ。modifiers への特記は行わない）。
3. `combo_setups` で元コンボへ紐付ける。**VAL-S05 のため親コンボ ID は必須**。
4. `recipe_cache` 等の既存機構は既存の流儀で再構築する。
5. **新テーブル・新列を作らない**。

**VAL-S04 に当たった場合の扱い**: `alreadyAdopted` により UI 側で事前に抑止するのが基本だが、競合等で保存が VAL-S04 で失敗した場合は、**エラーとして投げっぱなしにせず「このレシピは既にこのコンボに登録済みです」と利用者に分かる表示**にする（保存済みデータは壊さない）。

#### 4.6.3 提案の制約の告知（初回のみ自動表示・以降は明示操作）

**目的**: 本機能はフレーム計算のみで候補を導出するため、**実際には成立するセットプレイでも提案に出ないことがある**。「提案が出ない＝このコンボにセットプレイは無い」と誤解されると、利用者が有効な選択肢を捨ててしまう。**機能が万能でないことを最初に伝える**。

**表示仕様**:

- 提案セクションを**その利用者が初めて開いたときだけ自動表示**する（1 回のみ）。
- **2 回目以降は自動表示しない**。**注意アイコン（ⓘ／⚠ 等）を明示的に押したときのみ**表示する。
- 閉じる操作で消える。**提案を見るたびに出さない**（作業の邪魔をしない）。

**表示済みフラグの保持**:

- **DB 列を追加しない**（マイグレ禁止＝§2.2）。**クライアント側のローカル保持**（localStorage 等）で足りる。
- §3.3-7 の実査で**既存の「初回のみ表示」パターンがあればその流儀に合わせる**。無ければキーを 1 本置く（命名は既存規約に合わせる）。
- 保持に失敗した場合（ストレージ利用不可等）は、**毎回表示ではなく非表示に倒す**（アイコンからは常に読めるため情報は失われない）。

**文面（i18n・ja/en parity）**: 次の 3 点の趣旨を含める。実際の言い回しは §9.2（推測可）。

1. 提案は**フレーム計算のみ**で導出しており、**間合い・相手キャラの体格・ヒット時の状況は判定していない**。**必ず実機で確認**すること。
2. **提案が出なくても、成立するセットプレイが無いとは限らない**。
3. 現時点で**提案の対象外**となるもの＝有利フレーム未入力のコンボ／派生技・ラッシュ版・状態変種（`is_derived = true`）／空中技（`is_aerial = true`）／`active` 未入力の技。

> **★保守マーカー `M19-LIMITATION-NOTICE`（必須）**
>
> 上記 3 の内容は、**提案の制約に手を入れるたびに実態とズレる**（例: M19-02 で派生技が対象に入れば 3 の記述は古くなる）。文面と実装が離れた場所にあるため、更新漏れが構造的に起きやすい。したがって次を必須とする。
>
> - **`M19-LIMITATION-NOTICE`** という文字列を含むコメントを、**制約を決めている実装箇所すべて**と**ヒント文面の定義**に置く。
> - 対象（最低限 4 箇所）: (a) ヒント文面の i18n 定義（**ja / en 両方**）、(b) §4.2 の target 列挙規則、(c) §4.5 の filler 候補規則、(d) §4.3 の KA が NULL のときの扱い。
> - コメント本文に「**この制約を変更したらヒント文面（i18n `...limitations.*`）を同時に更新すること**」と、相互の参照先（ファイル・キー名）を書く。
> - これにより `grep -rn "M19-LIMITATION-NOTICE"` で**制約に関わる全箇所を一覧できる**。**DoD で grep 結果を報告させる**（§7.4）。

## 9. 注意事項・判断に迷ったら

### 9.1 推測で進めてはいけない事項

1. **提案 UI 面のレイアウト確定**。この面は **M18-03（マイリスト/登録導線）・followup E-1（F12-3・M23 の候補表示一本化）と交差**する。3 者が別々に触ると 1 本動線（E-20）が壊れる。**既存構造への追加に留め、面の再設計・既存要素の移動をしない**。判断が要る場合は開発者へ確認する。
2. **`moves` テーブルへの列追加**。派生技の由来判別・親参照は**中央帰属**であり、本サブで先回りして列を作らない。
3. **KA の意味論の再解釈**。KA＝無敵時間・起き上がり＝KA+1 は確定事項。実装中に疑義が生じても独自解釈しない。
4. **受理条件の式**。`==KA+1` へ変えるような「1 箇所調整」を行わない（それは N=1 固定であり、GC-5 を落とす）。§4.1.3 の帯を用いる。
5. **非攻撃技が target 候補へ混入しないか**。§3.3-2 で実査してから実装する（`active ≥ 1` で落ちない非攻撃技があれば追加除外条件を決める）。

### 9.2 推測で進めてよい事項（その旨を明示）

- 新規ファイルの配置・命名（既存構成に合わせる。判断を完了報告に記載）。
- エラーメッセージ・i18n キーの文言（ja/en 両ロケール parity を守る）。
- `setups.name` 自動生成のフォーマット詳細（VAL-S06 を満たす範囲で）。
- 空振り時硬直変動技を filler から除外しないこと（**既知割り切り**。完了報告に明記）。
- `MaxResults` の既定値の維持（変更する場合は根拠と実測を報告）。

### 9.3 不明事項発見時の対応

実装中に「設計が決めていない」事項を見つけた場合、**推測で実装せず**、完了報告の「要決定事項」に事実として記載する。特に **§4.2 の target 除外規則が実データで不都合**（有用な技が大量に落ちる等）と判明した場合は、件数の実数を添えて報告する。

### 9.4 実データ・実 UI での確認（E-11）

M19-RESEARCH-01 の PoC はクラウド seed（`combos`=0・`setups`=0）で実施したため、**実データ・実 UI 経路は未検証**である。「ロジックが正しく動く」と「機能が使える」は別（M17-E11）。本サブでは **実データを持つ環境で、実コンボから提案を出し、実 UI で採択→保存まで通す**ことを完了報告に含める。
