## 1. 背景と目的

### 1.1 背景——**復元は今、何も検証していない**

`M23-RESEARCH-01` 軸 H-4 が逐語で確定させた事実がある。

> `service.Restore` が呼んでいるのは 2 つだけである——`s.repo.Restore(ctx, tx, id)` と `s.notationSvc.RecomputeComboCache(ctx, tx, id)`。
> **`validation.` も `CalcRecipeHash` も `FindActivePublishedDuplicates` も呼んでいない。**
> **⇒ 復元は無条件に `deleted_at` を NULL に戻す。**

**★これ自体は不具合ではない。** 削除された行は編集経路から締め出されているため（軸 D-3）、**削除中に「自分の内容」が壊れることは無い。**

**★壊れうるのは「外部との関係」のほうである。**

### 1.2 ★★`M23-02` と `M23-03` が入ったことで、初めて壊れるようになった

**本サブの起票が `M23-03` の後に置かれているのは順序の都合ではない。前提が変わったからである。**

| いつ | 何が変わったか | 復元にとって何が起きるようになったか |
|---|---|---|
| **`M23-02`**（2026-08-20） | **セットプレイに論理削除・復元・完全削除が揃った** | **セットプレイが「削除済みだが行としては在る」状態を取りうるようになった。** それ以前は `DELETE` が中間表ごと物理削除しており、この状態は存在しなかった |
| **`M23-03`**（2026-08-22） | **参照側の `deleted_at` 除外の穴を塞いだ** | **削除済みのセットプレイは、コンボ詳細からも候補一覧からも出なくなった。** **⇒ 「紐付けは残っているのに画面には何も出ない」という形が成立する** |

**⇒ コンボを復元すると、紐付いていたセットプレイが全部ゴミ箱に居るせいで 0 件に見える、という状態が起こりうる。** **利用者から見れば「戻したのに戻っていない」である。**

**★この状態は `M23-03` の誤りではない。** 除外は正しい。**足りていないのは「戻したときに、戻りきっていないことを伝える手段」のほうである。**

### 1.3 ★既存の VAL コードが既に在る——**新設は最小限でよい**

**`DES-006` を実査した結果、本サブが必要とする検証の多くは既に定義されている。**

| 検証したいこと | 既存コード | 種類 |
|---|---|---|
| レシピ中の各ステップの `move_id` が該当キャラに存在する技か | **`VAL-C08`** | WARNING |
| セットプレイのレシピ中の `move_id` が該当キャラに存在する技か | **`VAL-S03`** | WARNING |
| `character_id` が存在するキャラクターか | **`VAL-D01`** | ERROR |

**⇒ 本サブの本体は「新しい検証を書くこと」ではなく、「既に在る検証を復元経路でも走らせ、結果を利用者へ届ける器を作ること」である。**

### 1.4 ★警告を載せる先は既に仕様が在る

**`DES-002` §4.2 に以下の 1 文が既にある**（第 1 版から在る記述であり、本サブが新設するものではない）。

> HTTPステータスコードは慣例に従う（4xx：クライアント起因、5xx：サーバー起因）。**バリデーション警告はエラーではなく `200 OK` のレスポンスボディに `warnings` フィールドとして含める。**

**★ただし、この `warnings` が実装として在るかは設計卓には見えない**（武装のため実装ソースを読めない）。**⇒ §3.3-1 の実査項目にしてある。** **在れば従う。無ければ本サブが最初の実装者になる。**

### 1.5 目的

1. **`POST /api/combos/{id}/restore` と `POST /api/setups/{id}/restore` の成功応答に、警告を載せる。**
2. **既存の `VAL-C08` / `VAL-S03` を復元経路でも走らせる。**
3. **復元特有の検証 `VAL-R01` / `VAL-R02` を新設する。**
4. **★作らないと決めた検証を、決めた理由付きで記録する**（§4.5）。**「検討していない」と「検討して作らないと決めた」を区別できる形で残す。**
5. **`DES-006` へ復元時バリデーションの節を新設し、`DES-002` §4.2 の持ち越し 1 件を決着させる。**

## 4. 詳細仕様

### 4.1 ★★原則——**復元は止めない**

**`M23-overview` §4.1 と `D-463` で確定済みの方針である。**

> **落とすと利用者は取り返す手段を失い、ゴミ箱が安全網でなくなる。**

**⇒ 本サブが足す検証は、種類が ERROR のものも含めて、復元を中止させない。**

| 検証の種類 | 通常の登録・更新経路 | **復元経路（本サブ）** |
|---|---|---|
| WARNING | 保存続行・警告表示 | **同じ。復元続行・警告を返す** |
| **ERROR** | **保存中止** | **★復元は続行する。警告として返す** |

**★これは `DES-006` §1.1 の「例外はブロッキング」に対する明示的な例外である。** **⇒ `DES-006` の新設節に、例外であることを書く**（設計卓が `CHANGE-124` で反映する）。**書かないと、後から「ERROR なのに止めていない」を不具合として直されうる。**

**★ただし「復元そのものが成立しない」ケースは従来どおり `404` である**（削除済みでない行の復元＝`DES-002` §4.2）。**これは検証ではなく前提条件であり、本サブは触らない。**

### 4.2 ★検証を走らせる位置——**復元と同じトランザクションの内側**

**`M23-02` が前チェックを Tx の外から内へ移した先例がある**（契約違反 2 件のうち 1 件・開発者承認済み）。**同じ理由が本サブにも当たる。**

- **Tx の外で検証すると、判定してから復元するまでの間に別の利用者が状態を変えうる**（TOCTOU）。
- **★本サブの検証は「復元を止めない」ため、TOCTOU が起きても壊れるのは警告の正しさだけである。** **⇒ 危険度は低い。それでも Tx の内側に置くほうが安い**（すでに Tx が張られており、外へ出す理由が無い）。

**⇒ `BeginTx` → `repo.Restore` → `Recompute...` → **検証** → `Commit` の順に置く。**

**★検証が失敗した（検証処理自体がエラーを返した）場合の扱い**——**復元は成功させ、警告は「検証できなかった」ものとして扱わず、`500` も返さない。** **★ログには残す。** 理由＝**検証は付加価値であり、それが壊れたことで復元という利用者の主目的を巻き添えにしない。**

### 4.3 ★応答の形

**★§3.3-1 で既存の形が見つかった場合はそれに従う。以下は見つからなかった場合の形である。**

```json
{
  "id": 42,
  "characterId": 3,
  "...": "（復元後に取得し直したコンボ表現。既存のまま）",
  "warnings": [
    {
      "code": "VAL-R01",
      "message": "（翻訳キー経由の文言）",
      "details": { "setups": [ { "id": 7, "name": "..." } ] }
    }
  ]
}
```

**★守ること 4 点。**

1. **キーは camelCase**（`CLAUDE.md` §4）。**`warnings` は既に camelCase である。**
2. **警告が 0 件のときは `warnings` を出さない**（`omitempty`）。**★空配列を返すと、フロント側が「警告があった」と誤って分岐しうる。**
3. **`details` の形は `M23-02` の `409 setup_in_use` に揃える**——**同サブは `details.combos` に `{id, memo}` の配列を返している。** **⇒ 本サブも「どれが問題なのか」を id 付きで返す。** **★新しい見せ方を作らない**（**D-417**）。
4. **`message` は翻訳キー経由**（`DES-006` §11.3）。**★サーバ側で日本語の文面を組み立てて返すのか、コードだけ返してフロントで組み立てるのかは、§3.3-1 で見つかった既存の形に揃えること。** **見つからなければコードとパラメータを返し、文面はフロントで組む**（`M17-05a` の「VAL エラーは FE 表示層で日本語化」＝`DES-006` §6 の先例）。

### 4.4 ★画面での見せ方

**`DES-006` §11.1 が既に規定している。**

> 保存時にサーバーから返された警告は、保存完了トーストと一緒に画面に表示

**⇒ ゴミ箱画面で復元したときも同じ形にする。** **★モーダルにしない**（§11.2 の ERROR の見せ方であり、本サブの警告は ERROR ではない）。

**★一括復元のときの扱いを決めること。**

| 状況 | 扱い |
|---|---|
| 1 件の復元 | **その 1 件の警告を出す** |
| **一括復元で複数件に警告が付いた** | **★件数を畳んで出す**（「3 件を復元しました。うち 2 件に注意があります」）。**★1 件ずつトーストを積み上げない**——**選択が 20 件のときトーストが 20 枚出る** |

**★既存の一括操作の失敗表示に倣うこと**——`TrashBulkActions` は一部失敗時に `role="alert"` を出す形を既に持っている（`M23-RESEARCH-01` A-3）。**同じ置き場を使えるなら使う。**

### 4.5 ★★作らないと決めた検証 3 件——**理由付きで記録する**

**`M23-overview` §4.7 は「削除中に世界が変わる」例を 4 つ挙げている。実査の結果、そのうち 3 つには検証を作らない。** **★これは手抜きではなく判断であり、根拠を残す。**

#### 4.5-1 `recipe_cache` が現在の表記規則と食い違う → **作らない。既に解決済み**

**復元は `RecomputeComboCache` を呼んでいる**（`M23-RESEARCH-01` D-1 の逐語）。**⇒ 復元した時点で現在のプリセット・エイリアスで作り直されている。食い違いは発生しない。**

**★`architecture-patterns` §11 の判断表で言えば段 4**（どちらでも実挙動が変わらない）。

#### 4.5-2 技の改名・削除 → **作らない見込み。ただし §3.3-4 で確かめる**

**`moves` / `characters` は seed 由来のマスタデータであり、アプリの操作で消える経路が無い見込みである。** **⇒ 「削除中に技が消える」は起こりえない。**

**★起こりえないことに対する検証を書かない**（**E-117** の型＝在るはずのものを作る／無いはずのものを守る）。

**★ただし `VAL-C08` / `VAL-S03` は走らせる。** 理由が違う——**これは「削除中に消えた」を見るためではなく、「そもそも登録時から不整合だった行が、検証の緩かった経路（CSV 取込・API 直叩き）で入っていた」場合に気づくためである。** **走らせるコストはほぼ 0 であり、判定の母集団も変わらない。**

#### 4.5-3 `superseded_by_combo_id` を持つ旧行の復元 → **作らない**

**`DES-002` §4.2 が本サブへ持ち越していた 1 件である。**

> **★`superseded_by_combo_id` にも触れない**〔印を持つ旧行でも id を直接叩けば復元できる。画面から到達できないため利用者操作では起こらない。**判断は `M23-04`**〕

**★裁定＝検証を作らない。** 根拠 2 つ。

1. **旧行はゴミ箱の一覧に出ない**（`M23-01` の as-built＝述語はゴミ箱の絞り込みに足された）。**⇒ 一括復元でも選べない。利用者操作では到達しない。**
2. **仮に API を直接叩いて復元しても、壊れる不変条件が無い。** **`PUT` は重複判定キーを変える操作であるため、旧行と新行のキーは通常異なる**（`M23-RESEARCH-01` H-5 の注記）。**⇒ 復元しても重複にならない。** **2 つの版が並ぶだけであり、それは利用者が望んで叩いた結果である。**

**⇒ 段 4。★`DES-002` の持ち越しは「`M23-04` で判断し、作らないと決めた」として閉じる**（設計卓が `CHANGE-124` で反映する）。

**★falsifier は §3.3-3 である**——**旧行がゴミ箱の一覧に出るなら根拠 1 が崩れる。その場合は実装を進めずに報告すること。**

#### 4.5-4 タグの紐付けが消えている → **作れない。作れないことを記録する**

**`combo_tags` は `ON DELETE CASCADE` である**（`M23-overview` §4.7）。**⇒ タグを削除した時点で `combo_tags` の行が消えており、復元の時点では「そこに何が紐付いていたか」の情報がどこにも残っていない。**

**★検証を作りようが無い。** 「消えたタグがあった」ことを検出するには、消える前の記録が要る——**それは監査ログであり、`FR013` の凍結対象である**（`M23-overview` §4.1）。

**⇒ 本サブでは作らない。★「検討していない」ではなく「検討して、作れないと結論した」として `DES-006` の新設節に 1 行残す**（設計卓が反映する）。**残さないと、次に同じ問いが来たときにまた同じ調査をする。**

### 4.6 マイグレーション——**1 本も消費しない**

**本サブはスキーマを変更しない。** **★`docs/process/parallel-board.md` §2.2 の連番は動かない。**

**★もし「これは列が要る」と判断した場合は、実装を進めずに報告すること**（§9.1）。**スキーマ変更は開発者の承認事項である**（`CLAUDE.md` §10）。

### 4.7 新設する VAL コード——**2 件**

**★採番は設計卓が行った**（`M22-08` の `VAL-N05` と同じ形）。**`VAL-R` は復元（Restore）の接頭辞であり、本サブが最初の消費者である。**

| ID | 検証内容 | 種類 | 適用経路 |
|---|---|---|---|
| **`VAL-R01`** | **復元するコンボが紐付けているセットプレイに、論理削除されたものが含まれる** | **WARNING** | `POST /api/combos/{id}/restore` |
| **`VAL-R02`** | **復元するセットプレイが紐付いている親コンボが、すべて論理削除されている** | **WARNING** | `POST /api/setups/{id}/restore` |

**★`VAL-R01` と `VAL-R02` で条件が非対称であることに注意すること。**

- **`VAL-R01` は「1 件でも削除済みが含まれる」で発火する**——**コンボ詳細のセットプレイ欄が、期待より少なく見えるためである。**
- **`VAL-R02` は「すべて削除済み」で発火する**——**セットプレイは親コンボ経由でしか画面に出ない**（`VAL-S05`＝親に紐付かない単独作成は禁止）。**⇒ 生きた親が 1 つでも残っている場合は、そこから見える。0 個のときだけ「戻したのにどこにも出ない」になる。**

**★この非対称は意図的である。揃えないこと。** **`architecture-patterns` §11 の「機能ごとに出すか出さないかを決める」と同じ形であり、揃えること自体が無償ではない**（**D-494**）。

**★`VAL-R03` 以降は未採番である。** **§3.3 の実査で `VAL-R01` / `VAL-R02` のどちらかが成立しないと分かった場合、その番号は `DES-006` へ載せずに未採番のまま残す**（欠番にしない）。**★`VAL-P06` は「載せた後に廃止した」ため再利用していないが、本件は「載せなかった」であり性質が違う。**

### 4.8 ★否定形確認——**本サブは「作らない」を 4 件持つ**

**完了報告に、以下 4 件を「作らなかったこと」として明記すること。**

| 2 | 技・キャラの消失の検証 | 4.5-2（起こりえない） |
