## 1. エンジン仕様（窓方式の実装形・確定案）

**受理帯方式（案 B）を推奨・確定案とする。**

- 予算: `budget_max = KA + 2 − NMin − target.Startup`。受理条件を現行の `remaining == 0` から **`0 ≤ remaining ≤ target.Active − NMin`** へ広げる（1 箇所変更）。受理時 `N = KA + 2 − (Σfiller.total + target.Startup)`。
- 反復深化・少手数優先・枝刈り・sanitize は現行のまま生きる。計算量は現行同等（受理判定の緩和のみ）。同一 filler 集合の重複列挙は構造的に発生しない。
- 対抗案 A（RESEARCH-02 ハーネス方式＝S を窓範囲で外側走査し既存 exact-match を反復呼び出し）はエンジン無改変で実証済みだが、呼び出しが active 段倍・重複解のデデュープが要るため、**移植（internal/ 化）と同時に案 B を採る**。

**API 変更**:

```go
type Target struct { Name string; Startup int; Active int }   // Active 追加
type Options struct { AllowRepeat bool; MaxFillers int; MaxResults int; NMin int } // NMin 追加（DefaultOptions で 1）
type Suggestion struct { Fillers []Move; Target Target; TotalFrames int /* =S */; HitActiveFrame int /* =N */ }
```

- `Target.Active < 1` → 新エラー `ErrInvalidTargetActive`（moves.active NULL の技はグルーが事前除外するのが原則、エンジンは防御）。
- `NMin > Target.Active` → エラーではなく**空結果**（N_min は絞り込み設定であり不正入力ではない＝確定事項 3）。`NMin < 1` は 1 に丸める。
- `Suggestion.TotalFrames` の意味が「常に KA」から「S（第 1 active の絶対フレーム）」に変わる点は破壊的変更として INTAKE/テストへ明記。
- エンジンは引き続き派生概念・DB・code 体系を持たない（不透明 Name と数値の素通し）。**セーフジャンプ用に第 2 受理規則を後付けできる形**（§9）だけ関数分割で確保する。

**品質根拠**: 窓方式 N_min=1 で golden-case は GC-1/3/4/5 成立（RESEARCH-02 実測）＋ GC-2 は訂正後レシピで S=42・N=3＝成立見込み。**5/5**。本実装時に GC-2 を含む 5 件の再実測を DoD に入れる（M19-DESIGN-04）。

## 2. target（当てたい技）の列挙規則（MVP 確定案）

target 候補 = 当該キャラの moves のうち、`startup ≥ 1` かつ `active ≥ 1` かつ次のいずれか:

1. `startup_basis = standalone`（相当）かつ**親参照なし**＝単独入力で出せる技。中央スキーマ確定までの暫定判定は `is_derived = false`（DES-003 判定原理「いきなり出せるか」による保守側ゲート。中央確定後は親参照導出が一次で、is_derived への依存は解消する）。
2. `startup_basis = through`（相当）＝通し値の派生技・ジャンプ入力起点の必殺技等。**通し値をそのまま `Target.Startup` に渡す**（親は計上しない）。

除外: `unknown`（判別未了・警告つき除外）／`standalone ∧ 親参照あり`（パターン 3・5・6＝単独入力不可）／状態変種（親参照なしだが is_derived=true＝MVP は保守側で除外・将来拡張枠）／`is_aerial = true`（C 型ジャンプ攻撃＝着弾可変でスカラー S 非対応）／**B 型 air-only 技**（人手除外マーキング・M19-DESIGN-01 §3-8）。非攻撃技（damage=0 のパリィ・魔身等）の除外基準は M19-01 実装時に確定（小残件・§10）。投げは golden-case GC-3 で target 実績があるため**含める**。列名・判別手段は中央スキーマ確定に依存（M19-DESIGN-01 R4・R7）。中央確定までの暫定 PoC は「golden-case の技を明示指定」で回避可能。

## 3. 計上規則と表記展開（二重計上問題の解・確定案）

- **計上**: `S = Σ(filler.total) + target.Startup`。through の target の直前に親ステップが表記されても**親は計上ゼロ**（R1）。through の技を **filler** に使う場合は通し `total`（例: 紫電 51）で計上可（同一規約で整合）。
- **表記展開（グルーの責務）**: エンジン解の target が through で**表記用親 move を持つ**場合、表示・保存時に親ステップを直前挿入する（例: 解 `[立ち弱P] > 紫電` → 表記 `立ち弱P > 奮迅脚 > 紫電カカト落とし`）。親がコマンド表の技でない場合（無影蹴のジャンプ）は展開しない。親特定は中央スキーマの親参照（R3）を引く。**表記展開は role 非依存（v1.0.1）**: through の技を filler（空振り）に使う解でも同じ規則で親ステップを前置し、計上は通し `total` 1 つ（前置親は計上ゼロ）。R6 の整合性検証も role 非依存に適用する。エンジンは探索後展開のため影響なし。
- **格納**: `setup_steps` は現行どおり 1 ステップ 1 move で**展開後の表記順**に格納（親行を含む 3 行）。modifiers への特記は不要——「through の子の直前に位置する親行は計上ゼロ」という決定論の規約で再計算可能（セットプレイは最速派生原則のため曖昧性がない）。手入力レシピで親なし子が現れた場合は R6 の検証で警告（保存はブロックしない＝FR305 系）。

## 4. `N_min` の持ち方（確定案）

- **MVP: リクエスト単位パラメータ**（`Options.NMin`・既定 1・UI から指定）。品質評価は常に N_min=1（確定事項 3）。
- **将来**: 技固有属性（「持続何 F 目以降ならコンボになるか」）へ拡張余地を残す。実効値は `max(リクエスト NMin, 技属性)` で合成すれば API 非破壊。機械導出は現データでは不可（per-active-frame 有利フレーム不在・on_hit 充足 39%＝RESEARCH-02 R-F）のため、導入するなら人手付与列（中央マター・今回は要求しない）。

## 5. filler（空振り技）候補の規則

- 基本: `total ≥ 1` の技（エンジン sanitize と整合）。through の技も通し total で参加可。
- `moves.setup_only`（予約列・seed 0 件）は「filler 候補を実用技に絞る」ユーザー付与フィルタとして**活用を開始**する（ON 行が 1 件以上あるキャラはそれのみ、0 件なら全技＝graceful）。付与運用は開発者に委ねる。
- 空振り時硬直変動技（DES-003 §3.3 注記「空振り時硬直 N フレーム増加は total 非算入」）は total が実挙動とズレるため、**raw_data/notes に当該注記を持つ技を filler から除外しない**が提案理由の注記対象とする（MVP は非対応・既知割り切りを DoD に明記）。

## 6. ランキング（確定案）

第 1 キー: **N 降順**（SF6 は後 active ほどヒット時有利が増えるため、深い持続で当たる解ほど実用価値が高い＝N_min 要件と同じ動機）。第 2 キー: 手数昇順（少手数優先＝入力簡単）。第 3 キー: Σtotal 昇順・Name 昇順（決定論）。エンジンは少手数順で列挙し（現行維持）、**並べ替えはグルーが行う**。UI にソート切替（N 順／手数順）を持たせる（§8）。

## 7. 提案 DTO と採択→保存の写像（確定案）

```
SuggestionDTO {
  steps: [ { moveId, code, role: "filler"|"parent"|"target", counted: bool } ],  // 表記展開後・表示順
  s: int, n: int, landing: int /* = KA+1 */, targetActive: int,
  alreadyAdopted: bool  // v1.0.1: 既存 setups とのレシピ一致（VAL-S04 と同じ基準）照合結果
}
```

`setups.name` に一意制約はない（code-facts DDL 現物確認）ため名前衝突では保存失敗しないが、**実衝突点はレシピ一致（VAL-S04）**＝同一 target・同一 N の再採択は同一レシピになる。`alreadyAdopted` で UI が採択済みを事前表示する。作成経路で VAL-S04 がブロックか警告かは指示書化時に DES-006 §6 の中央配布版で確認（M19-DESIGN-04 §3 へ登録）。

採択時: 既存 API 再利用（新テーブルなし）。`setups` を作成（name 自動生成案: 「{target 表示名} 重ね (N={n})」・VAL-S06 の必須名を満たす・ユーザー編集可）→ `setup_steps` に steps を表記順で格納（parent 行含む・modifiers なし）→ `combo_setups` で元コンボへ紐付け。`recipe_cache` は既存機構で再構築。生の提案リストは非永続（M19-overview §2.x）。

## 8. 提案 UI の整合方針（確定・面の詳細は中央経由調整）

単一コンボ候補面（DES-005 §5.6 項目 11／`SetupSelectorModal`）へ相乗り。表示: 展開後レシピ＋ **N の併記**（例「持続 3F 目ヒット」）・N_min コントロール（既定 1）・ソート切替（§6）。`selectedIds` は入口にしない。E-1（M23）統合先・M18-03 マイリスト導線と面が交差するため、**この面のレイアウト確定は中央経由**・E-14 突合ゲートを本実装 DoD に予約（M19-overview §5）。through target の行には「派生技（親＞子表記）」であることを示す注記を出す（DTO の role で描画可能・moves API への is_derived 露出には依存しない）。

## 9. セーフジャンプ（第 2 受理規則・設計予約＝MVP 実装外）

開発者確定の検出モデル: セーフジャンプは「特定の有利フレームでジャンプ（または A 型技）入力」で成立し、キャラ×ジャンプ変種ごとの**定数 1 個**（例: ディージェイ 42F）に畳める。エンジンには `Σ(filler.total) == KA − C` の**完全一致探索**（現行 exact-match と同型）を第 2 受理規則として後付けする。必要データ＝「キャラ×変種ごとの成立有利フレーム定数」（人手入力）と、並行マイルストーンで整備中のジャンプ/ダッシュフレームの器。**M19 は消費側**であり、データ形が見えた時点で開発者と詰める（未決事項として M19-DESIGN-04 に登録）。なお A 型（無影蹴等・through かつ自己完結）は通常の窓方式 target としてそのまま扱える（追加設計ゼロ）。

**定数 C の基準点（v1.0.1・1F ズレ防止）**: filler 列が絶対フレーム 1〜Σtotal を占め、ジャンプ（または A 型技）の入力は **Σtotal+1 フレーム目**——R1 の「入力フレーム＝1」連結規約と同一。`C ≡ KA − Σ(filler.total)`＝**入力時点で残っている有利フレーム数**と定義し、成立条件は `Σ(filler.total) == KA − C`。開発者の実測の与え方（「42F 有利でジャンプ」→ C=42）とそのまま一致する。導入時は開発者実測の golden 1 件（ディージェイ等）で ±1F 較正することを DoD とする。
