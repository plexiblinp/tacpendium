## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### ★1-1 `P-04` の記述は片側だけである。**`PRAGMA foreign_keys = 1` を返す接続を引く場合がある**（実測）

`SUPP-001` §7.3 と指示書 §3.3-7 は「`PRAGMA foreign_keys` が接続プール全体に効いていない」とする。**この記述は正しいが、そこから「FK は効かない」と読むのは誤りである。**

**実測（2026-08-13・`internal/testutil/dbtest` 上）**:

| 観測 | 内容 |
|---|---|
| `PRAGMA foreign_keys` | **`1` を返す接続を引いた**（`internal/service/preset/service_test.go` の `Test_Delete_LeavesNoOrphanAliases` が `t.Logf` で出力する） |
| `ON DELETE CASCADE` | その接続では**実際に発火する** |
| `presets.user_id → users(id)` の FK | **発火する**。実在しない `user_id` での `INSERT` が `FOREIGN KEY constraint failed (787)` で落ちた |

**⇒ 帰結が 2 つある。**

1. **「削除後に孤児行 0 件」の観測だけでは、CASCADE に頼っていないことを主張できない。** FK=ON の接続を引けば CASCADE が子行を消すため、**CASCADE 依存の実装でもテストが緑になる。** 指示書 §5 (g)・チェックリスト §8-4 が求めた検査は、**そのままでは主張が成立しない種類のもの**だった。⇒ `Test_Delete_DeletesChildrenExplicitly`（`service_test.go`）を足し、**サービス層が「子行 → 親」の順で明示削除していることを呼び出し順で固定**した。
2. **カスタムプリセットの作成は `users` に `id = 1` の行が実在することに依存する。** 同行はマイグレ `000007_seed_initial_tags_user1` が `INSERT OR IGNORE INTO users (id, name) VALUES (1, 'default')` で投入している。**`tags` も同じ構造の FK を持っており既存機能と同条件**だが、**P-04 が「FK は効かない」と読まれているとこの依存が見えない。**

> **⇒ `SUPP-001` §7.3 に「接続単位であるため、効く接続と効かない接続が混在する」旨と、上記 1 の検査上の帰結を明文化してほしい。** 「効かない」とだけ書かれていると、**次の担当が孤児件数の観測だけで CASCADE 非依存を主張してしまう。**

## §2 契約・設計に反する独自判断

### ★2-1 指示書 §4.2 に無い**公開 API を 1 本新設した**（`GET /api/presets/:id/aliases`）

**何に反したか**: 指示書 §4.2 は書き込み 3 本（`POST` / `PUT` / `DELETE`）のみを挙げ、`CHANGE-101` §2.2 も e/f/g の 3 本しか挙げていない。

**なぜそう判断したか**: **編集画面（`DES-005` §5.11「エイリアス一覧、技ごと、キャラ別にグループ化、編集可能」）を実装する手段が 1 つも無かった。** `GET /api/presets/:id` はプリセットのメタ情報（`id` / `code` / `name` / `basePresetCode` / `isBuiltin` / `userId`）しか返さない。指示書 §2.1 は「本表は予見できた範囲であって禁止列ではない」（**D-348**）とし、§2.2 の禁止列にも当たらないため追加した。

**実装がどうなっているか**: `internal/api/preset/routes.go:16` ／ `handler.go` の `ListAliases`。

```
GET /api/presets/:id/aliases?character_id=N[&limit=M]
→ [{ moveId, moveCode, moveCategory, characterId, aliasText, aliasTextEn?, officialAliasText? }]
```

- **`character_id` は必須**。1 プリセットのエイリアスは最大 **1,653 行**あり、全件を 1 応答で返すべきではない。欠落・不正は 400。
- `limit` は一覧画面のサンプル表記プレビュー用（4 件）。
- **`officialAliasText` は `official_ja_move` の同 move のエイリアス（公式技名）。** `moves` に技の表示名カラムが無いため（`SUPP-001` §7.3）、**記法プリセット（`numeric` / `srk`）の編集画面で「どの技の欄か」を判別する唯一の手掛かりになる。**

> **⇒ 親の裁定**: 受理して `DES-002` §4 と `CHANGE-101` §2.2 へ 1 行足すか、別の実現手段（例＝`GET /api/presets/:id` の応答に含める）へ差し戻すか。**後者は §5 (j) の「既存 2 本は不変」と衝突する。**

### ★2-2 `DES-005` §5.10 の表示項目「**作成日**」を実装しなかった

**何に反したか**: `DES-005` §5.10 の表示項目 2「カスタムプリセット一覧（名称、ベースプリセット名、**作成日**）」。

**なぜそう判断したか**: **`presets` テーブルに `created_at` が存在しない。** `migrations/000001_init_schema.up.sql:131-138` の DDL は 6 列のみで、**`DES-003` §3.8 にもタイムスタンプ列の定義が無い**（`internal/model/preset.go` のコメントが明記している）。列追加にはマイグレが要るが、**(a) 自採番しない**（**D-293**）**(b) `CHANGE-101` §1 が「スキーマを変えない」ことを非破壊性の根拠にしている。**

**実装がどうなっているか**: `web/src/features/preset/components/PresetListTable.tsx:27-30` に理由をコメントで明記した上で、当該列を出していない。

> **⇒ 親の裁定**: `DES-005` §5.10 から「作成日」を落とすか、**`presets` へ `created_at` を足すマイグレを払い出して将来対応とするか。** 後者なら `DES-003` §3.8 の改訂も伴う。

### ★2-3 `DES-004` §5.7-2「**直接 INSERT する経路を増やさない**」から逸脱し、代わりに検査をサービス層へ足した

**何に反したか**: `DES-004` §5.7-2（`CHANGE-100`・M20-03 で確定）。同項は「既存の生成器を通す。直接 INSERT する経路を増やさない」を義務づけ、理由を **D-317 の交差条件**（ある技の `alias_text` が、別の技の `alias_text_en` と一致する）が **DB では守れず検査に残る**ためとしている。

**なぜそう判断したか**: **利用者がエイリアスを編集する経路を作らないと、本サブ（`DES-005` §5.11）が成立しない。** 生成器は seed 投入のための仕組みであり、利用者の任意入力を通せない。

**実装がどうなっているか**: 新設した 2 経路の性質が違う。

| 経路 | 交差条件への影響 |
|---|---|
| **コピー**（`copyAliasesSQL`） | ベース行を verbatim 複製するため交差条件はコピー元と同一。**安全** |
| **編集**（`updateAliasTextSQL`） | **利用者が任意の文字列を入れられる。** 当初は `UNIQUE(preset_id, character_id, alias_text)` にも部分インデックスにも当たらず、**DB でもサービス層でも検出されない状態だった**（レビュー指摘 D で顕在化） |

⇒ **サービス層に交差検査を足して塞いだ**——`FindCrossingAliasEn`（`internal/repository/preset/`）＋ `Update` の事前検査 → `ErrAliasConflict`（409）。`Test_Update_RejectsCrossingWithAliasTextEn` が固定する。

> **⇒ 親の裁定**: **`DES-004` §5.7 の規約は「生成器を通す経路」だけを想定して書かれている。** seed 経路は `migrate_m2003_test.go` (g) が守っていたが、**利用者編集の経路には誰も検査を置いていなかった。** 同節へ「利用者編集の経路も交差検査を課す」旨を足すか、規約の適用範囲を「seed 投入経路に限る」と明示するかの判断が要る。

> **★実測で分かったこと**: `alias_text_en` が入るのは `micro_forward` / `micro_back` の 2 code だけであり、**その値は汎用語で、全キャラで同一の文字列である**（「back microwalk」等）。したがって **「別キャラなら同じ文字列を入れてよい」は成立しない**——別キャラへ入れるのも本物の交差である。

## §7 教訓（retrospective 行き）

> **★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映であり、実施者は設計担当（反映担当の廃止＝2026-08-11）。

1. **「観測できた」と「主張できた」は違う。検査が何を根拠に緑になっているかを、検査自身に書かせる。**
   本サブは「削除後に孤児 0 件」を観測できたが、**FK=ON の接続を引いていたため CASCADE が消していた可能性を排除できていなかった。** 同じ観測が、正しい実装でも誤った実装でも緑になる。⇒ **テストのコメントへ「このテストだけでは主張しきれない」と自ら書き、実装の形（呼び出し順）を固定する 2 本目を足す**形にした。**「検査を書いた」で止めず「その検査は何を排除できないか」を書くと、次の担当が穴を継がない。**（M20-01 §1-2「契約テストは書いただけでは効かない」の続き）

2. **「効かない」と書かれた既知課題は、「効く場合がある」を隠す。**
   `P-04` は「`PRAGMA foreign_keys` がプール全体に効いていない」と記録されており、**そこから「FK は効かない」と読める。** 実測では効く接続を引く場合があり、**CASCADE も `users` への FK も発火した。** ⇒ **接続単位・環境依存の性質を持つ既知課題は、「効かない」ではなく「混在する」と書く。** 前者は検査の設計を誤らせる。

3. **失効記述の走査は、キーワードだけでは足りない。「実在性の反転」を起点に探す。**
   指示書 §4.8 の 4 キーワードによる走査は**残骸 0 件**だったが、**実際には 5 箇所が失効していた**（`Header` / `HomePage` / 設定 / i18n キー / `model` のコメント）。いずれも「未実装である」という**実在性の主張**であり、キーワードでは当たらない。⇒ **「本サブが何を実在させたか」を起点に、その反対（『まだ無い』と言っている箇所）を全文走査する。** ルート名・機能名で grep すれば当たる。

4. **到達不能になった分岐は、消すか、動かせる形にするかの二択である。**
   `Header` の `disabled` 分岐は、最後の利用者を有効化した時点で到達不能になった。**`NAV_LINKS` がモジュールスコープの const であるため、テストから注入して動かす手段が無い。** 残せば「未実装リンクを置ける」という**検証されていない前提**が引き継がれる。⇒ **「将来使うかもしれない」で残す判断は、動かせる形（注入可能）にできるときだけ有効である。**

5. **「開発者手番」と書いた項目は、手順まで書いて初めて手番になる。**
   本サブは当初、完了報告 §9 に「`go run ./cmd/combomgr` で起動しての実機 1 周」と 1 行だけ書いていた。**手順を書こうとして実査したら、そのコマンドでは画面が出ないことが分かった**（`WebEmbedded = false`）。**指示書の DoD をそのまま写しただけでは、実行できない依頼を渡すことになる。** ⇒ **他人へ渡す手順は、渡す側が一度は経路を実査する。** 「§7.2 に書いてあるとおり」で済ませない。

6. **同じ落とし穴が記録済みでも、記録は踏むことを止めない。手順の中へ埋めて初めて効く。**
   `config.toml` 焼き付き（progress-log 4085）は**機序も対処案も記録済み**で、**3 回空振りさせた前科まで書かれていた**が、**本サブの実査でその状態がそのまま再現していた**。⇒ **「記録した」は「防いだ」ではない。** 防ぐには (a) 根治する か (b) **次に踏む人が必ず読む手順の第 0 手へ入れる** のどちらかが要る。本サブは (b) を採った（根治は他ドメインでスコープ外）。**`check-*.sh` を新設する運用が定着しているのは、同じ理屈である。**

7. **設計書の「投入経路の規約」は、書かれた時点で想定していた経路の集合を持つ。新しい種類の経路を作るサブは、規約がそれを含むかを明示的に確かめる。**
   `DES-004` §5.7 は「生成器を通す」を義務づけたが、**書かれた時点で存在したのは seed 投入経路だけだった。** M20-04 が作った**利用者編集の経路**は規約の想定外であり、**D-317 の交差条件を誰も検査しない状態になっていた**（レビューが検出）。⇒ **規約に従えないときは「逸脱した」と報告するだけでなく、規約が守ろうとしていた不変条件を別の場所で守る。** 「経路を増やすな」の目的は経路の本数ではなく不変条件である。
