## 発見 1【要修正】`expectedMovesDelta` を削除すると、**現在 green の 1403c が red になる**

### 1.1 事象

裁定 §2.2 #1 は「`TestRun_M1403d_OtherCharsUnaffected` は区間を変えず、**`expectedMovesDelta{"zangief": 3}` を削除する**」としている。**しかしこの map は 1403d 専用ではない。参照元が 2 つある。**

| 参照元 | 比較区間 | 現在 | **delta 削除後** |
|---|---|:--:|:--:|
| `migrate_m1403d_test.go:202`（`TestRun_M1403d_OtherCharsUnaffected`） | **v42 → v48** | **red** | **green**（`000051` は区間外なので delta 不要） |
| **`migrate_m1403c_test.go:148`（`TestRun_M1403c_OtherCharsUnaffected`）** | **v28 → `m.Up()`＝HEAD** | **green** | **★red になる** |

map の定義は **`migrate_m1403c_test.go:162`** にあり、コメント（`:159`）も「**v28/v42 以降の波が**…」と**両方の区間**を指している。**1403c は HEAD 終端なので `000051` を区間内に含み、delta の +3 があるおかげで現在 green** である。

### 1.2 実証（推論ではない）

**`"zangief": 3` を一時削除して実行した。**

```
    migrate_m1403c_test.go:154: zangief が変化: v28 → HEAD で moves=87 aliases=87 を期待したが moves=90 aliases=90(他キャラ波及)
--- FAIL: TestRun_M1403c_OtherCharsUnaffected (1.56s)
--- PASS: TestRun_M1403d_OtherCharsUnaffected (0.84s)
```

**⇒ 裁定 §2.2 を字面どおり実行すると、1403d が green になる代わりに 1403c が red になる。差し引きゼロで、red は解消しない。**

（実証後は即座に復元し、`git status --porcelain` が空・red が元の 3 件であることを確認済み。）

### 1.3 是正案 —**裁定の規約を 1 か所へ追加適用するだけで解ける**

**`TestRun_M1403c_OtherCharsUnaffected` も自サブ区間へ閉じる＝`v28 → v30`。**

M14-03c が消費した連番は **`000029` + `000030`** である（根拠＝同ファイル `:56` のコメント「**`000029+000030` の up 契約を検証する**」）。閉じれば `000051` が区間外になり、**`expectedMovesDelta` は 2 か所とも不要になって map ごと削除できる**。

**裁定 §2.4 の「表が要らなくなるのは、問題が消えたからである」が、1403c まで含めて成立する。**

### 1.4 是正案の実証 — **`go test ./...` が全パッケージ green になった**

裁定 §2.2 の 3 件に**発見 1 の 1403c を加えた 4 か所**へパッチを当てて実行した。

### 1.5 なぜ見落とされたか（再発防止のため）

**これは M14-03d 設計伝達レポート §4 の教訓「件数前提テストの洗い出しは grep だけでは漏れる。必ず全体実行で確定させる」が、そのまま再発したものである。**

裁定は **failing している 3 件だけ**を見て #1 を書いており、**`expectedMovesDelta` の参照元を grep していない**。**そして製造も、M19-04b の §4-1 で同じ見落としをしていた**（3 件の診断に 1403c が出てこない）。**設計卓と製造の両方が、同じ理由で同じ 1 か所を落とした。**

**⇒ 一般化**: **「共有された期待値テーブル」を消す前は、必ず参照元を全数 grep する。** テーブルは定義ファイル名と使用者が一致しない（本件は `migrate_m1403c_test.go` に定義があり `migrate_m1403d_test.go` から使われている）ため、**ファイル名から使用者を推測できない。**

### 製造の推奨

- **#2（発見 1）は必須。** やらないと M19-04d が完了条件を満たせない。
- **#1・#3・#4・#5 も M19-04d に含めることを推奨する。** 理由——**すべて同一ファイル（`migrate_m1403c_test.go`）にあり、後から別サブで触ると同じファイルを 2 度触ることになる**（ボード **D-172** の「同じファイルを 2 度触らない」方針と整合）。**#2 のために結局このファイルは開く。**
- **#7（`migrate_test.go:849`）は判断を仰ぐ。** 別ファイルであり、`custom_states` の down 往復という別系統のテストである。**含めても含めなくても M19-04d は完了する。**

**★ただし #1・#3・#4・#5 を含める場合、「HEAD 終端をやめると検査が弱くなるのではないか」という論点がある。** 現在これらは「v28 → HEAD で不変」という**より強い主張**をしており、自サブへ閉じると「M14-03c が壊していない」に**弱まる**。**裁定 §2.3 はこのトレードオフを明示的に受け入れている**（「契約 F-2 が求めているのは『そのサブが書き換えていないこと』であって『以後のどのサブも書き換えないこと』ではない」）が、**#2 以外にも適用してよいかは設計卓の判断としたい。** 製造が独断で「弱めてよい」と決める事柄ではない。
