### §1-4 公開スナップショットの許可リストの契約

**正本＝`scripts/public-snapshot-manifest.txt`（新設）。** 形式は `<ALLOW|DENY><TAB><グロブ><TAB><理由>`。**現在 ALLOW 34 / DENY 12。**

| # | 契約 |
|---|---|
| 1 | 母数は `git -c core.quotePath=false ls-files -z`。**★`-z` は必須**——非 ASCII を含む追跡パスが 4 本あり、素の `git ls-files` は C 形式の引用符で包んで出す |
| 2 | **ALLOW にも DENY にも当たらない追跡ファイルは「未判定」として赤。⇒ 新しいトップレベル・新種のディレクトリは既定で公開されず、かつ黙って通らない**（集合が閉じる） |
| 3 | **DENY は ALLOW より強い**（許可ディレクトリの中から 1 件だけ抜くため） |
| 4 | **DENY はグロブが 0 件に当たっても赤にしない。⇒「存在しても出さない」形で書ける**（`D-656`）。**この性質自体に陰性対照を置いてある** |
| 5 | **予防 DENY は必ず `**/` で書く**（レビュー 高-1 の是正。理由は §7-3） |
| 6 | 生成（`scripts/make-public-snapshot.sh`）の選別と検査は**同じ判定器 1 本**を呼ぶ。⇒「生成では通るが検査では落ちる」形にならない |

**実測（2026-09-06 の最終状態）**: 追跡 **2722 件のうち 13 件を除外**——`.devcontainer/` 5 ／ `docs/seed-data/` 8。

> **★実装直後は 14 件だった**（上記 ＋ `docs/human-notes/future-notes/combmgr-features.txt` 1）。**同日中に開発者が同ファイルを削除したため 13 件になった**（§4-5）。**★DENY 行は残してある**——`D-656` の「存在しても出さない」形であり、**0 件に当たっても検査は緑**（実地で確認済み）。**消すと、将来同名のファイルが復活したときに黙って公開される。**

**★`make-public-snapshot.sh` はリモートに触れる git 操作を 1 つも持たない**（`push` / `remote` / `fetch` / `clone` のいずれも使わない）。出力先の既定は `.gitignore` 済みの `tmp/public-snapshot/`。**公開リポジトリへは 1 バイトも落としていない**（指示書 §0.1 / §4-1）。

| **1** | **「自分の成果物が検査対象に入るか」を先に見ないと、「本サブ由来ではない」は書いた瞬間から腐る。** 本サブは完了報告で 2 つの検査について「本サブ由来ではない／入力は着手基点と byte-identical」と断定したが、**報告自身をコミットした時点で偽になった**——`docs/progress/` は両検査の走査範囲だからである。**⇒ 非破壊性を主張するときは、これから書く成果物が走査範囲に入るかを先に確かめる。** 検出したのはレビューだけで、テストも lint も型検査も緑のままだった。 |
| **2** | **陽性対照は「1 形だけ試して緑」を対照と呼ばない。** `check-migration-license.sh` の「静かな漏れ」検出は `INSERT INTO` の 1 形しか self-test で試しておらず、**`INSERT OR IGNORE INTO` を見逃していた**。**★仮定の形ではなく `migrations/000007` が実際に使う形である。⇒ 検出器が「書き方の集合」を相手にするとき、対照はその集合を代表しなければならない。** 是正後は 6 形。 |
| **3** | **予防規則は、外側の防壁と同じ深さで書かないと意味がない。** 許可リストの予防 DENY を `.env` / `secrets/**` / `tmp/**` と書いたが、グロブの `*` はパス区切りを跨がないため**リポジトリ直下にしか当たらず**、`web/.env`（Vite の既定位置）や `docs/tmp/**` が `web/**` / `docs/**` の ALLOW を素通りしていた。`.gitignore` の同名規則は深さ無制限で**非対称**。**★兆候は「同じファイルの中で書き方が割れていること」だった**——`**/*.pem` は正しく書けていた。**⇒ 同種の規則が並ぶとき、書式が揃っているかを 1 度読む。** |
| **4** | **同じ検査が 2 経路で数字を出すときは突き合わせる。** `check-md-emphasis.sh` の要約行「ベースラインから N 行増加」と `--list` の出力行数は、`--list` のヘッダ 9 行ぶんずれる。**本サブは `--list | wc -l` をそのまま写して 972 を 981 と書いた。同じ実行の要約行を見れば気づけた。** |
| **5** | **★予測が記録に残ると、後続は事実として扱う。** `D-708` の「★★ただし穴は 3 つになる」は**起票時点の予測**だったが、そのまま指示書 §2.3-2 とチェックリスト §3-2 へ「欠番は 3 つ」として写された。**統合で実現しなかったのに、2 つの下流文書が予測を事実として持っている。** **⇒ 未来形の判断をボードへ書くときは、「予測である」ことを語で残す。** ★`M19-DESIGN-08` §3.1 の `D-250`（後任は本文をコピーし注記を読まない）と同型である。 |
| **6** | **機械検査の偽陽性は、床（ベースライン）に混ざると「減らす作業」を妨げる。** `check-md-emphasis.sh` は行単位で描画するためフェンス（```）を認識できず、**コードブロック内のグロブ（`path = "**"`）を閉じない強調として数える。** 逐語引用を要求する指示書と組み合わさると、**要求どおり書くほど赤が増える**構造になる。**⇒ 「ベースライン固定型」の検査は、床の中身が何であるかを一度は数えておかないと、後から減らせない。** |
| **7** | **一次情報へ到達できないと決めつけない。** 指示書とチェックリストは「REUSE 仕様の構文は『確かめられなかった』と書いてあるのが正しい」としていたが、**`reuse.software` が FW で不達でも、FSFE の正本リポジトリを `raw.githubusercontent.com` 経由で読めた。** **⇒ 「到達できない」は経路を 1 つ試した結果であって、結論ではない。** ただし到達できた範囲と、できなかった範囲（`reuse lint` の実走）は**分けて書く**。 |
