## §7 教訓（`retrospective-log` 行き）

**★親チャットは本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映であり、**実施者は設計担当**。

1. **★★「実機確認」は仕様の穴を見つける工程でもある。** 本サブでは、6 項目を確認しただけで**追加要求が 2 件**出た（`config.toml` の置き場を開く ／ 失敗時にパスを出す）。**どちらも「動かして初めて、足りないものが分かった」ものである。**⇒ **実機確認の回答を「OK / NG」だけで畳まないこと**。開発者が「〜が欲しい気がした」と書いた行は、**設計の穴の報告**である。
2. **★★手順が環境の前提を書いていないと、確認は静かに別のものを測る。** ポートを埋める手順は、開発機で **VS Code が devContainer のポートを転送している**ために成立せず、しかも**アプリは正しく動いていた**（二重起動の判別が働いた）。⇒ **「出るはずのものが出ない」ときは、まず測定系を疑うこと。** 一般形＝**実機確認の手順には「何を止めてから測るか」を書く。**
3. **★分類を持たせた機構は、付け忘れても静かに壊れる。** `configProblem` の目印は、新しい失敗経路へ付け忘れると**フォルダが開かなくなるだけ**で、テストも lint も緑である。⇒ **意味の判断が要る分類は機械検査にできない。**申し送りとして残すしかない（本書 §4-2）。**★「機械にできないこと」を無理に機械化しようとしないのも判断である。**
4. **★利用者へ出す情報は「原因」と「参考」を分けて書く。** 設定と無関係な失敗でも設定ファイルのパスは切り分けに役立つが、**そのまま並べると原因だと読まれる。**⇒ `(参考)` の 3 文字で意味が変わる。**一般形＝「事実を出すこと」と「原因だと示すこと」は別の操作である。**
