## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★実測件数は設計書へ書かないこと**（`D-374` ／ `E-136`）。**正本は契約テストである**。本節の数値は反映の判断材料であって、設計書へ転記する値ではない。

### 1-1 第 3 段の位置と、「前 2 段が 0 件のときだけ引く」の実現形

`internal/aliasindex/aliasindex.go` の `Lookup`。**早期 return の直列**であり、条件式で表現していない。

```go
key := aliasnorm.Normalize(aliasText)
if codes := sortedCodes(ix.strict[key]); len(codes) > 0 { return codes }   // 第 1 段
if codes := sortedCodes(ix.relaxed[key]); len(codes) > 0 { return codes }  // 第 2 段
return sortedCodes(ix.saNumber[key])                                       // 第 3 段
```

**⇒ 第 3 段のコードへ到達する条件が「前 2 段がいずれも 0 件」以外に無い。** `DES-004` §5.0.2 規約 3（前の段の答えを変えない）は**気をつけて守るのではなく構造で守られており、(a)(b)=0 は測定結果ではなく論理から出る。**

**⇒ `DES-004` §5.0 へ第 3 段を書いてほしい**（`CHANGE-120` の反映先）。**★「前 2 段が 0 件のときだけ引く」を、実現形（早期 return の直列）まで含めて書くこと**——条件式で書く形にすると、条件の書き漏らしが起きうる。

### 1-2 SA / CA 番号の導出規則の置き場を下位へ移した

**`internal/seedgen` の非公開変数 `saPattern` を `internal/sanumber` へ移設した。** 消費者が 2 つになったためである。

| 消費者 | 用途 |
|---|---|
| `internal/seedgen`（`saAnnotation`） | 表記プリセットの層 A が付ける注記 `" (SA1)"`（M20-02 以来） |
| `internal/aliasindex`（`addSANumber`） | 逆引きの第 3 段の索引キー（本サブ） |

**★`seedgen` から export して逆引きが import する形は採らなかった**——**実行時の逆引きが seed 生成のパッケージへ依存する形になり、層が逆である。** **★同じ正規表現を 2 か所に書く形も採らなかった**（指示書 §4.2・§3.3-2 が明示的に禁じている）。

**⇒ `DES-004` §5.7 へ「SA 番号の導出規則は 1 か所に置き、seed 生成と逆引きの双方がそこを引く」を明文化してほしい。** **★`D-5`（SA 番号は `move_code` から導く。技名からは推測しない）の裁定は、これまでコード内注記にしか存在しなかった。**

### 1-3 第 3 段は `DES-004` §5.4 の再適用表に載らない

**規則であるため、新キャラの `moves` 行に対しても索引構築時に自動で当たる。** ⇒ 波ごとの再適用が要らない。

**⇒ §5.4 へ本サブ分の行を足す必要は無い。** **★足す必要があるなら、それは規則で解けていないということである**（チェックリスト §5-2 の趣旨）。

**⇒ あわせて §5.4 の注記へ「規則で解いた分は本表の対象外である」旨を書いてほしい。** **★`D-437` が警告した落ち方**（新キャラだけ空になり、フォールバックで日本語技名が出る。画面は壊れずテストも緑。人が見る以外に発見経路が無い）**が、SA 番号については構造的に消えた。** **★ただし消えたのは SA 番号だけである**——層 A / 層 B / `rush_variant` / 移動系 9 code / 層 C-3 は従来どおり波ごとの再適用が要る。

### 1-4 多義の組は「捨てる」ではなく「候補として返す」

**`DES-004` §5.5 は投入側の規約として「衝突組は両方落とす」と定めている。** 案 A / B / C（辞書へ行を足す形）はこれに当たって多義の組を捨てるが、**案 E は §5.0.2 規約 1（1 件のときだけ確定）により「未確定 ＋ 候補提示」へ倒れる。**

**⇒ §5.5 の近傍へ「規則から導く段では、多義は捨てずに候補として返る」を書き分けてほしい。** **★同じ多義に対する扱いが投入側と照合側で違うことが、いまどこにも書かれていない。**

## §7 教訓（retrospective 行き）

> **★親チャットは本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映であり、実施者は設計担当（反映担当は 2026-08-11 に廃止・責務は設計担当へ統合）。

1. **同じファイルを編集しながら、そのファイルの冒頭コメントの前提を更新し損ねる。** 本サブは `m2207_baseline_test.go` の本体を後状態へ更新しながら、冒頭の「Lookup(2 段)」と「件数は本ファイルでは主張しない」をそのまま残した（レビュー 高-1・高-2）。**★テストも lint も型検査も緑のままであり、人が読む以外に見つける経路が無い。** 機構化: **ファイル本体を触ったら、そのファイルの冒頭コメント（package doc・ファイル頭のブロック）を最後に読み直す。** 「自分が今書いた前提と矛盾していないか」だけを見ればよく、数十秒で済む。

2. **「実データだけを見る検査」では原理的に検出できない不変条件がある。** 段の順序（前段の答えを後段が上書きしないこと）は、**実データに競合するキーが 1 つも無ければ、順序を入れ替えても答えが変わらない**——ゆえに実データ全数走査のテストは全部緑のまま通る（本サブの破壊確認 A で実測）。機構化: **「この不変条件が破れたとき、実データ上で答えが変わるか」を先に自問する。** 変わらないなら**合成 fixture が必須**であり、そのとき「対照（後段が別の答えを持っていること）」も同じテストに入れないと主張が空振りする。

3. **実査していない節を「失効している」と断定しない**（`E-117`）。本サブの完了報告は当初 `CHANGE-118 §7` を失効と名指ししたが、**本ツリーの `CHANGE-118` は §1〜§6 しかなく §7 は存在しなかった**（レビュー 中-4）。しかも同じ完了報告の §0 が「§7 追補は見えない」と自ら書いていた。機構化: **否定形確認は「区分」で終えず「列挙」まで行い、実査したものと未実査のものを分けて書く。** 未実査は「未実査」と書けばよく、それ自体は欠陥ではない——**断定だけが欠陥である。**

4. **推測で書いた数値はテストが拾うが、拾われる前に報告へ書かない。** `preset_aliases` の行数を 4212 と推測で書いてテストが赤くなり、実測 4184 へ直した（§3-2 の 4）。**★テストに書いたから拾えた**——散文にだけ書いていれば、`M22-07` の「空き枠は制約②で塞がれる」と同じく検証されないまま複製された。機構化: **数値を書くときは、まず assert する場所を決める。** 決められないなら、その数値は報告に書かない。
