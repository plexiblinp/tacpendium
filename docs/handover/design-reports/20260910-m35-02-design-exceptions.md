## 1. 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1 ★★`rush_<元技code>` は「表記規則」ではなく「解決契約」である

#### (a) 設計書は命名を書いているが、破れたときに何が起きるかを書いていない

`DES-004` は命名そのものを既に持っている。

| 場所 | 記述 |
|---|---|
| `docs/design/04-notation-spec.md:100` | 命名パターン表 ── ラッシュ版技 ＝ `rush_<元技code>` |
| 同 `:129` | 「`rush_<元技code>` の命名で独立 move として登録する」／「`original_move_id` で対応する通常技を参照することで、ラッシュ版から元技を辿れる構造とする」 |
| `docs/design/03-data-model.md:382` | 同趣旨（`original_move_id` で元技を辿れる） |

**★どこにも「この命名が破れると入力面から到達できなくなる」と書かれていない。**

#### (b) 実装は `move_code` の文字列一致だけで引き、`original_move_id` へ落ちない

```ts
// web/src/features/combo/inputResolution.ts:60
export function resolveRushByCode(moves: Move[], baseCode: string): number | null {
  const move = moves.find((m) => m.code === `rush_${baseCode}`);
  return move ? move.id : null;
}
```

**★`original_move_id` を見るフォールバックは無い。** `DES-004` `:129` と `DES-003` `:382` は「`original_move_id` で元技を辿れる」と書いているが、**入力面はその経路を使っていない**。

**⇒ 命名が破れると `null` が返る。** 呼び出し側（`DirectSpecPanel.tsx:63`）はそれを**データ駆動の非活性**として扱い、`:71` の `disabled={targetId == null}` でボタンを不活性にする。

**★★したがって壊れ方は「ボタンが出ない」ではなく「ボタンは並ぶが押せない」である。エラーも警告もログも出ない。** テストも lint も型検査も緑のまま通る。**⇒ 人が実機で気づく以外に検出の経路が無かった。**

#### (c) ★★この機序が `ryu` で実際に起きた（**唯一の実例**）

`ryu` の基底技は `axe_kick_2`、rush 版は `rush_axe_kick` であった。**`isOnUniqueTab`**（`web/src/features/combo/moveSurfacing.ts:141-146`）**は rush の code から `rush_` を外した `axe_kick` を探すが、`unique` にその code は無い。⇒ 未分類バケットへ落ち、特殊技タブに出なくなる。**

**★`original_move_id` は正常に解決していた**（`axe_kick_2` は実在した）**。⇒ 「元技を辿れる」構造は生きていたのに、入力面はそれを使わないので救われなかった。★ここが本項の要点である。**

#### (d) 実データを数えた値が動いた（**裏づけ**）

`web/src/features/combo/moveSurfacing.roster.test.ts` は**フィクスチャではなく `character_data/*.csv` を読んで**「入力面に出ない行」を数えており、その `rush_variant` バケットが本サブで **5 → 4** に減った（`:172` 付近）。

**★★残る 4 件は `ryu` と別の理由で落ちている**（§0-1 (c)）——`alex` 2 件 ／ `jamie` 1 件 ／ `zangief` 1 件で、**いずれも基底が `normal` として実在し `original_move_code` も正しく、`HitBoxLayout` の方向×強度×ボタンから到達できないために落ちている。⇒ `M35-02` の射程とも `rush-original-move-code-typo` の射程とも別である。**

#### (e) ⇒ 反映依頼

**`DES-004` §3.2.1（または `DES-003` §3.3）へ次の 1 点を明文化してほしい。**

> **入力面（仮想コントローラ）のラッシュ版解決は `move_code` の文字列一致のみで行い、`original_move_id` へのフォールバックを持たない。⇒ `rush_<元技code>` の対応が破れると、`original_move_id` が正しく解決していても当該技は入力面から到達できなくなる。★エラーにならず「押せないボタン」として並ぶ。**

**★これは「値の記載漏れ」ではなく「as-built の記載漏れ」である。** 設計書は `:129` ／ `:382` で「`original_move_id` で元技を辿れる」と書いており、**読んだ人は入力面もその経路を使うと考える。⇒ 実装は使っていない。この差が `ryu` の 1 件を生んだ。**

**★★初版はここで「`DES-004` §3.2.1 が入力できない技を表記の例外として記録していた」と書いたが誤りである**（§0-1 (d)）**。同節の注記は dangling 参照 4 件を正確に記録していた。⇒ 請求の中身を「設計書の誤りの是正」から「as-built の追記」へ改めた。**

## 2. 契約・設計に反する独自判断（★親の裁定を要する）

### 2-1 ★版固定契約テストの主張を反転させた

**対象**: `internal/infra/migration/migrate_m1403c_test.go`（`TestRun_M1403c_UpContract`・**終端 `v30`**）。

#### 何に反したか

`SUPP-001` §5.5 の規約 (1)(2) は、版固定契約テストを「**そのサブが書き換えていないこと**を主張する装置」と定め、**HEAD を終端にしないこと**を求めている。趣旨は「後続サブの正当な変更で過去サブのテストが落ちないようにする」ことであり、**後続サブがその主張自体を書き換えるのは想定の外にある。**

#### なぜそう判断したか

同テストは 2 つのリストを持つ。

- `:117` … `axe_kick_2` を「**存在する** code」として 1 件を主張
- `:136` … `axe_kick` を「**不在であるべき** code」として 0 件を主張

golden `000030` が seed する code が開発者の確定（2026-09-08）で変わったため、**この 2 行は必ず反転する**（終端 `v30` は `000030` の直後）。**⇒ 三点更新の 2 点目（golden 再生成）を成立させるには追随が要る。** 追随しない選択肢は「golden を再生成しない」＝チェックリスト A-1 に正面から反する。

#### 実装がどうなっているか

- **2 つのリストの要素を対のまま入れ替えた**（`axe_kick` を存在側へ、`axe_kick_2` を不在側へ）。**要素数はどちらも不変**であり、判定の本数も強さも減っていない。
- 見出しコメントを**由来**（新体系 / 旧体系）から**役割**（`000030` が seed する code / seed 後に残っていてはならない code）へ書き直した（`:98` / `:124`）。**旧見出しでは `axe_kick_2` の 1 要素だけ意味が違うリストになるため**（レビュー 中-6）。
- **★先に赤を実測してから直した**（完了報告 §6 に出力を貼付）。
- 元の `axe_kick` が不在側に居たことで守っていたもの（`000029` が旧 seed を掃いたこと）は失われていない。同テストは `ryu moves = 93` と `rush_variant = 17` を別に固定しており、かつ `UNIQUE(character_id, code)` があるため旧 `axe_kick` 行が残ったまま `000030` が INSERT すればマイグレ自体が落ちる。

#### ⇒ 親への依頼

**この形を「受理して先例化する」か「差し戻す」かの裁定を求める。**

**★terry の先例には版固定テストが無い。** `migrate_m2805_test.go` / `migrate_m3002_test.go` はそれぞれ終端 `v106` / `v107` であり、**golden `000026` の版に固定されたテストは存在しない。⇒ 同型の改名で版固定テストの追随が発生したのは本サブが初めてであり、判断の前例が無い。**

**★受理する場合の一般則の候補**（設計卓の判断材料として）: 「**golden を再生成するサブは、その golden の版に固定された契約テストの主張も同じ手番で追随させる。ただし要素数を減らさず、対のまま入れ替える形に限る。**」

## 7. 教訓（retrospective 行き）

**★親（設計卓）は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映であり、**反映担当の廃止（2026-08-11）に伴い実施者は設計担当**。

### 7-1 検査スクリプトの守備範囲は「対象がどの波に属するか」で変わる

`go run ./cmd/seedgen -check` は **`character_data/ryu.csv` を旧 code へ戻しても `OK` / exit 0 を返す**（実測）。捕まえるのは `go test ./internal/seedgen/` だけである。

**★これは `CHANGE-163` §1（`:28`）が既に「第一波しか再生成しない。⇒ 第一波外のキャラは壊しても緑が返る」と述べていたことの実測による裏づけである。** `M28-05`（terry＝第一波）では `-check` が赤くなったため**裏面しか測れなかった**。

**⇒ 一般化**: **「同じ検査でも、対象がどの区分に属するかで守るかどうかが変わる」ものがある。⇒ 先例で緑・赤を見たことは、自分の対象で同じになる保証にならない。★守備範囲を述べた文書が在るなら、それを実測で確かめる手番として使う。**

### 7-2 golden を動かす前に、その版に固定された契約テストの有無を見る

`migrate_m1403c_test.go`（終端 `v30`）は `000030` の直後に固定されており、golden を再生成すると**必ず落ちる**。**★先例（terry / `000026`）には版固定テストが無かったため、先例をなぞるだけでは出てこない作業だった。**

**⇒ 一般化**: **golden を再生成する前に `grep` で「その版を終端にしている契約テスト」を探す。⇒ 落ちてから気づくと、緩和なのか追随なのかを落ち着いて判断できない**（先に赤を実測してから直せば、要素数と主張の強さを比較できる）。

### 7-3 識別子を改名するときは「DB の外」を走査軸に入れる

段 1 の走査は DB 内（`moves` / `preset_aliases` / `combo_steps` / `setup_steps`）と CSV 正本・golden・テストを網羅したが、**エクスポート成果物が `move_code` を文字列で持つこと**（`recipe` セル）**を軸に持っていなかった**。レビューの指摘で気づいた。

**⇒ 一般化**: **識別子の改名では走査軸を 2 本持つ。(1) 内部の参照（多くは id 参照で安全）／ (2) ★外へ出た成果物が識別子を文字列で持っていないか。⇒ (2) は「利用者データを壊さない」という断定の射程を決める。**

### 7-4 「証跡がある」と「その証跡が主張を支える」は別である

レビューは `logs/tacpendium.log` の `108/u` 4 件を「実 DB での適用証跡」として引くよう勧めた。**ログ行の存在そのものは正しい観測だったが、その DB は `web/e2e/.tmp/tacpendium-e2e.db`（使い捨ての E2E DB）であった。⇒ `v1` から通しで適用する新規 DB のため `UPDATE` は 0 行に当たり、追随の証跡にならない。**

**⇒ 一般化**: **証跡を引く前に「その証跡が生まれた条件」を確かめる。⇒ とくに「新規 DB では 0 行に当たる」型のマイグレでは、ログに行が出ていることと効いたことが一致しない。★レビュー指摘であっても前提を確かめてから採る。**

### 7-5 失効した記述は「誰が失効させたか」と対で書く

レビュー 高-1（`inputResolution.ts:78` の `ryu` の例示）は**着手前から失効していた**。是正するときに「`M35-02` が失効させたのではない」ことを併記した。

**⇒ 一般化**: **失効記述を直すときは「いつ失効したか／本サブ起因か」を 1 行添える。⇒ 添えないと、次の担当が「直前のサブが壊した」と読み、無関係な変更を疑って時間を使う。**

### 7-6 ★★走査式が何を測っているかは、拾った結果から逆算してはならない

**本レポートの初版が犯した誤りそのものである**（§0）。段 1 で次の式を使った。

```bash
awk -F, '$3=="rush_variant"{ if("rush_" $17 != $2) ... }'   # $17=original_move_code / $2=move_code
```

**この式は 2 種類の欠陥を区別せずに拾う**——(1) `move_code` の対応が破れている（＝入力面から到達できない）／ (2) `original_move_code` が dangling（＝`original_move_id` が NULL）。**`ryu` はたまたま両方の列が同じ値だったため、拾ったものが (1) だと思い込み、同じ式で拾った他の 4 件も (1) だと決めてしまった。**
