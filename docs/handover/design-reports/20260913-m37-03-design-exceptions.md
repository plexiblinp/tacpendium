### 1-2 `B01` の as-built —— ゴミ箱のコンボ側を削除日時降順にした

#### 1-2a ★★着手前は同じ画面の 2 つの表が食い違っていた

| 実体 | 経路 | 着手前の ORDER BY |
|---|---|---|
| **コンボ** | `GET /api/combos?only_deleted=true` | **`starter_move_id ASC, position ASC, hit_type ASC, opponent_stance ASC, opponent_size ASC, id ASC`** |
| セットプレイ | `GET /api/setups?onlyDeleted=true` | `deleted_at DESC, id DESC`(`internal/repository/setup/restore.go:197-221`) |

**原因**: ゴミ箱のフックは `sort` / `order` を送らない(`web/src/features/combo/hooks/useTrashCombos.ts`)。
`resolveSortClause` は whitelist に無い値を default 分岐へ落とすため、通常一覧と同じ始動状況順になっていた。

**★セットプレイ側のコードコメントは当初から意図を書いていた**——逐語＝「並びは削除日時の新しい順(ゴミ箱は直近に消したものから探す)」。
**⇒ コンボ側だけがその意図を満たしていなかった。**

#### 1-2b ★★`DES-005` §5.15 は並び順を一言も規定していない

同節の 表示項目 は「削除日時」を**表示する**とだけ定める(§5.15 の全文を grep 済み。並び／ソート／順 の語は本件と無関係な 2 件のみ)。

**⇒ 本件は既存記述の訂正ではなく、設計書への*追記*である。**

**⇒ `DES-005` §5.15 へ明文化してほしい**——**コンボ・セットプレイとも既定は削除日時の降順。副次キーは `id` 降順。**
**★副次キーが要る理由＝`deleted_at` は `datetime('now')` の秒精度である**(`internal/repository/combo/repository.go:1367`)**。**
**同じ秒に消した 2 行は日時だけでは順序が決まらず、`LIMIT` / `OFFSET` のページ境界で重複・欠落が起こりうる。**

### 1-3 ★★★API 契約が増えた —— `GET /api/combos` の `sort` が `deleted_at` を受理する(`DES-002` §4.2)

**★設計卓は完了報告を読まないため、参照ではなく実体を書く。**

**実装**: `internal/repository/combo/repository.go` の `sortFieldWhitelist` へ `"deleted_at": "deleted_at"` を追加。

#### 受理する値の全数(as-built)

`default` / `updated_at` / `damage` / `step_count` / `starter_move_id` / **`deleted_at`**(新規)。
**★whitelist に無い値は拒否されず、既定へ落ちる**(従来どおり。400 は返さない)。

#### ★母集団の述語(この経路が何を返し、何を返さないか)

**既定の並びが変わるのは `only_deleted=true` のときだけである。**

| 要求 | 並び |
|---|---|
| `only_deleted=true` ＋ `sort` 未指定 | **`deleted_at DESC, id DESC`**(新) |
| `only_deleted=true` ＋ `sort=deleted_at`(＋`order=asc`) | `deleted_at` の指定方向 ＋ `id` の同方向 |
| **`only_deleted=true` ＋ `sort=default`** | **始動状況順 ＋ `id ASC`**(★下記) |
| `only_deleted` 無し(通常一覧) | **従来どおり不変**。`sort` 未指定なら始動状況順 ＋ `id ASC` |

#### ★★持たせなかった分岐(誤読を防ぐために書く)

1. **`sort=deleted_at` を通常一覧で送っても拒否しない。** `deleted_at` が全行 NULL なので実質 `id` 順になるだけである。**⇒ エラーにする分岐は作っていない。**
2. **`sort=default` は「明示指定」として扱う。** ⇒ ゴミ箱で送ると始動状況順へ戻る。
   **★これは意図どおりである**——`default` は whitelist の 1 エントリであり「始動状況順で並べてくれ」という明示の要求だからである
   (一覧の並び替えで「始動状況順」を選ぶと同じ値が飛ぶ。**⇒ ここを変えるとそちらが壊れる**)。
   **★★将来ゴミ箱へ並び替え UI を足すときの落とし穴である**——**「既定へ戻す」操作に `sort=default` を使うと削除日時降順にならない。**
   `TestList_TrashSortDefaultIsTreatedAsExplicit` が本挙動を固定している。
3. **セットプレイ側(`GET /api/setups`)は 1 行も変えていない。** 既に正しいため。**⇒ `sort` パラメータも持たせていない。**
