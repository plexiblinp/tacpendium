### 1-4. ★★`SM-093` は表示だけの変更ではない（保存値が変わる）

- 新規登録の `opponent_stance` の既定を **空文字（→ NULL）から `"any"` へ**。定数は `web/src/constants/combo-list.ts` の `OPPONENT_STANCE_ANY`。
- **★実査で ledger と食い違った**——**空文字と `any` は同じ扱いではない**。保存時に `nullIfEmpty` を通って `""` は **NULL**、`"any"` は文字列になり、**重複判定キー（`internal/service/combo/duplicate_keys.go`）と一覧フィルタの単純等値（`internal/repository/combo/repository.go`）で別の値になる**。
- 既存データには一切触れていない（マイグレ 0 本）。編集・コピーは読込値のまま（対照テストあり）。

**⇒ 反映依頼**: **`DES-006` の `VAL-C02`（重複判定）の説明へ、`opponent_stance` の既定が `any` になったことによるキーの変化を書いてほしい。** `CHANGE-137` の射程へ `DES-006` を加えるかは設計卓の判断（完了報告 §9 判定 #3）。

### 1-5. 離脱ガードの機構（新設パッケージ・`SUPP-001` §5.2）

- 新設 `web/src/features/navigation-guard/`（`NavigationGuardProvider.tsx` / `useUnsavedChangesGuard.ts` / `dirty.ts` / `linkClick.ts`）。`App.tsx` に 1 組だけ置く。
- **掛かる経路は 4 つ**: 画面内リンク（document の click キャプチャ）／ ブラウザバック（番人の履歴エントリ＋`popstate`）／ リロード・タブを閉じる（`beforeunload`）／ ボタン（`leaveTo` / `leaveBack`）。
- **★公開 API は 4 つ**——確認つきの `leaveTo(to)` / `leaveBack()` と、**確認なしで番人の補正だけを行う `leaveWithoutConfirmTo(to)` / `leaveWithoutConfirmBack()`**（保存が済んだ直後に使う）。**任意の関数は預からない**——ガードは番人の履歴エントリを 1 枚積んでおり、離脱はその 1 枚ぶんを補正する必要がある。任意の関数（例 `navigate(-1)`）では補正のしようがなく、**「離れたつもりで編集画面自身のエントリへ戻る」＝離れられない状態になる**（レビュー 重大-3 で実際に起きていた）。
- **確認は共有プリミティブ `AlertDialog` を通す**（`DES-005` §5.7 規則9。自作オーバーレイは `M21-07` の物理入力抑止に参加しないため）。

**⇒ 反映依頼**: **`SUPP-001` §5.2 のパッケージ構成へ `web/src/features/navigation-guard/` を追加してほしい。** **★あわせて「離脱ガードを他の画面へ広げるときは同じ仕組みを通すこと（第 2 の方式を作らない）」を書いてほしい**——`useBlocker` が使えない理由（§3-2）は実装コメントにしか無い。

### 1-6. 検証 issue の `field` は生のフィールド名のまま持ち、日本語の呼び名は表示時に付ける

- `ValidationDisplay` に任意の `fieldLabel` prop を足し、`ComboEditor` だけが渡す。**データ側は生の名前で統一**（タブの振り分けが同じ値を見るため）。
- **副次的な挙動変化**: **サーバ由来の issue も日本語の呼び名で出るようになった**（従来は `driveAvailableAtStart:` のように生の名前がそのまま出ていた）。`steps[N].moveId` は「レシピ」へ畳む。
- **★何ステップ目かは出さない**——**BE の `stepOrder` は 1 始まり、FE zod の添字は 0 始まりで基点が違う。** 片方に合わせると他方が 1 つずれた番号を表示する。

**⇒ 反映依頼**: `DES-006` §11 の表示規定へ、**`field` は呼び名に翻訳して出す** ことと **ステップ番号は出さない（基点が 2 系統ある）** ことを書いてほしい。

### 1-7. `SM-112` の新しい呼び名 ／ `SM-060` のトースト

- **「共通システム（移動・その他）」→「技以外（ドライブラッシュ）」**（`labels.ts` の `NON_MOVE_GROUP_LABEL_JA`）。プレースホルダも「技・ドライブラッシュを選択」へ。**旧称リテラルは 5 箇所**あり（ledger の見込み 2 か所ではない）、定数 1 本へ集約した。
- **相方の `MOVE_CATEGORY_LABEL_JA.system`（「システム」）は変えていない**（消費者 7 ファイル・被りの解消には不要）。**★対比が片側だけである点は §4 へ回す。**
- トーストは**位置をヘッダの帯の外へずらし、閉じるボタンを出した**（`App.tsx`）。**表示時間 4000ms は変えていない**（実測で機序は「長い」ではなく「重なる」）。

**⇒ 反映依頼**: `DES-005` の該当節（レシピ入力の区分名・共通トースト）へ as-built を反映してほしい。

## §7 教訓（`retrospective-log` 行き・親は読まなくてよい）

**★本節の宛先は `retrospective-log` へのバッチ反映であり、実施者は設計担当である。親チャットは読まなくてよい。**

1. **★★「同じ要求を 2 面へ掛ける」ときは、網を面ごとに掛けること。** 本サブは「保存の成功で dirty を落とす」を `ComboEditor` と `SetupEditorPage` の 2 面へ掛ける要求だったが、**テストを `ComboEditor` にしか置かなかったため、`SetupEditorPage` の未実装が `make e2e` 198 passed と両立した。** 面の数はチェックリストが「2 面」と書いていたのに、テストの数は数えていなかった。**⇒ 要求が N 面に及ぶと書かれていたら、網が N 本あるかを数える。**
2. **★★離脱ガードのように「履歴を操作する」機構は、離脱の入口を型で絞ること。** 当初 `requestLeave(任意の関数)` という API にしたため、番人の履歴エントリ 1 枚ぶんの補正が**原理的にできない経路**（`navigate(-1)` を預かる）が生まれた。**⇒ 行き先を「どこへ」か「戻る」かの形で受け取ると、補正の仕方が型から決まる。** 「任意の関数を受け取る」は柔軟さではなく、**不変条件を守れなくする形**だった。**★その後の手動確認で「確認は出さないが補正は要る」場合（保存直後）があると分かり、入口は 4 つになった**（`leaveTo` / `leaveBack` / `leaveWithoutConfirmTo` / `leaveWithoutConfirmBack`）。**★増えたのは「確認を出すか」の軸であって、行き先の型は 2 つのままである。**
3. **★★破壊確認の期待経路は「その観測が何を見ているか」から立てる**（`D-572` の再確認）。「保存直後の遷移で確認が出ないこと」は、**dirty を落とすのをやめても緑のまま**だった——通常の保存はプログラム側の `navigate()` でありガードを通らないため、**何も観測していなかった**。この気づきが**レビューの重大-1 / 重大-3 の発見の起点にもなった**（レビュー報告書の「良かった点」2 に明記あり）。**⇒ 破壊確認は「赤くなったか」だけでなく「緑のままなら、その観測は何を見ていたのか」を書くと、次の欠陥が見つかる。**
4. **★★「履歴を操作する機構」は、機械検査だけでは穴が残る。** 本サブは **E2E 200 passed・破壊確認 6 件・独立レビュー 1 回**を通したうえで、**開発者の手動確認で 2 件出た**。**★どちらも `window.history` の実挙動に依存し、jsdom と E2E の両方をすり抜けた**——(a) `pushState` の state がリロードを跨いで残ること (b) state 更新（非同期）と `navigate()`（同期）の実行順。**レビュー報告書も「実機確認を推奨」と明記していた。** ⇒ **履歴・タイマー・ブラウザ標準ダイアログに触る変更は、緑を根拠にせず手動確認を前提に見積もる。**
5. **★★「原因が 1 つとは限らない」。** セットプレイ編集で離れられない不具合は、レビューが指摘した「dirty を落としていない」を直しても**消えなかった**——「番人の履歴エントリを補正していない」がもう 1 つの原因だった。**★1 つ目を直した時点でテストが緑になったため、直ったように見えた。** ⇒ **報告された症状が消えたことを、実際にその症状で確かめるまでは「直った」と言わない。**
6. **★契約テストは「何が契約か」の粒度で書く。** 保存後の遷移が `navigate(dest, { replace: true })` の形になった途端、`M24-01` の遷移先テストが**遷移先を 1 つも変えていないのに**落ちた。`toHaveBeenCalledWith(dest)` が**引数の形まで固定していた**ためである。⇒ **遷移先が契約なら遷移先だけを見る。** 形で固定すると、無関係な内部変更のたびに契約テストが巻き添えで落ち、「契約が壊れた」のか「形が変わっただけ」かの区別がつかなくなる。
7. **★件数はその場で数え直すこと（規則が実際に誤りを 2 件捕まえた）。** 完了報告の初出「ヘッダを描くページ 17 本」は正しくは **15 本**（テストファイル 2 本を数えていた）、「消費者 8 か所」は正しくは **7 ファイル**。**どちらもコマンドを併記していなかった箇所である。** ⇒ **コマンドを併記できない件数は、まだ数えていない件数である。**
8. **★整形した文字列を「出力」として載せない。** ポート確認をコマンド `|| echo "PORTS FREE"` と書きながら、出力を `PORTS FREE: 47390 / 5273 とも空き` と載せていた（そのコマンドからは出得ない行）。**⇒ 逐語でないなら「出力」と書かない。**
9. **★harness 由来の赤はテストが観測した赤ではない。** 破壊確認で `pnpm exec playwright test` を直に叩くと `PW_EXECUTABLE_PATH` が渡らず、ブラウザ起動失敗で赤になる。**証拠に採る前に、期待どおりの assert メッセージで赤になっていることを確かめる。**
10. **★flaky は retry で流さず機序を書く。** ガードは「dirty になった次の描画」で張られる（番人を積むのは `useEffect`）ため、待たずに `page.goBack()` を押すと本当に戻る。**⇒ 待ち合わせ点を出して待つ形にした。** 「タイミング依存だから」で retry に頼ると、同型の競合が他のケースにも残る。
