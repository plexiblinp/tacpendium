**先例がリポジトリ内に在る**：`000063` のヘッダ逐語＝「**`is_projectile` の追随は `000039` の code 列挙の書き換えで行った(指示書 §2.5 の案 1)**」（`M19-04c`）。**⇒ 本サブはこの先例をなぞった。**

**開発者の事前承認を得ている**（2026-09-12・Plan Mode。逐語＝「案1: 適用済みマイグレの code 列挙を書き換える (推奨)」を選択）。

## §7 教訓（retrospective 行き）

> **★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映であり、実施者は設計担当である。

### 7-1 ★★★「先例をなぞる」は、先例が踏んでいない面を見つけられない

`M35-02` / `M28-05` / `M30-02` の 3 先例は**いずれも改名 code が後続マイグレから参照されていなかった**（実測 0 件）。**⇒ 手順をなぞるだけでは §1-1 に到達しない。** 本サブが到達できたのは、**先例の手順ではなく「変わる値で `migrations/*.sql` を `grep` する」という規約 (16) の発想を、テストではなくマイグレへ向けたから**である。

**一般化**：**改名・削除を行う手番では、「その値を文字列で持っている場所」を*コードとテストだけでなくマイグレにも*探すこと。** 先例が静かだったのは、先例の対象がたまたま参照されていなかっただけである。

### 7-2 ★★★「経路が無い」は推論で書かず、その経路を再現するテストで確かめる

§3-3 のとおり、`move_derivations` について「取り落としの経路が無い」と書いた推論は誤りだった。**反証したのは、コホートを実際に再現するテストである。**

**一般化**：**「〜の経路は無い」と書くときは、その経路を再現しようと試みてから書く。** 再現に失敗して初めて「無い」と言える。**★再現のコストは高くない**——本件は「v62 まで上げて 10 行の code を旧へ戻す」だけで作れた。

### 7-3 ★★規約は「在る」だけでは届かない（**規約 (9) の不達**）

§4-2 のとおり、規約 (9) は**本件と同型の事故から生まれ、しかも「案の比較でこれを見落としやすい」と自ら警告していた**。**それでも届かなかった。**

**機序**：指示書が `SUPP-001` §5.5.4 の **(8) / (10) / (16) を名指しした**ため、製造はその 3 つだけを読んだ。**⇒ 名指しは「読むべきものを示す」と同時に「それ以外を読まなくてよい」という信号として働く。**

**一般化**：**規約の集積場から一部だけを名指しするときは、「この節には他にも規約があり、手番の性質によっては当たる」ことを併せて書く。** あるいは**節ごとに「どの手番で当たるか」の索引を持たせる**。**★「警告文を書く」は既に試みられており、失敗している**（規約 (9) の後段がまさにそれである）。

### 7-4 ★レビューの指摘が正しくても、その範囲が正しいとは限らない

レビュー 高-1 は規約 (9) の不適用を正しく指摘したが、**`move_derivations` については「救済は不要」と書いていた**（§3-3 で実測により反証）。**⇒ 採用した指摘の*範囲*まで受け入れると、1 件取り落とす。**

**一般化**：**「高」指摘を採用するときは、指摘が挙げた対象の集合が網羅的かを自分で数え直す。** 指摘の正しさと、指摘の網羅性は別である。
