## 1. 独自確定仕様（設計書に無い／設計書より細かい決めごと）

### ★★§1-1 Go の版が `go.mod` の 2 行で二層管理になった（`DES-001` 反映が要る）

**やったこと**——`go.mod` に **`toolchain go1.26.8` を新設した**。`go` ディレクティブ（`go 1.26.4`）は動かしていない。

```
go 1.26.4        ← 言語仕様・vet の既定・標準ライブラリの挙動を決める。不動
                    (指示書 §2.2-1 / §4-2 が禁じた行)
toolchain go1.26.8  ← ★新設。実際にビルドに使う版を決める
```

**★なぜ `toolchain` 行という手段を採ったか（設計上の含意があるので書く）**——**`.github/workflows/` は Go の版を 1 か所も直書きしていない。** 4 か所すべてが `go-version-file: go.mod` である（`pr-checks.yml:64,151` ／ `nightly-crossbuild.yml:70,183`）。**⇒ `go.mod` を触らない限り CI の Go は 1 mm も動かない。** `toolchain` 行なら `actions/setup-go@v7` も手元の `GOTOOLCHAIN=auto` も追従し、**言語版だけを据え置ける。**

**★この二層が持ち込んだ挙動**（実測）:

| 環境 | 効くもの | 結果 |
|---|---|---|
| 既定（`GOTOOLCHAIN=auto`） | `toolchain` 行 | `go env GOVERSION` → **`go1.26.8`**。1.26.8 未満の環境は**初回ビルドで `proxy.golang.org` から取得する** |
| `GOTOOLCHAIN=local` | `go` ディレクティブ | `toolchain` 行は**無視される**。強制されるのは **1.26.4** |

**⇒ 「Go 1.26.4 以上」という要求表記は `GOTOOLCHAIN=local` でも成立する**（`CLAUDE.md:39` / `README.md:9` をその形へ揃えた）。**★ただしオフライン環境の利用者にとっては挙動が変わっている**——既定では取得が走る。

> **★★`DES-001` へ書き写す前に読んでほしい注記**——**「CI は 1.26.8」は結果として正しいが、その機構はまだ観測していない。** `actions/setup-go@v7` が `go-version-file: go.mod` から **`toolchain` 行を読むのか `go` ディレクティブだけを読むのか**をログで確かめていない。**★Nightly の E2E が緑でも区別がつかない**——`setup-go` が 1.26.4 を入れても `GOTOOLCHAIN=auto` がビルド時に 1.26.8 を取得するため、**どちらの経路でもビルドは 1.26.8 で行われ、テストは緑になる。⇒ 実害は無く、未確定なのは機構だけである。** 確定手段は PR [#157](https://github.com/plexiblinp/combomgr/pull/157) の `Setup Go` ステップのログで、**製造は PR を読めない**（`gh` CLI が無く GitHub MCP ツールは deny）ため開発者の手番とした（完了報告 §7-10）。**⇒ `DES-001` には「ビルドに使う版は 1.26.8」と書けるが、「`setup-go` が 1.26.8 を install する」とは書かないこと。**

## 2. 契約・設計に反する独自判断（★親の裁定が要る）

### ★★§2-1 `web/package.json` の `pnpm.overrides` へ、リポジトリ初の「上限固定型」override を入れた

**何をしたか**——`"nwsapi@>=2.2.26 <2.3.0": "2.2.25"` を追加した。

**何に反したか**——**`CLAUDE.md` §6（依存ライブラリ追加ポリシー）の文言には当たらない**（新規依存でもなく、`indirect → direct` 昇格でもない。`nwsapi` は `dependencies` にも `devDependencies` にも現れず、`web/src` からの import は 0 件）。**しかし §6 の根拠——「直接依存にした時点で、そのモジュールの API に本体が縛られ、以後の更新・撤去の判断が本体の責任になる」——は exact pin にもそのまま当てはまる。** 版を固定した時点で、`nwsapi` を上げるかどうかの判断は本体の責任になった。

**★既存 4 件との性質の違い**（これが「初」である理由）:

```
"ws@>=8.0.0 <8.21.0": ">=8.21.0",     ← 下限引き上げ型。範囲を満たせば実質無害化する
"form-data@>=4.0.0 <4.0.6": ">=4.0.6", ← 同上
"esbuild@<0.25.0": ">=0.25.0",         ← 同上
"@babel/core@<7.29.6": "^7.29.6",      ← 同上
"nwsapi@>=2.2.26 <2.3.0": "2.2.25"     ← ★新規。上限を押さえる型
```

**なぜそう判断したか**——`pnpm update` をそのまま入れると **Vitest が 59 件落ちた**（10 ファイル・すべて `Test timed out in 5000ms`）。二分探索の実測:

| 状態 | 結果 |
|---|---|
| 版上げ前（`nwsapi 2.2.23`） | 19 passed / **2.87s** |
| 直接依存 26 本を段階的に全部上げる（user-event / RTL / radix 13 本 / react-query / vitest / 残り全部） | いずれも 19 passed / 約 2.7s |
| `pnpm update` 全適用（`nwsapi 2.2.27`） | **15 failed / 721.73s** |
| `nwsapi` を **2.2.24** / **2.2.25** に固定 | 19 passed / 2.88s・2.87s |
| `nwsapi` を **2.2.26** に固定 | **1 failed / 43.24s**（`--bail=1`） |

**⇒ 直接依存 26 本はすべて無罪で、犯人は推移依存の `nwsapi`（jsdom の CSS セレクタエンジン）。2.2.26 が回帰の入り口である。**

**★「正しさの修正に伴う低速化」ではなく純粋な性能回帰であることを実測で確定した**——上流の changelog は egress ブロックで引けなかったため、**2.2.26 のまま `--testTimeout=180000` で回した。19 件すべて passed（719.98s）で assertion は 1 件も落ちない。⇒ 挙動は同一で遅いだけ。**

**★緩和材料**: `nwsapi` の消費者は `jsdom`（devDependencies）1 本のみ（`web/pnpm-lock.yaml:3524`）。**本番バンドルには一切入らない。** 影響範囲はテスト環境の CSS セレクタ照会に閉じる。

**★形は自己解除するようにした**——`>=2.2.26 <2.3.0` に絞ってあるので、`jsdom` が `nwsapi ^2.3` を要求する版へ上がれば**この行は黙って無害化する**。解決結果が `nwsapi@2.2.25` のまま変わらないことは lock の `packages:` 集合突合で確認済み（コミット `26cfb57` 時点と差分ゼロ）。

**★指示書 §2.6-6「落ちたテストを skip / disable / quarantine しない」の潜脱ではない**——テストは 1 件も無効化しておらず `testTimeout` も動かしていない。**59 件は実際に走って passed している。** レビューも「潜脱ではない」と独立に判定した（`m28-03-review.md` の `M-3`(b)）。

**⇒ 親の裁定を求める 2 択**:

- **受理**する場合 → **`CLAUDE.md` §6 に「版を固定する `pnpm.overrides` / `go.mod` の `replace` も §6 の対象（提案してから入れる）」を明文化してほしい。** 現在の §6 は「追加」と「`indirect → direct` 昇格」だけを射程にしており、**固定は文言の外にある。**
- **却下**する場合 → override を外し、フロント依存の版上げ自体を差し戻す（`nwsapi` を上げると Vitest が落ちるため、**両立しない**）。

> **★開発者へは 2026-09-06 に報告済みで、異論があれば戻す旨を伝えてある**（完了報告 §7-4）。**追認は未取得。**
