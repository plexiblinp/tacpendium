## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★本節は `CHANGE-117` §2 の a〜d が「as-built 次第」として保留していた 4 点への回答である。** 指示書と異なる判断を下したものは §2 に分けてある。

### 1-1 §5.16「LAN共有モードON時のみ有効」の実体は **`disabled` でもガードでもなく「非描画」**（`CHANGE-117` §2-a）

`CHANGE-117` §2-a は「**ボタンが `disabled` なのか ／ モーダル側のガードなのか ／ 両方なのか**」を実測で確定させるとしていた。**実測の答えは、そのどれでもない。**

```tsx
// web/src/features/config/SettingsSectionNetwork.tsx
 84  {isLan && (
 93      {config.network.lanUrl && (
 99            <button type="button" onClick={() => setShowQr(true)}   ← disabled 属性は無い
105            </button>
119  {showQr && config.network.lanUrl && (   ← モーダル側のガードは「さらにその内側」
```

- **ボタンは二重の条件レンダリング内に在り、OFF のとき DOM に存在しない。** 押せない以前に無い。
- ファイル内で `disabled` を持つのは `:62` の `<Switch disabled={updateConfig.isPending}>` だけで、**QR ボタンとは無関係**である。
- モーダル側のガード（`:119`）は**ボタンより内側**にあり、**ボタンが無いときには到達しない**。二重になっている。
- ⇒ **`DES-005` §5.16 へ「非描画である」と書いてほしい。** **★「有効/無効」という語を残したままにしないこと**——次の担当が「押せてしまうのは欠陥だ」と読んで `disabled` を足す（**`CHANGE-117` §5 リスク 2 が名指しで警告した形**）。§2-1 と対。

### 1-2 「接続可能IP/ポート表示」は **在る。ただし代表 IP 1 件であり候補一覧ではない**（`CHANGE-117` §2-b）

**3 行そろって描画されている**（`SettingsSectionNetwork.tsx`）。

| 表示 | 位置 | 条件 |
|---|---|---|
| ポート | `:77-82` | **常時**（`local` 時は `127.0.0.1:<port>` 表記） |
| 代表 LAN IP | `:86-91` | `isLan` 時。空なら `settings.network.noLanIp`（「LAN IP を取得できませんでした」）へフォールバック |
| 接続 URL | `:93-98` | `isLan` かつ `lanUrl` が非空 |

**★ただし画面と stdout で粒度が違う。**

- 画面は `network.primaryLanIp`＝**代表 IP 1 件**（`SelectPrimaryLANIP()` の結果）。
- 一方 **`SUPP-001` §5.6 の起動時案内は「LAN モード時は LAN URL **一覧**」**と複数形で書かれており、`cmd/combomgr/main.go:349-353` が `netutil.ListPrivateIPv4()` で**実際に一覧を出している**。
- **`ListPrivateIPv4()` は `internal/api` から一度も呼ばれていない。** 画面へ一覧を出すには**サーバ側の新設が要る**（指示書 §4.3-2 は「サーバ側の新設は要らない見込み」としていたが、**それは代表 1 件で足りるという前提の下でのみ正しい**）。
- ⇒ **`DES-005` §5.16 の「接続可能IP/ポート表示」へ「代表 IP 1 件である」と明記してほしい。** **★書かないと、スマートフォンが別セグメントに居て繋がらないとき、利用者にも次の担当にも他の候補を出す手段が無いことが見えない**（`SUPP-001` §2.6.2 の「手動IP指定機能＝フェーズ3検討事項」がここに効く）。

### 1-3 QR の内容のテキスト表示は **2 か所に在り、§2-b とは別物である**（`CHANGE-117` §2-c）

`CHANGE-117` §4-1 は「**§2-b との重なり——同じものである可能性がある。同じなら §5.16 へ 1 項にまとめる**」としていた。**実査の結論は「別物」である。**

| 場所 | 実体 | 出現条件 | 選択 | コピーボタン |
|---|---|---|---|---|
| **QR モーダルの中**（QR の直下） | `QRCodeModal.tsx:54` の `<p className="text-center … break-all">{url}</p>` | **ボタンを押さないと出ない** | 可（通常の DOM テキスト） | **無し** |

### 1-4 代表 LAN IP は **CORS と「同じ関数」だが「同じ値」ではない**（`CHANGE-117` §2-d）

`CHANGE-117` §2-d は「**代表 LAN IP が CORS の許可 Origin と同じ関数で決まること**」を §5.16 へ 1 行書くとしていた。**それだけ書くと落ちるものがある。**

| | CORS（`cmd/combomgr/main.go:489-512` `buildAllowedOrigins`） | 設定 API（`internal/service/config/service.go:367-383` `resolveNetwork`） |
|---|---|---|

- **⇒ 稼働中に NIC が変わると、`network.primaryLanIp`（毎回再解決）が、凍結済みの CORS 許可 Origin から乖離しうる。** 画面には新しい IP が出るが、その Origin は許可されていない。
- ⇒ **§5.16 へは「同じ関数で決まる」だけでなく、この非対称も書いてほしい。** **★書かないと、片方だけを変えて他方が壊れる**（`CHANGE-117` §2-d 自身が「書かないと片方だけを変えて他方が壊れる」と書いており、**その懸念は「同じ関数だ」と書くだけでは解消しない**）。

## §2 契約・設計に反する独自判断（★親の裁定を要する）

> **本節の 2 件はいずれも「実装が正しく指示書が不足していた」型と考えるが、判断は親に委ねる。** 自分で「たぶん問題ない」と判断して §3 へ混ぜていない。

### 2-1 ★指示書 §4.3-1 が「埋める」と命じた穴を、**埋めなかった**

**何に反したか**——指示書 §4.3 の表・候補 1 の「埋めるか」列。逐語は次のとおりで、**明確に埋めろと書いてある。**

> **埋める。** **★無効にするだけでなく、理由が見える形にする**（`DES-005` §5.16 の「ON時のみ有効」を満たす最小形＋利用者が次に何をすればよいか分かる 1 行）

**なぜそう判断したか**——**前提が成り立っていなかった。** 同候補の根拠列は「**ボタンが押せてモーダルが出ないなら、それは『無反応なボタン』であり、利用者は理由を言語化できない**」であり、**「押せてしまう」ことを前提にしている**。**実測では押せないどころか DOM に存在しない**（§1-1）。**⇒ 埋めるべき穴が存在しない。**

**実装がどうなっているか**——**`SettingsSectionNetwork.tsx` に 1 バイトも触れていない**（`git diff f223723..HEAD -- web/src internal cmd migrations` の出力は `*.test.tsx` 3 本のみ）。代わりに **`SettingsSectionNetwork.qr.test.tsx:142` へ「LAN 共有モード OFF のとき、QR ボタンは描画されない」を回帰ゲートとして置いた。**

**★埋めなかったことの副次的な正当性**——`CHANGE-117` §5 リスク 2 が「**『押せてしまう』を欠陥と読んで二重の守りを作る**」を明示的にリスクとして挙げており、**モーダル側が既に守っているなら `disabled` は追加の層である。⇒ 実測してから決めさせる**としていた。**実測した結果が本項である。**

**⇒ 親への依頼**: (a) **この判断を受理し、指示書 §4.3-1 が前提を誤っていたと記録する**か、(b) **却下して「理由が見える 1 行」を足させる**かを裁定してほしい。**★(b) を採る場合、それは「穴埋め」ではなく新規の UI 追加である**——OFF のときネットワーク節には既に「接続モード: ローカル」と `127.0.0.1:<port>` が出ており、**何も無い画面ではない。**

### 2-2 指示書 §5.2 の「既存 spec へ足す」に従わず、**新規 spec ファイルを作った**

**何に反したか**——指示書 §5.2 の注記「**★資源ごとに 1 ファイルへ寄せること**（**D-362**）。**設定画面を触る既存 spec が在るなら、そちらへ足す。**」

**なぜそう判断したか**——**`D-362` が守ろうとしている「資源」は共有グローバル状態であり、設定画面という画面ではない。**

- 設定画面を触る既存 spec は **`m22-02-login-and-user-select.spec.ts`** と **`m22-08-auth-finishing.spec.ts`** の 2 本だが、**いずれも扱っている資源は認証状態**であり、本サブの QR / ネットワーク節とは資源が違う。
- **本サブの spec はサーバ状態を 1 バイトも書き換えない**（`page.route` でこのブラウザコンテキストの `GET /api/config` だけを差し替える）。**⇒ 取り合う資源そのものが無い。**
- 認証 spec へ QR のケースを混ぜると、**逆に「認証状態を書き換える spec」と「書き換えない spec」が同居**し、片方の `page.route` がもう片方に効く事故の面が増える。

**実装がどうなっているか**——`web/e2e/m22-06-connection-qr.spec.ts`（新規・4 ケース）。**`server.mode` を書き換えないため復元も不要**であり、その旨を spec ヘッダと完了報告 §4-2 の d に明記してある。**レビューはこの判断を「妥当」と評価したが、「指示書 §5.2 への明示的な回答が完了報告に無い」ことを○（軽微）として指摘した**（レビュー §5）。

**⇒ 親への依頼**: **`D-362` の適用単位が「画面」ではなく「書き換える共有資源」であることを、契約または `/add_e2e_spec` 側へ明文化してほしい。** **★現状の文言（「資源ごとに 1 ファイルへ寄せる」＋「設定画面を触る既存 spec が在るならそちらへ足す」）は、後者だけを読むと画面単位に読める。**
