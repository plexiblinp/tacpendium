### §1-2 ★★★「132 セルだけが動いた」ことの立証方法が確定した

**巨大な INSERT 群の中の 132 セルは目で追えない**（指示書 §4.6）。**⇒ 構造化差分が唯一の足場である。**

確定した式＝**VALUES タプルを、引用符とエスケープ `''` を尊重して `,` で分割し、列ごとに突き合わせる**。
出すのは 4 つ:

```
行タプル数: 旧 3057 / 新 3057 -> 一致
行タプル*以外*の行: 旧 561 / 新 561 -> 完全一致      ← ヘッダ・コメント・パス2 の UPDATE ブロック
構造差（インデント・末尾記号・列数）= 0 件
セル差分 総数 = 132 ／ 列 startup_basis: 132 件 ／ 値の遷移 = [("'standalone'", "'unknown'")]
```

**★「`git diff --stat` が 132 insertions / 132 deletions」だけでは足りない** —— 1 行の中で 2 セル動いていても同じ数字になる。

**⇒ `SUPP-001` §5.5 系へ「生成物のデータマイグレを直したときは、列ごとの構造化差分を報告へ貼る」を明文化してほしい。**

### §1-3 ★検証 DB の直し方が「作り直し」ではなく「`UPDATE` 1 本」で足りることが確定した

`golang-migrate` はファイルのチェックサムを取らないため、`version=9` を持つ DB では書き換えた 9 本は**二度と走らない**。
⇒ 手順を `scripts/migrate-userdata-prompt.md` へ節として追記した（**新規ファイルは作っていない**＝`CLAUDE.md` §10.Y）。

**乾式で確かめた**（★走らせるのは開発者・製造は自分で作った DB まで）:

| 確かめたこと | 結果 |
|---|---|
| 新系列（是正前）＋ 利用者データ（combos 1 / tags 4）の DB へ `UPDATE` 1 本 | 132 行に当たり、違反 132 → 0 |
| `PRAGMA foreign_key_check` | 違反なし ／ 利用者データ無傷 |
| **その DB の `moves` 全行ハッシュ** vs **是正済み系列で新規構築した DB** | **`2b2b6a7e4664de89…` / 3057 行で完全一致** |

**★ただし一般化しないこと**——**`UPDATE` 1 本で足りたのは差分が `moves` の 1 列に閉じていたからである。**
行の増減・`id` の変化・スキーマ変更を含む書き換えなら成立しない。⇒ その旨も手順書へ書いた。

## §7 教訓（retrospective 行き）

> **★親はこの節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映であり、実施者は設計担当である。

### §7-1 ★★★報告を入力に取る検査は、報告を書き終えた後にもう一度回す（**`D-890` を、その節を読んだうえで踏んだ**）

`check-progress-log-index.sh` を回して EXIT=0 を得て、その値を完了報告へ書いた。**⇒ その後に完了報告を作成したことで、同検査は「対応する索引行が無い」を検出して赤へ変わった。**
**製造は気づかず、赤い検査を「緑」と書いた表を残した。レビューが自分で回して検出した。**

**★これは製造 CLI の `<!-- FULL-TEST-RUN-EXIT-CODE -->` 節が `D-890`（`M36-01` §7-1）として名指しで警告している型そのものである。**
**⇒ 節を読んでいても踏む。** 一般形は「**検査を回した時点と報告を書いた時点がずれると、『緑』が偽になる**」。

**機構化の案**: 完了報告の末尾に「**報告作成後に回し直す検査**」のチェック欄を常設で置き、**回し直した出力を貼るまで完了としない**。
（現行 CLI は「回し直す」と書いているが、**回した証拠を報告へ残すことは求めていない**。⇒ 求めれば、回さなかったことが報告から見える。）

### §7-2 ★★「緑である」は「走った」の証明ではない（環境変数でゲートされたテスト）

カナリアの before を取るとき、`TestCanary_SetplayProjection` の環境変数を `CANARY_OUT` と取り違えた。
**⇒ テストは `EXIT=0`（緑）のまま黙って skip し、出力ファイルが 1 つも作られなかった。** 正しくは **`CANARY_SETPLAY_OUT`** である。

**終了コードだけを見ていたら「before を取った」と誤認していた。⇒ 出力ファイルの実在を確かめて気づいた。**
**★同型の前例が `CLAUDE.md` に在る**（`TACPENDIUM_AUDIT_DB` 未設定で skip され、追随を落としても `go test ./...` は緑のままだった）。

**一般形**: **環境変数で走行が切り替わるテストは、「回した」ことを終了コードで判定してはならない。⇒ 成果物の実在で判定する。**
（本サブの破壊確認テストを**環境変数でゲートしなかった**のは、この型を避けるためである。）

### §7-3 ★★自分が書いた新コメントが指している先の旧値を落とした

失効記述の追随を 6 箇所やったが、**2 箇所を落とした**（レビュー 高-2 / 高-3）。うち 高-3 はとくに重い ——
**本サブが `migrate_m3704_test.go` の冒頭へ足した新コメントが、同ファイル `:239` の (3) ブロックを名指しで参照していながら、そのブロック内の `110` を直していない。**

**⇒ `M33-03` の教訓（「段をまたぐ参照は最後にもう一度走査する」）と同型であり、走査を 1 度で終えたことが原因である。**

**一般形**: **失効記述を直したら、直した箇所が*参照している先*をもう一度走査する。⇒ 自分が新しく書いた参照は、書いた時点では走査済みの母集団に入っていない。**

### §7-4 ★レビューの指摘も鵜呑みにしない（数え直して初めて正しさが分かった例）

レビュー 中-1 は「`docs/design/` 配下に『全一致』の記述は 0 件」としたが、**`grep -c` は 3 件を返す**。
数え直したところ **3 件とも §2.2 の「完全一致」**（重複判定キーの話）であり、同一性検証とは無関係だった。
**⇒ レビューの*結論*は正しく、*根拠の述語*だけが粗かった。**

**一般形**: **指摘の結論だけを採らず、根拠を自分で回す。⇒ 結論が正しくても根拠が違えば、次に同じ式を使う人が外す。**

### §7-5 ★`pnpm test` に `--run` を直接渡すと赤くなる（テストは落ちていない）

`cd web && pnpm test --run` は **`ERROR Unknown option: 'run'` で `EXIT=1`** になる。正しくは **`pnpm test -- --run`**。
**⇒ 「フロントのテストが赤い」と読み違えかけた。** `package.json` の `"test": "vitest"` へオプションを渡すには `--` が要る。
