## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1. ★`warnings` は「既存に無く、本サブが新設した」——応答の逐語形

**`CHANGE-124` §5 リスク 3 は「`warnings` の実装が既に在るかを設計卓は判定できない。指示書 §3.3-1 の実査に委ねた」としていた。答えは「無かった」である。**

走査＝`grep -rn 'warnings' --include=*.go internal/`（実装ファイル 6 件・定義 5 個がヒット）。**その全部が取得・プレビュー系であり、形も違った。**

| 既存 | 場所 | 形 | 変更系か |
|---|---|---|---|
| CSV 取込プレビュー | `internal/api/comboio/dto.go:26,37` | `[]string`（`orEmpty` で**常に空配列化**） | ✗ プレビュー |
| 技一覧 | `internal/api/move/dto.go:31` | `[]movewarning.WarningCode` | ✗ 取得 |
| `ValidationResult.Warnings()` | `internal/service/validation/result.go:83` | **メソッド**。フィールドではない | — |

**⇒ 変更系の応答が持っていたのは `validations`（`*ValidationResult`）だけで、これは `400 validation_failed` の `details.validations` と対になる「登録・更新時の検証結果」である。**

**★`DES-002` §4.2 へ写す as-built の逐語形**（`CHANGE-124` §2.3 の具体化）:

```jsonc
// POST /api/combos/{id}/restore と POST /api/setups/{id}/restore の 200 応答
{
  "id": 42,
  "...": "（復元後に取得し直した表現。既存のまま）",
  "warnings": [
    {
      "code": "VAL-R01",
      "severity": "warning",
      "message": "紐付いているセットプレイ 1 件がゴミ箱にあります。復元してもコンボ詳細には表示されません",
      "details": { "setups": [ { "id": 7, "name": "起き攻めA" } ] }
    }
  ]
}
```

**⇒ `DES-002` §4.2 へ、次の 3 点を明文化してほしい。**

1. **警告 0 件のときは `warnings` キー自体が出ない**（`omitempty` ＋ ハンドラ側の `if len(warnings.Issues) > 0` の**二重**。`internal/api/combo/handler.go:441-447` ／ `internal/api/setup/restore_handler.go:44-48`）。**★空配列は返らない**——返すとフロントが「警告があった」と誤って分岐する。
2. **`severity` を落とさず載せている。** `VAL-C08` / `VAL-S03` / `VAL-R01` / `VAL-R02` はいずれも WARNING だが、**`CHANGE-124` §2.2 が「ERROR 種別も警告として返す」と定めた以上、種別を落とすとその区別が応答から消える。**
3. **`warnings` と `validations` は別フィールドである。** 前者は「復元は成功した上での注意」、後者は「登録・更新時の検証結果」。**復元応答に `validations` は載らない**（ハンドラテスト `TestHandler_Restore_200_WithWarnings` が不在を主張）。

**根拠**: `internal/api/combo/dto.go`（`ComboResponse.Warnings`）／ `internal/api/setup/dto.go`（`SetupResponse.Warnings`）／ テスト `TestHandler_Restore_200_WithWarnings` ／ `TestHandler_Restore_200_OmitsWarningsWhenEmpty`（**コンボ側・セットプレイ側の各 2 本。JSON へ落として検査しており、構造体では見ていない**）。

### 1-2. ★★`ValidationIssue` に `Details` を足した——共有型であり、波及は復元 2 経路を超える

**`CHANGE-124` は `details` の形に触れていない**（指示書 §4.3-3 が「`M23-02` の `409 setup_in_use` に揃える」と言うのみ）。**実装は既存の共有型 `validation.ValidationIssue` を広げる形を採った。**

```go
// internal/service/validation/result.go
type ValidationIssue struct {
    Code     string         `json:"code"`
    Severity Severity       `json:"severity"`
    Field    string         `json:"field,omitempty"`
    Message  string         `json:"message"`
    Details  map[string]any `json:"details,omitempty"`   // ★M23-04 で追加
}
```

**★JSON の契約は変わっていない。** `omitempty` であり、**設定するのは復元経路だけ**なので、他の全経路（`400 validation_failed` の `details.validations` を含む）の wire format は 1 バイトも変わらない。既存のハンドラテストが緑のままであることが証跡である。

**★ただし型としては、全 VAL 経路が `details` を持てるようになった。** 指示書 §2.2 は「既存の `400 validation_failed` ＋ `details.validations` の形」を変更しないと定めており、**wire format は守っているが、型を広げたこと自体は指示書に書かれていない判断である。**

**⇒ 裁定してほしい 2 点。**

- **(a) この形を受理するか。** 受理するなら **`DES-002` のエラー応答共通形（`details.validations` の典型構造）へ、`ValidationIssue` が任意の `details` を持ちうる旨を明文化**してほしい。書かないと、次に `ValidationIssue` を読む担当が「復元専用のフィールドがなぜ共有型に居るのか」を判断できない。
- **(b) 却下する場合は、復元専用の別型（`RestoreWarning` 等）へ切り出す形になる。** その場合 **`VAL-C08` / `VAL-S03` の結果を変換する層が要る**——現在は既存検証の `ValidationResult` をそのまま `warnings` へ流しており、変換が無いことが「既に在る検証を復元経路で走らせる」（指示書 §1.5-2）の実装上の担保になっている。

### 1-3. ★`VAL-R02` の境界——「親が 1 件も無い場合は発火しない」

**`CHANGE-124` §2.1 は「すべて論理削除されている」としか書いておらず、親が 0 件の場合が未定義である。** **as-built は非発火。**

```go
// internal/service/validation/restore.go:70-75
if len(allParents) == 0 { return }        // ★親が 1 件も無い → 発火しない
if len(liveParentComboIDs) > 0 { return } // 生きた親が 1 つでもある → 発火しない
```

**理由**: 親 0 件は「全部削除済み」ではなく「**紐付けが既に失われている**」状態であり（`M23-02` §4.2-6＝同サブ適用前に論理削除されたセットプレイ）、**別の話である。** 集合が空のときに真になる述語を書くと、該当する行が復元のたびに警告を浴びる。

**⇒ `DES-006` の新節へ、`VAL-R02` の発火条件を「親が 1 件以上あり、かつそのすべてが削除済み」と書いてほしい。** 「すべて削除済み」だけだと、空集合の扱いが読む人によって割れる。

**根拠**: テスト `TestRestoreSetup_VALR02_SilentWhenOneParentAlive` ／ `TestRestoreCombo_VALR01_SilentWhenNoSetups`（**`VAL-R01` 側にも同型の 0 件対照を置いてある**）。

### 1-4. `details` の中身の形——`SetupRef` を新設し、`VAL-R02` は `ComboRef{id, memo}` にした

| VAL | `details` のキー | 要素の型 | 出典 |
|---|---|---|---|
| **`VAL-R01`** | `setups` | **`model.SetupRef{id, name}`**（**本サブで新設**。`internal/model/setup.go`） | — |
| **`VAL-R02`** | `combos` | **`model.ComboRef{id, memo}`**（`M23-02` の既存型を再利用） | `M23-02` §4.4-3 |

**★`SetupRef` が `name` を持つのに `ComboRef` が `memo` なのは、`setups` に `name` 列があり `combos` に無いためである**（`M23-02` が memo を「名前に相当するもの」と読み替えた判断をそのまま踏襲）。

**★`VAL-R02` は当初 id だけを返していた。レビュー中-3 の指摘で `memo` を載せる側へ広げた**（`FindReferencingCombosAllowDeletedTx` を併設。既存の id 版 `FindComboIDsBySetupIDAllowDeletedTx` には触れていない）。**判断の根拠は「発火条件の非対称は意図的（`D-494`）だが、`details` の形の非対称には正当化が無い」である。**

**⇒ `DES-002` §4.2 の `details` 構造へ、上表を写してほしい。** **★`M23-06` / `M23-07` が「どの件か」を画面に出すときの材料はこれで揃っている**（両方とも人が読める文字列を持つ）。

**根拠**: `internal/service/validation/restore.go` ／ テスト `TestRestoreSetup_VALR02_DetailsCarryComboMemo`。
