## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1 `GET /api/setups` の絞り込み引数は `onlyDeleted`（camelCase）

**`DES-002` §4.2 へ写す際、コンボ側の `only_deleted` と綴りが違う点に注意されたい。**

裁定（**D-491**）が「引数の綴りは既存の同経路が使っているものに揃えること」と定めたため実査した結果:

| 経路 | 綴り |
|---|---|
| `GET /api/setups` | **camelCase**: `characterId` / `knockdownAdvantage` |
| `GET /api/combos` | snake_case: `character_id` / `only_deleted` / `is_draft` |

**⇒ `GET /api/setups?characterId=N&onlyDeleted=true` を採った。** 経路をまたいだ不統一は残るが、**同一経路内での分裂は避けた**（裁定の趣旨どおり）。

### 1-2 `SetupResponse` に `deletedAt` を追加した

`*time.Time` / `json:"deletedAt,omitempty"`。**`ComboResponse.DeletedAt` と同型。**
根拠は `DES-005` §5.15 が「削除日時」を表示項目として明記していること（**D-491**）。

### 1-3 拒否の応答は 409 ＋ `details.combos`（`{id, memo}` の配列）

逐語は完了報告 §5。**`memo` は `omitempty` であり、空のコンボでは省略される。**
`M23-04` が VAL コード化する際、**「名前」が `memo` であること**を前提にされたい（`combos` に `name` 列は存在しない）。

### 1-4 as-built は **4 経路**である（3 経路ではない）

復元 ／ 完全削除 ／ 挙動が変わる論理削除 ／ **削除済み一覧**。詳細は完了報告 §4。

## §2 契約・設計に反する独自判断（★独立カテゴリ・最優先）

### 2-1 ★★§4.1-6 の「2 か所限定」は、実装上 **ヘルパ 2 本 / 症状 3 つ**になった

**裁定は「対象は 2 か所に限定します」と書き、(a) 引き継ぎオプションの数え上げ ／ (b) 検証結果の書き込みガード を挙げた。実装では (b) の是正が 3 つ目の症状も同時に閉じている。**

**理由**: (b) の実体は共有ヘルパ `setuprepo.comboSetupExists` であり、**呼び元が 2 つある**。

| 呼び元 | 経路 | 是正しない場合 |
|---|---|---|
| `ComboSetupExistsTx` → `requireComboSetupLinkTx` | `PUT` / `DELETE .../results` | ゴミ箱のセットプレイへ検証結果を書けてしまう（**裁定が挙げた (b)**） |
| `ComboSetupExists` → `CreateSetupLink` | `POST /api/combos/:comboId/setup-links` | **ゴミ箱のセットプレイでも `exists=true` になり、後続の `SetupExistsActive` へ到達せず黙って成功を返す**（本来は `ErrNotFound`） |

**★スコープ拡大ではないと判断した根拠**——同一ヘルパ・同一不変条件であり、§9.1-2 の区別（**本サブの変更によって初めて挙動が変わる**）に合致する。撤回前は `combo_setups` の行ごと消えていたため `exists=false` に落ちていた。

**★むしろ片方だけ直すほうが不整合である**——`ComboSetupExistsTx` だけを直すと、同じヘルパの 2 呼び元のうち一方だけが不変条件を回復した状態になる。

**⇒ 設計卓の確認をいただきたい点**: 「2 か所」の数え方を**症状 3 つ / ヘルパ 2 本**として記録してよいか。`CHANGE-122` へ写す際の表現に関わる。

### 2-2 完全削除の前チェックを Tx 内へ置いた（コンボ側と揃えなかった）

指示書 §4.3-1 は「経路の形はコンボ側に揃える。揃えられない事情が出た場合は理由を書くこと」。**1 点だけ揃えていない。**

| | コンボ側 | セットプレイ側（本サブ） |
|---|---|---|
| 前チェックの位置 | `BeginTx` の**前** | `BeginTx` の**後**（同一 Tx 内） |

**理由**: `M23-RESEARCH-01` §D-6 が **「コンボ側の前チェックが Tx 外である事実は TOCTOU の窓を作る形である」** と実測して記録している。**新しい経路にその窓を最初から作らない側を採った。**

**★コンボ側は触っていない**（§2.2-2）。既存の窓の是正は §4-2 の followup 候補。

## §7 教訓（retrospective 行き）

> **★親（設計卓）は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映であり、**実施者は設計担当**（反映担当は 2026-08-11 に廃止）。

1. **★「更新した」と報告書に書いた時点では、まだ更新していないことがある。** 本サブのレビュー「高」は、**§4.9 の否定形走査で失効コメントを検出しながら手当てが落ち、かつ完了報告が「更新した」と書いていた**という二重の失敗だった（`web/e2e/m22-03-optimistic-locking.spec.ts`）。**走査で「見つけた」ことと「直した」ことは別の事象なのに、報告を書く時点では同じ記憶になっている。** **⇒ 否定形走査の節は「検出した箇所」と「手当てした箇所」を別の表にし、後者は `git diff --name-only` の実出力から起こす**（記憶から書かない）。これは `M23-01` の教訓 2「『済み』と書く前に、その成果物が実在するかを見る」の**再発**であり、1 サブ挟んで同型が出た。
2. **不変条件を壊す変更では、「他所の穴」と「自分が壊した箇所」の区別が最初の設計判断になる。** 本サブは §3.3-1 で穴を 5 件見つけ、当初は全件を「報告のみ」（指示書 §9.1-2）と読んだ。**設計卓の裁定は「本サブの変更が無くても同じ挙動なら他所の穴、本サブの変更によって初めて挙動が変わるなら自分が壊した」**（`D-491`）。**⇒ 走査で穴を数えるときは、件数と同時に「本サブ適用前後で挙動が変わるか」を 1 件ずつ判定する。** 判定せずに全件を報告へ回すと、**担当境界を守る規則が劣化の言い訳になる。**
3. **共有ヘルパを直すときは、呼び元を数えてから粒度を決める。** 裁定は是正対象を「2 か所」と指定したが、うち 1 つは**呼び元 2 つを持つ共有ヘルパ**であり、片方だけ直すと同じヘルパの半分だけが回復した状態になる（§2-1）。**⇒ 「N か所直す」という指示を受けたら、その N が関数の数か症状の数かを確かめる。** ずれるなら実装前に戻す。
4. **同じ経路の中の綴りは、経路をまたいだ統一より優先する。** 本サブは削除済み一覧の引数を、模倣元のコンボ側（`only_deleted` / `character_id`＝snake_case）から持ち込もうとしたが、**`GET /api/setups` は既に camelCase（`characterId`）だった**。**⇒ 引数・フィールド名を足すときは、模倣元ではなく「足す先の経路が今使っている綴り」を先に見る。**
5. **前サブの撤去を守るテストは、後サブの設計制約として先に読む価値がある。** `M23-01` が 8 列 → 7 列へ減らした撤去は、E2E とコンポーネントテストが `td` ちょうど 7 個で守っていた。**この 1 事実だけで「コンボ表に混ぜる」案が消え、独立テーブルが確定した。** **⇒ 同じ画面を触る後続サブでは、前サブのテストを「動くかどうか」ではなく「何を禁じているか」として読む。**
6. **肯定的アサーションの非対称は、片方を書いた時点で気づきにくい。** 本サブは `combo_setups` の残存を肯定的に固定したが、**同じ理由で残るはずの `combo_setup_results` には 1 本も無かった**（レビュー 中-1）。**⇒ 「A と B が同じ理由で残る」と報告に書いたら、テストも A と B の両方にあるかを見る。** 報告の文とテストの対応を突き合わせると安い。

7. **★「配線した」を確かめるときは、出口だけでなく入口も見る。** 本サブは §4.5-4 の求めに従いゴミ箱**から**の復元・完全削除を配線し、E2E も通した。**しかしゴミ箱へ**入れる**導線（`useDeleteSetup`）がどの画面からも使われていないことに、開発者が手動確認の手順を尋ねるまで気づかなかった**（§4-9）。**E2E は API で直接 `DELETE` を叩いて状態を作るため、この欠落を 1 つも検出しない。** **⇒ 新しい画面要素を足したら、「そこに項目が現れる経路が UI 上に存在するか」を 1 度は辿る。** 空のリストは、正しく空なのか到達不能なのか、見ただけでは区別がつかない。
8. **手動確認の手順を書くときは、その操作が実在するかを確かめてから書く。** 本サブでは「セットプレイ側から削除」という手順を、**導線の実在を確かめずに書いて開発者へ渡した**。**⇒ 手順書は自分が実行できる形（コマンド）か、実在を確認した UI 操作でだけ書く。** 「たぶんあるはず」で書くと、受け取った側が最初の 1 行で詰まる。
