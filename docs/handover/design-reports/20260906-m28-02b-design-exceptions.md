## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### §1-1 ★★`ComboResponse` へ `affectedMoves` を足す請求（宛先 `DES-002` §4.2）

#### なぜ要るか

**指示書 §2.3-4 は「1 行にどの技が変わったかを出すこと。★★これが本機能の目的である」と定めている**（開発者の逐語 `D-729`＝「どのコンボに影響があるかをユーザーに見せ修正しやすいようにする事が今回の目的」）。

**⇒ 現行 API では原理的に取れない。実物で 4 点を確認した。**

| # | 塞がっている理由 |
|---|---|
| **1** | **`GET /api/moves` からマーカーを取れない。** `internal/model/move.go:79` に `LastChangedGameVersion *string` は在るが、**`internal/api/move/dto.go` の応答 DTO（一覧・詳細とも）にこの欄が無く、詰め替えで落ちている** |
| **2** | **`games.current_data_version` を返す HTTP 経路が 1 本も無い**（ルート登録に `games` が無く、`GET /api/config` の応答にも含まれない）。**⇒ 比較の片側が FE に存在しない** |
| 3 | **`ComboSummary` に `steps` が無い**（持つのは `ComboDetail` だけ）。**⇒ 一覧応答からステップの `moveId` を辿れない** |
| 4 | **行ごとに `GET /api/combos/:id` を引く代替も成立しない。** `ComboStep` が持つのは `moveId` / `moveCode` / `modifiers` だけで、**N 回引いても答が入っていない**（N+1 の代償を払う以前の問題） |

**★さらに、仮に取れても FE で自前比較するのは指示書 §0.3 違反である**（判定条件を画面側で書き直すと 2 か所に割れて静かにずれる）。**しかも `CHANGE-159` §2.1 の「2 種類の NULL は向きが逆」を画面側で再現することになり、これは設計卓自身が「設計書に書くことが唯一の防御である」と書いた当のものである。**

#### 請求内容

**`ComboResponse` へ `affectedMoves` を足す。**

```json
"affectedMoves": [
  { "moveId": 123, "code": "2MK", "nameJa": "しゃがみ中キック",
    "lastChangedGameVersion": "2026.09.10.01" }
]
```

| # | 条件 |
|---|---|
| 1 | **判定式（`CHANGE-159` §2 の `EXISTS`）と同じ 1 か所から導出すること。★式を書き写さない** |
| 2 | **一覧の N 件ぶんはバッチ取得で作る。★先例＝`internal/api/combo/handler.go:344` の `ListSetupsByComboIDs`**（N+1 回避） |
| 3 | **`nameJa` は NULL 可**（`MoveResponse.NameJa *string`）。**⇒ 引けないときは `code` へ落ちる**作法を明記する（先例＝`starterMoveNameJa`） |
| **4** | **★★`affectedMoves.length > 0` で影響の有無を判定させないこと。** 画面は `affectedByGameUpdate` を見る。**長さで判定すると真偽が 2 か所で表せてしまい、それ自体が §0.3 の再発である** |
| 5 | **空のときの形（`[]` か キー無し か）を決めること。★`affectedByGameUpdate` が `omitempty` を持たないのと同じ理由で、`[]` を明示する側を推す** |

**★これが通らないとどうなるか**——**専用画面は「影響がある」としか言えず、利用者は直せない。⇒ `FR702` の目的が未達のまま画面だけが出来る。**

### §1-2 告知の経路 2 本 ＋ `COUNT` ＋ `games.current_data_version` の初の露出（宛先 `DES-002` §4.2）

| 経路 | 内容 |
|---|---|
| **`GET /api/notices/game-update`** | **`{currentDataVersion, affectedCount, postponedForVersion?}` を常に 200 で返す** |
| **`POST /api/notices/game-update/postpone`** | **要求本文を取らない。** サーバが `games.current_data_version` を読んで書く |

| # | 判断に要る点 |
|---|---|
| **1** | **★204 の作法から意図して外れている。** 指示書 §0.4 の逐語「流用できるのはバナーの形と **204 で『無い』を表す作法まで**である」は**上限の宣言**であって「必ず流用しろ」ではない。**しかも本経路が返すのは「有無」ではなく件数と現在版であり、204 では表現できない。★一覧のボタンは延期中でも件数が要るため、告知の有無と件数を同じ 1 本から取ることで出どころを 1 つに保つ** |
| **2** | **★代替（`GET /api/combos?affected_by_game_update=true&limit=1` の `count`）は原理的に不可能である**——`internal/api/combo/handler.go:383` が `Count: len(items)`（そのページの件数）であり、`internal/repository/combo/repository.go` が `limit <= 0 → 100` / `limit > 1000 → 1000` に丸める。**⇒ 総数は取れない。この代替の検討は打ち切ってよい** |
| **3** | **★★判定式を共有した `COUNT` の新設が要る。式を書き写さないこと**——現行 repository は `LIMIT` 付きの `SELECT` しか持たない。**`CHANGE-159` §2 が「判定式は 1 か所しかなく、SELECT の派生列と一覧の WHERE が同じ式を共有する」と明言しており、ここを崩すと §0.3 の再発になる** |
| **4** | **★`games.current_data_version` の初の HTTP 露出である**（独立した請求項目）。副産物としてコンボ詳細に「基準 2026.08.03.01（現在 2026.09.10.01）」と出せる |
| 5 | **★`postpone` が本文を取らないのは、`acknowledge-version` が「版数をクライアントから受けない ⇒ 任意の版へ進めたことにできない」を明示的に選んだ**（`CHANGE-159` §1.1）**のと同型にするため** |
| 6 | **★語を `/ack` ではなく `/postpone` にした**（「永久に既読」と「次の版まで延期」は意味が違う） |
| 7 | **★1 本にまとめる代償**——落ちると告知とボタンが同時に失敗表示になる。**許容する**（再試行 UI が 1 か所で済む利点の裏側） |

**★延期の保存先＝サーバ側のファイル。** `filepath.Dir(dbPath)` 直下（＝移行告知 `.migration-notice.json` と同じ場所）へ `.game-update-notice.json` を置き、`{"postponedForVersion": "2026.09.10.01", "at": ...}` を持つ。**`games.current_data_version` と一致する間だけバナーを抑止する。**
**★決め手＝コンボは利用者ごとの所有物ではない**（`combos` に `user_id` が無く、所有者を持つのは `tags` だけ。サービス層の `UserID` にも「**誰として保存するか**。コンボ本体の所有者ではない」とコメントが在る）。**⇒ 影響コンボの集合はアプリ全体で 1 つであり、その告知の延期もアプリ全体が素直である。**
**★★LAN で 1 人の延期が全員に効くことを許容する。ただし条件が 1 つ——延期が抑止するのはバナーだけであり、一覧のボタンは抑止しない**（これが「袋小路にならない」の実体。**★ボタンまで消す設計にすると LAN では許容できない。ここが分水嶺なので `DES-005` へ 1 行として残すこと**）。
**★マイグレもブラウザストレージ台帳も消費しない**（DB 列案・localStorage 案を落とした結果）。
