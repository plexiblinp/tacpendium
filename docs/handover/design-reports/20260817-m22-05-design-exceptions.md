## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★本節は `CHANGE-116` §2 が製造へ求めた成果物そのものである。** 同節は改訂 `DES-002` §4.4 へ「CORS の as-built（許可 Origin / メソッド / ヘッダ / `AllowCredentials`）」「本アプリの主経路はクロスオリジンではない」「境界を守っているのはバインドである」を書くと予告している。**⇒ 以下がその実測値である。**
>
> **★行番号はすべて本サブの HEAD 基準**（`cors.go` へコメントを 5 行足したため、着手前の行番号とは 27 行目以降が 5 行ずれる）。**完了報告 §8 が同じ表を持つが、親は完了報告を読まないため本節へ再掲する。**

### 1-1 許可 Origin の実値（**§4.4 の明文と食い違う。差は両方向にある**）

`cmd/combomgr/main.go:495-512`（`buildAllowedOrigins`）が**起動時に 1 回だけ**構築し、`internal/api/middleware/cors.go:20-23` が `map[string]struct{}` へ凍結する。**リクエスト時に NIC を再列挙しない。**

| モード | 許可 Origin | 本数 |
|---|---|---|
| `local`（既定） | `http://localhost:{port}` ／ `http://127.0.0.1:{port}` | **2 本** |
| `lan` | 上記 2 本 ＋ `http://{SelectPrimaryLANIP()}:{port}` | **3 本** |

- **すべて `http://`**（平文 HTTP が前提＝契約 F-3）。**ワイルドカード不使用・完全一致**（スキーム＋ホスト＋ポート）。**空リストは全拒否を意味する。**
- **実ポートに追従する**——`main.go:211-235` が listener を確保して `cfg.Server.Port = actualPort` を確定させた**後**に呼ぶ。⇒ ポート競合フォールバック（既定 47318〜47337）後も Origin が外れない。
- **`lan` で代表 LAN IP が見つからないと起動を中止する**（`netutil.ErrNoLANIP` → `main.go:503-509` が fatal）。**★§4-2 でこの挙動が効く。**
- **★食い違いの内訳**（§2-1 で裁定を仰ぐ）——§4.4 の明文「同一ホスト（サーバー自身の IP:PORT）のみ許可する」に対し、as-built は **`localhost` という名前も許可している点で広く**、**複数 NIC のうち代表 1 本しか許可しない点で狭い**。
- ⇒ **`DES-002` §4.4 の当該文を、上表の実値へ書き直してほしい。**

### 1-2 ★**許可外 Origin をサーバ側でブロックしない。これは意図した設計である**（**最重要**）

`cors.go:48,67` — 許可外 Origin の要求は **CORS 応答ヘッダを付けないだけで `next(c)` へ通る**。止めているのはブラウザ側であって、サーバは処理する。

**実測**（実バイナリ・`curl`。完了報告 §4 にコマンドと出力）:

```
POST /api/tags  Origin: http://127.0.0.1:47500   → 201 ＋ Allow-Origin / Allow-Credentials / Vary
POST /api/tags  Origin: http://192.168.1.50:47500 → 201、CORS ヘッダなし   ← 許可外だが到達する
POST /api/tags  Origin: http://evil.example       → 201、CORS ヘッダなし   ← 同上
```

**★これを「実装漏れ」と読んで締めると 2 つ壊れる。**

| 壊れるもの | 理由 |
|---|---|
| **`curl` 相当の復旧経路** | `DES-002` §8.2 の歯止め b。**Origin を送らない経路**であり、非 ASCII パスワードを決めた利用者の唯一の帰り道 |
| **Vite dev proxy 経由の開発と E2E** | `web/vite.config.ts` は `changeOrigin: false` のためクライアントの `Origin` を backend へ**逐語で転送する**——**dev は `http://localhost:5173`、E2E は `http://localhost:5273`**（`web/playwright.config.ts` の `BASE_E2E_VITE_PORT`）。**`buildAllowedOrigins` はそのどちらも生成しない。** ⇒ **いま dev と E2E が動いているのは、この「通す」実装のおかげである** |

- ⇒ **`DES-002` §4.4 へ「許可外 Origin はサーバ側で拒否しない（CORS ヘッダを付けないことでブラウザ側が拒否する）。これは意図であり、`curl` 相当の経路（§8.2 歯止め b）と Vite dev proxy 経由の開発・E2E を守るためである」を明文化してほしい。**
- **★書かないと次の担当が締めに行く。** 製造が実測で「締めると壊れる」と確かめた当のものであり、**しかも締めた結果は `localhost` で操作している限り 1 度も現れない。**

### 1-3 CORS の応答ヘッダとプリフライトの実値

| 項目 | 実値 | 実装 |
|---|---|---|
| 許可メソッド | `GET, POST, PUT, DELETE, PATCH, OPTIONS`（プリフライト応答時のみ） | `cors.go:26` |
| 許可ヘッダ（既定） | `Content-Type, Origin, Accept, X-Requested-With`。**ただし `Access-Control-Request-Headers` が来ればそれを逐語エコーする**。既定値は ACRH 空時のフォールバックにすぎない | `cors.go:32,55-60` |
| `Access-Control-Allow-Credentials` | **`"true"`。許可 Origin のときだけ。** `AllowOrigins` に `*` を使っていないため**組み合わせは成立している** | `cors.go:46` |
| `Vary: Origin` | **許可 Origin のときだけ**付与。許可外・Origin 不在の応答には付かない | `cors.go:45` |
| `Access-Control-Max-Age` | `600` | `cors.go:33` |
| OPTIONS | **すべて 204 で早期 return し、`next` を呼ばない** | `cors.go:64` |

- **★OPTIONS の早期 return が、入場ゲートを有効にしてもプリフライトが 401 にならない理由である**（`main.go:288-290` が CORS を Auth より前に置く根拠）。**⇒ ミドルウェアの順序が守っている性質であり、順序を変えると壊れる。** §4-1 も参照。
- ⇒ **`DES-002` §4.4 へ上表を明文化してほしい。** 現行 §4.4 には「CORS を適切に設定する」しかなく、実体は `cors.go` にしかない。

### 1-4 ★`allowedHeaders` の既定値は as-built の説明として **二重に古い**（新規発見）

`cors.go:32` の既定一覧は、**撤回された `X-Requested-With` を挙げている一方、実際にフロントが送っている独自ヘッダ `X-User-Id` を挙げていない。**

- `X-User-Id` の付与元は `web/src/lib/http-interceptor.ts:17,107-109`（`window.fetch` を包むラッパ。`M22-02` の as-built）。
- **実害は無い**——主経路は同一オリジンでプリフライトが飛ばず、仮に飛んでも ACRH が逐語エコーされるため通る（`cors.go:55-60`）。
- **★しかしこの一覧を「送ってよいヘッダの正本」として読むと誤る。**
- ⇒ **`DES-002` §4.4 に許可ヘッダを書くときは、この一覧をそのまま転記しないでほしい。** 「既定値は ACRH 空時のフォールバックであり、実運用では ACRH が逐語エコーされる」を併記するのが正確である。

### 1-5 ★**本アプリにクロスオリジン経路が存在しない**（「締めない」判断の根拠）

| 経路 | ブラウザから見た Origin 関係 | 根拠 |
|---|---|---|
| 本番（単一バイナリ） | **同一オリジン** | SPA を Go が embed 配信し、API は同じ host:port |
| 開発（Vite dev・`:5173`） | **同一オリジン** | `web/vite.config.ts` が `/api` を proxy、`web/src/lib/api-client.ts:4` は `API_BASE = ""` |
| E2E（Playwright・`:5273`） | **同一オリジン** | 同上（Vite 経由） |
| スマートフォン | **同一オリジン** | `http://<LAN IP>:47318` を開き、同じ host:port の `/api` を叩く |

**帰結**——ブラウザは同一オリジン要求に CORS を適用せず、**プリフライトも飛ばない**。⇒ `AllowCredentials` / `Vary` / `Max-Age` の設定は**実運用では 1 度も評価されない経路**にある。

**★とくに §4.1-3（指示書）が懸念した「LAN IP は 1 つとは限らない」問題は実害を持たない。** 副 NIC の IP・mDNS 名・ポート転送のいずれで開いても、**その端末から見れば同一オリジン**であり CORS は発動しない。

- ⇒ **`DES-002` §4.4 へ「本アプリの主経路はクロスオリジンではない。⇒ CORS が実際に評価される場面は限られる」を明文化してほしい**（`CHANGE-116` §2-c の予告どおり）。

### 1-6 `server.mode` は境界の構成を変えない（**バインドが守っている**）

`main.go:285-296` に条件分岐は 1 つも無く、**ミドルウェアの登録本数・順序・構成は `local` / `lan` で同一**である。`cfg.Server.Mode` を読むのはリポジトリ全体で 5 箇所のみで、ミドルウェアに影響するのは **`buildAllowedOrigins` の引数の値だけ**（許可 Origin が 2 本か 3 本か）。`internal/api/middleware/` の 5 ファイルはいずれも設定としての `mode` を読まない。

- ⇒ **`DES-002` §4.4 へ「境界を守っているのはバインドアドレス（`local`=`127.0.0.1` / `lan`=`0.0.0.0`）であって CORS ではない。⇒ `server.mode` で CORS/CSRF の構成を変えない」を明文化してほしい**（`CHANGE-116` §2-d の予告どおり）。**★書かないと「ローカルだから緩めてよい」と読んで分岐が生まれる**（`CHANGE-116` §2 自身の警告）。

### 1-7 `CHANGE-116` 案 A の as-built（**撤回の記録に要る**）

- **サーバ側に検証は 1 つも足していない**（`internal/` の CSRF 差分 **0**）。
- **フロント側の付与は 6 経路すべて撤去した**（`configApi.ts` の `PUT /api/config` ／ `userApi.ts` の POST・PATCH `/api/users` ／ `authApi.ts` の POST `/api/auth/{login,logout,password}`）。**指示書 §1.2 の「`PUT /api/config` の 1 経路だけ」は陳腐化していた。**
- **`cors.go:32` の応答側許可リストには残した**（§1-4・§3-2）。
- ⇒ **`DES-002` §4.4 の補助対策は、`CHANGE-116` §4.2 のとおり「実装しなかった」ではなく「要らないと判断した」＋理由（§4.1 の 1〜3）で書いてほしい。** **★製造側の完了報告にも同じ文言で書いてある。**

## §2 契約・設計に反する独自判断（★親の受理／却下の裁定を要する）

### 2-1 ★`DES-002` §4.4 の「同一ホストのみ許可」と as-built が食い違っており、**製造は as-built 維持を選んだ**

| 項目 | 内容 |
|---|---|
| **何に反したか** | **`DES-002` §4.4 の明文**——「Origin は同一ホスト（サーバー自身の IP:PORT）のみ許可する」 |
| **as-built** | §1-1 のとおり **2〜3 本**。**`localhost` という名前も許可**（サーバー自身の IP ではない）し、**複数 NIC のうち `SelectPrimaryLANIP()` の代表 1 本しか許可しない**（`cmd/combomgr/main.go:496-511`） |
| **いつからか** | **本サブの変更ではない。** `buildAllowedOrigins` は既存実装であり、**製造は 1 文字も変えていない**（`git diff 1b50017..HEAD -- cmd/combomgr/main.go` は空） |
| **なぜそう判断したか** | §1-5 のとおり**主経路がクロスオリジンでないため、許可リストの内容は主経路の可否を左右しない**。⇒ 「同一ホストのみ」へ厳格化しても**得るものが無く**、`localhost` を外せば自機のブラウザから使えなくなる。指示書 §9.2-3 が許可 Origin の組み立て方を製造裁量とし「**迷ったら塞がない側**」を定めているため、**現状維持を採った** |
| **裁定を仰ぐ点** | **(a)** §4.4 の明文を as-built へ合わせて書き直す（＝製造の判断を受理する）か、**(b)** as-built を §4.4 へ合わせて厳格化する（＝差し戻す）か。**★製造の推奨は (a)** ——(b) は §1-2 の「通す」実装と組み合わせても得るものが無く、`localhost` を外す実害だけが出る |

> **★裁量の範囲内ではあるが §3 へ混ぜなかった理由**——**結果として「設計書の明文と実装が食い違ったまま」が残る**。指示書が裁量と書いていることは、設計書の明文が失効していてよいことを意味しない。**⇒ 親が明文を直すまで乖離は消えない。**

**※ 上記以外に §2 該当なし。** とくに次はいずれも違反ではない——案 A に従ってサーバ側検証を足さなかったこと（`CHANGE-116` の承認済み方式）／ `web/src/features/user/` `features/auth/` を触ったこと（指示書 §2.1 の予見一覧に無いが §2.2 の禁止列にも無く、同節の注記が「一覧に無いファイルでも禁止列に当たらないなら触ってよい。ただし理由を完了報告に書く」と定めており、書いた）／ `internal/api/auth/cookie.go` のコメントを直したこと（§3-2 を参照。§2.2 の注記が「挙動の凍結であってバイト列の凍結ではない。失効した記述の是正は妨げない」と明記）。

## §3 製造の判断

### 3-1 開発者へ確認して確定した点

| # | 論点 | 確認の経緯 | 確定 |
|---|---|---|---|
| 1 | **フロント 6 経路の `X-Requested-With` を撤去するか残すか** | **指示書 §4.2-2 が「どちらでもよい」、チェックリスト §0.3/§10 が「残しても軽微」と定めており、`CLAUDE.md` §9 のハード列「正解がなく好みが決め手」に当たるため、判断材料を提示して確認した** | **撤去**（2026-08-16） |

| 3 | **`make e2e` が落ちたときの切り分け方針** | 開発者から「いくつかシナリオがエラーになり、個別実行したら解消することが時々ある」と提示された | **落ちたシナリオを個別実行して切り分ける**（実際に 1 件で適用。§4-5） |

**★#1 の判断材料**（親が同型の判断をするときの参考として残す）——挙動はどちらでも同一（サーバが読まないため）。**撤去を推した理由は機能ではなく記述である**: (a) 設計卓が §4.4 から補助対策を撤回した後もコードだけが「CSRF 対策」と主張し続ける、(b) `authApi.ts:48` のコメントが `X-Requested-With` を「**CSRF 第一対策の踏襲**」と書いており**案 A 確定以前の時点で既に誤りだった**（第一対策は `SameSite=Strict`）、(c) **3 ファイルすべてが「configApi と同じ」を理由に足されており複製が続く**（`configApi` → `M22-01` が `authApi` → `M22-02` が `userApi`）、(d) §4.9 の走査が今後ずっと再判定を要求する。

### 3-2 推測で進めた点（指示書 §9.2 の裁量事項）

| # | 判断 | 理由 |
