## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★本サブは `docs/design/` に差分を出さない契約であり、DES 側へ反映すべき仕様は無い。** ただし**運用ルール面の文書へ反映が要る確定事項が 3 件**あるため、宛先を明示して挙げる。

### 1-1 ★`go install` でツールを入れるときは `GOTOOLCHAIN` の固定が要る（**環境によって壊れる**）

**確定した事実**: `go install pkg@version` は **そのツール自身の `go.mod`** からツールチェーンを決める。**素の `go` が本体コードより古い環境では、本体コードを型検査できないバイナリができる。**

| 実測値 | 値 |
|---|---|
| クラウド実行環境の**素の** go | **`go1.24.7`**（`GOTOOLCHAIN=local go version`） |
| プロジェクト内で選ばれる go | `go1.26.4`（`go.mod` の `go 1.26.4` による toolchain 自動取得） |
| `go install govulncheck@v1.1.4`（素のまま） | go1.24 でビルド ⇒ **`package requires newer Go version go1.26 (application built with go1.24)`** で解析不能 |
| `@v1.7.0` へ上げた場合 | **同じく失敗**（v1.7.0 の go.mod が go1.25 を要求し go1.25.13 が降ってくる）。**版を上げても直らない** |
| `GOTOOLCHAIN="$(go env GOVERSION)"` を付けた場合 | **成功**（DB 取得段階まで到達する） |

実装: `.claude/hooks/session-start.sh:122-125`。**devContainer は素の go が 1.26 系のため従来から正しくビルドされており、本指定は無害**（同じ版が選ばれるだけ）。

**⇒ 反映依頼**: `CLAUDE.md` §11（実行環境・コマンド）または `docs/process/remote-ops.md` へ **「クラウド実行環境の素の `go` はプロジェクトの版より古い。Go 製ツールを `go install` で入れるときは `GOTOOLCHAIN` を固定する」** を 1 行。**次に Go のツールを足す担当が同じ穴に落ちる。**

### 1-2 ★クラウド environment の設定は**リポジトリからは変えられない**（2 種類あり、役割が違う）

**確定した事実**（公式ドキュメント実査）:

| 経路 | 置き場 | 何に効くか | キャッシュ |
|---|---|---|---|
| **SessionStart hook** | **リポジトリの `.claude/settings.json`** | **ローカルもクラウドも**。resume 含む毎セッション実行 | **載るかは未確定**（§4-5） |
| **Setup script** | **claude.ai/code の環境ダイアログ**（リポジトリ外） | **クラウドのみ**。Claude Code 起動前・初回のみ | **完了後にスナップショットされる**と明記あり |

## §7 教訓（retrospective 行き）

> **★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、実施者は設計担当。

### 7-1 ★「緑を返した経路が、確かめたい対象を通っていなかった」——`check-artifact-integrity.sh` §4.1 の再演

**本サブで最も高くつきかけた誤りである。** 起動確認で `govulncheck -version` が `No vulnerabilities found.` を返したのを「DB へ到達できた証拠」と読み、**一度は「到達可否は環境ごとに違う」という誤った結論を文書化して push した**（`39511ed`）。開発者の「設定を一切変更していない」という申告で再検証し、撤回した（`5058924`）。

**実体**: `govulncheck -version` は**パッケージ引数が無く走査対象がゼロのため DB を引かない。** `DB:` 行は設定値をそのまま印字しているだけで到達の有無と無関係、`No vulnerabilities found.` は走査対象ゼロの結果である。**403 の環境でも同じ出力になる。**

**★判定材料は出力の中に在った**——`govulncheck` は DB 取得に成功したときだけ **`DB updated: <日時>`** を追加する（成功時のみ印字。失敗は握り潰される）。**⇒ 到達可否はこの行の有無に現れていた。「出ている行が期待どおりか」だけを見て「出るはずの行が出ていない」を見なかった。**

**機構化案**:
- **目的別にコマンドを固定して文書へ書く**——版の確認は `govulncheck -version`、**到達可否は `govulncheck ./...` か `curl`**、簡易判定は **`DB updated:` 行の有無**（`DB:` 行では判定できない）
- **★既存の記録を覆す結論を出すときは、その結論だけを狙った独立の実測を 1 本足してから書く。副次的に出た出力の解釈で覆さない**
- **★照合は「期待される行の集合」に対して行う。** 欠落は目に入りにくい

### 7-2 ★誤りは実行側ではなく「検証手順を書いた側」に在った

起動確認プロンプトを書いたのは製造であり、そこに `govulncheck -version` を指定していた。**確認担当はそのとおり正しく実行した。** さらに製造は**自セッションで同じ出力を得ていながら `head -3` / `head -4` で末尾を切り落としており、`No vulnerabilities found.` の行を一度も見ていなかった**——見ていれば「403 なのにこの行が出るのはおかしい」と気づけた。**矛盾に気づく機会を自分で潰していた。**

**機構化案**: **出力を切る（`head` / `tail`）ときは、切った先に判定材料が無いことを確かめる。** とくに**他者へ渡す検証手順に含めるコマンドは、切らずに全文を一度見てから確定する。**

### 7-3 ★「記録が消える方向の誤り」は他の誤りより害が大きい

誤った観測に基づいて **`followup-backlog` §J の項目を閉じる方向の判断材料まで提示していた。** 確立された記録（`curl` の実測付き）と矛盾する観測を得た時点で、**疑うべきは記録ではなく新しい観測のほうだった。**

**機構化案**: **§J や followup を閉じる方向の提案には、閉じる根拠を独立に 1 本測ってから書く**というルールを停止規律の周辺に置く。

### 7-4 版を上げても直らない依存がある——「新しくすれば直る」の反例

`govulncheck` の解析失敗に対し、**最新版 v1.7.0 へ上げても直らなかった**（v1.7.0 の go.mod が go1.25 を要求し、go1.25.13 が降ってきて同じ結果になる）。**直ったのはビルドに使うツールチェーンを固定したときだけ**であり、**版は最初の v1.1.4 に据え置いたまま解決した。**

**機構化案**: **「版を上げる」を試す前に、失敗しているのが「そのツールの中身」なのか「ビルド/実行の環境」なのかを分ける。** 本件のエラー文（`application built with go1.24`）は**環境側だと最初から言っていた。**

### 7-5 hook を足すと、既存の壊れていた品質ゲートが動き出す

`node_modules` が揃った結果、**これまで黙って失敗していた既存 hook 2 本が実際に動き出した**——`post-edit-check.sh` の `tsc --noEmit`（`.ts`/`.tsx` 編集ごと）と `stop-test.sh` の `make test-web`（実測 91.7 秒）。**壊れていた品質ゲートが機能を取り戻す変化であり意図した方向だが、体感が変わる。**

**機構化案**: **「前提を揃える」変更は、その前提に依存していた仕掛けを同時に目覚めさせる。** 何が目覚めるかを着手前に数えて完了報告へ書くこと。**「急に遅くなった」と感じた次の担当が原因に辿り着けるようにする。**

### 7-6 失効した記述は、自分の差分が作ることもある

`.claude/settings.json` の `_hooks_comment` は hook の安全性を「読み取り系の検査 + テスト実行のみ。**ネットワーク無し**」と書いていた。**本サブの hook は `pip` / `go install` / `pnpm install` でネットワークへ出るため、この記述はその瞬間に失効した。** 同じ手番で書き換えた（現在の担保は「ソース改変なし・git 書込なし・取得先は公式レジストリのみ・`sudo` なし・パイプ実行なし」）。

**機構化案**: **既存の安全性・不変条件を述べた文を、自分の差分が偽にしていないかを確認する。** grep で「無し」「のみ」「しない」を含む近傍の記述を当たるのが安い。
