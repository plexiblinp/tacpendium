## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★いずれも「指示書・`CHANGE-113` に書かれていなかったので確定させた」ものである。** 指示書・設計書と異なる判断を下したものは §2 に分けてある。

### 1-1 401 の捕捉と `X-User-Id` の付与を、`window.fetch` のラッパ 1 か所へ集約した

指示書 §4.3-2 は「401 の判断を 1 か所に置く」としか言っていない。**「1 か所」を成立させられる層は実測では 1 つしかなかった。**

`web/src/lib/http-interceptor.ts` を新設し、`main.tsx` で render 前に 1 度だけ設置する。**理由は API 呼び出しが `lib/api-client.ts` の `fetchJSON` へ一本化されていないこと**——実測で 3 系統が併存する。

1. `fetchJSON`（`Error("HTTP 401: <生ボディ>")` を投げる）
2. `web/src/features/tag/api/tagApi.ts` の独自 `request`（`TagApiError` に `.status` を持つ）
3. `web/src/features/combo/api.ts` ほかの**素の `fetch` 8 か所**

- **同ラッパが `X-User-Id` の付与も担う**（同じ理由で、付与も 1 か所になる）。**`/api/auth/*` は除外**（ログイン失敗の 401 を巻き込むと入力欄が消えるため）
- **応答は改変しない**。`status` も本文も素通しし、副作用は購読者への通知だけ。**新しいリクエストを一切発行しない**
- 併せて `QueryClient` に **401 の再試行抑止**を入れた（既定の 3 回再試行は 401 では空転し、`M22-01` の E2E が実測した**約 7 秒**の待ちの原因だった）
- ⇒ **`SUPP-001` §5.3（フロント構成）へ「横断関心（認証・利用者の供給）は `lib/` の fetch ラッパ 1 か所に置く」を明文化してほしい。** **★これを書かないと、次の担当が `fetchJSON` にだけ足して 3 系統のうち 2 つを取りこぼす。**

### 1-2 ログイン画面・ユーザー選択画面は **URL を持たない条件表示**にした

指示書 §4.8-3 / §4.8-5 は振る舞い（更新で選択が消える・済んだ画面へ戻らない）だけを定め、**実現の形は指定していない**。

**採った形＝条件表示（オーバーレイ）。ルートを持たせない。**

- **理由**: `CHANGE-113` §7-1 の案 (α)〔選んだ利用者は保持しない〕を満たすには、選択を**メモリ上の React state だけ**で持つ必要がある（Cookie・ブラウザストレージ・サーバセッションはいずれも再読込を跨ぐ）。一方 URL を持たせると、戻る・進むで「済んだ画面」へ戻り §4.8-5 に反する。**⇒ 条件表示なら両立する唯一の形だった**
- `AuthGate` は **`App` の外側**に置いた（`main.tsx`）。`App` は先頭で保護対象の `GET /api/config` を呼ぶため、内側に置くと未認証時に読めない問い合わせを投げる
- ⇒ **`DES-005` §2 の画面一覧に載せるか（＝画面番号を振るか）は設計卓の判断。** **★URL を持たないため「画面」として番号を振ると、他の行と性質が揃わない。**

### 1-3 選ばれていないときの `userID` は **`users.id` の最小値**へ倒す

指示書 §9.1-2 が「推測で進めてはいけない事項」に挙げていた項目。**採った案＝`X-User-Id` が無い・壊れている場合は `SELECT MIN(id) FROM users`。**

- 実装: `internal/api/middleware/user.go` の `resolveUserID` → `usersvc.DefaultUserID`
- **理由**: ヘッダを送らない呼び出し元が実在する（**既存の E2E・`curl`・利用者が 1 人で選択画面を出さない場合**）。既定へ倒すと**いままでの挙動と 1 バイトも変わらない**（既存環境の `users` は `id=1` の 1 行のみ＝完了報告 §2 の実測）
- **★解決に失敗しても要求を止めない**（`0` のまま下流へ渡す）。ここで 500 にすると、利用者の面と無関係な全 API が巻き添えで落ちる
- **★壊れたヘッダを黙って既定へ倒す**（ログを出さない）。詐称された値を投げる相手に対して**リクエストごとにログが出る**のを避けるため（`VAL-N04` が「リクエストごとに検査・警告しない」を採ったのと同じ理由）。レビュー低指摘を理由付きで不採用にした
- ⇒ **`DES-002` §8 へ「利用者の指定が無いときの既定」を明文化してほしい。** **★「認証ではない」ことの帰結として、無指定を拒否しない設計になっている。**

### 1-4 送信経路は **`X-User-Id` ヘッダ**（CORS は不変）

ヘッダ名・付与層は設計書・指示書のいずれにも無い。**`X-User-Id`（定数 `mw.UserIDHeader`）を採った。**

- **★`cors.go` の変更を要さなかった**——プリフライトは `Access-Control-Request-Headers` を**エコーバックする**（`internal/api/middleware/cors.go:52-56`）。静的な `allowedHeaders` は要求ヘッダが空のときのフォールバックである。**⇒ CORS の diff 0。`M22-05` と衝突しない**
- ⇒ **`DES-002` §4.4 へ書くかは設計卓の判断。** 書くなら「**認証ではない**ため、詐称は脅威モデルに入っていない」を併記しないと、次の担当が署名を足そうとする

### 1-5 パスワードの初回設定は **「検証子の保存」と「有効化」の 2 本を続けて呼ぶ**

**`POST /api/auth/password` は検証子しか書かない**（有効化フラグは `PUT /api/config` の担当＝`M22-01` の as-built）。**初版はこれを配線しておらず、パスワードを決めても入場ゲートが効かなかった**（レビュー H-2）。

- **⇒ `PasswordSetForm` が設定成功後に `PUT /api/config` で `security.passwordEnabled = true` にする形にした**
- **★順序が要る**——検証子が未設定のまま有効化すると `VAL-N03` が 422 で拒否する
- **★有効化に失敗したら完了扱いにしない**（部分的成功を隠さない）
- **`CHANGE-113` §3.4 の文言**「ほかの機器からこのアプリを開くときに、このパスワードを入力してもらいます」は、**これで初めて事実になった**
- ⇒ **`DES-002` §8 へ「初回設定は有効化まで行う」を書いてほしい。** **★2 本に分かれていることは API の都合であり、利用者から見れば 1 操作である。**

### 1-6 既定タグ 3 件を、利用者作成と**同一トランザクション**で生成する

指示書 §4.5-6 は「生成する」としか言っていない。**件数・名前・色・原子性を確定させた。**

- **3 件**＝`使用中` / `練習中` / `頻度低下`、カテゴリ `mycombo_status`、色 `#10B981` / `#3B82F6` / `#6B7280`
- **出典は `migrations/000007_seed_initial_tags_user1.up.sql` の逐語**と突き合わせ、`internal/model/tag.go` の `DefaultMyComboStatusTags` へ定数化した（**記憶で書いていない**）
- **原子性**——`TestCreate_IsAtomic` が「タグ生成に失敗したら利用者も残らない」を固定。**生成しないと 2 人目はマイコンボのステータスを 1 件も引けず機能不全になる**
- **★`migrations/000007` のヘッダは「M6 着手時にウィザード経由生成へ切り替える」と宣言していたが、適用済みマイグレのため直せない。** 本サブで**実体だけが追いついた**。⇒ **ファイルの記述が恒久的に取り残される**（`M22-01` 横断課題 2 と同じ対象）
- ⇒ **`SUPP-001` §3.6 の「初回起動ウィザードで生成」を「利用者の作成時に生成」へ改めてほしい。**

### 1-7 ウィザードは **8 段**（LAN 無効時は 6 段）

`DES-005` §5.1 のステップ構成は **7 段で Step 6 = パスワード設定**だが、**実装の Step 6 は LAN 接続情報**（`Step06LanInfo.tsx`。本サブ以前からの as-built）だった。

- ⇒ **`DES-005` §5.1 を 8 段（LAN 無効時 6 段）へ改訂してほしい。**

### 1-8 ★`combo_tags` に「置換は自分の紐づけだけに効く」という契約が生まれた（`D-405` 案 B）

- ⇒ **`DES-003` §3.7 か `DES-002` §? へ「`combo_tags` の置換は利用者スコープである」を明文化してほしい。** **★次に同表を触る担当が全消し＋挿入へ戻すと、他人のデータが静かに消える。**

#### 日本語入力で具体的に起きうること（重い順）

1. **★正規化のゆれ（NFC / NFD）**——検証子は**受け取ったバイト列**に対して計算する（`password.go:52` が `password string` をそのまま `pbkdf2.Key` へ渡す）。**`が` は NFC（U+304C）と NFD（`か`＋U+3099）の 2 通りがあり、見た目が同一なのにバイト列が違う。** **⇒ 決めた端末と入れる端末で正規化が違うと、正しく打っているのに永久に入れない。** **★本アプリは「ほかの機器から開く」ことが目的であり、この経路は例外ではなく主経路である。** しかも症状は「パスワードが違います」だけで、**利用者からは原因が絶対に分からない。**
2. **全角・半角の取り違え**——`Ａ` と `A`、全角スペース（U+3000）と半角スペース。**マスク表示では見分けられない。**
3. **★マスク欄で IME が使えない可能性（要確認）**——初回設定欄は**表示が既定**（`D-396`）で IME が使えるが、**ログイン欄はマスクが既定**（`D-397`）。`<input type="password">` では OS / ブラウザが IME を無効化することがある。**⇒ 日本語で決めると、ログイン画面で「表示」を押すまで打てない事態が起こりうる。** **★本環境にブラウザ実行系が無いため実機でしか確かめられない。裏取りできていないので「要確認」として出す**——**開発者の実機確認が要る。**
4. **前後の空白が落ちない**——`trim()` はサーバ・画面のどこにも無い（実測 0 件）。**IME の確定操作で末尾に空白が入っても気づけない。**
5. **長さの下限・上限が無い**——**1 文字でも通る。** 上限も `BodyLimit` も無いため巨大な本文をそのまま受ける。**★ただし CPU は長さに比例しない**——PBKDF2 は HMAC の鍵正規化で長い鍵を 1 度ハッシュしてから 600k 回反復するため、**反復のコストは増えない**。効くのはメモリと帯域である。**⇒ 5 は 1〜4 より軽い。**

#### なぜ製造単独で直せないか（開発者の判断は正しい）

- **`DES-006` §7 の VAL 表に行を足す必要がある。採番は設計卓の手番である**（`VAL-N04` まで使用済み）

#### 設計卓への案（★判断ではなく材料である）

| 案 | 内容 | 効き方 | 代償 |
|---|---|---|---|
| **(a) 正規化して受ける** | 保存時・照合時とも **NFC へ正規化**してから導出する | **1 を根から消す。** 既存の検証子はそのまま使える（NFC で打てば一致する） | **★`golang.org/x/text/unicode/norm` の direct 昇格が要る**（`CLAUDE.md` §6・先例 `M20-07` / `D-382`）。2・3・4 は残る |

## §7 教訓（retrospective 行き）

> **★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、**実施者は設計担当**（反映担当の廃止＝2026-08-11 に伴う）。

1. **★「既に受け口がある」は、対象を数えてからでないと言えない。** 指示書 §4.5-2 は「サービス層・リポジトリ層は既に `userID` を受け取っている」としたが、真だったのは**タグとプリセットだけ**で、コンボは受け取っていなかった。**⇒ 「既に〜になっている」型の前提は、指示書に書く前に対象の全数を数えること。** チェックリストがその前提を検査項目に昇格させると、**正しい実装を違反と読む検査**になる。
2. **★接続表（中間テーブル）は、両端のスコープが違うと固有の穴が生まれる。** `combo_tags` はコンボ（共有）とタグ（個人）を繋ぐが、利用者の列を持たない。**読み出しを絞ると、全消し＋挿入が他人の紐づけを消す。** **⇒ 「絞り込み」と「置換」は必ず同じ手番で入れる。** 片方だけだと、**双方の画面に何も出ないまま他人のデータが消える**という最悪の形になる。設計時に「この表の両端のスコープは同じか」を問うだけで防げる。
3. **★モックしたハンドラテストは「値が届いているか」の網にならない。** 本サブは `userID` の供給元を差し替えたが、`internal/api/tag/handler_test.go` はサービスをモックしており、**供給元を定数へ戻しても緑のままだった**。レビューが見つけた `H-1`（API 層が `userID` を一度も渡していない → タグ付きコンボの保存が必ず 500）も同じ構造で、**サービス層のテストは入力を直接組み立てるため API 層の欠落を踏まない**。**⇒ 値の供給元を差し替えるサブでは、経路ごとに「HTTP から実 DB まで」を 1 本ずつ通すこと。** 破壊確認は「SQL の形」ではなく「配線」を的にする。
4. **★「アプリからは復旧できないが、ファイルを編集できれば復旧できる」型の設計は、手順を 1 度通してみないと成立を確認できない。** 本サブは復旧手順を 3 か所（`CHANGE-113` / `config.toml.example` / 案内文）に書いたが、**3 つとも同じ思い込みを写しており、実際には復旧できなかった**（`password_hash` が残ると変更フォームが出る）。設計・実装・製造が独立に同じ穴を作っている。**⇒ 「最後の逃げ道」を設計したら、その逃げ道を実際に歩く手順テストを 1 本置くこと。**
5. **★画面ごとに「その画面へ来られる人は誰か」を先に置くと、機能の要否がその場で決まる。** 「パスワードが分からないとき」に絶対パスを出す案は、設計（`CHANGE-113` §3.8）も製造（設定画面なら認証済みだから出せる、という提案）も出したが、**その案内が要る人はログイン画面に居て設定画面へ入れない**——この一点で不要と決まった。**⇒ UI の要求を書く前に「その画面の到達条件」を 1 行書く。**
6. **★「1 人運用の画面をいままでと変えない」は API だけの話ではない。** 最重要ゲート 2（無効なら何も増えない）は API の非回帰として書かれていたが、**UI にも同じ形で当てはまる**。ヘッダの利用者表示を「2 人以上のときだけ」にしたことで、**既存 E2E が 1 人構成のため非回帰が自動的に成立する**という実利もあった。**⇒ 非回帰ゲートは「サーバ」と「画面」の両方へ翻訳して書く。**
7. **★横断関心を「1 か所に置く」と書くときは、1 か所が実在するかを実査させること。** 本サブの指示書は「401 の判断を 1 か所に置く」としたが、API 呼び出しが 3 系統に散っており、**`fetchJSON` に足すと 2 系統を取りこぼす**状態だった。**⇒ 「1 か所」が成立する層は実装によって違う。** 指示書は層を指定せず、実査項目として「どこなら 1 か所になるか」を問う形にするのが正しい。
