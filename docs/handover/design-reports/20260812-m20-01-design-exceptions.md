## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1 削除・改称の波及は「旧識別子の文字列」だけでなく **「個数」** にも及ぶ

**確定した規約**: **列挙値を削除・改称するサブでは、走査軸を 2 本立てる**——(a) 旧識別子の文字列 grep、(b) **その列挙の「個数」を主張している箇所**。

**根拠**: 指示書 §4.6 の母数は `M20-RESEARCH-01` C-5（＝旧 code の文字列 grep）だった。しかし**旧 code の文字列を 1 つも含まず「プリセットは 5 個」という個数だけを主張していた箇所が 7 か所**あり、grep に出なかった（`migrate_test.go:922,923` ／ `repository/preset/repository_test.go:41` ／ `api/preset/handler_test.go:38` ／ `notation/cache_test.go:92,166` ／ `notation/setup_resolver_test.go:185`）。**`go test ./...` で初めて露見した。**

**あわせて確定した判定手順**: **7 件を機械置換せず、1 件ずつ「その `5` は何の `5` か」をコードで確認した。** その結果 `internal/service/combo/service_test.go:248-253` が `SELECT count(*) FROM presets` で**動的に数えている**ことが分かり、**追随不要と正しく除外できた**（機械置換なら誤って触っていた）。

- ⇒ **`SUPP-001` §5.5 へ「列挙値の削除・改称サブでは、文字列走査と『個数を主張する箇所』の走査を対で行う。個数側は 1 件ずつ意味を確認し、動的カウントを機械置換しない」を明文化してほしい。** 指示書テンプレートの §4.9 否定形確認（現在は走査キーワード＝文字列のみ）にも同じ軸を足すと、次に同型のサブが出たとき指示書側で拾える。

### 1-2 契約テストは **書いただけでは効かない**。ミューテーションで検査力を裏取りする

**確定した作法**: **「そのテストが守るはずの違反」を実際にマイグレへ入れて FAIL することを確認し、撤去後に `git diff` で差分 0 を確認する。**

**根拠**: 本サブの最重要ゲート 2 つ（`id` を詰めない／`down` の忠実復元）は、テストが green でも「テストが効いている」ことを意味しない。実際に確かめた。

| ミューテーション | 検出したテスト |
|---|---|
| down の `INSERT` から `id` を落とす | **DN-2 が FAIL** |
| up に `id` を詰める `UPDATE` を足す | **U-3 が FAIL**（副次的に U-5 も） |

- ⇒ **`SUPP-001` §5.5 の「マイグレ契約テストの規約」へ (10) として追記してほしい**——**「非破壊条件（`id` の不変・down の忠実復元）を主張するテストは、その条件を実際に破って FAIL を確認する。破壊テストの実施記録をコミットメッセージか完了報告に残す」。** M19-04d が §5 で破壊テスト 2 パターンを実施しており（同レポート §7-1・§7-2）、**本サブで 2 例目になった。2 例あるので規約化してよい段階だと考える。**

### 1-3 `preset_aliases.preset_id` は `ON DELETE CASCADE` を持つが、`PRAGMA foreign_keys` が効いていない（実測）

**実測値**: 一時 DB の当該接続で **`PRAGMA foreign_keys = 0`**（ボード **P-04** の既知課題が生きていることを実測で確認した）。DDL は `preset_id INTEGER NOT NULL REFERENCES presets(id) ON DELETE CASCADE`（`migrations/000001_init_schema.up.sql:145`）。

**本サブでは実害なし**——削除対象を指す alias が 0 件だったため。**波及しないことを U-7 / DN-3 で固定した**（行数不変＋ orphan 0 件の両面）。

- ⇒ **`SUPP-001` §7.3 へ「組み込みプリセット削除の保護」を書くときに、`PRAGMA foreign_keys` が効いていない前提を併記してほしい。** **M20-04 でカスタムプリセット削除を作るとき、CASCADE に頼ると孤児行が残る。** 保護をサービス層だけに置くか、PRAGMA の根治（P-04）を先に済ませるかの判断が要る。

## §7 教訓（retrospective 行き）

> **★親チャットは本節を読まなくてよい。宛先は `retrospective-log` へのバッチ反映で、実施者は設計担当**（反映担当は 2026-08-11 に廃止）。**外出先では §1〜§4 だけコピーすれば足りる。**

1. **★「行番号は行の同一性を示さない」。** 設計卓が §4.6 #2・#3 を「独立した 2 件」と読んだのは、`:157` と `:163` という**別々の行番号**を見たからである。実体は**同一関数の 2 行**だった。**現物を持たない側が行番号から構造を推定すると、この形で外す**（`E-117` の再演）。一般化——**指示書で「N 件」と件数を書くときは、それが「独立した N 個の変更単位」であることを構造で確認する。** 行番号は到達を速くする補助にすぎない。

2. **★削除・改称の走査軸は 2 本要る（文字列 ＋ 個数）。** 指示書 §4.6 の母数が「旧 code の文字列 grep」だったため、**個数だけで主張する 7 か所が丸ごと漏れた**。**「5 種を 3 種にする」変更は、`numeric_ja` という文字列を含まない場所も壊す。** 機構化するなら、**否定形確認のテンプレートに「その列挙の個数を主張している箇所」の走査軸を常設する**。

3. **★テストが green であることと、テストが効くことは別である。** 本サブは最重要ゲート 2 つをミューテーションで壊して FAIL を確認した。**M19-04d に続く 2 例目**であり、**2 例あるので規約化してよい段階**だと考える（§1-2）。**特に「非破壊条件」を主張するテスト**（何かが**変わらない**ことの主張）は、実装が空でも green になりうるため裏取りの価値が高い。

4. **★裁定は「出した」だけでは効かない。ファイルに入って初めて効く。** 設計卓は誤り 3 件を認めて裁定を出したが、**リポジトリ上の指示書は v1.0.0 のままだった**。その結果、**レビュアーへ裁定を明示的に渡さなければ、正しい実装が「重大」と誤判定されるところだった**。一般化——**差戻しに対する裁定は、回答と同じ手番でファイルへ反映する**（`D-277` の「払い出しと登録を別の手番にしない」と同型の失敗である）。**同じ手番でできないなら、指示書ヘッダに「本書の一部は別文書で上書きされている」旨の 1 行を置く。**

5. **削除サブはベースライン型検査のラチェットを緩める。** `check-enum-sync.sh` の散在数が 26 → 24 に減り、**放置すると次に 2 件増えても「ベースライン以内」で検知されなくなる**。製造は当初「スコープ外」として見送り、レビュー指摘で採用へ変えた。**機構化するなら、削除・整理系サブの DoD に「ベースライン型検査の締め直し」を常設項目として入れる。**

6. **クラウド実行環境の E2E は前提が違う。** ブラウザ取得がネットワークポリシーで拒否され、プリインストール版はバージョンが合わない。**「フルスイートで大量に落ちるが小バッチでは通る」という形の失敗**は、**本サブ起因の回帰と見分けがつきにくい**。切り分け手順（失敗の分布を見る → 小バッチ再実行 → 変更が壊しうる面を狙って実行）を `remote-ops.md` へ残すと、次の担当が 1 からやらずに済む（§4-5）。
