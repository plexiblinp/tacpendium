## §1 製造が独自に確定した実装仕様（DES / 台帳 反映が要るもの）

### 1-1. ★★`useSessionStorage` は `browser-storage.ts` 経由になった（台帳 §1 脚注「#7 の非整合」の解消）

**併せて確定したこと（★台帳へ載る形）**:

### 7-1. ★★★「規約から外れている」を書き換えの理由にするとき、**その規約に在庫（ベースライン）が在るかを見る**

### 7-2. ★★浅いクローンでは「初出コミット」は引けない。**`git log --diff-filter=A` は graft 境界を初出と偽って返す**

`.git/shallow` が在ると `git log --diff-filter=A` は**境界コミットを「追加」として返す**。
`M40-02` では 5 ファイルとも `b873d59`（2026-09-11 の merge）が返ったが、**実際の初出は 2026-05 のフェーズ1 である。**
**★これを証跡として書くと、誤った SHA が監査記録に残る。**

**⇒ 見分け方＝`git cat-file -t <初出と主張する SHA>` が通るか、`.git/shallow` が在るかを先に確かめる。**
**⇒ 本件は初回 SCANOSS の chronology CSV が `FirstCommit` 列を保持していたため代替できた。★CSV が無い対象では代替が無い。**

### 7-3. ★★失効記述の是正は、**自分で新しい失効記述を作りやすい**

`M40-02` は `DIRECT_ALLOW` から 1 件外したが、**直上のコメント「下記 2 本だけ」を同時に直さなければ、それ自体が失効記述になるところだった**（気づいて同じ手番で直した）。

**⇒ 数字や件数を書き換えるときは、`grep` で*同じ数字の写し*を全数拾うこと**（教訓 `E-118` と同型）。**★本件では同一ファイルの 8 行上に在った。**

### 7-4. ★レビュアーが「報告が無い」と言うのは、**工程順のせいであることがある**

本 CLI は Phase A → **B（レビュー）** → C → **D-0（完了報告）** → D（索引行）である。
**⇒ レビュー時点で完了報告が存在しないのは仕様どおりであり、レビュアーには知りようがない。**
