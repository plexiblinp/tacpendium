## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★いずれも「指示書・`CHANGE-112` に書かれていなかったので確定させた」ものである。** 指示書と異なる判断を下したものは §2 に分けてある。

### 1-1 ハッシュ方式は **標準ライブラリで足りた**（`x/crypto` の昇格枠は未使用）

`CHANGE-112` §4 は「**実査してから決める**。標準ライブラリに鍵導出関数が在ればそれ、無ければ `golang.org/x/crypto/bcrypt`」としか書いていない。**実査の結果は「在る」側だった。**

```
$ go version → go version go1.26.4 linux/amd64
$ go doc crypto/pbkdf2 → 在る（RFC 8018。Go 1.24 で標準入り）
$ go doc crypto/argon2 / crypto/scrypt / crypto/bcrypt → いずれも "is not in std"
```

- **⇒ `golang.org/x/crypto` の `indirect → direct` 昇格は行っていない。`go.mod` / `go.sum` の diff は 0 行。** **★`CHANGE-112` §4 が与えた昇格の承認枠は使わずに済んだ**（`CLAUDE.md` §6 ／ D-382 (2) の論点は発生しなかった）。
- **検証子の形式は製造が確定した**: `pbkdf2-sha256$<反復回数>$<ソルト>$<導出鍵>`（base64 パディング無し。ソルト 16B・導出鍵 32B・反復 600,000）。**反復回数とソルトを検証子自身へ埋めてある**ため、**将来 `hashIterations` を上げても既存の検証子を照合できる**。
- 実測コスト **315 ms/回**（`BenchmarkHashPassword-4 → 314923592 ns/op`）。**導出が走るのはログイン時とパスワード設定時だけ**で、セッション検証はメモリ上の索引を引くだけである。
- ⇒ **`SUPP-001` §5.8 へ検証子の形式を明文化してほしい**（`config.toml` に何が入るか）。**★`DES-002` §8 へアルゴリズム名を書くかは親の判断**——書くと将来の変更が CHANGE 案件になる。**書かないなら「検証子は自己記述形式であり、方式とパラメータは値の中にある」とだけ書けば足りる。**

### 1-2 セッションの受け渡しは **Cookie**（属性まで確定）

`DES-002` §4.4 は CSRF 第一対策として「SameSite=Strict Cookie」を**既に前提にしている**が、**Cookie の名前・属性は設計書に無い。**

```
Set-Cookie: combomgr_session=<session-id>; Path=/; HttpOnly; SameSite=Strict
```

| 属性 | 値 | 理由 |
|---|---|---|
| `HttpOnly` | あり | JavaScript から読めなくする |
| `SameSite` | `Strict` | `DES-002` §4.4 が前提にしている形。**`M22-05` がこの上に載る** |
| `Path` | `/` | SPA の静的配信と `/api/*` の両方へ送る |
| **`Secure`** | **なし** | **契約 F-3 ＝ 平文 HTTP。付けると LAN で Cookie が保存されず入場できない** |
| `Max-Age` | 指定なし | タイムアウトを設けない決定（§1.2-5）に対応 |

- **属性は `internal/api/auth/cookie.go` の `newSessionCookie` 1 関数へ集約**してある（発行と失効の両方が通る）。
- **★`web/src/` を 1 バイトも触っていない**——フロントの `fetch` は 10 箇所以上が既に `credentials: "same-origin"` を持ち、`cors.go:41` が `Access-Control-Allow-Credentials: true` を設定済みだったため、Cookie はそのまま乗った。
- ⇒ **`DES-002` §8 へ「セッションは Cookie で運ぶ」と、上表の属性を書いてほしい。** **★とくに `Secure` を付けない理由を書かないと、次の担当が「安全側に倒す」つもりで付けて入場できなくする。**

### ★1-3 **`password_enabled = false` のときは、正しいパスワードでもログインを拒否する**（`M22-02` の画面設計を縛る）

指示書 §4.9-4 は「**Cookie を発行する方式を採った場合、OFF でも Cookie が付いていないか**」としか書いていない。**「ログインそのものを拒否する」という挙動は製造が確定した。**

- as-built: `Service.Login` の冒頭で `if !s.Enabled() { return "", false }`（`internal/service/auth/service.go`）。**OFF なら 401 で、Cookie も付かない。**
- **★これは「ゲートを一度掛けて外した後」に効く。** `SetPassword` は `PasswordEnabled` を触らないため、**ゲートを外しても `password_hash` は残る**。⇒ **「OFF かつパスワード設定済み」は例外的な状態ではなく、ゲートを外した後の通常状態である。**
- **★初版はこの判定が無く、この状態で 204 ＋ `Set-Cookie` を返していた**（レビュー指摘 2-a。**製造側で独立に再現を確認して是正した**）。**破壊確認 C**（新設）で判定を外すと `TestLogin_DisabledButPasswordSet_IssuesNoCookie` が赤くなることを確認済み。
- ⇒ **`DES-002` §8 へ 1 行足してほしい**——**保護が無効な間はログインできない（セッションが何も守らないため）。** **★`M22-02` への影響が直接ある**: OFF のときにログイン画面を出しても通らないので、**画面は `GET /api/auth/status` の `passwordRequired` を見て出し分ける必要がある**（§1-6）。

### 1-4 保護対象の範囲（**`M22-02` が受け取る契約**）

指示書 §4.5-2 は「保護対象から外す経路を明示的に列挙すること（ログイン自身 ／ `GET /api/health` ／ 静的配信）」とだけ書いている。**全数は製造が確定した。**

**保護するのは `/api/` で始まるパスのみ。そのうち次の 5 本を外す。**

| # | 経路 | 外した理由 |
|---|---|---|
| 1 | `GET /api/health` | ヘルスチェック（指示書明示） |
| 2 | `POST /api/auth/login` | **これが無いとログインできない**（指示書明示） |
| 3 | `POST /api/auth/logout` | 冪等。情報を返さない |
| 4 | `GET /api/auth/status` | **未認証の画面が状態を知る唯一の経路** |
| 5 | `POST /api/auth/password` | **初回設定を通すため。** 設定済みの保護はハンドラ側（現在のパスワード要求）で成立する |

- **`/api/` で始まらないパス（SPA シェル・`/assets/*`・`/`）は保護しない。** **シェルが読めないと `M22-02` がログイン画面を出せない**ため。
- **⇒ 上記以外の `/api/*` はすべて保護対象**（`GET/PUT /api/config` を含む）。これにより §4.4-3′「認証なしで `password_enabled` を `false` にできない」が成立している。**切替は `PUT /api/config` に置いたままである**（§3-1）。
- ⇒ **`DES-002` §8 へ「保護は `/api/*` に掛け、静的配信には掛けない」を書いてほしい。** 5 経路の individual な列挙は実装内部の粒度なので不要と考える。

### 1-5 未認証時の応答（**`M22-02` が受け取る契約**）

```
HTTP/1.1 401 Unauthorized
{"error":{"code":"unauthorized","message":"authentication required"}}
```

- **リダイレクトはしない。** API はデータを返す層であり、遷移は画面が決めるため。
- **ログイン失敗は別コード**（`invalid_password`）。**★理由は区別しない**——「パスワード未設定」「不一致」「ゲート無効」がすべて同じ応答になることをテストで固定してある。
- ⇒ **`DES-002` §4.2（主要エンドポイント）へ 401 の形を足してほしい。** **★同節は楽観排他の 409 についても規定が無く、`M22-RESEARCH-01` §9-B-5 が「照合対象が無い」と報告した箇所と同じ面である。**

### ★1-6 **`GET /api/auth/status` を新設した**（設計書に無い API・**同名フィールドが別の値になる**）

指示書 §4.4-4 は「`GET /api/config` の `passwordEnabled` で足りるかを実査で判定し、足りないなら足す」と書いている。**足りなかった。**

- **理由**: **`GET /api/config` 自体が保護対象になる**ため、**未認証のクライアントは読めない。** `M22-02` が「パスワードを求めるべきか」を知るには未認証で読める経路が要る。
- 応答: `{passwordRequired, passwordSet, authenticated}`。**検証子・セッション ID は含めない。**

| フィールド | 意味 |
|---|---|
| `passwordRequired` | **実効値。** 入場ゲートが実際に効いているか |
| `passwordSet` | パスワードが設定済みか（初回設定と変更の分岐に使う） |
| `authenticated` | 現在のリクエストが有効なセッションを持つか |

- **★`GET /api/config` の `security.passwordEnabled` とは別物である。** あちらは **`config.toml` の生値**、こちらは**実効値**であり、**`password_enabled = true` かつパスワード未設定のとき両者は `true` / `false` へ割れる。**
- **★同名衝突を避けるため、新設側を `passwordEnabled` → `passwordRequired` へ改名した**（レビュー指摘 F。**消費者の `M22-02` が未着手の今が最も安く直せる**）。**`GET /api/config` 側は既存 API のため不変。**
- ⇒ **`DES-002` §4.2 へ本エンドポイントを追加してほしい。** **★「画面が見るべきは `passwordRequired` の方である」と明記してほしい**——書かないと `M22-02` が `GET /api/config` の同名フィールドを見て、不整合状態で誤った画面を出す。

### 1-7 `password_enabled = true` かつパスワード未設定は **2 経路に分けて塞いだ**

開発者は「(b) 警告を出して OFF として扱う」を選んだ（§3-1）。**「API 経路は 422 で拒否する」という片側は製造が足した。**

| 経路 | as-built |
|---|---|
| **API**（`PUT /api/config` で ON にしようとする） | **422 で拒否。**`ValidationIssue{Field: "security.passwordEnabled"}` ⇒ **アプリからは不整合状態を作れない** |
| **ファイル**（`config.toml` を手で書く） | **起動を止めず OFF として扱い、起動時に WARN を 1 度出す** |

- **★「ON にしようとした要求」だけを弾いている。** 既に不整合な状態のときに**無関係な設定変更まで巻き添えで 422 にしない**（テストで固定）。
- **警告は起動時 1 回**（`WarnIfMisconfigured()` を `main.go` から呼ぶ）。**★初版は `Enabled()` の中で警告しており、リクエストごとに出てログを埋めていた**（レビュー指摘 2-c）。
- ⇒ **`DES-002` §8 か `SUPP-001` §5.8 へ、この状態の扱いを 1 行書いてほしい**（**設定を手で書いた利用者が必ず作る状態**である）。**検証コード（`DES-006`）の番号は設計卓が採番してほしい**——製造は採番していない。

### 1-8 パスワード変更で **既存セッションを全破棄する**

`D-396` は「変更時は現在のパスワードを要求する」までしか決めていない。**変更が通った後の既存セッションの扱いは製造が確定した。**

- as-built: **全破棄**（`SetPassword` の末尾で `s.sessions` を作り直す）。**パスワードを変えた本人だけが入り直せる状態にするため。**
- ⇒ **`DES-002` §8 へ 1 行。** **★`M22-02` は「パスワード変更後にログイン画面へ戻る」導線を作る必要がある**（変更した端末自身のセッションも切れる）。

## §2 契約・設計に反する独自判断

**2 件ある。** いずれも**実装が正しく、明文が追いついていない**型と考えるが、**受理して明文を更新するか、却下して差し戻すかは親の裁定に委ねる。**

### ★2-1 E2E シナリオ B が **サーバを ON にしていない**（指示書 §5.2-B の明文と異なる手段）

**何に反したか**: 指示書 §5.2-B「**`password_enabled = true` のとき、既存画面がどう見えるかを固定する**」。

**as-built**: サーバの `password_enabled` は **`false` のまま**で、`page.route` によって**このブラウザコンテキストの API 応答だけ**を 401 に差し替えている（`web/e2e/m22-01-auth-gate.spec.ts`）。

**なぜそう判断したか**:

- **認証状態は共有バックエンドのグローバル資源であり、`fullyParallel: false` が直列化するのは「ファイル内」だけで、ファイル単位では並列に走る**（followup `e2e-shared-global-resource-parallel` / `D-362`）。
- **⇒ サーバを ON にすると、同時に走っている他 spec の API 呼出が軒並み 401 で落ちる。** **★`D-362` の「資源ごとに 1 ファイルへ寄せる」では防げない**——巻き添えになる相手が別ファイルだからである。
- **ON 側のサーバ挙動そのもの**（誰が通り誰が弾かれるか）は **Go テストで網羅**してある（`internal/api/middleware/auth_test.go` ／ `internal/api/auth/handler_test.go`）。**E2E が担うのは「画面がどう見えるか」だけである。**
- **副次的な利点**: `config.toml` を書き換えないため**復元も要らなくなった**（指示書 §5.2 の「元の値へ復元すること」が不要になった）。

**レビューの判断**: 「**逸脱としては受容可能**」（理由が spec 冒頭と完了報告に明記され、ON 側が Go で網羅されているため）。**ただし「ON にすると `M22-02` が使う経路がサーバ側でも本当に読めるか」は自動では守られておらず、手動 curl でのみ確認**している。

**⇒ 親への依頼**: **(a) 受理して、指示書テンプレ側に「共有資源を触る E2E は、サーバ状態を変えずコンテキスト単位で再現してよい」を一般規則として書く**か、**(b) 却下して、`workers: 1` 等の恒久策（`e2e-shared-global-resource-parallel` の残論点）を先に決める**か。**★(b) を採る場合、本サブ単独では直せない**（`playwright.config.ts` は改善レーンの担当）。

### 2-2 サービス層が **第一引数に `context.Context` を取っていない**（`CLAUDE.md` §4 の規約からの逸脱）

**何に反したか**: `CLAUDE.md` §4「**サービス層のメソッドは第一引数に `context.Context` を取る**」／ チェックリスト §6。

**as-built**: `internal/service/auth/Service` の 6 メソッドと `SecurityStore` の 2 メソッドは、いずれも `ctx` を取らない。

**なぜそう判断したか**:

- **渡す先が無い。** `SecurityStore` の実体である `internal/service/config` が `ctx` を取らない設計であり（同パッケージ `PresetExistsFunc` のコメントに理由と帰結が明記されている。`M20-05` §9.4 で公開 IF の組み替えは範囲外とされた）、**受けても素通しにしかならない。**
- **取れない `ctx` を型に載せると「キャンセルが効く」という誤った期待を呼ぶ**と判断し、既存 `configsvc` の先例に揃えた。
- **帰結を明記した**: `SetPassword` の鍵導出（315 ms）は**クライアント切断でも最後まで走る**。理由と帰結を `Service` の godoc へ書いてある。

**レビューの判断**: 「**既存先例に揃えたこと自体は妥当。逸脱の明示を求める**」（本レポートと godoc で対応済み）。「**全面的な `ctx` 導入は `configsvc` の公開 IF 組み替えを伴うため本サブの範囲外でよい**」。

**⇒ 親への依頼**: **★宛先が親ではなく開発者かもしれない**（`CLAUDE.md` は開発者のルールファイルであり設計卓の管轄外）。**判断は「`configsvc` を含めて `ctx` を通す改善を別レーンで立てる」か「規約に『依存先が `ctx` を取らない場合は逸脱を明記のうえ揃えてよい』という例外を書く」かの二択**と考える。**放置すると、次にサービス層を新設する担当が同じ判断を毎回する。**

| 1 | **★★「既定 OFF のとき何も変わらない」を守るテストは、機能の入口そのものにも当てる。** 本サブは OFF 側の網を「**保護対象が認証なしで通ること**」に寄せて張り、**認証 API 自身の OFF 挙動が抜けていた**——`Login` が `Enabled()` を見ておらず、**OFF かつパスワード設定済みで 204 ＋ Set-Cookie を返していた。** **★この状態は例外ではない**（ゲートを外しても検証子は残るため、**外した後の通常状態**である）。**⇒ 「OFF で既存が壊れないか」だけでなく「OFF で新機能が黙って動いていないか」を別項目として立てる。** 前者だけだと**新機能のテストは ON を通すため全部緑のまま**になる。 |
| 2 | **★★モックの照合パターンは、対象以外に当たらないことを先に確かめる。** E2E で API を 401 に差し替える `page.route("**/api/**")` が、**Vite が dev で配るソースモジュールのパス**（`/src/features/tag/api/tagApi.ts` 等）にも当たり、**JS が 401 JSON へ化けてアプリが起動しなくなった。** ⇒ **「保護すると白画面になる」という誤った結論を報告する寸前だった**（実際は外枠が完全に描画され、データ領域がエラー表示になる）。**★気づけたのは対照実験を置いていたからである**——「遮断すれば 401」だけでなく「**遮断しなければ 200**」を見ていたため、モックが広すぎることが露見した。**⇒ 観測結果が予想外に強い（全部壊れる）ときは、観測手段の側を疑う。** |
| 3 | **★リクエストごとに呼ばれる関数へ警告を置かない。** 不整合な設定の警告を `Enabled()` の中に置いたところ、**ミドルウェアが毎リクエスト呼ぶため静的アセット 1 枚ごとに WARN が 1 行出る**形になっていた。**しかもコメントには「起動時 WARN」と書いてあり、実装と食い違っていた。** ⇒ **判定と通知を分ける**（判定は純粋に・通知は起動時に 1 度）。**★「起動時に読むだけの設定」は起動時に検査しきれる**——毎回検査する必要が無いことを先に確かめる。 |
| 4 | **★ゲートを守っている当のファイルのコメントが、ゲートの守り方を誤って教えていることがある。** `internal/api/config/dto.go` の規約コメントは「機微フィールドは `json:"-"` で除外せよ」と書いていたが、**as-built の除外は「DTO へ足さないこと」で成立していた。** **⇒ このコメントに従うと `ConfigResponse` へフィールドを足したうえで `json:"-"` を付ける形になり、応答からは消えても要求側の入力口が残る。** **★否定形確認の走査キーワード（`M6` / `フェーズ2` / `未使用` 等）の外にあり取り逃がした**——**走査は正しく動いていたが、網の目が「実装したもの」側にしか張られていなかった。** ⇒ **自分が満たしたゲートについて、そのゲートを説明している記述を能動的に読み直す。** |
| 5 | **★同じ名前のフィールドが 2 つの API で別の値になるなら、消費者が現れる前に改名する。** `GET /api/config` の `security.passwordEnabled`（生値）と新設 `GET /api/auth/status` の `passwordEnabled`（実効値）は、不整合状態で `true` / `false` に割れる。**消費者（`M22-02`）が未着手の時点なら改名は 1 ファイルで済む。** ⇒ **「後で気をつける」ではなく、名前で衝突を消す。** |
| 6 | **★共有バックエンドの E2E で「グローバル状態を変える」テストは、1 ファイルへ寄せても守れない。** `fullyParallel: false` が直列化するのは**ファイル内だけ**であり、**巻き添えになる相手は別ファイル**である。⇒ **`D-362`（資源ごとに 1 ファイルへ寄せる）が効くのは「同じ資源を奪い合う」型まで**で、**「全 spec に影響する状態」には効かない。** **★本サブが採った回避は「サーバ状態を一切変えず、コンテキスト単位で再現する」形**——**復元も不要になる**という副次的な利点があった。 |
| 7 | **★指示書が「この形を警戒せよ」と名指ししている箇所は、テストの項目名にその文言をそのまま使う。** 指示書 §4.9-4 は「**Cookie を発行する方式を採った場合、OFF でも Cookie が付いていないか**」と書いていたが、**製造のテストは「OFF で保護対象が通る」という別の言い方で書かれており、名指しされた形が網に入っていなかった。** ⇒ **警戒文をテスト名へ写経すると、抜けが目視で分かる。** |
