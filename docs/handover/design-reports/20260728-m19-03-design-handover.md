## §1 製造が独自に確定した実装仕様(DES 反映が要るもの)

### 1-1【最重要・方式の確定】§4.2 の引き継ぎは「ON UPDATE CASCADE」と「明示再ポイント」の**併用**

指示書 §4.2 は選択肢 (a) 明示再ポイント / (b) `ON UPDATE CASCADE` の**択一**を想定していたが、**両方**を採った。単独ではどちらも不十分だったため。

- **(b) が必須である理由**: 本表の FK 親は `combos` ではなく **`combo_setups`** であり、その親キー `combo_id` は識別キー変更編集で**その場で UPDATE される**（`internal/repository/combo/repository.go:901 UpdateSetupReferences`）。FK=ON の接続では、結果行が 1 行でもあると `ON UPDATE CASCADE` 無しでこの UPDATE が **FK 違反で失敗し、キー変更編集そのものが 500 になる**。
- **(a) も必須である理由**: §1-2 のとおり FK が効かない接続が混在するため、CASCADE だけでは結果行が旧 `combo_id` 側に取り残される（＝**利用者の検証結果が編集しただけで消える**）。
- **呼び出し順は `UpdateSetupReferences` の「後」**（`internal/service/combo/service.go:628` 付近 `MoveSetupResultReferences`）。先に子を動かすと FK=ON 下で移動先 `(新 combo_id, setup_id)` が未作成で FK 違反になる。後なら FK=ON では 0 行更新の no-op、FK=OFF では実際に子行を移す。
- 同じ理由で**紐付け解除系**（`DeleteComboSetup` / `DeleteComboSetupsBySetupID` / `DeleteComboSetupsByComboID` / `...Excluding`）と**完全削除**（`HardDelete`）でも結果行を**明示削除**している。
- 根拠テスト: `TestUpdateWithKeyChange_CarriesSetupResults_{Default,CarryAll,Individual}` / `..._WithForeignKeysOff`（`internal/service/combo/setup_results_carry_test.go`）。**明示再ポイントを外すと FK=OFF ケースが 0 行＝データ消失を検知して落ちる**ことをミューテーションで確認済み。

⇒ **DES-003 §3.15／§3.17 に「`combo_setup_results` は `combo_setups` を親とする複合 FK で、キー変更編集では CASCADE と明示再ポイントを併用する」旨を明文化してほしい。** あわせて「FK 親が `combos` か `combo_setups` かで再ポイントの実装形が変わる」ことを注記いただけると、後続サブが `combo_punishes` の流儀をそのまま真似して誤らずに済む。

### 1-2【最重要・新発見／M19-03 に閉じない】`db.Open` の `PRAGMA foreign_keys = ON` が接続プール全体に効いていない

SQLite の外部キー制約は **接続単位**の設定だが、`internal/infra/db/db.go:42` は `*sql.DB.Exec` で PRAGMA を流しており、**プール中の 1 接続にしか適用されない**。本番コードに `SetMaxOpenConns` が無くプールは無制限に増えるため、**後から張られた接続は `foreign_keys=OFF` のまま**になる。着手時の使い捨てプローブでは **16 接続中 7 本が OFF** だった。

- 恒久的に担保しているのは**構造的主張**（`*sql.DB.Exec` の PRAGMA は 1 接続のみ／プール上限なし／生接続の既定は `foreign_keys=0`）で、いずれもコード上で独立に確認できる。具体値 16 中 7 のプローブスクリプトは残していない（レビューでも再現不可と指摘済み）。**再現可能な形で残しているのは回帰テスト** `TestUpdateWithKeyChange_CarriesSetupResults_WithForeignKeysOff`（PRAGMA 非適用の生接続を使用）。
- **影響は M19-03 に閉じない**: `combo_punishes` / `combo_punish_curations` / `combo_punish_prunings` / `combo_steps` / `setup_steps` 等、**`ON DELETE CASCADE` に依存している既存テーブルすべてに同じ不確実性が残る**（M18-01 系を含む）。
- M19-03 は**自表についてのみ** FK 非依存にした（§1-1）。**根治には手を付けていない**（DSN への `_pragma=foreign_keys(1)` 付与等は全テーブルの FK 強制挙動が変わる全体影響のため）。

⇒ **DES-002（アーキテクチャ）または SUPP-001 に「FK 強制は接続単位であり、現状の `db.Open` はプール全体を保証しない。CASCADE に依存する箇所は明示削除／明示再ポイントを併用する」旨を明文化してほしい。** 根治は §3-2 の followup 事項。

### 1-3【API 契約の確定】成立条件のエンドポイントとコンボ詳細への同梱

| 項目 | 確定内容 |
|---|---|
| 更新 | `PUT /api/combos/{comboId}/setups/{setupId}/results`（body `{techType, inCorner, result, note}`・upsert） |
| 未検証へ戻す | `DELETE /api/combos/{comboId}/setups/{setupId}/results?techType=&inCorner=` → **204**（行の物理削除） |
| 取得 | **専用 GET は設けない。**コンボ詳細 `GET /api/combos/{id}` の `setups[].results` に同梱（指示書 §4.3.1 の (a)） |
| 一覧 | `GET /api/combos` では取得せず、`omitempty` で `results` キー自体が出ない |
| エラー | 値域外 **400**（`invalid_setup_result`）／紐付け不在 **404**（`setup_link_not_found`）。**API 層でも明示的に弾く多層防御** |
| レスポンス型 | **`model.ComboSetupResult` をそのまま返す**（JSON タグが API 契約と一致し `combo_id` は `json:"-"`＝URL 側で表現）。api パッケージ間の相互 import を避けるため |
| 採用時 | `POST /api/combos/{comboId}/setups` に **`verifiedConditions`** を追加（**追加のみ・後方互換**）。省略可 |
| note の契約 | **全置換**。null を送ると既存メモは消える（部分更新ではない） |

N+1 回避のため `ListResultsByComboID` は **1 コンボにつき 1 回だけ**呼び `setup_id` で振り分ける。根拠テスト: `TestHandler_Get_200_IncludesSetupResults`（呼び出し回数を検証）。

⇒ **DES-002 の API 一覧に上記 2 ルートと `verifiedConditions` を追記してほしい。**

### 1-4【UI 操作モデルの確定・開発者テストで変更】「巡回トグル」→「セル選択＋3 択の直接指定」

指示書 §4.4.3 は「未検証 → 成立 → 不成立 → 未検証」の**巡回**を想定した書き方（§9.2 で操作形式は製造裁量）だったが、**開発者の実機確認で 3 点の問題が出たため作り替えた**。

| 指摘 | 対応 |
|---|---|
| 目的の状態にするのに最大 2 クリック要る | **3 択（未検証／成立／不成立）を直接押して 1 クリックで確定** |
| メモ欄を開くために押すと状態が変わる | **セルのクリックは選択のみ**（保存 API を呼ばない）。既定で左上セルを選択済みにし、開いた直後から入力できる |
| 未検証に戻すとメモが消える | **メモをセル単位のローカル下書きとして保持し、画面から消さない**（§1-5） |

- 実装: `web/src/features/setup/components/SetupResultEditor.tsx`。`constants/setup-result.ts` の巡回関数 `nextSetupResultState` は**廃止**。
- 併せて **セットプレイ名をリンク色へ**変更（`SetupAccordionItem.tsx`）。成立条件で情報量が増えたことで「行クリックで編集画面へ遷移」が分かりにくくなったため（**本サブが招いた可読性の劣化**）。遷移の挙動は不変。

⇒ **DES-005 §5.6 項目10 には「巡回トグル」ではなく「セル選択＋3 択の直接指定」で明文化してほしい。**

### 1-5【三値表現の帰結・要明文化】未検証セルのメモは**保存できない**

「未検証＝行が無い」（CHANGE-087 §2-d）を守る以上、`result` に NULL も「未検証」値も入れられないため、**未検証セルにはメモの保存先の行が存在しない**。

- UI は下書きとして画面に残し、**保存ボタンを無効化**して「未検証のセルのメモは保存されません。成立／不成立にすると保存できます」と明示する。成立／不成立に戻すとその下書きが保存される。
- **DB は一切変更していない**（未検証の行は作らない）。

⇒ **DES-003 の本表定義または DES-005 §5.6 項目10 に「未検証セルのメモは永続化されない」ことを明文化してほしい。** 永続化を求めるなら**三値の表現方式そのものの変更**（未検証の行を許す）になり、別 CHANGE が要る（§3-6）。

### 1-6【語彙の確定】画面端の 2 語と、受け身種別の SSOT 再利用

- **画面端**: 新規 i18n 2 語 = **「相手が画面端」／「画面中央」**（開発者確定）。`combos.position` の表示ラベル（画面中央／自分画面端／相手画面端…）と表記を揃えつつ、**`position` の値は流用していない**（position はコンボ開始位置、`in_corner` はコンボ終了時の相手位置で意味が違う）。
- **受け身種別**: `web/src/constants/oki.ts` の `OKI_TECH_TYPE_LABELS` を再利用（第 3 の語彙を作らない）。**この定数は i18n ではなく日本語固定**のため、**EN ロケールでも受け身ラベルだけ日本語で表示される**（既存 `ComboEditorBasicFields` と同挙動）。開発者判断で**当面許容**（§3-3）。

⇒ **DES-005 §5.6 項目10 に端の 2 語を追記してほしい。** EN での日本語混在は既知の制約として記録済み。

## §3 設計担当が未把握の残課題・申し送り

### 3-1【★要設計判断・開発者要望 2026-07-28】セットプレイ編集画面でも成立条件を編集したい

開発者から「セットプレイ編集画面（`/setups/:id`）でも変更できたらありがたい」との要望。**製造では実装していない。理由はコストではなく設計正典との衝突。**

- 指示書 §4.4.1 と **CHANGE-087 §2-h** が「**セットプレイ編集画面には置かない**」旨**とその理由**を正典に残すよう明示指定している（M19-01 の `SetupSelectorModal` が `comboId` を持たず採択保存が成立しなかった失敗の再発防止）。
- レビューチェックリスト §8 でも「編集画面に成立条件 UI を置いている」は**重大問題**の判定基準。
- 構造上の理由: `setups` は `combo_setups` 経由で**複数コンボに紐づき得る**ため、編集画面だけでは保存先の `combo_id` が一意に定まらない。

**実現案（判断材料）**: `SetupResponse.parentComboIds` は既に返っているので、**紐づくコンボが 1 件なら自動選択**、複数なら**対象コンボを選ぶセレクタを置く**ことで実装自体は可能。ただし「どのコンボの条件を編集しているか」が常に画面上で明示される必要がある。

⇒ **採否には CHANGE-087 の改訂（§2-h の撤回または条件付き緩和）が前提。設計判断をお願いしたい。**

### 3-2【★要 followup・開発者 OK 済み】`db.Open` の PRAGMA プール問題の根治

§1-2 の構造的事実に対する根治。**M19-03 では自表のみ FK 非依存にし、他テーブルは未対応。** 開発者から起票 OK を受領済み。

- 対応候補: DSN へ `_pragma=foreign_keys(1)` を付与する／`SetMaxOpenConns(1)` で接続を固定する／各 CASCADE 依存箇所を明示削除に置き換える。
- **いずれも全テーブルの FK 強制挙動が変わる全体影響**があり、既存フロー（FK=OFF で通っていた削除順序等）を壊し得るため、独立した調査＋回帰ゲートが要る。

### 3-3 `OKI_TECH_TYPE_LABELS` の i18n 化（レビュー L-2・**唯一の不採用指摘**）

EN ロケールで受け身種別だけ日本語表示になる（§1-6）。M16-03 の正典＝起き攻めラベルの単一 SSOT に手が入るため本サブのスコープ外とし、**開発者判断で当面許容**。英語版をまとめて直す際に併せて対応。

### 3-4 一覧・検索・エクスポートでの絞り込みは未実装（後続サブ）

指示書 §1.3 のスコープ外どおり。**本サブのデータモデルは絞り込み可能な形**になっている（`M19-DESIGN-06` §7-1）。

### 3-5 検証日時を持たない（CHANGE-087 §2-e の確定どおり）

バランス調整パッチ後に「記録がいつのものか分からない」制約が残る。**列を先回りして置いていない**（必要になれば NULL 可の ALTER 1 本で足せる）。

### 3-6 未検証セルのメモの永続化（§1-5 の裏返し）

現状は下書きのみ。永続化するなら「未検証の行を許す」＝**三値の表現方式そのものの変更**になるため、`result` の値域と「行の有無で三値を表す」設計の見直しが要る。**別 CHANGE 案件**。

### 3-7【M18 領域へ触れた事実の報告】`m18-03a` E2E の未追随 assert を本サブで修正した
