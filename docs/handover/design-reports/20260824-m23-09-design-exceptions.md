### 1-2. セットプレイ側の経路名とキー名を製造が確定した

- 経路 **`POST /api/combos/:comboId/setups/check-duplicate`**（`internal/api/setup/routes.go`）。登録経路 `POST /api/combos/:comboId/setups` の直下に置き、コンボ側と対称の位置にした。
- 応答のキー **`deletedDuplicates`**（**生きた側 `duplicates` は名前も意味も不変**）。

いずれも指示書 §9.2 が製造裁量を認めている範囲である。**⇒ `CHANGE-141` の逐語には上記の実名で書いてほしい。**

### 1-3. ★★母集団は「同じにした」のではなく「同じ 1 本である」

`findDeletedDuplicateRefsByKey`（`internal/service/combo/service.go`）を抽出し、**`VAL-C14` が使う `findDeletedDuplicateCandidates` はこれに委譲するだけ**にした。セットプレイ側は **`VAL-S07` が呼ぶのと同一の `FindDeletedDuplicateRefsInCombo`** をそのまま呼ぶ。

**構造的に観測できている**——破壊確認 1（保存前チェックの母集団から `deleted_at IS NOT NULL` を外す）で、**`M23-05` の `VAL-C14` テストが 5 本まとめて赤くなった**（完了報告 §7）。

**⇒ 依頼**: `DES-006` へ **「保存前チェックの母集団は `VAL-C14` / `VAL-S07` と同一実装を共有する（別々に同じ条件を書かない）」** を明文化してほしい。**★「同じ条件にする」と書くと、次の担当が 2 本目を書き起こして静かにずれる。**

### 1-4. ★★ダイアログの文面と配置の規律 — `DES-005` へ。あわせて §5.15 の「既知の限界」を撤去

**逐語（ja / en 11 キー）は完了報告 §6 が正本**である。すべて **`trash.preSaveDuplicate.*`** の新階層に置き、**`trash.warning.*` の既存キーには 1 文字も触っていない**（`M23-05` の文面の回帰ガードと構造的に衝突しない）。既存階層へ足したのは `trash.warning.unnamedSetup` の 1 件だけである。

**配置の規律**（`DES-006` §11.2 の 4 点に揃えた）:

1. **入力を保持したまま表示する** — ダイアログはフォームの state に一切触らない。
2. **進む道を示す** — 「ゴミ箱から復元する」「新しく作る」＋「戻って編集を続ける」。
3. **★消えることを押す前に伝える** — `restoreCaution`（**復元すると、いま入力した内容は保存されません。**）を**復元ボタンの直上に常時表示**する。開いた瞬間から見えている。押した後ではない。
4. **「失敗」と書かない** — ダイアログ内に「失敗」「エラー」の語を使っていない。**重複が在ることは失敗ではない。**

**★該当が 1 件のときはそのまま、複数のときはラジオ一覧（既定選択なし）。** 「1 件目を復元」にしていない。**名前が無い行も必ず選択肢に出す**（落とすとその行は復元できなくなる）。

**⇒ 依頼 2 点。**

- **(a) `DES-005` へ上記の文面と規律を写す。**
- **(b) ★`DES-005` §5.15 の「既知の限界」ブロック**（「警告は保存の成功後に出るため、利用者は重複を作ったあとでしか気づけない」）**を撤去する。** 本サブで解消した。**★開発者が実機で確認済みである**（§3-1-4）。

### 1-5. ★WARNING でモーダルを出すことは `DES-006` §11.1 からの逸脱ではない

**区別は severity ではなく「警告の表示」か「操作の分岐」かである。** 選ばないと次へ進めないものはモーダルが正しい。**先例＝`VAL-N02`**（`DES-006` §7）。

**⇒ 依頼**: `DES-006` §11 へこの区別を明文化してほしい（`CHANGE-141` §2.3 が既に予定している）。**★書かないと、次の担当が「WARNING なのにモーダルだ」を欠陥として起票する。** 実際に `M23-05` の指示書 §4.6 は「★モーダルにしない」を §11.1 を根拠に指示していた。

### 1-6. 仮登録（`is_draft`）ではダイアログを出さない

**指示書は仮登録の扱いを明示していない。** 実装は **出さない**を採った。根拠＝`VAL-C14` / `VAL-S07` が仮登録では走らないこと（`DES-006` §2.3・`CHANGE-125`）と、既存のリアルタイム警告が `enabled: !isDraft` であること。

**出す側に倒すと「保存後には出ない警告が保存前だけ出る」非対称が生まれる。** コード内コメントに理由を残し、専用テストを置いた。

**⇒ 依頼**: `DES-006` の `VAL-C14` / `VAL-S07` の節へ **「保存前チェックも仮登録では走らない」** を 1 行足してほしい。

## §7 教訓（retrospective 行き）

**★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、**実施者は設計担当**（反映担当は 2026-08-11 に廃止）。

1. **★★「テストが在る」と「経路が通っている」は別である。面が 2 つあるサブは、面ごとに E2E の有無を数える。** 本サブのセットプレイ側は**サーバ 13 本・単体 18 本が緑でありながら E2E 0 本**だった（走査で発覚）。**単体は stub の上で緑になるため、経路の断絶を構造的に検出できない。** レビューも指示書もこれを欠陥と判定しない——**契約としては満たされているためである。⇒ 面ごとの数え上げを実査項目に入れる。**
2. **★★リアルタイム検知のための「門」を、保存時の条件に流用しない。** `isFormReadyForDuplicateCheck` は**未完成のフォームで API を打たないための門**であり、判定の条件ではない。流用すると**状況を空のまま保存したコンボでダイアログが出ないのに `VAL-C14` だけが保存後に出る**（NULL 同士は一致するため）。**★型検査も lint も単体も緑のまま通り、E2E を書く段で初めて気づいた。**
3. **★★「赤くなった」だけでは破壊確認にならない。赤くなった理由を読む。** spec 単体実行で `PW_EXECUTABLE_PATH` を設定し忘れ、**ブラウザ起動失敗による 4 本全滅を破壊の証拠と読みかけた**（`make e2e` だけが同変数を設定する）。**⇒ 破壊確認では「狙ったテストだけが、狙ったアサーションで赤い」ことまで確認する。**
4. **★同じイベントハンドラ内で `setState` し、その値を読む関数を同期で呼ぶ形は必ず壊れる。** 捉えるのは更新前の値である。**⇒ 引数で渡す**（呼び出し位置と挙動が 1 行で対応する）。**★型検査も lint も緑のまま通る型の欠陥である。**
5. **★E2E の判定キーは spec ごとに分ける。`afterEach` の後片付けでは足りない。** playwright は `fullyParallel: false` でも**ファイル単位では並行**に走り、DB を 1 本共有する。**並行実行中は「まだ消していない時間」が必ず在るため、後片付けでは原理的に埋められない。**
6. **★「行が作られていないこと」を一覧の件数で判定しない。** 一覧はページングされるため、1 件増えても総数が変わらないことがある。**⇒ 登録要求の発生回数を見る。**
7. **★保存経路へ非同期の一段を挟むと、押下直後に同期でアサートしている既存テストが落ちる。** 新規テストだけを回して緑を確認した段階では見えない。**⇒ 触った経路を使う既存ファイルも必ず回す。**
