## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★いずれも「`CHANGE-119` に書かれていなかったので確定させた」ものである。** `CHANGE-119` や指示書と**異なる**判断を下したものは §2 に分けてある。

### 1-1 `VAL-N05`〜`N07` の通信上のエラーコード文字列（**`CHANGE-119` は 1 つも定めていない**）

`CHANGE-119` §2-c/d/e は **HTTP 状態と種類（ERROR）しか書いていない**。指示書 §9.2-2 が綴りを製造裁量と明記しているため確定させた。

| VAL | コード | 応答 | 実装 |
|---|---|---|---|
| `VAL-N05`（文字種） | **`password_charset_invalid`** | 400 | `internal/api/auth/handler.go:23` |
| `VAL-N06`（長さ） | **`password_length_invalid`** | 400 | 同 `:25` |
| `VAL-N07`（本文サイズ） | **`request_body_too_large`** | **413** | `internal/api/auth/bodylimit.go:26` |

- **★`invalid_password`（ログイン失敗）とは混ぜていない**——あちらは理由を区別しないのが仕様（`DES-002` §8.1）。こちらは「決めるとき」だけに出るため区別してよい
- テストは**リテラルで固定**してある（`TestSetPassword_RejectsNonASCII` ほか。`M22-03` の横断課題 1 の作法を踏襲）
- ⇒ **`DES-006` §7 の `VAL-N05`〜`N07` 行へ、上表のコードをそのまま書いてほしい。**

### 1-2 `VAL-N07` の応答は **413**（400 ではない）。**`Content-Length` 非申告でも 413 に揃えた**

`CHANGE-119` §2-e は HTTP 状態を定めていない。指示書 §4.1-6 の「拒否は 400」は `VAL-N05` / `VAL-N06` に掛かる文である。⇒ **本文サイズ超過の意味に合う 413 を採った。**

**★あわせて、当初は経路によって応答が割れていた**（レビュー中3 で発覚し、取り込みで是正）。

- `Content-Length` を申告した要求 → ミドルウェアが読む前に 413
- **申告しない要求（chunked）→ ハンドラが `c.Bind` のエラーを自分で畳んでいたため 400 `invalid_request` になっていた**（プローブで実測）
- 是正: `IsBodyTooLarge()` を公開し、`Login` / `SetPassword` の `c.Bind` エラー処理で判別（`internal/api/auth/handler.go:50` / `:100`）。`TestAuthRoutes_RejectOversizedBodyWithoutContentLength` で固定
- ⇒ **`DES-006` §7 の `VAL-N07` 行へ「413 ＋ `request_body_too_large`。`Content-Length` の申告有無によらず同じ」と書いてほしい。**

### 1-3 `VAL-N07` の上限値は **8KiB**、適用は **`/api/auth/*` の 4 経路・経路単位のミドルウェア**

- 上限値の根拠: 認証経路の最大の要求は `{"currentPassword":"<128 文字>","newPassword":"<128 文字>"}` で **300 バイト未満**。25 倍以上の余裕を持たせつつ鍵導出（約 315ms）の前段で頭打ちにできる（`internal/api/auth/bodylimit.go:23`）
- **★`e.Use` も `Group.Use` も使っていない。** `internal/api/middleware/auth.go:49-50` が「Echo の `Group.Use` は `/api` と `/api/*` へ `NotFoundHandler` を副作用で登録するため経路表が変わる（OFF でも変わる）」と実測付きで警告しており、**経路単位なら経路表が変わらない**（`internal/api/auth/routes.go:29-38`）
- **⇒ 結果として `cmd/combomgr/main.go` を編集せずに済んだ**（指示書 §2.1 は成果物一覧に挙げていたが、§2.2-3 の凍結対象＝`e.Use` のミドルウェア列に触れずに済んだ）
- ⇒ **`DES-002` §8 へ「認証経路の要求本文には上限がある（8KiB・`/api/auth/*` に限る）」を明文化してほしい。** **★現行 §8 / §8.1 には本文サイズの記述が 1 つも無く、実体は `main.go` と `routes.go` にしかない。**

### 1-4 `VAL-N06` のうち「前後の空白を除くと空」だけは `invalid_request` に落ちる

空は長さ 0 であり `VAL-N06` の一種だが、**`M22-01` からの既存挙動（`ErrEmptyPassword` → 400 `invalid_request`）を本サブは変えていない。**

### 1-5 ログアウトの表示条件は **`passwordRequired`（実効値）**。置き場は設定画面

## §2 契約・設計に反する独自判断（★最優先・**2 件**）

### 2-1 ★★非 ASCII の入力段階除去を、**ログイン欄と「いまのパスワード」欄にも**掛けた

**何に反したか**——**`CHANGE-119` §2-b（承認済み）**:

> 照合には文字種検査も長さ検査も掛けない。**理由**——掛けると、既に非 ASCII や短いパスワードで決めた利用者が入れなくなり、しかも変更もできなくなる。**⇒ 詰みが生まれる。★これは移行の都合ではなく恒久の規則である**——**検査の内容を将来変えたときも同じ問題が起きる**

**レビューチェックリスト §9-1 はこれを「重大」判定にしている。** 指示書 §4.1-8（ログイン欄は空だけ止めてよい・それ以外の検査は掛けない）にも触れる。

**なぜそう判断したか**——**開発者の要望と裁定**（2026-08-16・実機確認後）:

> 「そもそもフロント側で非 ASCII を入力不能にできますか？」「全角のままパスワードを入力してログイン失敗する可能性があり、非常に煩わしい」
> 「**本アプリはリリース前なので『いま設定されているパスワードで入れる』は重要ではないです。**」

**★§2-b が挙げる理由は 2 つあり、①だけが解除されている。**

| §2-b の理由 | 扱い |
|---|---|
| ① 既に非 ASCII / 短いパスワードで決めた利用者が締め出される | **★開発者が解除**（リリース前であり該当者が居ない） |
| ② **将来、検査の内容を変えたときも同じ問題が起きる** | **★残っている。実装側の歯止めで潰した**（下記） |

**★②を潰した歯止め 3 点（親はこれをそのまま `DES-002` §8 へ書き取れる）**:

1. **落とすのは「印字可能な ASCII 以外」だけである。** 長さ（`VAL-N06`）その他の規則には**連動させていない**。⇒ 将来 charset 以外の規則を変えても締め出しは起きない。**`LoginScreen.test.tsx` の「下限より短い / 上限より長い はそのまま送られる」が固定している**
2. **サーバ側は 1 行も変えていない**（追補分の `internal/` diff **0 ファイル**）。`Service.Login` と `SetPassword` の `current` は引き続き無検査であり、**最重要ゲート 1 のサーバ側は不変**。⇒ **`curl` からは従来どおり非 ASCII のパスワードで入れるため、復旧経路が残っている**
3. **⇒ 入力制限は「画面の入力補助」であって「照合の検査」ではない。** この線引きを `web/src/features/auth/passwordRules.ts:50-68` と `PasswordField.tsx:33-48` の doc コメントへ明記した

**実装がどうなっているか**: `stripNonPrintableASCII`（`passwordRules.ts:69`）を `PasswordField`（`PasswordField.tsx:84-94`）で**全 4 欄に無条件で**掛ける。IME 変換中は素通しし、確定時に落とす。

**⇒ 親の裁定**: **受理して `CHANGE-119` の addendum（`DES-002` §8 ＋ `DES-006` §10 への追記）を出すか、却下して差し戻すか。** **★「たぶん問題ない」で流さないこと**——承認済み CHANGE が「恒久の規則」と書いた条項である。

### 2-2 拒否の文言から「なぜ弾くか」の説明を削った

**何に反したか**——**指示書 §4.4 末尾**「**★とくに拒否の文言は「なぜ弾くか」を書くこと。**「使えない文字です」だけだと、利用者は日本語が悪いと分からない」／ **`CHANGE-119` §3.2 の文言案**（3 段落）。

**なぜ**——**開発者の指示**（2026-08-16）「**日本語パスワードが設定された時のメッセージは「日本語や全角の文字は使えません。」だけでいいです。他の説明は今回については過剰です。**」

**実装がどうなっているか**（`web/src/locales/{ja,en}.json` の `auth.setPassword.errorCharset`）:

| | 文言 |
|---|---|
| 旧（`CHANGE-119` §3.2 の案・当初の as-built） | 日本語や全角の文字は使えません。／ ほかの機器から開くときに、同じ文字が打てなかったり、見た目が同じでも別の文字として扱われたりすることがあるためです。／ 半角の英数字と記号で決め直してください。 |
| **新** | **日本語や全角の文字は使えません。** |

- **★指示書 §9.2-3 は文言の言い回しを製造裁量と明記しており、その意味では §3 でもよい。** ただし **§4.4 末尾は「なぜ弾くか」という内容の要求**であり、そこに反するため §2 へ挙げた
- **★原因は名指ししている**（「日本語や全角の文字」）ため、§4.4 が禁じた「利用者は日本語が悪いと分からない」状態にはならない
- **★あわせて、本文言は画面からは到達しなくなった**（§2-1 の入力制限により）。検査と文言は「到達しない防御」として残し、doc コメントへ明記した（`passwordRules.ts:76-80`）
- **⇒ 親の裁定**: **§4.4 末尾を狭めるか、本件を例外とするか。**

## §7 教訓（retrospective 行き）

> **★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、**実施者は設計担当**（反映担当は 2026-08-11 に廃止）。

1. **承認済み文書の規則を裁定で覆すときは、その規則が挙げていた理由を 1 つずつ数え直す。** `CHANGE-119` §2-b は理由を 2 つ持っており、開発者が解除したのは①だけだった。②（将来 検査を変えたときも同じ問題）は残ったため、実装側の歯止め 3 点で潰した。**⇒「開発者が裁定で覆した」で終わらせると、残った理由が無防備のまま流れる。**
2. **`type="password"` による IME 無効化はブラウザ任せであり、表示/マスクの切替えを持つ画面では成立しない。** 日本語が入っていたのは「決めるとき」の欄だけで、原因は表示既定により `type="text"` になっていたこと。**IME をページ側から無効化する標準の手段は存在しない**（`ime-mode` は非標準・Firefox も 2021 年に削除）。**⇒「パスワード欄だから IME は無効なはず」という前提は、切替 UI があると崩れる。**
3. **テストで固定できない実装は、その時点で選択肢から外す。** `InputEvent.isComposing` は jsdom で `fireEvent` の init から `nativeEvent` へ伝わらない（プローブで実測）。composition イベントで自前に持てば固定できる。**⇒ 実装案を選ぶ前に「これはテストで赤くできるか」を先に確かめる。**
4. **i18n キーの削除は ja↔en parity 検査を素通りする。** 両ロケールから同時に消えると parity が成立するため、型検査も全テストも緑のまま画面に生のキー文字列が出る。**⇒ parity は「両側が揃っているか」しか見ておらず、「参照されているキーが在るか」は別の検査が要る。**
5. **破壊確認で赤くなった本数を、網の厚みと読み違えない。** 本サブは 4 本赤くなったが、2 本は fixture の `"pw"` がたまたま 3 文字だっただけで、パスワードを変えれば緑のまま通る。**⇒ 赤くなった理由を 1 本ずつ確かめると、偶然の当たりが混じっている。**
6. **フレームワークのサブパッケージを import した瞬間に、新しいモジュールが依存グラフへ載る。** `echo/v4` 本体が既に direct でも、`echo/v4/middleware` は `golang.org/x/time/rate` を引き込む。**⇒「標準の仕組みを使え」と「依存を増やすな」は、サブパッケージでは両立しないことがある。指示書が特定の仕組みを名指しするときは、その import が何を足すかまで確かめてから書く。**
7. **文字範囲のような「同じ規則を 2 か所で使う」ものは、片方を他方から導く。** 判定（`validateNewPassword`）と除去（`stripNonPrintableASCII`）で正規表現を 2 つ持たず、**判定を除去から導いた**（`strip(s) !== s`）。**⇒ 範囲リテラルが 1 つしか無ければドリフトのしようがない。**
