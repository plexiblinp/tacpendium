## §1 as-built 差分（`DES` / `CHANGE-113` の改訂が要るもの）

### 1-1 「パスワードが分からないとき」——**パスもコピーボタンも出さない**

**`CHANGE-113` §3.8 の図**は次を描いていた。

```
  <config.toml の実際のパス>            [ コピー ]
```

**as-built は、パスもコピーボタンも出さない。** 代わりに**置き場所へ辿り着く手順**を 3 行で出す。

| キー | 出す文（ja） |
|---|---|
| `auth.forgot.fileName` | `config.toml`（コード表示のまま。**ボタンは付かない**） |
| `auth.forgot.fileLocation` | アプリを起動するときに使っているファイル（CombMgr 本体）と同じフォルダにあります。 |
| `auth.forgot.fileLocationHint`（新規） | 見つからないときは、起動に使っているアイコンを右クリックして「ファイルの場所を開く」を選ぶと、そのフォルダが開きます。 |
| `auth.forgot.fileOpenWith`（新規） | メモ帳などのテキストエディタで開けます。 |

**削除したキー**: `auth.forgot.copy` ／ `auth.forgot.copied`（ja・en 両方）。

**★開発者の裁定は 2 段階だった。**

1. **開発者の指摘**——「これはコピーしてもエクスプローラのパスとして使えないので意味がない」。**実装はファイル名だけをコピーしていた**（貼り付け先が無い）。
2. **製造から出した案**——「設定画面は認証済みなので `GET /api/config` に `configPath` を足せば実際のパスを出せる。ログイン画面は未認証で読めないため文言のままにする」。
3. **開発者の裁定**——**「そもそもパスは出さない。パスワードがわからない場合は設定画面に入れないので意味がない」。**

**⇒ この裁定は正しい。** 本案内が要る場面は**入場できないとき**であり、そのとき利用者はログイン画面に居る。**設定画面にどれだけ良いパスを出しても、そこへは辿り着けない。** **⇒ `GET /api/config` への `configPath` 追加は行っていない。サーバ側 diff 0。**

**★副次的に、未認証で読める `GET /api/auth/status` へファイルシステムのパスを載せる案も消えた。** その案は **LAN 上の未認証の機器から `C:\Users\<名前>\...` が読める**状態を作る。**採らなくて済んだのは幸いだった**——設計卓が `DES-002` §8 へ書くときも、**「パスは未認証の応答へ載せない」を明示しておくのが安全**である。

**★実行ファイル名は文面に書いていない。** 配布物は `combomgr-windows-amd64.exe`（`Makefile:21`）、`make build` のローカルビルドは `combomgr` であり、**固定名を書くと外れる。**

**★既知の限界（`DES` へ書くかは設計卓の判断）**: 実際の読込先は `configPath = "config.toml"`（`cmd/combomgr/main.go:81`）＝**相対パス**で、解決先は**アプリを起動したときの作業フォルダ**である。**ダブルクリック／ショートカット起動では実行ファイルのフォルダと一致する**ため上記文面で正しいが、**ターミナルから別フォルダで起動した場合はずれる。** 文面はダブルクリック起動に合わせた（その利用者は作業フォルダを理解しているため）。

> **⇒ 求める改訂**: `CHANGE-113` §3.8 の図を as-built へ差し替え、**`DES-005` のログイン画面定義に「パスは出さない」を理由付きで書く。** 理由を書かないと、次の担当が「親切のつもりで」パスを足す。

### 1-2 パスワード設定欄の注意文——**場面を具体にした**

**`CHANGE-113` §3.4 の逐語**は「入力した文字はそのまま表示されます。**周りに人がいるときは**「隠す」を押してください。」

**as-built**: 「入力した文字はそのまま表示されます。**外出先でノートパソコンを使っているときや、配信をしているとき**は「隠す」を押してください。」

**★開発者が示した想定シナリオは 2 つである**——**ノートパソコンにインストールして外出先で設定しているとき** ／ **配信中**。**「周りに人がいるとき」では、その 2 つが読み手の頭に浮かばない。**

**★これは `D-397`（ログイン欄をマスク既定にした理由＝「友人が来ているとき」「画面を配信する利用者」）と同じ場面を、設定側の文面で言い直したものである。** **⇒ 2 つの決定の根拠が同じ場面に揃った。**

> **⇒ 求める改訂**: `CHANGE-113` §3.4 の逐語を as-built へ差し替える。

### 1-3 パスワード変更の「いまのパスワード」——**表示切替を付けた（マスク既定）**

**`CHANGE-113` §3.7 の図**は、現在欄に切替を描いていない（新パスワード欄にだけ `👁 隠す` がある）。

**as-built**: **両方の欄が切替を持つ。既定値だけが非対称である。**

| 欄 | 既定 | 切替 | 根拠 |
|---|---|---|---|
| いまのパスワード | **マスク** | **あり（as-built で追加）** | 人が見ている前で開くことがある。既に決めてある値を最初から晒す理由が無い（`D-397` と同じ考え方） |
| 新しいパスワード | **表示** | あり | `D-396`。初回入力のタイプミスは `config.toml` の編集を招く |

**★開発者の指摘は「パスワード変更時、「いまのパスワード」に表示がない」。** **実装側は「打ち直せば済む」と考えて切替を持たせていなかったが、それは誤りだった**——**打ち間違えたとき返るのは「いまのパスワードが違います」だけで、自分が何を打ったのかを確かめる手段が無い。** 新規入力欄（打ち直せばよい）と、**照合される入力欄**（合っているかを確かめたい）では要求が違う。

**★実装のコメントも書き換えた。** 変更前は「現在欄は切替を持たない。⇒ 2 つの欄は揃っていない。揃えようとしないこと」と主張しており、**as-built では誤りになるためである。** 書き換え後の主張は「**既定値**が非対称。切替は両方が持つ」。

> **⇒ 求める改訂**: `CHANGE-113` §3.7 の図へ現在欄の切替を足し、**既定値が非対称であること**（と、その理由が欄ごとに違うこと）を明記する。

### 1-4 ヘッダに選択中の利用者——**`DES-005` §2 に無い新要素**

**`DES-005` §2 の共通ヘッダに、利用者の表示は無い。** `CHANGE-113` にも記述が無い。

**as-built**: **利用者が 2 人以上のときだけ**、ヘッダ右端（ハンバーガーの手前）に**選択中の利用者名**を出す。**押すと利用者選択へ戻る**（`test-id` = `header-current-user`）。

**★開発者の指摘は「選択中のユーザーが誰なのかわからない。ヘッダのどこかに小さくていいので表示が必要」。** M22-02 as-built では、表示は**設定画面の「利用者」欄の中だけ**（`settings-user-current`）で、**ふだん見る画面からは誰として操作しているか分からなかった。** **⇒ コンボやタグを保存したあとで「別人として保存していた」と気づく形になる。**

**確定した分岐（開発者裁定・2026-08-16）**

| 分岐 | 裁定 | 理由 |
|---|---|---|
| 表示条件 | **2 人以上のときだけ** | **1 人しかいない環境では選択画面も出さない**（`FR502`）。同じ考え方で、**1 人運用の画面はいままでと変えない**（最重要ゲート 2 と同じ性質の非回帰） |
| 押下時 | **押せる。押すと選び直し** | 設定画面まで行かずに切り替えられる。**交代しながら使う場面で効く** |

**★URL は動かない。** 利用者選択は `CurrentUserProvider` の条件表示であり、履歴に「済んだ画面」を積まない（指示書 §4.8-5 と整合）。

**★実装上の要点（`DES` には不要だが、次の担当のために記す）**: `CurrentUserValue` に **`multiUser: boolean`** を足し、context の既定値を `false` にした。**⇒ `CurrentUserProvider` の外で `Header` を描いても利用者表示は出ない**（既存の `Header` 単体テストが無改修で通る）。

> **⇒ 求める改訂**: `DES-005` §2（共通ヘッダ）へ**利用者表示を追加**し、**表示条件（2 人以上）と押下時の動作（選び直し）**を明記する。**★表示条件を書かないと、次の担当が「常に出す」に直して 1 人運用の画面を変えてしまう。**

### 1-5 ★復旧手順そのものが不完全だった（`CHANGE-113` §3.8 ／ `config.toml.example` ／ 本ラウンドの as-built すべて）

**開発者の追加の問い**——「**パスワードがわからなくなって、toml 編集で無効化した後の、パスワード変更はどうすればいいですか？**」

**⇒ 実装を辿った結果、`password_enabled = false` に戻すだけでは新しいパスワードを決められないことが分かった。** **設計・実装・案内文のすべてが同じ穴を持っていた。**

| 場所 | 判定 | 帰結 |
|---|---|---|
| `Service.PasswordSet()`（`internal/service/auth/service.go:93`） | `PasswordHash != ""` | 無効化しても **`password_hash` は残る**ため **true のまま** |
| `SettingsSectionUser.tsx:45` | `passwordSet` で分岐 | **「パスワードを変える」**（初回設定ではなく変更）を出す |
| `Service.SetPassword()`（同 `service.go:155`） | **`PasswordHash != ""` なら現在のパスワードの一致を要求。`password_enabled` は見ていない** | **忘れた当のパスワードを要求する** |

**⇒ 「アプリからは復旧できないが、設定ファイルを編集できれば復旧できる」という信頼の根が、実際には成立していなかった。** **`password_hash` の行も消して初めて成立する。**

**★誤っていた記述は 3 か所**——`CHANGE-113` §3.8 の手順（`password_enabled` のみ）／ `config.toml.example` の `[security]` コメント（「復旧は `password_enabled = false` に戻す方法のみ」）／ **本ラウンドで製造が書いた案内文**（`auth.forgot.step4`「そのあと、設定画面から新しいパスワードを決められます」）。**★3 つとも同じ思い込みを写していた。**

**開発者の裁定（2026-08-16）＝「案内文だけ直す」。** 振る舞い（`password_enabled = false` のときは現在パスワードを要求しない）は**採らない**。**理由**——無効な間は `POST /api/auth/password` も無認証で通るため、**LAN 上の誰でもパスワードを上書きできる状態が生まれる**（既知 followup `auth-anyone-can-set-initial-password-while-off` の射程が広がる）。**⇒ 信頼の根は「そのマシンのファイルを編集できること」に置いたままにする。**

**as-built（コード変更なし・文言のみ）**: 案内を 3 段に分けた。

1. `quitFirst`（新規）——書き換える前にアプリを終了する。**動かしたまま書き換えると、アプリ側の設定書き戻し（起動時に読んだ値が土台になる＝`configForPersistence`）で元に戻ることがある**
2. `password_enabled = true` → `false`（従来どおり）
3. `step5` / `step6`（新規）——**`password_hash = "..."` の行を消す。残っていると、新しいパスワードを決めるときに忘れた古いパスワードを聞かれる**
4. `step7`（新規）——保存して起動し直すと、設定画面から決められる

`config.toml.example` の `[security]` コメントも同じ 2 段手順へ差し替え、**(2) を落とすと復旧できない理由**（`SetPassword` が `password_enabled` を見ないこと）を書き添えた。

**テスト**: `LoginScreen.test.tsx` へ「案内が `password_hash` の削除まで含む」を 1 本追加（**手順が成立することを文言側で固定する**）。

> **⇒ 求める改訂**: **`CHANGE-113` §3.8 の手順を 2 行に直す。** **★`DES-002` §8 へ「復旧には検証子の削除も要る」を明記してほしい**——**書かないと、次に案内文を触る担当が同じ穴を再生産する（今回、設計・実装・製造の 3 者が独立に同じ思い込みを写している）。**
>
> **★もう一つの選択肢を潰しておく必要がある。** 「`password_enabled = false` なら現在パスワードを要求しない」という直し方は**自然に見えるが、無効中は当該 API が無認証で通るため採れない。** **この理由を残さないと、後から「親切な直し」として入る。**

## §4 設計担当が未把握の残課題

### 4-1 ログアウトの導線が画面に無い

**`POST /api/auth/logout` は `M22-01` で実装済み**（`internal/api/auth/routes.go:28`）で、**フロントの `authApi.logout` も存在する**が、**呼び出している画面が 1 つも無い**（実測 0 件）。

- **指示書 `M22-02` に要求が無かったため、意図して空けてある。** 本ラウンドでも足していない（開発者の指摘に含まれないため）。
- **★実害は小さい**——セッションは**サーバ再起動**と**パスワード変更**で切れ、タイムアウトは無い（`D-395`）。**「いま入っている端末を明示的に切る」手段だけが無い状態である。**
- ⇒ **共有 PC で使う場面を想定するなら要る。** 設計卓の判断を仰ぐ（**`M22` 内の別サブか、フェーズ 3 の後段か**）。

### 4-2 `Header.tsx` のナビゲーション文字列が i18n を通っていない

`NAV_LINKS` は生の日本語リテラル（`Header.tsx:22-36`）。**本ラウンドで足した文字列は i18n を通した**が、**既存の 13 本はそのままである。** 範囲外として触っていない。**⇒ `progress-log` へ横断課題として記録する。**

## §5 質問への回答（実装変更なし・記録のため）

**★以下 2 件は as-built と一致しており、`DES` 改訂は不要。** ただし**利用者に説明する文書（将来の README / ヘルプ）を書くときの正本**になるため記す。

### 5-1 パスワードの再入力が必要になるタイミング（開発者の質問 ③）

**タイムアウトは無い**（`M22-01` §1.2-5 ＝ `D-395`）。セッション Cookie は `MaxAge` 未指定（`internal/api/auth/cookie.go:39`）、実体は**サーバのメモリ上の map**（`internal/service/auth/service.go:51`）。**⇒ 再入力が要るのは次の 3 つだけ。**

1. **サーバを起動し直したとき**（メモリが消える）
2. **パスワードを変更したとき**（全セッションを破棄する＝`service.go:169`。変更した本人の画面も切れる）
3. **ブラウザを閉じたとき**（そのブラウザのみ）

**再読み込み・戻る・進む・時間経過では切れない**（E2E で固定済み）。**`CHANGE-113` §7-2 の表と完全に一致する。**

### 5-2 他の利用者が作ったタグの見え方（開発者の質問 ⑥）

**完全に見えない。** 一覧・取得すべてが `WHERE user_id = ?`（`internal/repository/tag/repository.go`）。**⇒ タグ管理画面に行そのものが出ない。プリセットのような「ほかの人が作った・削除できません」という状態表示は無い**（`D-402` の意図どおり）。

- **コンボに付いているタグも、自分のものだけが見える**（`D-405` 案 B）。**片方が保存しても相手の紐付けは消えない。**
- 利用者を追加すると**その人専用の 3 件**（使用中／練習中／頻度低下）が生成される。**同名タグが人数分並存するのは正常**（`UNIQUE (user_id, name)`）。
- **プリセットと形が違う理由**——プリセットは「コンボ表記の別名」で、**他人のものでも表示に使われる共有資産**であるため、見せたうえで「変えられない」と伝える必要がある。**タグは個人の分類なので、そもそも見せない。**
