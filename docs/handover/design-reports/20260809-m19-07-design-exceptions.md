## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1 `POST /api/combos` の `setups[]` に `verifiedConditions` を追加した（→ `DES-002`）

```jsonc
POST /api/combos
{
  "characterId": 1,
  "setups": [
    {
      "characterId": 1,
      "name": "...",
      "steps": [ ... ],
      // ★追加。省略可・空配列可。
      "verifiedConditions": [
        { "techType": "neutral_tech", "inCorner": false }
      ]
    }
  ]
}
```

- **`POST /api/combos/{comboId}/setups`（単独作成）の同名フィールドと完全に同じ形**（要素は `techType` / `inCorner` のみ。`result` は `ok` 固定、`note` は扱わない）。**追加のみの後方互換**。

## §3 製造の判断（設計卓の確認は要らないが、知っておいてほしいもの）

### 3-1 ★サービス層・リポジトリ層に変更が要らなかった（指示書 §2.1 との差）

指示書 §2.1 は「サービス層——コンボ作成のトランザクション内で、`combo_setups` を作った直後に `combo_setup_results` を書く」と書いており、サービス層に作業があるかのように読める。**実査の結果、そこは M19-03 の時点で既に完成していた。**

```
internal/service/setup/service.go:243  InsertComboSetup          ← combo_setups を作る
internal/service/setup/service.go:248  insertVerifiedConditions  ← 同一 Tx・紐付けの後
```

**欠けていたのは API 層の写像だけ**である（`internal/api/combo/dto.go` の `toServiceCreateInput` が `VerifiedConditions` を埋めていなかった）。指示書の前提（「片側にある形をもう片側へ揃える」）は崩れておらず、**作業が少ない方向の食い違い**だったため停止せず続行した。

⇒ `internal/service/` ／ `internal/repository/` に **diff 0**。R-4（新しい書き込み経路）は構造的に発生しない。

### 3-2 パッケージ境界の跨ぎ方（§8.2 で推測可とされた事項）

**`internal/api/combo` から `internal/api/setup` を import し、`setupapi.SetupResultConditionRequest` をそのまま使う。型を 1 つも新設しない。**

| 案 | 採否 |
|---|---|
| **import して型をそのまま使う** | **採用**。宣言ゼロで「型は 1 つ」が自明 |
| `combo` 側に type alias | 不採用。名前が 2 つになり「別型では？」の疑いを生む |
| 共有 DTO パッケージへ移動 | 不採用。該当パッケージが無く、`api/setup` の既存参照を全部書き換える＝対称化の範囲を超える |
| 同名同構造の型を再定義 | 不採用（R-8 に直撃） |

**安全性の実査**: `internal/api/setup` は `internal/api/combo` を **テストを含め一切 import していない**（循環しない）。層としては handler 層内の同層参照で、`DES-002` §2 の「依存方向は上から下への一方向」に反しない（上位層を参照していない）。`api/combo/dto.go` は既に `service/setup` を import しており、setup ドメインへの依存自体は新規ではない。

**★これが本プロジェクトで初めての api → api 参照である**（`grep` で既存 0 件）。パターンとして問題があれば `architecture-patterns.md` 側で方針を示してほしい。

## §4 設計担当が未把握の残課題

### 4-1 ★値域外 `techType` の HTTP ステータスが、同梱と単独で食い違う

| 経路 | 値域外 `techType` の応答 |
|---|---|
| **`POST /api/combos`（同梱・本サブ）** | **400 `invalid_setup_result`** |
| `POST /api/combos/{comboId}/setups`（単独・M19-03） | **500 `internal_error`** |
| `PUT /api/combos/{comboId}/setups/{setupId}/results`（M19-03） | 400 `invalid_setup_result` |

**原因**: `setupResultError`（`internal/api/setup/setup_results_handler.go:105-120`）が `ErrInvalidResultValue` → 400 を写像しているが、**`internal/api/setup/handler.go:46-53` の `CreateSetup` はこの写像を通っていない**（`setupsvc.ErrNotFound` しか特別扱いせず、他は 500）。**M19-03 からの既存の取りこぼし**である。

**本サブで直さなかった理由**: 指示書 §4-8 / R-2 が「`CreateSetupRequest` を使う既存経路が不変であること」を求めており、応答ステータスを変えるとこれに抵触する。**直すなら別サブで両方を揃えるべき**。

**⇒ 裁定をお願いしたい**: (a) 単独経路も 400 へ揃える（followup 起票）／(b) 現状のまま許容し `DES-002` に非対称として明記／(c) その他。

### 4-3 ~~★採用パネルだけが旧デザインで残っている~~ → **2026-08-10 解消済み**

### 9-1 「指示書が要求した作業が、実は既に入っていた」形

指示書 §2.1 はサービス層に作業があるかのように書いていたが、**M19-03 が `CreateSetupInTx` にも `insertVerifiedConditions` を入れていた**ため、実際に欠けていたのは API 層の写像 1 か所だけだった。

**★これは「実装が指示書を上回っていた」ケースであり、指示書が誤っていたわけではない**（M19-03 が対称に作ってくれていた）。**着手前の実査で「どこが欠けているか」を先に特定していなければ、既にあるものを二重に書いていた可能性がある**（同一 Tx 内で `insertVerifiedConditions` が 2 回呼ばれ、`ON CONFLICT DO UPDATE` のため**エラーにならず**気づけない形になっていた）。

**適用**: 「A を B へ揃える」型のサブでは、**B 側の全レイヤーを実査してから欠落箇所を確定する**。「指示書が書いている作業＝まだ無い作業」と読まない。

### 9-2 撤回された原則の「形」だけが、正しいアサーションに貼り付いて残る

`web/e2e/m19-03-setup-results.spec.ts:349` は、**アサーションも括弧内の理由も現行（v3）どおり正しい**のに、**文頭の言い回しだけが撤回済みの v1（画面名による禁止）の形**で残っていた。指示書 §5 の走査キーワード（`セットプレイ編集画面に置かない`）とは**文字列が一致しない**（実際は `セットプレイ編集画面には成立条件 UI を置かない`）ため、キーワードの完全一致では取り落とす。

**適用**: 否定形確認の走査は、**指定キーワードの近縁変形（助詞の挿入・目的語の追加）まで広げる**。「原則を撤回した」ときに危ないのは原則そのものではなく、**正しい判断に貼り付いた古い言い回し**である——中身が正しいぶん、レビューでも見逃されやすい。

### 9-3 「次の番号」を書いた行は、自分が予告したとおりに失効する

`change-number-registry.md:126` は「★この行は連番を消費するサブが完了するたびに古くなる」「サブの完了報告と対で更新する運用が要る」と**自ら警告していた**が、M19-06 が `CHANGE-095` を消費した時点で**その警告どおり失効した**（レジストリ §1 表にも 095 の行が無く、契約 §4 も 094 のまま）。

**適用**: 警告文を書くことは運用にならない。**「対で更新する」を運用にするには、更新する側（完了報告）のテンプレートに項目として入れる**。本レポートの §8 に「併せて更新が要るもの」を常設項目として置いたのはそのため。
