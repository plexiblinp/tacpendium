## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★実測件数は設計書へ書かないこと**（`D-374` ／ `E-136`）。本節の数値は反映の判断材料であって、設計書へ転記する値ではない。

### 1-1 nightly の 3 OS クロスビルドは **ubuntu ランナー 1 台**で成立する

`DES-002` §11.3 は「Windows / macOS / Linux 3OS向けのクロスビルドを毎回実行する」とだけ書いており、**どのランナーで行うかを規定していない。** 製造は **ubuntu-latest 1 台で `make build-all`** を呼ぶ形を採った（`.github/workflows/nightly-crossbuild.yml`）。

根拠は 2 つ。**(1)** `modernc.org/sqlite` が純 Go で CGO を要さないため、`Makefile` の `build-windows` / `build-darwin` / `build-linux`（いずれも `CGO_ENABLED=0`）がホスト OS を問わず成立する。**(2)** 本リポジトリは private であり、Actions の実行時間は **macOS が 10 倍・Windows が 2 倍**で消費される。OS ランナー 3 台構成にすると概ね 13 倍になる。

**ローカル実測で成立を確認済み** —— `make build-all` が exit 0 / 127 秒で 3 点を生成し、`file(1)` が **PE32+ x86-64 / Mach-O 64-bit arm64 / ELF 64-bit x86-64** を返した。

**⇒ `DES-002` §11.3 へ「3 OS 向けのクロスビルドは単一の Linux ランナーで行う。CGO を要する構成（`mattn/go-sqlite3` フォールバック）を導入するとこれが崩れる」を明文化してほしい。**
**★依存関係を明示することに意味がある** —— §11.3 は既に「フォールバックを行う場合は CGO 有効化が必要」と注記しているが、**それが CI の構成コストに直結することは書かれていない。**

### 1-2 「必須 check」はワークフローファイルでは決められない

指示書 §11-2 の暫定案（PR の高速検査のみ必須・nightly は必須にしない）は開発者が確定した（§3-1）。
**ただしこれは `main` の branch protection の設定であって、ワークフローファイル側には書けない。** 製造は README に方針と登録手順を書き、開発者が **2026-08-22 に 3 件**（`go vet + go build` ／ `go test` ／ `web test (Vitest)`）を必須 check として登録した。

**⇒ `CHANGE-129` の反映時に「必須 check の登録は repo 設定であり as-built の確認が要る」ことを 1 行で押さえてほしい。** 設計書に「必須にする」とだけ書くと、**設定されていないのに設定済みと読まれる。**

### 1-3 ★PR 作成直後にワークフローが起動しなかった（**原因未特定**）

**受入確認の伴走中（2026-08-22）に観測した事象である。** リポジトリにとって最初の
ワークフローを PR で持ち込んだところ、**PR 作成直後は run が 1 件も起動しなかった。**

**観測**（PR **#87**・head `9f5bbe5`・base `main`）
- ワークフロー 2 本は push 済みコミットに正しいパスで存在（`git ls-tree` で確認）／ `.gitignore` は `.github` を除外していない
- `Settings → Actions → General` の Actions permissions は **`Allow all actions and reusable workflows`**
- それでも `gh run list` は **`no runs found`**、`gh pr checks 87` は **`no checks reported`**
- Actions タブは存在するが **「Get started with GitHub Actions」の空状態**

**★その後、同じブランチへ push したところ `pull_request` の run が起動し、緑で完走した**
（run `32554255983` / 5m53s）。**この時点で `main` にワークフローは無い。**
**⇒ 「既定ブランチに載るまで `pull_request` で拾われない」という説明は誤りである。**

**原因は特定できていない。** 候補は 2 つ——(a) 開発者が `Settings → Actions → General` を
開いた際に設定が保存され、Actions が初期化された ／ (b) リポジトリ初回のワークフロー登録に
時間差があった。**どちらとも決められないため、断定しない。**

**⇒ 設計卓への依頼は 1 点だけ。** 受入条件 §5-1（PR ワークフローが緑で完走）は
**マージ前に満たせないことがある**。「**初回に限りマージ後の `push` 実行で代替してよい**」を
`CHANGE-129` の反映へ含めるかどうかを判断してほしい。

### 1-4 ★`go test | tee` は `pipefail` を明示しないと失敗を覆い隠した

**初回の意図的失敗確認で、テスト本体は失敗したのに `go test` job が緑になった。** run
`32558255492` のログでは `TestCIRedCheck` が `t.Fatal` で失敗し、`go test` の最終出力も
`FAIL` だったが、3 job とも成功扱いで完走した。

原因は、実ランナーの当該 step が `/usr/bin/bash -e` で実行され、`go test ... | tee go-test.log`
というパイプ全体の終了コードが末尾の `tee` の 0 になったためである。ワークフローのコメントは
「GitHub 既定シェルは `bash -eo pipefail`」を前提にしていたが、**実測と一致しなかった。**

**是正**: `go test` step の冒頭で `set -o pipefail` を明示した。再検証 run `32559162042` は
`go test` **失敗（4m29s）** ／ `go vet + go build` **成功（31s）** ／
`web test (Vitest)` **成功**（3m50s）となり、意図的失敗を狙った job だけへ伝播することを確認した。

**⇒ `CHANGE-129` への反映候補:** CI例を設計へ残す場合、ログ保存のためコマンドを `tee` へ
流す step は `set -o pipefail` を明示する。ランナー既定値への依存は、今回の実測で安全でないと分かった。

## §2 契約・設計に反する独自判断（★独立カテゴリ・最優先）

### 2-1 ★指示書 §2.3 / §9.1-3 の「書かずに停止」を採らなかった

**条文**: 指示書 §2.3 は「**CI が実行できない事情が判明した場合は、ワークフローを書かずに停止して報告する。★『書くだけ書いて動かさない』を成果物にしない —— 動いていないワークフローは、次の担当に『CI は在る』と誤読される**」と定める。§9.1-3 も同じ内容を**推測で進めてはいけない事項**に挙げ、チェックリスト §9 も**重大**として挙げている。

**実際に起きたこと**: 製造セッションからは **GitHub Actions を起動できず、実行結果も取得できなかった**。Actions API がエージェントプロキシで **HTTP 403**（`"Access to this GitHub Actions path is not permitted through this proxy."`）、GitHub MCP は `.claude/settings.json` の `mcp__*` 一括 deny、`gh` CLI 未インストール。**Actions が repo で有効かどうかすら読めない。**

**⇒ 製造は独断せず、指示書 §11-1 の暫定案（「Plan Mode で製造に確認させる」）に従って Plan Mode で提示し、開発者が「案 B（製造が書き、実行と緑の確認は開発者の手番）」を選択した**（2026-08-20）。

**★親の裁定を要する点は 2 つ。**

1. **§2.3 の条文が想定していた事情と、実際の事情が違う。** 条文は「**repo で Actions が使えない**」を想定していたが、起きたのは「**製造セッションからは起動も観測もできない**」である。後者は §4.2-5（実機起動は開発者の手番）と同じ形であり、**「人の手番へ渡す」で扱える。**
   **⇒ 条文を「repo で Actions が使えない場合」へ狭めるか、「製造が観測できない場合は人の手番へ渡す」を明示的な分岐として足すかを決めてほしい。**

   **レビュアーは「おおむね十分」と判定した上で穴を 2 つ挙げ、いずれも取り込み済みである**（必須 check の断定形 ／ 完了報告 §4 が未作成物を作成済みと書いていた）。

**★製造としての見解**: **案 A（書かずに停止）を採っていた場合、CI は 1 行も書かれず、`CO-017` は次の担当へ丸ごと戻っていた。** 一方で条文の懸念（「CI は在る」と誤読される）は実在する。**⇒ 条文を消すのではなく、「未検証マーカーと削除条件を置くこと」を条件つきの分岐として書くのが最も再現性が高いと考える。** 判断は設計卓へ委ねる。

**受入後の状態（2026-08-22）**: 緑・意図的失敗の赤・nightly artifact 3 点を確認し、必須
check 3 件を登録した。両ワークフローと README の未検証マーカーは受入後処理で削除済みである。

### 4-2 `ci-count1-machine-check`（**新規登録**）

## §7 教訓（retrospective 行き）

> **★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、**実施者は設計担当**（反映担当は 2026-08-11 に廃止）。

1. **★「記載済み」と書かれているものを確認するとき、走査対象を絞ると偽の否定が出る。**
   `followup-backlog` §F の「README/log 記載済」を確認する際、**`README.md` だけを走査して「無い」と結論しかけた。** 実体は **`README.txt`（配布物 README）** にあった。**⇒ 否定形確認では、まず「その名前のファイルが他にもないか」を見ること**（`find . -iname "README*"` を先に打っていれば防げた）。**本件は「書き直さない」が正解の分岐だったため、誤ったまま進めていれば二重管理を作っていた。**

2. **★検査を作る回では、作った検査の外に同型の穴が残っていないかを見ること。**
   CI に `-count=1` を入れることには成功したが、**同じ罠がフック（`stop-test.sh`）と `Makefile` と `CLAUDE.md` に残っている**ことは、指示書 §4.9-3 の走査を回して初めて分かった。**⇒ 否定形確認は「作ったものの検算」ではなく「同じ穴の全数探索」として使うと効く。**

3. **完了報告の成果物一覧を、作る前に書かない。**
   `progress-log.md` の追記と本レポートを「追記」「新規」と書いた時点では、どちらも存在しなかった（レビュー 高-1 / 高-2）。**未検証マーカーを 3 重に張って「在ると誤読させない」ことに注力した回で、報告自身が未作成のものを作成済みと書いていた。** **⇒ 成果物一覧は工程の最後に書くか、未作成のものには印を付ける。**

4. **★原因を特定できていない事象へ、もっともらしい説明を与えないこと。**
   PR 作成直後の `no runs found` だけから「最初のワークフローは既定ブランチに載るまで拾われない」と断定したが、後続の `pull_request` run が `main` へのマージ前に完走し、説明は否定された（§1-3）。**⇒ 観測と原因を分け、反証できるまでは「原因未特定」のまま記録する。**

5. **★パイプの途中にある検査コマンドは、失敗させて終了コードを実測すること。**
   `go test` の出力には `FAIL` が出ていたのに、`tee` の exit 0 によって job は緑になった。静的なコメントで既定シェルに `pipefail` があると仮定しても、失敗経路の検証にはならない。**⇒ `set -o pipefail` を明示し、意図的失敗で対象 job だけが赤になるところまでを受入条件にする。**
