## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1 実測資料からの転記マイグレは **1 行 1 UPDATE で書く**（条件式で束ねない）

- **事象**: 先行の `000052`（M19-04）は同値の行を `code IN ('standing_light_punch', 'crouching_light_punch')` のように**束ねて** UPDATE していた。本サブは指示書 §4.1 の明示要求により **16 本を 1 行 1 UPDATE** で書いた（`migrations/000060_backfill_moves_chain_cancel_total_third_wave.up.sql`）。
- **理由**: 束ねると「どの技にどの値を入れたか」が読んで確認できず、**写像の誤りが目視レビューで見えなくなる**。写像を誤ってもエラーにならない（別の技に値が入るだけ）ため、**レビューが最後の砦**になる。
- ⇒ **`SUPP-001 §5.5`（マイグレ契約テストの節）へ「実測資料など DB/CSV に一次源が無い値の転記マイグレは、1 行 1 UPDATE でキャラクターコードと `move_code` を明示する」を明文化してほしい。** 残り 12 キャラの seed 波で同じ形が繰り返される。

### 1-2 実測資料からの転記マイグレは **`IS NULL` を条件に持つ**

- **実装**: `000060` の全 16 UPDATE に `AND chain_cancel_total IS NULL` を付けた（`000052` には無い条件）。
- **効果**: 指示書は二重投入の防止として求めているが、副作用として「**既に値がある行は上書きしない**」という不変条件が入った。後続の波が同じ行を再投入しても既存値を壊さない。
- **down は `IS NULL` を持たない**（明示列挙した行を無条件で NULL へ戻す）。
- ⇒ **1-1 と同じ節へ併記してほしい。** ★ただし **これは契約 F-4 (2) の字面と衝突する。§2-1 を参照。**

### 1-3 非対称ロースターを持つ列の契約テストは、「**入れた行**」と「**入れてはいけない行**」を **対で固定する**

- **事象**: 指示書 §5 は「投入した 16 行」の固定しか求めていない。しかし**圏外への誤投入は件数 16 を保ったまま起こり得る**（ロースター内 1 行を落として圏外 1 行に入れれば 16 のままである）。
- **実装**: `m1904bOutOfRoster`（`internal/infra/migration/migrate_m1904b_test.go`）として**圏外 9 行が NULL のままであること**を独自に追加した。
- **実証**: 破壊テスト #3（`jamie` Stand LK → Stand LP の写像取り違え）で、**この検査が「どこへ誤って入ったか」の特定に効いた**（4 か所が独立に検出）。
- ⇒ **`SUPP-001 §5.5` へ「値域が非対称なデータ投入の契約テストは、投入行と非投入行を対で固定する」を明文化してほしい。**

### 1-4 down のスコープ限定は「**スコープ外の行を仕込んでから down する**」形で検証する

- **事象**: `move_derivations` には本サブの 9 行しか無いため、**`DELETE FROM move_derivations`（表を空にする誤実装）と正しい明示削除が同じ結果になる**。現状のデータでは区別できない。
- **実装**: テスト内で `ryu` の親子ペアを 1 行仕込んでから down し、**それが生き残ること**で明示削除であることを示した（`TestRun_M1904b_MoveDerivationsZangief`）。
- ⇒ **`DES-003 §3.20` の「明示削除の責務」の記述に、「明示削除であることの検証はスコープ外の行を作って行う」を補足してほしい。** 同じ問題は `combo_setup_results`（§3.19）にもある。

### 1-5 ★マイグレの契約テストは、比較区間の終端を **自サブの最終連番に閉じる**（`m.Up()` を使わない）

- **確定した規約**: 「既存値を書き換えていないこと」を検証するとき、**終端は自サブの最終連番**（本サブなら `m.Migrate(61)`）とする。**`m.Up()`（HEAD 終端）を使ってよいのは、「HEAD が何であっても成り立つ」ことを意図的に主張したいときだけ。**
- **理由**: 契約 F-2 が求めているのは「**そのサブが**書き換えていないこと」であって「**以後のどのサブも**書き換えないこと」ではない。HEAD で止めると、**後続サブが正当な是正を入れた瞬間に、無関係な過去サブのテストが落ちる**。そのとき「期待値を緩める」誘惑が発生し、契約テストが形骸化する。
- **経緯**: **本サブ自身がこれをやらかしてレビューで検出された**（レビュー報告書 H-1）。**§4-1 で「M19-04 の `TestRun_M1904_StartupTotalUnchanged` が HEAD 終端のせいで落ちている」と正しく診断しておきながら、新規テストで同じ形を書いていた。** 是正後、`000062` に M19-04c 相当の一時マイグレ（`guile` 6 行の `startup` 変更）を置いて **green のままであること**を実証してから削除した（是正前なら `changed = 6, want 0` で FAIL）。
- ⇒ **`SUPP-001 §5.5` へ「マイグレ契約テストの終端は自サブの最終連番に閉じる」を明文化してほしい。** **これは既存の欠陥（§4-1 の #3）の再発防止でもある。**

> **★同型の罠は `expectedMovesDelta`（§4-1 の #1・#2）にもある。** 「**増分を許容する表**」と「**比較区間**」は**セットで設計しないと必ずずれる**。**区間を自サブに閉じれば、そもそも増分表が要らなくなる場合が多い。**

## §2 契約・設計に反する独自判断（★親の裁定が要る・**1 件**）

### 2-1 契約 **F-4 (2)** の字面に反して、**CSV が空欄の 16 行を UPDATE した**

| | 内容 |
|---|---|
| **何に反したか** | `docs/process/m18-m19-contract.md` §2 **F-4 (2)**——「**新連番の backfill マイグレを生成するときは、CSV で値が空の行を UPDATE 対象に含めない**（既存 backfill 3 例と同型。**`COALESCE` マージの前例は無いので採らない**）」 |
| **実装がどうなっているか** | `migrations/000060_backfill_moves_chain_cancel_total_third_wave.up.sql` が、**`character_data/*.csv` の `chain_cancel_total` 列が空欄である 16 行を UPDATE している**（当該列は 17 本すべてで全行空欄。M19-04 が列だけ足して値は素通しにしたため） |
| **なぜそう判断したか** | F-4 (2) の**趣旨**は「**空欄の行が既存値を NULL で上書きする**（エラーにならない）」の防止である。`000060` はこれを起こさない——**(a) 値の一次源が CSV ではなく実測資料**（`character_data/chain-cancel-measurements.md` v2.3.0。ボード **D-99** が「CSV には転記しない」と決めている）、**(b) 投入する値は常に非 NULL**（実測資料の確定値）、**(c) `WHERE chain_cancel_total IS NULL` で既存値を保護**している |

**★製造はこれを「趣旨に反しないので問題ない」と判断して実装した。しかしそれは実装が契約の適用範囲を自分で裁定したということであり、親の裁定を仰ぐべき事柄である。**

**親に求める裁定は二択**:

- **受理する場合** ⇒ **F-4 (2) の条文へ「本項は CSV を一次源とする backfill に適用される」という限定を明記してほしい。** 現状の条文は「backfill マイグレ」一般を対象としており、**`000060` を『CSV 空欄行を UPDATE してよい前例』と読む余地が残る**（レビュー M-1 の指摘もこれ）。
- **差し戻す場合** ⇒ `000060` の投入方式そのものを再設計する必要がある（ただし **D-99 が CSV への転記を禁じているため、F-4 (2) を字面どおり適用すると `chain_cancel_total` はどの経路でも投入できなくなる**。この矛盾も併せて裁定されたい）。

> **★本項は初版レポートでは §2 ではなく完了報告 §9 の注記に置いていた。** 「趣旨に反しないから §2 ではない」と製造が判断したためだが、**それ自体が「自分で裁定して §3 へ混ぜる」形**であり、`/design_handover_report` の §2 定義に反していた。**改稿で §2 へ引き上げた。**

### ★4-1【要裁定・最重要】`go test ./...` が **着手前から red**（3 テスト）— **M19 の完了条件が満たせない**

### ★4-2【要裁定】第三波 6 キャラが `000050` の機械 backfill を受けていない

**`000050`（機械 backfill）は `000055`（第三波 seed）より前に適用される。** `000053`〜`000059` のいずれも `startup_basis` / `fastest_unreachable` に触れていない（grep ヒット 0）。**実 DB での確認結果**:

| 列 | 第三波 6 キャラの実測 | あるべき姿 |
|---|---|---|
| `startup_basis` | **`unknown` = 625 行（全行）** / `standalone` 0 / `through` 0 | `is_derived=0` → `standalone`／`category='rush_variant'` → `through` |
| `fastest_unreachable` | **`1` = 0 行** | `code` に `jumping_` を含む行（C 型）→ `1` |

**性質**: **「1 回きりの backfill マイグレ」は、その後に INSERT される行を拾えない。** `000051` のヘッダコメントは同じ罠を「静かに壊れる型」として警告し、連打版 3 行に新列を明示投入して回避している。**seed 波 6 キャラ分では同じ手当てが取られていない。**

**求める裁定**: **(a) 第三波への機械 backfill 追随サブの発行。** **(b) 「今後の seed 波は、既存の backfill マイグレの内容を自分の波にも適用する」という一般規約を seed 波の指示書テンプレートへ入れるか。** **残り 12 キャラで同じ取りこぼしが確実に再発する。**

## §7 教訓（retrospective 行き）

> **★親チャットは本節を読まなくてよい。宛先は反映係（Claude Code）であり、`retrospective-log` へバッチ反映される。** 外出先（スマホ）では **§1〜§4 だけコピーすれば足りる。**

1. **「自分が指摘した罠を、同じ成果物で踏む」は起こる。** 本サブは §4-1 で「HEAD 終端の比較区間は後続サブで落ちる」と正しく診断しておきながら、**新規テストで同じ形を書いた**（レビュー H-1 で検出）。**他人のコードの欠陥を診断した直後は、同じ観点で自分の成果物を見直す**——診断は「その観点を持っている」ことの証明にならない。**機構化するなら「診断した anti-pattern を成果物に grep する」を完了条件に入れる。**

2. **「増分を許容する表」と「比較区間」はセットで設計しないと必ずずれる。** `expectedMovesDelta` は M19-04 が正しく導入したが、M14-03e が比較区間の終端を変えたことで**適用区間と増分の出所がずれた**（§4-1 の #1・#2）。**区間を自サブに閉じれば増分表そのものが不要になる場合が多い。**「緩めない」ための表が、区間設計を誤ると「原理的に満たせない期待値」を作る。

3. **並行サブは、各自が green でも合流後に落ちる。誰も合流後を実行していない。** M14-03d の設計伝達レポート §4 は「**件数前提テストの洗い出しは grep だけでは漏れる。必ず全体実行で確定させる**」と申し送っているが、**「全体実行」の担当が並行運用では宙に浮く**。**機構化するなら「合流後に `go test ./...` を通す担当」をボードに明示的に置く**か、**seed 波と列追加波を並行させない**。

4. **「1 回きりの backfill マイグレ」は、その後に INSERT される行を拾えない。** `000050` と `000055` の順序で第三波 625 行が取り残された（§4-2）。**同じ罠を `000051` のコメントは認識していた**（連打版 3 行に新列を明示投入）が、**seed 波側には伝わっていない**。**列を足す波と行を足す波が並行するときは、両方向の追随を成果物に含める。**

5. **「壊して FAIL を確認する」は、合否だけでなく失敗メッセージの読みやすさまで見ると価値が上がる。** 破壊テスト #3 が当初「NULL を int へ変換できない」という**原因の分かりにくい `Fatalf`** で止まり、**後続の検査まで到達しなかった**。「非 NULL を先に確かめてから値を読む」へ変えたところ **4 か所が独立に検出**するようになった。**テストは落ちたときにしか読まれないため、落ち方の質がそのままレビュー・是正の速度になる。**

6. **クラウド実行環境では「実査せよ」が 2 段構えになる。** dev DB も SQLite CLI も無く、Plan Mode は read-only である。**マイグレ生成 SQL は DB 状態を完全に決定するため一次源として実用に耐える**が、**「導出値である」ことを明示し、実装冒頭で必ず実クエリと突合する**運用が要る（本サブは 8 項目すべて完全一致した）。**指示書テンプレートの「実査」節に、この 2 段構えを許容する但し書きを入れるとよい。**
