## §2 契約・設計に反する独自判断（★親の裁定が要る・4 件）

### 2-1【最重要】ザンギエフ連打版の `startup_basis` は指示書の示唆に反して `'standalone'` とした

- **何に反したか**: 指示書 `M19-04-frame-cost-columns.md` §4.6 の括弧書き —「`startup_basis` は連打版なので **`through`** が妥当だが、**DESIGN-07 §1-3 の実測記述に従うこと**」。
- **なぜそう判断したか**: **DESIGN-07 §1-3 は su/act/rec/total の実測値表であって `startup_basis` に言及していない。** `startup_basis` を明記しているのは同書 **§9-1** であり、そこには次のようにある。

  > 設計＝連打版 3 技を moves の通常行として新規登録（rush_variant と同型の変種別行パターン）し、**`basis=standalone`＋親参照（グループ員）を付与** → 既存導出で単独入力不可が成立し、§5-4 の一般則で単独 filler/target から自動排除。

  指示書自身が「DESIGN-07 の記述に従え」と委ねているため、**設計正本を優先した**。意味的にも整合する——連打版の `startup`（4/3/3）は「連打版という技そのものの単独値」であって、通常版から連携でつないだ通し値ではない。
- **実装がどうなっているか**: `migrations/000051_seed_moves_zangief_rapid.up.sql`（INSERT で `'standalone' AS startup_basis` を明示）。固定テストは `internal/infra/migration/migrate_m1904_test.go` の `TestRun_M1904_ZangiefRapid`。
- **レビューの独立確認**: fresh subagent が DESIGN-07 §9-1 の原文を確認し、**指示書の括弧書きが誤誘導であるという製造の指摘が正しい**と裏付けた。
- ⇒ **受理なら指示書 §4.6 の括弧書きを削除／`standalone` へ訂正してほしい。** 却下なら差し戻し（`through` へ変更するマイグレを別連番で追加する形になる）。

### 2-2 `chain_cancel_total` を 000051 の INSERT で与えず 000052 へ集約した

- **何に反したか**: 指示書 §4.6 —「**新規行にも新列の値を明示的に与えること**」。新列 3 つのうち `startup_basis` と `fastest_unreachable` は 000051 の INSERT で明示したが、**`chain_cancel_total` だけは 000051 で NULL のままとし、000052 でまとめて投入した**。
- **なぜそう判断したか**: **実測資料からの転記を 1 本のマイグレに集約し、37 行を 1 つの件数固定テストで担保するため**（値の一次源を 2 か所に散らさない）。指示書 §4.4.5 も「想定件数 **37 行**（うち 3 行はザンギエフ連打版＝§4.6 で新規登録する行）」と書いており、**37 行を 1 本で数える前提**になっている。
- **副作用（＝新しい順序制約）**: **000052 は 000051 より後でなければならない。** 前に置くと連打版 3 行が 0 件更新になり、**それはエラーにならない**。両マイグレのコメントに明記した。
- ⇒ **受理なら、指示書 §4.6 の「新規行にも新列の値を明示的に与えること」に「ただし実測値列は転記マイグレへ集約してよい（順序制約を明記すること）」を補ってほしい。**

### 2-3 `internal/seedgen/generate.go` の `validate()` へ `startup_basis` の値域検証を追加した（スコープ超過）

- **何に反したか**: 指示書 §4.2 が列挙する「三点更新（`csvColumns` / `parseRow` / `MoveRow`）＋ `testHeader` ＋テスト行リテラル」の**枠外**。M14-03c §4.3.1 の「I/O 境界のみ」という限定（ボード D-74）にも形式上抵触する。
- **なぜそう判断したか**: 既存の `category` と同じ分業（`parseRow` は型エラーのみ、意味検証は `validate` が problems に積む）に揃えるため。`validStartupBases` は `validCategories` と同型の map で、**空欄を許容する**（未記入＝DDL の DEFAULT `'unknown'` に委ねる）。
- **レビュー指摘（中・#5）**: **Phase 2 で開発者が CSV に値を書き始めると、タイポ 1 件で `Generate` 全体（既存 7 stem を含む）が停止する。** また 3 列で扱いが非対称。
- **製造の反論**: (a) 指示書が名指しで禁じたのは**生成側**（`writeMovesInsert` / `writeAliasInsert` / `rawDataSQL` / `CustomHeader`）であり `validate` は含まれない。(b) **golden 7 stem が byte-identical で green ＝変換規則は無改変**であることが機械的に証明されている（`-check` も OK）。(c) 非対称という指摘については、`chain_cancel_total` は `parseNullableInt`、`fastest_unreachable` は `parseBool` が**parse 時点で型検証している**ため、文字列 enum の `startup_basis` だけが `validate` を要するという構造であり、`category` と同じ形になっている。(d) タイポで止まるのは `category` の既存挙動と同一で、エラー文言はキャラ／技／値を含む。
- **実装がどうなっているか**: `internal/seedgen/generate.go:116-118`（`validate` 内）＋ `internal/seedgen/model.go:32-35`（`validStartupBases`）。テストは `TestGenerate_UnknownStartupBasisFails`。**現状は残している**（削ると CSV の値域逸脱が Phase 2 まで検出されなくなるため）。
- ⇒ **残すか、Phase 2 の新規ファイル側（`generate_m1904.go` 等）へ寄せるかの裁定をお願いしたい。** 「寄せる」なら Phase 2 の指示書で `generate.go` からの撤去を指示してください。

### 2-4 契約 F-4 は契約本体ではなく CHANGE-091 §3.4 の新形に従った

- **何に反したか**: `docs/process/m18-m19-contract.md:48` の F-4 は**旧文言のまま**（「CSV 再取込が新列の人手付与値を上書き・NULL 化しない」）。
- **なぜそう判断したか**: **CHANGE-091 §3.4 が「発生条件そのものが存在しない」と裁定して新しい不変条件へ書き換えている**（①CSV → 既存 DB へ値が流れる経路を新設しない ②CSV で空の行を UPDATE 対象に含めない ③`COALESCE` マージは採らない＝ボード D-75）。指示書 §4.8-2 も新形を明記している。
- **実装がどうなっているか**: 本サブは CSV → DB の経路を新設していない（新列は seedgen の SQL 非投入）ため、①②③いずれも自動的に満たしている。
- ⇒ **契約本体 §2 の F-4 を CHANGE-091 §3.4 の新形へ改訂してほしい**（現状は契約と CHANGE が食い違ったまま後続サブが読むことになる）。

## §7 教訓（retrospective 行き）

> **本節は親チャットが読む必要はない。** 宛先は反映係（Claude Code）で、`retrospective-log` へバッチ反映される。

1. **指示書の「括弧書きの示唆」と設計正本が食い違うとき、示唆のほうが後から書かれていても正本が優先とは限らない。** 本サブは指示書 §4.6 が `through` を示唆しつつ「DESIGN-07 に従え」と委ねていたため、**委任の文言を根拠に正本を読みに行って**食い違いを発見した。**指示書が「〜に従うこと」と外部文書へ委任している箇所は、委任先の該当節を必ず開く**（指示書が指した節番号が正しいとも限らない——本件は §1-3 を指していたが実体は §9-1 にあった）。
2. **値を持たない列を「通常版からコピー」で埋めたくなるが、実測されていない値は NULL が正しい。** 本サブは連打版の `damage`／`on_hit`／`on_block` を NULL のままにした。結果として**確定反撃の始動技候補から自動的に外れ**（`Damage == nil` スキップ）、**手動確認レーンに「わからない」として出る**という、設計どおりの穏当な挙動になった。**捏造した値は「もっともらしく間違った候補」を生むが、NULL は「わからない」を正しく伝播する。**
3. **「静かに壊れる」列を足したら、その列を消したときに落ちるテストを必ず 1 本書く。** 本サブは `insertRushVariantSQL` に `'through'` リテラルを足したが、**リテラルを消してもどのテストも落ちない**状態だった（レビューで検出）。ガードを足したあと、**実際にリテラルを外して FAIL することを確認**してから復元した。**「テストを足した」で終えず「そのテストが落ちること」を確認する**のが、この型の唯一の検証法である。
4. **件数前提テストが後続の波で落ちたとき、期待値を緩めてはならない。** `TestRun_M1403c/d_OtherCharsUnaffected` は「他キャラは 1 行も増減しない」という強い不変条件で、これを `!=` から範囲比較に緩めると価値が消える。**「意図的な増分の表」を別に持ち、それ以外はゼロを要求する**形にすれば強さを保ったまま追従できる。
5. **CSV を機械処理するときは「1 行だけ違う行」を先に探す。** `character_data/*.csv` 17 本のうち **`marisa.csv:80` だけがクォート付きフィールド**を持ち、カンマ数ベースの処理はこの 1 行で壊れる。**列追加のような一括処理の前に「引用符・改行・区切り文字を含む行が何行あるか」を数える。**
6. **自動生成資料の「次はここを見よ」という自己記述を信じない。** `code-facts.md` §10-1 は「次の連番を調べる場所」と自称しながら 000042 止まりだった（指示書が明示的に警告していた）。**連番のような一次事実は `ls` で実査する。**
7. **並行レーンで連番を配るときの不変条件は「穴を作らない」ではない。** `golang-migrate` の `Next()` はソート済み index を前方に辿るだけなので**穴は無害**で、**危険なのは「大きい番号が適用済みの後から小さい番号を差し込むこと」**（その 1 本は永久にスキップされる）。**未確証の制約を根拠に運用を縛る前に、ライブラリのソースを 10 行読む。**
