## §2 契約・設計に反する独自判断(★親の裁定が要る)

### 2-1 ★★★問い (ii) を指示書 §3-1 の既定の分岐から外して解いた(**開発者裁定済み・受理判定を請う**)

**何に反したか**: 指示書 **§3-1**(やらないこと)＝「`recipeCache` が構造を持たないと分かったとき、`DES-002` §4.11 の N+1 回避を作り直すこと。**⇒ 止まって請求する**」。チェックリスト **F-2** も「持っていなかった場合、*止まって請求している*か」を合否条件に置いていた。

**何が起きたか**: 段 1-6 の実査で、**`recipeCache` は構造を持たないことが確定した**——`internal/model/recipe.go:8` の逐語で **`{presetId: displayString}`**、つまりサーバが連結済みの 1 本の文字列であり、ステップ配列も修飾の配列も入っていない。

**★★★そこで止めていない。** 製造が 3 案を提示し、**2026-09-14 に開発者が案 C を選んだ**(逐語＝「3、案C」)。

| 案 | 中身 | 判定 |
|---|---|---|
| **A** | 揃えるのを諦めて請求する(**指示書 §3-1 の既定の分岐**) | 採らなかった |
| **B** | `recipe_cache` をステップ構造の JSON へ作り直す | **指示書が禁じている** |
| **C** | **サーバが既に出している `{表示語}` を、描画時にバッジへ替える** | **★採用** |

**なぜ案 C が成立するか**: `recipe_cache` の文字列の中には **既に `{目押し}` の形で表示語が入っている**。**⇒ 「構造化されていない」と読むと A / B の二択になるが、「粗く構造化されている」と読むと C が見える。**

**`DES-002` §4.11 に触れていないことは構造から言える**——**追加のクエリを 1 本も発行せず、`recipe_cache` の形式も 1 文字も変えていない。** 変えたのは `RecipeText`(描画部品)の中だけである。レビュー担当も独立に確認している。

**実装がどうなっているか**: `web/src/features/combo/recipeDisplay.ts` の純粋関数 `splitStepParts`(新設)＋ `web/src/features/combo/components/RecipeText.tsx` の `StepContent`。

**★★★描画は `[修飾] 技` の順である**(2026-09-14 開発者指示・§3-1 の 4)。**⇒ サーバ文字列 `技 {修飾}` とは順が逆になる。★サーバ側は 1 行も変えていない**——文字列はエクスポート・コピー・ホバー・**確定反撃サーチ**が従来どおり使うためである。**⇒ `DES-005` へ書くときは「修飾を技の前に描く」まで明記すること。順を書かないと、次の担当が文字列の順(技が先)に合わせて戻す。**

**★確定反撃サーチ(`PunishList:216` / `PunishTree:252, 606`)は本部品を通らず `combo.recipe` を素の文字列で直描きしている。⇒ あちらは従来どおり `{}` 付きの平文であり、バッジにも左寄せにもならない**(実測)**。★これは意図した現状である**——同面は「レシピの表示」ではなく候補の一行要約であり、`RecipeText` へ通すかは別の判断になる。

**★★★親へ請う裁定は 2 点である。**

1. **案 C を as-built として受理するか。** 受理するなら `DES-005`(一覧 §5.4 / 詳細 §5.6)へ「修飾は編集画面と同じバッジで描く」を明文化する必要がある
2. **`D-867`(波括弧は残す)との関係をどう書くか。** 実装は**両立させている**——描画はバッジ、`title`(ホバー)・エクスポート・コピーは波括弧付きの生文字列のままである。**⇒ 「波括弧を廃止した」ではない。ここを取り違えられると、次の担当が波括弧を消しにいく**

### 2-2 ★★指示書 §0.5 の前提が実物と食い違っていた(**指示書の側が不足**)

**何に反したか**: 指示書 **§0.5**＝「flags は 10 → 14 になる。⇒ `MAX_BUTTONIZED_OPTIONS = 10` を超える。★したがってボタン群をやめる」。§2.4-1 も「14 値をボタン群でなく別の形で選ばせる」を作業として指定していた。

**実測**: **modifier の欄は `MAX_BUTTONIZED_OPTIONS` の対象ではない。**

| 面 | 実装 | ボタン群か |
|---|---|---|
| `RecipeBuilder.tsx` | 素の `<input type="checkbox">` を `flex-wrap` で横並び | **違う** |

**どう処理したか**: 指示書 **§2.4-4** が「段 1-3 で『対象でない』と分かったら、ボタン群のままでよい。⇒ その場合も 14 値が並ぶ縦を測ること」という分岐を用意していた。**⇒ その分岐に入り、現行の形を維持して縦だけを測った**(§3-2)。

### 7-1 ★★★「〜は無い」と断言している既存記述は、それを覆した手番で `grep` して全数を拾う
