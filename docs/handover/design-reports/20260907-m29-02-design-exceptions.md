## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### §1-1 ★★`GET /api/export/csv` の応答ヘッダ 4 本（`DES-002` §4.2 の経路表に載る）

**本体は zip のバイト列であり、JSON の警告欄を混ぜられない。⇒ 切り捨ての観測をヘッダで運ぶ。**
実体＝`internal/api/comboio/handler.go`（`setExportObservationHeaders`）／ `internal/service/comboio/export.go` ／ `internal/service/comboio/types.go`（`ExportResult`）。

**応答ヘッダの実測**（開発者の実機・コンボ 86 件・2026-09-07）:

```
X-Export-Total: 86
X-Export-Included: 86
X-Export-Truncated: false
X-Export-Reimport-Blocked: false
```

| ヘッダ | 意味 |
|---|---|
| `X-Export-Total` | 対象範囲に一致するコンボの**総数**（上限を掛けない数） |
| `X-Export-Included` | 実際に zip へ**載った**件数 |
| `X-Export-Truncated` | `Total > Included` か（＝上限で切り捨てたか） |
| `X-Export-Reimport-Blocked` | **この出力を取込に掛けると上限で弾かれるか**（セットプレイ行数 > 1000 ／ いずれかの CSV が 10MiB 超） |

**あわせて `Access-Control-Expose-Headers` に上記 4 本を載せている**——`fetch` は CORS セーフリスト外のヘッダを既定で読めず、明示しないと **LAN 共有時に観測が静かに読めなくなる**ため。

**エラー契約の全行**（本サブで**変えていない**。現状の明文化）:

| 状況 | ステータス | コード |
|---|---|---|
| 成功 | **200** | —（`application/zip` のバイト列 ＋ 上記 4 ヘッダ） |
| `range` が不正／`characterId` 等のクエリが不正 | 400 | `invalid_request` |
| 対象コンボの取得に失敗（存在しない id を `range=selected` で指定 等） | 400 | `invalid_request` |

**母集団の述語**: `range=selected` は指定された id を順に引く。それ以外（`all` / `filter` / `mycombo`）は `combos.deleted_at IS NULL` の一覧を `Limit: 1000` で引く。

**★★持たせなかった分岐（読む側が誤読しないために要る）**:

| # | 内容 |
|---|---|
| 1 | **切り捨てを 4xx にしていない。** 上限を超えても **200 で zip を返し、ヘッダで知らせる**。⇒ 「上限超えは出力できない」という形は採っていない（鳴らし方は開発者選択の (c)＝件数を示して選ばせる） |
| 2 | **★切り捨てが無くてもヘッダを出す。** 4 本とも常に付く。**⇒ 「ヘッダが無い」と「切り捨てていない」を呼び出し元が区別できるようにするため**（`DES-002` §4.2 の `affectedByGameUpdate` に `omitempty` を付けなかったのと同じ考え方） |
| 3 | **`X-Export-Reimport-Blocked` は警告であって拒否ではない。** true でも出力は成功する。**⇒ 「自分が出したファイルを自分の取込が拒否する」ことを伝えるだけである** |

**⇒ `DES-002` §4.2 の `GET /api/export/csv` の行へ、上記 4 ヘッダと「切り捨ては 200＋ヘッダで伝える」を明文化してほしい。**

### §1-2 ★★`GET /api/combos` の応答へ `total` を追加（`DES-002` §4.2）

**応答の実測**（開発者の実機・2026-09-07）:

```json
{ "count": 2, "total": 86 }
```

| 欄 | 意味 | 本サブでの変更 |
|---|---|---|
| `count` | **items の件数**（＝この応答に載った数） | **不変**（従来どおり `len(items)`） |
| `total` | **絞り込みに一致する総数**（`LIMIT` / `OFFSET` を掛けない数） | **新設** |

**★★新設の理由**——一覧は `internal/repository/combo/repository.go` で**既定 100 件・上限 1000 件に黙ってクランプ**される。**`count` だけでは「ちょうど 100 件だった」と「100 件で切り捨てた」を区別できず、呼び出し元は切り捨てに気づけなかった。** ⇒ **`total > count` が「切り捨てた」の唯一の観測である。**

**母集団の述語**: `List` と**同一の WHERE を共有する**（`buildListWhere` を抽出して両者が読む）。**★条件を 2 か所に書かない**——片方だけ直すと「一覧に出る件数」と「総数」が静かにずれ、**ずれても両方とも正常に見える**。

**★★持たせなかった分岐**:

| # | 内容 |
|---|---|
| 1 | **`count` の意味を変えていない。** 既存の呼び出し元は 1 行も直していない |
| 2 | **`total` が数えられなかった場合も一覧は返す**（`total = len(items)` に倒し `WARN` を残す）。**⇒ 数えられないことを理由に一覧そのものを落とさない。ただし嘘の「切り捨てました」も出さない** |
| 3 | **ページングは実装していない。** `total` は取得できるようになったが**画面には出していない**。**⇒ 一覧は依然として 100 件で黙って切れる**（§4-3） |

**⇒ `DES-002` §4.2 の `GET /api/combos` の行へ `total` を明文化してほしい。**

|---|---|
| 1 | **開発者が選択した**（2026-09-07。逐語＝「**ERRORへ揃える。既存で空レシピデータはないので気にしなくて良い**」）。**★製造が単独で決めていない** |

### §2-2 ★「上限の値を変えない」の解釈を製造が下した（指示書 §2.1-5 / §4-1）

**何に反したか**: 指示書 §4-1 が「**上限の値そのものを変えること**」を明確に禁じている。

**実装がどうなっているか**: `web/src/features/combo-io/export-data.ts` が `GET /api/combos` へ **`limit=1000`（`MAX_EXPORT_SELECTION`）を明示して送るようにした**。着手前は `limit` を送っておらず、**リポジトリ既定の 100 件が効いていた。**

**なぜそう判断したか**: **従来効いていた 100 は「`limit` を送り忘れた結果たまたま効いていたリポジトリ既定」であり、設計上の上限ではない。** 設計上の上限は `MAX_EXPORT_SELECTION` ＝ `exportRowLimit` ＝ `csvcore.DefaultMaxRows` ＝ **1000 で一貫している**。**⇒ 意図した上限を実際に効かせただけであり、上限の変更ではない**、と解釈した。

**★上限の定義そのものは 1 文字も変えていない**（証跡は §5）。

**★★この解釈は開発者の「4 件とも直す」に含まれるが、解釈自体は製造が下した。⇒ 親の裁定を仰ぐ。**

**★あわせて**: この分岐は **`ExportDialog` が常に `range: "selected"` を送るため画面からは到達しない**（レビュー中-4 で判明）。**⇒ 実効のある修正は `exportTotalCount` を `count` から `total` へ替えたほうであり、`limit` の明示は予防である。** 完了報告 §4.2 に訂正を記録した。

### §2-3 `DES-002` §7.6 の後方互換の約束と `VAL-C15` が食い違っている（**本サブが作った状態ではない**）

**何に反したか**: `DES-002` §7.6 が「**旧 CSV（消費列なし）を後方互換で受理するため必須列としない**」と定めている。

**実態**（本サブの実測）: **列の不在は受理するが、値の不在は本登録では受理しない。** 消費ゲージが空の**本登録**行は、**`M27-02b`（`VAL-C15`）以降、確定で必ず落ちていた**（製造が実サービスへ通して確認。4 件の `VAL-C15` ERROR が出る）。

**★本サブが作った状態ではない。** 本サブは**それをプレビューでも見えるようにしただけ**である。**⇒ ただし「旧 CSV は取り込める」と読んだ担当が、実際には取り込めない行を作りうる。**

**緑が「後方互換は保たれている」と誤読されるのを防ぐため、実態を主張するテストを置いた**——`TestBackwardCompatOldCSV_PublishedRowIsRejectedByC15`（対照として仮登録行が通ることも主張）。

**⇒ `DES-002` §7.6 へ「列の不在と値の不在は別である」を明文化するか、`VAL-C15` の適用範囲を見直すか、親の判断を仰ぐ。**
