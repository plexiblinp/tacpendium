## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1. ★★削除済みコンボの読み取り専用取得の経路と応答（`CHANGE-128` が待っている逐語）

**`DES-002` §4.2 へ、次をそのまま書けます。**

```
GET /api/combos/{id}/deleted
```

| 項目 | 内容 |
|---|---|
| 用途 | **ゴミ箱の行から開く読み取り専用のコンボ詳細**（`DES-005` §5.15 の「行クリック → 詳細表示」） |
| 母集団 | **`deleted_at` の述語を持たない。削除済み行も、削除済みでない行も返す** |
| 応答型 | **既存の `ComboResponse` を流用**（**新しい DTO を作っていない**） |
| ステータス | `200` ／ `400 invalid_id` ／ `404 not_found`（`{"error":{"code":"not_found","message":"コンボが見つかりません"}}`） |

**★応答のフィールドは 1 つも増えていない。** 差は**値域**と**載らないもの**である。

| フィールド | `GET /api/combos/{id}` | **`GET /api/combos/{id}/deleted`** |
|---|---|---|
| `deletedAt` | **常に nil**（生存行しか返さないため） | **非 nil になりうる** |
| `defaultRecipe` | `recipe_cache` から抽出 | **★`combo_steps` から組み立てる**（削除済み行の `recipe_cache` は NULL）。**解決失敗時は空文字** |
| `steps` / `tags` / `okiOptions` / `starterMoveCode` | ロードする | **同じくロードする**（`attachComboChildren` を共用） |
| `setups` | **載る** | **★載らない**（§4.2-5 の帰結。空配列） |
| `validations` / `warnings` | 経路により載る | **載らない** |

**⇒ `DES-002` §4.2 へ「削除済みコンボの読み取り専用取得（新設）」として明文化してほしい。**
**★あわせて「`GET /api/combos/{id}` にフラグを足していない」ことも書いてほしい**——`M23-06` の `ResolveSetupRecipe` と同型であり、**次の担当が「1 本にまとめられる」と読んで統合するのを防ぐ**。

根拠: `internal/api/combo/routes.go`（`g.GET("/combos/:id/deleted", h.GetDeleted)`） ／ `internal/service/combo/service.go` の `GetDeleted` ／ `internal/repository/combo/repository.go` の `FindByIDAllowDeletedWithChildren`。

### 1-2. ★読み取り専用詳細の画面ルートは `/trash/combos/:id`

**指示書 §4.2-3 は「読み取り専用であることが URL から分かる形」とだけ定めており、具体形は製造が決めた。**

- **画面**: `/trash/combos/:id`（`web/src/router.tsx`）
- **サーバ**: `GET /api/combos/{id}/deleted`
- **★2 つを別の形にした理由**——画面 URL は利用者が見るため「ゴミ箱の中のもの」と読める形を優先し、API はコンボのサブリソース群（`/restore`・`/permanent`・`/recipe`）と揃えた。

**⇒ `DES-005` §5.15 のアクション「行クリック → 詳細表示（読み取り専用のコンボ詳細）」へ、遷移先が `/trash/combos/:id` であることを明記してほしい。**

**★あわせて記録**——**ゴミ箱の遷移リンクは 2 件（行全体の `onClick` と 2 列目の `<Link>`）で、両方を向け替えた。** **★ただし波及は 2 件で終わらなかった**（§7-2）。

### 1-3. ★セットプレイをゴミ箱へ入れる導線の置き場

**指示書 §4.1-1 は「置き場は設計卓が指定しない。画面の現物を見ないと決められない」としていた。**

- **置き場**: **コンボ詳細（`/combos/:id`）の、各セットプレイのカード内のボタン列の右端**（`web/src/features/setup/components/SetupAccordionItem.tsx`）。
- **文言**: 「**ゴミ箱へ移動**」（`setup.delete.action`）。塗りつぶしの赤。`data-testid="setup-soft-delete"`。
- **選定の理由**: `VAL-S05` によりセットプレイは親コンボ経由でしか画面に出ず、`DES-005` §5.9 も「紐付けはコンボ登録・編集画面またはコンボ詳細画面から」と定めている。**当のセットプレイの隣が最も近い。**
- **採らなかった案**: セットプレイ編集画面（`/setups/:id`）＝`DES-005` §5.9 が「同画面からの紐付け操作は誤操作リスクが高いため除外」としており同じ理由が削除にも当たる ／ ゴミ箱画面＝「入った後」の画面であり入口を置けない ／ コンボ一覧の子行＝読み取り専用の表示であり過密になる。

**★「コンボの削除と混ざらないこと」（§4.1-1 の守り）をどう守ったか**——(1) 面が離れている（コンボの削除はページ最上部の操作バー） (2) 文言が違う（`common.delete`「削除」対「ゴミ箱へ移動」） (3) 確認ダイアログが対象を名指しする (4) **`onDelete` prop を opt-in にした**（渡さない面では削除ボタンが出ない） (5) **テストが fetch を実観測し、`DELETE /api/combos/*` を 1 本も叩かないことを主張する**。

**⇒ `DES-005` §5.6 項目 10（紐づくセットプレイ一覧）へ「ゴミ箱へ移動」を追記してほしい。** 現行の記述は「行クリックでセットプレイ編集へ遷移・紐付け解除は維持」で止まっている。

### 1-4. ★一括操作バーの置き場は画面下部の sticky

**指示書 §4.4-2 の暫定案どおり。** `TrashBulkActions` 自身が `sticky bottom-0 z-20 ... shadow-lg` を持ち、`TrashPage` の `<main>` の**末尾**に置く。

- **理由**: バーはコンボ表とセットプレイ表の**両方**を受け持つのに、コンボ表の上に固定されていた。**`M23-06` により結果が残る間はバーが表示され続けるようになった**（`CHANGE-127`）ため、上に居座る時間も長くなっていた。
- **★sticky の指定はコンポーネント自身に持たせた。** ページ側でラッパ `<div>` を被せると、**バーが `null` を返している間も枠線だけが残る**（§7-3）。
- **`M23-06` が確定した規律は維持**——操作ボタンは選択が残っている間だけ／結果の表示は選択が空でも残る。**破壊確認 3 で退行防止を確認済み。**

**⇒ `DES-005` §5.15 へバーの置き場を明記してほしい。**

### 1-5. ★削除済みでない行を引いたときの挙動＝「返す」。ただし画面は `deletedAt` で見分ける

**`CHANGE-128` §7-2 の暫定案どおり「返す」を採り、テストで固定した**（`TestService_GetDeleted_AlsoReturnsLiveCombo`）。

**★ただしレビューで、画面側が `deletedAt` を見ないと事実と違う文面が出ることが判明した**（レビュー中-3）。

- **到達経路**: 読み取り専用詳細から「復元」を押すと `/trash` へ遷移するが、**ブラウザバックで同じ URL へ戻れる。そのときコンボはもう生きている。**
- **旧挙動**: 「ゴミ箱にあるコンボです。編集はできません」＋ 復元・完全削除ボタンが出た（**データは壊れない**——復元も完全削除もサーバ側で弾かれる。**壊れるのは文面**）。
- **是正後**: `deletedAt == null` のときは**ゴミ箱の文面と 2 ボタンを出さず、通常詳細への導線へ落とす**（`trash.detail.notInTrashNotice` ＋ `openNormalDetail`）。

**⇒ `DES-002` §4.2 へ「本経路は生存行も返す」と書く場合は、**「**画面は `deletedAt` で見分けること**」**を必ず併記してほしい。** **書かないと、次の担当が『返るのだから出してよい』と読む。**

## §7 教訓（`retrospective-log` 行き・**親は読まなくてよい**）

> **宛先は `retrospective-log` へのバッチ反映であり、実施者は設計担当**（反映担当は 2026-08-11 に廃止）。

### 7-1. ★「N 件」と書いたコメントを機械的に +1 すると、元から在ったずれが温存される

`internal/api/combo/routes.go` の「登録される N ルート」を **`10 → 11`** と増やしたが、**実数は 12 だった**（レビュー高-1 で発覚）。**元から 10 と 11 でずれており、+1 がそれを温存した。**

**★テスト・lint・型検査のいずれでも検出できない**——動作は正しく、数だけが嘘になる。**目録は、数が違えば目録として機能しない。**

**⇒ 機構化案: 「N か所」「N 件」を書き換えるときは、増やす前に数え直す。** **★本サブの指示書は §3.3-8 と §3.3-10 で 2 回も「数を鵜呑みにせず実測せよ」と求めており、実際に見立て 7 件 → 実測 11 件、見立て 2 件 → 実測 12 件（E2E ロケータ）を検出できていた。にもかかわらず、自分が書いた行では守れていなかった。** **⇒ 「他人の数を疑う」規律は「自分が書く数」へは自動では及ばない。**

### 7-2. ★画面 URL を変えると、`href` に依存するテストが広範囲に壊れる（実測 12 か所・6 spec）

指示書 §3.3-8 が数えさせたのは**画面側の遷移リンク 2 件**だったが、それを直すと **E2E の行ロケータ `tr:has(a[href="/combos/${id}"])` が `M23-01` / `02` / `03` / `04` / `05` / `06` の 6 spec・12 か所で壊れた。**

**⇒ 機構化案: 「URL を変える」変更では、画面側の参照だけでなく `href` を含む文字列の全数を先に `grep` する。** **★実装の参照数と、テストの参照数は別に数える。**

### 7-3. ★`null` を返しうるコンポーネントの外側で sticky / fixed をラップすると、空の枠だけが残る

一括操作バーを画面下部へ移す際、当初ページ側で `<div className="sticky ...">` を被せたが、`TrashBulkActions` は選択も結果も無いとき `null` を返すため**枠線だけが画面下部に貼り付いた**。

**⇒ 機構化案: レイアウトの装飾は、条件付きで消える当のコンポーネント自身に持たせる。** **★`M23-06` 横断課題 4（「テストの親が実アプリの親と違うと 1 フレームも表示されないまま緑になる」）と同じ面の落とし穴であり、どちらも「描画されない条件」を先に確かめれば避けられる。**

### 7-4. ★回帰テストは「描画されたこと」を先に主張しないと、何も検査しないまま緑になる

`TrashPage.i18n.test.tsx` は当初、**選択が空の状態で走査していた**ため一括操作バーが `null` を返し、**バーの文言 6 件（22 リテラル中）を 1 文字も走査していなかった**（レビュー中-4）。

**⇒ 機構化案: 「〜が残っていない」を主張する走査型テストは、走査の前に「対象が実際に描画されたこと」を 1 行アサートする。** **★`M23-06` 横断課題 4 と同型が本サブで再発した。2 サブ連続である。**

### 7-5. ★設計卓の「使うのは A だけ」というコメントを、新しい呼び出し元を足したあと狭めたまま残しやすい

`FindByIDAllowDeleted` の godoc は「完全削除の前チェックが使う」と書かれていた。**本サブが 2 つ目の呼び出し元（`FindByIDAllowDeletedWithChildren`）を足したのに、godoc を狭めたまま残した**（レビュー低-3）。

**⇒ 機構化案: 既存関数に新しい呼び出し元を足したら、その関数の godoc の「誰が使うか」を必ず読み直す。** **★呼び出し元の列挙は、増えたときにしか壊れない形の記述である。**
