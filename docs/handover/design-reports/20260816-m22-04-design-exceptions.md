## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1 保存エラーの分類を 1 本の関数へ集約し、**HTTP ステータスを一切見ない**契約にした

指示書 §4.2-1 は「エラーコードで分岐する」までしか言っておらず、**判定をどこに置くかは書いていない**。§4.2-4（同じ判定を 2 回書かない）と `E-76` から、分類関数 1 本へ集約した。

- 実装: `web/src/features/combo/saveError.ts` — `classifySaveError(err)` が `versionConflict` / `notFound` / `duplicateSetup` / `validation` / `other` の 5 種を返す。**`err.status` を 1 度も参照しない。** 参照は `ComboEditor.tsx` ／ `SetupEditorPage.tsx` ／ `features/setup/errors.ts` の 3 か所すべて
- 定数: `web/src/constants/api-error.ts`（`CLAUDE.md` §4 の列挙同期。バックエンド `internal/model/api_error.go` の `ErrorCodeVersionConflict` と対）

- ⇒ **`DES-006` §11.2 へ「409 の見分けはエラーコードで行い、ステータスでは行わない」を明文化してほしい。** **★書かないと、次に 409 を足す担当が `status === 409` で分岐する。本サブが直したのはまさにその状態である**（§1-2）。

### 1-2 `duplicate_setup` を版不一致から分離した（**★着手前は取り違えが現に起きていた**）

**着手前の `web/src/features/setup/errors.ts:26` は `err.status === 409` だけで判定しており、同一レシピ重複（`duplicate_setup`）が「他のタブで更新されています。ページを再読み込みしてやり直してください。」という版不一致の文言で表示されていた。**

## §7 教訓（retrospective 行き）

> **★親チャット（設計卓）は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、**実施者は設計担当**（反映担当は 2026-08-11 に廃止され責務が統合された）。

### 7-1 ★★「導線が出ていること」を固定しても、「そこから先へ進めること」は固定されない

**本サブは最重要ゲート 1（入力を失わせない）を破壊確認 A で固定し、導線の有無もテストと E2E で固定した。それでも利用者は行き止まりに入った**（§2-1 / §4-2）。

- **★テストは「モーダルが出る」「ボタンが 2 つある」「404 では読み込み直す導線を出さない」までを主張していた。** **主張はすべて正しく、すべて緑で、レビューも通った。** **見ていなかったのは「利用者がそこから目的（保存）を達成できるか」である。**
- **一般形**——**導線のテストは、存在ではなく到達可能性を主張しないと、行き止まりを緑で固定する。** 「エラー時に X が表示される」で止めず、「X から Y へ進める」まで書く。
- **★とくに危ないのは、本サブのように「出せない導線がある」と正しく判断したときである。** 「見る先が無い」「読み込み直す先が無い」は正しかった。**正しい消去法の結果、選択肢が 0 になったことに気づく仕組みが無かった。**
- **機構化の候補**: レビューチェックリストへ「**エラー時の画面から、利用者が当初の目的を達成できる経路が最低 1 本あるか**」を足す。**★「入力が消えないこと」と「進めること」は別の項目として並べる**（本サブのチェックリスト §1 は前者だけを最重要ゲートに置いていた）。

### 7-2 ★破壊確認は「主張が鈍い」ことも暴くが、暴かれた側が気づくとは限らない

破壊確認 A の 1 回目で「レシピ(ステップ)も消えない」が緑のまま空振りした。**件数 `=== 1` の主張は、初期値へ戻す実装ではリセットを検出できない。**

- **★何かが代わりに守っていたのではない。主張そのものが無力だった**（`SUPP-001` §5.5 (10′) が想定する「別の機構が守っていた」型ではない）。**⇒ (10′) には第 3 の分類が要る**——**「代替の守りがある」「本当に守れていない」に加えて「主張が失敗モードに対して無力である」。**
- **★「リセット」と「クリア」は別の失敗モードであり、1 つの主張で両方は見られない。** 分けて書く。
- あわせて分かったこと——**フォームのテストで入力を作るとき、キー項目を触ると経路が変わる**（コンボ編集でステップを足すと `hasKeyChanges` が真になり PATCH ではなく PUT へ分岐する）。1 回目はこれに気づかず 15 本を巻き込んで落とした。

### 7-3 ★前サブが意図して置いたテストの主張は、後サブで無効化されうる

`errors.test.ts` の「409 の分類はエラーコード文字列に依存しない」は `M22-03` が**意図して**置いた主張だった（見せ方は `M22-04` の担当という線引きを守るため）。**`M22-04` でその線引き自体が動いた。**

- **⇒ 期待値を緩めるのではなく主張を作り替えた**（`Header.test.tsx` / `D-308` と同じ扱い）。**旧テストが持っていた対照実験は形を変えて残した。**
- **★判断材料になったのは、テストのコメントに書かれていた「なぜこの主張を置いたか」である。** 理由が無ければ「緩めてよいのか」が判断できず、開発者へ聞くしかなかった。**⇒ 意図して置いた主張には理由を書く。**
- **★レビューはこの型をもう 1 件見つけた**——テスト名が「500 + version_conflict は版不一致にならない」なのに本体が `internal_error` を渡しており、**しかも名のとおりに書くと落ちる**（実装はステータスを見ない）。**旧主張が名前だけ残った形**であり、**緑・lint 緑・型検査緑で、人が読む以外に見つける経路が無い。**

### 7-4 ★「N 経路」と書かれた数字は、経路と画面のどちらを数えたものかを確かめる

指示書 §3.3-4 は「3 経路以外に版を送る画面が無いこと」と書き、**ルートの本数と画面の数を同一視していた**。実体はルート 3 本・**画面 4 つ**だった。

- **★`M22-03` §4-2（`instruction-total-counts-stale-at-start`）の隣にある型である。** あちらは「先行サブの as-built で全数が失効する」、本件は「**数える単位が取り違えられている**」。**どちらも指示書の数字をそのまま信じると外れる。**
- 本サブでは Plan Mode の実査で検出し、**開発者へ差し戻して裁定（`D-416`）を取ってから進めた。**

### 7-5 ★機械検査は「範囲」を書いておかないと、実際より広く読まれる

完了報告に「禁則語は**全文言で 0 件**（`ConflictDialog.test.tsx` が機械的に固定）」と書いたが、**実際に走査していたのは `versionConflict` × `combo` の 1 組だけ**だった（2 段目のダイアログは別 test-id のため `textContent` に含まれない）。
