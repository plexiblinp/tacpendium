## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1 改名 UPDATE には **`NOT EXISTS` ガード**が要る（指示書 §2.6 の適用範囲の誤り）

指示書 §2.6 は「golden 再生成後、`000063` の UPDATE は新規 DB では 1 行も更新しない。**マイグレは成功する。エラーにならない**」と述べる。**これはフレーム是正には当てはまるが、改名には当てはまらない。**

新規 DB は golden 由来で**既に新 code を持つ**ため、B-2 の `WHERE code = 'sonic_cross_2_meter_od'` は**「改名後の B-3」に当たり**、改名先の `perfect_timing_sonic_cross_od` も既に存在するので **UNIQUE `(character_id, code)` 違反でマイグレ全体が落ちる**。

- 根拠: 実装途中で `TestRun_FirstAndIdempotent`（`internal/infra/migration/migrate_test.go:37`）が `UNIQUE constraint failed: moves.character_id, moves.code (2067) in line 0: -- 000063_...` で実際に落ちた。
- 実装: `migrations/000063_correct_moves_data_m1904c.up.sql` の改名 3 文に `AND NOT EXISTS (SELECT 1 FROM moves m2 WHERE m2.character_id = moves.character_id AND m2.code = '<改名先>')` を付与（down も同形）。意味は**「改名先が既に埋まっている＝その改名は済んでいる」**。

⇒ **`SUPP-001 §5.5`（またはデータ是正の指示書テンプレ）へ「§2.6 の『0 行になる・エラーにならない』はフレーム是正限定であり、改名は 0 行にならず衝突する」を明文化してほしい。**

### 1-2 是正列は **「golden に載る／載らない」で UPDATE を当てる位置が変わる**（★本サブ最大の収穫）

`startup_basis` は **seedgen が SQL へ出力しない列**である（`internal/seedgen/generate_test.go:92` が「生成 up SQL に startup_basis の値が出力されている」で fail させて固定）。したがって **golden を再生成しても新規 DB の `startup_basis` は DDL 既定値 `'unknown'` のまま**残る。

フレームと同じ流儀で「改名前に旧 code で当てる」と、**新規 DB では 0 行になり `'unknown'` で取り残される**。**これはエラーにならない**——指示書 §2.6 が警戒していた失敗モードそのものである。実装中に一度踏み、`startup_basis = "unknown", want "through"` でテストが落ちて発覚した。

| 列の種別 | 例 | UPDATE を当てる位置 |
|---|---|---|
| **golden に載る**（新規 DB は是正済み） | `code` / `startup` / `active` / `recovery` / `total` | 改名**前**・旧 code。新規 DB では 0 行 |
| **golden に載らない**（新規 DB も未是正） | **`startup_basis`** / `is_derived` / `is_projectile` / `chain_cancel_total` / `fastest_unreachable` | 改名**後**・新 code。**新規 DB でも 1 行に当たる** |

⇒ **`SUPP-001 §5.5` へ上表を明文化してほしい。** これは `csv-edit-vs-golden-divergence` の核心を言語化したものであり、次の同型サブの指示書にそのまま入る形になっている。

### 1-3 ★`000039` の**案 1** は「その連番より前で止まった DB」を取り残す（指示書 §2.5 の案比較が片手落ち）

指示書 §2.5 は案 1（`000039` の `code` 列挙を書き換える）を採り、案 2（据え置き＋新マイグレで補完）を「v39 時点で新規 DB（102）と既存 DB（104）が乖離し、**飛び道具なのに `is_projectile=0` の行が 2 行ある DB を中間状態として作る**」として却下した。

## §7 教訓（retrospective 行き）

> **★親チャットは本節を読まなくてよい。宛先は反映係（Claude Code）。** 外出先では **§1〜§4 だけコピーすれば足りる。**

1. **★指示書が「エラーにならない」と書いているとき、その適用範囲を疑う。** §2.6 の「新規 DB では 0 行・エラーにならない」は**フレーム是正には正しく、改名には誤り**だった（改名は UNIQUE 衝突で落ちる）。**同じ節が「安全である」と「静かに壊れる」の両方を主張している場合、どの操作にどちらが当たるかを操作の種類ごとに確かめる。** 一般化——**「Xでは常にYになる」型の記述は、操作の種類（INSERT / UPDATE / 改名 / 列追加）ごとに成否が割れる。**

2. **★「正本を直せば全経路に届く」は列によって成り立たない。** CSV を直し golden を再生成すれば新規 DB は是正済みになる——**ただし seedgen が SQL へ出力しない列は除く**。`startup_basis` はその 1 つで、golden を再生成しても新規 DB は既定値のまま残る。**機構化するなら「是正対象の列が生成物に載るかどうか」を着手前確認の項目にする。** 載らない列は改名後・新 code で当てないと静かに取り残される。

3. **★件数ガードは「どの版で測った値か」を必ず併記する。** `is_projectile` の **104 は v39 時点**、**HEAD は 135**。指示書に頻出する 104 をそのまま HEAD 用のガードに持ち込んで一度落とした。**同じ列に複数の版のガードが並ぶとき、定数名とコメントに版を書く**（本サブでは `m1904cProjectileTotal = 135` に「v39 の 104 とは別物」と明記した）。

4. **★手書きの backfill マイグレを書き換えると、その連番より前で止まった DB が置き去りになる。** 案 1（書き換え）と案 2（据え置き＋補完）はどちらも「あるコホートに `is_projectile=0` を残す」——**指示書は案 2 の穴だけを見て案 1 を選んでいた**。**一般化＝「既存マイグレを書き換える」提案が出たら、`v < その連番` で止まった DB を必ず 1 つ想定して検算する。** 対処は安く（後段の no-op UPDATE 1 文）、放置の代償は判定誤りである。

5. **★レビュアーに「中間版 DB を再構築させる」と、実装者が見えない穴が出る。** 本サブの最大の欠陥（教訓 4）は、レビューが**旧マイグレ群から DB を実際に組み直して**見つけた。実装者は「新規 DB」と「手元の最新 DB」の 2 経路しか想定していなかった。**一般化＝マイグレを触るサブのレビュー観点に「v が途中で止まった DB」を明示的に入れる。** 経路の数は「新規／最新」の 2 つではなく「新規／最新／任意の中間版」の 3 つである。

6. **自由改訂資料のテーブル編集は、編集後にセル数を機械検証する。** `followup-backlog.md` の行を差し替えた際、旧行の後半が新行の末尾に残ってテーブルが崩れた。**`des-version-log-body-audit` が「本文はあるが描画されない」型として警戒している事故を実際に踏んだ。** 長大な 1 行のテーブル行を編集するときは、**区切り行とのセル数一致を必ず確認する**（バッククォート内のパイプも GFM では分割される）。
