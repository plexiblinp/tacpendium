## 1. 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1 ★★`GET /api/moves`（`DES-002` §4.2 の経路表）の応答が 1 フィールド増えた

**★実 DTO（実行結果。使い捨て DB へ本番同様のマイグレを全適用し、ハンドラを叩いて得た JSON をそのまま貼る）**

```json
{
  "active": 4,
  "category": "target_combo",
  "characterId": 1,
  "code": "high_double_strike",
  "id": 1067,
  "isAerial": false,
  "isDerived": true,
  "nameJa": "上段二連撃",
  "onBlock": -8,
  "recovery": 20,
  "setupOnly": false,
  "startup": 9,
  "total": 32,
  "warnings": []

```

**増えたのは `isDerived` の 1 キーだけである。他のキーは 1 つも動いていない。**

| 事項 | as-built |
|---|---|
| **型・既定** | `bool`（`moves.is_derived` は `INTEGER NOT NULL DEFAULT 0`）。**`omitempty` を付けていない ⇒ false でもキーが必ず出る**（`isAerial` / `setupOnly` と同じ扱い） |
| **母集団の述語** | 変更なし。`WHERE m.character_id = ? ORDER BY m.id`。**`is_derived` で 1 行も絞っていない** |
| **エラー契約** | 変更なし。`character_id` 未指定 → **400** ／ 不正値 → **400** ／ 存在しない `character_id` → **200 ＋ 空 `items`**（404 ではない）。**本サブは分岐を 1 つも足していない** |
| **★持たせなかった分岐** | **`GET /api/moves/:id`（`MoveDetailResponse`）へは `isDerived` を出していない。** 「書き忘れ」ではなく、**編集グリッドは本列を読まないため意図的に出していない**（§3-2）。⇒ **詳細 API の契約は 1 バイトも動いていない** |
| **後方互換** | 既存 consumer は無視できる純増。TS 側は `Move.isDerived: boolean` を**必須**にした（BE が常に返すため） |

**⇒ 反映依頼（3 件）**

1. **`DES-002` §11.3 / §4.2** の `GET /api/moves` 応答定義へ `isDerived` を追加してほしい。
2. **`DES-003` §3.3 の `is_derived` 行**に在る「**model の `Move` 構造体には持たせていない＝`GET /api/moves` のレスポンスに出ない**（UI で使う場合は model／DTO／SELECT 列の同期追加が要る）」は**失効した**。同じ行の **errata③ は失効していない**（`is_derived=true` を「単独入力が不可能」と読み替えてはならない、は維持）。⇒ 前者だけを as-built へ書き換えてほしい。
3. **`DES-005` 第6節**（仮想コントローラ）へ、必殺技ファミリー行の並び順規則（§1-2）を明文化してほしい。

### 1-2 必殺技ファミリー行の並び順に、初めて「規則」ができた

**着手時点の並びは規則ではなく副産物であった** —— `deriveSpecialFamilies` が基底ファミリーの初出順を保持し、その配列が `moves.id` 昇順（＝seed CSV の行順）だったにすぎない（`M30-02` の実測）。**本サブで初めて明示の規則になった。**

| # | 確定した規則 |
|---|---|
| 1 | **`isDerived` のファミリーを、そのキャラの必殺技ファミリー行の末尾へ回す** |
| 2 | **群の中の相対順は現行のまま**（＝`moves.id` 昇順）。非 derived どうしも derived どうしも動かさない |
| 3 | **1 件も落とさない。** 総数は前後で同じ（実測 372） |
| 4 | **UI の見た目は変えていない。** 区切り線・淡色化などの視覚的な区別は入れていない（指示書に無いため） |

**根拠**: `web/src/features/combo/inputResolution.ts` の `deriveSpecialFamilies` 段 3（`sort` を使わず 2 回の `filter` を連結）。テストは `web/src/features/combo/moveSurfacing.roster.test.ts`（31 キャラ全数）と `web/e2e/m30-04-derived-to-row-end.spec.ts`（実 DB 越しに jamie / blanka の 21 件を順序つきで全数固定）。

**⇒ `DES-005` 第6節への明文化を請う**（§1-1 の反映依頼 3 と同じ）。

### 1-3 ★★「ファミリーが derived である」の定義を製造が確定させた

**指示書 §2.2-1 は「`is_derived = true` のファミリー」と書くだけである。** `is_derived` は move の列である以上、**ファミリー単位でどう畳むかは定義されていなかった。**

**確定させた定義**——そのファミリーに属する move が**すべて**`is_derived=true` のときだけ derived とする（**AND**）。

**★これは机上の詰めではなく、実データに 5 件の反例が在る。**

| キャラ / ファミリー | 形 |
|---|---|
| `akuma/gou_hadoken` ／ `cammy/spiral_arrow` ／ `cammy/cannon_spike` ／ `cammy/hooligan_combination` ／ `luke/flash_knuckle` | **素の弱中強・OD は `is_derived=false`、ホールド変種だけ `true`。** 変種は `M30-02`（P4M-018 案 B）で基底へ畳まれるため、OR を採るとこの 5 ファミリーが**丸ごと末尾へ沈む** |

**⇒ OR を採ると「素が押せるのに末尾に居る」形が 5 件できる。** `M30-02` が「素は押せるが OD が押せない」を 7 組作ったのと同じ型の事故であり、AND を採った。

**⇒ `DES-005` 第6節へ「ファミリー単位の判定は AND である」を併記してほしい。**（規則 1 だけを書くと、次に読む人が move 単位で読み替えうる。）

**★この規則の床は 2 本ある**（どちらも本サブで足した）:

| 床 | 何を守るか |
|---|---|
| `web/src/features/combo/inputResolution.test.ts:477`（**合成データ**） | **段 1（raw ファミリー内）の AND。** ★**実データにこの形が 1 件も無いため、合成でしか張れない**（§7-2） |
| `web/src/features/combo/moveSurfacing.roster.test.ts` の分類オラクル（**実データ 31 キャラ・全 372 ファミリー**） | **段 2（変種を基底へ畳むとき）の AND。** `fam.byVariant` の id から元 move を引き直して `allD` を独立に計算し、実装の出力と突き合わせる。混在 5 件は名指しで全数固定 |

### 7-1 「失効した記述」の走査は、コードだけ見ても半分しか終わらない

**API 契約を広げると、失効するのはコードのコメントだけではない。** 本サブはコード側 5 か所を全数直したが、**`docs/handover/` を `grep` しておらず 1 件取りこぼした**（`M19-DESIGN-01` R7）。レビューが検出した。

**⇒ 機構化案**: **列や API を「露出させる」変更のときは、失効走査の対象を最初から 3 面にする** ——(1) `internal/` ＋ `web/src/`（コメント・godoc）／ (2) `docs/design/`（設計書本体）／ (3) `docs/handover/`（要件・引き継ぎ）。**`docs/change-notes/` は発行済み通知書＝歴史記録なので対象外。** 検索語は「非露出」「出ない」「持たせていない」「非搭載」等の**否定形**である。

### 7-2 「実データ全数の床を張った」は「その関数の全分岐に床を張った」を意味しない

本サブの畳み込みは 2 段（raw ファミリー内の AND → 変種を基底へ畳むときの AND）だが、**seed 実データには「同一 raw ファミリーの中で `is_derived` が割れる」組が 1 件も無い。⇒ 段 1 の AND を OR に取り違えても、31 キャラ全数を走る実データテストは全部緑のままだった**（取り込み中の変異注入で実測）。

**⇒ 機構化案**: **実データ由来の床を張ったら、その床に変異注入を 1 回入れて「効く範囲」を測る。** 効かない分岐が出たら**合成データで 1 本足す**。**「全数を走らせている」ことは、その関数の全分岐が実データに現れることを意味しない。**

**★★★【自己適用済み・本サブで実施】上の機構化案は提案ではない。本サブで実際に足してある。**

### 7-3 全キャラへ 1 行足すマイグレは、行数を固定した spec を全部壊す

`M31-04` の `000109` は `FROM characters c` で 31 行を投入し、**行数を固定していた E2E 3 本を赤にした**（§4-3）。**同サブは E2E spec を 1 本も触らず、全数 `make e2e` も回していない。⇒ 気づける経路が無かった。**

**⇒ 機構化案**: **`moves` へ全キャラ行を足すマイグレを書いたら、`grep -rn "items.length).toBe(" web/e2e` と「`moves[moves.length - 1]`」の 2 つを必ず走らせる。** 前者は行数固定、後者は「最後の技を選ぶ」形であり、**どちらも +1 で静かに壊れる。** あわせて、**全キャラ行を足すサブは的撃ちではなく `make e2e` 全数を 1 回回すこと。**

### 7-4 陽性対照は「実装と独立な軸」から作らないと対照にならない

本サブは着手時点の並びを **move id の最小値**から復元した。**実装の `outOrder` 構築を読み直して再現すると、実装が間違っていても同じように間違えるため対照にならない。** レビューもこの点を評価している。

**⇒ 一般化**: **「入れる前はこうだった」を測るときは、実装が使っていない軸を 1 本探す。** 見つからないなら、その対照は主張を支えていない。
