### 1-1 ★★`PATCH /api/combos/:id` の要求 DTO が 2 欄増えた(`DES-002` §4.2 / `DES-005` §5.7)

**★経緯は §2-1。ここでは as-built だけを書く。**

**要求 DTO の増分**(`internal/api/combo/dto.go:141` `UpdateMetadataRequest`):

```go
StartPositionMass comborepo.Optional[int] `json:"startPositionMass"`
CarryDistanceMass comborepo.Optional[int] `json:"carryDistanceMass"`
```

**★`Optional[T]` は presence-detection のトライステートである**(`memo` / `situation` と同じ)。

| 要求本文 | 意味 |

| キーが**無い** | 変更しない |
| `"startPositionMass": 80` | 80 を保存 |
| `"startPositionMass": null` | **NULL クリア** |

**応答 DTO は変わっていない。** `ComboResponse`(`dto.go:260/262`)は着手前から両欄を持っており(`*int` ／ `omitempty`)、本サブは 1 行も触っていない。

**エラー契約の全行**(`PATCH /api/combos/:id`。**★太字が本サブで増えた行**):

| 状況 | ステータス | コード |
|---|---|---|
| id が不正 | 400 | `invalid_id` |
| 本文が壊れている | 400 | `invalid_request` |

**★★母集団の述語**: 本経路が触るのは**識別キーが変わらない編集**だけである。⇒ `position` / `opponentStance` / `hitType` / `opponentSize` / `starterMoveId` / レシピは**この経路に載らない**(載るのは `PUT`)。**マス数 2 欄はキーではないため本経路に載る。**

3. **`startPositionMass` と `position` の整合検証も持たせていない。** ⇒ 本経路では両者が食い違いうるが、**フロントの振り分けにより実際には起きない。**

**⇒ `DES-002` §4.2 の `PATCH /api/combos/:id` 行へ 2 欄と `VAL-RANGE` を、`DES-005` §5.7 の「(b) メタデータ編集」の対象欄へマス数 2 欄を明文化してほしい。**
