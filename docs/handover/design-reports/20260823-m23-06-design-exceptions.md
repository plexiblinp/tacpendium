### 1-3. ★警告文面の終端句点・区切りを i18n キーへ切り出した

`CHANGE-127` §2.5 は「`details` のキーで分岐する」までを定めているが、**文面の連結規則は書いていない。**

指示書 §4.6-2（「2 種類同時発火時に末尾が句点で終わらない」）の是正として、**区切りと終端を翻訳キーにした**（`trash.warning.warningSeparator` = `" / "` / `trash.warning.warningTerminator` = `"。"` / en は `"."`）。

### 1-4. ★一括操作の結果表示は、選択が空になっても残る

**`CHANGE-127` §2.5 は「どの件に警告が付いたかを出す」までを定めているが、その表示の寿命を定めていない。**

**⇒ `DES-005` §5.15 へ「一括操作の結果は次の操作まで残り、明示的に閉じられる」を明文化してほしい。**

## §2 契約・設計に反する独自判断（★裁定が要る）

### 2-1. ★★`resolve-setup-recipe` の「本番呼び出し元をここで作る」は成立しなかった

**何に反したか**: 指示書 §4.3-2「**`resolve-setup-recipe` に相当する処理が既に存在し、本番の呼び出し元が 0 件である。⇒ 本サブがその呼び出し元になる**」／ `CHANGE-127` §4-5「**`resolve-setup-recipe` は撤去せず、使う側で決着させる**」。

```sql
SELECT recipe_cache FROM setups WHERE id = ? AND deleted_at IS NULL
```

であり（`internal/repository/setup/repository.go:581`）、削除済み行では `ErrNotFound` を返す。**同関数の godoc は「`M23-03` §4.2: combos 側とまったく同型であり、2 つで 1 組として塞いである」と明記しており、意図的な塞ぎである。**

**実装がどうなっているか**: **塞ぎには触らず**、レシピ解決の**計算本体**（`setupStepsToComboSteps` + `resolveRecipe`）を呼ぶ読み取り専用の経路 `ResolveDeletedSetupRecipes` を新設した（`internal/service/notation/setup_resolver.go:67-107`）。**`ResolveSetupRecipe` は撤去していない。**

**★残る事実**: **`ResolveSetupRecipe` 自体は、依然として本番の直接呼び出し元を持たない。** **⇒ `D-513`（「撤去するか」）は、厳密には決着していない。**

**★開発者裁定あり**（2026-08-23）——「**塞ぎに触らず、書き戻しもしない読み取り専用の経路を足す**」で確定済み。**ただし `CHANGE-127` §4-5 の逐語（「使う側で決着させる」）は as-built と食い違うため、反映時に補正が要る。**

**⇒ 親への依頼**: **(a)** `CHANGE-127` §4-5 を「**撤去しない。計算本体を本番の経路から使う。`ResolveSetupRecipe` 自体は引き続き直接の呼び出し元を持たない**」へ補正するか、**(b)** `D-513` を「未決のまま持ち越し」として再度立てるか。**どちらでも構いませんが、現状の逐語のままだと「決着した」と読まれます。**

### 7-1. ★★テストの親が実アプリの親と違うと、実装した機能が 1 フレームも表示されないまま緑になる

本サブが新規に実装した「一括復元の警告の内訳」は、**実アプリでは一度も表示されていなかった。** 一括操作の末尾で `onComplete()` を呼ぶと親が選択状態を空にし、子が「選択が空なら描画しない」で `null` を返すためである。**テストが緑だったのは、`onComplete` を何もしないモックにしており、親の再描画が起きなかったから**である。

**★同じ理由で、既存の「N 件失敗」の警告表示は 2 サブ前からずっと不可視だった。** 本サブが**同じ描画経路の上に新しい要求を載せた**ことで、既存の穴がそのまま新機能の穴になった。

- **一般化**: **「親から渡された状態が空になったら描画しない」子コンポーネントに、操作の結果を持たせてはならない。** 操作が親の状態を空にするなら、結果は**その条件から独立して**生存させる。
- **機構化**: **結果表示を主張するテストは、親と同じ状態遷移を持つラッパーで描画する。** モックの `onComplete` を no-op にすると、この型の欠陥は**構造的に検出できない**。
- **★検出できたのはレビューの静的読解だけだった。** テスト・lint・型検査はすべて緑であり、**人が呼び出し連鎖を追う以外に見つける経路が無かった。**
