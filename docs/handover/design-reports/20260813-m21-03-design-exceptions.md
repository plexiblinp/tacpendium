## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★いずれも「指示書に書かれていなかったので確定させた」ものである。** 指示書と異なる判断を下したものは §2 に分けてある。

### ★1-1 物理入力の受け手は常に 1 面である（**指示書が予見していなかった問題への新設仕様**）

**指示書は「2 面の両方で動く」（§4.9・`D-350`）としか書いておらず、2 面が同時に表示される場合を想定していない。** **実装ソースの実査で、想定が成り立たないことが判明した**——

- `ComboEditor` は「レシピ」節（`RecipeBuilder` → 入力面 1 個）と「このコンボに紐づくセットプレイ」節（`SetupRegistrationSection` → `SetupInputRow` × N → `SetupRecipeEditor` → 入力面 N 個）を持つ。
- `CollapsibleFieldset` は **既定 `defaultOpen = true`**（`web/src/features/combo/components/CollapsibleFieldset.tsx:7`）。
- ⇒ **素朴に入力面へ接続を置くと、(a) rAF ループが面の数だけ増え**（M21-01 §4.1-2 ／ M21-02 の「ループは 1 本に保つこと」に反する）**(b) 1 回の物理入力が全部の面へ同時にステップを足す。**

**確定した形**（`web/src/features/gamepad/GamepadInputProvider.tsx`）:

| # | 仕様 |
|---|---|
| 1 | **供給元はアプリ全体で 1 個**（`web/src/App.tsx` へマウント）。rAF ループ・同時押し判定・プロファイル解決・受け手の調停を 1 組だけ持つ |
| 2 | **入力面が 1 つも表示されていない間はポーリングを回さない**（M21-01 §4.1-2 を維持。参照カウント方式） |
| 3 | **確定したステップ候補は受け手 1 面にだけ配送する。** 既定は最初に現れた面（コンボ編集画面ではレシピ入力面） |
| 4 | **入力面のどこかを触る（`pointerdown` / `focus`）と、その面が受け手になる**（**開発者裁定＝「最後に触った面」**。§3-1 の 2） |
| 5 | **受け手であることを常時表示する**（`recipe-gamepad-owner`。受け手でない面は「他の面が受付中」、読取表示にも「この面は受付中ではありません」） |

- ⇒ **`DES-005` §6.4 へ「物理入力の受け手は常に 1 面であり、最後に触った入力面が受け手になる。受け手であることは画面に明示する」を明文化してほしい。** **`M21-04`（コントローラ完結入力）は確定・削除をパッドへ割り当てるため、「どの面へ効くか」がこの調停で決まる。** 書かれていないと M21-04 が別の調停を作る。
- ⇒ **`CHANGE-111` §2-e′（「対象面は 2 つである」）に、この 1 行を足す位置がある。**

### 1-2 告知・読取表示は「機体を観測できているとき」だけ出す

**指示書 §4.6 は「置き場は物理入力を使う面」としか書いておらず、出し分けの条件が無い。**

**初版は「供給元の内側にいるか」で出し分けていたが、供給元はアプリ全体に常設されるため本番では常に真であり、⇒ 物理コントローラを一度も接続したことがない利用者にも、告知（3 行の枠）と読取表示（3 区画）が常設されていた**（レビュー指摘 中-1。**`make e2e` が実機コントローラの無いヘッドレス環境で 73 件緑だったこと自体が、未接続でも DOM に出ていた証拠だった**）。

**確定した形**: **`status === "connected"`（機体を観測できている）でのみ告知・読取表示・受け手バッジを出す。** **接続状態の表示そのもの（`recipe-gamepad-status`）は M21-01 の導線であり常に出す。** 切断時は読取表示も捨てる。

- ⇒ **`DES-005` §6.4.2 の告知の行へ「接続中の入力面に出す」を 1 行。** 告知の目的は「まとまりうることを事前に伝える」ことであり、**物理入力を使わない利用者には出す理由が無い。**

### 1-3 「解決できなかった入力」の理由は **6 種**であり、うち 1 種は指示書の分類に無い

**指示書 §4.2-3 は「PP・KK・強度をまたぐ組み合わせ・3 ボタン以上」を解決できない入力へ倒すとしか書いておらず、読取表示へ出す理由の粒度を定めていない。**

**確定した形**（`web/src/features/gamepad/recipeInputResolution.ts` の `UnresolvedReason`）: `od_not_supported`（PP/KK）／ `mixed_strength`（強度をまたぐ P＋K）／ `too_many_buttons`（3 つ以上）／ `unknown_combination`（対応する操作が無い）／ `move_not_found`（当該キャラに技が無い）／ **`rush_not_available_in_air`**。

**★最後の 1 種は指示書に無い。** ラッシュ版トグル ON ＋ 上系方向は、既存の `resolveDirectionalRushInput` が `dir >= 7` で `null` を返す（空中ラッシュ不可＝`DES-005` §6.4）。**それをそのまま `move_not_found` として出すと、読取表示に「このキャラクターに該当する技がありません」と出て理由を取り違える**（レビュー指摘 中-4）。**⇒ 専用の理由へ分け、「ラッシュ版は空中では出せません」と出す。**

- ⇒ **`CHANGE-111` §2-b（読取表示の 3 つ目＝解決できなかった入力）へ反映する際、理由の粒度が as-built である。** **とくに「なぜ入らなかったか」が分かることが §4.3-3 の目的であり、`move_not_found` に丸めると目的を果たさない。**

### 1-4 点灯の対象——**ニュートラルは点灯させず、マクロの投げは方向で前後に分かれる**

**指示書 §4.4 は「押している間ずっと光り、離すと消える」としか書いていない。** 方向は M21-01 以来「状態」であり、**未入力でも `direction_neutral` が入っている**ため、素朴に点灯へ回すと**何も押していないのにテンキー 5 が光る**（レビュー指摘 中-2。初版はこの挙動をテストで固定してしまっていた）。

**確定した形**: **方向の点灯は非ニュートラルのときだけ。** あわせて、**専用の物理ボタンに「投げ」を割り当てている機体では、方向の後方成分に応じて画面上の「前投げ」「後ろ投げ」のどちらが光るかを切り替える**（解決結果と同じ向きに合わせる）。

- ⇒ **`DES-005` §6.4 の点灯連動（§6.6-5 の回収）へ「方向はニュートラルを点灯対象に含めない」を 1 行。** **「状態」と「押している」を同一視すると規約の文面と食い違う。**

## §2 契約・設計に反する独自判断（★親の受理／却下を要する）

### ★2-1 接続部品の出口に「方向」を独立フィールドとして持たせなかった

**何に反したか**——`docs/instructions/M21-03-recipe-input-and-readout.md` **v1.2.0 §4.9-2**:

> **★部品の出口は、面に依存しない中立な形にする**——**`move_code` ＋ 方向 ＋ 修飾**。**面ごとのステップ型への写し替えは、呼び出し元の面が行う**

**実装がどうなっているか**——出口は **`StepInput { moveId, moveCode?, modifiers? }`**（`web/src/features/combo/components/VirtualController/useControllerInput.ts:6`）であり、**方向を独立したフィールドとして持たない。**

**なぜそう判断したか**——2 点。

1. **方向は解決の時点で `move_code` へ畳み込まれる。** 段階1 の構造引きは方向ゾーンを `standing_` / `crouching_` / `jumping_` の接頭辞として `move_code` に含め（`web/src/features/combo/inputResolution.ts` の `ZONE_PREFIX`）、段階2 の解決表も方向込みの `token_key` で引く。**⇒ 出口に方向を別途持たせると、同じ情報を 2 か所に持つことになる**（`E-76`）。**しかも 2 つがずれても誰も気づけない**——`move_code` が正で、方向フィールドは誰も検証しない。
2. **`StepInput` は仮想コントローラが既に使っている中立形であり、2 面の写し替え（`RecipeBuilder.handleVCStepAdd` ／ `SetupRecipeEditor.handleVCStepAdd`）が実装済みである。** **新しい型を作らずに §4.9-2 の主旨（面に依存しない中立形・写し替えは呼び出し元）を満たせた**——結果として**セットプレイ入力面の変更は 0 行**になった。

**⇒ 親へ求めること（二択）**

| 選択 | 帰結 |
|---|---|
| **受理**（製造の推奨） | **`CHANGE-111` §2-e′ を `DES-005` へ写すときに §4.9-2 の文言をそのまま使わない。** 「出口は面に依存しない中立形（**当該キャラの `move_code` に解決済みのステップ**）とし、面ごとの写し替えは呼び出し元が行う」の形にしてほしい。**方向を独立に持つ形を設計書へ書くと、次の担当が実装を「不足」と読んで足しにくる** |
| **却下** | 出口へ方向を足す。**その場合、方向は `move_code` と重複する派生情報になるため、「どちらが正か」を設計書側で明示する必要がある**（明示しないと `M21-06` が方向フィールドを信用して読む） |

**★本件は動作に影響しない。** レビューも「**仮想 UI と同一の中立形に揃えたこの判断は正しい**」としたうえで、**「指示書の文言とは差があり、完了報告に差分として書かれていない」**（低-2）として検出した。**⇒ 完了報告 §3-11 へ記載済み。本レポートで親へ上げる。**

## §7 教訓（`retrospective-log` 行き）

> **★親はこの節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、実施者は**設計担当**（反映担当は 2026-08-11 に廃止）。

1. **「通念として正しい」ことと「その写像の入口が実装に在る」ことは別である。** 指示書 §4.2-2 の「2 ボタン同時＝OD」は格闘ゲームの通念としては正しいが、**OD の `move_code` は `<family>_od` であり、family を決める入口が既存の解決経路に無かった**（`token_key` は方向＋ボタンしか引かない）。**設計卓は実装ソースを読めないため、通念で書くと入口の有無を確かめられない。** **機構化**——**指示書で「A を B へ写す」と書くときは、B を確定させる既存の入口の所在（ファイル・関数名）を §3.3 の実査項目に必ず入れる。** 本サブでは v1.2.0 の §3.3-4 がまさにその形へ改められ、**停止条件 5（既存の入口が無ければ止める）まで用意された**——この形が正解である。

2. **「常設される UI」の出し分け条件は、機能の有無ではなく利用者の状態で決める。** 告知と読取表示を「供給元の内側にいるか」で出し分けたが、**供給元はアプリ全体に常設されるため本番では常に真**であり、物理コントローラを持たない利用者にも常設された。**機構化**——**新しい常設 UI を足したら「これを見なくてよい利用者は誰か」を 1 度問う。** 該当者がいるなら、その条件が出し分けに入っているかを確かめる。**なお本件は E2E が緑だったこと自体が証拠だった**（ヘッドレス＝実機無しの環境で DOM に出ていた）——**「テストが緑」は「出ていない」を意味しない。**

3. **「状態」を「押している」として扱うと、規約の文面と静かに食い違う。** 方向は M21-01 以来「イベントではなく状態」であり、未入力でも `direction_neutral` が入っている。それを点灯へ回した結果、**何も押していないのにテンキー 5 が光り、しかもその挙動をテストで固定してしまった**（誤った挙動の固定はレビューでしか見つからない）。**機構化**——**「常に値が入っている状態」を「押下」「選択」「発生」などのイベント語の表示へ流すときは、既定値を除外する必要がないかを必ず確かめる。**

4. **前方参照コメント（「〜は次のサブが作る」）は、そのサブが完了した時点で失効する。** 本サブでは M21-01 / M21-02 が書いた「M21-03 が作る」が 3 か所残り、うち 2 か所は**内容が偽になっていた**（配送バッファへ役割が変わった定数 ／ 5 件中 2 件しか生成しない旨）。**動作は正しいためテスト・型検査・lint のいずれでも赤にならない。** **機構化**——**指示書の完了条件へ「自分を名指ししている前方参照コメントを走査して是正する」を入れる。** 走査キーワードは自分のサブ ID で足りる（`grep -rn "M21-03" web/src`）。**否定形確認（§4.10）と同じ枠で回せる。**

5. **環境の前提が欠けていると、自分の変更が壊したように見える。** クラウド実行環境で `make e2e` が 73 件全落ちしたが、原因は `config.toml`（gitignore 済み・クローンに含まれない）の不在で、**アプリが全ページをウィザードへリダイレクトしていた**。**切り分けに要した時間の大半は「自分の変更を疑う」ことに使われた。** **機構化**——**「全件落ちる」ときは、まず 1 件だけ走らせてページのスナップショットを見る。** Playwright は失敗時に `error-context.md` へ DOM の要約を残しており、**そこに「初期設定 / ようこそ」と出ていれば 1 秒で分かる。** 個々のアサーションを追う前に、**アプリが想定の画面に居るかを見る。**
