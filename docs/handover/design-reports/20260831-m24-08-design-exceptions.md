### ★§1-1 詳細: 新ルート `POST /api/presets/:id/recipe-cache/rebuild`（`DES-002` §4.2）

**なぜ要ったか** — `recipe_cache` は `{presetId: 表示文字列}` の JSON であり、`preset_aliases` を直すだけでは追随しない。**着手前は作り直す手段が実質存在しなかった**（実査＝完了報告 §2 の 10）:

- 起動時の自動再構築は無い（`main.go:287` は `RecomputePresetCache` を config サービスへ**注入するだけ**）
- 設定画面の「キャッシュ再構築」ボタンは `disabled` の未実装で、**対応 API も無かった**
- 組み込みプリセット（`official_ja_move`）は `PUT /api/presets/:id` が **403**（`VAL-P01`）のため、エイリアス更新経由の再計算にも乗せられない

**⇒ 指示書 §9.1-3 の分岐が成立したため手を止めて報告し、「再構築ボタンを実装する」裁定を得た**（§3-1）。

**応答の実 DTO**（`internal/api/preset/dto.go:87-89`。実サーバの応答をそのまま）:

```
HTTP 200
{"presetId":1}
```

**エラー契約の全行**（`internal/api/preset/handler.go:75-103`）:

| 状況 | ステータス | コード |
|---|---|---|
| 正常 | `200` | —（`{presetId}` を返す） |
| `:id` が整数として読めない | `400` | `invalid_id` |
| そのプリセットが存在しない | `404` | `not_found` |
| プリセット取得が失敗した | `500` | `internal_error` |
| 再構築そのものが失敗した | `500` | `internal_error` |
| 再構築関数が注入されていない | `501` | `not_implemented` |

**母集団の述語** — 対象は **`:id` の 1 枚ぶん**の `recipe_cache` の作り直しである。真実（`preset_aliases`）から表示文字列を作り直すだけで、**プリセットの中身は 1 バイトも変えない**。**★件数を返さない**——`service/notation` 側が対象件数を返す形になっておらず、返すようにするには同パッケージの契約変更が要る（契約 F-1 の射程・本サブでは触らない）。**★全プリセットを一括で再構築する経路は無い**。設定画面が本ルートを枚数分呼ぶ形である。

**★持たせなかった分岐 2 つ**（返らない分岐を残さなかったことは、読む側が誤読しないために要る情報である）:

**(a) 組み込みプリセットでも `403` にしない。** `authorizeMutation` を通していない（`handler.go:56-60`）。あれは「組み込みは編集も削除もできない」（`VAL-P01` / `D-290`）の門番であり、**本ルートは編集ではない**。**★むしろ組み込みでこそ必要になる**（本サブが直した `official_ja_move` がまさにそれ）。実在検査（`service.Get`）だけを行う。**実サーバで確認済み**——同じ組み込みへの `PUT` は `403 builtin_protected` のままであり、`VAL-P01` を緩めていない。

**(b) 所有者検査を持たせていない。** カスタムプリセットについて requester と `preset.UserID` を突き合わせていない（`VAL-P07` は「他ユーザーが作成したものは参照のみ可」と定める）。理由 3 つ（`handler.go:62-74` に逐語）:

1. 本操作はプリセットの中身を 1 バイトも変えない。結果は誰が押しても同じである
2. 応答は `presetId` だけを返す。他ユーザーのプリセットの中身は 1 つも漏れない
3. `recipe_cache` は「そのユーザーのコンボの表示文字列」であり、作り直しても見えるものは変わらない

**★逆に所有者検査を入れると、組み込みを 403 にしたのと同じ理由で詰む**——既定プリセットが他ユーザーの作ったカスタムであるとき、作り直せなくなる。**⇒ `VAL-P07` の射程に「キャッシュ保守」を含めるかは設計判断であり、本サブの射程外である。設計卓の判定を仰ぐ。**

**実サーバでの疎通**（バイナリを建てて確認。ハンドラの単体テストは `RegisterRoutes` までしか見ておらず、`main.go` の関数注入が通るかは別の主張であるため）:

```
POST /api/presets/1/recipe-cache/rebuild      -> HTTP 200  {"presetId":1}
PUT  /api/presets/1                           -> HTTP 403  builtin_protected
POST /api/presets/999999/recipe-cache/rebuild -> HTTP 404
POST /api/presets/abc/recipe-cache/rebuild    -> HTTP 400
```

**⇒ `DES-002` §4.2 の経路表へ本ルートを 1 行足してほしい。「経路は変わっていない」とだけ読まれると、新ルートが表に載らない。**

### ★§1-7 詳細: Vitest の件数が summary に 1 度も出ていなかった（`DES-002` §11.3）

**発見の経緯** — 本レポートの手交後、開発者が `PR checks` を手動起動して 3 job の緑を確認した（確認 6 の消化）。**そのとき `web test (Vitest)` の summary の `Test Files` と `Tests` が空欄だった。** 他の行は埋まっており、job も緑である。

**根因（実測で特定した）** — **Vitest は色付けの判定に picocolors を使い、TTY でなくても `CI=true` なら色を付ける。** GitHub Actions は `CI=true` を必ず立てるため、`tee` したログの行頭は空白ではなくエスケープになる:

```
^[[2m Test Files ^[[22m ^[[1m^[[32m2 passed^[[39m^[[22m^[[90m (2)^[[39m
```

着手前の抽出は `grep -E '^[[:space:]]*Test Files'` であり、**行頭を空白と仮定していたため 1 件も当たらない**（同じログに当てて実測＝`[]`）。**`go test` 側の summary が埋まっていたのは、Go のテスト出力に色が付かないからである。**

**★実害の程度** — **テストは実際に走って緑である**（job 246 秒・`pnpm install` 2 秒）。壊れていたのは件数の記録だけである。**ただし `go test` 側の summary には「所要が数秒なら実行されていない」という注意書きが添えてあり、Vitest 側は同じ目的の数字が常に空だった。⇒ 「緑だが空欄」と「スイートが 1 件も走らずに緑」を区別できない状態だった。**

**是正（2 段）** — `.github/workflows/pr-checks.yml` の summary step のみを変更した。**合否を決める `pnpm test` step には触っていない。**

1. **抽出前に ANSI を落とす**（`sed 's/\x1b\[[0-9;]*m//g'`）
2. **空のときは行なしと分かる印を出す**（`**行が無い(読めなかった)**`）。**★着手前は空欄だったため、壊れていること自体が読めなかった**

**★2 は既存の形へ揃えた** — `nightly-crossbuild.yml` の E2E summary が同じ印を持っている。**★同 E2E summary は `grep -oE '[0-9]+ passed'` で行頭を見ないため無傷であり、壊れていたのは本 step だけである**（ワークフロー 2 本の抽出箇所を全数走査して確認）。

**破壊確認** — ANSI 除去だけを外して実物の色付きログへ当てると、`**行が無い(読めなかった)**` が出る。**⇒ 同じ欠陥が再発しても、今度は黙らない。**

**⇒ `DES-002` §11.3 へ「summary の件数抽出は ANSI を落としてから行う。空のときは印を出す」を 1 行残してほしい。★残さないと、次に summary を書く担当が同じ形を書く。**
