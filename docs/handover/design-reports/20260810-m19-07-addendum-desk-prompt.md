## 1. 開発者の追加要望と、実装した内容

### 要望①「確認できた条件（任意）が分かりにくい。コンボ詳細の『成立条件を編集』と見た目を揃えてほしい」

**製造の実装不足でした。** 指示書 §2.3 は「`DES-005` §5.6 項目10 と**同じ 2×2 グリッド**（受け身種別 × 画面端）を再利用する」と求めていたのに、既存の採用パネルのインライン実装を流用したため、**チェックボックス 4 個を横に並べただけ**になっており「2×2」という構造が画面に現れていませんでした。

**実装**: `SetupResultEditor`（項目10 の編集 UI）と**同じテーブル構造**へ作り替えました。列＝受け身種別／行＝画面端／セルに状態アイコン／凡例つき。

- 入力できるのは**成立（ok）のみ**という非対称は**変えていません**（項目10 は 3 択＋メモ、こちらは成立チェックのみ）。**凡例も「成立／未検証」の 2 値だけ**出しています——**選べない「不成立」を凡例に出すと「不成立も付けられる」と誤読される**ため。
- 状態アイコン・語彙・セルの組・端の i18n キーは**すべて項目10 の正典を再利用**（第 3 の語彙を作っていません）。

### 要望②「セットプレイ登録画面（`/combos/:comboId/setups/new`）でも入力したい」

**実装**: 同じ 2×2 を**新規登録モードのときだけ**置きました。

- **v3 原則の判定＝`親確定 ○`**。この面は **URL に `comboId` があり親コンボが確定**しています。保存は `POST /api/combos/{comboId}/setups` の `verifiedConditions` として**セットプレイ作成と同一トランザクション**で書かれます（この API は M19-03 で既に対応済みで、**バックエンドは無変更**です）。
- **★編集モード（`/setups/:setupId`）には出していません。** `DES-005` §5.6 が「実装しない（開発者判断 2026-07-28）」と明記しているためです。**両ルートは同一コンポーネント（`SetupEditorPage`）**なので、`mode === "create"` の分岐が唯一のガードになります。E2E でこれを固定しました。

### ③ 上記の帰結として、採用パネルも同じグリッドへ統一（開発者判断 2026-08-10）

要望①でグリッド化した結果、**「登録時＝2×2 グリッド／採用時＝チェックボックス 4 個」という不統一**が生まれました。2026-08-09 に「差し替えない」と判断いただいていた根拠が「**見た目は同じだから実害がない**」だったため、**前提が失効した**と判断し、開発者へ再提示のうえ**揃える**で確定しました。

⇒ **本番コードで「確認できた条件」を持つ 4 つの面すべてが同一の 2×2 グリッド**になりました。payload はセルの順序まで従来と同一で、既存テスト（採用パネル 26 件）は**無改変で green** です。

### (1) §5.9「セットプレイ登録・編集」の表示項目に成立条件が無い

**現行の逐語**（表示項目は 5 つで、成立条件が載っていません）:

```
**表示項目（上から順）**：
1. キャラクター選択（新規時のみ、または紐付け元コンボから自動設定）
2. セットプレイ名（**必須**＝M12-03/C-03。空不可・VAL-S06。create/update 両方で空クリア禁止）
```

**依頼**: **項目 4 と 5 の間に「成立条件（新規登録時のみ）」を追加**してください。実装の並びは レシピ入力領域 → 成立条件 → バリデーション表示 → 保存ボタン です。

**★あわせて「編集時は出さない」の明記をお願いします。** §5.9 は**登録・編集を 1 つの節で説明している**ため、書かないと編集画面にも出ると読めてしまいます（実装は同一コンポーネントなので、この記述が後続担当の唯一の手がかりになります）。

### (3) §5.6 項目12（採用パネル）の記述

**現行の逐語**（`05-screen-design.md:302`）:

```
   - **採用ダイアログでの条件チェック**（CHANGE-087・M19-03）：提案を**採用するダイアログで「確認できた条件」をチェックできる**。UI は項目10 と**同じ 2×2 グリッド**を再利用し、新しい操作モデルを作らない。
```

**依頼**: 記述の**意図どおりに実装が追いついた**ことの反映です（文面は概ねそのままで構いません）。M19-03 時点の実装は「同じ 2×2 グリッドを再利用」と書きながら**実体はチェックボックスの横並び**で、2026-08-10 に初めて記述どおりになりました。**「同じ」の実体が何かを 1 段具体化しておく**と、次に同型の面を作る担当が今回と同じ流用ミスをしません（例: 行＝画面端／列＝受け身種別のテーブル・状態アイコン・凡例つき）。

**★用語について 1 点**: 設計書・製造の双方が「採用**ダイアログ**」と呼んでいますが、**実体はモーダルではなくインラインで展開するパネル**です。今回この呼称が原因で、開発者が**別の UI（「既存から紐付け」ボタンが開く `LinkExistingSetupModal`）**のことと解釈し、いったん誤った判断をしかけました（当該モーダルは全 72 行で、成立条件を**そもそも持ちません**）。**用語を「採用パネル」等へ改めるか**、判断はお任せします。

## 3. あわせて判断をお願いしたいもの（本追補で顕在化）

### (a) `setplay.confirmedConditionsHint` の文言が「採用」語彙のまま

i18n キーを 4 面で共有しているため、**採用パネル以外にも「採用できます」という文言が出ます**。

```
ja: 「実機で成立を確認できた条件だけチェックしてください。チェックしなくても採用できます。
     不成立の記録は登録後にコンボ詳細から行えます。」
en: "…You can adopt without checking any. …"
```

**コンボ新規登録画面とセットプレイ登録画面には「採用」という操作が存在しません**（`採用` / `adopt` は項目12 専用の語彙）。**キーを共有した判断自体は正しい**（第 3 の語彙を作らない）ので、**直すなら文言側を 4 面で通じる形へ**——例: ja「チェックしなくても**登録できます**」／ en "You can save without checking any."。**ja / en 両方の同期が要る**ため、製造では変更していません。

### (b) 既に §4 で上げている 2 件（本追補では未対応・再掲のみ）

- **値域外 `techType` の HTTP ステータスが、同梱 400 ／ 単独 500 で食い違う**（単独側は M19-03 からの取りこぼし。直すと本サブの不変条件 R-2 に抵触するため触っていません）。
- **`PUT /api/combos/:id`（キー変更編集）では `verifiedConditions` が黙って無視される**（`CreateRequest` を POST と共用しているが `input.Setups` を読むのは `Create` だけ）。→ `DES-002` への併記が要ります。
