## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### ★1-1 `RecomputePresetCache` は tx を取らず、**内部の読みも tx を見ない**。`SUPP-001` §7.1 にこの性質が無い

**実測**（`internal/service/notation/cache.go` / `resolver.go`）:

| 観測 | 内容 |
|---|---|
| シグネチャ | **4 兄弟のうち `RecomputePresetCache` だけが `*sql.Tx` を取らない**（`RecomputeComboCache` / `DeleteComboCache` / `DeletePresetCache` は取る） |
| 内部の読み | `ComputeSingleCache` → `resolveRecipe` → `resolveMoveStep` → `presetRepo.FindAlias` / `FindPresetByID` / `FindPresetByCode` が**すべて `r.db` 直読み** |
| 帰結 | **書き込み tx の内側で呼ぶと、コミット前のエイリアスが見えず「古い表記」を書き込む。エラーにならず、テストも lint も型検査も緑になる** |
| 加えて | `internal/infra/db/db.go` はプールを無制限にし `busy_timeout = 5000`。⇒ **開いている書き込み tx の内側から非 tx の UPDATE を撃つと別コネクションになり `SQLITE_BUSY`** |

**★陽性対照で確かめてある。** 再計算の呼び出しを一時的にコミット前へ移すと `Test_Update_RecomputesAfterCommit`（`internal/service/preset/recipe_cache_wiring_test.go`）が `SQLITE_BUSY` で落ちる。対照実験後にコードは元へ戻し、差分が無いことを確認済み。

**⇒ `SUPP-001` §7.1 へ次の 2 点の明文化を依頼する。**

1. **`RecomputePresetCache` は書き込みトランザクションの外（コミット後）で呼ぶこと。** 内側で呼ぶと silent に古い表記を書く。
2. **一般規約として「署名が `*sql.Tx` を取るなら、その tx を読みにも使う。使わないなら取らない」**（**D-360** の条件 1）。**同表の他の行にも同じ検査を通してほしい**——実測で **`RecomputeComboCache` は tx を取りながら `ListAllPresets` と `resolveRecipe` 内のエイリアス読みが tx を見ない**（§4-4）。

### 1-5 `config` サービスへ公開型を 2 つ新設した（`DES-002` §4.2 の `PUT /api/config` の契約に効く）

```go
type PresetExistsFunc func(presetID int64) (bool, error)
type DefaultPresetChangedFunc func(presetID int64) error
```

- **`Service` インタフェース自体は不変**（`Get` / `Update` のシグネチャは変えていない）。増えたのは `NewService` の引数のみ。**⇒ §9.4 停止条件 2 には触れていない。**
- **config サービスは preset パッケージ・DB・notation のいずれにも直接依存していない**（`database/sql` の import も無いまま）。M20-04 が「config へ DB 依存を持たせる変更になる」として止めた形を、**依存の向きを増やさずに引き取った**。
- **★実在検査は「既定プリセットが変わるとき」だけ走る。** 他項目だけの部分更新で無駄な DB アクセスを増やさないため。
- **★両型とも `context.Context` を取らない。** `Service.Update(req)` が ctx を持たず、公開形の組み替えは §9.4 停止条件 2 で範囲外のため、呼出側が起動時の ctx をクロージャへ閉じ込めている。**⇒ `PUT /api/config` のクライアント切断では検査も再計算もキャンセルされない**（望ましい方向だが、将来 ctx を通すときの判断材料として godoc に残した）。

### 1-6 ★挙動差 1 件: エイリアス編集で `combos.updated_at` が動かなくなった

非 tx の `UpdateRecipeCache` は `updated_at = datetime('now')` を bump するが、**`UpdateRecipeCacheTx` は bump しない**（`internal/repository/combo/repository.go` / `setup/repository.go`）。§4.4-1 のため tx 版へ寄せた結果、**エイリアス編集で全コンボの `updated_at` が動かなくなった**。

**望ましい方向である**（キャッシュの作り直しは利用者によるコンボの編集ではない。`RecomputeComboCache` は元から tx 版を使っており、そちらに揃った形になる）。**ただし「更新日時でソートしていた画面の見え方が変わる」ため、挙動が変わった事実として記録する。**

### 1-7 リポジトリの公開メソッドを 2 本リネームした

`ListAllActiveCombos(ctx)` → **`ListAllActiveCombosTx(ctx, tx)`** ／ `ListAllActiveSetups(ctx)` → **`ListAllActiveSetupsTx(ctx, tx)`**（`tx` が nil なら DB ハンドルで読む）。

**§4.4-4（tx を取るなら読みにも使う）を `DeletePresetCache` で満たすために必要だった。** **呼出元は `internal/service/notation/` だけであることを実査で確認**しており、他マイルストーンへの波及は無い。**両リポジトリは既に `runner(tx)` ヘルパを持っており、変更は機械的。** 並行して `Tx` 無し版を残すと**呼出元 0 件の死んだメソッド**になるためリネームを選んだ。

### 3-2 推測で進めた点（指示書 §9.2 の許容範囲）

| # | 判断 | 理由 |
|---|------|------|
| 1 | **`RecomputePresetCache` は `*sql.Tx` を取らない形を採った** | §4.4-4 は「tx を取るなら読みにも使う」を求める。取る形にすると resolver とリポジトリ 3 本の読み経路を tx 対応にする必要があり、**設計卓が費用対効果で退けた案 B そのものの作業量**になる。⇒ 呼び出し元ではなく**本メソッドが自分で境界を持つ**形にした |
| 2 | **起動時フォールバックで `config.toml` へ書き戻していない** | env 上書き値の焼き付き followup `config-toml-write-back-env-asymmetry` に触れないため。**倒すのはメモリ上の値だけ。** 実機で書き戻されないことを確認済み |

## §7 教訓（`retrospective-log` 行き）

> **★親チャットは本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、実施者は**設計担当**。

1. **否定形確認のキーワードは、コメントが書かれている言語で書く。** 本サブは「`未実装` を含む行」を `grep -iE "recipe|preset|cache"` で絞ったが、**本リポジトリのコメントは日本語であり「プリセット」は ASCII の `preset` に一致しない**。⇒ 1 件を取りこぼし、**件数を実態より少なく報告した**（レビュー指摘 高-1 で是正）。**★走査は「網の目が対象の言語に合っているか」を先に確かめる。** ASCII 識別子だけの網では、日本語コメントの残骸は構造的に見えない。
2. **「diff 0」は不変条件そのものではなく proxy である。proxy を守るために振る舞いを隠す形を採ったら、proxy は嘘をつくようになる。**（設計卓が **D-360** で記録した一般則。製造側の教訓としては）**⇒ 凍結面に触れざるを得ないと分かったら、黙って回避策で proxy を満たさず、照会する。** 本サブは「可変プロセス状態で diff 0 を保つ」案を作れたが、**それは検査を通しつつ振る舞いを同じだけ変える形**だった。
3. **「委任された判断」の前提が実装と違っていたら、実装ではなく照会で解く。** 指示書 §9.2 は境界と寄せ先を実装判断に委ねていたが、**委任の前提**（tx を取れる／`punishfinder` に触れずに寄せられる）**が実測で崩れていた**。⇒ **委任は前提ごと委任されているわけではない。** 前提が崩れたら委任は失効すると考える。
4. **順序が正しさの根拠になるなら、順序が壊れたことを検出する検査を置く。** かつ**陽性対照で検出力を確かめる**。本サブは呼び出し順テストを書いたあと、実際に呼び出しをコミット前へ移して落ちることを確認した。**★「テストを書いた」と「テストが効く」は別である。**
5. **チェックポイントコミットで `git add -A` を使うと、コミットしてはいけないものを巻き込む。** 本サブは開発者が「コミットしないでください」と指示した指示書 2 本を巻き込み、**`revert` / `reset` が deny のため自力で是正できない状態**になった（§2-2）。**⇒ 「コミットするな」と言われたファイルがある回は、`git add -A` を使わずパスを列挙する。**
6. **E2E の共有資源は、ファイル単位の並列実行と相性が悪い。** `fullyParallel: false` は**ファイル内**の直列化しか保証しない。**★「作る側」だけでなく「消す側」も資源を触る**——全削除を `beforeEach` で撃つ spec は、上限テストがカスタムを保持している最中に走ると**そちらを数え損ねさせる**。
