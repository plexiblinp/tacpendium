## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1. ★仮登録（`is_draft = true`）を「作る／復元する」ときも 4 件とも走らせない

**指示書が明示しているのは母集団側の `is_draft = 0` だけである**（§3.3-4 / §1.4-5）。**「draft を作るとき・draft を復元するときに判定するか」は書かれていない。**

実装は **走らせない**を採った。根拠は `DES-006` §2.3「仮登録と本登録の間では重複判定は行わない」と、既存 `VAL-C02` の先例（`internal/service/validation/combo.go:114` の `if !isDraft { validateC02Duplicate(...) }`）。

- ガードの位置＝`internal/service/combo/service.go` の `CheckTrashDuplicate`（`combo.IsDraft` で早期 return）／ 同 `validateR03` ／ セットプレイ側は親コンボ 0 件で発火しない構造。
- テスト＝`TestCheckTrashDuplicate_VALC14_SkippedWhenCreatingDraft` ／ `TestCheckTrashDuplicate_VALC14_ExcludesDraftRows` ／ `TestRestore_VALR03_SkippedForDraft`。

**⇒ `DES-006` §13（または `VAL-C14` の新設節）へ「4 件とも仮登録では走らない。母集団の `is_draft = 0` とは別の話であり、両方を守る」を明文化してほしい。** 走らせる側に倒すと、**試案を作るたびにゴミ箱の警告が出る。**

### 1-2. ★`POST /api/setups` というルートは存在しない — 実ルートは `POST /api/combos/:comboId/setups`

指示書 §4.1 / §2.1 は `VAL-S07` の適用経路を `POST /api/setups` と書いているが、**そのルートは無い**（`internal/api/setup/routes.go:8`）。実装は実ルートへ載せた。

**⇒ `CHANGE-125` の逐語には実ルート名で書いてほしい。** 併せて **`VAL-S04` の応答は `409 duplicate_setup`** であり `400 validation_failed` ではない（`internal/api/setup/handler.go:56`）。`VAL-S07` は同じ経路の **`200` 応答の `warnings`** に載る別物である。

### 1-3. ★登録 2 経路の `warnings` は `DES-002` に記述が無い（本サブが最初の実装者）

`M23-04` が `DES-002` §4.2 / §4.3 へ書いたのは**復元 2 経路だけ**である。本サブが登録 2 経路へ広げた（指示書 §4.6 が明示的に解禁）。

**★`DES-002` §4.3 規則 3 は「新しい経路で `details` を設定するときは、その経路の応答形が本書に在ることを先に確かめる」と定めている。** 登録 2 経路は本書に無いため、**`CHANGE-125` で追記が要る。**（`400 validation_failed` の経路ではないので 2 段入れ子にはならない。）

as-built の逐語形:

```jsonc
// POST /api/combos の 201 応答 ／ POST /api/combos/{comboId}/setups の 200 応答
{
  "id": 42,
  "...": "(既存のまま)",
  "warnings": [
    {
      "code": "VAL-C14",
      "severity": "warning",
      "message": "同じ内容のコンボ 1 件がゴミ箱にもあります(登録は成功しています)",
      "details": { "combos": [ { "id": 7, "memo": "…" } ], "totalCount": 1 }
    }
  ]
}
```

**警告 0 件なら `warnings` キー自体が出ない**（`omitempty` ＋ ハンドラ側 `if len(...) > 0` の二重。`internal/api/combo/handler.go:96` ／ `internal/api/setup/handler.go:72`）。

### 1-4. ★登録応答では `validations` と `warnings` の両方に警告が載りうる

`DES-002` は「`warnings` と `validations` は別フィールドであり、**復元応答に `validations` は載らない**」としか書いていない。**登録応答は事情が違う。**

`POST /api/combos` は `VAL-C03` / `VAL-C08` / `VAL-C10` / `VAL-C11`（**いずれも `severity=warning`**）を従来どおり `validations` に載せたまま、`VAL-C14` を `warnings` に載せる。**⇒ 同じ severity の警告が 2 経路に分かれた状態が新しく生まれている。**

実害は無い（画面はそれぞれ別の表示経路を持つ）が、**明記しないと後任が「登録応答の警告はどちらを見ればよいか」で迷う。** `CHANGE-125` へ必須の注記として挙げる。

### 1-5. ★`VAL-S07` / `VAL-R04` は `M23-02` 適用前に論理削除されたセットプレイを検出できない

両者は `combo_setups` の JOIN で親コンボを絞るため、**紐付けが失われている行は 1 件も拾えない。** 当時の論理削除は `combo_setups` を DELETE していたためである（`M23-02` §4.2-6。`internal/service/setup/restore.go` のコメントが同じ事実を引いている）。

**⇒ `DES-006` へ「同一親コンボの削除済みセットプレイを見る」とだけ書くと、この限界が落ちる。** **dev DB で件数を数えたときに「0 件だった」の解釈を誤らせる**——検出できていないのか本当に無いのかが区別できない。**注記を必須にしてほしい。**

### 2-1. ★★`VAL-R03` の母集団から旧行を除いていない — 指示書 §4.2 に反する（§4.4 には従っている）

**★製造の所見**: 着手時点で気づいて報告すべきだった（レビュー高-3 の指摘どおり）。**指示書の散文と表が食い違うことは他サブでも起こりうる。**

### 2-2. ★`details` に `totalCount` という新キーを足した — `DES-002` §4.3 規則 1 に対する差分

| 項目 | 内容 |
|---|---|
| **何に反したか** | **`DES-002` §4.3 規則 1**（`details` は `{id, name}` ／ `{id, memo}` の形で返す＝**新しい見せ方を作らない**・`D-417`） |

## §4 設計担当が未把握の残課題・申し送り

### 4-1. ★★【判断を求めている】保存前ダイアログ — 指示書 §1.3 の目的が §2.1 / §4.6 の手段では達成できない

**開発者が実機で見つけた。本サブの最重要の申し送りである。**

**問題**: 指示書 §1.3 は登録側の警告をこう位置づけている。

> **登録側の警告は「作り直す前に、ゴミ箱に同じものがある」を告げる。⇒ 重複そのものが減る。**

**しかし §2.1 / §4.6 が指定した手段は「保存成功後の応答に載せるトースト」である。保存後に告げるものは、定義上「作り直す前」に告げられない。⇒ 重複は減らない。** 利用者にできるのは「いま作ったものを自分で消し、ゴミ箱から戻す」手作業だけである。

**開発者の提案（逐語）**:

> 登録時に同一のレシピであれば、いったんダイアログを出して、入力内容を入れるかゴミ箱から復元するか、両方入れるかを選ばせるべきです。

**★設計判断が要る点が 3 つある。**

| # | 論点 |
|---|---|
| **a** | **「両方入れる」はセットプレイでは矛盾する。** 同一親・同一レシピの生きたセットプレイ 2 件は、いま **`VAL-S04` が ERROR（`409 duplicate_setup`）で拒否している状態**である。許すと**通常の登録では作れない状態を、この導線からだけ作れる**ことになる。コンボ側も `VAL-C02` と同じ関係 |
| **b** | **保存前チェックの土台は片側にしか無い。** コンボは `POST /api/combos/check-duplicate` ＋ `DuplicateRealtimeWarning` が在るが**生きた行しか見ない**（削除済みを見る口が要る）。**セットプレイ側には同等の事前チェック API が無い** |
| **c** | **`DES-006` §11.2 は「ERROR はモーダル」としており、WARNING でモーダルを出すのは §11.1 からの逸脱**になる。指示書 §4.6 の「★モーダルにしない」もこれを根拠にしている |

**★本サブでは文面のみ是正した**（完了報告 §10）。**実装（保存後トースト）は変えていない。**

**⇒ 開発者から製造へ、次の判断が求められている（本レポート提出時点で未決）。**

**★製造の所見**: **(B) を推す。** 論点 a は `VAL-S04` / `VAL-C02` の ERROR 契約に手を入れる話であり、論点 b は API の新設を含む。**どちらも「文面の是正」の粒度を超えており、本サブの射程外である。** ただし **(A) を選ぶ判断があれば従う。**

## §7 教訓（retrospective 行き）

**★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、**実施者は設計担当**（反映担当は 2026-08-11 に廃止）。

1. **★★文面は「設計の目的」ではなく「実装がしていること」から書く。** 本サブは指示書 §1.3 の目的（「作り直す**前に**告げる ⇒ 重複が減る」）を文面へ写したが、**実装は保存後に告げるトーストであり、その目的を構造上達成できなかった。** 結果、文面が実装のしないことを約束した。**⇒ 文面を書くときは「この文を読んだ利用者が次に取れる行動」を 1 つ挙げ、それが実装に在るかを確かめる。** 無ければ、文面か実装のどちらかが間違っている。**自動テストでは検出できない**——翻訳キー経由で正しく描画され、テストも lint も型検査も緑になる。
2. **★指示書の散文と表が食い違うことがある。着手前に突き合わせる。** 本サブは §4.2（散文）と §4.4（表）が `VAL-R03` の母集団で食い違っていたのに、**表だけを見て実装し、レビューで指摘されるまで気づかなかった。** **⇒ 実査項目に「同じ事項を 2 か所以上が書いていないか、書いていたら一致しているか」を入れる。** とくに**散文で範囲を広げ、表で列挙する**構造は食い違いやすい。
3. **★「器を広げる」変更は、その器を説明している全箇所を先に `grep` で数える。** 本サブは `warnings` を復元 2 経路 → 登録 2 経路へ広げたが、**「設定するのは復元経路だけ」と断言したコメントが 5 ファイルに残った**（レビュー高-1）。**⇒ 広げる前に「この器の制約を説明している箇所」を数え、その全数を直す前提で見積もる。**
4. **★E2E の fixture を流用するときは「その fixture で検証が走るか」を確かめる。** `m23-04` spec は仮登録（`isDraft: true`）でコンボを作るが、**本サブの 4 件は仮登録を判定しない。** そのまま流用すると**検証が 1 度も走らないまま緑になる。** 事前に気づいて本登録の経路を書き起こした。**⇒ 「テストが在る」と「テストが効く」は別**（`M23-04` 教訓 1 の別形）。
5. **★検査が緑でも欠落は実在する。** `check-progress-log-index.sh` は索引行が 0 行でも緑を返した（先行サブの本文に後続サブの ID 文字列が含まれるため）。**⇒ `check-artifact-integrity.sh` の注記「他の検査が緑でも、その緑が信用できるとは限らない」が実際に当たった。** 手順で担保すべきものを検査に委ねない。
6. **★flaky を「フレーク」で閉じない。** `make e2e` の flaky 2 件は、`--workers=1` で 22 passed・既定の並列で 3 failed と**再現条件が判っている競合**だった。**⇒ 再実行して緑になったら終わり、にしない。** 切り分けの最小手は「隔離実行」と「直列実行」の 2 手である。
