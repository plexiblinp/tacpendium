### §1-4 `combos.oki_verified` の意味論と backfill 規則

```sql
ALTER TABLE combos ADD COLUMN oki_verified INTEGER NOT NULL DEFAULT 0;
UPDATE combos SET oki_verified = 1
    WHERE EXISTS (SELECT 1 FROM combo_oki_options WHERE combo_id = combos.id);
```

| 状態 | 表現 |
|---|---|
| 未検証（まだ調べていない） | `oki_verified = 0` |
| **調べたが成立するものが無かった** | **`oki_verified = 1` かつ 行 0 件** |
| 調べた結果これらが成立する | `oki_verified = 1` かつ 行あり |

- **backfill は「行が 1 つでもあれば調べた」**（開発者確定）。チェックを付けたのなら明らかに調べているため。
- **★行が無いコンボは `DEFAULT 0` のまま＝未検証。** ここを逆にすると、調べていないコンボが「調べたが無かった」と主張することになり本サブの目的と逆になる（`TestRun_ComboOkiVerifiedBackfill` で固定）。
- **★移行で失われる情報は無い。** 現行スキーマに明示的な false がそもそも存在しないため、既存の「行なし」はすべて未検証へ落ちるのが正しい読みである。

### §1-5 「調べたか」の入力と表示

**入力**（編集画面）:

## 7. 教訓（★親は読まなくてよい）

**本節の宛先は `retrospective-log` へのバッチ反映であり、実施者は設計担当である。親チャットは §1〜§4 だけ読めばよい。**

1. **★★「N 状態にする」を受けたら、状態の数より先に *何に掛かるか* を確かめること。** 「2 状態を 3 状態に」を**セル**と読み、開発者は**節**を指していた。数が合っていても対象が違えば作り直しになる。**代償は波及の幅で出る**（読む面 6 か所 → 1 か所）。
2. **★★レビューもテストも、誤った前提の内側では全部緑になる。** fresh subagent の 17 件指摘も、Go/FE のテストも、E2E 全数も、**セル単位という前提の内側で整合していたため何も言わなかった**。**「正しく作れているか」は検査できるが、「正しいものを作っているか」は検査できない。⇒ 段 2 へ入る前に実物を触ってもらう手順が唯一の検出器だった。**
3. **★★マイグレの「番号据え置きの書き換え」が安全なのは、そのファイルをどの DB も適用していないときだけである。** `main` へ入っていないことは条件の半分にすぎない——**実機確認を依頼した先の DB は適用済みだった**。`golang-migrate` は**版数しか見ない**ため何も適用されず、**`no such column` が「重複判定の失敗」という無関係な顔で出た**。**⇒ 作り直すときは、依頼先の DB の巻き戻し手順を同時に出すこと。**
4. **★★表せる状態は、自明に見える組合せでも画面に出すこと。** 「行があれば検証済みは自明」と推論して省いた結果、**利用者が最も普通に踏む経路だけフラグが不可視**になった。**推論で削った表示は、その推論が破れる経路（本件は解除ガードと CSV 取込）ごと消える。**
5. **★「どの経路が主経路か」は実装で確かめること。メソッド名から推測すると外す。** 「編集画面の保存＝`PUT`」と書いたが、実装は識別キーが変わらない限り `PATCH` だった。**⇒ 必須化を守る経路が主経路に無かった。**
