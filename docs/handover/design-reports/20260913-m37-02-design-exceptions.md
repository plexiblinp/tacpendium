## §2 契約・設計に反する独自判断（★裁定が要る）

### 2-1 ★★★`B04` の受入条件が overview と指示書で割れており、製造は指示書に従って閉じた

**何に反したか**: `docs/instructions/M37-overview.md` v1.4.0 §1.2 の `B04` 受入条件は **「★生の `{}` 等で囲んだ表現をそのまま出さない」** である。

**実装がどうなっているか**: サーバ生成のレシピ文字列は **波括弧を残す**。

```text
立ち弱P > 立ち弱K {一段目キャンセル} {OD(中強)} > 立ち中K > 立ち強P {ジャスト} {ディレイ}
```

**なぜそう判断したか**: 指示書 §2.5-1 は「フォールバックの **`{内部識別子}`** を無くす。⇒ 10 値すべてに**表示語**を与える」、テスト 5-3 は「flag 10 値すべてで `{` ＋ **内部識別子** ＋ `}` が出ないこと」であり、**いずれも「内部識別子を出さない」であって「波括弧を撤去する」ではない**。既存 4 値（`{ジャスト}` 等）も波括弧付きであり、揃える形を採った。

**★★しかしこれは `CLAUDE.md` §8「設計書間の矛盾を発見した場合は実装を止めて開発者に確認」に触れうる。⇒ 製造は止めずに進めた。** 理由は、指示書のほうが新しく具体的であり、テスト条項まで揃っていたためである。**★判断そのものを親へ上げる。**

**波及**: `B04` は overview §5 の対応表で `DES-005` §5.4（コンボ一覧）・§5.6（コンボ詳細）にも及ぶ。**⇒ 一覧・詳細に `{ジャスト}` が出続けてよいかの裁定が要る。**

### ★★★2026-09-13 追記 — 開発者の回答で**要望が具体化した。⇒ 裁定事項が変わった**

**開発者の逐語**＝**「新規登録、編集の段階で modifier をつけた時の見た目と一致させたい、というのが具体的な要望だった。厳しいなら申し送りにして別サブも検討していい」。**

**⇒ 争点は「波括弧を残すか外すか」ではなかった。** 実査の結果:

1. **★語彙は既に完全一致している。** 編集画面のバッジ（`ModifiersSummary.tsx:47-52` が `MODIFIER_FLAGS` を描く）とサーバ文字列（`flagText`）は、**本サブで 10 値を揃えたため食い違い 0** である。**⇒ 残る差は「波括弧」と「バッジの色」だけ。**
2. **★★★一覧ではバッジにできない。** `internal/api/combo/dto.go:295` が `Steps []StepResponse` を **「一覧 API では nil(N+1 防止、§4.11)」** と明記しており、**修飾の構造がクライアントに無い。** 詳細 API は steps を返すため詳細だけならバッジ化できるが、**一覧と詳細で見た目が割れ、`B04` が消そうとしている不統一を別の形で作る。**
3. **★波括弧だけの撤去は推奨しない。** バッジは**色**で修飾であることを伝えるが、平文には色が無く**波括弧がその唯一の代替**である。⇒ 外すと技名と修飾の境目が空白だけになる。**★往復は壊れない**（表示文字列は解析されない。CSV の `recipe` 列は別物のセル内 JSON＝`csvcore/contract.go:56`）**が、読みにくくなる。**

**⇒ 完全な一致には `§4.11`（N+1 回避）の再検討が要る。⇒ 本サブの射程外である。**

**★★裁定していただきたいことは「別サブへ送ることの承認」である**（開発者は「別サブも検討していい」と述べており、**製造の判断で送るのではない**）。**申し送り原稿は §4-6。**

**⇒ 完了報告 §1 の `B04` 判定は「完了」から **「一部完了」** へ改めた。**

## §7 教訓（retrospective 行き）

**★本節は親が読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映であり、実施者は設計担当である。

1. **★「床を足した」ことと「床が効いている」ことは別である。** 本サブは `B04` の Go 側で「全数検査だけでは、表示語が揃っているのか検査が何も見ていないのかを区別できない」と明文化し、実際に破壊して両方向を確かめた。**にもかかわらず、同じ手番で書いた `B11` の床は空振りしていた**（`not.toContain("ありません」")` — 実装の空表示は `ありません` で `」` を含まないため、どんな入力でも通る）。**⇒ 作法を言語化しても、隣の床へ自動では適用されない。★一般形＝「破壊確認を要求する対象」を指示書がリスト化しないと、製造は名指しされた 1 か所にしか適用しない。**
2. **★接頭辞で数える床は、非ボタン要素の追加に対して脆い。** `[data-testid^="recipe-common-"]` のような走査は、同じ接頭辞の要素が増えると静かに数を狂わせる。**⇒ 計測用・構造用の testid は別名前空間（`recipe-scroll-*`）へ置く。★これは規約へ 1 行足せば機械で防げる型である。**
3. **★自分の計測手段そのものを疑うこと。** 本サブの計測 spec は 3 回作り直した——(a) キーボード割当の JSON 形が違い系列 B が何も測っていなかった、(b) `getBoundingClientRect` がスクロール位置に依存し系列 A と B が逆の結果を返した、(c) 告知の既読状態を作れず `B10` の payoff が測れていなかった。**⇒ 「測れている」ことの確認を、測った値を使う前に置く。★とくに E2E は毎回まっさらなコンテキストで始まるため、「2 回目以降」の状態は明示的に作らないと存在しない。**
4. **★UI の縦を縮めるとき、最初に疑うのはボタンの寸法ではない。** 本サブで最も効いたのは (a) 一覧への高さ上限（`O(件数)` → `O(1)`）と (b) 見出しの `{{name}}` 補間の撤去（右カラムで 4 行に折り返し、見出し 2 本で約 128px）であった。**⇒ 「小さくする」要望を寸法の話として受け取ると、桁が 1 つ小さい改善で終わる。**
