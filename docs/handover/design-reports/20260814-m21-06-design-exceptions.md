## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★いずれも「指示書に書かれていなかったので確定させた」ものである。** 指示書と異なる判断を下したものは §2 に分けてある。

### ★1-1 モーション用の読み取り経路＝**既存の解決表とは別ルートで、素通しの表を返す**（`§4.6` の as-built・**本サブ最重要の構造**）

**着手時の実査で停止条件 3 が発火した**——`move_commands` を読む経路が**存在しなかった**。既存の `command-index` は `^[1-9]?(LP|MP|HP|LK|MK|HK)$` で**多方向コマンドを全て落とす**ため使えない。**D-379 で「同フィルタは広げない・別経路を新設する」と裁定され、`§4.6` の 7 制約が与えられた。** **経路の中身は製造が確定した。**

| # | 確定した形 | 根拠 |
|---|---|---|
| 1 | **`GET /api/characters/:characterId/motion-commands`** を新設（`internal/api/inputresolve/routes.go`）。既存 `command-index` のハンドラ・DTO・畳み込みには**触れていない** | `§4.6-1` `§4.6-2` |
| 2 | **応答は `{characterId, commands:[{tokenKey, moveCode}]}` の配列**であって map ではない。**★同じ `token_key` を複数の技が持つ組が実在するため**、map にすると `§4.2-4`（同長複数なら解決しない）が**そもそも実装できなくなる** | 実データ |
| 3 | **service 層は素通し**（`MotionCommands()`。畳み込みも絞り込みもしない）。**既存 `CommandIndex()` は 1 行も変えていない** | `§4.6-4` |
| 4 | **`repository/movecommand` は 1 行も変えず既存 `ListByCharacter` を再利用** | `§4.6-4` |
| 5 | **解決規則は 1 つもバックエンドに置いていない**（前方一致・最長一致・同点判定はすべて `commandMotion.ts` の純関数） | `§4.6-5` |

- **対照テストを 2 本置いた**（service / handler の両層で「**多方向コマンドが `command-index` には載らないこと**」を固定）。**これが無いと、後から誰かが既存フィルタを広げても誰も気づかない。**
- ⇒ **`DES-002` §4.2 の API 一覧へ本経路を書いてほしい**（**`CHANGE-109` §2.1 追補が反映先に `DES-002` §4.2 を加えているのは、まさにこの経路のためである**）。**★「既存の解決表とは別ルートである」ことと、「配列であって map ではない理由」まで書いてほしい**——書かないと、次の担当が「重複だから畳もう」として `§4.2-4` を壊す。

### ★1-2 操作の種別を **4 値**へ増やし、モードの割当は **弱K**に置いた（`§4.1-2` の as-built）

**指示書は「4 つ目の操作を足す」としか書いておらず、どのボタンに置くかは製造判断だった。**

- **列挙は `web/src/features/gamepad/shortcut.ts` の 1 か所のみ**（`PhysicalInputActionKind` = `delete | save | modifier | command_mode`）。**キーボードは独自列挙を持たず同型を import しているため、1 行の変更が両側へ効いた**（`E-76` を構造で満たしている）。
- **Gamepad 側は「前置き ＋ 弱K」**。**弱K を選んだ理由＝削除（強K）から最も遠い**——**モードの出入りは頻繁に行う操作であり、隣に置くと誤爆時の損失が「ステップの削除」になる。**
- ⇒ **`DES-005` §6.5 の操作種別を 3 → 4 で書き換えてほしい。** **★「種別は Gamepad とキーボードで共有する（新しい列挙を作らない）」は `M21-05` §1-5 で申し送った内容であり、本サブでそれが実際に効いた実例である。**

### 1-3 台帳 `keyboard-bindings-v1` は **16 → 17 件**（`gamepad-profiles-v1` は **14 件のまま**）

**`web/CLAUDE.md` §1 の #9 を 17 件へ更新した**（`D-362` に基づき製造が直接編集）。

- **★このとき #8 は動かない。** Gamepad で増えたのは**前置きのあとに押す後続ボタン**であって、**登録する前置きボタンは 1 件のまま**だからである。⇒ **「操作が 1 つ増えたから両方 +1」ではない。** `M21-05` §1-4 が書いた「件数を釣られて直さない」が**実際に効いた場面**であり、脚注へその旨を明記した。
- ⇒ **`DES-005` §6.3.2 へ反映する際は、キーボード 17 件・Gamepad 14 件を併記し、差が出る理由（前置きの有無）も一緒に書いてほしい。**

### 1-4 モードの配送は **既存のステップ配送チャネルへ相乗り**させた（第 2 の配送系を作らない）

`PhysicalInputProvider` が **`MotionCandidate`** を既存のチャネルへ流し、`isMotionCandidate()` で受け手が判別する。**読取表示も既存 `GamepadRecipeReadout` の 5 区画目**として足した（第 2 の表示系を作らない）。

- ⇒ **DES への反映は不要と考える**（実装内部の配送形であり `DES-005` の粒度ではない）。**ただし「モード中の入力は判定層へ届かない」ことは `DES-005` §6.6 の記述に効く**ため申し送る。
