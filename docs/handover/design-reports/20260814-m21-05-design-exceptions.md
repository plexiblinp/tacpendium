## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

> **★いずれも「指示書に書かれていなかったので確定させた」ものである。** 指示書と異なる判断を下したものは §2 に分けてあるが、**本サブでは §2 は 0 件である。**

### ★1-1 供給元が 2 つになる形＝**合流させてから 1 つの判定へ渡す**（`§4.6-3` の答え・**本サブ最重要**）

**指示書 §4.6-3 は「受け手の調停は 1 つを共有したまま、供給元が 2 つになる形を採る」としか書いておらず、その形の中身は製造へ委ねられていた。** 実査の結果、**既存構造のままでは成立しないことが判明した**（`§3.3-8` の答え）。

**なぜ成立しないか**——判定層は **1 本の押下集合の差分**で立ち上がりを採る（`stepDetection.ts:399` の `rising = current \ state.held`）。⇒ **2 つの供給元が各自の押下集合を独立に push すると、片方の push がもう片方を「離した」と見せる。** 具体的には、**パッドで強K を押したままキーを 1 つ叩くと強K が押下集合から消え、次にパッド側のサンプルが来た瞬間に強K が「もう一度立ち上がった」ことになって、押していないステップが増える。**

**確定した形**（`web/src/features/keyboard/mergeNormalized.ts`・純粋関数）:

| # | 仕様 |
|---|---|
| 1 | **各源の最新の `NormalizeResult` を provider が ref で保持し、どちらかが変化したら合流結果を 1 回だけ判定へ push する**（`GamepadInputProvider.tsx` の `handleSources`） |
| 2 | **方向は合流後の上下左右から採り直す**（両源の digit を比べて選ぶのではない）。**パッドで `6`・キーボードで `2` を入れているとき、正しい答えは `3`（下前）であって「どちらかの digit」ではない**。⇒ **SOCD 規則と斜めの導出は `cardinalsToNumpad` の 1 か所のまま** |
| 3 | ボタン・`actions` は和集合。`resolved` はどちらかが true なら true |
| 4 | **切断時に Gamepad 側の ref を捨てる。** 捨てないと、切断時に押されていたボタンが合流に残り続け、**以後キーボードで入力するたびに幽霊の同時押しが混ざる** |

- 固定テスト: `mergeNormalized.test.ts` **15 件**（うち **恒等性 7 件**＝片側が中立なら元の結果と `toEqual`）／統合の「パッドを押したままキーを叩いても、パッド側が離されたことにならない」（**パッドのボタン ＋ キーボードの方向で `crouching_heavy_kick` が出ることを主張**＝両源が同時に効いていることの証明）。
- ⇒ **`DES-005` §6.4.3 項目 4 の「供給元はアプリ全体で 1 個であり、ポーリングも判定も 1 組だけ持つ」を書き分けてほしい。** **`CHANGE-110` §2-f の予告どおり**だが、**as-built は「供給元 2・受け手 1・判定 1・配送チャネル 1」であり、合流層が両者を橋渡ししている**。**★「1 個」が何にかかるのかを明示しないと、`M21-06` が 3 つ目の供給元を足すときに同じ実査をやり直すことになる。**

### ★1-2 判定層へ「正規化済みの結果」を渡す入口を開けた（`§2.3` の例外条項の使い方）

**指示書 §2.3 は「`§4.5` の接続に伴い、供給層の共通部分へ手を入れることを許容する」としか書いておらず、どこに何を開けるかは製造判断だった。**

**実査で判明した構造**——`useStepDetection` の公開 API は `onSample(snapshot, at)` しか無く、**内部で `normalizeSnapshot` をもう一度呼んでいた**（provider 側と合わせて **1 サンプルにつき 2 回**）。キーボードは `GamepadSnapshot` を持たないため、この入口には乗れない。

**確定した形**: `useStepDetection` へ **`pushResult(result: NormalizeResult, at: number)`** を足し、`onSample` はそれへ委譲する形へ整理した。

- **`stepDetection.ts`（判定の本体）は 1 行も変えていない**（`git diff` は docblock のみ＝§5）。判定窓の値・アルゴリズム・半開区間・方向の扱いはすべて不変。
- **副次的に、重複していた正規化が 1 回に畳まれた。**
- **★`onSample` は本番から呼ばれなくなった**（現在の呼出元は `useStepDetection.test.ts` だけ）。**残す判断をしたうえで、その旨と「消すならテストを `pushResult` ベースへ寄せてから」を godoc へ明記した**（レビュー高-2 の指摘を受けて是正）。
- ⇒ **DES への反映は不要と考える**（実装内部の入口であり、`DES-005` が持つ粒度ではない）。**ただし `M21-06` が同じ層に乗るため、本レポートで申し送る。**

### 1-3 登録導線は Gamepad と共有せず新設した（`§9.2-1` の委任に対する回答）

**理由は「重複を避けるより凍結を守るほうが優先」である。** Gamepad の `calibration.ts` は `GamepadProfile` / `PhysicalBinding{kind:"button"|"axis"}` に固く結びついており、キーボードを通すには `calibration.ts` / `profile.ts` / `types.ts` の一般化が要る。**それは `§2.2-5`「Gamepad 側の登録導線を書き換えない」（重大 16）に正面から触れる。**

- **⇒ 別に持つのは重複ではなく、凍結を守るための帰結である。** レビューもこれを重複とは見ていない（レビュー §2 の注記）。
- **保存先も分けた**（`keyboard-bindings-v1`）——`gamepad-profiles-v1` は `version:1` ＋ `browserKey::padId` 鍵で、`profile.ts:46` の `KNOWN_BUTTONS` サニタイザが**未知のキーを黙って捨てる**。相乗りすると「登録できたのに次回起動で消えている」形で壊れる。
- ⇒ **`DES-005` §6.3.2 は「登録対象」を Gamepad の 14 件で書いているが、キーボードは別導線・別保存で 16 件である。** **§1-4 とあわせて反映してほしい。**

### 1-4 登録対象は **16 件**（`§4.2-5` の as-built 確定）

| 区分 | 件数 | 内訳 |
|---|---|---|
| **必須** | **10** | 方向 4（上・下・左・右）＋ 攻撃 6（弱中強 P / 弱中強 K） |
| 任意（マクロ） | 3 | ドライブインパクト ／ ドライブパリィ ／ 投げ |
| **任意（操作）** | **3** | **削除 ／ 保存 ／ 修飾**（`§4.2-1` の直接割当） |

- **Gamepad の 14 件との差 +2 の理由**——**キーボードは前置きボタン 1 件を持たない代わりに、操作 3 件を直接持つ**（`-1 + 3 = +2`）。
- **★件数を釣られて直さないこと。** 14 と 16 は**別々の理由で決まっており、一方を動かしても他方は動かない**。台帳（`web/CLAUDE.md` §1）の #8 / #9 の脚注にも同じ注意を書いた。
- **斜めは登録しない**（Gamepad と同じ）。4 方向の同時状態から `cardinalsToNumpad` が導出する。
- ⇒ **`DES-005` §6.3.2 へ「キーボードは 16 件（必須 10 ＋ 任意 6）」を、Gamepad の 14 件と**併記**してほしい**（`CHANGE-110` §2-e が「as-built 次第」としていた箇所）。

### 1-5 操作用のキーは、保存の時点で技用と分けた（`§4.2-4` をより強い形で満たした）

**Gamepad は同一 Record（`GamepadProfile.buttons`）へ格納してから `normalizeSnapshot` が `actions` へ振り分ける形だが、キーボードは `KeyboardBindings.moves` / `.actions` の 2 つの Record に分けた。**

- ⇒ **`normalizeKeyboard` は `.actions` を参照すらしない**ため、**操作用のキーが押下集合へ混ざる経路が構造的に存在しない**。
- **操作の種別は `GamepadActionKind`（`shortcut.ts:27` の 3 値）をそのまま import している**（`§4.2-3`・重大 4 非該当）。**新しい列挙は作っていない。**
- ⇒ **`DES-005` §6.5 へ「キーボードは前置きを持たず、操作 3 種を直接割り当てる」を反映してほしい**（`CHANGE-110` §2-g の予告どおり）。**★種別そのものは Gamepad と共有していることも書いてほしい**——書かないと、次の担当が「キーボード用の操作列挙」を作りうる。

### 1-6 テキスト入力欄との衝突回避は **`:read-write` による性質判定**で解いた（`§4.4-2` の as-built）

**指示書 §4.4-2 は「要素の種類を列挙しない」とだけ定めており、判定手段は製造判断だった。**

`web/src/features/keyboard/editableFocus.ts` が `document.activeElement` に対して **`matches(":read-write")`（CSS Selectors Level 4 の「利用者が編集できる要素」擬似クラス）** と `isContentEditable` の **OR** を採る。

- **★着手時に jsdom（nwsapi）での挙動を実測してから順序を決めた**——text / number / textarea / contenteditable = 真、readonly / disabled / checkbox / button / ただの div = 偽。**同じ実測で `isContentEditable` が jsdom では `undefined` であることも判明**し、**それ単独に頼る形は採れなかった**（採っていれば、テストは通るのに本番でしか効かないガードになっていた）。
- **`keyup` はガードを通していない**——通すと、押下中にフォーカスがテキスト欄へ移ったときに解放イベントが捨てられ、**そのキーが恒久的に「押されたまま」になる**。
- ⇒ **`CHANGE-110` §2-h が「テキスト入力欄との衝突回避を書く」としている箇所へ、この判定方針（種類の列挙ではなく編集可能性で判定する）を含めてほしい。** **★`M21-06` も同じガードの下に入る。**

### ★1-7 既定動作の抑止は「利用者が割り当てたキーかどうか」だけで決める（**実機確認で確定した仕様**）

**指示書・`CHANGE-110` のいずれにも記述が無い。** **開発者の実機確認で「矢印キーを方向に割り当てるとブラウザがスクロールする」と報告され、是正の過程で確定した。**

| # | 仕様 |
|---|---|
| 1 | **利用者が登録したキーなら、リピートでも必ず `preventDefault()` する**（`useKeyboardInput.ts` の `handleKeyDown`）。**キー名を列挙しない**ため、矢印・Space・PageUp/Down・Home/End など**既定動作を持つ登録済みキーがまとめて塞がる** |
| 2 | **登録されていないキーには一切触らない。** 触ると、利用者が割り当てていない矢印キーでのスクロールやブラウザのショートカットまで殺す |
| 3 | **`keyup` でも抑止する**——ネイティブ `<button>` は **Space の活性化を keyup で行う**ため、keydown だけでは取りこぼす |
| 4 | **編集可能な要素にフォーカスがある間は抑止しない**（§1-6 のガードが先に効く）。⇒ **テキスト欄では従来どおり空白も矢印も使える** |

- ⇒ **`DES-005` へ「物理入力が担うキーの既定動作は抑止する。ただし抑止の対象は利用者が割り当てたキーに限る」を明文化してほしい。** **★これは「書かないと落ちる」種類の要件である**——実際に落ちた。**`M21-06`（方向キーの連続入力）は方向キーを更に多用するため、書かれていないと同じ壊れ方をする。**

> **★親は本節を読まなくてよい。** 宛先は `retrospective-log` へのバッチ反映で、**実施者は設計担当**（反映担当は 2026-08-11 に廃止）。

| # | 教訓 |
|---|---|
| 1 | **「テストが通ること」と「守れていること」は別である。** 本サブでは 3 つの形で出た——(a) 破壊確認で緑のまま（別の機構が守っていた・3 件）(b) `defaultPrevented` を見ていないテストがスクロール不具合を素通りさせた (c) E2E の「押しっぱなし」がイベントを 1 回しか飛ばしておらず、不具合を復元しても緑だった。**⇒ ガードを足したら「そのガードを外すと赤くなるか」を、そのガードと同じ層で必ず確かめる。** |
| 2 | **日本語の散文を否定文字クラス（`[^。]` 等）で走査するときは `LC_ALL=C.UTF-8` を付ける。** `LC_CTYPE=POSIX` ではバイト単位で解釈され、多バイト文字の構成バイトが衝突して**静かに 0 件を返す**。**「緑だが効いていない走査」は 3 度目で、毎回スコープの取り方が違う**（正規表現 → キーワードの言語 → **実行環境のロケール**）。**⇒ 走査は「回したこと」ではなく「当たることを確かめたこと」を証跡にする。** |
| 3 | **症状の説明は推論ではなく実測で書く。** 登録ダイアログのリピート不具合を「次々と別の対象へ割り当たる」と説明したが、実測では衝突検出が 2 件目で止めるため**実際に見えるのは確認ダイアログだけ**だった。**開発者から「イメージがついていない」と指摘を受けて初めて実物を確認した。** **★この差はテストの強さに直結した**——「暴走しないこと」だけを主張したテストはガードを外しても緑で、**「衝突が出ないこと」まで主張して初めて固定できた。** |
| 4 | **既定動作の抑止は「押し始めの 1 回」では足りない。** `preventDefault()` を early-return より後ろに置くと、**OS のキーリピートが素通りする**。**押しっぱなしが普通の使い方である入力（方向）では、実質ほぼ毎回漏れる。** **⇒ 「自分が担うイベントか」を先に決め、抑止はその直後に置く。** |
| 5 | **凍結された層の隣に新しい層を作るとき、「重複を避ける」より「凍結を守る」が優先することがある。** 既存の登録導線を一般化すれば重複は消えるが、それは凍結指定に正面から触れる。**⇒ 「別に持つのは重複ではなく凍結を守るための帰結である」と理由を明示すれば、レビューも重複とは見ない。** |
| 6 | **2 つの供給元を 1 つの判定へ入れるときは、差分を採る側の前提を先に確かめる。** 判定が「1 本の押下集合の差分」で立ち上がりを採る構造では、**各源が独立に push した瞬間に片方が「離された」ことになる。** **⇒ 供給側で合流させてから渡す。** |
