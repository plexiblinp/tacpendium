## 0. TL;DR

- 現行フローの残りの人手は大きく 4 種——①セッション間のリレー係、②セッション起動、③定期メンテの起動タイミング、④スマホからの判断回答。それぞれに対応する新機能が存在する。
- **早期採用（開発者決定済み・2 件）**: セッション間メッセージング（§4.1）と Git 権限見直し（§4.2）。
- **後回し（§7）**: Routines／PR Auto-fix／Workflow ツール／Artifacts 判断ページ／規律のフック昇格。
- **不採用（§8）**: Agent teams／ヘッドレス実行。いずれも本プロジェクトの統制思想（隔離・人間ゲート）と逆方向のため。
- 横断課題 2 件: 設計卓の交換規律の緩和（§5・開発者所見）とプロセス重量の定点観測（§6）。

## 1. 調査の方法

公式ドキュメントを対象にサブエージェント調査を実施し、「複数セッション・複数エージェントの人手リレーを減らす」観点で 2026-09 時点の機能を棚卸しした。その結果を、repo の運用正本 3 点（remote-ops／roles-and-routing／settings.json）と突合して、現行フローのどの人手に何が刺さるかをマッピングした。

**変えない前提**: main への正史化は人間マージのみ（remote-ops §1-1）、実装系 PR の手動 E2E ゲート（§1-2）、設計卓の武装、計画提示→開発者応答の往復（§1-3）。以下の提案はすべてこの統制を崩さない範囲で選んでいる。

## 3. 自律化レベルの現在地（評価）

開発者の問い「他の個人・企業と比べてどうか。5 ヶ月目として良いか悪いか」への回答を記録する。

- **個人比**: 上位数%。典型的個人利用は単一セッション＋その場のプロンプトで、役割分離すらない。本プロジェクトの「sparse-checkout による物理的コンテキスト隔離」「検査を検査する検査」「台帳による課題の寿命管理」「AI の規律違反を実測→フック・検査へ昇格させるループ」は上級実践例でも稀。
- **企業比**: 強弱が分かれる。プロセスの自己修復・指示書駆動・隔離設計では多くの企業より先行。一方、AI 先進チームが持つ 3 点——(a) イベント駆動（webhook→エージェント起動、人間のリレー不介在）、(b) エージェントプロセス自体の回帰テスト（eval）、(c) サーバ側 CI ゲート＋条件付き自動化——は未導入で、ここが差分。本書の採用候補は主に (a) を埋めるもの。
- **5 ヶ月目として**: 良い。ただし §6 の懸念（プロセス重量）を併記する。

## 4. 早期採用の 2 件（開発者決定・2026-09-09）

### 4.1 セッション間メッセージング

**機能**: v2.1.224+ で導入。セッション同士が名前で宛先指定してプレーンテキストを直接送り合える（`@セッション名` 指定、`/list-agents` で到達可能一覧）。同一マシン内はローカル IPC（上限約 100 万字）、マシン跨ぎは Anthropic サーバー経由。

**削減される人手**:

1. 「宛先: 設計担当」質問の開発者リレー（roles-and-routing 共通原則 2 のリレー係が不要になる）。
2. design_handover_report の還流リレー。**注意**: レポートは repo に着地するが、設計卓は fetch が deny のため未マージ分を読めない。**メッセージ本文にレポート全文を載せる形なら「マージ待ち→リレー」が丸ごと消える**（同一マシン上限 100 万字。マシン跨ぎの上限は要実測）。
3. 完了通知（「製造が終わった」を人間が伝える手番）。

**できないこと**: 新規セッションの起動には使えない（既存セッション宛のみ）。起動の自動化は `claude --cloud`・Web UI・モバイルアプリ・Routines トリガーの領分。

**既知の制約**:

- クラウドセッションは受信できるが、**受信側から送り返す経路が未整備**（一方向）。まずは「製造→設計卓への通知＋内容は repo／メッセージ本文」の片方向運用から。
- 受信側は `crossSessionInbound` 設定で hold／refuse 可能。受信セッションの permission プロンプトは通常どおり発火する。

**★次の担当への調査依頼（開発者指示）**: 新しい機能のため、**不具合・既知バグの報告が出ていないかを導入前に外部調査すること**（`/ask_external_ai` で Perplexity 調査プロンプトを作る型が既存）。あわせてクラウド↔クラウドの送受信可否・マシン跨ぎのメッセージ上限を実測し、remote-ops §8 の V 項目（V-8 相当）として記録するのがよい。

### 4.2 Git 権限見直し

**背景（deny の由来）**: 現 deny 列（fetch／pull／checkout 等）は devContainer 前提（2026-06）で書かれた。そこでは Claude が開発者の作業コピーを共有するため、fetch／pull／checkout は「開発者の手元状態を勝手に動かす」操作だった。クラウドセッションは自分専用のクローンを持つため、この前提は半分失効している。

**直近の実害**: 開発者がコンフリクト解消コミットを claude/ ブランチへ push すると、当該ブランチに紐づくクラウドセッションが pull できず（deny）、リモート更新を取り込めないまま動けなくなる。

**提案（3 段階・開発者裁定案件）**:

| # | 操作 | 現状 | 提案 | 理由 |
|---|---|---|---|---|
| 1 | `git fetch origin` | deny | **解禁（ただし設計卓の武装中は引き続き拒否）** | 履歴追記すらしない純読み取り（remote-tracking ref の更新のみ）。CLAUDE.md §10 の目的のどれにも触れない。武装中除外は §5 の交換規律との干渉回避 |
| 2 | `git pull --ff-only origin claude/<自ブランチ>` | deny | **単一形のみ許可** | 実害への直接解。開発者の解消 push はセッションの push 済みコミットの子孫なので fast-forward で取り込める。ff-only はマージコミットを作らず、分岐していれば安全に失敗するだけ |
| 3 | `git merge origin/main`（自 claude/ ブランチへの取り込みのみ） | deny | オプション（第 2 段。まず #1・#2 で様子見） | §10 の実体は「正史 main への反映は人間」であり、作業ブランチへの main 取り込みは正史化ではない。コンフリクト解消を解消用 AI に任せる現運用とも整合。ただし統制変更として一段大きい |

**実装方式の推奨**: allow 行のプレフィックス一致ではなく、**pre-push-guard と同じ「単一形のみ通すフック」型**で入れる。理由は 2 つ——(a) クラウドでは ask が実質機能しない実測（remote-ops V-2）があり、allow に足すことはクラウドで無条件に通ることを意味する。(b) プレフィックス一致は refspec 形の取りこぼし（V-2 で実測済みの穴）を防げない。

**据え置き（理由が現役のもの）**: reset／rebase／checkout／switch／restore／clean（破壊・履歴改変）、config（フック迂回・committer 偽装の経路）、clone（スコープ外リポジトリ）、tag、stash（作業状態が見えなくなる害が利便を上回る）。

**波及**: 採用時は `.claude/settings.json`・CLAUDE.md §7／§10・remote-ops §6 の改訂と `/sync_codex_config` の実行が必要。

## 5. 設計卓の交換規律の緩和（開発者所見・2026-09-09）

開発者所見を記録する: **devContainer 上での作業もまだあること、ボード等の仕組みにより同じ卓を長期使用しても壊れなくなったことから、設計卓の交換規律はかなり緩められそう**。

本書からの補足 2 点:

1. **fetch 解禁（§4.2 #1）と交換規律は連動している。** remote-ops §6.1／§6.2 トリガ 1 は「fetch が deny のため、新しい情報を取り込む唯一の方法が畳んで起動し直すこと」を交換の強制力として使っている。fetch を解禁するなら、「サブ完了時に必ず畳む」既定を緩めて「観測可能な劣化の合図（§6.2 の 4 点）＋ `/context` 実測」を主軸に移す改訂とセットで行うのが整合的。**緩めてよいのは「同期点で必ず畳む」の側であり、「劣化は自覚できない」原則と合図ベースの交換は残すこと。**
2. V-7（設計卓の `/context` 消費実測）が未計測のまま。閾値ベースへ移すならこの実測が先。

## 6. プロセス重量の定点観測（開発者要求により記録）

本プロセス機構は企業級の重さがあり、ソロ OSS としては「機能 1 つあたりのメタ作業（docs の docs、検査の検査）のコスト」が利益を食い始めるリスクがある。CLAUDE.md の TEMPLATE NOTE が示すとおりプロセス自体を流用可能な資産として育てる意図があるなら投資として合理的だが、**重さが利益を上回った時点を検出する仕組みだけは持っておく**。

**提案（軽量な定点観測）**:

- 四半期に 1 回程度、直近マイルストーンから 1〜2 サブをサンプリングし、「製品コード・テストに使ったトークン ： プロセス（検査・docs・棚卸・レビュー往復）に使ったトークン」の比を概算して progress-log に記録する。
- 比率の絶対値より**傾向**を見る。あわせて次の兆候が出たら黄信号として扱う: (a) 新機能 1 つの実装で触るメタファイル数が増加傾向、(b) 検査スクリプトの増加率が機能の増加率を上回る、(c) 改善レーンの対象が「プロセスのプロセス」ばかりになる。

## 7. 後回しにしたもの（理由付き）

> **共通注意**: いずれも「今の判断」であり、機能アップデート・フェーズ移行で前提が変わりうる（§9）。

### 7.1 Routines（クラウド定期実行: schedule／API／GitHub trigger）

- **何か**: Anthropic ホストで PC 不要のセッション自動起動。schedule trigger（cron 式・最小 1 時間）、API trigger（HTTP POST＋bearer token。スマホのショートカットからも撃てる）、GitHub trigger（Claude GitHub App が webhook を受け、PR オープン・ラベル・リリース等に反応。author／タイトル／ラベル／ブランチ／draft／merged でフィルタ）。実行は非対話（permission プロンプトなし）だが、pre-push-guard 等のフックはコミット配布のため効く。
- **後回しの理由（開発者判断・2026-09-09）**: (a) 非対話実行のため「計画提示→開発者応答」（remote-ops §1-3）が物理的に成立しない。(b) 現在は問題の数が多く、寝ている間に一括で「治って」しまうと検収できない。(c) 曖昧な指示で走った場合、誤方向へ進んだトークンを止める人間がいない。
- **再検討の条件**: 問題が減って「検出だけ自動化したい」状態になったら、**「検出のみ・修正しない Routine」**（read-only 検査→レポート 1 本）から入る。誤解釈のコストがレポート 1 本分で収まる。

### 7.2 PR Auto-fix（CI 失敗・レビューコメントへの自動対応）

- **何か**: PR をウォッチし、CI 失敗やレビューコメント到着時に自動でセッションが起きて修正 push する。Claude GitHub App 必須。
- **後回しの理由**: 本プロジェクトは `mcp__*` 一括 deny＋`gh api`／`gh pr merge` deny（多層防御の MCP 層）であり、導入には「読み取り・コメント系のみ許可し merge 系 deny は維持する」統制改訂が前提になる。§6 多層防御の改訂は開発者裁定案件で、早期採用 2 件より優先度が下。
- **再検討の条件**: PC 電源 OFF 運用を本格化するとき最も効く候補。§4.2 の権限見直しが安定してから。

### 7.3 Workflow ツール（決定的マルチエージェントオーケストレーション）

- **何か**: JavaScript スクリプトで複数サブエージェントを決定的に並列実行（レビュー指摘ごとの検証エージェント自動起動、失敗地点からの resume 等）。
- **後回しの理由**: 現行のクリーンルームレビュー→トリアージは implement_plan_full で既に回っており、固定化の利益が今は小さい。導入するならレビューのファンアウト部の再現性向上が用途。

### 7.4 Artifacts による判断回答ページ（スマホ往復の軽量化）

- **何か**: 判断待ちリストや design-report を公開ページ化し、スマホでコメント→セッションがコメントで起きて処理。
- **後回しの理由**: 現行の GitHub モバイル＋クラウドセッション直対話で回っており、導入コストに対する削減幅が早期採用 2 件より小さい。

### 7.5 規律のフック昇格（次点候補・後回しの中では最有力）

- **何か**: 「docs/progress/ へ書いたら当該ファイルに check-md-emphasis を自動発火」「完了報告作成後に check-progress-log-index を発火」等、お願いベース規律（D-775 型）を PostToolUse フックで機械強制へ昇格する。
- **後回しの理由**: 早期採用 2 件と違い実害が今出ていない（検査体系が防御している）。ただし低リスク・低コストで、次の改善レーンの束に入れる価値がある。

## 8. 不採用にしたもの（理由付き）

### 8.1 Agent teams

- **何か**: experimental（環境変数で opt-in）。リードセッション＋複数 teammate の構成で、各 teammate は独立コンテキストウィンドウを持つフルの Claude Code インスタンス。共有タスクリスト（claim／complete）、teammate 間ダイレクトメッセージ、split-pane 表示。サブエージェントとの違いは寿命と対等性（teammate は長生きし相互に会話、ユーザーも直接介入可）。
- **不採用の理由**: 本プロジェクトの芯は隔離（武装・クリーンルーム・worktree 分離）であり、teams は共有状態へ向かう設計で思想が逆。加えてローカル限定・同一作業ディレクトリ共有・experimental で挙動変化が速い。
- **状況が変わる条件**: クラウド対応と安定化が進み、かつ「隔離を保ったままタスクリストだけ共有する」使い方が可能になった場合は再評価余地がある。

### 8.2 ヘッドレス実行（`claude -p` ／ `--bare` ／ Agent SDK）

- **何か**: CLI 層は 1 ターン非対話実行（構造化出力・スキーマ強制・permission mode 指定・多ターン継続）。`--bare` は CLAUDE.md・hooks・skills・MCP を一切読まない決定的モード。SDK 層（Python／TypeScript）はエージェントループ自体を自プログラムへ埋め込み、permission 判定もコードで自前実装する。
- **不採用の理由**: 本プロジェクトの統制はまさに CLAUDE.md＋hooks に載っており、`--bare` はそれを丸ごと外すスイッチ。人間ゲートなし前提の道具であり、Plan 往復規律と根本的に相容れない。
- **状況が変わる条件**: 将来 research_plan 系（read-only 厳守・事実列挙のみ）だけをヘッドレス化する場合に限り適用余地がある。

## 10. 設計卓への畳み込み候補（board／backlog の種）

5. 規律のフック昇格（§7.5）→ 次の改善レーン束の候補。
