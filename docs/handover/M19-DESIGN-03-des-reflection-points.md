## 1. DES-002（API 設計）への反映要点 — M19 が主

- §4.2 に提案エンドポイントの追加（見込み形）: `GET /api/combos/:id/setplay-suggestions?n_min=1&sort=n|steps`。入力はコンボの `knockdown_advantage`（NULL なら 400 系）、出力は SuggestionDTO 配列（M19-DESIGN-02 §7）。**副作用なし（非永続）**。採択・保存は既存 `setups`/`combo_setups` 系 API を再利用し**新規保存 API は設けない**。
- エンジン統合方式（`internal/service/setplay` への stdlib-only 移植）を DES-001 側と整合させる場合はその旨 1 行（NFR303/304 維持）。

## 2. DES-005（画面設計）への反映要点 — M19 が主

- §5.6 項目 11（単一コンボ候補面／`SetupSelectorModal`）: 提案リストの相乗り。各行＝展開後レシピ・**N（持続何 F 目ヒット）併記**・派生技注記（親＞子表記であることの表示）。N_min コントロール（既定 1）とソート切替（N 順／手数順）。`selectedIds` は入口にしない（既定事項の再掲）。
- **面の交差**: E-1（M23）統合先・M18-03 マイリスト導線と同一面のため、レイアウト確定は中央経由調整・E-14 突合ゲートを M19-01 DoD に予約（M19-overview §5 の再掲。新規の決定ではない）。

## 3. DES-003（データモデル）への反映要点 — 中央預かり分（要件参照のみ）

- §3.4 `knockdown_advantage` の意味論明確化（無敵ダウン時間・起き上がり＝KA+1）＝**中央預かり済み**（記録のみ・重複起票しない）。
- §3.3 moves の派生技フレームモデル（basis 判別＋親参照＋計上規約の明文化）＝**中央（moves 系）が設計・起票**。M19 からの入力は M19-DESIGN-01（利用側要件 R1〜R7＋申し送り事実）。本書からは重複記載しない。
- エンジン API 変更（Target.Active・NMin・TotalFrames 意味変更）は別リポ内の変更であり DES 対象外だが、`internal/` 移植時に DES-001/DES-002 の記述対象になる（M19-01 で確定）。

## 4. DES-004（表記正典）への反映要点 — 中央預かり分（要件参照のみ）

- 汎用の親＞子派生技表記規定（現行は rush と `_lv` 接尾のみ＝RESEARCH-02 R-E-1）と、表記展開規則「親がコマンド表の別行の技なら親ステップを前置」＝中央の設計対象。M19 の消費形は M19-DESIGN-02 §3。
