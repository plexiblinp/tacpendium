## 0. 本書の使い方

本書は **マイルストーン固有** の引き継ぎ資料。プロジェクト恒久の運用ルール・開発スタイルは `design-instruction-playbook.md` を参照すること。

新セッションで読む順序:

1. **`design-instruction-playbook.md`**(プロジェクト恒久) — 開発スタイル全般を理解
2. **本書(m2-to-m3-handover.md)** — M2 完了状態と M3 着手の現在地を把握
3. **設計書本体**(REQ-001、DES-001〜006、SUPP-001) — M3 着手時に必要な節を view ツールで確認

## 3. 継続して使う運用ルール

playbook が恒久資料なので詳細はそちらを参照。M3 着手時に **特に意識すべき** ものを抜粋:

### 3.1 開発スタイル(playbook §1, §2)

- 設計担当 Claude(本書を読む人) / 製造担当 Claude Code / レビュー担当 Claude Code / 開発者 の4役割分担
- 指示書テンプレート §1〜§10 の標準節構成

### 3.2 禁則表現除去(playbook §4)

- 指示書・チェックリストで以下を使わない: 「あれば」「必要に応じて」「実装時に決定」「任意で」「適切に」「既に〜していれば不要」「動作するはず」
- セルフチェック必須: `grep -n 'あれば\|必要に応じて\|...' {file}`

### 3.3 設計書節への行レベル参照(playbook §5)

- DTO・構造体・SQL 定義に対応する設計書節(DES-X §X.Y、行レベル)を併記
- セルフチェック: `grep -nc 'DES-001\|...' {file}` で参照回数確認

### 3.4 モデル配分(playbook §7)

- 行数ではなく「関心の絡み合い」で判断
- レビューモデルは実装と同じか1段下(SUPP-001 §6.1)
- M3 着手時に各サブマイルストーンのモデル配分を model-allocation.md に追記

### 3.5 Plan Mode 必須化基準(playbook §8)

- 複数機能の関心が絡む / 既存ロジック再利用が中心 / 設計判断が条件付き / バックエンド追加変更ありの場合は必須
- 任意の場合は §3.4 着手前確認を簡略化可

### 3.6 並列実行不採用方針(playbook §15)

- M2 から完全直列、M3 でも継続
- 同時稼働ターミナル数3本(Web版1 + 製造1 + レビュー1)を超えない

## 5. M2 期間の反省点と M3 で意識すべき事項

### 5.1 指示書設計時の確認不足(M2-02 / M2-04 で発生)

**事象**:

- M2-02: `UpdateMetadataInput.IsDraft *bool` 拡張を §2.4 例外条項に書き忘れ → 製造担当の質問で発覚
- M2-02: `DuplicateInfo.label` の生成形式を曖昧記述 → 製造担当・レビュー担当の認識ずれで発覚
- M2-04: 「コンボ一覧のルート列でも notes が見える」と書いた副次効果が成立しない前提を見落とし → 開発者の E2E テストで発覚(§6 課題7)

**原因分析**:

- 指示書設計時に既存実装(M1-03 / M1-05)の細部確認が不足
- 「副次効果」のような曖昧記述で確認不足を補ってしまった

**M3 で意識すべき対策**:

- 指示書 §2.4 例外条項を**先回りで検討する**(フロントだけで完結するか?を必ず自問する)
- 「副次効果として〜」「自動的に〜される」という表現を使う前に、その前提が成立するかを view ツールで確認する
- 既存 API のレスポンス DTO(json タグ含む)を確認する習慣を持つ
- 複雑なフィールド構造(label のような文字列フォーマット)は、「フォーマット例」だけでなく「構造化フィールド vs 単一文字列のどちらか」を §2.4 / §4 で明確にする

### 5.2 retro R-01 の継続的注意

設計書本体との行レベル照合を怠ると指示書ミスが発生する。M2-04 で起きた「コンボ一覧ハイフン問題」は、`model.Combo` の `json:"-"` タグを確認していれば防げた。

**対策**: 指示書作成時に「副次効果」を主張する前に、その経路を確認する習慣。

### 5.3 Q&A 対応で開発者の認知負荷を抑える(M2-02 で実例)

製造担当からの質問 Q1/Q2 に対応する際、回答を冗長にしない・選択肢を多すぎる形で並べないことが重要。

**M2-02 で実践した形**(M3 でも継続):

- 結論を最初に明示(「案 X を承認」)
- 推奨理由を簡潔に
- コピペ用テキストを別途提示(message_compose_v1 ツール活用)
- 指示書修正は並行して設計担当が実施

### 5.4 スコープ拡大の判断軸

M2-04 で「Sonnet 4.6 → Opus 4.6 に格上げ」したのは適切な判断だった(連絡事項3件追加でスコープが M2-02 同程度に膨らんだため)。M3 でも同様にスコープが当初想定を超えた場合、**指示書のサイズではなく関心の絡み合いで判断** する(playbook §7)。

## 6. 持ち越し課題(M3 以降に対応)

M2 期間で記録された持ち越し課題7件の詳細。playbook §11.3 のクローズ記録方針に従って progress-log.md にも記録済み。

| # | 課題 | 出処 | 対応マイルストーン | 内容 |
|---|------|------|----------------|------|
| 1 | useCharacters フック実装時の差し替え | M2-02 連絡事項1 | **M3** | DuplicateRealtimeWarning.tsx の `CHARACTER_NAMES` 定数マップを useCharacters フック呼び出しに差し替え。現状はリュウ1キャラ固定なので問題ないが、複数キャラ対応時に必須 |
| 2 | 重複警告リンクの新規タブ開き | M2-02 連絡事項2 | **M7** | DuplicateRealtimeWarning の「既存コンボの詳細を見る」リンクに `target="_blank" rel="noreferrer"` 追加。レビューで「軽微」分類済み |
| 3 | useCheckDuplicate の setIsLoading タイミング | M2-02 連絡事項3 | **M7** | デバウンスタイマー発火前に `setIsLoading(true)` が呼ばれる実装。現状 UI 影響なしだが、将来ローディング表示追加時に修正必要 |
| 4 | console.warn テスト追加 | M2-01 連絡事項2 | **M3 以降の任意** | useControllerInput の moves not found 時の console.warn のエッジケーステストが未追加。レビューで「品質向上」扱い |
| 5 | PutConfirmDialog ESC キーハンドラ追加 | M2-04 持ち越し(M2-02 起源) | **M3 以降** | ESC キーでキャンセル動作させるハンドラが未実装。M2-02 の設計時に欠落、M2-04 範囲外として持ち越し |
| 6 | PutConfirmDialog `role="dialog"` 位置移動 | M2-04 持ち越し(M2-02 起源) | **M3 以降** | `role="dialog"` がモーダル外側でなく内側の要素に付いている構造的問題。M2-02 の設計時に欠落、M2-04 範囲外として持ち越し |
| 7 | コンボ一覧のルート列ハイフン問題(レシピ表示) | M2-04 完了時に判明 | **M3 以降の独立検討事項** | ComboTableRow.tsx で `recipePreview = "-"` 固定。原因は (a) 一覧 API が steps をロードしない(N+1 防止)、(b) `recipe_cache` が `json:"-"` で API 開示されていない、(c) プリセット依存。recipe_cache の API 開示は別マイルストーンの設計判断 |

### 6.1 M3 スコープへの組み込み判断

課題1(useCharacters フック差し替え)は M3 で複数キャラ対応開始時に確実に対応する。**M3 のスコープに含める**。

課題4(console.warn テスト追加)は M3 で扱うか、後続マイルストーンに送るか開発者判断。M3 のスコープに含める場合は M3 サブマイルストーンの「統合・仕上げ」相当に組み込む。

課題7(コンボ一覧のルート列ハイフン問題)は **新たな設計判断** が必要(recipe_cache の API 開示方針)。M3 着手時に開発者と相談して、独立サブマイルストーンとするか、M4 以降に送るかを決める。

### 6.2 M7 持ち越しの記録

課題2、3 は M7(仕上げ)で対応。M7 着手時の指示書に組み込む。

### 6.3 M3 以降に持ち越す課題の記録

課題5、6(PutConfirmDialog の構造的問題)は M3 以降で扱う。M3 のスコープに余裕がある場合はサブマイルストーンに組み込む。難しい場合は M4 以降に送る。
