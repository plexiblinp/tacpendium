## 3. M1 期間で確定した主要設計判断

### 3.1 データモデル

- **Combo は集約モデル**: `Combo.Steps []ComboStep`、`db:"-"` でリポジトリ層が組み立てる(N+1 防止策あり、M1-03 §4.11)
- **Modifiers は型付き struct**: `{Flags []string, Type string, Notes string}`(SUPP-001 §3.3.0)
- **recipe_cache は combos.recipe_cache カラム(JSON)**: 別テーブルではない(DES-003 §3.4)
- **recipe_hash は on-the-fly 計算**: DB に保存しない(SUPP-001 §2.2、M1-03 §4.3.1)
- **counter_type → hit_type にリネーム**: ガード破壊系コンボ拡張のため(CHANGE-006)
- **presets.code カラム追加**: DES-004 のプリセットコード(`official_ja_move` 等)を機械可読キーとして格納(CHANGE-007)
- **combos.name カラムは存在しない**: コンボ識別はキャラ + レシピ + 状況、ニックネーム用途は memo で代用

### 3.2 バリデーション

- **VAL-C / VAL-D の分離**: 本登録時 VAL-C01〜C12、仮登録時 VAL-D01〜D03 のみ(DES-006 §2.1 / §2.2)
- **VAL-C02 重複判定の対象**: `is_draft=false AND deleted_at IS NULL` の本登録コンボのみ(仮登録は対象外)

### 3.3 技術スタック確定

- **Go バージョン**: 1.26.2
- **パッケージマネージャ**: pnpm 9.13(npm/yarn 禁止、`pnpm dlx` 使用)
- **shadcn/ui**: M1 では未導入(標準HTML + Tailwind で代替)、M2 以降で統一導入を協議
- **zod**: M1-06 で導入済み(フォームバリデーション用)
- **React Hook Form**: 未導入(useState で十分)

## 4. M1 期間で確立した運用ルール

### 4.1 並列実行(段階的並列、2並列×2段階)

`parallel-execution-guide.md` を参照。M2 以降も同パターンで運用する。

- 直列群(基盤を作るマイルストーン序盤)
- 並列群(独立性高いタスク)
- ペアリング: バックエンド系 + 独立小規模 → 同種(両方フロント等)の順
- git worktree 推奨

### 4.2 指示書テンプレート

各 M1 指示書を参考にする。標準構成:

1. メタ情報・更新履歴
2. 背景と目的
3. 成果物(作成ファイル、修正ファイル、変更しないもの、例外条項)
4. 前提条件(必読・任意参照・参照不要)
5. 詳細仕様(本文)
6. テスト要件
7. レビュー観点(別ファイルへ分離)
8. 完了条件(Definition of Done)
9. 参照ドキュメント
10. 注意事項・判断に迷ったら
11. 完了後の次ステップ

### 4.3 機械レビュー

- レビューチェックリストは別ファイル(`docs/instructions/reviews/M{N}-{NN}-review-checklist.md`)
- レビューモデルは実装と同じか1段下(`model-allocation.md` で管理)
- 製造担当の指示書必読範囲を最小化(レビュー観点を含めない)

### 4.4 CHANGE 通知書

設計書本体の変更が必要な場合に起票する。M1 期間で起票したのは:

- CHANGE-006(counter_type → hit_type リネーム)
- CHANGE-007(presets.code カラム追加)

通知書フォーマットは `change-report-006-counter-to-hit-type.md` または `change-report-007-presets-code-column.md` を参照。

### 4.5 製造担当との Q&A

製造担当(Claude Code)が Plan Mode で質問してきた場合、以下のフローで対応:

1. 質問内容を評価(設計書・SUPP-001 を参照)
2. 開発者に判断を仰ぐ(複数案提示、推奨を明示)
3. 開発者の判断を踏まえて回答案をコピペ用で作成
4. 必要に応じて指示書を修正・バージョンアップ

## 6. M1 期間の反省点(M2 で改善すべき事項)

### 6.1 指示書記述の曖昧さによる実装漏れ

- 「M1-04 で recipe_cache を ComboResponse に展開」「notes 表示」等、責任所在が曖昧な記述で実装漏れ発生
- **改善策**: 指示書で「どのコンポーネント / どのファイルで実装するか」を明示する。「実装時に決定」のような曖昧表現を避ける

### 6.2 設計書本体との照合不足

- M1-02 製造担当のレビューで `moves.name_ja`、`presets.name_ja`、`(preset_id, alias_text)` インデックス等、DES-003 にない要素を指示書に書いていたミスが発覚
- **改善策**: 指示書作成時、対応する設計書節を明示し、DDL や型定義はそこから引用する形にする

### 6.3 並列実装の依存関係の見落とし

- M1-06 で `/api/moves` エンドポイントが必要なのに、事前に M1-04 等で実装されていなかった
- **改善策**: フロント指示書を作成する際、必要な API が揃っているか逆算チェックする手順を入れる

これらは M2 指示書作成時に意識する。
