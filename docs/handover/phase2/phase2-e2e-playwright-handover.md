## 2. たたき台（前セッションで作成、開発者へ提示済み）

### 開発者の疑問 6 点（本件で答えるべき問い）

1. フェーズ3 からにしてた理由は何か？
2. 導入により省略できる部分と、開発者が確認すべき部分は何か？
3. 開発者による手動 E2E の頻度はどうするか？
4. Playwright 実装も Claude に任せられるか？
5. Playwright の実装・修正コストは？
6. Playwright をいまから導入するのはコスパが良いか？

### 現時点のたたき台回答

- **(1) 理由**: 上記 §1。決定は §4.5 に記録、踏み込んだ理由は薄い（MVP優先の一般方針の一部と推定）。
- **(2) 自動化 / 手動の分担**: 自動化向き = ブラウザ上の反復フロー回帰（コンボ登録・編集・削除・一覧フィルタ・比較・タグ・セットプレイ紐付け等、リファクタで壊れやすい既存フロー）。手動に残る = 視覚・レイアウト・レスポンシブ判断、LAN 実機、操作感の主観 UX、格ゲードメインの正しさ（データ・記法の妥当性）、新機能の初回探索。
- **(3) 手動頻度**: 自動スイートが毎変更で回帰を捕捉 → 手動は (a) 新機能初回 + (b) 見た目/UX + (c) 定期 LAN 実機 に絞れる。全シナリオ手動の頻度を大幅減。
- **(4) Claude 委任**: 可能。Playwright spec は TS コード = 製造担当 Claude Code の領域。既存 `m*-e2e-scenarios.md` が spec 変換の素地。設計担当が指示書 → 製造担当が実装の既存フローに乗る。注意 = Claude は実機/LAN を走らせられない、`data-testid` 付与の小リファクタが要る場合あり、パス確認は開発者か簡易ランナー。
- **(5) コスト**: 初期 = 導入 + 設定 + test-id 規約 + ローカル実行スクリプト（1サブユニット規模・一回限り）。記述 = シナリオ→spec 変換（フロー数比例・有界）。保守 = E2E は最も壊れやすいが、大規模 UI 改修（shadcn/ui統一・Header共通化）は M7 完了済みで以降は加算的寄り → churn は小さい見込み。保守も Claude Code 委任可で開発者負担は限定的。
- **(6) コスパ**: **フェーズ2 前倒しはコスパ良の見込み**。賛成 = 手動 E2E が既に実コスト（ボトルネック）/ M8〜M12 各々に統合 E2E があり償却が効く / 先行リリース（知人配布）で回帰安全が要る / 大規模 UI churn は終了 / Claude Code が実装・保守 / 既存シナリオが素地。慎重 = フェーズ2 も UI 変更は残る（キャラ複数化・custom_states UI）/ 小規模個人アプリで手動でも足りる論 / 初期構築が機能作業と競合 / LAN 実機は自動化しきれない。
- **結論（たたき台）**: フルスイート一括ではなく「基盤 + 高価値・安定フローのスモーク/回帰」から**段階導入**。手動 E2E を新機能 + 見た目 + LAN 実機に寄せる。タイミングは **M8（スキーマ確定）後〜M9 前後に基盤**を入れると、以降 M9〜M12 が自動回帰の恩恵を受け償却が最大化。

## 3. 推奨する進め方（既存パターン準拠）

1. **M-RESEARCH（調査担当運用パターンの5例目、architecture-patterns §6）**: 現行フロー棚卸し + `data-testid` 準備状況 + Playwright 適合 + 既存シナリオ→spec 変換の工数見積り。事実列挙のみ（判断・提案を含めない RESEARCH 運用）。→ §2 (5)/(6) のコストとコスパを実数化。
   - 指示書命名例: `M{N}-RESEARCH-{NN}-e2e-playwright-feasibility-check.md`。推奨モデル Sonnet クラス。
2. RESEARCH 結果を見て **採否判断**（開発者）。
3. 採用なら **DES-002 §12 / SUPP-001 §4.5 の「フェーズ3以降」前倒しを CHANGE で改訂**（DES-002 = 設計書本体 = CHANGE 通知書必須、次回採番は registry の最新を確認。本書作成時点で 024）。SUPP-001 §4.5 は補足資料で自由改訂だが、DES-002 と整合させる。
4. **基盤導入サブユニットの指示書**（Playwright 導入 + 設定 + test-id 規約 + 高価値フローのスモーク/回帰）を起票 → Claude Code で実装。
5. phase2-overview へ E2E 基盤サブユニットを位置づけ（M8 後〜M9 前後を推奨）。model-allocation へモデル配分追記。
