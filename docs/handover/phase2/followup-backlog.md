## A. 製造工程の独自判断の設計確認（申し送り §1）

| # | 製造判断 | 設計確認 |

### B-1【最重要】official_ja_move / ラッシュ命名 / name 編集クラスタ（申し送り §2-1・§2-6d）

- **必要作業**: (a) 組み込み official_ja_move（DES-004 §2.1 read-only）の **data-admin 編集可否の整理**（設計判断 + DES-004 CHANGE 見込み）、(b) **ラッシュ版命名自動生成ルール**（`DR>` 前置等＝DES-003 §3.3 L291）、(c) FR703 通常投げ命名補正。(a)(b)(c) は一体設計が望ましい。
- **優先/依存**: 高（最も目立つ UX 課題）。DES-004 の read-only 方針の再整理が前提。
- **想定**: 専用の後続マイルストーン（命名/プリセット系。M9-04 候補 or フェーズ3 プリセット作業）。

### B-2 編集グリッドの操作機能拡張（申し送り §2-5・§2-6 a/e/f）
- **内容**: (a) 行追加（新規 move 手動登録、`POST /api/moves`）／(b) 行削除（`DELETE /api/moves/:id`）／(c) 行コピー（雛形複製）／(d) 一括ラッシュ版生成／(e) 表示順並び替え（クライアント表示のみ）／rush 済みボタン非活性化（§2-6a）／rush 生成タイミング 2 段階化（§2-6e）／新規行のみ code・category 編集可（§2-6f）。
- **必要作業（重要な設計判断）**: (a)(b) は **DES-003 §616「moves 等マスタは論理削除を用いず公式データ更新時に上書き管理」との整合**が前提＝「手動追加 move と取込上書きの共存（取込で消えない/衝突しない）」「行削除と combo_steps 参照 FK・論理削除採用要否」の**データモデル設計判断**。新規エンドポイント（POST/DELETE）＝CHANGE。(d) は反復 or バルク API の二択。(e) は UI 完結（最軽量、DES 未記載の要望として記録）。
- **優先/依存**: 中。(a)(b)(c)(f) はデータモデル判断クラスタ。(d)(e) と rush ボタン非活性は独立の小～中。
- **想定**: M9-04 候補（FR703 拡張）。rush ボタン非活性化（§2-6a）と (e) 表示順は軽量で先行可能。

### B-3 フレーム自動算出【開発者課題】（申し送り §2-6 b/c）
- **内容**: (b) ラッシュ版は通常版から全フレームが変化＝**変換計算式の特定が必要**（現状は元技コピー + 手動補正）。式が確定すれば生成時に自動算出（B-1(b) 命名と合わせてラッシュ版生成ロジック本設計）。(c) ジャンプ技フレームは**決定可能**＝算出・補完方法を検討（要確認 total NULL の自動解消にも寄与）。
- **必要作業**: **開発者によるドメイン調査（計算式特定）が前提**。式確定後に設計・実装。
- **優先/依存**: 中（B-3b は B-1b と連動）。開発者課題が解けるまでブロック。

### B-4 要確認シグナルの永続化／再導出（申し送り §1-2＝A-2）
- **内容**: 取込済 moves は WarningCode を持たず、編集グリッドは total NULL のみを要確認シグナルに使用。FR703 完全化には全要確認種別を出したい。
- **必要作業**: (案1) WarningCode を moves に永続化（raw_data に warnings 等＝スキーマ/契約変更・CHANGE）／(案2) **編集時に move データから再導出**（unknown_properties・extra_throw 等を計算。スキーマ不変・単一情報源＝推奨）。
- **優先/依存**: 中（FR703 の完成度に効く）。B-2 の編集グリッド改修と同時が効率的。
- **想定**: M9-04 候補（B-2 と同梱）。

### B-5 取込の複数 CSV / フォルダ一括（M9-02 領域。申し送り §2-7）
- **内容**: 取込本体は行ベースで複数キャラ混在 CSV を扱える（バグでない＝確認済み）が、FR701 ツールが 1 キャラ 1 ファイル出力のため UI は 1 ファイルずつ。複数選択（`multiple`）/ フォルダ指定（`webkitdirectory`）一括取込の要望。
- **必要作業**: preview/commit は単一ファイル前提＝「ファイルごとに順次ループ（既存 API 流用）」or「複数ファイル受領 API 新設」の判断。レポートはファイル単位＋行単位の二層、途中失敗の継続方針（行単位 tx と整合）。
- **優先/依存**: 低（必須でない UX 改善。dist 一括投入・全キャラ更新時に効く）。CHANGE 対象。
- **想定**: 後続（M9-02 系 UX。優先低）。

### B-6 検証強度の穴（低。申し送り §2-2）
- **内容**: 現 PATCH 対象に NOT NULL/FK 列がほぼ無く DB 制約違反経路が無い。将来 FK/NOT NULL 列を PATCH 対象に加える際、サービス層で 400 マッピングが必要（現状は raw error → 500）。
- **必要作業**: 将来の編集対象拡張時のガード（設計時の注意事項）。
- **優先/依存**: 低（予防的）。B-2 で編集対象を増やす際に併せて対応。
