## 1. 【要確認・本体取込に直結】combo_scaling の JSON キー名の突合

- **事象**: ツールは公式の補正ラベルを JSON キーへ写像して CSV の `combo_scaling` 列に出力する。現在の写像は `始動補正→initial` / `コンボ補正→combo` / `即時補正→immediate` / `乗算補正→multiplicative`(TOOL-002 §9.5、実装 internal/normalize/scaling.go)。
- **問題**: このキー名は設計提案値であり、**本体 DES-003 §3.3 の moves.combo_scaling が実際に使う JSON キー文字列との突合が未完了**(ツール側の参照資料に実キー文字列が無い)。本体 FR704 はこのキー前提で補正値を解釈するため、不一致だと補正値が読めない。
- **依頼**: 本体 M9-02 着手前に DES-003 §3.3 の実 JSON キー名を確認し、ツール写像と一致するかを判定されたい。不一致ならツール側写像を本体定義へ追従する(ツールは冪等のため再生成は安価)。**本ツールで最も本体連携リスクが高い点**。
- ブロッカーではない: M9-01(ツール製造)のクローズは妨げない。M9-02 取込前の確定で足りる。

## 2. notes の3層書式の契約共有

- **事象**: ツールは moves.notes を3層構造で出力する(TOOL-002 §9.8、実装 internal/normalize/normalize.go)。
  1. 原文ブロック: 公式備考の複数項目を `;`(スペースなし)連結。
  2. 境界: `【ツール付記】`。
  3. 付記ブロック: ツール付与タグ(`ヒット時ダウン(D)`、`公式名: 背負い投げ` 等)を `; `(スペースあり)連結。
- **依頼**: 本体 FR704 が notes を構造解析する場合、この書式を契約として共有されたい。推奨パースは `【ツール付記】` での2分割(ブロック境界優先)で、前半=原文・後半=付記。これなら原文に `;` が含まれても破綻しない。
- **残リスク**: 原文区切り(`;`)と付記区切り(`; `)はスペース有無で区別するが、原文自体が `; `(スペースあり)を含むと境界が曖昧になり得る。本体の notes 取扱い方針(原文ブロックを再分割するか・表示要件)と整合確認されたい。

## 3. 【認識共有】フレーバー判定の母集団

- フレーバー判定の不変条件 1,041 件(除去 568 + 89 / 保持 384)は、**スコープフィルタ前の全マージ行**(共通システムのパリィ・ステップ等の取込対象外行を含む)が母集団。2相正規化(Names=全行で判定 → scope filter → Values=取込行のみ)の帰結。
- 将来、本体側または検証者が「フレーバー全件」を**取込行のみ**で数え直すと母集団がずれて 1,041 に一致しない。検証時は必ずスコープ除外前の全マージ行を母集団とすること(TOOL-002 §9.1 に明記済み)。
