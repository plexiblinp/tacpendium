## 0. このドキュメントの位置づけ

本書は **整理工程担当 Claude(本書作成者) → フェーズ2「先行リリース準備」キックオフ担当 Claude への引き継ぎ文書**。

時系列は フェーズ1(M0〜M7)完了 → 整理工程(ドキュメント整理 + 本セッションのスケジュール再設定・フェーズ番号再設定)→ **フェーズ2 着手** の順。キックオフ担当の最初の仕事は **M8 以降のマイルストーン分割を策定する(フェーズ2-overview ドラフト)** こと。コンテキストに余力がある場合は、そのまま序盤マイルストーン(M8 = moves スキーマ見直し見込み)に着手してよい。

> マイルストーン番号は **M8 以降の連番を継続**(開発者方針 2026-06-07)。フェーズ番号(フェーズ1〜4)とマイルストーン番号(M0〜)は別軸。

- **整理工程で確立した追従原則**: フェーズ番号は **item 単位**で対応付ける(blanket 置換は危険)。**歴史記録は据え置き + 冒頭注記**(retrospective-log / cleanup-report / judgment / 過去 CHANGE 通知書)。**私的表現は中立化**(「先行リリース」「近しい関係者」を使う)。
- **禁則表現 grep 規約**: `あれば|必要に応じて|実装時に決定|任意で|適切に|既に〜していれば不要|あったら|動作するはず|副次効果として|自動的に` を設計担当作成文書すべてでセルフチェック。
- **ターミナル 3 本 + 完全直列**: 設計担当(本セッション)/ 製造担当 Claude Code / レビュー担当 Claude Code。調査担当は一時起動可(レビュー兼用不可)。
- **モデル運用**: 関心数 1 + 単純 → Sonnet、2〜3 + 既存パターン → Sonnet 推奨(安全側で Opus)、3 以上 + 新規/複雑統合 → Opus。コンテキスト圧迫 × Sonnet × マイルストーン後半の三重要因に注意。

- **役割境界**: 設計担当 = 設計書本体 + 補足資料 + 指示書作成 + handover まで。製造 / レビュー = Claude Code。開発者 = 実機 E2E / リポジトリ反映 / 最終承認。

## 8. フェーズ2 の特殊事情(キックオフ担当への参考情報)

- **フェーズ2 = 先行リリース準備**。フェーズ1(MVP・リュウ単独完成)から、複数キャラ + 正式 moves データ + custom_states 機能へ広げる、本プロジェクトで初めて「外部の目」が入るフェーズ。
- **moves スキーマ見直しがゲート**(順1 / M8): 取込ツール・CSV 取込・登録 UI がすべて依存。最初に固める。
- **複数キャラ初投入**: フェーズ1 は登録系がリュウ固定。A-1 / A-2(M11)で他キャラ登録 UI を解禁。閲覧系は既に複数キャラ動的化済み。
- **custom_states 初実装**(M12): 3 状態形の設計が要る。フェーズ1 では保存 + API のみ。
- **CHANGE 番号の消費**: フェーズ2 は moves スキーマ + custom_states で少なくとも 2 件の CHANGE 見込み。次回採番は **022**。
- **検証データ**: フェーズ1 完了時に `scripts/clear-validation-data.sql` で全クリア済み。ただし migration 000012 が耐久 seed 36 件を再投入する点に注意(A-3 / M14)。
- **配布形態**: 単一バイナリ + LAN 共有。先行リリースは近しい関係者向け(私的表現は資料上中立化済み)。LAN 利用は inbound FW 許可が前提、サードパーティ AV が Windows FW を代替制御する既知制約あり(architecture-patterns §10)。
