## 1. 確定事項（指示書へそのまま落とせるもの）

1. **エンジン窓化＝受理帯方式**。受理条件 `0 ≤ remaining ≤ Active − NMin`・`Suggestion` に N 返却・`Target.Active` / `Options.NMin` 追加・`ErrInvalidTargetActive` 新設・`NMin > Active` は空結果。`TotalFrames` の意味が S に変わる（破壊的・テスト改修対象）。移植先は `internal/service/setplay`（stdlib-only）。詳細 M19-DESIGN-02 §1。
2. **golden-case は 5/5 見込みで確定**。GC-2 期待レシピは「立ち弱P＞奮迅脚＞紫電カカト落とし」へ**開発者承認済み訂正（2026-07-23）**＝S=42・N=3。golden-case 台帳の現物訂正と、本実装 DoD「N_min=1 で 5/5 実測」を指示書に入れる。
3. **計上規則**: S = Σfiller.total + target.startup（through は通し値）。through 直前の親ステップは計上ゼロ。親 total は派生時に不使用（単独使用時のみ）。
4. **表記展開**: エンジン解→表示/保存時にグルーが親ステップを挿入（親がコマンド表別行の技の場合のみ）。`setup_steps` は展開後の順で 1 ステップ 1 move・modifiers 特記なし。手入力の親なし子は警告（非ブロッキング）。
5. **N_min**: リクエスト単位・既定 1。将来は `max(リクエスト, 技属性)` 合成で非破壊拡張。
6. **ランキング**: N 降順 → 手数昇順 → total/Name 昇順。並べ替えはグルー。UI にソート切替。
7. **DTO・保存写像**: M19-DESIGN-02 §7 の SuggestionDTO（steps に role/counted）。保存は既存 setups+setup_steps+combo_setups 再利用・新テーブルなし・生提案は非永続。setups.name 自動生成（VAL-S06 充足・編集可）。
8. **UI**: SetupSelectorModal 相乗り・N 併記・N_min/ソートコントロール・selectedIds 非入口・E-14 突合ゲートを DoD 予約・面の確定は中央経由。

## 2. M19 本実装の分割提案（M19-01／M19-02・フラット連番）

派生技モデルの起票は中央の直列リソースであり、待ち時間が生じ得る。**非依存部分の先行**を提案する（枝番でなくフラット連番＝overview 規約準拠。サブ数変化は開発者リレーで中央へ連絡＝M19-overview の中央条件。overview §3 の表更新は指示書担当のメンテ範囲）:

- **M19-01（先行可・中央非依存）**: エンジン移植＋窓化＋テスト改修、提案 API 口、グルーの非派生部分（target 列挙は standalone×単独技のみ＋明示指定モード）、UI 相乗り（N 表示・N_min）。golden-case は GC-1/3/4/5 の 4 件で DoD。
- **M19-02（中央スキーマ反映後）**: basis 判別・親参照の消費（through target 解禁・表記展開・R6 警告）、GC-2 を加えた 5/5 DoD、E-14 突合ゲート。

一体で進める判断も可（中央起票が速い場合）。判断材料として工数の重心は M19-01：M19-02 ≒ 7：3 の見込み。

## 3. 未決事項（指示書の「開発者確認」候補）

1. セーフジャンプ定数のデータ形（並行 MS のジャンプ/ダッシュフレーム整備待ち・開発者と打ち合わせ）。第 2 受理規則の設計予約は M19-DESIGN-02 §9。
2. `setup_only` の付与運用開始（filler 絞り込みフィルタとして活用開始・0 件時は全技 graceful）。
3. standalone×単独入力不可技（パターン 3/5/6・状態変種）の target 化は将来拡張（MVP 除外）。
4. 空振り時硬直変動技の filler 精度は既知割り切り（MVP 非対応を DoD に明記）。
5. VAL-S04（レシピ一致）が作成経路でブロックか警告かの現物確認（DES-006 §6・中央配布版で。alreadyAdopted 表示＝M19-DESIGN-02 §7 の前提確認・v1.0.1）。
6. B 型 air-only 技の人手除外マーキングの持ち方、rush_variant の basis（いずれも開発者・v1.0.1）。

## 4. 経緯の要点（指示書の背景節用・3 行）

二重計上（GC-2）の真因は「データ欠陥」ではなく、通し値規約（親入力起点・親は最速キャンセルで total 不消費）を消費側が知らず親 total を加算したこと。規約は開発者確認で確定し（通し値＝パターン 1/2/4×条件 C/D）、GC-2 は期待レシピ訂正で窓方式に整合（S=42・N=3）。残る構造課題（basis 判別・親参照）は中央帰属で、M19 は利用側要件（M19-DESIGN-01）を提出済み。
