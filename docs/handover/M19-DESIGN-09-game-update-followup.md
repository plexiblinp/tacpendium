## 1. 割り込み判断 — **B′（分割 B）を採る**

### 1.1 なぜ A（即時割り込み）を採らないか

**現行タスク（Phase 2）は `startup_basis` の人手付与であり、判断の対象は「値の由来」であって「値」ではない。**

- `startup` が 12 → 11 に変わっても、その値が**単独値なのか通し値なのか**は変わらない
- ラッシュ版の通し値（連絡 §3-2 の 5 技）は `category = 'rush_variant'` であり、**Phase 2 の抽出条件が除外している**（ボード D-188）
- **記入済みの 45 行は 1 行も無駄にならない**

**⇒ Phase 2 を止める理由が無い。**

### 1.2 なぜ C（リリース前にまとめて）を採らないか

**連絡 §6-1 が自ら挙げているとおり、`on_block` が −4 の境界を跨いだ技が 5 件ある。** これは**確定反撃の候補集合を動かす**——契約 **F-1** の canary（`37 / 39 / 16`）が動く。

**★M19-05 も候補集合を動かす**（P-16 の緩和で +4 行、TP-01 の除外で −3 行）。`M19-DESIGN-08` §4 が「候補集合を動かす変更を 1 回にまとめる」と裁定したのと**同じ構造の問題**である——**2 つが近接すると、canary の判定値が 2 回動き、2 回目の変更が 1 回目の影響と混ざって切り分けられなくなる。**

C は「リリース直前に大量の値更新」であり、**M19-05 との間隔が最も短くなる形**である。**逆に最も切り分けにくい。**

### 1.3 ★ただし B をそのまま採ると 1 つ損をする

**B の「現行タスク完了後」を M19 全体と読むと、`startup_basis` が付与済みであることの恩恵を捨てることになる。**

連絡 §4-2 が自ら書いている——

> `startup_basis='through'`（通し値）で格納されている行は、両方が効いて合計で動きます。`standalone` の行は発生の変更ぶんだけ動きます。

**これは「実測の前に `startup_basis` を引く」ことを前提にしている。** そして **Phase 2 が終わっていなければ、引く先が `unknown` である**（308 行が未付与）。

**⇒ Phase 2 は update の前に終わっているべきである。** これは順序の制約であり、**B の中でも Phase 2 を優先する理由になる。**

### 2.2 設計判断 — **列も表も足さない。注記の「軸」を書き換える**

**現行の `DES-003` §3.3 の注記は「移動 system move は `total` 直接保持で、算出式の検算対象外」という形になっている。**

**★これは軸が誤っている。** 正しい軸は「**移動かどうか**」ではなく「**`active` が定義できるかどうか**」である。

| 技の性質 | `active` | `total` の持ち方 |
|---|---|---|
| 攻撃判定を持つ | 定義できる | `total = startup + active − 1 + recovery` で検算できる |
| **移動 system move** | **定義できない** | **`total` 直接保持** |
| **攻撃判定を持たない特殊技**（OD ランヴェルセ・フェイント等） | **定義できない** | **`total` 直接保持** |

**⇒ 注記を「移動 system move」から「`active` が定義できない技（移動 system move ／ 攻撃判定を持たない特殊技）」へ広げる。**

> **★これは playbook §4.21 (1)〔原則は画面名・ファイル名でなく**性質**で書き、既存全ケースに当てて検算する〕の適用である。** **「移動 system move」はカテゴリ名であり、性質ではない。** 性質で書き直せば、今回のような「移動ではないが `active` が無い技」が現れても、注記を足さずに済む。

### 2.3 やること

1. **実査**——現行 seed での格納形 ＋ 同型の全数（`active IS NULL` かつ `total IS NOT NULL` の行の全数と内訳）
2. **`DES-003` §3.3 の注記を性質ベースへ書き換える** → **CHANGE 起票が要る**
3. **★実査で「同型がゼロ件」だったら、注記の書き換えは行わない。** 現物に 1 件しか無いなら、それは注記ではなく行ごとの記録で足りる

## 4. §4-3 — 連打キャンセルの猶予変更と `chain_cancel_total`

### 4.1 ★開発者の指摘が正しい。陰性記録を残す

> 「測ったが変わらなかった」を残さないと、次のアップデートで同じ疑いをゼロから持ち直すことになります。

**これは本プロジェクトが既に 2 回踏んでいる形の第 3 の形である。**

| # | 形 | 決着 |
|---|---|---|
| 1 | **`chain_cancel_total` の NULL に「圏外だから NULL」と「未実測だから NULL」の 2 種類がある** | ボード **D-137／D-143**——機械条件では区別できない。区別できるのは確定ロースターだけ |
| 2 | **`startup_basis` の `unknown` に「未判断」と「判断して確定」の 2 種類がある** | ボード **D-138**——`保留` と `unknown` を書き分ける |
| **3** | **「測っていない」と「測って不変を確認した」が区別できない** | **★本件。同じ根である** |

**根は 1 つ——「値が同じでも意味が違うものを、同じ表現に寄せている」。**

### 4.2 やること

**`character_data/chain-cancel-measurements.md`（値の正本）に「再実測ログ」の節を設ける。**

記録する内容:

| 項目 | 内容 |
|---|---|
| 実測日 | 2026-08-XX |
| ゲームバージョン | **★アップデート後のバージョン番号** |
| 対象 | kimberly の小技 3 種および各連打キャンセル版 |
| 契機 | 2026-08-04 アップデート（連打キャンセル猶予の拡大） |
| 結果 | **不変を確認**（または新値） |
| 判定の根拠 | `chain_cancel_total` は**最速時**の実消費であり、猶予の拡大は最速時の値に効かない——**という推論は成立するが、規則で埋めてはならない列なので実測した** |

> **★「規則で埋めてはならない列」だからこそ、陰性記録の価値が高い。** 推論では埋められない列は、**実測しない限り誰も「変わっていない」と言えない**。記録が無ければ次回も同じ実測が要る。**記録があれば「前回のバージョンでは不変だった」から始められる。**

ボード **D-206** で「TP-02 の対象行の全数は M19-05 の Plan Mode で実査する」と裁定した。**その結果も同じ資料に記録する。**

## 7. §6-2 — `combo_setup_results` の検証日時

### 7.1 判断 — **正式リリース前に入れる。ただし update 波には混ぜない**

**開発者の指摘が正しい。** 今回は「その時が来た」ことの実例である。

### 7.2 なぜ update 波に混ぜないか

**連絡 §7 の想定は「スキーマ変更は不要と見込む」である。** そこにスキーマ変更を 1 本混ぜると、**波の完了条件が「値が合っている」から「値が合っている ∧ スキーマが正しい」へ膨らむ。**

**⇒ 別波にする。** ALTER 1 本・NULL 可なので、値とは完全に独立に進められる。

### 7.3 列追加審査（`M19-DESIGN-07` §7）を通す

| 審査項目 | 判定 |

| **事実列に第 2・第 3 の用途を載せていないか** | **✓ 新設列であり、既存列に用途を追加しない** |

| **恒久依存を作らないか** | **✓ NULL 可。読まなければ既存挙動は不変** |
| **既にある列で導出できないか** | **✓ 導出できない。** 検証がいつ行われたかは、どの既存列からも復元できない |

### 7.4 ★ただし列を足すだけでは目的を達成しない

**`verified_at` を足しても、「いつゲームが更新されたか」を持っていなければ陳腐化は判定できない。**

## 8. §7 の「DB を作り直す」選択肢について

### 8.1 ★これは作業を減らさない

開発者が挙げている選択肢だが、**減るのは「元々不要な作業」だけである。**

| 作業 | 「DB を作り直す」で減るか |
|---|---|
| `character_data/*.csv` の更新 | **★減らない。** 直さないと次の再 seed で誤りが復活する |
| golden の再生成 | **★減らない。** 直さないと CI が落ちる |
| UPDATE マイグレを書く | **減る**（既存 seed マイグレを直接編集すれば） |
| ユーザーデータの救済 | 減る——**★が、§0-3 により元々不要** |

**⇒ 実質的に減るのは「UPDATE マイグレ 1 本」だけである。** その代わりに次を負う。

### 8.2 ★既存 seed マイグレを直接編集すると、最悪の乖離が生まれる

- **適用済みの連番は再実行されない。** 編集しても**開発者自身の DB には届かない**
- **CI は clean DB から流すので通る**
- **⇒「CI は green だが、手元の DB は古い」** という、**最も検出しにくい形の乖離**になる

**これは `followup-backlog` の `csv-edit-vs-golden-divergence` が指している構造そのものであり、開発者の §7 の記述が正しく捉えている。**

**⇒ 既存マイグレは編集しない。UPDATE マイグレを積む。** 開発者の §7 の想定どおりで正しい。

### 8.3 ★ただし `csv-edit-vs-golden-divergence` は今回、全面的に発火する

**17 本の CSV × 約 57 項目 ＋ golden ＋ UPDATE マイグレの三点を同期させる作業**である。**followup が「登録済み」のまま、決着していない。**

**⇒ update 波の指示書で決着させる。** M19 のスコープ外だが、**update 波の前提**である。M19-04c で得た知見（改名 UPDATE の `NOT EXISTS` ガード／是正列が golden に載るか載らないかで UPDATE を当てる位置が変わる／件数ガードには測った版を併記）は、**`SUPP-001` §5.5 へ昇格させてから指示書に引く**（連絡 §7 末尾の要望に応える形）。
