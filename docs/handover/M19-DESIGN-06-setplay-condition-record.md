## 1. 何を解決するか

提案機能は**フレーム計算のみ**で候補を導出しており、**間合いを一切モデル化していない**。実際に成立するかは、**相手の受け身種別（その場／後ろ）**と、**コンボ終了時に相手が画面端にいるか**で変わる。

したがってユーザーが実機検証した結果を**登録済みセットプレイに記録し、後から絞り込める**ようにする。**提案ロジックはこれを消費しない**（提案は距離を判定しないため、記録は絞り込みと表示にのみ使う）。

**確定した要件**（開発者回答 2026-07-26）:

| 論点 | 確定 |
|---|---|
| 帰属先 | **コンボ × セットプレイの組ごと**。同一 KA でも距離等で変わり得るため |
| 端の扱い | **独立軸**。`combos.position` は**コンボ開始位置**であり、セットプレイに効くのは**コンボ終了時**の位置。ただし**コンボほど詳しい区分は不要で、「端にいるか」の真偽のみ** |
| 記録する状態 | **未検証／成立／不成立**の三値。攻撃種別（シミー・投げ重ね）の軸は**不要**＝記録するのは「**セットプレイの最後の重ねが成立するか否か**」の 1 軸 |
| 理由の記録 | **最初から持たせる**（`note`） |

## 2. データモデル（確定案）

### 2.1 新テーブル 1 本

```
combo_setup_results（セットプレイ成立条件の検証結果）

| カラム     | 型       | 制約                    | 説明 |
|-----------|----------|-------------------------|------|
| combo_id  | INTEGER  | NOT NULL                | コンボID |
| setup_id  | INTEGER  | NOT NULL                | セットプレイID |
| tech_type | TEXT     | NOT NULL                | 相手の受け身（'neutral_tech' / 'back_tech'） |
| in_corner | BOOLEAN  | NOT NULL                | コンボ終了時に相手が画面端にいるか |
| result    | TEXT     | NOT NULL                | 検証結果（'ok' / 'ng'） |
| note      | TEXT     | NULL可                  | 不成立の理由・補足 |

主キー：(combo_id, setup_id, tech_type, in_corner)
外部キー：(combo_id, setup_id) → combo_setups(combo_id, setup_id) ON DELETE CASCADE
```

**1 組あたり最大 4 行**（受け身 2 × 端 2）。

### 2.2 なぜこの形か

**(a) 三値を「行の有無 × `result`」で表現する。**
行が無い＝未検証／`ok`＝成立／`ng`＝不成立。**NULL に意味を持たせない**。`BOOLEAN NULL` で三値を表すと「NULL は未検証か、それとも入力漏れか」が読めなくなる。

**(b) 軸を列名に焼き込まない。**
`combo_setups` に列を足す案では `result_neutral_mid` / `result_neutral_corner` / `result_back_mid` / `result_back_corner` の**4 列**になり、**軸が 1 つ増えるたびに列が倍増**する。行方式なら軸は列 1 本で済み、将来「相手の体格」等を足したくなっても壊れない。

**(c) `combo_setups` を純粋な関連テーブルのまま保つ。**
現在 `combo_setups` は PK `(combo_id, setup_id)` のみの関連テーブル。ここに属性を持たせると関連が実体に変質し、意味論が濁る。

**(d) 既存の先例に乗る。**
`combo_oki_options`（CHANGE-063／M16-03）が「条件の組み合わせごとに 1 行」という同型の構造を既に持つ。**新しい流儀を発明しない**。ただし本テーブルは**攻撃種別と DR の軸を持たない**（開発者確定＝セットプレイに攻撃種別は不要）ため、`combo_oki_options` より**軸が少なく単純**である。

### 2.3 各列の判断根拠

| 列 | 判断 |
|---|---|
| `tech_type` | 値は **`combo_oki_options` の既存値域を再利用**（`neutral_tech` / `back_tech`）。**第 3 の語彙を作らない**。表示ラベルも `web/src/constants/oki.ts` の `OKI_TECH_TYPE_LABELS` を単一正典として再利用（DES-005 §5.6 項目6 で正典化済み） |
| `in_corner` | **真偽のみ**（開発者確定）。`combos.position` の値域（`corner_self` / `mid_screen` / `corner_opponent` / `corner_opponent_near`）を**流用しない**——position はコンボ**開始**位置であり、意味が違う。**混同を避けるため別の語彙にする** |
| `result` | `BOOLEAN` ではなく **TEXT のコード値**。DES-003 の既存流儀（`position`・`opponent_stance`・`hit_type` が文字列コード値）に合わせ、将来 `unstable`（安定しない）等を足す余地を残す |
| `note` | **最初から持たせる**（開発者確定）。不成立を記録する動機は「次に同じ検証を繰り返さないため」であり、**「なぜ駄目だったか」が最も価値が高い** |
| ~~`updated_at`~~ | **持たない**（開発者判断 2026-07-26）。バランス調整パッチへの対応をどう扱うかは**後続フェーズの範囲**であり、今それを前提にした列を先回りして置かない。**必要になった時点で ALTER 1 本**で足せる（NULL 可で追加すれば既存行を壊さない） |
| PK / FK | **複合 FK で `combo_setups` を参照**し、紐付けが存在しない行が生まれないことを保証する。**`ON DELETE CASCADE`**（紐付け解除時に検証結果も消える）。※ `combo_setups` の削除が物理削除であることを実装時に実査で確認する（コンボ本体は論理削除だが、関連テーブルの流儀は別） |

### 2.4 スキーマ以外への波及

- **マイグレ 1 本**（CREATE TABLE のみ・データ移行なし）。**既存テーブルへの ALTER なし**。
- **`recipe_hash` / `DuplicateKey`（VAL-C02）の対象外**。`RecomputeComboCache` に非波及。
- **seed / golden への波及なし**（新規テーブルは空で開始。backfill 不要＝未 seed キャラへの申し送りも不要）。
- **`moves` に触れない**＝**M18-03 との衝突なし**（中央の整合観点 §3-1 をクリア）。
- **M19-02 の提案ロジックに非波及**（提案は本テーブルを読まない）。

## 4. 画面設計（確定案・微調整は製造担当と）

### 4.1 ★編集導線は「コンボ詳細」に置く（セットプレイ編集画面ではない）

**成立条件は `combo_id` と `setup_id` の両方が無いと保存先の行を特定できない。** セットプレイ編集画面は **setup 単位**であり、`comboId` を持たない（`setups` は `combo_setups` 経由で複数コンボに紐づく）。したがって**セットプレイ編集画面には置けない**。

> これは M19-01 で `SetupSelectorModal` が `comboId` を持たず採択保存（VAL-S05）が成立しなかった件と**同型の失敗**である（M19-01 完了報告 教訓①＝「UI 相乗り先は名指しの一意性ではなく必須動線の充足で確定する」）。先回りして潰しておく。

**編集導線＝DES-005 §5.6 項目10「紐づくセットプレイ一覧」の各行**（コンボ詳細画面）。この面は `comboId` を持ち、各行が `setupId` を持つ。**両方が揃う唯一の面**である。

### 4.2 表示の骨格：2×2 グリッド

軸が 2 つあるため、チェックボックスを 4 個並べるより**マトリクスのほうが読める**。

```
              その場受け身    後ろ受け身
  中央（非端）     ○             ×
  端               ○             —
```

- **`○` 成立／`×` 不成立／`—` 未検証**。
- **記号ではなくアイコンで描く**（`○`/`×` は日本語圏の慣習で、英語圏では `✓`/`✗` が自然。**i18n サーフェスとして扱う**）。
- **凡例を近くに置く**（初見で読めないため）。
- ラベルは `OKI_TECH_TYPE_LABELS` を再利用（その場受け身／後ろ受け身）。端の語彙は**新規 2 語**（端／中央）を i18n に足す（ja/en parity）。

### 4.3 3 つの面での扱い

> **実装サブ＝M19-03**。M19-02 では採用パネルに手を入れない（§3）。

| # | 面 | 表示 | 編集 |
|---|---|---|---|
| 1 | **コンボ詳細 §5.6 項目10**（紐づくセットプレイ一覧） | 各行に 2×2 のミニグリッドを併記。**全 4 セルが未検証なら本要素を出さない**（tags / メディアと同じ hidden-when-empty の流儀＝DES-005 §5.6 項目9） | **各行から編集**（インライン展開またはモーダル。`comboId` × `setupId` を両方渡す） |
| 2 | **提案からの採用パネル**（提案からの採用操作） | 「確認できた条件」として 2×2 のチェックグリッド。**既定は全て未チェック**。**チェック＝成立（`ok`）のみ**を記録する（開発者確定 2026-07-26） | 不成立（`ng`）と `note` は**ここでは扱わない**（採用は「使えたから登録する」動作であり、不成立の記録は後から面 1 で行う）。**チェックせずに採用できる** |
| 3 | セットプレイ一覧での絞り込み | **後続スコープ**（§7-1） | — |

### 4.4 編集 UI の要件（面 1）

- 各セルが **3 状態**（未検証 → 成立 → 不成立 → 未検証）を巡回するか、セルごとに選択肢を出すか。**操作形式は製造担当が既存流儀に合わせて決めてよい**。要件は「**3 状態が明示的に区別でき、未検証へ戻せる**」ことのみ。
- **`note` はセル単位**。選択中のセルに対して入力欄を開く。**成立（`ok`）のセルにも書ける**（「端では距離がシビア」等）。
- 保存は既存の楽観的排他の流儀に合わせる。
- **未検証へ戻す操作は行の物理削除**（`result` に「未検証」の値を持たせない＝§2.2(a) の一貫性）。

### 4.5 表示しないもの

- 4 セルの集計（「4 条件中 2 条件で成立」等）は**出さない**。条件ごとの可否が意味を持つのであり、集計値に意味は無い。

## 5. 既知の限界

1. **端の判定はユーザーの主観**。「コンボ終了時に相手が端にいるか」を機械判定しない（アプリはゲーム状態を読まない）。記録は自己申告である。
2. **同一コンボ内の位置の揺れを表現しない**。中央始動でも開始位置により端に入る／入らないが分かれるが、本モデルは `in_corner` の真偽 2 値で吸収する（開発者確定＝コンボほど詳しい区分は不要）。
3. **提案ロジックは本記録を消費しない**。提案は距離を判定しないため、記録済みの不成立条件が提案から除外されることはない。
4. **バランス調整パッチで無効化され得る**。**検証日時を持たない**ため、記録がいつのものかは分からない。パッチ対応の扱いは**後続フェーズの範囲**（開発者判断 2026-07-26）。

## 7. 後続・スコープ外

1. **セットプレイ一覧での絞り込み**（「後ろ受け身で成立するものだけ」）。**構造化の目的そのもの**だが、対象画面が広がる（セットプレイ一覧・検索・エクスポート）ため**別サブ**とする。データモデルは本設計で絞り込み可能な形になっている。
2. **提案ロジックへの反映**（不成立と記録済みの条件を提案から外す等）。提案は距離を判定しないため、**現時点では接続しない**。
3. **バランス調整パッチへの対応**（検証日時の保持・古い記録への注意表示等）。**後続フェーズの範囲**（開発者判断 2026-07-26）。本設計では列を置かず、必要時に ALTER 1 本で足す。
