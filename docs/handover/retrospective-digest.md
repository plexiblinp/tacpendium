## 1. 構造的アンチパターン(最重要・毎回意識)
- **A 既存実装の確認漏れ**: 「実装済み」前提は code-facts で裏取り。とくに **症状のレイヤ ≠
  真因のレイヤ**。フロント↔バックエンドを決めつけず両層を疑う(M7-16/18)。**実データ/DB 実査 ≠ 仕様正典**
  ——code 規約等の正典は DES 本体(最新 CHANGE 反映後)で確認する(M10-1)。**方針確定済みの事項も、
  後続の利用実態と突き合わせ「特定 DES の一節だけ旧方針」の取り残しが無いか点検する**(M10-DP)。
  **修正対象・E2E 起点の導線は「あるはず」で書かず実コードで存在確認してから指示書に書く**(M10-4)。
  **部分更新 PATCH に nullable 項目を足すときは、フロント組立だけでなく DTO→service→repo の受け口まで
  経路全体を view 確認する(CREATE が素通しでも PATCH 経路が同一とは限らない)**(M11-1)。
  **「統一/直す/0 件のはず」系の修正指示も現状(バラバラ/未対応/不在)を決め打ちせず、対象を
  grep 全数特定・実方式を全列挙してから §3.4 着手前確認でスコープを切る(表記・i18n の対象未確認=M12-1、
  UI 構造の現状未確認=M12-3、症状ベース修正の入口/経路未確認=M15-4〔タグ作成が TagFormDialog と
  TagSelector の 2 入口〕)。**
  **設計担当自身が §3.2 前提事実に書く DES 引用は、節番号・確定/推奨の別まで実ファイルで確認する**
  ——RESEARCH 指示書の前提が誤ると後続 report に伝播するため、前提事実こそ最も裏取りが要る(M13-1、
  M14-2 で再発。自己/前任の前提記述版——**overview 等の自プロジェクト資料に既記録の削除・件数変更も
  実コードで裏取り**する〔M14-2 = aki/jamie/guile が 000017 で完全 DELETE 済と overview 自身が記録済だった〕)。
  **引き継ぎ書 / overview の残タスク欄・「未反映」記載も実ファイル照合で裏取りしてから起票・引き継ぐ**(M16-1)。
  **逆に、確定判断が出たら overview(正本)の要決定欄・footer 版数まで同期する**——「未回答」体裁のまま
  残すと後続サブが誤読する(M16-C1=handover では全確定済だが overview §4.8/§6 が未回答のままだった)。
  **破壊的移行の対象は設計書記述を決め打ちせず実データ実測で確定する**——RESEARCH 前置が幽霊仕様/隠れブロッカー/
  DES 自己矛盾を摘出(M16-2)。`CalcRecipeHash` 等の静的抽出非対象関数は code-facts に出ず実コード直読み要。
  **「〜画面で表示追従/表示する」は対象画面が当該フィールドを実際に描画しているか grep で裏取りしてから書く**(M16-3)。
  **「表現を直す/表記を揃える」系 FB の rollout は、対象の現行 rendered 状態を grep/実査してからスコープを確定する**

  **二段パイプライン/外部経路を挟む機能は「自分が作らない側(アプリ外プロンプト等)の入口」こそ、設計が前提にした運用条件(アプリ経由・moves 同梱等)で実データ検証する**——スコープ外にした入口が全体の成否を握る。
  **「② が正しく動く」と「機能が使える」は別**(M17-E11 = 本期最大の見落とし。② は diff ゼロで動いたが ① が実コンボを落としきれず。**検証条件を誤ると結論も過小評価**〔生プロンプト直貼りで「大半未解決」→アプリ経由で 54/67≈81%〕)。
  **spec の定義語(curation 等)は自分の直感で補完せず、使う前に定義節の原文にあたる。「除外/隠す/採用」のような正負が逆転しやすい語は、対象が採用集合か候補集合かを原文で確定する**——RESEARCH 報告の解釈が正典と食い違う場合は正典(spec/overview)を優先する(M18-E30)。**spec が「単位」を規定している概念(マッチアップ/コンボ/始動技等)は、定義語だけでなく単位もキー軸ごとに原文と1:1で突合する**——keep 表と hide 表のように、同じ「除外」でも単位が異なり得る(M18-E31、E30 の粒度版)。
  **「先行実装がある」前提のタスクは、RESEARCH がその所在・実体を確定するまで設計の枠(基線/評価対象/段階構成)を承認しない**——別リポ・別ツールを含む全コード grep を既定手順にする。code-facts 不在は「存在しない」ではない(本体の事実であって先行資産の全部ではない。M18-E32、M17-E11 の「先行実装の所在確認」版)。[D]
  **「既に受け口がある」「既に〜になっている」型の前提は、指示書に書く前に対象の全数を数える**——`M22-02` の指示書は 「サービス層・リポジトリ層は既に `userID` を受け取っている」としたが、真だったのは**タグとプリセットだけ**だった。 **★チェックリストがその前提を検査項目に昇格させると、正しい実装を違反と読む検査になる**(E-144)。 **指示書が実測値として書いた「全数」は、サブが 2 本挟まれば同じだけ古くなる**——`M22-RESEARCH-01` の 33 / 28 件は `M22-03` の着手時点で 38 / 31 件だった。**★指示書は調査レポートより後に書かれるため「新しい」と読まれやすい。** **あわせて「N 経路」と書いた数字は、経路と画面のどちらを数えたものかを確かめる**(ルート 3 本・画面 4 つ＝E-152／E-153)。[D]
- **B ユーザーフロー視点の欠落**: 画面単位でなく「初回登録/既存操作/削除解除」の3経路が
  揃うかをフローで確認。**「未解決/エラー/対象外を正常な結果」と設計したら、それを含んだまま前へ進む導線(行ドロップ・除外・警告)まで設計する**——許容する設計と完走できる導線は別物(M17-E13 = 取込の「進む」が未解決 0 条件で、割当不能な補足行〔`適当`/`...`/`2KKK`〕を含むコンボが取り込めなかった)。
  **複数入力を持つ画面は「上から下へ何を入力してどうアクションするか」を 1 本の動線として設計・レビューする**——個々の入力欄が各々の要件を満たしても動線全体でちぐはぐが出る。動線の自然さは実使用でしか出ない(M17-E20 = (c) 独自ルールは画面入力なのにコンボ本体は手貼りのままだった)。[D]
- **C 既存パターンとの整合**: 過去マイルストーンの確立パターンと矛盾しないか(arch-patterns 参照)。[S/T 済]
- **D 必須項目の消化**: §5 必須テスト ↔ §7 DoD を明示リンク。テストは「ファイル有無」でなく
  「ケース数」で語る。[T]
- **E 完了基準を設計書要件監査から導出**: DoD/スコープは REQ/DES の該当章をチェックリスト化して
  突き合わせる。**配布・起動・運用など横断要件**は主担当が曖昧で取りこぼしやすい——明示監査する。[T]

## 2. 跨セッションのマインド [D]
- 前任設計担当の前提記述を疑う。誤った前提は世代を超えて連鎖する(M4-1)。**起動時に与えられた版数記述を鵜呑みにせず、
  直読した実ファイルのヘッダ版数と、起動プロンプト・ボード・handover の記載版数を突合してから読む。乖離したら実ファイルが正**
  (M16-C2 の直読前提への言い換え・2026-07-30。原型は「PASTED 版数 vs 実添付」だが直読では「実添付」が存在しない)。
  **直読・ナレッジはいずれも「最終 push + Sync now 時点」のスナップショット**であり、作業中に repo が進んでいる可能性を前提に置く。
  **ナレッジは検索ベース取得で取りこぼす**ため、**ロック・counter(採番 registry・ボード・契約)は検索に委ねず明示パスで読む**(parallel-ops §10)。
- 多段フィードバックループ(Plan Mode 質問 / 完了後連絡 / E2E 指摘 / 開発者の仕様確認質問)は
  設計担当のセルフチェック限界を補う仕組み。指摘は「不備の発見」として歓迎し v1.0.x 小修正で応える
  (M14 最重量クラスタでも製造 Plan Mode が前提誤り・スコープ境界・死蔵を繰り返し捕捉=M14-7)。
- レビュー承認 ≠ 完了承認。E2E 実機確認を完了の必須ゲートとして扱う(M4-02)。UX/導線系はコードレビューで
  ゼロ件でも実機で構造欠陥が出る——実機確認を要件とし、Plan Mode の選択肢は帰結(誰にどの経路で届くか)まで
  詰める(M15-6=オンボーディングが PC/タブレットで能動到達不能)。
- 成果物(指示書・レビューチェックリスト)を提示しても commit は開発者の別作業。「提示済み=リポジトリにある」と
  前提せず、引継ぎ・完了時に commit 状態を確認事項に挙げる(M13-5。パターン D の commit 版)。
- **先に書いた指示書は「書いた時点の as-built」で凍る。未投入の指示書がある状態で別サブが完了したら、完了報告の
  「触ったファイル」と未投入指示書の「改造対象」を突合し、交差があれば回帰ゲート(壊れていないことを E2E で証明=§4.14)を足す**
  (M17-E14 = M17-04 完了で入った連携口を M17-05a 指示書が知らないまま「投入可」だった。§4.9 実物確認原則の時間軸版・playbook 昇格候補)。[D]
- **原則を新設・昇格したら、既存の未投入指示書を grep して遡及追従させる**——昇格しても既存文書への遡及適用は
  自動では起きない(M17-E15 = §4.15〔連番を数字で固定しない〕新設後も M14-03d 指示書に旧形の連番直書きが残存)。[D]
- **並列運用(中央＋複数指示書担当)で累積更新される成果物(DES 等)を CHANGE ごとにスナップショット複製すると「どれが最新か」判別不能になる。成果物はファイル名に版を入れる(または内部版スタンプ)・単一パスで出し、「現行版の正本の所在」を集約したマニフェストをセッション終了時に必ず出す**——並列では指示書担当が中央の版を参照するため、版付き単一正本がないと即破綻する(M18/M19-E29。playbook §21.3 の実務版・昇格候補)。[D]
- **中央(並列運用の設計統括)の成果物は「生成した」時点では完了しておらず、リポジトリへ着地する(開発者が配置し、それを確認する)までが完了条件**——三点セットの完了条件に「作る」だけでなく「配置・確認」を含める。着地していない改訂は指示書担当に届かない(M18/M19-E33。E-29 の続編=「出し方」でなく「届いたかの確認」)。[D]
- **フレーム・入力・立ち回り等ドメイン知識に依存する設計判断は、推論が内的に整合していても確定前に開発者へ確認する**——「2 件が 1 つの規則で同時に解決する」ように見えるときほど、両方の前提を個別に検算する。説明の綺麗さは根拠の強さではない。列の意味は定義の一文でなく実際の値の分布と付与運用で確認する(M18/M19-E34)。[D]
- **複数案から選んだときは、採用案だけでなく不採用案とその理由も残す**——「案C で決定」とだけ記録され、**案A・案B の内容が
  どの文書にも残らなかった**。**後から「なぜこの形なのか」を追跡できず、同じ議論を繰り返す。** 決定を書く場所に「検討した案」と
  「採らなかった理由」を 1 行ずつ併記する。**担当者が替わった瞬間に顕在化する**(M18-(c)/E-100)。[D]
- **followup／playbook 等の項目を記号((f) 等)で引くときは、記憶で引かず毎回実物を開き、記号の隣に内容の要約を併記する**——記号参照は中身を持たないため誤りが自己検出できない。ID の無い論点を見つけたら参照する前に ID を与える(M18/M19-E35。**2 セッション連続で同型のミスが再演した重点教訓**)。[D]

- **実物の観測を報告するときは、観測した時点（commit）を書く**——書かないと「現在の状態」についての報告どうしが矛盾し、**どちらが誤っているかを判定できない**。M23 期に「解消済み」と「古いまま」の 2 報告が食い違い、**どちらも誤っていなかった（観測時点が違っただけ）**という形で実際に起きた。**★設計卓は実装ソースを読めないため、食い違ったときに自力で決着できない**(E-250)。[D]
- **「作業ツリーに無い」は「`main` に無い」の証拠にならない。逆に、取り消し・撤回は取り消した先の状態を実査してから閉じる**——設計伝達レポート 9 本を「無いから」と投入したが `main` には既に在り（E-260）、その取り消しが今度は **add/add の解決で削除側に倒れ、9 本とも `main` から消えた**（E-265）。**⇒ 「重複を消す」変更は、残るはずの側が実在することを別経路で確かめる**（履歴の全走査で 2 つの ADD が見えていた）。[D]
- **★見立てを「証拠」として報告へ書く前に、1 件ずつ裏を取る。上流から降りてきた理由付けも同じ**——Plan Mode で挙げた証拠 3 件が**すべて実測で否定された**。**★裁定に書かれた理由付けも同様で、上流の文書は正しさの根拠にはなるが事実の検証を免除しない**(E-276)。[D]
- **★★「撤回した」は、本文・コード注記・索引のすべてを同じ手番で直して初めて成立する**——撤回した主張が設定ファイルのコメントに事実として残り、次は撤回した数字が同じコミットのコード注記に断定形で残った。**★同一サブで 2 度目は、1 度目でこの教訓を自分で言語化した直後である。** **⇒ 「撤回」を書いたら、その値の出現箇所を `grep` で全数当たる。記憶で「直した」と判断しない**(E-277)。[D]
- **原因を特定できていない事象へ、もっともらしい説明を与えない**——観測と原因を分け、**反証できるまでは「原因未特定」のまま記録する**。1 つの観測から断定した説明が、後続の観測で否定された(E-243)。[D]

- **報告やレビューから写した事実も、自分の主張として確かめる**。複数資料が同じ値を持っていても源泉が同じなら独立の証拠ではない。数だけでなく理由・不在主張・過去裁定も対象にする。本期間 **8 サブ**で同型。§4.59 の数値規約は実在するが、名指し以外の数に適用が漏れた（E-334/E-351/E-360/E-362/E-422/E-462/E-467/E-471）。[D]

## 3. 指示書を書く前の型・スコープ規律 [T:playbook 未組込=意識で守る]
- 一覧用 / 詳細用でレスポンス型を分ける。詳細型を一覧 API に流用しない(M4-5)。
- Props は最小限(YAGNI)。同時に、表示用 state と送信用 state の**責務境界**は Props 定義に明示(M4-5/14)。
- 「文字数制限なし」「console.warn なし」など **規定なしも明示的に書く**。暗黙仕様を作らない(M4-7)。
- 設計書本体の一般論規定(例 DES-006 §10)は新ドメインの各フィールドへ具体値で落とし込む(M4-7)。
- 設計書本体の §5.x は「表示項目」と「アクション」を**ペアで**読む。遷移/クリック挙動を落とさない(M4-6)。
- 設計書本体の具体値(ブレークポイント・API パス・フィールド名)を例示するときは原典を確認(M6-10)。
- 二重定義の集約は GET 読取路変更を伴う。読取路不変が選ばれたら**集約は後続へ切り分け**、集約しない判断には乖離検出の安価なガード(共有フィールド一致テスト)を添える(M9-A4)。[D]
- **固定前提/未消費前提を動的化・有効化する改修**では、消費側のキャラ別ハードコード定数・コード正典の一致・phase-1 時代の固定 defect が残っていないかを着手前に監査する(M10-2/5。M11-5 で的中=ryu `'{}'`〔phase-1「固有状態なし」前提〕を発見し電刃定義へ是正)。[D]
- **nullable 項目を PATCH でクリア可能にするなら、不在/null/値のトライステートを設計時に決め切る**。フロントの「空=null 送信」と BE の「null=不変更」が衝突するとクリア不能になる(「あり→なし」が保存されない)。`nil=不変更` を採るならクリアの表現手段(空文字センチネル / presence-detection 等)を同時に規定する(M11-2。半更新 API のトライステート設計=パターン A の新切り口)。[D]
- **局所センチネルの暫定対処は「一般化の要否」を別途判断し、一般化は別サブで合意のうえ起票する**(局所修正に一般解を詰め込まない)。部分 PATCH の呼出元が部分キーしか送らない API では full-replace を採れず presence-detection が要る(M11-3。M9-A4 切り分けの同型・正例)。[D]
- **「1入力=1move」等の確立済み原則がある概念に新入力経路を足すときは、DES 横断(DES-004 §2.1 ⇔ SUPP-001 §3.3.3 ⇔ DES-003 §3.3)で原則違反の重複が残っていないかを着手前監査する**(M15-3=dash が system move と modifier.type で二重表現し保存データが揺れた。§3 固定前提監査の横断版)。[D]
- **「検証しない / VAL 非連動」は BE VAL と FE zod の双方で範囲 ERROR を設けないと一文で明示する**。非連動には (i) BE/CSV/UI 全非強制 (ii) BE/CSV 非強制・UI 担保 の 2 段があり、確定時に一段掘っておけば実装後の差戻し(「上限を強制したい」)を防げる(M16-5。半更新 API の VAL 連動 2 段)。[D]
- **「将来の拡張に備えて汎用の器を用意する」より「今の判定基準を素直に表現する」方が良い場合がある。開発者のドメイン知識に基づく対案を軽視しない**
  (M17-D6=command 索引 1:N を priority 汎用列でなく派生技フラグで解決=後発技への都度 priority 付与が不要・priority は将来の表示順用に温存できた)。[D]
- **新しい区別が要る時は (1) 分類(category/type)か属性かを見極め (2) 既存/導入予定の属性で兼ねられないか先に検討する。category はユーザーが技を選ぶ軸に保つ**
  ——分類軸を増やすと UI の技選択の分類が壊れる(M17-D7=ターゲットコンボの空振り類型を新 type でなく `is_derived` で兼ねた)。[D]
- **視覚出力(PDF/PNG 等)は出力先の用紙寸法を最初から固定して設計し、出力系サブの DoD に「開発者の実出力目視」を明示的に組み込む**
  ——分割の正しさと用紙適合の正しさは別軸で、「用紙に載せた見た目」は実出力レビューでしか出ない(M17-E17 = 製造完了・レビュー合格後に
  実 PDF で末尾見切れ。playbook 昇格候補)。[D]
- **「重複時 X する」等の振る舞いの分岐を書くときは、それを実現する既存 VAL-* / UNIQUE 制約の「判定キー」を DES/実コードで
  先に引いてからテストケースの軸を決める**(M17-E19 = setups 重複 3 ケースが既存 VAL-S04〔名前非依存・レシピ一致 ERROR〕と原理的に矛盾
  =「別名＋同レシピ=取込む」は実現不能だった。DES-006 §6 を読めば防げた)。[D]
- **指示書が X を規定したら、「X と同じ語で呼ばれる別の対象が実装に無いか」を 1 回探す**——「論理削除されたコンボ」を規定したが「論理削除された**セットプレイ**」を書き落としていた（製造が実装実査で拾った）。**規定した語をキーに、その語が掛かる対象を全数列挙する**(E-108。E-46「軸を数え落とさない」の語彙版)。[D]
- **★★母集合を宣言してから数える。キーワードを 2 通り当てても、母集合が狭ければ件数は動かない**——指示書が母集合を指定していたのに手で選んだ集合へ当てており、**その中の 1 本は既に残骸と判っていたもの**だった（＝**答えを知ってから母集合を選ぶ形**）。**`E-236` はキーワードの話であって母集合の話ではない**(E-266)。**★あわせて「列挙そのものが全数か」を疑う**——数が合っていても、**数える対象の集合が指示書で狭められている**ことがある(E-267)。[D]
- **★母数は「数」ではなく「数え方」を書く。コマンドを併記すれば自動的にそうなる**——除外したものと除外理由が無いと、レビューが再現できない(E-268)。**★合計の一致を内訳の正しさの証拠にしない**（2 つの誤りが打ち消し合って合計だけ正しく見える＝E-269）。**★母数は「見る単位」で割れることがある**——食い違いを見たら、まず単位が違わないかを疑う(E-270)。[D]
- **★「任意の関数を受け取る」は柔軟さではなく、不変条件を守れなくする形である**——離脱ガードを `requestLeave(任意の関数)` にしたため、**補正が原理的にできない経路**が生まれた。**⇒ 行き先を「どこへ」か「戻る」かの形で受け取ると、補正の仕方が型から決まる**(E-303)。[D]
- **★「N 実装を 1 本へ寄せる」サブでは、寄せた後の公開面が本番の必要と一致しているかを DoD に入れる**——公開したままだと**入口を経由しない 3 つ目の呼び元が生えうる**＝統合前の状態へ別の形で戻ること(E-309)。[D]
- **★共有部品を i18n 化したら、消費側の面を全数挙げて「その面は i18n 側か直書き側か」を 1 件ずつ判定する**——部品の側だけを見ても混在は見えない。**全面直書きの画面 5 つに埋まっており、キャラ名をロケール従属にした時点で日本語の画面のなかでその部品だけが英語になった。★レビューも見落とした**（残存一覧を行数順で読んだため小さい面が埋もれた）(E-311)。[D]
- **内部値／DB 値／表示ラベル／CSV 写像は指示書内で行を分けて記述する**——1 行に混在させるとラベル変更の波及範囲が局所化できない(M18-E27)。[D]
- **2 つの供給元を 1 つの判定へ入れるときは、差分を採る側の前提を先に確かめる**——判定が「1 本の押下集合の差分」で立ち上がりを採る構造では、**各源が独立に push した瞬間に片方が「離された」ことになる**。**⇒ 供給側で合流させてから渡す。** **★「供給元を増やすだけ」に見える変更が、受け手の不変条件を壊す形である**(E-130)。[D]
- **同じ表現力を持つ 2 つの入力経路を並べると、「片方でしか入らないもの」が必ず出る**——同じ入力の結果が状態で変わる。**⇒ 新しいモード・経路を足すときは「既存経路で入るものが新経路で入らなくなる組」を実データで数えて報告させる。** **★片方の索引だけを細工して解こうとしない**（別の穴が開く）(E-133。**E-108** の経路版)。[D]

- **規約は「目的」で書き、「既定の形」と「形を外れてよい条件」を併記する**——形（`WHERE <当該列> IS NULL` 等）だけで書くと、**形が合わない事例が出た瞬間に「違反」と「正しい判断」の区別がつかなくなる**。**形を外れた実装は、目的で書かれていないと「違反」に見え、適用者は正しく判断したのに上申する形になる**(E-96。playbook §4.21 (1)〔原則は画面名でなく性質で書く〕の規約版)。[D]

- **UI の要求を書く前に「その画面の到達条件」を 1 行書く**——「パスワードが分からないとき」の案内を設定画面へ置く案は 設計・製造の双方が出したが、**その案内が要る人はログイン画面に居て設定画面へ入れない**。この一点で不要と決まった(E-148)。[D]
- **「横断関心を 1 か所に置く」と書くときは、層を指定せず実査項目として「どこなら 1 か所になるか」を問う**——`fetchJSON` に足すと 3 系統のうち 2 つを取りこぼす状態だった。**「1 か所」が成立する層は実装によって違う**(E-150)。[D]
- **「締めない」「やらない」を選ぶときは、締めた場合に壊れるものを名指しする**——「不要だから」は次の担当に上書きされ、 「実行すると X が壊れる」は残る。`M22-05` の根拠は思想ではなく実測 2 点だった(E-165)。[D]
- **指示書の「穴の候補」は仮説である。根拠列に実測が無いなら「実査で在否を決める」側へ倒す**——`M22-06` の §4.3-1 は 「埋める」と命じていたが、根拠列の前提（押せてしまう）が実測では成立せずボタン自体が存在しなかった。 **★表の「埋めるか」列だけを読むと命令に見える**(E-175)。[D]
- **★理由の無い対称を作らない**——「A と B の両方」と並べる前に、**挙げた根拠が B にも当てはまるかを 1 件ずつ確かめる**。M23-05 は「`VAL-C14` と `VAL-R03` の両方の母集団から旧行を除く」と書いたが、根拠 2 つはどちらも「削除済みを見る母集団」にしか当てはまらず、**述語を足すと偽陰性になった**。**実装が正しく、指示書が誤っていた**(E-253 ＝ 計測点 `M-69`)。**★同型が `M-73` として同一マイルストーン内で再発した。** [D]
- **同じ事項を 2 か所以上が書いていないか、書いていたら一致しているかを実査項目に入れる**——**とくに「散文で範囲を広げ、表で列挙する」構造は食い違いやすい**。M23-05 の §4.2（散文）と §4.4（表）が食い違い、製造は表に従い、レビューで指摘されるまで誰も気づかなかった(E-212)。[D]
- **「N か所直す」の N は調査時点の値であって着手時点の値ではない**——**同じマイルストーンの先行サブが同じ領域に触っているなら必ず増減しうる**。調査が数えた 5 か所は着手時に 7 か所になっていた(E-202)。**★「N か所直す」の N が関数の数か症状の数かも確かめる**——共有ヘルパなら片方だけ直すと半分だけ回復した状態になる(E-195)。[D]
- **「塞がない」「残す」と決めたときは、その理由を 2 つとも書く**——1 つしか書いていないと、後から「もう使われていないから消せる」と読まれる。M23-03 が意図的に塞がなかった理由の 2 つ目が、4 サブ後の M23-07 で回収された(E-256)。[D]
- **裁定は正しくても、裁定の「理由」は別に検証が要る**——「結論が正しいから理由も正しい」と扱わない。**理由が as-built と食い違ったら、裁定は変えず理由だけを訂正する**(E-249 ＝ 計測点 `M-68`)。**★理由は、その読み取りの結果を誰がどう引くかまで 1 段辿ってから確定する。場所と機能だけでは段を決められない**(E-201)。[D]
- **不変条件を壊す変更では、「他所の穴」と「自分が壊した箇所」の区別が最初の設計判断になる**——判定軸は **「本サブの変更が無くても同じ挙動なら他所の穴、本サブの変更によって初めて挙動が変わるなら自分が壊した」**。**判定せずに全件を報告へ回すと、担当境界を守る規則が劣化の言い訳になる**(E-194)。[D]

- **数えた集合と、数値を出した経路を分けて書く**。「実測／算出／転記」を値の隣に示し、集合の一致は内訳で確かめる。母集団が正しくても計算値を実測として出せるため、母集団の宣言だけでは足りない（E-427/E-428/E-454）。[D]

## 4. UI 画面・API の網羅性 [T]
- BE 指示書は UI 動線から逆算し、必要 API が §4.2 に揃うか机上シミュレーション(M4-4)。
- API のオプショナルパラメータは **取得方式+フィルタ+並び順+件数制限** の軸で個別に扱いを確定(M6-7)。
- 新規 queryKey を足すマイルストーンでは、既存 mutation の onSuccess で invalidate 対象に
  含める要否を明示(M4-03)。
- **クロスコンポーネント(ツール↔本体)の責務は、片側に処理を課す前に相手側の出力実態を確認**し、
  設計書の責務記述を実態と揃える(M9-2)。[D]
- 工程の出力(判定結果 WarningCode 等)が**後工程に届く形(永続化 or 再導出経路)で残るか**を設計時に確認する(M9-4)。[D]
- **表示トークン / 表記正典を変える改修は、保存済みキャッシュ(recipe_cache 等)に旧表記が固定化されていないか + 同一トークンを使う全表示箇所(一覧/詳細/比較/編集)を全数調査してから、スコープ・CHANGE・キャッシュ再生成要否を確定する**(M12-2。M9-4「後工程に届く形で残るか」の表示版)。[D]
- **ラベル / i18n キーを再利用する前に、既存 UI に占有されていないかを調査で確認する**(既存「状況/situation」キーは独立カラム用に占有済みだった→別系統キーで命名衝突を回避。M11-4)。[D]
- **★「どの欄がどのパネルに在るか」と「エラーをどのタブへ振り分けるか」は別々のコードに書かれ、別々に育つ**——パネルへ節を足したら、その節が出しうる `field` が振り分け規則に載っているかを見る。**★既定が先頭タブへ落ちる形なので、載せ忘れても静かに間違ったタブを指す。テストも lint も緑のままである**(E-312)。[D]
- **★UI の要素を分割すると、それに依存していた E2E が静かに壊れうる。セレクタを緩めるのではなく実装側に `data-testid` を足して名乗らせる**——技名が単独要素になった結果、レシピ文字列と**完全一致で衝突**し strict mode 違反になった。同 spec は「連結文字列だから完全一致では当たらない」という**偶然の前提**に依存していた(E-317)。[D]
- **★遅延初期化子で「後から届く値」を読むと、検査が永久に効かない画面ができる**——**毎描画で解決し直す画面は自己修復するが、`useState` の遅延初期化子で 1 回だけ読む画面は修復しない**(E-306)。**★あわせて共有部品の DOM 種別を変える変更は `selectOption` / `toHaveValue` の全数を先に `grep` する**(E-316)。[D]
- **契約には「あるべき姿」を書き、現状の取りこぼしは既知の乖離として併記する**——同じ入力誤りに対し経路で応答が食い違っていたとき、**契約は正しい側を書き「片方の経路は現状こう返す既知の取りこぼしがある」を併記する**。**現状を正として契約に書くと、揃える作業に収束先が無くなる**(E-112)。[D]
- **成功応答を返しながら黙って捨てる経路が最も悪い。直せないあいだは契約に書いて観測可能にする**——エラーにも警告にもならず無視されるフィールドがあった。**★限定して書かない**（無視されるのが構造全体なら、一部のフィールド名で書くと「他は書ける」と読まれる）。**★「UI が無いこと（意図）」と「API が無視すること（取りこぼし）」は別の事実**であり、分けて書かないと「その機能は扱わない設計だ」と丸められる(E-113)。[D]
- **UI の呼称は「何をする面か」と「どう表示される面か」の 2 つを含む。後者を実体と違えると面そのものの取り違えを生む**——インラインで展開するパネルを「ダイアログ」と呼んでいたため**開発者が別のモーダルと解釈して誤った判断をしかけた**。**形態の呼称は実体に合わせ全数 grep して揃える。ただし操作の語彙は変えない**（i18n キーと利用者の理解に触れる）(E-116)。[D]
- **test-id / i18n キー / ラベルの命名規約を指示書に例示する前に、既存規約の実値を grep で確定し、それを正として例示する**(提案例が実装と乖離すると後続サブがセレクタを誤用。M15-1=`combo-meta-*` を例示したが実在は既存 `combo-editor-*`。M11-4 と同根の命名占有・実値確認)。[D]

- **既定 OFF の非回帰は「既存が壊れないか」と「新機能が黙って動いていないか」の 2 項目に分ける**——前者だけだと **新機能のテストは ON を通すため全部緑のまま**になる。`M22-01` は `Login` が OFF でも 204 ＋ Set-Cookie を返していた。 **★これは例外状態ではなく、ゲートを外した後の通常状態である**(E-137)。[T]
- **「最後の逃げ道」を設計したら、その逃げ道を実際に歩く手順テストを 1 本置く**——`M22-02` は復旧手順を 3 か所へ書いたが **3 つとも同じ思い込みを写しており実際には復旧できなかった**。設計・実装・製造が独立に同じ穴を作っている(E-147)。[D]
- **非回帰ゲートは「サーバ」と「画面」の両方へ翻訳して書く**——「無効なら何も増えない」は API の非回帰として書かれがちだが、 UI にも同じ形で当てはまる(E-149)。[T]
- **★「配線した」を確かめるときは、出口だけでなく入口も見る**——**空のリストは、正しく空なのか到達不能なのか、見ただけでは区別がつかない**。M23-02 はゴミ箱**から**の復元・完全削除を配線し E2E も通したが、**ゴミ箱へ入れる導線がどの画面からも使われておらず、開発者が手動確認の手順を尋ねるまで気づかなかった**。**E2E は API で直接叩いて状態を作るため、この欠落を 1 つも検出しない**(E-199。M23-07 を生んだ)。[D]
- **★★文面は「設計の目的」ではなく「実装がしていること」から書く**——**「この文を読んだ利用者が次に取れる行動」を 1 つ挙げ、それが実装に在るかを確かめる**。無ければ文面か実装のどちらかが間違っている。**自動テストでは検出できない**（翻訳キー経由で正しく描画され、テストも lint も型検査も緑）(E-211。設計卓側の同型は playbook §4.30 へ機構化)。[D]
- **レイアウトの装飾は、条件付きで消える当のコンポーネント自身に持たせる**——外側で `sticky` / `fixed` をラップすると、中身が `null` を返したとき**枠だけが残る**(E-222)。[D]
- **起票時に数えた経路数は as-built で増える。経路表を「想定 N 本」で閉じない**——M23-02 の経路は想定 3 本ではなく 4 本だった(E-248)。**★引数・フィールド名を足すときは、模倣元ではなく「足す先の経路が今使っている綴り」を先に見る**——同じ経路の中の綴りは、経路をまたいだ統一より優先する(E-196)。[D]

## 5. SQL・テスト・診断 [T]
- 候補抽出/一覧抽出 SQL は境界値(ID 重複・多対多重複紐付き・論理削除両端・NULL 比較・空集合)を
  WHERE 句で机上検証。テストケース表を併記(M4-10)。
- API クライアントテストはヘルパをフルモックせず、ヘルパ自身のステータスコード契約も試験(M4-02)。
- E2E 不具合の診断は **リロード後の挙動 + バックエンドレスポンス実検証** で切り分ける。
  症状から短絡的にフロント/BE を決めない(M4-10)。
- **破壊的マイグレ(seed クリア等)を指示書に課す前に、test ハーネス(`dbtest.Setup` が全マイグレを適用する事実)への波及を確認する**。
  破壊的クリア=配布クリーン初期状態は別スコープ(M12-02)へ切り分ける(M9-1。パターン A/E 複合)。[D]
- **破壊的マイグレ指示書では「マイグレ接続は FK=OFF → 子行は ON DELETE CASCADE に頼れず全て明示 DELETE が必要」を定型化**し、
  FK=OFF と CASCADE 連鎖を同一指示書で同居させない(M12-5。パターン A + §7 自己整合の複合)。[D]
- **キャラ/行の除去を伴う指示書では、旧形 code の直書きだけでなく対象の `character_id`(数値直書き)/ `code`('aki' 等)への依存も
  grep 観点に加える**(tag テストが id 依存で旧形 code grep に掛からず FK 違反で発覚=M12-6。M9-1 検出網の拡張)。[D]
- **永続スキーマに依存しがちな機能(export/import 等)は意味単位(character_code/move_code・論理キー、DB 管理列除外)で
  設計し、後続の破壊的スキーマ変更(M14 等)から保護する**(M13-6。正の前例・設計頑健性。M14 の moves 6 列削除で往復不変を実証)。[D]
- **逆依存を伴うパッケージ削除は、共有シンボルの中立パッケージ移設→参照差し替え→削除に段階化する**(一括物理削除は
  温存側のコンパイル不能を招く)。**先行サブの削除が後続の移設対象を縮小する場合は活用する**(M14-4。正の設計)。[D]
- **画面文言の変更は、その文言を assert しているテストの突合まで含めて 1 つの変更である**——**文言を assert している E2E spec は
  golden／snapshot と同じ出力固定資産**（E-23／E-14 の突合対象）。M18-03b が 03a の告知文言を書き換え、**03a の E2E spec が追随せず
  恒常的に失敗**していた（M19 製造担当が発見＝実装が正しくテストだけが古い）。**★危険なのは検出のされ方**——**この E2E 環境は
  SQLite 書き込み競合で恒常的に 1〜2 本 flaky になり、本物の回帰が環境ノイズとまったく同じ見え方をする**。
  **文言を変える指示書には、その文言を assert している資産の洗い出しを DoD に入れる。「既知の flaky だから流す」を既定にせず、
  落ちた本数でなく落ちた spec 名で判断する**(M18-(b)/E-99)。[D]
- **配布物・配布判定はマイグレ由来のクリーン DB を基盤にし、配布前に一度クリーン DB で全 E2E を実行する**
  (dev DB 流用禁止)。※前段だった「編集系 FE E2E が永続 dev DB を汚す」は**解消済み**＝E2E は使い捨て DB ＋
  専用ポートの独立スタックで走る〔CLAUDE.md §5〕。**残る論点は配布判定の基盤 DB のみ**(M14-6)。[D]
- **列追加(ADD COLUMN)・正規化系マイグレの down は列 / 新変種を失い破壊的**(型変更の down は再構築で値保持)。**combos 等への新規列は任意列(`requiredImportColumns` 除外・列末尾追加)にして旧 CSV import の後方互換を保つ**(M16-6。DES-002 §7.6 正典化=以後の列追加の標準)。[D]

  実コードで確定する**——recipe_hash 再計算・in-migration dup 検出・targeted cache 再生成は pure SQL から呼べず幽霊ステップになりうる

  残行が再計算で生 code 化するため、残行ゼロ化の後続計画(掃き取り follow-up マイグレ)を DoD に紐づける(M16-C4。M15 全数監査の時間軸版)。[D]

  由来」から「だから既存 DB は考えなくてよい」へ誤って敷衍しない(M17-D1／M17-E5。**§1 パターン G として昇格**
  ＝開発者裁定 2026-08-09。運用面は playbook §4.17)。[D]

  **実ユーザーが生まれるのは全体公開から**(Phase 3 完走とは限らず **Phase 4・拡張 Phase を挟みうる**)。
  **それまでは dev DB のみ考えればよく**、「残すものの列挙＋NOT IN」「down の忠実復元」を**前倒しで払わない**。
  **公開直前に戻す**＝followup `restore-real-user-premise-before-public-release`(§F-1) に登録済み。
- **人が経由する経路(コピペ・AI チャット UI)を挟む契約は、その経路で壊れないかを実物で確かめる**——「フォーマットとして正しい」と「経路を通っても保たれる」は別。
  **モデル差(高性能前提)も実測する**(M17-E12 = TSV はチャット UI のコピーがタブを空白へ潰し 0 行認識→Markdown パイプ表へ。Gemini 無料版はパース不能)。[D]

- **同じ述語でも「誰が何を問うているか」で意味が変わる。共用する前に両側の問いを文にして並べる**——「単独では出せない技」を除外する述語は、**自分が入力できるかを問う側では正しく、相手が出しうるかを問う側では偽陰性になった**（実在する反撃機会を落とす）。**★述語が同じ形をしていることは、同じ問いを立てている証拠ではない**(E-102)。[D]
- **2 つの別の集合を 1 つと数えると、分けられるはずの段階が分けられないように見える**——「どちらも候補集合の件数を動かすので段階を分けられない」と書いたが、**動く集合が別（測定も golden と canary で別）だった**。**「分けられない」と判断する前に、動く集合とその測定手段を対で書き出す**(E-103)。[D]
- **「これは誤りだ」と断じる前に、その実装が意図的な対照群でないかを潰す**——テストの前方一致を「古い書き方」と裁定したが、**従来方式を意図的に再現した対照群**だった。**「是正」すると対照群と本命が同値になり、canary と増分検証がまとめて無効化される**(E-104)。[D]
- **golden の green は実データでの動作を保証しない**——golden は**合成 fixture が前提を作っている**ため達成するが、実データはその前提を満たさないことがある。**「golden が通っているから実装できている」と読まれないよう、限界を完了報告に書かせる**(E-107。E-84 の fixture 版)。[D]
- **値域の要素数から導出した定数は「導出のままであること」をテストで固定する**——`len()` 導出は「今」の保証であって「将来も導出のまま」の保証ではない。**後任がリテラルへ戻しても、値域が増えるまで誰も気づかず、増えたときに壊れるのは絞り込みの結果でありコンパイルでも既存テストでもない（静かに壊れる）**。**固定するのは実装の形ではなく性質**（値域を 1 要素増やした状態での挙動）(E-109)。[D]
- **テストの入力は実データの形へ揃える。省略したフィールドが、そのテストが守るはずのガードの鍵でありうる**——fixture を「必要最小限」に絞った結果、**ガードが鍵にしているフィールドを落としており、固定表を置かれても赤くならなかった**。実データ側はそのフィールドを持つ。**★破壊確認が無ければ緑のまま通していた**(E-124。**E-107** の fixture 版)。[T]
- **「制約の単位」と「照合の単位」が違うとき、検査は照合の単位で行う**——DB 制約が `(A, B)` 単位でも、実際の照合が A を横断して引くなら、**制約の単位で数えた「衝突 0 件」は本物の衝突を見落とす**。**★0 件は「無い」ではなく「その単位では見えない」でもある**(E-127。**E-84** の単位版)。[T]
- **値が同じでも意味が違うものを、同じ表現に寄せない**——「圏外だから NULL」と「未実測だから NULL」／「未判断の unknown」と「判断した結果の unknown」／「確認して false」と「そもそも対象外」／「測っていない」と「測って不変を確認した」。**「実装上の結果が同じ」は「同じ値に寄せてよい」を意味しない。寄せると後から復元できない**。**書き分けた値は完了報告で別々に数えさせる**(E-98。同一 MS で 4 回)。[D]

- **★★緑を返した経路が、確かめたい対象を通っていなかった**——`govulncheck -version` の `No vulnerabilities found.` を 「DB へ到達できた証拠」と読み、**誤った結論を文書化して push した**（走査対象ゼロのため DB を引いていない。403 でも同じ出力）。 **★判定材料は出力の中に在った**（成功時だけ `DB updated:` 行が追加される）。**「出ている行が期待どおりか」だけを見て 「出るはずの行が出ていない」を見なかった。** **⇒ 照合は「期待される行の集合」に対して行う。** **★あわせて、出力を切る（`head` / `tail`）ときは切った先に判定材料が無いことを確かめる**(E-182／E-183。`E-84` の実行層版)。[T]
- **破壊確認で空振りしたとき、「別の機構が代わりに守っている」の他に第 3 の分類がある＝主張そのものが失敗モードに対して無力** ——件数 `=== 1` は「初期値へ戻す」実装を検出できない。**「リセット」と「クリア」は別の失敗モードであり、1 つの主張で 両方は見られない**(E-155。`SUPP-001` §5.5.4 (10′) の補い)。[T]
- **破壊確認で赤くなった／ならなかった本数を、網の厚みと読み違えない**——赤くなった 4 本のうち 2 本は fixture がたまたま 条件に当たっただけだった。**逆に「緑のままだった」を根拠に「既存は何も守っていない」と一般化するのも誤り**。 **⇒ 「その破壊で赤にならなかったテスト」ではなく「その項目を主張しているテスト」を数える。** **★あわせて、締める変更では「検出できる」を、締めない変更では「巻き込んでいない」を示す**(E-162／E-169)。[T]
- **検査の足場（環境設定・モック・fixture・docblock）そのものに陽性対照を掛ける**——`@vitest-environment-options` が 効かなければ検査は**無言で空回りして緑を返す**。`E-84` は走査だけの話ではない(E-173)。[T]
- **実データだけを見る検査では、原理的に検出できない不変条件がある**——段の順序（前段の答えを後段が上書きしないこと）は **実データに競合するキーが 1 つも無ければ順序を入れ替えても答えが変わらない**。**⇒ 「この不変条件が破れたとき実データ上で 答えが変わるか」を先に自問し、変わらないなら合成 fixture を必須にし、対照も同じ検査へ入れる**(E-180)。[T]
- **実装案を選ぶ前に「これはテストで赤くできるか」を先に確かめる。固定できない実装はその時点で選択肢から外す** ——`InputEvent.isComposing` は jsdom で伝わらない（プローブで実測）(E-160)。**あわせて i18n キーの削除は ja↔en parity 検査を 素通りする**（両側から同時に消えると parity は成立し、画面に生のキー文字列が出る＝E-161)。[T]

- **★★「テストが在る」と「テストが効く」は別である**（M23 期の中心教訓・以下 6 件はすべてこの系列）。**「述語や母集団の取り違えで結果が空になる」形の実装を書いたら、破壊確認を 1 回入れる**——この型が有効なのは「**壊れても緑のまま通る**」構造を持つ箇所である(E-206)。[D]
- **破壊確認で赤くならなかったら、壊し方ではなくテストを疑う。「複数の経路を区別する」テストの fixture に、経路をまたいで同じ識別子を使わない**——最重要ゲートが**振り分けを逆にしても緑のまま通った**。原因は fixture でコンボ id とセットプレイ id を同じ値に衝突させていたこと（逆にしても集合が同じになる）。**⇒ 集合ではなく「どの id がどちらの経路へ渡ったか」の対応で主張する**(E-218)。[D]
- **「赤くなった」だけでは破壊確認にならない。狙ったテストだけが、狙ったアサーションで赤いことまで確認する**——環境変数の設定漏れによる**全滅を破壊の証拠と読みかけた**(E-230)。[D]
- **「落ちないこと」を主張するテストには、同じ接続で「落ちること」を 1 本添える**——**「5 件とも通った」だけでは「守りが効いていないから通った」と区別がつかない**。緑が何を意味するかを緑自身に語らせる(E-238)。[D]
- **★面が 2 つあるサブは、面ごとに E2E の有無を数える**——「テストが在る」と「経路が通っている」は別。M23-09 のセットプレイ側は**サーバ 13 本・単体 18 本が緑でありながら E2E 0 本**だった。**単体は stub の上で緑になるため経路の断絶を構造的に検出できず、レビューも指示書もこれを欠陥と判定しない（契約としては満たされているため）**(E-228)。[D]
- **読み取り関数の返り値の条件を変えるときは、その関数を「事実の観測手段」として使っている箇所も数える**——実装側の呼び元は全数数えていたが、**テスト側の呼び元は数えていなかった**。主張が変わっていないなら観測手段のほうを差し替える(E-203)。[D]
- **フロントの i18n テストで「キーをそのまま返す `t` モック」を使うと、文面に関する主張は空振りする**——実 `ja.json` を引いて `{{var}}` を差し込む最小の `t` に替える（副産物として**翻訳キーの実在**も守られる）。**既存テストの大半は同じ穴を持つ**(E-207)。[D]
- **flaky を「フレーク」で閉じない。切り分けの最小手は「隔離実行」と「直列実行」の 2 手である**——M23-05 の flaky 2 件は `--workers=1` で緑・既定の並列で 3 failed と**再現条件が判っている競合**だった(E-216)。[D]
- **守るテストが無い変更は黙って劣化する。一度直したものが、より悪い数値で再発することがある**——`P-04` は M19-03 期に一度直したはずが **16 接続中 15 本が FK=OFF**（当時の 7 本より悪い）で再発していた。**根治本体は約 5 行だが、価値の本体は「戻されたことを検出し続ける回帰ゲート」である**。**★そのゲートは書き方を 1 つ間違えると現行実装のままでも緑になる**(E-259)。[D]
- **★★「既知」は「測った」を意味しない。射程も、測るまで分からない**——静的走査と probe が示せるのは「**可能性**」までであり、**実データの計測だけが「起きていた」を示す**（1 年近く「既知の課題」だった `P-04` は、実 DB を開いたら orphan が 19 件実在した）。**★あわせて射程そのものが誤っていた**——失効していたのは `foreign_keys` だけでなく `busy_timeout` と `synchronous` も同じ 15/16 本。**後 2 者は「壊れている」と気づく契機が無い分だけ危ない**(E-257 / E-263)。[D]
- **★★緑のままだったら「その観測は何を見ていたのか」を書く。そこから次の欠陥が見つかる**——「保存直後の遷移で確認が出ないこと」は dirty を落とすのをやめても緑のままだった（通常の保存はガードを通らないため**何も観測していなかった**）。**★この気づきがレビューの重大 2 件の発見の起点になった**(E-281)。[T]
- **★壊し方は「クラスを足す」ではなく「構造を変える」側で選ぶ**——playbook §4.32 (b) は 2 つの理由で破れる。**(a) jsdom は Tailwind CSS を読まないため、非表示クラスを足しても単体テストでは観測が変わらない** ／ **(b) state が親へリフトアップされていると、子のアンマウントは値の消失として観測されない**(E-282)。**★あわせて「型が通る壊し方」を選ぶ**——単純な早期 return は `noUnusedParameters` 等でビルドを落とし、**テストが赤いのではなく、webServer が起動しない**という形になる(E-283。**3 サブで同型**)。[T]
- **★破壊確認・基準値の採取を `head` / `tail` で切らない**——`head -20` で切ったため「Go は全緑」と誤読しかけた（実際は 4 テストが赤）。**★基準値でも同じことが起き、着手前との対照を主張できなくなった**(E-284)。[T]
- **★部分一致のマッチャは、破壊確認を無音で通す**——文字列の**末尾に 1 文字足した**破壊確認が 180 passed で返った（`getByRole` の `name` は既定で部分一致）。**★同型が `toContain` でも起きた。⇒ 置換でやり直して初めて対照になる**(E-285)。[T]
- **★「将来の防御」として置くものには、外れたことを検出する仕掛けまでが一組**——今日は結果を変えない防御は**破壊確認が空振りする**。**「今日は必須でない」防御は、外れても誰も気づかない**(E-286)。**★破壊確認は「効いていない側の観測」も返す**——赤くなったのが自分の足した観測 1 本だけなら、その事実を隠さず書く。**「効いていることを示せた」で止めると後任は射程を誤解する**(E-287)。[T]
- **★破壊確認は「どの経路が赤くなったか」を数えると、統合の完了を証明できる**——統合後の 1 本を壊して**3 経路すべてが赤・赤くならない経路 0 件**を数えた。**「テストが赤くなった」では、経路が 1 本だけ繋がっていない状態を見逃す**(E-288。**正の教訓**)。**★統合前の実測値を統合後のテストの期待値に据える**——統合**前**にプローブで値を採り golden として固定すると、**レビュー担当が独立に再計算して裏取りできる**(E-310。**標準手順にする価値**)。[T]
- **★回帰の検出器には `retries: 0` を宣言する**——既定が `retries: 1` のままだと、**捉えるべき変更が入っても「1 回目は赤・retry で緑」で終了コード 0** になり、検出器が黙って効かなくなる(E-289)。[T]
- **★★「テストが効いているが、対象が違う」型（M24 期に 12 件）**——**(a) 引数の意味が変わっても、テストが旧い使い方を固定していれば緑**（型も両方 `Record<string,string>` で効かず、フォールバックに偶然救われていた。**⇒ 契約が変わったら型で分けられないかを先に考える**＝E-291）／**(b) 辞書だけを走査するテストは「コードが合成した文字列」を守れない**(E-292)／**(c) 要求が N 面に及ぶなら網が N 本あるかを数える**（チェックリストは「2 面」と書いていたが**テストの数は数えていなかった**＝E-293）／**(d) 「共通部品へ通した」だけでは守られない**（直書きへ差し戻しても全緑＝E-294）／**(e) テスト名は「守られている」という記述として機能する**（名乗っている操作を実際にはしていなかった＝E-295）。[T]
- **★単体実行の緑は、通し実行の緑を意味しない**——jsdom の `history.go(-1)` は非同期で、cleanup 後に popstate が**次のテストへ流れ込んでいた**(E-296)。**★フィクスチャが「既定状態」を表しているか確かめる**——名前が紛らわしい定数はフィクスチャ側で取り違えられる(E-297)。[T]
- **★「唯一の観測である」と書くときは、消費側が本当にそれを見ているか確かめる**——押さえたのは WARNING 側だが**フロントは `severity !== "error"` を捨てる**ため、実際の唯一の生産者は ERROR 側だった(E-300)。**★`BEGIN IMMEDIATE` があると「直っていなくても緑」になる**(E-299)。[T]
- **★実測は同一セッション内の背中合わせだけを根拠にする。別時点の値どうしを引き算しない**——与えられた母数が今日は再現しなかった(E-319)。**★環境が変われば再現率は変わる**（一次源「10 回中 1 回」が本環境では 7/10。**「出やすくなった」も環境差である**＝E-320）。**★確率的な再現手順を「決定論的」と呼ばない**——用語が一段ずれたまま次工程へ渡ると、原因究明に時間が溶ける(E-321)。**★実機で出た症状は、同じ入力で再現できるまで原因を断定しない。仮説の質が高いほど確かめずに書きたくなる**(E-322。`E-243` の実装層版)。[D]
- **「実物が無くて確かめられない」ときは、実物の何が効いているのかを 1 段分解する**——再現できる部分が残ることが多い（実 DB を持たない環境で「できない」で終わらせず、素の接続で残骸を仕込む形へ置き換えた）(E-237。正の教訓)。[D]

- **対照が赤くなるだけで、主要な主張が守られたとは限らない**。主張ごとに入力条件・通る経路・壊す箇所・落ちる assertion を対応付ける。空データ、実データに無い分岐、新しい呼出元、ビルド変数から成果物への接続も見る。本期間 **11 サブ**で到達範囲のずれを観測。式を別に書いても分類集合を写せば独立な対照にならない（E-331/E-341/E-343/E-344/E-358/E-370/E-373/E-384/E-390/E-425/E-426/E-435/E-444/E-482、E-473）。[T]

  書き換えると「実装済み」と読める(反映工程委譲=パターン D の裏返し)。着手前ゲートの通知書はステータス欄に「起票(反映案・着手前ゲート)」と明記する
  (M17-D10=CHANGE-068 メディア 3 列を着手前ゲート起票・DES 反映は実装後)。[D]
- **「A か B か」を机上で決める前に、そもそも適用面があるかを実測で確かめる。判断の選択肢は 2 つではなく
  「決める必要がない」という第三の結論があり得る**——materialize のダメージ丸め規則は実測 10 件がすべて非始動技
  =適用面なしと判明し規則自体が不要になった。机上で四捨五入を選んでいたら**存在しない問題に対する規則を
  正典化していた**(E-41。正の教訓・「実測が出るまで確定させない」運用の成果)。[D]
- **候補集合を動かす変更は、実装を確定する前に実データで増減を測る。測る前に判定法を決めない**——見込み値は繰り返し失効した（除外は 3 行の見込みに対し実測は桁違い／ある案は見積りの 2.7 倍）。**★「どう除去するか」を決める前に「何が問題か」を測る**——測る前に判定法を決めると、**問題の所在が変わったときに判定法だけが残る**(E-123。E-41 の一般化)。[D]

- **スコープ外の指定は「検討してはいけない」ではなく「このサブでは決めない」である。裁定に影響しうる選択肢は 設計伝達レポートへ書き出す**——`M22-07` は指示書がスコープ外にしたため E 案を検討から外していたが、裁定の場では E が最有力になった。**書かなければ次の担当は「A / B / C しか無い」と読む**(E-178)。[D]
- **「対策 A と対策 B の多層防御」を書くときは、片方だけが実装された状態を検出する機構を同時に決める**——`X-Requested-With` は付ける側だけが実装され、**検証側が無いので増えても何も起きず 6 経路まで複製され、2 年近く残った**。 **★動作は正しいままなので、テストも lint も型検査も緑になる**(E-166)。[D]
- **射程を広げるときは黙って広げず、広げた事実を明記する**（新規採番はしない先例あり）。**★あわせて「どちらでもよい」と書いた選択肢が、実装では選択肢でないことがある**——「1 文でも 2 文でもよい」と書いたが実装では 1 文にできなかった。**順序は制約であり選択ではない**(E-246)。[D]
- **達成できない数字を契約へ書くと、以後その検査は常に未達として扱われる**——受入条件の数値は as-built の実測から決める。**★あわせて「速く終わった」は「速い」ではなく「走っていない」ことがある**——結果キャッシュの無効化を付けないと**実行していないのに緑になり、所要が 3 桁違っても終了コードはどちらも 0**(E-247)。[D]
- **新しいスラッグを作る前に、原因が既存行そのものでないかを見る**——新規スラッグを作ると、**原因と症状が別行に分かれて追えなくなる**(E-251)。[D]

## 7. 自身の文書の内部整合(出力前セルフチェック)[T:出力前セルフチェック]
- 同一指示書内で同じ概念に異なる型/命名が混在しないか grep(M4-3)。
- §1.3 スコープ外宣言で除外したキーワードが §5.2/§7 に残っていないか grep(M4-6)。
- 本文の「Plan Mode で確定」「開発者協議で決定」が §3.4.7 必須項目リストに明示列挙されているか(M6-2)。
- 自分が過去に書いた仕様を別指示書で参照するときは原指示書 §4.x を逐語確認(M4-16)。
- 出力前 grep 校正に「簡体字・禁則表現」だけでなく **頻出ドメイン用語の誤字(`grep 起き攻け`)＋『DR』略記
  (画面ラベルは『ドライブラッシュ』が正。`OKI_USES_DR_LABEL` 等コード定数・規約引用は除く)** を毎回必ず実行する。
  置換スクリプトのプレースホルダに置換対象文字列(`DR` 等)を含めない(M16-7=長セッションで用語校正の穴が 3 回再発)。[D]
- **合計・件数・行数・寸法を DES/指示書に書くときは「何を・どの単位で数えたか」を必ず併記する**(「28」=出力行か
  チェックボックスか。M17-E16)。**向きラベル(「A4 横」)と絶対値(「1122px 原寸」)を並記したら px/mm を揃えて高さ・幅を検算する**
  (M17-E18 = A4 横の高さ 794px に 1122px 原寸は入らない矛盾を検算せず見逃した)。**件数にはさらに「基準時点」と「一次源か参考値か」も併記する**——外部要因で増減する母数(実装完了件数等)は一次源にしない(M18-E24、M17-E16 の拡張)。[D]

- **「機械的に固定した」と書くときは、走査範囲を同じ文に書く**——「禁則語は全文言で 0 件（機械的に固定）」と書いたが 実際の走査は 1 組だけだった。**違反は 1 件も無く、問題は記載が実態より広く読めることである**(E-157。`E-106` の自己適用)。[D]
- **否定形確認は「区分」で終えず「列挙」まで行い、実査したものと未実査のものを分けて書く**——存在しない §7 を「失効」と 名指しした例がある。**未実査は「未実査」と書けばよく、それ自体は欠陥ではない。断定だけが欠陥である**(E-181)。 **★あわせて、既存の安全性・不変条件を述べた文を自分の差分が偽にしていないか確かめる**（grep で「無し」「のみ」「しない」を 含む近傍を当たるのが安い＝E-187)。[D]
- **★★工程順として「まだ無い」ものを、完了報告に過去形で書かない**（**M24 期に 4 サブで再発**＝`E-189` / `E-193` / `E-242` の続き）——`progress-log` の索引行・設計伝達レポートは**レビュー後の工程の成果物**であり、完了報告を書いた時点では存在しない。**★工程順としては正しく、誤りは申告の側だけである——だからこそ気づきにくい**(E-272)。**★機構は半分だけ在る**（`implement_plan.md` の索引行テンプレートはプレースホルダ化済み。**残るのは完了報告本文側**）。[T]
- **★★回していない検査の結果を報告へ書かない**（**2 サブ連続**）——検査表に「違反なし」と書いたが**索引行を追記しておらず検査も回していなかった**。**★しかも落ちたのは、その教訓が書かれているファイルへの追記そのものである。** **⇒ 「検査表は実際の出力から埋める」と書くだけでは 2 回落ちた。機構案＝各行に標準出力を 1 行貼る形にする（貼れないものは書けない）**(E-273)。[D]
- **★検査は「報告書を書いたあと」にもう一度回す**——`check-md-emphasis.sh` は実装完了時点で緑だったが、**報告書を書いたことで赤に転じた**（増えた行はすべて報告書自身）。**「書く前に採る」の裏返し**(E-274)。**★整形した文字列を「出力」として載せない。逐語でないなら「出力」と書かない**(E-275)。[D]
- **★★「済み」と書く前に、その成果物が実在するかを見る。走査で「見つけた」ことと「直した」ことは別の事象である**（**M23 期に 3 度再発**＝E-189 / E-193 / E-242）。**機械検査の緑は「書いた」の証拠にならない**（`check-progress-log-index.sh` は本文中の言及でも緑になる）。**⇒ 章立てを先に書く運用では、未実施の節に「済み」と書かず未来形にする。否定形走査の節は「検出した箇所」と「手当てした箇所」を別の表にし、後者は変更ファイル一覧の実出力から起こす**（記憶から書かない）。[D]

## 8. 分業（設計卓 ⇄ 製造 ⇄ 個別設計）と伝達手段 [D]

> **M19 期（親チャット方式）で新設。** 設計卓が repo の現物を直接見られない構造から生じる型を集めた。
> **E-88〜E-98 のうち 7 件、E-102〜E-123 のうち 5 件は設計卓自身の誤りの記録である**——「誰かが間違えた」ではなく
> **「この役割は構造的にこの形で間違える」**という記録として読むこと。
> **【2026-08-12 更新】反映レーンは 2026-08-11 に廃止され、設計卓の面は Claude Code へ移った。**
> **本節の型は消えていない**——**見えるようになったのは `docs/` だけで、実装ソースの確度は移行前と同じ**（playbook §12.0）。
> **むしろ「docs が見えているのだから実装も見えているつもり」という新しい誤り方が加わる。**
> 委任先が反映係からサブエージェント・個別設計チャットへ変わっただけで、**発行側と適用側が分かれる構造は不変。**

**■ 正典・写し・追跡表**

- **正本を改訂したとき、写し側は「注記を足す」だけで済ませない。コピーされる形（コードブロック・表・定義文）そのものを正本に揃える**——**人はコードブロックをコピーし、注記は読まない**(E-90)。[D]
- **「§X 欄のみ」と範囲を限定するときは、同じ正典内に同じ記述が無いかを先に確認する。確認していないなら範囲を限定せず「同じ記述の全出現箇所」と書く**。**適用側は、範囲外だが当てないと正典が自己矛盾する場合、当てたうえで「委任範囲の外縁」と報告する**(E-91)。[D]
- **同じ情報を 2 か所に持つと必ずドリフトする。「合わせる」の前に「片方を消せないか」を検討する**——追従は原因を残したまま症状を消す対処(E-76。204 件中 51 件=25% が不一致だった)。[D]
- **版マニフェストの実査は 2 方向で行う**——**(a) 載っている行 → 現物**（版・文書名の一致）／**(b) 現物 → 載っている行**（収録基準に合う文書がすべて載っているか）。**「今回動いた版だけ直す」では止まらない**（参照元が増え続けるため差分ベースでは追えない）。**(a) だけでは収録漏れを検出できない**(E-94。1 レーンで 5 か所の虚偽)。[D]
- **要約を「状態の正本」にしない**。どうしてもそうするなら、**要約と原本を機械的に突合する手順を配布の前に置く**(E-87)。[D]

**■ 指示媒体の一貫性・発行の粒度**

- **同一対象への指示は、台帳・依頼文・パッチの 3 者を突合してから発行する。★台帳は依頼文と同じ強さの指示媒体である**——「作業台帳だから緩くてよい」ではない。**台帳に書いた撤回は、撤回対象の本文にも当てる**(E-95)。[D]
- **是正は「作業をブロックするか」で分ける。ブロックしないものは束ねる**——判定軸は「早いほうが良いか」ではなく**「遅れると次の作業が誤った前提で進むか」**。**発行側の「1 件増えただけ」は、適用側では「1 サイクル増えた」になる**(E-74)。[D]
- **「前提」と「順序の指定」を書き分ける**。依存でないものを前提と書くと**適用者は正しく止まり、そのぶん往復が増える**。**適用者の律儀さは資産であって、そこへ不要な停止条件を置くのは発行側のコスト**(E-79)。[D]
- **成果物には複数の経路がある（パッチは適用報告が返る／全文の文書は開発者が配置する）。経路ごとに「着地したか」の確認手順が要る**。**★他の文書からその文書を参照するパッチを出すときは、参照先が着地しているかを先に確認する——参照は着地より先に書ける**(E-78)。[D]

**■ 数字・検査・部分着地**

- **数字を報告する側は「どこからどこまでを数えたか」を併記する。受け取る側は裁定文へ埋め込む前に 1 度検算する**——**裁定文に入った数字は生きた台帳へ転写される**(E-93＝337 行と報告し実測 75 行。4.5 倍)。[D]
- **検査が「0 件」を返したら、検査が動いていることを先に確かめる**——「0 件」は (a) 対象が無い (b) 検査が対象を見ていない の 2 通りに読め、**出力が同一**。**検査には「見つかった件数」だけでなく「検査した件数」を出させる**(E-84)。**★正の実例**——`check-md-emphasis.sh` は依存不在時に「未実行として非ゼロ終了・緑を返さない」陽性対照を自ら持っており、そのとおり赤を返した。**「回せなかった」を「問題なし」と同じ出力にしない**(E-134)。[D]
- **症状の説明は推論ではなく実測で書く。説明の粗さはテストの弱さに直結する**——不具合を推論で「次々と別の対象へ割り当たる」と説明したが、**実測では衝突検出が 2 件目で止めるため、実際に見えるのは確認ダイアログだけ**だった（開発者の「イメージがついていない」で初めて実物を確認）。**★「暴走しないこと」だけを主張したテストはガードを外しても緑で、「衝突が出ないこと」まで主張して初めて固定できた。** **⇒ 症状を推論で書くと、その推論の粒度でしかテストが書けない**(E-128。**E-117** の実装層版)。[D]
- **凍結された層の隣に新しい層を作るとき、「重複を避ける」より「凍結を守る」が優先することがある**——既存導線を一般化すれば重複は消えるが、それは凍結指定に正面から触れる。**⇒「別に持つのは重複ではなく、凍結を守るための帰結である」と理由を明示する。** **★理由を書かないと、次の担当が「重複だから統合しよう」と正しく見えるかたちで凍結を破る**(E-129。**E-105** の対)。[D]
- **部分着地には 5 つの形がある**——(1) 版ログにあるが本文に無い (2) 空マーカーだけ残る (3) 本文はあるが描画されず読めない (4) **本文はあるが別の文脈に読まれる**(E-75。既存の箇条書きの途中に見出しを挿入すると後続項目が黙って配下に移る。**「途中に挿入する」操作そのものが危険**) (5) **本文はあるが強調が反転し記号がリテラル描画される**（検出＝**変更行の強調記号の個数が偶数か**）(E-97)。**★形 3 の検出でコードスパン内を保護扱いにすると捕まらない**——**GFM は表のセル分割をインライン解析より先に行うためバッククォートでは保護されない。エスケープ表記はコードスパンの外に置くしかない**。[D]
- **指示を実行できても目的を達成できないなら、実行せずに報告する**（**正の運用事例**）。**発行者は実行環境を見ていないため、この判断は適用者にしかできない**(E-77)。[D]
- **「現物 → 台帳」方向の実査は、除外の判断を書かないと収束しない**——(a)**台帳 → 現物**は drift を検出し**毎回ゼロに収束する**が、(b)**現物 → 台帳**は漏れを検出し、**意図的な除外を記録しないかぎり次の実査で同じものが再検出される**。**収録しないと決めた分を否定形として収録基準へ書く。否定形の記録は検査を安くするための投資である**(E-120。E-94 の (b) 方向の続き)。[D]
- **検査の対象を、本文で使う記号と同じにしない**——転記待ちのプレースホルダに通常の約物と同じ記号を使ったため「適用後確認＝当該記号が 0 件」が字義どおり成立しなかった。**判定が正しかったのは適用者が中身を読んだからで、機械検査は機能していなかった**。**「X が 0 件であること」を確認項目に置くなら、X が本文に現れない保証をセットで作る**(E-119)。[D]
- **版を上げたら、その改訂を運ぶ文書自身の中の参照も全数 grep する**——項目数を広げたとき**タイトル・本文の件数・末尾の締めを直し損ね、メタ表だけが新しい版だった**。**メタ表と本文が食い違う文書は、受け取る側に「どちらが正か」の判断を強いる（受け取る側は現物を持つが、発行者の意図は持たない）**。**★最善手はそもそも写さないこと**——**生きた表の行数は、裁定文が持ってよい種類の数字ではない。裁定文が持ってよいのは変わらない事実（判断・規律・根拠）であり、計数は台帳が持って参照側は都度実査する**(E-118。E-94 の自己適用版)。[D]

**■ 発行側が漏らすもの・断定してはいけないもの**

- **発行側は凍結条項を列挙し損ねる。解除表は「漏れる」前提で作り、適用側に全数突合させる**——解除表が 3 本しか挙げていなかったが、当該サブが必ず触れる条項が 2 本あった（製造が契約の全数列挙との突合で検出）。**★報告では「触れたが凍結対象外である」を「触れていない」と書かない**——後者と書くと後任は参照の変更に気づけない(E-105)。[D]
- **「根拠が無い」と書くときは、どの資料の範囲で無いのかを同じ文に書く**——「根拠が無い」と書いたが正しくは**「名前はあるが仕様が無い」だった**。**範囲を書かないと、台帳へ入った時点で「どこにも無い」と読まれる**。**★あわせて参照可資料を着手後に広げない**（仕様が無いものを実装させると**製造が仕様を書くことになる**）(E-106。E-70 の範囲明示の具体化)。[D]
- **「既存の X と同じ」と書くときは、X の実体を 1 段だけ具体化する**——設計書が「項目 10 と同じ 2×2 グリッドを再利用」と書いたが**参照先の実装は横並びで 2×2 が画面に現れていなかった**。次のサブが流用して乖離が伝播した。**レビューチェックリストは項目を持っていたが参照先の確認で通ってしまい、開発者の目視でのみ捕まった**。**★UI の構造は自動テストにもレビュー報告にも映らない**(E-115。E-90 の参照先側)。[D]
- **委任するとき「一意に定まる」は判断であり、判断は誤りうる**——委任の条件 3 つ＝**(A) 事後報告に「何を根拠に一意と判断したか」を書く／(B) 一意に定まらないものは当てずに上げる（委任は「止まらなくてよい」ではない）／(C)「消す」変更を伴わない**。**★委任の根拠は「止める判断の質」である**。**★「参照先が実在すること」だけで一意と判断しない**——実在したうえで内容が違い、正しい指し先が当時存在しなかった例がある(E-122)。[D]
- **古い記述の扱いは 3 分類。一方の結論をもう一方へ持ち込まない**——**(1) 生きた設計文書＝本文を正本へ揃える**（**旧本文を残すとそれが実装される。実装者はコードブロックをコピーし注記は読まない**）／**(2) 裁定行＝書き換えず errata 注記**（当時どう判断したかの記録）／**(3) 完了済みサブの指示書＝書き換えず撤回マーカーを 1 行**（**実装指示としては読まれないが検索には当たる**）。**軸は「これから実装されるか」と「記録としての価値があるか」の 2 つである**(E-111)。[D]
