### 1-1【最重要・仕様追加】「区分を判定できない反撃」セクションの新設(指示書 v1.0.1 に無い)

**指示書の穴を製造が検出し、開発者裁定を得て実装した。** 指示書側にも事後反映が要る。

- **事象**: 探す画面の「確定反撃に採用」は `hit_type` を見ない(`web/src/features/punish/components/PunishTree.tsx` の採用ボタン、および母集合の `combo.List(ListFilter{CharacterID, StarterMoveIDs})` とも `hit_type` で絞らない)。したがって `hit_type` が `normal` / `counter` / **NULL** のコンボが `combo_punishes` に入り得る。
- **指示書 §4.3-3 の「hit_type でタブ絞り」を literal に実装すると、それらはガード／ジャストパリィどちらのタブにも出ず黙って消える。** 指示書 §4.4-1 は `combo_punishes` に入るのが PC 系だけであることを暗黙の前提にしていたが、その前提は成り立たない。
- **開発者裁定(2026-07-26)**: 件数を出す案を採用。**条件 3 つ**(すべて実装済み):
  1. 件数だけでなく**展開して中身が見える**(折りたたみで相手技・コンボ・`hit_type` バッジ)
  2. **理由と次のアクション**を書く(「ガード始動／ジャストパリィ始動のどちらか判定できない記録です。パニッシュカウンター版に変換すると、上の一覧に出ます。**変換機能は M18-03b で対応予定です。**」)
  3. **3 つ目のタブにしない**。`hit_type=normal` は「ガードかジャストパリィか判定できない」＝タブと同じ軸に並ぶものではないため、**両タブ共通で画面下部に 1 セクション**。見出しは **「区分を判定できない反撃(N 件)」**(「その他」は理由が伝わらないため不可)
- **ドメイン上の位置づけ(設計に効く)**: このバケツは **M18-03b の materialize が処理すべき入力キュー**であり、ゴミ箱ではない。確定反撃は相手の硬直中に当てるため本来 PC 系であるべきで、そこを埋めるのが materialize である。
- **API 契約への影響**: `GET /api/punish-list` のレスポンスに **`unclassifiedNodes`**(`nodes` と同じ `MoveNode` 構造)を追加した。`guard` に依らず内容は同一。
- 根拠: `internal/service/punishlist/service.go`(`punishHitTypes` / `List` の 3 分岐)、`web/src/features/punish/components/PunishList.tsx`、テスト `TestList_UnclassifiedHitTypes`(normal / counter / **NULL** の 3 パターン)、E2E `web/e2e/m18-03a-punish-mylist.spec.ts` の test C。

### 1-2【最重要・スコープ外変更・**開発者承認済み**】共有 Header の nav がナビ 13 本目で破綻したため degrade を追加

- **事象**: 指示書 §2.1-11 のとおり `NAV_LINKS` に「確定反撃マイリスト」を 1 行足したところ、**既存 E2E が 15 本失敗**した。原因は nav が 13 本目で 1280px 幅(Playwright の Desktop Chrome)に収まらなくなり、**はみ出した nav が本文を覆って全画面のクリックが通らなくなった**こと。nav リンクを一時的に外すと 15 本すべて green に戻ることで因果を確定した。
- **対処**: `web/src/components/Header.tsx` のデスクトップ nav に **`min-w-0 overflow-x-auto whitespace-nowrap`** を追加し、はみ出しを nav 内の横スクロールに閉じ込めた。**収まる幅では見た目は従来どおり**で、既存 E2E は全 green に復帰。
- **スコープ外に踏み込んだ理由**: リンク追加は指示書の要求であり、それが**全画面のクリックを壊す**以上、リンクだけ足して放置する選択肢が無かったため。変更は 1 クラス文字列の追加に留めている。
- **設計上の含意**: 本件は「**グローバルナビの項目数に事実上の上限がある**」という制約が顕在化したものである。今後もマイルストーンごとに画面が増えると同じ壁に当たる。
- 根拠: `web/src/components/Header.tsx`(`NAV_LINKS` は 13 項目。デスクトップ nav とモバイル Sheet ドロワーが同一配列を map)。
- ⇒ **DES-005 の共通ヘッダ記述に「nav が収まらない場合は nav 内横スクロールへ degrade する」を明記してほしい。** あわせて **「グローバルナビの項目数上限と、超過時の情報設計(カテゴリ化・ドロワー常用化等)」を設計課題として起票**いただきたい。代替案として「デスクトップ nav の表示ブレークポイントを上げてドロワーへ倒す」があるが、1280〜1535px の利用者が横並びナビを失うため製造では採らなかった。**2026-07-26・開発者が実機確認のうえ本方針を承認済み**（「Header ナビの degrade 方針はこれで良い」）。ただし §3-2 の**ナビ項目数上限の情報設計は設計課題として残る**。

### 1-3 `GET /api/punish-list` のレスポンス構造(製造が確定)

指示書 §4.6 は「マイリストのツリー ＋ 隠したもの一覧を返す」までを規定し、構造は未定だった。以下で確定した。

```
{ selfCharacterId, opponentCharacterId?, guardType, hitType,
  nodes: [ MoveNode ],              // 現タブ(hit_type 一致)
  unclassifiedNodes: [ MoveNode ],  // §1-1。guard に依らず同一
  hiddenPrunings:  [ { opponentMoveId, code, nameJa?, opponentCharacterId, opponentCharacterNameJa, note? } ],
  hiddenCurations: [ { comboId, opponentMoveId, code, nameJa?, opponentCharacterId,
                       opponentCharacterNameJa, starterMoveCode?, starterMoveNameJa?, note? } ] }

MoveNode  = { moveId, code, nameJa?, opponentCharacterId, opponentCharacterNameJa, combos: [ ComboNode ] }
ComboNode = { comboId, damage?, stepCount, hitType?, starterMoveId?, starterMoveCode?, starterMoveNameJa?, note?, recipe? }
```

- `hitType`(トップレベル)は `guardType` に対応する `combos.hit_type` の実値を返す。FE が対応表を持たないための配慮。
- `recipe` は既定プリセットのレシピ表示文字列(`combos.recipe_cache` から抽出。欠損時は省略)。**2026-07-26 の開発者フィードバック 7 で追加**。`GET /api/punish-finder` 側の `ComboNode` / `RegisteredComboNode` にも同名で追加した。
- 空配列は `null` でなく `[]` でシリアライズする(既存 `Tree` と同じ流儀)。
- 根拠: `internal/service/punishlist/service.go`、`web/src/features/punish/types.ts`。
- ⇒ DES-002 §4.2 に本構造を反映してほしい。

### 1-4 `GET /api/punish-finder` の拡張は `registeredCombos` を**別型**で追加

- 指示書 §4.5 は「登録済みの `combo_punishes` を配下に表示」までを規定。製造は `ManualReviewNode` に **`registeredCombos: RegisteredComboNode[]`** を追加した(既存フィールドの意味・型は不変＝後方互換)。
- **成立ツリーの `ComboNode` と型を分けた**理由は、`RegisteredComboNode` が `adopted`(採否トグルの状態)を持たず「登録済みであること自体」しか意味しないため。同一型に畳むと採否の意味が曖昧になる。
- **絞り込みを一切かけない**ことを確定した(指示書は silent):
  - **curation で絞らない** — curation は「使う」画面の表示制御であり、探す画面では登録済みの事実をそのまま見せる(§4.1 の役割分担に沿う)。
  - **`hit_type`(タブ)で絞らない** — タブは走査の判定根拠であって手動登録された反撃の区分ではない。絞ると登録済みが黙って消える。
- 根拠: `internal/service/punishfinder/service.go`、テスト `TestScan_ManualReviewShowsRegisteredCombos` / `TestScan_RegisteredCombosDoNotLeakIntoAcceptedTree`。
- ⇒ DES-005 §5.20 に「登録済みは curation・タブのいずれでも絞らない」を明記してほしい。**ただし「既知の限界 2 を解消済み」とは書けない**。表示側は完成しているが、**そこへ至るデータを UI から作れない**ため、ユーザーから見た限界は残っている(§3-9)。**「表示側は実装済・登録導線は M18-03b」**の形で反映されたい。

### 1-5 隠したもの一覧のフィルタ規則(製造が確定)

| 一覧 | `opp`(相手キャラ)で絞る | `guard`(タブ)で絞る | 論理削除済みコンボ |
|---|---|---|---|
| `hiddenPrunings` | **絞る** | **絞らない** | (コンボ非依存のため対象外) |
| `hiddenCurations` | **絞る** | **絞らない** | **除外する** |

- `guard` で絞らない理由: pruning は区分(ガード/ジャストパリィ)に依らない事実であり、curation もタブで消えると「隠したのに管理画面で見つからない」という新たな片道操作を生むため。
- `hiddenCurations` から論理削除済みコンボを除外する規則は指示書に無い(マイリスト本体の §4.3-2 と扱いを揃えた)。`ON DELETE CASCADE` は**物理削除**にのみ効き、論理削除(`deleted_at`)では curation 行が残るため明示除外が要る。
- 根拠: `internal/repository/punish/queries.go`(`listCurationsBaseSQL` の `c.deleted_at IS NULL`)。
- ⇒ DES-005 画面21「隠したもの管理」に上表を明記してほしい。

### 1-6 `DELETE /api/combo-punishes` の curation 連動削除を**リポジトリ層**に置いた

- 指示書 §4.1 は「同一トランザクションで削除」を要求。製造は `internal/repository/punish/crud.go` の **`RemovePunish` 自体をトランザクション化**した(サービス層ではなく)。
- **効果**: `punishfinder` 経由の既存 `DELETE /api/combo-punishes` が**シグネチャ不変のまま**自動的に孤児を作らなくなる。将来 `RemovePunish` を呼ぶ経路が増えても取りこぼさない。
- 原子性は「curations 表を DROP して 2 文目を失敗させ、`combo_punishes` の行が残る」テストで固定(`TestRepository_RemovePunish_AtomicOnFailure`)。
- ⇒ DES-002 §4.2 の既存 endpoint 挙動追記に「連動削除はリポジトリ層で担保(呼び出し経路に依らない)」を添えてほしい。

- **空状態**: 自キャラだけ選んだ状態で「まだ確定反撃が登録されていません。」＋「確定反撃サーチで採用するとここに出ます。」のリンクが出て、**リンクから探す画面へ行けるか**。
- **2 階層ツリー**: 相手技の行ヘッダー全体(シェブロン+技名+相手キャラ名+件数バッジ)をクリックして開閉できるか。探す画面と同じ操作感か。
- **コンボ行の情報量**: 始動技・ダメージ・手数・`hit_type` バッジ・メモが 1 行に並ぶ。**横に長すぎないか**、折り返しが不自然でないか。
- **始動技で階層を切っていない**(探す画面の 3 階層と非対称)ことが、使う場面で自然か。

### 6-5 タブ 2 軸の分かりにくさ(§2-2 の推測)

上位タブ[確定反撃マイリスト / 隠したもの管理]と、その下のタブ[ガード / ジャストパリィ]の **2 段構成**は製造の推測。

- 2 軸あることが**直感的に分かるか**。上下で意味が違うタブが並ぶ違和感がないか。
- 「隠したもの管理」に切り替えるとガード/JP タブが消える挙動(区分に依らないため)が自然か。
- 別案(アコーディオン化・サブナビ化等)が望ましければご指示いただきたい。

### 6-6 相手キャラ絞りの「すべての相手」ボタン

共有 `CharacterSelector` に解除操作が無いため、選択中のみ横にボタンを足した(§2-2)。

- 相手キャラを選ぶ→「すべての相手」ボタンが現れる→押すと絞りが外れる、が**直感的か**。
- ボタンが出たり消えたりする挙動が煩わしくないか。

### 6-7 探す画面の非回帰(E-14)

- 「自動判定できない相手技」(飛び道具など)に確定反撃を登録した状態で `/punish/search` を開き、配下に **「登録済みの確定反撃」** 見出しで出るか。
- **成立ツリーの候補と混ざって見えないか**(フレーム判定の結果ではないと分かるか)。
- 既存操作が回帰していないか: 始動技の採否トグル・pruning ボタン・**note 入力欄 2 系統**・「前提と限界」ヒント・新規登録導線。

### 6-8 トーストの文言

成功/失敗の文言が状況に合っているか。「使わない反撃として隠しました」/「確定反撃の採用を解除しました」/「再表示しました」/(失敗時)「解除に失敗しました: …」。
