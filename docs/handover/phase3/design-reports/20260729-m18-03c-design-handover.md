## §1 製造が独自に確定した実装仕様（DES 反映が要るもの）

### 1-1【最重要・実機確認で確定】両登録レーンは入力を固定し、自動採用だけを手動確認レーンへ限定

確定反撃サーチからコンボ新規登録へ進む 2 導線は、最終的に次の非対称で確定した。

| 導線 | 検索キャラクター | `hit_type` | `combo_punishes` 自動採用 |
|------|------------------|------------|---------------------------|
| 成立ツリー「このコンボを新規登録する」 | 固定 | ガード=`punish_counter` / ジャストパリィ=`just_parry_punish_counter` に固定 | **しない**。保存後、探す画面で利用者が明示的に採用 |
| 手動確認レーン「手動で確定反撃を登録」 | 固定 | 同上 | **する**。保存後に既存 `POST /api/combo-punishes` を呼ぶ |

実装上は `punishSelfCharacterId` と `hitType` を両導線で渡し、`opponentMoveId` だけを手動確認レーンへ渡すことで責務を分けた（`web/src/features/punish/components/PunishTree.tsx:100-124`, `:404-418`, `:550-561`）。`ComboEditor` は検索文脈を検証したうえでキャラクターとヒット種別を固定表示にする（`web/src/features/combo/components/ComboEditor.tsx:79-117`, `:520-545`、`ComboEditorCharacterField.tsx:20-46`、`ComboEditorBasicFields.tsx:233-252`）。

自動採用の防御として、保存要求時または保存結果のキャラクターが検索条件と異なる場合は、コンボを保存したまま紐づけをスキップして理由を通知する（`web/src/features/combo/components/ComboEditor.tsx:371-398`）。これは UI 固定を将来別経路が迂回しても、別キャラの `combo_punishes` を作らないための多層防御である。

根拠テスト:

- `PunishTree.test.tsx`「成立ツリーの新規登録はキャラと hit_type を固定するが、自動採用用の相手技は渡さない」（`:154`）
- `ComboEditor.test.tsx`「成立ツリー経由はコンボ保存だけを行い、確定反撃へ自動採用しない」（`:840`）
- 同「保存結果のキャラが検索条件と異なる場合は紐づけず詳細へ退避する」（`:872`）
- E2E B / C（`web/e2e/m18-03c-drainage.spec.ts:292`, `:355`）

⇒ **DES-005 §5.20 と §5.7 に「確定反撃サーチ経由では両導線とも検索キャラクターとタブ別 `hit_type` を変更不可とし、手動確認レーンだけが保存後に確定反撃へ自動採用する。成立ツリーはコンボ保存のみで、採用は探す画面から明示操作する」と明文化してほしい。**

### 1-2【最重要・実機確認で確定】materialize 新規生成の長文通知は、読み終えるまで残し右上の×で閉じる

新しい PC 版を生成したときの説明は、計算前提と注意事項を含み既定表示時間では読み切れなかったため、**当該通知だけ**次の契約へ変更した。

- `duration: Infinity` で自動消去しない。
- 閉じるボタンを表示し、一般的な配置である**右上**に置く。
- 「開く」操作は維持する。
- FR301 で既存 PC 版を返しただけの経路は生成結果ではないため、この長文通知を出さない。
- 共通 `Toaster` と通常の短い通知の表示時間・閉じる位置は変更しない。
- 連続生成では、通常加算／counter 変換を `materialize-result`、加算スキップ（SA／CA・値欠損・未知理由）を `materialize-result-attention` へ固定する。同種は最新 1 件へ置換し、永続通知は最大 2 件とする。
- 加算スキップ理由は通常結果から回復しにくいため、通常結果では置換しない。次の加算スキップ結果だけが説明文と「開く」の対象を更新する。

通知の共通挙動は `MATERIALIZE_RESULT_TOAST_BEHAVIOR`、結果別 ID は `materializeResultToastBehavior` に集約し、`PunishTree` と `PunishList` の新規生成時だけ適用する。右上配置は専用クラスの CSS 変数だけで上書きしている。

E2E A は、専用クラス・CSS 変数・実座標の右上・5 秒後も表示継続・×で消えることを固定する。E は同種 2 回で 1 件へ置換され、文言と「開く」が最新生成物へ更新されることを固定する。F は 390×844 で SA／CA→通常→値欠損を連続生成し、通常／要注意の 2 件に収まり、3 回目の操作が通知に妨げられないことを固定する。共通通知の仕様変更ではない。

⇒ **DES-005 §5.21 の materialize 結果通知に「新規生成時の説明は自動消去せず、右上の×で閉じるまで表示する。生成物を開く操作を併置する。既存一致時と他の短い通知には適用しない。連続生成時は通常／要注意の固定 ID で各 1 件へ置換し、最大 2 件とする」と明文化してほしい。**

### 1-3【利用者への説明契約】自動ダメージ変更を計算前提から説明し、全生成結果で実測調整を促す

利用者は materialize がダメージを自動変更することを事前に知らない、という開発者所見を受け、単なる「概算です」ではなく生成結果別に前提から説明する形へ確定した（`web/src/constants/punish.ts:72-112`）。

| 結果 | 説明契約 |
|------|----------|
| 通常加算 | 「通常版の合計ダメージに、始動技ダメージの20%を加えた」ことを先に説明 |
| SA / CA・値欠損等で加算なし | 理由、元の値で登録したことを説明 |
| counter 版からの変換 | 加算せず元の値を使ったことを説明 |
| 全新規生成 | 多段始動は実測と異なる可能性があるため、生成後に実測値へ調整するよう案内 |
| 未知の `damageSkipReason` | silent にせず、未対応の理由コードを表示 |

BE の SA / CA 判定と理由コードは `internal/service/combo/service.go:892-925`。既知・未知理由と計算前提は `materializeDamageDescription` の単体テストで固定している（`web/src/constants/punish.test.ts:8-43`）。

⇒ **DES-005 §5.21 に上記の結果別説明を、DES-002 §4.2 に `starter_move_not_pc_scaled` と未知理由コード時の表示フォールバック方針を明文化してほしい。** API が未知コードを返す契約を増やすのではなく、BE / FE の版ずれや将来の同期漏れを silent にしない表示側の防御である。

## §2 製造の判断

### 2-1 開発者へ確認して確定した点

| # | 論点 | 確定 |
|---|------|------|
| 1 | キャラクター変更 | 確定反撃サーチ経由では、成立ツリー・手動確認レーンとも検索キャラクターへ固定する。保存時の一致確認も残す |
| 2 | `hit_type` | 両レーンともタブから一意に決まる値をプリフィルし、選択欄を非活性にする |
| 3 | 自動採用の境界 | `combo_punishes` の自動採用は手動確認レーンだけ。成立ツリーは保存のみ |
| 4 | materialize 通知のタイミング | 通常のコンボ登録時ではなく、PC 版を**新規生成した時だけ**表示する |
| 5 | materialize 通知の内容 | 自動変更の前提から説明し、全生成結果で多段技の実測差と生成後の調整を案内する |
| 6 | 長文通知の寿命と閉じ方 | 自動消去せず、右上の×で明示的に閉じる。「開く」は維持する |
| 7 | 共通通知への波及 | materialize 新規生成だけに限定し、共通 `Toaster` と短い通知は変更しない |
| 8 | 未知の `damageSkipReason` | 現行では通常発生しないが、将来の同期漏れに備えて理由コード付きでフォールバック表示する |
| 9 | curation note | 登録成功後に行ごとのブラウザ内入力 state を削除し、解除後に古い理由が再表示されないようにする（`web/src/features/punish/components/PunishList.tsx:180-197`） |
| 10 | 連続 materialize の通知 | 通常／counter と加算スキップを別の固定 ID へ分け、同種は最新へ置換する。最大 2 件とし、回復しにくいスキップ理由を通常結果で消さない |

### 2-2 推測で進めた点（指示書 §8.2 の許容範囲）

| 事項 | 選択 | 根拠 |
|---|---|---|
| 入力固定の表現 | キャラクターは選択 UI を固定表示へ置換し、`hit_type` は値を表示したまま select を disabled にする。双方に同じ固定理由を添える | 新しい画面や確認モーダルを増やさず、変更できない理由を画面上で説明できる最小構成 |
| 自動採用の識別 | `opponentMoveId` の有無を自動採用の境界にし、`punishSelfCharacterId` + 妥当な `hitType` を固定入力の境界にした | 既存 `location.state` を拡張する流儀を維持し、`ComboEditor` の Props 契約を変えない |
| 未知理由の文言 | 「未対応の理由コード: <code>」として内部コードを表示する | 同期漏れを利用者・調査者の双方が特定でき、誤った既知理由へ丸めない |
| 長文通知の実装方式 | 共通通知部品を変更せず、専用 class と Sonner の toast 単位オプションを使用 | 開発者が許容した「共通部品への申し送り」より、対象を局所化して既存短文通知を不変に保てる |
| seed 件数回帰 | 21 / 23 / 7 を基準日・一次源付きの名前付き canary 定数にした | seed 変更時に数字だけを機械更新せず、案 C の差分再実測を促すため |

## §3 設計担当が未把握の残課題・申し送り

### 3-1【唯一の後続候補】`hit-type-named-constants`

`PUNISH_HIT_TYPE_BY_GUARD` は既存 SSOT の `HIT_TYPE_VALUES[2]` / `[3]` を参照しており、4 値リテラルの追加定義は避けている。一方、配列の並び替えや要素挿入が型エラーにならず、写像だけが静かに変わる余地がある（`web/src/constants/punish.ts:54-67`）。同じ構造により `PUNISH_COUNTER_HIT_TYPES` で non-null assertion も 2 箇所必要になっている。

Claude 独立レビューの中-2 / 低-4 は同一課題として整理し、M18 の設計凍結範囲を越えるため本サブでは延期した。現行値は unit / E2E で固定されており、M18-03c の blocker ではない。

⇒ `combo-list.ts` 側へ `HIT_TYPE_PUNISH_COUNTER` / `HIT_TYPE_JUST_PARRY_PUNISH_COUNTER` のような名前付き定数を置き、正典配列と punish 写像を同定数から構成する後続を、設計担当で採否判断してほしい。

### 3-2 M18-03c の未解決実装指摘は 0

- Codex レビューの中指摘 1 件（seed 21 / 23 / 7 と相手技 A→B の回帰テスト）は取り込み済み。
- Claude 独立レビューは重大 0 / 高 0 / 中 3 / 低 5。開発者判断後、後続候補 1 クラスを除く 6 件を取り込み、実機確認 4 点と最終の×位置も反映した。
- 一次受け Q4 で、永続通知が連続 materialize の回数だけ積み上がる未保護箇所を修正した。二固定 ID と回帰 E2E を追加済みで、後続候補を除くコード上の未解決指摘・新規 blocker はない。

設計本体は製造側で変更していないため、**CHANGE-090 の実装後反映と M18 クローズ処理は設計側に残っている**。
