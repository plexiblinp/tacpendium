## 2. M15 で確定した設計判断（M16 に効くもの）

1. **dash（前/後ステップ）二重表現の canonical = system move**（DES-004 §2.1 line 103「移動は 1入力=1move の独立 move。2通り表現はデータ揺れを生むため不採用」原則からの帰結）。**SUPP-001 §3.3.3 の modifier.type `dash_forward`/`dash_back` が原則違反の重複**。M15-03 で新規入力経路は system move へ寄せた（近手当て）。**modifier.type dash の廃止＋既存データ移行は M16**（phase3-overview §M16 ④''）。**parry_drive_rush は cancel 注釈のため modifier.type のまま正**。
2. **target_combo（多段特殊技）の区分正典化 = M16**（④'）。現状 enum 値はあるが段数付き行は normal/unique に紛れ・`tc_<番号>` は FR703 用に温存＝信頼分類として未機能。**別技の move_code 命名は既存**（命名新設でなく分類の正典化が論点）。
3. **① 始動 vs 消費の区別 = M16**。ドライブ/SA ゲージの始動 vs 消費が未確定で、FB⑨⑪⑬ の表記（M15-07）は**これが確定してからでないと誤ラベルになる**（順序依存）。
4. **段階1（通常技の方向ゾーン×ボタン決定論引き当て）は実装済・非スキーマ・command 非依存**。**段階2（command 依存の特殊技解決）＋索引元 command 再確立（G-k）は M17**。
5. **M15 の非スキーマ規律**: OD/modifier 変種＝既存 `modifiers.flags`（JSON）、別技＝残置プルダウン、タグ色＝既存 `tags.color`（HEX）、UI 状態＝localStorage（`browser-storage.ts`）に載せ、**データ論点は全て M16 へ routing**して非スキーマを守った。M16 はこの「宿題」を回収する。

## 8. M15 教訓ダイジェスト（M16 に効くもの・TMP から抜粋）

- **経路/入口の全数監査**: 同一症状/概念に複数の入口がある（dash 2経路＝L-M15-3-3／tag 作成 2経路＝L-M15-4-1／比較の名称解決＝M15-05②）。**修正/正典化の前に grep で全数列挙**。M16 の taxonomy/一本化はまさにこの「全経路の統一」。
- **供給側（BE）の補完非対称**（M15-05②＝L-M15-5-1）: 共有ヘルパにフォールバック（空→生 ID 等）があると、供給側（List 補完済/FindByID 未補完）の漏れが特定消費者だけで症状化。**真因を BE の補完一貫性まで追う**。
- **確立済み原則の横断ドキュメント監査**（L-M15-3-3）: dash は DES-004 §2.1 に「1入力=1move」原則が既にあったのに SUPP-001 §3.3.3 が違反していた。**原則がある概念は DES 横断で違反を監査**（M16 の taxonomy 明文化で重要）。
- **実機確認 ≠ コードレビュー**（M15-06）: fresh subagent のコードレビューでは PC 到達不能の欠陥を検出できず、開発者の**実機確認**で発覚。UX/導線系は実機確認が要。Plan Mode の選択肢は**帰結（どの経路で誰に届くか）まで詰める**（「トースト or Home 誘導」の2挙動並記のまま実装させない）。
- **非スキーマ境界を data milestone へ routing**（L-M15-3-6）: M15 はデータ論点を M16 へ送って非スキーマを守った。M16 はその宿題（④/④'/④''/①）を承認ゲート付きで回収する。
