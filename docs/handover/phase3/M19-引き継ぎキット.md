## 2. 未着手 3 本の中身と落とし穴

### 2.1 M19-04（moves スキーマ＋backfill＋付与）

**設計は確定している。指示書化から始められる。**

| 追加物 | 内容 |
|---|---|
| `moves.startup_basis` | TEXT enum `standalone`/`through`/`unknown`・NOT NULL・既存行は `unknown` 起点 |
| `moves.chain_cancel_total` | INTEGER NULL。**非 NULL であること自体がチェーングループ員であることを兼ねる**（別フラグを作らない） |
| `moves.fastest_unreachable` | BOOLEAN。**(f) `is_aerial` の意味乖離と (a) B 型 air-only を 1 本で解消** |
| `move_derivations`（新表） | `child_move_id`・`parent_move_id`・PK(child, parent)。複数親へ**行追加だけで**伸びる |

**★落とし穴 4 件**

1. **FK CASCADE に依存しない**（overview §9）。M19-03 で「`PRAGMA foreign_keys` が接続プール全体に効いていない」ことが判明した。`move_derivations` が CASCADE を前提にしているなら、**M19-03 と同じ手当て（`ON UPDATE CASCADE` ＋ 明示再ポイント／明示削除の併用）が要る**。**指示書化の際に必ず確認する。**
2. **`is_derived` / `is_aerial` は現行セマンティクスのまま**にする。DES-003 の**説明文言の是正のみ**。値やロジックを触ると M18 の確定反撃走査に波及する。
3. **確定反撃の走査列（`is_projectile` / `is_aerial` / `on_block` / `recovery`）に非干渉**であることを実装で担保する。
4. **人手 backfill が挟まる。** 機械化できるのは basis 796 行と C 型 air フラグ。**真の人手範囲は約 148 行＋チェーン分**（B 型判定・`chain_cancel_total` の実測値・親参照）。**M19-04 と M19-05 を分けたのはここが天然の継ぎ目だから**で、統合しないほうがよい。

**開発者預かりの未決 1 件**: **新列の値の置き場所**（CSV／入力ツール vs DB backfill 専用）。設計側は **DB backfill 専用を推奨**（M18-01 で「seedgen に新列を出力」が原理的に不成立で撤回された前例）。ただし**どちらを採っても守る不変条件**がある——**CSV 再取込（upsert）が新列の人手付与値を上書き・NULL 化しないこと**。

**別途の個別承認が要るもの**: **ザンギエフの連打版 3 行を `moves` に新規登録**する（rush_variant と同型の変種別行パターン）。通常版↔連打版のリンク列は対象 3 行のみのため設計では見送っており、**着手時に個別承認**とした。

### 2.2 M19-05（消費側）

- **合成 filler 単位**: チェーンを 1 単位に機械合成して既存 subset-sum に渡す。**これにより順序依存が発生しない**＝エンジンの探索構造・受理帯・恒等式は不変（設計時に懸念した「区分3＝探索構造の変更」は**回避された**）。
- **through target 解禁・表記展開・親なし子の警告（R6）**。
- **golden 5/5**（GC-2＝ケン「立ち弱P＞奮迅脚＞紫電カカト落とし」・KA=43・S=42・N=3 が通る）。
- **target ゲートの切替**（`fastest_unreachable` の消費）。
- **残件導線の再検討**: gap 全種別で `maxLimit`(3000) < `totalFound`(4884)。through 解禁で件数が更に増えるので**ここで併せて見直す**。

**★落とし穴 2 件**

1. **filler 規則の変更 4 点のうち #4 は「新機能」ではなく「既存の穴の是正」である。** 現行の filler 規則には**「単独入力不可」の除外が無く、パターン 3/5/6 の派生技が単独 filler として提案され得る**。つまり**いま誤った候補が出ている**。したがって回帰確認は golden（既存が壊れていない）だけでは不十分で、**「誤った候補が消えたこと」の確認が要る**。
2. **突合ゲートの区分定義に穴がある。** `M19-02` 指示書 §10-3 は影響を 3 区分（候補集合の**緩和**／ステップ費用の再定義／探索構造の変更）に分けたが、上記 #4 は**候補集合の縮小**である。**区分1 は「候補集合の変更（緩和・縮小の双方）」と読み替えること。** 緩和だけを想定して読むと縮小側の回帰確認が漏れる。

### 2.3 後続サブ（成立条件の絞り込み ＋ コンボ新規登録時の入力）

**2 つを 1 サブに同梱する前提**（どちらも「成立条件の使い勝手を広げる」同種の UI 作業。分けると同じ面を二度触る）。**サブ数は増えない。**

**(a) 一覧・検索・エクスポートでの絞り込み**（例: 「後ろ受け身で成立するものだけ」）。これが構造化の当初目的。データモデルは絞り込み可能な形になっている。

**(b) コンボ新規登録時の成立条件入力**（設計＝`M19-03-完了報告-一次受け` v1.1.0 §3.3）。要点のみ:
- **API**: M19-03 が追加した `POST /api/combos/{comboId}/setups` の `verifiedConditions` は**既存コンボ用**で使えない（`comboId` 未発番）。**コンボ作成 API（`useCreateCombo`）の紐付け要素にも同じものを足す**。
- **Tx**: `combos` INSERT → `combo_id` 発番 → `setups`／`combo_setups` → **`combo_setup_results` を同一 Tx**。親より先に結果行を書かない。
- **`copy` モードでは成立条件を引き継がない**（全セル未検証で開始）。引き継ぐと**未検証のものが検証済みに見える**。
- **UI は項目10 と同じ 2×2 グリッド**（「セル選択 ＋ 3 択の直接指定」）を再利用。新しい操作モデルを作らない。
- **セットプレイ編集画面（`/setups/:id`）は実装しない**（開発者判断）。

**★落とし穴**: この入力は **`SetupSelectorModal` と同じコンボエディタ上**に載る。**M19-01 がまさにそこで失敗した**ため、`CHANGE-087 §2-h` の現行の書き方（「セットプレイ編集画面に置かない」）と M19-01 の前例をそのまま読むと、**後続やレビューが「M19-01 の再発」と判定して弾く**。**overview §11 の v3（保存 UI を置く面は、親が確定しているか親と同一 Tx でコミットできること）で判定すること。** §2-h の v3 への改訂は `DES-005` §5.6 へ着地済みである（**2026-08-10 実査で確認**）。

## 7. 逆に、うまく働いた仕組み（残す価値があるもの）

1. **否定形確認（撤回した仕様が資産に残っていないかの全文走査）。** M19-02 で gap 定義を是正した際、**本番コードは正しく直っていたが engine テストのコメントとヘルパ名に旧定義が残っていた**。指示書の否定形確認に「旧 gap 定義の残骸」を項目として登録していたため、差分レビューで検出できた。**動作に影響しないため通常のテストでは絶対に検出できない**種類の残骸である。
2. **恒等式を式で書くこと。** `N = KA + 2 − S`／`G = N − active`／`N = remaining + NLo` を式で固定したため、**製造が独立に検算して設計の誤りを見つけられた**。散文で書いていたら解釈で吸収されていた。
3. **Plan Mode で「実体のパスと関数名まで特定して Plan に書く」ことを要求する。** M19-03 §4.2 で「独断で `ON UPDATE CASCADE` を付けて済ませない」と明記した結果、**引き継ぎが「明示再ポイントと ON UPDATE CASCADE の併用」でないと成立しない**ことが実装前に判明した（私は択一だと想定していた）。
4. **受理帯を「帯の下限・上限」に一般化したこと。** gap の定義が根本から変わったのに、**定数の差し替えだけで吸収できた**。恒等式も meaty 経路も無傷だった。
5. **一次受けを挟むこと。** M19-02 で**完了報告が as-built より古い**ことを検出できた。完了報告は DES 反映の一次源なので、そのまま流していれば**実装は正しいのに設計書だけが間違う**——最も発見しにくい不整合が生まれていた。
