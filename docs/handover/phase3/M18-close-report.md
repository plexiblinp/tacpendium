## 0. 新任者への前置き（M18 とは何か・3 分で読める要約）

**M18 ＝ 確定反撃記録。** 相手の攻撃をガード／ジャストパリィした後の有利フレーム中に始動する確定反撃を記録する機能です。中核は **materialize**——ノーマルヒットで記録済みのコンボから、**パニッシュカウンター版を別コンボとして生成**し、出自（`combos.materialized_from_combo_id`）を記録して**以後は独立フォーク**として扱う仕組みです。

**画面は 2 つ。** 画面20「確定反撃サーチ（探す）」＝相手技→始動技→コンボの 3 階層でフレーム判定から候補を出す。画面21「確定反撃マイリスト（使う）」＝採用済みを相手技→コンボの 2 階層で見返す。

**サブ構成と状態**：

| M18-02 | 確定反撃サーチ（探す） | 083／084 | 000040／000041 | 完了 |

**M18 の設計思想の核（これを知らないと反映時に誤読します）**：

- **silent に消さない。** 除外は「消す」のでなく「**理由バッジ付きで別レーンに出す**」。走査から外れた相手技は「自動判定できない相手技」レーンへ、区分が判定できない採用は「区分を判定できない反撃」セクションへ、変換済みのノーマル版は「変換済み (N 件)」の折りたたみへ——**すべて同じイディオム**です。

- **規則は BE に一元化し FE は引くだけ**（DES-002 §4.2）。走査規則・ダメージ計算・重複判定はすべて BE。

### 2.2 【重要】登録導線の契約（指示書を超えて確定した仕様）

**指示書は §4.5 で「`hit_type` の**プリフィル**」としか書いておらず、実機確認を経て「**固定**（変更不可）」へ強化されました。指示書だけでは最終仕様を再現できません。**

| 導線 | 検索キャラクター | `hit_type` | `combo_punishes` 自動採用 |
|---|---|---|---|
| 成立ツリー「このコンボを新規登録する」 | **固定** | ガード＝`punish_counter`／ジャストパリィ＝`just_parry_punish_counter` に**固定** | **しない**（保存後、探す画面で明示的に採用） |
| 手動確認レーン「手動で確定反撃を登録」 | **固定** | 同上 | **する**（保存後に既存 `POST /api/combo-punishes` を呼ぶ） |

**この非対称は正当です。根拠を明記して反映してください**（後任が「不統一」と誤認して揃えにかかるのを防ぐため）：

- **手動確認レーンには採用ボタンが存在しません。** フレーム判定ができない相手技には始動技→コンボのツリーが出ないためです。**自動採用しなければ、登録したコンボが画面のどこにも現れません**（これがまさに DES-005 §5.20 の「既知の限界 2」でした）。
- **成立ツリーには採用ボタンがあります。** 登録直後に他の候補と比べてから採用する余地を残すのが自然で、自動採用すると**比較せず採用**を強制することになります。

**多層防御も反映対象です**：保存要求時または保存結果のキャラクターが検索条件と異なる場合、**コンボは保存したまま紐づけをスキップして理由を通知**します。UI 固定を将来別経路が迂回しても、**別キャラの `combo_punishes` を作らない**ための設計です。

### 2.3 materialize 新規生成通知の契約

**新規生成時の説明のみ**、次の契約に従います（**既存一致時と他の短い通知には適用しません**）。

- **自動消去しない**（`duration: Infinity`）。**右上の×で閉じる**まで表示。「開く」操作を併置。
- **結果別に、計算前提から説明する**：通常加算＝「通常版の合計ダメージに始動技ダメージの 20% を加えた」／SA・CA や値欠損＝理由と元の値で登録したこと／counter 版からの変換＝加算せず元の値を使ったこと。
- **全新規生成で**、多段始動は実測と異なりうるため**生成後に実測値へ調整するよう案内**する。
- **未知の `damageSkipReason` は silent にせず**、未対応の理由コードを表示する。
- **共通 `Toaster` と通常の短い通知の表示時間・閉じる位置は変更していません**（`materialize-result-toast` 専用クラスの CSS 変数のみで上書き）。

**【v1.0.1・追記】複数生成時の挙動（一次受け Q4 で対処）**

自動消去しない通知は、**連続 materialize すると回数だけ積み上がる**問題がありました（`toast.success` に id を渡していないため Sonner が呼び出しごとに新 ID を生成する）。**固定 ID を 2 つに分けて解決**しています。

| 通知の種別 | 固定 ID | 挙動 |
|---|---|---|
| 通常加算・counter 版からの変換 | `materialize-result` | 同種の次の通知で**置換** |
| **加算スキップ**（SA／CA・値欠損・未知の理由コード） | `materialize-result-attention` | 同種の次の通知で置換。**通常結果の通知では置換されない** |

**永続通知は最大 2 件**に収まります。**ID を 2 つに分けた理由を反映時に残してください**——情報の回復可能性が非対称だからです。**通常加算を見逃してもダメージ値を見れば回復できる**が、**加算スキップを見逃すと回復しにくい**（「なぜ加算されていないのか」は SA／CA は補正が等倍というドメイン知識を要し、利用者が自力で気づけない）。§2.3 の通知はまさにその知識を伝えるために設けたものです。したがって**持続性も非対称にしています**。

**回帰テストの担保**：E2E **E** ＝同種 2 回で 1 件へ置換され、文言と「開く」が最新生成物へ更新される。E2E **F** ＝ **390×844（モバイル幅）**で SA／CA → 通常 → 値欠損 を連続生成し、**通常／要注意の 2 件に収まり、3 回目の操作が通知に妨げられない**。

## 5. M18 の lessons-learned（**E 番号の採番は中央**）

5 件を送ります。**(a)(b)(d) は私自身の失敗**から、(c) は引き継ぎ前の記録欠落から、(e) は既に playbook §4.20 に収載済みです。

**(a)「当然そうなる」と感じたものこそ、指示書の処理順に書き下す**
M18-03b の指示書 §4.4 は、materialize の処理順に「基底コンボの採用を解除する」を書き落としていました。一方 §5.3（E2E）と §1.2 は「変換後に基底が第3セクションから消える」と書いており、**指示書の中で仕様が二重定義され、片方が欠落**していました。原因は、私が「消える」を materialize の**当然の帰結**だと思い込んだことです。実際には明示的な削除操作が要ります。**L-1（「既存と同型」を実機序で確認する）の、自分の設計に対する版**です。

**(b) 画面文言の変更は、その文言を assert しているテストの突合まで含めて 1 つの変更である**
M18-03b が 03a の告知文言を書き換えた際、**その文言を assert している 03a の E2E spec が追随せず恒常的に失敗**していました（M19 製造担当が発見）。**実装が正しくテストだけが古い**状態です。**E-22／L-3 の適用漏れ**——「出力を固定している資産（golden／スナップショット／期待 SQL／契約テスト）も E-14 の突合対象に含める」。**文言を assert している E2E spec は出力固定資産**であり、golden や snapshot と同じカテゴリだと認識できていませんでした。
**さらに危険なのは検出のされ方です。** この E2E 環境は SQLite 書き込み競合で恒常的に 1〜2 本 flaky になることが実測されており、**本物の回帰が環境ノイズとまったく同じ見え方をします**。「既知の flaky」を理由に失敗を流す運用は、この種の回帰を隠します。

**(c) 複数案から選んだときは、採用案だけでなく不採用案とその理由も残す**
`neutral_jumping_heavy_kick` の件は「案C で決定」とだけ記録され、**案A・案B の内容がどの文書にも残っていません**。後から「なぜこの形なのか」を追跡できず、同じ議論を繰り返す危険があります。

**(d) 制度・手続きの根拠も、文書のステータス欄からの推論ではなく一次文書を引く**
私は CHANGE-085 の通知書を見ずに DES-002 のステータス欄から「スキーマ変更なし＝実装後起票」と推論し、着手前ゲートの分界を**もっともらしく再構成**しました。実際の分界（M17-D10）は「通知書＋registry は着手前／DES 本体＋change-report は実装完了後」で、**スキーマの有無は無関係**です。playbook を引けば確認できました。**retrospective-digest §0「想定で書かず必ず引く」の運用ルール版**です。

**(e) 自由改訂資料の項目は、番号ではなくスラッグで参照する**（**playbook v2.3.0 §4.20 に収載済**）
`followup-backlog` の番号が 2 度食い違いました。1 度目は「担当が完了報告に『起票済み』と書いても、中央帰属の実物には何も起きない」という構造が原因（中央にて G-9 として記録）、2 度目は単純な採番競合です。**番号は動きうるがスラッグは動きません。**
