## 設計準拠性以外の指摘事項

### 高-1: 第 2 段の注記除去を**入力側にも**掛けているため、利用者が明示した SA/CA を黙って捨てて別の技へ確定しうる

**箇所**: `internal/aliasindex/aliasindex.go` `Lookup`

```go
if codes := sortedCodes(ix.strict[aliasnorm.Normalize(aliasText)]); len(codes) > 0 {
    return codes
}
return sortedCodes(ix.relaxed[aliasnorm.NormalizeRelaxed(aliasText)])   // ← 入力側にも Relaxed
```

**何が起きるか**（ryu の実データで成立する形）:

| 入力 | 辞書 | 現在の挙動 |
|---|---|---|
| `236236P (SA3)` | `236236P (SA1)` → `sa1_shinku_hadoken` ／ ryu の SA3 は `236236K` | 第 1 段 `236236p (sa3)` は 0 件 → 第 2 段が**入力の `(SA3)` を落として** `236236p` で引く → `sa1_shinku_hadoken` 1 件 → **`Resolved = true` で確定** |

利用者は「SA3」と明示的に書いたのに、SA1 の技として確定した結果が取込 CSV へ流れる。**これは第 1 段の衝突検査（`StrictCollisions()`）では検出できない**——第 1 段のキー空間は無傷であり、壊れているのは「入力の情報を捨ててよいか」という判断の側である。既存テストにもこの経路は無い（`TestLookup_StrictStageWinsOverRelaxed` は第 1 段が当たる場合しか見ていない）。

**裁定 1 との関係**: 裁定は「第 2 段＝SA/CA 注記を落として再照合」であり、**どちら側の注記を落とすかは書かれていない**。一方で `NormalizeRelaxed` の godoc・`aliasindex` の godoc・完了報告 §2.2 はいずれも根拠を「利用者はメモに `236236P` としか書かない」＝**入力に注記が無い場合**に限って説明している。⇒ 実装は文書化された根拠より広い。

**推奨**: 第 2 段は**辞書側だけを緩める**——`relaxed[aliasnorm.Normalize(aliasText)]` で引く。こうすると

- 注記を省いた入力（本来の目的）は従来どおり拾える
- 注記を明示した入力が第 1 段で外れたら、**未解決のまま候補として人へ出る**（§4.3-2 と同じ考え方）

という形になり、「どれが正しいかはメモの書き手しか知らない」という本サブの原則と揃う。あわせて `TestLookup_TaggedInputThatMissesStrictStageStaysUnresolved` 相当の 1 本を置き、破壊確認（両側 Relaxed へ戻すと赤くなること）を取ること。

**なお両側適用が裁定 1 の意図であるなら**、実装を変えるのではなく `NormalizeRelaxed` の godoc・完了報告 §2.2 の根拠記述を「入力側の注記も落とす（利用者が誤った SA 番号を書いた場合、注記を無視して確定する）」へ広げ、上記の表を明示的な仕様として固定するテストを置くこと。**どちらにせよ現状の「実装 > 文書」のずれは残せない。** 判断は裁定の解釈に関わるため開発者・設計卓の手番。

### 中-2: `unresolvedKind` が「トークン索引由来の候補」と「別名由来の候補」を区別しないため、未解決の理由表示が実態とずれる場合がある
