## 設計準拠性以外の指摘事項

### 1. 報告に、根拠が存在しない主張が残っている（最重要）

- §7.3 の表に `check-progress-log-index.sh` が `EXIT 0 / 112 件すべて progress-log に在り` と書かれているが、**レビュー時点の実測は EXIT=1（違反 1 件）** である。出力は `NG 作業 ID m36-01 が docs/progress/progress-log.md に現れない(完了報告: docs/progress/M36-01-completion-report.md)`。`grep -n "M36-01" docs/progress/progress-log.md` も 0 件で、`git status` に同ファイルは現れない。
- §9 の完了条件 10 が「満たす」判定で、根拠欄が「Phase D で実施」と書かれている。これは未来形の記述であり、実施済みの根拠ではない。実際に未実施である。
- （レビュー中に解消）§7.4 の全数テストが `<!-- TEST-RESULTS-PLACEHOLDER -->` のままだった。現在は実測で埋まっている。

残る 2 件は同じ型である。**検査が緑であることと、検査結果を報告へ写したことと、そもそも検査を回したことが、報告上で区別されていない。** 本プロジェクトが `check-artifact-integrity.sh` を 1 本目に置いている理由（他の検査が緑でも、その緑が信用できるとは限らない）が、報告の書き方の側で崩れている。皮肉なことに、§7.5 はまさにこの型の事故を自分で記録している。

**★とくに重いのは「表に EXIT 0 と書いてあること」である。** 追記漏れそのものは 1 行で直るが、赤い検査を緑と書いた表は、次の担当が「この検査は通っている」という前提で読む。`check-progress-log-index.sh` は `docs/progress/` を常時走査しない類の検査ではなく、回せば即座に赤と分かるものであるため、写し間違いであっても表の信頼性を損なう。

### 2. 「選べる形」が組み立て側だけにある（`RELEASE_EXTRA_FILES`）

`scripts/check-release-archive.sh` は `RELEASE_EXTRA_FILES` を 1 度も参照していない。同梱すると決めて `release-targets.sh` へ 1 行足しても、

- 組み立て側は入れる
- 検査側は入っているかを見ない

という非対称になる。将来、`cp` に失敗しても（ファイル名変更・移動・タイポ）検査は緑のままである。本サブが「zip ができることと中身が正しいことは別」を看板にしている以上、追加同梱物だけがその外に置かれているのは一貫しない。

あわせて、`cp -p "$extra" "$stage/$(basename "$extra")"` はパスを平坦化する。`LICENSES/MIT.txt` を足すと `MIT.txt` として root に落ちるため、`LICENSES/` 配下の 3 本を足した場合に出所が分からなくなる。将来、同名 basename を 2 本足すと **警告なく上書きされる**。

### 3. SHA-256 の検証手順が、検証したい時点では読めない場所にしかない

`README.txt` の新設節は文面として良いが、その `README.txt` はアーカイブの中にある。ダウンロード直後にチェックサムを照合したい利用者は、まだ展開していない。E-3 の文言（`README.txt` か説明書に 1 行）は満たしているが、実効性は `M36-02` のリリースページ側に同じ 1 行が載って初めて成立する。この従属関係が §8 の申し送りに書かれていない。

### 4. `README.txt` 末尾の「リポジトリを扱う人向けの注記」が、本サブで初めて利用者の手元へ届く

末尾ブロックは `docs/usermanual/dist-readme.txt` から生成されていること、`bash scripts/check-dist-readme.sh --write` で作り直すことを案内している。`CHANGE-191` の時点では `README.txt` はリポジトリの中にしか無かったため妥当だったが、**本サブが配布アーカイブへ同梱したことで、リポジトリ内部の手順書が配布物に載る形になった**。「利用者の方は読み飛ばしてください」と断ってはいるので実害は小さいが、状態が変わったこと自体が報告に無い。

### 5. 画像 0 枚のまま緑になることが、リリース可否の申し送りとして上がっていない

版ゲート 3b により画像 0 枚で止まらないのは正しく、実装もそのとおりである。しかし結果として、現時点で `make release-archives` を打つと **`<img>` 27 箇所がすべてリンク切れの説明書が入ったアーカイブ 3 本が、検査全緑で出来上がる**。事実としては §1 の 3b と §2.4 に書いてあるが、§8 の申し送り（開発者・設計卓が読む面）に「撮影前の成果物を配布してはならない」という形では上がっていない。本サブの成果は「組める」ことであって「配布してよい」ことではない、という境界を §8 に 1 行置くべきである。

### 6. 自己検査の `images/` 対照が、常に `.gitkeep` を含んでいる

`_stage` は必ず `manual/images/.gitkeep` を作る。したがって自己検査は「中身 1 件の `images/`」しか対照に持っておらず、「真に空の `images/`」は対照に含まれていない。レビュー側で手作業で確かめた結果 zip / tar.gz とも緑だったので現状は問題ないが、版ゲート 3b の保証が `.gitkeep` の存在に依存しているように読める。陰性対照を 1 件足すか、`.gitkeep` に依存していないことをコメントに明記しておくと強い。

### 7. コード上の細かい点

- `check-release-archive.sh` の `check_archive` 内で `src` を取り出して `[ -n "${src:-}" ] || src=""` まで書いているが、以後 1 度も使っていない。未使用変数である（`CLAUDE.md` §4「不要なコメントアウトコードは削除する」と同趣旨）。
