## 3. ★設計判断：§2-h の再定式化と、入力経路の追加（開発者判断 2026-07-28 反映）

### 3.1 私の記述に誤りがあった（原則を画面名で書いた）

指示書 §4.4.1 と CHANGE-087 §2-h は「**セットプレイ編集画面には置かない**」と書き、理由に M19-01 の `SetupSelectorModal` の失敗を挙げた。**原則の趣旨は正しいが、画面名で禁止したため誤りになっていた。**

**M19-01 で何が起きていたか**（`code-facts` の現物 Props で確認）:

```
SetupSelectorModal (web/src/features/combo/components/SetupSelectorModal.tsx)
  open, characterId, knockdownAdvantage, excludeSetupIds, onSelect   ← comboId が無い

SetupCandidateList (web/src/features/setup/components/SetupCandidateList.tsx)
  parentComboId: number, candidates                                  ← 持っている
```

`SetupSelectorModal` は **`features/combo/components/` にあり、コンボエディタ（新規／編集／コピー）から呼ばれる**。**新規登録の途中で呼ばれ得るため、その時点でコンボは存在せず `comboId` は発番されていない。** 提案の採択保存は `combo_setups` を作る＝親コンボ必須（VAL-S05）であり、**存在しない `comboId` では保存が完了しない**。

つまり失敗の本質は「あの画面が悪い」ではなく、**親が存在しない状態で即時保存しようとしたこと**である。

### 3.2 原則の再定式化（v3）

| 版 | 原則 | 評価 |
|---|---|---|
| v1（現行 §2-h） | セットプレイ編集画面に置かない | **画面名で禁止＝誤り** |
| v2 | 保存先が一意に特定できない面に保存 UI を置かない | 改善。**ただし新規登録を弾いてしまう**（親がまだ存在しないため） |
| **v3（採用）** | **保存 UI を置く面は、保存先の親が確定しているか、親と同一トランザクションでコミットできること** | 全ケースを正しく判定 |

v3 による判定:

| 面 | 判定 |
|---|---|
| コンボ詳細 項目10 | 親確定 **○**（M19-03 実装済み） |
| 提案の採用ダイアログ 項目12 | 親確定 **○**（M19-03 実装済み） |
| **コンボ新規登録（コンボエディタ）** | 親は未発番だが**同一 Tx でコミット可 ○** ← **今回の追加スコープ** |
| セットプレイ編集画面 `/setups/:id` | 親が複数あり得る。一覧または選択で確定させれば ○ だが **今回は実装しない**（§3.4） |
| M19-01 の `SetupSelectorModal` | ステージング機構が無く**即時保存しようとした ×** |

**★v3 への書き換えは、編集画面のためではなく「新規登録を通すため」に必要である。** 新規登録の入力は **`SetupSelectorModal` と同じコンボエディタ上**に載る。現行 §2-h と M19-01 の前例をそのまま読むと、**後続の担当やレビューがこれを「M19-01 の再発」と判定して弾く**。v3 なら「親と同一 Tx でコミットするので可」と正しく判定できる。

### 3.3 追加スコープ：コンボ新規登録時に成立条件を入力する

**開発者要望 2026-07-28。私の `M19-DESIGN-06` は入力経路を 2 つ（提案からの採用／後から項目10 で編集）しか想定しておらず、これが抜けていた＝設計の穴である。**

実運用の主導線はおそらくこちらである——トレーニングモードで検証し、**動くものが分かってからコンボ・セットプレイ・条件をまとめて登録する**。後から思い出して入力するより自然である。

**構造的な曖昧さは無い。** 編集画面は「setup 1 : コンボ N」で保存先が定まらないが、新規登録は**作ろうとしているコンボが 1 つ**なので、各セットプレイとの組がその場で一意に決まる。

**既存機構に乗る**（`code-facts` で確認）:

```
コンボエディタ側 Props: linkedSetups: SetupSummary[], onLinkedSetupsChange: (setups) => void
```

紐付けは**ローカル状態でステージングし、コンボ保存時にまとめてコミット**する形になっている。ここに成立条件を持たせ、同じタイミングでコミットすればよい。

**要点（後続サブの指示書化に向けて）**:

1. **API**: M19-03 が追加した `POST /api/combos/{comboId}/setups` の `verifiedConditions` は**既存コンボに足す経路**であり、新規登録には使えない（`comboId` が未発番）。**コンボ作成 API（`POST /api/combos`・`useCreateCombo`）の紐付け要素にも同じものを足す**。
2. **トランザクション**: `combos` INSERT → `combo_id` 発番 → `setups`／`combo_setups` → **`combo_setup_results` を同一 Tx で INSERT**。**親が作られる前に結果行を書かない**（複合 FK が成立しない）。
3. **モード別の扱い**（エディタは `new / edit / copy` の 3 モード）:
   - `new`: 本スコープ。
   - `edit`: 親が確定しているので既存条件を表示・編集できる（`copy` と違い引き継ぎの問題が無い）。**実装するかは後続サブの判断**。
   - **`copy`: 元コンボの成立条件を引き継がない**（開発者確定 2026-07-28）。**全セル未検証で開始**する。コピーは位置や始動を変えるために作ることが多く、**引き継ぐと未検証のものが検証済みに見える**——この誤認のほうが手間より害が大きい。
4. **UI**: 項目10 と**同じ 2×2 グリッド**（「セル選択 ＋ 3 択の直接指定」＝M19-03 §1-4 の as-built）を再利用する。**新しい操作モデルを作らない**。
5. **未検証セルのメモは保存されない**制約（§1-5）は新規登録でも同じ。

### 3.4 編集画面（`/setups/:id`）は実装しない

**開発者判断 2026-07-28。** v3 の原則上は「一覧または選択で親を確定させれば可」だが、**今回は対応しない**。

将来やりたくなった場合の設計メモとして記録する: **セレクタではなく「親コンボごとにグリッドを並べる一覧」を推奨**する。セレクタは選択を見落とすと**別のコンボの条件を書き換え、しかもエラーにならず気づけない**。一覧なら選択という状態が無いので構造的に起きず、加えて「コンボ A の後では成立、コンボ B の後では不成立」が一目で分かる（コンボ詳細側では見られない情報）。

## 5. 後続への申し送り

### 5-1【要 followup 起票】FK 強制の接続単位問題の根治（§1-2・§3-2）

開発者の起票 OK 済み。**根治は独立サブを推奨**する。対応候補（DSN へ `_pragma=foreign_keys(1)`／`SetMaxOpenConns(1)`／各 CASCADE 依存箇所を明示削除へ）は**いずれも全テーブルの FK 強制挙動を変える**。FK=OFF 前提で通っていた既存の削除順序を壊し得るため、**独立した調査＋全テーブルの回帰ゲート**が要る。**M19 の中で片付けるべきではない。**

### 5-2【M18 担当へ連絡】`m18-03a` E2E の assert を M19-03 が修正した（§3-7）

`web/e2e/m18-03a-punish-mylist.spec.ts` の C ケースが**恒常的に失敗**していた（assert が M18-03b で書き換え済みの告知文言を期待していた＝**実装が正しくテストが古い**）。開発者指示で製造側が即修正。**punish 系のソースは 1 本も変更していない**（spec 1 本のみ）。結果 E2E は 62 passed / 0 failed。**M18 担当が同じ spec を触る予定なら、この修正を前提にしていただきたい。**

### 5-3【★M19-04 の設計に反映が要る】`move_derivations` を CASCADE に依存させない

§1-2 は **M19-04 に直接効く**。`M19-DESIGN-07` の `move_derivations`（新テーブル）が `ON DELETE CASCADE` を前提にしているなら、**M19-03 と同じ手当て（明示削除の併用）が要る**。**M19-04 の指示書化の際に必ず確認すること。**
