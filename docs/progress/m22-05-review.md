## 総評

**案 A の実装として正しく、しかも「締めなかった」ことの根拠が実測で裏づけられている。** 製造の主張（「本アプリにクロスオリジン経路は存在しない」「締めても得るものが無い」）は、レビュー側で一次ソース（`web/vite.config.ts` の `changeOrigin: false` ／ `api-client.ts` の `API_BASE = ""` ／ `cors.go` の許可外 Origin 素通し ／ `playwright.config.ts` の `baseURL`）を独立に読んで**すべて裏が取れた**。追認ではない。

**契約テストの検出力も独立に検証した**（`go test -overlay` で `cors.go` に 5 種の変異を注入。**リポジトリは 1 バイトも変更していない**）。「全部拒否」「全部許可」「案 B へ倒す」「Origin 必須化」の 4 変異すべてが赤くなり、**しかも `curl` 経路と LAN 経路のテストは締めすぎ変異のときだけ赤くなる**——テストは主張していることを実際に検出できている（§テスト検証を参照）。差分が小さいことは欠陥ではない（チェックリスト §0.2 / §0.3）。

### 中-1: `allowedHeaders` は as-built の説明として二重に古い（**撤回されたヘッダを名乗り、実際に送っているヘッダを落としている**）

`cors.go:32` の既定値は `"Content-Type, Origin, Accept, X-Requested-With"` である。**本アプリがいま実際に送っている独自ヘッダは `X-User-Id`**（`web/src/lib/http-interceptor.ts:17` / M22-02）であり、**この一覧には入っていない**。一方、撤回された `X-Requested-With` は残っている。

- **★`X-Requested-With` を残したこと自体は指摘しない**（チェックリスト §0.3・§10 が「重大でない」と明示している。コメントで誤読を防いだ判断も妥当）。**指摘は「この一覧が as-built の説明として使われること」である**——完了報告 §8-2 #10 が**この文字列を `DES-002` §4.4 へ書き足す as-built として設計卓へ渡している**。
- 挙動上の実害は無い。ACRH が来れば逐語エコーされる（`cors.go:55-60`）ため既定値は事実上 inert であり、そもそも同一オリジンでプリフライトが飛ばない。**問題は記述だけである。**
- **是正案**: §8-2 #10 に「**実際に送られている独自ヘッダは `X-User-Id` であり、既定の一覧には含まれない（ACRH のエコーで通るため実害は無い）**」の 1 行を足す。コード側は変えなくてよい。

### 中-2: `assertNoCORSHeaders` が `Vary` の**不在**を契約にしている（過剰固定）

`boundary_test.go:110-121` は許可外 Origin・Origin 不在の応答について `Access-Control-Allow-Origin` / `Access-Control-Allow-Credentials` に加えて **`Vary` が空であること**を主張している。

**変異 E で実測したとおり、`Vary: Origin` を常時付与する（＝応答が Origin に依存する以上、HTTP キャッシュの観点ではむしろ正しい）変更を入れると 4 本が赤くなる。** `Vary` は CORS の許可・拒否を表すヘッダではないため、**「境界が締まっていない」ことの主張には不要**である。将来の正しい修正がレビューで「非回帰違反」と読まれる形になっている。

**是正案**: `assertNoCORSHeaders` の対象から `Vary` を外し、`Allow-Origin` / `Allow-Credentials` の 2 本に絞る。`Vary` が付くことの主張は `TestBoundary_LANOriginNonGETIsAllowed`（許可 Origin 側）に既にあり、そちらは残してよい。

### 中-3: 契約テストは**ミドルウェア列を再構成している**ため、`main.go` 側の順序変更を検出できない

`boundary_test.go:77-95` の `newBoundaryServer` は `main.go:285-291` と同じ並びを**手で組み直している**（コメントもそう書いてある）。`main.go` で Auth を CORS より前へ動かすと **プリフライトが 401 になる**が、`boundary_test.go` は自前の並びを見ているので緑のまま、`cmd/combomgr/main_test.go` は `buildAllowedOrigins` しか見ていないので緑のまま——**リポジトリ全体で赤くなるテストが 1 本も無い。**

**本ファイルのヘッダは「検出できる層はここしかない」と書いており、その主張はミドルウェア列の順序については成立していない。** 順序の理由（CORS が OPTIONS を早期 return する）は `auth.go:46-47` と `main.go:288-290` の**コメントだけ**が支えている。
