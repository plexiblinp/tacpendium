## 総評

本サブの中心（「成功の自動断定」を鳴らす）は概ね達成されている。上限の値を 1 つも動かさず、既存データへの影響を開発者へ照会してから直し、鳴らし方は開発者選択に従い、`VAL-C09` は `DES-006` §2.1 の正典・`CHANGE-139` の裁定と同じ向きへ揃えており、重大度→文言の順序も守られている。射程外（`draft-gauge-default-zero` ／ 符号反転 ／ 単一 HTML ／ クラウド）にも触れていない。§2.3 / §2.4 は推測で直しておらず、`M23` / `M27-02b` の as-built も巻き戻していない。

一方で「1 か所鳴らして他が黙ったまま残る」（チェックリスト §0.4-1）が **経路の単位では潰れているが、判定の単位では残っている**。プレビュー↔確定の重大度の非対称は「全数」と宣言されているが、`VAL-S02`（セットプレイのレシピが空）という `VAL-C09` の完全な双子が表に載っておらず、いまも「プレビュー通過 → 確定で ERROR」のままである。加えて本サブの中心機能である「書出の切り捨て観測」の**配線そのもの**（`Count` の結果を `ExportResult` へ載せる部分）に主張するテストが 1 本も無く、完了報告 §9.3 が自ら一般形として書いた無観測の型が中心機能に残っている。

さらに `en.json` の `export.maxReached` が「exported」→「compared」へ書き換わっており、これは本サブが作った誤った文言が残っている状態である（完了報告に記載なし・テストも型検査も緑）。優先度較正の指示に従い「高」に置く。

## 設計準拠性以外の指摘事項

1. **`ExportDialog` の切り捨て確認がダイアログを閉じてもリセットされない。** `truncationConfirm` を落とすのは `handleRun` の中だけであり、`open` を監視する `useEffect`（`ExportDialog.tsx:98-101`）は `baseNameEdited` しか戻さない。Esc / オーバーレイクリックで閉じると `handleOpenChange(false)` が走るが状態は残るため、**次に開いたときは警告が出たまま・ボタンが「このまま出力する」の状態で、1 クリック目がそのまま出力へ進む**。件数が変わっていても確認を経ずに出る。
2. **`web/src/features/combo/types.ts` の `total` が必須（`total: number`）なのに、`export-data.ts:80` が `res.total ?? ids.length` と「total が無い応答（古い BE）」を想定した分岐を書いている。** 型の上では到達不能であり、コメントの前提と契約が食い違う。どちらかへ寄せること（契約として必須なら `??` を外す、任意なら型を `total?: number` にする）。
3. **`internal/api/comboio/import_upload_errors_test.go` の `testMaxUploadBytes` が `maxUploadBytes` のリテラル写しである。** コメントで「handler.go の maxUploadBytes と一致」と書いているが機械では守られない。外部テストパッケージから参照できないなら、上限を返す小さな公開関数か `export_test.go` で橋渡しするのが本プロジェクトの作法（`ExceedsImportRowLimit` を抽出したのと同じ理由）。
4. **上限超過の利用者向け文言に内部のフォーム欄名が出る。** `fmt.Errorf("%w(%s)", errUploadTooLarge, field)`（`handler.go:281`）により `アップロードファイルが上限(10MiB)を超えています(combo_file)` が画面へ出る。`CHANGE-161` §3.1 の「語彙統一の射程は利用者の目に入る文字列」に照らすと、`combo_file` / `setup_file` は表示語ではない。半角括弧が直前に空白なく付く点も既存の書式と揃っていない。
5. **`VAL-I03` の日本語訳に上限値が入らない。** 着手前は英語の `row count exceeds limit 1000` が出ていたので上限値だけは読めた。今回はじめて訳に当たるようになった結果、`行数が上限を超えています` となり **1000 という数字が消える**。`{{message}}` は `formatIssue` が既に渡しているので、`行数が上限を超えています（{{message}}）` 等で数値を残せる。
6. **`GET /api/combos` が毎回 `SELECT COUNT(*)` を追加で発行するようになった**（`handler.go:385`）。`affectedByGameUpdate` の `EXISTS` 副問合せやタグの `IN (SELECT ...)` を含む WHERE を 2 回評価する。SQLite ローカルなので実害は小さいと思われるが、**実測の記録が報告に無い**。`buildListWhere` を `List` / `Count` で共有した設計自体は正しい（条件を 2 か所に書かない）。
7. **完了報告 §0 の変更統計が古い。** 報告は `37 files / 2169 insertions / 130 deletions` だが、`git diff --stat 233f48e` の実測は `38 files / 2319 insertions / 130 deletions`（最終コミット `29335a9` を含む）。`E-225` の観点の結論（新規 8 本とも deletions 0）は正しいので判断は変わらないが、数値は最終形へ揃えること。

## 推奨修正（優先度別）

### 高（M29 完了前に修正必須）

- **高-1: `web/src/locales/en.json` の `export.maxReached` が誤った文言に書き換わっている。**
  `"Maximum {{max}} combos can be exported"` → **`"Maximum {{max}} combos can be compared"`**（`en.json:522`）。同キーは `ComboListPage.tsx:118` / `MyComboPage.tsx:205` の**エクスポート選択上限**（`MAX_EXPORT_SELECTION` = 1000）のトーストであり、比較（`compare.maxReached`・`en.json:354`）ではない。日本語側は `エクスポート対象は最大 {{max}} 件までです` のままなので、**和英で意味が割れている**。
  完了報告のどこにも記載が無く、`M29-01`（語彙統一）の成果に対する回帰にあたる。動作は正しいままなのでテスト・lint・型検査はいずれも緑であり、人が読む以外に見つける経路が無い型なので「高」に置く。**`exported` へ戻すこと。**

- **高-2: プレビュー↔確定の重大度の非対称が「全数」に達していない（`VAL-S02` / `VAL-C12`）。**
  - `VAL-S02`（セットプレイのレシピが空）: `internal/service/setup/validate.go:127`・`:162` が **ERROR**（`レシピは 1 ステップ以上必要です`）で落とすのに、`internal/service/comboio/csvcore/validate.go` の `decodeSetupRow`（L470〜）には空レシピの検査が存在しない。recipe セルが空だと `s.Steps = nil` のまま **1 件も issue が出ず `StatusOK`** になり、確定で `commitOneSetup`（`import.go:288`）が `検証エラー` として失敗させる。**これは本サブが直した `VAL-C09` の完全な双子であり、向きも (b) で同じ。`VAL-S06` を揃えるときに同じ関数の 20 行下にある**。
  - `VAL-C12`（ラッシュ版の元技が存在しない）: `validation/combo.go:490,496` が **ERROR**、プレビュー層に対応する検査なし（`csvcore` は `VAL-I07` の WARNING で技の存在しか見ない）。同じく (b)。
  完了報告 §5.2 は「**向きと全数**」を掲げ 4 件で閉じており、チェックリスト §2-1 / 指示書 §2.2-1 が求める「同じ入力で重大度が一致するか」を満たしていない。**少なくとも `VAL-S02` は本サブで揃えること**（`VAL-C09` と同じ根拠がそのまま通り、既存データへの影響も同じ理屈で無い）。`VAL-C12` は工数が要るなら「揃えない理由」を報告へ明記すること。

- **高-3: 書出の切り捨て観測の「配線」が無観測である。**
  `ExportCSV` は `resolveTargetCombos` が返した総数を `res := &ExportResult{TotalCombos: total, IncludedCombos: len(combos)}`（`export.go:27`）へ載せているが、**この代入を主張するテストが 1 本も無い**。
  - `export_observation_test.go` は構造体へ手で値を入れて `Truncated()` を呼ぶ純関数テスト。
  - `export_headers_test.go` はサービスを `mockService` へ差し替えているためサービスを通らない。
  - `service_test.go` / `multiuser_test.go` は `data.Data` を見るだけで観測欄を見ていない（`grep -rn "TotalCombos" internal/ --include=*_test.go` の結果はハンドラの mock と純関数テストのみ）。
  ⇒ **`TotalCombos: total` を `TotalCombos: len(combos)` に書き換えても全テストが緑のままである。** これは完了報告 §9.3 が自ら一般形として書いた「判定関数の単体テストと呼び出し側のモックテストが両方在っても、繋ぐ配線は無観測でありうる」そのものであり、**本サブの中心機能に残っている**。既存の `newHarness` を使い、`Count` が返す総数 > `List` が返す件数になる状況（`Options` ではなくリポジトリ既定 100 を踏ませる、あるいは fake の `comboSvc` で `Count` を差す）で `ExportCSV` を呼び、`res.Truncated() == true` と `TotalCombos` の値を主張するテストを 1 本置くこと。置いたうえで、**その配線を殺す破壊確認（`total` を `len(combos)` へ）をやり直して赤を見ること。**
