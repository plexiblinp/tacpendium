## 4. 設計判断とその理由

### 4.1 ★★★連動の形 —— マス入力は `position` も更新する

```
区分を選ぶ     → position = 選んだ区分、startPositionMass = 代表値
マス数を入れる → startPositionMass = 入力値、position = positionFromMass(入力値)
％を入れる     → MassPercentInput の中でマス数へ換算(区分へは触れない)
```

**チェックリスト B-3「マスから position を埋めて送っていないか」に対する説明:**

- **禁止の射程は「保存時」である。** §0.2 は「区分を選んだらマスを埋める」を**保存時に**やり直さないこと、§4.2 の見分け方は「**送信の直前に**値を書き換える」。
- **本実装の連動は入力時に起きる。** 利用者の画面上で数字が動くのが見える。**そもそも §2.2-1 が「どれを動かしても他の 2 つが追随する」ことを要求している。**
- **`buildCreatePayload` / `buildPatchPayload` は state をそのまま送る。** 送信直前の書き換えは 1 行も無い。
- **★導出の権威はサーバである。** 区分とマス数が食い違って届いたら `normalizePositionAndMass` がマス数を優先して `position` を導出し直す。⇒ UI は権威ではないので、同じ判断が 2 か所に**在る**のではなく、UI の値は上書きされる側である。

**★代案として「`position` を書かず、`utils.ts` に `effectivePosition` を置いて振り分けだけ直す」形も検討した。不採用の理由 2 つ:**

1. **区分表の導出が 3 か所目になる**(サーバ `model.PositionBands` ／ フロント `positionFromMass` ／ 振り分け用)。§2.2-3 の「新しい変換を書かない」に反する。
2. **点灯している区分と、送る `position` が食い違う窓ができる。**

### 4.2 ★★PATCH / PUT の振り分けが正しくなる(4.1 の帰結)

**サーバの PATCH 経路は `normalizePositionAndMass` を呼ばない。** ⇒ 区分をまたぐマス変更を PATCH で通すと、DB の `position` とマス数が食い違う。

4.1 の形だと `position` が入力時に動くため、既存の `hasKeyChanges` がそのまま正しく働く:

| 操作 | `position` | 経路 | DB の整合 |
|---|---|---|---|
| 区分内のマス変更(80 → 85) | 不変 | **PATCH** | 元から正しい ○ |
| 区分をまたぐマス変更(80 → 100) | 変化 | **PUT** | サーバが導出し直す ○ |
| 区分の選択 | 変化 | **PUT** | 現行どおり ○ |
| 運び量の変更 | 不変(キーでない) | **PATCH** | 段 1 で通る ○ |

**⇒ `web/src/features/combo/utils.ts` の `extractKeyFields` / `hasKeyChanges` は 1 行も触っていない。** 重複事前チェック(`checkInput`)も無傷であり、`duplicate-precheck-ignores-position-mass` は射程外のままである(指示書 §3-6・チェックリスト D-7)。

**★実装中に一度、`buildCreatePayload` へ足すつもりのアンカーが重複事前チェック側にも一致した。** 機械的に置換していたら射程外の面を触っていた。⇒ 関数スコープを切って `buildCreatePayload` の中だけへ入れた。

### 4.3 ★★丸めの向き(指示書 §2.2-4・チェックリスト C-4)—— 1 か所に決めた

| 向き | 規則 |
|---|---|
| **表示**(マス → ％) | `Math.round(massToPercent(mass) * 10) / 10`(**小数第 1 位へ四捨五入**) |
| **入力**(％ → マス) | 既存の `percentToMass`(**四捨五入 ＋ 0〜160 クランプ**) |

**★小数第 1 位にした根拠**: 整数 % だと `1% = 1.6 マス` で往復が壊れる(`position.test.ts` が陽性対照で固定済み)。**小数第 1 位なら誤差上界 0.08 マスとなり、0〜160 の全 161 値で `マス → % → マス` が不変。** 全数をテストで固定した。

**★詳細画面の `formatPositionMass` も同じ規則である。** ⇒ 入力欄と詳細画面で違う数字は出ない。

**★★帰結を 1 つ明示する**: **パーセント欄からは値域外の値を作れない**(`percentToMass` がクランプするため)。⇒ **161 / -1 の拒否はマス欄からしか到達しない。** これは「丸めの向きを 1 か所に決めた」ことの副作用であり、隠さずテストで固定した。

### 4.4 ★マス欄をクランプしなかった → **★★2026-09-13 開発者裁定で差し戻した**

既存の消費ゲージ欄は `clampNumericString` で UI 上限クランプしている。**本サブでは使わなかった。**

**着手時の理由**: `clampNumericString` は 161 を黙って `"160"` にする。⇒ 指示書 §5-4 の「161 を拒否する」が観測できなくなる。

**★★2026-09-13 開発者裁定で差し戻した。** 要望は「**他の項目と同じように、所定の範囲外は画面的に入力できないこと**」であり、**画面の一貫性が優先された。** ⇒ `clampNumericString` を適用した。

**★zod と `VAL-RANGE` は残している。** CSV / API から入る経路は画面を通らず、防衛線を外すと値域外が DB の `CHECK` 違反(500)になるためである。**⇒ §5-4 の「161 / -1 を拒否」は「そもそも画面から入らない」へ意味が変わった**(§5 の表を参照)。

### 4.5 ★★別の `Field` にした(順送りの到達性)

**マス数欄を区分ボタン群と同じ `Field` へ入れると、キーボードから永久に到達できなくなる。**

`Field` が `data-seq-stop` の単位であり、`useFieldSequence` の `focusableIn` は **その停止点の最初の focusable しか拾わない**(`useFieldSequence.ts:29-33`)。⇒ 区分ボタンだけが拾われ、Enter は次の `Field` へ飛ぶ。

**★★型検査もテストも E2E も緑のまま落ちる型である。** ⇒ 別 `Field` にした上で、「順送りでマス数欄へ到達できる」テストを新設して固定した。

### 4.6 表示側の置き場(指示書 §2.3-1)

- **始動位置のマス数・％** … `ComboDetailHeader` の状況ブロック、区分の `<dd>` に後置。**3 つが同じ 1 つの値を表すため。**
- **運び量** … `ComboDetailMetadata` の数値ブロックに新設。

**★★運び量を状況ブロックへ置かなかったのは意図である。** あちらは**重複判定キーの 4 欄そのもの**であり、そこへ並べると「運び量もキーの一部」と読める。**⇒ 置き場そのものが `D-731` の不変条件 1 を補強する。**

**★マス数が未入力なら何も足さない**(区分だけの旧データが大半のため。「-」を足すと既存コンボの状況欄が一斉に汚れる)。運び量は独立した欄なので他の任意欄と同じく「-」を出す。

### 4.7 ★一覧に列を足さなかった(指示書 §2.3-2・チェックリスト E-2)

**理由 3 つ:**
