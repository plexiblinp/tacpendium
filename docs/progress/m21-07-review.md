## 総評

**最重要ゲート（§9-1「軸が供給元ごとではなく合流層に 1 か所」）と次点ゲート（§9-2「観測を止めていない」）は、いずれもコードで確認して合格である。** `isAnyModalOpen()` の呼び出しは `PhysicalInputProvider.tsx` の 2 か所（`handleSources` / `dispatchAction`）だけで、供給元側（`useGamepadPolling` / `useKeyboardInput`）には 1 バイトも条件が入っていない。点灯の更新を抑止分岐より**前**へ移し、抑止中も `seedNow` で判定層の押下状態を同期し続ける形は、§4.2 の要求を正確に実装している。破壊確認も 4 通り（B1〜B4）を当て、「赤にならなかった項目に対して何が代わりに守っていたか」を判定層の立ち上がり性質まで掘って特定しており、`SUPP-001` §5.5 (10′) の要求水準を満たしている。

**一方で、判定の入口（何をモーダルとして数えるか）に実測で確認できる穴が 1 つ残っている。** 完了報告 §3.1 と `modal-presence.ts` 冒頭のコメントは「アプリ内のモーダルは例外なく共有プリミティブ 3 つを通る」と書いているが、**実際には共有プリミティブを通らない自作モーダルが 2 か所あり、うち 1 か所は入力面と同じ `ComboEditor` の中にある**。実装の穴そのものは 2 行で塞がるが、**誤った断定がコードのコメントとして残っている**点を「高」として扱う（後任が本文を複製し、注記を読まないため）。

それ以外は良質である。対照実験の置き方（抑止の主張 1 つにつき「開かなければ入る」対照を対で置く）、`ModalPresenceMarker` を Content の内側へ置くことで置き場所の誤りを構造的に防いだ設計、E2E の破壊確認で「A・C が赤／B が緑」の非対称まで見た点は、いずれも本プロジェクトが繰り返し落としてきた型を先回りして潰している。

### 記述と実体の乖離（優先度較正により「高」）

- `web/src/lib/modal-presence.ts` L15-16: 「**アプリ内のモーダルは例外なくこの 3 つを通るため、新しいモーダルは何もしなくても対象になる。**」
- 同 L19: 「**誤検出は「拾わないことの確認」ではなく構造的に 0 である。**」
  → こちらは**モーダルでない重なりを拾わないこと**の主張であり、正しい。ただし直前の断定と並ぶことで「網羅性も構造的に保証されている」と読めてしまう。
- 完了報告 §3.1「アプリ内のモーダル 22 ファイルは例外なく共有プリミティブ 3 つを通っていた」。

**本プロジェクトの較正どおり「高」に置く。** 動作は（自作モーダル以外では）正しいままなので lint も型検査もテストも緑であり、**人が読む以外に見つける経路が無い**。そして本コメントは「新しいモーダルは何もしなくても対象になる」という**次のサブの前提として複製される形**をしている。実際には「**共有プリミティブ 3 つを通ったモーダルだけが対象になる。自作の重なりを足したら申告が要る**」が正しい。

### モーダル表示中もキー既定動作の抑止（§6.5.1 (3)）が掛かり続ける

`useKeyboardInput.ts` L95 / L123 の `event.preventDefault()` は capture フェーズで、**編集可能要素にフォーカスがある場合を除き、モーダルが開いていても掛かり続ける**。本サブは §2.2-5 により §6.5.1 を触らない方針なので**規約違反ではない**が、利用者から見える帰結が 1 つある。

- `ModifiersEditor` は **Radix の `RadioGroup` と `Checkbox`** を持つ（それぞれ矢印キーで移動／Space で切替）。
- 利用者が矢印キーを方向に、Space をいずれかの技に割り当てていると、**そのダイアログ内でのキーボード操作が効かなくなる。**
- これは M21-05 由来の既存挙動であり本サブの回帰ではない。ただし**本サブが「モーダルが開いている間」という軸を導入した以上、「その間は既定動作の抑止も外すか」は設計判断として起票に値する。**
