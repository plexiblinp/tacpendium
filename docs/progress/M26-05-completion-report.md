## 3. 設計判断とその理由

### 3.1 同意の見せ方は「段内のインライン切替」を採った

指示書 §2.2 は「ダイアログか、段内のインライン表示か」を製造の判断としている。**インラインを採った。**

- **入れ子を避けられる** — ウィザードは既にダイアログの 3 段を段として展開した形である。ダイアログを開くと、その中の setPassword 段と Step 7 そのものが二重になる
- **リセットが構造から出る** — `WizardPage.tsx` は `{step === 7 && lanEnabled && ...}` で条件描画しており、段を離れると `Step07Password` ごと unmount する。⇒ 「開き直したら同意はリセット」が `useState` の初期値として自然に満たされる
- **「あとにする」の導線に手を入れずに済む** — `PasswordSetForm` は `onSkip` を渡すかどうかしか seam を持たず、`disabled` プロップもラベル差替えも無い。ダイアログ方式でもインライン方式でも `onSkip` のコールバックを差し替えるだけで足り、**同ファイルを 1 文字も触らなくてよい**

**★★【2026-09-12 訂正】初版は「実機で見て『これは違う』と思った点は無い」と*製造が*書いていたが、これは誤りである。⇒ 製造はアプリを起動して画面を見ていない。** 回したのは単体テストと **headless** の E2E だけであり、**見た目の妥当性を 1 度も観測していなかった。** **★結果的に妥当であっても、それは書いてよい理由にならない**——断定を書いた時点で、それが観測ではなく予測であったことは記録から消える（`D-510` と同型）。

**★★【2026-09-12 追記】その後、開発者が実機で確認し「問題なし」と判定した**（§8-6）。**⇒ 指示書 §7 が求める実機の所見は、開発者の実観測として得られている。★製造の所見ではない。**

実機を見ずに決めた形が 1 つあった——**同意ビューでは段の「戻る」を出さない。** 同じ名前のボタンが 2 つ並ぶと役割名で一意に指せなくなるためであり、段へ戻るにはいったんパスワードの段へ戻る（2 クリック）。**★この形も開発者の実機確認の対象に含まれ、問題なしと判定された。**

### 3.2 新しく立てた i18n キーは 3 本。それぞれ「なぜ既存で足りないか」

| キー | 既存キーで足りない理由 |
|---|---|
| `wizard.step5.lanWarningBody` | `enableConfirmBodyNoPassword` は「**いまはパスワードが設定されていません**」と述べるが、Step 5 ではまだ Step 7 が来ていないため**事実として早い**（指示書 §2.3-2 が名指しで禁じている）。`enableConfirmBodyWithPassword` は「パスワードの入力が必要です」と述べるが Step 5 では**偽**である |
| `wizard.password.consentTitle` | `settings.network.consentTitle` は「パスワードなしで **ON にします**」。ウィザードではこの時点で ON にならない（適用は Step 8 の `handleFinish`） |
| `wizard.password.consentAction` | `settings.network.consentAction` は「**ON にする**」。ウィザードのボタンは段を進めるだけである |

**文面は書き起こしていない**（指示書 §4.4）。`lanWarningBody` は `enableConfirmBodyNoPassword` からパスワードの段落だけを外し、冒頭の「この設定を ON にすると」をウィザードの語へ替えたものである。

### 3.3 新ブロックを `wizard.password` にした理由（**★罠がある**）

i18n の `wizard.step7.*` は**完了画面**（`Step07Complete.tsx`）が使っている。`Step07Password.tsx` は `wizard.step7` を 1 つも持たず、`auth.setPassword.title` と `wizard.prev` を借りている。**⇒ i18n のブロック名と `Step07*.tsx` のファイル名は 1 つずれている。** パスワード段のキーを `wizard.step7` へ入れると完了画面のキーと混ざるため、新ブロック `wizard.password` を立てた。

### 3.4 E2E はサーバ状態を 1 バイトも変えない

完了ボタンは `PUT /api/config` で `server.mode: "lan"` を使い捨てスタックの設定ファイルへ**永続化する**。`fullyParallel: false` が直列化するのはファイル内だけで、ファイル単位では並列に走るため（`D-362`）、書き換えると同時に走る他 spec が別モードのサーバを相手にすることになる（`D-466` / `E-142`）。**`m22-06-connection-qr.spec.ts` が同じ `server.mode` について同じ判断をしている。**

⇒ オリジン直下の `/api/` に限った route で **PUT だけ**を捕まえ、送信ボディを検証して合成応答を返す。GET は素通しする。**書き換えないので復元も要らない。**

### 3.5 `D-396` には抵触していない

**「あとにする」の導線そのものは残してある**（`Step07Password.test.tsx` に 1 本の床を置いた）。同意チェックは詰みを作らない — 忘れようがなく、いつでも入れ直せる。`D-396` が消したのは「パスワードを忘れると LAN 共有が二度と使えない」詰みであり、そこには触れていない。
