## 設計準拠性以外の指摘事項

### 高-1: ファイル名欄の「編集済み」フラグが二度と復帰しない（連続エクスポートで衝突する経路が残る）

**根拠**: `web/src/features/combo-io/components/ExportDialog.tsx:63-64`（`const [baseNameEdited, setBaseNameEdited] = useState(false)`）／`:76-82`（`if (!open || baseNameEdited) return;`）／`:242-245`（`onChange` で `setBaseNameEdited(true)`）。**`baseNameEdited` を `false` へ戻す経路がファイル内に 1 つも無い。** かつ `ExportDialog` は `ComboListPage.tsx:337` / `MyComboPage.tsx:405` で**常時マウント**されており、`open` の出し入れで unmount されない。

**起きること**（そのページに居る限り継続する）:

1. 利用者がファイル名を `my-combos` に書き換えて出力 → `my-combos.zip`。
2. ダイアログが自動クローズ → 選択を変えて再度開く → **欄は `my-combos` のまま**。対象・件数の変化に追従しない（`useEffect` が `baseNameEdited` で早期 return するため）。
3. そのまま実行 → **再び `my-combos.zip`。連続エクスポートで名前が衝突する。**

指示書 §4.4 の「書き換えていれば尊重する」は `SM-088`（セットプレイ名）と同じ作法を指しており、あちらは**1 つの対象に対する 1 つの名前**である。ここでは**別の対象に対して前回の名前が黙って再利用される**ため、作法の写し取り方が一段ずれている。memo の原文「連続エクスポート時に名前を一々変えないといけないのでしんどい」が、欄に一度でも触れた利用者にはそのまま残る。

**なぜテストで落ちないか**: `ExportDialog.test.tsx` の「連続して実行しても同じ名前を渡さない」は**未編集経路**を見ており、「書き換えを尊重する」は**1 回の実行**しか見ていない。「編集後に 2 回実行」「編集後に閉じて開き直す」を見るケースが無い。

**修正案**（いずれか）:
- `open` が `false → true` に変わったときに `setBaseNameEdited(false)` する（＝編集はそのダイアログ 1 回ぶんの意思とみなす。`useEffect` に `if (open && !prevOpen)` の分岐を足す形）。
- あるいは編集済みでも `issueExportBaseName` 相当の重複回避を通し、同名の 2 回目に連番を付す。

**重大へ寄せなかった理由**: 既定（未編集）経路は純粋関数テストで決定的に守られており衝突しない。衝突は利用者が明示的に固定名を入れた後にだけ起きる。ただしチェックリスト 1-12 の文面（衝突なら重大）に触れうる位置にあるため、**M24 完了前の修正を必須**とする。

### 高-2: 本サブが書き換えた E2E ヘッダに、事実でない担保先が残っている

**根拠**: `web/e2e/m17-05b-export-flow.spec.ts:18-20`

```
// CSV ダウンロードの非回帰は combo-csv-io.spec.ts / m17-01-media-fields.spec.ts が
// `make e2e` 実行の一部として担保しているため、本 spec では重複して再検証しない。
```

`web/e2e/m17-01-media-fields.spec.ts` を `grep -n "export\|download"` すると**ヒット 0 件**である。同 spec はメディア 3 フィールドの入力→詳細表示→クリア→削除だけを見ており、CSV ダウンロードには一切触れていない。本サブは**この段落を書き換えており**（「温存対象」→「M24-06 で廃止した」）、誤りの半分をそのまま再掲した。
