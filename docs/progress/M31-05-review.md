データ投入そのものは堅い。既存 `custom_states` の非破壊性は、レビュー側で v107 の DB を独立に組み立てて up / down を往復させ、9 キャラすべてで既存 state の JSON が 1 バイトも変わらないこと・down が投入前へ完全に戻ることを確認した。完了報告に載る実数（案 (ii) / 案 (vi) の state 数、9 キャラの before → after、追加 code の単独ヒット数）は、レビュー側の独立計測とすべて一致しており、製造の主張は検算に耐えている。束 A-4 と束 B-2 という本チェックリスト最重要の 2 点も、機械検査つきで満たされている。

## 推奨修正（優先度別）

### 高（M31 完了前に修正必須）

**高-1. 舞の `kachousen` が選択肢 11 個で、ボタン化の上限 10 を超えている（開発者裁定違反・検査は緑のまま）**

- 事実: `migrations/000110_..._up.sql` の `mai` / `kachousen` は `options` を 11 件（値 0〜10）持つ。`ComboEditorBasicFields.tsx` の新分岐は `opts.length > 0` で無条件に `OptionButtonGroup` を出しており、`shouldButtonizeOptions` を通らない。
- 反している規約: `web/src/features/combo/optionButtons.ts` の冒頭に置かれた開発者の逐語「10を超えるものはボタン化の対象外。」（`D-578(4)`）。`optionButtons.test.ts` は `shouldButtonizeOptions(11) === false` を明示的に固定しており、11 は線の外側である。
- 実害: `shortcutKeyForIndex(10)` が `null` を返すため、11 個目の「焔乱れ」だけ数字キーが割り当たらない。同じ群の中に「キーで選べる選択肢」と「選べない選択肢」が混在する。`OptionButtonGroup` の roving tabindex は群全体を 1 停止にするため、矢印キーでも群内を移動できない。結果として、焔乱れはマウス以外で選べない。
- なぜ検査で捕まらないか: 新分岐が `shouldButtonizeOptions` を呼ばないため、線引きを固定しているテストの射程外に居る。`optionButtons.test.ts` の「実際の欄の個数」表にも今回の欄が足されていない。型検査・単体・E2E のいずれも緑のまま通る。
- 対応: 次のいずれかを開発者判断で選ぶこと（選択肢の見せ方はユーザー体験に影響するため `roles-and-routing` ハード列に当たる）。
  1. 舞の選択肢を 10 以内へ畳む（例: 焔版を `flame_stock` との組み合わせで表す。ただし完了報告 §5-8 が「焔ストックが 0 なのに焔版がバウンド中」を許してしまうとして退けた案であり、退けた理由は妥当）。
  2. 舞だけ 2 つの state に分ける（例: 通常版 6 択と焔版 6 択）。語幹はどちらも `kachousen` を含むためタブ照合は保たれる。
  3. 選択肢が 10 を超えるときはプルダウンへ落とす分岐を足し、`shouldButtonizeOptions` を実際に呼ぶ。線引きが「人が欄ごとに決める」ものである以上、これは `optionButtons.ts` の設計意図を変える変更になるため、独断では入れないこと。
- あわせて: 採る案が決まったら `optionButtons.test.ts` の「実際の欄の個数」表へ今回の欄を追記し、次に選択肢を増やす人が線を越えたことに気づけるようにすること。

**高-2. `DES-003` §3.2 の「設置系は `type: flag`」が as-built で失効したのに、CHANGE 請求に含まれていない**

- 事実: `DES-003` §3.2 の「対応可能なケースの例」に「**設置技が置かれた状態から始まるコンボ** → …自分の側に立つ状態は `subject: self`, `type: flag`」という行がある（`CHANGE-154` で `subject` の軸が是正された際に書かれたもの）。今回投入した 11 件のうち `flag` は `saihasho_is_set` と `blanka_chan_bomb_is_set` の 2 件だけで、7 件が options 付き `level`、1 件が `stock` である。
- なぜ「高」か: 動作は正しいままであり、テストも lint も型検査も緑になる。人が読む以外に見つける経路が無い。かつ、この節は「設置系をどう表すか」を次に調べる人が最初に開く場所であり、旧記述がそのまま次のサブの前提として複製される（`M19-DESIGN-08` §3.1 の `D-250` と同型）。同じ節は `CHANGE-154` と `CHANGE-169` で既に 2 度同型の是正を受けている。

**高-3. 完了報告 §2.6 の「`show_delta` は 1 件も付けていない」が実装と §3.2 に反する**

- 事実: `mai` の `kachousen` などの options 付き state に `show_delta` が無いのは正しい。しかし `kimberly` の `shuriken_bomb_is_set` は `"show_delta":true` を持っており、完了報告 §3.2 の表自身が「stock 0〜3・`show_delta`」と書いている。§2.6 の「1 件も」は同じ文書の中で矛盾している。
- なぜ「高」か: 完了報告は実装の細部の正本である（`CLAUDE.md` §8）。この一文は「本サブは `show_delta` を扱っていない」と読めるため、次に `custom_states` を触る人が kimberly の delta 表示の存在を知らずに設計する。実装は正しいので、テストでは永久に検出されない。
- 対応: §2.6 の一文を「options を持つ state には `show_delta` を付けていない」へ限定すること（`customStates.ts` の `OPTION_PHRASE` のコメントは既にこの限定形で正しく書かれている）。

### 中（M32 着手と並行可）

**中-1. kimberly を `type: stock` にした判断に、裁定としての記録が無い**

- 指示書 §2.1 の分岐表は「実査 5 が『居る』だった → そのキャラだけ案 (ii) を使い、止めずに進む」と明示している。実際に採ったのは案 (ii) でも案 (vi) でもない `type: stock` である。完了報告 §2.5 は理由を書いており（フラグでは同じ強度を 2 つ置いた場合の個数が落ちる）、その理由自体は妥当。
- 問題は記録の側。根拠が「（2026-09-10 開発者確認）」という括弧書き 1 行のみで、裁定番号もボードの行も無い。同様に ingrid の 9 択も「（2026-09-10 開発者回答）」だけである。選択肢の粒度はユーザー体験に影響するためハード列に当たり、後から「誰がいつ何を決めたか」を引けない形で残すべきではない。
- 対応: 設計伝達レポート §2（契約違反の独自判断）または §3（製造判断）へ、指示書の指示との差分として明示的に書き、設計卓に裁定番号を払わせること。
- あわせて: 検討表に第 3 の案が無い。変種ごとの `stock` を 6 本置けば「どの強度を何個置いたか」を両立できる（案 (ii) を `flag` ではなく `stock` で実施する形）。採否は別として、退けた理由が残っていないと後任が同じ検討を繰り返す。

**中-2. kimberly の 2 つの state が、画面上でどちらも「ストック数」と表示される**

- `shuriken_bomb_is_set` は options を持たないため `STOCK_PHRASE` を通る。結果、エディタと詳細に次の 2 行が並ぶ。
  - 「手裏剣ストック：始動時に必要な最低のストック数」
  - 「細工手裏剣設置数：始動時に必要な最低のストック数」
- 指示書 §0.3 / §4.1 と `CHANGE-169` §2.5 が名指しした「残弾とフィールド上の設置数の取り違え」が、実装ではなくラベルの側で再現している。開発者が逐語で「別物として扱ってください」と述べた区別が、利用者から見て文言上つぶれる。
- 対応: `STOCK_PHRASE` は既存の全 stock state が通る共有文言であり、独断で書き換えないこと。設置系の stock 用に第 3 の固定句（例「始動時に置いてある数」「終了時に置いてある数」）を足すか、既存文言のままでよいかを開発者へ確認すること（ユーザー体験に影響＝ハード列）。

**中-3. options 付き state で既定値「なし」を押すと、保存内容が変わらないのにフォームが dirty になる**

- `setIntField` は空文字以外では必ず `nextPair[which]` へ値を書く。既定値（min ＝「なし」）を選ぶと `{ start_min: 0 }` が入る。`buildSituation` は `isDefaultIntValue` で落とすため保存ペイロードは変わらないが、`formDirtyKey` が見るのは `basic.customStates` の生の値であり、`normalizeForDirtyCheck` は「0 と false は値である」として 0 を残す。
- 実害: 「なし」は既定で選択済みに見せる設計（完了報告 §5-6）であるため、利用者が確認のつもりで押しただけで離脱ガードの確認ダイアログが出る。キャラ変更確認（`isFormDirty`）も同様に発火する。
- 対応: `setIntField` の末尾で、正規化後の値が `isDefaultIntValue` を満たすなら `setCustomState(def.code, undefined)` へ落とす。既存の数値入力欄でも同じ現象は起きうるが、options では「押しても何も起きないはずの選択肢」が可視化されたぶん踏みやすくなっている。
