## 総評

本サブの最重要ゲート 2 件——**「子表の一覧がハードコードされていないこと」**と**「self-FK が NULL 化であって削除でないこと」**——はいずれも満たされている。とくに `fk_on` / `fk_off` の 2 枝を持たせ、破壊確認 1 で **`fk_on` が緑のまま通った**ことを観測として残した判断は、指示書 §1.2 が求めた「忘れたことが分かる仕組み」の本質を掴んでいる。FK=ON だけで回すテストではこの明示削除は 1 行も守られない、という事実をコードとテストの両方に刻んだのは本サブ最大の成果である。

実装面の欠陥は見つからなかった。`SoftDelete` の 0 行分岐、`PermanentDelete` の名前付き `err` 経由のロールバック、`unlink_all` へ `UpdateSetupReferences` を足さないと FK 違反で編集自体が落ちるという実測——いずれも踏むべき地雷を先に踏んでいる。既存テストの上書き事故を自分で検出し教訓ごと残した点も評価できる。

一方で、**「高」が 2 件ある**。(a) `docs/progress/progress-log.md` への索引行が 1 行も無く、`scripts/check-progress-log-index.sh` が実測で違反 1 件を返す。M23-05 / M23-06 が 2 サブ連続で「検査が偽陽性で緑になる／手順で担保する」と決めた直後の欠落であり、今回は検査が正しく赤を出しているにもかかわらず落ちている。(b) `internal/api/combo/handler_test.go` の godoc が、本サブが撤回した前提（`WHERE id = ?` で `RowsAffected=1` になる）を**仕様の根拠として**書いたまま残っている。mock service を使うテストのため永久に緑であり、人が読む以外に検出経路が無い。

そのほか、子表の機械列挙が `on_delete = 'CASCADE'` に限定されているため「`combos` を参照するが CASCADE 句を持たない新表」は明示削除もテストも素通りする、という残穴がある。指示書 §4.1-3 の文言どおりではあるが、本サブの目的そのものに対しては穴なので中として挙げる。

### 中-1: 子表の機械列挙が `ON DELETE CASCADE` に限定されており、「CASCADE 句を持たない新しい子表」を素通りさせる

`hard_delete_children_test.go:78-80`

```go
`SELECT "from" FROM pragma_foreign_key_list(?)
  WHERE "table" = 'combos' AND on_delete = 'CASCADE'`
```

指示書 §4.1-3 の文言（「`combos` を `ON DELETE CASCADE` で参照する子表を機械的に列挙する」）どおりではあるので**契約違反ではない**。しかし本サブの目的は「子表の一覧が将来ずれることを検出し続ける」ことであり、その観点では穴が残る:

- 新しい子表が `ON DELETE` 句なし（既定 `NO ACTION`）で作られると、**列挙に出ず・明示削除もされず・テストも緑**。FK=ON の接続では完全削除が FK 違反で落ち、FK=OFF では dangling が残る。
- **これはまさに本サブ §4.2 が扱った `materialized_from_combo_id` の型そのものである。** その self-FK は `table == "combos"` の分岐（`:75-77`）で列挙から除外され、別テストが担保しているが、**「`combos` 以外の表が `combos` を CASCADE 以外で参照する」場合を見ている主張はどこにも無い。**

**修正案（設計卓の判断が要る）**: 列挙を「`combos` を参照する全 FK」へ広げ、`on_delete` の値で期待を分岐させる（`CASCADE` → 削除後 0 行 ／ `SET NULL` → NULL 化 ／ それ以外 → **未知の扱いとして落とす**）。「未知の `on_delete` が現れたら赤くする」形にすると、一覧のずれを取りこぼさない。射程の判断は設計卓へ。

### 中-3: `unlink_all` の意味論が変わったことが、契約反映の申し送りに名指しされていない
