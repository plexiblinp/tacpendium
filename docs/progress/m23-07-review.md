## 総評

**最重要ゲート（「セットプレイの削除がコンボを消しうるか」）は塞がれている。** 導線は `useDeleteSetup` → `setupApi.remove` → `DELETE /api/setups/{id}` の一本道で、コンボ側の mutation とは面もフックも文言も分かれている。ゲートのテストは fetch を実観測し、**危険側（`/api/combos/*` への DELETE）を先に検査して**、id 取り違え（`/api/combos/{setupId}`）まで含めて空配列を主張している。fixture の id も combo=10 / setup=7 と別値で、`M23-06` が踏んだ空振りを避けている。

配線 3 本（入れる／開く／逃げる）はいずれも指示書の定めた形で通っており、`GET /api/combos/{id}` にフラグは足されず、`FindByIDAllowDeleted` の述語も無傷、`recipe_cache` への書き戻しも無い。スキーマ変更 0・マイグレ 0・新 API 0（紐付け解除は既存経路）。**独自判断は `D-485` の上書き 1 件だけで、理由・影響・裁定依頼が明示されている**——指示書 §4.3-1 とチェックリスト §9 が列挙を必須にしている以上、判断は妥当である。

自分でも全数を再実行して確認した: `go test ./...` FAIL 0 ／ `pnpm test` 178 files・1771 tests green（完了報告の件数と一致）／ `tsc --noEmit` 緑 ／ `gofmt -l` 差分なし ／ `check-browser-storage-keys.sh` `check-enum-sync.sh` `check-progress-log-index.sh` `check-md-emphasis.sh` いずれも違反なし。**`make e2e` は本レビューでは未実行**（§制約事項）。

## 良かった点

1. **★★最重要ゲートのテストが「フックのモック」ではなく「fetch の実観測」で書かれている。** フックをモックすると「どのフックを呼んだか」しか見られず、フック内部で URL を取り違えている形を検出できない。**守るべきものが「どの URL へ、どのメソッドで飛んだか」であることを正しく特定している。** さらに**危険側の検査を先に置いた**ため、失敗メッセージが「コンボの削除 API を叩いている」と危険そのものを名指しする。
