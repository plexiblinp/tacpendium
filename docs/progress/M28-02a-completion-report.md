## 2. §2.2-3 バージョン文字列の順序をどう解いたか（**本サブの中心**）

### 2.1 形式

`YYYY.MM.DD.NN`（`D-728`）。正本は **`internal/gameversion`**。
正規表現 `^\d{4}\.(0[1-9]|1[0-2])\.(0[1-9]|[12]\d|3[01])\.\d{2}$`。

**★★順序の解き方は「順序用の列を足さない」である。**
全フィールドが固定幅のゼロ埋めであるため **TEXT の辞書順が時系列順と一致する**。
SQL 側も単純な `>` で比較している。

`internal/gameversion/gameversion_test.go` が次の 3 つを固定した。

1. **時系列に並べた 10 件の隣接ペアがすべて文字列比較で昇順**
   （`2026.08.03.09` < `2026.08.03.10` を含む＝`"1.9" < "1.10"` 型の誤りが起きない）
2. **ゼロ埋めなしの版数なら実際に壊れる**ことの陽性対照（`"1.10" < "1.9"` が真であることを assert）
3. 同値は「新しい」ではない（判定は基準より新しいものだけを出す）

### 2.2 §2.2-3-b 形式の検証 —— **どこまで塞いだか**

**★入口は 4 つあり、4 つとも塞いだ。**

| # | 入口 | 実装 | 検証 |
|---|---|---|---|
| **1** | **DB** | **3 列すべてに `CHECK` 制約**（GLOB で固定幅・全桁数字、`substr`+`CAST` で月 1〜12・日 1〜31） | `TestRun_M2802a_GameUpdateTrackingSchema` が **10 種の崩れた値**（`2026.8.3.1` / `2026.08.03.1` / `2026.13.01.01` 等）を 3 列すべてへ入れて弾かれることを見る。正しい 4 種が通ることも見る |
| **2** | **アプリ** | `internal/gameversion.Valid` / `Validate` | `gameversion_test.go` が 17 種の不正値を弾く |
| **3** | **`seedgen`** | `validate()` へ値域検証（`startup_basis` と同型。不正値で `Generate` そのものを fail） | `TestRead_InvalidGameVersionFails` |
| **4** | **マイグレの値そのもの** | `000104` が直書きする `'2026.08.03.01'` | 上記 CHECK が同じマイグレ内で効く |

> **★★1 は本スキーマ初の CHECK 制約である。** `DES-003` §3.4 ／ `internal/model/combo.go:6` の
> 「CHECK は DB 側に付けずアプリ層で制約する」方針に対する **意図的な例外**であり、
> 指示書 §2.2-3-b が DB 側の CHECK を名指しで要求している。
> **★例外にした理由＝アプリ層だけでは生 SQL の `UPDATE` を塞げない**。マーカーを立てるのは
> 配信者（開発者）であり、その経路は DML マイグレ ＝ 生 SQL である。
> **⇒ §6 で `DES-003` への反映を請求する。**

### 2.3 §2.2-3-c 「現在のデータバージョン」の持ち場

**`games.current_data_version`（1 行・`sf6`）**。設計卓の見立てどおり。
`games` の現物を実査した結果、列 4 本のみ・後続マイグレでの改変 0 件・**リポジトリ層が存在しない**
（`internal/model/game.go` は参照 0 件の死にコードだった）。⇒ `internal/repository/game/` を新設した。

**★★`MAX(moves.last_changed_game_version)` では代用していない。**
代用すると、move を 1 行も変えないアップデート（入力ミスの訂正が moves 以外だった ／ 機能追加で列が
増えただけ）で `MAX` が動かず、版が上がったことを表せない。後半 `NN` はまさにその型の版である。

## 3. §2.2-4 `seedgen` の出力にマーカーを入れたか

### 3.1 **入れた。`-mode game-version` という独立したモードとして。**

**★★初版は「moves 波の INSERT 直後へ UPDATE を出す」形だった。それは誤りであり、レビューが実測で検出した。**

`assertGolden` は **「現在の CSV から再生成した SQL」と「適用済みマイグレ」を byte 比較する**。
⇒ マーカーを moves 波の出力へ混ぜると、**CSV へ値を 1 つ書いた瞬間に `000026` の golden が落ちる**。
しかも失敗メッセージは「**適用済みマイグレであり上書き再生成してはならない**」であり、**直し方の無い赤**になる。

**★初版の報告は「golden 17 本は緑のまま」と書いていたが、それは値が 1 つも無い状態でしか成り立たなかった。**
**⇒ 「配信者がマーカーを立てる」という、この機能を実際に使う唯一の操作が成立していなかった。**

**★同じ壁に本プロジェクトは既に一度当たっている** —— `zangief` / `dhalsim` の連打版を
`character_data` に載せていないのは「**載せると生成物が変わって golden が壊れる**」ためである
（`csv_db_sync_test.go` 冒頭・`D-94` / `D-99`）。**初版の設計はこの先例と正面衝突していた。**

### 3.2 採った形（是正後）

1. `character_data/*.csv` へ **24 列目 `last_changed_game_version`**（全 31 ファイル）
2. **`writeMovesInsert` も moves 波の生成物も 1 文字も変わらない**
   ⇒ **golden はマーカーの有無に関わらず永続的に安全**である
3. **`cmd/seedgen -mode game-version`** が **独立したマイグレ**としてマーカーの `UPDATE` を生成する
   （`derived-backfill` / `move-commands` と同じ流儀。新しい流儀を作っていない）
4. **★あわせて `games.current_data_version` を引き上げる**（`current_data_version < ?` を条件に置き、引き下げはしない）
   —— **マーカーだけ立てて現在版を据え置くと、以後に登録されるコンボが「登録した瞬間に影響可能性あり」で出る**

### 3.3 **★★配信者がマーカーを立てる運用手順**（実測して全緑を確認した）

| 順 | 操作 |

**★実測（`terry` の 1 行へ `2026.09.01.00` を入れて上記 1〜4 を実行）:**

- `TestGolden_*` 17 本 **緑**（moves 波の生成物が不変であるため）

## 4. §2.3-3 NULL の扱いと、その向き

**★★向きは安全側である**（`FR307` と同じ向き）。

| 状態 | 判定 | 理由 |
|---|---|---|
| `combos.baseline_version` が NULL | **影響可能性あり** | **「いつの前提か分からない」＝不明 ⇒ 出す。出し漏らさない** |
| `moves.last_changed_game_version` が NULL | 影響なし | **★これは「不明」ではない。**`D-725` により「初回公開より前は存在しない」＝「まだ一度も変わっていない」という**既知**の状態 |
| `combo_steps.move_id` が NULL | 判定に入らない | 非技ステップ（`DES-003` §3.5 の taxonomy）。`JOIN moves ON m.id = cs.move_id` で構造的に落ちる |
| マーカー ＝ 基準（同値） | 影響なし | 基準より**新しい**ものだけを出す |

**★★この 2 つの NULL を混同しないことが要である。** 混同すると、出し漏らすか（基準 NULL を影響なしに
倒す）、全件が出続けるか（マーカー NULL を影響ありに倒す）のどちらかになる。

**判定は保存していない**（`affectedByGameUpdateCondSQL` の相関 `EXISTS`）。影響コンボを持つテーブルは無い。
**★判定式は 1 か所しかなく、SELECT の派生列と一覧の絞り込みが同じ式を共有する**
—— 書き写すと「表示される値」と「絞り込まれる集合」が静かにずれる。

### 7.3 `position` は列として残した（§2.4.4-4 の判断）

**残す。** 理由 3 つ:
1. `position` は `DuplicateKey` 7 項の 1 つであり、**6 か所の SQL 述語**が直接比較している。導出にすると重複判定のたびに `CASE` の計算が要る
2. `idx_combos_situation_filter(position, opponent_stance, hit_type)` に含まれる
3. **「既存値を書き換えない」（§4-8）を、列を残すことで構造的に満たせる**

**整合の規則（`normalizePositionAndMass`。★重複判定より前に呼ぶ）:**

| 入力 | 振る舞い |
|---|---|
| マス数あり | **マス数が勝つ。**区分を導出して上書き |
| マス数なし・区分あり | 区分の**代表値**をマス数へ入れる（**★既存エディタはこの経路 ⇒ 現行画面は無改修で動く**） |
| どちらも無し | 両方 NULL（不問） |

**★★重複判定より前に呼ぶ必要がある** —— 判定は `input.Position` を直接読む箇所が 3 つあり、
正規化前に走ると「マス数から導いた区分」ではなく「送られてきた区分」で重複を見てしまう。

### 7.4 §2.4.6-2 **「画面中央」の意味が狭くなることを受容する**

区分が 5 → 7 になり、旧「画面中央」の一部は新区分（`mid_self` / `mid_opponent`）に当たる。
**どれがそうかを判別する記録は無い。⇒ 直せない。受容する。**
既存の「画面中央」のコンボは一律 `80` になり、利用者が後から実測値へ直せる。

### 7.5 §2.4.6-3 重複判定

**`DuplicateKey` は引き続き区分（`position`）を使う。マス数は重複キーに入れていない。**
**★既存コンボの重複判定が変わっていないことを実際に確かめた** ——
`000105` のマイグレテストが移行前後の `position` の分布（8 種）を突合し、
**行数も種類も 1 つも変わっていない**ことを見ている。`position` の値が動いていない以上、
既存ペアの判定結果は変わりえない。
