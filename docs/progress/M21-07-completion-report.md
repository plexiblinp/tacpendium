## 1. 何をしたか

**「モーダルが開いている間」という軸を、合流層に 1 本だけ置いた。**

供給元（Gamepad の rAF ／ キーボードの `KeyboardEvent`）ごとには置いていない。置くと、次の供給元を足したサブで同じ穴がもう一度開くためである（`M21-05` が 2 つ目の供給元を、`M21-06` がモードを足した時点で既に 2 度この形を通っている）。

## 2. 軸をどこへ置いたか、なぜそこか（指示書 §7.5-1・§4.1-4）

### 2.1 置いた場所

**`web/src/features/physical-input/PhysicalInputProvider.tsx`（合流層）。** 軸の実体は `isAnyModalOpen()` の 1 本で、**合流層の 2 つの入口**が同じものを読む。

| 入口 | 何が通るか | 置いた処置 |
|---|---|---|
| `handleSources()` | **押下集合**（Gamepad・キーボードの両方が合流したあと） | 観測を済ませてから作用の手前で早期 return |
| `dispatchAction()` | **操作**（削除・保存・修飾トグル・モードの出入り） | 冒頭で return |

**★入口が 2 つあるのは、操作が押下集合を通らないためである。** `DES-005` §6.5 が「操作用のキーが押下集合へ混ざらない」ことを要件にしているため、キーボードの操作キーは `handleSources` を経ず `onAction` → `dispatchAction` へ直行する。**軸そのものは 1 本であり、供給元ごとの分岐は 1 つも無い。**

### 2.2 なぜそこか（候補の比較）

| 候補 | 採否 | 理由 |
|---|---|---|
| **合流層（採用）** | ○ | 押下集合・操作のいずれも、供給元を問わずここで 1 本になる。モードの方向列もここに溜まる |
| **受け手側**（`usePhysicalRecipeInput` の `handleCandidate` / `handleAction`） | × | **実査の結果、成立しない。** コマンド技入力モードの方向列は provider（合流層）に溜まるため、受け手で配送を弾いても**モーダルの裏で列が伸び続ける**——指示書 §4.4-1 を満たせない |
| **供給元ごと**（rAF ループ ／ `KeyboardEvent` ハンドラ） | × | 指示書 §4.1-1 が明示的に禁じている |

**⇒ 候補は 2 つあったが、実査の結果 1 か所しか成立しなかった**（§4.1-4 の但し書きに当たる）。

### 2.3 ★`isAnyModalOpen()` を ref へ写していない理由

前置き（`shortcutActiveRef`）・モード（`commandModeActiveRef`）は state を ref へ写しているが、本サブは**写していない**。写すと、写す効果が走るまでの間だけ古い値を読む隙ができ、**モーダルが開いた直後に来た 1 サンプルが裏へ抜ける**。ストアはモジュールレベルの計数であり、読み取りは ref と同じだけ安い。

## 3. モーダルであることを何で判定したか（指示書 §7.5-2・§4.5-3）

### 3.1 判定の手段

**Content がマウントされている間だけ申告する登録ストア**（`web/src/lib/modal-presence.ts`・新規）。**DOM のセレクタ・属性値を 1 つも見ていない。**

共有プリミティブ 3 つ（`DialogContent` / `AlertDialogContent` / `SheetContent`）へ目印を置いた。**これらを通るモーダルは、足した人が何もしなくても対象になる**（`modal={false}` の使用は 0 件）。

#### ★★初版の断定は誤りであり、レビューで是正した（**高-1 / 高-2**）

初版の本節は「**アプリ内のモーダル 22 ファイルは例外なく共有プリミティブ 3 つを通っていた**」と書いていた。**これは事実と異なる。**

- **22 という数は「`components/ui/{dialog,alert-dialog,sheet}` を import しているファイル」の数**である（`grep -rln`）。**⇒ 母集合が「共有プリミティブを使うファイル」であり、「アプリ内のモーダル」ではない。** **問いに答えていない数を根拠にしていた。**
- **`import` を grep する形の実査は、自作のオーバーレイを構造的に見つけられない。** 探すなら `aria-modal` ／ `createPortal` ／ `fixed inset-0` のような**見た目の側**からも当たる必要がある。
- **実際に反例が 2 件あった**（下表）。**うち 1 件は入力面と同じツリーに居り、`D-383` の欠陥がそのまま残っていた。**

| # | 場所 | 形 | 影響 |
|---|---|---|---|
| a | `ComboEditor.tsx`「保存完了 — 警告があります」 | `role="dialog" aria-modal="true"` の自作オーバーレイ | **★同ファイルに `RecipeBuilder`（入力面）が同居している。** ⇒ 表示中に技キー・技ボタンを押すと**裏のレシピにステップが入り、削除・保存も効いていた** |
| b | `QRCodeModal.tsx` | `createPortal` の自作モーダル | 設定・ウィザードでのみ使われ入力面が無いため実害は無いが、断定の反例 |

**⇒ 両方へ `<ModalPresenceMarker />` を 1 行置いて塞いだ。** あわせて **`modal-presence.ts` のコメントと本節の断定を実体に合わせた**（「共有プリミティブを通るモーダルは自動で対象。**自作の重なりは自分で申告する**」）。

#### ★取りこぼしの再発を防ぐ番人を置いた

`modal-presence.components.test.tsx` に 「**`aria-modal` を自分で書いているファイルは、必ず `ModalPresenceMarker` を参照している**」という検査を追加した（共有プリミティブ本体は除外）。

- **破壊確認**: `ComboEditor.tsx` から目印を外すと**当該ファイル名を挙げて赤になる**ことを実測した。
- **⇒ 新しく自作モーダルを書いた人はここで落ちる。** **除外リストを安易に増やさないこと**（増やした時点で本検査は存在しないのと同じになる）。

### 3.2 「モーダルでない重なり」を拾わないことの確認

**構造的に拾わない。** トースト（sonner）・ツールチップ・ポップオーバー・選択メニュー・ドロップダウンは**いずれも別のプリミティブであり、登録経路を通らない。** 「拾わないよう気をつけている」のではなく、**拾う経路が存在しない。**

> **★本項（抑止しすぎない側）と §3.1（取りこぼさない側）は、保証の強さが違う。** 前者は構造的に 0 だが、**後者は「申告に参加していること」が要る**。**両者を同じ強さで書いたことが初版の誤りだった。**

機械での確認は `web/src/lib/modal-presence.components.test.tsx`（7 件）——Dialog / AlertDialog / Sheet が数えられること 3 件と、**Popover / Tooltip / DropdownMenu が数えられないこと 3 件を同じ数だけ置いてある**（対照実験。「数えられること」だけを見ると、全部を数えていても緑になる）。

### 3.3 ★DOM 監視方式を採らなかった理由（開発者確認のうえ決定）

1. **`D-380` に真っ向から当たる。** 「守りたい不変条件が成り立つときに観測される形」を実装の契約にしてしまい、UI ライブラリの更新で失効する。
2. **誤検出の危険が非対称。** Radix の Popover は版によって Content に `role="dialog"` を出す。**モーダルでない重なりを拾う側へ倒れやすく、症状は「たまに入力が効かない」であって利用者が言語化できない**（チェックリスト §9-5）。
3. **着手時点で実査できなかった。** `node_modules` が未インストールであり、指示書 §9.1-2「実査せずにセレクタを決めない」／停止条件 3 に触れる。登録方式ならこの実査自体が不要になる。
4. **破壊確認を決定的に書ける。** MutationObserver は属性反映のタイミングに依存し、テストが実装の内部タイミングに縛られる。

### 3.4 ★実装中に検出した罠（同型を次に踏ませないために記録する）

**最初は共有プリミティブのラッパ本体（`DialogContent` の関数の中）でフックを呼んだ。これは誤りである。**

`DialogContent` は**自身が Portal を描画している**ため、**ダイアログが閉じていてもマウントされたままである**（開閉で入れ替わるのはその内側）。⇒ **画面に置いてあるだけのダイアログが常に「開いている」ことになり、物理入力が恒久的に効かなくなる。**

- **検出したのは「閉じれば戻る」という 1 件のテストである。** 「開いていれば数えられる」だけを見ていた 3 件は**全部緑のまま通った**。
- ⇒ **描画を持たない目印コンポーネント `ModalPresenceMarker` を Content の内側（＝開閉で入れ替わる側）へ置く形に改めた。** フックではなくコンポーネントにしたのは、**置き場所を間違えにくくするため**である——Content の子として書くしかなく、その位置は必ず開閉に追従する。

## 4. §4.6 の判断: 既存の名指しの抑止を畳むか → **畳まない**（指示書 §7.5-3）

### 4.1 実査した現行の抑止条件（§3.3-1）

followup の記録は「2 つ」。**実査でも 2 つで一致した**（`M21-06` の as-built で動いていない）。

| # | 条件 | 場所 | 効く範囲 |
|---|---|---|---|
| a | `enabled = surfaceIds.length > 0`（入力面がマウントされているか） | `PhysicalInputProvider.tsx` | rAF ポーリング **と** キーボード購読の両方 |
| b | `keyboardCapturing`（キー登録ダイアログを開いているか） | 同（`enabled && !keyboardCapturing`） | **キーボード購読のみ**。面ごとの id 集合方式 |

（別軸として `DES-005` §6.5.1 (1) の `isEditableElementFocused()` があるが、**これは本サブが足すものと別の軸であり触っていない**＝指示書 §2.2-5。）

### 4.2 判断と理由

**b（キー登録ダイアログの名指し）を畳まない。** 単純な包含関係ではない（§4.6-3 のとおり）。

1. **b は「購読そのもの」を止める＝観測も止める。** 本サブの軸は**観測を止めない**（§4.2）ため、b を置き換えると登録ダイアログでキーを押すたびに押下集合が動く。
2. **キー登録ダイアログは「押されたキーを捕まえる」という固有の要求を持つ。** 購読が生きていると、こちらの listener が登録対象のキーに `preventDefault()` を掛ける。一般の軸（作用だけ止める）ではこの要求を満たせない。
3. **一般の軸に飲ませると停止条件 4**（キー登録ダイアログが機能しなくなる）**に直行する。**

**⇒ 重複ではなく別要求である**（`E-76` の「同じ情報が 2 か所」には当たらない）。両方を残したうえで、役割の違いをコードのコメントに明記した。**「決めずに両方残す」ことは避けている**（§4.6-4）。

### 4.3 ★実査で分かった副次的な事実

**`GamepadCalibrationDialog` は `setCapturing` を呼んでいない。** ⇒ b は Gamepad 側に対応物を持たず、**キャリブレーション中もパッド入力は裏へ流れていた**。本サブの一般の軸がこれも塞ぐ。**これは `D-383` の非対称（Gamepad には DOM フォーカス由来の守りが構造的に掛からない）が、報告された編集ダイアログ以外にも出ていた実例である。**

## 5. §4.4-2 の判断: モードから強制的に出すか → **出さない**（指示書 §7.5-4）

**理由**——「入る条件」と「出る条件」は別物であり、可用性の条件を出口へ掛けると**利用者が意図せずモードを失う**（playbook §4.4.1。`E-131`〔閉じ込め〕の逆の失敗）。モーダルは一時的な状態であり、閉じれば元の作業へ戻るのが自然である。

- **モーダルの裏で方向列が溜まらないこと**（§4.4-1）は合流層の抑止分岐が担う。
- **モードの出入りそのものも起きないこと**（§4.4-4）は `dispatchAction` の同じ軸が担う。
- 契約テストで「閉じたあともモードが続いている」ことを固定した。

### 5.1 ★前置き（ショートカット）からは抜ける — モードとの扱いの違い

モーダルが開いた瞬間に `leaveShortcut()` を呼んでいる。**これは §4.4-2 が言う「モードを意図せず失う」には当たらない**——**前置きはもともと 2 秒で自動解除される保留状態である**（`DES-005` §6.5 項目 7 の「時間経過」）。放置すると `followUpDownRef` が古いまま残り、**閉じた直後の後続ボタンが誤って操作として成立しうる。**

### 6.1 ★赤にならなかった項目と、代わりに守っていたもの（`SUPP-001` §5.5 (10′)）

**破壊 B3（観測まで止める素朴な形）を当てたところ、初版の 20 件は全部緑のまま通った。** 「テストが弱い」で済ませず、**何が代わりに守っていたか**を特定した。

- **代わりに守っていたのは判定層の性質である。** 判定層は**立ち上がり**で窓を開く（`stepDetection.ts`）。⇒ 抑止中に押下そのものを見落とせば、その解放も何も起こさない。
- **⇒ 「押されたまま」の害は、ステップが増える方向ではなく、ステップが増えなくなる方向に出る。** 初版の 2 件（開く→押す→閉じる→離す）は**害の出ない側だけを見ていた。**
- **実際に壊れる筋道**——**モーダルが開く前から押していたボタンを、開いている間に離す。** 観測を止めていると判定層は「まだ押されている」と思い込んだままになり、**閉じたあとに押し直しても立ち上がりに見えず、その入力が黙って消える。**
- **⇒ 同じ層（合流層の抑止分岐）に対する契約テストを 3 件足した**（キーボード 1 件 ＋ 供給元の表を通した 2 件）。**足したあとに B3 を当て直すと 3 件が赤になる。**

### 6.2 ★B2 で赤にならなかった 1 件が示した、処置の分担

「開く前から押しっぱなしのボタンも、閉じたあと離すだけではステップにならない」は **B2 では緑のまま**で、**B4（遷移処理を落とす）で赤になった**。⇒ **開いた瞬間に判定窓を閉じる処置は、毎サンプルの抑止分岐とは別の仕事をしている**（サンプルは入力が変化したときにしか来ないため、マウスでモーダルを開いただけでは 1 サンプルも来ない）。**どちらか一方では足りない。**

### 6.3 E2E の破壊確認（**D-375**）

軸を丸ごと外して欠陥を復元した状態で `m21-07-modal-input-suppression.spec.ts` を実行した。

```
A: ダイアログを開いている間、技キーを押してもステップが増えない   ✘ 失敗（retry も失敗）
B: 対照 — ダイアログを開かずに押すとステップが増える              ✓ 成功のまま
C: 押しっぱなしのまま閉じて離す                                   ✘ 失敗（retry も失敗）
★ダイアログを開いている間は操作キー（削除）も効かない            ✘ 失敗（retry も失敗）
  → 3 failed / 1 passed
軸を戻すと 4 passed
```

**★A と C が赤に、B（対照）が緑のまま**という非対称が出ている。**両方赤なら「入力そのものが飛んでいない」空振り**であり、そちらではないことを確かめた。
