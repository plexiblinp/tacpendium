## 3. 推論（測定値ではない）

1. **新条件が上回ったのは、索引経由の取得が「読む対象を選ぶ」作業を強制するためと考えられる。** ツール呼出が +22.9% であるのに対しトークンは +1.9% にとどまる＝**1 回あたりの読取が小さく、狙って読んでいる**。旧条件の「まず全部読む」は、大きな塊を読んで細部に届かない読み方になりやすい。
2. **① の変更にトークン削減効果は無い。** 2 タスクとも新条件のほうが同等〜やや多い。パイロット §3 の解釈（旧条件は指示に従っていなかった／従えなかった）と整合する。**効果は「読む量」ではなく「読み方」に出ている。**
3. **正解「高」3 件のうち GT-3 は、5 本すべてが「低」に置いた。** 原レビューが「高」に置いた理由（撤回済み記述はテストで検出できない＝本プロジェクトが最も嫌う型）は**プロジェクト固有の価値観**であり、汎用のレビュー基準からは出てこない。優先度較正はコンテキスト量ではなく**規約の明示度**の問題である。
4. **裁定書の不在（6/6 検出・5 本が「高」）は、原レビューが進まなかった一段の推論に届いている。** 原レビューは「現物を参照していない」と制約事項に書くに留めたが、6 本は「参照できない＝完了条件の検証不能」まで進めた。**ただし §1.4.1 のとおり、これは修正すべき欠陥ではなかった**（Plan Mode 資材はコミット対象外）。→ **「原レビューより深く読む」ことと「有用な指摘を出す」ことは別である。** 到達できない資料を欠陥として報告する挙動は、**repo 外に正本がある運用と噛み合っていない**。
5. **収束した 3 件のうち 2 件（裁定書・13 行）は同一原因の下流である**——決着文（D-260 §1.2）が Plan Mode 資材にしかなく repo から到達できない。**6/6・4/6 という一致率は「2 つの独立した発見」ではなく「1 つの構造の 2 つの現れ」と読むべきで、Retention の証拠としては額面より弱い。**

## 5. 未決事項・本評価の限界

1. **n=3 での優劣は確定的に扱えない。** 5/9 対 8/9 は方向としては明確だが、trial 間のばらつき（旧 1〜2・新 2〜3）を考えると**「新条件が劣っていない」までが確実に言えることで、「新条件が優れている」は暫定**である。
2. **`CLAUDE.md` の自動ロードは HEAD 固定**（パイロット §5-1 と同じ）。旧条件は削除節を足し戻す形で `OLD ⊇ NEW`。**回帰を検出しにくい向きの保守的バイアス**であり、それでも新条件が上回った点は結論を強める方向に働く。
3. **Restraint 未測定**（E-5）。誤検出が増えていないことの証明にはなっていない。
4. **正解集合外の「高」指摘（旧 7・新 6）のうち、収束した 3 件のみ §1.4.1 で裏取りした。単発のものは未判定である。** 3 件の結果は「観測は正しいが欠陥ではない」（裁定書）・「裁定済み」（13 行）・「レビュー時点では真・その後解消」（followup 未登録）で、**いずれも「原レビューが見落とした標準的な欠陥」ではなかった**。→ **拡大ラウンドの Retention 実績は、パイロット（`progress-log.md` 未追記＝実際に 2 サブで再発した実害）ほど強くない。**
5. **`web/CLAUDE.md` の補償は結局テストできていない。** `web/src/locales/*.json` は HEAD と差分があり `git show` 経由になったため、`web/` 配下の Read が発生せず on-demand ロードが発火しない。**発火したのは `internal/model/move.go` 経由の enum-sync rule のみ**（それも Read を選んだ trial に限る）。
6. **①（読込構成）と ②（`CLAUDE.md` 縮小）を束ねたまま。** 回帰が出ていないため切り分けは不要だったが、**新条件の優位がどちらに由来するかは分からない**。
7. **汚染リスク**（パイロット §5-5 と同じ）。正解ファイルと `f6fee98` 以降のログは禁止したが、HEAD の `followup-backlog.md` 等には M19-05 由来の項目が登録済みで、**広く読む旧条件のほうが汚染を受けやすい**（旧条件に有利なバイアス）。
