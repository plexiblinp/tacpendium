4. **値域外クエリの正規化が他軸と揃っていない**（→ 中-1）。`useComboListFilters.ts:197` の `parseIntOrNull` は `0` と負値をそのまま通す。⇒ `?starter_move_id=0` で
   - `activeFilterKeys` が「効いているフィルタ」に数える（`filters[key] !== null`）、
   - 要約ピルに「始動技: 始動技#0」が出る、
   - コントロールの表示は「全て」（`selected={... ?? 0}` が 0 の選択肢に一致する）、

   という 4 つの不整合が同時に起きる。他軸は `parseSetupResultOrNull` / `parseOkiTechTypeOrNull` / `isValidSortField` が値域外を `null` へ落とす既存の流儀を持っており、**新軸だけがその外に居る**。あわせて `?starter_move_id=1.5` は FE が `1` へ丸め、BE は 400 という**強度の食い違い**もある（`parseInt` と `ParseInt` の差）。

5. **要約ピルの技名解決だけ `code` へ落ちない**（→ 中-2）。`ComboListFilters.tsx`

   `Move.nameJa` は `string | null` であり、`formatStarterStatus` のコメント自身が「**ラッシュ版は alias を持たないため実際に起こりうる**」と明記している。⇒ その技を選ぶと**トリガには技コード、ピルには `始動技#42`** と同一画面で別表記になる。ピルのコメントは「隠さず id を出す（`formatStarterStatus` と同じ既存規約）」と書いているが、`formatStarterStatus` の規約は **段2＝code → 段3＝#id** であり、ここでは段 2 が抜けている。

6. **エラーコードの流儀**（→ 中-3）。`DES-002` §4.2 の `GET /api/combos` 行と followup `combos-query-error-code-split` が「**パース失敗＝`invalid_query` ／ 値不正＝`invalid_query_param`**」と明記している。本サブは `err != nil || id <= 0` を 1 本にまとめ、**パース失敗も `invalid_query_param`** にした。最も近い先例である `character_id`（同じく整数 id のパース）は `invalid_query` である。加えて `character_id` / `tag_ids` は `0` や負値を弾かないのに `starter_move_id` だけが弾く——**強度の非対称そのものは妥当な改善だが、既知 followup に触れずに新しい判断を入れている**（followup が「次に同 API へクエリを足す人がまた同じ判断を 1 から迫られる」と予告していた事象がそのまま起きた）。
