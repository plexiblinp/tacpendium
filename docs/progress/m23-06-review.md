## 総評

**本サブの中心——「同じ根に逆の答えを出す」判断——は、実装・テスト・コメントの三方で正しく実現されている。** ルート列は空表示ではなく列ごと撤去され、セットプレイのレシピはサーバ側(`ResolveDeletedSetupRecipes`)で `setup_steps` から解決され、`ResolveSetupRecipe` は撤去されずに温存されている。最重要ゲートである一括操作の種別振り分けは、選択状態を 2 本の配列へ分ける案 (b) により**構造的に**取り違えが起きない形になっており、破壊確認 1 で fixture の id 衝突という空振りを自力で発見して作り替えた点は、この工程で最も価値のある仕事だった。

一方で、**本サブが新規に作った「一括復元の警告の内訳」(§4.6-3 / §5.1-10)は、実アプリでは 1 フレームも表示されない。** `onComplete()` が選択を空にした瞬間に `TrashBulkActions` が `return null` するためであり、テストは `onComplete` が no-op のため緑になっている。followup `bulk-restore-warning-detail-unreachable` は「導線が無い」ことを指した項目であり、**導線を足したが依然として到達不能**という状態で閉じられようとしている。これが本レビュー唯一の「重大」である。

加えて、**失効した記述が 2 系統残っている**——`formatBulkRestoreSummary` の godoc が「どの件に警告が付いたかは本サブでやらない」と書いたまま直下でそれを実装しており、Go 側 6 か所が「M23-06 が導線を作るときの材料」と書いているが導線は `M23-07` へ移っている(§1.6-1〜3)。また **`docs/progress/progress-log.md` への索引行が 1 行も無い**(DoD §7.4 / `CLAUDE.md` §8)。

サーバ側は契約を 1 バイトも動かさずに読み取りだけで解いており、`DoesNotWriteBackRecipeCache` で「読み取りが書き戻さない」不変まで固定してある点は特筆に値する。

## 設計準拠性以外の指摘事項

### A. 実行時に到達しない表示(重大)

**`web/src/features/combo/components/TrashBulkActions.tsx:167`**

```ts
if (totalCount === 0) return null;
```

`handleBulkRestore` は末尾で `onComplete()` を呼び、`TrashPage.handleComplete` が `setSelectedComboIds([])` / `setSelectedSetupIds([])` を実行する。⇒ 同じイベントハンドラ内で `selectedCombos` / `selectedSetups` が空になり、`totalCount === 0` で **コンポーネントごと `null` になる**。直前に `setWarnedItems(warned)` / `setErrors(...)` で立てた状態を描画する JSX(191〜207 行)は、**利用者の目に入る前に消える**。

- **§5.1-10 のテストが緑なのは、`renderBulkActions` の `onComplete` が `vi.fn()`(何もしない)だからである**——テストの中では選択が空にならないので `null` にならない。実アプリの親と挙動が違う。
- **同じ理由で「N 件失敗」の `role="alert"`(191-195 行)も表示されない。** こちらは `M23-02` 期からの既存不具合であり本サブが持ち込んだものではないが、**本サブが同じ描画経路の上に新しい要求(§4.6-3)を載せたため、既存の穴がそのまま新機能の穴になった。**
- followup `bulk-restore-warning-detail-unreachable` は「出す導線が無い」項目である。**導線を足しても到達しないままでは、この項目は閉じていない。**

### C. サーバ側の堅牢性

3. **`internal/service/setup/restore.go:293-298`** — `ResolveDeletedSetupRecipes` のエラーをそのまま返すため、**1 件のレシピ解決失敗でゴミ箱のセットプレイ一覧全体が 500 になる。** 従来の `extractDefaultRecipe` は純関数で失敗しなかった。`resolveMoveStep` は別名が無ければ `moves.code` へ、それも無ければ `move:<id>` へ段階的に落ちる作りだが、**`presetRepo.FindPresetByID`(`resolver.go:89`)は行が無ければエラーを返す**——既定プリセットが失われた環境では、**ゴミ箱を開けず復元も完全削除もできなくなる。** 本サブの動機(「識別手段がゼロだと取り違える」)に照らすと、一覧全体が落ちるのは最悪の縮退である。
