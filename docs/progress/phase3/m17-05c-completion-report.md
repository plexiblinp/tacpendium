## 1. Plan Mode 着手前確認（指示書 §3.3 の 7 項目）

1. **現行生成経路の実査**: PDF は pdf-lib のネイティブテキスト描画では**ない**。実体は `ComboExportDocument`(DOM) → html-to-image `toCanvas`(pixelRatio 2) → 1 枚の PNG → `pngToPdf` が画像同寸 1 ページに埋め込み。PNG も同じ 1 枚から生成。→ 指示書の「pdf-lib で自然に分割可能」という前提は成立せず、**DOM を意味単位で測り、ページごとに部分 DOM を再描画して複数回キャプチャ → 各 PNG を各 PDF ページに埋め込む**方式を採用（ネイティブテキスト化は JP フォント埋込問題が再燃するため不採用）。
2. **分割規則（実測に基づく提案・下記 §2）**: 実測のうえ「単独=カード境界の行分割/比較=列→行分割・見出し再掲」を確定。
3. **PNG の canvas 上限（実測・下記 §3）**: 実測のうえ「事前警告＋PDF 推奨・ハード例外をバックストップ」を確定。
4. **28 項目の反映**: 全項目選択で 28 行（メディア 3 項目含む・CHANGE-068）を単体テストで固定。メディアは文字列のみ（実体埋込なし）。
5. **オプション UI の要否**: 不要（分割は既定挙動）。オプションは追加していない（M17-05b ダイアログ不変）。
6. **fonts.ready（M13-j・任意）**: **未実施**（followup §151 に残置）。本サブの必須要件ではないため見送り。
7. **i18n**: UI 文言（警告トースト・PNG 上限 hint）は ja/en 両ロケール。**エクスポート文書内のラベル・見出し・ページ番号は固定 ja**（i18n キーを足していない＝M16-06 境界）。

## 2. 分割規則の最終形と実測値

**実測環境**: Chromium（Playwright 同梱）で `ComboExportDocument` の inline スタイルを忠実再現し、全 28 項目・現実的な最悪ケース内容で実測（2026-07-18）。html-to-image は DOM をそのまま canvas 化するため、描画高さ＝canvas 高さ（×pixelRatio）となり本実測が PDF/PNG 寸法を代表する。

| 出力 | 実測（CSS px） | canvas（×2） | 何で溢れるか |
|------|----------------|--------------|--------------|
| 単独（1 件・全 28 項目） | 720 × **1121** | 1440 × 2242 | 高さが A4 縦 usable(~1075px) を僅かに超過 → 2 ページに行分割 |
| 比較表（幅） | 幅 = 160 + 件数×360 | — | — |
| 比較表（高さ・件数不変） | ~**1159** | ~2318 | 28 項目で A4 縦を超過 → 行分割 |

**確定した分割規則**:
- **単独**: カード（行）境界で切る（行を跨がない）。継続ページにタイトル（見出し）を再掲し「（続き）」を付す。ページ番号 `N / M`。
- **比較表**: 列 → 行の順で分割。1 ページあたり **4 列（コンボ）**（`PDF_COLUMNS_PER_PAGE=4`。実測 n=4 で幅 1600px/canvas 3200px＝可読・上限内）。各ページに**項目名列（見出し列）＋コンボ名 thead を再掲**。行が溢れれば行分割し、継続ページにも thead を再掲。ページ番号＋範囲ラベル（例「コンボ 1–4 / 全 12」）。
- **行分割の基準高**: `PDF_PAGE_CONTENT_HEIGHT_CSS=1122`（A4 縦@96dpi）。プランナが padding・ヘッダ・フッタの実測分を差し引いて行予算を算出。
- **切る順序＝列→行**（判断根拠）: 比較は「同じコンボ群を縦に読む」行為のため、列を跨いで項目を追うより読みやすい（§9.2）。

## 3. PNG の canvas 上限（16384px）実測と採用した対処

- **何件で当たるか（実測）**: 比較表は幅がコンボ数で伸びる。**n=23 で canvas 幅 16880px > 16384px** となり `capture` がスロー（n=22 は 16160px で可）。**単独（1 件）は 720×~1121px で上限に届かない**。高さ側は 28 項目固定のため何件でも上限に届かない（律速は幅）。
- **現状の振る舞い（実測）**: 従来から `capture.ts` が上限超過時に**ハード例外**を投げる（＝静かに壊れない。切れる/空になるではない）。
- **採用した対処（開発者承認）**: **PNG は 1 枚のまま**（分割しない）。
  1. `EXPORT_IMAGE_WARN_COUNT=22`（実測 23 件破綻の直前）で、**PNG 選択時のみ**実行前に警告トーストを出し PDF（自動ページ分割）を推奨（`run-export.ts` の `needsImageWarn` を PNG 限定に変更＝PDF は分割で失敗しないため）。
  2. `ExportDialog` に PNG 選択時の**静的な上限注意書き**（`pngLimitHint`・「およそ 22 件超」＝実測値ベース）を追加し PDF を促す。
  3. 上限に実際に達した場合は既存のハード例外がバックストップ（静かに情報が欠けることはない）。

## 7. 持ち越し（レビュー軽微・低優先度）

- PDF 分割時の `renderHidden→capture` 直列実行（多ページで所要増）。正確性・メモリ安全（並列の隠しレンダはメモリ急増リスク）を優先し直列を採用。実測: E2E の 5 件 PDF 出力は数秒内。将来、件数が非常に多い場合の並列化は followup 候補。
- 比較表で各ページごとに全コンボ分 `buildComboFields` を再構築（メモ化余地・低）。
- `measure.ts` の直接単体テストは jsdom がレイアウトを計算しないため見送り（プランナは純関数として網羅・実挙動は E2E でカバー）。
- n≥23 の PNG で警告トースト＋失敗トーストの二重通知（低）。いずれも情報提供として妥当なため据え置き。
- **fonts.ready（M13-j・followup §151）未実施**（任意・followup に残置）。
