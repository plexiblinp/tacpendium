## 設計準拠性レビュー結果

### §1 出力内容の不変 — ◎
- 28 項目不変を `ComboExportDocument.test.tsx`「全項目選択の単独出力は 28 行」で明示検証（`tr[data-row]` が 28）。`buildComboFields` はメディア 3 項目（link/videoPath/imagePath）を含み、CHANGE-068（25→28）を反映済み。メディアは文字列のみ（実体埋込なし）。
- 分割は `selectRows`（行フィルタ）と列 slice のみで、値整形ロジック（`export-model.ts`）は無改変。**内容を削って収める実装ではない**（1 行が予算超なら単独ページに置く＝§9.3 準拠、`packRows`）。
- `page` 未指定時は全件 1 枚・フッタなしで従来出力と一致（テストで page-footer が null を確認）。既定挙動は不変。

### §2 PDF の分割規則 — ◎
- 単独: `packRows` がカード（行）境界で切り、行を跨がない。継続ページはタイトルを再掲し「（続き）」を付す（`SingleLayout`・テスト済み）。
- 比較表: 列 slice `[columnStart, columnEnd)` で列方向分割。各ページに項目名列（tbody の `<th scope="row">`）と thead（コンボ名）を再掲。**再掲欠落なし**（`headerCells` = 5 を検証）。値は元の列インデックス `colStart + j` から引くため、2 列目以降のページでもオフセットが正しい（`5555` のみ・`1111` 不出のテストで担保）。
- 切る順序＝列→行（列グループ外側・行内側）。理由（比較は同一コンボ群を縦読み）をコード §9.2 として明記。
- ページ番号 `N / M` と範囲ラベル「コンボ 1–4 / 全 6」を `PageFooter` で出力。テストで確認。
- 境界値テスト: 1 件／ちょうど 1 ページ（合計＝予算）／1 件超過／1 行が予算超、比較の N≤列/ページ を網羅。

### §3 PNG の上限対処（静かに壊れない） — ◎
- PNG は 1 枚のまま。`exportComboImage` の png 経路は全件ノードを 1 回 capture（テストで capture 1 回を検証）。**分割していない**。
- canvas 16384px 到達時は `capture.ts` の `defaultRaster` がハード例外（切れ・空を黙認しない）。実測（Chromium・比較表 n=23 で幅 16880px 超過、n=22 は 16160px で可）をコメントに記録。
- 事前警告 `EXPORT_IMAGE_WARN_COUNT=22` を PNG 選択かつ件数 > 22 で発火（`run-export.ts` の `needsImageWarn`）。PDF は自動分割のため警告対象外（テストで png のみ発火・pdf/clipboard 非発火を確認）。
- UI 注意書き `pngLimitHint`（「およそ 22 件超」＋ PDF 推奨）を PNG 選択時に表示。E2E で「22」「PDF」を含むことを検証。

## 設計準拠性以外の指摘事項

1. **【性能・中】PDF 分割時のレンダリング直列実行**: `buildPdfPageRasters` は全件ノードで 1 回計測後、各ページを個別に `renderHidden`（2×requestAnimationFrame 待機＋React マウント）→ `capture` を**直列**で回す。ページ数×（2フレーム＋マウント＋ラスタライズ）分の待ち時間になる。多数コンボ（例 28 項目×多列で列→行 2 段）ではページ数が増え体感遅延が出うる。機能上は正しいが、完了報告に所要時間の実測があると良い。
2. **【性能・低】比較表で全コンボ分の `buildComboFields` を毎ページ再構築**: `ComparisonLayout` は可視列に関わらず `combos.map(buildComboFields)` を実行（値引きに元インデックスが要るため意図的だが、ページごとに全 N 件を再計算する）。N が大きいと無駄が積む。メモ化余地あり（将来対応で可）。
3. **【UX・低】警告と失敗の二重トースト**: n≥23 の PNG は事前警告トースト（「失敗する場合があります・PDF 推奨」）が出た後、実際に `capture` がハード例外→ `allFailed`/`partialFailure` トーストも出る。情報としては正しいが二重通知になる。警告は実行を止めない設計（開発者暫定案「警告して促す」に沿う）なので許容範囲だが、報告に明記しておくと良い。
4. **【テスト・低】`measure.ts` 未テスト**: `headerHeight = firstRow.top - rootRect.top - PDF_ROOT_PADDING_CSS` は非自明なロジックだが単体テストがない。jsdom は geometry を返さないため getBoundingClientRect のモックが要る。テスト方針（§5.5）上「必須」ではない（純関数でなく DOM 依存）が、回帰検知の観点で薄い。
5. **【テスト・低】比較表 行継続ページの thead 再掲の直接検証なし**: `ComboExportDocument.test.tsx` の比較ページテストは `rowContinuation:false` のみ。構造上 thead は継続ページでも常に描画されるが、明示テストがあると安心。
6. **【整合・情報】警告閾値の境界表現**: 実失敗は 23 件以上（n=22 は 16160px で成功）。警告文「およそ 22 件超」＝ >22＝23 件以上で、`run-export` の `length > imageWarnCount(22)` と一致し失敗点と警告点が揃っている。矛盾はない（記録として明記）。
7. **【スコープ・情報】既存 05b 文言 `imageWarnCount` の改稿**: 「対象を絞る」→「PDF を推奨」に変更。PDF がページ分割対応した以上の妥当な追随であり、指示書 §4.5/§7.1 の「注意書き」要件に沿う。M17-05b 動線への実質的な機能変更ではないと判断（記録として明記）。
- コーディング規約（§4）: 定数 SCREAMING_SNAKE_CASE、純関数分離、JSON/型は camelCase、マジックナンバー定数化（`PDF_*`）を遵守。console.log 等の残置・簡体字・「起き攻け」誤字・裸「DR」略記は grep で未検出。
