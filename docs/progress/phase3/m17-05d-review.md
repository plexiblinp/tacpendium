## 設計準拠性以外の指摘事項

1. **`String.prototype.replace` の `$` 特殊置換パターン（低）**: `prompt.ts` L154-157 で `PROMPT_BODY.replace("{{USER_RULES}}", userRulesSection)` の第 2 引数が文字列のため、ユーザーが自由ルール欄に `$&`・`$'`・`$1` 等を入力すると特殊置換として解釈され、意図しない文字列（マッチ部分等）が混入する。実害は「稀にプロンプト末尾が化ける」程度で照合結果には影響しないが、`userRules` は完全な自由入力で最も `$` を含みやすい。`{{CHARACTER}}`/`{{MOVES}}` も同型だが混入確率は低い。根治するなら置換関数形式（`.replace("{{USER_RULES}}", () => userRulesSection)`）を推奨。

2. **UI 配置：自由ルール欄がコピーボタンより下（低〜中/UX）**: 「プロンプトをコピー」ボタン（L175）の後に (c) textarea・(a) 注記・(b) 折りたたみが並ぶ。自由ルールはコピー出力に反映されるが、ボタンより下にあるためユーザーがルール未入力のままコピーしやすい導線。チェックリスト §10 上は「配置＝軽微・スマホ幅で成立すれば可」で許容範囲だが、textarea をボタンの上に置く／ボタン近傍に「独自ルールも一緒にコピーされます」の一言を添えると導線が明確になる。文言・配置は開発者確定事項（指示書 §6-1）。

3. **保存が毎キーストローク（低/情報）**: `handleUserRulesChange` が入力ごとに `localStorage.setItem`。小容量テキストで実害なし・仕様「変更のたびに保存」に合致するため対応不要。デバウンス不要と判断。

4. **規約遵守（良）**: `console.log`/`fmt.Println` 残置なし。`any` なし。ストレージキーは `-v1` suffix・専用ヘルパ経由・try-catch（`browser-storage.ts` 側）で CLAUDE.md §10.X の実装ガイドライン準拠。定数 `INTAKE_USER_RULES_STORAGE_KEY`/`USER_RULES_HEADER` として文字列を定数化。
