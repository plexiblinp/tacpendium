### ④ `progress-log` は横断インデックス型（実態の追認）＋ 製造 CLI へ組み込み

**裁定**: 3 段階のうち 1・2 を実施し、3 は見送る。

**★根本原因（実測）**: **型を変えても追記漏れは直らない。**

```markdown

- **結果**: <1 行。テスト green ／ 消費マイグレ番号 ／ 主要な確定事項>

```

（実測: `m19-07` は `対象指示書` / `作成日`、`m19-06` は `指示書` / `実装日`）。**開発者裁定 3**
（初回リリースまでは承認・トリアージ・単発短時間の作業のみ。継続的な労働を要する改善は Phase 4 以降）に該当する。

### ⑤ 古さは優先順位ルールで扱う（機械検査は作らない）

**裁定**: 「同じ状態が 2 か所にあるときは `parallel-board` を優先し、`progress-summary` は
**マイルストーン境界時点の記録**として読む」を両者のメタ表へ 1 行ずつ置く。**機械検査は作らない。**

**★当初案（git 最終コミット時刻を唯一の判定軸にする）を取り下げた理由**:

**board と summary は更新時点の定義が違う**——board は「状態変化時」、summary は「マイルストーン完了時」。
したがって **「summary が board より古い」は正常状態**であり、git 時刻で検査すると**毎回誤警報を出す**。
誤読の対策は鮮度指標ではなく**優先順位ルール**である。

**既存の鮮度機構は据え置く**: `scripts/check-derived-docs.sh` は源泉→派生の 4 ペア
（code-facts / docs-map / retrospective-digest / custom-commands）を git 最終コミット時刻で判定しており、
**こちらは源泉と派生の関係が明確なので誤警報にならない**。board↔summary をこの機構へ足さない。

**適用先**: `docs/process/parallel-board.md` メタ表 ／ `docs/progress/progress-summary.md` メタ表。

### ⑧ `environment-reliability-plan` §4 は warn レベルで扱う

**裁定**: **warn レベルでよい**（blocking にしない）。

**★ただし調査で 2 つの問題が判明した。裁定の適用にあたって留意すること。**

**(a) §4.2 の「ファイル編集 → 再読込して確認」は現行 harness の指示と衝突する。**
Claude Code の harness は「**編集した直後のファイルを検証目的で読み直すな。Edit/Write は失敗すれば必ずエラーになるし、harness がファイル状態を追跡している**」と明示している。
ルール化すると毎回の無駄読みを強制することになる。**harness が保証しない 4 つだけが実効的**——
複数ファイル変更の manifest 突合／生成処理の再生成差分／DB 変更の件数・不変条件／テストの exit code と失敗件数。

**(b) 「AI が warn を無視しないか」という懸念は正しい。証拠がある。**
`check-enum-sync.sh` は warning だが「誤検出が多く blocking にできない」ため、
運用が「**件数がベースラインから増えたかだけ見る**」に退化している。**warn は読まれるが行動されない。**

**⇒ 実効性がある形は 2 つだけ**（単なる warn 出力は採らない）:

1. **ベースライン固定型**（`check-enum-sync` が既にこの形）— 現状値を記録し、**増えたら赤**。誤検出を許容しつつ効かせられる
