## 0. 要約

`KeyboardEvent` の経路を足し、既存の 3 つの土台〔判定層・受け手の調停・操作の配送〕へ**新しい経路を作らずに**乗せた。

**本サブの設計上の答えは 1 行で言える——判定・調停・配送は 1 組のまま、供給元だけを 2 つにした。**

```
[Gamepad] rAF        → normalizeSnapshot ─┐
                                          ├→ mergeNormalized → useStepDetection（無改造）→ ownerId 調停 → 入力面
[Keyboard] KeyboardEvent → normalizeKeyboard ─┘
                                          └→ 操作キー → dispatchAction（M21-04 の配送チャネル）
```

- **`stepDetection.ts`（判定の本体）は 1 行も変えていない。** 判定窓の値・アルゴリズム・半開区間・方向の扱いはすべて不変（`§2.2-1`）。
- **新しい調停も新しい配送チャネルも作っていない**（`§4.6-1`・`§4.6-2`）。
- **操作の種別は `M21-04` の `GamepadActionKind`（3 値）をそのまま共有**している（`§4.2-3`）。

### 3.1 ★`Space` の解禁（2026-08-14・開発者要求）

**格闘ゲームの操作として Space を使う利用者が実在するため、除外から外した。**

- **設計書の対象外である。** `CHANGE-110` §1.3 が「**除外するキーの具体的な集合**」を CHANGE 対象外と定め、指示書 `§9.2-2` が製造へ委ねている。⇒ **CHANGE 通知書は不要**。
- **★代償を承知のうえで解禁した**（**2026-08-14・開発者裁定**）。**Space を登録した利用者は、入力面が表示されている間、Space でフォーカス中のボタン・スイッチを実行できなくなる**（`useKeyboardInput` が既定動作を止めるため）。**★この代償は製造から開発者へ明示的に提示し、「良い」との判断を得ている。** **⇒ 見落とされた副作用ではない。**
  - **これは Space を自分で割り当てた利用者にだけ起きる。** 未登録なら抑止対象外であり、既存の挙動は変わらない。
  - **テキスト欄では従来どおり空白が入力できる**（`isEditableElementFocused` が先に効く）。
- **★`Enter` は解禁しない**（**2026-08-14・開発者裁定**）。**製造から「Space と同じ理屈で解禁できる」と提示したうえで、「解禁は不要」との判断を得た。**
  - **⇒ これは「判断した結果の現状維持」であって、やり残しではない。** フォーカス中のボタン実行とフォーム送信の**最後の経路**が `Enter` に残る。
  - **★次の担当は、この判断を覆さずに `Enter` を除外表から外さないこと。** 解禁自体は `ACTIVATION_KEYS` から 1 行外すだけで可能だが、**それは上記裁定を覆す変更である。**

> **★判断の一般則**——**「登録できたのに動かない」が最悪の形である。** OS 側が先に横取りするキーを登録させると利用者からは本アプリの不具合に見え、しかも**本アプリのログには何も残らない**（イベントが届かないため）。⇒ 迷った場合は除外側へ倒した。
>
> **★除外は必ず理由つきで返す。** `keyExclusionReason()` が `boolean` ではなく理由（または `null`）を返す形にしてあるのは、**無反応で弾く実装を書けないようにするため**である（`§4.3-2`）。

### 判定方法（`§4.4-2`＝要素の種類を列挙しない）

`web/src/features/keyboard/editableFocus.ts` が `document.activeElement` に対して**性質**を問う。

1. **`el.matches(":read-write")`** — CSS Selectors Level 4 の「利用者が編集できる要素」擬似クラス。
2. `el.isContentEditable === true` — 1 が使えない環境向けの保険。

**★着手時に jsdom（nwsapi）での挙動を実測した**（`:read-write` に依存してよいかの確認）。

| 対象 | `:read-write` |
|---|---|
| `input[type=text]` / `input[type=number]` / `textarea` / `contenteditable` | **true** |
| `input[readonly]` / `input[disabled]` / `input[type=checkbox]` / `button` / ただの `div` | **false** |

**★同じ実測で `isContentEditable` が jsdom では `undefined` であることも判明した。** ⇒ **保険の 2 を一次にする形は採れなかった**（採っていれば、テストは通るのに本番でしか効かないガードになっていた）。順序はこの実測に基づく。

**★`keyup` はガードを通していない。** 通すと、押下中にフォーカスがテキスト欄へ移ったときに解放イベントが捨てられ、**そのキーが恒久的に「押されたまま」になる**。あわせて `blur` / `visibilitychange` でも押下集合を捨てている。

## 5. `§4.6-3` をどう解いたか（供給元が 2 つになる形）

### 5.1 何が問題だったか（`§3.3-8` の答え）

**既存構造のままでは成立しなかった。** 判定層は**1 本の押下集合の差分**で立ち上がりを採る（`rising = current \ state.held`）。⇒ **2 つの供給元が各自の押下集合を独立に push すると、片方の push がもう片方を「離した」と見せる。**

具体的には——**パッドで強K を押したままキーを 1 つ叩くと、強K が押下集合から消え、次にパッド側のサンプルが来た瞬間に強K が「もう一度立ち上がった」ことになって、押していないステップが増える。**

### 5.2 採った形

**供給層で 2 源を 1 本の押下集合へ合流させてから判定へ渡す**（`web/src/features/keyboard/mergeNormalized.ts`・純粋関数）。

- 各源の最新の `NormalizeResult` を provider の ref に保持し、**どちらかが変化したら合流結果を 1 回だけ判定へ push する。**
- **方向は合流後の上下左右から採り直す**（両源の digit を比べて選ぶのではない）。パッドで `6`・キーボードで `2` を入れているとき、正しい答えは `3`（下前）であって「どちらかの digit」ではないため。**SOCD 規則は `cardinalsToNumpad` の 1 か所のままである。**
- ボタン・`actions` は和集合。`resolved` はどちらかが true なら true。
- **切断時に Gamepad 側の ref を捨てる。** 捨てないと、切断した時点で押されていたボタンが合流に残り続け、**以後キーボードで入力するたびに幽霊の同時押しが混ざる。**

### 5.3 判定層へ開けた入口（`§2.3` の例外条項）

`useStepDetection` の公開 API は `onSample(snapshot, at)` しか無く、内部で `normalizeSnapshot` を**もう一度**呼んでいた（provider 側と合わせて **1 サンプルにつき 2 回**）。ここへ **`pushResult(result: NormalizeResult, at: number)`** を足し、`onSample` はそれへ委譲する形へ整理した。

- **`stepDetection.ts` は 1 行も変えていない。**
- 副次的に、**重複していた正規化が 1 回に畳まれた。**

### 5.4 排他にしていない（`§4.6-4`）

「キーボードモード」は無く、**どちらからでも同時に入る**。テストで固定済み（`§5` (i)）——とくに「パッドのボタン ＋ キーボードの方向」で `crouching_heavy_kick` が出ることを主張しており、**両源が同時に効いていることの証明**になっている。

## 6. `§4.8` の走査結果（★走査コマンドそのもの）

> ### ★★走査コマンドには `LC_ALL=C.UTF-8` を付けること（**本サブで実際に踏んだ**）
>
> **初回の走査 [3] は 0 件を返したが、それは false negative だった**（レビュー指摘 高-1 で検出）。
>
> **原因は実行環境のロケールである。** 本環境の `LC_CTYPE` は `POSIX` であり、この状態では
> `grep -E` の否定文字クラス `[^。]` が**バイト単位**で解釈される。`。`（`E3 80 82`）の構成バイトが
> 除外集合に入るため、`を`（`E3 82 92`）が `[^。]` に一致せず、**`供給元を 1 個` を拾えなかった。**
>
> ```bash
> # 壊れていた形（POSIX ロケールでは 0 件＝false negative）
> grep -rnE "供給元(は|が)?[^。]{0,30}1 ?個" --include='*.ts' --include='*.tsx' web/src/   # → exit 1
>
> # 是正した形
> LC_ALL=C.UTF-8 grep -rnE "供給元[^。]{0,40}1 ?個|単一の供給元|供給元を 1" \
>   --include='*.ts' --include='*.tsx' web/src/
> # → web/src/App.tsx:35 ／ GamepadInputProvider.tsx:4
> ```
>
> **★教訓は「日本語の散文を否定文字クラスで走査するときは必ずロケールを固定する」である。** 軸 (b)
> （前提を述べている散文）は本プロジェクトで常用されるため、**本件限りの回避ではなく運用の型**として残す。
> **★壊れたコマンドを完了報告へ残すと、次の担当も同じ false negative を引く**——走査コマンドを残す運用の
> 目的は「次の担当が同じ走査を回せること」にあるため、**コマンドの正しさ自体が成果物である。**

## 8.1 ★実機確認で見つかった不具合（2026-08-14・開発者報告 → 是正済み）

**開発者の実機確認で 2 件の報告があり、うち 1 件は実装の不具合、1 件は仕様要求だった。** あわせて、その調査中に**同型の不具合を 1 件自力で見つけた**。

### (1) 矢印キーを方向に割り当てるとブラウザがスクロールする【不具合・是正済み】

**原因**——`useKeyboardInput.handleKeyDown` が `preventDefault()` を呼ぶ**前に** early-return していた。

```ts
if (event.repeat) return;               // ← ここで抜けると preventDefault されない
...
if (heldRef.current.has(code)) return;  // ← 同じ
event.preventDefault();                 // ← ここまで到達しないと止まらない
```

⇒ **押し始めの 1 回だけ抑止され、OS のキーリピートは素通りしていた。** 方向入力は押しっぱなしが普通の使い方であるため、**実質ほぼ毎回スクロールした。**

**是正**——「**自分のキーか判定 → 即 `preventDefault()` → その後にリピート／重複の判定**」の順へ組み替えた。**キー名を列挙しない**ため（`§4.4-2` と同じ流儀）、矢印・Space・PageUp/Down・Home/End など**既定動作を持つ登録済みキーがまとめて塞がる**。あわせて **`keyup` でも抑止する**——ネイティブ `<button>` は **Space の活性化を keyup で行う**ためである。

### (2) `Space` を登録可能にしたい【仕様要求・対応済み】

`§3.1` を参照。

### (3) 登録ダイアログでキーを押しっぱなしにすると、身に覚えのない二重割当の確認が出る【不具合・是正済み】

**開発者の報告には無かったが、(1) の調査中に発見した。** ダイアログの keydown ハンドラに**リピートガードが無かった**ため、押しっぱなしのリピートが**次の対象**に対して同じキーを記録しようとし、**「W は『上』に割り当て済みです」という確認が勝手に出る。** 16 件を順に登録する導線であるため、押しっぱなしは実際に起こる。

> **★当初は「次々と別の対象へ割り当たる」と見立てたが、実測したら違った**——2 件目で二重割当が検出され、**未解決の衝突が次の記録を止めるため暴走はそこで止まる**。**⇒ 利用者が実際に見るのは「勝手に出る確認ダイアログ」である。**
>
> **★この差はテストの強さに直結した。** 「暴走しないこと」だけを主張した最初のテストは、**リピートガードを外しても緑のまま通った**（衝突検出が代わりに止めるため）。**「衝突が出ないこと」まで主張して初めてガードを固定できた。**
