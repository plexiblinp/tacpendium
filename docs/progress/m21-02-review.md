## 総評

**チェックリスト §9 の「重大」12 件は 1 件も踏んでいない。**判定窓は `SIMULTANEOUS_PRESS_WINDOW_MS = 90`（ms）の 1 か所に集約され、実測最大（押し始め 45.80 / 離し始め 83.30）を両方とも上回り、その関係を定数直読みで固定する §5.1 (f) のテストが実在する——本サブで唯一 silent な失敗になりうる箇所が、正しく機械で守られている。判定は `window`／`Date`／`performance` に一切触れない純粋関数として切られ、時刻は引数で注入されるため、時刻つき状態列をテストから直接食わせられる。SOCD は M21-01 の `cardinalsToNumpad` へ委譲して 2 実装に割らず、判定窓を通していない。チャタリングは「実装しない」を選び、その旨と根拠をコード内に明記したうえで空テストを置いていない——いずれも指示書の求めどおりである。

一方で、**後続 3 サブ（M21-03 / 05 / 06）が乗る層としては、記述と実装の食い違いが 2 か所ある。**最も重いのは `flushPendingStep` の godoc が「副作用層はタイマーからも本関数を呼ぶ」と書いているのに、実際の副作用層は `closePendingStep` を呼んでおり `flushPendingStep` に本番の呼出元が 1 つも無いことである（本プロジェクトの較正では「失効した記述がコード上に残る」型は高扱い）。

**設計上の実質的な指摘は 1 件、方向の取得時刻である。**ステップの方向は窓の起点のスナップショットから 1 度だけ引かれ、窓の内側で立ち上がった方向は捨てられる。押し始めのズレは実測で中央値 8.30 ms・最大 45.80 ms あり、レバーレスでは方向も物理ボタンであるため、`6 + 強P` が `5 強P`（ニュートラル強P）として確定しうる。この挙動を固定するテストも無い。§4.1-2 が禁じているのは「方向をまとめる対象にすること」であって「窓の起点で 1 度だけ引くこと」までは要求していないため、選択の余地が残っている論点である。

## 設計準拠性以外の指摘事項

これは動作に影響せず、型検査も lint もテストも緑のままであるため、人が読む以外に見つかる経路が無い。かつ本サブの公開インターフェースは **M21-03 / M21-05 / M21-06 の 3 サブが乗る**前提であり（§3.4）、次の担当は「窓を時間で閉じるのは `flushPendingStep`」と読んで採用する——**実際には `pushSample` が次サンプルで閉じるか、副作用層が `closePendingStep` を呼ぶかの 2 経路しか動いていない。** 本プロジェクトの較正（失効した記述の残置 = 高）に従って高に置く。

- 推奨: (i) `flushPendingStep` の説明を実態（「時間経過を条件に閉じる純粋関数。現状の副作用層は使っていない」）へ直すか、(ii) `useStepDetection` 側を `flushPendingStep` へ寄せて記述を真にするか、(iii) 使わないなら削除する。**どれでもよいが、記述と実装のどちらかを動かすこと。**

**指摘 5（中）: `mergedCount` の意味づけが `GamepadStepPreview` のコメントで狭く書かれている。**

`stepDetection.ts:96` は「**同じボタンの再立ち上がりも 1 と数える**」と正しく定義しているが、`GamepadStepPreview.tsx:63` は「**2 以上なら同時押しがまとまったということ**」と書いている。同じボタンの再立ち上がり（`test:168` が固定している挙動）でも 2 になるため、後者は偽である。可視化の目的が「窓が広すぎる／狭すぎるの切り分け」である以上、**この数の読み方を誤ると切り分け自体が誤る。**

**指摘 6（中）: `resolved: false → true` の遷移でボタンを保持していると、幻のステップが 1 つ出る。**

`pressedButtons()` は `resolved !== true` のとき空配列を返す（`stepDetection.ts:213`）。`GamepadStatusControl` はプロファイルを `useEffect` 経由で `setProfile()` に流すため（`GamepadStatusControl.tsx:29`）、**初回描画〜effect 実行までの数フレームは `profileRef.current === null` → `resolved: false` → `held = []`** になる。M21-01 の接続導線は「コントローラのボタンを 1 度押してください」であり、**利用者はまさにその瞬間にボタンを押している。**押しっぱなしのままプロファイルが解決すると、保持中のボタンが立ち上がりとして拾われ、実際には押し直していないステップが 1 つ確定する。キャリブレーションのやり直し（`profile` の差し替え）でも同型が起きうる。

- `reset()` は `status !== "connected"` のときだけ呼ばれ（同:32）、**プロファイル変化では呼ばれない。**
- 推奨: (i) `resolved: false` を「押下なし」ではなく「未知」として扱い、未知 → 解決の最初のサンプルでは `held` を種付けするだけで立ち上がりを出さない、または (ii) `profile` が変わったら `reset()` する。**(ii) のほうが 1 行で済む。**

**指摘 7（中）: `closedAt` が「窓が閉じた時刻」ではなく「閉じたことに気づいた時刻」になりうる。**

`pushSample()` の窓クローズ経路は `toCandidate(pending, now)` を使う（`stepDetection.ts:347`）。`now` は**次に入力が変化したサンプルの時刻**であり、`startedAt + windowMs` ではない。利用者が押して 5 秒放置すれば `closedAt - startedAt ≒ 5000 ms` になる。本番では副作用層のタイマーが先に閉じるため通常は表面化しないが、**公開インターフェースとして宣言されている一括版 `detectSteps()` にはタイマーが無い**ため、M21-03 がこれをレシピ組み立て（ステップ間隔の算出など）に使うと誤った値を引く。`GamepadStepPreview` の tooltip「窓の起点からの経過 N ms」も同じ理由で誤表示しうる。

- 推奨: `closedAt` を `min(now, startedAt + windowMs)` にする、または `StepCandidate` の godoc に「窓の満了時刻ではなく確定を観測した時刻である」と明記する。**後者だけでも次サブの誤用は防げる。**

**指摘 8（低）: レンダリング中の ref 書き換え。**

`useStepDetection.ts:54`（`windowMsRef.current = windowMs`）と `useGamepadPolling.ts:169`（`onSampleRef.current = onSample`）はレンダリング中に ref を書き換えている。React の推奨（レンダリングを純粋に保つ）から外れ、Concurrent 機能下では捨てられたレンダリングの値が残りうる。現状の使い方では実害は出ないが、`useEffect` / `useLayoutEffect` 内での代入が定石である。

**指摘 9（低）: `scheduleFlush()` がサンプルごとにタイマーを張り直す。**

`snapshotChanged()` はアナログ `value` の変化でも真になるため、スティック・トリガーのノイズがある機体では `onSample` が毎フレーム（実測 約 238 Hz）発火しうる。そのたびに `clearTimeout` + `setTimeout` が走る。`pending.startedAt` が変わっていなければ張り直す必要は無い（`closesAt` は不変）ので、早期 return を 1 行入れられる。

**指摘 10（低）: `GamepadStepPreview` の React key が衝突しうる。**

`startedAt` と `buttons.join("-")` を連結した key（`GamepadStepPreview.tsx:61`）は、時刻が同値へクランプされた場合（(k) の巻き戻り・NaN 経路）に同一キーになりうる。`mergedCount` や連番を混ぜるのが安全。

**指摘 11（低）: マジックストリング `"direction_"` の直書きが 2 か所。**

`isDirectionButton()`（`stepDetection.ts:161`）の `startsWith("direction_")` と `directionLabel()`（`GamepadStepPreview.tsx:20`）の `replace("direction_", "")`。`CLAUDE.md` §4「マジックストリングは定数化」に照らすと接頭辞を定数化するのが規約どおり。ただし後者は撤去前提のファイル（§4.6-3）であり、共有定義を作らない方針とのトレードオフがあるため強くは求めない。

**指摘 12（低）: テストフィクスチャの `90` 直書き。**

`GamepadStepPreview.test.tsx:15` の `closedAt: 90` は判定窓と同値のリテラル。表示テストなので実害は無いが、`SIMULTANEOUS_PRESS_WINDOW_MS` を参照させておくと「窓の値を変えたのに残った 90」を作らない。

**指摘 13（低・情報）: `StepCandidate` が `cardinals` を持たない。**

M21-01 が `cardinals` を残した理由は「M21-02 が別の SOCD 規則を採れるようにする」ことだった（同完了報告 §4 申し送り 1'）。本サブでその役目は果たされたが、`StepCandidate` は解決済みの `direction` しか持たないため、**M21-06（実モーション入力）が生の上下左右を要する場合、`NormalizeResult` まで配管を戻す必要がある。** 現時点で足す必要は無いが、公開インターフェースの記述にこの制約を 1 行書いておくと次サブが設計時に気づける。
