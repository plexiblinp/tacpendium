## 総評

**機序の側は正しく閉じている。** DSN の `_txlock=immediate` は `modernc.org/sqlite v1.50.0` のソース（`sqlite.go:195-201` / `tx.go:22-25`）で独立に裏取りでき、`opts.ReadOnly` で読み取り専用が除外されることも確認した。判定条件・`deleted_at IS NULL` / `is_draft = 0`・`migrations/`・DSN の `_pragma` 4 種・凍結パッケージのいずれにも差分は無く、`go test ./... -count=1` を再実行して **55 パッケージ ok / FAIL 0** を独立に確認した。破壊確認 3 が当初空振りしていたことを自ら発見して是正し、「`*sql.Tx` の束ねは今日は必須ではない」という非対称を隠さず書いた姿勢は本サブの白眉である。

**しかし `VAL-C02` の適用面の数え上げに欠落がある。** `ValidateComboForCreate` の呼び出しは 4 か所あり（`service.go:326` / **`:596`** / `:722` / materialize の探索 `:1383`）、このうち **`UpdateMetadata` の仮登録→本登録昇格（`PATCH /api/combos/:id`、`service.go:596`）だけがトランザクションの外・非 tx ハンドルのまま**である。完了報告は「昇格」「`UpdateMetadata`」「`PATCH`」のいずれの語も持たず、§4.4 の一覧にも載っていない（§6.2-3 の「`combo.Update` の前段読み（`service.go:561-571`）」は着手基点で M4-03 の KA 検査を指しており、昇格の `VAL-C02` は別ブロック `:533-546` である）。**⇒ 本サブが閉じたはずの欠陥が 4 経路目に残っており、しかもそのことが as-built に記録されていない。**

もう 1 点、**コード上のコメントが実測より古い**（`val_c02_race_test.go:291` が「非 tx の呼び出しは **5 本**」「書きは 0 件」と書いたまま。完了報告 §3.2.1 は 9 本へ数え直しており、§3.2 は「書き」に当たる形を 1 件見つけて直したと書いている）。本プロジェクトの較正どおり「高」に置く。

テストの作り込みは総じて丁寧だが、**緑が意味を持たない箇所が 3 つ**ある（成立しえない assertion 1 件、goroutine のエラー黙殺による空振り緑 1 件、発火しない対照 1 件）。同時実行の欠陥を扱うサブであるだけに、ここは詰めておきたい。

## 設計準拠性以外の指摘事項

### 高-1（重大に準じる）: `VAL-C02` の 4 経路目——**仮登録→本登録昇格が tx の外のまま、かつ一覧に無い**

**何が**: `ValidateComboForCreate`（＝`VAL-C02` を含むフルバリデーション）の呼び出しは production に 4 か所ある。

```
internal/service/combo/service.go:326   Create               → s.txScopedDeps(tx)   ✅ tx の内側
internal/service/combo/service.go:596   UpdateMetadata(昇格)  → s.validDeps          ❌ BeginTx(:629) より前・非 tx
internal/service/combo/service.go:722   UpdateWithKeyChange  → s.txScopedDeps(tx)   ✅ tx の内側
internal/service/combo/service.go:1383  Materialize(探索)     → s.txScopedDeps(tx)   ✅ tx の内側
```

**どの根拠で**: `:596` は `input.IsDraft != nil && !*input.IsDraft` かつ `current.IsDraft` のとき、すなわち **`PATCH /api/combos/:id` による仮登録→本登録の昇格**（`M2-02`。ルートは `internal/api/combo/routes.go:26`）で走る。判定は `s.validDeps`（非 tx）で行われ、実際の書き込み（`s.repo.UpdateMetadata`）は `:629` で開いた別の tx で行われる。**⇒ 判定と登録の間に隙が空いたままの check-then-act であり、本サブが `POST` / `PUT` / `materialize` で閉じたものと同型である。**

**どう違うか**: 昇格経路は `is_draft` を 0 にする＝**重複判定の母集団（`is_draft = 0 AND deleted_at IS NULL`）へ新しい行を持ち込む操作**である。したがって
- 同一識別キーの仮登録 2 件を同時に昇格させる、または
- 昇格と `POST` を同時に走らせる

## ★製造が自己申告した弱点 3 点の独立評価

### 1. 「`*sql.Tx` の束ねは `VAL-C02` の正しさにとって今日は必須ではない」
