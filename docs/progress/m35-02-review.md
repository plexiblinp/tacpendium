## 総評

三点更新（CSV 正本 ／ golden 再生成 ／ 追随マイグレ）は 3 点とも揃っており、チェックリストが最重要とした A-1 / C-1 / C-5 はいずれも実測で確認できた。golden は手編集ではなく再生成であることを `go run ./cmd/seedgen -check`（exit 0・生成物一致）で機械確認でき、差分は 8 ファイル 11 行すべてが 1 対 1 置換である。追随マイグレは層 B と判定され、`NOT EXISTS` ガード・`character_id` との対絞り・`down` の 3 点も揃う。C-5 の「DB 側の追随 UPDATE は要らない」という結論も、`preset_aliases` のスキーマ（`move_id` / `alias_text` / `alias_text_en` / `character_id` のみ・`move_code` 列なし）を読んで正しいと確認した。

陽性対照は純粋関数・入力面の両方に置かれており、機序が SQL コメント・テスト・報告の 3 か所へ残っている。破壊確認 6 件も、単に「赤になった」ではなく「どの検査が捕まえ、どの検査が緑のままだったか」まで書き分けており、本プロジェクトで繰り返し問題になってきた「緑だが効いていない」の型を正面から扱っている。版固定テストの主張反転も、緩和ではなく対のままの入れ替えであることを確認した（後述）。

一方で、失効した記述をコード上に残した判断が 2 件ある（`inputResolution.ts:78` と `VirtualController.test.tsx` のテスト名）。どちらも製造が自ら実測して失効を確認しながら射程外として残しており、本プロジェクトの較正では「高」に当たる。加えて、走査軸に `comboio` の CSV 入出力契約（`recipe` セルが `move_code` 文字列を運ぶ）が入っておらず、`down` 方向の非対称の検討が v107 で止まっている点に指摘がある。

### 版固定テストの主張反転の妥当性

`internal/infra/migration/migrate_m1403c_test.go` の 2 つのリストを入れ替えた判断は妥当であり、「落ちたテストを緩めた」には当たらない。根拠は 3 つある。

1. 要素数がどちらのリストも不変で、`axe_kick` が「存在する」側へ、`axe_kick_2` が「不在」側へ、対のまま入れ替わっている。判定の本数も強さも減っていない。
2. 反転後の主張は「新体系が使う code はこれである」という同じ意味を保っている。golden `000030` が seed する code が開発者の確定で変わった以上、v30 終端の契約テストが動くのは必然である。
3. 元の `axe_kick` が「旧体系のみの code が不在」側に居たことで守っていたもの（`000029` が旧 seed を掃いたこと）は失われていない。同テストは `ryu moves = 93` と `rush_variant = 17` を別に固定しており、旧 seed 行が復活すれば件数が動く。さらに `UNIQUE(character_id, code)` があるため、旧 `axe_kick` 行が残ったまま `000030` が `axe_kick` を INSERT すればマイグレ自体が落ちる。

なお、先に赤を実測してから直した手順（報告 §6）も正しい。terry の先例に版固定テストが無かったという主張も、`migrate_m2805_test.go` / `migrate_m3002_test.go` がそれぞれ v106 / v107 終端であり golden `000026` の版に固定されたテストが存在しないことを確認して裏づけた。

## 設計準拠性以外の指摘事項

### 指摘 1（高）失効したコメントが本番コードに残っている — `web/src/features/combo/inputResolution.ts:78`

```
// 特殊技タブのラッシュトグル表示可否に用いる(存在しなければトグルを出さない=ryu 等での空状態回避)。
```

`ryu` は `rush_collarbone_breaker` / `rush_solar_plexus_strike` / `rush_short_uppercut` / `rush_axe_kick` / `rush_whirlwind_kick` を持つため、`hasUniqueRushVariant` は着手時点から `true` である。つまり `ryu` は「トグルを出さない例」ではなく、むしろ「トグルは出るのに 1 ボタンだけ押せない」という本サブの実害そのものを示す例だった。

製造は §12.1-2 でこの失効を実測で認定しながら、射程外として残す判断をしている。本プロジェクトの優先度較正では、この型の指摘は「高」である。理由は 2 つで、(a) 動作は正しいままなのでテストも lint も型検査も緑になり、人が読む以外に見つける経路が無い、(b) 後任がこの行を前提として読み、`ryu` を「unique ラッシュ版を持たないキャラ」として扱う。加えて本サブは、まさにこの誤解を否定するための面のテストを新設した手番である。同じ手番で誤解の源を残すのは筋が通らない。

修正はコメント 1 行の書き換えで済み、挙動へのリスクはない。

### 指摘 2（高）テスト名が失効している — `web/src/features/combo/components/VirtualController/VirtualController.test.tsx`

```
it("特殊技タブ: 既定(ryu 相当・unique ラッシュ版なし)ではラッシュトグルが出ない", ...)
```

このテスト名は「`ryu` は unique ラッシュ版を持たない」と述べている。ところが同一ファイルの 8 行ほど上、本サブが新規に足したコメントは次のように述べている。

### 指摘 3（中）走査軸に CSV 入出力契約が入っていない — `internal/service/comboio`

報告 §2.3 は次のように結論している。

> これは「参照が 0 件だった」ではなく「参照の仕組み上ありえない」である。（中略）`move_code` の改名は、利用者データを 1 行も壊さない。

DB 内についてはこの結論で正しい。しかし `move_code` を文字列として運ぶ経路が DB の外に 1 本ある。コンボ CSV の `recipe` セルはセル内 JSON `[{move_code, modifiers}]` であり（`internal/service/comboio/csvcore/contract.go:56` / `combo.go:102`）、取込時に `codeResolver` が `(character_code, move_code)` → `move_id` を解決する（`lookup.go:73`）。未知の `move_code` は `VAL-I07` の WARNING となり、`move_id` を NULL にしたまま取り込まれる（`validate.go:200` / `service_test.go:320`）。

したがって、本サブ以前にエクスポートされた ryu のコンボ CSV が `axe_kick_2` を含んでいた場合、再取込するとそのステップは技を失った状態で入る。エラーで止まらず WARNING に落ちるため、利用者が警告を読み飛ばせば静かに欠落する。フェーズ3 が共有・発信を扱う以上、外部に出た CSV が戻ってくる経路は今後増える。

これは本サブで直すべきものではない（指示書 §2.1-2 の「止めて報告」条件にも、厳密には DB 内の `code` 経由参照ではないため当たらない）。指摘は 2 点である。

- 段 1 の走査軸に「DB 外の成果物が `move_code` を文字列で持つか」が無かった。`SUPP-001` §5.5.4 (11) が求める 2 本目の軸（旧識別子を含まずに主張している箇所）と同じ性質の見落としである。
- 「利用者データを 1 行も壊さない」という断定は DB に限定して書くべきである。断定を残すと、次に同型の改名を行う担当がこの文をそのまま複製する。

対応としては、followup へ 1 行（旧 `move_code` を含む既存エクスポート CSV の再取込は VAL-I07 になる、という既知の帰結）を残すことを推奨する。同じ帰結は `000063` / `000106` / `000107` にも当たるため、本サブ固有ではなく三点更新という型に属する申し送りになる。

### 指摘 4（中）`down` 方向の非対称の検討が v107 で止まっている

`000108` の down コメントは次のように非対称を認めている。

> golden 再生成後の新規 DB は v30 の時点で既に axe_kick を持つ。そこから v107 へ down すると axe_kick_2 になるが、それは「その DB の v107 時点の本来の状態」ではない。

ここまでは正しい。しかし v107 より下へ降ろすと、認識されている以上のことが起きる。`000030_seed_moves_ryu.down.sql:9` / `:11` は削除対象を code 列挙で指定しており、その列挙は golden 再生成で `axe_kick` になっている。一方、v108 → v107 の down で当該行の code は `axe_kick_2` に戻っている。したがって v108 から v29 まで降ろすと、

1. `000030.down` の `DELETE FROM preset_aliases ... AND m.code IN (... 'axe_kick' ...)` が当該別名 3 件に当たらない
2. 続く `DELETE FROM moves ... AND code IN (... 'axe_kick' ...)` が当該 move 行に当たらない
3. `000029.down` が旧体系の `axe_kick` を再投入する。code が異なるため `UNIQUE` 衝突は起きず、成功する

という順で、`axe_kick_2` の move 1 行と別名 3 件が取り残される。その後 v108 まで上げ直すと、`000108.up` の `NOT EXISTS` ガードが「`axe_kick` が既に居る」と判定して何もしないため、孤児行は残り続ける。UI 側からは重複した「かかと落とし」に見える。

これは本サブが新たに作った欠陥ではなく、`000063` / `000106` / `000107` が共有する既存クラスである（down コメント自身がその 3 本を挙げている）。また `m.Down()` や `Migrate(0)` を呼ぶテストは 1 本も無い（実測）ため、現状どのテストも通らない経路でもある。とはいえ down コメントが結論の 1 歩手前で止まっており、「往復で復帰することだけを保証する」という書き方だと、読み手は「往復以外は未定義」ではなく「往復以外も概ね安全」と読みうる。

対応は followup への 1 行の記録を推奨する。本サブでの修正は不要と判断する（`M33` のマイグレ統合で旧系列が畳まれれば消える性質の問題でもある）。

### 指摘 5（中）`SUPP-001` §5.5.4 (8)(iii) の id 同一性が down 側でしか固定されていない

規約は「契約テストは、旧 code 0 件・新 code 1 件の対に加えて、`id` の同一性を固定する」と定める。理由は、改名が「削除 + 再作成」で実現されていた場合に件数は一致するが id が変わり、参照側が静かに切れるためである。

`TestRun_M3502_LinksSurvive` は v108 で id を取り、down 後に同じ id であることを主張している。ここは規約を満たす。しかし固定されていない経路が 1 本残る。`TestRun_M3502_DownUpRoundTrip` は re-up 後に `assertRenamedM3502`（件数のみ）を呼ぶだけで、id を見ていない。既存 DB で実際に走るのはこの up 側であり、規約が想定している「削除 + 再作成」の事故が起きるとしたらここである。
