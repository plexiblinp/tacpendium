### 2.3 利得「最大」の 3 件がなぜ最大か

**7（DES 反映）・11（board 維持）・12（backlog 維持）は、Web 版だと人手が媒体になる。**

### 3.2 ★パス単位の遮断は書けない（前段プランの誤り）

プラン段階では「`internal/service` `internal/api` `web/src/features` `web/src/pages` を How 面として遮断する」案を立てた。**実査で成立しないことが分かった。**

**playbook §4.9.2 が、まさにその `web/src/features/` の直読を明示的に義務づけている:**

> 1. **構造の確認**: `web/src/features/<domain>/components/<Name>.tsx` を **view し**、JSX のトップレベル構造を把握する
> 2. **責務の確認**: 同ファイル内で `useMutation` / `useQuery` / `useState` / `useEffect` の有無を確認し、副作用を自身で持つか親に委ねるかを判別する

### 3.4 ★フックによる Read 遮断は成立しない（実測・2026-08-11 開発者提起）

開発者から **「最近のモデルは賢いため、何とか回避してコードを読もうとする可能性がある。物理的に閲覧不可にした方がフックより安全では」** という指摘があり、実査した。**指摘は正しかった。**

`.claude/settings.json` の allow リストを機械的に読むと、次が **パス制限なしで事前承認済み**である。

```
Bash(cat:*)  Bash(sed:*)  Bash(head:*)  Bash(tail:*)
Bash(grep:*) Bash(rg:*)   Bash(find:*)  Bash(awk:*)
```

**⇒ `PreToolUse(Read)` を塞いでも、`sed -n '1,200p' internal/service/x.go` が承認プロンプトすら出さずに通る。**

しかも **本プロジェクトは同じ型の失敗を既に 2 回学んでいる**。`settings.json` の `_hooks_comment` に明記がある。

> 重要: **フックはパーミッション層をバイパスして実行される**ため deny リストはフック内コマンドに効かない

> MCP は **Bash と別ツール面の API 実行のため Bash の deny が効かず**、push_files 等で main へ直接書けてしまう

**「チャネル別のガードはチャネルを跨がれる」**——MCP を一括 deny した理由がこれである。Read 遮断も同じ型に落ちる。

### 3.5 ★クラウドでは `ask` が効かない（担保設計の制約）

`settings.json` に V-2 の実測が記録されている。

> **クラウド（Claude Code on the web）では ask が実質機能せず**任意ブランチ push が通ることの実測（V-2）への対策

**⇒ 「危ないことをしたら開発者に聞く」設計はクラウドでは成立しない。クラウドで効くのは deny と PreToolUse フックだけである。** `pre-push-guard.sh` はまさにこの理由で存在する。

### 3.6 推奨（確定）：物理排除 ＋ git 系遮断 ＋ 検出の 3 枚

#### ① 物理排除（主）— `scripts/design-desk-arm.sh`

セッション冒頭で sparse-checkout を張り、作業ツリーを `docs` `.claude` `scripts`（＋リポジトリ直下のファイル）だけにする。

**実装ファイルが作業ツリーに存在しなくなるので、§3.4 で挙げた classic テキストツール群はまとめて空振りする。** チャネル別ガードの最大の弱点を、チャネルに依存しない形で克服する。

#### ② git 系遮断（従）— `.claude/hooks/design-desk-guard.sh`

物理排除後に残る漏れ経路は **git のオブジェクト読み出しだけ**になる。これは有限の閉じた集合である。

**遮断は「ブロックする verb の列挙」ではなく「安全な verb の許可リスト」で書く。** 列挙方式は必ず取りこぼす（`show` / `log -p` / `diff <rev>` / `grep` / `blame` / `cat-file` / `archive` / `format-patch` / `bundle` / `read-tree` / `checkout-index` …）。許可リストなら集合が閉じ、**過剰ブロックは可視で直せるが取りこぼしは silent** という非対称に正しく倒せる。

| 区分 | git サブコマンド | 扱い |
|---|---|---|
| 内容を出さない | `status` `add` `commit` `branch` `remote` `rev-parse` `ls-files` `ls-tree` `shortlog` `describe` `push` `init` | 無条件で通す |
| 条件付き | `log`（パッチ指定時）／ `diff`（リビジョン参照時） | 許可領域への pathspec が要る |
| 常に内容を出す | `show` `blame` `grep` | 許可領域への限定が必須 |
| その他すべて | — | **ブロック** |

あわせて、**武装マーカーがあるのに実装ソースが作業ツリーにある状態**（＝前提の崩れ）を検出して全ブロックする。

#### ③ 検出 — 接触の記録

実装パスへの接触を記録し、成果物の「読んだ資料」節に出させる。**新設の統制ではない**——`parallel-ops` §06 の最終レポート様式 §2 が既に採用している。

> 読んだ資料 — 鮮度ズレを親が安く検出するためのパリティチェック

#### 自己武装の弱さをどう扱うか

**武装しないリスク** → 開発者が確認できる。`ls` でトップレベルが短いことが一目で分かり、③の記録にも出る。

**武装後に外すリスク** → **②が塞ぐ。** 外す経路が有限（`git sparse-checkout` / `git worktree` / マーカー削除）だからである。Read の広域遮断が破られたのは経路が無限だったからで、**物理排除後はそれが有限になる。性質が違う。**

#### ローカルとクラウドの差

同じ `design-desk-arm.sh` を使う。ローカルでは worktree ＋ sparse を張れるので、**武装が開発者の手で行われる分 1 枚強い**。クラウドは自己武装だが、②③ が同一なので成立する。

### 3.7 ★別リポジトリ化を採らない理由

## 4. 並列設計を Code でどうやるか

### 4.1 現行方式（M20 以降の正本）は 4 層

`parallel-ops` §00〜§01:

```
開発者 ─起動プロンプト→ 個別設計チャット（使い捨て・Web）─レポート1本→ 親チャット（設計卓・Web）
                                                                    │ 指示書      ↑ 設計伝達レポート
                                                                    ↓             │
                                                        製造担当 Claude Code ─完了報告→ repo
                                                        反映係 Claude Code（★2026-08-11 廃止済み）
```

### 4.2 Code 版への写像

| 現行の層 | Code 版での対応 | 効果 |
|---|---|---|
| **個別設計チャット**（使い捨て・Web） | **サブエージェント** | **人手リレーが消える**（開発者がプロンプトをコピペし、レポートをコピペで戻す往復） |
| **親チャット（設計卓）** | Code セッション（本体） | ボード・backlog・DES を直接 Edit できる（§2.3） |
| **反映係** | **消滅**（2026-08-11 廃止） | — |
| **複数マイルストーンレーン** | **git worktree** | 前例あり＝`implement_plan_wt` / `review_plan_wt` / `research_plan_wt` |
| **クリーンルームレビュー** | **サブエージェント** | 前段資料 §2.1 の調査対象。Code 版でのみ使える |

### 4.3 最終レポート様式はそのままサブエージェントの出力スキーマになる

`parallel-ops` §06 が定める「個別設計チャットの最終レポート様式（固定）」8 節は、変更なしでサブエージェントの返却契約として使える。

| § | 節 | サブエージェント出力での役割 |
|---|---|---|
| 1 | 目的 | 何を決めるために起動されたか |
| 2 | 読んだ資料 | **鮮度ズレを親が安く検出するためのパリティチェック** |
| 3 | 検討した選択肢 | 却下案とその理由（1 行ずつ） |
| 4 | 確定事項 | 親が読む本体 |
| 5 | 開発者判断が要る未決 | 残ったもの |
| 6 | DES 差分案 | **どの DES のどの節をどう変えるか**。ここまで書かせると親の仕事はレビューとパッチ発行だけになる |
| 7 | 指示書に入れるべき制約 | 製造への申し送り |
| 8 | 教訓 | retrospective 行き。**親は読まなくてよいと節に明記** |

> **`parallel-ops` §06 V2.2 の注意はサブエージェント化しても残る**——「**委任するときは返却物の文書番号まで指定する。番号を割り当てないと委任先が自然に次番を取り文書番号が二重発番される**」。サブエージェントでも同じことが起きる。

### 4.4 §06 の「読むべき文書名を明示（project knowledge の検索は取りこぼす）」は形が変わる

Code 版にはプロジェクトナレッジも検索取得も無い。**「取りこぼすから明示せよ」という理由は消えるが、「明示せよ」という結論は残る**——理由が「検索の取りこぼし」から「**読ませないため**」（§3.6）へ入れ替わる。**規則の文面は同じでよいが、根拠の書き換えが要る。**

### 4.5 ★M20 + M21 の並列（2026-08-11 開発者方針）

開発者が **M20 と M21 を並列で設計したい**と表明した。**これは Code 化の根拠を強める。**

M18/M19 の並列で実際に壊れたものがボード §8.1 に 4 件記録されているが、**うち 3 件は設計卓が Web にあることが直接の原因**である。

| 壊れたもの | Web 起因か |
|---|---|
| 開発者がメッセージバス化した | **○**（人手リレーが媒体） |
| 中央が人力ロックサーバー化した | △（採番の同期調停。`parallel-ops` §02 のブロック事前割当で別途解決済み） |
| **搬送段が断絶した（G-5）＝ 中央が repo を見られないまま「反映済」と宣言** | **○（Web 版固有の failure mode）** |
| 番号払い出しとゲートを混同した（G-8） | ✕（プロセス問題） |

**G-5 は並列で 2 マイルストーン分の反映が走ると 2 倍露出する。**

#### 委譲の形

| 層 | 面 | 数 | 持ち物 |
|---|---|---|---|
| **親（設計卓）** | Code・メインツリー | **1** | 契約 2 枚（M20/M21）・registry・board・DES 反映 |
| サブ設計 | 親の中のサブエージェント | N | 使い捨て。§4.3 の 8 節を出力契約とする |
| 製造 | Code・**worktree** | 2 | M20 レーン / M21 レーン（`implement_plan_wt` の前例） |
| レビュー | 製造セッション内のサブエージェント | — | 現行どおり |

**★親を 2 つ立ててはならない。** `parallel-ops` §04 V2 の強化点は「**契約の発行者が親チャット 1 人になることで DES 所有権の排他性が構造的に保証される**」ことである。M20 用と M21 用に親を分けると、この保証が崩れる。

共有直列リソース（CHANGE 番号・DES 本体・マイグレ連番）は親 1 人が持つので衝突は原理的に起きない。マイグレは `parallel-ops` §02 のプレースホルダ＋マージ時採番を面と無関係にそのまま使う。

> **並列は §2.2 の論点 4 件のコストも 2 倍にする。** 指示書作成が M20/M21 で 2 本走るため、そこを Web に残す判断のコストは倍で効く。

#### ブランチ戦略と設計卓の交換時期

**正本は `docs/process/remote-ops.md` §6.1・§6.2**（2026-08-11 新設・v1.1.0）。要点だけ:

- **設計卓と製造はどちらも main から分岐し、どちらも main へマージする。** 設計卓ブランチから製造を分岐させない
- 理由の芯は §3.7 と同じ——**分岐上に `parallel-board.md` ／ `change-number-registry.md` ／ `followup-backlog.md` の正本が載ると「main の版と分岐版のどちらが正か」が曖昧になる**（E-33／G-5 の再演）。加えてマージが 2 段になり人間の作業が倍になる
- **分岐させなくてよいのは、設計卓が武装により `internal/` `web/src/` を持たず、触れるファイルが物理的に分かれているため。** 製造が要るのは「マージ済みの指示書」で、指示書は docs 系なので即マージできる（`remote-ops` §1-2）
- **交換時期の判定の芯が変わった**——`parallel-ops` §05 の「状態はボードへ出す＝いつでも使い捨て可」が、反映係の廃止で初めて成立する（「未反映」という状態が消えるため）。既定のトリガは**サブマイルストーンの完了時**（設計卓は `fetch` が deny で、畳んで作り直す以外に main の進行を取り込めない）

## 5. 面を分けた場合に発生する継ぎ目

**開発者の希望は「Web 版と Code 版どちらでも進められるようにしたい」。両面を持つこと自体は妥当だが、継ぎ目には既知の失敗型がある。**

| # | 継ぎ目 | 内容 |
|---|---|---|
| 1 | **状態の受け渡し** | 正本はボード（`parallel-board.md`）。**Web 側の設計卓はボードを直接書けない**ため、Web で決めたことは (a) 開発者が貼る (b) 後から Code 側が書く のいずれかになる。**(b) は「設計の意図が反映側へ伝わらない」＝C 案が却下された理由と同型** |
| 2 | **契約の所有権** | `parallel-ops` §04 V2 の強化点は「**契約の発行者が親チャット 1 人になる**」ことで、これにより **DES 所有権の排他性が構造的に保証される**。同一マイルストーンを 2 面で同時に持つと、この保証が崩れる |
| 3 | **鮮度** | Web 側は「最終 push + Sync now 時点」のスナップショット、Code 側は HEAD。**同時稼働すると Web 側が古い前提で判断する** |
| 4 | **§12 ツール手順の二重化** | playbook §12 が両面ぶん必要になる（前段資料 §4 条件 3 の C パターン） |

### 5.1 ⇒ 面を分けるなら「時間で分ける」

**同一マイルストーンについて、両面を同時に持たない。** 局面ごとにどちらか一方だけが動く形にすれば、継ぎ目 1〜3 はいずれも発生しない（引き継ぎ点が 1 箇所に固定されるため）。

開発者案の「overview 作成までは Web、個別は Code」は、**まさにこの時間分割になっている**——マイルストーン起動時に Web、サブ設計に入ったら Code。**継ぎ目の観点からは筋が通っている。**

**残る論点は §2.4 のとおり「高リスクの指示書作成が Code 側に来る」ことだけで、それは §3.6 の担保で処理できる。**

### 5.2 ★決定：時間分割は採らず、Web 版は「個別設計チャット」へ配置換えする（2026-08-11）

**M20 + M21 を並列にすると、時間分割が成立しない。** 進行がずれるため **M21 の overview 期と M20 のサブ期が重なり**、同時に両面を持つ状態になる。継ぎ目 1〜3 が全部発生する。

そもそも A（全件 Code）と B（時間分割）の差は **`M{N}-overview.md` の作成・更新（#13）1 件だけ**である——Q1 で #1 契約ファイル発行と #2 ブロック事前割当が Code 確定した以上、overview 期の中で面が割れてしまう。

**⇒ 全 19 件を Code に置く。** ただし開発者の希望「Web 版と Code 版どちらでも進められるように」は、**Web 版の居場所を変えることで満たす**。

| 旧 | 新 |
|---|---|
| Web 版 ＝ 親（設計卓） | Web 版 ＝ **個別設計チャット**（`parallel-ops` §06） |

`parallel-ops` §06 の定義がそのまま当てはまる——**設計変更権限は一切持たない／開発者と打ち合わせ、最後に整理されたレポート 1 本を出す／目的達成で役目を終える**。長い合議が要る設計判断はここへ外注でき、外出先（スマホ）でも成立する。**親が 1 つであるという §4.5 の前提を壊さない。**

### 7-A2 の決着（2026-08-12・工程改善レーン）

**旧「判断が要る点」**: Codex が `PreToolUse` の exit 2 によるブロックを解釈するかは未確認である——**実査の結果、解釈する。同期は可能だった。**

**⇒ `.codex/hooks.json` へ `PreToolUse` を追加した**（`pre-push-guard.sh` ＋ `design-desk-guard.sh`）。Codex 形のペイロードを直接流す実測で、`git push origin main` → exit 2 ／ `git push origin claude/x` → exit 0 ／ `git push --force origin claude/x` → exit 2 を確認済み。**両スクリプトは `.tool_input.command` を読み、解析不能時は生入力全体を判定対象にする安全側フォールバックを持つ**ため、ペイロード差異があっても**取りこぼしではなく過剰ブロック側**へ倒れる。

### ★★ その後の実測で覆った（2026-08-12・同日）

**「同期は可能」は配線レベルの話でしかなく、実際には発火しなかった。** 決定的だったのは**対照実験**——武装マーカーを置き `internal/` が在る状態で、**同一の `git status --short`** を両経路から打った:

| 経路 | 結果 |
|---|---|
| **Claude Code** | `design-desk-guard: 武装マーカーが…存在します` で **exit 2** |
| **Codex** | **普通に実行された** |

フック実装は同一ファイルなので、**差はディスパッチ側にしかない。**

**原因は機能の無効化ではない**——`codex features list` は `hooks  stable  true`。**書式か置き場所が違う。** ⇒ **`.codex/hooks.json` は Claude の `settings.json` 書式を写して作られ、一度も検証されていなかった**と考えられ、**既存の `PostToolUse` / `Stop` も発火していなかった公算が大きい**。

> **★訂正（2026-08-12・`f716d56` で決着後）**: 本節は当初「**傍証として `Stop` は Codex のフックイベントに存在しない**（Codex は `session_end` / `subagent_stop`）」と書いていたが、**これは誤りだった**。実際の欠落は**トップレベルの `"hooks": { … }` ラッパ**で、イベント名（`PreToolUse` / `PostToolUse` / **`Stop`**）は Claude と同じ PascalCase のまま正しかった。
>
> **誤った理由**: バイナリの文字列から snake_case の列挙（`pre_tool_use` / `session_end` …）を拾い、それを設定ファイルの受理形式と解釈した。**実際にはその列挙は別モジュール（外部エージェント設定の取り込み）のものだった。** バイナリ実査は「その語が実行ファイル内に在る」ことしか示さず、**どの経路で使われるかまでは示さない**。§7-A2 の教訓「呼ばれるかは呼ばれる側からしか測れない」は、**語の意味についても同じ**である。

**⇒ §7-A2 冒頭の「判断が要る点」が示していたフォールバック分岐**——「**その場合は『Codex 側では本フックの層が無い』ことを `remote-ops.md` §6 の多層防御の説明へ明記すべき**」——**が結局あてはまった。** 理由は「Codex がブロックを解釈しないから」ではなく「**こちらの設定が Codex の読む形になっていないから**」である。`remote-ops.md` §6 と `human-notes/codex/README.md` §5 へ反映済み。追跡は §J `codex-hooks-json-not-dispatched`。

> **★方法論の教訓**: バイナリ実査（イベント名・ブロック文言・ワイヤ形式）と**ペイロードを直接流す実測**は、どちらも「スクリプト側は正しい」ことしか言えない。**「呼ばれるか」は呼ばれる側からしか測れない。** 本プロジェクトが繰り返し記録している「**資料の記述は証拠ではない**」の、実装版にあたる。

**以下は 2026-08-12 午前時点の記録（上記により①②は解決不要になった。③は依然未確認）**（追跡＝`followup-backlog.md` §J `codex-hooks-json-not-dispatched`）:

① **`matcher` に何を書けば shell コマンドに当たるかが不明。** Claude は `Bash` だが Codex のツール名は未確認。**`PreToolUse` は matcher を書かずに登録した**——当たらない matcher は **silent に無効**になるのに対し、両ガードは無関係なら即 exit 0 する設計（`design-desk-guard.sh` はマーカー不在で即 0、`pre-push-guard.sh` は `git push` を含まなければ即 0）なので、全ツール対象でも実害が無い。**「過剰ブロックは可視で直せるが取りこぼしは silent」という §3.6 ② と同じ非対称に倒した。**

② **★既存の `PostToolUse` も同じ疑いがある。** matcher が `"Edit|Write"` のままで、**Codex に `Edit` / `Write` というツール名が存在するかを確認していない**。存在しなければ `post-edit-check.sh` は**一度も発火していない**ことになり、上表の「同期済み」は名目だけだったことになる。**本作業では触っていない**——検証してから決める話であり、便乗で変えると「直したつもり」がもう 1 件増えるため。

③ **Codex は hook を `trusted_hash`（`HookStateToml`）で信頼管理している。** 追加した hook に信頼付与の操作が要るかもしれない。

**確認方法（開発者の Codex セッションが要る。改善担当は Codex を起動できない）**: (a) `git push origin main` を試して `Command blocked by PreToolUse hook:` が出るか (b) ファイル編集後に `post-edit-check.sh` が動くか。

### 8.1 完了報告 §2 のベースライン（2026-08-11 計測・Q6）

**計測規則**（再測時は同じ規則を使うこと）: §2 節の直下にある `###` 見出しの数を件数とする。`###` が無く「なし」と書かれていれば 0 件。どちらでもない場合は表のデータ行数を代替とする。

```bash
for f in $(find docs -path "*design-reports*" -name "*.md" | sort); do
  sec=$(awk '/^## §?2[ .．]/{p=1;next} /^## §?[3-9][ .．]/{p=0} p' "$f")
  [ -z "$sec" ] && continue
  h=$(printf '%s\n' "$sec" | grep -cE '^### ')
  if [ "$h" -gt 0 ]; then c=$h
  elif printf '%s\n' "$sec" | grep -qE '該当なし|\*\*なし|^なし'; then c=0
  else c=$(printf '%s\n' "$sec" | grep -E '^\|' | grep -vcE '^\|[ :|-]+\|?$|^\| *(#|項目|No|条項)')
  fi
  printf '%-58s %3s\n' "$(basename $f)" "$c"
done
```

**結果**: 対象 15 本（§2 節を持つ設計伝達レポート）／合計 **27 件**／平均 **1.8 件**／0 件が **4 本**。
