## 総評

第 1 部（`CO-009`）は指示書が求めた形をほぼ完全に満たしている。第 1 部の完了コミット `0eaabf3` は本番コード 44 ファイル + 新規 3 ファイルのみで、既存テストファイルを 1 本も含んでいない（`git show --numstat 0eaabf3` で確認済み）。「既存テストの期待値を変えていない」は自己申告ではなく diff から機械的に裏が取れる。`query-keys.invalidation.test.ts` は実物の `QueryClient` に種を投入して「ちょうど当たる集合」を表で固定しており、片側だけキーをずらせば構造的に必ず赤くなる形になっている。チェックリスト §8 の重大判定 13 項目のうち 12 項目は問題なしと判定した。

一方で、報告の記述と実出力の食い違いが 1 件ある。完了報告 §11 の `check-doc-inventory.sh` の行が「新種の検出なし」と書かれているが、同スクリプトを実際に回すと `結果: 型に無いファイル 5 件` を出す。5 件はいずれも着手基点 `6c9d8c6` に既に存在しており、製造が回した時点でも同じ出力だったはずである。チェックリスト §8 の「回していない検査の結果を報告へ書いている」に隣接する形であり、重大として扱う。

加えて、本プロジェクトが「高」に置くと定めている「失効した記述がコード上に残っている」型の指摘が 3 件ある。`CharacterSelector.tsx` の件数コメントと `TrashPage` の定数ハードコードへの言及、`DES-005` §5.16 の `USERS_KEY` 参照、および `DES-005` §5.16 が要求する「進捗表示付き、中断耐性あり」が実装で満たされていないのに as-built に記録されていない件である。最後に、重複差分欄が取得失敗時に「違いはありません」と断定する実装上の欠陥を 1 件見つけた。

## 設計準拠性以外の指摘事項

### コーディング規約

1. **import 順の規約違反を新規に約 27 ファイル分増やした。** `CLAUDE.md` §4 TypeScript は「import 順: React → サードパーティ → エイリアスパス（`@/`）→ 相対パス」と定めている。本サブは多くのファイルで `import { queryKeys } from "@/lib/query-keys";` を相対 import の**後**に置いた。例:

   ```ts
   // web/src/features/setup/hooks/useSetup.ts
   import { useQuery } from "@tanstack/react-query";

   import { setupApi } from "../api/setupApi";
   import { queryKeys } from "@/lib/query-keys";   // ← @/ が相対の後
   ```

   実測では、この形の違反ファイル数は着手基点 `6c9d8c6` で 54 件、`HEAD` で 81 件（`import` 行の並びを走査して計測）。既存の乱れが大きい領域ではあるが、1 サブで 50% 増やしたことになる。ESLint の `import/order` が入っていないため機械では止まらない。

2. `PresetEditPage.tsx` に追加した 4 つの文字列（ボタンラベル 2・説明 1・トースト 2）が `t()` を通っていない。ただし同ファイルは着手前から全面的にハードコード日本語であり、英語ロケールの残りは `CO-026` の手番として据え置きが確定している（指示書 §1.6-10）。**規約違反というより既存の債務への追随**であり、単独では欠陥としない。`SettingsSectionData.tsx` 側は正しく `t()` を通している。

3. `settings.data.cacheRebuildDone` が `{{count}}` を使っている。i18next では `count` は複数形の予約キーであり、`_one` / `_other` が無い現状は base key へフォールバックして動くが、将来 `_other` を足した担当が base key を消すと ja 側が壊れる。`presetCount` 等の名前にするのが安全。

### 実装

4. **`RebuildRecipeCache` が所有者検査を落としている。** `authorizeMutation` を通さない判断（組み込みを 403 にしない）は正しく、理由もコメントに書かれている。しかし `authorizeMutation` は「組み込みか」と「自分のプリセットか」の 2 つを見ており（`internal/service/preset/service.go:368-378`）、代わりに使った `service.Get` は利用者スコープを持たない。結果として、任意の利用者が他人のカスタムプリセットに対して再構築を投げられる。再計算は真実（`preset_aliases`）からの冪等な作り直しであり情報漏洩も破壊もないため実害は小さいが、`scope_test.go` が守っている所有権モデルからは外れている。コメントは組み込みの件しか説明しておらず、所有権を落としたことが読めない。

5. **設定画面の一括再構築が部分失敗を扱えない。** `for (const p of presets) await rebuild.mutateAsync(p.id)` は 3 枚目で失敗すると残りを回さず `catch` へ落ち、「失敗しました」のトーストだけを出す。何枚成功したかは利用者にも次の担当にも残らない。`DES-005` §5.16 の「中断耐性あり」はここを指している可能性が高い（高-2 と同じ根）。また `presets.length === 0` のとき `return` するだけで、ボタンは押せるのに何も起きない。
