## 1. 発見 1 — Plan Mode 必須化基準が 2 か所にあり、**1 項目も重なっていなかった**【是正済み】

### 観測

`Plan Mode` の必須化基準を**実体として**持つ文書は 2 つある。

| 文書 | 基準 |
|---|---|
| `CLAUDE.md` §9 | 複雑ロジックを含む指示書 ／ 全体に影響するリファクタリング ／ **スキーマ・API 契約・データ移行を伴う変更** |
| playbook §8.1 | 複数機能の関心が絡む ／ 既存ロジック再利用の整合確認が中心 ／ 設計判断が条件付き ／ バックエンドへの追加変更がある ／ 着手前の確認結果次第で実装範囲が変わる |

**共通項はゼロである。**

### 根拠

- 2026-08-10 に `CLAUDE.md` §9 は是正されている。本文に経緯が残っている——
  「旧版は M0／M1 の全指示書を挙げていたが、両マイルストーンはフェーズ1 完了で終了済みであり、**現行フェーズの判断条件として機能していなかった**」
- **その是正は playbook §8 に届いていない。** §8 は当時のまま。

### 推論

**是正した人が、もう 1 つの基準リストの存在を知らなかった**と考えるのが自然である。
2 か所に実体があること自体はただちに誤りではない——**この 2 つは読み手も時点も違う**からである。

- playbook §8 ＝ **設計担当が指示書ヘッダの `Plan Mode: 任意/推奨/必須` を決める**ときの基準
- `CLAUDE.md` §9 ＝ **製造担当が着手時に自分で判定する**ときの基準

**問題は分業ではなく、両者が互いを参照していなかったこと**である。実際に穴が開いていた——

> **`CLAUDE.md` §9 は「スキーマ・API 契約・データ移行を伴う変更」を必須と定めているが、playbook §8 にこの条件が無い。**
> さらに §8.2「Plan Mode 任意の場合」は「既存パターンの応用が中心」を任意としており、
> **前例踏襲のカラム追加マイグレは §8.2 で「任意」と書けてしまう**。
> **設計担当が「任意」と書いた指示書と、`CLAUDE.md` §9 の「必須」が正面から衝突する。**

### 是正（実施済み）

playbook §8 冒頭に**正本の分担表**を置き、§8.1 の先頭へ `CLAUDE.md` §9 の 3 条件を**最低ライン**として取り込んだ。
§8.2 には **「§9 の 3 条件に触れないことが前提」** と明記した。

**規則の実質は変えていない**——`CLAUDE.md` §9 に既にあった必須条件を、設計担当側からも見えるようにしただけである。

## 2. 発見 2 — §16.4.1 の対処法に従うと、**我々自身の検査が赤になる**【是正済み・機構側の誤り】

### 観測

playbook §16.4.1 は、Markdown テーブルのセル内にパイプを書くときの対処法を明記している。

> GFM はセル分割をインライン解析より先に行うため、**バッククォートでは `\|` を保護できない。`\|` とエスケープする**

**この記述は描画については正しい。** ところが本プロジェクトの機械検査 2 本は、**エスケープを尊重せず raw の `|` で列を数えていた**。

### 根拠（実測）

```
行:  | a | `curl \| bash` | c |
GFM の描画:            3 セル
検査の分割（raw |）:   前後の空を含めて 5 → 実効 4 セル
```

- `scripts/check-stop-discipline.sh` — `local IFS='|'` で `read -ra`
- `scripts/archive-resolved.sh` — `body.split("|")`

**どちらもエスケープを見ていない。**

### 推論

**規則ではなく機構が誤っていた。**
§16.4.1 の指示どおり `\|` と書くと、**描画は直るが検査は赤になる**。書き手は原因を「エスケープが効かない」と誤解し、
**内容のほうを削って回避する**圧力がかかる。これは **§J 停止時記録のような、削ってはいけない記録に対しても働く**。

**本日 2 回再発した**（`curl * \| bash` の行と、grep 正規表現を含む行）。
**同じ間違いを 2 回したのは、原因が書き手ではなく機構にあったから**である。

### 是正（実施済み）

両スクリプトが `\|` を尊重するよう変更し、**陰性対照を self-test へ追加**した。

- `check-stop-discipline.sh` — `\|` を一時退避してから分割し、復元する
- `archive-resolved.sh` — `re.split(r'(?<!\\)\|', body)`
- **エスケープしない生の `|` は引き続き列崩れとして扱う**（描画も壊れるため、これは正しい挙動）。
  `archive-resolved.sh` の陽性対照 `pipe-row` が SKIP のままであることを確認済み

playbook §16.4.1 にも **「機構側が追従していなかった。是正済み」** の注記を入れた（規則の記述自体は変えていない）。

## 5A. 発見 6 — `check-derived-docs.sh --self-test` が「何も検査せず緑を返して」いた【是正済み】

### 観測

監査の検証中に**偶発的に発見**した。全 self-test を回したところ `check-derived-docs.sh` だけが落ちたので調べると——

- 本スクリプトは **`--self-test` を含む引数を一切見ていなかった**
- `--self-test` を渡すと**通常の鮮度レポートを exit 0 で出力**する

### 根拠

`check-artifact-integrity.sh` の ALLOW 表に、理由つきで登録されている——
「判定が git のコミット時刻の大小比較のみで、対照を作っても比較演算子を確かめるだけになる」。
**免除そのものは設計どおりで、機構の穴ではない。**

### 推論

**問題は免除ではなく、免除であることが実行者に見えないことである。**

> `bash scripts/check-derived-docs.sh --self-test` を叩いた人は、
> **整然としたレポートと exit 0 を受け取り、「自己検査が通った」と読む。**
> 実際には**対照は 1 つも走っていない。**

これは本セッションで既に 2 度出た型である——クリーンルームレビュー指摘 **高 1**（self-test の存在確認が冒頭コメントで満たせた）、
および裁定 21 の教訓（**出力があることと、検査が働いたことは別**）。**同じ型が 3 度目に出た。**

### 是正（実施済み）

引数を明示的に検証するようにした。

- `--self-test` → **exit 2** ＋「本検査は自己検査を持たない（意図的な免除）。理由: `--list-allow` を見よ」
- 不明な引数 → **exit 2**
- 引数なし → 従来どおり exit 0

**免除の理由へ誘導する形にした**——黙って拒否すると、次の人が「壊れている」と誤読して不要な self-test を書き足すため。

### 派生した是正

同じ調査で、**引き継ぎ書の常設検査表に `check-derived-docs.sh` が載っておらず「7 本」と書かれていた**（実際は 8 本）ことも判明した。
見出しの **「すべて `--self-test` を持つ」も、免除 1 本がある以上いま正確ではない**。両方を是正した。

> **この表は本日すでに一度是正されている**（「5 本」→「7 本」・`check-enum-sync.sh` が self-test を持たなかった件）。
> **一度直した表が、同じ型でもう一度ずれていた。**
> **本セッションで「資料の記述は証拠ではない」型が出るのは、これで 3 度目**である
> （`environment-reliability-plan` §4.1 の原則が、その原則を実装した当日に 3 回発火した）。
