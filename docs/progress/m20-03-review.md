## 総評

制約そのものの設計・実装は**極めて良い**。鍵に `preset_id` を含む形（`UNIQUE(preset_id, character_id, alias_text)`）が正しく張られ、714 件の無害な重複を巻き込んでいない。破壊テスト (i)(j)(k) は実在し、実行するとエラーメッセージに狙った索引の構成列がそのまま現れることまで確認しており、「張っただけで効いているか分からない」状態を確実に潰している。生成器の 2 本目（`generate.go`）を実査で発見して両方直した判断も的確である（片方だけだと nullable ゆえに静かにすり抜ける）。

一方で、**本サブの外側にある 2 つの機構を壊した／落とした**。① `go run ./cmd/seedgen -check`（「変換規則の無改変ゲート」として全設計伝達レポートが証拠に挙げてきた常設ゲート）が**恒常的に赤になり、しかも自らのエラーメッセージが適用済みマイグレを上書きする操作へ誘導する**。② `docs/progress/progress-log.md` への索引行が**存在しない**にもかかわらず、完了報告が 3 箇所で「追記済み」と書いている。どちらも `go test` では緑のままであり、人が読む以外に見つける経路が無い型である。

なお、チェックリスト §7 の N-1〜N-9 に該当する事象（`(character_id, alias_text)` の 714 件重複／nullable のまま／FK 無し／`DES-003`・`DES-004` 未改訂／フロント無変更 等）は**すべて仕様どおりであり、本報告では指摘していない**。

## 設計準拠性以外の指摘事項

### 高-1 `go run ./cmd/seedgen -check`（変換規則の無改変ゲート）が恒常的に赤になり、CLI のエラーメッセージ・usage コメント・golden テストのコメントが失効した

**実測（本レビューで実行）:**

```
$ go run ./cmd/seedgen -check
DIFF: migrations/000026_seed_moves_first_wave.up.sql は生成物と一致しません
seedgen: 生成物と既存ファイルに差分あり(go run ./cmd/seedgen で再生成)
exit status 1
```

`cmd/seedgen` は `Option` を渡さないため既定の `FormatCurrent` で生成する。既定経路（`-chars` 省略）の出力先は**適用済みの `000026`** に固定されているため、`-check` は今後**常に**差分を報告する。問題は 3 段ある。

1. **ゲートが死んだ。** `-check` は `docs/handover/design-reports/` の 6 本（M14-03d / M14-03e / M19-04 / M19-04b / M19-04c / M19-04d / M19-phase2）が「変換規則の無改変」の証拠として毎回貼ってきた常設ゲートである。以後は誰が回しても赤で、「赤いのが普通」になれば実際のドリフトを検出できなくなる。
2. **エラーメッセージが有害な操作へ誘導する。** 表示される `(go run ./cmd/seedgen で再生成)` に従うと、**適用済みマイグレ `000026` を新形式で上書きする**（指示書 §2.2 と `SUPP-001` §5.5 が禁じる操作）。`generate_test.go:229` の失敗メッセージ ``"%s がコミット済みと不一致。`go run ./cmd/seedgen` で再生成すること"`` も同じ誘導であり、**golden が落ちたときに従うと事態が悪化する**。
3. **「再生成コマンド」の doc コメントが 4 ファイル 6 stem で失効した。** `generate_test.go:240`（000030）／ `generate_m1403d_test.go:37`（000045）／ `generate_m1403e_test.go:38`（000055）／ `generate_m2002_golden_test.go:60,77`（000072/000073）／ `cmd/seedgen/main.go:8-15` の usage。いずれも書かれたコマンドを実行しても**もうそのファイルを再現しない**（`FormatPreM2003` を指定する手段が CLI に無い）。各テストの呼び出し直前には「★旧形式を指定する」注記が足されたが、**コマンド行そのものは旧のまま**であり、後任はコマンド行をコピーする。

**優先度を「高」に置く理由**は本レビューの較正どおりである——動作は正しいままでテスト・lint・型検査はすべて緑になり、人が読む以外に見つける経路が無い。かつ後任は本文（コマンド行）をコピーして注記を読まない。

**完了報告 §5.2 の案比較にこの観点が無い。** 案 A の利点として「`cmd/seedgen`（本番経路）は無改変で新形式になる」と書かれているが、その無改変こそが `-check` を壊している。**検討されていない案が 1 つある**——`cmd/seedgen` 側に形式の口を作ること。

### 低-1 `000075` の down が `DROP INDEX` に `IF EXISTS` を持たない

既存の down 5 本（`000033` / `000036` / `000037` / `000040` / `000049`）はいずれも `DROP INDEX IF EXISTS` で書かれている。本サブだけ素の `DROP INDEX` であり、部分適用状態からの down で止まる。実害は小さいが、リポジトリ内で唯一の書き方になっている。

### 低-2 索引名の接頭辞 `ux_` はリポジトリ初出である

`migrations/` に既存の `CREATE UNIQUE INDEX` は 1 本も無く、非 UNIQUE 索引はすべて `idx_`（例 `idx_preset_aliases_preset_move`）。`ux_` は意味が明確で妥当だが、**どこにも規約として書かれていない**ため次の担当が `idx_` を使って揺れる。as-built を書く `CHANGE-100` の三点セットか `SUPP-001` §5.5 に 1 行残すのが望ましい（設計卓の手番）。

### 低-3 `aliasValueDigest` の `group_concat` は行順に依存する

`group_concat(alias_text_en, '|')` は SQLite が順序を保証しない。値が同じでもスキャン順が変われば digest が変わり、**偽の FAIL**（「値が変わった」と誤報）になりうる。`ORDER BY` を伴う形（例: サブクエリで `ORDER BY id` してから畳む）にしておくと安定する。現状で落ちてはいない。

### 低-4 破壊テストの対象 move 選定が、将来のデータ投入で成立しなくなる

`TestRun_M2003_ConstraintActuallyBites` は「`numeric` のエイリアスをまだ持たない同一キャラの move 2 件」を実データから引く。followup `numeric-aerial-vs-crouching-collision`（通常技全体に `j` を付けて衝突組 35 キーを投入する）や P-34 の 27 件が入ると候補が減る。落ちるときは `t.Fatalf("エイリアス未投入の同一キャラ別 move を 2 件取得できない")` という自己説明的なメッセージになるため実害は限定的だが、**将来ここが落ちても「制約が効かなくなった」ではない**ことを、テストのコメントに 1 行残しておくと次の担当が迷わない。

## 良かった点

1. **破壊テスト (i)(j) の質が高い。** 単に「INSERT が落ちた」ではなく、エラー文字列に `preset_aliases.preset_id, preset_aliases.character_id, preset_aliases.alias_text` と**狙った索引の構成列がそのまま出ている**ことまで実見でき、`strings.Contains(err, "UNIQUE")` で偶発的失敗も排除している。さらに **初回に「既存の `UNIQUE(preset_id, move_id)` が先に発火して区別できなかった」という失敗を完了報告 §6 に残した**のは、`SUPP-001` §5.5.4 (10) の趣旨（「効くか分からない」を潰す）を最もよく体現している。
2. **§3.3-5 の実査で生成器の 2 本目を発見し、両方直した。** 指示書は `generate_m2002.go` しか名指ししていない。`generate.go`（`official_ja_move`）を落としていたら、次のキャラ波で `character_id` が NULL の行が入り、**nullable ゆえにマイグレもテストも緑のまま制約をすり抜けていた**。「等」に逃げず実査した判断が効いている。
3. **マイグレのコメントが次の担当を守っている。** `000075` の「なぜ `preset_id` が鍵に要るのか（ここを読まずに `(character_id, alias_text)` で張ると落ちる）」は、714 の正体・`srk` が機械変換でない理由・逆引きが畳む仕組みまで書いてあり、`CHANGE-100` §2.1-b が設計書へ求めている説明と同じ内容が実装側にも残っている。
