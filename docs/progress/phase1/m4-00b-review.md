### 低（将来対応・記録）

**指摘①: §3.4.2 Plan Mode 合意取扱の表記が不明瞭**

- **該当箇所**: `docs/progress/progress-log.md` M4-00b §3.4 確認結果表
- **状況**: §3.4.2 の判定欄に「単一フィールドのみ・確認不要」と記録されているが、チェックリスト §1.4 が要求する「Plan Mode で開発者の合意を得てから実装に着手したか」が明示的でない。M4-00b 指示書 §3.4.2 では「視覚的 UI 警告の対象が複数フィールドある場合、製造担当が Plan Mode で開発者に確認」と定めており、単一フィールドであったため Plan Mode 不要と判断した経緯は正しい。
- **影響**: 実装の正しさに影響なし。将来の同種指示書でのレビュー担当が判定を誤読する可能性が残る。
- **対応方針**: 今回の修正は不要。次の同種指示書作成時に「単一フィールドのため Plan Mode 確認省略」と明記する慣例にする。

**指摘②: 既存 describe("ModifiersEditor", ...) のテストが console.warn ノイズを発生させる可能性**

- **該当箇所**: `ModifiersEditor.test.tsx` lines 96–111「notes を 50 文字超で入力すると警告色クラスが付与される」
- **状況**: このケースは `"あ".repeat(51)` を入力するため、M4-00b で追加した `useEffect` が `console.warn` を発火させる。しかしこの `describe` ブロックに spy 設定がないため、テスト実行時に実際の `console.warn` が出力される可能性がある。テストのアサーション自体は `border-red` クラスのチェックのみで `console.warn` を検証しないため、テストは通過する。
- **影響**: テスト実行時の console ノイズ。M4-00 の RecipeBuilder 側も同じ状況であり、一貫した扱い。
- **対応方針**: M4-00 が同パターンで承認済みのため今回も不問。将来課題 §8.3「警告ヘルパフック統一」時に全体整理する機会に対処するか、その前に jest/vitest の `--silent` オプションまたは `vitest.config.ts` での console 設定で一括対処する選択肢がある。

## 良かった点

1. **M4-00 との完全な対称性**: useEffect の構造・spy 方式・文言形式・テスト 3 ケース構造がすべて RecipeBuilder 側と一致しており、将来の `useFieldOverflowWarning` 統一作業の前提が整えられた。

2. **NOTES_MAX_LENGTH 定数の再利用**: 指示書例示の `> 50` ではなく既存定数を使用。M4-00 と同様に自発的に規約準拠。

3. **テスト実行時の明示的 clear**: 新規 3 ケースが `await user.clear(textarea)` を明示的に実行してから入力している。textarea の初期値が空であっても clear するのは、将来的に初期値がある step を使うように変更された際のテスト脆弱性を防ぐ防御的な書き方。

4. **隠れ P-01 清算の記録**: progress-log に「M2-04 設計担当ミスの双子事例 → M3-05 での見落とし → M4-00 起票時確認漏れ → M4-00b で双子清算」という連鎖の経緯が明記されており、retrospective-log §1 パターン A の追跡に資する記録になっている。
