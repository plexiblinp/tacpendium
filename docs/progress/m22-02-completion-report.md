## 2. ★既存データの `user_id` の実測値（followup `research-db-dependent-items-m22` を閉じる根拠）

**測定対象**: `make e2e` が作った使い捨て DB（`web/e2e/.tmp/combomgr-e2e.db`）。**マイグレーションを全適用した直後の状態＋E2E が作ったコンボ 1 件**である。

```
users の行数: 1
  users[1] = "default"
tags.user_id の分布:
  user_id=1: 3 件
presets.user_id の分布:
  user_id=NULL(組み込み): 3 件
combo_tags の行数:
  1 件
```

- **`users` は 1 行**（`id=1`, `name='default'`。`migrations/000007` が `INSERT OR IGNORE` で投入）
- **`tags` は 3 行すべて `user_id = 1`**（`使用中` / `練習中` / `頻度低下`。同マイグレ）
- **`presets` は 3 行すべて `user_id IS NULL`**＝**組み込み**（`migrations/000005` ＋ `000069` の整理後）。**⇒ 「既存のプリセットはすべて `user_id = 1` に紐づいている」という指示書 §4.5-3 の前提は、実測では成り立たない。** 組み込みプリセットは所有者を持たないため、**2 人目でも編集不可なのは「組み込みだから」であって「他人のものだから」ではない**（`VAL-P01` と `VAL-P07` の別）。他人のカスタムプリセットは、2 人目が作って初めて発生する

> **★測定環境の限界**: 本環境（クラウド実行）には長期運用された開発 DB が存在しない。上記は**新規インストール直後の確定値**であり、開発者の手元 DB に**利用者が作ったカスタムプリセットやタグがあれば `user_id = 1` に紐づく**（そこへ書ける経路が `defaultUserID = 1` しか無かったため）。**⇒ 分布の形（すべて 1 人目に集中）は確実であり、件数だけが環境依存である。**

## 4. ★選ばれていないときの `userID` の既定（§4.5-4 / §9.1-2）

**採った案: `X-User-Id` ヘッダが無い・壊れている場合は `users.id` の最小値へ倒す。**

- 実装: `internal/api/middleware/user.go` の `resolveUserID` → `usersvc.DefaultUserID`（`SELECT MIN(id) FROM users`）
- **理由**: ヘッダを送らない呼び出し元が実在する——**既存の E2E・`curl`・利用者が 1 人で選択画面を出さない場合**。既定へ倒すことで**いままでの挙動と 1 バイトも変わらない**（既存環境の `users` は `id=1` の 1 行のみ＝上記 §2 の実測）
- **解決に失敗しても要求は止めない**（`0` のまま下流へ渡す）。ここで 500 にすると、利用者の面と無関係な全 API が巻き添えで落ちるため
- フロント側は、利用者が 1 人なら**選択画面を出さずに自動選択して送る**（`FR502`）

## 5. 401 を捕まえた場所（§4.3-2）

**`web/src/lib/http-interceptor.ts`。`window.fetch` を 1 度だけ包み、`main.tsx` で render 前に設置する。**

**★なぜ fetch を包んだか**——API 呼び出しが `lib/api-client.ts` の `fetchJSON` へ**一本化されていない**ためである。実測で次の 3 系統が併存する。

1. `fetchJSON`（`Error("HTTP 401: <生ボディ>")` を投げる）
2. `features/tag/api/tagApi.ts` の独自 `request`（`TagApiError` に `.status` を持つ）
3. `features/combo/api.ts` ほかの素の `fetch`（8 か所）

**⇒ 「401 の判断を 1 か所に置く」（`E-76`）を実際に成立させられる層はここだけである。** 同ラッパが `X-User-Id` の付与も担う（同じ理由で、付与も 1 か所になる）。

- **`/api/auth/*` は除外**（§4.3-4）。ログイン失敗の 401 を巻き込むと入力欄が消える
- **応答は改変しない**。`status` も本文も素通しし、副作用は購読者への通知だけ
- **新しいリクエストを一切発行しない**（§4.2-2 の「余計な問い合わせを増やさない」）

**併せて `QueryClient` に 401 の再試行抑止を入れた**（`isUnauthorizedError`）。既定の 3 回再試行は 401 では空転になり、M22-01 の E2E が実測した約 7 秒の待ちの原因だった。

## 13. ★履歴操作（戻る・進む・更新）の実測（§4.8）

**採った形: ログイン画面・ユーザー選択画面とも URL を持たせず、条件表示（オーバーレイ）にした。**

**理由**——`CHANGE-113` §7-1 の案 (α)〔選んだ利用者は保持しない〕を満たすには、選択を**メモリ上の React state だけ**で持つ必要がある（Cookie・ブラウザストレージ・サーバセッションはいずれも再読込を跨いでしまう）。一方 URL を持たせると、戻る・進むで「済んだ画面」へ戻り §4.8-5 に反する。**⇒ 条件表示なら §4.8-3 と §4.8-5 が同時に成立する。**

| 操作 | パスワードの面 | 利用者の面 |
|---|---|---|
| **更新（リロード）** | **入り直しにならない**（Cookie が残り、実体はサーバのメモリ） | **★選択が消えて選択画面へ戻る**（保持しないため） |
| **戻る** | ログイン画面は出ない | 選択画面は出ない |
| **進む** | 同上 | 同上 |
| **パスワード変更の直後** | **入り直しになる**（全セッション破棄＝`DES-002` §8.1 の 14）。案内文で説明が付く | — |

**★利用者の選択が消えることは仕様である**（`CHANGE-113` §7-1 の案 (α)＝`D-401`）。**欠陥として報告しないこと。**

E2E で固定済み: `m22-02-login-and-user-select.spec.ts` の「通ったあと画面を更新しても入り直しにならない」「入場済みなら戻る・進むでログイン画面へ戻らない」「画面を更新すると選択画面へ戻る(保持しない)」「選択済みなら戻る・進むで選択画面へ戻らない」。
