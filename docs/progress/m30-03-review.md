本サブで A2 は必殺技タブへ移り、未分類に残る `special` は 0 件になった。この注記は未分類タブの `TabsTrigger` に付いており、次に未分類タブを触る担当が最初に読む位置にある。完了報告 §3.1 は「実装が変わったのに記述が旧のまま残る形を、この手番で全数直した」と書いているが、成り立っていない。

同じ注記の後半（`jamie 2 / mai 1 / blanka 2 / manon 0`）は E2E の実測どおりで有効なので、書き換えるのは前半のみ。

### 2. `parseSpecialCode` の戻り値型から `| null` を外した判断について

判断そのものは妥当と評価する。`isOnSpecialTab` に常に真の枝を残すのは「まだ何かを弾いている」という誤読を生むという理由は正しく、波及も呼び出し側 2 か所に閉じている。型で `null` を潰したため、将来 `parseSpecialCode` が `null` を返す形に戻せば `deriveSpecialFamilies` 側が型エラーで止まる。

ただし副作用が 1 つある。`isOnSpecialTab` と `deriveSpecialFamilies` が**同じ述語を共有しなくなった**（前者は `category` だけ、後者は `parseSpecialCode` の全域性を前提）。両者がずれても型検査は通る。この結合は `moveSurfacing.test.ts:209` の「述語が `deriveSpecialFamilies` と一致する」で見ているが、そちらは合成 `MOVES`（`special` 数件）に対してのみ動く。実データ規模で結合を守っているのは roster テストの座標一致（`slots == specials`）であり、**そちらが実質的な要である**。コメントは `moveSurfacing.test.ts` を参照しているが、実データを守っているのは roster 側であることを明記しておくほうが安全である。

なお `isOnSpecialTab(move: Move)` は引数 `move` の `category` しか見なくなったため、関数としては `move.category === "special"` の別名になっている。残す判断には賛成する（呼び出し側の意味が読める）が、恒真化したテストを生んだ原因でもある（高-2 参照）。

### 3. テストのフィクスチャ差し替えについて

`german_suplex`（区分 E の投げ）への差し替えは妥当。「省かれてはならない側の代表」という役は維持されており、主張は弱まっていない。`RecipeBuilder.test.tsx` / `SetupRecipeEditor.test.tsx` / `VirtualController.test.tsx` の 3 本とも、差し替えの理由がコメントで説明されている。

`moveSurfacing.test.ts` の「★状態 code を渡すと、その技は未分類へ落ちない」で**合成 code `flame_air_throw` を使った判断**については、主張自体は弱まっていない（状態 code の語幹一致で未分類から外れる、という検査対象はそのまま）。ただしこの差し替えが露わにした事実のほうが重要である。完了報告の注記によれば、M30-03 後の実 seed には「未分類に残り、かつ状態 code を含む」行が 1 件も無い。つまり **2026-09-08 の開発者判断（案 C・固有状態タブを掲載済みに数える）は、現行データに対して効果を持つ行が 0 件になった**。これは設計判断の前提の変化であり、合成フィクスチャの採否より上の論点である。設計卓へ回すべき（中-4 に含める）。

### 4. コメントに埋めた実測値の一部がどのテストにも固定されていない

`inputResolution.ts` のコメントにある `moves` テーブル 3026 行 / 31 キャラ、強度語 2 つ以上が 15 件、うち末尾にも持つのが 12 件、規則 2 で決まるのが 3 件は、いずれもテストで固定されていない。データが動けば静かに陳腐化する。`SUPP-001` §5.5.3.2 の趣旨（実測値の置き場を契約テストの 1 か所へ寄せる）に照らすと、少なくとも「15 / 12 / 3」は roster テストで数えて主張するか、コメントから落とすかのどちらかが望ましい。

### 5. 軽微な数値の不整合

`SpecialMovePanel.tsx:170` は「着手時点では強度接尾辞を持たない 186 件が」と書いているが、`inputResolution.ts` は同じ母集団を 187 件と書くようになった。前者は M30-02 着手時点の歴史的記述として読めば誤りではないが、同一リポジトリ内で 186 と 187 が並ぶことになるため、片方に時点を明記すると読み違いが減る。

## 推奨修正（優先度別）

### 高（M30 完了前に修正必須）

**高-1. `VirtualController.tsx:292-298` の失効した注記を書き直す。**

「いま残る special は A2 だけである（seed 実測 105/144）。⇒ M30-03 の射程である」は撤回済みの記述。本番ファイルであり、未分類タブの定義を読む担当が最初に当たる位置にある。動作は正しいままなのでテストも lint も型検査も緑であり、人が読む以外に見つける経路が無い。あわせて完了報告 §3.1 の「全数直した」を訂正すること。

**高-2. 「素は押せるが OD が押せない 7 組 → 0 件」のテストが恒真になっている。主張の取り方を変える。**

対象は `web/src/features/combo/moveSurfacing.roster.test.ts` の同名テスト（245〜281 行）。`found.push` に到達する条件は `!isOnSpecialTab(sibling)` であり、本サブで `isOnSpecialTab` は `move.category === "special"` になった。`sibling` は同一キャラの `moves` から code 一致で引いた行であるから、`sibling.category !== "special"` にならない限り `found` は空になる。

レビュー側で CSV 全 31 キャラを走査して確認した実測は次のとおり。

- 内側の兄弟判定に到達する組: **102 組**
- そのうち `category !== 'special'` の兄弟: **0 組**

つまり `expect(found.sort()).toEqual([])` は、`parseSpecialCode` の実装が何であっても成立する。`parseSpecialCode` を着手時点へ巻き戻しても（`deriveSpecialFamilies` 側が A2 を落とし、7 組が再びファミリー UI から消えても）このテストは緑のままである。チェックリスト A-3 が名指しした「テストの期待値を 0 件へ書き換えるだけでも緑になる」より一段悪く、**式そのものが赤になれない形**になっている。

破壊確認が 2 本（規則 1/2 の順序入れ替え・強度語を全数抜く）で止まっており、そのどちらもこのテストを対象にしていないため、恒真化が検出されなかった。

直し方の提案（実装は製造の裁量）。

- 判定を `isOnSpecialTab` ではなく `deriveSpecialFamilies` の座標に置く。素と OD の 2 つの `move.id` が**同じファミリーの別々の強度として在ること**を主張すれば、A2 の取り込みが効いている場合にだけ緑になる。
- あわせて束 A-2 に応えるため、7 組の code を名指しで残し、7 組それぞれについて上記を主張する。集約 0 件だけにしない。
- 直した後、`parseSpecialCode` の規則 2 を一時的に外して**赤になること**を確認する（破壊確認 C として完了報告 §4.2 へ追記）。

**高-3.（高-2 の付随）恒真化した他の主張を仕分ける。**

同じ理由で、次の 3 つも「実装が効いていること」ではなく「`isOnSpecialTab` が category だけを見ること」を測る形になっている。

- roster テスト「★★special は 1 件も未分類に残らない」の `leftover` が空であること
- 同「未分類の内訳」の `expect(byCategory.special).toBeUndefined()`
- 同 キャラ別未分類件数の `special` 寄与分

これらは座標一致テスト（`slots == specials`）が実データ規模で裏を取っているため**主張が丸ごと無価値なわけではない**。ただし「A2 が載ったから 0 になった」と読める注記が付いているので、注記を「述語が category だけを見るようになったので構造上 0 である。A2 が実際にファミリーへ載ったことは座標一致テストと `parseSpecialCode` の単体テストが持つ」と直すこと。高-1 と同種の「実装が変わったのに記述が旧のまま」に当たるため 高 に置く。
