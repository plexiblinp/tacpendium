## 設計準拠性以外の指摘事項

### 依頼された 2 つの判断についての見解

**(1) ポート証跡が無効だったという自己申告の扱いは妥当か。妥当である。**

`ss` が本環境に存在せず `grep` が常に空振りして「OK: 空き」と誤答していた、という自己申告は、証跡の性格を正しく評価している。チェックリスト 3-2 の趣旨は「汚染された実測は実測が無いより悪い」であり、無効を無効と宣言して主張を取り下げたのは、その趣旨に沿う唯一の正しい振る舞いである。文字どおりに読めば 3-2 は「高」だが、本レビューは以下の理由で「中」に置く。

- 影響を受けるのは実測 1・2 のみで、いずれも全緑であり結論の荷重を担っていない。結論の根拠である実測 4・破壊確認・5 回連続実行の証跡は是正後で有効である。
- 是正が「差し替えた」で終わらず、listener を実際に立てて検知できることの対照実験まで行われている(D-375 の型)。
- 構造的な緩和が 1 つある。`web/playwright.config.ts:112,124` は両サーバとも `reuseExistingServer: false` であり、ポートが埋まっていれば Playwright 自身が明示エラーで落ちる。つまり「他プロセスがポートを占有していたのに気付かず偽の緑が出る」経路は設定上ふさがれている。報告はこの緩和材料を挙げていない。挙げれば、無効な証跡が残す残リスクの上限を読み手が判断できる。

**(2) 本番コードのバグを直さず報告のみとした判断は妥当か。妥当である。かつ、バグの診断はレビュー側でも裏が取れた。**

- `internal/service/combo/service.go:253-279` で、`ValidateComboForCreate`(VAL-C02 を含む)は `s.db.BeginTx` の呼び出しより前に実行されている。判定と INSERT は同一トランザクションに入っていない。
- `migrations/` 全体の `UNIQUE` 制約を走査したが、6 項識別キー(`character_id` / `starter_move_id` / `position` / `opponent_stance` / `hit_type` / `opponent_size`)に対する一意制約は存在しない(存在するのは `combo_steps` / `combo_oki_options` / `combo_punishes` 等の別キー)。DB 側の最後の砦も無い。
- したがって check-then-act の競合は実在し、報告の機序は推定ではなく構造から読み取れる事実である。
- §2.3 の 3 条件のうち条件 2(DES-002 §4.2 の経路表に載る API の挙動に該当しない)が `POST /api/combos` で成立しないため、直さず報告するのが指示書の定めどおりである。条件 3(1 ファイル数行)も、正しい修正がトランザクション境界の移動または一意インデックスの追加である以上、満たさない可能性が高い。判断は正しい。

### 高(M24 完了前に修正必須)

**H-1. `web/playwright.config.ts:63-64` のコメントが、完了報告 §10.1 で撤回した主張を事実として書いている。**

4 つ挙げられた資源のうち、完了報告で裏が取れているのは 1 つもない。

修正案: 実測で裏が取れているものだけに絞る。たとえば「本サブの probe が構成した識別キー(決定論的に再現)」と「プリセット総数(M20-05 の実測。followup `e2e-shared-global-resource-parallel`)」の 2 つに限定し、出所を添える。撤回済みの「既定プリセット」と未測定の「相手技のフレームデータ」は削る。

**H-2. 決定論 spec の 10 回実測が `retries` いくつで取られたかが報告に無く、既定の `make e2e` 経路で回帰を検出できるかが未確認である。**

- 報告で `retries` の値が明示されているのは §9 の再現手順だけで、そこは `--retries=0` である。§2.6 の 10 回、§4 の 10 回ずつ、§5 の破壊確認 1・2 については `retries` の記載が無い。
- 一方、`make e2e` は `pnpm e2e` = `playwright test` であり(`web/package.json:13`)、`web/playwright.config.ts:78` の `retries: 1` がそのまま効く。
- `workers: 1` を誰かが外した場合、probe は 1 回目に落ちても retry で通れば `flaky` として扱われ、スイートの終了コードは 0 になる。つまり緑で通過する。
- ところが `web/playwright.config.ts:70-72` は「外すと何が起きるかは probe が決定論的に示す」「本行を消す変更は、その 2 本が赤くなることで検出される」と断言している。この断言は `retries: 0` でしか保証されていない可能性がある。

これは H-1 と同じ型(コード上の記述が実測条件を超えて書かれている)であり、かつ本サブの成果物である回帰検出の仕組みそのものの成否に関わるため「高」に置く。
