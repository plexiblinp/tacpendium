**8 要素中 6 が明確な置き場を持つ。** 本プロジェクトのテンプレートは、監査タスク B が想定した水準を**おおむね既に満たしている**。

**★想定を超えていた点**: **§4.5 否定形確認**（撤回した仕様の残骸を 3 系統＝本番コード／テスト資産／設計文書へ全文走査する）は、
タスク B の 8 要素には無い項目である。「Must preserve」の裏返しとして、**撤回した定義が資産に残る**という本プロジェクト固有の
劣化パターン（D-250）に対する機構であり、8 要素より一段進んでいる。

### 2.2 △ の中身

**(a) In scope に独立節が無い。** §2.1 は「作成/修正するファイル」であり、**ファイルの列挙は範囲の宣言ではない**。
「何ができるようになるか」の範囲（例: この API はどの呼び出し元まで面倒を見るか）は §4 詳細仕様に溶けている。
実害の確認はできなかった（19 本を読んだ範囲でスコープ逸脱の記録は無い）ため、**優先度は低い**。

**(b) Contracts が種別を列挙していない。** タスク B が挙げる契約は 7 種
（DTO・API・DB・式・互換性・エラー・VAL 参照）だが、§4 の記入指針が名指ししているのは **「式」だけ**である
（「恒等式・成立条件・計算規則は、散文でなく『式』で固定する」）。
残る 6 種は「DTO/構造体/SQL には対応 DES 節を引用」という一文に畳まれており、**互換性・エラー・VAL 参照は名指しされていない**。

**⇒ ただしこれを「欠落」と断ずるには証拠が足りない。** 実物 19 本ではエラーコード・VAL 参照は必要な回で書かれている
（例: `M19-06` は 400 のエラーコード割り当てを §3-3 で表にしている）。**指針が無くても書けている**なら、
チェックリスト化の効果は「抜けたときに気づける」ことに限られる。§5 の提案では優先度を中に置いた。

### 3.1 実測（19 本横断）

**⇒ 削減対象は総じて小さい。** タスク B が想定した「推測で書かれた実装詳細で膨らんだ指示書」は、

### 3.2 ★行番号: 一律削除ではなく「識別子との併記」が答えである

**M19-04d の 14 件を実際に引いて確かめた。**

| 引用 | 指示書が主張した対象 | 現物 | 判定 |

**★失効の機序が特定できた。** 指示書 `M19-04d`（`9cb04af`・2026-08-03）が引用したのは、
**そのサブ自身が編集対象とするテストファイル**である。同日の実装コミット（`d14bdc8` / `fd23354`）が同ファイルを書き換え、
`expectedMovesDelta` は **M19-04d 自身が削除した**（現物のコメント `migrate_m1403c_test.go:176` が「★expectedMovesDelta と
parseSnapshot は M19-04d で削除した」と記録している）。

**⇒ 行番号は「そのサブが変更するファイル」を指しているとき、そのサブの完了と同時に失効する。**
外れ方も小さい（61 vs 75・324 vs 334）＝行の挿入でずれた形であり、誤記ではない。

**★しかし実害は出ていない。** 14 件すべてに **識別子（テスト関数名・定数名）が併記されている**ため、
行番号がずれても参照は復元できる。実際 M19-04d は完走している。

**⇒ 提案は「行番号を削減対象にする」ではなく「識別子との併記を必須にする」である**（§5 B-1）。
併記のある行番号は**初回到達を速くする補助**であり、害は識別子が吸収している。**単独の行番号だけが危険**である。

### 3.3 固定件数: hedge が効いている

**実害の実例は 1 件確認できた。** `M19-05` §4.2-2 が「63 行」を置き、**裁定 §4 で「実測値 76 行で固定」へ読み替えられた**
（`docs/handover/design-reports/20260809-m19-05-design-exceptions.md` §0 の読み替え表）。

**ただし指示書側の書き方は正しかった。** 同書 §4.2 の該当箇所は「Phase 2 で 63 対／子 37 行 ＋ 既存 9 行の**見込み**。
**実測値を報告**」と書いており、**確定値でなく見込みであることと、実測して報告することの両方を指示している**。
裁定はその報告を受けて固定値を確定させた——**設計どおりに機能した経路**である。

**⇒ 固定件数それ自体は削減対象ではない。** 危険なのは「見込み」と明示せず、実測の指示も無い固定値である。

### 3.4 保持対象は保持されている

タスク B が「削らない」とした式・DTO・エラーコード・非破壊条件・受入契約は、いずれも実物に存在する。
特に**式**は §4 の記入指針が最重要事項として扱っており、その根拠（`G = 1 − N` の実例で、
**式だったから製造が反証でき、設計側の誤りに到達できた**）まで書かれている。**この節は削らないこと。**

## 4. B3: 探索モード — ★前提が成立していない

### 4.1 観測

タスク B3 は「探索モードのテンプレートに 6 要素が揃っているか」を問うが、
**本プロジェクトに探索モードは存在しない。** RESEARCH テンプレートは **read-only の調査モード**であり、別物である。

| B3 の要素 | RESEARCH テンプレートの在否 |
|---|---|
| 目的仮説 | **✗**（「仮説」の語は 0 件。§1.2 は「目的」であって仮説ではない） |
| 明らかにしたい問い | **△**（§4「調査項目」が実質これに当たる。語としては無い） |
| タイムボックス／停止条件 | **✗**（0 件） |
| 触ってよい範囲 | ✅（§0.2 read-only 厳守。ただし「**何も触らない**」であり探索の「触ってよい範囲」とは意味が逆） |
| 本番・main へ入れない条件 | **✗**（0 件。read-only ゆえ成果物が無く、条件を書く必要が生じない） |
| 持ち帰る成果 | **△**（§5 報告様式はあるが、「破棄可能な試作」「次の正式指示書案」は無い） |

**⇒ 3 件が 0 なのは欠落ではなく、測っている対象が違う。**

### 4.2 ★しかし探索モードは実務で必要になり、その場で手書きされている

**`M19-RESEARCH-01`（セットプレイ自動提案エンジンの実体確定と出力品質 PoC）が、§0.2 で read-only を明示的に拡張している。**

- 種別欄が「**調査指示書 + PoC デモ**」
- §0.2 の見出しが「**read-only の範囲（PoC 実行を含むよう明確化）**」
- 許可: 「**一時的な PoC ハーネスの作成**（`/tmp` 配下など**リポ外の使い捨て領域**に限る。エンジンへ入力を渡し出力を集めるだけの薄いドライバ）」
- 禁止: 「本体 DB 原本への**書き込み**（INSERT/UPDATE/DELETE/マイグレ適用）」
- §0.1: 「**本実装（エンジンの本体統合・提案 UI・保存導線）は本調査の対象外**で、PoC 品質確認後に**別指示書**（M19-01）で扱う」

**これは事実上の探索モード定義であり、B3 の 6 要素のうち「触ってよい範囲」「本番へ入れない条件」「次の正式指示書へ渡す移行条件」の 3 つを満たしている。**

**★ただし再利用されていない。** 後続の `M19-RESEARCH-02` / `-03` / `-04` はいずれも純 read-only に戻っており、
**テンプレートにも昇格していない**。次に PoC が要るとき、設計担当は同じ判断をゼロから書き直すことになる。

- **個別指示書 19 本への修正提案** — **採らない**。D-274 (3) により完了済み指示書の本文は書き換えないため（§1）。

## 6. 設計担当への申し送り
