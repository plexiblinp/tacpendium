### 高-1. `RecipeInputContext` の doc コメントが実装と食い違っている（失効記述）

`web/src/features/combo/moveSurfacing.ts` の型 doc:

```

 *   既定を "combo" にすると新しいセットプレイの面が静かに減り、"setup" にするとコンボ側へ漏れる。

```

同じファイルの `surfaceBuckets` は `context: RecipeInputContext = "combo"` を持つ。すなわち**このコメントが「事故を作る」と名指しした既定が、同じファイルに実在する**。`surfaceBuckets` 側には「テストの呼び出しの都合」という注記が別に在るが、型 doc の断定はそのまま残っている。後任は型の doc を規約として読むため、片方が偽であることに気づかない。

実害の形も具体的である。`moveSurfacing.roster.test.ts` は `surfaceBuckets` を 6 か所で既定に頼って呼んでおり、将来セットプレイ側の面を追加する呼び元が既定へ落ちると、その面から `setup_only` が静かに消える（本サブ最大の事故の形そのもの）。

推奨: 型 doc を「既定を持つのは `surfaceBuckets` だけであり、それは `M30-05` との衝突回避のための暫定である」と実物に合わせて書き直すこと。あわせて `M30-05` のマージ後に既定を外す手番を `followup-backlog.md` §J へ 1 行残すこと（本サブの射程内で既定を外すと共有テスト 6 か所を書き換えることになり、並列上の判断としては現状維持が妥当である）。

### 高-2. `isControllerSurfaced` の母集団が 2 種類あり、フェーズ5 で等式が静かに崩れる

| 呼び元 | 走査対象 | 第 2 引数（母集団） | `normalIds` の材料 |
|---|---|---|---|
| `surfaceBuckets` | `inputMoves` | **`inputMoves`** | **`inputMoves`** |
| `useControllerInputOmission` | `selectableMoves` | **`moves`（生）** | **`moves`（生）** |

`selectableMoves` と `inputMoves` は同じ式で作られており（同じ `moves` と同じ `context`）、走査対象は揃っている。揃っていないのは**判定材料**である。完了報告 §2.5 は「掲載可否の判定材料であって、省く対象ではない」と理由を書いているが、この理由は `surfaceBuckets` 側には適用されていない。同じ述語を「裏返し 1 本」で共有するという `moveSurfacing.ts` ヘッダの前提、`CHANGE-176` §2.5 の等式、`DES-005` §6 の記述は、この不一致を許さない。

崩れる具体例（フェーズ5 でフラグが立った直後に起きうる形）:

- 段階2 の解決表 `entries` が、あるトークン（例 `6MP`）を `setup_only` の技へ割り当てている。
- `surfaceBuckets`（コンボ側）: その技は `inputMoves` に居ないため `resolveDirectionalInput` が段階1 へフォールバックし、**別の通常技 N** が解決される。⇒ `N` は通常技タブから押せる状態になり、未分類には落ちない。
- `useControllerInputOmission`: `normalTabMoveIds(moves)` は生の母集団で解決するため `entries` 側が当たり、`N` は `normalIds` に入らない。⇒ `N` は「どの面からも押せない技」と判定され、**押せるのにトグル ON で残り、`omittedCount` も 1 件ずれる**。

同型の崩れは `isOnUniqueTab` のラッシュ元引きでも起きる（元技が除外され、`rush_<元技code>` が残る組）。なお `InsertRushVariant` は `src.SetupOnly` を複写するため、API 経由で生成されたラッシュ行については同じフラグが伝播する。したがって当面の再現経路は `entries` 側が主である。

いずれも `setup_only` の実データが 0 件のうちは再現せず、型検査もテストも緑のまま通る。本サブが「経路だけを先に作る」サブであり、フェーズ5 でこの経路が再レビューされる保証が無いことを踏まえ、**高**に置く。

推奨: `useControllerInputOmission` の `isControllerSurfaced` / `normalTabMoveIds` へ `selectableMoves` を渡し、2 つの面で同じ材料を使うこと。あわせて「プルダウンが省く集合 ＝ 当該面の未分類タブ」を 1 本のテストで固定すること（現状、この等式を実データ以外で固定しているテストは無い）。別案として「生の `moves` を使うのが正しい」と判断するなら、`surfaceBuckets` 側も生の `moves` を渡して揃えたうえで、その理由をコメントに残すこと。**揃っていないことが問題であり、どちらへ揃えるかは製造の裁量で構わない。**

### 中-2. 母集団を絞ったことの副作用が 2 件、どこにも記録されていない
