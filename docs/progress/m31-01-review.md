## 総評

中心の 2 件は、いずれも指示書が要求した水準で処理されている。`materialize` の穴は tx の内側・INSERT の直前で `ValidateRequiredForPublished` を通す形で塞がれ、陽性対照（必須 4 欄が空の本登録**基底**は現に作れる）と是正（そこから生成すると 400・行は 0 件）が別テストで対になっている。`SD-006` の連動を入れても `VAL-C11` が実質死んでいないという結論も、本レビューで実装を追って裏づけられた——連動は `on && !spec.usesDr` のときだけ対を足すため、ドライブラッシュ版のボタンを先に押せば「DR のみ」が 1 クリックで作れる。BE 側 3 経路（既存行・CSV 取込の独立実装・API 直叩き）も実在を確認した。

一方で、**「歯止め」の主張は実測と食い違う**。`m31_01_c11_population_test.go` はモデルを直接組んで BE の検証を呼ぶだけであり、FE の連動を双方向にしても 1 件も赤くならない。実際に赤くなるのは `ComboEditorBasicFields.test.tsx` の「★SD-006 (b)」である。チェックリスト §0.2 が最も警戒する地点で、存在しない安全網が宣言されている。

もう 1 つの大きな穴は**設計書への請求漏れ**である。本サブは API 契約に 2 か所触れている（materialize が `400 validation_failed` を返すようになった ／ `DELETE /api/setups/{id}` に `unlinkFrom` を足した）が、完了報告 §9.1 の CHANGE 請求 3 件はどちらも含んでいない。`DES-002` §4.2 に 4 行、`DES-005` に 2 行、コード内コメントに 2 行、**撤回済みの記述が残る**。

加えて、`materialize` の 400 が画面に届いていない。`onError` が `e.message` を捨てて「生成に失敗しました」とだけ出すため、4 欄のどれが空なのかが利用者に一切伝わらない。開発者実測（本登録 83 件中 68 件が必須 4 欄のいずれかを空にしている＝`D-724`）に照らすと、これは稀な経路ではなく既定の経路になる。

機械検査は `check-import-order.sh` が **NG**（新規テストファイルが 1 件増やした）。完了報告 §8-4 は「違反なし・増加なし」と書いており、実測と食い違う。

## 設計準拠性以外の指摘事項

### 1. `materialize` の 400 が画面に届かない（**高**）

`web/src/features/punish/components/PunishTree.tsx:206` と `web/src/features/punish/components/PunishList.tsx:140` は同じ形である。

```ts
onError: () => toast.error("パニッシュカウンター版の生成に失敗しました"),
```

`fetchJSON`（`web/src/lib/api-client.ts:14`）は `HTTP 400: <body>` を `Error.message` に載せるが、両方の `onError` が引数を取らずに捨てている。⇒ **`details.validations` に載っている「どの欄が空か」が利用者に一切伝わらない。**

同じファイル内の他のミューテーションは `onError: (e) => toast.error(\`非表示に失敗しました: ${e.message}\`)`（`PunishList.tsx:265` / `288`）と `e.message` を出しており、**materialize だけが情報を捨てている**。

これが重い理由は母集団である。完了報告 §2.6 が引く `D-724` の実測は「既存の本登録 83 件のうち 68 件が必須 4 欄のいずれかを空にしている」。⇒ 探す画面／マイリストから変換を押す基底コンボの多くがこの経路に入る。着手前は成功していた操作が、**原因の分からない失敗**に変わる。

完了報告 §3.3 は「400 で弾かれる」とだけ書き、画面側の帰結を書いていない。指示書 §5-2 の「『弾かれる』なら、それでよいのかを報告に書くこと」は、利用者から見た形まで含めて答えるべき問いである。
