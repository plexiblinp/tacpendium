## 総評

9 項目のうち 8 件が実装され、実査 15 件は母数付きで報告され、指示書・ledger との食い違い 4 件が別掲されている。破壊確認 2 の予測外れを隠さず記録し、観測できる経路（`VAL-C03` 警告で画面に留まる分岐）へテストを作り直した点、flaky を retry で流さず根治した点は、この工程で望まれる仕事そのものである。ラベル 4 通りの一元化・`SM-112` の旧称リテラル全数の定数化も、レビュー側の grep で残存 0 を確認できた。

一方で、**離脱ガードの土台（履歴に積む「番人」エントリ）の後始末が無く、`navigate(-1)` を使う離脱経路が「離れない」状態になっている**。これは `ComboEditor` の「キャンセル」と `SetupEditorPage` の保存後遷移の両方に効く。さらに **`SetupEditorPage` は保存成功で dirty を落としておらず**（チェックリスト 1-4 / §8-3）、**下部の「キャンセル」ボタンが `requestLeave` を通っていない**（CO-003 の穴）。いずれも既存 E2E がその経路を踏んでいないため、`198 passed` と両立する。

加えて、タブへのエラー振り分けが完全一致集合であるため、**バックエンドが `steps[N].moveId` で返す ERROR（`VAL-C12`）が「基本情報」タブに計上される**。「エラーがどのタブに在るか分かること」は指示書が落とせない条件としたものであり、誤ったタブを指す形は穴として残っている。

## 設計準拠性以外の指摘事項

### 重大-1. `SetupEditorPage` は保存成功で dirty を落としておらず、編集モードの保存で画面から離れない

**何が**: セットプレイ編集（`/setups/:setupId`）で内容を変えて「保存」を押したあと、画面から離れられず、代わりに「保存していない変更があります」が出る見込みである。

**どの根拠で**:
- `web/src/pages/SetupEditorPage.tsx` で `setDirtyBaseline` を呼ぶのは `:73`（初期化）と `:89`（読込時 hydrate）の 2 か所だけである（`grep -n "setDirtyBaseline" web/src/pages/SetupEditorPage.tsx` → `73` / `89` の 2 行のみ）。**保存成功のハンドラ `:215 onSuccess: () => navigate(-1)` は dirty を落としていない。**
- 一方 `ComboEditor` は `web/src/features/combo/components/ComboEditor.tsx:496` で落としている。**同じ要求（指示書 §4.1「保存の成功で dirty を落とすこと」・`CHANGE-137` 判断 5）に対して 2 面のうち 1 面だけが対応している。**
- さらに機序として、ガードが張られている間は `web/src/features/navigation-guard/NavigationGuardProvider.tsx:126-129` が **URL を変えない番人エントリを 1 枚積んでいる**（`window.history.pushState(window.history.state, "")` は第 3 引数を省くと URL 不変）。したがって保存時点の履歴は `[…, 前の画面, /setups/:id, 番人(/setups/:id)]` であり、`:215` の `navigate(-1)` は **番人の 1 つ前＝編集画面自身のエントリ**へ戻る。URL が同じなのでルートは変わらず、画面は離れない。
- その `popstate` を `NavigationGuardProvider.tsx:131-135` の `onPopState` が受ける。dirty が落ちていないので購読は生きており、番人を積み直して確認ダイアログを出す。

**どう違うか**: チェックリスト 1-4 は「落ちないなら重大」、§8-3 も重大判定に挙げている。加えて「保存したのに離れない」は `M24-01`（`CHANGE-130`）が決めた保存後の遷移そのものを壊す。

**なぜテストが緑のままか**: 既存 E2E で `/setups/:setupId` を開くのは `e2e/m19-03-setup-results.spec.ts:372` と `e2e/m19-07-setup-conditions.spec.ts:128` の 2 本だけで、どちらも**表示を見るだけで保存していない**。`web/src/pages/SetupEditorPage.test.tsx` にも「保存成功で dirty が落ちる」テストが無い（チェックリスト 5-3 の網が片面にしか掛かっていない）。

**確認の要否**: 履歴 API の実挙動に依存するため、**実ブラウザでの再現確認を推奨する**（`/setups/:id` を開く → 名前を変える → 保存 → 遷移するか / ダイアログが出るか）。コード上の経路としては上記のとおり成立する。

### 重大-2. `SetupEditorPage` 下部の「キャンセル」ボタンが `requestLeave` を通っていない（CO-003 の穴）

**何が**: セットプレイ編集画面の、**保存ボタンの隣にある「キャンセル」ボタン**は、未保存の入力があっても確認なしで離脱する。

**どの根拠で**: `web/src/pages/SetupEditorPage.tsx:439-448`

```
          onClick={() =>
            mode === "create"
              ? navigate(`/combos/${comboId}`)
              : navigate(-1)
          }
```

`requestLeave` を通していない。上部の「← キャンセル」（`:362-370`）だけが `onClick={() => requestLeave(() => navigate(-1))}` になっている。`<button>` なので `NavigationGuardProvider` の click キャプチャ（アンカー限定＝`linkClick.ts:51-55`）にも掛からない。

### 重大-3（要実機確認）／高相当. 番人エントリの後始末が無く、`navigate(-1)` 系の離脱が空振りする

**何が**: ガードが張られると積まれる番人の履歴エントリが、**ガードが外れても解除されても取り除かれない**。その結果、

1. **`ComboEditor` の「キャンセル」→「保存せずに離れる」で離れない。** `NavigationGuardProvider.tsx:157-178` の `leave()` は、`kind: "href"` では `navigate(href, { replace: hadSentinel })`、`kind: "back"` では `history.go(-2)` と番人を補正しているが、**`kind: "action"` だけ補正が無い**（`:177 target.run()`）。`ComboEditor.tsx:835-843` の `handleCancel` は `punishReturn` が無ければ `navigate(-1)` を渡すため、番人 1 枚ぶんしか戻らず編集画面に留まる。
2. **dirty を打ち消しただけでブラウザバックが 1 回空振りする。** `NavigationGuardProvider.tsx:137-140` の cleanup は `sentinelRef.current = false` にするだけで `history.go(-1)` をしない。入力して消す（dirty → clean）と番人が 1 枚残り、次の「戻る」は同じ URL のエントリへ着地して何も起きない。**本サブ以前には無かった挙動である。**
3. **`history.go(hadSentinel ? -2 : -1)` は番人が 1 枚である前提。** `:126-141` の effect は `blocked` が false→true になるたびに積むため、dirty ↔ clean を往復すると 2 枚以上たまる。その状態で「戻る」→「離れる」を選ぶと `-2` では足りず、やはり離れない。

**併発する副作用**: `leave()` の `:162 setBlockedIds(new Set())` は id レジストリを迂回して全解除する。`useUnsavedChangesGuard.ts:16-19` の effect は deps（`id` / `isDirty` / `setBlocked`）がどれも変わらないため**再登録しない**。上記 1 で遷移が起きなかった場合、**入力が未保存のままガードだけが恒久的に外れる**。

**どう違うか**: 指示書 §1.2 の目的（「入力を失う」を減らす）に対して、ガードを通した離脱が完了せず、かつガードが黙って外れる状態が生まれる。

**推奨の方向**（実装は製造の裁量）:
- 番人の枚数を数えて持つ（`sentinelRef` を boolean ではなく counter にする）か、cleanup で確実に 1 枚戻す。
- `kind: "action"` でも番人ぶんを補正する（例: 先に番人を戻してから `run()` を呼ぶ）。
- 全解除ではなく「解除した id を覚える」形にして、遷移が起きなかったときに再武装できるようにする。
