## 3. 【A】第三波への機械 backfill（`000062`）

**`000050` の述語をそのまま踏襲した。規則は一切変えていない。**

| 列 | 規則 |
|---|---|
| `startup_basis` | `is_derived = 0` → `'standalone'` |
| `startup_basis` | `category = 'rush_variant'` → `'through'` |
| `fastest_unreachable` | `code LIKE '%jumping\_%' ESCAPE '\'`（**部分一致**） → `1` |

- **対象を第三波 6 キャラに限定**（`character_id IN (SELECT ... WHERE c.code IN (...) AND c.game_id IN (...))`）。全キャラを対象にしていない。
- **既存値の保護**: 全 UPDATE に `AND startup_basis = 'unknown'` ／ `AND fastest_unreachable = 0`（契約 F-4 (2') の (c) と同じ形＝ボード D-179）。
- **provenance コメント**: `000050` の規則を第三波へ追随させるものであること／**`000050` は適用時点の行だけを対象とし、その後 INSERT された行を拾わないこと**／`000053`〜`000059` が `startup_basis` に一切触れていないこと。
- **down** は当該行を `unknown` / `0` へ戻す。**up と同じ WHERE を使いつつ、`IS NULL` 相当の条件の代わりに「up が付与した値そのもの」（`'standalone'` / `'through'` / `1`）を条件に加えて限定**した（`AND startup_basis='unknown'` を down にそのまま持ち込むと 0 行にしか当たらないため）。

### 3.1 ★`c_viper` / `dhalsim` の除外条件を **書かなかった**理由（製造の判断）

`000050` は `standalone` の UPDATE に `AND character_id NOT IN (c_viper, dhalsim)` を持つが、**`000062` には書いていない。**

**あの除外は「キャラ単位」の措置である**——両キャラは移動 system move のみを持ちフレーム列が全 NULL で、「その `startup` がどちらの意味か」を語る対象が存在しない（`000050` のコメントと `000041` の先例）。**第三波 6 キャラはいずれも実技を持つので除外に当たらない。** 第三波を対象にした `WHERE` に `c_viper`/`dhalsim` を書いても **0 行にしか当たらない無意味な条件**になる。

**結果として、第三波の移動 system move 54 行（`000054` 由来）も `standalone` になる。これが踏襲の正しい形である**——既 seed 11 キャラの移動 move も `000050` で `standalone` になっており、同じ扱いに揃う。**なぜ不要かをマイグレのコメントに明示した。**

### 3.2 ★`fastest_unreachable` の部分一致は、**本サブのテストでは守れない**（正直な申告）

指示書どおり**部分一致 `'%jumping\_%' ESCAPE '\'` で書いた**。しかし**第三波 6 キャラのデータでは部分一致と前方一致がどちらも 38 行で一致する**（実測）。

**つまり `000062` を前方一致に書き換えても、本サブの件数テストでは検出できない。** これは「静かに壊れる」ものを足したのに、それを壊したときに落ちるテストが書けなかったケースである。**マイグレのコメントに明記した。**

**大域の取り落とし検出は `000050` 側のテストが引き続き担保する**——`migrate_m1904_test.go` の `m1904PrefixMissed = 2`（`juri` / `ken` の `neutral_jumping_heavy_kick`）。**第三波にはこの型の code が存在しないため、本サブ側では原理的にガードを作れない。**
