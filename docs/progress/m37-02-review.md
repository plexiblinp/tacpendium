## 総評

本サブの本体である「縦の消費を減らす」は、段 1 を先に取り（spec と計測アンカーが `8e154e8`、レイアウト変更は `e53a710` と、コミットグラフが順序を裏づけている）、段 6 で同じ系列を測り直し、区画ごとの内訳まで出している。チェックリスト束 A の骨格は満たされている。束 C も強い——既存の床 7 ファイル 31 行を当方でも数え直して 31 で一致し、7 ファイルはいずれも diff に現れない。`B11` で「区画ごと消す」形へ寄りかけたところで §0.4 の合図に従って引き返した経緯（報告 §5.2）は、指示書がいちばん恐れていた失敗の回避そのものである。

## 推奨修正（優先度別）

### 高（M37 完了前に修正必須）

**高-1. `GAMEPAD_NOTICE_COLLAPSED_FORM = "hidden"` に開く導線が無い。コメントは在ると書いている**

`web/src/features/gamepad/components/GamepadInputNotice.tsx:43-48` は次のように書いている。

```
 *   - `"hidden"`    … 畳んだときは何も描かない。縦は 0。
 *                     ⇒ 開く導線は `VirtualController` の見出し行が持つ
 *                       （同ファイルが `useGamepadNoticeOpen` を読んでボタンを出す）。
```

実測では `useGamepadNoticeOpen` の参照は `GamepadInputNotice.tsx:52` の 1 か所だけである。`VirtualController.tsx` は import もしておらず、見出し行（同 `:230-244`）にトグルは無い。同ファイルは `gamepad.inputActive` の内側で `<GamepadInputNotice />` を描くだけである。

帰結は 3 つ。

1. 記述が事実と食い違う。後任がこのコメントを前提に読む。
2. 完了条件 5 とチェックリスト B-3「ラベル 1 行 / 完全に消す の両方を 1 か所の変更で試せる」が実質不成立である。1 か所を変えると片方の形が壊れる。
3. `"hidden"` を選んだ瞬間、告知へ到達する経路がゼロになる。これは `D-347` の「畳むことは落とすことではない——明示操作で開ける限り、伝える場所は在る」という本サブの成立根拠そのものを崩す。開発者が `P-59` (2) で実物を見て `"hidden"` を選ぶことは明示的に想定されているため、そのときに初めて壊れる形にしてはいけない。

対応は、(a) `VirtualController` の見出し行へ実際にトグルを置く、または (b) `"hidden"` 形でも `GamepadInputNotice` 自身が極小の開くボタンを描く、のいずれか。あわせて `GAMEPAD_NOTICE_COLLAPSED_FORM === "hidden"` の分岐を単体テストで 1 本押さえること（現在この分岐はテストが 0 本である）。

**高-2. `docs/progress/progress-log.md` への索引行が無い**

完了条件 10 / チェックリスト G-9 / `CLAUDE.md` §8。当方で検査を実行した結果は次のとおり。


完了報告 §12 の検査表に本検査が載っておらず、回していないことが欠落の直接の原因と読める。`M37-01` の索引行（`progress-log.md:6004` 以降）が形の見本になる。あわせて、本サブは横断課題を複数持っている（付録C の 4 件、とくに接頭辞走査 5 か所と表示語の 3 か所二重化）ため、索引行の「完了報告に書けない横断課題」欄はこの 4 件を運ぶ場所である。

**高-3. 「未解決 6 理由」を守るはずのテストが空振りしている**

`web/src/features/gamepad/components/GamepadRecipeReadout.test.tsx` の 6 理由ループは、次の 2 つしか主張していない。

```ts
expect(pane.textContent).not.toContain("ありません」");
expect(pane.textContent?.length ?? 0).toBeGreaterThan("解決できなかった入力".length);
```

1 本目は必ず通る。実装の空表示は `GamepadRecipeReadout.tsx:268` の `"ありません"` であり、閉じ括弧 `」` を含まない。したがってこの assertion はどんな入力でも真である。

2 本目も実効が無い。`UNRESOLVED_LABEL` からキーを 1 つ削っても、レンダリングは `— undefined` になって文字列長の条件を満たすため緑のままである。

つまりチェックリスト D-2（★★★）と完了報告 §6 の「未解決 6 理由」という主張を、この床は支えていない。修正は 1 行で足りる。

```ts
expect(pane.textContent).toContain(UNRESOLVED_LABEL[reason]);
```

（`UNRESOLVED_LABEL` は現在エクスポートされていないため、export するか、テスト側に 6 値の期待文字列を写して母数固定と対で持つ。）

本サブは `B04` の Go 側で「全数だけでは検査が何も見ていない場合と区別できない」という理屈を明文化し、実際に破壊して両方向を確かめている（報告 §4）。同じ作法をこちらへも適用してほしい。

### 中（次サブ着手と並行可）

**中-2. 段 1 と段 6 で `measure()` の手続きが変わったことを開示していない**

`2c3f3ca` は spec に 3 つの変更を入れている。

1. 計測前の `await page.evaluate(() => window.scrollTo(0, 0))` を追加。コメント自身が「初版は実際にこれで系列 A と B が逆の結果を返した」と書いている。
2. 系列 B を B（初回）と C（既読）へ分割。
3. `recipeVisibleWhileInputting` を追加。

報告 §2.3 は 3 だけを開示している。1 と 2 は開示が無い。技術的には、報告 §2.1 が比較している `controllerRoot` / `specialPanel` / `pageOverflow` はいずれもスクロール位置に依存しない値（`boundingBox().height` と `scrollHeight - clientHeight`）なので、前後比較は成立していると判断した。ただしチェックリスト A-2 が「同じ条件か」を ★★★ で問うている以上、「手続きは変わったが、変わった部分は測っている値に影響しない」ことを報告に 1 行書くべきである。

あわせて、段 1 の生 stdout がリポジトリのどこにも残っていない（報告 §2.1 の要約表のみ）。段 1 はもう取り直せない値であるから、生出力を報告の付録に貼っておくと後任が再計算できる。

**中-3. 「27 条件すべて true」は床の主張としては広すぎる**

報告 §2.3 は `recipeVisibleWhileInputting` について「27 条件すべて `true`」「これは床として主張している（spec が `expect(...).toBe(true)`）」と書いている。

spec で `expect(row.recipeVisibleWhileInputting).toBe(true)` が在るのは系列 A のテストだけであり、9 件である。系列 B（告知が展開されている初回）と系列 C（既読）は値を記録して stdout へ出すだけで、assert していない。

しかも押し下げが最も強いのは告知と読取欄が出ている系列 B である。守りたい条件がいちばん危ない側で守られていない。系列 B / C の測定関数は共通なので、`measure()` の戻り値に対して同じ expect を置けば 3 行で 27 件になる。

**中-4. 区画 3 / 4 は「畳んだ」のではなく削除している**

指示書 §2.3 の基準は「案内文は畳んでよい」であり、末尾に「区画 3 / 4 は条件表示で畳む」と手段まで書いてある。実装は文言そのものを短縮した恒久削除である。

- ショートカット: `未登録（コントローラ設定で「ショートカット前置き」を登録すると使えます）` → `未登録`
- コマンド: `このキャラクターのコマンド表を取得できていないため使えません` → `コマンド表を取得できていないため使えません`

前者で失われたのは「どうすれば使えるようになるか」であり、これは案内文というより復旧手順である。得た縦は報告 §2.2 の実測で 390px のとき 16px、1280px では 0px である。

`title` 属性へ逃がす、`DisclosureToggleButton` で畳む、コントローラ設定へのリンクにする、のいずれかを検討してほしい。少なくとも「復旧手順を消した」ことは報告に明示し、開発者の判断を仰ぐべきである。

**中-5. 描画フェーズで `localStorage` に書いている**

`web/src/features/gamepad/gamepad-notice-storage.ts` の `getSnapshot()` は、初回に `decideInitialOpen()` を呼び、その中で `storage.save(true)` を実行する。`getSnapshot` は `useSyncExternalStore` が描画中に（React 18 では同一描画内で複数回）呼ぶ関数であり、副作用を持たない純関数であることが要求される。

現状はモジュールレベルの `open` キャッシュがガードしているため 1 ページ読込につき 1 回に収まっており、実害は出ていないと判断した。ただし StrictMode の二重描画や将来の並行描画で挙動が読みにくくなる。既読の書込みは `useEffect` 側（または `GamepadInputNotice` のマウント後）へ寄せるのが安全である。判定ロジック（読んで開閉を決める）は純粋なままにできる。

### 低（将来対応）

- **低-1**: `CommonMovePanel` の生ラッシュボタンが `grid grid-cols-3` の 1/3 幅から `footer` 直下の単独ボタン（`display:flex` により全幅）へ変わっている。完了報告はこの見た目の変化に触れていない。意図どおりか確認されたい。
