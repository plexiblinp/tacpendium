## 総評

**最重要ゲート 3 つは、いずれも実装・テストの両面で成立している。** 入力は保存拒否時に一切触られず（`handleError` がフォーム state を触らない形になっている）、分岐は `classifySaveError` 1 本へ集約されてエラーコードだけで行われ、キー変更編集に負けた 404 も同じモーダルへ寄せられている。破壊確認 A / B はどちらも赤くなっており、A の 1 回目が空振りしたことを自己申告したうえで主張を作り替えた処置も適切である。案 (A) の帰結（上書きの道を出さない）も守られ、`internal/` ／ `auth/` ／ `mycombo/` ／ 依存ファイルの diff はすべて 0 で実測どおりだった。

**一方で「高」が 4 件ある。** うち 3 件は**コード上の記述と実装のズレ**——(1) 非 API エラー時のトーストが `Failed to fetch` のような生の英語文字列を利用者へ出す形へ**後退**しており（本サブの対象外経路だが、本サブの変更で入った）、(2) `errors.test.ts` の対照実験がテスト名の主張と別の入力を検証しており、(3) セットプレイ**新規登録**の 404（＝**親コンボが見つからない**）が「このセットプレイを作り直したか、削除した」と読み替えられている。4 件目は指示書 v1.4.0 ／ チェックリスト v1.2.0 ／ `D-416` が**リポジトリのどこにも存在しない**ことである（完了報告が引用する節を後任が検証できない）。

**as-built 差の記載は概ね揃っているが、全数としては 3 か所欠けている**（§7 の表）。設計卓が `CHANGE-115` を反映するときに使う値であるため「高」ではなく「中」に置いたが、反映前に補うこと。

## 推奨修正（優先度別）

### 高（M22 完了前に修正必須）

**高 1. 通信エラー時のトーストが生の英語メッセージを出す形へ後退している（本サブの変更で入った回帰）**

- 位置: `web/src/features/combo/components/ComboEditor.tsx:479`
- 旧: `if (!(err instanceof ApiError)) { toast.error("通信エラーが発生しました。"); return; }` ＋ 末尾 `toast.error(err.message || "サーバーエラーが発生しました。")`
- 新: `toast.error(parsed.message || "通信エラーが発生しました。")`
