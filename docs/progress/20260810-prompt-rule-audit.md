## 2. 根拠（出典付き外部知見）

採否の正本は `tmp/kaizen_before_M20/evidence-based-review.md`。本書では本監査の判断に直接効いたものだけを挙げる。

- Anthropic は、全資料の事前読込ではなく**小さな先行コンテキスト＋パス・検索による just-in-time 取得**を説明している。→ §1.2 の是正方針の根拠。 <https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>
- Anthropic は、出力の非決定性を理由に**複数 trial** を実行し、エージェントの発言ではなく**環境の最終状態**を評価するとし、初期評価セットは実障害から **20〜50 タスク**を集める案を示している。→ §1.5・§4-1 の設計基準。 <https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents>
- Anthropic の 2026-04 postmortem は、数週間の内部試験を通った system prompt 変更が、より広い ablation で 3% 低下を示し撤回された事例である。**少数比較は回帰を見逃す。** <https://www.anthropic.com/engineering/april-23-postmortem>
- OpenAI Codex チームは、既知違反だけでなく安全な反例も含め **coverage / restraint / 通常バグの保持 / actionability** を評価している。→ 単一指標での採否を禁じる根拠。 <https://developers.openai.com/blog/custom-code-review-rules-for-codex>

### 4-1. タスク0: 縮退版の評価設計（開発者裁定 3 準拠）

開発者は初回リリースまで採点負担を割けないため、**機械採点可能な指標を優先し、人間 blind 採点は重大区分のスポットに限定**する。

| 区分（監査プロンプト §2.1） | 母集団からの割付 | 件数目安 |
|---|---|---|
| 過去に重大指摘が出たレビュー対象 | 「高指摘あり」17 本から、指摘数が多い順に | 10 |
| 指摘なしが正しい安全な反例 | 「高: なし」明記の 7 本 | 7 |
| 指示書外の通常バグを見つけるべき対象 | 「設計準拠性以外の指摘事項」を持つ報告書 | 5 |
| スキーマ・API・データ境界の違反 | `m14-01`(schema) / `m19-03`(condition record) / `m19-04`(columns) 系 | 4 |
| UI / Go / DB / 文書のみの変更 | `m15-*`(UI) / `m16-*`(Go・型) / `m14-03*`(seed・DB) / `m19-*` 文書パッチ | 各 1〜2 |
| アーカイブ参照が必要な対象と不要な対象 | `m18-03a`（過去 M 参照あり） vs `m16-01`（自己完結） | 2 |
| 仕様駆動モードと探索モード | 指示書ベース vs `*-RESEARCH-*` | 2 |

**採点（機械優先）**

| 指標 | 機械採点の方法 | 人間の関与 |
|---|---|---|
| Coverage | 過去報告書の「高」指摘を正解集合とし、新条件の出力に**同一箇所（ファイル＋事象）**が含まれるかを突合 | 重大区分のみスポット確認 |
| Restraint | 「高: なし」7 本に対し新条件が「高」を出さないか | 出した場合のみ人間が誤検出か判定 |
| Retention | 正解集合外の指摘のうち、実在するコード上の欠陥かを `go vet` / テスト / 型検査で機械判定できる分だけ数える | 判定不能分は件数のみ報告 |
| Actionability | 指摘に**ファイルパス・行・修正方向**が揃っているかの形式検査 | なし |
| Task success | 最終状態（テスト exit code・lint exit code・生成物差分）で判定 | なし |
| Efficiency | トークン・所要時間 | なし |

**実行方法**: 同一入力・同一ツールで新旧条件を比較し、**各条件 3 trial**（分散を記録。絶対的な閾値としない）。モデル変更とプロンプト変更を同時に行わない。**AI の完了宣言ではなく最終状態を採点する。**

**採用条件**: 「重大問題の coverage が低下しない」だけでは足りない。**誤検出の増加・通常バグ発見の低下・実行不能な指摘の増加も回帰とする。**

**開発者工数見積**: 評価セットの確定承認 **15 分** ／ 重大区分のスポット blind 採点 **30〜45 分** ／ 結果の裁定 **15 分**。**合計 1 時間強・単発**。これを超える完全 blind 採点は **Phase 4 以降（初回リリース後）の backlog** とする。
