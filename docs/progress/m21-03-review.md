## 総評

**差し戻し事由（重大 1〜9）はいずれも成立しない。** とくに重大判定の 3 本——**出口が `move_code` であること**（物理側に解決規則が 0 件。既存の `resolveDirectionalInput` / `resolveDirectionalRushInput` / `resolveSystemButtonStep` を呼ぶだけ）、**告知 3 点の設置**、**2 面の部品化**（`VirtualController` の内側 1 か所。セットプレイ側の変更 0 行）——はいずれも構造で担保されており、テストが外から固定している。**`_od` へ写す枝はコードに存在せず**（差し戻し事由 9 不成立）、`moves` に `hadoken_od` があっても OD へ解決しないことを**否定形でテスト固定**している点は、指示書が求めた水準を超えている。

**実装中に指示書内の両立不能（`D-352`）を検出して止めて上げた判断、および「入力面が同時に複数マウントされる」という指示書が予見していなかった問題を単一 provider ＋ 受け手調停で解いた判断は、いずれも本サブの最大の価値である。**

一方、**「高」に相当する指摘が 2 件ある。** どちらも**動作は正しく、テスト・型検査・lint のいずれでも検出できない**——M21-01 / M21-02 が「M21-03 が作る」と書いた前方参照コメントが、**M21-03 完了後も旧のまま残っている**箇所である。後任（M21-04 / M21-05 / M21-06）が本文をコピーして前提を複製する型であり、本プロジェクトの較正では「高」に置く。

**告知の文言・読取表示の見た目はチェックリスト §9 により判定対象外だが、本件は「見た目」ではなく出し分け条件（`available` か `status` か）の問題として指摘する。** `status === "connected"` を条件に加えれば、告知が要る利用者にだけ出る。

**なお完了報告 §8.1-5(c) が「告知の置き場が邪魔になっていないか」を開発者の実機確認事項として挙げているため、判断材料として本指摘を添えること。**

### 【中-2】方向ニュートラル（テンキー 5）が常時「点灯」扱いになる

`VirtualController.tsx:76` は `heldDirection = numpadFromDirection(gamepad.held.direction)` とし、`held.direction` の既定は `direction_neutral` → **5**。`HitBoxLayout` は `held={heldDirection === dir}` なので、**何も押していなくても `recipe-dir-5` に `data-held="true"` が付く**（`gamepadRecipeInput.test.tsx:376` がこの挙動を固定している＝意図的な実装）。

§4.4 は「**押している間ずっと光り、離すと消える**」と定めており、**押していない状態が点灯として出るのは規約の文面と食い違う。** さらに【中-1】と重なり、**コントローラ未接続でも `5` が緑のリングで光る**。`5` は既定で `active`（青）でもあるため、二重の強調になる。

**是正案**: 方向の点灯を「非ニュートラルのときだけ」にする（`held.direction === "direction_neutral"` なら `null`）。ニュートラルを可視化したいなら、点灯とは別の表現にする。

### 【中-3】React の state updater 内で別の `setState` を呼んでいる（`GamepadInputProvider.tsx:220-227`）

```ts
const unregisterSurface = useCallback((id: string) => {
  handlersRef.current.delete(id);
  setSurfaceIds((prev) => {
    const next = prev.filter((s) => s !== id);
    setOwnerId((owner) => (owner === id ? (next[0] ?? null) : owner));   // ← updater の内側
    return next;
  });
}, []);
```

**updater 関数は純粋でなければならない**（React 公式）。StrictMode では updater が二重呼び出しされるため、`setOwnerId` も 2 回走る。現状は冪等なので実害は出ていないが、**「updater の中で副作用を書いてよい」という前例をこのファイルが作る**。`M21-04`（コントローラ完結入力）が同じ調停へ確定・削除を足すときに増幅しやすい箇所である。

**是正案**: `surfaceIds` を ref でも持つか、`unregisterSurface` 内で `setOwnerId((owner) => owner === id ? …)` を updater の外へ出す（次の owner は `surfaceIdsRef` から取る）。

### 【中-4】ラッシュ ON ＋ 上系方向の物理入力が `move_not_found` として出て、理由の文言が実態と食い違う

`resolveDirectionalRushInput` は `dir >= 7` で無条件に `null` を返す（`inputResolutionStage2.ts`。**空中ラッシュ不可**＝`DES-005` §6.4「ラッシュ ON 中は上系方向を非活性」）。物理経路はこれを受けて `move_not_found` を返し、読取表示に「**このキャラクターに該当する技がありません**」と出る。

**実際の理由は「そのキャラに技が無い」ではなく「ラッシュ版は空中に存在しない」である。** §4.3-3 は「解決できなかった入力を出す」ことを求めており、その目的は**なぜ入らなかったかが分かること**である（読取表示の理由文は本サブの as-built として `CHANGE-111` へ写る＝完了報告 §3-6）。誤った理由が設計書へ写ると訂正しにくい。

**是正案**: `UnresolvedReason` に `rush_not_available_in_air`（仮）を足すか、少なくとも `move_not_found` の文言を「該当する技が見つかりません（ラッシュ版は空中では出せません）」のように**取り違えない語**にする。**なお仮想 UI 側はボタンが非活性なので出力自体は一致しており、契約違反ではない。**

### 【中-5】読取表示の 5 件バッファを解決済みと解決不能で共有しており、成功入力で理由が押し出される

`useGamepadRecipeInput.ts:107` は `[entry, ...prev].slice(0, MAX_READOUT_ENTRIES)` の**単一バッファ 5 件**で、`GamepadRecipeReadout` がそれを `filter` で 2 区画に分けている。⇒ **解決できなかった入力が出た直後に 5 回成功入力すると、理由の表示が消える。**

出た瞬間には見えているので差し戻し事由 4（黙って捨てている）には当たらないが、**「素早く入力するとまとまる」利用者ほど押し出されやすい**——告知が想定している利用者像とちょうど重なる。区画ごとに独立の上限を持たせるのが安全。

### 【低-1】`logicalButtonLabel` の型キャストと到達不能な既定値（`logicalButtons.ts:139-142`）

`BUTTON_LABEL[button as CalibrationButton] ?? button` は、`LogicalButton` を `CalibrationButton` へ**アサーションで通している**。`noUncheckedIndexedAccess` が無効なため型上は `string` になり、`?? button` は型的に到達不能に見える（実行時には効く）。`throw_forward` / `throw_back` / `dash_*` を渡すと**生の識別子がそのまま画面へ出る**。現状これらは `held.buttons` に入らないため実害は無いが、`M21-04` が対象を広げると露出する。`Partial<Record<LogicalButton, string>>` の別表を作らずに済ませたい意図（第 2 のラベル表を作らない＝`E-76`）は正しいので、**型を `Partial<Record<LogicalButton, string>>` として宣言し直すのが素直**。

### 【低-2】§4.9-2 の「出口＝`move_code` ＋ 方向 ＋ 修飾」との差分が完了報告に明示されていない

実装の出口は `StepInput { moveId, moveCode, modifiers? }` で、**方向を独立したフィールドとして持たない**（方向は解決の時点で `crouching_` / `jumping_` として `move_code` に畳み込まれる）。**仮想 UI と同一の中立形に揃えたこの判断は正しい**が、指示書の文言とは差がある。完了報告 §2.1 は「仮想コントローラと同一の中立な形」とだけ書いており、**§4.9-2 との差分としては書かれていない。** `CHANGE-111` の反映時に設計卓が §4.9-2 の文言をそのまま `DES-005` へ写すと、実装と設計書がずれる。1 行で理由を添えること。

### 【低-3】`handleSystemButton` が同じ写像を 2 回引いている（`useControllerInput.ts:73-82`）

`const code = SYSTEM_BUTTON_TO_MOVE_CODE[button]` を分岐条件と `console.warn` のメッセージのために引き、`resolveSystemButtonStep` の内側でもう一度引いている。既存挙動（warn の文言）を保つための形であり実害は無いが、`resolveSystemButtonStep` が「対象ボタンか」と「解決できたか」を `null` 1 種で潰しているのが遠因。将来 `resolveSystemButtonStep` の戻り値を判別可能にすると 1 回で済む。

### 【低-4】切断時に判定と点灯は捨てられるが、各面の読取表示は残る

`GamepadInputProvider.tsx:179-185` は切断・入力面消滅で `reset()` と `held` のクリアを行うが、**`readout` は `useGamepadRecipeInput` のローカル state** であり残る。切断後も「押している入力」は消えるのに「確定したステップ」は残る、という中途半端な状態になる。`available` / `status` を見て `readout` も捨てるか、意図なら 1 行コメントを添えること。

### 【低-5】中P＋中K を前方向で押しても `drive_parry` になる（`parry_drive_rush` にはならない）

`parry_drive_rush` は「中P+中K のあと 6」＝**方向の連続入力**であり、本サブでは出せない（§4.1-1）。**設計どおりであり指摘ではない**が、**`M21-06` への申し送りとして完了報告 §10 相当の場所に無い。** OD（申し送り 2 件のうち 1 件）と同じ理由で M21-06 が最初に解ける場所になるため、`dash_forward` / `dash_back` とあわせて**3 件目の申し送り**として残すのが親切。

### 【低-6】告知が入力面の数だけ描画される

コンボ編集画面はレシピ節 1 個 ＋ 紐づくセットプレイ行 N 個の入力面を持ち、**告知の枠が N+1 個並ぶ。** 文言の正本が 1 定数である点は §4.9-5 を満たしており**差し戻し事由ではない**。ただし【中-1】と組み合わせると常設の占有が大きい。開発者の実機確認（完了報告 §8.1-5(c)）の判断材料として添えること。
