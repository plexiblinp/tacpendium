## 3. 起き攻めの 3 状態化（`P4M-011`）と既存データの移行

### 3.1 実査した現在の持ち方（指示書 §2.3-1）

**`combo_oki_options` は sparse であり、「調べたか」を持つ列がどこにも無かった。**

`000021` のヘッダに判断が逐語で残っている——**「sparse 型。行の存在＝そのオプションが利用可能。available 列は持たない。」** `DES-003` §3.4 はさらに、**旧 6 BOOLEAN の nullable tri-state（null/false/true）を presence 型へ意図的に縮約した**（false と null を非区別）と記録している。

**⇒ 「既に nullable なら表現できるのに使っていないだけ」ではなかった。スキーマ変更が要る。**

### 3.2 ★★方式は実機確認で作り直した（セル単位 → コンボ単位）

**初版はセル単位の 3 状態（`combo_oki_options.available`）で作った。⇒ 開発者の実機確認で取り下げた（2026-09-03）。**

> **逐語**: 「2段になっているが入力量が増えて大変なので戻して欲しいです。私が欲しかったのは起き攻め全体として、一度調べたか？必須入力じゃないので完全に飛ばしたか？を表すフラグでした。**なのでやりたいことがそもそもずれていました。**」

**★★指示書 §2.3 の「2 状態を 3 状態にする」を、私はセルの状態のことだと読んだ。開発者が言っていたのは「起き攻めという節を調べたか」であった。** 同じ「3 状態」という語で、**掛かる対象（セル / 節）が食い違っていた**。

**⇒ 採った方式（開発者確定）**:

```sql
ALTER TABLE combos ADD COLUMN oki_verified INTEGER NOT NULL DEFAULT 0;
UPDATE combos SET oki_verified = 1
    WHERE EXISTS (SELECT 1 FROM combo_oki_options WHERE combo_id = combos.id);
```

| 状態 | 表現 |
|---|---|
| 未検証（まだ調べていない） | `oki_verified = 0` |
| **調べたが成立するものが無かった** | **`oki_verified = 1` かつ 行 0 件** |
| 調べた結果これらが成立する | `oki_verified = 1` かつ 行あり |

**★`combo_oki_options` のセル単位の意味論は M16-03 のまま 1 文字も変えていない**（行の存在＝成立する）。**⇒ セル側の実装・テスト・CSV・読む面はすべて着手前の状態へ戻した。**

**backfill は「行があれば調べた」**（開発者確定）。チェックを付けたのなら明らかに調べているため、意味の通る推定である。**★行が無いコンボは `DEFAULT 0` のまま＝未検証**——ここを逆にすると、調べていないコンボが「調べたが無かった」と主張することになり本サブの目的と逆になる（マイグレテストで固定した）。

**★★実データでの効き方**（開発者実測・83 件の本登録コンボ）: 起き攻めの行を持つコンボが「調べた」になり、残りは未検証から始まる。**移行で失われる情報は無い。**

### 3.2.1 入力の形

- **起き攻めのチェックは M24-12 のまま**（攻撃種別ごとに 1 群 × 4・2 列・数字キー `1`〜`4`・停止点 3 つ）。**★初版で 6 群にしたのは戻した。**
- **トグルは節見出しの隣**（畳んでいても状態が読める）。
- **★チェックに触れると「調べた」が自動で就く**（付ける／外すのどちらでも。どちらも「起き攻めを見た」ことの証拠であるため）。**自動で外すことはしない。**
- **★★解除には確認を挟む**——「一度検証済みにして、かつチェックを付けたものがある時に解除するのは操作ミス」（開発者逐語）。**トグルの無効化は採らなかった**: 外すにはチェックを全部外す必要があるが、**チェックに触れると自動で就くため循環する**。⇒ 先例（`DeleteComboConfirm` 等）に合わせて `AlertDialog` で止める。**チェックが 0 件のときは確認を出さない**（ミスではない）。
- **編集画面にも出す**（開発者確定。当初「新規のみ」だったが、既存 83 件のフラグを後から直せなくなるため見直された）。

## 7. 教訓

1. **★必須化の影響の実数は、DB が無くてもテストが教える。** 件数を測れない環境でも、**既存テストが 58 件落ちたこと自体が「本登録コンボを 4 欄なしで作っている箇所」の実測**だった。⇒ 「データが無いから測れない」で止まらず、**コードの側の母集団を数える**手がある。
2. **★データの意味を変えたら、その意味を読んでいる側を全数洗う。** 型検査は書く側（`OkiOption` の構築）を全部見つけたが、**読む側の「presence を真偽として解釈しているコード」は型では見つからない**。実際 6 か所あり、うち 3 か所は放置すると**嘘の表示**になっていた（§3.4）。

4. **★ゼロ値が意味を持つ欄は、省略と false を区別できる型にする。** API DTO を `bool` にすると、**古いクライアントの「省略」が「不成立」になる**。`*bool` にして省略を `true`（従来の意味）へ寄せた。
5. **★★`E-225` を実際に踏んだ。「`ls` を実行したか」ではなく「出力を読んだか」である。** `schema.test.ts` を新規のつもりで上書きし、`M24-13` の既存テスト 12 件（88 行）を消した。**`ls` は実行しており、出力にパスも出ていた**（＝存在した）。⇒ 手順は踏んだが**結果を読まずに次の行へ進んだ**。**★★テストは何も言わなかった**——上書き後も新規 8 件が緑で通る。気づけたのは `git status` が `A` ではなく **`M`** を返したからである。**⇒ 新規ファイルを作ったら、`ls` の結果を読むだけでなく `git status` の A/M を確かめること。** 指示書 §Phase A 補足 (b) が「`git diff --stat` の deletions を読む」を求めているのはこの型のためであり、**本サブは報告を書く段で実際にそれに救われた。**

### 7.1 ★取り残した DB の修復手順（記録）

旧 `000096`（`add_combo_oki_options_available`）を適用済みの DB を、新 `000096` へ乗せ直す手順。**アプリを停止してから行う。**

-- 診断（読み取りのみ）。version=96 / available=1 / oki_verified=0 なら本件。
SELECT * FROM schema_migrations;
SELECT COUNT(*) FROM pragma_table_info('combo_oki_options') WHERE name='available';

UPDATE schema_migrations SET version = 81, dirty = 0; -- 81 = 本ブランチで 096 未満の最大版数
