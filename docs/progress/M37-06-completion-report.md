## 4. 設計判断とその理由

### 4.1 ★★★案 C の足場は「サーバが既に表示語を出していること」である

`recipe_cache` はステップ構造を持たない。**しかし文字列の中に `{目押し}` が入っている。⇒ 描画のときにそこだけ拾えばよい。**

**★これは `recipe_cache` を「構造化されていない」と読むか「粗く構造化されている」と読むかの違いである。** 前者だと案 A / B の二択になるが、後者だと案 C が見える。

### 4.2 ★★★未知の `{...}` は**バッジにしない**

`splitStepSegments` は、波括弧の中身が**既知の表示語 17 件のいずれかに一致するときだけ**バッジにする。それ以外は素の文字列のまま残す。

**理由は 2 つある。**

| # | 理由 |
|---|---|
| 1 | 技名など、修飾でない文字列がたまたま波括弧を含んでも誤ってバッジにしない |
| **2** | **★★★表示語の埋め忘れを隠さない。** Go 側に表示語が無いと `{od_lm}` が出るが（`M37-02` / `B04` が消したかった状態）、**それをバッジで飾ると「壊れているのに整って見える」** |

### 4.3 ★★★Go ⇄ フロントの表示語一致を**機械検査にした**

**着手前は検査が無かった**（`DES-004` §2.3 の逐語＝「★★★機械検査は無い」。followup `modifier-flag-labels-triplicated-without-check`）。

**★★足した理由は「あると良いから」ではない。⇒ 案 C が両側の一致に*依存するようになった*からである。** `RecipeText` は Go が出した表示語をフロントの表と照合してバッジへ替えるため、**両側がずれるとバッジが黙って出なくなる。**

**★これは followup が言う「定数の移設」ではない。** 移設（`features/combo/` → `constants/`）は波及が読めないため単独の手番が要る、という判断は生きている。**⇒ ここでやったのは照合だけであり、定義の置き場は 1 文字も動かしていない。**

**★★検査そのものを破壊して確かめた**（実測・§5.4）。

### 4.4 `juggle_high` / `juggle_low` のコード名は設計卓案を採った

**開発者承認**（2026-09-14・逐語＝「1、juggle案採用」）。`high_hit` / `low_hit` が*上段 / 下段*と読まれる問題は実在するため。

### 4.5 `cancel_drive_rush` の表記の割れは**触らなかった**

サーバ「キャンセルラッシュ」／ UI「キャンセルドライブラッシュ」という**同型の割れが `parry_drive_rush` の隣に残っている**（実測）。指示書 §2.6-3 が名指ししたのは `parry` の 1 件だけであり、**開発者が 2026-09-14 に「そのままでよい」と裁定した**（逐語）。⇒ 事実として記録し、畳んでいない。
