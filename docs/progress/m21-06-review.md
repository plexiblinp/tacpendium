## 設計準拠性以外の指摘事項

1. **`as MotionResolution` による必須フィールドの欠落**（`usePhysicalRecipeInput.ts:299-302` / `:322-325`）。`MotionResolution` の `unresolved` 枝は `candidates: MotionCommand[]` を必須にしているが、両所は `{ status, reason }` だけの literal をアサーションで通しており、**実行時に `candidates` が `undefined` になる値が型上は配列であると偽装されている。** いまは読取表示が参照していないだけで、参照した瞬間に落ちる。`candidates: []` を渡すか、型側を `candidates?:` にすること。CLAUDE.md §4 が `any` を禁じている趣旨（型検査の迂回を残さない）と同じ問題である。
2. **`handleSources` の依存配列に `deliverMotion` が無い**（`PhysicalInputProvider.tsx:653`）。現状は `deliverMotion` が `[]` 依存の `useCallback` で安定しているため無害だが、**`pnpm lint` の実体は `tsc --noEmit` であり `react-hooks/exhaustive-deps` は動いていない**（`web/package.json:12`）。将来 `deliverMotion` に依存が付いた時点で、モードの配送だけが古いクロージャを掴む形で静かに壊れる。
3. **共有列挙の置き場**。`PhysicalInputActionKind` は Gamepad・キーボード・provider の 3 者が参照する共有列挙になったが、定義は供給元固有の `features/gamepad/shortcut.ts` に残っている。`§4.0` が「供給元に依存しない層」を `features/physical-input/` へ切り出した判断と一貫しない。**1 か所であることは満たしているため差し戻し事由ではない**が、次に触るときの置き場としては `physical-input/` 側が正しい。
4. **`GamepadRecipeReadout` の名実不一致**（完了報告 §14-3 で残課題として自認済み）。据え置きの理由として挙げられた「**test-id と対であり改名すると回帰になる**」は**正確ではない**——コンポーネント名と `data-testid` 文字列は独立に変更でき、名前だけを改めても test-id は不変にできる。残課題として上げる判断自体は妥当だが、**理由の記述が後任に誤った制約として伝わる**ため、引き継ぎ時に訂正すること。

- **`move_commands` が未 seed のキャラへ切り替えた場合**（BE は 200 ＋ 空配列を返す仕様＝正常系）。

このとき起きることは次のとおりで、**利用者は自力で復帰できない。**

1. モードは `active` のままなので、**方向はステップにならず列に溜まり続ける**（既存の入力経路が動かない＝`§4.6-6` の約束が破れている）。
2. 攻撃ボタンを押しても索引が空なので必ず `no_match`。
3. **モード操作キーを押しても `unavailable` で弾かれ、抜けられない**（チェックリスト重大 8「モードから抜けられない」の条件）。
4. 読取表示は `!commandModeAvailable` 枝が優先されるため（`GamepadRecipeReadout.tsx:198`）、**溜まっている列すら画面から消える**（`§4.1-6` も同時に破れる）。

**修正方針（最小）** — 可否ガードは**入るときだけ**に掛ける。抜ける操作は索引の有無に関わらず常に通すこと。

```ts
if (commandModeActiveRef.current) { setCommandModeActiveRef.current(false); outcome = "done"; }
else if (!commandModeAvailableRef.current) outcome = "unavailable";
else { setCommandModeActiveRef.current(true); outcome = "done"; }
```

**あわせて**、`commandModeAvailable` が `false` へ転んだときにモードを畳む（＝`setCommandModeActive(false)` を通して**溜めた列を `E-84` の形で吐き出す**）か、少なくとも読取表示で `active` の表示を `available` より優先させるかを決めること。**どちらへ倒すかは §9.2 の製造裁量の範囲**だが、「列が黙って画面から消える」形だけは避ける必要がある。

> **★これは「抜け方の細部」（チェックリスト §9-4）への口出しではない。** 判定しているのは §9-4 が明示的に残した「**溜めた列が黙って消えないこと**」と、重大 8 の「**抜けられない**」の 2 点だけである。

### 中（M22 着手と並行可）

**中-1. `as MotionResolution` で必須 `candidates` を欠いたオブジェクトを作っている**（`usePhysicalRecipeInput.ts:299` / `:322`）。上記「設計準拠性以外の指摘事項 1」。`candidates: []` を渡すのが最小修正。

**中-2. Gamepad で入ったモードが、前置きを後に離すと空列の確定を起こす**

`setCommandModeActive` はモード開始時に `attackDownRef.current.clear()` するだけで、**そのとき既に押されている攻撃ボタンを取り込んでいない**（`PhysicalInputProvider.tsx:484`）。一方、前置き側は同じ問題に対して `prefixRose` 時に「押されたままの後続ボタンを先に取り込む」処置を持っている（`:536-541`）。**この非対称が実害になる経路がある。**

- モードへ入る後続ボタンは**弱K であり、これは攻撃 6 ボタンの 1 つ＝モード内では確定の契機**である。
- 前置きを押したまま弱K を押して**前置きを先に離す**と、次のサンプル（`[light_kick]`）でモードの分岐に入り、弱K が**立ち上がりとして誤検出**される。
- 結果、方向を 1 つも入れていない状態で確定が走り、読取表示に「**（方向なし）＋ 弱K — この方向の並びに一致するコマンドがありません**」が 1 件出る。

ステップは増えないため実害はノイズに留まるが、**読取表示の上限 5 件を 1 つ消費し、モードに入った直後に必ず「解決できませんでした」が出る**のは要件（`FR106` の「正確にゆっくり入力できるよう読み取り表示する」）の趣旨に反する。既存テストは前置きを離してから弱K を押す順序（`commandMode.test.tsx:546-549`）しか駆動していないため検出できていない。

**修正方針** — 前置き側と同じく、モード開始時に `lastSampleRef.current` の押下状態から攻撃ボタンを `attackDownRef` へ取り込む。**実機確認（完了報告 §8.2）でこの順序を試すこと。**

**中-3. 索引に載っているが当該キャラの `moves` に無い場合を `no_match` として表示している**（`usePhysicalRecipeInput.ts:316-334`）。安全側に倒す判断そのものは正しい（出口が必ず `move_code` であることを守っている）が、利用者へ出る文言は「この方向の並びに一致するコマンドがありません」であり、**実態（索引と技一覧の不整合）と食い違う。** 理由コードを 1 つ足すか、少なくともコメントで「この枝はデータ不整合であり利用者の入力ミスではない」と残すこと。
