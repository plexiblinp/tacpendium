## 1. 変更の概要

**`M23-05` は「ゴミ箱に同じものがある」ことを告げる検証を 4 件足した。** **しかしその手段は「保存が成功した後の応答に載せるトースト」であり、同サブの指示書 §1.3 が掲げた目的——「作り直す前に告げる ⇒ 重複そのものが減る」——を構造上達成できない。**

**★これは製造の実装の漏れではない。設計卓の起票の誤りである**（**D-518**。**開発者が実機で発見**）。

**本 CHANGE は、告げる場所を「保存の後」から「保存の前」へ移す。**

1. **保存前チェックの経路を、コンボ側とセットプレイ側の両方に用意する**（§2.1）。
2. **保存ボタン押下時にダイアログを出す**（§2.2）。
3. **`DES-006` §11 へ「警告の表示」と「操作の分岐」の区別を明文化する**（§2.3）。
4. **`DES-005` へダイアログの規律を書く**（§2.4）。**★入力が失われることを押す前に伝える。**

**★CHANGE 対象外**——**「両方入れる」の選択肢**（§3-1）／ **`VAL-C02` / `VAL-S04` の ERROR 契約** ／ **生きた重複に対するダイアログ** ／ **入力中のダイアログ** ／ **`M23-05` の判定内容** ／ **`PUT` / `PATCH` / CSV 取込 / materialize / コンボ同時登録** ／ **ゴミ箱画面**（`M23-06` / `M23-07`）。

## 2. 変更の内容

### 2.1 `DES-002` §4.2——**保存前チェック 2 経路**

| 経路 | 扱い |
|---|---|
| **`POST /api/combos/check-duplicate`** | **★既存だが `DES-002` §4.2 に載っていない**（2026-08-23 走査＝ヒット 0 件）。**⇒ 本 CHANGE で as-built を載せ、あわせて削除済みの一致も返すよう広げる。** **★実装が在るのに経路表に無い形は `M23-01` と同じである** |
| **セットプレイ側**（**新設**） | **同型の経路が無い。** **⇒ 新設する。形はコンボ側に揃える** |

**★3 点。**

1. **★生きた側と削除済み側を別のキーで返す。混ぜない。** **画面は「生きた重複」と「ゴミ箱の重複」で違う振る舞いをする。**
2. **★母集団は `M23-05` の `VAL-C14` / `VAL-S07` と同じにする**（**`M23-05` が作った処理を呼ぶ。判定を書き直さない**）。
3. **★応答は人が読める文字列を持つ**（コンボ＝`memo` ／ セットプレイ＝`name`）。**★id だけでは、ダイアログが「どれを復元するのか」を見せられない。**

**★生きた重複は本 CHANGE では扱わない**（応答には載せるが、ダイアログは出さない）。**理由＝既に `VAL-C02` / `VAL-S04` の ERROR で止まっている。**

### 2.2 ダイアログ

**保存ボタン押下 → 保存前チェック → 削除済みの一致が在ればダイアログ → 選択 → 実行。**

| 選択肢 | 何が起きるか |
|---|---|
| **ゴミ箱から復元する** | **復元 API を叩く。★いま入力した内容は保存されない** |
| **新しく作る** | **従来どおり登録する。ゴミ箱の行はそのまま残る** |
| **キャンセル** | **何もしない。編集を続ける** |

**★入力中には出さない**——**入力のたびにモーダルが出る。**

**★チェックが失敗したら、ダイアログを出さずに保存へ進む**（**★チェックは付加価値であり、登録という主目的を巻き添えにしない**。`M23-04` §4.2 と同じ規律）。

**★ダイアログで告げたことを、保存後にもう一度告げない。** **★抑制は画面側で行い、サーバの契約は変えない**——**サーバが「確認済み」の意味を持つと、API を単体で叩いたときの意味が曖昧になる。**

### 2.3 ★★`DES-006` §11——**「警告の表示」と「操作の分岐」は別である**

**§11.1 は WARNING を「入力フォーム下部に警告リストとして表示」とし、§11.2 は「ERROR はモーダル」としている。** **本サブのダイアログはその線を越えるように見える。**

**★★越えていない。区別は「警告の表示」か「操作の分岐」かである。**

| 種類 | 利用者は何をするか | 見せ方 |
|---|---|---|
| **警告の表示** | **読むだけでよい** | **§11.1 の形** |
| **操作の分岐** | **★選ばないと次へ進めない** | **モーダルで出す。種別が WARNING でもよい** |

**★先例がある**——**`VAL-N02`**（§7）。**LAN 共有モードをパスワード未設定で有効にするとき、種別は WARNING でありながら「明示的な同意ダイアログで承認を得る」としている。**

**⇒ §11 へこの区別を明文化する。** **書かないと、次に読んだ担当が「WARNING なのにモーダル」を欠陥と読む。**

### 2.4 `DES-005`——**ダイアログの規律**

**★★「復元する」を押すと入力内容が失われる。押す前に伝えること。**

**利用者は入力を終えて保存ボタンを押している。** **⇒ 手元に未保存の作業がある。**

**★先例がそのまま当たる**——**§11.2 の版不一致の規律**：

> **★読み込み直すと自分の編集が消えることを、押す前に伝える。**

**⇒ 文面と配置を §11.2 の 4 点に揃える**（入力を保持したまま表示する ／ 進む道を示す ／ 消えることを押す前に伝える ／ 「失敗」と書かない）。

**★あわせて 2 点。**

- **どれが該当したのかを、人が読める文字列付きで示す。** **該当が複数のときは選ばせる**（**★「1 件目を復元」としない**）。
- **復元後は詳細画面へ行く。編集画面へは行かない**（**★復元したものと、いま入力した内容は違いうる**）。

| **3** | **入力中（リアルタイム）にダイアログを出す** | **★入力のたびにモーダルが出る。** コンボ側には既にリアルタイム警告の表示が在り、それは変えない |
| **4** | **サーバへ「確認済み」フラグを送って警告を抑制する** | **★サーバが「確認済み」の意味を持つと、API を単体で叩いたときの意味が曖昧になる。** 抑制は画面側で行う |
| **5** | **復元後に編集画面へ行く** | **★復元したものと、いま入力した内容は違いうる**（判定キーとレシピは同じでも memo やダメージは違う）。**利用者に「戻したものを見る」機会を先に与える** |
