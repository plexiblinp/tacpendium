## 1. ★★§2-1——**`DES-002` §11.3 契約 (4) との正面衝突**

### 1.1 何が起きたか

**`DES-002` §11.3 の契約 (4) は「★E2E は CI に載せない。載せる前提の設定が未適用であり、受入条件も未達である。★否定形で書いておかないと、次の担当が再実行で緑にして載せる」と明文化していた。**

**⇒ 本サブは nightly へ E2E job を載せた。**

**★★製造の独自発案ではない。** 指示書 §4.3 ／ `D-594` ／ `CHANGE-145` §2.2 が明示的に命じている。

**★★原因は設計卓にある**——**`CHANGE-145` の影響設計書欄が `SUPP-001` §5.5 / §4.5 のみで `DES-002` を含まず、起票時に本契約が 1 度も参照されなかった。**

### 1.2 裁定＝**(a) 受理して契約 (4) を改訂する**

**★根拠＝本契約が挙げていた 2 つの理由が、どちらも消えていた。**

| 契約が挙げた理由 | 現状 |
|---|---|
| **「載せる前提の設定が未適用」** | **`workers: 1` は `CHANGE-135` / `M24-09c` で適用済み。** `reporter` / `retries` は **「調整しない」が積極的な判断として立った**（§3） |
| **「受入条件も未達」** | **CI 実機で緑、かつ件数がローカルと一致**（**215 passed** / failed 0 / flaky 0。2026-08-30 開発者がマージ前に手動起動） |

**★★製造の「緑よりも件数一致のほうが強い根拠である」という主張を採る。** **`E-125`〔緑だが 1 件も走っていない〕の排除であり、本サブの主題「緑は根拠にならない」と一貫している。** **⇒ 改訂後の契約へ「受入は緑ではなく件数の一致で見る」を書き込んだ。**

### 1.3 ★★設計卓が足した 1 点——**`flaky` の扱い**

**`retries: 1` のまま回すと「1 回目赤・retry 緑」が緑として報告されうる**——**`M24-09c` / `CHANGE-135` が「flake 対策の成否は緑の回数では判定できない」と書いた面である。**

**★実測を見ると Playwright は `passed` / `failed` / `flaky` を別に数えている**（§1-3 の報告が 3 つとも出ている）。**⇒ 情報は失われない。**

**⇒ 契約へ「判定は 3 つを見る。`flaky > 0` は緑ではない扱いにする」を書き足した。** **★これが無いと、`retries: 1` を維持した判断（§3）が「flake を隠す」形に転ぶ。**

### 1.4 撤回の記録

**★★契約本文には旧記述を打ち消し線で残し、撤回の経緯を書いた。** **理由＝この契約は「次の担当が再実行で緑にして載せる」と予告していた。★実際に起きたのはそれではない。**

**⇒ 予告つきの否定形契約でさえ、参照経路が無ければ機能しない。★契約を書くことと、契約が読まれることは別である。**

## 2. §2-2——**`web/CLAUDE.md` の 1 行の内容差し替え**

### 2.1 裁定＝**受理。設計卓が指定した内容が誤りだった**

**指示書 §4.4 は「`tsc --noEmit -p tsconfig.json` はテストファイルを型検査しない」を逐語で指定した。⇒ 製造の 4 通りの実験（A〜D）で再現しなかった。**

**実測**——`pnpm exec tsc -p tsconfig.json --listFilesOnly` は **`*.test.ts(x)` を 198 本読んでいる**。`web/tsconfig.json` は単一プロジェクトで `include: ["src","vite.config.ts"]`。**⇒ 守備範囲は `pnpm build` と同一であり、外れているのは `web/e2e/`（spec 58 本）と `playwright.config.ts` である。**

**★★これは設計卓の誤りである（計測点 `M-100`）。** **出所は `M24-13` 完了報告 §10 であり、`D-598` で設計卓が「これは教訓ではなく事実である」と格上げした。** **★「事実である」という判断をしたのは設計卓であって、その根拠を確かめていない。**

**★★機序＝1 回の実行からの一般化を、母数を出さずに恒久資料へ書かせようとした。**

### 2.2 followup の扱い＝**閉じない。書き換える**

**★「`tsc --noEmit` はテストファイルを型検査しない」は誤りなので消す。★しかし `web/e2e` と `playwright.config.ts` が型検査外である事実は残る。**

**⇒ スラッグを `e2e-specs-not-type-checked` へ書き換え、未着手で残した。** **★実害の芽＝E2E spec の型エラーは `pnpm build` でも `tsc --noEmit` でも捕まらず、Playwright の実行時まで分からない。** **★これは `SUPP-001` §4.5 の「積み残し」そのものである**（製造の指摘）。

## 3. §2-3——**`retries` / `reporter` の調整を実施しなかった**

### 3.1 裁定＝**受理。しかも製造の判断のほうが正しい**

**製造の理由＝「本 job の目的は『main の E2E が緑か』を観測することである。ローカルの `make e2e` と別条件で回すと、nightly が観測しているものがローカルと別物になる。『nightly は緑だがローカルは赤』が起きたとき、差が実装なのか設定なのか切り分けられなくなる。」**

**★★設計卓が §4.3 の表へ「調整」を書いた根拠は、旧除外理由の逐語をそのまま写したことだけだった。** **⇒ 「なぜ調整が要るのか」を自分で確かめずに、失効しつつある理由を指示へ転記していた。**

**★`reporter: dot` は旧除外理由に出てくるだけで、`list` で CI ログとして困る点は無かった**（製造の実測）。

### 3.2 反映

**`SUPP-001` §4.5 へ「nightly はローカルと同一設定で回す。それが観測の目的である」を明文化した。**

## 4. §1——**as-built の反映**

### 4.1 `SUPP-001` §5.5.4（新設）——テンプレート方式

| 追加 | 内容 |
|---|---|
| **保存先** | **メモリ上のバイト列**（ファイルとして残さない）。**★理由＝Go にはプロセス終了時に走る後片付けの経路が無く、ファイルで持つとテストバイナリ 1 本につき 1 個の DB が残る。★バイト列なら `-wal` / `-shm` の混入経路も構造的に消える** |
| **観測点** | **マイグレーション実行回数**（`MigrationRunCount()`）。**★速度ではない** |

### 4.2 ★★`CHANGE-145` に無い機構 1 つ——**除外の「逆向き」のガード**

**`CHANGE-145` §5 のリスク 2 は「除外すべきパッケージを見落とす」だけを挙げていた。⇒ 逆向き（除外すべきでないパッケージが除外される）に検出器が無かった。**

**★★逆向きは静かに壊れる**——**除外しすぎても、テストは全部緑のまま遅くなるだけである。** **★本サブが立てた「速度は根拠にならない」の裏返しがそのまま当てはまる。**

**⇒ 製造は許可一覧ガードを足した**（一覧外からの呼び出しは実行時に落ちる）。**⇒ `SUPP-001` §5.5.4 の規約 4 として反映した。**

**★★これは一般形として価値がある**——**「速度でしか差が出ない変更」を入れたら、その裏返しにも検出器が要るかを 1 度問う。** **⇒ playbook §4.53 へ。**

### 4.3 ★除外が現時点で no-op であることも書いた

**破壊確認 2 で除外を外しても赤くなったのは本サブが足した観測 1 本だけで、既存 99 テストは全緑・所要も 0.9 秒しか変わらない。**

**★★製造がこれを隠さず書いた点を評価する。** **「効いていることを示せた」で止めると、後任は除外の実際の射程を誤解する。** **⇒ `SUPP-001` §5.5.4 へ「それでも残す理由」とともに記録した。**
