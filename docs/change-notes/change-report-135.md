## 2. ★★設計卓が自分の記述を訂正したもの（3 件）

### 2-1 ★★`SUPP-001` §4.5 の「動的ポート読取」は、役割そのものが誤っていた

**旧記述の逐語＝「`resolveBackendPort()` が起動時に `config.toml` を読み、バックエンドの実ポートを動的取得」。**

| 誤り | 実装 |
|---|---|
| 関数名 `resolveBackendPort()` | **`readDevBackendPort()`**（実装に前者は存在しない） |
| **★役割「バックエンドの実ポートを動的取得」** | **★★`scripts/wt-new.sh` が作る worktree ごとのポートオフセットの決定。** バックエンドのポートは **`COMBOMGR_PORT`** で明示的に渡される |

**★★この誤りが `CHANGE-135` v1.0.0 §2.2 の想定（「読み先を揃えないとポートがずれる」）を生んだ。** **⇒ 揃えさせると、むしろ worktree のポート分離が壊れる指示になっていた**（計測点 `M-83` ／ `D-569` で撤回済み）。

**⇒ §4.5 へ「E2E 専用 config へ切り替えてはならない」を明記した。**

### 2-2 ★★`D-569` の理由付けに、成り立たないものが 1 件あった（計測点 `M-84`）

**裁定は `embed_web` の代償として「React が dev → prod になり `StrictMode` の effect 二重実行が消える」を挙げた。**

**★★これは `vite preview` でも同じく起きる。** `vite preview` が配るのは `vite build` の成果物であり、React は production モードで動く。

**⇒ 2 案を分ける論点ではなかった。採った案でも失う検査である。**

**★★製造は最初の判断依頼で「`vite preview` ではこのうち 6 と『dist の鮮度』の 2 件だけが残ります」と明記していた。設計卓はそれを読んだうえで、同じ項目を `embed_web` 側の理由へ流用した。**

**★裁定の結論（`vite preview`）は変わらない。** **分ける論点として残るのは 2 つである**——**(1) `launchBrowser` の運用障害**〔抑止手段が無く、抑止には本番コードの 3 か所目が要る〕 ／ **(2) 静的要求が全ミドルウェアを通り、ページ遷移ごとに余計な DB 参照とアクセスログが出ること。**

**⇒ §4.5 の「採らなかった案」の理由を 2 つへ直して書いた。**

### 2-3 ★★速度の数字を差し替えた

| 出所 | 値 | 状態 |
|---|---|---|
| `CHANGE-135` v1.0.0 | 現状 386 秒 → `embed_web` 156〜158 秒 | **★再現しなかった** |
| `CHANGE-135` v1.1.0 | 現状 307〜309 秒 ／ `vite preview` 156〜159 秒 | **★再現しなかった** |
| **★as-built（同一セッション背中合わせ・同一 HEAD・`workers: 1`・180 テスト）** | **`pnpm dev` 402 秒 ／ `vite preview` 223 / 225 / 253 秒**（一発緑 3/3）。**`pnpm build` の上乗せは 20〜27 秒** | **★これが正本である** |

**★★同じ環境が別時点で 307〜309 と 402 を出しており、環境側の変動幅のほうが比べたい差より大きい。** **⇒ 別時点の値どうしを引き算しない。**

**★`embed_web` との同一セッション比較は取られていない。** **⇒ 「速度は実測で同じ」とは、もう書かない。**

**★★ただし `D-569` は速度ではなく影響範囲で決めており、この訂正は裁定の前提を崩さない**（裁定文自身が「決め手は速度ではない」と明記している）。
