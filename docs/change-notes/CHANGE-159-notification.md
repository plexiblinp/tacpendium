## 1. 新設した経路 2 本（`DES-002` §4.2）

### 1.1 `POST /api/combos/:id/acknowledge-version` — 「確認した」

**基準（`combos.baseline_version`）を `games.current_data_version` へ進める。**

| 状況 | ステータス | コード |
|---|---|---|
| 成功 | **200**（`ComboResponse` を返す） | — |
| `:id` が整数でない | 400 | `invalid_id` |
| 対象が無い／**論理削除済み** | 404 | `not_found` |
| write lock を取れない | 503 | `database_busy` |
| それ以外 | 500 | `internal_error` |

**母集団の述語＝`WHERE id = ? AND deleted_at IS NULL`。⇒ ゴミ箱の行は「確認した」にできない。★仮登録は対象に含む**（下書きも基準を持つため）。

**★★持たせなかった分岐（読む側が誤読しないために要る）**

| # | 内容 |
|---|---|
| **★★1** | **要求本文を取らない。版数をクライアントから受けない。⇒ 任意の版へ「進めた」ことにできない** |
| **★★2** | **楽観的排他を要求しない**（`version` を受けず、上げもしない）**。⇒ 409 は無い。★理由＝基準の前進はコンボの内容の変更ではなく「利用者が見た」ことの記録であり、他端末で編集中の版を無効にしない** |
| **★★3** | **一括操作は無い。1 件ずつだけである**（部分消化＝`M28-overview` §3.2.7 の軸 3）**。⇒ `M28-02b` が一括を採るなら経路の追加が要る** |
| **4** | **冪等ではないが安定である。** 同じ版のまま何度呼んでも結果は変わらない |
| **5** | **`updated_at` を進める。⇒ 更新日時順の一覧では並びが動く。★据え置くと「いつ確認したか」がどこにも残らない** |

### 1.2 `GET /api/combos?affected_by_game_update=true|false`

| 値 | 挙動 |
|---|---|
| `true` | 影響可能性ありのみ |
| `false` | 影響なしのみ |
| 省略 | 絞り込まない |
| **上記以外** | **400 `invalid_query_param`** |

**★値域外を 400 に落としたのは既存の `setup_in_corner` と同じ扱いである**——「絞り込まない」に倒すと typo が全件返却に見える。**★既存の `position` / `hit_type` / `opponent_stance` は値域を見ない**（既存挙動。本フィルタだけが bool のため厳密に見る）。

### 1.3 `ComboResponse` に足した 4 欄

| JSON | 型 | 備考 |
|---|---|---|
| `baselineVersion` | `string?` | `omitempty` あり |
| `affectedByGameUpdate` | `bool` | **★★`omitempty` を付けていない**——**`false` は「影響なし」という情報であり、キーが消えると「判定していない」と区別が付かない** |
| `startPositionMass` | `int?` | 0〜160 |
| `carryDistanceMass` | `int?` | 0〜160 |

**★`POST` / `PUT` が受けるのは `startPositionMass` / `carryDistanceMass` の 2 欄だけである。`baselineVersion` / `affectedByGameUpdate` は受けない。★`PATCH` には 4 欄とも無い**（`followup` `combo-baseline-not-advanced-on-patch`）。

## 2. `FR702` の判定（`REQ-001` ／ `DES-003`）

**★★保存しない。SELECT のたびに導出する。⇒ 影響コンボを持つ表は無い。**

```sql
EXISTS (
    SELECT 1 FROM combo_steps cs
    JOIN moves m ON m.id = cs.move_id
    WHERE cs.combo_id = combos.id
      AND m.last_changed_game_version IS NOT NULL
      AND (combos.baseline_version IS NULL
           OR m.last_changed_game_version > combos.baseline_version)
)
```

**★判定式は 1 か所しかなく、SELECT の派生列と一覧の WHERE が同じ式を共有する**（書き写すと表示と絞り込みが静かにずれる）。

### 2.1 ★★2 種類の NULL は向きが逆である

| 状態 | 判定 | 根拠 |
|---|---|---|
| **基準が NULL** | **影響可能性あり** | **「いつの前提か分からない」＝不明。⇒ 安全側**（`FR307` と同じ向き）**。出し漏らさない** |
| **マーカーが NULL** | **影響なし** | **★これは「不明」ではない。** `D-725` により「初回公開より前は存在しない」＝**「まだ一度も変わっていない」という既知の状態** |
| `move_id` が NULL のステップ | 判定に入らない | `JOIN moves` で構造的に落ちる |
| マーカー ＝ 基準（同値） | 影響なし | 基準より**新しい**ものだけを出す |

**★★混同すると、出し漏らすか（基準 NULL を影響なしに倒す）、全件が出続けるか（マーカー NULL を影響ありに倒す）のどちらかになる。★どちらも `NULL` という同じ値で表されるため型では区別できない。⇒ 設計書に書くことが唯一の防御である。**

## 3. ★★本スキーマ初の `CHECK` 制約を受理した（`DES-003` §3.4）

| 項目 | 内容 |
|---|---|
| **反した先** | `DES-003` §3.4＝「**CHECK 制約は DB 側に付けず、アプリ層で制約する方針**」（**実測＝着手前の 103 マイグレに CHECK は 0 件**） |
| **なぜそうなったか** | **★指示書 §2.2-3-b が DB 側の `CHECK` を名指しで要求した**（「入口を全部塞ぐこと——DB 側の `CHECK` 制約 ／ アプリ側のバリデーション ／ マイグレで投入する値そのもの」） |
| **裁定** | **★★受理する** |

### 3.1 ★★受理の理由は 2 つある。どちらか一方では足りない

| # | 理由 |
|---|---|
| **★★1** | **アプリ層だけでは塞げない経路が在る。** マーカーを立てるのは配信者であり、**その経路は DML マイグレ＝生 SQL である。⇒ サービス層を通らない** |
| **★★2** | **壊れ方が静かである。** `YYYY.MM.DD.NN` は**固定幅が崩れた瞬間に辞書順が壊れる**が、**エラーにはならない**。**⇒ 「間違ったまま動き続ける」** |

**★★§3.4 の方針を撤回しない。⇒ 例外の条件を書く**（下記）。

### 3.2 例外の条件（**★★これを満たさないものに CHECK を付けない**）

| # | 条件 |
|---|---|
| **1** | **アプリ層を通らない書き込み経路が実在すること**（DML マイグレ・生 SQL・外部ツール） |
| **2** | **値が壊れても実行時エラーにならず、結果だけが静かに狂うこと** |
| **3** | **値域が固定であり、仕様変更で動く見込みが小さいこと**（§3.4 が CHECK を避けた理由＝「変更時の手間が大きい」に直接当たる） |

**★★3 つすべてを満たすときに限る。⇒ 「範囲を守りたい」だけでは足りない**——`drive_available_at_start` / `sa_gauge_consumed` / `drive_gauge_consumed` は条件 1 を満たさないため CHECK 不使用のままである。

> **★実測が 1 つ味方している**——**`ALTER TABLE ... ADD COLUMN` のインライン `CHECK` は通り、`DROP COLUMN` も CHECK 付き列に対して通る**（`modernc.org/sqlite v1.50.0`）**。⇒ テーブル再構築を伴う down は不要だった。★§3.4 が挙げた「変更時の手間」は、少なくとも列単位の追加・削除については想定より小さい。**

## 4. `position` が 5 値 → 7 値になった（`SUPP-001` §3.2 ／ `DES-003` ／ `DES-005`）

| 順 | code | ラベル | マス | 代表値 |
|---|---|---|---|---|
| 1 | `corner_self` | 自分画面端 | 0〜25 | 12 |
| 2 | `corner_self_near` | 自分画面端寄り | 26〜47 | 36 |
| 3 | **`mid_self`** | **自分中央寄り** | 48〜69 | 58 |
| 4 | `mid_screen` | 画面中央 | 70〜90 | 80 |
| 5 | **`mid_opponent`** | **相手中央寄り** | 91〜112 | 102 |
| 6 | `corner_opponent_near` | 相手画面端寄り | 113〜134 | 124 |
| 7 | `corner_opponent` | 相手画面端 | 135〜160 | 148 |

### 4.1 ★★「値域」と「表示順」は別に数える

**★指示書 §2.4.6-1 の「既存の 5 区分はそのまま残り、間に 2 つ挿入されるだけである」は、値域の話としては正しいが表示順の話としては誤りだった**（計測点 `M-130`）。

**表示順では末尾 2 値の順序も入れ替わっている**——旧 `corner_opponent, corner_opponent_near` → 新 `corner_opponent_near, corner_opponent`。

**★副作用＝エディタの数字キー割当が動く**（`shortcutKeyForIndex` は index+1）。

| 値 | 旧キー | 新キー |
|---|---|---|
| 画面中央 | **2** | **5** |
| 自分画面端 | 3 | 2 |
| 相手画面端 | 5 | **8** |

**★ボタン数は 8（不問込み）で上限 10 の内側。⇒ ボタン群のまま。★開発者が「問題なし」と確認済み**（2026-09-06）。

### 4.2 マス数 ⇄ 区分の不変条件

| 入力 | 振る舞い |
|---|---|
| **マス数あり** | **マス数が勝つ。**`position` を区分表から導出して上書きする |
| マス数なし・`position` あり | `position` の**代表値**をマス数へ入れる（**★既存エディタはこの経路。⇒ 現行画面は無改修で動く**） |
| どちらも無し | 両方 NULL（不問） |

**★★正規化は重複判定より前に呼ぶ必要がある**——判定は `input.Position` を直接読む箇所が 3 つあり、**正規化前に走ると「マス数から導いた区分」ではなく「送られてきた区分」で重複を見てしまう**。

**★`position` は列として残した。⇒ `DuplicateKey` は 1 文字も変えていない**（重複判定キーの 1 項であり 6 か所の SQL 述語が直接比較しているため、導出にすると判定のたびに `CASE` の計算が要る）。

## 6. CSV 列契約へ 2 列（`DES-002` §7.6）

**末尾へ任意列として `start_position_mass` / `carry_distance_mass`**（`oki_verified` の先例どおり）。

**★★`baseline_version` は載せない**——**DB 管理列であって利用者の入力ではない**（先例＝`materialized_from_combo_id` / `superseded_by_combo_id`）。

**★載せた理由**——載せないと**出力 → 取込で値が消える**。始動位置は `position` の代表値へ丸め戻され（73 が 80 になる）、**運び量は `position` から逆算できないため完全に失われる**。

**★後方互換**＝旧 CSV の取込は通る（必須列 22 は不変）／ 新 CSV を旧版へ食わせると unknown 列の**警告**であり取込は止まらない。

## 7. 裁定 2 件

### 7.1 `VAL-RANGE` → **`VAL-C16` を採番する**

| 項目 | 内容 |
|---|---|
| **製造の判断** | マス数の値域（0〜160）を弾く必要があるが `VAL-Cxx` を自採番できないため、記述的コード `VAL-RANGE` を使った（**★先例＝`VAL-ENUM`**） |
| **★★裁定** | **`VAL-C16` を採番する。⇒ 実装は置き換える** |
| **理由** | **★★本検証はサービス層に居る**（`internal/service/validation/combo.go`）**。⇒ `VAL-C04` / `C05` / `C13` と同じ族＝本体の範囲検証である。★`VAL-ENUM` は `csvcore` 層だけの記述的コードであり、族が違う** |
| **★as-built の注記** | **実装は当面 `VAL-RANGE` を返す。⇒ 置き換えは `followup` `val-range-code-not-numbered` として登録した。★設計書と実装のずれを黙らせず、見える形で残す** |

**★あわせて `DES-006` へ「`csvcore` 層の記述的コードは番号を持たない別の族である」と明記した。⇒ 「記述的コードは使わない」という契約は現状の実装と合っていない、という製造の指摘は正しい。**

### 7.2 マイグレ 1 本／アップデートの運用負荷 — **許容する**

**★製造が判断を求めた点**（`M28-overview` §3.2.8 の軸 10＝開発者のアップデート対応のしやすさ）。

**★★設計卓の評価＝許容できる。理由 3 つ。**

| # | 理由 |
|---|---|
| 1 | **SF6 のバランス調整は年に数回である。⇒ 頻度が低い** |
| 2 | **手順が 4 行で固定されており、生成は `seedgen` が行う。⇒ 人が SQL を書かない** |
| 3 | **★連番の払い出しは既に設計卓の一元管理である**（`D-293`）**。⇒ 新しい運用を足していない** |

**★★ただし条件が 1 つある**——**連番の払い出しが設計卓を経由する以上、開発者が単独でアップデート対応を完結できない。⇒ 公開後に設計卓が常駐しなくなったら、この手順は成立しない。★`followup` `game-version-migration-serial-requires-design-desk` として登録した。**
