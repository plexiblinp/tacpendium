## 1. ★★最も重い 1 件 — `materialize` の抜け穴が塞がった

**着手前、`POST /api/combos/{id}/materialize` は `ValidateComboForCreate` を一度も呼ばず、`gen := *base` で基底を複製して `InsertCombo` していた。⇒ 必須 4 欄が空の【本登録】コンボが生成できた。**

**★製造の実測**（着手前の probe）:

```
生成された combo id=2  isDraft=false
damage=<nil> knockdownAdvantage=<nil> driveGaugeConsumed=<nil> saGaugeConsumed=<nil>
```

**★★これは `M27-02b` が入れた必須化の穴であり、UX の改善ではなく欠陥だった**（`M31-overview` §2.3 がそう位置づけていた）**。**

### 1.1 反映（`DES-002` §4.2 の `VAL-C15` 経路表）

**★逐語「`Materialize`（確定反撃からの生成）｜ ★走らない ｜ `ValidateComboForCreate` を呼ばない。⇒ 必須 4 欄が空のまま本登録コンボが生まれうる」が失効した。**

**⇒ 「通る」へ書き換え、母集団の述語と持たせなかった分岐を書く。**

| 項目 | 内容 |
|---|---|
| **母集団の述語** | **生成物が本登録になるときだけ**（`gen.IsDraft == false`）**。★`gen.IsDraft` は基底からの複製であるため、仮登録の基底から生成した物は仮登録であり必須 4 欄を要求しない**（`VAL-C15` は仮登録を完全スキップする＝`M27-02b`） |
| **判定の位置** | **書き込みトランザクションの内側・`INSERT` の前。⇒ `VAL-C02` と同じ位置である**（`M24-11` / `CHANGE-136`）**。★判定と書き込みの間に隙を空けない** |
| **★★持たせなかった分岐 (1)** | **FR301 の既存一致**（`alreadyExisted:true`）**は `VAL-C15` の手前で返る。⇒ 必須 4 欄が空の基底でも `200` で通る。★これは意図である**——**新しい行を作らないため。塞ぐと、既に在る確定反撃版へ到達する手段が消える** |
| **★持たせなかった分岐 (2)** | **既存の生成物**（4 欄が空のまま在る行）**の編集・保存の挙動は 1 文字も変えていない。★`PATCH` は着手前から `VAL-C15` で弾いていた**（`M27-02b`） |
| **移行** | **不要。⇒ 開発者裁定**（2026-09-08・逐語＝「そもそも今はもう空のデータは入らないはず。移行等は考えなくていい」） |

## 2. `DELETE /api/setups/{id}` にクエリパラメータ `unlinkFrom` が増えた

**★指示書 §2.4 は「セットプレイを削除したとき、紐付けを解除する」までで API の形を指定していない。⇒ 製造が確定させた。**

| 項目 | 内容 |
|---|---|
| 形 | `DELETE /api/setups/{id}?unlinkFrom=<comboId>` |
| **省略時** | **着手前と 1 バイトも変わらない**（`combo_setups` を残す） |
| 指定時 | **削除と同一トランザクション**で `DeleteComboSetup(comboID, setupID)` を呼ぶ |
| 不正値（`abc` / `0` / 負数） | **`400` `invalid_request`**（サービスを呼ばない） |
| 既に外れている | **冪等**（`ErrNotFound` を無視） |
| **★★消す範囲** | **指定された 1 組だけ。⇒ `DeleteComboSetupsBySetupID`**（全消し）**は呼ばない**——**`D-484` が撤回した案 P1 に戻ることになるため** |

**⇒ §4.2 の「変更後＝`deleted_at` の設定 ＋ `recipe_cache` の物理削除 の 2 つだけ」が失効した。★副作用は 2 つ → 3 つになりうる。**

## 4. `DES-005` §5.21（確定反撃マイリスト）— 第 3 セクションの内側を割る

**★開発者が承認した案 A＝第 3 セクションの内側を ①反撃に転用可能 / ②再利用可能 に割る。骨格は壊さない。**

### 4.1 ★★「PC 版が既にある」ぶんの扱い（**設計卓が逐語からずらした形を受理した**）

**★開発者の逐語**（`phase4-memo.txt:48`）**＝「①はすでにパニッシュカウンター版が作られているコンボはそのそも出さない。」**

**★★実装は「折りたたんだ別枠へ回し、その行の『確定反撃の採用を解除』だけは押せる」形である。**

| # | 受理した理由 |
|---|---|
| **★★1** | **丸ごと外すと、その行の解除手段が画面から消える。⇒ 同ファイルの既存コメント**（`PunishList.tsx:277-278`）**が「そこにしか現れないコンボの解除手段を残すため」に区分不明セクションが在ると書いている** |
| **★★2** | **逐語の意図は「① を汚さない」であって「解除手段を奪う」ではないと読んだ。⇒ 「① に出さない」は満たしている** |
| **★3** | **前例がある＝`DES-005` §5.20 が同じ問いに「畳む ＋ バッジ」で答えている。⇒ 形を揃えた** |
| **★4** | **戻すのは安い。⇒ 開発者が「逐語どおり完全に出さない」を選ぶなら、そのとき解除手段の置き場を別途決める** |

### 4.2 `hasMaterializedVersion` の新設

**`GET /api/punish-list` の `ComboNode` へ `hasMaterializedVersion?: boolean` を追加した。⇒ 「この基底コンボからパニッシュカウンター版が既に作られているか」を示す。**

- **材料は既存の `ListMaterializedBaseComboIDs`**（探す画面の §5.20 の畳み込みが使っているのと同じメソッド）**。⇒ 新しい判定を書き起こしていない。**
- **取得に失敗しても一覧そのものは落とさない**（`slog.Warn` を残してフラグを落とす）**。★`M23-04` の「検証が壊れても復元は落とさない」と同じ扱いである。**

### 4.3 振り分けの述語

**★①② の振り分けは既存の `PUNISH_COUNTER_HIT_TYPES` を見る。⇒ 変換ボタンの出し分けと同じ 1 本である。★新しい集合を書き起こすと片方だけ直って静かにずれる。**
