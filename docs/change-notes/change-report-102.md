## 2. ★as-built が起票内容から動いた点は無い。動いたのは「前提」である

**`CHANGE-102` §2 の a〜g はすべてそのまま反映できた。** **しかし着手前実査で、指示書 §9.2 が実装判断へ委ねていた 2 件の前提が崩れており、`D-360` で裁定した**（下記 §3）。**反映内容はその裁定を織り込んだ形になっている。**

### 2.1 `SUPP-001` §7.1 に無かった性質を §7.1.1 として新設した

**製造の実測**——**`RecomputePresetCache` は 4 兄弟のうち唯一 `*sql.Tx` を取らず、さらに内部の読みが渡されたトランザクションを見ない。**

**⇒ 書き込みトランザクションの内側で呼ぶと、コミット前のエイリアスが見えず「古い表記」を書き込む。** **エラーにならず、テストも lint も型検査も緑になる。** **加えて接続プールが無制限・`busy_timeout` 5 秒のため、開いた書き込み tx の内側から非 tx の UPDATE を撃つと別コネクションになり `SQLITE_BUSY`**（**製造が陽性対照で確認済み**——再計算をコミット前へ動かすと落ちる）。

**★同節は関数名とシグネチャを載せながらこの性質を書いていなかった。** **⇒ 同節を読んだ次の担当は「tx を取らないなら内側で呼んでよい」と読む。** **これが「誰かが必ず踏む地雷」の実体だった。**

**あわせて一般規約を書いた**（**D-360**）——**署名が `*sql.Tx` を取るなら、その tx を読みにも使う。使わないなら取らない。**

> **★同じ検査を他の行にも通した結果、`RecomputeComboCache` が逆の形で残っていることが分かった**（tx を取りながら preset / alias の読みが tx を見ない）。**今日は害が無い**（コンボ書き込み tx は `presets` / `preset_aliases` を書かない）**が、規約に照らせば逆である。** **⇒ followup `notation-recompute-combo-cache-tx-read-asymmetry`。**

### 2.2 `SUPP-001` §7.2 の呼出元表は、件数は合っていたが内訳が違った

| 旧記載 | as-built |
|---|---|
| `create.go` / `update_aliases.go` / `delete.go` の 3 ファイル | **3 ファイルとも存在しない。** 実体は 1 ファイルである |
| （記載なし） | **★`PUT /api/config`（既定プリセットの切替）が呼出元に加わる**（`D-313` の帰結） |

**★「作成」と「コピー」は同一経路である**——`POST /api/presets` が組み込みのエイリアスを複製する形で、独立した duplicate の経路は無い。**⇒ 指示書 §4.1-4 とチェックリストが数えた「4 経路」は、as-built では 3 経路だった**（**設計卓が §7.2 の「想定」を数えて書いたためである**＝ボード **M-59**）。

### 2.3 `SUPP-001` §7.4.1・§7.4.3 は失効した

**既定プリセットを表す固定値は 3 か所あった**（`D-313` の記録「2 か所」より 1 多い）。**3 つとも撤去し、値は注入で渡す形へ寄せた。** **⇒ 同期更新の対象は注入の配線 1 か所だけになり、§7.4.3 の列挙は歴史記録になった。**

### 2.4 `SUPP-001` §7.5.4 へ「明示的な例外」を書いた

**プリセットの作成経路とエイリアス更新経路の 2 つが、「メインの DB 操作と同一トランザクション」から外れる**（§3 の判断 1）。**★逸脱ではなく例外である**——**同節が守ろうとしている不変条件は「保存とキャッシュが食い違わないこと」だが、ここでの食い違いは stale であって不整合ではない。** **真実は `preset_aliases` にあり、キャッシュは再実行で回復できる。**

**★削除経路は例外に当たらない**（`DeletePresetCache` は tx を取り、既存トランザクションの内側にそのまま置ける）。

## 3. `D-360` の裁定 2 件（着手前実査を受けたもの）

| # | 論点 | 裁定 | 決め手 |
|---|------|------|--------|
| 1 | **再計算の境界** | **コミット後に、再計算だけを 1 つの境界で走らせる**（案 A）＋条件 2 つ（**署名が tx を取るなら読みにも使う** ／ **呼び出し順を固定する検査を置く**） | **読み経路を tx 対応にする案（案 B）を採らなかった**——**`SUPP-001` §7.5.4 が守る不変条件に照らすと、ここでの食い違いは stale であって不整合ではない。** **★`D-356` で開発者が許容した状態と同じ形でもある** |
| 2 | **既定プリセット値の寄せかた** | **注入で寄せる**（案 B）＋ **`punishfinder` の diff 0 に明示的な例外** | **★設計卓の誤りである**——**「diff 0」と「固定値を 1 か所へ寄せる」が両立しなかった**（寄せ先の共有関数を `punishfinder` が呼んでいる）。**可変プロセス状態で diff 0 を保つ案は、検査を通しつつ振る舞いを同じだけ変える形だった** |

**★判断 2 から一般則を 1 つ立てた**——**diff 0 は不変条件そのものではなく proxy である。** **proxy を守るために振る舞いを隠す形を採ったら、proxy は嘘をつくようになる。** **⇒ proxy を外し、不変条件を直接測る検査へ置き換える**（**既定プリセットを変えても候補集合が変わらない**）。**製造は当該検査に陽性対照まで内蔵している**（表示文字列のほうは実際に変わる）。

**★例外は `m20-contract` §5 の F-3 へも写した**（**製造の指摘**）。**F-1 が M21 契約にも写してある運用と揃える**——**片方だけ直さない。**
