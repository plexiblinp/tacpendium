## 1. 不変条件

### 1.1 成り立つもの（**3 経路すべて**）

```
position が区分  ⇒  start_position_mass IS NOT NULL
（対偶）start_position_mass IS NULL  ⇒  position = 不問
```

**★`POST` / `PUT` / `PATCH` の 3 経路で成り立つ。⇒ `PATCH` は `M37-05` で揃った。**

**★★★NULL の意味は 1 つである＝「区分が不問である」。⇒ 「未測定」「クリア済み」といった 2 つ目の意味を持たせない**（`D-864`）**。**

### 1.2 ★★★成り立たないもの（**逆向き**）

```
start_position_mass IS NOT NULL  ⇒  position が区分     ★これは成り立たない
```

**★★`position` が不問の行へ `startPositionMass: 80` を送ると、`position` は NULL のまま値だけが入る。**

**★★★これは欠陥ではなく、3 つの制約が同時には成り立たないためである。**

| # | 制約 | 出所 |
|---|---|---|
| **1** | **`PATCH` は `position` を書かない** | **`position` は重複判定キーであり、`PATCH` は「識別キーが変わらない編集」の経路である**（`CHANGE-195` §2.3 / §2.4） |
| **2** | **`PATCH` は新しい拒否を足さない** | **開発者の逐語＝「API を直接叩く経路は基本的に想定しなくていいです」**（`D-864`） |
| **3** | **逆向きの不変条件を守る** | — |

**⇒ 1 と 2 を守る限り、3 は `PATCH` では守れない。★★設計卓が当初 `⇔` と書いたのは誤りであった**（計測点 `M-177`）**。**

### 1.3 ★★逆向きを実際に閉じているもの（**2 つだけ**）

| # | 何が | どこまで |
|---|---|---|
| **1** | **画面がマス数から区分を導出する** | **★UI からは不問 ＋ マス数の状態を作れない** |
| **2** | **区分が変われば `PUT` へ振り分けられ、`normalizePositionAndMass` が導出する** | 同上 |

**★★★どちらも*画面*である。⇒ API を直接叩く経路は射程外である**（`D-864`）**。**

**★★★したがって本節を「3 経路で成り立つ」と*無限定に*書かないこと。⇒ 書くと、実装が保証していない契約が設計書へ入る。**

## 2. `DES-002` §4.2 — `PATCH /api/combos/{id}` が補完する

**★`CHANGE-195` §2.3 の「持たせなかった分岐 1」が変わった。⇒ 着手前の `PATCH` はマス数を送られたとおりに保存していた。**

### 2.1 保存される値（**as-built**）

| 要求本文 | DB の現在値 | DB の `position` | 保存される `start_position_mass` |
|---|---|---|---|
| `"startPositionMass": 80` | 何でも | 何でも | **80**（**★埋めない。利用者の値が勝つ**） |
| `"startPositionMass": null` | 何でも | **区分** | **★区分の代表値** |
| `"startPositionMass": null` | 何でも | **不問** | **NULL のまま** |
| **キーが無い** | **NULL** | **区分** | **★★区分の代表値**（**★メモだけの `PATCH` でも入る**） |
| **キーが無い** | 値あり | 何でも | **DB の値のまま**（**★埋めない**） |
| **キーが無い** | NULL | **不問** | **NULL のまま** |

**★代表値の出所は 1 本である**〔`12 / 36 / 58 / 80 / 102 / 124 / 148`〕**。⇒ 3 本目の表は作っていない。**

### 2.2 増分が無いもの

| 項目 | 状態 |
|---|---|
| 要求 DTO | **★1 バイトも変わっていない**（`CHANGE-195` のまま） |
| 応答 DTO | **★同上** |
| エラー契約 | **★同上。⇒ 補完で入る値は必ず 0〜160 であり、新しいエラーを返さない** |
| 母集団の述語 | **★同上**（識別キーが変わらない編集だけ） |

### 2.3 ★★★持たせなかった分岐（**`CHANGE-195` §2.3 を更新する**）

| # | 持たせなかったもの | 帰結 |
|---|---|---|
| **1** | **`position` を書く分岐** | **★★構造的に不可能である。⇒ 更新の入力に `Position` 欄が無く、SET 句にも現れない** |
| **2** | **マス数から `position` を導出する分岐** | **★★★`normalizePositionAndMass` を*そのまま*呼んでいない。⇒ *補完の半分だけ*を切り出して使う。★区分をまたぐマス数を `PATCH` へ直接投げても `position` は動かない**（破壊確認あり） |
| **3** | **`carry_distance_mass` を埋める分岐** | **★運び量は区分を持たず代表値の概念が無い**（`D-731` 不変条件 2）**。⇒ NULL は正常な状態である** |
| **4** | **不問の行を埋める分岐** | **★代表値が定義されていない。⇒ NULL のまま** |
| **5** | **CSV / API へ新しい拒否** | **★開発者が「想定しなくていい」と述べている**（`D-864`） |

## 3. `DES-005` §5.7 — 画面が「保存より前に」代表値を入れる

| 画面要素 | as-built |
|---|---|
| 始動位置の **マス目 / パーセンテージ** 欄 | **★欄から離れた時点で**、空欄かつ区分が決まっていれば**代表値が入る**。⇒ 不問なら空のまま |
| 入力中 | **★空のままである**（**★打ち直せる**） |
| **運び量** | **★★掛からない**（`D-731` 不変条件 2） |

**★★★これは「保存してから値が生えてくる見え方にしない」ための措置である。⇒ サーバ側も同じ補完を行うため保存結果は同じだが、利用者には「消したのに生えてきた」と映る。**

**★代表値の出所は区分ボタンを押したときと同じ 1 本である。⇒ 3 本目の表は作っていない。**

### 3.1 ★★入力部品に `onBlur` の口が増えた（**props の凍結を 6 → 7 へ**）

**★同部品の props は「区分の口を持たせない」ために完全一致で凍結されている**〔`D-731` 不変条件 2 を「付けられない形」で固定する 3 層の 1 層目〕**。**

**★★★緩和を受理した**（`D-871`。**開発者裁定済み**）**。⇒ 理由 3 つ。**

| # | 理由 |
|---|---|
| **1** | **`onChange` では埋められない。⇒ 毎キーストロークで発火するため、消して打ち直そうとした瞬間に元の値が戻り*打ち直せなくなる*。★確定の合図が要る** |
| **2** | **代表値の知識は親にしか置けない。⇒ 層 2 が同部品のソースに区分表の識別子が現れることを*禁じている*** |
| **3** | **★★層 2 は 1 文字も変えていない。⇒ 趣旨の本体は無傷である。★`onBlur` は区分と無関係な汎用の口であり、本部品は代表値も区分表も受け取らない** |

**★★★却下した代案＝親の要素で `focusout` をバブリングで拾う形。⇒ 凍結テストを 1 文字も触らずに済むが、*将来だれかが始動位置と運び量を同じラッパへまとめた瞬間に運び量まで埋まり、型もテストも何も言わない*。**

**★★運び量の呼び出しには `onBlur` を渡していない。⇒ 「運び量が埋まらない」ことが構造として保証される。★緩和の前より強い。**

## 4. `DES-003` §3.3 — 列の意味

**★既存の記述**〔マス数が勝つ ／ 代表値で補完 ／ 両方 NULL〕**は `POST` / `PUT` の正規化として引き続き正しい。**

**⇒ 足すのは 2 点である。**

| # | 足すこと |
|---|---|
| **1** | **`PATCH` も同じ補完を行う。⇒ 3 経路で「区分あり ⇒ マス数あり」が成り立つ** |
| **2** | **★★★NULL に 2 つ目の意味を持たせない。⇒ NULL は「区分が不問である」だけを意味する** |

**★★★§1.2 の限定を必ず添えること。⇒ 逆向きは成り立たない。**
