## 1. なぜ要るか

**★★設計書は「`original_move_id` で元技を辿れる」と 2 か所で書いている。⇒ 読んだ人は、入力面もその経路を使うと考える。★実装は使っていない。**

| 場所 | 記述 |
|---|---|
| `DES-004` `:129` | 「`rush_<元技code>` の命名で独立 move として登録する」／「`original_move_id` で対応する通常技を参照することで、ラッシュ版から元技を辿れる構造とする」 |
| `DES-003` `:382` | 同趣旨 |

**★どこにも「この命名が破れると入力面から到達できなくなる」と書かれていない。⇒ この差が `ryu` の 1 件を生んだ。**

---

## 2. 変更内容 — `DES-004` §3.2.1 へ 1 点を明文化する

> **★★入力面（仮想コントローラ）のラッシュ版解決は `move_code` の文字列一致のみで行い、`original_move_id` へのフォールバックを持たない。⇒ `rush_<元技code>` の対応が破れると、`original_move_id` が正しく解決していても当該技は入力面から到達できなくなる。★エラーにならず「押せないボタン」として並ぶ。**

**★実体**（as-built・2026-09-10 実測）:

| 何が | どこ |
|---|---|
| タブ判定 | `web/src/features/combo/moveSurfacing.ts:141-146` の `isOnUniqueTab`（**rush の code から `rush_` を外した文字列を `unique` の中に探す**） |
| 解決 | `web/src/features/combo/inputResolution.ts:60` の `resolveRushByCode`（**`m.code === 'rush_' + baseCode` の一致のみ**） |
| 帰結 | `DirectSpecPanel.tsx:63` がデータ駆動の非活性として扱い、`:71` の `disabled={targetId == null}` でボタンを不活性にする |

**★★★したがって壊れ方は「ボタンが出ない」ではなく「ボタンは並ぶが押せない」である。⇒ エラーも警告もログも出ない。★テストも lint も型検査も緑のまま通る。⇒ 人が実機で気づく以外に検出の経路が無かった。**

**★実例は 1 件だけである**（`ryu`。`M35-02` が是正）**。⇒ 基底技が `axe_kick_2`、rush 版が `rush_axe_kick` であった。★`original_move_id` は正常に解決していた。⇒ 「元技を辿れる」構造は生きていたのに、入力面はそれを使わないので救われなかった。**

---

## 3. ★★変更しないもの

| 対象 | 理由 |
|---|---|
| **`DES-004` §3.2.1 の `:320` 直下の注記** | **★★正しい。⇒ `rush_glowing_touch_1hits` ほか 4 件を dangling 参照**（`_1hits` とすべきところが `_1`）**として正確に記録している。★製造の初版レポートは「誤っている」と請求したが、それは誤読であった**（`M35-02` レポート §0）**。⇒ 直さない** |
| **`ryu` の `axe_kick` という値そのもの** | **設計書は個別の値を持っていない。⇒ 持たせると seed 波ごとに陳腐化する** |
| **`DES-004` `:129` ／ `DES-003` `:382`** | **記述そのものは正しい**（DB 上は辿れる）**。⇒ 足すのは「入力面はその経路を使わない」という 1 点である** |

---

## 4. 影響

- **★`rush_<元技code>` は「表記規則」ではなく「解決契約」である。⇒ seed で `move_code` を決めるとき、この対応を破ると静かに入力できなくなる**
- **★同型の残りは `original_move_code` の dangling 4 件であり、別の壊れ方である**（`followup` の `rush-original-move-code-typo`。**独立サブ・`000111`**＝`D-809`）
