## 2. ★★裁定——**契約違反 1 件は受理。誤っていたのは指示書のほうである（`D-532` / `M-73`）**

### 2.1 何が起きたか

**指示書 §5.3 の表・1 行目は次の期待を書いていた。**

> 保存前チェックの母集団から「削除済み」の条件を外す ⇒ **サーバ側のテストとフロント側のテストが赤くなる**

**実際は、サーバ側は赤くなり、フロント側は緑のままだった。**

### 2.2 ★★受理する

**理由は 1 つに尽きる**——**フロントのテストは API の応答を stub するため、サーバの問い合わせ条件の変更を原理的に観測できない。**

**★期待を満たす方法は「赤くなるように見えるテスト」を捏造することだけであり、それは破壊確認の意味を消す。**

**★製造は捏造しなかった。** 代わりにサーバ側へ受け皿を新設し、期待とのずれを完了報告へ明記した。**⇒ 正しい振る舞いである。**

**★チェックリスト §9 が求めていたのは「破壊確認 2 件が実施され、コマンドと出力が完了報告に在ること」だけであり、期待欄との一致までは求めていなかった。** **重大判定には当たらない。**

### 2.3 ★★誤りは設計卓の側にある（`M-73`）

**「サーバとフロントの両方が赤くなる」と対称に並べたが、対称の根拠を確かめていなかった。**

**★これは `M-69`（理由の無い対称）と同じ型であり、設計卓としては 2 件目である。**

**⇒ playbook §4.28 を新設した。**

| # | 規則 |
|---|---|
| 1 | **期待に挙げるテストは、壊す対象と同じ層のものだけにする** |
| 2 | **層をまたぐ期待を書きたいなら、その継ぎ目を実際に通るテストを名指しする**（本プロジェクトでは実 DB を通る E2E だけ） |
| 3 | **「両方」と対称に並べる前に、対称の根拠を確かめる** |

**★★チェックリスト側の要求は「実施とコマンドと出力」に留めること。** **期待欄との一致を重大判定にすると、捏造が正解になってしまう。**

## 4. `DES-005` §5.15——**「既知の限界」を撤去し、「登録の前に選ばせる」を置いた**

**`M23-05` の反映時に書いた「警告は保存の成功後に出るため、利用者は重複を作ったあとでしか気づけない」は、本サブで解消した。** **★撤去しないと、設計書だけが古い前提を語り続ける。**

**★新設したブロックで、落としてはいけない点。**

- **選択肢は 3 つ**——**★「両方入れる」は出していない**（**D-519** の裁定どおり。開発者の当初の提案には在った）。
- **★★消えることを、押す前に伝える**——**「復元すると、いま入力した内容は保存されません」を復元ボタンの直上に常時表示する。押した後ではない。**
- **既定選択なし・名前が無い行も必ず出す**（落とすとその行は二度と復元できなくなる）。
- **★件数上限を掛けない**——**警告の `details` とは用途が違う。** `details` は「どの行が該当したか」を知らせるもので、多いときは総数を伝えれば足りる。**ダイアログは「そのどれを復元するか」を選ばせるため、切ると選べない行が生まれる。**
- **★仮登録では出さない**——**出す側に倒すと「保存後には出ない警告が、保存前だけ出る」非対称が生まれる。**

## 5. `DES-006`——**モーダルの可否を決めるのは severity ではない**

**§11.1.1 を新設した。**

| 種別 | 形 |
|---|---|
| **警告の表示** | 利用者は読むだけで、そのまま進める ⇒ §11.1 のとおり |
| **★操作の分岐** | **選ばないと次へ進めない** ⇒ **モーダルが正しい** |

**★先例＝`VAL-N02`。** **★書かないと、次の担当が「WARNING なのにモーダルだ」を欠陥として起票する。**

**★★実際、`M23-05` の指示書は §11.1 を根拠に「モーダルにしない」と指示していた。** **そのときは正しかった**（当該の警告は読むだけのものだった）**が、根拠の引き方が残ると、次に「選ばせる」warning が出たときに同じ引き方をされる。**

**★あわせて §2.1 へ「保存前チェックの母集団は `VAL-C14` / `VAL-S07` と同一実装を共有する」を明記した。** **「同じ条件にする」ではなく「同じ 1 本を呼ぶ」**——**条件で書くと 2 本目が書き起こされて静かにずれる。**
