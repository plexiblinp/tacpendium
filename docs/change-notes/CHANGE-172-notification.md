## 1. ★★`DELETE /api/tags/{id}` のエラー契約（**`DES-002` §4.2 へ新規記載**）

### 1.1 全行

| 状況 | ステータス | コード | `details` |
|---|---|---|---|
| ID が正の整数でない | `400` | `invalid_id` | 無し |
| **他人のタグ ／ 存在しないタグ** | `404` | `not_found` | 無し |
| 使用中のタグを `force` 無しで削除 | `409` | `tag_in_use` | **有り**（§1.2） |
| それ以外の失敗 | `500` | `internal_error` | 無し |
| 成功 | `204` | — | 本体無し |

### 1.2 ★★`409 tag_in_use` の応答（**逐語**）

```json
{"error":{"code":"tag_in_use","message":"このタグは使用中です。確認の上削除してください","details":{"forceDeleteQuery":"?force=true","usageCount":3}}}
```

| キー | 型 | 意味 |
|---|---|---|
| `usageCount` | number | **そのタグを付けたコンボの件数** |
| `forceDeleteQuery` | string | **強制削除に付けるクエリ。値は常に `"?force=true"`** |

**★★旧キーは `usage_count` / `force_delete_query` であった。⇒ `CLAUDE.md` §4**（JSON タグは camelCase で統一）**に従って改名した。**

**★実査＝タグ以外のハンドラの `details` は元から camelCase であった**〔`aliasText` / `existingId` / `combos` / `validations` / `limit` / `field`〕**。⇒ タグが唯一の逸脱であり、本修正で API 全体が揃った。**

### 1.3 ★★持たせなかった分岐（**読む側が誤読しないために要る**）

| 分岐 | 実装 |
|---|---|
| **他人のタグに対する `403`** | **無い。`404` を返す**（**存在そのものを明かさない**） |
| **他人のタグに対する `409`** | **無い。★試験で固定してある**（§3） |
| `details.existing_tag_id` | **廃止した。★元から 1 か所も返していない死んだ項目であった** |

## 2. ★★`PATCH /api/tags/{id}` は未設定へ戻せない（**`DES-002` ＋ `DES-006` §5 へ新規記載**）

**★★開発者判断**（2026-09-08）**＝「未設定へ戻す処理はいらない」。⇒ 実装は現状のままでよい。★差分がゼロなので、書かないと消える。**

### 2.1 ★★機序（**すべて実測**）

| 段 | 所在 | 何が起きるか |
|---|---|---|
| 1 | `web/src/features/tag/hooks/useTagFormDialog.ts:57-58` の `values.category || undefined` | **入力欄を空にすると空文字が `undefined` になる** |
| 2 | `web/src/features/tag/api/tagApi.ts:80` の `JSON.stringify` | **`undefined` のキーが JSON から落ちる** |
| 3 | `internal/model/tag.go:67-71` の `*string` ＋ `internal/repository/tag/repository.go:165-179` の動的 SET | **nil を「変更なし」としてスキップする**（`SET` 句が組み立てられない） |

### 2.2 ★★`null` を送っても救えない

**★Go の `encoding/json` は `null` をポインタの nil へ落とす。⇒ 「キーの省略」と「明示的な `null`」を区別できない。**

**⇒ フロント側の小修正では直らず、契約の決めごとが要る。★本書はその決めごとを「戻せない」で固定する。**

### 2.3 ★★書く内容

| 反映先 | 内容 |
|---|---|
| **`DES-002`** | **`category` / `color` は省略＝変更なしであり、未設定へ戻す表現を持たない。★`null` を送っても同じである** |
| **`DES-006` §5** | **一度設定したカテゴリ・色は UI から未設定へ戻せない。★これは欠陥ではなく仕様である**（2026-09-08 開発者判断） |

## 3. ★★削除の利用者スコープは 2 段で成り立つ（**`DES-006` §5 へ新規記載**）

**★指示書は「Update / Delete は `WHERE id = ? AND user_id = ?` で絞っている」を前提としていたが、Delete はそれだけではない。**

| 段 | 所在 | 役割 |
|---|---|---|
| **1** | `internal/service/tag/service.go:106` の `s.repo.Get(ctx, userID, tagID)` | **他人の `tagID` が `CountUsage` へ届くのを止める** |
| **2** | `internal/repository/tag/repository.go:207` の `DELETE ... AND user_id = ?` | 他人の行を消させない |

**★★★段 1 が要る理由が実装上にある**——**`repository.CountUsage`**（`repository.go:222`）**は tag リポジトリで唯一 `userID` を取らない**（`SELECT COUNT(*) FROM combo_tags WHERE tag_id = ?`）**。**

**⇒ 段 1 を外すと、他人の「使用中」タグへの `DELETE` が `409` ＋ `usageCount` を返し、他人のタグの存在と使用件数が漏れる**（実測）**。**

**★★`Update` は同じ形ではない**——`UpdateTag`（`service.go:82-102`）**は `Get` を通さず `repo.Update` を直接撃つ。⇒ 「Update と Delete は同じ形」と読むと外れる。**

**★★★したがって恒久の規約を 1 行置く＝`CountUsage` は利用者で絞らない。⇒ 単独で呼ぶ新しい経路を作ると、同じ漏れが再発する。**

**固定した試験**（**実装は 1 行も変えていない**）:

| 試験 | 何を固定するか |
|---|---|
| `internal/repository/tag/repository_test.go` `TestDelete_IsScopedToUser` | 段 2 |
| `internal/api/tag/scope_test.go` `TestDelete_DoesNotLeakAnotherUsersTagUsage` | **段 1** |
| `internal/api/tag/scope_test.go` `TestDelete_CannotTouchAnotherUsersTag` | 経路全体 |

## 4. ★`409 tag_in_use` は UI から通らない（**`DES-005` §5.12 へ 1 行**）

**★★`TagManagementPage.tsx:68-75` が、削除の前に一覧の `Tag.usageCount` を見て `force` を先に付ける。⇒ 通常経路で `409` が発生しない。**

**⇒ `409 tag_in_use` は API の契約としてのみ存在する。**

**★★開発者判断**（2026-09-09）**＝現状維持。逐語＝「画面で 409 が起きないなら、API の仕様はあまり気にしません」。**

**★これは「直さない」の記録であって「気づかなかった」ではない。⇒ `TagApiError.usageCount` の getter に読み手が無いことも、この判断の帰結として説明が付く。**
