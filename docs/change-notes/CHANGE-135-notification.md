## 3. ★真因の記録

### 3-1 ★★`CLAUDE.md` §5 の「dev DB・dev サーバに影響しない」は双方向とも偽だった

| 方向 | 状態 |
|---|---|
| **E2E → dev** | **既報告。** E2E が `PUT /api/config` を踏んで `config.toml` を再シリアライズし、コメントを落とす（`Makefile` が自認） |
| **★★dev → E2E** | **★未報告だった側であり、実害が大きい。** **E2E の結果が「開発者が最後にアプリで選んだ既定キャラ」に依存する** |

**★★機序**——**E2E は test ごとに新規ブラウザコンテキストなので、既定キャラの解決順の段 1（URL）と段 2（session）が常に空になる。** **⇒ 段 3b（`config.toml` の `defaults.characterId`）が単独で決める。**

**★製造環境では構造的に踏めなかった**——**クリーン clone では `config.toml` が存在せず example から生成される。** **⇒ 製造の落ち度は「踏めなかったこと」ではなく、汚染の片側しか報告していなかったことである。**

### 3-2 ★★「既存が書かれていないから、新しいものも書かなくてよい」は成り立たない

**製造の CHANGE 不要判定の論拠＝「既存の env 3 つが `docs/design/` に記載が無く、env は設計書の管理外である」。**

**★★これは先行の欠落を根拠にする形である。** **欠落は、次の欠落を正当化しない。**

**⇒ 本 CHANGE では逆に、既存 3 つの存在も §5.8 へ書く。**

**★実査の手そのものも誤っていた**——**探すべきは「env 変数の名前」ではなく「設定ファイルの置き場所の記述」であった。** **⇒ 「無いこと」を示す検索は、探す語を誤ると簡単に 0 件になる。**

### 3-3 ★★遅さの正体は直列化ではなかった

**`workers: 1` は正しかった**（開発者実測＝**180 ケース一発成功・flaky 0・failed 0**）。

**★遅さの主因は Vite dev サーバである**——**dev サーバはバンドルせず ESM を 1 モジュールずつ配るため、1 ページロードで数百リクエストが出る。Playwright は test ごとに新規コンテキストを使うので HTTP キャッシュが毎回空になり、その固定費を毎回払い直す。** **★並列時は重なって隠れ、直列にすると露出する。**

**★★「直列にしたから遅い」という見立ては、実測で否定された。** **⇒ ビルド済みを配る形にすると、直列のまま従来の並列（248 秒）より速くなる**（**`embed_web` 156〜158 秒 ／ `vite preview` 156〜159 秒。★実測で差は無い**）。

### 3-4 ★測定環境の代表性

**製造の測定環境は 4 コア＝2 worker であり、開発者の 24 コア＝12 worker からの直列化を一度も測っていない。** **⇒ 完了報告の「1.54 倍」は 2→1 の値であり、一般化してはいけなかった。**
