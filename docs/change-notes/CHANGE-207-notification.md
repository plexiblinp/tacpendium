## 1. 8 つ目のキー

**★開発者裁定**（`D-874`・逐語）**＝「重複判定キーに入れる（カウンターやパニッシュカウンターのようにレシピ等が同一でも、この区分が違えば別コンボ判定になる系と認識した上での回答）」。**

| | |
|---|---|
| 列 | **`starter_meaty`** |
| 意味 | **そのコンボの始動技を持続当てしたか** |
| 型 | `INTEGER NOT NULL DEFAULT 0` の bool。**★NULL を取らない** |

### 1.1 ★★★なぜ NULL を取らないか

**★重複判定キーに入る列で NULL を許すと、SQL の `NULL != NULL` により「不明どうし」が別コンボへ分かれる。⇒ 意味の無い分岐が生まれる。**

**★★同じ理由で 3 値**〔持続当て / 非持続当て / 不問〕**にしない。**

### 1.2 ★★`hit_type` とは別枠である

**★開発者の逐語＝「始動技用としては別枠として欲しい。ヒット種別とも別枠」。**

**★★★持続当ては*ヒットの種類*ではなく*当て方*である。⇒ 「持続当てのカウンターヒット」がありうる。★1 つの列に畳めない。**

### 1.3 ★`combo_oki_options` の打撃重ねとは向きが違う

| | |
|---|---|
| `oki_strike_meaty_*`（`CHANGE-063`） | **このコンボの*後に*どんな起き攻めができるか**〔出る側〕 |
| **`starter_meaty`** | **このコンボの*始動が*持続当てか**〔入る側〕 |

**⇒ 同表は 1 バイトも変えていない。**

## 2. ★★★「将来の変更可能性」の節を実態へ書き換えた

### 2.1 旧記述は実装に存在しない構造を約束していた

**★旧記述の逐語＝「重複判定で比較するフィールドは、サービス層で**リスト定数として定義**する。将来『modifiers を比較から外す』等の変更が必要になった場合、リスト定数を 1 箇所修正するだけで挙動を切り替えられる構造とする」。**

**★★実測**（2026-09-14・`grep -rn "DuplicateCheckFields" --include=*.go .`）**＝定義行のみの 1 件。⇒ 判定ロジックからも、自身のテストからも参照されていない。**

**★★★「1 箇所修正すれば切り替わる」は 1 度も成立していなかった。**

### 2.2 ★★なぜ書き換えを選んだか

**★偽の約束を正本に残すほうが、書き換えるより高くつく**——**次に足す担当がそれを信じ、1 箇所だけ直して終える。⇒ 残りの足し先が黙って古い値のまま動く。**

**★★本サブの製造は 30 箇所を数え直す羽目になった。⇒ そのうえ `grep` を `| head -20` へ通して 11 箇所を取りこぼし、レビューが検出した**（同レポート §7-1）**。**

### 2.3 ★★★実装を記述へ合わせる案は採らない

| 案 | 中身 | 判断 |
|---|---|---|
| **A** | **記述を実態へ合わせる** | **★採用** |
| **B** | **実装を記述へ合わせる**〔判定の各所を 1 本の定義から導く〕 | **★不採用。⇒ `repository` と `validation` は層独立性のため*意図的に*二重定義している**（`M1-03` 機械レビュー・高優先の対応）**。★素直には畳めない** |
| **C** | **定数と足し先の全数が一致することをテストで固定する** | **★`followup` へ登録**（`duplicate-key-constant-is-not-wired`）**。⇒ 層は畳まないまま、ドリフトしたら赤になる** |

**★★★約束の*目的*は「キーを増減するときに足し先を探し回らずに済むこと」であった。⇒ その目的は生きている。★案 C はそれを層を畳まずに満たす。**
