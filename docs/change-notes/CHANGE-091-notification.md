## 1. 変更の概要

セットプレイ提案は**フレーム計算のみで候補を導出している**が、その計算が**連打キャンセルを考慮していない**ため、**物理的に入力できないレシピを提案している**（弱P を 2 発つなぐとき実機 22F を 26F として計算）。

原因は、`moves.startup` / `moves.total` に「**単独で出したときの値**」と「**連携の中で出したときの通し値**」が**同じ列に混在しており、行を見ても判別できない**ことである。この区別を持つ列を足す。

**M19-04 は「列を足して値を入れる」までで、値の消費は M19-05。** 新列はエンジン・既存 API に露出させない（契約 F-3）。

### 2.3 人手判断の導線（★本サブの成果物に含める）

**人手が要るのは 3 系統。いずれも候補集合は機械で絞れる。絞れないのは判断だけである。**

| 系統 | 候補の絞り込み（機械） | 開発者が判断すること |
|---|---|---|
| `startup_basis` | `is_derived = 1` **かつ** `category != 'rush_variant'` | その行の `startup` が単独値か通し値か |

| `chain_cancel_total` | 連打キャンセルがつながり得る技（弱攻撃を中心に候補を出す） | つながるか。つながるなら**実測値** |

**記入先は `character_data/*.csv`**（本サブで空欄の 3 列が入るため、書き込み先は用意される）。

**成果物 o: 記入された CSV から人手 backfill マイグレを生成する seedgen の新モードを追加する。**

> **★なぜ手書き SQL にしないか**: 一覧に書き込んで返す方式だと**その一覧はどこにも残らず、値の出所が SQL だけになる**。CSV から生成すれば、**ゲームアップデートで値が変わったときも CSV を直して再生成するだけ**で済み、**golden で機械検証できる**。「CSV が正本」という判断（ボード D-36）を実装として成立させるには、こちらしかない。

## 3. 判断の根拠

### 3.1 seedgen の SQL 出力は変更しない（前例 5 列と同型）

`M18-01` が「seedgen へ新列を出力する」案を撤回した理由 **3 点**（golden byte-identical ／ 既存マイグレ非改変 ／ **000026・000030 が新列 DDL より前に実行され `no such column`**）は**現存し、今回の 3 新列にそのまま適用される**（RESEARCH-04 A-4 で一次記録を裏取り済み）。

**`is_projectile` / `is_derived` / `command` / `condition_ja` / `condition_en` の 5 列が、現に「CSV に持つが SQL 非出力（保全のみ）」で共存している。** 本件も同型とする。**三点更新（§2.3 k〜m）を行い、出力を変えなければ golden 4 stem は green のまま維持される。**

**M19-04 では `internal/seedgen` の生成ロジック（`writeMovesInsert` 等）に一切触れない。** 触るのは**読取り層（`csvColumns` / `parseRow` / `MoveRow`）と、それに追随するテストのみ**。これは M14-03c §4.3.1 の「**I/O 境界のみ**」に該当する（ボード D-74）。

### 3.2 ザンギエフ連打版 3 行を CSV に足さない理由

**`zangief.csv` に行を足すと `Generate` が読む行が増え、`000026` の生成物が変わって golden が壊れる。** 再生成しても**既存 DB には反映されない**（適用済み連番は再実行されない＝RESEARCH-04 C-2）ため、**手書き INSERT マイグレは別途必要**であり、CSV にも足すと**同じ 3 行が 2 か所に存在してどちらが正か不明になる**。

**したがって M19-04 では手書き INSERT のみとし、CSV への反映は followup `csv-edit-vs-golden-divergence` の範囲とする。** **乖離が生じることを認識したうえで、紐づけ先を明示する。**

### 3.3 backfill の生成方式（★D-85 → D-93 → 本項で確定）

**機械 backfill と人手 backfill で方式が違う。**

| 種別 | 値の出どころ | 方式 |
|---|---|---|
| **機械 backfill** | 既存 DB 列（`is_derived` / `category` / `code`）からの**導出** | **条件式 3 文の手書き SQL**。行の列挙は不要で、seedgen は不要 |
| **人手 backfill** | **開発者が CSV へ記入した値** | **seedgen の新モードで生成**（§2.3 成果物 o） |

> **経緯（訂正 2 回）**: ボード **D-85** は「手書きにすると 796 行の UPDATE を人が書くことになる」として全面的に seedgen 生成を採ったが、**機械 backfill が条件式で書けることを見落としていた**。**D-93** でこれを訂正して「seedgen は不要」としたが、今度は**人手 backfill の入力導線を設計していなかった**（開発者からの指摘で判明）。**人手 backfill の値は CSV にしか置き場所が無く、CSV から生成する以上 seedgen の新モードが要る。** 本項が確定形である。

### 3.4 契約 F-4 の書き換え

**F-4「CSV 再取込が新列の人手付与値を上書き・NULL 化しない」は、発生条件そのものが存在しない**（RESEARCH-04 C-2＝既存 DB への CSV 再取込機構は現行コードに無い）。

**新しい不変条件（ボード D-75）**:

1. **CSV → 既存 DB へ値が流れ込む経路を新設しない。**
2. **新連番の backfill マイグレを生成するときは、CSV で値が空の行を UPDATE 対象に含めない**（既存 backfill 3 例と同型。**COALESCE マージの前例は無いので採らない**）。

## 6. 開発者への確認事項

1. **`chain_cancel_total` の実測値を、本サブの実装期間中に受領できますか。**
   なぜ：受領できれば人手 backfill を本サブ内で 1 本追加して閉じられます。**対象は seed 済み 10 キャラ ＋ manon で、2〜4 技 × 11 キャラ ≒ 22〜44 件、うち 7 件は実測済み**なので、残りは 15〜37 件です。
   **暫定案**：**受領できなければ既定値（NULL）のまま進め、後続マイグレで補います。** M14-03d が移動 5 code の `total` でこの運びを実証済みで、**推測で埋めないことが最優先**です。

2. **ザンギエフ連打版 3 行の登録を、本サブで行ってよいですか**（保留 P-02 の個別承認）。
   なぜ：実測値は `M19-DESIGN-07` §1-3 に確定済みで追加実測は不要ですが、**`moves` への新規行登録は確定反撃サーチの候補集合を増やし得ます**（列は不変だが行が増える＝F-1 のグレーゾーン）。
   **暫定案**：**本サブで登録し、確定反撃サーチへの非干渉を実装で担保する**（候補件数の canary テストで固定）。**M14-03d で manon 追加により jump-lane の判定値が 21→23 に動いた実績がある**ため、**同じ canary が再び動きます。数字を名前に埋め込まない**運用（M14-03d §3.3-1）に従ってください。
