## 1. 変更の概要

**`DES-002` §8（認証・ユーザー管理）は、実装が 0 件のまま方針だけが書かれている状態である。** **`M22-01` で骨格を作るにあたり、開発者の方式承認（**D-395** ／ **D-396**）を受けて 5 点を as-built へ寄せる。**

**★非スキーマ・非破壊である。** **DB のテーブル・列・制約を 1 つも変えない**（パスワードは `config.toml` に置く。`users` 表は既存のまま触らない）。**マイグレーションを消費しない。**

**★本 CHANGE の性格**——**§8 の大半は変えない。** **同節の中核（「厳格な認証ではなくラベル付け程度」「防御責任の主体はルーター・ファイアウォール」「必須化はしない」）は、開発者の「認証を過剰にしない」という方針と一致しており、そのまま残す。** **変えるのは 5 点である**——**実装しないと決めた 1 点**〔タイムアウト〕**／ 実装の置き場を確定させる 2 点**〔ハッシュの保管先・セッションの持ち方〕**／ 設計書に無かったものを書き足す 2 点**〔**パスワードの変更・無効化の導線** ／ **`password_enabled` を切り替える経路の保護**〕。

## 2. 変更の内容（`DES-002` §8 ／ `SUPP-001` §5.8）

| # | 対象 | 変更 |
|---|------|------|
| **a** | **`DES-002` §8「セッションタイムアウト」の段落** | **★「セッションタイムアウトは最低12時間以上に設定する」を「セッションタイムアウトは設けない」へ改める。** **理由を併記する**——**同段落が挙げる目的は「編集画面を長時間開いたまま放置されるケース（コンボ検証でゲーム側にフォーカスしている間）を考慮し、放置後の入力継続を支援する」ことであり、タイムアウトを長く取るのはその手段であった。** **⇒ 設けないことは目的に反しない。むしろ目的に対してより素直である。** **`FR603` の下書き自動保存との組み合わせの記述は残す** |
| **b** | **`DES-002` §8「LAN共有モードON時：簡易パスワード（全ユーザー共通の1パスワード）を要求可能とする」** | **★方針は変えない。置き場と既定を追記する**——**パスワードのハッシュは `config.toml` の `[security] password_hash` に保管する** ／ **`[security] password_enabled` の既定は `false`** ／ **`users.password_hash` 列は使用しない**（利用者ごとのパスワードは採らない） |
| **c** | **`DES-002` §8「セッション管理はサーバーサイドセッション（メモリ保持）で十分」** | **★方針は変えない。性質を明記する**——**セッションはプロセスのメモリに保持し、永続化しない。** **⇒ 再起動で失効する** |
| **d** | **`SUPP-001` §5.8 の設定ファイル例** | **`[security]` の記述を実体へ合わせる**——**`password_enabled`（既定 `false`）と `password_hash`（設定時のみ記載）。** **★現在コメントで予約されている `# password_hash = ""` を、予約ではなく実在する項目として書く。** **★他の 5 グループの差分は本 CHANGE で直さない** |
| **e** | **★新規追記——パスワードの変更・無効化の導線**（`DES-002` §8） | **★これまで設計書に無かった。** **⇒ 次を書き足す。** **(1) パスワードを変えるときは、アプリの設定画面から行う。現在のパスワードを要求する** ／ **(2) パスワードを忘れたときは、`config.toml` を直接編集して `password_enabled = false` に戻す。★アプリからの復旧手段は用意しない** ／ **(3) `password_enabled` を LAN 共有モードの前提条件にしない**（**§2.1 の「必須化はしない」を保持することの帰結**）。**⇒ パスワードを忘れても LAN 共有そのものは使い続けられ、詰みが原理的に起きない** |
| **f** | **★新規追記——`password_enabled` を切り替える経路の保護**（`DES-002` §8） | **★これまで設計書に無かった。** **`password_enabled = true` のとき、`password_enabled` を `false` にする操作は保護対象に含める。** **⇒ 認証を通らずにゲートを外せる形にしない。** **★これを外すと、パスワードを掛けた意味がその場で消える** |

### 2.1 ★変えないもの（網羅宣言）

**`DES-002` §8 のうち、次はそのまま残す。**

- 「利用者が1人の場合：認証を行わず即座に操作可能」
- 「利用者が2人以上の場合：起動時にユーザー選択画面を表示（パスワードなし、単なる『誰として操作するか』の選択）」——**`M22-02` の担当であり、`M22-01` 完了時点では未実装のままである**
- 「厳格な認証ではなく『他人の編集を誤って上書きしない』ためのラベル付け程度の位置づけである」
- 「監査ログ（誰がいつ編集したか）は実装しない（FR013参照）」
- **LAN共有モード時の認証ポリシー**の 3 点（警告・同意ダイアログ・必須化はしない）——**★`M22-02` の担当**。**`LanModeConfirmDialog.tsx` は実在するが `passwordEnabled` を参照する分岐が 0 件である**（`M22-RESEARCH-01` §9-B-4）
- **防御責任の整理**の段落全文

## 3. 真因の記録

**★バグ修正ではない。** **§8 は「方針を書いたが実装が追いついていない」状態であり、誤りが在ったわけではない。**

**★ただし 1 点、記録に値する経緯がある**——**`migrations/000007_seed_initial_tags_user1.up.sql` のヘッダが「本来は M6 初回起動ウィザードで生成（`SUPP-001` §2.5）。M3 期間は未実装のため seed で凌ぐ。」「M6 着手時にウィザード経由生成へ切り替える。」と宣言したまま、切り替えが行われずに残っている**（`M22-RESEARCH-01` §9-B-7）。**`internal/{api,service,repository}/user/` も `doc.go` のみの空パッケージとして 3 レイヤ分残っている。**

**⇒ 本 CHANGE では扱わない**（`M22-01` は `userID` の供給元を変えないため）。**followup `user-package-stubs-since-m6` として登録済みであり、`M22-02` の設計で決着させる。**

**★適用済みマイグレのヘッダは改変できない。** **失効しても直せないため、`M22-01` の否定形確認で当たっても直さず、当たったことを完了報告へ書かせる**（指示書 §4.9.1-3）。

## 4. 確定した設計判断（開発者承認済み・**D-395**）

| 項目 | 判断 | 根拠 |
|------|------|------|
| **簡易パスワードを実装するか** | **する。既定は OFF** | 開発者判断。**`FR502`（一人ならスキップ）と整合し、一人で使う間は何も増えない** |
| **パスワードの置き場** | **`config.toml` の `[security] password_hash`** | **`DES-002` §8 の逐語が「全ユーザー共通の1パスワード」である。** **`SUPP-001` §5.8 が既にコメントで予約している場所でもある** |
| **`users.password_hash` を使うか** | **使わない** | 上記。**★利用者ごとのパスワードは、人数分の管理・忘却時の導線・変更の導線がすべて人数分要り、「過剰にしない」方針と逆向きである** |
| **`users.password_hash` 列を削除するか** | **削除しない** | **列の削除は破壊的変更である**（`CLAUDE.md` §10）。**扱いは `M22-01` の完了報告を受けて別途判断する** |
| **ハッシュのアルゴリズム** | **「依存を増やさない方」を優先。実査してから決める** | 開発者判断。**標準ライブラリに鍵導出関数が在ればそれ、無ければ `golang.org/x/crypto/bcrypt`。** **★後者の `indirect → direct` 昇格は本承認に含まれる**（`CLAUDE.md` §6 ／ **D-382 (2)**） |
| **セッションタイムアウト** | **設けない** | 開発者判断。**§2-a のとおり、§8 が挙げる目的（放置後の入力継続の支援）に反しない** |
| **セッションの持ち方** | **プロセスのメモリ。永続化しない** | **`DES-002` §8「メモリ保持で十分」と一致** |
| **「ユーザー選択」と「パスワード」の関係** | **直交した別の仕組みとして扱う** | **`DES-002` §8 が「ユーザー選択画面を表示（パスワードなし、単なる『誰として操作するか』の選択）」と明記している。** **⇒ ユーザー選択は認証ではない** |
| **LAN 共有モード ON にパスワードを必須にするか** | **★必須にしない**（`DES-002` §8「必須化はしない」を保持） | 開発者判断（**D-396**）。**★これが「忘れたら二度と LAN 共有を使えない」という詰みを原理的に消す。** **忘却時は `password_enabled = false` へ戻すだけで LAN 共有を使い続けられる。** **★一人で LAN 共有を使う場合〔PC → 自分のスマートフォン〕にパスワードを強制しない利点もある** |
| **パスワードの変更手段** | **アプリの設定画面から。現在のパスワードを要求する** | 開発者判断（**D-396**）。**★「変更できない」は運用として成立しない。** **UI は `M22-02`、サーバ側の経路は `M22-01`** |
| **パスワードを忘れたときの復旧手段** | **★`config.toml` の直接編集のみ。アプリからは復旧できない** | 開発者判断（**D-396**）。**★これは不便ではなく設計である**——**アプリから「パスワードを知らないまま無効化」できてしまうと、ゲートの意味がその場で消える。** **⇒ 信頼の根を「そのマシンのファイルを編集できること」に置く。** **`DES-002` §8 の防御責任の整理と同じ層の割り切りである** |
| **初回パスワード設定欄の既定表示** | **★設定画面は表示を既定、ログイン画面はマスクを既定。どちらも切替可能** | 開発者判断（**D-396** ／ 根拠を **D-397** で差し替え）。**★設定側を表示にする理由は失敗の代償の非対称性である**——**初回設定でタイプミスすると `config.toml` の編集が要り、初めて使う人がそこで離脱する。** **一方ログインは間違えても打ち直せば済む。** **★表示が既定であるため、確認入力〔2 回打たせる〕は設けない。** **★ログイン側をマスクにする理由は開発者が示した 2 つである**（**2026-08-15**）——**友人が来ているときに入力する場面** ／ **画面を配信する利用者が使う場面**。**★設計卓が当初挙げた「外出先のスマートフォンから打つ」は誤りであった**——**本アプリはローカルネットワーク完結であり、その場面は成立しない**（§4.1） |

### 4.1 ★設計卓の誤りの訂正（2026-08-15・**D-397**）

**設計卓は「ログイン画面はマスクを既定にすべき」の根拠として「外出先のスマートフォンから打つ可能性がある」を挙げていた。** **★これは誤りである。**

**開発者の指摘**——**「本アプリはローカルネット完結なので外出先のスマホから打つ可能性はありません。ポート開放をするとインターネットから接続も可能となる認識ですが、その使い方はサポートしていません。」**

**⇒ 結論（ログインはマスク既定）は変わらないが、根拠を差し替えた。** **開発者が示した実在する場面は次の 2 つである。**

| # | 場面 |
|---|---|
| 1 | **友人が来ているときに入力する**（**★`DES-002` §8 の「正規のLAN内部ユーザー〔家族・ゲスト等〕による意図しない閲覧・編集を防ぐ」という位置づけと正面から合う**） |
| 2 | **画面を配信する利用者が使う**（**★これは設計卓が想定していなかった。配信中はパスワードが視聴者全員に見える**） |

**★誤りの型**——**設計卓が「LAN 共有の主目的はスマートフォン接続だから、外出先からも打つはずだ」と推論した。** **前半は正しいが、後半は本アプリの前提〔ローカルネットワーク完結〕を踏み外している。** **⇒ `E-117` の変種であり、本レーンで 5 件目である。**

**★併せて、この訂正は §6.2 の判断を補強する**——**「モバイル通信のスマートフォンから接続できるか試す」を確認テストとして採らなかったのは正しかった。** **そもそも外部から接続する使い方をサポートしていない以上、その確認手順を案内すること自体が、サポート外の使い方を示唆してしまう。**

### 6.1 ★文言の方針（`M22-02` への申し送り）

**開発者の指摘**（2026-08-15）——**「『平文で LAN を流れます』はエンジニア向き過ぎる。IT リテラシーの低い人には訳がわからない。『ルーターでポートを外部公開しないでください』も仕組みを理解していない人には分からない。」**

**⇒ 次を方針とする。**

| # | 方針 |
|---|---|
| 1 | **★利用者が「自分で確かめられること」「自分で決められること」だけを書く。** **仕組みの説明を前提にしない** |
| 2 | **★「〜しないでください」より「〜という状態です」を先に書く。** **禁止は、状態を理解したあとでないと守れない** |
| 3 | **★心当たりの無い操作については「心当たりがなければ、その設定はされていません」と添える。** **不安だけを残さない** |
| 4 | **★「安全です」と書かない**（契約 F-3）。**書けるのは「この条件下でこう振る舞う」までである** |

**★開発者が提案した「モバイル通信に切り替えたスマートフォンから接続できないことを伝える」案について**——**「説明」としては採るが、「確認テスト」としては採らない。** **理由は §6.2。**

### 6.2 ★モバイル通信からの接続確認を「テスト」として採らない理由

**接続 URL のホスト部はプライベート IP である**（`192.168.x.x` 等。`netutil.SelectPrimaryLANIP` が返す）。**プライベート IP はインターネット上で経路を持たない。**

**⇒ モバイル通信のスマートフォンからこの URL を開くと、ルーターがポートを外部公開していてもいなくても、同じように失敗する。**

**★したがって「開けなかったから外部公開されていない」とは言えない。** **⇒ これを確認手順として案内すると、誤った安心を与える。**

**★外部からの到達性を本当に確かめるには、グローバル IP が要る。** **本アプリはそれを知らず、知るには外部サービスへの問い合わせが要る**（`M22-06` §1.3-6 で禁止済み。`DES-002` §8 の LAN 前提にも反する）。

**⇒ 採るのは「説明」としての形である**——**「同じ Wi-Fi につないだ機器からだけ見えます。外出先のスマートフォンからは開けません」。** **これは事実であり、利用者が LAN 共有の範囲を掴むのに最も効く 1 行である。**
