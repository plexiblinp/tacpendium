## 2. 変更の内容

### 2.1 ★★`SUPP-001` §5.5——**テスト DB の構築方式**（**主対象**）

#### 2.1.1 現状（**変更前**）

**`SUPP-001` §5.5 はテスト最低ラインとマイグレ契約テストの規約を持ち、`CHANGE-135` で `workers: 1` が加わった。⇒ 「テスト実行の規約」がここに集まっている。**

**★★しかしテスト DB がどう作られるかは書かれていない**（**設計卓の実査＝`dbtest` の語は `docs/design/` に 1 件も無い**）。

#### 2.1.2 変更後（**as-built で確定する**）

**次の内容を §5.5 の小節として足す。**

| # | 内容 |
|---|---|
| **1** | **テスト DB はテストバイナリ（パッケージ）ごとに 1 回だけマイグレーションを流してテンプレートを作り、各テストはそのファイルをコピーする** |
| **2** | **★★テンプレートは `wal_checkpoint(TRUNCATE)` の後に閉じ、単一の `.db` ファイルとしてコピーする。★`-wal` / `-shm` を持ち込まない** |
| **3** | **★★マイグレーション自体を検証するテストはテンプレートを使わない**（**再生させることが目的であるため**）。**★対象パッケージの全数は as-built で確定する。★設計卓が起票時に知っているのは `internal/infra/migration` の 1 本だけである** |
| **4** | **★★導入・変更の正しさは「速くなったこと」では示さない。`go test ./... -count=1` の ok パッケージ数・FAIL 数・テスト本数が不変であることで示す** |

**★★4 が最も重要である**——**テンプレートのコピーに失敗して空の DB でテストが走っても、「その行は存在しない」を確かめているテストは緑のままになり、しかも速くなる。**

#### 2.1.3 ★なぜ CHANGE が要るか

**`SUPP-001` §5.5 は `D-564` が「契約を持つ節」と定めた 5 節の 1 つである**（§4.5 / §5.2 / §5.5 / §5.7 / §5.8）。

**★`workers: 1`（`CHANGE-135`）と同格の「テスト実行の規約」である。⇒ テスト DB の構築方式と除外対象も、同じ性質の規約として通知書を要する。**

### 2.2 ★`SUPP-001` §4.5——**CI の as-built**（**条件付き**）

#### 2.2.1 現状

**§4.5 の逐語＝「CI は本フェーズでは構築せずローカル実行。spec 実装・保守は製造担当 Claude Code へ委任可。」**

**★「本フェーズ」はフェーズ2 を指す。⇒ フェーズ3 で `M24-09a` が `pr-checks.yml` を作った後の as-built が §4.5 に書かれているかは、設計卓は確かめていない。**

**★★これは指示書 §3.3-11 の実査項目である。**

#### 2.2.2 変更後（**§4.3 が成立した場合のみ**）

| # | 内容 |
|---|---|
| **1** | **E2E は nightly で回る。`pr-checks.yml` には載せない**（**★PR ごとに 4.4 分を足すかは別の判断である**） |
| **2** | **★★nightly でも `workers: 1` を維持する**（`CHANGE-135` の理由がそのまま効く） |
| **3** | **★★これが「main の E2E が緑かを独立に知る」唯一の経路である**（`D-594`） |

**★★§4.3 が CI ランナーで成立しなかった場合、本節は反映しない。⇒ 代わりに「成立しなかった分岐点」を change-report へ記録する。**
