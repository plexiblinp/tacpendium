## 2. ★起票案から as-built へ確定した 4 点

### 2.1 `warnings` は無かった——**本サブが最初の実装者である**

**`CHANGE-124` §5 リスク 3 は「実装が既に在るかを設計卓は判定できない。指示書 §3.3-1 の実査に委ねた」としていた。答えは「無かった」。**

**既存の `warnings` は 2 件だけで、どちらも形が違った**——CSV 取込プレビュー（`[]string`・常に空配列化）と技一覧（`[]WarningCode`）。**⇒ どちらも取得・プレビュー系であり、変更系の成功応答が警告を返す形は本経路が最初である。**

**⇒ `DES-002` §4.2 へ逐語形を「復元経路の `warnings`」として写した。** **落としやすい 3 点も併記した**——**警告 0 件のときはキー自体が出ない**（空配列を返さない）／ **`severity` を落とさず載せる**（復元経路は ERROR も警告として返すため、種別を落とすと区別が応答から消える）／ **`warnings` と `validations` は別フィールドであり、復元応答に `validations` は載らない**。

### 2.2 `VAL-R02` の発火条件を具体化した——**「親が 1 件以上あり、かつ」を足した**

**起票時は「すべて論理削除されている」としか書いておらず、親が 0 件の場合が未定義だった。**

**as-built は非発火。理由は「親 0 件は『全部削除済み』ではなく『紐付けが既に失われている』状態であり、別の事象だから」である**（`M23-02` 適用前に論理削除されたセットプレイ）。**空集合のときに真になる述語を書くと、該当する行が復元のたびに警告を浴びる。**

**⇒ `DES-006` §13.3 へ「親が 1 件以上あり、かつそのすべてが論理削除されている」と書いた。** **★「すべて削除済み」だけだと、空集合の扱いが読む人によって割れる。**

### 2.3 `details` の構造が確定した

| VAL | キー | 要素 |
|---|---|---|
| **`VAL-R01`** | `setups` | **`{ id, name }`**（`SetupRef` を新設） |
| **`VAL-R02`** | `combos` | **`{ id, memo }`**（`M23-02` の `ComboRef` を再利用） |

**★`setups` が `name` で `combos` が `memo` なのは、`setups` に `name` 列があり `combos` に無いためである**（`M23-02` が memo を「名前に相当するもの」と読み替えた判断の踏襲）。

**★`VAL-R02` は当初 id だけを返していた。** レビューの指摘で `memo` を載せる側へ広げている。**判断の根拠は「発火条件の非対称は意図的だが、`details` の形の非対称には正当化が無い」であり、これは正しい**——**`D-494`（揃えることは無償ではない）は「理由のある非対称を守る」であって「非対称なら何でも守る」ではない。**

### 2.4 `superseded_by_combo_id` の持ち越しを閉じた

**`DES-002` §4.2 が「判断は `M23-04`」で終わっていた 1 件を、「`M23-04` で判断し、検証を作らないと決めた」へ書き換えた。**

**★根拠が実査で健在であることも確認済み**——**ゴミ箱一覧の読み取りが `superseded_by_combo_id IS NULL` を無条件に足しており、旧行は出ない。** **⇒ 指示書 §3.3-3 の falsifier は発火しなかった。**

## 3. ★★`ValidationIssue.Details` の裁定（**D-511**）

**製造は復元専用の型を作らず、共有型 `validation.ValidationIssue` へ `Details map[string]any`（`omitempty`）を足す形を採り、受理の可否を求めてきた。**

### 3.1 **受理する**

**決め手は「変換層を作らないこと」である。** 復元経路は既存検証の `ValidationResult` をそのまま `warnings` へ流しており、**変換が無いことが「既に在る検証を復元経路でも走らせている」ことの実装上の担保になっている。** **⇒ 復元専用の型へ切り出すと変換層が要り、そこは「既存の検証を走らせている」が静かに成り立たなくなりうる場所になる。**

**★もう 1 つ**——**切り出すと、ほぼ同じ形の型が 2 つ並ぶ。** **`M23-03` が `#6` の分割で「2 つとも現役であり求めている集合が違う」と守らなければならなかったのと同じ形を、理由なく新しく作ることになる。**

### 3.2 ★ただし `details` の使い方の規則を 3 点、`DES-002` へ書いた

**書かないと、この欄は模倣で広がる。**

1. **`details` は「どの行が該当したか」を返すためのものである。** id だけでなく人が読める文字列を併せて載せる。
2. **★`message` の一部を `details` へ逃がさない。** `details` を読まないと `message` が意味をなさない形にしない。
3. **★新しい経路で `details` を設定するときは、その経路の応答形が `DES-002` に在ることを先に確かめる。** **`400 validation_failed` の経路で設定すると `details.validations.issues[].details` の 2 段入れ子になる。**

### 3.3 ★製造の「§1 か §2 か」の線引きについて——**結論は正しいが、根拠を差し替える**

**製造は「wire format が変わったか」を分かれ目にして §1（独自確定仕様）へ置いた。** **★結論は正しい。根拠は正しくない。**

**★正しい判定軸は「指示書が固定した対象が動いたか」である。** 指示書 §2.2 が固定したのは「既存の `400 validation_failed` ＋ `details.validations` の**形**」＝wire format であり、それは動いていない。**⇒ 契約違反ではない。**

**★なぜ「wire format」を軸にすると危ないか**——**wire format が変わらない契約変更は在りうる。** 本件がまさにそれで、**`ValidationIssue` が「任意の構造化情報を持ちうる」という約束を新しく獲得している。** 今日は後方互換だが、それは「契約が変わっていない」ことを意味しない。

**⇒ 一般形＝「wire format が不変であること」は、契約違反でないことの十分条件ではない。** **十分条件は「その手番で固定すると宣言したものが動いていないこと」である。** **⇒ `retrospective-log` 行き。**
