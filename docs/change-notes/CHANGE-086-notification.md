## 1. 変更の概要

セットプレイ自動提案の **filler（つなぎ技）の条件**を、現行の **`total ≥ 1` の全技**から **`total ≥ 1` かつ `category != target_combo`** へ変更する。

**スキーマ変更なし**（既存 `category` 列の条件を 1 つ足すのみ）。着手前ゲート＝反映案。

## 3. 判断の根拠

### 3.1 中央の当初案は撤回した（記録）

中央は当初、M19-01 完了報告 §3.7-1／-2 に対して「**filler 条件に `is_derived=false` を足せば 2 件が同時に解決する**」と推奨した。**この推奨は撤回済み**である。開発者のドメイン確認（2026-07-26）で前提が 2 つとも崩れたため。

| 中央が置いた前提 | 開発者回答（＝正） |
|---|---|
| rush 版の startup 基準は**未検証**なので filler から外すべき | **空振りドライブラッシュを繋ぎに挟むのは実戦的に有用**・**+11 は実測で正しい** |
| `is_derived=true` ＝**単独で出せない技** | **違う**。単独で出せる技でも**他とコマンドが被り得れば true**（索引衝突回避が付与理由） |

**教訓 G-6** として台帳に記録済み（ドメイン依存の判断は推論の一貫性ではなく開発者の実測で確定する／「A と B が同じ規則で解決する」と気づいたときほど両方の前提を個別に検算する）。

### 3.2 M19-RESEARCH-03 の実測（本 CHANGE の一次源）

| ID | 実測結果 |
|---|---|
| **R-B** | 「単独入力不可」と「コマンド被り」は**機械判別できない**（`denjin_charge`／`thunder_kick` が (b) と同一シグネチャ）。→ **`is_derived` を除外条件に使えない** |
| **R-C** | `target_combo.total` の意味（派生部分のみ／連携全体）は**判別不能**。加算検算で **+6〜+40 の乖離・負値も発生**。**〔2026-07-26 出所注記〕**本行に併記していた「`startup` も 97% が非 NULL」は、**M19 指示書担当のリレー文（2026-07-26）を一次源とする伝聞**であり、**中央は RESEARCH-03 report 実物で未確認**。M19 側からも report に該当記述が見当たらない旨の申告があったため、**本 CHANGE の判断根拠からは外す**（`total` の意味が判別不能である事実は加算検算の乖離のみで十分に成立する） |
| **R-D** | 現行の全技 filler では、**ryu KA=40・既定 3 種別の 210 件中 19 件（9.0%）が `target_combo` を filler に含む**。**`denjin_charge` を filler にした提案は 0 件** |

### 3.3 `category != target_combo` を採る理由

1. **実害の実体が `target_combo` filler に一致する**（R-D の 9.0% が全数）。**`category` 列だけで機械除外でき、新スキーマを要さない**。
2. **ドメイン的にも filler 不適格**：ターゲットコンボは 2 段目だけを空振りで出すことができない。
3. **`total` の意味が判別不能（R-C）**なまま `S = Σ(filler.total) + target.startup` に足すと**二重計上**になり得る（**GC-2 と同型の誤り**）。

### 3.4 除外しないものと、その扱い

- **判別不能な「単独入力不可」相当（`denjin_charge` 等）は機械除外しない**。R-B で判別不能、かつ R-D で**実出現 0 件**であるため、除外規則を無理に作ると副作用（有効な filler の取りこぼし）の方が大きい。**残余は制約告知 1 行で吸収**する（利用者が検証して採用する前提＝FR307）。
- **rush 版 filler は維持**する（§3.1 のとおり有用・+11 は実測値）。

### 3.5 負 KA を 400 にしない理由（v2 で追加）

KA が **NULL**（未入力）は **400 `knockdown_advantage_required`** を返す現行仕様を**維持**する。一方 **負 KA は 200 のまま**とし、理由コードだけを足す。両者は性質が異なるためである。

| | KA が NULL | KA が負 |
|---|---|---|
| 状態 | **未入力**＝データが無い | **入力済み**＝データはあり、構造的に成立しない |
| 利用者に促すこと | 「有利フレームを入力してください」 | 「このコンボは起き上がりに重ねられません」 |
| 応答の性質 | リクエストが処理できない＝**エラー** | **正常に計算した結果が 0 件**＝エラーではない |

**変えるのは文言側であってステータスではない**（0 件は正しい計算結果であり、200 のまま理由を添えるのが素直）。

### 3.6 rush filler 維持の裏付けが確定した（v2 で追加）

followup §H(e)『`rush_variant` 通し値の起点』が**開発者確認によりクローズ**した（2026-07-26・M19 リレー）。回答＝**「ニュートラル起点で、ラッシュを最速キャンセルして技を出したときのラッシュ分＋技分」**。起き攻めはニュートラルから入るため**前提が一致**しており、`rush_variant.startup`／`total` の +11 を filler・target の双方でそのまま使える。**rush を filler から除外しない判断は、推測ではなく実測と起点定義の両方で裏付けられた**。

> なお本回答は、`rush_variant.startup` が**通し値（親のラッシュ分を含む合算値）**であることを明示している。これは中央帰属の `startup_basis`（standalone／through／unknown）設計の一次源となる（§5 後続）。
