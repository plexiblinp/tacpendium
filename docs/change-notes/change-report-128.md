## 2. ★★裁定——**`D-485` を撤回した（`D-528`）**

### 2.1 何が起きたか

**製造は「契約・設計に反する独自判断 1 件」として §2-1 を上げてきた。**

| 項目 | 内容 |
|---|---|
| **反した相手** | **`D-485`**（`M23-02`・2026-08-20）。`DES-005` §5.15 の `CHANGE-122` 注記「画面は**専用の一覧を出さない**」。**実装側にも 6 か所のコメントが `D-485` を根拠に「列挙しない」と書いていた** |
| **何をしたか** | 拒否されたとき `details.combos` の `{id, memo}` をパネルへ列挙し、各行から紐付けを解除できるようにした。**新しい API もデータ取得も足していない** |
| **既存のテストを反転させた** | **`M23-02` が意図して置いた否定テスト「拒否のとき、参照元コンボを列挙しない」を、肯定へ書き換えた** |
| **コメントも是正した** | 実装側 **6 か所** |

### 2.2 ★★裁定＝**受理する。`D-485` は撤回する**

**理由は 2 つある。**

1. **`D-485` は「拒否されたあとに紐付けを解除する導線が無い」という状態を想定していなかった。** **`CHANGE-122` 注記自身が「解除そのものは既存の経路で行えるが、ゴミ箱の拒否からそこへ至る道が無い。後続サブが扱う」と書いている。** **⇒ 撤回は `D-485` の否定ではなく、その注記が予告していた後続の実行である。**
2. **費用がほぼゼロである。** **応答は `D-485` の時点で既に `{id, memo}` を持っていた**〔`D-485` 自身が「画面が使わなくても後続が導線を作るときの材料になる」として載せさせた〕。**⇒ 撤回にあたって足したものは画面の描画だけである。**

**★開発者の実機確認済み（2026-08-23・動作に問題なし）。**

### 2.3 ★★ただし「製造の独自判断」ではない——**起票が先に上書きしていた（`M-72`）**

**★設計卓は `CHANGE-128` §2.3 に、自分で次のように書いていた。**

> **★どのコンボが参照しているのかを見せる。** **材料は `details.combos` の `{id, memo}` に在る。新しくデータを取りに行かない。**

**⇒ `D-485` を上書きしたのは製造ではなく、`CHANGE-128` の起票そのものである。** **製造は指示書とチェックリストに従っただけであり、契約違反として上げてきたのは正しい報告だが、違反の主体は設計卓である。**

**★問題は「上書きしたこと」ではなく「上書きしたと書かなかったこと」である。**

- **通知書にも指示書にも「`D-485` を撤回する」の 1 行が無かった。**
- **その結果、製造は「指示書と裁定のどちらが正か」を自分で決める羽目になり**〔採ったのは指示書側で、結論は正しい〕、**実装側 6 か所のコメントと否定テスト 1 本を「独自判断で」書き換えることになった。**
- **★もし製造が裁定側を正としていたら、指示書とチェックリストの完了条件を満たせないまま止まっていた。**

**⇒ 計測点 `M-72` として §6 へ記録した。** **一般形＝過去の裁定を上書きする起票では、上書きされる裁定の番号を通知書に名指しし、「撤回」または「上書き」と書く。** **★「新しい指示書のほうが新しいのだから当然そちらが正」は成立しない**——**実装コードのコメントは古い裁定の番号を持って残っており、指示書はコードを書き換える権限を暗黙には持たないからである。**

## 3. `DES-002` §4.2 へ書いた本体——**`GET /api/combos/{id}/deleted`**

**★製造の §1-1 の逐語をそのまま写した。** **落としやすい点は次の 3 つである。**

1. **★応答のフィールドは 1 つも増えていない。** 差は**値域**（`deletedAt` が非 nil になりうる ／ `defaultRecipe` の解決元が `combo_steps` へ変わる）と**載らないもの**（`setups` は空配列 ／ `validations` / `warnings` は載らない）である。**⇒ 「新しい DTO を作った」と読まないこと。**
2. **★★母集団は `deleted_at` の述語を持たない。生存行も返す。** **だからといって画面が出してよいわけではない**——**`deletedAt == null` のときはゴミ箱の文面と 2 ボタンを出さず、通常詳細への導線へ落とす。** **★「返す」だけを書くと、次の担当が「返るのだから出してよい」と読む。だから両方を同じ場所に書いた。**
3. **★`GET /api/combos/{id}` にフラグを足していない。** **`M23-06` の `ResolveSetupRecipe` と同型の判断であり、`M23-06` は同じ理由で「1 本にまとめられる」と読まれるのを防ぐ記述を入れている。** **⇒ 既存経路の母集団を緩めるとゴミ箱の行が通常の詳細画面に出る。**

**★画面ルート `/trash/combos/:id` と API の形をわざと別にした理由も書いた**——**書かないと「揃っていない」と読まれて片方が動かされる**（**`D-494`**＝**揃えること自体は無償ではない。理由のある非対称は理由ごと残す**）。
