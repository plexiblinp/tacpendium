## 1. 変更の概要

**3 つを 1 本の CHANGE で扱う。いずれも `M23-02` の as-built で確定する。**

1. **機能の新設 3 本**（**★2026-08-20 に 2 本から 3 本へ＝D-491**）——**`POST /api/setups/:id/restore`** ／ **`DELETE /api/setups/:id/permanent`** ／ **削除済みセットプレイの一覧**〔**復元ボタンを押す対象を画面に出す手段が現状ゼロであるため**〕。**★`M23-RESEARCH-01` 軸 C-1 が 4 層すべてを走査し、どちらも 1 層も存在しないことを確定させた。** ルート 11 本の全数、リポジトリ 36 メソッドの全数を目視した結果である。
2. **既存挙動の変更 1 件**——**`DELETE /api/setups/:id`（論理削除）で `combo_setups` を物理削除するのをやめる**（**D-483**）。**★これはフェーズ1 の意図的判断「案 P1」の撤回である**（§3）。
3. **新しい制約 1 件**——**生きたコンボから参照されているセットプレイの完全削除を拒否する**（**D-484**・開発者要求）。

**★CHANGE 対象外**——**`GetRecipeCache`（setups）の `deleted_at` 除外の穴**（`M23-03`）／ **ゴミ箱画面でのセットプレイの見せ方**（`M23-06`）／ **復元時バリデーションの VAL コード化**（`M23-04`）／ **コンボ側の CASCADE 依存 5 表**（`M23-06`）。

## 3. ★真因の記録——**案 P1 はなぜ生まれ、なぜ撤回するのか**

**本節が本通知書で最も重要である。** **「前任が間違えた」という記録にしないこと。**

- **`combo_setups` の物理削除は事故ではない。** `M4-01`（フェーズ1）で **開発者と Plan Mode で確認して採られた**（`docs/instructions/phase1/M4-01-setup-backend-foundation.md` §4.2.6）。実装にもコメントが残っている——**`// 案 P1: combo_setups を明示的に削除（論理削除時は CASCADE 不発火）`**。
- **当時の根拠は同書の逐語で残っている**——**「setup が論理削除中の場合、紐付け表示の意味がないため」**、および **「M4-02 のフロント側でも論理削除中の setup は表示しない方針」**。
- **★当時の前提は「論理削除されたセットプレイは二度と戻らない」だった。** 復元の経路が無かったのだから、紐付けを保つ意味も無かった。**判断は当時の前提の上では正しい。**
- **⇒ 撤回の理由は「前任が誤った」ではなく「前提が変わった」である。** `FR601` を満たすために復元を足す以上、紐付けは保たれていなければならない。
- **★一般形として記録する**——**「その時点で戻す手段が無い」ことを根拠に情報を捨てる判断は、戻す手段を足した瞬間に負債へ変わる。** **捨てる判断を書くときは、根拠となっている「無いもの」を明示しておくと、それが作られたときに見直しの対象として浮かぶ。** 案 P1 はコメントに根拠を残していたため、**フェーズ1 から 2 か月半を経ても根拠を辿れた**——**これは良い先例である。**（`SUPP-001` §5.5.4 規約 (15)＝**「無いこと」を固定する前に、それが契約なのか現状なのかを分ける** の同型）

   **開発者回答の逐語＝「セットプレイの完全削除は拒否で良い。なお生きたコンボに紐づくのでセットプレイは消さなかったという表示は別にユーザーに出す必要はない」。**
   **⇒ API は `409` で拒否し、応答の本体には参照元コンボの id と名前を含める**〔画面で使わなくても `M23-06` の材料になり、切り分けにも効く〕。**画面は既存のエラー表示に乗せるだけで、専用のダイアログ・パネル・一覧を新設しない。**
   **★1 点だけ設計卓の判断が入っている**——**「何も起きない」形にはしない**（指示書 §4.4-3c）。**押しても無反応だと、削除できたのか壊れたのか利用者に判別できず、同じ操作を繰り返す。** **開発者回答は「専用の表示は要らない」であって「無反応でよい」ではないと読んだ。**

2. **【確定・記録】ゴミ箱に居るコンボからの参照は拒否の理由に含めない**（**D-486**・2026-08-20）
   **開発者回答＝「実装が複雑になりそうなので含めなくて良いと思っている」。設計卓も同じ結論である。**
   **★ただし複雑になる先は実装ではなく利用者の逃げ道である**——**判定の SQL はむしろ述語が 1 つ減って単純になる。** 複雑になるのは、**ゴミ箱のコンボが拒否の理由になったとき、利用者はそのコンボを編集できない（ゴミ箱に居るため）ため、復元 → 紐付け解除 → 再び削除 の手順を踏むしかなくなる**点である。
   **★失われるものは小さい**——**セットプレイが完全に削除されている以上、紐付けが無いのは正しい状態である。** 失われるのは事前警告の機会だけであり、**保持は無期限なので完全削除を急ぐ必要も無い**（**D-458**）。

3. **【確定・記録】`M23-overview` 確認事項 6 は決着済み**（**D-483**・2026-08-20）——**案 1。スキーマ変更なし。**
4. **【確定・記録】開発者要求への応答**（**D-484**・2026-08-20）——**論理削除は紐付けを保ち、完全削除は生きたコンボからの参照が残っている間は拒否する。**
