**`DES-001` の技術スタック表は `Go 1.22+` と書いていた。★これは意図的な下限表記ではなく更新漏れである**（`M28-03` の実査。指示書 §6-4 がこの弁別を実査項目に挙げていた）。

## 1. Go の版は 2 行で管理される

```
go 1.26.4           ← 言語仕様・vet の既定・標準ライブラリの挙動を決める。不動
toolchain go1.26.8  ← ★新設。実際にビルドに使う版を決める
```

### 1.1 ★★なぜ `toolchain` 行という手段なのか

**`.github/workflows/` は Go の版を 1 か所も直書きしていない。4 か所すべてが `go-version-file: go.mod` である**（`pr-checks.yml:64,151` ／ `nightly-crossbuild.yml:70,183`）。

**⇒ `go.mod` を触らない限り CI の Go は 1 mm も動かない。★`toolchain` 行なら `actions/setup-go@v7` も手元の `GOTOOLCHAIN=auto` も追従し、言語版だけを据え置ける。**

### 1.2 二層が持ち込んだ挙動（実測）

| 環境 | 効くもの | 結果 |
|---|---|---|
| 既定（`GOTOOLCHAIN=auto`） | **`toolchain` 行** | `go env GOVERSION` → **`go1.26.8`**。**★1.26.8 未満の環境は初回ビルドで `proxy.golang.org` から取得する** |
| `GOTOOLCHAIN=local` | **`go` ディレクティブ** | `toolchain` 行は**無視される**。強制されるのは **1.26.4** |

**⇒ 「Go 1.26.4 以上」という要求表記は `GOTOOLCHAIN=local` でも成立する。★ただしオフライン環境の利用者にとっては挙動が変わっている**——既定では取得が走る。

### 1.3 ★★書いてはいけないこと（**製造の注記をそのまま守る**）

**「CI は 1.26.8」は結果として正しいが、その機構はまだ観測していない。**

**★`actions/setup-go@v7` が `go-version-file: go.mod` から `toolchain` 行を読むのか `go` ディレクティブだけを読むのかを、ログで確かめていない。**

**★★Nightly が緑でも区別がつかない**——**`setup-go` が 1.26.4 を入れても `GOTOOLCHAIN=auto` がビルド時に 1.26.8 を取得するため、どちらの経路でもビルドは 1.26.8 で行われ、テストは緑になる。**

**⇒ `DES-001` には「ビルドに使う版は 1.26.8」と書き、「`setup-go` が 1.26.8 を install する」とは書かなかった。**

> **★★これは `M-126` の教訓の適用である**〔**読めない機構を事実として断定しない。⇒ 「もし〜なら」の形で書くか、書かない**〕**。★製造が自分でこの線を引いて報告してきた点を記録しておく。**
