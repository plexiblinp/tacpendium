## 1. 変更の概要

**M20-04 がプリセットの書き込み経路を作ったが、`recipe_cache` の再計算はそのどこからも呼ばれていない**（**実測＝`RecomputePresetCache` / `DeletePresetCache` の本番呼出元が 0 件**＝**D-354**）。**M20-05 がこれを配線する。**

**あわせて 3 件を同じ手番で処理する**——**既定プリセットへの追随**（**D-313**）／**`config.preset_id` の実在確認の残り半分**（followup `preset-config-preset-id-existence`）／**再計算の途中失敗が部分更新として残る欠陥**（**D-303** の実測 (2)）。

**非スキーマ・非破壊である。** **DB スキーマ・マイグレーションのいずれも変えない見込みであり、API の応答の形も変えない。** **変わるのは「いつ再計算されるか」と「どの値を読むか」と「どの入力を拒否するか」である。**

### 1.1 何を確定させるか

| # | 対象 | 現状 |
|---|------|------|
| 1 | **プリセット書き込み時の再計算** | **`SUPP-001` §7.2 が呼出元を既定しているが、本番の呼出元が 0 件である。** **DES-002 §4.2 のプリセット 3 本（POST / PUT / DELETE）は副作用を記していない** |
| 2 | **既定プリセットへの追随** | **`PUT /api/config` で `defaults.preset_id` を変えても、`recipe_cache` から取り出すキーは別の固定値のままである**（**D-313**）。**DES-002 §4.2 の `PUT /api/config` は「設定更新（LAN共有モード切替等）」としか書いていない** |
| 3 | **`config.preset_id` の実在検査** | **値域のみを見ており、DB 上の実在を見ない**（followup）。**`DES-006` §4 に対応する検証コードが無い** |
| 4 | **再計算の境界** | **全体を囲むトランザクションが無く、途中でエラーが返ると先行行の更新が残る**（**D-303**） |

### 1.2 CHANGE 対象と対象外の切り分け

| 区分 | 内容 |
|---|---|
| **CHANGE 対象** | **`DES-002` §4.2**（`PUT /api/config` の契約 ／ プリセット書き込み 3 本の副作用 ／ 実在しない `preset_id` のエラー） ／ **`DES-006` §4**（プリセット関連の検証を 1 本追加） |
| **CHANGE 対象外** | **`SUPP-001` §7.1・§7.2・§7.4**（**補足資料であり CHANGE を要しない**＝registry §0。**as-built への是正は同じ手番で自由改訂する**） ／ **`docs/handover/architecture-patterns.md` §9.2**（同上） ／ **`DES-003`**（**スキーマを変えない**） ／ **`DES-004`**（**表記の生成規則を変えない**。**変換の結果をいつ作り直すかだけを扱う**） ／ **`DES-005`**（**画面を作らない**。**既定プリセットの選択 UI は既存**） ／ **`REQ-001`**（**機能要件は増えない**） |

**★`DES-004` を対象外とした理由**——**本サブは表記の生成規則を 1 文字も変えない。** **`DES-004` を触る必要が出たら、それは §4.1 の「再計算のロジックを書き直さない」に触れている兆候である。**

**★`SUPP-001` を CHANGE 対象外としたうえで、同じ手番で是正する**——**§7.1 の「delete → insert」は as-built と食い違い**（実測は行単位の UPDATE＝**D-303**）、**§7.4.1 の「デフォルトプリセット = ID 1 の暗黙前提」は本サブで失効する。** **どちらも補足資料であり、バージョン bump のみで改訂してよい**（registry §0）。

## 3. 確定した設計判断

| # | 論点 | 判断 | 根拠 |
|---|------|------|------|
| 1 | **eager か lazy か** | **★eager で確定する** | **`D-292` が置いた条件「実件数の実測で閾値を超えたら lazy を再検討する」は、超えなかった**（**D-303**＝有効 `combos` 39 行・有効 `setups` 14 行の計 53 エンティティ・215 move step）。**`architecture-patterns` §9.2 の「1000 件規模の同期バッチ」という見積りは、実データでは 53 行だった** |
| 2 | **再計算を新しく書くか、既存の 2 メソッドを呼ぶか** | **★既存を呼ぶ** | **同じ計算が 2 か所にあると、規則が変わったときに片方だけ追随して、他方は古い規則で書き続ける。** **エラーにならない**（`E-76`） |
| 3 | **既定プリセットへ追随させるか** | **★追随させる**（**2026-08-12 開発者判断＝D-313**） | **同じ概念を `config` とコード上の固定値の 2 か所で独立に持っている。** **`PUT /api/config` で変えても取り出すキーが変わらないのは、利用者から見て設定が効いていない状態である** |
| 4 | **切替先にキャッシュが無い状態をどうするか** | **★切替時に当該プリセット分を再計算する** | **追随させると新しい状態が 1 つ生まれる**（**一度もエイリアスを触っていないプリセットへ切り替えるとキーが存在しない**＝**D-313**）。**lazy に倒すと `D-292` の判断と食い違う** |
| 5 | **`config.preset_id` の実在確認を本サブで引き取るか** | **★引き取る** | **M20-04 が実装しなかった判断は正しい**（**config サービスへ DB 依存を持たせる変更であり、同サブの指示書が閉じよと定めたドメインの外だった**＝**D-354**）。**⇒ 明示的に引き取る先が要る。** **`SUPP-001` §7.3 が名指しした 3 点のうち、これだけが半分残っている** |
| 6 | **実在しないプリセットを指した状態で起動したときの振る舞い** | **★起動は止めず、組み込みの既定へ倒してログへ残す**（**2026-08-14 開発者判断で確定**＝**D-358**） | **`config.toml` を手編集した利用者が起動できなくなる形は、個人利用のツールとしては重い。** **★暫定案がそのまま採られた。** **⇒ 画面への告知は本サブでは行わない**——**要ると判断した時点で別に足す**（**告知の置き場を決める作業は、それ自体が独立した設計判断である**） |
| 7 | **エイリアス編集の直後に古い表記が一時的に見える中間状態を許容するか** | **★許容する**（**2026-08-14 開発者判断＝D-356**） | **★ただし開発者の前提は実測と食い違っていた**——**「非同期に少しずつ再計算される」ではなく、1 プリセットにつき対象エンティティを逐次一括で処理する**（**D-303**）。**⇒ 許容の結論は変わらない。** **帰結として、編集の応答を再計算の完了まで待たせるかどうかを実装判断に委ねられる** |
| 8 | **再計算の途中失敗をどう扱うか** | **★部分更新として残さない。失敗を握り潰さない** |
| **★9** | **【2026-08-14 追加＝D-360】書き込みと再計算を同一トランザクションに入れるか** | **★入れない。コミット後に再計算だけを 1 つの境界で走らせる** | **★製造の実査で委任の前提が違っていた**——**`RecomputePresetCache` は tx を取らず、内部の読みも渡された tx を見ない。** **⇒ 書き込みの内側で呼ぶとコミット前のエイリアスを読み、古い表記を書く**（**エラーにならず、テストも緑のまま通る**）。**加えて SQLite の接続プールが無制限・`busy_timeout` 5 秒のため、開いた書き込み tx の内側から非 tx の UPDATE を撃つと別コネクションになり競合する。** **★読み経路をトランザクション対応にする案は採らなかった**——**`SUPP-001` §7.5.4 が守ろうとしている不変条件は「保存とキャッシュが食い違わないこと」だが、ここでの食い違いは stale であって不整合ではない**〔真実は `preset_aliases` にあり、再実行で回復できる〕。**★`D-356` で開発者が許容した状態と同じ形でもある** |
| **★10** | **【2026-08-14 追加＝D-360】既定プリセット値の寄せかた** | **★注入で寄せる。可変なプロセス状態を作らない。** **`punishfinder` の diff 0 に明示的な例外を出す** | **★設計卓の誤りである**——**「`punishfinder` diff 0」と「固定値を 1 か所へ寄せる」が両立しないことに気づかずに書いた**〔**寄せ先の共有関数を `punishfinder` が呼んでいる**〕。**★共有関数が可変状態を内部に持つ案は、diff 0 を形式的に満たすが `punishfinder` の振る舞いは同じだけ変わる**——**検査は通り、守りたかったものは守られない**〔**D-354** で記録した型〕。**★契約 F-3 が実際に凍結しているのは `moves` の意味論と値であり、本変更は触れない。** **⇒ diff 0 の代わりに「既定プリセットを変えても候補集合が変わらない」テストで固定する** | **握り潰した失敗は stale な表記として残り、利用者からは「反映されない」としか見えない**（`E-84`＝**「起きなかった」と「失敗した」を同じ顔で出さない**） |
