## 1. 変更の概要

**`M22-RESEARCH-01` が「QR は既に実装され、設定画面へ配線されている」と実測した**（`qrcode.react@4.2.0` ／ `QRCodeModal.tsx` ／ `SettingsSectionNetwork.tsx` ／ i18n 4 キー ／ テスト 3 ケース）。

**⇒ `M22-06` は「作る」サブではなく「検証と穴埋め」のサブである。**

**★本 CHANGE が固定するのは、`DES-005` §5.16 の QR に関する記述と実装の関係である。** 現行 §5.16 は次の 1 行しか持たない。

> 接続用QRコード表示ボタン（FR407、押下でモーダル表示。LAN共有モードON時のみ有効。QRコードには接続URLのみを含めパスワードは含めない）

**★「LAN共有モードON時のみ有効」が、ボタンの `disabled` なのかモーダル側のガードなのかが書かれていない。** **実測ではモーダル側が `{showQr && config.network.lanUrl && ...}` で守っているが、ボタン自体の状態は未確定である**（指示書 §3.3-2 で実査させる）。

**★非スキーマ・非破壊である。** **DB のテーブル・列・制約を 1 つも変えない。** **マイグレーションを消費しない。**

### 1.1 CHANGE 対象外（切り分け）

| 項目 | 対象外の理由 |
|---|---|
| **QR にトークン・パスワードを載せること** | **`FR407` が「接続 URL のみを含め、パスワードは含めない（撮影漏洩リスク回避）」と定めている。** **★変えない** |
| **代表 LAN IP の決定ロジック** | **`SUPP-001` §2.6.2 の既存仕様**（CORS の許可 Origin と同じ関数を使う）。**★変えると `M22-05` が固定した CORS の as-built も動く** |
| **QR ライブラリの差し替え・追加** | `CLAUDE.md` §6。**既に入っているものを使う** |
| **外部サービスへ問い合わせて QR を得る形** | **`DES-002` §8 の LAN 前提に反する。** **★既にクライアント側描画である** |
| **平文 HTTP / CORS / 認証** | 契約 F-3 ／ `M22-05` ／ `M22-01` の as-built |
| **LAN 共有モードの切替そのものの挙動** | 既存。**本サブは QR の面だけを触る** |

## 3. ★`REQ-001` は改訂しない（**指示書 §4.3-4 の穴候補は成り立たない**）

**指示書 v2.2.0 まで §4.3 の穴候補 4 に「`FR407` の状態記述が失効している——`FR407` は『希望・フェーズ3』として書かれているが、実物は既にある」と書いていた。**

**⇒ 「希望」は優先度、「3」はフェーズであって、実装済みかどうかとは無関係である。**

**★実証**——**`FR501`（簡易ログイン）は `M22-01` で実装済みだが、いまも「重要 / 3」のままである。** **`FR406`（LAN ホスト）も同様。** **⇒ 実装しても列は動かないのが本書の運用である。**

**⇒ 穴候補 4 を撤回し、指示書を v2.3.0 で是正した。** **★製造にこの仮説を追わせない。**

## 8. 追補（**2026-08-18**＝**D-432**）——**`SUPP-001` §2.6.2 を「変えないもの」から外す**

> **★本節は §2.1 の網羅宣言を部分的に覆す。** **覆した理由と、覆さなかった範囲を明示する**（`CHANGE-119` §8 と同じ作法）。

### 8.1 何を外したか

**§2.1 は `SUPP-001` §2.6.2（代表 IP 決定ロジック）を「変えないもの」に挙げていた。** **⇒ `M22-06` の実査で、同節の 1 行が as-built と食い違っていることが判明したため、この宣言を外す。**

| | 内容 |
|---|---|
| **食い違い** | **§2.6.2 は QR に埋め込む URL を `http://<IP>:<Port>/`（末尾スラッシュ付き）と書くが、実装はスラッシュを付けない** |
| **機能差** | **無い**（ブラウザが `/` へ正規化する。開発者の実機確認でもアクセスは成立している） |
| **★では、なぜ放置しないか** | **「仕様どおりに直した」つもりの変更が将来入るためである。** **URL 生成は CORS の許可 Origin 構築と隣接しており**（§2.6.1 ／ `DES-002` §4.4）、**機能差の無い変更のためにその面を触られるのが最も避けたい結果である** |
| **どちらへ寄せたか** | **`SUPP-001` を as-built へ寄せた**（**コードは変えない**）。**⇒ 「as-built が設計書と違えば、設計書が as-built に従う」という本プロジェクトの反映規約どおりである** |

### 8.2 覆さなかった範囲

**★§2.6.2 の代表 IP 決定ロジックそのもの**（除外するインタフェース・優先順位・同一優先度内の採り方）**は 1 文字も変えていない。** **外したのは URL の表記 1 行と、as-built の注記 2 件だけである。**

**★`REQ-001` `FR407` は §2.1 のまま「変えないもの」である**——**同書の `http://<IP>:<Port>/` は URL の形の例示であって、末尾スラッシュを要件として課したものではない。** **⇒ `SUPP-001` と `REQ-001` の表記が揃わないことは意図である**（**D-432**）。
