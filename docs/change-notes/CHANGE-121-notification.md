## 1. 変更の概要

**3 つを 1 本の CHANGE で扱う。いずれも `M23-01` の as-built で確定する。**

1. **スキーマ変更 1 件**——**`combos` へ `superseded_by_combo_id INTEGER NULL REFERENCES combos(id) ON DELETE SET NULL` を足す**（マイグレ `000078` を消費）。**★開発者の個別承認事項であり、2026-08-20 に承認済み**（`CLAUDE.md` §10 ／ **D-479**）。**M22 は全 9 サブでマイグレ消費 0 で終わったため、本 CHANGE が `000078` の最初の消費者になる。**
2. **仕様の撤回 1 件**——**`DES-005` §5.15 の「自動完全削除までの残日数」を撤回する**（**D-458**＝保持は無期限）。**★設計書だけでなく画面の表示も撤去する**——**現状は表示だけが在り機構が無い**（`M23-RESEARCH-01` 軸 A-2 の実測）。
3. **as-built の追記 1 件**——**`DES-002` §4.2 の経路表に、ゴミ箱系の 4 経路が 1 本も載っていない**（設計卓が 2026-08-20 に同文書を実査）。**★これは仕様変更ではなく、経路表が実態に追いついていなかった分の是正である。**

**★CHANGE 対象外**——**ゴミ箱の行クリックが 404 になる件**（followup `trash-row-click-404`）**と、materialize の出自が `PUT` で失われる件**（同 `materialize-origin-lost-on-put`）**は本 CHANGE の範囲に含めない。** 前者は `M23-06` 以降、後者は `M18-03b` の領域である。

## 3. 真因の記録——**「表示だけが在り機構が無い」がなぜ起きたか**

- **`DES-005` §5.15 は当初から「自動完全削除までの残日数」を表示項目に挙げていた。** 画面はその記述に従って実装され、**サーバ側の機構は作られなかった。**
- **★これは実装の漏れではなく、設計書が「表示項目」だけを定めて「その値を誰が保証するか」を定めていなかったことによる。** **画面設計書に数値の表示を書くときは、その値の供給元を併記する**——`SUPP-001` §5.5.4 規約 (15)（**「無いこと」を固定する前に、それが契約なのか現状なのかを分ける**）**の裏返しにあたる。**
- **⇒ 本 CHANGE は仕様変更であると同時に、「画面が利用者に嘘をついていた」状態の是正である。**

## 8. ★as-built の確定（2026-08-20・`M23-01` 完了 ＋ 開発者の実機確認）

**★本節は `M23-01` の設計伝達レポートを受けて設計卓が追記した。** **反映時は §2 より本節を優先する**（as-built が正である＝設計卓の規律 2）。

### 8.1 実測に委ねていた 1 件は、暫定と一致した

**§2.1-d ／ 指示書 §3.3-7＝「後継を完全削除したときの旧行の見え方」。**

| 系 | 実測 | ゴミ箱での見え方 |
|---|---|---|
| **FK=ON**（単一接続） | `ON DELETE SET NULL` が**発火する** | **旧行が再び現れる** |
| **FK=OFF**（PRAGMA を当てない接続） | **連鎖しない**。指す先を失った id が残る | **隠れたまま** |

**⇒ 設計卓の暫定「現れてよい」は FK=ON の系と一致した。実装は変えていない。** **★どちらの系でもデータは壊れない**——旧行は物理削除されず `FR601` の対象として残る。**割れるのは見え方だけである。** **⇒ `DES-003` §3.4 へ §2.1-d を書くときは「接続によって割れる」ことまで書く。** followup `superseded-row-visibility-splits-by-connection`（§V）へ登録済み。

### 8.2 印の書き込みは 2 文である（**指示書の「1 文でも 2 文でもよい」は結果として 2 文に決まった**）

`UpdateWithKeyChange` は **旧行の論理削除（楽観排他チェックを兼ねる 1 文）を先に実行し、そのあとで新行を INSERT する。** 旧行を消す時点では新行の id がまだ存在しないため、**印の書き込みは新行 id が確定したあとの 2 文目になる。** 同一トランザクション内であることは変わらない。**★順序（論理削除 → INSERT → 印の書き込み）は実装の制約であり、選択ではない。**

### 8.3 応答に出るが、どの画面も読まない

**製造は `superseded_by_combo_id` を DTO へ出す側を採った**（指示書 §9.2-2 が委ねた判断）。`ComboResponse` に `supersededByComboId`（`omitempty`）を持ち、フロント型にも足してある。**理由＝バックエンドが返さない値をフロント型が持つと、型が実態と食い違う**——本サブが畳もうとしている食い違いと同じ型の負債になるため。

**★本番コードで本列を読むのは、ゴミ箱の絞り込みの述語 1 か所だけである。** **⇒ `DES-002` へ as-built を書くときは「応答に出るが、どの画面も読まない」ことを明記する。** **書かないと、次の担当が「使われていない＝消してよい」と読む。**

### 8.4 通常一覧には述語を足していない

`OnlyDeleted` の分岐にだけ述語を足し、**通常一覧には足していない。** 通常一覧は `deleted_at IS NULL` で既に旧行を除外しており、足すと同じ事実を 2 か所で判定することになる（`architecture-patterns` §11 が警告する型）。**⇒ §2.2-i を書くときは「ゴミ箱の絞り込みにのみ足した」と限定して書く。**

### 8.5 i18n の撤去は「対象が無い」で終わった

**ゴミ箱画面は i18n を通っていない**（生の日本語文字列）。ロケールファイルに該当キーは **0 件**であった。**⇒ 片側だけ消えている状態は発生しえない。** **★これは撤去漏れではなく、そもそも i18n 化されていないという別の事実である。** **`P-11`（`OKI_TECH_TYPE_LABELS` の i18n 化）と同じ面であり、`M24-07`（用語・i18n）の入力になる。**

### 8.6 ★射程から漏れていた残骸が 1 件見つかった——`DES-003` §5

**指示書 §4.9 の否定形走査（系統③＝設計文書）が拾った。**

- **`DES-003` §5（論理削除と復元）**——**「物理削除は以下のタイミングで実施する。… ゴミ箱に90日以上保持されたレコード（設定で変更可能）」**
- **起票時の本通知書は `DES-003` §3.4（列追加）だけを挙げており、§5 は射程に入っていなかった。**
- **`DES-005` §5.15 だけを撤回すると、こちらが生き残って次の担当の前提になる**（**D-458** は保持を無期限で確定させている）。**しかも「（設定で変更可能）」という、存在しない設定項目まで書いてある。**

**⇒ 本通知書の反映先へ `DES-003` §5 を足した**（**D-487**）。**新規採番はしない**——**同一の撤回の射程を広げただけである**（先例＝`CHANGE-083` / `085` / `087` / `094`）。**★黙って広げず本節と `change-report-121` §1 に明記する**（playbook §4.18）。

### 8.7 ★ゴミ箱画面の 3 件は本 CHANGE で扱わない

開発者の実機確認で挙がった 3 件（**ルート列が常に空 ／ タグ列が常に `-` ／ 行クリックが 404**）は、**いずれも本サブの差分の外にあり退行ではない。** **★`DES-005` §5.15 は列構成を定義していない**——同節の表示項目は 1 行だけであり、「ルート」「タグ」という列は**設計書に根拠が無く実装が独自に持っている。** **⇒ 3 件のうち 2 件は「仕様どおりか」を判定する基準そのものが存在しない。**

**⇒ 本 CHANGE では扱わず、`M23-06`（ゴミ箱の利用者体験）の入力とする。** followup §V へ 3 件とも登録済み。**★列定義を `DES-005` §5.15 へ起こすのは `M23-06` の CHANGE で行う**——本 CHANGE でやると、撤回の射程がさらに広がって反映の単位が崩れる。
