## 2. 起票内容から動いたもの（★1 件）

### 2.1 §2-b の反映内容が「窓の起点」だけでは足りなかった

**起票時の §2-b は「窓の起点」と「押し始め／離し始め」の別を書けば足りるとしていた。** **as-built はこれに 1 項目を足した**——**窓の内側で変化する状態＝方向を、どの時点で採るか。**

**★製造の初版は窓の起点で 1 度だけ方向を引いており、レビューが欠陥を検出した**——**押し始めのズレ**（実測 中央値 8.30 ms ／ 最大 45.80 ms）**は方向にも等しく効く。レバーレスでは方向も物理ボタンである。** **⇒ `6` と強Pを同時に押して `6` が数 ms 遅れて立ち上がると、起点固定では「ニュートラル ＋ 強P」として確定する。**

**⇒ 受理した**（**D-347**）。**根拠 3 点**——**(1) `D-324` の実測が直接支持する欠陥である ／ (2) 方向は依然として集合に加わらず、指示書 §4.1-2 の「まとめる対象にしない」に抵触しない ／ (3) 実機確認で受理側の挙動が正しく出ている**（開発者・2026-08-13）。

**★設計卓の書き落としである。** **「その時点の方向」と書いて「その時点」を定義しなかった。** **時間窓を持つ仕様では、窓の長さ・起点・境界の 3 点は書かれやすいが、窓内で変化する状態の採取時点が落ちやすい**（本 report §5 の教訓へ）。

## 4. 追加で明文化したもの（★通知書 §2 の h〜k）

**いずれも「指示書に書かれていなかったので実装が確定させた」ものである。** **公開インターフェースに乗るため、DES へ落とさないと M21-03 / 05 / 06 が別々の解釈を採る。**

| # | 明文化した内容 | 書かないと何が起きるか |
|---|---|---|
| **h** | **判定はデジタル（`pressed`）で行う。アナログ値は使わない** | **「どこから押下とみなすか」という第 2 の閾値が復活する**（本サブが 1 つに絞った閾値を 2 つに戻す）。**トリガーを浅く触っただけでステップが生まれる** |
| **i** | **境界は半開区間 `[t0, t0 + W)`** | **後任が逆に読むと 1 フレーム分ずれる** |
| **j** | **★下限は「実測最大のうち大きいほう」＝ 83.30 ms** | **次の担当が 45.80 ms を下限と読み、窓を約半分に狭める余地が残る。** **⇒ それは唯一 silent な失敗の方向である**（利用者の入力が黙って落ちる） |
| **k** | **「窓が閉じた時刻」は「閉じたことに気づいた時刻」ではない** | **M21-03 がステップ間隔の算出に使い、誤った値を引く** |

**★j は本 report で最も重い 1 行である。** **通知書 §2-a は「実測の最大値を下回らせない」としか書いておらず、最大値が 2 つある**（押し始め 45.80 ／ 離し始め 83.30）**ことに触れていなかった。** **判定に押し始めを使う以上、押し始めの最大値を採るのが自然に見える——そして自然に見える読みのほうが、silent な失敗へ向かう。**

## 5. 「silent でない」の限界（★§2-c の補強）

**起票時の §2-c は「広すぎる誤りも狭すぎる誤りも読取表示があるかぎり画面に出る ⇒ 保守的に広く置いてよい」と論じた。** **この論理は正しかった**——**実機で実際に画面へ出た。**

**しかし開発者の実機確認で、その論理に足りないものが見えた**（2026-08-13）——**「素早く入力すると、別々のつもりの 2 入力が 1 ステップにまとまる」。** **画面には出ている。** **だが、まとまりうること自体を事前に知らない利用者は、その表示を「そういうものだ」としか読めない。**

**⇒ `DES-005` §6.4.2 へ 1 文を足した**——**「silent でないことは、気づかれることを保証しない」。** **あわせて告知の要件と置き場**（**M21-03**）**を同節へ書いた**——**まとまりうること ／ ゆっくり正確に入力すること ／ 不具合ではなく取りこぼしを防ぐための意図的な設定であること**の 3 点。

**★窓は狭めない**（開発者判断＝「コンボの入力アプリという意味で、ゲームより緩い感度にするのは悪くない」）。**設計側の裏付けも同じ向きである。**
