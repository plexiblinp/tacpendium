## 1. 変更の概要

**`VAL-C02`（同一キャラ・同一レシピ・同一状況のコンボの重複登録）の検証をすり抜けて、同一識別キーの本登録コンボが 2 件同時に存在した。**

**★一次源＝`M24-09c` の E2E 並列実行。製造は決定論的な再現手順を持っている。**

| # | 変更 | 対象 |
|---|---|---|
| **1** | **書き込みトランザクションを `BEGIN IMMEDIATE` で開始する** | `DES-002` §6.4 |
| **2** | **`VAL-C02` の検証を、登録と同じトランザクションの内側で `*sql.Tx` を使って行う** | `DES-006` §2.3 |
| **3** | **`NFR203` の実現方式へ「INSERT 経路は書き込みトランザクションの直列化で守る」を足す** | `REQ-001` |
| **4** | **`SQLITE_BUSY` の応答を決める**（**★as-built で確定**） | `DES-002` §4.2 |

**★★`VAL-C02` の判定ロジックそのものは 1 文字も変えない。** **変えるのは「いつ判定するか」だけである。**

**★CHANGE 対象外**——**UNIQUE 制約の追加**（§4-1） ／ **`deleted_at IS NULL` ／ `is_draft = 0` の述語** ／ **楽観排他（`version` カラム）** ／ **既存データに入り込んだ重複の掃除**（§5 リスク 6） ／ **保存ボタンの二度押し防止**（`M24-04` の面）。

## 2. 変更の内容

### 2.1 ★★`REQ-001` `NFR203`——**楽観排他が守れない領域を明記する**

**現行の逐語:**

> **「複数名利用時に同時実行による問題（データ競合・消失）が起きないこと。実現方式として楽観的排他制御を採用（`combos` テーブルに version カラムを保持し**更新時に**バージョン比較）、衝突時はユーザーにエラー表示し再読込を促す。SQLite の WAL モードを併用して DB レベルの同時書き込み問題を軽減する。」**

**★★楽観排他は UPDATE を守る手であって、INSERT を守らない**——**比較すべき既存行が無い。**

**⇒ `VAL-C02` の check-then-act は、`NFR203` が挙げた実現方式が構造的にカバーできない領域である。** **★「対策済み」の顔をした穴が空いていた。**

| 論点 | 決めたこと |
|---|---|
| **足すこと** | **★「検査してから書く」形（重複判定・上限判定など）は、検査と書き込みを同じ書き込みトランザクションの内側に置き、そのトランザクションを直列化することで守る** |
| **★楽観排他は撤回しない** | **UPDATE を守る手として不変**（`CHANGE-114` / `M22-03`。対象は `combos` / `setups` の 2 表・粒度は集約） |
| **★「悲観ロックは採用しない」との関係** | **★★抵触しない**（§3-2） |

### 2.2 ★★`DES-002` §6.4——**同時実行制御**

**現行の逐語＝「書き込み処理はサービス層でトランザクション境界を設け、楽観的排他制御（更新時のバージョン番号チェック）を導入して上書き事故を防ぐ。」**

| 論点 | 決めたこと |
|---|---|
| **★★書き込みトランザクションは `BEGIN IMMEDIATE` で開く** | §3-1 |
| **★★適用範囲は書き込みトランザクション全部** | **経路ごとに選ばない**（§4-3） |
| **★読み取り専用トランザクションは含めない** | 不要に write lock を取らせない |
| **★発行方法は as-built で決まる** | **指示書 §3.3-5 で実査させる**——**DSN の `_txlock=immediate` は全トランザクションに効くため上の 1 行と衝突する ／ 書き込み用のヘルパ 1 本で発行する形が筋である** |
| **★★`M23-10` の型と混同しない** | **`CHANGE-142` の「接続単位の PRAGMA は DSN で入れる」は接続単位の設定の話である。`_txlock` はトランザクション単位の話であり、同じ型ではない** |

### 2.3 `DES-006` §2.3——**判定のトランザクション境界**

| 論点 | 決めたこと |
|---|---|
| **★★判定条件は不変** | **6 項 ＋ `recipe_hash`**（`DES-005`:1336）／ **`deleted_at IS NULL`** ／ **`is_draft = 0`** ／ **NULL 同士は一致** ／ **`Flags` は `sort.Strings` 正規化**。**すべて 1 文字も変えない** |
| **★足すこと** | **判定は登録と同じ書き込みトランザクションの内側で行い、`*sql.Tx` を使って読む** |
| **★★`*sql.DB` 直読みを残さない** | **`D-360` の規約＝「署名が `*sql.Tx` を取るなら、その tx を読みにも使うこと」。** **⇒ tx の内側へ移しても `*sql.DB` で読んでいたら、未コミットの行が見えず意味が無い** |
| **★適用面** | **`POST /api/combos` ／ `PUT /api/combos/{id}` ／ materialize の 3 経路**（**★materialize の「同一レシピ ＋ `punish_counter` の探索」も check-then-act である**＝`CHANGE-089`） |

### 2.4 ★`DES-002` §4.2——**`SQLITE_BUSY` の応答**（**as-built で確定**）

**`BEGIN IMMEDIATE` は最大 `busy_timeout` 待ち、それでも write lock を取れなければ `SQLITE_BUSY` を返す。**

| 論点 | 決めたこと |
|---|---|
| **★現在の契約に無い** | 経路表にこの応答は載っていない |
| **★★混ぜないこと** | **重複エラー（`VAL-C02` の 400 `validation_failed`）とも、版不一致（409）とも区別する。** **`DES-006` §11.2 が「409 は 2 種類あり見分けはエラーコードで行う」と定めている。⇒ 第 3 の区別を作る** |
| **★形は製造の裁量** | ステータスとエラーコードの選択。**★理由を報告させ、設計卓が本 CHANGE の射程で反映する** |
| **★UI を作り込まない** | **1 人利用では `busy_timeout` を使い切ることは実質起きない** |

## 3. ★真因の記録

### 3-1 ★★「トランザクション境界を前へ動かす」だけでは、この欠陥は閉じない

**★製造の「検証が `BeginTx` の前に走る」は現象の記述であって、直し方ではない。**

**SQLite の既定の `BEGIN`（DEFERRED）は、最初の読みで read lock を、最初の書きで write lock を取る。**

**⇒ 検証 SELECT をトランザクションの内側へ入れても、2 つのトランザクションが両方 SELECT して「重複なし」を見たあと、順に INSERT できる。check-then-act はそのまま残る。**

**★★要るのは `BEGIN IMMEDIATE`**（開始時点で write lock を取る）。**⇒ 2 本目は 1 本目の commit を待ち、その後の SELECT は commit 済みの行を見る。**

### 3-2 ★★`NFR203` の「悲観ロックは採用しない」とは抵触しない

**SQLite は WAL モードでも writer を元来 1 本に直列化している。**

**⇒ `BEGIN IMMEDIATE` は新たな悲観ロックを導入するのではなく、そのロックを取る時刻を早めるだけである。** **★並行度は実質変わらない。**

### 3-3 ★★案 (a)（UNIQUE 制約）を採らなかった理由——**3 つある**

**開発者は 2026-08-26 に案 (b) を選択した**（`P-43` / `D-568`）。**理由は好みではなく、設計書から出た 3 点である。**

| # | 理由 |
|---|---|
| **1** | **★★`recipe_hash` は `combos` の列ではない。** `DES-003` の `combos` に在るのは `recipe_cache`（表示用 JSON）であり、**レシピの実体は子表 `combo_steps` のシーケンスである。** **子表を跨ぐ UNIQUE は書けない。** **⇒ 永続列の新設 ＋ 全行バックフィルが要る**〔**ハッシュは Go 計算のため素の SQL マイグレでは埋められない**〕 |
| **2** | **★★`DES-006` §2.3 の逐語「NULL 同士は『一致』として扱う」。** **SQL の UNIQUE は NULL を互いに異なるものとして扱う。** **⇒ 素の UNIQUE では `VAL-C02` の意味を再現できず、`COALESCE` 等の式インデックスで正規化の規則をもう 1 か所へ書き写すことになる** |
| **3** | **★★`DES-006` §2.1 が自ら書いている——「同じ条件にする」ではなく「同じ 1 本を呼ぶ。条件で書くと 2 本目が書き起こされて静かにずれる」。** **UNIQUE インデックスは構造的に 2 本目の実装である** |

**★あわせて 4 つ目の実務上の障害がある**——**既存データに重複が 1 件でも在ると `CREATE UNIQUE INDEX` が失敗する。**

### 3-4 ★★害の形——**静かに壊れる**

| # | 何が起きるか |
|---|---|
| **1** | **`PUT`（識別キーを変える編集）は「旧行を論理削除 → 新行を登録」なので、どちらが supersede されるかが不定になりうる** |
| **2** | **`materialize` は「同一レシピ ＋ `punish_counter` の既存を見つけたら生成せず既存 id を返す」ので、返る id が不定になる** |
| **3** | **利用者から見ると「消しても消しても同じコンボが残る」形になる** |

**★どれもエラーにならない。⇒ 気づく契機が無い。**

### 3-5 ★「1 人利用だから確率が低い」は成り立たない

**★設計卓は 2026-08-26 に一度そう書き、同日に訂正した**（`D-567`）。

| # | 理由 |
|---|---|
| **1** | **`NFR203` の既知の未達である**（§2.1） |
| **2** | **`FR406`（LAN 共有・複数端末から編集）はフェーズ3＝現行フェーズの要件である** |
| **3** | **★保存ボタンの二度押しで 1 人でも踏みうる**（**送信中に無効化しているかは実査項目**） |

**★★確率の見積もりを根拠に優先度を下げるときは、要件側に既に書かれた約束を先に引くこと。** **`NFR203` は設計書に在り、設計卓は読める位置にいた。**
