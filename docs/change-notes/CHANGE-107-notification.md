## 1. 変更の概要

**`DES-005` §6.4 の「将来（物理・M21）」に書かれた判定仕様は、PoC の実測と合わない。** 本 CHANGE はその是正と、チャタリングの扱いの明文化である。

**非スキーマ・非破壊である。** **DB スキーマ・マイグレーション・API 契約のいずれも変えない**（`m21-contract` §4.2）。

### 1.1 何が合っていないか

**§6.4 の現行記述**——「**同時押し判定は時間窓（例：16ms）内の入力を1ステップにまとめる（M21 で詳細調整）**」。

**PoC の実測**（**D-324**。USB・Chrome 151・rAF 間隔 中央値 4.20 ms・標本 各 90）——

| 指標 | レバーレス | パッド |
|---|---|---|
| 押し始めのズレ 中央値 | 8.30 ms | 8.30 ms |
| 同 p95 | **20.90 ms** | **33.30 ms** |
| 同 最大 | **20.90 ms** | **45.80 ms** |
| 離し始めのズレ 中央値 | 12.50 ms | 12.50 ms |
| 同 最大 | **50.00 ms** | **83.30 ms** |

**⇒ 16 ms では p95 に届かない。** **「例」として書かれた値だが、実装が引く唯一の数値がここしか無いため、そのまま採られる危険がある**（**`DES-004` §3.4 のサンプル表が現に固定点として引かれた前例がある**＝**D-339**）。

### 1.2 CHANGE 対象と対象外の切り分け

| 区分 | 内容 |
|---|---|
| **CHANGE 対象** | **§6.4 の判定仕様**（時間窓の値・単位・導出の根拠）／ **§6.6-3**（OD 技の同時押しの入力補助）**を実装フェーズ決定事項から回収** ／ **チャタリングの扱い** ／ **SOCD の規則** |
| **CHANGE 対象外** | **§6.2 ／ §6.3 ／ §6.4.1 ／ §6.8**（**CHANGE-106 で反映済み**）／ **§6.5 ／ §6.6-4**（**M21-04・`CHANGE-108`**）／ **§6.3 のキーボード行**（**M21-05・`CHANGE-110`**）／ **`DES-006`**（**下記**） |

**★`DES-006` を対象外とした理由**——**`m21-contract` §2 は「同時押し・チャタリングの入力バリデーション（要否は PoC 後に判断）」を M21 の所有節に挙げていた。** **PoC の結果、本件は入力層の集約の話であってバリデーション仕様ではないと判断する**——**受理するかしないかの判定ではなく、複数の入力を 1 ステップへ写す規則だからである。** **出口は既存の `move_code` であり、`DES-006` の検証仕様は変わらない。**

## 2. 変更の内容（`DES-005`）

| # | 対象 | 変更 |
|---|------|------|
| a | **§6.4「将来（物理・M21）」の判定仕様** | **「時間窓（例：16ms）」を、実測から導いた as-built の値へ差し替える。** **★値そのものより「導出の根拠」を書く**——**窓は `M21-RESEARCH-01` の実測分布から導き、最大値を下回らせない。** **★ミリ秒が一次であり、フレーム数は環境依存の換算値である**（計測環境は約 238 Hz。**60 Hz 環境では同じ実時間が約 1/4 のフレーム数になる**） |
| b | **§6.4 へ「窓の起点」と「押し始め／離し始め」の別を明記** | **as-built で確定した。** **★押し始めと離し始けで分布が違い、離し始めが一貫して大きい**（D-324）。 **【2026-08-13 追記＝D-347】★「窓の起点」だけでは足りない。** **窓の内側で変化する状態＝方向の採取時点**も同項で決める必要がある——**方向は窓の内側で観測しつづけ、最後の非ニュートラルを採る**（**起点の 1 点で固定しない**）。**理由＝押し始めのズレは方向にも等しく効き、レバーレスでは方向も物理ボタンであるため、起点固定では `6` が数 ms 遅れただけで「ニュートラル ＋ 強P」として確定する** |
| c | **§6.4 へ「窓を広く取ることは silent な失敗にならない」を明記** | **広すぎる誤り**（別入力が 1 ステップにまとまる）**も狭すぎる誤り**（同時押しが 2 ステップに割れる）**も、読取表示**（`FR106`）**があるかぎり画面に出る。** **⇒ 判定を保守的に広く置いてよい根拠になる**。 **【2026-08-13 追記＝D-347】★あわせて「silent でないことは、気づかれることを保証しない」を書く。** **実機で「素早く入力すると意図せず 1 ステップにまとまる」が確認された**——**画面には出ているが、まとまりうること自体を事前に知らない利用者は「そういうものだ」としか読めない。** **⇒ 告知の置き場を同じ手番で決める**（**M21-03**） |
| d | **§6.4 へ Bluetooth 未計測の明記** | **開発者が BT 接続の機体を所有しておらず計測できない**（**D-328**）。**かつ Gamepad API に接続方式のフィールドが無く、実行時に分岐もできない。** **⇒ 「BT でも動く」と書かない**（`E-84`） |
| e | **§6.4 へ SOCD の規則を新設** | **相反する方向の同時入力の解決規則。** **★1 スナップショット内の状態合成であり、時間窓の判定ではない。** **as-built で確定する** |
| f | **§6.4 へチャタリングの扱いを明記** | **`FR108` の決着。** **★「対策しない」も正当な決着である**（実測で観測されなかったため＝`E-41` 型）。**採る場合は「2 機種・USB・Chrome で観測されなかった」を根拠として明記し、一般化しないと書く** |
| g | **§6.6 の 5 件から「3. OD 技（弱中強同時2ボタン）などの同時押しの入力補助」を回収** | **本 CHANGE で決着するため、実装フェーズ決定事項から外す。** **★§6.6 の残り 4 件は据え置き**（1 → M21-06 ／ 2・5 → M21-03 ／ 4 → M21-04） |
| **h** | **【2026-08-13 追加＝D-347】§6.4 へ「判定はデジタル（`pressed`）で行う」を明記** | **アナログ値を判定に使わない。** **★使うと「どこから押下とみなすか」という第 2 の閾値が要る**（本サブが 1 つに絞った閾値を 2 つに戻すことになる）。**アナログ量は論理ボタンの状態として残り、必要になった面が読める。** **M21-05・M21-06 がこの前提に乗る** |
| **i** | **【2026-08-13 追加＝D-347】§6.4 へ判定窓の境界を明記** | **半開区間。** 窓の開始時刻を `t0`・窓長を `W` として **`[t0, t0 + W)`**——**ちょうど `t0 + W` の立ち上がりは新しいステップになる。** **★後任が逆に読むと 1 フレーム分ずれる** |
| **j** | **【2026-08-13 追加＝D-347】§6.4 の「下限」を「実測最大のうち大きいほう」と明記** | **★a の「最大値を下回らせない」だけでは足りない。** **押し始め 45.80 ms と離し始め 83.30 ms の 2 つがあり、判定に押し始めを使うため、どちらを下限とするかを書かないと次の担当が 45.80 を採って窓を約半分にする余地が残る。** **⇒ それは唯一 silent な失敗の方向である**（§4 のリスク行） |
| **k** | **【2026-08-13 追加＝D-347】§6.4 へ「窓が閉じた時刻」の意味を明記** | **「窓が閉じた時刻」であって「閉じたことに気づいた時刻」ではない。** 時間経過で閉じた場合は**窓の開始時刻 ＋ 窓長ちょうど**。**★M21-03 がステップ間隔の算出に使うため、実装側の気づきの遅れを混ぜると誤った値を引く** |

## 3. 確定した設計判断

| # | 論点 | 判断 | 根拠 |
|---|------|------|------|
| 1 | **判定窓を設計書に固定値で書くか** | **★書かない。導出の根拠と下限を書く** | **利用者からの報告で調整しうる**（**D-328** の条件 3）。**値だけを書くと、次の担当が根拠を失ったまま数値だけ引き継ぐ**——**`DES-004` §3.4 のサンプル表と同じ事故になる**（**D-339**） |
| 2 | **判定法を (α) 単一の広い窓 と (β) 実行時の自己校正 のどちらにするか** | **★設計書では決めない。実装サブが実査で選ぶ** | **`Gamepad.timestamp` の意味づけにブラウザ差がありうるため、成立するかを見てから決める。** **測る前に判定法を決めない**（**D-294** ／ `E-123`） |
| 3 | **チャタリング対策を実装するか** | **★設計書では決めない。実装サブが実測を根拠に決める** | **PoC で観測されなかった**（立ち上がり総数 50 ＝ 指示回数 50 ＝ 画面カウンタ 50 が 2 機種とも一致。1〜32 ms の帯に 3 指標とも 0 件）。**`E-41` 型の「対策不要」が候補である** |
| 4 | **`DES-006` を触るか** | **触らない** | §1.2 の理由 |

### 3.1 as-built で確定したもの（★2026-08-13・M21-02 完了。**D-347**）

| # | 論点 | 確定内容 |
|---|------|----------|
| 1 | **判定法 (α) / (β)** | **(α)＝単一の広い窓を採った。** **★(β) を棄却した決め手は同時押しのズレの分布ではない**——**`Gamepad.timestamp` の更新率が実測 2.2% ／ 4.2% であり、校正の材料そのものが得られなかった**（**PoC の軸 B-3 の観測**）。**分布以前の問題である** |
| 2 | **チャタリング対策** | **対策しない**（`E-41` 型）。**根拠＝2 機種・USB・Chrome で観測されなかった。一般化しない** |
| 3 | **SOCD の規則** | **左右は相殺してニュートラル・上下は上優先**（起票時の見込みどおり）。**★ただし実測は無い**——**PoC は SOCD を課題に含めておらず、「観測されなかった」ではなく「未計測」である**（`E-84`） |
| 4 | **窓を狭めるか** | **狭めない**（開発者判断 2026-08-13＝「コンボの入力アプリという意味で、ゲームより緩い感度にするのは悪くない」）。**設計側の裏付けも同じ向き**＝**狭める側の誤りが唯一 silent である**（§4） |
| 5 | **方向の採取時点** | **窓の内側で観測しつづけ、最後の非ニュートラルを採る**（§2-b の追記。**D-347 で受理**） |
