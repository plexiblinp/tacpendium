## 1. 変更の概要

DES-002 §4.2 主要エンドポイント表から `POST /api/combos/compare`(複数コンボの比較データ取得)行を削除する。

実装方式は M5 で「既存 `GET /api/combos/{id}` を N 件並列呼出し(フロント側で TanStack Query の `useQueries` を使用)」する案 1 を採用するため、本エンドポイントは新規実装しない。設計書本体と実装を一致させるための削除改訂。

---

## 2. 変更の理由

### 2.1 案 1 採用の経緯

M5 期間担当 Claude(設計担当)が M5-overview 作成にあたり、DES-005 §5.8 コンボ比較画面の表示項目 11 種を既存 API レスポンス(`GET /api/combos/{id}`)から取得可能かを評価した。M5-RESEARCH-01 調査(2026-05-22、製造担当 Claude Code を調査担当として運用)の結果、以下が確認された:

- 比較画面表示項目 11 種のうち、`recipeCache` 以外の全項目が `ComboResponse` に含まれている
- `recipeCache` 非含有だが、`defaultRecipe`(既定プリセット解決済み文字列)で代替可能(コンボ一覧画面 §5.4 の表示パターンと同等)
- セットプレイ展開(`setups` 配列埋め込み)は M4-02 で実装済み = 比較画面のセットプレイ列表示も既存 API のみで実現可能
- TanStack Query の `useQueries` は標準機能で導入可能(本プロジェクト初導入だが技術的問題なし)

これにより、`POST /api/combos/compare` を新規実装する必然性がなくなった。

### 2.2 設計書本体との整合性

DES-002 §4.2 は「代表的なエンドポイントのみ示す」と冒頭に明記されており、未実装エンドポイントを残すこと自体は設計書として不正とは限らない。しかし以下の理由で **削除する方が将来の保守に資する** と判断:

- M3 期間の CHANGE-006(`counter_type` → `hit_type` リネーム時の旧名削除)の運用と整合 = 「設計書本体は現在の実装と一致させる」原則
- 「実装されないエンドポイントが設計書に残っている」状態は将来のメンテナで混乱を生む(M4-1 由来教訓「設計書本体の前提記述は実態確認対象」と関連)
- フェーズ 2 以降に比較対象上限を大幅に増やす等で `POST /api/combos/compare` の必要性が再浮上した場合は、その時点で再度 CHANGE 通知書を起票して追加する形が自然(YAGNI 原則、playbook §17.1)

## 6. リスク

| リスク | 評価 | 対策 |
|--------|------|------|
| フェーズ 2 以降に比較対象上限を大幅に増やした場合、`useQueries` での N 件並列が現実的でなくなる可能性 | 低(現在の上限 5 件、フェーズ 2 以降の拡張時に再評価) | 拡張時に CHANGE 通知書を新規起票して `POST /api/combos/compare` を再追加する形で対応可能 |
| TanStack Query の `useQueries` が本プロジェクト初導入 | 低(TanStack Query 標準機能、技術的問題なし) | M5-01 指示書本体で利用方針を明文化、`web/src/features/combo/hooks/useCompareCombos.ts`(仮)で集約 |
| 設計書本体からの削除を後で復活させる必要が生じた場合の手戻り | 低(CHANGE 通知書経由の正規ルートで復活可能、過去の通知書履歴を辿れる) | change-report-015 + change-number-registry に CHANGE-015 の経緯を残すことで将来の参照を容易にする |
