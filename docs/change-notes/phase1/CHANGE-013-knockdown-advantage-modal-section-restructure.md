## 1. 変更の概要

DES-005 §5.7「コンボ登録・編集」**編集保存の動作** 節における `knockdown_advantage` 変更時の確認モーダルの **配置位置を修正** し、(a) 重複判定キー変更編集 / (b) メタデータ編集 のどちらの保存フローでも発火する仕様であることを明確化する。

**仕様の実体は変更しない**(解釈整合化のための節編成修正のみ)。実装方針も M4-overview §3.4 で定めた内容(案 X: knockdown_advantage 変更時の確認モーダルは保存方式によらず発火)を変更しない。

---

## 2. 変更の理由

### 2.1 設計書本体の節編成上の矛盾

現行 DES-005 §5.7 編集保存の動作節は、編集対象によって保存時の挙動を 2 種類に分離する旨を述べた後、(a)(b) のサブセクションを並べる構造をとる。

- **(a) 重複判定キー変更編集**(L286-290):
  - 重複判定キー(レシピ本体・始動技・position・opponent_stance・hit_type・opponent_size の 6 項目)のいずれか変更時 → 旧コンボ論理削除 + 新コンボ登録
  - **(a) の説明文の中段(L288-290)に「knockdown_advantage 変更時の確認モーダル」の仕様が記述されている**
- **(b) メタデータ編集**(L292):
  - ダメージ・ゲージ消費・起き攻め情報・`knockdown_advantage`・タグ・メモのみ変更時 → PATCH 直接更新
  - セットプレイ引き継ぎ処理は発生しないと明記

**矛盾の構造**: `knockdown_advantage` の変更は (b) メタデータ編集に分類されている(L292)のに、(a) の説明文の中段(L288)で「knockdown_advantage 変更時の確認モーダル」が書かれている。読者にとって以下の解釈分岐が生じる:

- **案 X**: 確認モーダルは保存方式(a)(b)によらず、knockdown_advantage が変更されたら発火(モーダル配置位置のみの節編成ミス)
- **案 Y**: 確認モーダルは (a) フローでのみ発火、(b) フローでは発火しない(節編成通りの解釈、ただし knockdown_advantage が (a) の重複判定キーに含まれていないため成立しないシナリオが多く、(a) フロー単独では「レシピ + knockdown_advantage 同時変更」のような複合変更のみが対象になる)

**M4-03 起票準備中に M4-7 反省の「設計書本体の §5.x 表示項目とアクション節をペアで読む」セルフチェックを実施した結果として本矛盾を発見**(2026-05-17)。

### 2.2 案 X 採用の根拠(2026-05-17 開発者判断)

開発者と協議の結果、**案 X**(確認モーダルは保存方式によらず knockdown_advantage 変更時に発火)を採用する。根拠:

- **論理的整合性**: `knockdown_advantage` が変わるとセットプレイの成立条件が変わる可能性があるのは、保存方式(a)(b)によらず同じ。確認モーダルの発生条件は「knockdown_advantage が変更されたこと」であり、保存方式(論理削除+新規 / PATCH 直接)とは独立した関心事
- **UX 観点**: knockdown_advantage 単独変更(これは (b) フロー)でもセットプレイ成立条件は変わる可能性があるため、モーダルなしで PATCH 直接実行する案 Y は UX 上の懸念がある
- **既存記述との整合**: 設計書本体の「セットプレイの成立条件が変わる可能性があるため」という記述は、保存方式によらない一般論として読むのが自然

### 2.3 M4-overview §3.4 との整合

M4-overview §3.4「knockdown_advantage 変更検知 → 紐付き setup 一覧取得 → 確認モーダル表示」は、本変更の案 X 採用と整合する(M4-overview 起票時点で案 X / 案 Y の区別を明示していなかったが、本通知書で案 X を確定とする)。

### 2.4 設計書本体を直接修正する根拠

M4-03 指示書の §4.x で「設計書 §5.7 (b) のメタデータ編集でも knockdown_advantage 変更時はモーダルを表示する」と書く案(指示書側で解釈を明示)もあり得るが、以下の理由で **設計書本体を修正する** ことを選んだ:

- 設計書本体の節編成の不整合は将来の設計担当・製造担当が同じ解釈ミスを再生産するリスクが高い
- 仕様変更ではなく解釈整合化のため、修正影響範囲が小さく、修正リスクが低い
- playbook §16 の精神「設計書本体は常に最新の確定仕様を反映する」と整合する

## 3. 変更の内容

### 3.1 DES-005 §5.7 編集保存の動作節の再構成

**現行(問題のある節編成)**:

```markdown
**編集保存の動作**:FR004の方針に従い、編集対象によって保存時の挙動を2種類に分離する。

- **(a) 重複判定キー変更編集**:レシピ本体・始動技・position・opponent_stance・hit_type・opponent_size のいずれかが変更された場合、保存ボタン押下でバックエンドは「旧コンボの論理削除」と「編集後内容での新コンボ登録」をトランザクション内で実行する。これにより重複判定(FR301)と衝突せず、訂正履歴も論理削除レコードとして残る。旧コンボに紐付いていたセットプレイは原則として自動的に新コンボに引き継がれる。

  **knockdown_advantage 変更時の確認モーダル**:knockdown_advantage が変わるとセットプレイの成立条件が変わる可能性があるため、紐付いているセットプレイがある場合は保存前に確認モーダルを表示する。「knockdown_advantage が変わるため、紐づくセットプレイN件が成立しなくなる可能性があります。引き継ぎますか?」とし、「すべて引き継ぐ」「紐付けを外す」「個別に選択」の選択肢を提示する。「個別に選択」の場合はセットプレイ一覧と各引き継ぎチェックボックスを表示する。

  knockdown_advantage が変わらない場合は従来通り自動引き継ぎでスムーズに保存し、保存完了後にトースト通知で「紐づくセットプレイN件を引き継ぎました。必要に応じて内容を確認してください」と表示する。トーストからセットプレイ詳細画面への遷移リンクを含めると親切。

- **(b) メタデータ編集**:ダメージ、ゲージ消費、起き攻め情報、knockdown_advantage、タグ、メモなどのメタデータのみが変更された場合、PATCH APIで直接該当コンボを更新する。ゴミ箱に不要なレコードが溜まらず、セットプレイ引き継ぎ処理も発生しない。

バックエンドは保存時に「どの項目が変更されたか」を判定し、自動的に適切な保存方式を選択する。ユーザーはこの切替を意識しなくてよい。
```

**変更後(節編成を整合化)**:

```markdown
**編集保存の動作**:FR004の方針に従い、編集対象によって保存時の挙動を2種類に分離する。

- **(a) 重複判定キー変更編集**:レシピ本体・始動技・position・opponent_stance・hit_type・opponent_size のいずれかが変更された場合、保存ボタン押下でバックエンドは「旧コンボの論理削除」と「編集後内容での新コンボ登録」をトランザクション内で実行する。これにより重複判定(FR301)と衝突せず、訂正履歴も論理削除レコードとして残る。旧コンボに紐付いていたセットプレイは原則として自動的に新コンボに引き継がれる(knockdown_advantage 変更時は下記「knockdown_advantage 変更時のセットプレイ引き継ぎ処理」に従う)。

- **(b) メタデータ編集**:ダメージ、ゲージ消費、起き攻め情報、knockdown_advantage、タグ、メモなどのメタデータのみが変更された場合、PATCH APIで直接該当コンボを更新する。ゴミ箱に不要なレコードが溜まらず、コンボ本体の置き換えは発生しない(knockdown_advantage 変更時は下記「knockdown_advantage 変更時のセットプレイ引き継ぎ処理」に従う)。

バックエンドは保存時に「どの項目が変更されたか」を判定し、自動的に適切な保存方式を選択する。ユーザーはこの切替を意識しなくてよい。

**knockdown_advantage 変更時のセットプレイ引き継ぎ処理(保存方式 (a)(b) 共通)**:

knockdown_advantage が変わるとセットプレイの成立条件が変わる可能性があるため、**(a)(b) どちらの保存方式でも** 紐付いているセットプレイがある場合は保存前に確認モーダルを表示する。「knockdown_advantage が変わるため、紐づくセットプレイN件が成立しなくなる可能性があります。引き継ぎますか?」とし、「すべて引き継ぐ」「紐付けを外す」「個別に選択」の選択肢を提示する。「個別に選択」の場合はセットプレイ一覧と各引き継ぎチェックボックスを表示する。

knockdown_advantage が変わらない場合の挙動は保存方式によって異なる:

- (a) 保存方式の場合: 紐付いていたセットプレイは自動的に新コンボに引き継がれる。保存完了後にトースト通知で「紐づくセットプレイN件を引き継ぎました。必要に応じて内容を確認してください」と表示する。トーストからセットプレイ詳細画面への遷移リンクを含めると親切。
- (b) 保存方式の場合: コンボ本体の置き換えが発生しないため、`combo_setups` の状態は変化せず、セットプレイ引き継ぎ処理も発生しない(トースト通知も表示しない)。
```

### 3.2 修正の要点

- 「knockdown_advantage 変更時の確認モーダル」の説明を **(a) のサブ項目から独立した小節** として再配置
- 確認モーダルが (a)(b) どちらの保存方式でも発火する旨を明示
- (a)(b) 各保存方式の末尾に「knockdown_advantage 変更時は下記の引き継ぎ処理に従う」のクロスリファレンスを追加
- knockdown_advantage が変わらない場合の挙動を (a)(b) 別々に整理(従来 (a) のみに記述されていたが、(b) 側の挙動を明示)

### 3.3 仕様の実体への影響

- **新規追加される仕様**: なし
- **削除される仕様**: なし
- **挙動が変わる仕様**: なし(現行も案 X として実装されるべきだったが、節編成上 (a) サブ項目に書かれていたため案 Y と読めた)
- **明確化される仕様**:
  - knockdown_advantage 変更時の確認モーダルは保存方式 (a)(b) 共通で発火する
  - knockdown_advantage が変わらない場合の挙動が (a)(b) 別々に明示される

## 6. リスクと考慮事項

### 6.1 既存実装への影響

- **コンボ編集画面の現行実装**(M2-02 編集 2 方式分離): 影響なし。本変更は設計書本体の節編成修正のみで、現行実装は M4-03 で knockdown_advantage 確認モーダルを **新規追加** する形(現状実装には確認モーダルが存在しない)

### 6.2 M4-03 起票への影響

本変更が反映されることで、M4-03 指示書を以下のように書ける:

- 「knockdown_advantage 変更時の確認モーダルは、(a) 重複判定キー変更編集 / (b) メタデータ編集 のどちらの保存フローでも発火する」と素直に書ける

- 指示書側で「設計書本体と解釈が異なる」旨の補足が不要になる

### 6.3 未承認の場合の代替案

開発者が本通知書を承認しない場合、設計書本体を変更せずに M4-03 指示書側で解釈を明示する形(設計書本体との解釈差分を v1.0.0 §4.x で根拠付き説明)で M4-03 起票することも可能。ただし、設計書本体の節編成不整合は将来の設計担当・製造担当が同じ解釈ミスを再生産するリスクが高いため、本通知書による設計書修正を推奨する。
