## 1. 背景

M3-05 完了報告(2026-05-15)で製造担当から、**バリデーションエラー時の `APIError.Details` の格納形式** が DES-002 §4.3 の JSON フォーマット例に明示されていない事実が指摘された。

### 1.1 現状の実装(M3-05 で確定)

M3-05 で combo ハンドラのバリデーションエラー時、以下のレスポンス形式で返している:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "バリデーションエラーがあります",
    "details": {
      "validations": {
        "issues": [
          {"field": "name", "message": "コンボ名は必須です"},
          {"field": "damage", "message": "ダメージは 0 以上の整数で指定してください"}
        ]
      }
    }
  }
}
```

`Details.validations.issues` の構造は `validation.ValidationResult` 型(`internal/validation/` 配下)に対応する。

### 1.2 DES-002 §4.3 の現状(CHANGE-010 取り込み後)

CHANGE-010 で追記した JSON 例:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "コンボに同一レシピが既に登録されています",
    "details": { "existing_combo_id": 42 }
  }
}
```

`details` フィールドは `map[string]any` で任意キー・値型を許容する旨は明示されているが、**バリデーションエラー時の典型的な構造(`validations.issues` 配列)** は JSON 例として示されていない。

### 1.3 必要性

- M4 以降で新規ハンドラが増えた際、バリデーションエラーの格納形式を `validations.issues` 構造で統一する基準が必要
- フロントエンド側のエラー表示ロジックが共通形式に依存する場合、設計書本体に正規仕様として明記しておく必要がある
- M3-05 で確立した実装パターンを設計書側に反映し、実装と設計書の乖離を解消する

## 2. 変更内容

### 2.1 DES-002 §4.3 への JSON 例の追加

CHANGE-010 §2.1 で追記した「共通 Go 型」節の末尾に、**バリデーションエラー時の典型例** として以下を追加する。

#### 追記内容(案)

> #### Details.validations の典型構造
>
> バリデーションエラー時の `details` フィールドは、`validations` キーの下に `issues` 配列を持つ構造を **推奨形式** とする。各 issue は `field`(フィールドパス文字列)と `message`(エラーメッセージ)を持つ。
>
> ```json
> {
>   "error": {
>     "code": "validation_failed",
>     "message": "バリデーションエラーがあります",
>     "details": {
>       "validations": {
>         "issues": [
>           {"field": "name", "message": "コンボ名は必須です"},
>           {"field": "damage", "message": "ダメージは 0 以上の整数で指定してください"}
>         ]
>       }
>     }
>   }
> }
> ```
>
> Go 側では `internal/validation/` 配下の `ValidationResult` 型(`Issues []Issue` フィールドを持つ)を `Details: map[string]any{"validations": result}` で渡す形が標準パターン。ハンドラ独自のフィールド構造を新設する場合は、本パターンと整合する形(配列構造の入れ子)を維持する。
>
> バリデーション以外のエラー詳細情報(例: 重複コンボの ID 等)は、`details` 直下に任意キーで配置してよい:
>
> ```json
> {
>   "error": {
>     "code": "DUPLICATE_COMBO",
>     "message": "同一レシピのコンボが既に存在します",
>     "details": { "existing_combo_id": 42 }
>   }
> }
> ```
>
> 上記 2 パターン(`details.validations.issues` 形式 / `details.<任意キー>` 形式)はいずれも共通型 `model.APIErrorResponse` の範囲内で表現可能であり、`Details: map[string]any` の柔軟性を活かした使い分けとなる。

## 5. 設計判断の根拠

### 5.1 CHANGE-010 と分けて起票した理由

製造担当の指摘(2026-05-15)を受けて DES-002 §4.3 の JSON 例を補強する変更だが、以下の理由で CHANGE-010 v1.1.0 への bump ではなく **別通知書として起票**:

- CHANGE-010 は「Go 共通型の明示」が主題、本通知書は「JSON 例の補強」が主題で、議論の焦点が異なる
- 番号運用ルールとして、起票済み通知書の改訂(v1.1.0 等)よりも別通知書での追加変更の方が、後続マイルストーンからの参照性が高い
- M4 以降の新規ハンドラ実装時に「CHANGE-010 + CHANGE-011 を併せて参照」する運用の方が、改訂版を辿るより明示的

### 5.2 `validations` キーの命名根拠

- Go 側の `internal/validation/` パッケージ名と整合
- 単数形 `validation` ではなく複数形 `validations` を採用する理由: バリデーション結果は `issues` 配列を含む集合体であり、複数形の方が概念的に妥当
- M3-05 製造担当の実装(`Details: map[string]any{"validations": result}`)と整合

### 5.3 `issues` 配列構造の根拠

- 1 つのリクエストで複数のフィールドエラーが同時発生するケース(例: コンボ名空 + ダメージ負数)に対応
- 各 issue が `field` + `message` のみのシンプルな構造で、フロントエンド側のレンダリングが容易
- Go 側 `validation.ValidationResult` 型と直接対応

### 5.4 「推奨形式」とした理由

- ハンドラごとに微妙に異なるバリデーションロジックがあるため、強制ではなく推奨とする
- ただし新規ハンドラは本形式を採用することを M4 以降の指示書で明記する運用とする
- 既存実装(M3-05 まで)は本形式に統一済みで、推奨形式と実態が一致している
