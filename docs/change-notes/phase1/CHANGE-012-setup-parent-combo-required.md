## 1. 変更の概要

セットプレイの作成 API において、**親コンボ ID を必須パラメータ** とし、親コンボに紐付かない単独のセットプレイ作成(下書き的・テスト的な単独作成も含む)を禁止する。本ルールをバリデーション設計書(DES-006)§3 に **VAL-S05** として正式追加する。

---

## 2. 変更の理由

### 2.1 設計上の必然性

- DES-005 §5.9「セットプレイ登録・編集」のアクション節で、「セットプレイとコンボの紐付けは、コンボ登録・編集画面(§5.7 item 10)またはコンボ詳細画面(§5.6)から行う。セットプレイ編集画面からの紐付け操作は除外する」と明記されている(CHANGE-003 で確定済み方針)。
- 上記方針により、UI 動線上はセットプレイ単独作成のエントリポイントが存在しない。
- しかし DES-006 §3 の現行 VAL-S01〜S04 にはこの制約が明示されておらず、サービス層 API としてはセットプレイ単独作成が成立してしまう状態にある(API 単体使用時の防御欠落)。

### 2.2 playbook §4.5.2 の精神との整合

playbook §4.5.2「サーバー側のエラー応答は API 単体使用時の防御として位置づける」の精神に従い、UI 動線だけで担保せずバックエンドのバリデーションとして明文化する。これにより、将来 API を直接叩くツール(取り込みツール等、フェーズ3)や CSV インポート(フェーズ2、VAL-I 系)でも同じ制約が一貫して効く。

### 2.3 retrospective-log §1 パターン A(過去ミス)との対応

「UI で守れているから API 層で書かなくていい」という判断は、retrospective-log §1 パターン A(既存実装の確認漏れ)に近い構造を持つ(UI 動線への暗黙依存)。明文化により、後続マイルストーンの設計担当・製造担当がこの暗黙前提を見落とすリスクを下げる。

## 3. 変更の内容

### 3.1 DES-006 §3 セットプレイ登録時のバリデーション表に追記

**現行(DES-006 v1.8.0)**:

```markdown
## 3. セットプレイ登録時のバリデーション

| ID | 検証内容 | 種類 |
|----|----------|------|
| VAL-S01 | `character_id` が存在するキャラクターか | ERROR |
| VAL-S02 | レシピが空でないか | ERROR |
| VAL-S03 | レシピ中の `move_id` が該当キャラに存在する技か | WARNING |
| VAL-S04 | 同一キャラの同じ親コンボに、同一レシピのセットプレイが既に紐付いていないか | ERROR |

セットプレイは親となるコンボの完走が前提条件のため、コンボのような状況を持たない。重複判定は「あるキャラの同じ親コンボに、同一レシピのセットプレイが紐付いていないか」で行う。異なる親コンボに同一レシピのセットプレイが紐付くこと自体は問題ない(セットプレイ転用支援FR011の対象となる)。
```

**改訂後(DES-006 v1.9.0)**:

```markdown
## 3. セットプレイ登録時のバリデーション

| ID | 検証内容 | 種類 |
|----|----------|------|
| VAL-S01 | `character_id` が存在するキャラクターか | ERROR |
| VAL-S02 | レシピが空でないか | ERROR |
| VAL-S03 | レシピ中の `move_id` が該当キャラに存在する技か | WARNING |
| VAL-S04 | 同一キャラの同じ親コンボに、同一レシピのセットプレイが既に紐付いていないか | ERROR |
| **VAL-S05** | **セットプレイ作成 API リクエストに親コンボ ID(`parent_combo_id`)が指定されているか。親コンボに紐付かない単独作成(下書き的なものを含む)は禁止する** | **ERROR** |

セットプレイは親となるコンボの完走が前提条件のため、コンボのような状況を持たない。重複判定は「あるキャラの同じ親コンボに、同一レシピのセットプレイが紐付いていないか」で行う。異なる親コンボに同一レシピのセットプレイが紐付くこと自体は問題ない(セットプレイ転用支援FR011の対象となる)。

**VAL-S05 の補足**: セットプレイは必ず親コンボに紐付く形でのみ作成可能とする。UI 動線上は DES-005 §5.9「セットプレイ登録・編集」のアクション節(CHANGE-003 確定方針)で「セットプレイとコンボの紐付けは、コンボ登録・編集画面または コンボ詳細画面から行う」と規定されており、本バリデーションはその UI 動線の暗黙前提を API 層で明文化したもの。サーバー側のエラー応答は **API 単体使用時の防御** として位置づける(将来の取り込みツール経由作成・CSV インポート時も同制約が適用される)。
```

### 3.2 リクエスト DTO の改訂(派生ドキュメント、参考)

M4-01 指示書で具体的に確定するが、`POST /api/setups` および `POST /api/combos/{id}/setups` のリクエスト DTO で `parent_combo_id` を必須フィールドとして扱う。Go DTO 例:

```go
type CreateSetupInput struct {
    ParentComboID int64    `json:"parentComboId"`  // 必須、未指定または 0 で VAL-S05 エラー
    CharacterID   int64    `json:"characterId"`
    Name          string   `json:"name,omitempty"`
    Description   string   `json:"description,omitempty"`
    Steps         []Step   `json:"steps"`
}
```

エラーレスポンス(CHANGE-010 / CHANGE-011 統一形式に準拠):

```json
{
  "error": {
    "code": "validation_failed",
    "message": "バリデーションエラーがあります",
    "details": {
      "validations": {
        "issues": [
          {"field": "parentComboId", "message": "親コンボ ID は必須です(セットプレイは親コンボに紐付く形でのみ作成可能)"}
        ]
      }
    }
  }
}
```

(本ブロックは指示書執筆時の参考。設計書本体への記載はバリデーション ID と意味のみで、DTO 詳細は SUPP-001 または指示書側で扱う)

### 4.3 実装(M4-01 で対応)

- `internal/service/setup/` のサービス層関数(`CreateSetup` 等)で `parent_combo_id` を必須引数として受け取り、未指定時は `model.APIErrorResponse`(`code: "validation_failed"`)を返す。
- ハンドラ層(`internal/api/setup/`)でリクエスト DTO の `ParentComboID` を `int64` 型(0 がデフォルト値)として受け取り、0 の場合はサービス層でバリデーションエラーとする。または `*int64` ポインタ型として nil チェックを行う(SUPP-001 §5.9 PATCH 送信ポリシーと類似の判定形)。具体実装はM4-01 指示書で確定。
- バリデーション関数 `ValidateSetupCreate(input)` の単体テストに「parent_combo_id 未指定 → VAL-S05 エラー」のケースを追加(playbook §11 テスト要件参照)。

## 5. 移行影響

### 5.1 データ移行

- **不要**。新規制約のため、既存データは影響を受けない(M3 完了時点でセットプレイレコードは未作成)。

### 5.2 後方互換

- **API 後方互換性なし**(M4 で初めて `POST /api/setups` 系を実装するため、現時点で API 自体が存在しない)。
- フェーズ2の CSV インポート(VAL-I 系)実装時、セットプレイ CSV には `parent_combo_local_id` 列が既に DES-005 §5.14 / DES-006 §6 で設計済み。本制約と整合する(セットプレイ単独 CSV インポートは既に禁止方向で設計されていた)。

### 5.3 既存実装への影響

- M0〜M3 完了時点で setup ドメインのバックエンド実装は未着手のため、既存実装への影響なし。
- フロントエンド側も M3 完了時点で setup 関連 UI は未着手のため、既存実装への影響なし。

## 6. リスク

### 6.1 想定されるリスク

| # | リスク | 影響度 | 対策 |
|---|--------|-------|------|
| R-1 | 「下書き的なセットプレイ作成」のユーザー要望が後発的に発生し、本制約を緩める CHANGE が必要になる | 低 | 開発者の確認済み方針(2026-05-16 本チャットでの回答「親なしセットプレイの作成は禁止したい、下書き的なものもなし」)。要望発生時は別 CHANGE で対応 |
| R-2 | M4-04(コンボ + セットプレイ同時登録)実装時、コンボ作成 API が一括で setups 束を受け取る形になるため、その内部処理で `parent_combo_id` が「これから作成されるコンボの ID」となり、API リクエスト時点では未確定になる | 中 | M4-04 指示書で「同時登録 API は内部的にトランザクション内でコンボ作成 → 親コンボ ID 取得 → セットプレイ作成の順序で実行する」と明記し、リクエスト DTO 上は `parent_combo_id` を要求しない別エントリポイント形にする(`POST /api/combos`(拡張) vs `POST /api/setups`(VAL-S05 適用))。M4-01 でこの差異を考慮した API 設計を行う |
| R-3 | コンボ詳細画面(§5.6)からの既存セットプレイ紐付け追加と、新規セットプレイ作成の API エントリポイントが混同される | 低 | M4-01 で API 設計時に明確に分離(`POST /api/combos/{id}/setup-links` で既存セットプレイの紐付け追加、`POST /api/combos/{id}/setups` で新規セットプレイ作成+紐付け)。M4-02 起票時の Q&A で再確認 |

### 6.2 リスク R-2 の補足

M4-01 設計時に最も注意が必要なポイントは R-2。リクエスト DTO レベルでの「parent_combo_id 必須」は **API 単体使用時のエントリポイント** に対するもので、コンボ + セットプレイ同時登録の内部処理ではトランザクションスコープで親コンボ ID が動的に確定するため、VAL-S05 はサービス層関数の引数レベルで `parent_combo_id != 0` をチェックする形が望ましい(ハンドラごとに親コンボ ID の渡し方が異なるため)。

具体的な実装方針は M4-01 指示書で確定する。
