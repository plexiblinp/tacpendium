## 1. 変更の概要

REQ-001 FR603(下書き自動保存、必須要件)+ FR603a(高度な復元動作、希望要件)を **論理削除パターンで廃止** する。これに伴い、DES-005 §5.7 下書き保存仕様の段落に廃止注記を追加する。

CHANGE 通知書の対象は **REQ-001 + DES-005 の 2 ファイルのみ**(プロジェクトの基盤的成果物 = ゴール定義に該当)。関連する補足資料(SUPP-001 §4.1、architecture-patterns.md §5、CLAUDE.md §4 / §10.X)の改訂は CHANGE 通知書の対象外であり、設計担当 Claude が本変更に伴う派生作業として自由改訂する(本書 §10 で別途明示)。

M6 マイルストーン全体スコープのうち、下書き自動保存は M6-04 で実装予定だったが、本変更により M6-04 のスコープは「M6 統合 E2E + 残課題 4 軽微修正」のみに縮小される。

---

## 2. 変更の理由

### 2.1 仕様変更の根拠

M6-02 / M6-03 までの動作確認(設定画面 + 初回起動ウィザード + スマホ専用ホーム + スマホフッター)を通じて、開発者が **下書き自動保存機能は当アプリの利用形態に対して過剰と判断**(2026-05-23)。SF6 コンボ管理は単発のコンボ登録・編集が中心で、長時間放置されるケースが想定よりまれであり、ブラウザクラッシュ・PC 再起動時の入力消失リスクに対する保護機能としての必要性が低いと評価された。

判断根拠:

- **実際の利用形態との乖離**: SF6 コンボ管理は 1 コンボあたり数分で入力完了するケースが大半、12 時間以上の長時間放置(FR603a の前提)は想定外
- **YAGNI 原則の正しい適用**(playbook §17.1 個人開発の規模感): 動作確認後の判断としての「過剰」評価は、実装前に発見できた最良のタイミング
- **保守コストの回避**: localStorage キー管理(`combo-draft-<comboId|new>-v1`)、復元ダイアログ UX、自動保存タイミング(debounce vs 定期保存の判断)、SUPP-001 §5.7 セッションタイムアウト 12 時間設定など、付随する設計判断・実装コストを M6-04 で投下する価値がないと判断
- **代替手段の存在**: 一般的なブラウザは「タブを閉じる際の確認ダイアログ」+「フォーム入力中の意図しないリロード防止」をデフォルトで提供しており、最低限の保護は実現されている

### 2.2 論理削除パターンの採用根拠

REQ-001 では既存運用として **論理削除パターン**(`FR007 | (FR301に統合のため廃止) | - | -` 形式)が確立されている(`FR007` が `FR301` に統合された際の先例)。FR603 / FR603a も将来復活させる可能性に備え、同パターンを採用する:

- 復活時の参照容易性: 仕様廃止の経緯と当時の規定内容を辿れる
- FR ID の欠番回避: ID を物理削除すると採番管理が複雑化
- 過去マイルストーン担当の作業履歴の温存

DES-005 §5.7 にも同パターンを適用(該当段落に打ち消し線 + 「※CHANGE-016 により廃止」等の注記を残す)。

### 2.3 CHANGE 通知書の対象範囲(影響範囲を REQ-001 + DES-005 に限定する根拠)

CHANGE 通知書は **プロジェクトの基盤的成果物(REQ-001 = 要件定義 + DES-001〜006 = 基本設計)の変更管理** が本来の役割。ゴール定義のブレを防ぐために承認手続きを経る。一方、補足資料(SUPP-001 / architecture-patterns / CLAUDE.md / playbook / handover / retrospective-log 等)は **要件定義・基本設計を実装に落とすための運用資料** であり、設計担当 Claude が柔軟に改訂できる(playbook §16 / change-number-registry §0 規定通り)。

本通知書は **REQ-001 + DES-005 の 2 ファイル** を CHANGE 対象とし、関連する補足資料の改訂は **派生作業として設計担当 Claude が自由改訂する** 形で扱う(本書 §10 参照)。これは過去の CHANGE-015(DES-002 1 ファイル + change-number-registry は派生作業)と同じ運用方針。

### 2.4 設計書本体との整合性

CHANGE-006(`counter_type` → `hit_type` リネーム時の旧名削除)+ CHANGE-015(`POST /api/combos/compare` 削除)の運用と整合 = 「設計書本体は現在の実装方針と一致させる」原則。ただし本件は論理削除パターン採用のため、設計書本体に廃止注記が残る点が CHANGE-006 / 015 と異なる(両件は物理削除だった)。
