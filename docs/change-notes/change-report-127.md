## 2. ★★裁定 1——**`resolve-setup-recipe` の扱い（`D-521`）**

### 2.1 何が起きたか

**指示書 §4.3-2 と `CHANGE-127` §4-5 は「`resolve-setup-recipe` に本番の呼び出し元が 0 件である ⇒ 本サブがその呼び出し元になる」と書いた。**

**★成立しなかった。** **`ResolveSetupRecipe` は論理削除済みの行に使えない**——**内部で最初に引く `GetRecipeCache` の SQL が `WHERE id = ? AND deleted_at IS NULL` を持ち、`M23-03` が意図的に塞いだ述語だからである**（同関数の godoc が「`M23-03` §4.2: combos 側とまったく同型であり、2 つで 1 組として塞いである」と明記している）。

**⇒ 製造は塞ぎに触らず、レシピ解決の計算本体を呼ぶ読み取り専用の経路を新設した**（開発者裁定 B・2026-08-23）。

### 2.2 ★★受理する。ただし逐語を補正する

**実装は正しい。** **`M23-03` の塞ぎは正しく、それを迂回せず、書き戻しもしない形は最も安全である。**

**★`CHANGE-127` §4-5 の逐語を補正した**——**「使う側で決着させる」は as-built と食い違う。** **`ResolveSetupRecipe` 自体は依然として本番の直接呼び出し元を持たない。**

### 2.3 ★★「使う／撤去する」の二択が粗かった

**`D-513` は本項を `M23-08` から `M23-06` へ差し戻し、「撤去の可否は『レシピ文字列を画面に出すか』に従属する」とした。** **その判断は正しかった。**

**★だが二択の立て方が粗かった。** **関数は「入口」と「計算本体」に分かれており、片方だけ使うことができた。**

| | 結果 |
|---|---|
| **計算本体** | **使われるようになった**（本サブが新しい入口から呼ぶ） |
| **`ResolveSetupRecipe`（生存行用の入口）** | **依然として直接の呼び出し元を持たない** |

**★★これは `M23-03` が `#6` で「表示用と検証用に関数を 2 つに分けた」のとまったく同じ構造である**——**求めている集合が違えば、入口も別に要る。** **`ResolveSetupRecipe` は「生存行用の入口」であり、削除済み行には別の入口が要った。**

**⇒ 殻の扱いは followup `resolve-setup-recipe-wrapper-still-unused` へ。** **撤去の可否は「セットプレイのレシピを生存行でも画面に出すか」に従属し、それはまだ誰も決めていない。**

**指示書 §2.3 / §9.1-2 は「画面の外に在る欠けを見つけた場合は、直さずに報告する」としている。** **製造は 7 か所のコメント（「導線づくりは `M23-06`」）を `M23-07` へ書き換えた。**

**★受理する。** **対象は「欠け」ではなく「本サブの完了によって失効する記述」である。** **放置すると `M23-06` を検索した後任が「済んだはず」と読み、`M23-07` の入力が静かに 1 件落ちる。**

**⇒ 一般形＝「サブの分割・移送の写し先には、実装コード内の言及も含まれる。」** **設計卓はそれを見られない。**

## 5. ★★`CHANGE-127` §2.1 の症状に但し書きが要った（`D-522`）

### 5.1 何が分かったか

**本書 §2.1 と指示書 §1.2 / §4.3-1 は「ゴミ箱の名無しセットプレイは『(名称未設定)』でしか識別できない」を中心の症状として挙げた。**

**★現行の登録・更新経路では、名前が空のセットプレイを 1 件も作れない**（`VAL-S06`＝`DES-006` §3。create / update の両方で空文字・空白のみを弾く）。**★開発者の dev DB 実査でも 0 件だった。**

**⇒ 名無しの行は `VAL-S06` 導入前に作られた既存データだけである。** **クリーンな DB では症状が発生しない。**

### 5.2 ★実装は残す。但し書きを書く

**製造の推奨 (a) を採る**——**`DES-005` §5.15 へ「名無しは `VAL-S06` 導入前の既存データにのみ存在する。レシピ文字列はその救済である」と条件付きで書く。**

**★残す理由 3 つ。**

1. **旧データには名無しが在りうる**（dev DB は 0 件だが、他の環境は分からない）。
2. **フォールバックは「名前が空になりうる将来」への備えとして機能する。**
3. **★既に実装済みであり、撤去するコストのほうが高い。** **開発者からも「やらなくてもよい」との判断が出ている。**

### 5.3 ★★設計卓の誤り——**前提を 2 か所とも確かめなかった（`M-70`）**

**本サブの指示書は、2 つの前提を確かめずに書いた。**

| # | 書いたこと | 実際 |
|---|---|---|
| 1 | **「`resolve-setup-recipe` の本番呼び出し元が 0 件だから、本サブがその呼び出し元になる」** | **使われていないのは「使えないから」だった**（`M23-03` が意図的に塞いでいた） |
| 2 | **「名無しセットプレイは識別手段がゼロになる」** | **その状態のデータは現在の経路では作れない**（`VAL-S06`） |

**★★共通の一般形＝「使われていない／起きている、と書く前に、なぜそうなのかを確かめる。」**

- **使われていないのは、使えないからかもしれない。**
- **起きているのは、過去データにだけかもしれない。**

**★皮肉にも、これは `M23-06` 自身のテーマ（同じ根から出た 2 つの症状）とまったく同じ形である。**

**★救ったのは指示書自身の実査項目だった**——**§3.3-1 が「入力と出力を**逐語で**確かめる」と書いてあったため、1 は着手前に判明した。** **★「在ることを確かめる」ではなく「逐語で確かめる」と書いてあったことが効いた。** **2 は Go テストを書く段階（`VAL-S06` に弾かれた）で初めて気づいており、実査項目が無かった。**

**⇒ 機構化**——**症状を挙げるときは「その状態のデータが現在も生まれるか」を実査項目に置く。** **`design-instruction-playbook` へ規則として足した。**
