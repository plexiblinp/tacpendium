## 1. 変更の概要

**M23 が進む中で、削除の周りに「別のサブで」と送られた是正が 5 件溜まった。** **共通点は「画面を触らない」ことである。**

1. **完全削除が CASCADE に依存している 5 表を明示削除へ移す**（**確認事項 5** の決着）。
2. **★子表の一覧が将来ずれることを検出し続けるテストを入れる**（§2.2。**★本 CHANGE でいちばん重要**）。
3. **`combos.materialized_from_combo_id` の self-FK を明示的に NULL 化する**（§2.3）。
4. **コンボ側の完全削除の前チェックを Tx 内へ移す**（§2.4）。
5. **論理削除が削除日時を上書きするのをやめる。ただし成功は返し続ける**（§2.5）。
6. **引き継ぎオプションの母集団に削除済みセットプレイを含める**（§2.6）。

**★CHANGE 対象外**——**`P-04` の根治**（`M23-overview` §1.3-5 が M23 のスコープ外としている。この判断は変えない）／ **他の表の CASCADE 依存** ／ **既存 orphan の掃除**（データを消す変更＝開発者の判断）／ **未使用のレシピ解決経路の撤去**（**D-513** で `M23-06` へ差し戻した）／ **画面の変更**。

## 2. 変更の内容

### 2.1 CASCADE 依存 5 表を明示削除へ（確認事項 5 の決着）

**`HardDelete` が明示削除するのは 3 表であり、`combos(id)` を `ON DELETE CASCADE` で参照する子 6 表のうち明示削除は `combo_setups` の 1 表だけである**（`M23-RESEARCH-01` 軸 F）。

**⇒ CASCADE 依存は 5 表**——`combo_steps` / `combo_tags` / `combo_oki_options` / `combo_punishes` / `combo_punish_curations`。

**★`P-04` の影響下にあることは逐語で確定している**——`PRAGMA foreign_keys = ON` は `*sql.DB.Exec` で 1 回だけ流されており、プールは無制限に増えうる。**⇒ PRAGMA を受け取っていない接続では CASCADE が発火しない。**

**★★そしてその 5 表が消えたことを主張するテストは 0 件である。発火しなくても全テストは緑のままである。**

### 2.2 ★★本 CHANGE の核心——**明示削除は「忘れられる形」であり、それを補う仕組みを同時に入れる**

**★明示削除へ移すことは、無条件に良い変更ではない。**

| | CASCADE 依存 | 明示削除 |
|---|---|---|
| **新しい子表が増えたとき** | **何もしなくても消える**（FK が効いていれば） | **★誰かが `HardDelete` に 1 行足すのを忘れる** |
| **FK が効いていないとき** | **黙って orphan が溜まる** | **確実に消える** |

**⇒ 移すなら、忘れたことが分かる仕組みを同時に入れなければならない。**

**★★入れる仕組み＝スキーマから `combos` の子表を機械的に列挙し、完全削除の後にそのすべてが空であることを主張するテスト。**

- **★表名をハードコードした一覧で書かないこと。** **それでは目的を果たさない**——**表を足す人は、テストの一覧も一緒に忘れる。**
- **★列挙が 1 件以上あることを先に主張すること。** **0 件の一覧に対する「すべて空である」は常に真である**（`M23-04` / `M23-05` と同じ形の罠）。

**★★設計卓は、このテストが無いなら明示削除への移行を推奨しない。**

### 2.3 self-FK を明示的に NULL 化する

**`combos.materialized_from_combo_id` の self-FK は `ON DELETE` 句を持たない**（既定の `NO ACTION`）。**⇒ materialize 生成物を持つ基底コンボの完全削除は、FK=ON なら FK 違反、FK=OFF なら dangling 参照になる**（**★実挙動は未実査**）。

**⇒ `combos` の行を消す前に、同一トランザクション内で `materialized_from_combo_id` を NULL にする。**

**★2 点。**

1. **★マイグレーションで FK 句を変えない。** **SQLite は制約の `ALTER` を持たず、表の作り直しになる。** コストが目的に見合わない。
2. **★NULL 化であって削除ではない。** materialize 生成物は独立したコンボであり、基底が消えても利用者のデータとして残る。**消すと利用者のデータが黙って失われる。**

**★`superseded_by_combo_id` は `ON DELETE SET NULL` であり**（`DES-003` §3.4）、**挙動を揃えることになる。**

### 2.4 完全削除の前チェックを Tx 内へ

**`PermanentDelete` は `FindByIDAllowDeleted` で存在と削除済みを確かめてから `BeginTx` している**（軸 D-6）。

**★実害——判定してから Tx を張るまでの間に、他の利用者がその行を復元しうる。⇒ 復元されたコンボが完全削除される。** **データの消失であり、TOCTOU の中でも重いほうである。**

**⇒ `M23-02` がセットプレイ側で採った形と同じく、Tx の内側へ移す。** **★応答は変えない。**

### 2.5 論理削除が削除日時を上書きするのをやめる

**コンボの論理削除は既に削除済みの行にも成功し、`deleted_at` を上書きする**（軸 E-1）。**⇒ 利用者から見ると「消した日が後ろへずれる」。**

**★★「2 度目は `404` を返す」へは変えない。** **`M23-03` が `DES-002` §4.2 へ契約として固定したばかりである**——**「論理削除は楽観排他を行わず冪等に成功する」。排他を入れると「消したいのに消せない」経路が生まれる。**

**⇒ `UPDATE` の条件に `deleted_at IS NULL` を足し、0 行でも成功を返す。**

| | 変える前 | 変えた後 |
|---|---|---|
| **2 度目の応答** | 成功 | **成功**（変えない） |
| **`deleted_at`** | 上書きされる | **★最初の値のまま** |

**★既存テスト「2 度目も成功する」は緑のまま通る。**

**★★セットプレイ側は触らない。非対称は残す。** **理由＝揃えるべきなのは実装ではなく性質である。** 守りたい性質は「削除日時がずれないこと」であり、**セットプレイ側は 2 度目が通らないので元からずれない。** **⇒ 両者は同じ性質を、違う実装で満たしている。**

### 2.6 引き継ぎオプションの母集団

**`PUT` の `setupCarryOptions`（`unlink_all` / `individual`）が読む紐付けの母集団に、削除済みセットプレイを含める。**

**★除外していると、ゴミ箱に居るセットプレイの紐付けが利用者に見えないまま落ちる。** **`M23-02` の看板「復元すると紐付いていた全コンボへ一斉に戻る」が、見えない条件で成立しなくなる。** **★見えない条件で成立しない約束は、成立しない約束より悪い。**

**★`M23-03` が塞いだ「参照側の除外」とは逆向きの判断である**——**`architecture-patterns` §11 の判断表でいえば段 1**（**塞ぐと機能が壊れる**）。

## 3. 真因の記録——**「守っているつもり」が 2 種類ある**

**★本 CHANGE の 5 件は、性質で 2 つに分かれる。**

| 種類 | 該当 | 何が起きていたか |
|---|---|---|
| **(A) 仕組みに委ねていたが、その仕組みが効く保証が無かった** | (1) CASCADE 依存 ／ (2) self-FK | **FK に委ねていたが、`P-04` により発火が保証されない。** **★そして委ねたことを守るテストが 0 件だった** |
| **(B) 片方だけ直して、もう片方が置き去りになった** | (3) 前チェックの Tx 位置 ／ (4) 削除日時 ／ (5) 引き継ぎの母集団 | **`M23-02` / `M23-03` がセットプレイ側や参照側を直したときに、対になる側が残った** |

**★★(A) の一般形＝「仕組みに委ねたところには、委ねたとおりに動いていることを主張するテストを置く。」**

**委ねること自体は正しい。** **委ねたまま何も確かめないと、効かなくなったことに誰も気づかない**——**効かなくてもテストは緑である。**

**★★(B) の一般形＝「非対称を直すサブは、直した側と対になる側の一覧を残す。」**

**`M23-02` / `M23-03` はどちらも「本サブは触れていない」と正しく報告した。** **⇒ 報告があったから本サブがある。** **報告が無ければ、非対称は誰にも数えられないまま残っていた。**

**⇒ `architecture-patterns` §11 へ (A) を 1 段落として足す**（§4-1）。
