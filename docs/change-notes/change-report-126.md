## 2. ★★裁定 1——**指示書 §4.5 の機序が逆だった（`D-526` / `M-71`）**

### 2.1 何を書き、何が実際だったか

**指示書 §4.5 は「引き継ぎオプションが読む紐付けの母集団に、削除済みセットプレイを含めること」と書いた。**

**★実測。**

| 側 | 述語 |
|---|---|
| **読み取り 3 か所**（引き継ぎの選択肢を作る） | **`s.deleted_at IS NULL` を持つ**（削除済みを利用者に見せない） |
| **解除側**（`DELETE ... NOT IN`） | **★述語が 1 つも無く、`combo_setups` の全行を対象にしていた** |

**⇒ 落ちる機序は「読みが除外している」ではなく「★読みが除外しているものを、書きが除外せずに消している」だった。**

### 2.2 ★文言どおりに直していたら壊れていた

**読み側を緩めると、ゴミ箱のセットプレイがコンボ詳細画面に出る。** **`CHANGE-122` / `CHANGE-123` が意図して入れた除外を壊し、同じ指示書の §4.7「画面を 1 バイトも触らない」にも反する。**

**⇒ 製造が Plan Mode の実査（§3.3-6）で機序を数え直したことで防がれた。**

### 2.3 ★★誤りの起点——**followup の記述をそのまま信じた**

**followup `setup-carry-drops-trashed-links` は「引き継ぎオプションが削除済みのセットプレイを**見ない**ため、ゴミ箱のセットプレイの紐付けも黙って落とす」と書いていた。**

**★「見ないため」＝読み側の話である。** **設計卓はそれを検証せずに指示書へ機序として写した。**

**★★一般形＝followup の記述は「症状の観察」であって「機序の特定」ではない。** **指示書へ写すときに機序として扱ってはいけない。**

**⇒ `M-71` として §6 へ。`design-instruction-playbook` §4.26.1 を新設した。**

## 5. ★★`P-04` の物証（`D-527`）

**開発者が 2026-08-23 に実 DB を読み取り専用で開いて計測した**（データ変更なし）。

| 対象 | 件数 |
|---|---:|
| `combo_oki_options` | **12** |
| `combo_steps` | **6** |
| `combo_tags` | **1** |
| 他の子表 ／ self-FK 側 | 0 |
| **合計** | **19** |

**★★これが `P-04` の位置づけを変える。**

- **静的走査と probe が示せたのは「可能性」までだった。**
- **実データに残骸があるということは、本番で実際に発火していなかった時期があるということである。** **⇒ 推論ではなく物証がある。**
- **⇒ 根治サブを起こすかどうかの判断材料が、仮定ではなく実測として揃った。** **★開発者の手番へ置いた。**

**★self-FK 側が 0 件だったことの読み方**——**実装前の probe では FK=ON の接続で完全削除そのものが落ちていた。** **⇒ 「落ちていたから dangling が残らなかった」という読み方もできる。** **`M23-08` の NULL 化は、既に出ている実害を消す変更ではなく、これから出る実害を防ぐ変更である。**

**★★`combo_tags` の 1 件は今この瞬間の実害である**——**タグ削除ガードの使用数え上げが `combo_tags` を単独で数えており、結合も述語も持たない。** **⇒ orphan の 1 行がタグを「使用中」に見せ続け、利用者はそのタグを消せない。** **★同じ表を読む 2 つの経路で結論が割れている。**

**★★orphan の供給源は 2 つあり、塞いだのは 1 つだけである**——**タグの削除は `combo_tags` を CASCADE に委ねたままである。** **⇒ 「今後 orphan は増えない」と読まないこと。**

**★掃除はしていない**（データを消す変更＝開発者の判断）。

## 6. `DES-003` §5 へ書いた本体

**`HardDelete` の全 10 操作**（明示削除 7 表 ＋ self-FK 2 本の NULL 化 ＋ 行の削除）**と、宣言と実装の関係。**

**★★宣言された `ON DELETE` 句は「意図の記録」であり、完全削除の実挙動は実装が持つ。**

| 列 | 宣言 | 実装 | なぜ |
|---|---|---|---|
| `materialized_from_combo_id` | **`ON DELETE` 句なし** | **コードで NULL 化** | 宣言のままでは FK=ON の接続で完全削除そのものが失敗する（実測） |
| `superseded_by_combo_id` | **`ON DELETE SET NULL`** | **コードでも NULL 化** | **宣言はあるが発火が保証されない** |

**★どちらも「削除」ではなく「NULL 化」である。** **★`version` / `updated_at` は動かさない。** **★スキーマは変えていない。**

## 7. 製造の上位集合 1 件——**設計卓が次に書くときの改善点**

**製造がレビューの取り込みで、子表の機械列挙を指示書 §4.1-3 の文言（「`combos` を `ON DELETE CASCADE` で参照する子表を列挙する」）より広げた。**

**広げた先＝「完全削除の後に、消えたコンボの id を指していてはいけない列」**（6 件 → 9 件。直接の子 6 ＋ self-FK 2 ＋ 孫 1）。

**★製造の判断が正しい。** **CASCADE に絞ると「参照するが CASCADE 句を持たない新表」が、列挙にも明示削除にもテストにも出てこない。** **★それはまさに同じ指示書が別途扱っていた self-FK と同じ型の穴である。**

**⇒ `design-instruction-playbook` §4.26.2 を新設した**——**同型の指示書を書くときは、最初から「参照列」で書く。**
