## 1. 変更の概要

**`DES-002` §4.4 は CSRF 対策を 2 本立てで定めているが、成立しているのは 1 本だけである。**

| # | 対策 | 状態 |
|---|---|---|
| 1 | **SameSite=Strict Cookie** | **★成立した**（`M22-01`。`combomgr_session; Path=/; HttpOnly; SameSite=Strict`）。**★従来は「Cookie を発行するコードが 0 件」で前提そのものが無かった** |
| 2 | **`X-Requested-With` の要求 ＋ CORS preflight** | **★サーバ側の検証が 0 件。** フロントは **`PUT /api/config` の 1 経路にだけ付与**しており、**他の非 GET ルートには付けていない** |

**⇒ 本 CHANGE は 2 をどうするかを決め、§4.4 を as-built へ揃える。**

**★非スキーマ・非破壊である。** **DB のテーブル・列・制約を 1 つも変えない。** **マイグレーションを消費しない。**

### 1.1 CHANGE 対象外（切り分け）

| 項目 | 対象外の理由 |
|---|---|
| **HTTPS の導入** | **契約 F-3。** 平文 HTTP が前提である |
| **未認証で叩ける経路のレート制限** | followup `auth-unauthenticated-kdf-cost`。**`NFR102`「過剰でない対策」と LAN 前提から現状のままで整合している。** **★しかも `golang.org/x/time/rate` の新規依存が要る**（`M22-08` の実測） |
| **保護対象の判定をメソッド対にすること** | followup `auth-unprotected-paths-are-method-agnostic`（記録のみ・低） |
| **Cookie の属性** | `CHANGE-112`（`M22-01`）の as-built。**★`Secure` を足さない**（平文 HTTP で送られなくなる） |
| **脅威モデル** | **`DES-002` §4.4 の「LAN 内は信頼する」を変えない** |

## 2. 変更の内容

| # | 対象 | 変更 |
|---|------|------|
| **a** | **`DES-002` §4.4 の「第一対策」** | **★as-built を書き足す**——**`combomgr_session; Path=/; HttpOnly; SameSite=Strict`。** **★`Secure` は付けない**（**平文 HTTP が前提であり、付けると Cookie が送られなくなる**）。**⇒ この一文を書かないと、次の担当が「`Secure` が抜けている」と読んで足す** |
| **b** | **`DES-002` §4.4 の「補助対策」** | **★§4 で確定した案に従って改訂する**（撤回 ／ 全経路へ要求 ／ 設定変更系のみ） |
| **c** | **`DES-002` §4.4 へ CORS の as-built を追記** | **許可 Origin ／ メソッド ／ ヘッダ ／ `AllowCredentials` の実値**（`M22-05` の実査で確定）。**★あわせて「本アプリの主経路はクロスオリジンではない」ことを明記する**——**スマートフォンは `http://<LAN IP>:47318` を開き、同じ Origin へ API を叩く** |
| **d** | **`DES-002` §4.4 へ「境界を守っているのはバインドである」を 1 行** | **ローカルモードは `127.0.0.1` にバインドしており外から届かない**（§3.2）。**⇒ CORS/CSRF は `server.mode` で構成を変えない。** **★書かないと「ローカルだから緩めてよい」と読んで分岐が生まれる** |

### 2.1 ★変えないもの（網羅宣言）

- **`DES-002` §4.4 の脅威モデル**（「LAN 内は信頼する」・WPA2/WPA3 前提・ネットワーク側の防御責任）
- **`DES-002` §3.2**（バインドアドレスの制御） ／ **§3.4**（公開状態の明示と警告。**`CHANGE-113` で改訂済み**）
- **`DES-002` §8 / §8.1 / §8.2**（認証・パスワードの検査。**★とくに §8.2 の歯止め b＝`curl` が唯一の復旧経路**）
- **`REQ-001`** / **`DES-001`** / **`DES-003`** / **`DES-004`** / **`DES-005`** / **`DES-006`** / **`SUPP-001`**

### 2.2 真因の記録

**★バグ修正ではない。** **`DES-002` §4.4 は設計として妥当だった。**

**★足りなかったのは「補助対策が実装されないまま 2 年近く経った」という事実の扱いである。**

| # | 内容 |
|---|---|
| 1 | **★第一対策が成立していなかった期間が長かった**——**Cookie そのものが無く、認証も無かった。** **⇒ その間、補助対策だけを実装しても守るものが無かった** |
| 2 | **★`M22-01` で第一対策が成立した。** **⇒ いま初めて「補助対策が要るか」を判断できる状態になった** |
| 3 | **★同時に、`M22-08` が「`curl` 相当が唯一の復旧経路である」と定めた**（`DES-002` §8.2 の歯止め b）。**⇒ 補助対策を全経路へ掛けると、この経路が消える** |

**⇒ 2 と 3 が同じ日に揃ったため、いま決める。**

## 4. ★確定を要する設計判断（**開発者の承認事項**＝**D-386 (4)**）

**★CSRF の補助対策（`X-Requested-With`）をどうするか。**

| 案 | 内容 | 得るもの | 失うもの |
|---|---|---|---|
| **★A（設計卓の推奨）** | **要求を撤回し、`SameSite=Strict` Cookie の 1 本立てにする**（`DES-002` §4.4 の補助対策の記述を撤回） | **★実装差分がほぼ 0。** **`curl` 相当の経路が無傷で残る**（`DES-002` §8.2 の歯止め b）。**`NFR102`「過剰でない対策」と整合する** | **★多層防御が 1 層になる。** **`SameSite` を解さない古いブラウザでは CSRF が成立しうる** |
| **B** | **非 GET の全経路へ要求する**（**`/api/auth/*` は除外**） | **設計書どおりの多層防御になる。** **★サーバ側に明示的な拒否が 1 つ増え、レビューで確認しやすい** | **★`curl` からの操作が `/api/auth/*` 以外で全部壊れる**——**疎通確認・障害時の調査・開発者の手作業。** **★付け漏れると「その画面だけ 403」になり、他は全部動くので気づくのが遅れる。** **★経路が増えるたびに付け忘れが起きる。** **⇒ フロント側の実装コストは低い**（**`M22-02` の `http-interceptor.ts`＝`window.fetch` のラッパが在るため 1 か所で済む**）。**★preflight の性能コストも実質 0**（**同一オリジンのため preflight が飛ばない**） |
| **C** | **設定変更系 API だけに要求する** | **B より影響が小さい** | **★「設定変更系」の定義を持ち続ける必要がある。** **経路が増えたときに判定が漏れ、しかも漏れは「守られていない」側に出る** |

### 4.1 ★設計卓が A を推す理由

| # | 理由 |
|---|---|
| 1 | **★第一対策で目的は達成されている。** **`SameSite=Strict` は、クロスサイトからの要求に Cookie を載せない。** **⇒ CSRF が成立しない。** **本アプリが対応する範囲のブラウザはすべて `SameSite` を解する** |
| 2 | **★脅威モデルが「LAN 内は信頼する」である**（`DES-002` §4.4）。**⇒ 同一 LAN 内の悪意あるデバイスはネットワーク側の防御責任としており、多層防御の 2 層目が守る相手は既にモデルの外にある** |
| 3 | **★2 つの層は独立していない。** **`SameSite` を守っているのはブラウザであり、`X-Requested-With` を付けさせないのも**ブラウザである〔CORS preflight〕。**⇒ 「SameSite を honor しないブラウザ」は、たいてい CORS preflight も正しく実施しない。** **⇒ 1 層目が破れる状況では 2 層目も一緒に破れる。** **★多層防御に見えて、同じ 1 つの前提〔ブラウザが仕様どおりに動く〕に両方が乗っている** |
| 3-1 | **★`NFR102`「過剰でない対策」。** **得るもの〔上記 3 のとおり小さい〕と、失うもの〔`curl` の経路・維持コスト〕が釣り合わない** |
| 4 | **★`DES-002` §8.2 の歯止め b と正面から当たる**（2026-08-16 に定めたばかり）。**「`curl` 相当が唯一の復旧経路である」と書いた翌日にそれを塞ぐのは、設計としてちぐはぐである** |
| 5 | **★C は「定義を持ち続ける」形であり、いちばん壊れやすい。** **経路が増えるたびに判定が要り、漏れは「守られていない」側に静かに出る**〔エラーも出さずに無防備になる〕 |

> **★2026-08-16 是正**——**起票時の理由 3 は「B は 35 以上の経路へ横断の実装を入れる」と書いていたが、これは当たらない。** **`M22-02` が `http-interceptor.ts`（`window.fetch` のラッパ）を作っており、フロント側の付与は 1 か所で済む。** **⇒ B のコストのうち「実装量」は小さい。** **A を推す根拠は「実装量」ではなく、上記 3〔層が独立していない〕と 4〔`curl` の帰り道〕である。**

### 4.2 ★A を採る場合に設計書へ書くこと（**撤回の記録**）

**★「補助対策を実装しなかった」ではなく「要らないと判断した」と書く。** **理由（§4.1 の 1〜3）を併記する。**

**★これは重要である**——**書かないと、次に §4.4 を読んだ担当が「未実装の宿題が 1 つ残っている」と読み、掛けに行く。** **followup `csrf-design-vs-implementation-gap` も同じ形で 2 年近く残っていた。**
