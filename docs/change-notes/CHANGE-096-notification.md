## 1. 変更の概要

**コンボ新規登録の時点で、同梱するセットプレイの「確認できた条件」を入力できるようにする。**

**★本 CHANGE は既存の非対称を揃えるだけである。** 単独作成経路（`POST /api/combos/{comboId}/setups`）には既に `verifiedConditions` があり、**同梱経路（`POST /api/combos` の `setups[]`）だけに無かった。**

**非スキーマ・追加のみの後方互換。** **サービス層・リポジトリ層に変更は要らなかった**——**M19-03 が `CreateSetupInTx` にも `insertVerifiedConditions` を入れており、欠けていたのは API 層の写像 1 か所だけだった**（`internal/service/` ／ `internal/repository/` に diff 0）。

**★満たしている 3 つのゲート。**

| # | ゲート |
|---|---|
| **G-1** | **同一トランザクション**——コンボ作成が失敗すれば `combo_setups` ごと巻き戻り、`combo_setup_results` も残らない |
| **G-2** | **「対称にする」を超えていない**——`CreateSetupRequest` に diff 0。`result` は `ok` 固定、`note` は扱わない |
| **G-3** | **`copy` で成立条件を引き継がない**——引き継ぐと「元のコンボで確認した成立」が「このコンボで確認した成立」に見える |

### 2.3 ★`DES-002` — 値域外 `techType` の応答（**D-275**）

**契約として「値域外 `techType` は 400 `invalid_setup_result`」を、`verifiedConditions` を受け取る全経路に共通で定める。**

**★あわせて既知の乖離を明記する**——**`POST /api/combos/{comboId}/setups`（単独作成）は現状 500 `internal_error` を返す。** M19-03 からの取りこぼしであり（`CreateSetup` が `setupResultError` の写像を通っていない）、**followup `setup-create-invalid-value-status` で 400 へ揃える。**

> **★契約に 500 と書かない理由**——**500 は「サーバの不具合」を意味するが、実際は利用者の入力誤りであり、監視の側から見ると偽の障害として上がる。** **契約は「あるべき姿」を定義する場所であり、現状の取りこぼしを正としてしまうと、揃える作業に収束先が無くなる。**

### 2.4 ★`DES-002` — `PUT /api/combos/:id` は `setups` を読まない（**D-276**）

**`PUT /api/combos/:id`（キー変更編集）は `POST /api/combos` と同じリクエストボディ（`CreateRequest`）を取るが、`setups` 全体を読まない。** **エラーにも警告にもならず、単に無視される。**

- **本 CHANGE が作った挙動ではない**——`setups` 自体が以前から同じ扱いである。FE は edit モードで `setups` を送らないため実害も無い。
- **★`verifiedConditions` に限定して書かないこと。** 限定すると「他のフィールドは書ける」と読まれる。
- **弾く実装は followup `combo-put-ignores-setups`。**

> **★本 CHANGE の立場から特に必要である。** 本サブは**「`edit` には入力 UI を出さない」を明示的な仕様として選んだ。** **UI が無いこと（意図）と API が無視すること（取りこぼし）は別の事実であり、分けて書かないと「edit では成立条件を扱わない設計だ」と丸められる。**
