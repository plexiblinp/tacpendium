## 1. 変更の概要

**`DES-002` は楽観排他を §6.4 の 1 文でしか定めていない。**

**逐語（現行）**——

> 書き込み処理はサービス層でトランザクション境界を設け、**楽観的排他制御（更新時のバージョン番号チェック）を導入して上書き事故を防ぐ**。

**★これは方針であって契約ではない。** **どの資源が対象か ／ 版が合わないとき何を返すか ／ どの粒度で衝突するかが、どこにも書かれていない。**

**`DES-002` §4.2 には注記が入っている**（`M22-RESEARCH-01` §9-B-5 が「照合対象が無い」と報告した箇所）——

> **★楽観排他の 409 については本節にまだ規定が無い**……`M22-03` / `M22-04` で書き足す。

**⇒ 本 CHANGE がその「書き足す」を行う。**

**★非スキーマ・非破壊である。** **DB のテーブル・列・制約を 1 つも変えない。** **マイグレーションを消費しない。** **`D-394` が案 A（集約）を採り、新しい `version` 列を 1 本も足さないと確定しているためである。**

### 1.1 CHANGE 対象外（切り分け）

| 項目 | 対象外の理由 |
|---|---|
| **409 の利用者への見せ方**（画面・文言・再読込の導線） | **`M22-04` の担当。** **★本 CHANGE はサーバの契約までである** |
| **`recipe_cache` の `updated_at` / `version` 非同期の是正** | **契約 F-5 で凍結。** **★直さない。** **仕様として明記するだけである**（§2-e） |
| **CORS/CSRF** | **`M22-05` の担当**（followup `csrf-design-vs-implementation-gap`） |
| **論理削除・復元で `version` を上げること** | **★現状どおり。削除は「編集」ではない。** **上げると、削除のたびに他の端末の編集が弾かれる** |
| **`version` 列の追加** | **`D-394` で確定済み。1 本も足さない** |

### 2.1 ★エラーコードを `version_conflict` に統一する（**割付を `M22-04` から `M22-03` へ移した**＝**D-406**）

**現状は資源によって異なる**（followup `conflict-error-code-inconsistency`）——**`combos` 系が `conflict`、`setups` 系が `version_conflict`。**

**★`M22-overview` §4.2.2 の脚注は、当初これを `M22-04` の担当としていた**（「どう見せるかを決めるサブと同じ面だから」）。**⇒ 本 CHANGE で `M22-03` へ移す。**

| # | 移した理由 |
|---|---|
| 1 | **★§2-a が書けなくなる。** **実装が資源によって 2 つの異なるコードを返したままでは、契約を 1 つに書けない。** **「コンボは `conflict`、セットプレイは `version_conflict`」と設計書に書くことになり、それは契約ではなく現状の記述である** |
| 2 | **★エラーコードは通信の契約であって、見せ方ではない。** **`M22-04` は「競合したときの利用者体験」を作るサブであり、そこでサーバの応答本文を変えるのは面の逸脱である** |
| 3 | **★`M22-03` で現状のコードをテストで固定すると、`M22-04` の変更が「回帰」に見える。** **既知の不整合をテストで固めるのは、後で直す人の妨げになる** |

**★`version_conflict` を正とする理由**——**409 は既に一意制約違反で使われている**（`DES-005` §5.11＝`CHANGE-101` / `M20-04` の as-built「一意制約違反は 409 で衝突表記を載せる」）。**⇒ `conflict` は総称であり、どの衝突かが読めない。** **総称を版不一致に割り当ててはならない。**

**⇒ `M22-04` の担当は「409 をどう見せるか」に純化する。** **`M22-overview` は本裁定に合わせて改訂済みである。**

### 2.2 ★変えないもの（網羅宣言）

- **`DES-002` §6.4 の既存の 1 文**——**「書き込み処理はサービス層でトランザクション境界を設け、楽観的排他制御（更新時のバージョン番号チェック）を導入して上書き事故を防ぐ」。** **★方針は正しい。足りないのは契約である**
- **`DES-002` §6.4 の WAL モードの記述**
- **`DES-003` の `combos` / `setups` のスキーマ定義**（**★列も制約も 1 つも変えない**）
- **`DES-005` §5.11 の一意制約違反の 409**（**★版不一致とは別物である。触らない**）
- **`REQ-001`**（**★本 CHANGE は要件を動かさない**）

### 2.3 真因の記録

**★バグ修正ではない。** **§6.4 は「方針を書いたが契約を書いていない」状態であり、誤りが在ったわけではない。**

**★ただし記録に値するのは、この状態が実害を生んでいた点である。**

| # | 実害 |
|---|---|
| 1 | **エラーコードが資源によって割れた**（`conflict` / `version_conflict`）。**★照合対象が無いため、どちらが正しいかを判定できなかった** |
| 2 | **ハンドラ層テストの固定強度も割れた**（`combos` はステータスのみ・`setups` はコードまで＝`M22-RESEARCH-01` A-5）。**★「何を固定すべきか」が書かれていないため** |
| 3 | **`ComboEditor.buildPatchPayload` が `version: 0` を送る経路が残った**（followup `combo-editor-version-zero-fallback`）。**`combos.version` は `NOT NULL DEFAULT 1` であり、`0` の行は生成経路が無い。** **⇒ 必ず版不一致になる。** **★契約が書かれていれば「送ってよい値の範囲」が決まっていた** |

**⇒ 契約を書かないと、実装が 3 通りにばらける。** **本 CHANGE はその照合対象を作る。**

## 7. ★as-built 確定に伴うスコープの拡大（2026-08-16・**D-413**）

> **★起票時（2026-08-15）には見えていなかったものである。** **`M22-03` の as-built と設計伝達レポートで判明した 4 件を、本 CHANGE の反映へ含める。** **★宣言してから反映する**（`CHANGE-113` §2.4・§2.5 と同じ扱い）。

### 7.1 拡大 1 — `SUPP-001` §5.2：**API エラーコードは `internal/model` のパッケージ定数として定義する**

**指示書 §4.3 は「`version_conflict` へ揃える」までしか言っておらず、定数にするか生リテラルのままにするかを書いていなかった。** 製造は `CLAUDE.md` §4（列挙的文字列定数はパッケージ定数として定義）に依って定数化し、**本サブが触る 3 箇所に限った**（`internal/model/api_error.go:9` の `ErrorCodeVersionConflict`）。

**⇒ 結果として「版不一致 1 種類だけが定数、409 を返す他の 10 種は生リテラル」という中途の状態が残っている**（followup `api-error-codes-not-centralized`）。

**★書かないと、次に同型の不整合（同じ事象に 2 つのコード）が起きたときに、また 1 種類だけ定数化されて中途の状態が増える。**

### 7.2 拡大 2 — `SUPP-001` §5.5 規約 (12)：**通信の契約を固定するテストは、本番コードの定数を参照しない**

**★本サブで最も価値のある確定であり、破壊確認が無ければ気づけなかった。**

初版はハンドラ層 3 本の期待値に `model.ErrorCodeVersionConflict` を使っていた。**破壊確認 B（コードを総称 `"conflict"` へ戻す）を回したところ 3 本とも緑のままだった**——**定数の値を変えると期待値も一緒に動くためである。**

**⇒ 固定できていたのは Go 内部の一貫性だけで、線を流れる文字列ではなかった。**

**★「本番コードが定数を使うこと」と「テストがリテラルで固定すること」は、両立させるべき別の要求である**——**前者は散在の防止、後者は契約の固定。**

**★一般形は「テストの期待値が被検査対象と同じ源を参照していないか」であり、エラーコードに限らない**（HTTP のステータス・JSON のキー・ファイル形式・DB のカラム名）。

**★是正後の形**——`internal/api/combo/handler_test.go` ／ `internal/api/setup/handler_test.go` に `const wantVersionConflictCode = "version_conflict"` を各パッケージで宣言し、期待値に使う。**同型の空振り（期待値が定数参照になっているテスト）は HEAD に 0 件であることをレビューが独立に確認済み。**

### 7.3 拡大 3 — `DES-002` §4.2：**`PUT /api/combos/:id` に負けた側は 404 である**（契約の例外）

**同経路は旧行を論理削除して新 id で採番し直す**（`internal/service/combo/service.go:597-599` → `:625` が `Version = 1` で INSERT）。**⇒ 旧 id と旧 `version` を握っていた別の文脈が `PATCH` を撃つと `ErrNotFound`＝404 になり、`version_conflict` は返らない。**

**★実装は正しい。旧行はもう存在しないため 404 が正しい。**

### 8.1 `recipe_cache` と `updated_at` の非同期（**★`combos` と `setups` の両表について書くこと**）
