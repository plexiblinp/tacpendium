## 2. ★★本反映で最も再利用される 2 件

### 2.1 設計書が 1 系統だけを「推奨形式」として示していた

**`DES-002` の「Details.validations の典型構造」は 1 つの形を推奨形式として示すだけで、実装が 3 系統に分かれていることを書いていなかった。**

**⇒ 読んだ担当は (1-b)(1-c) を「漏れ」と読む。** 実際、`M27-02a` は全数調査の途中でその判断を迫られ、**「揃えに行かない」と自分で決めて報告した**。書いていなければ、次の担当が同じ判断を一からやり直す。

**★一般形＝「推奨形式」を書くときは、それに従っていない経路が在るかを併記する。** **⇒ 「推奨」は「他は間違い」を意味しないが、書かなければそう読まれる。**

### 2.2 「到達不能である」という観測は、経路 1 本で失効する

**`M24-13` 期の実測「画面から到達できる検証エラーが 1 件も無くなった」は、`M27-02a` の実測で覆った**——**`setups[*]`（`VAL-S02` / `VAL-S04`）は FE の zod が検証しないため BE だけが持ち、UI から到達できる。**

**★★`D-684` の裁定（(a) そのまま残す）は結果として正しいが、根拠が変わった。**

| | `D-684` 時点 | 実測後 |
|---|---|---|
| なぜ残すか | 将来の BE 検証への備え | **★現に使われている** |

**⇒ 「備え」より強い理由が在った。★裁定は変えない。根拠だけを差し替える。**

**★一般形＝「到達不能である」と書くときは「いつ・どの経路について測ったか」を添える。** 添えないと、後から「もう到達不能ではない」と気づく手掛かりが消える。

## 3. ★★`M27-02a` §4-1 の指摘への回答——**追記は済んでいた。ただし製造のツリーからは見えなかった**

**製造の報告**——「指示書 §2.1.3.2 末尾は『`PATCH` の発見を追跡行へ写す手番は設計卓が持つ。⇒ 本追補の時点で設計卓が済ませた』と書いているが、**実ファイルを開いて照合したところ写されていない**」。

## 5. ★★E2E について本サブが実証したこと（**設計卓が引き取る**）

**★★「単独で緑」は「全数で緑」の証明にならない。両方向で実証された。**

| # | 事実 |
|---|---|
| **(a)** | **本サブが新設した動線 E2E は単独で緑・全数で赤だった。** **E2E の DB は spec 間で共有され、`ryu` ＋ 先頭技という「よくある形」で親コンボを作ると重複判定に当たる。⇒ `VAL-C02` が検証段階で ERROR になり、見たかった `VAL-S02` まで到達しなかった** |
| **(b)** | **既存の `m24-12` (3) は単独で赤・全数で緑だった。** 先行 spec が残す状態でタイミングが変わる |

**⇒ 完了の根拠にするのは常設のゲート（`make e2e`）であり、`make e2e-only` の緑ではない。**

**★★あわせて——重複判定に載る形のデータを作る E2E は、キャラとレシピの 2 つで他と離すこと。** 他の spec はいずれも先頭技の 1 ステップであり、`ryu` は 97 か所で使われている。

**★★「2 台で再現した」は「常に落ちる」の証明ではない。** `m24-12` (3) を開発者機でも再現させた時点で「既存の失敗」と結論したが、**両方とも単独実行という同じ条件で測っていただけ**だった。**⇒ 再現条件を変えてみるまで、再現の範囲は分からない。★本件は先行 spec を 1 本足すだけで結果が反転した。**

**⇒ 上記 3 点は `add_e2e_spec` コマンドと `CLAUDE.md` §5 へ載せる価値がある。★どちらも開発者の手番であるため、followup として出す。**
