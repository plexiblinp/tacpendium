## 2. 修正概要

- **案 C を as-built へ昇格した。** 始動技の抽出条件を `is_aerial=1 AND category='normal' AND code に "jumping_heavy_" を含む`（**中間一致**）へ是正した。**接頭辞のままでは `neutral_jumping_heavy_kick` を取り落とし、実装と食い違う**ため、条件式そのものの書き換えが必要だった。候補は **21 行 → 23 行**、増分 2 件（`juri` / `ken`）。
- **変換済みノーマル版の畳み込み表示**を明文化した。単純除外を採らず、折りたたみ ＋ バッジで出す（**silent に消さない**）。判定は相手技を問わず、`is_draft` も問わない。PC 版を削除すればノーマル版が自動復活するのは正しい挙動である旨も残した。
- **既知の限界 2（手動確認レーンの登録導線）を「解消済み」へ更新**した。§5.21 の既知の限界（curation の登録 UI）も同様に解消済みとした。
- **登録導線の契約を新規に明文化した。** 両導線でキャラクターと `hit_type` を固定し、`combo_punishes` の自動採用は手動確認レーンだけに限る。**この非対称が意図的である旨と、その根拠**（手動確認レーンには採用ボタンが無く、自動採用しなければ登録したコンボが画面のどこにも現れない）を併記した。**多層防御**（保存結果のキャラが検索条件と異なる場合は紐づけをスキップ）も反映した。
- **materialize 新規生成通知の契約**を明文化した。永続表示・右上×・「開く」の併置・結果別の説明・実測調整の案内・未知理由コードの表示、および**固定 ID を 2 つに分けた理由（情報の回復可能性が非対称であること）**。
- **DES-002 §4.2 に加算スキップ理由コードを 1 つ追加**し、未知コードに対する表示側フォールバック方針を注記した。**API が未知コードを返す契約を増やすものではない**旨を明示した。
- **許容した非対称 3 件を「欠陥ではない」と明記**した（後任の誤修正を防ぐため）。
- **§5.21 に残っていた撤回済みの見立てを、撤回として明記した。** 「`EXISTS` 判定だけでは相手技を問わず全部隠れて過剰除外になる」という懸念が既知の限界として残っていたが、**FR301 の dup キーが相手技を含まない**ことを実コードで引き直した結果、**1 つの基底から作れる PC 版は 1 つだけ**であり過剰除外ではないと訂正されていた。**削除せず撤回として残した**——消すと後任が同じ懸念を独立に再発見して「バグだ」と直しにかかるためである。

## 4. 整合性チェック結果

- **抽出条件の数の整合**：`is_aerial=1` の 70 件のうち接頭辞を持たない 9 件は、「案 C で拾う 2 件」＋「`category='normal'` で自動除外される unique 系空中特殊技 7 件」に分解でき、DES-005 §5.20 の既存記述（接頭辞併用の理由＝非接頭辞が 9 件）と矛盾しない。**接頭辞から中間一致への変更で新たに入るのは 2 件だけである**ことが数で裏付けられている。
- **CHANGE-089 との関係**：本 CHANGE の項目 6 は、CHANGE-089 で入れたダメージ計算ロジックの**訂正**である。DES-003 §3.3 の 2026-07-27 errata が根拠（PC 補正は初段のみ・SA / CA は等倍・多段は機械判別できない）を先に保全しており、本反映はその実装状態を更新するにとどまる。**新しいドメイン事実を持ち込んでいない。**
- **二重定義の回避**：登録導線の契約は **DES-005 §5.20 に本文を置き、§5.7 からは相互参照とした**。同一仕様を 2 か所に書かない（M18-03b で、指示書内に仕様が二重定義され片方が欠落した事例があったため）。
- **実装詳細の非記載**：定数名（`MATERIALIZE_RESULT_TOAST_BEHAVIOR` 等）・ファイルパス・テスト名は DES の規定文言ではないため本文に載せていない。**契約として書いたのは挙動のみである。**
- **★版ログと本文の乖離**：本反映で **CHANGE-089 の §5.20 本文欠落**が判明した（§3.0）。**版ログは「何をしたか」の記録であって、本文が存在することの証明ではない。** 本反映では CHANGE-089 の 8 件すべてについて**本文の存在**を確認した（結果は本節末尾に反映係が記す）。
- **「解消済み」と書く条件**：CHANGE-088（M18-03a）の反映時、限界 2 について「**表示側は実装済だが到達不能のため『解消済み』とは書かない**」という判断を行っていた。本反映では**登録導線が `combo_punishes` まで到達した**ため、初めて「解消済み」と書ける状態になっている。過去の判断と一貫している。
