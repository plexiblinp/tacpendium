## 1. ★★`DES-002` §4.2 — 経路 3 本の as-built（**「★未実装」を外す**）

### 1.1 `ComboResponse.affectedMoves`

| # | 確定した仕様 | 根拠（`M28-02c` の実測） |
|---|---|---|
| 1 | **`omitempty` を付けない。空でも `[]` を返す** | `internal/api/combo/dto.go`。`toComboResponse` が nil のとき空スライスを入れる。`TestComboResponse_AffectedMovesKeyIsAlwaysPresent` |
| 2 | **`nameJa` は `omitempty`。★サーバ側では `code` へ落とさない** | **落とすのは画面側の 1 関数である。★先例＝`starterMoveNameJa`**（サーバは両方返す）**に揃えた** |
| 3 | **同じ技を 2 回使うコンボでも 1 行だけ出す**（`DISTINCT`）。並びは `ORDER BY cs.combo_id, m.id` | `listAffectedMovesSQLTemplate` |
| **★★4** | **★★載る面は「コンボを返す全経路」である** | **注入は `List` の末尾と `attachComboChildren` の 2 か所。★書き込み系**（Create / PUT / PATCH / Restore / acknowledge）**はいずれも最後に `FindByID` を通る。⇒ 応答から落ちる経路は無い** |

**★母集団の述語＝そのコンボの `combo_steps` のうち `move_id` が非 NULL のもの**（`JOIN moves` で非技ステップは構造的に落ちる）**で、基準より後に変わった技だけ。**

**★★持たせなかった分岐＝`affectedMoves` から真偽を導く経路を 1 つも作っていない。⇒ 真偽の正本は `affectedByGameUpdate` の 1 本である**（`CHANGE-162` §1.2-4）**。**

### 1.2 `GET /api/notices/game-update`

**エラー契約（全行）**:

| 状況 | ステータス | コード |
|---|---|---|
| 成功 | **200** | — |
| write lock を取れない | **503** | `database_busy` |
| それ以外（DB エラー・告知ファイルの IO 失敗） | **500** | `internal_error`（**非空の `message` を持つ**） |

**★母集団の述語＝`affectedCount` は `deleted_at IS NULL` かつ影響可能性ありのコンボの総数**（全キャラ合計）**。⇒ ゴミ箱の行は数えない。**

**★★持たせなかった分岐 4 件**:

| # | 内容 |
|---|---|
| 1 | **204 は無い。** 0 件でも 200 を返す |
| 2 | **`postponedForVersion` は現在版と一致するときだけ載る。** 版が上がれば消え、抑止が外れる |
| **★★3** | **壊れた JSON はエラーにしない。**「延期していない」として扱い、告知そのものは 200 を返す（**★安全側＝告知が出るほう**） |
| 4 | **キャラ別の内訳は返さない**（アプリ全体の合計 1 値のみ） |

### 1.3 `POST /api/notices/game-update/postpone`

**エラー契約（全行）**:

| 状況 | ステータス | コード |
|---|---|---|
| 成功 | **204** | — |
| **データディレクトリが未設定** | **500** | `internal_error` |
| write lock を取れない | **503** | `database_busy` |
| それ以外 | **500** | `internal_error` |

**★★「データディレクトリが未設定 → 500」はレビュー中-3 で改めた。⇒ 当初は保存せずに 204 を返していた。**

**★★理由＝「保存できないのに成功を返す」は、「延期したのに次も出る」を利用者が説明できない形になる。**

**★★持たせなかった分岐 4 件**:

| # | 内容 |
|---|---|
| 1 | **要求本文を取らない**（`acknowledge-version` と同型） |
| 2 | **404 が無い。** 延期はアプリ全体で 1 つであり、対象を指す ID が無い |
| 3 | **409 が無い。** 楽観的排他を要求しない（延期は内容の変更ではない） |
| **★★4** | **「延期の解除」の経路を本番に作っていない。** 版が上がれば自然に外れるため。**⇒ 解除は debug ビルドにだけ在る**（§5） |

### 1.4 ★★`COUNT` の記述を改める

**★現記述＝「判定式を共有した `COUNT` の新設が要る。★式を書き写さないこと」。**

**★★as-built はもう一段強い。⇒ `Count` は判定式を持たない。**

`List` の絞り込み条件の組み立てを `buildListWhere(filter) (string, []any)` として括り出し、`Count` がそれを通す。**⇒ 「式が 2 本」自体が起こらない。`deleted_at IS NULL` も同じ述語を通る。**

**⇒ 記述を「`List` と同じ絞り込みの組み立てを共有する `COUNT`」へ改める。**

## 2. ★★`DES-003` §3.4 — 判定式は 4 経路である（**記述が実態より狭い**）

**★現記述＝「判定式は 1 か所しかなく、SELECT の派生列と一覧の WHERE が同じ式を共有する」。**

**★★as-built は 4 経路である。⇒ 行レベルの述語を 1 段外へ括り出した形になった。**

| 利用者 | どこから組まれるか |
|---|---|
| 真偽（`EXISTS`） | `affectedByGameUpdateCondSQL` ＝ 行レベルの述語を連結 |
| SELECT の派生列 | `affectedByGameUpdateExprSQL` ＝ 同上 ＋ `AS` |
| **列挙**（`affectedMoves`） | `listAffectedMovesSQLTemplate` ＝ 同上を直接連結 |
| **総数**（`COUNT`） | **判定式を持たない。`List` と同じ `buildListWhere` を共有する**（§1.4） |

**★生成される SQL は着手前と 1 文字も変わっていない**（`Cond` の中身が定数連結になっただけ）**。**

**★★構造での担保＝`internal/` 全体を `go/ast` で走査し、「マーカーと基準の両方に言及する文字列リテラルは 1 本だけ」を主張するテストが在る。⇒ サービス層や別のリポジトリへ書き写しても検出する。**

**★★「SELECT と WHERE の 2 つ」と書いたままだと、次の担当が列挙・総数を別に書いてよいと読む。⇒ ここが本節を直す理由である。**

### 2.1 ★★不変条件を 1 つ足す — **削除・復元は基準に触らない**

**★`baseline_version` を書く本番コードは 2 か所しか無い**〔`insertComboSQL` の `COALESCE` と `AdvanceBaselineVersion`〕**。論理削除も復元も `deleted_at` / `updated_at` しか触らない。**

**★★これが崩れると、影響コンボを 1 度ゴミ箱へ入れて戻しただけで「確認済み」に化ける**——**利用者が中身を見ていないのに警告が消える形であり、`FR307` の向きに反する。**

**★`TestDeleteAndRestore_DoesNotTouchBaseline` が実 DB で固定した。★ゴミ箱の行でも判定そのものは生きていること（＝印が出ること）も併せて主張している。**

## 3. ★★`DES-005` §5.19b — 「★未実装」を外し、3 件を書く

### 3.1 行アクションは ［詳細 / 編集 / 削除］（**★コピーは出さない**。2026-09-07 開発者確定）

| # | 確定 | 理由（実装の事実に基づく） |
|---|---|---|
| 1 | **［コピー］を出さない** | **★★コピーで生まれる行は基準が登録時の現在版で埋まる**（`insertComboSQL` の `COALESCE`）**。⇒ コピーは「影響なし」として生まれ、元の行は影響ありのまま残る。★「変わった技を確認して直す」という画面の目的に対して、何も進まない操作である** |
| 2 | **［削除］を出す** | 直す代わりに捨てる、が自然な選択肢である |

**★開発者の逐語＝「専用画面でコピーをするのはあまり良く分からない運用」**（2026-09-07 実機確認時）**。**

**★既存 4 面の行アクションは不変である**（`showCopy` の既定は `true`。専用画面だけが `false` を渡す）**。**

### 3.2 上限 1000 件と、打ち切りの出し方

- 一覧 API の `limit` は BE 側で 1000 に丸められる。**⇒ 専用画面は 1000 を渡す。**
- **★★件数の正本は告知 API の `affectedCount` である**（一覧の応答は打ち切られている）**。⇒ バナー・ボタンはそちらを出す。**
- **★★打ち切りの注記を出す条件は「行数が上限に達したこと」である。⇒ 総数と行数の差だけで判定しない。**

**★★理由＝総数（告知 API）と行数（一覧 API）は別のクエリであり、片方だけ先に更新される瞬間が実在する**（削除した直後など）**。⇒ 差だけを見ると、その瞬間に「1 件中 0 件を表示しています」と嘘を言う。**

### 3.3 ★★保存後の戻り先には限界がある（**実測**）

| 入口 | 戻る先 |
|---|---|
| **専用画面の行の［編集］** | **`/game-update/combos`**（`showGameUpdateColumns` が真のときだけ `state` を積む） |
| **専用画面 →［詳細］→［編集］** | **★★戻らない**（詳細の編集リンクに `state` が無い） |

**★★`CHANGE-162` §7 の文面は「専用画面から［編集］へ入った場合」なので、契約としては満たしている。**

**★★ただし「変わった技を確認してから直す」利用者は詳細を経由するのが自然であり、実運用では踏まれる経路である。⇒ `followup` `game-update-return-to-lost-via-detail` へ登録した。**

**★採った形＝既存の `punishReturn` と同じ仕組みに 1 値足しただけである。⇒ 新しい戻り方を作っていない。履歴の形は 1 枚も変えていない**（`M24-12` (3) の契約と `history.go` の勘定はそのまま）**。**

## 5. ★★`SUPP-001` §4.4・§4.5 — E2E を debug ビルドで回す（**★★裁定事項**）

### 5.1 何が起きたか

**★指示書 §5-5 は E2E 1 本**（バナー → 専用画面 →「問題なし」→ 件数が減る）**を要求した。⇒ 素の構成では「影響コンボが 1 件以上ある状態」を作れない。**

| 経路 | 可否 |
|---|---|
| `PATCH /api/moves/{id}` | **不可**（マーカーは対象外） |
| 既存の debug API | **不可**（read-only 2 本のみ） |
| `POST` / `PUT` / CSV 取込で基準を渡す | **不可**（`baselineVersion` は受けない ／ CSV にも載せない＝`CHANGE-159`） |
| マーカーを立てる | **DML マイグレのみ**（`cmd/seedgen -mode game-version`） |

**★★しかも `D-725` により初回は必ず 0 件である。⇒ 「画面を開いても何も出ない」ので、動かして確認したことが証拠にならない。**

### 5.2 ★★裁定＝**受理する**

**★★理由 3 つ。**

| # | 理由 |
|---|---|
| **★★1** | **これは仕様の穴ではなく観測の穴である。⇒ 観測の口が無いと、破壊確認そのものが成立しない。★「テストで作れない状態」を仕様の側で緩めるほうが害が大きい** |
| **★★2** | **却下したときの代替が重い**——**マイグレ 1 本を消費して固定の seed マーカーを置くと、配布 DB に恒久的なテスト用データが入る。⇒ `D-725`（初回は必ず 0 件）と正面から衝突する** |
| **★★3** | **先例が既に在る**——**`make test-go-debug` が debug ビルドを回している。⇒ 「debug タグでビルドしたものを検査する」形は本プロジェクトに前例がある** |

### 5.3 ★★`CHANGE-135` §5-1 との関係（**取り違えないよう明記する**）

**★`CHANGE-135` §5-1 は「どの経路から E2E スタックを起こしても必ず本物を検査する形を保つ」と書いている。**

**★★これは「本物のバックエンドを起こす」という意味であり、「本番のビルドタグで起こす」という意味ではない。⇒ 本 CHANGE は §5-1 に反しない。**

### 5.4 ★★代償を明記する（**§4.5 の既存の書き方に揃える**）

**★★E2E が本番ビルドではなく debug ビルドを検査する。**

**★差分は debug ルート 6 本の登録だけであり、本番コードの経路は同一である。★本番バイナリには 1 バイトも出ない**（`routes_noop.go` は不変。`go build ./...` と `go build -tags=debug ./...` の両方が通ることを実走確認）**。**

**★★ただし担保が 1 回の手動確認である。⇒ 恒久の担保があるかを確かめること**（§7-1）**。**

**★★§4.5 には既に同型の代償が 1 件書かれている**〔`vite preview` が配るため、本番の配信経路が E2E で一度も検査されていない〕**。⇒ 本件は 2 件目である。★同じ節に並べる。**

### 5.5 `SUPP-001` §4.4 — debug 経路を 4 本足す

| 経路 | 用途 |
|---|---|
| `GET /api/debug/game-version` | 現在の版を読む |
| `POST /api/debug/moves/:id/game-version` | **マーカーを立てる** |
| `POST /api/debug/combos/:id/baseline-version` | **基準を戻す** |
| `DELETE /api/debug/notices/game-update` | **延期を解除する**（**★本番には無い経路である**＝§1.3） |

**★`internal/api/debug/handler.go` の `NewHandler` シグネチャが変わった**（`(db)` → `(db, dir)`）**。★告知ファイルの位置を知るため。**
