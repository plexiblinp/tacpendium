## 2. ★★裁定 1——**`VAL-R03` の母集団から旧行を除かなかった件（`D-517`）**

### 2.1 **実装を受理する。設計卓の指示書が誤っていた**

**指示書 §4.2（散文）は「`VAL-C14` と `VAL-R03` の母集団から `superseded_by_combo_id IS NOT NULL` の行を除くこと」と書き、§4.4（表）では `VAL-R03` に旧行除外の述語を置いていなかった。** **製造は表に従い、理由を添えて報告した。**

**★製造の理由は 3 つとも正しい。**

| # | 理由 | 検証 |
|---|---|---|
| 1 | **§4.2 の根拠「旧行はゴミ箱の一覧に出ず利用者が復元できない」は当てはまらない** | **`VAL-R03` の母集団は生存行である。そこに居る行は画面に見えている** |
| 2 | **§4.2 の根拠「`PUT` のたびに警告が出る」も当てはまらない** | **`PUT` が積む旧行は論理削除済みであり、生存行の母集団に入らない** |
| 3 | **述語を足すと偽陰性になる** | **生存行の母集団に旧行が入りうるのは「隠されている旧行を API 直叩きで復元した」場合だけであり、そのとき旧行は画面に見えている生きたコンボである。除くと、見えている重複を黙って見逃す** |

### 2.2 ★★誤りの原因——**対称の適用範囲を広げすぎた**

**`D-512` で「2×2 の対称は正当である〔4 面とも同じ機構で開いている〕」と書いた。** **その対称は『開き方』については正しかったが、『母集団の除外』については成り立たなかった。**

**⇒ 対称であることを 1 つの軸で確かめて、別の軸へそのまま持ち込んだ。**

**★これは `D-494`（揃えることは無償ではない）の逆パターンである**——**同書は「理由のある非対称を守れ」だが、本件は「理由の無い対称を作った」。** **⇒ §6 の `M-69`。**

## 5. ★★`DES-006` §2.3 へ書いた本体——**`deleted_at IS NULL` を外してはならない**

**同節の「編集による再登録時の扱い」が、この述語が在る理由そのものである。** **`PUT` は同一トランザクション内で「旧行を論理削除 → 新行を登録」の順に実行する。** **⇒ 述語を外すと、`PUT` が自分の消した旧行に衝突し、あらゆる編集が重複エラーで落ちる。**

**⇒ 「削除済み行が重複判定の外に居る」ことは穴ではなく、`PUT` を成立させるための条件である。**

**★★一般形＝1 つの述語が 2 つの要求を背負っていると分かったら、述語を緩めるのではなく、判定をもう 1 つ足す。**

## 6. ★★開発者が実機で見つけた設計上の欠陥（`D-518`）

**`M23-05` 指示書 §1.3 は「登録側の警告は『作り直す前に、ゴミ箱に同じものがある』を告げる ⇒ 重複そのものが減る」と書いた。** **しかし §2.1 / §4.6 が指定した手段は「保存成功後の応答に載せるトースト」である。**

**★★保存後に告げるものは、定義上「作り直す前」に告げられない。⇒ 重複は減らない。**

**★これは実装の漏れではなく設計卓の起票の誤りである。** **目的は正しかった。手段がその目的を果たさなかった。**

### 6.1 設計卓の裁定 3 件（**起票の前提はこれで揃っている**）

| # | 論点 | 裁定 |
|---|---|---|
| **a** | **「両方入れる」を出すか** | **★出さない。** **製造は「`VAL-S04` / `VAL-C02` の ERROR 契約に手を入れる話だ」と読んだが、そうではない**——**現状も「削除 → 作る → 復元」で同じ状態へ到達でき、`VAL-R03` / `VAL-R04` がそれを警告している。禁止された状態ではなく警告される状態である。** **★それでも出さない理由は「目的と逆行するから」である**——**ボタン 1 つで重複を作れるようにすると、重複を減らすための導線が重複を増やす。** **⇒ 選択肢は「復元する」「新しく作る」の 2 つ** |
| **b** | **保存前チェックの土台** | **コンボ側は `POST /api/combos/check-duplicate` が在るが生きた行しか見ない**〔削除済みを見る口を足す〕**／ セットプレイ側には同等の経路が無く新設が要る。** **⇒ 規模が違う** |
| **c** | **WARNING でダイアログを出してよいか** | **★よい。逸脱ではない。** **先例＝`VAL-N02`**〔LAN 共有でパスワード未設定のとき「明示的な同意ダイアログで承認を得る」・種別 WARNING〕。 **★★区別は「警告の表示」か「操作の分岐」かである。** **保存前に選択肢を出すのは後者であり、`DES-006` §11.1 / §11.2 の見せ方の話ではない** |

### 6.2 送り先——**`M23-09` の新設を推奨（開発者の承認事項）**

**製造は `M23-06` / `M23-07` を推したが、採らない。** **`M23-06` は「ゴミ箱の列と見せ方」、`M23-07` は「ゴミ箱の未達の導線」であり、どちらもゴミ箱側の面である。** **本件は「登録画面 × サーバ API の新設」であって面が違う。**

**★開発者の承認事項が 2 件ある**——**(1) サブの新設 ／ (2) CHANGE ブロックの新規払い出し**（`121`〜`128` は `M23-07` で使い切る。次の空きブロックは `141` から）。

**★`M23-06` の投入は止めない。**

### 6.3 ★一般形

**「目的」と「手段」を同じ節に書いたら、手段でその目的が達成できるかを 1 行で確かめる。** **本件では「保存後に出るものが『作る前』に告げられるか」を問えば、起票の時点で気づけた。** **★目的の記述は手段の妥当性を保証しない。**
