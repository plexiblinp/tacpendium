## 1. ★★単一強度の必殺技は、ファミリー UI に載らない（`DES-004` §2.1 ＋ `DES-005`）

### 1.1 何が起きるか（**as-built**）

**★強度接尾辞**（`_light` / `_medium` / `_heavy` / `_od`）**を持たない `move_code` は、必殺技クイック入力パネルのファミリー UI に載らない。⇒ 「全技一覧から選ぶ」プルダウンからの入力になる。**

**★これは意図された設計である**——**実装側にその旨のコメントが逐語で在る**（`M28-05` の実測）**。**

### 1.2 実例は 2 件（**どちらも「単一強度の必殺技」の正しい姿である**）

| キャラ | ファミリー | 中身 |
|---|---|---|
| `guile` | ソニックブレイク | **`sonic_break`**（非対象）**＋ `sonic_break_od`**（OD） |
| `terry` | クイックバーン | **`quick_burn`**（非対象）**＋ `quick_burn_od`**（OD） |

**★ファミリー名は「クイックバーン」のまま出る**（表示名から `^(弱|中|強|OD)` を落とす処理が在るため）**。**

**★★強度ボタンは［弱］が非活性・［OD］が活性になる。⇒ 退行ではない。`guile` の先例とまったく同じ形である。**

### 1.3 ★★問題は、どの設計書にも書かれていないことである

| 設計書 | 現状 |
|---|---|
| **`DES-005`** | **「ファミリー ＋ 強度の 2 段選択」は書かれているが、「ファミリーに載らない技がある」ことが書かれていない。⇒ 画面から**（パネルで）**入力できない技が存在することを設計書から知る手立てが無い** |
| **`DES-004` §2.1** | 必殺技のパターンは **`<技名>_<強度>`** だけを挙げており、**`<技名>` 単体の形が表に無い**（特殊技の行から類推はできる） |

**⇒ 両方へ書く。**

## 2. ★★裁定＝`SUPP-001` §5.5.4 (8) の「`name_ja` との対」は、改名マイグレの `WHERE` 句には当たらない（**(a) を採る**）

### 2.1 何が問われたか

**★規約 (8) の明文＝「転記キーを `move_code` 単独にしない。`name_ja` との対で確認する。`move_code` だけで突き合わせると、別の技を上書きしてもエラーにならない」。**

**★`M28-05` の `000106` の `WHERE` は `character_id` ＋ `code` の対 ＋ `NOT EXISTS` ガードのみで、`name_ja` を見ていない。**

### 2.2 ★★裁定＝(a)。**規約を明確化する。`000063` の遡及はしない**

| # | 理由 |
|---|---|
| **★★1** | **`moves` に `name_ja` 列が無い**（実装事実）**。⇒ 表示名は `preset_aliases` を引く設計である。★規約 (8) が想定している「対」は、この表では素直に取れない。** |
| **★★2** | **規約 (8) が書かれた文脈は「手入力 CSV から値を転記するとき」である。⇒ そこには `name_ja` が在る。★改名マイグレの `WHERE` 句は別の場面である。** |
| **★★3** | **先例 `000063`**（`sonic_break_light` → `sonic_break`・`M19-04c`）**が同じ規約の下で同じ形である。⇒ (b) を採ると遡及になり、`D-535`**（適用済みマイグレの凍結）**と衝突する。** |
| **4** | **趣旨は別の手段で満たされている**——`character_id` ＋ `code` の対 ／ `NOT EXISTS` ガード ／ 往復テスト ／ **実 DB のコピーで `WHERE` 一致が 1 行であることを適用前に確認**、の 4 重である |

### 2.3 ★★あわせて、規約 (8) を強くする 2 点（**`M28-05` の実測から**）

**★★(i) 適用前に `WHERE` 句そのものを流して、当たる行を確定させる。**

**★これは `M28-05` の委託先が自発的に足した手であり、手順書には無かった。⇒ `000106` の `WHERE` を適用前の DB へ流して 1 行を得たことが、「1 行に当たった」ことの最も直接的な証拠になった。**

**★★「0 行に当たっても成功する」型のマイグレでは、これが唯一の事前の担保である。**

**★★(ii) 改名の契約テストは、旧 code 0 件・新 code 1 件の対に加えて、`id` の同一性を固定する。**

**★★件数だけでは「別の行に付け替わった」形の事故を取り落とす。⇒ 改名が「`UPDATE` による改名」ではなく「削除 ＋ 再作成」で実現されていた場合、件数は一致するが `id` は変わる。★参照側**（`combo_steps.move_id` 等）**は静かに切れる。**

## 3. `SUPP-001` §5.5.4 (10) — 実測の対照を添える

**★規約 (10) は「`seedgen` の引数なし `-check` は第一波しか再生成しない ⇒ 恒久のガードは `go test ./...` の golden 群である」と定めている。⇒ `M28-05` が最初の適用先であり、対照を得た。**

**★`migrations/000035` の索引 1 行だけを改名前の値へ戻した状態で:**

| 実行 | 結果 |
|---|---|
| `go test ./internal/seedgen/ -run 'TestGolden_MoveCommandsMatchesRegeneration'` | **FAIL / exit 1**（「コミット済みと不一致」） |
| `go run ./cmd/seedgen -check` | **`OK: 生成物は既存ファイルと一致` / exit 0** |

**★★「`-check` が緑だから golden は守られている」と読む余地が消えるのは、片方だけでなく両方を並べたときである。⇒ 対照として規約へ添える。**
