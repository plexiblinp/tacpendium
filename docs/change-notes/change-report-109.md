## 2. `D-381`——§2-1 は受理する

**製造は指示書 §4.2 の解決規則（3 段）に無い「ボタン具体度の同点判定」を、2 段目と 3 段目の間へ足した**（開発者判断・2026-08-14）。

**裁定＝受理する。** **`DES-005` §6.4.4 の解決規則へ「2.5 段」として書き足した。**

| # | 決め手 |
|---|--------|
| 1 | **★決定論的なタイブレークである。** **設計卓が 2 段目の最長一致を加えたのと同じ種類であり、曖昧一致・編集距離・入力ミスの補正ではない。** **入力を「直して」いない** |
| 2 | **★第 3 段〔同長で複数なら解決しない〕が生きている。** 2.5 段で絞ったあとに複数残れば、従来どおり解決しない |
| 3 | **★回帰が実測で 0 である。** 答えが変わった入力 0 件 ／ 解決しなくなった入力 0 件 ／ 新たに解決 27 件。**⇒ 「解決の追加」だけを行っている** |
| 4 | **★落とすと竜巻旋風脚が入らない。** 実データで 21 通りの主力技が同じ形で落ちていた |

**★副作用は受け入れる**——**強度を問わないコマンドの技は、同じ方向列に強度指定の技があると常に負け、モードから出せない。** **2.5 段の前は「どちらも出せない」状態であり、悪化した技は 1 つも無い。** **いずれも仮想側から入力できる。**

> **★設計卓の側の原因を書いておく。** **§4.2 の 3 段は、実データに当てずに構造だけを見て書いたものである。** **2 段目の最長一致は「SA のコマンドは必殺技のコマンドを先頭に含む」という構造から導けたが、「同じ方向列に強度指定と強度不問が同居する」は実データを見ないと出てこない。**
>
> **⇒ 機構化した**——**指示書テンプレート §4.5 へ「解決規則・判定規則を新設するサブは、実装の関数そのもので実データ全数を突き合わせることを完了条件に置く」を足した。** **★着手前の実測では足りない**——**着手前には実装の関数がまだ無い。**
>
> **★製造の側でも同じ穴が開いていた**（レポート §7-1）——**事前実測を自作の近似で行い、ブラケット付きの token を除外していた。** **⇒ 母集合が実装と違い、もっともらしい件数を返した。** **`SUPP-001` §5.5 (11″) として規約化した。**

## 3. 申し送り 3 件への判断

### 3.1 溜め `[n]` を「方向 1 つ」として扱う扱い（§4-1）——**受理する**

**`[4]6HP` を `4` → `6` の 2 方向として受け、保持時間は一切見ない。**

| # | 判断 |
|---|------|
| 1 | **★`DES-004` §2.4.1 の死守 2〔モーション解析はしない〕には触れない。** **記法の字句を方向へ写しているだけであり、時間軸の解釈を 1 つもしていない。** **製造の整理が正しい** |
| 2 | **★帰結として、後ろへ溜めずに 4 → 6 と入れても溜め技が入る。これを許容する** |
| 3 | **★許容の理由を設計判断として書いた**——**本アプリはレシピの入力器であって入力練習器ではない。** **利用者が「どの技か」を指せれば足りる。** **ゲームの成立判定を再現する必要はない** |
| 4 | **★「溜め時間を見るべきだ」と次の担当が足さないよう、明示的に塞いだ**——**足すと死守 2 に正面から触れる** |

**★角括弧を外さない形は採らない。** **外さないと溜めキャラの必殺技がほぼ全滅する。**

### 3.2 モード外で入るのにモード中に入らない 5 件（§4-2）——**現状維持**

**空中技としゃがみ通常技が同じ方向列 ＋ 同じボタンになる組である。** **`numeric-aerial-vs-crouching-collision` が指す組と完全に一致する。**

- **(b) モード用索引で `is_aerial` を除外する**は採らない——**空中必殺技がモードから入らなくなり、別の穴が開く**
- **(c) 曖昧なとき候補を出して選ばせる**も採らない——**モードの解決規則が「勝手に選ばない」で統一されているところへ、選択 UI だけ別の流儀を持ち込むことになる**
- **⇒ 恒久対応は「通常技全体に一貫した規則で空中を示す」であり、モード用の索引だけを細工することではない**（followup へ束ねた）

**★`DES-005` §6.4.4 へ「同じ入力の結果が状態で変わる」ことを事実として書いた。** **書かないと、次の担当が実装の欠陥と読んで片方を細工する。**

### 3.3 索引への参加可否の推測 1〜3（§1-5）——**DES へは「載せないもの」の表として書いた**

**個々の推測（方向部が空・ボタン部が複数・語彙外の形）は実装の粒度だが、「何が入らないか」は利用者に見える事実である。** **⇒ §6.4.4 へ表として残した。**

**★「入るものを決めた」だけでは終わっていない。** **書かないと、次の担当が「なぜ OD が入らないのか」を実装から読み取ることになる。**
