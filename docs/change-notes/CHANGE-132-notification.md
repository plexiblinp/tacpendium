## 2. 変更の内容

### 2.1 `SUPP-001` §5.2——**`internal/recipehash/` を追加する**

**`CalcRecipeHash` 相当の 3 実装を 1 本へ統合し、新しいパッケージへ置いた。**

| # | 統合前の所在 | 名前 | 本番の呼び元 |
|---|---|---|---|
| 1 | `internal/service/combo/duplicate_keys.go` | `CalcRecipeHash` | **10 か所** |
| 2 | `internal/service/setup/duplicate_keys.go` | `CalcSetupRecipeHash` | **7 か所** |
| 3 | `internal/repository/setup/repository.go` | `calcSetupRecipeHashFromSteps` | **2 か所** |

**統合後は `internal/recipehash` の `CalcCombo` / `CalcSetup` の 2 本だけが公開されている。** **★公開入口 3 本は残し中身を委譲 1 行にしたため、本番の呼び元 19 か所は 1 行も変更していない。** `canonicalModifiersJSON` **3 本**・`emptyRecipeHash` **3 本**も同じ手番で統合した（走査 0 件）。

**★★置き場の理由を本文へ書く。** **これが `SUPP-001` へ載せる価値の中心である。**

| 候補 | 採否 | 理由 |
|---|---|---|
| `internal/service/notation/` ／ `internal/service/preset/` | **不採用** | **契約 F-1 の凍結パッケージ**（指示書 §2.2 の停止条件） |
| `internal/service/setup/` | **不採用** | **`repository/setup` が service を import すると依存の向きが逆転する**（統合前のコメント「パッケージ循環を避けるため独立実装」がこの制約を指していた） |
| `internal/model/` | **不採用** | **ドメインモデルへ `crypto/sha256` を持ち込むことになる** |
| **`internal/recipehash/`** | **採用** | **サービス層・リポジトリ層の両方より下に置ける。** `internal/aliasnorm` / `internal/sanumber` / `internal/moveindex` / `internal/aliasindex` と同じ「純粋ユーティリティは `internal` 直下」の既存の型 |

**★`VAL-C02` の判定結果は 1 件も変わっていない**——**統合前に 3 実装へプローブを入れ、9 入力クラスの出力を採取し、3 本が全クラスで一致することを確認したうえで、その実測値を統合後のテストの golden として固定した。** **⇒ 「統合前 = 統合後」がテストを信じずに独立検証できる**（レビュー担当が `sha256sum` で 6 本を再計算して裏取り済み）。**⇒ `DES-006` の反映は不要である。**

### 2.2 `SUPP-001` §5.8——**`config.toml` の書き戻し経路が 1 本になった**

**統合前は `internal/config.Save`（公開）と `internal/service/config.writeAtomic`（非公開）が論理的に同一の処理を持っていた**（**差はエラー文言 1 か所のみ**）。**後者を削除し `appconfig.Save` へ寄せた。**

**⇒ 起動時のポート競合フォールバック（L-04）と `PUT /api/config` の両方が同関数を通る。**

**★あわせて `Save` を `encodeTOML`（表現）＋ `replaceAtomically`（置換）の 2 段へ分けた**（指示書 §4.4 が求めた「書き換えの方式を差し替え可能な形に」）。**新しい interface・設定項目・分岐は 1 つも作っていない。**

**★★ただし「前段を差し替えればコメントを保てる」ではない。** **現行の `github.com/BurntSushi/toml` にコメントを保持したまま値を書き換える API が無い。** **⇒ 実現するなら (i) 別ライブラリの Document API＝新規依存の追加（`CLAUDE.md` §6 により開発者への提案が必須）か (ii) 自前の行単位パッチャで、いずれも挙動の変更である。** **この見通しを §5.8 へ併記する**——**書かないと、次の担当が「2 段に分かれているのだから前段を差し替えるだけだ」と読む。**

## 3. ★真因の記録——**指示書 §9.4 の 3 条件が `SUPP-001` を含んでいなかった**

**指示書 §9.4 は「CHANGE 要否は as-built で判定する」とし、その判定条件を 3 つ挙げた。** **3 つとも `DES-002` / `DES-003` / `DES-006` の話であり、`SUPP-001` が入っていない。**

**⇒ 製造は §9.4 のとおりに判定して「CHANGE 0 件」と報告し、同時に §1-1 / §1-3 で「`SUPP-001` へ反映してほしい」と書いた。** **★製造の振る舞いは正しい。誤っていたのは条件表のほうである。**

**★★機序＝`SUPP-001` は「設計補足資料」という位置づけのため、CHANGE の要否を考えるときに落ちやすい。** **しかし同書 §5.2 は Go のパッケージ構成の正本であり、パッケージの増減は必ず追随が要る。**

**⇒ 指示書テンプレートの §9.4 相当へ「`SUPP-001` §5.2（パッケージ構成）に増減があるか」「`SUPP-001` §5.8（設定ファイルの決定事項）が変わるか」を条件として足した**（`D-552`）。
