## 2. 反映の中身

### 2.1 `DES-002` §8.2 — 検査の規則（**新設**）

**★核は 1 である**——**サーバ側の照合には、文字種検査も長さ検査も掛けない。恒久の規則である。** 掛けると既存の利用者が入れず、しかも変更もできない（**詰み**）。

**あわせて as-built を 3 点書いた**——**検査はサービス層に置く**（ハンドラを経由しない呼び出しでも破れない）／ **印字可能な ASCII のみ**（**目的は安全性ではなく「入力できること」である**）／ **認証経路の要求本文は 8KiB・`/api/auth/*` の 4 経路のみ・経路単位のミドルウェア**。

**★最後の 1 点には理由まで書いた**——**`Group.Use` は `/api` と `/api/*` へ `NotFoundHandler` を副作用で登録し、経路表が変わる**（OFF でも変わる）。**⇒ 経路単位でしか掛けられない。** **かつ全経路へ掛けると取り込み（CSV）が壊れる。**

### 2.2 `DES-002` §8.2 — 入力補助の歯止め（**★受理の条件**）

**`M22-08` の as-built は、画面の全 4 欄で非 ASCII を入力段階から落とす。** **⇒ ログイン欄と「いまのパスワード」欄に及んでおり、起票時の §2-b（「恒久の規則」）に部分的に反する。**

**★開発者裁定で受理したが、規則そのものを書き直した**（**D-419**）。**§2-b は理由を 2 つ持っており、解除されたのは①（既存利用者の締め出し）だけである。**

**②（将来 検査を変えたときも同じ問題）に対する歯止めを 4 点書いた。**

| # | 歯止め |
|---|---|
| a | **落としてよいのは「印字可能な ASCII 以外」だけ。長さその他に連動させない** |
| b | **★`curl` 相当が唯一の復旧経路である。サーバ側に検査を足すと詰みが復活する** |
| c | **★文字種の規則そのものを狭めるときは、入力段階の除去も同時に見直す**（**a が守っているのは「文字種以外」であって、文字種自体の変更は守っていない**） |
| d | **★b は一般の利用者には使えない。** **LAN 内の数人・管理者が開発者本人という前提でのみ成立する** |

**★c と d は設計卓が足した。** 製造の歯止めは 3 点で、**残っていた穴（文字種自体の変更）と、前提の明示**が抜けていた。

### 2.3 `DES-006` §7 — `VAL-N05`〜`N07`

**物理順は `N04` と `N08` の間**（`N05`〜`N07` は起票時に予約し、`N08` / `N09` は `CHANGE-113` の反映が先に取っていた）。

| VAL | 応答 | 注記 |
|---|---|---|
| `N05`（文字種） | **400 ＋ `password_charset_invalid`** | 照合には掛けない |
| `N06`（長さ） | **400 ＋ `password_length_invalid`** | **★例外 1 つ**——**trim 後に空だけは `invalid_request`**（`M22-01` からの既存挙動）。**書かないと「下限未満は `password_length_invalid`」が `""` のときだけ嘘になる** |
| `N07`（本文サイズ） | **★413 ＋ `request_body_too_large`** | **`Content-Length` の申告有無によらず同じ**（当初 chunked で 400 に割れており、レビューが是正した） |

### 2.4 `DES-006` §10 — パスワード欄

**第一防衛線の表へ 1 行足した。** **★「入力補助であって照合の検査ではない」ことを同じ行に書いた**——**§10 は「エラーを未然に減らす」位置づけの節であり、ここに置くこと自体が線引きの表明になる。**

### 2.5 `DES-005` §4.1 — **ヘッダ表の是正**（★通知書 §8.3）

**現行は「ユーザー表示 ｜ 現在のユーザー名表示、ログアウト（複数ユーザー時のみ）」で、as-built と 3 点で食い違っていた。**

| 面 | 旧 | as-built |
|---|---|---|
| 置き場 | ヘッダ | **設定画面**（§5.16） |
| 表示条件 | 複数ユーザー時のみ | **`passwordRequired`（実効値）。利用者の人数とは無関係** |
| 利用者表示との関係 | 同じ行に束ねている | **★別物。** ヘッダの利用者表示は「使う人を選び直す」であり、**入場ゲートを出るわけではない** |

**★これは `M22-08` §4-1 が拾った。** **起票時の §2-g は §5.16 への追記しか書いておらず、反映しても §4.1 が取り残される形だった。** **⇒ 放置すると次の担当が「ログアウトはヘッダに在るはずだ」と読んで二重に作る。**

### 2.6 `DES-005` §5.16 — ログアウトと改名

**★表示条件に `passwordSet` を使わないことを、理由つきで書いた**——**検証子が在っても `password_enabled = false` ならゲートは効いておらず、押しても何も起きない導線が出る。** **★この 2 つは通常の操作では割れないため、独立したテストでしか押さえられない。**

**改名は「ヘッダが追随する」ところまで書いた**——**明示的な同期コードを持たず、`USERS_KEY` の invalidate から導出し直す形である。** **⇒ 配線が偶然壊れても改名そのものは成功し、ヘッダだけ古い名前が残る。**

### 2.7 test-id — **2 か所へ書いた**

**`DES-005` §6.8 と `docs/design/testid-convention.md` の両方が台帳である**（`M22-08` §1-7 の指摘）。**⇒ `M22-08` の 10 件に加え、`CHANGE-115` で `DES-005` 側にだけ入れていた `M22-04` の 9 件も `testid-convention.md` へ揃えた。**
