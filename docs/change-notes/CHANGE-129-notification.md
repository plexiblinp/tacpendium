## 1. 変更の概要

**`DES-002` §11.3 は CI を「Windows / macOS / Linux 3OS向けのクロスビルドを毎回実行する」用途で規定している**（逐語）。**⇒ PR ごとの高速検査という目的が同じ節に同居しており、実測に照らすと両立しない。**

**★これは仕様の誤りではない。** 同節が書かれた時点では CI が無く、**「毎回」が PR 単位を指すのか統合単位を指すのかを分ける必要が無かった。** **⇒ 本 CHANGE は、実測を得たことで初めて分けられるようになった区別を書き足すものである。**

**★スキーマ変更 0・マイグレ消費 0・新規依存 0・API 契約の変更 0。** **本番コードの diff も 0 の見込みである**（指示書 §5-5 が `git diff --stat` で証明することを求めている）。

## 2. 変更の内容（`DES-002` §11.3）

| # | 対象 | 変更 |
|---|------|------|
| a | **「クロスビルドを毎回実行する」** | **★2 本立てへ分ける**——**PR ＝ `go vet` / `go build` / `go test -count=1` / フロントのユニットテスト ／ nightly ＝ 3 OS クロスビルド。** **★目的の記述はそのまま保つ**（「ビルドが通らなくなった時点で気づける体制を維持する」「動作検証は Windows のみ公式」「Claude Code が主な開発者であり macOS/Linux での動作検証が行われないリスクをカバーする」の 3 点は変えない） |
| b | **★`-count=1` を明記する** | **付けないと結果キャッシュにより「実行していないのに緑」になる。** **ベースライン計測の 1 回目で実際に 46/46 が cached だった**（同書 §1.1）。**⇒ 契約として書く。実装の細部ではない** |
| c | **★job の分割** | **`go vet` ＋ `go build` の job と `go test` の job を分けて並列に走らせる**（同書 §4 A0-2）。**根拠＝`go test` が支配項**〔2 コア相当で 245.6 秒。上位 3 パッケージで 47%〕 |
| d | **★受入の数値** | **PR の time-to-green は 10 分以内。** **★「5 分程度」は目標に置かない**——**同書 §6 の受入判定が「10 分以内は満たす見込み・5 分は未達の見込み」と記録している。** **達成できない数字を契約へ書かない**（`E-152` の同型） |
| e | **★E2E は本節の対象外である旨** | **`playwright.config.ts` の CI 向け設定（`workers: 1` / `dot` / retry の扱い）が未適用であり、Track B の開始条件も未達**（同書 §1.5 / A0-6）。**⇒ 「まだ載せない」を否定形で書く。** **★書かないと次の担当が retry で緑にして載せる** |
| f | **★成果物の扱い** | **nightly は artifact として残すところまで。** **§11.3 の現行記述にある「GitHub Releases に添付する（無保証）」は、公開の手番として人が持つ**——**本 CHANGE で撤回はせず、CI が自動で添付するのではないことを明記する** |
| g | **★キャッシュの位置づけ** | **ビルドキャッシュのリストアは高速化であって正しさの根拠にしない**（同書 A0-3。冷 143.2s → 温 130.2s＝差 13 秒）。**⇒ cache hit / miss の別を記録する** |
| h | **★flaky の扱い** | **現時点で CI 非搭載一覧は空である**（3 回とも緑・分散も小さい＝同書 §1.3 / A0-5）。**同時に「3 回緑は flaky でないことの証明ではない」も書く**（同書 §5-5）。**★この 2 つを両方書く**——**片方だけだと「flaky だから再実行」か「flaky は起きない」のどちらかへ倒れる** |

## 3. 決着の記録——**なぜ分離を採ったか**（**D-480**）

**`M24-overview` v0.1.0 の確認事項 6 は「ベースライン計測 §4 の提案 A0-1〜A0-6 を読んでから決めたい」を暫定案としていた。** **⇒ 2026-08-20 に読んだうえで決めた。**

| # | 根拠 | 出どころ |
|---|---|---|
| 1 | **`go test` が支配項であり、PR 毎に 3 OS クロスビルドまで回すと 10 分に収まらない** | 同書 §1.2 / §1.4 / §3 |
| 2 | **A0-2 が「`go vet` + `build` の job と `go test` の job を分けて並列実行する」を提案しており、分離はその延長である** | 同書 §4 |
| 3 | **目的が違う**——**3 OS クロスビルドは「ビルドが通らなくなった時点で気づける体制」の維持であり、毎コミットで確かめる必要が無い** | `DES-002` §11.3 の逐語 |

**★あわせて節番号の誤りを是正した**——**`M24-overview` v0.1.0 は本節を「`DES-002` §589」と書いていた。** **これは行番号であり、節番号は §11.3 である。** **⇒ v0.2.0 で是正済み。**

## 4. 確定した設計判断

| 項目 | 判断 | 根拠 |
|------|------|------|
| **PR / nightly の分離** | **採る** | §3 の 3 点 |
| **`-count=1`** | **契約として書く** | 実測で「実行せず緑」が起きた（同書 §1.1） |
| **5 分の目標** | **置かない** | 未達の見込みが実測で分かっている（同書 §6） |
| **E2E の搭載** | **本 CHANGE では載せない** | Track B の受入が先（同書 §1.5） |
| **Releases への自動添付** | **作らない** | 公開の手番は人が持つ。**§11.3 の現行記述は撤回しない** |
| **必須 check の範囲** | **PR の高速検査のみ**（暫定） | **nightly の赤は当該 PR の責任ではない**（指示書 §11-2） |
