## 4. 設計判断の実装時確定

| 項目 | 確定内容 |
|---|---|
| **`RemovePunish` の置き場所** | **リポジトリ層でトランザクション化**（指示書は「同一トランザクション」としか書いておらず、担当はサービス層を想定していた）。リポジトリ層に置いたことで **`DELETE /api/combo-punishes` がシグネチャ不変のまま孤児を作らず、将来呼び出し経路が増えても取りこぼさない**。**指示書より良い解**。原子性は「curations 表を DROP して 2 文目を失敗させる」テストで固定 |
| **タブ絞りの置き場所** | **SQL ではなくサービス層**。SQL を 2 回引くと「**どちらのタブにも出ない採用**」を数え漏らすため、1 回の取得結果から 3 分岐する。**第3セクションの存在意義そのものを実装構造で担保** |
| **`registeredCombos` を別型に** | 成立ツリーの `ComboNode` と畳まない。`adopted`（採否トグルの状態）を持たない以上、畳むと採否の意味が曖昧になるため |
| **`invalidate` ヘルパー** | 両キー無効化へ拡張（`[punish-finder]`＋`[punish-list]`）。8 mutation はいずれも両画面に影響し得るため、**片側だけ無効化する組み合わせを作ると必ずどちらかが stale になる** |
| **第3セクションの位置づけ** | **M18-03b の materialize が処理する入力キュー**（**ゴミ箱ではない**）。3 つ目のタブにはせず、両タブ共通・画面下部・折りたたみ |
| **共通ヘッダ** | nav が収まらない場合は **nav 内横スクロールへ degrade**（開発者が実機確認のうえ承認） |
| **query 名の 2 流儀** | **現状維持**。**punish 系の新規 endpoint は冗長形（`self_character_id` 形式）に揃える方針のみ DES-002 §4.2 に明記**（中央裁定＝統一は既存 FE の書き換えを伴う破壊的変更で、得られるのは一貫性のみ） |

> **実機確認で silent failure を 1 件検出**：`punishfinder` の pass2 で `ComboNode.Recipe` への代入が抜け、未代入＝空文字が FE の「空なら行を出さない」分岐に**吸収されて静かに通っていた**。**M18 が一貫して警戒してきた形**であり、実機確認（E-17 の思想）が効いた事例。
