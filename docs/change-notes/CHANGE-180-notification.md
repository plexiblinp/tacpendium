## 1. なぜ要るか

**★★同節は「設置系をどう表すか」を次に調べる人が最初に開く場所である。⇒ 旧記述がそのまま次のサブの前提として複製される。**

**★★★同じ節は `CHANGE-154`**（`subject` の軸）**と `CHANGE-169`**（対象の選定基準）**で既に 2 度、同型の是正を受けている。⇒ 3 度目にしない。**

## 2. 変更内容

### 2.1 ★★`value_definition.options`（ラベル付き選択肢）を新設する

```json
"value_definition": {
  "kind": "integer", "min": 0, "max": 4,
  "options": [
    { "value": 0, "label_ja": "なし", "label_en": "None" },
    { "value": 1, "label_ja": "弱",   "label_en": "Light" }
  ]
}
```

**★在れば画面は数値入力ではなく選択を出す。無ければ従来どおり数値入力である。**

**★★★不変条件が 3 つある。**

| # | 不変条件 | 破れたときに何が起きるか |
|---|---|---|
| **★★1** | **`min..max` が「ちょうど」選択肢の値の集合であること**（欠けても余っても赤） | **★食い違うと `clampIntForDef` が別の選択肢へ黙って化ける** |
| **★★2** | **`label_en` は必須である** | **★無いと `label_ja` へフォールバックし、EN 画面に日本語が出る。⇒ `no-japanese-in-en.test.ts` は locale ファイルしか見ないためこの経路は素通りする** |
| **★★★3** | **`options` を持たない `level` は従来どおり数値入力である。⇒ 1 行も変わらない** | **★as-built で唯一の `level` である `ingrid` の `sun_crest` は不変である**（3 経路のテストで固定） |

**★★★`type` は増えていない。`isSupportedState` は 1 文字も変えていない。⇒ 撤回済みの `type: composite`**（`000009` → `000017` で削除）**を復活させる形ではない。★ここを書かないと「また新しい型が増えた」と読まれる。**

### 2.2 ★★`value_definition.single_value`（int state を 1 つの値として扱う）を新設する

**`true` のとき、画面は 1 欄・表示は 1 行・ラベルは state 名だけになる。省略時は従来どおり ①`start_min` / ②`end` の 2 値である。**

**★★★あわせて次を明文化する＝①② はストック系のためのものであり、開始時の状態だけを持つ state は 1 値である。**

**★根拠＝①② は `M16-07`**（`CHANGE-067`）**が**ストック系のために**足した拡張であり、`custom_states` の原点は `CHANGE-040` の「開始時状態の付与のみを扱う。消費（減少・解除・レベル技変化）は一般モデル化しない」である。**

**★★これが無いと、次に `custom_states` を足す人が同じ取り違えをする。⇒ `M31-05` が実際に取り違え、開発者が実機で見て初めて分かった。**

**★格納形は `{start_min, end}` のまま両方へ同じ値を書く。⇒ 形を分岐させない。★片方だけに値が入った形**（手書き JSON・旧データ）**も、既定でない側を採って畳む。**

**★既存のストック系 6 件**〔`fuha_stock` / `flame_stock` / `windclad` / `blanka_chan_bomb` / `shuriken_bomb_stock` / `sun_crest`〕**は `single_value` を持たないため 1 文字も変わらない。**

### 2.3 ★★★「設置系は `type: flag`」を是正する

**同節の「対応可能なケースの例」は次のように書いている**（`CHANGE-154` で `subject` の軸が是正された際に書かれたもの）:

> **設置技が置かれた状態から始まるコンボ** → …自分の側に立つ状態は `subject: self`, `type: flag`

**★★as-built では、投入した 12 件のうち `flag` は 2 件だけである**〔`saihasho_is_set` / `blanka_chan_bomb_is_set`〕**。⇒ 7 件が `options` 付き `level`、1 件が `stock`、あとの 2 件が発動中の `flag` である。**

**⇒ 次のとおり書き換える。**

> **★★設置系の `type` は `flag` に限らない。⇒ 変種を持つものは `options` 付き `level`、個数を持つものは `stock` を採る。★`flag` は「置いたかどうか」だけを持つものに使う。**

### 2.4 `custom_states` の `code` の付け方

| 種別 | 形 | 先例 |
|---|---|---|
| **設置物の有無・数** | **`<family>_is_set`** | `m_bison` の `psycho_mine_is_set` |
| **発動中の状態** | **素の `<family>`** | `blanka` の `lightning_beast` ／ `juri` の `feng_shui_engine` |

**★★★根拠はキャラ固有状態タブの語幹照合である**（`CHANGE-170` §2.5）**。⇒ `_is_set` は `STATE_CODE_SUFFIXES` に在るため語幹化され、ファミリー全変種に当たる。**

**★★★`_set` 単独では語幹化されない**（実測 0 件）**。⇒ `<family>_set` という自然な命名を選ぶと「足したのにタブに出ない」が起きる。★検査は緑のままである。**

---

## 3. 変更しないもの

| 対象 | 理由 |
|---|---|
| **`type` の列挙**（`level` / `flag` / `stock` / `composite`） | **★1 つも増えていない。⇒ `isSupportedState` も無改変である** |
| **`sun_crest`**（唯一の as-built `level`） | **`options` を持たないため不変** |
| **既存のストック系 6 件** | **`single_value` を持たないため不変** |
| **API・スキーマ** | **`characters.custom_states` は元から生 JSON を素通しする列である。⇒ `DES-002` §4.2 の経路表に載る変更 0 件** |

---

## 4. 影響

- **★★次に `custom_states` を足す人は、§2.2 の「①② はストック系のためのもの」を読んでから設計すること。⇒ 読まないと同じ取り違えをする**
- **★`options` を 11 個以上にすると、11 個目以降がマウス以外で選べない。⇒ 型検査・単体・E2E がすべて緑のまま通る**（`followup` の `custom-state-options-count-unchecked`）
- **★`ingrid` の `order_of_the_sun` が 10 個で余白 0 である。⇒ 次に 1 つでも足すと線を越える**
