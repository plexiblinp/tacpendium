## 2. 起票内容から動いたもの（★2 件）

### 2.1 §2-e′ の「出口の形」を、指示書の文言のまま写せなかった

**指示書 §4.9-2 は「部品の出口は `move_code` ＋ 方向 ＋ 修飾」と書いていた。** **as-built は方向を独立したフィールドとして持たない。**

**⇒ 受理した**（**D-353**）。**理由 2 点**——

1. **方向は解決の時点で `move_code` へ畳み込まれている**（段階1 の構造引きは方向ゾーンを `standing_` / `crouching_` / `jumping_` の接頭辞として含め、段階2 は方向込みの `token_key` で引く）。**⇒ 出口に別途持つと同じ情報が 2 か所になる**（`E-76`）。**しかも `move_code` が正であるため、方向フィールドは誰も検証しない。**
2. **既存の中立形**（仮想コントローラが使っている `StepInput`）**に揃えたことで、§4.9-2 の主旨——面に依存しない中立形・写し替えは呼び出し元——を新しい型を作らずに満たせた。** **結果としてセットプレイ入力面の変更は 0 行だった。**

**★設計卓の書き方の誤りである。** **実装ソースを持たない側が、出口の「中身」を具体的に描写した**（`E-117`）。**本サブで 2 度目である**（1 度目＝§4.2-2 の「2 ボタン同時は OD 技」＝**D-352**）。

### 2.2 「2 面の両方で動く」だけでは足りず、受け手の調停が要った

**通知書も指示書も、2 面が同時に表示される場合を想定していなかった。** **実装ソースの実査で、コンボ編集画面がレシピ節とセットプレイ節を同時に開くことが判明した**（節は既定で開いている）。

**⇒ 素朴に入力面へ接続を置くと、(a) ポーリングのループが面の数だけ増え、(b) 1 回の物理入力が全部の面へ同時にステップを足す。**

**⇒ 製造が受け手の調停を新設した。** **`DES-005` §6.4.3 の項目 4〜5 として明文化した。**

| 論点 | 起票時 | as-built |

| **読取表示** | 3 区画（押されている入力 ／ 確定したステップ ／ **解決できなかった入力**） | **維持。** **★理由の粒度が as-built で確定した**——**6 種**。**とくに「ラッシュ版は空中では出せない」を「技が無い」へ丸めないこと** |

## 4. 告知の出し分け（★「常設される UI」の落とし穴）

**初版は「供給元の内側にいるか」で出し分けていた。** **供給元はアプリ全体に常設されるため本番では常に真であり、⇒ 物理コントローラを一度も接続したことがない利用者にも、告知と読取表示が常設されていた。**

**★`make e2e` が実機コントローラの無い環境で全緑だったこと自体が、未接続でも DOM に出ていた証拠だった。** **「テストが緑」は「出ていない」を意味しない。**

**⇒ `status === "connected"` でのみ出す形へ是正し、`DES-005` §6.4.2・§6.4.3 の両方へ書いた。**
