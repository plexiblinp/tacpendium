## 1. 変更の概要

**`M22-02` が入場の画面を作ったが、パスワードの検査は「空でないこと」だけだった。**

**開発者が実機で「日本語入力が通る」ことを見つけ、製造担当が実測して確定した**（`M22-02` 設計伝達レポート §4.1）——**長さ・文字種・正規化・前後の空白・本文サイズがすべて素通りする。**

**★最も重いのは正規化のゆれである。** **検証子は受け取ったバイト列に対して計算する。** **`が` は NFC（U+304C）と NFD（`か`＋U+3099）の 2 通りがあり、見た目が同一なのにバイト列が違う。** **⇒ 決めた端末と入れる端末で正規化が違うと、正しく打っているのに永久に入れない。**

**★本アプリは「ほかの機器から開く」ことが目的であり、この経路は例外ではなく主経路である。** **しかも症状は「パスワードが違います」だけで、利用者からは原因が絶対に分からない。**

**⇒ 本 CHANGE は方針を `DES-002` §8 へ書き、検証コードを `DES-006` §7 へ採番する。**

**★非スキーマ・非破壊である。** **DB のテーブル・列・制約を 1 つも変えない。** **マイグレーションを消費しない。**

### 1.1 CHANGE 対象外（切り分け）

| 項目 | 対象外の理由 |
|---|---|
| **パスワードの複雑さ要件**（文字種の構成・使い回しの検査・辞書照合） | **`FR501`「簡易的なログイン」／ `DES-002` §10 `NFR102`「過剰でない対策」。** **★本 CHANGE の目的は安全性ではなく「入力できること」である**（§3） |
| **試行回数制限・多要素認証** | 同上 |
| **未認証で叩ける経路のレート制限** | **`M22-05` の担当**（followup `auth-unauthenticated-kdf-cost`） |
| **`SecurityStore` の TOCTOU の是正** | 改善レーンの担当（followup `auth-setpassword-toctou`） |
| **利用者の削除** | **★開発者の指示で「作らない」**（followup `user-delete-not-provided`）。**消すと `ON DELETE CASCADE` でその人のタグ・プリセットが一括で消えるため、何が消えるかを見せる設計から要る** |
| **無効中に `POST /api/auth/password` が無認証で通ること** | **★塞がない**（followup `auth-anyone-can-set-initial-password-while-off`）。**塞ぐと「パスワードを忘れたときの復旧」が成立しなくなる**（**D-407**） |
| **HTTPS の導入** | **契約 F-3** |

## 2. 変更の内容

| # | 対象 | 変更 |
|---|------|------|
| **a** | **`DES-002` §8 へ「パスワードの文字種と正規化の方針」を 1 項追記** | **★次を書く**——**(1) 受け付けるのは印字可能な ASCII（`U+0020`〜`U+007E`）のみである**〔**半角スペースを含む**〕 ／ **(2) 前後の空白は除去する** ／ **(3) 長さに下限と上限を設ける** ／ **(4) ★NFC 正規化は行わない。** **★理由を必ず併記する**——**問題を半分しか解かない**〔正規化のゆれは消えるが、全角・半角の取り違えと、マスク欄で IME が使えない可能性が残る〕。**⇒ 書かないと、次の担当が「正規化すればいいのに」と読んで足す** |
| **b** | **★`DES-002` §8 へ「検査は決めるときだけに掛ける」を 1 項追記**（**★本 CHANGE で最も重要な項目**） | **照合には文字種検査も長さ検査も掛けない。** **★理由**——**掛けると、既に非 ASCII や短いパスワードで決めた利用者が入れなくなり、しかも変更もできなくなる**〔変更は現在のパスワードを要求するため〕。**⇒ 詰みが生まれる。** **★これは移行の都合ではなく恒久の規則である**——**検査の内容を将来変えたときも同じ問題が起きる** |
| **c** | **`DES-006` §7 へ `VAL-N05` を追加**（**★`N08` / `N09` は `CHANGE-113` が使用済み。番号は起票の順である**） | **★パスワードを決める要求で、印字可能な ASCII 以外を含むなら拒否する**（400）。**★適用は「決めるとき」だけ**（§2-b）。**種類＝ERROR** |
| **d** | **`DES-006` §7 へ `VAL-N06` を追加** | **★パスワードを決める要求で、前後の空白を除去したうえで長さが範囲外なら拒否する**（400。**下限 `4` ／ 上限 `128`**）。**★適用は「決めるとき」だけ**（§2-b）。**★下限の目的は「打ち間違いで空に近い値が通るのを防ぐ」ことであり、強度ではない。** **★上限は反復コストには効かない**〔PBKDF2 は HMAC の鍵正規化で長い鍵を 1 度ハッシュしてから反復する〕**——効くのはメモリと帯域である。** **種類＝ERROR** |
| **e** | **`DES-006` §7 へ `VAL-N07` を追加** | **★認証まわりの要求本文にサイズの上限を設ける。** **★全経路へ掛けない**——**取り込み（CSV）は利用者のファイルを丸ごと受ける経路であり、上限が小さいと取り込めなくなる。** **★掛ける範囲を明記する**（既定は `/api/auth/*`）。**種類＝ERROR** |
| **f** | **★済み**——**`CHANGE-113` の反映（2026-08-16）が先に行った**（`change-report-113` §3.2）。**理由＝同反映が `VAL-N08` / `N09` を足した時点で、節タイトルの射程が破れるためである。** **⇒ 本 CHANGE の反映では確認だけを行う**（**★`DES-006` §7 の節タイトルの射程を是正**。**★2026-08-16 に気づいた隣接の食い違い。§2.2 参照**） | **現行のタイトルは「LAN共有モード切替時のバリデーション」だが、`VAL-N03` / `VAL-N04`（`CHANGE-112`）と本 CHANGE の `VAL-N05`〜`N07` は切替時の検証ではない。** **⇒ 節の射程を「LAN 共有と入場ゲートのバリデーション」等へ広げる。** **★`VAL-N01`〜`N04` の中身は変えない** |
| **g** | **`DES-005` §5.16 の「2. ユーザー」へ 2 点を追記** | **(1) ログアウトの導線**（**★パスワード保護が有効なときだけ出す**。**押すとログイン画面へ戻る**。**★「利用者の選び直し」とは別物である**——あちらはヘッダの利用者表示が担う） ／ **(2) 利用者の改名**（**★`DES-005` §5.16 の「ユーザー追加・編集」の「編集」を満たす**。**重複名は 409、空名は 400**。**★選択中の利用者を改名したらヘッダの表示が追随する**） |

### 2.1 ★変えないもの（網羅宣言）

- **`DES-006` §7 の `VAL-N01`〜`VAL-N04` の中身**（**★タイトルの射程だけを直す**＝§2-f）
- **`DES-002` §8 の中核**（「厳格な認証ではなくラベル付け程度」「防御責任の主体はルーター・ファイアウォール」「必須化はしない」）
- **`DES-002` §8.1 の 16 項目**（**★`M22-01` の as-built。本 CHANGE は追記だけである**）
- **検証子の形式と導出**（`pbkdf2-sha256$<iterations>$<salt>$<key>`・反復回数）——**★触ると既存の検証子が読めなくなる**
- **`REQ-001`**（**★本 CHANGE は要件を動かさない**）
- **`DES-003`**（**★DB スキーマを 1 つも変えない**）

### 2.2 ★隣接する既知の食い違い 2 件（**本 CHANGE で併せて直す。新規採番はしない**）

| # | 食い違い | 扱い |
|---|---|---|
| 1 | **`DES-006` §7 のタイトルが「LAN共有モード切替時のバリデーション」のままである** | **`VAL-N03` / `VAL-N04`（`CHANGE-112`）の時点で既に射程を超えていた。** **本 CHANGE が `VAL-N05`〜`N07` を足すと、節の 7 項目中 5 項目が「切替時」ではなくなる。** **⇒ §2-f で直す** |
| 2 | **★`VAL-N02` が利用者ごとのパスワードを前提にしている** | **逐語**——「LAN共有モードON切替時、**パスワード未設定のユーザーが1人でも存在する場合**は警告を表示し……」。**★パスワードは全員共通の 1 本であると `CHANGE-112` で確定しており、「パスワード未設定のユーザー」という概念は存在しない。** **⇒ 「パスワードが設定されていない場合」へ改める。** **★これは `CHANGE-113` が撤回した仕様の残骸である**——**同 CHANGE の否定形確認が本番コードとテスト資産を主対象としており、`DES-006` の散文まで届かなかった。** **`D-361` の対象そのものである** |

**★新規採番は不要**（本数は 1 本のまま＝**D-323** の先例）。**先例＝`CHANGE-112` §3 ／ `CHANGE-113` §2.2・§2.4。**

### 2.3 真因の記録

**★バグ修正ではない。** **`DES-002` §8 も `DES-006` §7 も、パスワードの入力そのものについて何も定めていなかった。** **⇒ 実装は「空でないこと」だけを守り、それは設計に反していない。**

**★記録に値するのは、この穴が「利用者から見た症状」と「原因」が最も離れる型だった点である。**

| 層 | 見えるもの |
|---|---|
| 利用者 | **「パスワードが違います」** |
| 実際 | **正規化が違うだけで、打った文字は正しい** |

**⇒ 利用者は「打ち間違えた」と思って何度も打ち直し、最後に諦める。** **★しかも `M22-01` が「理由を区別しない」を仕様として決めているため**（`DES-002` §8.1）、**区別する情報は原理的に出てこない。**

**★この型は、入力の検査が無い限り必ず起きる。** **⇒ 「過剰でない対策」の下でも、入力できることの保証は要る。**

## 3. ★文言案（**指示書 `M22-08` §4.4 が参照する**）

**★本節は「そのまま使ってよい案」である。** **より良い言い回しを思いついたら変えてよい**（**★変えた場合は完了報告へ新旧を並べる**）。

**方針は `CHANGE-113` §6.1 の 5 点をそのまま引き継ぐ**（**★「正規化」「エンコード」も説明なしに使わない**）。

### 3.1 パスワードを決めるとき（**入力欄の下の案内**）

```
半角の英数字と記号で決めてください。
```

### 3.2 日本語・全角が含まれていたとき

```
日本語や全角の文字は使えません。

ほかの機器から開くときに、同じ文字が打てなかったり、見た目が同じでも
別の文字として扱われたりすることがあるためです。

半角の英数字と記号で決め直してください。
```

**★「なぜ弾くか」を書くこと**（指示書 §4.4 末尾）。**「使えない文字です」だけだと、利用者は日本語が悪いと分からない。**

### 3.3 短すぎるとき / 長すぎるとき

```
4 文字以上で決めてください。
```

```
128 文字までにしてください。
```

### 3.4 ログアウト（**設定画面**）

```
この機器からログアウトする

もう一度開くときに、パスワードの入力が必要になります。

  [ ログアウト ]
```

**★「利用者の選び直し」と混ぜないこと**（指示書 §4.3-4）。**あちらはヘッダの利用者表示が担う別物である。**

### 3.5 利用者の改名（**設定画面**）

```
名前を変える

  [ 現在の名前              ]

  [ 変える ]
```

**重複したとき**——

```
その名前はすでに使われています。
```

**空のとき**——

```
名前を入れてください。
```

## 4. 確定した設計判断（**開発者承認済み＝D-408**）

| 項目 | 判断 | 根拠 |
|------|------|------|
| **文字種** | **★印字可能な ASCII（`U+0020`〜`U+007E`）のみ。半角スペースを含む** | **D-408**。**★日本語入力による 3 つの失敗**〔正規化のゆれ ／ 全角・半角の取り違え ／ マスク欄で IME が使えない可能性〕**をまとめて消す** |
| **NFC 正規化** | **★行わない** | **D-408**。**★問題を半分しか解かない**〔正規化のゆれは消えるが、全角・半角の取り違えと IME の問題が残る〕**うえ、`golang.org/x/text` の direct 昇格が要る**（`CLAUDE.md` §6） |
| **決めるときの警告**（案 c） | **★不要** | **D-408**。**弾くので警告する対象が無い** |
| **前後の空白** | **除去する。「決めるとき」と「入れるとき」の両方** | **★IME の確定操作で末尾に空白が入っても気づけないため。** **★受け入れる代償**——**前後に空白を含む既存のパスワードは使えなくなる**〔確率は極めて低く、復旧経路も在る〕 |
| **長さ** | **下限 `4` ／ 上限 `128`** | **設計卓の判断。** **★下限の目的は「打ち間違いで空に近い値が通るのを防ぐ」ことであり、強度ではない。** **★上限は反復コストには効かない**——**効くのはメモリと帯域である** |
| **★検査の適用範囲** | **★「決めるとき」だけ。照合には掛けない** | **★掛けると、既に非 ASCII や短いパスワードで決めた利用者が入れなくなり、変更もできなくなる。詰みである。** **★開発者の手元がこれに当たりうる** |
| **本文サイズの上限** | **設ける。★ただし全経路へ掛けない** | **★取り込み（CSV）は利用者のファイルを丸ごと受ける経路である。** **既定は `/api/auth/*` に限る** |
| **★実装の手段** | **★標準ライブラリ ／ フレームワークの仕組みで足りるなら、それを使う。自前で書かない** | **開発者の指示**（2026-08-16＝**D-410**）。**★本 CHANGE が定めるのは「何を弾くか」であって「どう弾くか」ではない。** **⇒ 文字種の判定・前後の空白の除去・本文サイズの上限は、いずれも標準の仕組みで表せる見込みが高い。** **★自前で書くと、境界の扱い〔多バイト文字・空文字・上限ちょうど〕を自分で正しくする責任が生まれる** |
| **複雑さ要件** | **★課さない** | **`FR501`「簡易的なログイン」／ `NFR102`「過剰でない対策」。** **★本 CHANGE の目的は安全性ではなく「入力できること」である** |
| **利用者の削除** | **★作らない** | **開発者の指示**（`D-407`）。**`ON DELETE CASCADE` でその人のタグ・プリセットが一括で消えるため、何が消えるかを見せる設計から要る** |

## 8. ★addendum（2026-08-16・**D-419**）——`M22-08` の as-built を受けた改訂

> **★本節は `M22-08` の完了後に足した。** **as-built が §2-b の「恒久の規則」に部分的に反しており、受理するには規則そのものを書き直す必要があるため。**

### 8.1 ★§2-b の規則を書き直す（**受理 ＋ 条件付き**）

**§2-b の逐語**——

> 照合には文字種検査も長さ検査も掛けない。**理由**——掛けると、既に非 ASCII や短いパスワードで決めた利用者が入れなくなり、しかも変更もできなくなる。**⇒ 詰みが生まれる。★これは移行の都合ではなく恒久の規則である**

**`M22-08` の as-built は、画面の全 4 欄（ログイン・いまのパスワード・決める・新しい）で非 ASCII を入力段階から落とす。** **⇒ ログイン欄と「いまのパスワード」欄に及んでいる。**

**★開発者裁定で受理する**（2026-08-16）。**ただし §2-b が挙げていた理由は 2 つあり、解除されたのは 1 つだけである。**

| # | §2-b の理由 | 扱い |
|---|---|---|
| ① | **既に非 ASCII / 短いパスワードで決めた利用者が締め出される** | **★開発者が解除**——**リリース前であり該当者が居ない**（2026-08-16 の明示的な回答） |
| ② | **将来、検査の内容を変えたときも同じ問題が起きる** | **★残っている。** **下記の歯止めで潰す** |

**★書き直したあとの規則**（**`DES-002` §8 へ逐語で書く**）——

| # | 規則 |
|---|---|
| 1 | **★サーバ側の照合には、文字種検査も長さ検査も掛けない。** **これは引き続き恒久の規則である**（`Service.Login` と `SetPassword` の `current` は無検査） |
| 2 | **★画面のパスワード欄が入力段階で非 ASCII を落とすのは、照合の検査ではなく入力補助である。** **⇒ 1 と矛盾しない** |
| 3 | **★入力段階で落としてよいのは「印字可能な ASCII 以外」だけである。** **長さその他の規則に連動させてはならない**（**★連動させると ② が復活する**。`LoginScreen.test.tsx` の「下限より短い / 上限より長い はそのまま送られる」が固定している） |
| 4 | **★`curl` 相当の経路からは従来どおり非 ASCII のパスワードで入れる。** **⇒ これが唯一の復旧経路である。** **★サーバ側に検査を足すとこの経路が消え、詰みが復活する** |
| 5 | **★文字種の規則そのものを将来狭めるときは、入力段階の除去も同時に見直すこと。** **★歯止め 3 が守っているのは「文字種以外の規則」であって、文字種自体の変更は守っていない**（**⇒ ② の残りはここに集約されている**） |

**★4 は「一般の利用者には使えない復旧経路」である。** **本アプリは LAN 内の数人で使う個人 OSS であり、管理する人が開発者本人であるため実用上は成立する。** **⇒ この前提が変わったら 1〜5 を見直すこと。**

### 8.2 ★拒否の文言は 1 文でよい（**§3.2 の案を差し替える**）

**`CHANGE-119` §3.2 は 3 段落の案を置いていたが、開発者の指示で 1 文になった**（2026-08-16）——**「日本語や全角の文字は使えません。」**

**★受理する。** **指示書 §4.4 末尾が求めていたのは「なぜ弾くか」という説明そのものではなく、「利用者が日本語が悪いと分からない」状態を避けることである。** **⇒ 原因を名指ししている以上、趣旨は満たす。**

**★あわせて、本文言は画面からは到達しなくなった**（§8.1 の入力段階の除去による）。**⇒ 検査と文言は「到達しない防御」として残す。** **これは正しい**——**`curl` 相当の経路と、将来 入力補助を外したときのために要る。**
