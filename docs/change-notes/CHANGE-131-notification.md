## 1. 変更の概要

### 1.1 何が食い違っていたか

**開発者は 2026-08-25 に次の判断を明かした**（逐語）。

> なおマノンは一応 character の custom_state にメダル(付与数でダメージだけ変わる)を含めないという意味にはなる

**理由は逐語のとおり——付与数で変わるのはダメージだけである。** **コンボの成立・分岐を変えない状態は、キャラ固有状態として持つ意味が無い。**

**★★これは設計書 2 冊と正面から食い違っていた**（**D-544**）。

| 場所 | 記述 | 性格 |
|---|---|---|
| **`REQ-001` §6.4** | 「マノンのメダルレベル、AKIの毒状態などのキャラクター固有の特殊状態は『状況』の一部として扱う」 | **要件文。名指しで「扱う」と書いている** |
| **`DES-003` §3.2**（JSON 例） | `custom_states` のスキーマ例の 1 件目が `medal_level` | スキーマの表現力の例示 |
| **`DES-003` §3.2**（対応可能なケースの例） | 1 行目が「マノンのメダルLv → subject: self, type: level」 | 同上。**ただし名指しである** |
| **`DES-003` §3.4**（situation の例） | `{"custom_states": {"medal_level": 3}}` | コンボ側の保持例。**同じ code 名の 4 つ目の写し先** |

### 1.2 実測——**実データに存在しない**

**2026-08-25 の read-only 調査（使い捨てセッション・指示書なし＝`D-546`）が次を実測した。**

1. **マノンの `characters.custom_states` は SQL NULL である**（`typeof()`＝null ／ `quote()`＝NULL。**空オブジェクト `{}` ですらない**）。
2. **DB 走査 4 通り**〔`medal_level` 完全一致 ／ 生テキスト LIKE を medal / Medal / MEDAL / メダル / medaille / médaille の 6 綴りで ／ level・Lv の名称走査 ／ 行連結の大小無視走査〕**と、ファイル走査 2 通りが、いずれも 0 件。**
3. **19 キャラのうち 8 キャラに定義があり（計 9 state）、11 キャラが NULL である。** **⇒ 「マノンだけが空」ではない。**
4. **出所は `migrations/000043_seed_characters_manon.up.sql` の INSERT 列リストである**——**`(game_id, code, name_ja, name_en)` であり `custom_states` を含まないため、列の既定値 NULL が適用される。** **同ファイルの直前行に「スコープ外」と明記したコメントが在る。**
5. **書き込み経路は migrations しか無い**〔CSV に該当列なし ／ seedgen は `custom_states` に触れない ／ Go 側は SELECT のみで `UPDATE characters` が 1 件も無い〕。**⇒ どのマイグレーションもメダルを書いていない以上、定義は生まれない。**
6. **`type: level` を使っている as-built の state は `sun_crest` 1 件だけである。**

**⇒ `D-544` が挙げた 2 分岐のうち (i) が確定した**——**as-built が開発者の判断と一致しており、設計書 2 冊のほうが古い。**

### 1.3 ★起票と反映を同一手番で行う理由

**通常の CHANGE は「起票（着手前ゲート）→ 実装 → as-built 確定 → 反映」の順を踏む。** **本件はその形に当てはまらない。**

- **実装すべきものが 1 つも無い。** 設計書の記述を as-built へ揃えるだけであり、コード・マイグレーション・データのいずれも変えない。
- **as-built は既に確定しており、実測されている**（§1.2）。**⇒ 「実装はこうなるはず」で書く余地が無く、設計卓の規則〔DES は as-built 確定後に change-report と同時に改訂する〕は満たされている。**
- **待つと害がある。** **同じ code 名の写し先が 4 か所あり、片方だけ直った状態は `E-114` / `E-191` そのものである。** **4 か所を 1 手番で揃えるほうが安い。**

## 2. 変更の内容

### 2.1 `REQ-001` §6.4——**名指しを外し、否定形で理由ごと残す**

**旧**（第30版まで）:

> マノンのメダルレベル、AKIの毒状態などのキャラクター固有の特殊状態は「状況」の一部として扱う。

**新**: 名指しから「マノンのメダルレベル」を外す。**そのうえで、扱う条件と、マノンを扱わない理由を書き足す。**

- 扱うのは「その状態によってコンボの成立・分岐が変わるもの」に限る。
- **値が変わってもダメージしか変わらない状態は、キャラ固有状態として定義しない。**
- **★マノンのメダルレベルは扱わない**（2026-08-25 開発者判断）。**第30版までの「扱う」を撤回する。**

**★「撤回する」と明示的に書く**（playbook §16.3 ／ `E-258`）。**消すだけにすると、次の担当が「書き忘れではないか」と読んで復活させる。**

### 2.2 `DES-003` §3.2——**JSON 例から `medal_level` の項を落とす**

**スキーマ例の 1 件目（`medal_level` / メダルLv / `type: level` / integer 1..5）を削除する。**

**★削除の代わりに、`type: level` の as-built の実例が `sun_crest` であることを本文で示す。** **定義本体は転記しない**——**同書は第54版で「設計書に実測値を書くときは正本がどこかを必ず併記する。併記できないなら書かない」と自ら定めている。** **⇒ 正本は seed（`migrations/`）であり、本書が定めるのは形だけである。**

### 2.3 `DES-003` §3.2「対応可能なケースの例」——**1 行目を型の例へ置き換え、否定形を 1 行足す**

- **旧 1 行目**「マノンのメダルLv → subject: self, type: level」を、**キャラを名指ししない型の例**へ置き換える。
- **末尾へ否定形を 1 行足す**——**マノンのメダルレベルは扱わない**（`REQ-001` §6.4 ／ 本 CHANGE）。
- **★あわせて as-built の注記を足す**——**本節の例のうち seed に定義が入っているものと入っていないものがある**（19 キャラ中 11 キャラが NULL）。**★入っていないことは「扱わない」を意味しない**（§3）。

### 2.4 `DES-003` §3.4——**situation の例の code を差し替え、同時に形式も現行へ揃える**

**旧**: `{"custom_states": {"medal_level": 3}}`

**新**: **as-built に実在する `level` 型の code を使い、int state の現行の構造で書く。**

**★形式も同時に直す理由**——**旧例はスカラ形式であり、これは `CHANGE-067` / `M16-07` 以降は「後方互換で `end` へ写像される旧形式」である。** **同節の上流（§3.2）は既に `{"start_min": n, "end": m}` を規定している。** **⇒ code だけ差し替えると、新しく書いた例を旧形式で書くことになる。** **既存の記述を引き継ぐのと、自分で旧形式を書き起こすのは別である。**

### 2.5 ★変更しないもの

| 対象 | 変更しない理由 |
|---|---|
| **`DES-003` §3.2 の `drunk_level`（ジェイミーの酔いレベル）** | **未実装であって、不採用ではない**（§3）。**as-built では jamie も NULL だが、理由は seed のスコープ外であり、開発者の設計判断ではない。** |
| **`DES-003` §3.2 の `poison` / `solid_puncher`** | 撤回の対象ではない。 |
| **`characters` 表のスキーマ・`custom_states` 列の定義** | **1 文字も変えない。** 列は残る。 |
| **`migrations/000043`** | **1 バイトも編集しない**（`D-535`＝適用済みマイグレーションは歴史的記録である）。 |
| **`combos.situation` の opaque JSON 扱い** | 変えない。§3.2 の規定どおり BE 素通し・`DuplicateKey` / `recipe_hash` 非対象。 |

## 3. ★★機序の記録——**同じ NULL に理由が 2 つある**

**実測は「19 キャラ中 11 キャラの `custom_states` が NULL」を示した。** **★この 11 件は同じ観測値だが、設計書への反映は正反対である。**

| 型 | 何が起きているか | 該当 | 設計書での扱い |
|---|---|---|---|
| **(a) 設計判断で「持たない」** | 開発者が「キャラ固有状態として定義しない」と決めた | **マノンのメダルだけ** | **撤回する。** 理由ごと否定形で残す |
| **(b) seed のスコープ外で「まだ無い」** | `M14-03d` が定義の投入をスコープ外とした | **残り 10 キャラ**（jamie ほか） | **残す。** 「あるべき姿」であり、消すと将来の実装の根拠が失われる |

**★★一般形＝「実装に無い」を設計書へ反映する前に、無い理由を (a) / (b) のどちらかに判定する。** **理由を確かめずに撤回すると、あるべき姿を消す。**

**★これは `D-545` で記録したのと同じ機序である**〔`users.password_hash` の撤回理由を確かめずに `main_character_id` へ形だけ写した件＝`E-210` の裏返し〕。**2 手番連続で同じ型に当たったため、playbook §4.31 へ昇格させた。**

**★もう 1 つの機序——判断が記録された場所と、反映されるべき場所は別である。**

**調査は、同じ「スコープ外」の判断が既に 4 か所に記録されていることを見つけた。**

1. `migrations/000043_seed_characters_manon.up.sql` のコメント
2. `docs/handover/design-reports/20260731-m14-03d-design-exceptions.md`
3. `docs/progress/m14-03d-completion-report.md`
4. `character_data/command-correction-history.md`（**教訓20**。**jamie の酔いLv を同じ型として名指ししている**）

**⇒ 実装側に 4 か所も書いたのに、設計書 2 冊には 1 文字も届いていなかった。** **★通常の `E-114`〔写し先の同期漏れ〕は設計書 → 実装の方向で起きるが、本件は逆向きである。** **★とくに 2 は「設計例外レポート」であり、設計卓へ渡すことがその文書の目的だった。渡ったが、畳まれなかった。** **⇒ 計測点 `M-76` を立てた。**

## 5. 影響範囲・移行影響・リスク

### 5.1 影響範囲

**実装・データ・マイグレーションへの影響は無い。** **本 CHANGE は設計書のテキストだけを動かす。**

### 5.2 ★残っている未計測が 1 つある——**開発者のローカル実 DB**

**調査は `combos.situation` に `medal_level` を含む行が 0 件であることを確かめたが、走査したのは使い捨て環境の新規 DB である。** **同環境の `combos` は 0 行であり**〔`000012` が入れた 36 行は `000017` が削除している〕、**かつ `situation` を書くマイグレーションは 1 本も存在しない。** **⇒ 実質的に「利用者が入力した行」しか候補が無く、そこは走査されていない。**

**★★ただしこれは本 CHANGE を止めない。**

- **`situation` は opaque JSON であり、BE は素通しする**（`DES-003` §3.2）。**定義の無いキーが入っていても `DuplicateKey` も `recipe_hash` も動かない。** **⇒ 実在しても機能は壊れない。**
- **そもそも入力経路が無い。** 画面はキャラの `custom_states` 定義から入力 UI を作るため、**定義が NULL のマノンでは `medal_level` を入力できない。** **残る経路は API を直接叩くことだけである。**

**⇒ 開発者の手番として §7-2 へ回す。緊急ではない。**
