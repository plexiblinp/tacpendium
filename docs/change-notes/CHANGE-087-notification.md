## 1. 変更の概要

セットプレイ提案は**フレーム計算のみで候補を導出しており、間合いを一切モデル化していない**。実際に成立するかは**相手の受け身種別（その場／後ろ）と画面端の有無**で変わるため、**ユーザーが実機で検証した結果を「コンボとセットプレイの組」に対して記録し、後から絞り込めるようにする**。

そのための新表 **`combo_setup_results`** を新設する。**非破壊**（新規 CREATE TABLE のみ・既存テーブルへの ALTER なし）。着手前ゲート＝反映案。

## 3. 判断の根拠

### 3.1 帰属先を `combo_setups`（の組）にした理由（R-E の解決）

`setups` は `combo_setups` で**複数コンボに紐づき得る**。同じセットプレイを別のコンボへ転用すると、**コンボの終わり際の距離が違うため成立条件も変わり得る**。したがって成立条件は**セットプレイ単体の属性ではなく「コンボとセットプレイの組」の検証結果**である。**開発者回答 2026-07-26 により R-E は解決済み**。

> **DES-003 §3.11 の「`setups` は situation を持たない」という性質とは矛盾しない**（本表はセットプレイ単体の属性ではないため）。

### 3.2 三値（未検証／成立／不成立）を「行の有無 ＋ `result`」で表す理由

**R-B（未検証と不成立の区別・前方互換）**を満たしつつ、**NULL に意味を持たせない**。行が無ければ未検証、行があれば `result` が成立／不成立を表す。既存行を壊さずに値を足せる。

### 3.3 代替案の不採用理由

| 代替案 | 不採用の理由 |
|---|---|
| `combo_setups` へ 4 列追加 | **軸が増えるたびに列が倍増**する（受け身 × 端 で 4、次の軸が入れば 8）。**関連テーブルの実体化**を招く |
| `setups.description` への自由記述 | **絞り込みができず、要望の核心（R-C）を満たさない**。CHANGE-086 v4 でこの非構造版は範囲から除外済み |

## 4. 開発者裁定（2026-07-26・確認事項は解決済み）

1. **DES-006 に `tech_type` / `in_corner` / `result` の値域検証（VAL）を足すか → 【裁定】足さない**。理由＝**入力経路が画面のチェック UI に閉じており自由入力が無い**こと、および **DES-006 §2.7 の errata（2026-07-26）で `hit_type` について「VAL が守ってくれる前提を置かない・値域は UI と写像で閉じる」と整理した方針と揃う**ため。**値域の正典は DES-003 の本表定義**とする。
2. **REQ-001 への FR 新設**（M19-01 完了報告 §4-6 の積み残し）→ **【裁定】M19 クローズ時に 1 本**（**M19-01/02/03/04** のスコープが確定してから。いま起票すると文言を二度書き直すため）。
