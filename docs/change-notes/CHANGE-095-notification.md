## 1. 変更の概要

**M19-03（CHANGE-087）で作った `combo_setup_results`〔セットプレイ成立条件の検証結果〕を、コンボ一覧の絞り込みから引けるようにする。** 表は作られていたが、**一覧側に消費者が無かった。**

**非スキーマ・非破壊。** 既存のフィルタ群に 3 項目が加わるだけで、**新項目を指定しないときの結果は変更前と一致する。**

**★本 CHANGE の芯は「3 つの状態を混ぜないこと」である。**

| 状態 | 意味 |
|---|---|
| **成立**（`ok`） | 対象セルのいずれかで成立が記録されている |
| **不成立**（`ng`） | 対象セルのいずれかで、**そのセル内に**不成立が記録され、かつ**そのセル内に**成立が無い |
| **未検証**（`unverified`） | セットプレイを 1 つ以上持ち、かつ**未記録のセルが 1 つ以上残っている** |

**★セットプレイを 1 つも持たないコンボは、3 値のどれにも該当しない。** **「問いが成立しない対象（圏外）」と「未検証」を混ぜない**——**`chain_cancel_total` の NULL 2 種（D-137／D-143）と同じ形の予防である。**

## 2. 変更の内容

### 2.1 `DES-002` §4.2（`GET /api/combos`）— クエリ 3 本の追加

| # | 対象 | 変更 |
|---|------|------|
| a | **`setup_result`** | `ok` / `ng` / `unverified`。**値域外は 400**（既存の値不正系のコードに合わせる） |
| b | **`setup_tech_type`** | `OKI_TECH_TYPES` の値域。**値域外は 400**（同上） |
| c | **`setup_in_corner`** | 真偽値。**パース失敗は 400**（既存のパース失敗系のコードに合わせる＝`is_draft` と同型） |
| d | **軸の従属** | **`setup_result` が無いときは軸 2 本を読まない。** 軸だけでは絞り込みにならない |
| e | **既存クエリ** | **不変。** 新項目を指定しないときの結果は変更前と一致する |

> **★400 のコードが 2 系統に割れているのは既存の状態であり、本 CHANGE は踏襲しただけである**（統一していない＝「壊れていないものを直さない」）。**事実として followup `combos-query-error-code-split` に登録した。**

### 2.2 `DES-002` §4.2 ／ `DES-005` §5.4 — ★判定の単位と 3 値の関係（**D-271**）

**開発者裁定（2026-08-09）により、判定の単位は「セル」（`tech_type` × `in_corner` の組）である。** 次の 4 点を明記する。

| # | 内容 |
|---|---|
| **(a)** | **軸の「全て」は、対象セルそれぞれで問うた答えの OR である**（セルを問わず 1 回だけ問う形ではない） |
| **(b)** | **`unverified` は「未記録のセルが 1 つ以上残っている」である**——**「1 セルも記録が無い」ではない** |
| **(c)** | **★3 値は排他ではない。** 画面端では成立し画面中央では不成立のコンボは、**`ok` にも `ng` にも該当する** |
| **(d)** | **★`ng` の「`ok` が 1 つも無い」はセル内に限定される**（コンボ全体ではない） |

**★不変条件は単調性である**——**個別指定の結果 ⊆ 「全て」の結果。** **「3 値の合計＝セットプレイを持つコンボ数」は成立しない**（(c) による）。**軸を両方指定したときの結果は、裁定前と完全に一致する**（対象セルが 1 つに定まるため）。

### 2.3 `DES-003` §3.19 — ★論理削除された `setups` を数えない（**D-270**）

**成立条件の絞り込みは、論理削除された `setups` に紐づく行を数えない。**

**理由**——`setups` の論理削除は `deleted_at` を立てるだけで `combo_setups` の行を消さないため、**`combo_setup_results` の行が残る。** 一方、**画面は `deleted_at IS NULL` で絞って見せている。** 数えると、**「画面上セットプレイが無いコンボが `unverified` に出る」「削除済みセットプレイの `ok` で拾われる」という食い違いが起きる。**

> **★反映先を `DES-005` §5.4 ではなく `DES-003` §3.19 とした理由**——**これは「画面がどう絞り込むか」ではなく「何を検証結果として数えるか」の定義である。** **§3.19 は既に「未検証は行の有無で表現する」という同じ型の規則を持っており、同じ場所に置くのが自然である。** **画面側に置くと、将来べつの面が同じ表を引くときに辿れない。** **`DES-005` §5.4 には参照だけを置く。**

### 2.4 `DES-005` §5.4（コンボ一覧）— フィルタ 3 項目

| # | 対象 | 変更 |
|---|------|------|
| a | **配置** | **既存のフィルタ群の中**（新しい面を作らない）。**native select**（M12-04 の as-built を維持） |
| b | **保持** | **既存の保持機構に相乗り**（新規のブラウザストレージキーを作らない） |
| c | **クリア** | 「フィルタをクリア」で 3 項目とも戻る |
| d | **★軸の無効化** | **成立条件が「全て」のあいだは、受け身種別・画面端の 2 つを `disabled` にする**（効かない指定を作れないようにする）。**挙動そのものは API の規則と同一で、見せ方のみの追加**（開発者裁定 2026-08-09） |
| e | **★軸の値** | **成立条件を「全て」に戻したとき、軸 2 つの値も戻す。** **`disabled` は「操作できない」であって「値が無い」ではない**——**値を残すと、利用者が個別に消せない値が URL とセッションに残る** |
| f | **列カスタマイズ** | **触らない。** 一覧に成立条件の列は追加しない（**本サブは絞り込みだけ**） |
| g | **語彙** | 既存の正典を再利用（`OKI_TECH_TYPE_LABELS` ／「相手が画面端」「画面中央」／`setupResult.state.*`）。**第 3 の語彙を作らない** |

**★「未検証」というラベルは「手つかず」を想起させるが、意味は「埋め残しがある」である**（2.2 (b)）。**文言の再検討は followup `setup-result-unverified-label`——本 CHANGE では変えない。**

## 3. 確定した設計判断（報告への回答）

| 項目 | 判断 | 根拠 |
|------|------|------|
| 軸の「不問」の意味（A / B / C） | **B を採用**（開発者裁定 2026-08-09） | **3 値とも単調増加になり、「全て」が個別指定の和集合になる。** A では `ng` と `unverified` が単調でなく、**「全て」が最も狭い**という直感に反する結果が実データで 2 例観測された |
| 論理削除された `setups` の扱い | **3 述語すべてから除外。正典は `DES-003` §3.19** | **D-270**（2.3） |
| 対象セル数を値域から導出すること | **追認。★導出のままであることをテストで固定すること** | **D-272**。`len()` 導出は「今」の保証であって「将来も導出のまま」の保証ではない。**リテラルへ戻されても、`tech_type` が増えるまで誰も気づかず、壊れるのは絞り込み結果であってコンパイルでも既存テストでもない** |
| 値域外をリポジトリ層で 0 件に倒す | **追認。DES には書かない** | API 層で 400 に落ちるため外から観測できる契約ではない。**「絞り込まない＝全件返却」に倒さなかった判断が正しい**——**typo が全件返却として現れると、絞り込めているかどうかの区別がつかない** |
| 400 のコードの 2 系統 | **踏襲。統一しない** | 「壊れていないものを直さない」。**事実は followup へ登録済み** |
