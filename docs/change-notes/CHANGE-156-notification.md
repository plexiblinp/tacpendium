## 1. `DES-002`（アーキテクチャ）— 1.76.0 → 1.77.0

### 1.1 冒頭注記の失効

**「仮称である」を削除し、「名前は確定した＝`Tacpendium`」へ置き換えた。**

**★★あわせて `combomgr-importer`**（`FR701` の別リポジトリ）**は置換しない旨を明記した**——**本アプリの名前ではない。⇒ 書かないと次の担当が一括置換で巻き添えにする。**

### 1.2 旧名の置換

| 箇所 | 内容 |
|---|---|
| 構成図・シーケンス図 | `combomgr.exe` → **`tacpendium.exe`** |
| ディレクトリ構成 | `combomgr/` ／ `cmd/combomgr/` → **`tacpendium/` ／ `cmd/tacpendium/`** |
| **リリースアーカイブ構成** | `combomgr-windows-amd64.zip` / `combomgr.exe` / `combomgr-macos-arm64.tar.gz` / `combomgr-linux-amd64.tar.gz` → **`tacpendium-*`**（**★Makefile / CI の実物と一致させた**） |
| Cookie | `combomgr_session` → **`tacpendium_session`** |
| データディレクトリ | `%APPDATA%\combomgr\` → **`%APPDATA%\tacpendium\`** |

### 1.3 ★★既定データディレクトリの自動移行を明文化した（新規）

**★名前は 2 段で変わった。ディレクトリだけではない**——**ディレクトリ ／ DB ファイル名 ／ ログ既定 ／ Cookie ／ 環境変数 4 本。**

| # | 明文化した不変条件 |
|---|---|
| **★★1** | **「旧を 1 バイトも動かさない」ではない。正しくは「検証が通るまで、旧ディレクトリの中身は失われない」である。** **★検証より前に旧へ 2 つの書き込みが起きる**——**ロックファイル `.migrating.lock` の作成 ／ `PRAGMA wal_checkpoint(TRUNCATE)` による移行元 DB への書き戻し。⇒ 破壊ではないが、初版の記述は実装より強かった。** |
| **★★2** | **移行の判定は「新 DB ファイルが在り非空か」で行う。「移行先ディレクトリが空でなければ skip」ではない。** **★理由＝`applog.Init` / `migration.Run` / `db.Open` はいずれも書き込み先の親を `MkdirAll` するため、どれかが移行判定より先に走ると「ディレクトリはあるが DB は無い」状態になり、経路が黙って化ける。** |
| **★3** | **検証に失敗してもアプリは旧データディレクトリで起動する。⇒ 止めるのは移行であってアプリではない。★起動を止めるのは「別プロセスが移行中」の 1 件だけである**（2026-09-05 設計卓裁定＝`D-724`）。 |
| **★4** | **`config.toml` は移行の対象ではない**（アプリ実行ディレクトリ直下）**。⇒ やることは中の絶対パスの書き換えだけである**（同裁定）。 |
| **★5** | **`GET /api/config` の `database.path` の契約は不変である**（値は変わるが、キーも型も意味も変えていない）。 |

**★★上記 3 / 4 は、指示書 `M28-01` §2.3-2 / §2.3-4 の逐語に対する解釈である。⇒ 指示書本文は完了済みのため触らず、設計書側へ明文化した**（レポート §2-3 の申し送り）。

### 1.4 ★★§4.2 の経路表へ新設 API 2 本

| メソッド | パス |
|---|---|
| `GET` | `/api/notices/data-migration` |
| `POST` | `/api/notices/data-migration/ack` |

**★契約は経路表へ全行を書いた**（応答フィールド ／ エラー契約 6 行 ／ 母集団の述語 4 通り ／ **持たせなかった分岐 5 件**）。

**★★「持たせなかった分岐」を書いた理由＝読む側が「たぶん出来るはず」と誤読しないためである**。とくに——

- **既読の告知を読み返す手段は API に無い**（`GET` が 204 に化ける）。**⇒ 「もう一度見せて」の要求が来たら経路の新設が要る。**
- **一覧も履歴も無い**（常に 0 件か 1 件。`id` を持たない）。
- **DB を触らない**（マイグレを 1 本も消費していない）。
- **ブラウザストレージを使わない**（既読の状態はサーバ側のファイルが持つ）。

### 1.5 ★★露出の判断（設計卓が明示的に決めた）

**本ルートは `/api` 配下で `mw.Auth` を通るが、`mw.Auth` は `password_enabled = false` のとき素通しであり、それが既定である。`lan` モードなら LAN 内の任意の端末から読め、応答に絶対パスが載る。**

**★★設計卓は載せたままでよいと判断した**（`D-734`）。

| # | 根拠 |
|---|---|
| 1 | **同条件で `GET /api/config` が既に `database.path` を返しており、露出の種類が増えない** |
| 2 | **利用者が「移行前のデータがどこに残っているか」を知らないと、消してよいか判断できない。⇒ パスを落とすと情報の目的そのものが達せられない** |
| 3 | **実質的な利用者は現在 1 人である**（`D-664`） |

**★★ただし公開後に利用者が増えたら判断は変わりうる。⇒ `M26`（公開ゲート）で再検討する**（`followup` `migration-notice-exposes-absolute-paths`）。
