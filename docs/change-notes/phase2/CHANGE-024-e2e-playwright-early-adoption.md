## 1. 変更の概要

E2E テスト(Playwright)の導入時期を「フェーズ3以降」から「**フェーズ2(先行リリース準備)で前倒し・段階導入**」へ改める。

1. **DES-002 §12 テスト方針**(設計書本体・CHANGE 対象):E2E 行の「Playwright(フェーズ3以降)」を「Playwright(フェーズ2 で前倒し導入・段階導入)」へ改訂し、段階導入の範囲(機能回帰を自動化、視覚・LAN 実機は手動継続)を注記する。
2. **SUPP-001 §4.5**(補足資料・自由改訂、DES-002 と整合):「E2Eテスト先送り」を「E2Eテストの段階導入(フェーズ2 前倒し)」へ改訂する。

本 CHANGE は **テスト方針の時期変更**であり、アプリのデータモデル・スキーマ・API・画面仕様は変更しない。

---

## 2. 変更の理由

- 開発者の手動 E2E(実機シナリオ実行)が反復負担=ボトルネックになっており、早期改善の意向がある(phase2-e2e-playwright-handover §6)。
- **M8-RESEARCH-01 の実現性調査**(2026-06-10)で前倒しの妥当性を実数で確認した:
  - 機能回帰フロー(コンボ登録・編集・削除・一覧フィルタ・比較・タグ・セットプレイ紐付け等)は各統合 E2E に**反復再実行**として繰り返し出現する(レポート §5 特記2 = 回帰再実行の重複)。これは自動化の償却が強いことを示す。
  - フェーズ2 は M9〜M12 各々に統合 E2E があり(phase2-overview)、基盤導入後の償却窓が存在する。
  - 先行リリース(知人配布)に向けて回帰安全性が要る。
- DES-002 §12 / SUPP-001 §4.5 の「フェーズ3以降」は 4 フェーズ再設定(CHANGE-020)時に E2E 時期が見直された形跡がなく、新体系で意図どおりの時期を指すか曖昧だった(phase2-e2e-playwright-handover §1)。本 CHANGE で新体系に整合させる。

## 3. 変更の内容

### 3.1 DES-002 §12 テスト方針の改訂(設計書本体)

§12 のテスト方針表 E2E 行を改訂する。

| | 現行(DES-002 v1.11.0) | 改訂後 |
|---|----------------------|--------|
| レベル | E2Eテスト(将来) | E2Eテスト |
| 対象 | 主要ユーザーフロー | 主要ユーザーフロー(機能回帰) |
| ツール | Playwright(フェーズ3以降) | Playwright(フェーズ2 で前倒し導入・段階導入) |

表の直後に次の注記を追加する:

> E2E(Playwright)はフェーズ2(先行リリース準備)で段階導入する(CHANGE-024、M8-RESEARCH-01 の実現性調査に基づく)。基盤導入後、高価値・安定した機能フロー(コンボ登録・編集・削除・一覧フィルタ・比較・タグ・セットプレイ紐付け等)の回帰を自動化する。視覚・レスポンシブ・LAN 実機・操作感 UX の確認は手動 E2E に残す(自動化対象外)。CI は本フェーズでは構築せず、ローカル実行(`pnpm` スクリプト)とする。

### 3.2 SUPP-001 §4.5 の改訂(補足資料・自由改訂)

§4.5 の見出しを「**E2Eテストの段階導入(フェーズ2 前倒し)**」へ改め、決定内容を次に置き換える(旧「E2E導入はフェーズ3以降」を撤回し、DES-002 §12 と整合)。

> **決定内容(CHANGE-024 で更新):**
>
> - フェーズ1 では Playwright 等の E2E フレームワークを導入しなかった(MVP 優先。手段はユニットテスト + 手動動作確認)。【過去事実として保持】
> - **フェーズ2(先行リリース準備)で前倒し・段階導入する**。根拠は M8-RESEARCH-01 の実現性調査(手動 E2E のボトルネック化、機能回帰の頻回再実行=償却、配布前の回帰安全)。
> - **段階導入の手順**: M8 スキーマ確定後〜M9 前に基盤(`@playwright/test` 導入・`playwright.config`・test-id 規約・ローカル実行スクリプト)を入れ、以降は高価値・安定フローのスモーク/回帰 spec を漸進的に拡充する(M9〜M12 の統合 E2E に相乗り)。
> - **テスト手段**: ユニット(Go test / Vitest)+ Playwright(機能回帰の自動化)+ 手動 E2E(視覚・レスポンシブ・LAN 実機・操作感 UX・新機能初回)。
> - CI は本フェーズでは構築せずローカル実行。spec 実装・保守は製造担当 Claude Code へ委任可。

### 3.3 段階導入の方針・スコープ(本 CHANGE で確定する設計判断)

**基盤サブユニットの内容**:

- `@playwright/test` 導入(pnpm)、`playwright.config.ts`(`webServer` で vite=5173 + バックエンド=47318 を起動、または Makefile ターゲット活用)。
- test-id 規約の制定(現状 data-testid は製造コードに 1 件のみ = M8-RESEARCH-01 §2。高価値フローの操作要素へ `data-testid` を付与する小〜中規模リファクタを伴う。shadcn/ui=Radix の暗黙 `role` を `getByRole` で活用し、全要素への testid 付与は行わない)。
- ローカル実行スクリプト(`pnpm e2e` 等)+ Makefile ターゲット。
- 高価値・安定フローのスモーク/回帰 spec を最小本数。素地は `docs/progress/phase1` の統合 E2E 結果スイート(M8-RESEARCH-01 §5 特記1)の**機能サブセット**(視覚・LAN・UX 評価項目を除く)。

**自動化対象外(手動 E2E に継続)**:

- 視覚・レスポンシブ(スマホ 375/390px のレイアウト崩れ等)・LAN 実機・QR・操作感 UX・新機能の初回探索(M8-RESEARCH-01 §3 の困難語の量が裏付け)。

**タイミング**: M8(moves スキーマ確定)後〜M9 前に基盤導入。以降 M9〜M12 の機能追加に合わせて spec を漸進拡充。

## 6. リスク

| リスク | 内容 | 緩和策 |
|--------|------|--------|
| testid retrofit の工数過小評価 | 製造コードの data-testid が 1 件のみ(M8-RESEARCH-01 §2)で、基盤は「小リファクタ」でなく実サブユニット規模 | Radix 暗黙 role を `getByRole` で活用し全要素 testid 化を回避。高価値フローに限定して付与。基盤を独立サブユニット(`M8-02`)として計画 |
| spec の churn | フェーズ2 でも UI 変更(M10 キャラ複数化・M11 custom_states UI)が残り、spec が壊れやすい | 大規模 UI 改修(shadcn/ui 統一・Header 共通化)は M7 完了済みで以降は加算的寄り。spec は安定フローに絞り、保守も製造担当へ委任 |
| 自動化不可領域への過剰期待 | 視覚・LAN・実機は Playwright で代替不可 | §3.3 で手動継続を明示。Playwright は機能回帰の反復を肩代わりするものと位置づけ、手動 E2E を消さない |
| 旧シナリオのポート陳腐化 | 一部旧シナリオが 3000/8080 表記(M8-RESEARCH-01 §5 特記3)、現行は 5173/47318 | spec 化時に現行ポート(vite 5173 / backend 47318)を `playwright.config` で一元管理 |
| CI 不在 | 自動回帰がローカル実行のみで、コミット毎の自動実行が担保されない | 本フェーズはローカル実行モデルを許容(M8-RESEARCH-01 §4.2)。CI 構築はフェーズ3 以降の選択肢として残す |
