## 1. 変更の概要

コンボ登録・編集画面（DES-005 §5.7）の **新規登録モードでキャラクターを変更したときの挙動** を規範として追記する。具体的には、入力済みの内容がある状態でのキャラクター変更時に確認ダイアログを表示し、確定時はフォーム全体を新キャラクターの新規初期状態にリセット、取消時はプルダウンの選択を変更前へ戻す、という挙動を §5.7 に明記する。

## 2. 変更の理由

- M10-01 で ComboEditor のリュウ固定を解消し、§5.7 表示項目2「キャラクター選択プルダウン（新規時のみ、編集時は固定表示）」を実装上も機能させる。フェーズ1 ではキャラが固定で「新規モード中のキャラ変更」という操作自体が存在しなかったため、その挙動が設計書本体に未規定だった。
- code-facts.md（生成 2026-06-18 / commit `ff0620b`）§7-2「API リクエスト/入力 DTO」で、`CreateRequest`（`POST /api/combos` のバインド先）の `steps`（`StepRequest.moveId`）・`starterMoveId`・束ねた `setups`（`BundledSetupRequest.characterId` + `BundledSetupStepRequest.moveId`）が **いずれもキャラクタースコープ**（move ID は当該キャラに属する）であることを確認した。したがってキャラクターを変更すると、変更前に入力したレシピ・始動技・束ねたセットプレイのレシピは引き継げず、無効化が避けられない。
- 無効化＝**利用者の入力データの破棄**を伴うため、無確認の自動クリア（不意の損失）や切替の完全ブロック（過剰な不便）を避け、確認ダイアログで意思確認する挙動を規範化する。
- 破棄範囲は「フォーム全体リセット」を採用する（開発者確定、2026-06-18）。残せるメタデータ（ダメージ・ドライブダメージ・起き攻め・situation 等）は破棄されたレシピに紐づく値で、空のレシピに対し旧キャラの値が残ると陳腐・誤解を招くため、選択的保持より全体リセットが正しさ・単純さの両面で優れると判断した。

## 3. 変更の内容

DES-005 §5.7「コンボ登録・編集」に、以下の節（太字ブロック）を追記する。挿入位置は §5.7 内の「コピーモードの動作」「リアルタイム重複検知」ブロックの直後を想定（表示項目リストの前）。

> **新規モードのキャラクター変更時の挙動（CHANGE-036）**
>
> 新規登録モード（コピー元からの新規登録を含む）では、表示項目2のキャラクター選択プルダウンでキャラクターを変更できる。キャラクターを変更すると、レシピのステップ・始動技・束ねたセットプレイのレシピは選択キャラクターに属する技で構成されるため、変更前の入力内容はそのまま引き継げない。これに伴い以下の挙動とする。
>
> - 入力済みの内容（レシピ・始動技・状況・ダメージ・タグ・メモ・束ねたセットプレイ等のいずれか）がある状態でキャラクターを変更しようとした場合、確認ダイアログを表示する。
>   - 「変更して入力を破棄」を選ぶと、フォーム全体を選択した新キャラクターの新規初期状態にリセットする。
>   - 「キャンセル」を選ぶと、キャラクター変更を取り消し、プルダウンの選択を変更前のキャラクターに戻す（フォーム内容は保持する）。
> - フォームが初期状態（ユーザー入力なし）の場合は、確認なしでキャラクターを切り替える。
> - リアルタイム重複検知（前述）は、変更後の選択キャラクターを基準に行う。
> - 編集モードではキャラクターは固定表示で変更不可（前述「編集保存の動作」および表示項目2）。コピーモードはフォームに内容が投入済みのため、キャラクター変更時は上記の確認ダイアログが表示される。

> 補足（規範ではないが設計意図）: ダイアログのボタンは曖昧な「はい / いいえ」ではなく、破棄を伴う操作であることが伝わる明示ラベル（例「変更して入力を破棄」「キャンセル」）とする。確認ダイアログは既存の確認ダイアログ群（コンボ削除・本登録切替等）の UI パターンを踏襲する。

## 5. 移行影響

- **データ移行**：不要。既存コンボデータ・スキーマに変更なし。
- **後方互換**：フェーズ1 はキャラ固定で「新規モード中のキャラ変更」操作が存在しなかったため、本挙動は純粋な機能追加。既存の保存済みコンボ・編集モードの挙動に影響しない。

## 6. リスク

- **制御コンポーネントの revert 漏れ**：「キャンセル」時にプルダウン表示を変更前へ戻さないと、表示（新キャラ）とフォーム state（旧キャラ）が乖離する。→ M10-01 指示書で「キャラ選択は制御コンポーネント・取消時にコントロールを戻す」を Plan Mode 必須＋実装確認項目として明記する。
- **dirty 判定の取りこぼし／過検出**：判定漏れで無確認破棄、または過検出で過剰プロンプト。→ 「ユーザー入力が何かあれば確認」を基準に、テスト要件でケース化する。
- **コピーモードの初期 dirty**：コピーは投入済み＝初回のキャラ変更で必ずダイアログが出る。意図どおりだが、E2E シナリオで明記して想定外動作と誤認させない。
