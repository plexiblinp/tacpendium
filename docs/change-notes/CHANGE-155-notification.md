## 0. なぜ急いだか

**★★`DES-003` と `DES-005` の現行記述が、実装と真っ向から食い違う状態になっていた。**

**`drive_damage` の符号の意味を反転した**（`M27-03`）**ため、設計書が「回復で負値」と書いている一方、実装は「削りで負値」で動いている。**⇒ この状態で誰かが設計書を読むと、**既に入っているデータの意味を取り違える。**

**★受領と同じ手番で反映した。**

## 1. `DES-003`（データモデル）— `drive_damage` 列

**「回復で負値」→「★負が削り／正が回復」。**

| # | 内容 |
|---|---|
| **★★1** | **開発者の指示（2026-09-05）＝「マイナスの方を削り、プラスの方を回復に」。** |
| **★★2** | **★これは表示だけの変更ではない。** 着手前の意味は設計書どおり「正 ＝ 削り／負 ＝ 回復」であり、**既存の行はその規則で入力されている。⇒ 語だけ入れ替えると、既に入っている値の実世界の意味が黙って反転する。** |
| **★★3** | **⇒ 既存データをマイグレ `000103_flip_drive_damage_sign` で移行した**（`UPDATE combos SET drive_damage = -drive_damage WHERE drive_damage IS NOT NULL`）**。★down は up と同一である**（符号反転は自己逆元）**。★論理削除行も含める**——**除くとゴミ箱から復元したときだけ古い意味の値が混ざる。** |
| **4** | **値域 `-6〜6` は不変**（`VAL-C13`。**★対称なので反転しても範囲外にならない**）**。★`DuplicateCheckFields` にも `recipe_hash` にも入っていないため派生値の再計算は不要**（製造が実装で確認済み）。 |

## 2. `DES-002`（アーキテクチャ）— §4.2 の `GET /api/combos`

**`starter_move_id` を追記した**（省略可・正の整数のみ）。**★応答形は 1 バイトも変えていない。**

**★★「持たせなかった分岐」も書いた**——**(1) 404 は無い**（実在しない `move_id` でも 200 ＋ 空一覧）**／ (2) カンマ区切りの複数値は受けない**（リポジトリ層は `IN` 句で表現できるが HTTP の受け口は単一値だけ。画面の絞り込みが単一選択のため）**／ (3) キャラとの整合は検証しない**（別キャラの id でも 400 にはならず 0 件）。

**★書いた理由＝読む側が「たぶん出来るはず」と誤読しないためである。**

**★エラーコードが 2 系統に割れているのは既存の状態であり、本軸は 3 つ目を持ち込んでいない**（`character_id` ＝ `invalid_query` ／ `setup_result` ＝ `invalid_query_param` の各前例へ合わせた）。**★`starter_move_id` は 2 系統の両方を使う最初の軸である**（`followup` `combos-query-error-code-split` の統一時の対象として記録）。
