## 2. 反映の中身

**★§4.4 の旧記述は 3 文とも as-built と食い違っていた**——「CORS を適切に設定する」（内容が無い）／「Origin は同一ホストのみ許可する」（**両方向にずれ**）／「補助対策として `X-Requested-With` を要求する」（**サーバ側の検証が 0 件**）。

### 2.1 CORS の as-built

**許可 Origin は起動時に 1 回だけ構築し、リクエストのたびに NIC を再列挙しない。** `local` は 2 本、`lan` は 3 本。**完全一致・ワイルドカード不使用・実ポートに追従。**

**★`lan` で代表 LAN IP が見つからないと起動を中止する**ことも書いた。**⇒ 私用アドレス（RFC1918）を持たない環境では、代表 LAN IP を要する機能が実測できない**（followup `cloud-env-cannot-start-lan-mode`。**`M22-06` の QR がこれに当たる**）。

**★許可ヘッダの一覧は「正本ではない」と書いた**（as-built §1-4）——**`Access-Control-Request-Headers` が来ればそれを逐語エコーするため、既定の一覧は ACRH 空時のフォールバックにすぎない。** **実際その一覧は、撤回した `X-Requested-With` を挙げる一方、フロントが実際に送っている `X-User-Id` を挙げていない。** **⇒ そのまま転記すると誤った as-built を設計書へ複製することになるため、転記せず読み方を書いた。**

**★OPTIONS が 204 で早期 return し後続を呼ばないこと**、**それが「入場ゲート有効時にプリフライトが 401 にならない」理由であること**を書いた。**⇒ ミドルウェアの順序が守っている性質であり、順序を変えると壊れる。**

### 2.2 ★許可外 Origin を拒否しないのは意図である（**本反映で最も重い項目**）

**as-built §1-2。** **許可外 Origin の要求は CORS 応答ヘッダを付けないだけで処理される。止めているのはブラウザである。**

**★これを「実装漏れ」と読んで締めると 2 つ壊れる。**

| # | 壊れるもの |
|---|---|
| 1 | **`curl` 相当の復旧経路**（§8.2 の歯止め b） |
| 2 | **★Vite dev proxy 経由の開発と E2E**——**dev サーバが `changeOrigin: false` でクライアントの `Origin` を逐語転送するため、backend には dev / E2E の Vite ポートの Origin が届く。** **許可リストはそれを生成しない。** **⇒ いま開発と E2E が動いているのは、この「通す」実装のおかげである** |

**★2 は設計卓が指示書を書いた時点で見えていなかった。** 製造が `vite.config.ts` の `changeOrigin` と `buildAllowedOrigins` を突き合わせて初めて分かったものである。**⇒ 「締めなかった」の根拠が思想ではなく実測になった。**

### 2.3 主経路はクロスオリジンではない ／ 境界はバインドが守っている

**4 経路（本番・dev・E2E・スマートフォン）すべてが同一オリジンである。** **⇒ `AllowCredentials` / `Vary` / `Max-Age` は実運用では評価されない経路にある。**

**★指示書 §4.1-3 が懸念した「LAN IP は 1 つとは限らない」は実害を持たない**——**副 NIC・mDNS 名・ポート転送のいずれで開いても、その端末から見れば同一オリジンだからである。**

**ミドルウェアの構成は `local` / `lan` で同一**であり、**モードが変えるのは許可 Origin が 2 本か 3 本かだけ**。**⇒ 外から届かないようにしているのはバインドアドレスである。**

### 2.4 CSRF 対策 — **撤回の記録**（通知書 §4.2 の要求）

**★「未実装」ではなく「要らないと判断した」と書き、理由を 3 点併記した**（`SameSite` で目的達成 ／ **2 つの層が独立していない** ／ `curl` の経路が消える）。

**★あわせて「この判断を覆すときは 3 点をそのまま反証すること。『設計書に書いてあるのに実装されていない』という読み方で掛けに行かないこと」を書いた。** **followup `csrf-design-vs-implementation-gap` が同じ形で 2 年近く残っていたためである。**

**`Secure` を付けない理由**（平文 HTTP）も同じ節に置いた。

## 3. ★§2-1 の裁定 — **受理した（案 (a)）**

**製造の申告**——`DES-002` §4.4 の明文「Origin は同一ホスト（サーバー自身の IP:PORT）のみ許可する」と as-built が**両方向で**食い違う（`localhost` という名前も許可する点で広く、複数 NIC のうち代表 1 本しか許可しない点で狭い）。**製造は as-built 維持を選んだ。**

**★受理する**（**D-425**）。理由——

| # | 理由 |
|---|---|
| 1 | **主経路がクロスオリジンでない以上、許可リストの内容は主経路の可否を左右しない**（§2.3）。**⇒ 厳格化しても得るものが無い** |
| 2 | **`localhost` を外すと、自機のブラウザから使えなくなる。** **⇒ 実害だけが出る** |
| 3 | **「代表 1 本しか許可しない」も同様に実害を持たない**——**副 NIC から開いてもその端末から見れば同一オリジンである** |
| 4 | **指示書 §9.2-3 が「迷ったら塞がない側」を定めており、判断は裁量の範囲内である** |

**★製造が §3 ではなく §2 に置いた判断は正しい。** **「裁量である」ことは「設計書の明文が失効していてよい」ことを意味しない。** **⇒ 明文を as-built へ書き直すのは設計卓の手番であり、本反映で行った。**
