## 1. ★★なぜ畳むか

**★同書は「プロジェクト全体の `data-testid` を一元管理する。新規付与時は必ずこの一覧を更新すること」と宣言している。**

| 実測 | 値 |
|---|---|
| `web/src` の `data-testid` 出現数 | **430 件** |
| 同書「付与済み一覧」の表の行数 | **21 行** |

**★★一覧はもはや一元管理として機能していない。⇒ 現用中の spec が掴む `combo-editor-damage` / `combo-editor-knockdown-advantage` / `combo-editor-drive-damage` / `export-open-button` / `game-update-banner` 等が軒並み未登録である。**

**★製造の実査でも同型が出た**（`M30-01` §4-4）**＝同一覧には既存の `recipe-tab-*` / `recipe-direct-*` / `recipe-dir-*` も載っていない**（`grep "recipe-"` は 3 行のみ）**。**

### 1.1 ★★最も害があるのは、宣言のほうである

**★★「一覧に無い＝未付与」と読める状態を放置するのが最も害が大きい。⇒ 実際、この宣言を信じて読むと誤る状態が今ある。**

### 1.2 ★★なぜ (a)「一覧を実態へ追随させる」を採らないか

| # | 理由 |
|---|---|
| **★★1** | **人手で維持する運用は既に 1 度破綻している。⇒ 430 対 21 まで開いた。★同じ運用を再宣言しても、同じ結果になる。** |
| **★★2** | **機械検査で維持するなら、結局 `grep` して表を再生成する形になる。⇒ それは一覧ではなく派生資料であり、`generate-*.sh` の型の話になる。★`docs/design/` に置く物ではない。** |
| **★3** | **同書は自分が挙げたギャップの解消にも気づいていない**（§3）**。⇒ 一覧だけでなく、記録全体が更新されない構造である。** |

**★★一般形＝「一元管理する」と宣言した一覧は、機械検査を伴わないと必ず腐る。⇒ 乗せられないなら、一覧をやめて規約だけ残すほうが正直である。**

## 2. 反映内容 (1) — 「付与済み一覧」を「実例集」へ改める

**★★表そのものは消さない。⇒ 消すと、`M29-01` が書いた「同じ testid を面ごとに分けるかは『同時に画面へ出うるか』で決まる」という判断の実例まで失われる。**

**★変えるのは位置づけである。**

| | 旧 | 新 |
|---|---|---|
| 節の名 | **付与済み一覧** | **★★付与の実例**（**判断の根拠が残っているものだけ**） |
| 宣言 | 「プロジェクト全体の `data-testid` を一元管理する。新規付与時は必ずこの一覧を更新すること」 | **★★「本表は全数ではない。⇒ 一元管理は行わない」** |
| 更新義務 | **必ず更新する** | **★★無い。⇒ 「判断が要った付与」だけを後から足す** |

**★★全数が要るときの手段を明記する＝`grep -rn "data-testid" web/src --include='*.tsx'`。⇒ 実装が正本である。**

## 3. 反映内容 (2) — 解消済みのギャップを消す

**★同書は「数値メタデータ入力（ダメージ / ドライブゲージ / …）に testid 無し → 数値項目を spec で直接操作できない」をギャップとして記録し、解消方法として「`combo-editor-{field}` を最小付与してこの一覧へ登録する」を挙げている。**

**★★その解消方法は既に実施済みである。⇒ `web/src/features/combo/components/ComboEditorBasicFields.tsx:372` / `:535` / `:603` に `combo-editor-damage` / `combo-editor-drive-damage` / `combo-editor-knockdown-advantage` が実装され、E2E の `fillRequiredComboFields`**（`web/e2e/support/editor-input.ts:51-57`）**が実際に使っている。**

**⇒ 解消済みのギャップが未解消として残り、一覧への登録だけが漏れていた。★行を消し、経緯だけを 1 行残す。**
