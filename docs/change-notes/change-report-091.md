## 2. 修正概要

- **`moves` に新列 3 本を定義した。** いずれも**ゲームの事実を記録する列**であり、特定機能の判断結果ではない（`M19-DESIGN-07` §7 の列追加審査規約）。
  - **`startup_basis`**：格納されている `startup` の**由来**（単独値／通し値／不明）。**この区別が列に無かったことが、フレーム計算が連打キャンセルを考慮できず「物理的に入力できないレシピ」を提案していた原因**である（弱P 2 発の実機 22F を 26F として計算）。**`unknown` を暗黙に単発扱いしない**三値である旨を明記した。
  - **`chain_cancel_total`**：連打キャンセル時の**実消費フレーム**。**非 NULL であること自体がチェーングループ員であることを兼ねる**（別フラグを作らない）。**値は技ごとの実測であり `total` から導出できない**——「一律 `total − 4`」は反証済みで、**同一の単発値が最大 3 通りに割れ、キャラ間だけでなくキャラ内でも割れる**。**規則で埋めることを禁止する旨を本文に残した。**
  - **`fastest_unreachable`**：**単独最速入力で地上の相手に当てられない**技。**「最速では」がこの事実の核**であり恒常的性質と読ませない旨を残した（命名の選定理由）。機械付与が**部分一致**である旨も残した——**前方一致では `neutral_jumping_heavy_kick` を取り落とす**（M18-03c で同じ 2 行の取り落としを是正した経緯がある）。
- **`move_derivations` を §3.20 として新設した。** **列 1 本でなく関連テーブルにした理由**（1 技が複数の親を持ち得る）、**FK 強制に依存しない実装**、**FK 親の段数**（親は `moves`＝1 段なので `combo_punishes` の流儀でよく、`combo_setup_results` の流儀を流用してはならない）、**明示削除の責務**（seed 再生成波で `moves.id` が再発番されると残存行が別の技を指し、**削除エラーにならず静かに壊れる**）を明記した。
- **★`move_derivations` の行数が固定ではないことを本文に明記した。** 親参照は `startup_basis` の人手付与と**同一パスで付与される**設計であるため、**人手付与が進むほど増える**。**「テーブル全体の行数を固定するテストを書いてはならない」**を DES 側に残した（ボード D-139）。
- **`is_derived` / `is_aerial` の説明文言を是正した。値とロジックには一切触れていない**（契約 F-5）。`is_derived` には「単独入力の可否を担う手段が `startup_basis` ＋ 親参照として用意された」旨を、`is_aerial` には「**『空中で出る技か』は表すが『単独最速で地上に当てられるか』は表さない**（後者は `fastest_unreachable`）」旨を追記した。**2 つの軸が同じ列で兼ねられていたために M19 側で誤読が生じた**という経緯が、列を分けた根拠である。
- **`moves` へ手書き INSERT する操作は `preset_aliases`（`official_ja_move`）の対投入を伴う**ことを §3.3 に明文化した。**`moves` に `name_ja` 列は無く、alias を入れないと画面に生の `move_code` が出る。** **この規約は従来 seed 波の指示書と生成マイグレのコメントにしか無く、手書き INSERT を指示した M19-04 §4.6 では落ちていた**（製造が実装時に検出して対投入した）。

## 4. 整合性チェック結果

- **節番号の採番**：`move_derivations` は **§3.20（末尾採番）**とした。**§3.14 は `move_commands` で使用済み**であり、途中へ挿入すると **§3.15〜§3.19 が繰り下がり、CHANGE-078〜090 の反映先指定が一斉に外れる**（§3.19 `combo_setup_results` の採番で同じ判断をしている＝ボード D-35）。**適用前に `^### 3\.` の全数 grep で末尾が §3.19 であることを確認する**手順をパッチに含めた。
- **FK 親の段数の一貫性**：§3.19 が「本表の親は `combo_setups`（1 段深い）であり `combo_punishes` の流儀では誤る」と注記している。**§3.20 はその逆側**——**親が `moves`（1 段）なので `combo_punishes` の流儀でよい**。**両方向を書いたことで、後続が段数を確認せずに流儀を選ぶ経路を塞いだ。**
- **★「静かに壊れる」経路を 3 つ本文に残した**：(1) **rush 生成経路に `startup_basis = 'through'` を明示しないと、backfill 後に生成される rush 行だけが `unknown` のまま残る**（型エラーにも実行時エラーにもならない）(2) **`move_derivations` の明示削除を怠ると、seed 再生成波で残存行が別の技を指す**（削除エラーにならない）(3) **`chain_cancel_total` の転記マイグレ（000052）を INSERT（000051）より前に置くと、連打版 3 行が 0 件更新になる**（エラーにならない）。**いずれも設計書に書かないと再現できない**。
- **件数の母数を基準時点つきで書いた**：`startup_basis` の人手 **160 行**・`fastest_unreachable` の B 型 **7 行**（いずれも基準時点 2026-08-02）。**DESIGN-07 §4-1 の「約 148 行」・§4-3 の「数件〜十数件」は古い**（ボード D-141）。**外から増える母数は基準時点を併記する**（E-16／E-18／E-24）。
