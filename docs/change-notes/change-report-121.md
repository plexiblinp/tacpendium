### 2.2 `DES-003` §5——90 日保持の撤回

物理削除のタイミングを **「ユーザーがゴミ箱から明示的に完全削除した場合」の 1 つだけ**にし、**保持は無期限**であることを明記した（**D-458**）。

**★撤回の経緯を引用ブロックで残した。** 同じ記述を将来もう一度書かないためである——**同機構は一度も実装されていない。** 90 日という数字は画面側の表示にだけ存在し、サーバ側に削除する経路は無かった。**「（設定で変更可能）」という設定項目も存在しなかった。**

**あわせて `architecture-patterns` §11 の内容を 1 段落として本節へ入れた**（論理削除された親の子は物理的に残り、復元は親の `deleted_at` を戻すだけで足りる）。**正典側だけを読む人がいる前提で書いた。**

### 2.3 `DES-005` §5.15——残日数の撤回と、旧行の非表示

**表示項目 1 から「自動完全削除までの残日数」を落とした。** 引用ブロックで 4 点を足した。

| # | 書いたこと |
|---|---|
| 1 | **撤回は設計書だけでなく画面からも行った**——**「表示だけが在り、機構が無い」状態だった。** 設計書だけを直すと嘘が画面に残る。**8 列 → 7 列** |

| 3 | **`PUT` が積む旧行を既定の一覧に出さない** ＋ **述語を足したのはゴミ箱の分岐だけである** ＋ **一覧・件数・一括操作の 3 つが同じ集合に揃っている** |
| 4 | **既知の制約 3 件**——**旧行への導線を持たない（意図である）** ／ **マイグレ適用前の旧行は隠れない（非対称）** ／ **後継の完全削除で見え方が接続依存に割れる（データは壊れない）** |

### 2.4 ★`DES-005` §5.15——本節が列構成を定義していない旨を記録した

**開発者の実機確認で 3 件が挙がったが、判定の基準が存在しなかった**——**同節の表示項目は 2 行だけであり、実装が持つ「ルート」「タグ」といった列は本節に根拠が無い。**

**⇒ 「列構成を定義していない」ことを明記し、3 件を事実として記録した**（列定義を起こすのは `M23-06` の担当）。

| # | 事象 | 性質 |
|---|---|---|
| (a) | **ルート列が常に空** | **★消す側の候補。** 論理削除の時点で `recipe_cache` が NULL になるため、**削除済み行に出せるレシピは構造的に存在しない。** **残日数と同じ「存在しない概念の列」である** |
| (b) | **タグ列が常に `-`** | **★出す側。** データは応答に届いており、描画していないだけである |

### 2.5 `DES-002` §4.2——ゴミ箱系 4 経路の as-built

**4 本とも実在するのに、経路表に 1 本も載っていなかった**（2026-08-20 に設計卓が実査）。**仕様変更ではなく、経路表が実態に追いついていなかった分の是正である。**

| 経路 | ★落としやすい点 |
|---|---|
| `PUT /api/combos/{id}` | **`201 Created` で新しい id を返す**（`200` ではない） |
| `POST /api/combos/{id}/restore` | **楽観排他を持たない** ／ **削除済みでない行にも `404` を返す** |
| `DELETE /api/combos/{id}/permanent` | **`204`** ／ **ゴミ箱に無い行へは `409`** ／ **CASCADE に委ねず 2 表を明示削除する** |

## 3. ★as-built で確定し、起票時の記述を上書きした 3 件

**通知書 §8 が正本である。** 反映では以下を優先した。

### 3.1 印の書き込みは 2 文である

指示書は「1 文でも 2 文でもよい」としていたが、**実装では 1 文にできない。** `PUT` は旧行の論理削除（楽観排他チェックを兼ねる 1 文）を先に実行し、**その時点では新行 id が存在しない。** **⇒ 新行 id が確定したあとの 2 文目として書く。** **同一トランザクション内であり、新行の作成が失敗すれば巻き戻る。**

**★順序（論理削除 → INSERT → 印の書き込み）は実装の制約であり、選択ではない。**

### 3.2 見え方は接続で割れる（データは壊れない）

**設計卓の暫定「現れてよい」は、FK が有効な接続の系と一致した。**

| 系 | 実測 | ゴミ箱での見え方 |
|---|---|---|
| **FK 有効** | `ON DELETE SET NULL` が**発火する** | **旧行が再び現れる** |
| **FK 無効** | **連鎖しない**。指す先を失った id が残る | **隠れたまま** |

**★どちらの系でもデータは壊れない**——旧行は物理削除されず `FR601` の対象として残る。**割れるのは見え方だけである。** **⇒ `P-04` の実測された症例として followup §V へ登録した。**

### 3.3 応答には出るが、どの画面も読まない

**製造は DTO へ出す側を採った**（指示書が委ねた判断）。**理由＝バックエンドが返さない値をフロント型が持つと、型が実態と食い違う**——本サブが畳もうとしている食い違いと同じ型の負債になるため。

**★本番コードで本列を読むのは、ゴミ箱の絞り込みの述語 1 か所だけである。** **⇒ `DES-003` §3.4 へ「使われていない＝消してよい」と読まないよう明記した。**

## 6. ★教訓（`retrospective-log` へのバッチ反映は設計担当が行う）

1. **同じ数字の写し先が複数あるとき、片方だけ直った状態は「緑に見える」。** ボード §2.1 は `000079` へ直っていたが §2.2 は `000078` のままだった。**⇒ 数字を写している箇所は、直した側からではなく `grep` で全数を拾って確認する。**
2. **撤回の射程は、本番コードだけを見ていると足りない。** `DES-003` §5 の残骸は**設計文書の走査でしか見つからない**。**⇒ 撤回を含む CHANGE では、起票時に「同じ仕様を書いている節」を設計文書側で先に数える。**
3. **「表示項目」だけを定めて「その値を誰が保証するか」を定めない画面設計書は、実装されない機能の告知を生む。** 残日数がその実例であり、**ルート列（常に空）も同じ構造で生まれている。** **⇒ 画面設計書に値の表示を書くときは、供給元を併記する。**
4. **「無いこと」の確認は、あったときと同じ強さで報告する。** i18n キーの撤去は「対象が無い」で終わったが、**それは撤去漏れではなく「そもそも i18n 化されていない」という別の事実**であり、次の担当への入力になる。
