## 2. 告知の経路 2 本 ＋ `games.current_data_version` の初の露出（**★未実装**）

| 経路 | 内容 |
|---|---|
| **`GET /api/notices/game-update`** | **`{currentDataVersion, affectedCount, postponedForVersion?}` を常に 200 で返す** |
| **`POST /api/notices/game-update/postpone`** | **要求本文を取らない。** サーバが `games.current_data_version` を読んで書く |

### 2.1 ★★204 の作法から意図して外れている

**指示書 §0.4 の逐語「流用できるのはバナーの形と 204 で『無い』を表す作法までである」は上限の宣言であって「必ず流用しろ」ではない。**

**★★しかも本経路が返すのは「有無」ではなく件数と現在版であり、204 では表現できない。**

**★一覧のボタンは延期中でも件数が要る。⇒ 告知の有無と件数を同じ 1 本から取ることで、出どころを 1 つに保つ。**

### 2.2 ★★代替は原理的に不可能である（**検討を打ち切ってよい**）

**`GET /api/combos?affected_by_game_update=true&limit=1` の `count` では総数が取れない**——**ハンドラが `Count: len(items)`（そのページの件数）であり、リポジトリが `limit <= 0 → 100` / `limit > 1000 → 1000` に丸める。**

**⇒ 判定式を共有した `COUNT` の新設が要る。★式を書き写さないこと**（現行リポジトリは `LIMIT` 付きの `SELECT` しか持たない）。

### 2.3 延期の保存先＝サーバ側のファイル

**`filepath.Dir(dbPath)` 直下**（移行告知 `.migration-notice.json` と同じ場所）**へ `.game-update-notice.json` を置き、`{"postponedForVersion": ..., "at": ...}` を持つ。⇒ `games.current_data_version` と一致する間だけバナーを抑止する。**

**★★決め手＝コンボは利用者ごとの所有物ではない**——**`combos` に `user_id` が無く、所有者を持つのは `tags` だけである**（サービス層の `UserID` にも「誰として保存するか。コンボ本体の所有者ではない」とコメントが在る）**。⇒ 影響コンボの集合はアプリ全体で 1 つであり、その告知の延期もアプリ全体が素直である。**

**★★LAN で 1 人の延期が全員に効くことを許容する。ただし条件が 1 つある**——**延期が抑止するのはバナーだけであり、一覧のボタンは抑止しない。**

> **★★ここが分水嶺である。⇒ ボタンまで消す設計にすると LAN では許容できない**（他の利用者が入口を失う）**。★この 1 行を消さないこと。**

### 2.4 その他の設計判断

| # | 内容 |
|---|---|
| 1 | **語を `/ack` ではなく `/postpone` にした**（「永久に既読」と「次の版まで延期」は意味が違う） |
| 2 | **`postpone` が本文を取らないのは、`acknowledge-version` が「版数をクライアントから受けない」を明示的に選んだのと同型にするため** |
| 3 | **1 本にまとめる代償＝落ちると告知とボタンが同時に失敗表示になる。★許容する**（再試行 UI が 1 か所で済む利点の裏側） |
| 4 | **マイグレもブラウザストレージ台帳も消費しない**（DB 列案・localStorage 案を落とした結果） |

## 4. ★★告知のマウント先はホーム画面 ＋ コンボ一覧の 2 か所

### 4.1 実査で出た事実

**`App.tsx` が `if (location.pathname === "/" && !isMobile) return <Navigate to="/combos" replace />` であり、`useIsMobile` の閾値は `(max-width: 639px)`。**

**⇒ ★★640px 以上では `HomePage` が一度も描画されない。**

**★そして既存の移行告知バナーの唯一のマウント先は `HomePage` である。**

**⇒ 「移行告知と同型」を素直に採ると、指示書が「これが主動線である」と書いた経路が PC で丸ごと消える。**

### 4.2 採った案

| 案 | 判定 |
|---|---|
| (i) `AppRouter` の外（全画面） | **採らない。**「しょっちゅう使う機能ではない」に対してうるさすぎる |
| **(ii) `HomePage` ＋ `ComboListPage`** | **★★採る。** PC の実質的な入口は `/combos` である（上のリダイレクト先そのもの） |
| (iii) `ComboListPage` だけ | **採らない。** 一覧を開かないと告知が来ない。**`M28-01` の告知が解こうとした「開かなければ誰にも伝わらない」が再発する** |

**★★バナーとボタンは同時に出す**（PC で `/combos` を開いた既定の状態＝利用者が最も長く見る状態）**。⇒ 「バナーが出ている間はボタンを隠す」は採らない**——**延期した瞬間にボタンが現れる形になり「消したのに別のものが出てきた」と読まれる。**
