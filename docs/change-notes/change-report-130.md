## 2. 修正概要

### 2.1 `DES-005` §4.3.1 を新設——**対象キャラの解決順（5 段）**

**通知書 §2.1 のとおり 5 段を書いた。** **段 3a（`users.main_character_id`）は as-built 注記で「未実装」と併記した**（先例＝§5.16 の as-built 表・`CHANGE-117`）。

**★★実装が決めた線を 2 つ、設計書へ書いた。どちらも指示書には無い。**

| # | 線 | なぜ書くか |
|---|---|---|
| **1** | **実在検査を掛けるのは段 3 系だけである** | 段 1・段 2 に掛けると `?character=` の既存挙動（正の整数なら採用）が変わり、**既存の遷移を壊す**。**書かないと次の担当が「全段に掛けるのが自然だ」と読む** |
| **2** | **キャラ一覧が未取得のあいだは検査をスキップして採用する** | **★検査できないことを「不在」と読むと、取得前に段 4 へ落ちて表示が飛ぶ。** これは実装の都合ではなく**利用者に見える挙動**であり、設計書に属する |

### 2.2 ★★`DES-005` §4.3.1——**「既定を書き換えたら段 2 の記憶を捨てる」を対で書いた**

**★これは 2026-08-25 の開発者の実機確認で見つかった穴である。順序を決めただけでは足りなかった。**

**再現**: ①初回起動 → ②ウィザードでキャラ選択 → ③一覧で対象キャラを変える → ④`config.toml` を消す → ⑤再起動 → ⑥ウィザードで**③とは違う**キャラを選ぶ → ⑦一覧を開く → ⑧**⑥の既定ではなく③のキャラが出る。**

**機序**: 既定キャラを**書く**経路は 2 つ（ウィザード ／ 設定画面）で、**どちらもセッション記憶を触っていなかった。** **段 2 は段 3b より優先されるため、段 2 が残る限り新しい既定は表に出ない。** ウィザードの完了は SPA 遷移で同じタブのため `sessionStorage` が生き残る。

**★★`config.toml` を消したときだけの話ではない。設定画面から既定キャラを変えたときも同じであり、実運用で普通に通る導線である。** 利用者には「設定を変えたのに効かない」と見える。

**★段 3b を段 2 より優先させる案は採らない**——`SM-044`（一覧でキャラを選んで詳細へ行って戻ったら維持される）が壊れる。**開発者裁定は「両方（ウィザード・設定）でセッションを捨てる」。**

**★捨てるのはキャラだけ**（タグ・仮登録・ソート・セットプレイ関連は残す）。**解決順そのものは変えない。**

### 2.3 `DES-005` §5.4——**ヘッダ帯の構成と「セットプレイ数」列**

**キャラ選択をフィルタ欄からヘッダ帯へ移した**（§3.1 の裁定 1 の帰結）。**キャラ名の大見出しは撤去した**（プルダウンが同じ名前を出しており重複していたため）。

**★兼務を書いた補足文を添える**——「一覧の絞り込みと、新規登録の対象を兼ねます」。**★兼ねている事実そのものは消さない**（消すと `SM-044` と正面衝突する）。

**★移した狙いは 2 つある**——**兼務が読み取れること** ／ **キャラが増えたときプルダウン以外の選択方法へ変えられる余白を確保すること**（2026-08-25 開発者判断）。**後者は設計書に書かないと失われる意図である。**

**「セットプレイ数」列**——列カスタマイズ対象・既定は表示・**0 件も `0` と出す**（空欄だと「未取得」と区別できない）・**★マイコンボにも出る**（列カスタマイズの仕組みを共有しているため。**意図した挙動である**）。

### 2.4 `DES-005` §5.7——**保存後の遷移先の表を新設**

**新規登録のみ一覧へ**（`/combos?character_id=<保存したコンボのキャラ>`）。**編集・コピー・確定反撃サーチ復帰は不変。**

**★対象キャラは URL クエリ（段 1）で渡す。セッション記憶（段 2）に頼らない**——一覧は URL が空のときにしか記憶から復元しないため。

**★コピーを含めなかったのは開発者判断である**（逐語＝**「現状のまま（詳細画面）」**）。**コピーは元から値が入っている分、入力ミスに気づきにくい。まず 1 件を詳細で確かめられるようにする。**

**★あわせて 1 条**——**保存後の警告ダイアログの「移動先の呼び名」は実際の遷移先から導く。** 固定文言にすると、遷移先を変えたときに「詳細へ移動」と言いながら一覧へ飛ぶ状態になる（§3.1 の裁定 2）。

### 2.5 ★★`INITIAL_CHARACTER_ID` の旧定義を 3 か所是正した

**同定数は §4.3.1 の最終フォールバックであって「デフォルト表示キャラ」ではない。**

| 箇所 | 旧 |
|---|---|
| **§4.3 の部品表（キャラクター選択プルダウン）** | 「既定はデフォルト表示キャラ」 |
| **§5.7 新規モードの既定キャラクター** | 「従来どおりデフォルト表示キャラ（`INITIAL_CHARACTER_ID`）」 |
| **§5.9 コンボ追加モーダルの既定キャラクター** | 「比較リストが空の場合はデフォルト表示キャラ `INITIAL_CHARACTER_ID`」 |

**★★この 3 か所こそが `SM-041`「配線が漏れている」の正体である。** **設計書が最終フォールバック定数を「デフォルト表示キャラ」と呼んでいたため、実装がそのとおりに書いても誰も誤りと気づけなかった。**

## 3. 裁定

### 3.1 ★★裁定 1——**`SM-119` の解き方の変更を受理する。`CHANGE-130:78` は失効した**

**指示書 §4.1-4 と `CHANGE-130:78` は「新規登録画面の側に『このコンボのキャラ』を明示する入力を置く」形を指定していた。** **実装は一覧画面のヘッダ帯へキャラ選択を移した。**

**⇒ 受理する。★製造の独断ではない。** 実装後に開発者が対象画面の思い違いを訂正し、形も指示した（§2.3 の逐語）。

**★★誤っていたのは設計卓の読みである**——**`SM-119` の memo 原文から「新規登録画面の話」と読んだが、開発者の意図は一覧画面だった。** **⇒ `CHANGE-130:78` に失効の取り消し線と、採った形への差し替えを書いた。**

**★計測点は立てない。** **memo の一行から書き手の意図を復元することは、設計卓の実査で潰せる誤りではない**（`M24-RESEARCH-01` の ledger にも原文しか無い）。**⇒ 型としては「memo 由来の項目は、対象画面まで開発者に確認する」であり、`M24-02` 以降の起票へ効かせる**（§5）。

### 3.2 ★裁定 2——**保存後ダイアログの文面の是正を受理する**

**指示書 §2.2 の変更対象一覧に無いが、同節は「失効した記述の是正は妨げない」としている。** **`SM-084` で遷移先が一覧になったため、「詳細へ移動」と言いながら一覧へ飛ぶ状態が生まれていた。**

**⇒ 受理する。** **★これは `E-254`（目的を書いたら、その手段で目的が達成できるかを書いた本人が確かめる）の実演である**——**遷移先を変えるサブは、遷移先を名乗る文面も同時に動かす。** **⇒ `DES-005` §5.7 へ 1 条として書いた**（§2.4）。

**★i18n を通していないのは正しい。** 周囲のダイアログ文面が元から素の日本語であり、**1 語だけ通すと同じダイアログ内で 2 系統が混在する。** **⇒ ダイアログごと `M24-07` で移すのが正しい単位である。**

### 3.3 ★★裁定 3——**`web/e2e/support/` を運用の型として認める**

**`SM-084` が 12 か所 / 10 spec の「保存後 URL」に波及し、作成された combo id を応答から取る必要が生じた**（「一覧の一番新しい行」は使えない＝`E-232`）。**製造は同じ 3 行を 10 ファイルへ複製せず、`web/e2e/support/new-combo.ts` を 1 本置いた。**

**⇒ 認める。理由 4 つ。**

1. **複製すると、その 3 行が持つ理由（並行実行を避ける）がコメントごと 10 か所へ散る。** **次に 1 か所だけ直されても誰も気づけない。**
2. **playwright の既定 `testMatch` は `*.spec.ts` / `*.test.ts` のみであり、`support/` が誤ってテストとして収集される事故が構造的に起きない。**
3. **★同じ形へ Go 側も独立に到達している**——**`M24-09b` が `internal/testutil/dbtest/` を新設した。** **2 つのサブが独立に同じ形へ至ったことは、型として妥当であることの傍証である。**
4. **禁止されていたわけではない。** 指示書 §2.1 が予見していなかっただけであり、同節冒頭は「一覧は禁止列ではない」と明示している。

**⇒ `SUPP-001` §5.3 へ 1 行足す**（別手番。**★本 CHANGE では扱わない**——`M24-01` の as-built ではなく運用の型の話であり、`M24-09b` の `internal/testutil/dbtest/` と対で書くほうが読みやすい）。**⇒ 残ゲート §6-2。**

**★`.claude/commands/add_e2e_spec.md` への反映は開発者の手番**（同ディレクトリは設計卓も製造も触らない）。
