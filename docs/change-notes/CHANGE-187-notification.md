## 1. なぜ要るか

**`M34-02` は黒窓（コンソールウィンドウ）を消した。⇒ 利用者に残る手掛かりが、トレイのアイコンと `MessageBox` だけになった。**

**★これらは設計書のどこにも書かれていない。** 書かないと、次に起動経路を触る担当が「何を壊してはいけないか」を知らないまま触る。

**★★あわせて 1 件、`CLAUDE.md` §10「セキュリティ関連の自己判断」に当たる変更が入っている**（§2 (b)）。**⇒ 明示的に受理し、以後の条件を書く。**

---

## 2. 変更内容

### (a) `SUPP-001` §5.8 —— 相対パスの解決基準（新設）

| 入力 | 解決先 |
|---|---|
| 空文字・絶対パス | そのまま |
| 相対パス | **`AppBaseDir()` からの絶対パス** |
| `AppBaseDir()` | 実行ファイルのディレクトリ（**ただし祖先に `go-build*` があるときはカレント**＝`go run` / `go test`。**配布 exe はこの分岐へ入らない**） |

**★適用先は 2 つだけ**＝`config.toml` と `logging.file`。**⇒ `database.path` は今もカレント基準である**（`followup` の `database-path-relative-cwd-basis`）。

**★解決結果を `*config.Config` へ書き戻していない**——書き戻すと `PUT /api/config` の再シリアライズで絶対パスが利用者の `config.toml` へ焼き付く。

**⇒ 同節の旧記述と食い違っていた**（旧記述は `logging.file` の相対値を「CWD 配下」と書いている）**。★解決の*基準*は移ったが、検証の*許可ルート*には CWD も残っているので両立する。**

### (b) ★★★`SUPP-001` §5.8 —— パス検証の許可ルートが 3 → 4 へ**広がった**

**`M34-02` §2-2 を受理した。**

| # | 許可ルート | 由来 |
|---|---|---|
| 1 | 既定データディレクトリ | `CHANGE-049` |
| 2 | 旧既定データディレクトリ | 移行のため |
| **3** | **`AppBaseDir()`** | **本 CHANGE（新規）** |
| 4 | 実行時カレントディレクトリ | `CHANGE-049` |

**★★「明文化」ではなく「許可範囲の拡張」として書いた。** 完了報告の初版は「明文化」と書いており、レビュー 中-9 が是正した。**その是正が正しい。**

**★受理の根拠＝実害の増分が小さい。** exe をダブルクリックすればカレントディレクトリが exe の隣になるので、**ルート 4 経由で着手前から許可されていた。⇒ 増えるのは「ショートカットの作業フォルダが exe と別の場所」の場合だけである**（製造の実測）。

**★★★以後、許可ルートを増やすときは CHANGE を通すこと**（`D-834`）。**⇒ 本検証は `CLAUDE.md` §10 の対象であり、ルートが増えるほど「アプリ管轄」の定義が薄まる。★4 つになった時点で、5 つ目を足す議論が同じ形で再来する。**

### (c) `DES-002` §3.1 —— 常駐化の as-built（6 ブロック）

| # | 内容 |
|---|---|
| (a) | **起動オプションの契約**＝引数なしが唯一の正規形。未知の引数・位置引数・`-h` はすべて `exit 1`（**★これは仕様変更である**——着手前は黙って無視していた） |
| (b) | **`config.toml` 不在**＝既定値で続行し、解決後のパス付きで WARN を 1 行残す |
| (c) | **二重起動の判別**＝`/api/health` の厳密一致（3 条件・700ms）。**★同エンドポイントの応答形が起動経路の契約になった** |
| (d) | **★起動失敗時の表示**＝エラー ＋ 設定ファイルの絶対パス（設定由来でなければ `(参考)`）、**設定由来ならその置き場を開く** |
| (e) | **トレイのメニュー 6 項目** |
| (f) | **終了の経路**＝トレイのみ |

**★(d) の根拠＝`run()` の失敗契機 15 種のうち 8 種が「`config.toml` を直せば直る」ものである。⇒ 半分以上が同じ 1 ファイルに帰着する。**

### (d) ★★`DES-002` §3.1 (f) —— 画面側の終了ボタンは作らない

**`M34-02` §2-3 を裁定した。⇒ 作らない。**

**★理由＝停止用の HTTP ルートを新設すると、LAN の他端末から認証なしでアプリを止められる口ができる。⇒ 公開ゲート `A` に逆行する**（`followup` の `lan-consent-gate-is-ui-only` と同じ層の話）。

**★`M34-overview` §1-6 は「画面内の終了ボタン、*または* アイコンの右クリックメニューから」と *または* で書いており、要求は満たされている。★トレイに常駐している以上、終了導線は常に手元にある。**

### (e) `DES-002` §3.1 —— ブラウザで開く URL は `localhost`

**`D-790` は「`127.0.0.1` にする」と書いていたが、2026-09-12 に開発者が `localhost` 維持を裁定した。⇒ 文面を as-built へ補正した。**

**★理由は origin である**——`localStorage` は origin 単位であり、綴りを変えると `web/CLAUDE.md` §1 台帳の実装済み 9 キーが丸ごと見えなくなる。**★`keyboard-bindings-v1`（17 件）と `gamepad-profiles-v1`（14 件）は既定を持たず、全件が利用者の登録である。**

**★待ち受け（`determineBindHost` / `determineBindAddr`）は無改変であり、LAN 共有は壊れていない。⇒ 違えたのは「開く URL の綴り」だけである。**

### (f) `DES-002` §8 —— 簡易パスワードの復旧導線

**トレイの「設定ファイルのフォルダを開く」。⇒ アプリからは復旧できず、`config.toml` の手編集だけが手段である。★従来はそこへ辿り着く手段が書かれていなかった。**

### (g) `SUPP-001` §5.2 —— `cmd/tacpendium/` の構成と、配布ビルドの門 2 つ

新ファイル 4 本（`args.go` / `tray.go` / `notify.go` / `instance.go`）。

**★★門は 2 つあり、守る面が違う**——`make check-windows` は**コンパイル**、`windows_gui_link_test.go` は**リンク**（PE の Subsystem を `debug/pe` で判定）。

**★後者に「レシピが変数を渡していること」の検査が要る理由＝初版は変数の値だけを見ており、レシピが `-ldflags=` を落としても緑のままであった。⇒ 門は「赤くなりうること」だけでなく「守りたい対象に届いていること」を別に確かめる必要がある。**

**★`OpenURL` は `pkg/browser` へ委譲する**（新規依存 0）。**⇒ 戻るタイミングが OS で違う**（Windows はすぐ返る／Linux・macOS は待つ）。

### (h) `DES-001` §4.4（新設）—— 配布ビルドのリンク指定

**`make build-windows` だけが `-H=windowsgui` を渡す。⇒ これが黒窓を消す実体である。**

### (i) `DES-005` §5.16 —— `/settings?qr=1`

**トレイの「設定画面をブラウザで開く」が開く URL。⇒ フロントのルート契約であり API 経路ではない**（新設 API・DTO・エラー契約はいずれも 0 件）。
