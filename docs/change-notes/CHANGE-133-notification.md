## 1. 変更の概要

**タグもキャラも「全部を平らに並べる」形で作られており、件数が増えることを想定していない。**

- **キャラは 31 中 17 が seed 済で、今後さらに増える**（ledger `SM-120`）。
- **タグは利用者によっては大量に付けうる**（同 `SM-127`）。

**⇒ 本 CHANGE は「並べる」から「絞る」へ変える。**

| # | 変更 | ledger |
|---|---|---|
| **1** | **一覧のタグフィルタをドロップダウン化し、中に検索を置く** | `SM-010` / `SM-064` / `CO-004` ／ `SM-127`-(b) |
| **2** | **一覧のフィルタ欄を折りたためるようにする** | `SM-104` / `SM-117` |
| **3** | **キャラ選択を検索で絞れる形にする**（**★§7 確認事項 1 の回答待ち**） | `SM-043` / `SM-120` / `SM-136` |
| **4** | **タグ管理画面に検索を足す** | `SM-127`-(a) |
| **5** | **★★キャラの表示名をインゲーム表示へ揃える**（マイグレ `000079`） | **ledger 外**（2026-08-26 開発者要求＝`D-560`） |

**★★形は 2 件とも memo が名指ししている**——**「これも表示列と同じように」**（＝列カスタマイズと同じドロップダウン）／ **「新規登録みたいに、閉じたり展開したり」**（＝既存の折りたたみ部品）。**⇒ 設計卓が新しい形を発明しない。**

**★CHANGE 対象外**——**キャラのグループ化**（§3-2） ／ **タグ検索のサーバ側実装**（§5 リスク 1） ／ **`TagSelector`（付与側）の作り直し** ／ **`queryKey` の統一**（`M24-08`） ／ **locale の語彙見直し**（`M24-07`）。

## 2. 変更の内容

### 2.1 `DES-005` §5.4——**タグフィルタのドロップダウン化**

**現行の §5.4 は「タグフィルタ（複数選択可）」としか書いていない。** **⇒ 形式と、閉じたときの見え方を足す。**

| 論点 | 決めたこと |
|---|---|
| **形式** | **ドロップダウン。列カスタマイズと同じ作りに揃える。★同じ画面に 2 種類のドロップダウンを作らない** |
| **中身** | タグ一覧 ＋ **検索欄**（`SM-127`-(b) をここで満たす） |
| **★★閉じた状態の表示** | **「何件選ばれているか」が分かること。** **⇒ 選択が隠れると「絞り込んだまま忘れる」事故が起きる** |
| **解除** | 閉じた状態から解除できる経路を 1 つ残す |
| **カテゴリ** | **★マイコンボのステータスタグを一覧のフィルタへ持ち込まない**（§5.5 の除外） |

### 2.2 `DES-005` §5.4——**フィルタ欄の折りたたみ**

| 論点 | 決めたこと |
|---|---|
| **形式** | 新規登録画面の折りたたみ部品と同じ作り |
| **既定** | **開いた状態。★既定で閉じると「フィルタが効いているのに見えない」状態が初回から起きる** |
| **★★閉じているときの表示** | **★★「フィルタが効いている」ことが分かること。** **⇒ これが無いと、折りたたみが「絞り込んだまま忘れる」事故を増やす** |
| **状態の保持** | **保持する**（列カスタマイズが保持しており一貫する）。**★保持先は as-built で決まる**——既存キーへの相乗りか新キーか（§5 リスク 2） |
| **対象** | **一覧 `/combos` のみ。★マイコンボへ広げない** |

### 2.3 `DES-005` §4.3——**キャラ選択（★2026-08-26 確定）**

**★検索欄付きのコンボボックス**（開発者回答）。

**★★あわせて並び順を変える**——**ロケール依存の昇順。日本語なら あ〜ん、英語なら a〜z**（開発者回答。**現在はキャラクター登録順**）。

- **i18n の現在の言語に従う。⇒ ソートは表示時に行い、データ取得時に固定しない。**
- **★★落とし穴＝`characters` に読み仮名の列が無い**（DDL＝`id` / `game_id` / `code` / `name_ja` / `name_en` / `custom_states`）。**`name_ja` に漢字が含まれると、ロケール照合が音訓を解決できず、その行だけ意図した位置に来ない。** **⇒ 件数を実測させ、1 件以上なら実装せず報告させる**（§5 リスク 6）。

**★★設計卓の暫定案「並び順を変えない」は撤回する。** **理由＝登録順は利用者が覚えられる順序ではない**（seed の投入順であり波ごとに増える）。**⇒ 動かして困る「いつもの位置」は最初から無かった。**

**★★取りこぼさないこと**（開発者が明示的に警告した論点）——**キャラを選ばせる UI は複数画面に在る。** **⇒ 全数を数えさせ、部品を共有していないものも揃えさせる**（指示書 §4.3.2 / §3.3-12）。

**★★グループ化は採れない**——**`characters` にグループ化に使える列が無い。** 作るならスキーマ変更であり本 CHANGE の外である。

**★`DES-005` §4.3.1 の解決順（5 段）は 1 文字も変えない**（`CHANGE-130` が確定させた契約）。

### 2.4a ★★キャラ表示名の是正（**設計書の変更は無い**）

**開発者申告**——**キャラの表示名がインゲーム表示と不一致である**（例＝`不知火舞` → `舞`）。

**★★「舞 1 件」ではなく「全キャラの突合と是正」として行う。理由 3 つ。**

| # | 理由 |
|---|---|
| **1** | **★★同じ不一致は `M19-04` の完了報告に既に記録されていた**〔逐語＝**「DB の `characters.name_ja` は `不知火舞` で資料表記と不一致。`character_code` で解決した」**〕。**当時は回避され、followup にも ledger にも上がらなかった。** **⇒ 他にも埋まっている可能性が高い** |
| **2** | **1 件ずつ直すとマイグレを何本も消費する** |
| **3** | **★★並び順（§2.3）の前提である。** **「不知火舞」は「し」、「舞」は「ま」であり並び位置が大きく動く。** **⇒ 別手番にすると、利用者から見て並びが 2 回変わる** |

**★★落とせない 3 点**——**(1) `characters.code` は 1 文字も変えない**〔`mai` は `mai`。**変えると `moves` / `combos` / seed の参照が全部動く**〕 **／(2) 技名を巻き込まない**〔**`mai` の `不知火流・炎舞仇桜`（SA3 / CA）は技名でありキャラ名ではない。インゲームでもこの技名である**〕 **／(3) `down` は元の表示名へ戻す `UPDATE`。子行も利用者データも消さない。**

**★★設計書の変更は無い見込みである**——**`DES-003` も `REQ-001` もキャラ名を持たない。** **⇒ 規約は `docs/seed-data/check-criteria.md` へ 1 行残させる**〔「キャラの表示名はインゲーム表示に合わせる」＋ 突合の結果〕。

## 3. ★真因の記録

### 3-1 ★★3 クラスタに共通する機序は 1 つである

**タグもキャラも「全部を平らに並べる」形で作られている。** **⇒ 件数が増えると、崩れる（タグ）か、探せなくなる（キャラ）。**

**★これは個別の UI の不具合ではなく、同じ設計の帰結である。** **⇒ 別々に直すと、次に増える別の一覧で同じことが起きる。**

### 3-2 ★グループ化を採らない理由は「好み」ではなくデータである

**`characters` テーブルに、ロール・強さ・系統といったグループ化に使える列が無い。** **⇒ 現データでは作れない。**

**★これを書いておかないと、次の担当が「なぜグループ化しなかったのか」を再検討する。**

### 3-3 ★`M24-01` が下ごしらえを済ませている

**キャラ選択がフィルタ欄からヘッダ帯へ移った理由の 1 つが、本 CHANGE である**（開発者の逐語＝**「キャラクターが増えてきたため、将来的にプルダウン以外の選択方法も検討中なので、フィルター欄よりも広く余白が余っているところへ移動しておきたい狙いもある」**）。

**⇒ 場所は既に確保されている。本 CHANGE は中身を変える。**
