**★★設計卓は当該行を触らない。** **`D-382` の理由は「設計卓と製造の両方が既存行を編集するとマージが競合する」であり、いま私が同じ行を書き直すと、まさにその競合を私の側から作ることになる。** **⇒ 本レポートと followup §AX に「本行は製造が更新した」とだけ記録し、行そのものは製造の版を採る。**

**裁定＝受理する。★製造の判断が正しい。**

### 1.3 §2-3 `DES-005` §5.16 の「進捗表示付き、中断耐性あり」が未達

**裁定＝★★「中断耐性あり」を撤回する。「進捗表示付き」は as-built へ改める。followup は立てない。**

**「中断耐性あり」を撤回する理由**——**再構築は冪等である。** 真実である `preset_aliases` から表示文字列を作り直すだけで、プリセットの中身を 1 バイトも変えない。**⇒ 途中で閉じても、もう一度押せば足りる。中断からの再開を覚えておく機構を別に持つ意味が無い。**

**「進捗表示付き」を残す理由**——**枚数の進捗**〔`N / M 件`〕**は実装されており、部分失敗も扱える**〔1 枚落ちても残りを試し、落ちた枚の名前を出す〕。**⇒ 未達ではなく、粒度が節の書きぶりより粗いだけである。** **節のほうを「何枚目のどこを処理中かのリアルタイム表示は求めない」と明示する形へ改める。**

**★followup を立てない判断の根拠**——**followup は「いつか誰かがやる」を置く場所である。** **本件は「やらないと決めた」ものであり、置くと次の担当が「未着手の宿題」と読む。**

## 6. ★★手交後の追記 1 件（2026-08-31・`D-629`）

### 6.1 何が起きていたか

**★本サブが作った回帰ではない。`M24-09a` の新設時から一度も働いていなかった。**

**根因**——**Vitest が使う picocolors は `CI` 環境変数を見て、TTY でなくても色を有効にする。** GitHub Actions は `CI=true` を必ず立てるため、`tee` したログの行頭は空白ではなくエスケープになる。着手前の抽出は `grep -E '^[[:space:]]*Test Files'` であり、**行頭を空白と仮定していたため 1 件も当たらない。** **`go test` 側が埋まっていたのは、Go のテスト出力に色が付かないからである。**

**★実害の程度**——**テストは実際に走って緑である。壊れていたのは件数の記録だけ。** **★★ただし `go test` 側の summary には「所要が数秒なら実行されていない」という注意書きが添えてあり、Vitest 側は同じ目的の数字が常に空だった。** **⇒ 「緑だが空欄」と「スイートが 1 件も走らずに緑」を区別できない状態だった。**

### 6.2 是正（2 段）と反映

`.github/workflows/pr-checks.yml` の summary step のみを変更。**合否を決める `pnpm test` step には触っていない。** **(1) 抽出前に ANSI を落とす ／ (2) 空のときは「読めなかった」と名乗らせる。** **★2 は既存の形へ揃えた**——`nightly-crossbuild.yml` の E2E summary が同じ印を持っている。**★同 E2E summary は行頭を見ない形のため無傷であり、壊れていたのは本 step だけである**（ワークフロー 2 本の抽出箇所を全数走査して確認）。

**破壊確認**——ANSI 除去だけを外して実物の色付きログへ当てると、印が出る。**⇒ 同じ欠陥が再発しても、今度は黙らない。**

**⇒ 反映＝`DES-002` §11.3 へ契約 8 を新設した**（`DES-002` **1.73.0** / 第71版）。
