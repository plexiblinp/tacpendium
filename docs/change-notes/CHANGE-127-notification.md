## 1. 変更の概要

**`M23-01` が実測して記録したとおり、`DES-005` §5.15 は列構成を定義していない**——**「表示項目」は 2 行だけであり、実装が持っている「ルート」「タグ」といった列は同節に根拠が無い。**

**⇒ 本 CHANGE は「実装に合わせて書く」のではなく、「どの列を持つべきかを決めて、実装と設計書の両方を揃える」。**

1. **`DES-005` §5.15 へ列構成を定義する**（§2.1）。**★消した列とその理由も書く。**
2. **`DES-002` §4.2 へ、削除済みセットプレイ一覧の応答にレシピ文字列が載る旨を足す**（§2.4）。
3. **`DES-005` §5.15 の警告の見せ方の未達 2 件を解消し、記述を更新する**（§2.5）。

**★CHANGE 対象外**——**行クリックの 404 ／ ゴミ箱へ入れる導線 ／ 紐付け解除の導線**（`M23-07`）／ **サーバ側の削除・完全削除の是正**（`M23-08`）／ **論理削除で `recipe_cache` を消すのをやめること**（§3-3。**採らない**）。

## 2. 変更の内容

### 2.1 ★★中心の判断——**同じ根から出た 2 つの症状に、逆の答えを出す**

**入力のうち 3 件が 1 つの原因に収束していた。**

| 症状 | 原因 |
|---|---|
| **ゴミ箱の「ルート」列が常に `(レシピ表示なし)` の固定値** | **論理削除の時点で `combos.recipe_cache` が NULL になる** |
| **名無しセットプレイが「(名称未設定)」でしか識別できない** | **論理削除の時点で `recipe_cache` を物理削除しており、レシピ文字列へのフォールバックが到達しない** |
| **セットプレイのレシピ文字列を解決する処理に本番の呼び出し元が 0 件** | **★上の 2 つを解く手段が、使われないまま存在している** |

**★★そして逆の答えを出す。**

| 対象 | 答え | なぜ |
|---|---|---|
| **コンボのルート列** | **★消す** | **コンボは `memo` と始動状況を持っており、それだけで行を識別できる。** **⇒ レシピ列は「あると親切」であって「無いと困る」ではない** |
| **セットプレイの識別** | **★出す**（レシピ文字列で） | **セットプレイは名前が空だと識別手段がゼロになる。** **★完全削除は不可逆であり、取り違えは取り返しがつかない** |

**★★判断の軸は「その情報が無いと利用者が困るか」であって「技術的に出せるか」ではない。** **どちらも技術的には出せる。**

**★これは `architecture-patterns` §11 の「機能ごとに『出すか出さないか』を決める」と同じ形であり、`M23-03` が 6 か所を 1 件ずつ違う扱いにしたのと同じ判断の型である。**

### 2.2 ★もう 1 つの軸——**「出せない列」と「出していない列」は別である**

| 列 | 状態 | 答え |
|---|---|---|
| **ルート** | **★出せない**（列を残す限り常に定数） | **消す。** **★「存在しない概念の列を残さない」**（**D-458** で残日数に適用したのと同じ論理） |
| **タグ** | **★出せる。出していないだけ**（一覧 API は応答へ常に非 nil で載せている。描画していない） | **出す。** **★新しくデータを取りに行かない** |

**★この 2 つを同じ「列が空である」として扱わないこと。**

### 2.3 `DES-005` §5.15——**列構成の定義**

**★具体の列は `M23-06` の完了報告の逐語を待って書く**（**★`M22-08` の `VAL-N05` と同じ形＝列挙は製造、確定は設計卓**）。

**★書く内容**——**コンボ側のテーブルの列**（見出しと中身）／ **セットプレイ側のテーブルの列** ／ **消した列とその理由** ／ **各列が空になりうる条件。**

**★あわせて「本節は列構成を定義していない」という記述を消す。**

### 2.4 `DES-002` §4.2——**削除済みセットプレイ一覧の応答**

**レシピ文字列が載る**（`resolve-setup-recipe` 相当の処理をサーバ側で呼ぶ）。

**★サーバ側で解決する理由 2 つ。**

1. **既にサーバ側に処理が在る。** クライアントへ `setup_steps` を丸ごと送って組み立て直すのは、既にある処理を使わない形になる。
2. **★表記はプリセット・エイリアスに依存する**（`DES-004`）。**クライアント側で組み立てると、その規則を 2 か所に持つことになる**（`E-76`）。

### 2.5 `DES-005` §5.15——**警告の見せ方の未達 2 件を解消**

**`CHANGE-124` が「未達 2 件」として書いた記述を更新する。**

| # | 未達だったもの | 本 CHANGE 後 |
|---|---|---|
| 1 | **一括復元で「どの件に警告が付いたか」を出す導線が無い** | **出す。** **★材料は `details` に揃っている**（`{id, name}` / `{id, memo}`） |
| 2 | **単件復元に完了トーストが無い** | **出す。** **★警告があるときは 1 枚に畳む** |

**★あわせて 1 点を明文化する**——**★警告の表示は VAL コードで分岐しない。** **`details` のキーで分岐する。** **理由＝警告の種類は `M23-04` の 2 件から `M23-05` で 4 件へ増えており、今後も増えうる。**

## 3. 採らなかった案

| # | 案 | なぜ採らないか |
|---|---|---|
| **1** | **ルート列も出せるようにする**（`combo_steps` から組み立てる） | **★技術的には可能だが、コンボは `memo` と始動状況で識別できる。** **「あると親切」のために解決経路を 1 本増やす価値が、セットプレイ側ほど高くない。** **★開発者の逐語もある**（「常に表示なしなら一覧から消したい」） |
| **2** | **名無しセットプレイを id や削除日時で識別させる** | **★弱い。** 「(名称未設定)」が 3 つ並んだときに、利用者は id を手がかりにできない |
| **3** | **論理削除で `recipe_cache` を消すのをやめる** | **★根本から解けるが採らない。理由 3 つ**——**(a) 削除の副作用を変える判断であり `DES-002` §4.2 の契約に触る**〔`M23-03` が as-built で固定したばかり＝**D-504**〕**／(b) コンボ側の NULL 化は `PUT` の旧行の扱いと絡んでおり、片方だけ変えると非対称が増える ／(c) `M23-06` は画面のサブであり射程が違う**〔`M23-08` でも扱っていない〕。**⇒ 読み取り側で解く** |

## 4. 確定した設計判断

| # | 判断 | 根拠 |
|---|---|---|
| **1** | **ルート列は消す** | §2.1 / §2.2。**「存在しない概念の列を残さない」＋「コンボは他の列で識別できる」** |
| **2** | **タグ列は出す** | §2.2。**データは既に届いている。配線が抜けているだけである** |
| **3** | **セットプレイはレシピ文字列で識別する** | §2.1。**★完全削除は不可逆であり、識別手段がゼロなのは許容できない** |
| **4** | **レシピ文字列はサーバ側で解決する** | §2.4。**表記規則を 2 か所に持たない**（`E-76`） |
| **5** | **★★2026-08-23 補正——`resolve-setup-recipe` は撤去しない。ただし「使う側で決着させる」は as-built と食い違う** | **D-521**。**★`ResolveSetupRecipe` は論理削除済みの行に使えない**——**内部で引く `GetRecipeCache` の SQL が `WHERE id = ? AND deleted_at IS NULL` を持ち、`M23-03` が意図的に塞いだ述語だからである。** **⇒ `M23-06` は塞ぎに触らず、レシピ解決の計算本体を呼ぶ読み取り専用の経路を新設した。** **★`ResolveSetupRecipe` 自体は依然として本番の直接呼び出し元を持たない。** **⇒ 「使う／撤去する」の二択が粗かった**——**関数は「入口」と「計算本体」に分かれており、片方だけ使えた。** **殻の扱いは followup `resolve-setup-recipe-wrapper-still-unused` へ。** 以下は起票時の記述： **★`resolve-setup-recipe` は撤去せず、使う側で決着させる**（**D-513** の差し戻しの決着） |
| **6** | **警告の表示は `details` のキーで分岐し、VAL コードをハードコードしない** | §2.5。**警告の種類は増えうる** |
| **7** | **選択状態はブラウザストレージへ保存しない** | **画面内の一時状態である**（`CLAUDE.md` §10.X。**台帳未記載のまま運用しない**） |

## 7. 開発者への確認事項

**★2 件。どちらも暫定案で進み、投入は止めない。**

1. **★★ルート列を消すこと**（§2.1）——**暫定案＝消す。**

   **★開発者の逐語がある**——**「常に表示なしなら一覧から消したい」**（2026-08-20 実機確認時）。**★ただしこれは「常に表示なし」という前提の下での発言である。**
