## 1. ★★中心は `VAL-C15` が非ブロッキング原則に 3 つ目の例外を作ったことである

**`REQ-001` `FR305` は「バリデーション結果はあくまで参考値であり、入力・登録を阻害しない（重複・例外エラー時を除く）」と定める。`DES-006` §1.1 も同じ原則を持つ。**

**`M27-02b` が入れた `VAL-C15`（本登録の必須項目）は severity ERROR ＝ 保存中止であり、この但し書きに触れる。**

### 1.1 ★受理する。理由 3 つ

| # | 理由 |
|---|---|
| **1** | **開発者の指示が「保存を止める」意図で明確だった**（2026-09-03。必須にする 4 欄と適用モードを名指しで確定した） |
| **2** | **`FR305` の趣旨は「計算値・推定値の不一致で登録を止めない」である。必須欄の欠落は参考値ではない。⇒ 趣旨と衝突しない** |
| **3** | **仮登録の入口を塞いでいない**（`is_draft=true` には掛からない＝`SUPP-001` §2.1 の「未確定でも保存できる入口」は不変） |

**★先例＝`CHANGE-139`（`M24-13`）で `VAL-C09` を仮登録へ広げたとき、同じ是正が要った。そのとき「`FR305` が起票時の影響設計書に挙がっていなかった」という計測点 `M-94` が記録されている。**

### 1.2 `VAL-C15` の契約（全行）

**コード `VAL-C15`**（★製造の仮置き番号を本 CHANGE で確定する）／ **severity ERROR**（保存中止）。

| `field` | 文言 | 判定 |
|---|---|---|
| `damage` | ダメージは本登録では必須です | `Damage != nil` |
| `knockdownAdvantage` | 有利フレームは本登録では必須です | `KnockdownAdvantage != nil` |
| `driveGaugeConsumed` | ドライブゲージ消費は本登録では必須です | `DriveGaugeConsumed != nil` |
| `saGaugeConsumed` | SAゲージ消費は本登録では必須です | `SAGaugeConsumed != nil` |

**★`field` 値はフロントのフォーム名（camelCase）である。エラー表示のタブ振り分けがこの値を見る**（`CHANGE-152` の振り分け規則と対）。

### 1.3 ★★経路ごとの効き方（`DES-002` §4.2 へ写す）

| 経路 | 走るか | 効き方 |
|---|---|---|
| `POST /api/combos` | **走る** | 本登録で 4 欄が空なら 400 |
| **`PATCH /api/combos/{id}`** | **走る** | **★★編集画面の保存はこちらである**（識別キー 7 項目が変わらない限り）。**★見るのは「更新後の姿」**。**⇒ 4 欄が空の既存本登録コンボは、必須欄に触らない `PATCH` でも咎められる** |
| `PUT /api/combos/{id}` | **走る** | **識別キー 7 項目が変わったときだけ通る経路**であり、編集画面の既定ではない |
| **本登録への昇格**（draft→final） | **走る** | 4 欄が空の仮登録は昇格できない |
| CSV 取込 | **走る** | **行単位で `status: "failed"`。バッチは止まらない** |
| **`Materialize`**（確定反撃からの生成） | **★走らない** | **抜け穴。`followup` §BI `materialize-bypasses-required-fields`** |
| seed（マイグレの直 INSERT） | 走らない | — |
| 一覧・詳細・比較・出力・ゴミ箱 | 走らない | **既存データが読めなくなることはない** |

### 1.4 ★持たせなかった分岐（読む側が誤読しないために要る）

- **仮登録には掛けない。** フロントの zod も公開スキーマ側だけを `extend` しており、仮登録スキーマは不変である。
- **値域は見ない。空かどうかだけを見る。** `DES-006` §2.5（消費ゲージは範囲 VAL 非連動）は**変えない**。必須化を口実に範囲チェックを足していない。
- **CSV の必須列 22 は不変。** 旧版が出力したファイルも従来どおりヘッダを通る（必須列を増やすと `buildHeaderIndex` が丸ごと弾く＝M16-02 の事故形）。

### 1.5 ★既存データへの影響（受理済み）

**本登録 83 件のうち 68 件は、必須欄に触らない `PATCH` でも保存できなくなる**〔ダメージ空 50 / 有利フレーム空 63 / ドライブ消費空 68 / SA 消費空 68〕。**仮登録で昇格できなくなるものは 0 件。**

**★開発者は「編集不可になるだけ」として続行を承認済み**（2026-09-03）。**⇒ 欠陥ではなく移行の負担として `followup` §BI `required-fields-migration-burden` に記録した。**

## 2. 起き攻めの「調べたか」（`DES-003` §3.4 ／ `DES-005` §5.6・§5.7）

### 2.1 ★★方式は実機確認で 1 度作り直された

**指示書 §2.3 の「2 状態を 3 状態にする」を製造は*セル単位*と読み、開発者が指していたのは*節単位*だった**（逐語「やりたいことがそもそもずれていました」）。**⇒ セル側は着手前の状態へ全面差し戻し、`combos.oki_verified`（コンボ単位の 1 フラグ）を採った。**

**★代償の差**——セルに掛けると 12 セル × 2 群の入力になり読む面 6 か所へ波及したが、節に掛けるとトグル 1 個・詳細 1 か所で済んだ。

**★計測点 `M-121`＝設計卓が「状態の数」だけを書き、「何に掛かるか」を書かなかった。**

### 2.2 スキーマと意味論

```sql
ALTER TABLE combos ADD COLUMN oki_verified INTEGER NOT NULL DEFAULT 0;
UPDATE combos SET oki_verified = 1
    WHERE EXISTS (SELECT 1 FROM combo_oki_options WHERE combo_id = combos.id);
```

| 状態 | 表現 |
|---|---|
| 未検証（まだ調べていない） | `oki_verified = 0` |
| **調べたが成立するものが無かった** | **`oki_verified = 1` かつ 行 0 件** |
| 調べた結果これらが成立する | `oki_verified = 1` かつ 行あり |

- **backfill は「行が 1 つでもあれば調べた」**（開発者確定）。
- **★行が無いコンボは `DEFAULT 0` ＝未検証。** 逆にすると、調べていないコンボが「調べたが無かった」と主張することになる。
- **★★`combo_oki_options` の sparse 意味論は不変である**——「行の存在＝そのオプションが利用可能。`available` 列は持たない（開発者確定 2026-07-05）」は**失効していない**。**本サブが取り戻したのはコンボ単位の区別だけであり、セル単位では取り戻していない。**

### 2.3 入力（`DES-005` §5.7）

- **トグルは起き攻め節の見出しの隣**（畳んでいても状態が読める）。**新規・編集の両方に出す。**
- **★チェックに触れると「調べた」が自動で就く**（付ける／外すのどちらでも）。**自動で外すことはしない。**
- **★★解除には確認ダイアログを挟む**（開発者逐語「操作ミスと思われる」）。**チェックが 0 件のときは確認を出さない。**
  **★トグルの無効化は採らない**——外すにはチェックを全部外す必要があるが、チェックに触れると自動で就くため循環する。
- **★★起き攻めの*入力*は `M24-12` のまま。** 保持の意味論・`data-testid`・「攻撃種別ごとに 3 停止 × 各停止 `1`〜`4`」の 3 つはいずれも不変。

### 2.4 表示（`DES-005` §5.6・詳細画面のみ）

| 状態 | 見出し隣の印 | 一覧が空のときに添える文 |
|---|---|---|
| 未検証 | 「未検証」 | 「起き攻めはまだ調べていません」 |
| 調べたが無かった | 「検証済み」 | 「調べましたが、成立する起き攻めはありません」 |
| 調べて成立するものがあった | 「検証済み」 | （オプションの一覧を出す） |

- **★★印は行の有無によらず常に出す。** 当初は「行が 1 つも無いとき」だけ読んでおり、**利用者が最も普通に踏む経路でフラグが不可視だった**（2026-09-05 実機確認で発覚）。**★「行があれば検証済みは自明」は推論であり、解除ガードと CSV 取込で破れる。**
- **★印と文は役割が違う**（印＝調べたか、文＝一覧が空である理由）。
- **★一覧・比較・出力は変えていない。**

### 2.5 ★状態名と操作名は別キー

トグルの操作名＝「起き攻めを調べた」／ 詳細の状態名＝「検証済み」「未検証」。**同じ語を 2 用途へ兼ねると、片方の文言を直したとき他方が黙って変わる。**

## 3. 必須・任意の印（`DES-005` §5.7 ／ `P4M-010`）

- **必須の欄にだけ印を付け、節の先頭に「この節では、印の無い欄は任意です。」の凡例を 1 回だけ出す。** 必須 4 欄に対し任意は 13 欄あり、**両方に印を付けると任意の印が 13 個並んで読めなくなる**ため。
- **★印を出す経路は `Field` 部品 1 か所だけ。** ⇒ `Field` の外に在る欄（キャラ＝画面上部 ／ レシピ＝別タブ）には印が出ない。**そのため凡例を「この節では」と限定してある**——言い切ると、その 2 つ（どちらも必須）について嘘になる。
- **★印は `is_draft` で出し分ける。** 仮登録では必須が掛からないため出さない（常時「必須」と出すと、保存できるのに必須と見える）。
- **★正典は `web/src/constants/field-requirement.ts` の `REQUIRED_PUBLISHED_COMBO_FIELDS`。サーバ側の `requiredPublishedFields` と対であり、片側だけ足すと画面は通るのに保存で落ちる（またはその逆）。**
- **★印は視覚のみで `required` / `aria-required` は付いていない**（`Field` がラベルと入力欄を結んでいない既存構造のため）。**⇒ `followup` §BI `required-fields-visual-only`。**

### 3.1 「コンボ開始時」の語（`P4M-024`）

**逐語は「始動時の状態」だが、画面の既存語は「コンボ開始時」である**（`DES-005` の始動ゲージ欄の正典ラベル）。**⇒ 新語を作らず既存語へ揃えた。用語統一は `M29` の持ち物であり、ここで先取りしない。**
