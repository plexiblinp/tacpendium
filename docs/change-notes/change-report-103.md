## 2. 起票内容から動いた点

### 2.1 条件付きだった (d) は条件を満たした

**`CHANGE-103` §2-d は `alias_text_en` の対象範囲を「増える場合のみ改訂する」としていた。** **増えた**——**76 行 → 102 行**（層 C-3 の 13 code × 2 プリセット ＝ 26）。

**★しかし as-built の値をそのまま書き写さなかった。** **製造の提案を採り、実測件数を設計書から外して原則だけを残した。**

**理由**——**件数は投入のたびに失効し、設計書の側だけが古くなる。** **実際に旧記述「移動系 2 code のみ・76 行」は本サブの投入で失効した。** **★さらに適用済みマイグレのヘッダにも同じ値が焼き込まれているが、そちらは改変できないため失効したまま残る**（`M20-03` §2.2）。

**⇒ 一般規約を 1 本立てた**——**設計書に実測値を書くときは「正本はどこか」を必ず併記する。併記できないなら書かない。**

## 3. `D-374` の裁定 3 件

| # | 論点 | 裁定 | 決め手 |
|---|------|------|--------|
| 1 | **`SQLFormat` の意味拡張**（設計伝達レポート §2-1） | **受理（案 A）。型を分けない** | **★「意味を拡張した」という理解を採らない**——**同型は最初から生成器の世代の proxy であった。** **`M20-03` の時点では世代差が「`character_id` を含むか」としてしか現れなかったため、そう名づけられただけである。** **⇒ 露呈したのは、名前が実体より狭かったことである** |
| 2 | **明文化の置き場** | **`SUPP-001` §5.5.8**（`DES-004` §5.4 ではない） | **`DES-004` は「何を生成するか」の規則を持ち、`SUPP-001` は「どう作るか」を持つ。** **世代ゲートは後者である** |
| 3 | **`DES-004` §5.7 へ「列そのものを出しているかのテスト」を足すか** | **足す** | **「値は生成結果に載るのに DB へ入らない」は `E-84` の型そのものである**——**行数も表示も変わらないため気づけない。** **§5.7 は投入経路の規約であり、ここに属する** |

**★裁定 1 から一般則を 1 つ立てた**（`SUPP-001` §5.5.8）——**生成規則を足すサブは必ず世代ゲートを通す** ／ **ゲートを新しいフラグで実現しない**（付け忘れた実行が適用済みファイルを壊す） ／ **型を 2 つに割らない**（呼び出し側が 2 つを渡すことになり、片方だけ更新する事故が生まれる）。

> **★`D-360` と同じ構造である**——**あちらは「diff 0 は不変条件ではなく proxy である」、こちらは「`SQLFormat` は形式ではなく世代の proxy である」。** **どちらも proxy を実体と取り違えると壊れる。**
